合同履约与付款发货的资金一致性设计

Payment & Delivery - 付款方式、短溢货款、开票保证金与一致性保障

项目背景：合同签约之后，"付款"和"发货/过户"是资金风险最集中的环节。一笔合同可能同时涉及预付款、尾款、分期、短溢货款、开票保证金冻结/解冻；而付款动作还要和支付通道、银行、仓单系统、物流系统、税务系统多方交互，任何一环超时或重复回调，都可能造成资金与账目不一致。这个模块的目标只有一个：钱和货的状态，永远对得上。

我的角色：技术经理 / Java 侧负责人。我主导了这条链路的资金一致性方案：用 Saga + 状态机 + 事件溯源编排跨系统长流程，用 Kafka + outbox 本地消息表 + 消费幂等保证消息不丢不重，再以日终对账兜底。方案让"3 年零资金差错"从口号变成可复制的工程约束。

付款与资金构成

1. 付款方式：预付款 / 尾款 / 分期

付款计划与履约节点绑定：签约后付预付款（比例按租户配置），发货/过户前后付尾款，大额项目按节点分期。每个付款节点都是一次独立的幂等支付，付款成功后通过状态机推进合同。

  • 预付款：合同金额 × 预付比例（配置化）；
  • 尾款：按实际交货数量结算的剩余货款；
  • 分期：把付款拆成多个履约节点，逐节点触发；
  • 手续费：平台服务费，与货款同笔或独立扣取，口径统一进资金流水。

2. 短溢货款：多发少发的差额

大宗商品按批次称重/计量，实际发货量常与合同量有偏差，产生"短溢货款"。差异金额 = （实际数量 − 合同数量）× 单价，正数向买方收取、负数向卖方退还。这是最容易产生对账争议的地方，必须独立建流水类型、单独结算、单独可查。

3. 开票保证金：冻结 / 解冻

为保障开票履约，开票前按配置比例冻结开票保证金，发票开具完成后解冻。冻结与解冻各生成一条不可逆资金流水（解冻为负向），保证任意时点的保证金余额可由流水推导。

核心方案：资金一致性设计

履约长流程（Saga 编排）

Saga 开始

扣款 / 冻结

过户 / 发货

开票 / 解冻

Saga 完成

任一步失败触发补偿动作（反向解冻/退款/回滚过户）；长流程不依赖一个大事务，跨月场景也能收敛。

1. Saga + 状态机 + 事件溯源

每个履约节点是一个 Saga 步骤，步骤的成功/失败都写入事件表（事件溯源），状态机校验迁移合法性。这样任意时刻都能"重放"出合同与资金走到哪一步，出问题可定位到具体事件。 

/** Saga 编排：每步幂等，失败执行补偿，事件落库可追溯 */
@Service
public class FulfillmentSaga {

    @Autowired private ContractStateMachine stateMachine;
    @Autowired private EventStore eventStore;
    @Autowired private CompensationHandler compensation;

    public void execute(Contract c, PaymentPlan plan) {
        try {
            for (SagaStep step : plan.steps()) {
                // 1) 幂等执行当前步骤
                step.run(c);
                // 2) 事件溯源：记录"发生了什么"
                eventStore.append(step.toEvent(c));
                // 3) 状态机校验并推进
                stateMachine.transition(c, step.targetStatus());
            }
        } catch (Exception e) {
            // 4) 逆序补偿，保证钱货回到一致状态
            compensation.compensate(plan.completedSteps(), c);
            throw new SagaRollbackException("履约失败已补偿", e);
        }
    }
}

2. Kafka + outbox 本地消息表 + 消费幂等

"付款成功"与"发消息通知下游"必须同时成功或同时失败。我用 outbox 本地消息表：业务操作与消息写入同一本地事务；再由定时任务/CDC 把 outbox 投递到 Kafka。消费侧用幂等表去重，避免重复扣款或重复过户。 

@Service
public class PaymentService {

    @Autowired private PaymentRepository paymentRepository;
    @Autowired private OutboxRepository outboxRepository;

    /** 业务写入 + outbox 写入在同一本地事务，保证不丢消息 */
    @Transactional
    public void paySuccess(Payment p) {
        if (p.getStatus() == PaymentStatus.SUCCESS) return; // 幂等：已处理直接返回
        p.setStatus(PaymentStatus.SUCCESS);
        paymentRepository.save(p);

        outboxRepository.save(OutboxMessage.of(
            "payment.success",
            p.getPaymentId(),           // 幂等键
            new PaymentSuccessEvent(p)));
    }
}

/** 消费侧：以消息幂等键去重，重复投递不会重复处理 */
@Component
public class PaymentSuccessConsumer {

    @Autowired private IdempotentTable idempotentTable;

    @KafkaListener(topics = "payment.success")
    public void onMessage(String msgId, PaymentSuccessEvent e) {
        if (!idempotentTable.tryLock(msgId)) {
            return; // 已消费过，直接忽略
        }
        contractService.onPaid(e.getContractId(), e.getAmount());
        idempotentTable.markDone(msgId);
    }
}

3. 日终对账兜底

再严密的实时链路也需要兜底。每天日终用 XXL-Job 定时任务，把本地资金流水与银行/支付通道对账单（经外联网关拉取）做全量比对，以资金流水为唯一事实，差异项自动生成待办并告警。这一步把对账从 9 人天的人工核对压缩到 2 小时的自动化任务。 

/** XXL-Job 日终对账：本地流水 vs 银行/通道账单 */
@XxlJob("dailyReconciliationJob")
public void dailyReconcile() {
    LocalDate bizDate = LocalDate.now().minusDays(1);

    List<CapitalFlow> localFlows = capitalFlowRepository.findByBizDate(bizDate);
    ChannelStatement channelStmt = externalGateway.fetchStatement(bizDate); // 外联网关拉账单

    Map<String, BigDecimal> localMap = localFlows.stream()
        .collect(Collectors.groupingBy(CapitalFlow::getOutBizNo,
                 Collectors.reducing(BigDecimal.ZERO, CapitalFlow::getAmount, BigDecimal::add)));

    List<DiffItem> diffs = channelStmt.diff(localMap); // 逐单比对
    if (!diffs.isEmpty()) {
        alertService.raise("资金对账差异", diffs);   // 生成待办并告警
    }
    reconReport.save(bizDate, localMap.size(), diffs);  // 留档
}

踩坑与解决

坑 1 · 支付回调重复：银行/通道回调可能重复到达。早期无幂等导致同一笔款被记账两次。
解：以支付业务号作为幂等键，处理前先查状态/幂等表，重复回调直接返回成功。

坑 2 · 消息发送与业务不一致：付款成功但通知下游的消息没发出去（或发了两次），造成合同状态与资金不一致。
解：outbox 本地消息表：业务与消息同事务写入，后台可靠投递 + 消费幂等，做到"最终一致、不丢不重"。

坑 3 · 短溢货款对不平：实际交货与合同量差异导致预付款、货款、尾款对不平，人工核对耗时且易错。
解：短溢单独建流水类型、单独结算并纳入日终对账口径，差异自动暴露。
