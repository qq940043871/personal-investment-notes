客服管理

CS Management — 客服不建账号体系，只做「身份接入 + 能力配置 + 记录留存」三件事

LDAP / OAuth / SSO 能力 + 技能 + 状态 会话记录 30 天 服务统计

场景背景：客服是最难「系统化」的一类使用者：他们已经在企业里有一套账号（OA / 域账号），再让他们记一套客服系统密码，结果一定是密码贴在显示器上；他们的能力是动态的（临时下线吃饭、技能新加了一项、今天最多接 5 个），这些变化必须实时影响派单；他们的服务过程要被复盘（时长、满意度、处理量），否则没法考核也没法改进。

我的角色：客服域模型的设计与实现。三个判断：① 不新建账号体系，用 Provider 模式适配企业现有认证（LDAP / OAuth / SSO），新增一种认证只加一个实现类；② 能力不用一个数字表示，而是「在线 + 有空位 + 技能匹配」三条件，交给排队侧判断；③ 记录不放在线库，会话结束后落 Redis 记录并设 30 天 TTL，在线态与历史态彻底分开。

四个模块

1. 第三方认证接入

客服直接用工号 / 域账号 / 企业 SSO 登录，认证成功即拿会话 token（12 小时），不额外维护密码与找回流程。

我的关注点：用 Provider 模式把认证方式做成可插拔的 Map：ldap / oauth / sso 各一个实现。这样「客户换成了 ADFS」这种需求，改的是配置和一个类，不是整个登录流程——这是多客户交付里最省事的一层抽象。

2. 服务能力与在线状态

每人配最大接待数（默认 5）、技能标签、在线 / 离线状态；剩余能力 = 上限 − 当前会话数，会话增减时同步加减。

我的关注点：能力判断必须是「读时判定」而不是「写时缓存」——current_sessions < capacity 每次现算。把「还有没有空位」缓存成一个布尔值，必然在并发派单时出现两个用户同时抢最后一个位置，最后客服被塞爆。

3. 下线自动转接

客服点「离线」时，系统先把名下进行中的会话转给其他可用客服，再把人置为离线。

我的关注点：这个动作不能只是「改个状态」——先转接、后离线的顺序决定了有没有用户被挂在空气里。反过来做，会话就永远停在「已分配但没有人在看」的状态，用户等到自己放弃。

4. 会话记录与统计

每个会话记一条记录（起止时间、满意度、归属客服），保留 30 天；按人按天可算出会话量、平均时长、平均满意度。

我的关注点：记录用「客服 → 会话 ID 列表」的 List + 单条 Hash 两层结构，查某人某天的记录只扫这个人的列表，不做全表扫描。统计口径必须在写入时就固定（时长 = endTime − startTime，只算已结束的），否则事后统计会出现「同一个数字三种算法」。

实现：能力判定与转接

能力判定的本质是三条件交集，这段代码量很小但被调用得最频繁（每次派单、每次手动接入都会走一遍），所以它必须无副作用、可并发。 

@Service
public class CsCapacityService {

    /** 剩余能力：读时现算，不缓存布尔值（否则并发派单会抢爆最后一个位） */
    public boolean hasRoom(String csId) {
        Map<Object, Object> info = redisTemplate.opsForHash().entries("cs_info:" + csId);
        Integer cap = (Integer) info.get("capacity");
        Integer cur = (Integer) info.get("current_sessions");
        return cap != null && cur != null && cur < cap;
    }

    /** 可派单客服 = 在线 ∩ 有空位 ∩ 技能匹配，按当前会话数升序（最不忙的优先） */
    public List<CsUser> available(String skill) {
        List<CsUser> list = new ArrayList<>();
        for (String key : redisTemplate.keys("cs_info:*")) {
            CsUser u = toUser(redisTemplate.opsForHash().entries(key));
            if (u.getStatus() == CsStatus.ONLINE
                && hasRoom(u.getCsId())
                && u.getSkills().contains(skill)) {
                list.add(u);
            }
        }
        list.sort(Comparator.comparingInt(CsUser::getCurrentSessions));
        return list;
    }

    /** 下线：先转接名下会话，再置离线——顺序反了就会有人被挂在空气里 */
    public void offline(String csId) {
        transferSessions(csId);
        redisTemplate.opsForHash().put("cs_info:" + csId, "status", CsStatus.OFFLINE.name());
    }
}

闭环：从登录到可被派单

企业认证登录

配能力 / 技能

置为在线

进入可派单池

会话结束留记录

这条链上有两个「顺序敏感点」，也是这套系统真正区别于「能跑通」的地方：登录后必须先配能力再置在线（否则会以 0 能力上线、永远接不到单，看起来人是在线的）；下线必须先转接再置离线（否则有人被挂在空气里）。

  • 身份：Provider 模式接企业认证，不另建账号；
  • 能力：读时判定，三条件交集，会话数升序派单；
  • 状态：上线 / 下线都带副作用，不是一个孤立字段；
  • 复盘：会话记录 30 天留存，口径写入时固定。

行业背景（一句话）

客服管理的行业共识是「能用组织架构解决的，就不要在业务系统里再造一套」。账号、组织、角色这些企业已有的事实，重复维护一次就多一处不一致——这也是后来把客服系统接进统一认证的直接原因。

关键点与结果

认证可插拔

LDAP / OAuth / SSO 三种 Provider，换认证只加一个类

能力读时判定

不缓存布尔值，并发派单不会抢爆最后一位

下线不甩客

先转接后离线，没有用户被挂在空气里

记录可复盘

会话量 / 时长 / 满意度，30 天留存

技能驱动派单

技能标签直接参与队列与分配

在线态自过期

Redis + TTL，不写清理任务
