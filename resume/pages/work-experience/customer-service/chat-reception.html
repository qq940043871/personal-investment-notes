接待客户

Chat Reception — 微信入口、WebSocket 实时收发、敏感词前置、断线可续，一条消息都不能凭空消失

微信 OAuth2.0 WebSocket 双向 Trie 敏感词 3 秒自动重连

场景背景：「聊天」两个字容易让人低估这件事：发出去的消息不能丢、顺序不能乱、内容要合规、客服换人要能接上。用户侧是在微信里点开一个 H5，网络环境是地铁、电梯、4G 切 WiFi；客服侧同时挂着多个会话。任何一次「消息没到」都会立刻变成投诉，所以这个模块的设计重心不在界面，而在消息的可达性与可恢复性。

我的角色：接待链路的设计与实现。核心决策两条：① 消息先落 Redis 再转发——顺序反过来，一旦对端连接假死，消息就永久丢了；② 在线态以 Redis 为准，不以 Channel 对象为准——Netty 的 Channel 在 TCP 半开时依然 isActive() 为真，只信连接对象会产生「显示在线却收不到」的幽灵用户。

四个模块

1. 微信登录（用户身份入口）

用户在微信里点链接即可进入，一次授权换 openId 与昵称头像，无需注册、不用记密码。登录态存 7 天，会话 token 存 24 小时。

我的关注点：微信侧只作为身份来源，业务系统内部仍用自己的 sessionToken——这样以后接支付宝、接 App 原生登录都不用动业务逻辑。另外 access_token 与用户资料都是缓存而非每次实时拉取，避免把微信接口变成链路上的单点。

2. 实时通信（WebSocket 长连接）

建立连接后双向推送，用户与客服之间毫秒级送达；连接断开自动重连，重连后能拉到历史消息，不出现「聊天记录空了一段」。

我的关注点：重连不是「重新 new 一个 WebSocket」那么简单——重连后要补拉断线期间的消息。所以消息一定带 sessionId 落在 Redis List 里，前端重连后按最后一条消息的时间/序号拉增量。没有这一步，弱网下的聊天会持续丢片段，而且用户说不清丢了什么。

3. 敏感词过滤（合规前置）

消息进入系统后的第一道处理就是敏感词替换，内置词库走 Trie 树匹配，需要时再叠加第三方内容安全检测。

我的关注点：过滤必须发生在「落地之前」而不是「展示之前」。一旦先存后滤，Redis 里就留下了未过滤原文，等于把风险存进了日志。Trie 树的选择也是为了性能——一次扫描 O(n)，不需要对每个词跑一遍 contains。

4. 消息转发、文件与会话转接

客服之间可以转接会话，用户不用重复描述问题；支持图片与文件；新消息有提醒，避免会话在后台静默堆着没人管。

我的关注点：转接本质上是改 session 的归属人，而不是新建会话——新建就会把上下文割裂，用户要重讲一遍。会话 ID 不变、客服 ID 变，历史消息自然延续，统计时也能算清「这个会话经过几个人」。

实现：连接、重连与消息补拉

客户端只做三件事：建连、收消息、断了就重连。看起来平平无奇，但「重连」必须是幂等的——不能每次重连都往消息数组里重放一遍历史，否则用户会看到重复消息。 

const connect = () => {
  const ws = new WebSocket(`wss://${host}/ws?token=${sessionToken}`);

  ws.onopen = () => {
    // 重连成功后按最后一条消息的游标补拉，而不是全量重载
    ws.send(JSON.stringify({ type: 'RESUME', sessionId, afterSeq: lastSeq.value }));
  };

  ws.onmessage = (e) => {
    const msg = JSON.parse(e.data);
    if (msg.seq <= lastSeq.value) return;      // 幂等：丢弃已收到的
    lastSeq.value = msg.seq;
    messages.value.push(msg);
  };

  ws.onclose = () => {
    // 3 秒后重连；指数退避可在此处加权，避免服务重启时全员同时打进来
    setTimeout(connect, 3000);
  };
};

onMounted(connect);
onUnmounted(() => ws?.close());

这条路径上唯一不可调换的是「过滤 → 落库 → 转发」的顺序。任何一步提前或滞后，都会分别导致：原文入库（合规风险）、消息丢失（体验事故）、或者把未过滤内容推给对方（双份风险）。

  • 身份：微信只提供身份，业务侧发自己的 sessionToken；
  • 传输：长连接 + 序号，断线重连按游标补拉；
  • 合规：过滤在读入时完成，Trie 树一次扫描；
  • 连续性：转接只换归属人，会话与历史不变。

行业背景（一句话）

在线客服的用户预期被微信和淘宝养了出来：秒回、能发图、换人不重讲、聊天记录找得到。任何一条做不到，用户不会认为「系统有 bug」，而会认为「这家公司不靠谱」——这就是客服链路必须按金融级可达性设计的原因。

关键点与结果

入口零门槛

微信 OAuth2.0，授权即用、无需注册

实时双向

Netty WebSocket，长连接直推

断线不丢片段

3 秒重连 + 按序号补拉，幂等去重

合规在入口

Trie 过滤先于落库，原文不入库

换人不重讲

转接只改归属人，会话与历史延续

消息先存后发

落地优先，发送失败也能补
