大模型管理

Model Management — 多模型接入、按数据敏感度分通道、模型中立不被厂商锁定

底座 · 平台建设方 数据不出域 模型可换，代码不动

口径声明：本页描述的是平台整体方案。个人参与 = 前期「数据敏感度决定通道」的判断与底座选型；模型接入的日常运维由团队推进。

一、为什么必须有「模型管理」这一层

如果业务代码里到处是 openai.chat.completions.create，那么换一次模型就等于一次全量改造。而模型这个市场，一年换三轮是常态。所以这一层要解决两件事：

数据敏感度不同，通道必须不同

通用咨询（商品怎么下单、流程怎么走）走第三方模型，见效快、成本低；涉密数据（合同、客户资料、内部制度）必须走内网私有化。一刀切只有两种结局：要么全内网、成本与效果都拖垮，要么全公有云、合规先出事。

不被单一厂商锁定

模型价格、能力、可用性都会变。要求是：换模型不改业务代码、不影响业务连续性。做不到这一点，所谓「技术选型」其实是一次不可逆的押注。

平台内的一句话判断（前期选型的核心结论）：模型选型风险不由架构承担——用 OpenAI-compatible 端点 + 中台网关抽象，把「用哪个模型」变成一个配置项而不是一个架构决策。

二、三通道：按敏感度分流

通道 技术形态 适用 代价
公有通道 第三方模型 API（OpenAI-compatible） 通用咨询、公开政策解读、话术改写——不涉密、要求效果好、要快 按量计费；数据出域需评估
私有通道 内网 vLLM 部署开源模型 涉密文档解析后的问答、合同条款、客户资料类场景 要 GPU 与运维；小模型效果弱于旗舰
轻量通道 Ollama（开发 / 边缘 / 单机验证） 本地调试、演示环境、轻量任务（分类、抽取、改写） 并发与吞吐有限，不进生产主链路

分流点放在哪？不在业务代码里 if-else，而是在中台网关按数据的敏感等级路由。业务侧只说「我需要一个能回答合同问题的模型」，不关心它跑在哪。

三、模型中立怎么落成机制

① 统一协议
OpenAI-compatible

所有模型套同一个请求/响应契约，国产、开源、私有都走这个口。

② 网关抽象
中台统一出口

鉴权、限流、熔断、重试、日志、计量都在这一层，业务不重复实现。

③ 配置而非代码
模型 = 配置项

切换模型改配置 + 回归测试，不改业务代码。

④ 退出路径
编排引擎也可换

AI 能力一律经网关暴露，保留「换掉 Dify」的可能。

四、监控与计量：让「值不值」有数据

运行态监控

  • 可用性 / 错误率 / 超时率（分模型、分通道）
  • 首字延迟与总耗时（P50 / P95）
  • 私有通道：GPU 显存与并发队列长度
  • 降级触发次数（模型不可用时的兜底是否生效）

用量与成本计量

  • token 按部门 / 租户 / 应用三维归集
  • 直击库命中（0 生成 token）单独计数——这是省钱的证据
  • 配额与告警：超阈值先告警再限流，按部门分摊
  • trace_id 串联业务操作日志与 AI 调用日志，可归因到人、到单据

五、验收口径

换模型成本 = 改配置 + 回归

目标口径：切换到新模型不产生业务代码改动；实测人日待 POC 记录。

涉密场景 0 出域

涉密等级数据的调用 100% 落在内网通道，可审计抽查。

单会话 token 消耗

度量口径已定（按会话/部门归集），实测值待采集，不填估算数。

边界：这一层不做算法创新，也不承诺「换个模型效果就好了」。它保证的是可替换性与可控的账——效果提升要靠检索质量与场景设计。
