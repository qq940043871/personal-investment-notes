知识库与智能检索

Knowledge Base & Retrieval — 把散在个人脑子里的口径，变成平台可查的唯一版本

价值出口 · 内外通用 采集 → 解析 → 分块 → 索引 → 发布 元数据过滤防越权

口径声明：本页描述的是平台整体方案。个人实际参与集中在文档解析与入库链路（MinerU 改造 + 批量调度 + 元数据对齐）；知识运营流程由业务团队承接。

一、知识库到底在解决什么

它不是「上传文档的地方」，而是把散在个人经验里的口径收敛成唯一版本的过程。三件具体的事：

口径不一

同一个「能不能退」，销售、客服、财务三套说法。知识库给出唯一版本，并标明依据来源。

找不到 / 找得慢

制度散在 OA、群文件、个人电脑。自然语言一问即得，把「会查库」的门槛降到「会说话」。

说了但没出处

答案必须能落到「哪份文件的哪一段」，否则无法核实，也不敢对外讲。

知识来源三路：业务文档（商品、规格、流程、制度）· 政策文件（带文号、时效、效力位阶）· 已验证问答（召回测试里答对的样本，沉淀成独立 Q&A 库，可被多个应用共享、可进版本管理）。

二、五步管道：从一堆文件到可检索知识

① 采集

文件 / 网页 / 云盘 / 业务系统

② 解析

统一为 Markdown 中间态

③ 分块

通用 / 父子 / QA 三选一

④ 索引

高质量 vs 经济型（不可逆）

⑤ 发布

权限 · 版本 · 召回测试

箭头方向不是画着好看：②解析错了，③④⑤再怎么调都是错的。这也是为什么解析这一环要单独做工程化（见「RAG 与解析」页）。

三、三个不能拍脑袋的设计点

设计点 为什么不能随便选 我们的做法
分块策略 切太碎语义断裂、切太大召回不准；政策条款与商品规格的天然边界完全不同。 政策类走父子分块（小块检索、大块喂给模型）；FAQ 类走 QA 结构；普通文档走通用分块。
索引方式 「经济型」用倒排关键词、几乎零成本但没有语义泛化；换索引方式需要重建全库，不可逆。 主库一次性选高质量（embedding）；成本敏感的临时库才用经济型。这个决定写在选型文档里，不允许中途改口。
元数据过滤 权限与版本都挂在这上面；一旦只靠 Prompt「请不要说别人的数据」，越权只是时间问题。 入库即写 部门 / 密级 / 有效期 / 版本 四类元数据，检索节点按当前身份做前置过滤。

四、增量更新与版本：改一个字不该重建全库

增量更新三原则

  • 文档 / 分段级 CRUD，改段落自动重索引
  • 入库带幂等键（来源 + 版本），重复推送不产生重复分段
  • 旧版本不物理删除，置为失效并保留替代链

知识治理是业务流程

  • 入库审批：谁有权把内容变成「平台口径」
  • 同步周期：政策类按发布节奏，商品类按变更频率
  • 过期下架：到期自动失效，不靠人记得

五、验收口径

召回率 / 准确率

用 50–100 条真实问题做召回测试，取基线；实测值待 POC 采集。

解析成功率

按文档类型分桶统计，失败必须有告警与人工兜底，不能静默丢。

可溯源率

答案能给出「文件 + 段落位置」的比例，目标口径 100%（无依据不开口）。

一句话：知识库的质量不取决于向量库选型，取决于源头文档干不干净 + 分块是否尊重原文结构 + 元数据是否老实填写。这三件事没有一件是「买个组件」能解决的。
