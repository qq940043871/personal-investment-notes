PRODUCT · 产品是什么

行业的卡点不在「找货」，在「签了合同之后」

死结 01 · 信任

跟陌生人做生意不敢

大额交易、决策链长，对「信任」的敏感度远高于对「价格」的敏感度。
解法：平台担保 + 资金监管，钱不过对方手；履约率与成交记录公开。

死结 02 · 效率

一笔交易跑断腿

比价靠打电话、合同来回寄、催货靠喊、对账靠翻凭证。
解法：询价 → 合同 → 支付 → 仓储 → 物流 → 质检 → 结算 → 开票全链路线上化。

死结 03 · 资金

有好机会但缺钱

货压仓库占资金、账期 30-90 天拖垮现金流。
解法：预付款融资 / 仓单质押 / 应收账款融资——让钱不够的买方也能成交，直接提高成交率。

一句话概括：把大宗贸易里「签了合同之后的事」全部线上化、可信化、金融化——把生意从「靠人脉、靠电话、靠运气」变成「靠数据、靠系统、靠信用」。

【45 秒 · 业务判断】这一页替代传统开场里的「我参与了一个电商平台」。

【口播】「我先讲对这个行业的判断。大宗商品 B2B 的卡点不在『找货』——信息撮合早就被做烂了；卡点在『签了合同之后』：货权怎么确认、钱怎么安全地走、交收扯皮怎么办。谁能把签了合同之后的事可信地线上化，谁就有定价权。

三个死结对应三件事：信任、效率、资金。所以我们做的不是撮合信息，而是把交易、支付结算、合同履约、仓单、物流、税务打通成闭环，在这个闭环上叠加供应链金融——让钱不够的买方也能成交，直接提高成交率。在这个业务里，技术不是成本，是增长引擎。」

【讲法】先说三个死结，再讲闭环——功能清单（在线交易、支付结算、合同履约、仓单、物流、开票税务……）留给产品说明书。

【金融服务价值必须背死这一句】「让钱不够的买方也能成交，直接提高成交率」——不是「增加交易效率」。开口说几条就数几条。

【口播顺序：从上到下还是从下到上？从下到上更有逻辑——先讲约束从哪来】
「我们系统最大的技术挑战是：既要保证交易撮合的极致性能，又要支撑复杂多变的业务规则。这两个要求是矛盾的，我们用异构分工来解。

第一层，撮合引擎用 C 语言：单线程、纯内存、异步落库。为什么不用 Java？撮合是 CPU 密集型，盘口匹配、价格优先时间优先的排序，Java 的 GC 停顿在撮合场景不可接受——每一次停顿都可能造成不公平。

第二层，DS 数据中心，我把它定位为防腐层。它用 Java 开发，下层用 TCP 自定义二进制报文跟 C 引擎通信，上层通过 Hessian 向 Java 微服务暴露标准接口，中间管连接、心跳、协议版本兼容。C 引擎对我们 Java 团队是个黑盒，DS 做的事情就是把异构通信的复杂性封装起来，让上层服务看到的都是干净的 Java 接口调用。

第三层，业务中台，12+ 微服务。这里要分清两个自研网关：midservice 是业务网关，管请求怎么进；midmon 是监控网关，管系统怎么样。

第四层，接入层和外部生态：三端接入，对接 9+ 外部系统，统一适配层。」

【管理岗必说的一句】「我不写 C 代码，但我通过 DS 这层桥接管住了异构通信的全链路。你能管住的边界，就是你能负责的边界。」

TRADE-OFF · 每层都是取舍的结果

C 换确定性 · Java 换迭代速度 · DS 换边界可控

如果不这么拆

  • 撮合用 Java：GC 停顿带来交易不公平，资金链路心脏不可接受
  • 每个服务直连 C 引擎：二进制协议解析散落各处，出错率高、没法维护
  • 业务逻辑塞进 C 层：这一层不好改，等于把迭代速度锁死
→

所以这么拆

  • 撮合层只干撮合：C 换纳秒级确定性，代价是这层不好改
  • DS 收敛复杂度：上层调 C 就像调本地方法；C 团队与 Java 团队独立演进、互不阻塞
  • 中台承载变化：Java 换迭代速度，业务规则全部落在这一层

每层先答三问（追问时的通用框架）：为什么存在 / 不这么做会怎样 / 取舍了什么。

例：Hessian 而不是 JSON——高频二进制交互，序列化体积和性能都要；Canal 而不是业务双写——用 binlog 解耦读写，不把同步逻辑压进主链路。

【30-45 秒】这一页证明「设计者」身份：把两个网关的区别讲清楚，而不是只报架构名词。

【口播】「这套架构的每层都是取舍的结果：C 换确定性、Java 换迭代速度、DS 换边界可控。

举个例子：为什么不直接让每个 Java 服务去对接 C 引擎？因为协议解析会散落得到处都是，出错率高、没法维护；收敛在 DS 一层，上层调 C 就像调本地方法，而且 C 团队和 Java 团队可以各自独立演进。

再比如中间件选型：RPC 用 Hessian 不用 JSON，因为我们是高频二进制交互，序列化体积和性能都要；缓存同步用 Canal 读 binlog，而不是业务代码双写——同步逻辑不该压进主链路。」

【万能框架】被追问任何一层，先答三问：这一层为什么存在 / 不这么做会怎样 / 取舍了什么。答得出取舍，你就是设计者。

ENGINEERING · 底线信任与数据一致

底线信任 → 等保信创 · 数据安全  ·  数据可信 → 缓存一致

07 · 等保 + 信创

安全合规与国产化双达标

等保分区分域、最小权限 + 双因子、全链路审计；信创适配层切换 MySQL↔GaussDB / Tomcat↔TongWeb / CentOS↔openEuler，L2/L3 分级报价。测评不再「测评前突击」，「国产化不降级」成为投标差异化卖点。

08 · 数据安全脱敏

一处声明，处处生效

敏感字段元数据分级打标 → 统一脱敏引擎（注解声明式）+ 四类场景分治（展示 / 接口按角色 / 日志切面 / 测试出口），明文查看全程留痕，数据库动态脱敏视图兜底。安全从「合规负担」变成可向客户展示的信任能力。

11 · 缓存服务改革

CDC 总线 + 规则驱动自动失效

谁改库谁删缓存，绕过代码就用日志监听删。代码路径先更 DB 再 DEL；手动刷数走 Canal(binlog) / openGauss 逻辑解码(WAL)；规则集中在配置表，跨语言生效；批量刷数合并 + 防抖 + 前缀失效，所有 key 设过期兜底。缓存一致性从「靠自觉」升级为「靠架构保证」。

洞察：合规与数据一致是平台「敢碰钱、能进国企」的底线能力——不是成本项，是获得入场券的信任能力。

【2 组 · 每组 45 秒 · 缓存这页是大杀器，值得深讲】

【口播示范 · 缓存】「缓存这项是我们的真痛点。写库方太多，C 服务、Java 中台各写各的删缓存逻辑；更麻烦的是 DBA 手动刷数、脚本批量修复根本不经过业务代码，数据库是新的但页面就出脏数据。我们的方案主线一句话：谁改数据库谁就负责删缓存；改库动作不经过代码，就用数据库日志监听自动删。代码路径写库后立刻 DEL 绝不 SET 新值；手动刷数走日志监听，MySQL 用 Canal，信创的 openGauss 没有 binlog 只有 WAL，就做逻辑解码。删哪些 key 不写死在代码里，统一放一张规则配置表，任何语言读同一份。批量刷数合并加防抖，万级删 key 压成几个命令，再给所有 key 设过期兜底。结果就是只要库变缓存一定失效，一致性从靠协议变成靠架构。」

【加分句】「这项同时应对了信创替换——换数据库不影响缓存链路，正好呼应前面的等保信创。」
