# 慢 SQL / 慢服务的故障传导与后果分析

> 问题：如果出现**慢 SQL**（微服务→DB）或 **C 撮合核心慢服务**，会如何层层传导、最终导致什么后果？
> 结论先行：在这套「同步阻塞 + 有限连接池 + 无隔离/无熔断」架构下，任何一个慢点都会被**逐层放大**，从「一个接口变慢」演变成「全链路雪崩」。

---

## 一、一句话结论

> **慢本身不可怕，可怕的是"慢"沿着同步阻塞的调用链向上占用有限的线程/连接资源，并触发关池重试的正反馈，最终把单点慢放大成全系统不可用。**

---

## 二、传导链总览

```
慢 SQL（DB 慢查询）                     C 撮合慢服务（撮合计算慢/锁竞争/队列堆积）
        │                                      │
        ▼                                      ▼
   微服务 Hessian 调用 RT 变长             撮合请求 RT 变长
   （100ms → 10s/30s）                    （100ms → 1s/10s）
        │                                      │
        └──────────────┬───────────────────────┘
                       ▼
         dataShare 处理线程被同步阻塞
         （ConnHessianCommandParse / ConnSocketCommandParse）
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   ① 连接池耗尽    ② 关池递归重试   ③ 全局锁冻结
   ④ 单 IO 停摆    ⑤ per-user 锁
        └──────────────┼──────────────┘
                       ▼
         网关 DS 池 / Tomcat 线程占满
                       ▼
         网关无法处理新请求 → 全链路雪崩
```

---

## 三、慢 SQL 的传导链（微服务 → DB）

慢 SQL 发生在最末端（微服务内部查 DB），但会一路向上烧：

| 层 | 发生什么 | 后果 |
|---|---|---|
| DB | 慢 SQL 占住 DB 连接、持锁、吃 CPU/IO | DB 连接池耗尽、其他 SQL 等锁、buffer pool 被污染 → 命中率下降 → 更慢（恶性循环） |
| 微服务 | Hessian 调用 RT 从 100ms 拉到 10s+ | `http.maxConnections` 默认 **5** 个连接被慢调用长期占用，几个并发就打满 |
| dataShare | `ConnHessianCommandParse` 同步阻塞在 `Method.invoke` | dataShare 处理线程被占；若单 IO 线程 → **整个 dataShare 停摆 10s** |
| 网关 | `DSUtils.callHession` 同步等响应 | DS 客户端池连接被占、Tomcat 工作线程被占 |
| 全网关 | Tomcat 200 线程全部在等慢 SQL | 网关无法接新请求 → 所有接口 RT 飙升 |

---

## 四、C 慢服务的传导链（撮合）

C 撮合是资金主链路，慢的破坏力更大：

| 层 | 发生什么 | 后果 |
|---|---|---|
| C 撮合 | 撮合计算慢 / 锁竞争 / 队列堆积 | 撮合请求 RT 变长，队列越积越长 |
| dataShare | `ConnSocketCommandParse` 阻塞读 | 后端 socket 池（`SOCKET_MAX`）连接被占满 |
| 重试放大 | `Read timed out` → `callDSProtocol(count+1)` 递归重试 | **深度最多 100**，一次 10s 超时 → 约 **1000s 占用** |
| 网关 | 撮合请求超时（`SOCKET_TIMEOUT`） | 若配置了自动重试 → 重复撮合 → **资金重复委托风险**（要靠幂等/对账兜底） |

---

## 五、共性后果（五类放大机制）

慢点会被下面五个机制**放大**，而不是线性传导：

| # | 机制 | 源码位置 | 放大效果 |
|---|---|---|---|
| 1 | **连接池耗尽 + 排队** | `maxWaitMillis=5000`（6 处硬编码） | 池耗尽后每个请求阻塞 5s 才失败 |
| 2 | **关整池递归重建** | `BIOSocketConnectManager.java:54-64`、`SocketClientConnectManager.removeConnetPoll` | 池耗尽 → 关闭整池 → 所有在途连接被强杀 → 全部请求同时失败 |
| 3 | **全局锁冻结** | `ShardedReidsPool.java:58-75`（全局锁内 `getResource`）、`LockCache.java:41-54`（锁序倒置） | Redis 池耗尽 → 全系统所有 Redis 操作（缓存/锁/队列）**归零** |
| 4 | **单 IO 线程停摆**（待实测） | `HandlerImpl.run()` 无线程移交 | 一个慢后端 = 全平台停摆 10s |
| 5 | **递归重试放大** | `ConnSocketCommandParse.java:142-163` | 10s 超时 × 100 次递归 ≈ 1000s 占用 |

**正反馈回路**（最致命）：慢 → 占用资源 → 池耗尽 → 关池 → 更多失败 → 更多重试 → 后端更慢 → …… 一旦进入这个循环，不重启很难自愈。

## 六、量化推演：一个 10s 慢 SQL 如何打挂全链路

假设：Tomcat 200 线程、DS 池 `maxCon=100`、Hessian `http.maxConnections=5`、dataShare 单 IO 线程（待实测）。

```
T0   一个 Hessian 请求命中慢 SQL，RT 从 100ms → 10s
T0+1s 5 个并发请求就占满 http.maxConnections=5 的全部连接
T0+2s dataShare 单 IO 线程被阻塞在 Method.invoke → 全 DS 停摆
T0+3s 网关 100 个 DS 池连接全部在等 dataShare 响应
T0+5s Tomcat 200 线程全部被占用等待
T0+10s 池耗尽 → maxWaitMillis 超时 → 关整池 → 递归重建 → 所有在途请求失败
T0+10s+ 更多重试打到慢 SQL → 慢 SQL 更多 → DB 连接也耗尽 → 雪崩
```

**结论：一个 10s 慢 SQL，足以让 200 线程的网关在 10 秒内全部挂起，并触发池重建雪崩。**

## 七、防护手段（对应《网关百万并发与协议隔离设计》）

| 后果 | 防护 |
|---|---|
| 连接/线程被慢调用长期占用 | **超时分级 + 快速失败**：每协议独立超时，超时即释放；慢调用不无限占用 |
| 池耗尽 → 关池 → 雪崩 | **只销毁坏连接 + 熔断**：去掉「关整池递归重建」 |
| 全局锁冻结 | **借连接移出全局锁**、锁序修正、分段锁 |
| 单 IO 线程停摆 | **引入业务 worker 线程池**（异步化），慢后端不再阻塞 IO 线程 |
| 重试放大 | **不自动重试**（撮合靠幂等/对账兜底）、指数退避 + 熔断 |
| 慢 SQL 拖垮 DB | **慢查询治理**（索引/改写/分页）、连接池隔离、读写分离、限流 |
| 慢协议拖垮快协议 | **舱壁隔离**（协议级线程池/信号量 + 熔断），慢协议只在自舱壁内被熔断 |
