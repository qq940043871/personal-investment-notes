# B2B 连接池参数配置建议

> 基于 `midservice`（网关）与 `dataShare`（数据中心）源码走读，梳理全链路连接池的**当前默认值**与**压测/生产建议值**。所有位置可回溯 `文件:行号`。
> 建议值均为**压测基线**，最终以压测拐点实测为准；标注「改代码」的是当前硬编码、需改源码或加参数化。

---

## 一、配置总览（一句话结论）

| 层 | 池 | 当前默认 | 建议压测基线 | 关键风险 |
|---|---|---|---|---|
| 网关 | DS 客户端池（→dataShare） | maxCon=100（SDK）/ 生产疑似=5 | **200~300** | 第 2 跳硬顶，池耗尽关整池雪崩 |
| 网关 | 21 个后端业务池 | maxCon=50 / initCon=1 / timeOut=10000 | 核心 100~200 / 查询 50 | 部分池无默认值 → NPE |
| 网关 | Tomcat 线程 | server.xml 默认 200 | 200~500 | 同步阻塞模型下是硬顶 |
| 数据中心 | 后端 socket 池（DB） | 无默认值（`TB_DS_PROTOCOL`） | 撮合 200~300 / 查询 50~100 | `maxWaitMillis=5000` 硬编码 |
| 数据中心 | Redis 池（服务端） | 空字符串（NPE 风险） | MaxTotal 300 | 全局锁内借连接，耗尽归零 |
| 数据中心 | Redis 池（客户端 SDK） | 200 / **5** / 1000 | MaxIdle 5→50 | MaxIdle 偏小 |
| 数据中心 | Hessian HTTP 连接 | JVM 默认 **5**/主机 | `-Dhttp.maxConnections=200` | 最隐蔽的硬约束 |

## 二、网关侧（midservice）

### 2.1 DS 客户端池（网关 → dataShare，第 2 跳硬顶）

**定义位置**：
- `DSBean.java:32-41`：`timeOut=5000`、`initCon=1`、`maxCon=100`、`tcpNoDelay=true`（SDK 默认）
- `DSClientAPI.java:145-153`：`maxTotal=maxCon`、`minIdle=initCon`、`maxIdle=initCon+10`、**`maxWaitMillis=5000` 硬编码**
- midservice 侧实际赋值：`ServiceConfig.DS`（`timeOut/initCon/maxCon` 均**无默认值**，需外部配置）；`ImageCompressUtils.java:88-90` `setMaxCon(5)`（测试 main，非生产）；`ThirdNoitfyController.java:162-164` `setMaxCon(30)`
- **生产真实赋值**在外部 core 模块 `CoreUtils.getDSClientAPI()`，**不在源码树内，必须到生产核实**

**建议**：

| 参数 | 建议值 | 依据 |
|---|---|---|
| `maxCon` | **200（撮合密集 300）** | 同步 BIO 下 1 连接=1 请求，`maxCon` = 第 2 跳并发上限；先核实生产值，再按 dataShare 实测并发能力定 |
| `initCon` | **20（maxCon 的 10%）** | 默认 1 → 冷启动后首个请求现场建连，预热可消除首包毛刺 |
| `timeOut` | **3000** | 撮合短超时 + 不自动重试（幂等/对账兜底） |
| `maxWaitMillis` | 保持 5000，或按 RT P99 设 | **不要盲目改小**：它是「池耗尽时的快速失败护栏」不是「排队窗口」。前提是 `maxCon` 先匹配容量（正常不耗尽），否则改小 = 把排队变成「拿不到连接」 |

> ⚠️ `DSBean.java:37-38` 构造函数把密码误赋给 `userName`，`userPswd` 永远为 null —— **必须显式 `setUserPswd()`**，否则登录 DS 失败。

### 2.2 21 个后端业务连接池

**字段**（`ServiceConst.java:56-78`）：`connectPool_xsg/ctp/bd/bp/xht/xhtQuery/plzg/plzgQuery/PLZBzg/PLZBzgQuery/xydls/xydlsQuery/xhtV5/xhtV5Query/cxgp/CNYS/cnjy_trade/cnjy_query/dsd` + `fundsV1/V2ConnectManager` + `monPool`。

**默认值分两类**（`ServiceConfig.java`）：

| 类型 | 类 | 当前默认 |
|---|---|---|
| 有默认值 | `cnys`/`Bp`/`Bd`/`Cnjy.Query/Trade`/`Ctp`/`Xsg` | `maxCon=50`、`initCon=1`、`timeOut=10000` |
| **无默认值（`Integer` 裸对象）** | `Cxgp`/`Xht.Query/Trade`/`XhtV5.*`/`Plzg.*`/`PLZBzg.*`/`Xydls.*` | `null` → 未配置则**自动拆箱 NPE，启动即崩** |

**建议**：

| 池类型 | `maxCon` | `initCon` | `timeOut` |
|---|---|---|---|
| 核心撮合/资金（`bd/bp/cnjy_trade/fundsV2/xht` 等） | 100~200 | 20 | 1000~2000 |
| 查询类（`xhtQuery/plzgQuery/cxgp` 等） | 50 | 10 | 3000~5000 |

> 无默认值的池（`Cxgp`/`Xht`/`Plzg`/`PLZBzg`/`XhtV5`/`Xydls`）**必须逐一显式配置**，这是压测环境搭建的必查项。

### 2.3 Tomcat 线程池 + 本地 Redis

- **Tomcat**：`conf/server.xml` 的 `<Connector maxThreads=...>`（默认 200，代码只读 port 不读 maxThreads，`ServiceServlet.java:135`）。同步阻塞模型下它是第 1 跳硬顶，建议 **200~500**（配合 AsyncContext 异步化后可保持小）。
- **本地 Redis**（`ServiceConfig.Redis`）：`host/port/password`，无独立池参数，走 `RedisClient`。

## 三、数据中心侧（dataShare）

### 3.1 后端 socket 池（`TB_DS_PROTOCOL`，第 4 跳硬顶）

**定义位置**：
- `ProtocolBean.java:83-85`：`socketTimeout/socketInit/socketMax` 读 DB `SOCKET_TIMEOUT/SOCKET_INIT/SOCKET_MAX`，**无代码默认值**，缺配置 `((Integer)null).intValue()` NPE
- `SocketConnRunnable.java:112-120`：`maxTotal=socketMax`、`minIdle=socketInit`、`maxIdle=socketInit+10`、**`maxWaitMillis=5000` 硬编码（5 处重复）**、未设 `testOnBorrow`

**建议**：

| 协议类型 | `SOCKET_MAX` | `SOCKET_INIT` | `SOCKET_TIMEOUT` |
|---|---|---|---|
| 撮合类（connType=2 主链路） | 200~300 | MAX 的 20% | 1000（不自动重试） |
| 查询/报表类 | 50~100 | MAX 的 20% | 3000 |

```sql
-- 压测前核实并修正
SELECT PROTOCOL_KEY, SOCKET_MAX, SOCKET_INIT, SOCKET_TIMEOUT
FROM TB_DS_PROTOCOL WHERE IS_VALID = 1;

UPDATE TB_DS_PROTOCOL SET SOCKET_MAX=200, SOCKET_INIT=40, SOCKET_TIMEOUT=1000
WHERE CONN_TYPE=2 AND MAIN_HIGH='撮合协议主号';   -- 按实际协议号
```

> `maxWaitMillis=5000` 硬编码：**不要直接改小**。正确的组合拳是——① `SOCKET_MAX` 先匹配「峰值并发 × RT」（尤其撮合/DB 类长 RT 协议）；② 池耗尽改成「只销毁坏连接 + 熔断」而非「关整池递归重建」；③ 加 `testOnBorrow=true`。在 ①②③ 到位后，`maxWaitMillis` 才可作为异常快速失败护栏，且取值应 **≥ 后端 RT 的 P99**（如 DB RT P99=2s，则至少 2000~3000，而非 500），否则正常慢查询也会被误伤成「拿不到连接」。

### 3.2 Redis 池（服务端 `redis.properties`）

**定义位置**：`RedisPropertiesLoad.java:16-21` → `SystemRedisConfig`：`REDIS_LIST/MaxTotal/MaxIdle/MaxWaitMillis/AUTH`，**默认全是空字符串**，漏配即 `Integer.valueOf("")` NPE。

**建议**：

```properties
# redis.properties（COMMON 段）
REDIS_LIST=10.0.0.1:6379,10.0.0.2:6379
MaxTotal=300
MaxIdle=50
MaxWaitMillis=1000
AUTH=******
```

> ⚠️ `ShardedReidsPool.getConnect()` 在**全局锁内**调用 `getResource()`，池耗尽时全系统 Redis 归零。`MaxTotal` 要大于「后端并发 × Redis 往返占比」，且借连接务必移出全局锁（改造项）。

### 3.3 客户端 SDK Redis 池

**定义位置**：`ShardedReidsPool.java:35-37`：`MAXTOTAL=200`、`MAXIDLE=5`、`MAXWAITMILLIS=1000`、`testOnBorrow=false`。

**建议**：`MAXIDLE` 从 5 调到 **50**（当前偏小，高并发下频繁建/销连接）；`MAXTOTAL` 保持 200 或按客户端直连场景调大。

### 3.4 Hessian HTTP 连接（最隐蔽的硬约束，查 DB 场景尤其关键）

**位置**：`HessianFactoryUtils.java:108` 走 JDK `HttpURLConnection`，HTTP keep-alive 由 JVM 全局 `http.maxConnections` 管理，**默认 5/主机**。

**关键澄清**：Hessian（connType=1）**不走** §3.1 的 commons-pool socket 池，也没有 `maxWaitMillis` 概念——它的连接复用完全靠 `http.maxConnections`。因此：

- Hessian 容量 = `http.maxConnections` × (1/RT)，**与 `SOCKET_MAX` 无关**。
- 若 Hessian 后端内部是查 DB，RT 普遍几百 ms~几秒，默认 5 个连接 × 长 RT = 极低吞吐，**这才是 Hessian 路径真正的头号瓶颈**，而非 `maxWaitMillis`。

**建议**：

1. JVM 启动参数 `-Dhttp.maxConnections=200`（JDK8 为 `sun.net.http.maxConnections`）——先把连接数从 5 放开。
2. 按「峰值并发 × DB RT」评估 Hessian 需要的有效连接数，`http.maxConnections` 要 ≥ 该值。
3. Hessian 本身是同步阻塞 HTTP RPC，长 RT（查 DB）会长期占用连接/线程；要彻底解决需异步化或走 connType=2 TCP 协议（见《网关百万并发与协议隔离设计》§六）。

## 四、压测前必核实的配置清单（Checklist）

| # | 核实项 | 方法 |
|---|---|---|
| 1 | 生产 DS 池真实 `maxCon`（是否=5） | `grep -rn "setMaxCon" $APP_HOME/1018/core/`；`jmap <pid> \| grep ConnectPool` |
| 2 | `TB_DS_PROTOCOL` 的 `SOCKET_MAX/INIT/TIMEOUT` | `SELECT COUNT(*), SUM(SOCKET_MAX) FROM TB_DS_PROTOCOL WHERE IS_VALID=1` |
| 3 | `redis.properties` 的 `MaxTotal/MaxIdle/MaxWaitMillis` | 读配置（当前默认空字符串，NPE 风险） |
| 4 | Tomcat `maxThreads` | `grep -o 'maxThreads="[0-9]*"' $CATALINA_HOME/conf/server.xml` |
| 5 | 无默认值的后端池（Cxgp/Xht/Plzg 等）是否配置 | `ServiceServlet.java` 装载逻辑 + 外部 properties |
| 6 | `is.open.syncLock` + `syncLockMap` | 决定 per-user 锁是否生效（单用户并发 1 还是 N） |
| 7 | JVM `http.maxConnections` | `java -XX:+PrintFlagsFinal -version \| grep http.maxConnections` |

## 五、配置示例汇总

```bash
# 1) JVM（网关 & 数据中心）
JAVA_OPTS="$JAVA_OPTS -Dhttp.maxConnections=200"   # Hessian 连接数

# 2) server.xml（Tomcat）
<Connector protocol="org.apache.coyote.http11.Http11NioProtocol"
           maxThreads="300" acceptCount="2000" maxConnections="30000" connectionTimeout="20000" />

# 3) redis.properties（dataShare）
REDIS_LIST=host1:6379,host2:6379
MaxTotal=300
MaxIdle=50
MaxWaitMillis=1000
AUTH=******

# 4) TB_DS_PROTOCOL（撮合协议）
UPDATE TB_DS_PROTOCOL SET SOCKET_MAX=200, SOCKET_INIT=40, SOCKET_TIMEOUT=1000 WHERE <撮合协议>;
```
