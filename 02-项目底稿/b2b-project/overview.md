## 一、项目背景：大宗交易的三个「死结」

大宗商品（煤炭、钢铁、矿石、农产品等）客单价从数十万到上千万，交易金额大、周期长、环节多。要把陌生买卖双方搬到线上成交，必须先解开三个死结：

1. **死结一 · 陌生人大额交易的信任**
   买卖双方互不相识却要打出百万级资金，谁先付款、谁先发货？需要平台提供**资金监管、货权控制、电子签章与履约担保**，把「信任」做成可执行的产品能力。

2. **死结二 · 比价与履约效率**
   价格随行就市、交易模式多样（挂牌/竞价/询价/招标/基差点价），且合同签订后还牵着仓单、物流、税务。需要**高效撮合 + 全链路履约闭环**，否则一次交易周期长达数天。

3. **死结三 · 买方资金不足**
   下游买方常因囤货（如冬储）缺现金流而不敢下单。需要**供应链金融**把订单、仓单、应收账款变成可融资资产，打通资金侧堵点。

> **平台定位**：以交易为核心，打通**交易、支付结算、合同履约、仓单、物流、税务**闭环，并叠加供应链金融。底层用 C 语言内存撮合引擎保障撮合性能，上层用 Java 微服务业务中台承载复杂业务编排与外部集成。

## 三、整体架构：四层异构桥接

```
┌──────────────────────────────────────────────┐
│  外部系统（External Systems）                 │
│  5 家银行 · 物流 WMS · 税务 · 电子签章 … 9+   │
└──────────────────────────────────────────────┘
                 ↑↓  统一外联网关适配层
┌──────────────────────────────────────────────┐
│  Java 微服务业务中台（12+ 微服务）            │
│  交易 · 支付结算 · 合同履约 · 仓单 · 物流 ·   │
│  税务 · 供应链金融 · 公共服务 · 认证          │
└──────────────────────────────────────────────┘
                 ↑↓  统一报文 / 幂等 / 链路追踪
┌──────────────────────────────────────────────┐
│  自研 DS 数据中心（防腐层）                   │
│  协议转换 · 可靠性保障 · 可观测性             │
└──────────────────────────────────────────────┘
                 ↑↓  Hessian RPC / TCP 自定义二进制协议
┌──────────────────────────────────────────────┐
│  C 语言内存撮合引擎（Matching Engine）        │
│  挂牌 · 竞价 · 询价 · 招标 · 基差点价         │
└──────────────────────────────────────────────┘
```

> **设计哲学**：让「擅长的交给擅长的」——C 撮合引擎负责低延迟、高吞吐的订单撮合；Java 业务中台负责复杂的业务编排、事务、外部集成与多租户配置。两者中间的 **DS 数据中心（防腐层）** 负责把协议、可靠性与可观测性收敛到一层，使 C 团队与 Java 团队可以各自独立迭代、互不阻塞。

## 四、核心技术决策与踩坑

| 决策点 | 背景 / 问题 | 我的决策 | 收益 / 结果 |
|--------|-------------|----------|-------------|
| ① 否决「C 重写成 Java」 | 新人接手时有人提议用 Java 重写撮合引擎以统一技术栈。 | 坚决否决。撮合是资金链路的心脏，Java GC 停顿不可接受，重写带来的性能倒退与业务中断风险远超收益。 | 保住撮合性能与稳定性，避免一次可能长达数月的重写悬崖。 |
| ② 多租户可配置化 | 每个客户交易规则、审批流、单据模板都不同，定制开发导致上线周期长。 | 「一套引擎 + 每客户一套配置」：Drools 规则引擎 + 策略模式 + 配置化模板，把差异从代码下沉到配置。 | 新客户上线周期 **2 个月 → 1 周**。 |
| ③ Saga + 状态机 + 事件溯源 | 一笔交易跨月存在（合同签署→备货→发运→验收→结算），跨服务、跨月，传统事务无法覆盖。 | 以状态机描述单据生命周期，Saga 编排跨服务补偿，事件溯源保留全量状态变迁历史。 | **3 年零资金差错**，任意单据可回溯。 |
| ④ Kafka + Outbox + 消费幂等 | 早期服务间点对点直连同步数据，耦合重、丢消息、重复投递难处理。 | 改造为 Kafka 事件驱动；本地消息表（Outbox）保证「写库与发消息」原子；消费端按业务键幂等去重。 | 数据同步解耦、可重放，杜绝重复入账。 |
| ⑤ 外部集成统一网关 | 银行、WMS、税务、签章各说各话，每家对接都要重写一遍认证、重试、对账。 | 抽象统一网关适配层：防腐 + 协议转换 + 幂等 + 对账兜底，新渠道以「接插件」方式接入。 | 对接 9+ 系统，新系统对接 **2-3 周 → 3-5 天**。 |

## 六、子系统详解

- **DS 数据中心（防腐层）**：收敛 C 与 Java 之间的协议转换、可靠性、可观测性，两侧独立演进。源码走读 → [`dataShare/`](./dataShare/)（SDK 网关能力 / 分布式能力与瓶颈 / 系统缺陷 / 端到端并发，共 4 篇）
- **中间件网关与契约治理**：统一入口、路由与流量治理，以及「管连线不管黑盒」的接口契约治理。源码走读 → [`midservice/`](./midservice/)（HandlerController 前台网关 / ToBackController 后台网关 / 百万并发与协议隔离设计，共 3 篇）
- **外联网关适配层**：5 家银行、物流 WMS、税务、电子签章等 9+ 外部系统的统一接入层。
- **业务模块**：交易、支付结算、合同履约、仓单、物流、税务等业务中台微服务。
- **公共服务**：文件存储、消息推送、字典、配置中心等通用基础服务能力。
- **认证模块**：单点登录、权限管理、角色控制、多租户隔离等安全能力。
