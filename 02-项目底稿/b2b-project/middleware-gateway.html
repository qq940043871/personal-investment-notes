一、项目背景与要解决的问题

B2B 平台对外要承载多租户门户、机构端、第三方合作渠道与内部微服务调用。早期没有统一入口，各服务各自暴露接口，认证、防重放、脱敏各写各的；更麻烦的是接口契约没人管——上游改了字段不通知下游，上线当天才暴露兼容问题，跨模块协作互相踩脚。

入口不统一

认证、鉴权、防重放逻辑散落在各服务，安全策略无法统一收敛与审计，加一个渠道改一圈。

契约会漂移

接口字段、错误码、版本各改各的，下游不知道上游变了，联调才发现不兼容。

高峰易雪崩

冬储高峰流量突增，全链路同步阻塞调用，一个慢服务就能占满网关线程，缺少隔离与快速失败。

核心定位：自研 Java Web 网关（Spring MVC，多实例部署）作为平台唯一南北向 API 入口。前台网关只做六件事：协议路由 → 安全校验 → 参数校验 → 反射调用 → 响应治理 → 可观测；业务逻辑全部下沉到 54 个协议执行器，协议元数据全部收敛在 api.json 配置——目标是「加一个接口不用发版」。同时承担接口契约治理：管连线（契约/版本/兼容），不管黑盒（服务内部实现）。

四、网关核心能力

配置驱动路由：加接口零发版

  • api.json 登记协议号 → 执行器（类#方法）绑定、参数校验规则、鉴权/缓存/脱敏开关
  • 业务逻辑在 54 个协议执行器中，网关按元数据反射调用
  • RESTful 反查、协议别名映射、内部协议隔离（APISTYLE=inner）
  • 批量协议（directives）一次请求多个能力，上限可配

纵深安全体系

  • 传输混合加密：RSA 加密传递 AES Key，业务体 AES/CBC，响应同钥回加密
  • 防重放（时间戳签名+时间窗）、协议号防伪、客户端私钥签名+服务端验签
  • 四套认证体系（电子签章/云签/平台认证/分级登录）按协议切换
  • 出参字段级脱敏、日志隐私参数掩码、单账号异地互斥登出

三级缓存与幂等防重

  • 配置化三级缓存：PUB 全局共享 / FRM 按机构 / CLI 按请求参数
  • TTL 配置化（CACHE_EXPIRE），命中则完全不进入反射调用
  • 收益公式：QPS × 命中率 × (后端RT − 缓存RT) − 一致性风险
  • 幂等 Greencard（≤4 次复用）+ 用户维度防重锁防重复下单

全链路可观测

  • logKey（协议/版本/流水号/IP/用户）ThreadLocal 贯穿全链路
  • 登录/注销/改密全量审计经 DS 总线投递（1018_APP_LOG）
  • 协议调用量监控数据上送（1018_MONITOR_DATA），集群维度聚合
  • 慢接口 >1s 自动 WARN，三套日志流分级输出

五、接口契约治理：管连线，不管黑盒

网关不关心服务内部怎么实现（黑盒），但必须管住服务之间怎么连（连线）：契约、版本、兼容性。我们把它落在一套配置元数据 + 评审流程上：

契约即配置

api.json 就是活的契约清单：每个协议的入参规则（必填/长度/正则）、缓存类型、鉴权强度、隐私参数都登记在案，可查询、可审计。

兼容性校验

接口变更走评审，做前后向兼容性检查；参数校验规则与版本字段（zd_version）配合，不兼容变更必须升版本并通知下游。

版本与渠道并存

版本号随请求上下文注入执行器；文案与校验规则按渠道（reffer）差异化覆盖——同一协议对不同渠道呈现不同契约面。

契约看板

协议调用量探针持续统计调用量、成功率、耗时分布（P50/P95/P99），契约执行情况一目了然，异常自动告警。

六、配套管理机制

Java 侧排班值班，网关有统一告警与排障入口，出问题凭 logKey 流水号快速定位，值班记录沉淀进复盘。

跨模块接口变更必须走契约评审，上游改字段需提前通知下游，把联调问题前置到设计阶段。

七、关键决策与踩坑

决策一 · 前台/后台双网关：安全做在协议层，权限做在菜单层

前台 /api 面向互联网 C 端与机构第三方，入口不可信——把加密、防重放、验签、脱敏全部做在协议层；后台 /toBack 面向内网运营人员，操作者可信但权限边界要清晰——只保留 func_id 菜单功能码鉴权，砍掉 29 项 C 端对抗能力（后台流量低 2~3 个数量级，砍掉的是攻击面对策与合规项）。一句总结：前台防坏人，后台管越权。

决策二 · 一切协议元数据进配置，加接口不发版

校验规则、缓存类型、鉴权强度、脱敏字段、隐私参数全部登记在 api.json，网关启动加载、执行器动态绑定。踩坑：早期部分校验硬编码在代码里，每接一个渠道都要发版回归；收敛到配置后，新接口上线只加配置+执行器，网关零改动。

决策三 · 缓存是配置不是代码，但要用公式算

三级缓存加一条配置就能开，但我们立了规矩：先过「收益 = QPS × 命中率 × (后端RT − 缓存RT) − 一致性风险」五判据——写协议绝不缓存；公共数据 PUB 全局共享优先；客户资产类 CLI 命中率低要谨慎；资金余额强一致直接不做。踩坑：曾把参数空间巨大的接口配了 CLI 缓存，命中率趋近 0 还白占 Redis。

决策四 · 熔断限流：诚实面对现状，分级演进

现状只有系统级人工熔断开关（发版/升级期间一键降级，文案可配）+ 批量协议数量上限；没有自动熔断与 QPS 限流——根因是全链路同步阻塞。我们制定了五层防线演进方案：网关限流熔断降级 → 后端线程池舱壁隔离 → 缓存 90% 命中 → DB 慢查询治理 → 超时逐层递减（网关 1s > 后端 800ms > DB 500ms）且不自动重试，以幂等+对账兜底。

踩坑拾遗（源码走读发现）

① AES/CBC 把 Key 同时当 IV 用，不符合 CBC 语义——列入安全整改，改为随机 IV 随报文传输；② 用户防重锁的锁 Map 无淘汰机制，key 随在线用户数单调增长——补 LRU 过期；③ 路由查找是 List 线性扫描（1296 个协议），热路径 O(n)——改 Map 双索引 O(1)；④ 前后台两个 Controller 4000+ 行大量复制——规划抽 AbstractGateway 模板 + 责任链，前后台按需装配 Filter。

八、关键实现

api.json 协议契约（配置驱动核心）

协议号绑定执行器与全部元数据：校验、缓存、鉴权、隐私——契约即配置。

{
  "API_PROTOCOL": "MT1100",              // 协议号（登录）
  "API_NAME": "用户登录",                 // 审计用名称
  "API_ISLOGIN": "N",                    // 是否需登录态
  "API_BINDCLASS": "com.xxx.handler.MT1100Handler#execute",
  "API_HANDLETYPE": "B",                 // B=Bean绑定 / D=协议号自动映射
  "APISTYLE": "custom",                  // inner=内部协议禁止外呼
  "PARAMS": [
    { "PARAM_CODE": "username", "PARAM_ISREQUIRE": "Y",
      "PARAM_LENGTH": "32", "PARAM_MEMO": "登录名[隐私]" },
    { "PARAM_CODE": "password", "PARAM_ISREQUIRE": "Y",
      "PARAM_LENGTH": "64", "PARAM_MEMO": "密码[隐私]" }
  ],
  "CACHE_TYPE": "",                      // PUB/FRM/CLI，空=不缓存
  "CACHE_EXPIRE": "60"                   // TTL 秒
}

三级缓存判定（命中即短路反射）

按缓存类型构造 Redis Key：全局共享 / 按机构隔离 / 按请求参数，TTL 配置化。

// HandlerController 执行前缓存检查（机制示意）
ApiCache conf = ServiceConst.ApiCacheMap.get(api);
if (conf != null) {
    String redisKey;
    switch (conf.getType()) {
        case "PUB":   // 行情/公告/字典：全用户共享
            redisKey = conf.getKey(); break;
        case "FRM":   // 费率/机构配置：按机构隔离
            redisKey = conf.getKey() + "-" + token.getFirmId(); break;
        case "CLI":   // 客户资产：按请求参数指纹
            redisKey = conf.getKey() + "-" + MD5(params); break;
        default: throw new ApplicationException("暂不支持此缓存类型");
    }
    String cached = redis.get(redisKey);          // Base64(JSON)
    if (cached != null) return respond(cached);   // 短路，不进反射
}
Object data = new MCallable(router, params).call(); // 反射执行
redis.setex(redisKey, conf.getExpire(), encode(data));

前台 / 后台双网关能力对比

维度前台 HandlerController（/api）后台 ToBackController（/toBack）
服务对象App / 小程序 / 机构端 / 第三方合作渠道内网运营、柜面、客服（后台 SPA）
鉴权模型协议级 + 用户类型（个人/机构/第三方），四套认证体系分级func_id 菜单功能码，Token.AUTHS 统一校验

取舍逻辑：前台把「安全」做在协议层，因为入口不可信；后台把「权限」做在菜单层，因为操作者可信但需要清晰的权限边界。
