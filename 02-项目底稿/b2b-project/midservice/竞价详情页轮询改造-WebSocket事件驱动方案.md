# 竞价详情页轮询改造：WebSocket 事件驱动技术方案

> 目标：**移除竞价详情页所有实时轮询**，用 WebSocket 事件驱动替代；对「变化不频繁」的数据保留低频轮询，但**仅穿透到网关层**（缓存/Redis 命中，不下穿 DS→后端）。
> 范围：前端页面 / midservice 网关 / dataShare 数据中心 / C 撮合引擎（事件上报）。

---

## 一、现状问题分析

### 1.1 竞价详情页当前的轮询模式

```
页面定时器（500ms~1s） ──轮询──▶ 最优价 / 出价记录 / 成交流水
        │
        ▼
   每次轮询都穿透完整链路：网关 → dataShare → C 撮合引擎（5 跳）
```

### 1.2 轮询的四大合理性缺陷

| 缺陷 | 说明 | 后果 |
|---|---|---|
| **空轮询** | 数据没变也照打后端 | 绝大多数轮询是无效请求，浪费后端算力 |
| **延迟与频率的天然矛盾** | 间隔短→延迟低但压力大；间隔长→压力小但延迟高 | 无法两全，实时性被轮询间隔锁死 |
| **后端压力随在线用户线性放大** | QPS = 在线用户数 × 轮询频率 | 竞价高峰（用户集中盯盘出价）时后端压力陡增 |
| **不可缓存 → 必然穿透** | 最优价/出价记录是实时撮合数据，不能走缓存 | 每次轮询都是完整 5 跳穿透，RT 长、连接/线程占用高 |

### 1.3 协议「不可缓存」的硬约束

最优价、出价记录命中了缓存判断的**③变更快 + ⑤强一致**两条，**绝不能进 PUB/FRM/CLI 缓存**：

- 最优价：每次出价都可能变，毫秒级变更；
- 出价记录：实时追加，强一致；
- 成交流水：实时产生，强一致。

> 结论：这三类实时数据「要么穿透查询、要么事件推送」，**没有缓存这条中间路**。轮询的问题本质是「把『事件驱动』该干的活，用『定时穿透』硬扛」。

## 二、WebSocket 事件驱动的查询机制设计

### 2.1 核心思想：从「拉」到「推」

```
改造前（拉）：客户端定时轮询 → 服务端被动响应（大多空转）
改造后（推）：出价变动 → 服务端主动推送事件 → 客户端按需查询/更新
```

### 2.2 事件流（复用 dataShare 已有推送能力）

```
C 撮合引擎（出价变动/最优价变化/成交流水）
   │  事件上报（复用 dataShare 订阅协议 00010034 / MQ 00010033 / Redis 队列）
   ▼
dataShare（事件汇聚 + 按场次 topic 分发，复用 0x08 服务端推送通道 AnsyResponseQueue）
   │
   ▼
midservice 网关（WebSocket 会话管理 + 事件路由）
   │  WebSocket 推送给订阅该场次的会话
   ▼
客户端（收到「变动事件」→ 触发一次查询最优价/出价记录）
```

### 2.3 推送策略：事件 + 快照 + 按需拉取（混合）

| 数据 | 推送方式 | 理由 |
|---|---|---|
| 最优价 | **事件 + 最新快照**（变动即推） | 数据小，直接随事件下发，省一次查询 |
| 出价记录 | **事件通知 + 按需拉取** | 列表可能大，客户端收到事件后拉最近 N 条 |
| 成交流水 | 事件通知 + 按需拉取 | 同上 |

### 2.4 WebSocket 协议设计

```jsonc
// 连接（复用现有 Token 鉴权）
ws://gateway/ws/bid?token=<现有登录Token>

// 客户端订阅竞价场次
{ "action": "subscribe", "topic": "bid_<场次ID>" }
{ "action": "unsubscribe", "topic": "bid_<场次ID>" }

// 服务端推送：最优价变动
{ "type": "best_price_changed", "topic": "bid_xxx",
  "bestPrice": "1020", "bestBidder": "xxx", "ts": 1698000000 }

// 服务端推送：出价记录变动（仅通知）
{ "type": "bid_log_changed", "topic": "bid_xxx", "ts": 1698000000 }

// 心跳
{ "type": "ping" }  ⇄  { "type": "pong" }
```

### 2.5 断线重连与消息补偿（关键）

1. **心跳**：客户端 30s 无消息主动 `ping`，服务端超时断开。
2. **指数退避重连**：断线后 1s/2s/4s… 重连。
3. **重连补偿**：重连成功后**重新订阅 + 拉一次全量快照**（最优价 + 最近出价记录），补偿断线期间漏掉的事件。
4. **事件序号（可选）**：服务端为每个场次的事件带递增序号，客户端据此检测漏事件、触发快照对齐。

## 三、轮询移除清单与改造范围

### 3.1 移除的轮询

| 轮询项 | 原频率 | 替代方案 |
|---|---|---|
| 最优价 | 500ms~1s | WebSocket 事件 + 快照 |
| 出价记录 | 1s | WebSocket 事件通知 + 按需拉取 |
| 成交流水 | 1s | WebSocket 事件通知 + 按需拉取 |
| 竞价倒计时 | 1s | 本地倒计时（服务端时间对齐）或事件驱动 |

### 3.2 保留但降频/降穿透的轮询

| 轮询项 | 原穿透 | 改造后 | 说明 |
|---|---|---|---|
| 场次状态/竞价规则 | 穿透 DS→DB | **仅穿透网关层**（PUB 缓存/Redis） | 变更慢，5~10s TTL |
| 公告/合约模板 | 穿透 DS→DB | 仅穿透网关层 | 变更慢 |
| 费率 | 穿透 DS→DB | 仅穿透网关层（FRM） | 变更慢 |

### 3.3 改造范围（四端）

| 端 | 改造内容 |
|---|---|
| 前端 | 移除轮询定时器；接入 WebSocket（连接/订阅/重连/心跳）；事件驱动查询 |
| 网关 midservice | WebSocket 会话管理（复用 `webSocketServer`）；事件路由；低频数据 PUB/FRM 缓存配置 |
| dataShare | 订阅/推送通道接线（复用 `00010034`/`00010033`/`0x08`） |
| C 撮合引擎 | 出价变动事件上报（C 侧，若不能改则从 dataShare 侧识别出价报文变化） |

## 四、低频轮询数据「仅穿透网关层」的实现策略

「仅穿透到网关层」= **请求在网关层返回，不下穿 DS→后端**。

| 策略 | 做法 | 适用 |
|---|---|---|
| **网关三级缓存（PUB/FRM）** | 给场次状态/公告/规则/费率配 `ApiCacheMap` 缓存，TTL 5~10s，命中即网关层返回 | 变更慢、共享度高的数据 |
| **Redis 直连** | 网关直接连 Redis 查（`00010030` 下发连接串），绕过 DS | 需要跨实例一致的缓存 |
| **本地缓存 + 事件失效** | `PubConfigCache` 类本地缓存，配合事件推送触发失效/刷新 | 配置类数据 |

**关键**：低频数据仍在轮询，但轮询请求在网关层就被挡住，**后端穿透降为 0**，只剩网关层的轻量内存/Redis 查询。

## 五、可缓存与不可缓存协议的划分标准

复用缓存判断五判据，落到竞价场景：

| 数据 | 变更频率 | 一致性 | 是否缓存 | 处理方式 |
|---|---|---|---|---|
| 最优价 | 毫秒级 | 强一致 | ❌ 不可缓存 | WebSocket 事件 + 快照 |
| 出价记录 | 实时追加 | 强一致 | ❌ 不可缓存 | WebSocket 事件 + 按需拉取 |
| 成交流水 | 实时 | 强一致 | ❌ 不可缓存 | WebSocket 事件 + 按需拉取 |
| 可用资金/持仓 | 实时 | 强一致 | ❌ 不可缓存 | 出价前按需查询 |
| 场次状态/规则 | 慢（分钟级） | 弱一致 | ✅ PUB，TTL 5~10s | 仅穿透网关层 |
| 公告/合约模板 | 慢 | 弱一致 | ✅ PUB，TTL 10~30s | 仅穿透网关层 |
| 费率 | 慢 | 弱一致 | ✅ FRM，TTL 60s | 仅穿透网关层 |

**划分标准一句话**：**「实时 + 强一致 + 影响交易决策」→ 事件推送/穿透查询，绝不缓存；「慢变 + 弱一致 + 展示类」→ 网关层缓存，仅穿透网关层。**

## 六、改造后的性能与一致性预期

### 6.1 性能

| 指标 | 改造前（轮询） | 改造后（事件驱动） |
|---|---|---|
| 后端穿透 QPS | 在线用户 × 轮询频率（高峰巨大） | 仅「实际出价变动」时触发，降低 1~2 个数量级 |
| 最优价延迟 | 轮询间隔 500ms~1s | 事件推送 <100ms，**实时性反而更好** |
| 网关层负载 | 全量穿透 DS | 低频数据被网关缓存挡住 |
| 连接资源 | 每次轮询建/用连接 | 一条 WebSocket 长连接复用 |

### 6.2 一致性

- **最优价/出价记录**：事件驱动后客户端看到的是「变动后立即推送/查询」的最新值，**一致性和实时性均优于轮询**（轮询在两次间隔之间本来就看不到中间态）。
- **低频数据**：网关层缓存 TTL 内可能稍旧（秒级），但这类数据变更慢，业务可接受；配合事件失效可进一步收敛。

## 七、分阶段实施计划

| 阶段 | 内容 | 交付 | 风险 |
|---|---|---|---|
| **P1 通道打通** | dataShare 订阅/推送接线 + 网关 WebSocket 会话管理，先推最优价事件 | 事件能端到端到达 | 中 |
| **P2 前端接入** | 前端接入 WebSocket，移除最优价/出价记录轮询，事件驱动查询 | 核心轮询移除 | 中 |
| **P3 低频缓存化** | 场次状态/公告/费率配 PUB/FRM 缓存，轮询仅穿透网关层 | 后端穿透降为 0 | 低 |
| **P4 优化收敛** | 事件带快照、出价记录增量、压测验证、灰度放量 | 性能达标报告 | 低 |

**灰度策略**：新老双通道并存（WebSocket + 轮询降频），按比例切流，观察事件送达率与数据一致性后逐步放量。

## 八、风险点与应对

| 风险 | 说明 | 应对 |
|---|---|---|
| **事件丢失/乱序** | 推送通道丢消息或乱序，客户端看到旧数据 | 事件带递增序号；重连补偿全量快照；关键交易数据出价前强制查询 |
| **WebSocket 连接管理** | 大量长连接、断线、假死 | 心跳保活；连接数监控；负载均衡 + 会话迁移 |
| **竞态一致性** | 「推送变动」与「客户端查询」之间数据又变 | 客户端查询接口返回带版本/时间戳，页面取最新 |
| **撮合引擎改造受限** | C 侧事件上报若无法改造 | 由 dataShare 侧识别出价报文变化并生成事件（旁路） |
| **网关缓存失效** | 低频数据缓存后，事件要能触发失效 | 事件同时触发网关缓存失效/刷新 |
| **灰度双通道** | 新老并存期间数据可能不一致 | 灰度期用事件序号 + 快照对齐，出价关键路径不依赖缓存 |

---

## 九、结论

竞价详情页的改造核心是**把「实时强一致数据」从「定时穿透」换成「事件推送」**，把「慢变数据」从「穿透后端」降到「网关层缓存」。改造后：

1. **移除所有实时轮询**，最优价/出价记录改为 WebSocket 事件驱动，实时性更高、后端压力降 1~2 个数量级；
2. **低频轮询仅穿透网关层**，后端穿透归零；
3. 划分标准清晰：**实时强一致 → 事件推送；慢变弱一致 → 网关缓存**。

---

*本方案基于源码能力（midservice `webSocketServer`、三级缓存 `ApiCacheMap`、dataShare `0x08` 推送/`00010034` 订阅/`00010033` MQ），行号可回溯；事件序号、撮合事件上报为需 C 侧/服务端配合的增量改造项。*
