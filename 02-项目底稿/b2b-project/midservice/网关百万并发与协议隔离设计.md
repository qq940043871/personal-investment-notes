# 网关支撑百万并发 + 协议间隔离设计（mids 网关改造方案）

> 关联文档：[`HandlerController-网关功能详解.md`](./HandlerController-网关功能详解.md)、[`ToBackController-后台网关与HandlerController对比.md`](./ToBackController-后台网关与HandlerController对比.md)
> 现状来源：[`../dataShare/dataShare-系统缺陷与并发能力分析.md`](../dataShare/dataShare-系统缺陷与并发能力分析.md)、[`../dataShare/dataShare-端到端链路并发能力分析.md`](../dataShare/dataShare-端到端链路并发能力分析.md)
> 回答两个问题：**(1) 怎么支撑「百万并发」；(2) 怎么保证协议之间互不影响、慢协议不拖慢快协议。**

---

## 一、先对齐口径：你说的「百万并发」是哪种

「百万并发」是面试里最容易答偏的词，必须先拆成三种口径，否则方案是空中楼阁：

| 口径 | 定义 | 现状能否做 | 怎么做 |
|---|---|---|---|
| **连接并发** | 同一时刻保持的在线连接数（长连接、推送场景） | ✅ 可做，且这是「百万」最合理的落点 | 异步 IO + 内核调优 + 无状态集群，单机 10 万~100 万连接 |
| **吞吐并发（QPS）** | 每秒处理的请求数 | ⚠️ 集群能力，单机做不到百万 QPS | 全异步 + 高核机器 + 水平扩展 + 后端也扛得住 |
| **业务在途并发** | 同一时刻正在执行业务逻辑的请求数 | ❌ 伪命题，没人做也不需要 | 业务在途通常几千~几万，被后端容量封顶 |

> **关键结论**：说「支撑百万」时先反问问清楚是**百万连接**还是**百万 QPS**。前者单机就能摸到，后者是「全链路异步 + 几十上百台」的集群能力，且**瓶颈往往在后端（内存撮合 / DB / Redis）而非网关本身**——网关再快，后端每秒只能吃 5 万笔，链路就只有 5 万 QPS。

---

## 二、当前撑不住的根因：同步阻塞 + 无隔离

mids 现在这套为什么连几千都悬，根子只有一句话：

> **一请求一线程、自顶向下全同步阻塞，且协议之间共享同一批执行资源。**

```
Tomcat 工作线程（默认 200，同步 BIO）
  → HandlerController 20 道校验（含 8 次串行 DS 往返）
  → 反射调 handler → DSUtils → dataShare → 后端
  → 线程全程阻塞等后端返回，期间不释放
```

由此派生出三个「互相影响」的机制：

1. **共享 Tomcat 线程池**：任何一个慢协议（如一次 10s 的撮合超时）会长期占住一个 Tomcat 线程，挤占其他协议的处理能力。
2. **全局串行点**：三类后端、所有协议共同经过同一批锁——`DSUtils.getClient()`（`static synchronized`，135 个调用点全经过）、`SocketClientConnectManager.releaseConnection()`（全协议共享的归还锁）、`ShardedReidsPool.getConnect()`（全局锁内做 `getResource()`）。
3. **无熔断/无舱壁**：慢协议不会被快速失败，也没有独立资源池兜底，故障沿共享资源横向扩散。

> 一句话：**「资源隔离靠分池，故障隔离靠线程池 + 熔断 + 异步化；只分池不分线程，慢协议照样通过共享的 Tomcat 线程池拖垮全链路。」**

## 三、目标架构：异步非阻塞 + 舱壁隔离

```
改造前（同步 BIO，全阻塞）
  客户端 ──▶ Tomcat(200同步线程) ──▶ 同步校验 ──▶ 同步 DS 往返 ──▶ 后端

改造后（异步 Reactor + 舱壁隔离）
  客户端 ──▶ Netty/WebFlux(少量 IO 线程, 不阻塞) ──▶ 协议路由(无状态 O(1)) ──▶ 协议级舱壁 ──▶ 异步后端
                                                    (独立线程池 + 信号量 + 熔断 + 超时)     (内存/DB/Redis 各自异步客户端)
```

四根支柱，缺一不可：

- **异步化** —— 解决「资源被阻塞占用」（线程/事件循环不再傻等后端）
- **舱壁** —— 解决「资源被共享争抢」（每个协议有独立、有上限的执行资源）
- **熔断** —— 解决「故障不扩散」（慢协议快速失败，不拖别人）
- **分池 + 无状态** —— 解决「容量上限」（连接池/线程池按类型隔离，网关可水平扩展）

## 四、支柱一：接入层异步化（撑起连接数）

百万连接的地基是**把「一连接一线程」换成「一连接一线程」的反面——少量事件循环线程复用管理海量连接**。

| 项 | 现状 | 改造 |
|---|---|---|
| 容器 | Tomcat 同步 Servlet（`maxThreads` 默认 200） | Netty（epoll Reactor 主从）或 WebFlux/Reactor |
| 线程模型 | 每请求一个工作线程，阻塞 | N 个 EventLoop（N = CPU 核数 × 2），只做编解码收发，**零业务逻辑** |
| 连接上限 | 受 `maxThreads` 封顶 | 受内核 fd + 内存封顶 |

**内核与 JVM 调优（C1000K 必做）**：

```bash
# 文件描述符 / 端口
ulimit -n 1048576
sysctl -w fs.file-max=2000000
sysctl -w net.ipv4.ip_local_port_range="1024 65535"
sysctl -w net.ipv4.tcp_tw_reuse=1
# 半连接/全连接队列
sysctl -w net.ipv4.tcp_max_syn_backlog=65536
sysctl -w net.core.somaxconn=65536
# 内核缓冲
sysctl -w net.ipv4.tcp_rmem="4096 87380 16777216"
sysctl -w net.ipv4.tcp_wmem="4096 65536 16777216"
```

```java
// JVM：Netty 用堆外内存，压低每连接对象开销
-XX:MaxDirectMemorySize=8g
-Dio.netty.allocator.type=pooled
```

**每连接内存账单**（决定单机能挂多少）：Socket 内核缓冲（可压到 8~16KB）+ Netty Channel 对象（几 KB）。优化后每连接 ~10KB，**100 万连接 ≈ 10GB**，一台大内存机器可撑；控制面再走无状态集群横向加。

> 单机百万连接是「连接保持」能力，不等于百万请求都在压后端。真正决定吞吐的是下面两支柱。

## 五、支柱二：舱壁隔离（协议互不影响的核心）

**慢协议拖慢快协议的本质 = 共享执行资源被占用。** 舱壁（Bulkhead）就是给每个协议（组）配一套**独立、有上限**的执行资源，任一协议打满自己的资源也不会外溢。

### 5.1 三种隔离力度对比

| 隔离方式 | 原理 | 隔离强度 | 开销 | 适用 |
|---|---|---|---|---|
| **线程池隔离** | 每协议独立线程池 | 强（线程级物理隔离） | 高（线程数总和平摊） | 核心协议：交易、资金、行情 |
| **信号量隔离** | 每协议独立并发许可数 | 中（限并发，不隔离线程） | 低 | 非核心协议：查询、报表 |
| **纯超时** | 只设超时 | 弱 | 最低 | 兜底，绝不单独使用 |

> 线程池隔离是唯一能保证「慢协议 A 占满自己的 8 个线程后，快协议 B 的线程一个都不受影响」的方式；信号量隔离仍复用同一线程，慢调用仍会占线程，**必须配超时**。

### 5.2 落地：协议分组 + 分级舱壁

1296 个协议不可能每个开一个线程池（线程碎片化、上下文切换爆炸），按**协议组**分池：

```
核心组（线程池隔离，独立池 + 独立熔断 + 独立超时）
  ├─ 交易类：下单/撤单/改单     —— 池 16 线程，超时 1s，不自动重试
  ├─ 资金类：出入金/转账/冻结   —— 池 16 线程，超时 2s，不自动重试
  └─ 行情类：快照/推送          —— 池 8 线程，超时 300ms，可降级
非核心组（信号量隔离 + 超时 + 降级）
  ├─ 查询类：合约/模板/字典     —— 信号量 200，超时 500ms，可缓存
  ├─ 报表/统计                  —— 信号量 50，超时 3s，可降级
  └─ 审计/监控/推送             —— 独立队列 + 有界缓冲，异步不阻塞主链路
```

### 5.3 每协议的四件套（配置化）

把隔离参数做成协议元数据的一部分（现成的 `api.json` 思路直接扩展）：

```json
{
  "api": "MT1200",
  "group": "trade",
  "bulkhead": { "type": "threadPool", "size": 16 },
  "timeout": 1000,
  "circuitBreaker": { "slowRate": 50, "slowDuration": 800, "minCalls": 10 },
  "retry": "none",
  "fallback": "cache:lastSnapshot"
}
```

## 六、支柱三：后端全异步 + 分池（内存 / DB / Redis 各自隔离）

网关异步化了，后端调用如果还是同步阻塞，事件循环照样被拖死。三类后端必须**各自用异步客户端 + 独立池**：

| 后端 | 现状（同步阻塞） | 改造（异步 + 分池） |
|---|---|---|
| **内存撮合服务**（C 引擎） | `callSocket/callHession` 同步 BIO，1 连接 = 1 请求 | Netty 异步 TCP/RPC 客户端 + 多路复用（复用 `ansyKey` 配对思路），独立连接池，**短超时 + 不自动重试**（幂等/对账兜底） |
| **DB** | 同步 JDBC，每请求可能 1 次 `queryForList`（`PubConfigServiceImpl`） | R2DBC 异步，或**阻塞 JDBC 收进独立「阻塞线程池」**与 IO 线程隔离；HikariCP 分池；`PubConfigCache`（5s TTL 已写好）接线消除每请求查库 |
| **Redis** | Jedis 同步 + 全局锁包 `getResource()` | Lettuce 异步客户端；独立池；**本地直连双通道**（`00010030` 下发连接串、数据走直连，网关不成为单点） |

**关键纪律**：异步链路里不允许出现任何一次同步阻塞调用（否则一个阻塞点就把整个 EventLoop 线程卡死，异步化前功尽弃）。凡是无法异步化的（如老 JDBC、文件 IO），统一丢进**独立的阻塞线程池**，与核心 EventLoop 物理隔离。

## 七、支柱四：故障隔离（熔断 / 限流 / 降级 / 背压）

舱壁解决「资源争抢」，还要解决「故障扩散」：

| 机制 | 作用 | 关键设计 |
|---|---|---|
| **熔断器** | 慢协议/坏协议快速失败 | 三态（CLOSED/OPEN/HALF_OPEN）；`slowCallRateThreshold` + `slowCallDurationThreshold` 专门识别「慢」而非「错」；熔断后 **fail-fast 释放资源** |
| **超时** | 给慢调用封顶 | 每协议独立超时；超时即释放线程/连接；**不自动重试**（防重试放大，靠幂等+对账兜底） |
| **限流** | 每协议 QPS 上限 | 令牌桶/滑动窗口；核心协议保底配额，非核心协议可被挤压 |
| **降级** | 慢协议给兜底 | 返回缓存/默认值/最近快照；核心交易链路**不自动降级**（避免误降级中断交易） |
| **背压** | 防雪崩 | **有界队列** + 拒绝策略（拒绝而非无限堆积）；响应式流控全链路传导 |

> 对照现状：dataShare 的 `isSuccessRun/errMsg` 标记**已存在却不参与任何流量决策**，熔断/挂起/恢复（`T0001fa01/02`）是空壳。这四件套本质是「把这些半成品真正接进流量决策」。

## 八、现状瓶颈 → 改造动作 对照表

| 现状瓶颈（源码证据） | 改造动作 | 收益 |
|---|---|---|
| 同步 BIO，Tomcat 200 线程 | Netty/WebFlux 异步 Reactor | 连接数从千级 → 百万级 |
| `DSUtils.getClient()` 全局 `synchronized` | `volatile` 读，去锁 | 消除 135 个调用点串行 |
| `SocketClientConnectManager.releaseConnection()` 全局锁 | 按 `clientFlag` 分段锁 | 消除全协议归还串行 |
| `ShardedReidsPool.getConnect()` 全局锁内 `getResource()` | 借连接移出锁 + Lettuce | 消除 Redis 全局瓶颈 |
| 业务处理跑单 IO 线程（`HandlerImpl.run` 无线程移交） | 协议级舱壁线程池 | 慢协议不再拖全平台 |
| `HandlerController` per-user 锁跨整个远程调用 | 锁收窄到真正临界区 | 单用户单 API 并发 1→N |
| 路由 O(n) 线性扫描（1296 协议） | `Map<api,router>` 双索引 O(1) | 消除每请求 2 次扫描 |
| `DSUtils.revert` 原生序列化往返 ×113 | ThreadLocal 复用 / 改 Hessian | 消除 CPU + 分配开销 |
| 敏感词 Trie 每次重建 + O(len²) | 真单例 + 定时刷新 + 命中 break | 消除每请求 DS 往返 |
| 池耗尽 → 关整池 → 递归重试雪崩 | 循环 + 指数退避 + 熔断，只销毁坏连接 | 消除雪崩放大器 |

## 九、量化测算：单机与集群分别到多少

### 9.1 单机（异步化后，一台 32 核 / 64GB）

| 指标 | 数值 | 推导 |
|---|---|---|
| 长连接 | **50 万~100 万** | 每连接 ~10KB，内核缓冲 + Channel 对象；受内存/fd 限制 |
| 业务吞吐 | **3000~8000 QPS** | 核心线程池 64 线程 / 平均 RT 10~20ms（异步化 + 缓存后 RT 显著下降） |
| 纯内存极简协议 | 可到**几十万 QPS** | 无 DB/无序列化损耗时，瓶颈转为 CPU 编解码 |

### 9.2 集群（无状态水平扩展）

| 目标 | 需要的机器量级 | 前提 |
|---|---|---|
| 100 万长连接 | **2~10 台** | 单机 50 万 + LB 无状态 |
| 10 万 QPS | **15~30 台** | 后端（内存撮合/DB/Redis）也得扩到对应容量 |
| 100 万 QPS | **150 台 +，且后端是绝对瓶颈** | 几乎必然落在后端扩容，而非网关 |

> **诚实结论**：「百万连接」是网关侧能兑现的；「百万 QPS」是**全链路 + 集群**命题，瓶颈最终在内存撮合引擎的撮合能力和 DB/Redis 的分片容量，网关负责的是「不成为更早的那个瓶颈」。

## 十、协议互不影响的验证方式

方案对不对，用「慢协议注入」压测验证——这是验收隔离效果的**唯一硬标准**：

```
1. 基线：协议 A（快，RT 20ms）打到 3000 QPS，记录 A 的 P99
2. 注入：协议 B（慢）注入 5s 延迟 / 触发后端超时，并发打到其舱壁上限
3. 观察：A 的 P99 是否波动

  隔离前（现状）：A 的 P99 从 50ms 飙到 5s+  —— 慢协议拖慢快协议 ✅ 复现问题
  隔离后（改造）：A 的 P99 稳定在 50ms 以内 —— 舱壁 + 熔断生效 ✅ 验证通过
```

再叠加一轮**熔断验证**：让 B 持续慢调用，观察 B 的熔断器是否在阈值后 OPEN、B 的请求是否 fail-fast、C 协议（另一快协议）是否全程无感。

## 十一、落地顺序（按「收益 / 风险比」排序）

| 阶段 | 动作 | 性质 | 预期收益 |
|---|---|---|---|
| **P0 止血** | 去全局锁（3 处 `static synchronized`）、`computeIfAbsent`、路由改 O(1)、Redis 借连接移出锁 | 不改架构 | 消除每请求串行点，吞吐翻数倍 |
| **P1 隔离** | 协议分组 + 舱壁（线程池/信号量）+ 每协议超时 + 熔断 + 降级 | 中等改造 | **解决「慢协议拖慢快协议」** |
| **P2 异步化** | 接入层换 Netty/WebFlux；后端换异步客户端（内存/DB/Redis） | 结构性改造 | 连接数、吞吐质的飞跃 |
| **P3 扩展** | 网关无状态化（会话 Redis 化）+ 水平扩展 + 全链路压测 | 架构 | 从单机到百万级集群 |

> **一句话收尾（面试话术）**：支撑百万并发不是「加线程」，而是**「异步化让资源不被阻塞占用、舱壁让资源不被共享争抢、熔断让故障不扩散、无状态让容量可水平扩展」**四件事的组合；而「协议互不影响」的答案就是——**给每个协议（组）独立且有上限的执行资源，慢协议只会在自己的舱壁里被熔断，快协议全程无感。**

## 十二、约束场景：只能使用 Web 容器（不换 Netty）时的方案

如果受团队/生态约束**不能换 Netty、不能上 WebFlux**，只能继续用 Tomcat/Servlet 容器，方案依然成立——只是把「异步化」从「换容器」改成「容器内异步化」。

### 12.1 先破除误区：Web 容器 ≠ 只能同步阻塞

Tomcat 分三层，瓶颈只在中间一层：

1. **Connector 层**：Tomcat 8+ 默认 `NioEndpoint`，已经是异步 IO 收连接，连接数不占线程；
2. **Servlet 工作线程池**：`service()` 同步执行，默认 200 线程 —— **这才是瓶颈**；
3. **业务调用**：同步等后端 → 工作线程被占死。

所以「只能 web 容器」照样能异步化，关键是**干掉第 3 层的同步等待**，让 Servlet 线程只做「收请求 → 提交业务 → 立即释放」。

### 12.2 容器内异步化：Servlet 3.1 AsyncContext

```java
@WebServlet(urlPatterns = "/api/*", asyncSupported = true)
public class AsyncGatewayServlet extends HttpServlet {
    protected void service(HttpServletRequest req, HttpServletResponse resp) {
        AsyncContext ctx = req.startAsync();       // ① 释放 Tomcat 工作线程
        ctx.setTimeout(5000);                       // ② 异步超时
        bulkheadExecutor.submit(() -> {             // ③ 丢进业务舱壁线程池
            try {
                Object rtn = routeAndInvoke(ctx);
                ctx.getResponse().getWriter().write(toJson(rtn));
            } catch (Exception e) {
                handleError(e, resp);
            } finally {
                ctx.complete();                     // ④ 完成，写回响应
            }
        });
        // service() 立即 return → Tomcat 线程回到池里接下一个请求
    }
}
```

Spring MVC 等价物：返回 `Callable` / `DeferredResult`，或用 `@Async` + 自定义线程池——底层同样是 AsyncContext。

> 收益：Tomcat 的 200 个线程只做「取请求、提交、返回」，不碰业务；真正承载并发的是业务舱壁线程池（可配到数百~数千线程），**并发上限不再被 `maxThreads` 锁死**。

### 12.3 Tomcat 参数调优（NIO 撑连接）

```xml
<Connector protocol="org.apache.coyote.http11.Http11NioProtocol"
           maxThreads="300"        <!-- 工作线程，异步化后只需少量 -->
           acceptCount="2000"      <!-- 排队队列 -->
           maxConnections="30000"  <!-- NIO 连接数，可开到几万 -->
           connectionTimeout="20000" />
```

关键认知：NIO 下 `maxConnections` 可开到几万，**连接数不再等于线程数**；`maxThreads` 在异步化后保持小（只做收发）。

### 12.4 后端仍要异步客户端（否则只是把阻塞换个池子）

Servlet 异步化后，若后端调用仍同步阻塞，只是把「Tomcat 线程阻塞」换成「业务舱壁线程阻塞」——线程够多也能扛，但仍是占线程：

| 后端 | 处理 |
|---|---|
| 内存撮合服务 | 异步 RPC 客户端 / 连接池 + 短超时 |
| DB | 连接池 + 慢查询治理 + 缓存（或独立阻塞线程池隔离） |
| Redis | Lettuce 异步 / 连接池 + 短超时 |

无法异步化的同步 JDBC / 文件 IO → 丢进**独立阻塞线程池**，与核心业务线程池物理隔离。

### 12.5 舱壁隔离（与 Netty 版一致，仅执行器换成业务线程池）

协议分组 + 线程池隔离 + 信号量 + 熔断 + 超时 + 降级，在 Servlet 容器内**完全适用**，是「协议互不影响」的核心，不因容器改变。

### 12.6 量化与边界

| 指标 | Web 容器方案 | 对比 Netty |
|---|---|---|
| 单机长连接 | 几万 ~ 十几万 | Netty 可到 50 万~100 万 |
| 单机吞吐 | 几千 ~ 上万 QPS | Netty 更高 |
| 百万连接 | 需集群（无状态 + LB） | 单机逼近 |
| 改动成本 | 低，兼容 Spring MVC / 拦截器 / 过滤器生态 | 高，重写接入层 |

> **结论**：「只能 web 容器」也能把单机从几千提到**几万连接、上万 QPS**，百万级靠**无状态集群**；核心不是换容器，而是**「容器内异步化（AsyncContext）+ 舱壁隔离 + 后端异步客户端」**。只有真要单机百万连接、极致吞吐时，才必须换 Netty。
