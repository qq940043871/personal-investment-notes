# 协议调用量探针机制设计（midservice）

> 目标：在现有协议调用链中引入**调用量探针**，精确统计各协议的调用次数与调用量（QPS），支持按协议/调用方/时间窗口查询展示，且对调用链路性能影响可控。
> 数据通道：Kafka（推荐）或 Redis 队列。
> 现状依据：`HandlerController.java` 已有监控雏形，本方案在其基础上补齐「发起前探针 + 本地聚合 + 异步批量上报」。

---

## 一、现状埋点分析（已有基础 + 四个局限）

### 1.1 现有调用链与埋点

```
HandlerController.execute 循环（每个协议一次）
  lockApi(token, api)                    // 712 行，发起前加锁
  startTime = now()                      // 714 行，计时开始
  isCacheApi 判断 → callable.call()      // 717~756 行，反射调用（发起/执行）
  unLockApi(token, api)                  // 761 行 finally
  doAuthRtn / done                       // 764~766 行
  endTime = now(); costTime = ...        // 872~873 行
  if (is.open.monitor=Y)                 // 876~887 行，现有监控上报
      redis.rpush("1018_MONITOR_DATA", {STARTTIME, ENDTIME, API, RESULT, MSG, COST_TIME, MACHINE_IP})
```

### 1.2 现有机制的四个局限

| 局限 | 说明 |
|---|---|
| **无「发起前」探针** | 只在响应返回后上报一次，无法统计「发起数 vs 完成数」「在途数」「超时未返回」 |
| **同步 rpush 阻塞** | `redis.rpush` 在调用线程内同步执行，高 QPS 下监控本身拖慢业务链路 |
| **维度单一** | 只有 API + 结果 + 耗时，缺**调用方（FIRM_ID/用户）、协议类型（connType）、缓存命中** |
| **明细而非聚合** | 一笔一条 rpush，量大后 Redis List 膨胀、消费压力大 |

## 二、探针埋点位置设计

### 2.1 埋点位置选型（关键：MCallable 是 `new` 出来的）

`HandlerController.java:744/754` 是 `new MCallable(...).call()` **直接 new 对象**，不是 Spring 注入 bean，所以 **Spring AOP（代理）切不到它**。因此：

| 方案 | 可行性 | 结论 |
|---|---|---|
| Spring AOP `@Around` 切 `MCallable.call()` | ❌ 切不到 new 出来的对象 | 不采用（除非改 Spring 管理或用 AspectJ LTW） |
| **手动埋点（execute 循环两处）** | ✅ 能拿到全部细节 | **主探针** |
| HandlerInterceptor（中间件拦截层） | ✅ 覆盖所有入口 | **兜底探针**（入口级 QPS，拿不到 connType/缓存细节） |

### 2.2 三个埋点

**① 调用发起前（主探针-前置）**：`HandlerController.java:714` `startTime` 处

```java
ApiMetricsProbe.incrStart(api_protocol, token.getFIRM_ID(), token.getUSERFLAG());
```

**② 响应返回后（主探针-后置）**：`HandlerController.java:872` `costTime` 计算后

```java
ApiMetricsProbe.incrFinish(api_protocol, costTime, success, cacheHit);
```

**③ 中间件拦截层（兜底）**：`HandlerInterceptor.preHandle / afterCompletion`

```java
// 统计入口级 QPS，覆盖「校验失败提前返回」等 execute 未走到的路径
preHandle:  MetricsProbe.entryIncr(path);
afterCompletion: MetricsProbe.entryFinish(path, ex == null);
```

> 主探针（①+②）负责「按协议的精确计数」，兜底探针（③）负责「入口级全量覆盖」，二者互补。

## 三、统计维度与数据模型

### 3.1 统计维度

| 维度 | 来源 | 说明 |
|---|---|---|
| **协议** | `api_protocol`（如 MT1100）、`api_name`、`conn_type`（0/1/2/3）、读/写分类 | 核心维度 |
| **调用方** | `FIRM_ID`（机构）、`USERFLAG`（1 个人/2 机构/3 第三方）、`tokenId`、IP | 定位调用来源 |
| **时间窗口** | 秒 / 分钟 / 小时 / 天 | 滚动聚合 |
| **结果** | 成功 / 失败 / 异常类型 | 成功率 |
| **缓存** | 命中 / 未命中 | 评估缓存收益 |
| **耗时** | count / sum / P50 / P95 / P99 / max | 性能分布 |

### 3.2 本地聚合结构（内存，O(1) 无锁）

```java
public class ApiMetricsProbe {
    // key = api_protocol，value = 分钟级分桶计数
    private static final ConcurrentHashMap<String, Window> METRICS = new ConcurrentHashMap<>();

    static class Window {
        final LongAdder count      = new LongAdder();  // 调用次数（发起数）
        final LongAdder success    = new LongAdder();  // 成功数
        final LongAdder fail       = new LongAdder();  // 失败数
        final LongAdder cacheHit   = new LongAdder();  // 缓存命中数
        final LongAdder costSum    = new LongAdder();  // 耗时总和（算均值）
        // 调用方维度：ConcurrentHashMap<firmId, LongAdder> 单独一层（按需）
    }

    public static void incrStart(String api, String firmId, int userFlag) {
        METRICS.computeIfAbsent(api, k -> new Window()).count.increment();
    }
    public static void incrFinish(String api, long cost, boolean ok, boolean hit) {
        Window w = METRICS.get(api);
        if (w != null) { (ok ? w.success : w.fail).increment(); w.costSum.add(cost); if (hit) w.cacheHit.increment(); }
    }
}
```

- **调用次数** = `count`（发起数）；**调用量（QPS）** = `count / 时间窗口`。
- 用 `LongAdder` 而非 `AtomicLong`：高并发下分散热点，几乎无竞争。

## 四、数据上报方式与聚合周期

### 4.1 核心原则：本地计数 + 异步批量上报（零阻塞主链路）

```
调用线程：incrStart/incrFinish → 纯内存 LongAdder（O(1)，无 IO 无锁竞争）
后台线程：ScheduledExecutor 每 30s 把窗口快照组装成批量消息 → 异步发送 → 清零换窗
```

### 4.2 Kafka vs Redis（推荐 Kafka）

| 通道 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **Kafka（推荐）** | 大流量、多消费者、可回溯、异步批量天然契合 | 需引入 Kafka 运维 | 生产高频场景 |
| Redis 队列 | 复用现有 `1018_MONITOR_DATA`，简单 | List 无限膨胀、消费端需及时拉取 | 小流量/过渡 |

**Kafka 消息（聚合后一条 = 一个时间窗的一个协议）**：

```jsonc
// topic: mid_api_metrics
{
  "window": "2026-10-24 10:00:00",   // 分钟窗
  "machine_ip": "10.0.0.1",
  "api": "MT1100", "api_name": "用户登录", "conn_type": 0,
  "firm_id": "F123", "user_flag": 2,
  "count": 1200, "success": 1190, "fail": 10,
  "cache_hit": 0, "cost_sum": 36000     // 均值 = 36000/1200 = 30ms
}
```

### 4.3 聚合周期

| 层 | 周期 | 说明 |
|---|---|---|
| 本地计数 | 实时（LongAdder 秒级累加） | 零成本 |
| 本地分桶 | 分钟级 | 按分钟滚动 |
| 上报 flush | **30s~60s**（可配） | 定时批量，一次发多协议 |
| 下游聚合 | 分钟 / 小时 / 天 | 消费端滚动 |

## 五、性能影响可控的保证

| 手段 | 说明 |
|---|---|
| **纯内存计数** | `LongAdder` 累加，无 IO、无锁竞争，单次耗时纳秒级 |
| **异步批量上报** | 独立后台线程 flush，不与调用线程共享；一条消息聚合一个时间窗 |
| **有界队列 + 丢弃** | 上报队列满了**丢弃监控消息**（监控可丢、业务不可受影响） |
| **独立开关** | 复用 `is.open.monitor`，新增 `is.open.metrics`（聚合探针）单独控制 |
| **采样降级** | 超高 QPS 时：100% 计数 + 1% 明细（耗时分布可采样） |

> 对比现状：现有 `rpush` 是**调用线程内同步**（每次调用一次 IO），新方案是**后台异步批量**（每 30s 一次 IO），对调用链路的性能影响从「每次微秒级 IO」降到「零阻塞 + 秒级批量」。

## 六、下游聚合与查询展示

```
Kafka(mid_api_metrics) → 消费端（Flink/Spark/Java 消费者）
  → 按 api/firm_id/时间窗口 聚合
  → 落存储（ClickHouse / ES / Redis Hash）
  → 查询展示
```

### 6.1 支持的查询（按协议维度）

| 查询 | 输出 |
|---|---|
| 协议 QPS 排行 | Top N 协议 + 调用量（QPS） |
| 协议调用趋势 | 指定协议按分钟/小时的 count 曲线 |
| 调用方分布 | 按 FIRM_ID / USERFLAG 的调用量占比 |
| 成功率 / 失败分布 | 指定协议成功/失败数、异常类型 |
| 耗时分布 | P50/P95/P99/max |
| 缓存命中率 | 命中/未命中占比（评估缓存改造收益） |

### 6.2 存储选型

- **ClickHouse**：海量时序计数，聚合查询快（推荐）。
- **Redis Hash**：`HINCRBY` 实时累加，短期窗口快速查询（轻量过渡方案）。

## 七、实施要点与风险

| 项 | 说明 | 应对 |
|---|---|---|
| **埋点侵入** | 在 `HandlerController.execute` 两处手动加一行 | 改动极小，封装成 `ApiMetricsProbe`，后续可切换 |
| **时钟/窗口对齐** | 多机上报，窗口需对齐 | 用分钟整点对齐（`window = ts / 60000 * 60000`） |
| **消息量** | 协议数 × 时间窗数，分钟级可控 | 聚合后消息量 = 活跃协议数 × 分钟数，远小于明细 |
| **丢失容忍** | 监控数据可容忍少量丢失 | 有界队列丢弃策略，保证不反压业务 |
| **与现有监控共存** | 现有 `1018_MONITOR_DATA` 明细 | 明细保留（低流量开），聚合探针为高频主通道 |

## 八、结论

在现有 `HandlerController.execute` 调用链上，用**「发起前 incrStart + 返回后 incrFinish」两个手动埋点 + 本地 LongAdder 聚合 + 每 30s 异步批量上报 Kafka**，即可实现：

1. **精确统计**各协议调用次数（发起数）与调用量（QPS）；
2. 维度覆盖**协议 / 调用方 / 时间窗口 / 结果 / 缓存命中 / 耗时**；
3. **性能零阻塞**——纯内存计数 + 异步批量，替代现有同步 rpush；
4. 下游消费 Kafka 落 ClickHouse/Redis，**按协议维度查询展示**调用量排行、趋势、分布、成功率、耗时。

## 九、明细通道（需要逐条明细时）

聚合方案解决「调用量统计」，但若业务要求**逐条明细**（审计、问题排查、精确分析），需单独设计明细通道。

### 9.1 明细 vs 聚合的本质区别

- 聚合可本地合并（`count++`），30s 上报一条；明细**无法合并，必须逐条上报**。
- 明细数据量 = QPS 条/秒：5 万 QPS = 5 万条/秒 = 43 亿条/天，这是「同步 rpush + SQLite」绝对扛不住的量级。

### 9.2 正确姿势：三件事

```
调用线程 → 本地有界队列（异步入队，零阻塞）
  → 后台批量消费者（攒批 1000 条 / 500ms）
  → Kafka(topic: mid_api_detail)
  → 消费端（midmon 或新消费者）
  → ClickHouse（明细落库 + 聚合查询）
```

| 环节 | 选型 | 说明 |
|---|---|---|
| 本地队列 | Disruptor / ArrayBlockingQueue | 异步入队，纳秒级，调用线程零 IO |
| 批量发送 | Kafka（producer 自带 `batch.size` + `linger.ms`） | 攒批降 IO |
| 存储 | **ClickHouse**（百万行/秒）/ Kafka 缓冲 / ES（全文搜）/ MySQL 分表 | SQLite 明确不行 |

### 9.3 关键决策：明细能不能丢

| 类型 | 例子 | 可否丢失 | 队列满策略 |
|---|---|---|---|
| 监控明细 | 调用量/耗时/结果 | 可容忍少量丢 | **丢弃** + 丢弃计数告警 |
| 审计明细 | `1018_APP_LOG` 安全审计 | **不能丢** | 阻塞 / 本地 WAL 兜底，恢复补传 |

### 9.4 结合 midmon 的务实演进

保留 midmon 框架，最小改动换两个组件：`Redis List → Kafka`、`SQLite → ClickHouse/MySQL 分表`；midmon 改为「批量消费 Kafka + 批量写入」。若明细量低，继续 Redis + SQLite 也需**批量事务 + SQLite 开 WAL**，否则单写者瓶颈依旧。
