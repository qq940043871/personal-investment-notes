## 二、本人核心选型复盘（真实参与）

### 2.1 平台底座：Dify vs 自研

| 维度 | Dify（低代码平台） | 自研（FastAPI + LangChain 等） |
|------|-------------------|------------------------------|
| 前期开发效率 | 可视化编排，出活快 | 需自建，前期慢 |
| 定制化能力 | 受平台能力约束 | 完全可控 |
| 数据与安全 | 需评估部署形态与数据边界 | 可完整内网化 |
| 运维成本 | 平台本身需维护 | 全栈自维护 |
| 团队适配 | 业务 / 非技术亦可用 | 依赖研发投入 |
| 与既有体系集成 | 需适配 | 可与 Java 后端深度集成 |

**本人的选型结论（判断，非落地结果）**：

- **前期验证 / 快速试错**阶段：可用 Dify 提速，先跑通链路；
- 涉及**涉密数据、深度定制、与既有 Java 后端体系集成**时：倾向**自研（或以自研为主 + 平台辅助）**；
- 实际项目中，本人负责该**选型对比与结论输出**（平台底座），后续落地由团队推进。

### 2.2 数据敏感度分层通道策略

**核心原则：数据敏感度决定模型通道。**

| 数据敏感度 | 通道 | 取舍 |
|-----------|------|------|
| 通用咨询 / 公开知识 | 第三方大模型 API | 能力强、成本可控；数据出境需评估 |
| 涉密 / 内部数据 | 内网私有化部署（vLLM 等候选） | 数据不出内网；牺牲部分能力与成本 |
| 混合场景 | 路由 / 脱敏后分流 | 敏感字段脱敏或本地处理 |

**判断依据**：数据是否出境、合规要求、能力要求、成本、时效。

**本人工作**：完成该**分层通道判断**；**未做生产级 vLLM / Ollama / Qdrant 部署**。

### 2.3 文档解析链路选型：MinerU（本人参与）

**选择理由**：把**多格式文档统一成结构化 Markdown**，降低下游向量化的格式耦合。

| 环节 | 选择 | 关注点 |
|------|------|--------|
| 文档解析 | MinerU | 多格式（PDF/Word/Excel/PPT/扫描件）→ Markdown，表格/公式/版面结构保真 |
| 分块与元数据 | 结构化分块 | 元数据可对齐，便于检索过滤 |
| 向量化与入库 | Embedding + 向量库 | 统一下游入库格式，减少格式差异耦合 |

**本人负责**：批量解析调度、失败兜底、下游入库格式衔接（详见 [`./02_商品知识库与智能检索.md`](./02_商品知识库与智能检索.md)）。

## 三、调研结论（供技术判断，非已落地）

### 3.1 基础模型调研

| 模型 | 提供商 | 适用场景 | 优势 | 劣势 |
|------|--------|---------|------|------|
| GPT-4o | OpenAI | 通用对话/复杂推理 | 能力强、生态完善 | 成本高、数据出境 |
| Claude 3.5 | Anthropic | 长文本处理/代码 | 长上下文、安全性强 | 国内访问受限 |
| 通义千问2.5 | 阿里云 | 中文对话/企业场景 | 中文强、合规好 | 能力中等 |
| Kimi (moonshot) | 月之暗面 | 长文本/搜索增强 | 200K上下文 | 生态较新 |
| DeepSeek-V3 | 深度求索 | 性价比方案 | 成本低、能力强 | 稳定性待验证 |
| Qwen2.5-72B | 阿里开源 | 本地部署 | 开源可私有化 | 需要算力 |
| Llama-3.1-70B | Meta开源 | 本地部署 | 完全开源 | 中文能力弱 |

### 3.2 Embedding 模型调研

| 模型 | 维度 | 特点 | 适用场景 |
|------|-----|------|---------|
| text-embedding-3-large | 3072 | OpenAI官方，效果好 | 通用场景 |
| BGE-M3 | 1024 | 中英双语、中文优化 | 跨境电商 |
| M3E | 768 | 开源免费、部署简单 | 成本敏感场景 |
| GTE | 1024 | 阿里开源、中文强 | 大宗商品 |
| SFund | 1024 | 金融领域优化 | 金融场景 |

### 3.3 向量数据库调研

| 数据库 | 优势 | 劣势 | 适用规模 |
|--------|------|------|---------|
| Milvus | 功能全面、社区活跃 | 运维复杂 | 亿级向量 |
| Qdrant | 性能高、部署简单 | 生态较新 | 千万级 |
| Elasticsearch | 既有ELK栈、可扩展 | 性能一般 | 已用ES团队 |
| Chroma | 轻量级、开发友好 | 不适合生产 | 原型验证 |
| Pinecone | 云原生、免运维 | 云服务、成本 | 快速上线 |

### 3.4 开发框架调研

| 框架 | 定位 | 优势 | 劣势 |
|------|------|------|------|
| LangChain | Agent开发框架 | 生态最全、文档多 | 复杂度高、迭代快 |
| LlamaIndex | RAG专用框架 | RAG场景优化 | Agent能力弱 |
| AutoGen | 多Agent协作 | 微软背书、代码生成强 | 上手难度高 |
| CrewAI | 多Agent编排 | 概念清晰、易上手 | 功能较新 |
| Dify | 低代码平台 | 可视化、部署简单 | 定制化受限 |

### 3.5 模型部署方案调研

| 方案 | 适用场景 | 性能 | 部署难度 |
|------|---------|------|---------|
| vLLM | 生产环境、高并发 | 最优 | 中等 |
| Ollama | 开发测试、快速验证 | 中等 | 简单 |
| TensorRT-LLM | 极致性能 | 最优 | 高 |
| Hugging Face TGI | 灵活部署 | 良好 | 中等 |
| FastChat | Chat模型部署 | 良好 | 简单 |

> 上表 3.1~3.5 均为**调研结论**，用于选型判断，**非本人已落地的生产配置**。

## 四、选型决策树（调研参考）

### 4.1 基础模型选型决策

```
业务场景 →
    │
    ├── 通用对话/智能客服
    │       └── 优先：通义千问 / Kimi（国内）
    │           次选：GPT-4o（出海业务）
    │
    ├── 复杂推理/代码生成
    │       └── 优先：GPT-4o / Claude 3.5
    │           次选：DeepSeek（性价比）
    │
    ├── 长文本处理/文档分析
    │       └── 优先：Kimi（200K上下文）
    │           次选：Claude 3.5
    │
    ├── 成本敏感/大用量
    │       └── 优先：DeepSeek / Qwen开源
    │           次选：GLM-4
    │
    └── 数据合规要求高
            └── 必须：通义千问 / 私有化部署开源模型
```

### 4.2 向量数据库选型决策

```
数据规模 →
    │
    ├── 小规模（<100万）
    │       ├── 快速上线 → Pinecone / Qdrant Cloud
    │       └── 开源自建 → Chroma / Qdrant
    │
    ├── 中等规模（100万~1亿）
    │       ├── 有运维团队 → Milvus
    │       └── 运维能力弱 → Qdrant / Elasticsearch
    │
    └── 大规模（>1亿）
            └── Milvus + 分布式集群
```

### 4.3 开发框架选型决策

```
团队技术栈 →
    │
    ├── Python为主
    │       ├── RAG场景 → LlamaIndex / LangChain
    │       ├── Agent场景 → LangChain / AutoGen
    │       └── 快速原型 → Dify / LangFlow
    │
    ├── 前后端分离团队
    │       ├── 后端用FastAPI + LangChain
    │       └── 前端对接API即可
    │
    └── 非技术团队
            └── Dify（低代码）+ 运维部署
```

## 五、技术组合设想（供参考，非本项目落地）

### 5.1 快速验证组合

适用于：POC验证、原型演示

```
技术栈（设想）：
• 模型：GPT-4o API / 通义千问 API
• RAG：Pinecone Cloud + LangChain

劣势：

✗ 有调用量限制
✗ 定制化受限
```

### 5.2 企业级组合（设想）

适用于：需要数据自主可控的正式环境

```
技术栈（设想）：
• 模型：通义千问（阿里云百炼）/ DeepSeek
• 部署：vLLM + GPU服务器
• RAG：Milvus + LangChain
• 前端：Vue3 / React
• 后端：Spring Cloud / FastAPI
• 监控：Prometheus + Grafana

优势：
✓ 数据自主可控

✓ 支持高并发

劣势：
✗ 运维成本高
✗ 需要专业团队
✗ 初期投入大
```

### 5.3 大规模生产组合（设想）

适用于：日活百万级、超大规模应用

```
技术栈（设想）：
• 模型层：混合部署（主力模型+小模型）
• 推理优化：TensorRT-LLM + vLLM
• RAG：Milvus集群 + 多级缓存
• 向量模型：BGE-M3 + Rerank
• Agent编排：LangChain + 自研调度
• 基础设施：Kubernetes + GPU集群
• 监控告警：全套可观测性

优势：
✓ 性能最优
✓ 可扩展性强
✓ 稳定性高

劣势：
✗ 开发周期长
✗ 团队要求高
✗ 成本最高
```

## 六、选型 Checklist

### 6.1 选型评估维度

| 维度 | 评估要点 |
|------|---------|
| 能力匹配 | 能否满足业务场景需求 |
| 成本 | API费用/硬件成本/运维成本 |
| 性能 | 响应速度/并发能力/准确率 |
| 安全合规 | 数据安全/隐私保护/合规要求 |
| 运维难度 | 部署复杂度/监控告警/容灾备份 |
| 团队能力 | 学习曲线/人员储备 |
| 生态支持 | 社区活跃度/技术支持/更新频率 |

### 6.2 常见坑点

```
⚠️ 模型能力
• 不要只看基准测试，要实际评估业务场景
• 长上下文不等于长记忆，需要配合其他机制
• 国产模型中文能力强，但代码/英文场景可能弱

⚠️ 成本
• API调用成本容易被低估，要有计量和告警
• GPU服务器不只是购买成本，电费和运维是大头
• 开源模型需要大量调优，人力成本不可忽视

⚠️ 性能
• 向量数据库QPS不只取决于模型，召回率同样重要
• Embedding模型选择比向量数据库更重要
• 大模型推理首token延迟比总延迟更影响体验

⚠️ 合规
• 数据出境问题必须提前评估
• 开源模型可能有许可限制（Llama系列限制商用）
• 内容安全审核不可省略
```
