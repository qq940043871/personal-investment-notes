# CI/CD 建设方案 与 Code Review 规范

> **定位**：面向"客户交付型"研发团队的工程效能建设方案，从现状（无 CI/CD、全人工接力）到目标态（规范 + 门禁 + 自动化交付）的分阶段演进路径。
> **适用场景**：B 端/政企项目交付，需求批量交付、客户现场部署、客户环境不可控、发布频率低但单次发布风险高。
> **作者角色**：技术经理（部门规范、技术规范、CI/CD 体系制定者）

---

## 一、先校准目标：这类团队要的 CI/CD 是什么

客户交付型研发的 CI/CD 走自己的模型（区别于互联网"一天发布十次"），目标是四件事：

| 目标 | 含义 | 改造前现状 |
|---|---|---|
| **质量前移** | 缺陷在提交阶段暴露，而不是在检测/客户现场暴露 | 靠多轮人工测试兜底 |
| **交付可重复** | 同一个版本号，任何人任何时间构建出的包一致 | 谁打包谁清楚，换人就要重来 |
| **发布可追溯** | 客户现场的包能反查到 commit、需求、缺陷、检测结论 | 版本库里只有"程序"，无对应关系 |
| **失败可回滚** | 升级失败能在客户现场快速退回上一版本 | 升级靠手工，回滚无预案 |

> **判断标准**：不是"有没有流水线"，而是"**质量是否还取决于某个人的状态**"。

## 二、现状梳理（As-Is）

### 2.1 现有流程

| # | 阶段 | 主责 | 产出 | 现状问题 |
|---|---|---|---|---|
| 1 | 客户反馈需求 → 产品多轮迭代 | 产品经理 | 需求文档 + 原型 | 技术介入晚，原型定稿即事实需求 |
| 2 | 产品价值表评审 | 产品/业务 | 评审结论 | 只有业务价值，无技术成本口径 |
| 3 | 开发排期 | 技术经理 | 排期表 | 依赖个人经验估算，无历史基线 |
| 4 | 设计文档（按任务大小决定是否写）→ 评审 | 开发 | 设计文档 | **"要不要写"是主观判断，最容易失控** |
| 5 | 开发 + 单元测试 | 开发 | 代码 + 单测 | 单测覆盖无门槛，质量靠自觉 |
| 6 | 多轮测试 + 测试人员跟测 | 测试/开发 | 缺陷记录 | 无准出标准，靠"感觉收敛" |
| 7 | 提交到隔离检测环境 → 检测人员检测 | 检测 | 检测报告 | 人工全量回归，是交付瓶颈 |
| 8 | 填发布单 → 发版到公司程序版本库 | 开发 | 发布单 + 程序包 | 发布单手工填，版本与源码无绑定 |
| 9 | 运维取程序 → 升级 → 验证 → 交付客户 | 运维 | 客户可用版本 | 手工升级，无灰度、无回滚脚本 |

### 2.2 六个断点（改造靶点）

1. **需求阶段缺技术前置**——可行性判断发生在写代码时，返工成本最高。
2. **设计文档靠主观判断**——"任务大小"没有量化定义，等于没有规则。
3. **提测无门禁**——单测、扫描都不构成准入条件，测试成了质量第一道防线。
4. **测试无准出标准**——多轮测试但没有"什么条件下可以停"的定义。
5. **检测环节纯人工**——重复回归消耗人力，且无法保证一致性。
6. **制品与源码脱钩**——版本库只是"存放处"，不是可追溯的制品库，回滚无依据。

## 四、分阶段演进路线（L1 → L4）

### 4.1 四级台阶

| 级别 | 建什么 | 前提条件 | 验收标志 | 周期 |
|---|---|---|---|---|
| **L1 可重复构建** | 分支规范；一条命令构建出与 commit 严格对应的包；依赖版本锁定 | 代码全在 Git（含前端、脚本、SQL、配置模板） | 任意历史 commit 都能构建成功 | 2–3 周 |
| **L2 CI 门禁** | 触发即执行：编译 → 静态扫描 → 单测 → 制品归档 | 有可跑的核心单测；有扫描工具 | 不绿不许提测；制品带版本号入库 | 3–6 周 |
| **L3 检测环境自动化** | 自动部署检测环境 + 自动化冒烟/接口回归 + 自动检测报告 | 部署脚本化；有 30–50 条核心用例 | 检测人力从全量回归转业务验收 | 6–10 周 |
| **L4 交付闭环** | 发布单自动生成 → 制品库 → 运维一键升级/回滚 | 有标准发布单元（包+配置+升级+回滚脚本） | 发布可追溯、失败可回滚 | 持续 |

> **顺序不可颠倒**：先 L2 再 L3。很多团队先做自动部署，结果产物本身不可信，自动化只是把不合格的包更快地发出去。

### 4.3 必须先补的三个缺口

| 缺口 | 具体做法 | 为什么优先 |
|---|---|---|
| 制品与源码绑定 | 制品名 `应用名-版本号-commit短哈希-构建时间`；入库附构建清单（commit、分支、需求/缺陷号、构建人） | 没有这层对应关系，CI/CD 无从谈起，回滚也无依据 |
| 部署脚本化 | 开发把升级步骤写成脚本：建表/改配置/启停/健康检查 | CI/CD 的真实成本不在流水线，在"部署靠人手" |
| 自动化用例最小集 | 挑 30–50 条"挂了客户就会投诉"的接口/冒烟用例 | 是 L3 的核心资产，不求覆盖率，求关键路径 |

## 五、CI 流水线设计

### 5.1 Stage 与门禁

| Stage | 内容 | 失败处理 | 责任人 |
|---|---|---|---|
| 1 构建 | 编译通过、依赖可解析、产物可生成 | **阻断**，禁止提测 | 提交人 |
| 2 静态扫描 | 空指针/资源泄漏/硬编码密钥/SQL 拼接/圈复杂度 | P0 阻断，P1 记录限期整改 | 提交人 |
| 3 单元测试 | 核心模块覆盖阈值 + 全绿 | **阻断** | 提交人 |
| 4 制品归档 | 打包 → 版本号 → 入制品库 → 生成构建清单 | **阻断** | 流水线 |
| 5 变更登记 | 自动汇总本次提交涉及的需求号/缺陷号 | 提示（缺失则发布单阻断） | 提交人 |

### 5.2 门禁阈值（起始值，后续按数据调整）

| 指标 | 起始阈值 | 12 个月目标 |
|---|---|---|
| 核心模块单测覆盖率 | ≥ 30% | ≥ 50% |
| 单测通过率 | 100% | 100% |
| 静态扫描 P0 问题 | 0 | 0 |
| 静态扫描 P1 问题 | 不新增（增量管控） | 存量清零 |
| 构建成功率 | ≥ 95% | ≥ 98% |
| 单次 CI 时长 | ≤ 10 分钟 | ≤ 8 分钟 |

> 门禁原则：**人工会忘的交给流水线；流水线能判的不写进规范文档。**

### 5.3 分支与触发策略

| 分支 | 触发 | 门禁强度 |
|---|---|---|
| `feature/*` | 每次 push | 构建 + 扫描（快速反馈） |
| 合并请求 → `develop` | MR 创建/更新 | 全量：构建+扫描+单测+归档 |
| `release/*` | 打 tag | 全量 + 制品正式入库 |
| `master/main` | 合并 | 全量 + 自动生成变更清单 |
| `hotfix/*` | 每次 push | 全量（不得降级） |

## 六、CD 与交付流水线设计

### 6.1 检测环境（L3）

| Stage | 动作 | 门禁 |
|---|---|---|
| 部署 | 拉指定制品 → 执行升级脚本 → 健康检查（端口/依赖/关键接口） | 健康检查失败自动回滚到上一版本 |
| 冒烟 | 核心链路 30–50 条用例 | 100% 通过 |
| 接口回归 | 关键接口断言（状态码/关键字段/业务不变量） | 100% 通过 |
| 报告归档 | 自动生成检测环境验证报告（版本/用例/结果/耗时） | — |
| 交接 | 通过后通知检测人员做业务验收 | 未通过不进入人工检测 |

### 6.2 发布与交付（L4）

| 环节 | 自动化内容 | 人工只做 |
|---|---|---|
| 发布单 | 自动汇总：变更清单 + 制品版本 + 检测报告 + 回滚版本号 + 影响范围 | 审批签字 |
| 制品入库 | 制品 + 构建清单 + 检测报告 三者绑定入库 | 抽检 |
| 客户升级 | 运维按发布单取指定版本 → 升级脚本 → 验证脚本 | 现场确认与沟通 |
| 回滚 | 回滚脚本 + 上一版本制品随时可取 | 决策是否回滚 |

### 6.3 制品命名与目录规范

```
{应用名}-{版本号}-{commit前7位}-{yyyyMMddHHmm}.zip
例：order-service-2.3.1-a1b2c3d-202610221430.zip

制品库目录：
  /release/{应用名}/{版本号}/    ← 正式发布件
  /snapshot/{应用名}/{版本号}/   ← 检测/预发件
  每个目录必须含：制品包、构建清单(build-info.json)、检测报告(test-report.pdf)
```

## 七、工具选型（内网/离线环境）

| 用途 | 推荐方案 | 说明 |
|---|---|---|
| 代码仓 + 流水线 | **GitLab CE + Runner** | 代码、MR、CI、包registry 一体，最适合中小团队；一次内网部署到位 |
| 纯流水线引擎 | Jenkins | 灵活但插件维护成本高；已有 GitLab 时不必引入 |
| 制品库 | Nexus 或 GitLab Package Registry | **必须独立于"程序版本库"**；版本库只存已发布件 |
| 静态扫描 | SonarQube CE | 质量阈可配，天然适合做门禁 |
| 自动化用例 | Postman/Newman（接口）+ JMeter（已有压测能力可复用） | 先接口层，UI 自动化后续再上 |
| 部署编排 | Ansible / Shell 脚本 | 客户环境不可控，脚本比容器编排更现实 |
| 离线环境 | 离线镜像 + 私有镜像仓库 + 离线插件包 | 内网落地的最大工作量在此，须提前准备 |

> **容器化建议**：客户现场多为物理机/虚拟机，先做到"脚本化部署"，容器化作为后续独立议题推进。

## 八、90 天落地计划

| 周次 | 目标 | 交付物 | 验收 |
|---|---|---|---|
| W1–W2 | 选 1 个在研项目做样板；梳理代码仓与构建方式 | Git 分支规范、依赖锁定 | 任意历史 commit 可构建 |
| W3–W4 | 制品命名与构建清单；部署脚本化 | 制品规范、升级/回滚脚本 | 一键部署到检测环境 |
| W5–W6 | 搭 GitLab Runner + Sonar；CI 第一阶段（构建+扫描） | CI 配置文件、扫描质量阈 | 提交即出结果 |
| W7–W8 | 补核心单测；接入单测与制品归档；**试运行门禁（只告警不阻断）** | 单测基线报告 | 误报率可接受 |
| W9–W10 | 门禁转强制；30 条冒烟/接口用例落地 | 自动化用例库 | 不绿不提测执行 |
| W11–W12 | 检测环境自动部署 + 报告自动生成；发布单模板自动组装 | CD 流水线、发布单模板 | 检测周期可对比 |
| W13 | 复盘 → 固化为部门规范；复制到第 2 个项目 | 《CI/CD 使用规范》《发布规范》 | 第二个项目独立跑通 |

> **节奏要点**：先样板验证 → 再定门禁 → 最后写规范。让规范是"已验证的实践"，而不是纸面要求。

## 九、Code Review 规范

### 9.1 作用（四个维度）

| 作用 | 具体体现 | 价值 |
|---|---|---|
| **缺陷前移** | 评审期修复成本约为测试期的 1/5、线上/客户现场的 1/20 | 用最低成本换质量 |
| **规范落地** | 编码/接口/异常/日志规范真正被执行 | 规范有人检查才有效 |
| **知识扩散** | 每段代码至少 2 人理解，降低单点依赖与交接风险 | 团队韧性 |
| **架构一致性** | 防止"每人一套写法"，避免系统熵增 | 长期可维护性 |

> 最容易被忽略的第五个作用：**Review 是技术标准最有效的传递方式**。技术经理的架构意图，靠文档传达效率最低，靠评审评论传达效率最高。

### 9.2 触发条件与粒度

| 项 | 规定 |
|---|---|
| 触发 | 所有合并到 `develop`/`master` 的代码必须经评审；`hotfix` 后补评审（≤24h 内） |
| 单 PR 规模 | **≤ 400 行有效变更**，超出必须拆分（超 400 行后评审质量显著下降） |
| 评审人数 | 1–2 人：模块负责人 + （关键改动）技术经理 |
| 首轮反馈 | ≤ 24 小时，超时自动提醒 |
| 顺序 | 作者自查 → CI 通过 → 人工评审 → 合并。**CI 未过不启动人工评审** |
| 豁免 | 纯配置/文案/依赖版本调整，可由模块负责人单人快速审（仍不可跳过） |

### 9.3 审什么（按优先级分配注意力）

| 优先级 | 维度 | 典型问题 |
|---|---|---|
| **P0 必须挡** | 正确性 | 边界条件、空值、并发、事务边界、幂等、异常被吞、循环内查库 |
| **P0 必须挡** | 安全 | SQL 拼接、越权（缺权限校验）、敏感信息落日志、文件上传校验、硬编码密钥 |
| **P1 重点议** | 设计 | 职责是否单一、是否重复造已有能力、扩展点在哪、是否过度设计 |
| **P1 重点议** | 兼容性 | 接口/表结构变更是否影响存量客户、字段能否兼容、发布顺序是否安全 |
| **P2 建议改** | 可维护性 | 命名、函数过长、魔法值、注释只写"是什么"不写"为什么"、日志缺 traceId |
| **P3 忽略** | 代码风格 | **能被格式化/静态扫描解决的，一律不进人工评审** |

### 9.4 评论分级（消除无效争论）

| 标记 | 含义 | 是否阻塞 |
|---|---|---|
| `[blocking]` | 必须改，否则不合入 | 是 |
| `[suggest]` | 建议改，作者可自主决定 | 否 |
| `[question]` | 求解释，不一定改代码 | 否 |
| `[nit]` | 细节，可不改 | **否（硬规定）** |

> 规定 `[nit]` 不得阻塞合并，能消掉团队约 80% 的评审摩擦。

### 9.5 评审流程（6 步）

1. **提交前自查**：作者对照检查清单自评，减少低级评论。
2. **CI 先过**：构建/扫描/单测不绿，不进入人工评审。
3. **描述结构化**：改了什么、为什么改、影响范围、如何验证（缺这三项直接退回）。
4. **评审人分工**：一人主看正确性与实现，技术经理看设计与兼容性。
5. **评论分级**：按 9.4 标注，避免"所有意见都同等重要"。
6. **结论明确**：Approve / Request changes / Comment（不表态不算通过）。

### 9.6 检查清单（可直接作为模板）

**通用**

- [ ] 变更范围与描述一致，无夹带无关改动
- [ ] 无调试代码、注释掉的代码、临时开关残留
- [ ] 异常处理完整：不吞异常、不空 catch、错误有日志与上下文
- [ ] 日志级别合理，含关键业务标识（订单号/客户号/traceId），不含敏感信息
- [ ] 无硬编码（地址、账号、密钥、阈值）

**Java/后端**

- [ ] 入参校验（非空/长度/枚举/范围）齐全，不信任前端
- [ ] 事务边界正确：跨服务调用不在事务内、事务内不做远程 IO
- [ ] 并发安全：共享可变状态、单例成员变量、缓存更新顺序
- [ ] 幂等：重复提交/重试/消息重投是否会重复扣款、重复发货
- [ ] 数据库：索引是否命中、有无全表扫描、是否有 N+1 查询
- [ ] 分页与批量：无 `select *`、批量大小有上限
- [ ] 接口兼容：新增字段可空、不修改语义、保留旧字段过渡期

**数据库变更**

- [ ] 变更脚本可重复执行（幂等 DDL/DML）
- [ ] 大表变更评估锁表时间与执行窗口
- [ ] 有对应回滚脚本，且回滚已被验证
- [ ] 与代码发布顺序兼容（先加字段→发代码→再删旧字段）

**前端**

- [ ] 接口异常/空数据/超时均有兜底 UI
- [ ] 关键操作防重复提交；权限按钮受控
- [ ] 无敏感信息写入 localStorage；无 XSS 风险点（`v-html`/`innerHTML`）

**测试**

- [ ] 新增/修改逻辑有对应单测，关键分支被覆盖
- [ ] 单测断言有效（不是只跑通不断言）

### 9.7 度量（只测过程，不测个人）

| 指标 | 健康参考 | 说明 |
|---|---|---|
| 评审覆盖率 | 100% | 主干分支强制 |
| 首轮反馈时长 | ≤ 24h | 反映团队节奏 |
| 单 PR 中位规模 | ≤ 300 行 | 规模过大必然低质 |
| 缺陷来源占比（Review） | 逐季上升 | 说明缺陷前移生效 |
| 合入后返工率 | 下降 | 评审有效性的反向指标 |

> **禁止**用"评论条数/评审速度"考核个人，会直接退化为敷衍式评审（LGTM）。

### 9.8 常见反模式

| 反模式 | 后果 | 对策 |
|---|---|---|
| 橡皮图章（只回 LGTM） | 评审形同虚设 | 必须有至少 1 条实质性意见或明确"已审无问题" |
| 变成风格争吵 | 消耗信任 | 风格交给工具，评审聚焦设计与边界 |
| 超大批量评审 | 漏看关键逻辑 | 单 PR ≤ 400 行强制拆分 |
| 只有技术经理在审 | 成为瓶颈、团队不长能力 | 培养模块 owner，技术经理只审关键改动 |
| 设计问题拖到代码评审 | 返工成本高 | 设计评审阶段解决，代码评审不纠正架构 |
| 评审即返工全推倒 | 作者抵触 | 分级评论，明确"必须改"与"可讨论" |

## 十、三层落地关系（这套体系为什么成立）

```
第一层  规范文档层   部门规范 / 技术规范 / 发布规范
        └─ 作用：定义标准与边界，解决"应该怎样"
                 ↓ 能被工具检查的，全部下沉
第二层  工具门禁层   CI 门禁 + CD 自动检测 + 制品库
        └─ 作用：强制执行，解决"必须怎样"
                 ↓ 工具判不了的，交给人
第三层  人工评审层   Code Review + 设计评审 + 价值评审
        └─ 作用：判断设计与业务语义，解决"是否合理"
```

> **核心结论**：规范如果不能被工具强制，就只是文档；工具如果没有人审设计，就只能挡住低级问题。三层缺一层，体系就会退化成形式主义。
