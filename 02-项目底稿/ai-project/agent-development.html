智能体开发

Agent Development — Workflow 保确定性，Agent 补开放环节；工具调用一律过中台网关

底座 · 能力封装 确定性优先 写操作人工确认

口径声明：本页描述的是智能体的设计原则与边界。个人未承担智能体编排落地（由团队推进）；此处讲的是「为什么这样设计」，不是「我写了这些工作流」。

一、智能体在平台里到底干什么

一句话：把多步骤流程串成一次可执行的任务——查数 → 判断 → 调用 → 写回。它解决的不是「答得更聪明」，而是「把跨系统的动作接起来」。

拆不掉的多步

「查这个客户的合同 → 看有没有逾期 → 有则生成催办」这类任务，单轮问答模型做不了。

要跨系统

数据在交易、合同、仓单、结算不同服务里，需要工具调用而不是检索。

但要能被管住

自主性越强，越需要鉴权、只读优先、写操作确认、全程留痕。

二、Workflow 与 Agent 的分工：确定性优先

Workflow · 关键路径

步骤已知、顺序确定、必须可解释可回滚。

  • • 政策解读主链路（规范化 → 意图 → 槽位 → 直击 → 检索 → 生成 → 核验）
  • • 智能客服的知识类/数据类分流
  • • 输出前终检与降级判定

好处：每一步看得见、错在哪查得到、改一处不影响别处。

Agent · 开放环节

步骤不确定、需要模型自己决定「先查什么、再查什么」。

  • • 检索策略选择（该查知识库还是查单据）
  • • 多工具编排（一次没查到时换个条件再查）
  • • 追问与澄清

代价：不可预测，必须配套超时、最大步数、失败退出条件。

为什么不全用 Agent？因为业务要的是「确定性可解释」。关键路径交给 Agent，等于把一条资金/合规链路交给概率——今天对明天错，还说不清为什么。Workflow 保确定性与可解释，Agent 补开放性，这个组合不是保守，是必要。

三、工具怎么接：四类工具，四种权限

工具类型 例子 管控要求
只读查询按单号查合同、查物流进度、查账户余额鉴权到人（身份级别 L1/L2/L3）+ 结果脱敏
写操作创建工单、提交催办、修改资料必须人工确认；幂等键防重复提交
外部系统ERP / OA / CRM / BPM 接口经中台统一收敛：鉴权、限流、熔断、对账兜底
人工节点审批、复核、异常处置HITL 显式插入点，不允许「模型自己决定跳过」

四、四条安全约束（写进架构规范）

权限校验永远在中台侧。不把数据过滤责任交给 Prompt——「请不要说其他客户的数据」不是权限。

不直连业务数据库。只通过中台暴露的受控工具/API 访问，这是硬约束不是建议。

工作流内不写复杂业务逻辑。只做路由、拼装、调用与格式化；事务与补偿留在中台。

写操作默认加人工确认。只读优先；LLM 调用不具备 ACID，写操作的事务边界不在模型手里。

五、失败与降级：Agent 必须有的退出条件

失败形态 兜底动作
工具调用超时限次重试 → 仍失败则降级为「告知 + 转人工/建工单」，不空转
反复查不到最大步数 / 最大时长硬上限，到点退出并如实告知
越权请求中台侧直接拒绝，不把拒绝理由与库内组织信息暴露给用户
写操作重复提交幂等键 + 人工确认双重保险，避免重复下单/重复建单

边界：多智能体协作（多个 Agent 互相委派）被排在阶段四——前三个阶段的价值没被度量之前，它只是烧钱又难排查的复杂度。这条与「微调」同属「先证明再上」的清单。
