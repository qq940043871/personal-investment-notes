模型微调

Model Fine-tuning — 非必选项：只在效果瓶颈明确时才上，否则纯烧钱

底座 · 可选项 标注集即训练集 不做算法创新

口径声明：本页是方案设计，不是个人交付记录。个人未承担微调训练执行；此项在平台中定位为「效果瓶颈明确时的可选项」，由团队按阶段四推进。

先立规矩：微调是最后一张牌，不是第一张。

绝大多数「效果不好」的真实原因是解析质量差、分块不合理、检索没做混合、Prompt 没约束。这些没解决就上微调，等于花几万块把一个错误的输入喂得更熟练——而且从此要养一套训练流水线。

一、决策顺序：先排查，再微调

第 1 步
解析对不对

源文档进向量库的 Markdown 是否干净？

第 2 步
召回得到吗

正确分段在不在 TopK 里？混合检索开了吗？

第 3 步
Prompt 约束够吗

强制 schema、强制引用、温度设了吗？

第 4 步
评测集有吗

没有评测集，「变好了」无从证明。

第 5 步
才轮到微调

且必须是「风格/格式/领域术语」类问题，而不是知识缺失。

关键区分：微调擅长「怎么说」（风格、格式、术语、稳定输出结构），不擅长「说什么」（事实与知识）。知识类问题应该用 RAG 解决——把文档塞进参数里，既贵又容易过期。

二、五步流程

阶段 做什么 容易翻车的地方
① 数据准备从标注集与真实会话里整理「输入 → 期望输出」样本，清洗、去重、划分训练/验证拿模型自己生成的答案当训练数据（自举污染）
② 配置选基座、LoRA 秩与学习率、轮数、序列长度样本量不足就全参微调，直接过拟合
③ 执行训练任务与日志、断点续跑、显存与时长控制没有固定随机种子与版本号，结果无法复现
④ 评估在同一套回归集上与基座对比：格式合规率、拒答率、关键字段准确率只看「感觉更顺了」，不做对照
⑤ 部署与回滚新模型以独立端点上线，灰度量；保留旧端点随时切回直接覆盖线上模型，出问题没有退路

三、代价与收益要对得上

要付的代价

  • • GPU 与人工成本，且要持续维护训练流水线
  • • 知识更新不再「改文档」，而是「重训一次」
  • • 版本管理复杂度上升：模型版本 × Prompt 版本 × 知识库版本

什么时候值得

  • • 输出结构必须严格稳定（固定字段的抽取、分类、话术模板）
  • • 领域术语多、通用模型总说外行话
  • • 私有化小模型效果不够，又不能用公有云
  • • 高频任务，微调后可降级到更小模型跑，长期省成本

顺序纪律：平台落地四阶段里，微调排在阶段四——前提是前三阶段的价值已被度量并认可。反过来做，很容易在打通与训练上耗掉全部预算，一个价值都没证明。
