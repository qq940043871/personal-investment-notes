# B2B电商架构方法论

> 基于大宗贸易供应链实战经验的方法论沉淀。面向技术经理/架构师的决策框架，不是代码实现指南。

---

## 前言：B2B电商为什么需要独立的架构方法论

大多数架构师的第一反应是"电商架构我熟"——然后他们会发现，B2B的世界和B2C完全不是一回事。

B2C电商的架构范式（秒杀、推荐、购物车、统一定价）在B2B场景下几乎全部失效。你不是在做一个"更大的淘宝"，你是在做一个**企业间的交易操作系统**。

本方法论回答三个核心问题：
1. **B2B电商和B2C电商的本质差异是什么？**——决定技术选型的前提
2. **B2B电商的核心架构模式有哪些？**——可复用的设计决策
3. **如何向面试官/CTO/投资人说清楚你做的东西？**——叙事框架

---

## 第一章：B2B vs B2C 六大维度本质差异

架构设计的第一步，是理解业务本质。以下六个维度的差异，直接决定了技术架构的走向。

### 1.1 交易主体

| 维度 | B2C | B2B |
|------|-----|-----|
| 买家身份 | 个人消费者 | 企业法人/机构 |
| 账号体系 | 单一用户 | 多层级企业账户（管理员+采购员+审批人+财务） |
| 认证方式 | 手机号/邮箱 | 营业执照+法人认证+对公账户验证 |
| 决策链 | 个人决策 | 多角色审批链（询价→审批→下单→付款） |

**架构影响**：RBAC（基于角色的访问控制）从"可选功能"变为"核心设计"。你需要一个完整的企业账户体系，不是一个加了`role`字段的用户表。

### 1.2 交易模式

| 维度 | B2C | B2B |
|------|-----|-----|
| 交易流程 | 浏览→加购→支付→发货 | 询价→报价→合同→订单→发货→签收→对账→结算→开票 |
| 交易周期 | 分钟级 | 天到周级 |
| 交易频次 | 高频小额 | 低频大额 |
| 定价方式 | 统一售价 | 协议价/阶梯价/信用价/基差点价/期货升贴水 |
| 库存策略 | 实物库存 | 在途库存+预售+信用额度库存 |

**架构影响**：价格不是一张表能解决的，你需要价格引擎。订单不是CRUD，你需要状态机。库存不是简单的加减，你需要多维度库存模型。

### 1.3 履约体系

B2C的履约 = 快递。B2B的履约 = 一套完整的供应链操作系统。

```
B2C履约链路: 下单 → 仓库发货 → 快递 → 签收 → 完成
B2B履约链路: 下单 → 备货 → 质检 → 物流调度 → 在途跟踪 →
             签收 → 质检确认 → 对账 → 结算 → 开票 → 完成
```

**架构影响**：履约不是订单的一个"物流状态"字段，而是一个独立的子系统。你需要处理分批发货、部分签收、质量异议、退货退款、账期结算——每一个节点都可能回退或分支。

### 1.4 数据复杂度

| 维度 | B2C | B2B |
|------|-----|-----|
| 商品数量 | 百万到亿级SKU | 千到万级SPU |
| 单商品复杂度 | 低（品牌+规格） | 高（多规格/多单位/产地/品质/交割标准） |
| 订单数据量 | 亿级（高并发） | 十万到百万级（低并发） |
| 单订单复杂度 | 低（几行） | 极高（合同+附件+审批+多行明细） |
| 价格数据 | 单一价格 | 多维度价格矩阵 |

**关键洞察**：B2B的挑战不是"高并发"，而是"高复杂度"。你的技术瓶颈不在QPS，而在状态一致性和数据准确性。

### 1.5 外部对接

B2C电商的生态相对封闭（支付宝/微信+快递公司），B2B则是开放生态：

- 银行对接：银企直连、电子回单、资金归集
- 税务对接：电子发票、税务申报
- 物流对接：仓储系统(WMS)、运输系统(TMS)
- 风控对接：企业征信（企查查/天眼查）
- 期货对接：行情数据、期现结合
- 供应链金融：保理、质押、信用融资
- 监管对接：行业监管平台数据上报

**架构影响**：你的系统不是孤岛，而是一个**生态连接器**。防腐层（Anti-Corruption Layer）不是可选项，是必选项。

### 1.6 业务规则复杂度

B2C的规则简单（满减/优惠券/包邮），B2B的规则是**真正的业务逻辑**：

- 客户准入规则（注册资金/经营年限/行业资质）
- 信用额度规则（动态额度/保证金/担保）
- 定价规则（客户级别+采购量+付款方式+提货方式）
- 合同条款规则（质量标准/违约金/不可抗力）
- 结算规则（账期/折扣/费用分摊）

**架构影响**：你需要一个规则引擎，而不是hard-code的业务逻辑。

## 第二章：B2B电商核心业务架构

### 2.1 领域划分

B2B电商的核心领域模型：

```
┌─────────────────────────────────────────────────────────────────┐
│                        B2B电商核心领域                            │
├───────────┬───────────┬───────────┬───────────┬───────────────────┤
│  客户中心  │  商品中心  │  交易中心  │  履约中心  │   结算中心        │
├───────────┼───────────┼───────────┼───────────┼───────────────────┤
│ 企业信息   │ SPU管理   │ 询价报价   │ 订单管理   │  信用/额度        │
│ 多级账户   │ 品类体系   │ 合同管理   │ 发货签收   │  账期管理         │
│ 认证签约   │ 多规格/单位│ 撮合匹配   │ 物流跟踪   │  对账核销         │
│ 信用评估   │ 价格体系   │ 订单管理   │ 质量异议   │  发票管理         │
│ 会员等级   │ 库存管理   │ 审批流程   │ 退货退款   │  资金归集         │
└───────────┴───────────┴───────────┴───────────┴───────────────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
   ┌────┴────┐          ┌────┴────┐          ┌────┴────┐
   │ 风控中心 │          │ 规则引擎 │          │ 生态网关 │
   │ 企业征信 │          │ 定价规则 │          │ 银行对接 │
   │ 交易风控 │          │ 审批规则 │          │ 物流对接 │
   │ 反欺诈  │          │ 合同模板 │          │ 税务对接 │
   └─────────┘          └─────────┘          └─────────┘
```

### 2.2 价格中心的复杂度——B2B架构的第一个试金石

B2B的价格模型是区分"做过B2B"和"没做过B2B"的最佳话题。

**价格维度矩阵**：

| 价格类型 | 举例 | 适用场景 |
|---------|------|---------|
| 基准价 | 挂牌价、指导价 | 所有客户可见的公开展示价 |
| 协议价 | 年度框架协议价 | 大客户签订年度合同后的专属价 |
| 阶梯价 | 100吨以下5000，100-500吨4900，500吨以上4750 | 按采购量自动分段 |
| 信用价 | 现款4950，30天账期5000，60天账期5050 | 付款方式影响价格 |
| 基差点价 | 期货价+升贴水 | 期现结合的大宗商品定价 |
| 区域价 | 华南+50，华北+80 | 物流成本差异 |
| 渠道价 | 经销商价、终端价 | 不同渠道类型不同价格 |

**设计决策**：
- 是否做独立的价格中心？——建议是。价格逻辑与商品/订单解耦。
- 价格优先级如何确定？——协议价 > 阶梯价 > 基准价，越"专属"越优先。
- 历史价格如何追溯？——每次下单记录快照，而不是查当前价格。

### 2.3 交易中心——从询价到合同的全链路

B2B交易的完整链路：

```
询价 → 报价 → 协商 → 合同 → 订单 → 履约 → 结算
  │      │      │      │      │
  └── 多轮次 ──┘      │      │
                └── 审批链 ──┘
```

**撮合引擎设计**（这是你的核心竞争力）：

撮合引擎不等于"撮合交易"——它可以是多种模式：
- **挂牌撮合**：卖方挂牌，买方选购（类似京东模式）
- **竞价撮合**：买方出价，卖方竞争（类似拍卖）
- **匹配撮合**：买卖双方互不可见，系统按规则匹配
- **协商撮合**：意向匹配后进入人工/系统辅助协商

**架构核心问题**：
- 撮合引擎用内存还是数据库？——高频用内存（你的C引擎），低频用数据库
- 撮合结果如何保证不丢失？——内存撮合 + 异步落库 + 消息队列兜底
- 部分成交如何处理？——撮合引擎需支持"部分匹配"语义

### 2.4 履约中心的架构难点

履约看起来是"发货→签收"，但实际上有大量异常分支：

```
正常履约：下单 → 发货 → 在途 → 签收 → 完成

异常分支：
  下单 → 备货不足 → 部分发货 → 等待补货 → 续发
  发货 → 在途 → 质量异议 → 退货 → 退款
  发货 → 在途 → 签收 → 质量异议 → 部分退货 → 部分退款
  发货 → 在途 → 签收 → 对账 → 价格争议 → 调价 → 重新结算
```

**设计原则**：
- 履约是一张状态机，不是一个状态字段
- 异常分支的代码量通常是正常流程的3-5倍
- 履约状态的变更需要事件溯源（Event Sourcing），方便审计和回溯

## 第三章：技术架构模式与设计决策

### 3.1 异构架构模式（你的实战沉淀）

B2B大宗贸易系统最常见的模式：**高性能核心 + 灵活性业务层**。

```
┌──────────────────────────────────────────────┐
│                 接入层                        │
│      大屏 / PC端 / 移动端（Vue多端）           │
└────────────────────┬─────────────────────────┘
                     │
┌────────────────────┴─────────────────────────┐
│              网关层 (midservice)              │
│         鉴权 / 限流 / 路由 / 监控              │
└────────────────────┬─────────────────────────┘
                     │
        ┌────────────┴────────────┐
        │                         │
┌───────┴───────┐          ┌──────┴──────┐
│  C语言撮合引擎  │          │ Java业务中台 │
│  单线程内存撮合 │◄────────►│  微服务集群   │
│  异步落库      │ Hessian  │ 12+服务     │
│  微秒级响应    │ +Socket  │ 管理系统     │
└───────────────┘          └─────────────┘
```

**为什么C+Java异构？**

这是面试中最有含金量的话题。不是"为了炫技"，而是：

1. **C语言撮合引擎的价值**：
   - 单线程内存撮合，无锁竞争，微秒级延迟
   - 大宗商品行情变动快，撮合延迟=成交失败=真金白银损失
   - 不能用Java是因为GC停顿不可接受（哪怕STW只有几十毫秒）

2. **Java业务中台的价值**：
   - 业务规则多变，需要快速迭代
   - 12+微服务需要成熟的生态（Spring Cloud/MyBatis/Redis）
   - 团队招聘——找C程序员做业务不现实，找Java程序员做撮合也不对

3. **桥接层（DS数据中心）的设计哲学**——这是你作为技术经理能"管住"异构架构的抓手：
   - C引擎对外暴露二进制协议（Socket），但不理解业务语义
   - DS作为防腐层（Anti-Corruption Layer），负责协议转换（Hessian序列化）
   - 同步走HTTP+Hessian（查询场景），异步走Socket（行情推送/交易通知）
   - **关键洞察**：DS不是"翻译官"，它是"外交官"——它定义了C和Java之间的边界和契约

**面试叙事框架**（这一节是精华）：

> "我们的架构选择C+Java异构，不是因为C语言更酷，而是因为GC停顿对撮合引擎不可接受。C引擎负责微秒级撮合，Java中台负责复杂的业务逻辑。中间通过专门的桥接服务（DS）做协议转换——我们用了Anti-Corruption Layer模式，确保两个技术栈互不污染。这个设计的关键不在技术，而在边界定义：什么逻辑放C，什么逻辑放Java，什么逻辑放桥接层。"

### 3.2 数据架构模式

**读写分离与缓存策略**：

```
写入链路：业务服务 → MySQL主库 → Canal binlog → 缓存服务（刷新Redis）
读取链路：Web前端 → 缓存服务（封装的Redis） → 返回
```

**为什么缓存服务是独立封装的？**

不是"套一层Redis"，而是有明确的架构价值：
1. **协议的关注点分离**：业务服务不关心Redis配置，只调用缓存服务API
2. **缓存策略集中管理**：过期策略、预热策略、降级策略统一在缓存服务中
3. **监控和告警统一**：缓存命中率、延迟、连接池状态集中监控
4. **切换成本低**：从单机Redis切换到集群，只需改缓存服务，业务无感

### 3.3 外部系统对接的防腐层设计

B2B系统对接的外部系统远超B2C：

```
外部系统（9+）：
  银行 × N    → 银企直连、电子回单
  短信        → 验证码、通知
  证书(CA)    → 电子签章
  物流 × N    → WMS、TMS
  CTRM        → 期现系统
  开票        → 电子发票
  咨询        → 行情、资讯
  企查查      → 企业征信
  供应链金融   → 保理、融资
```

**防腐层的核心原则**：
- 每个外部系统一个独立的适配器（Adapter）
- 外部系统的数据模型绝不直接暴露给业务层
- 外部系统的异常不传导到核心业务流程
- 外部系统不可用时，核心流程不受影响（熔断+降级）

### 3.4 事件驱动与最终一致性

B2B交易链路长，强一致性会拖垮系统。正确做法是事件驱动：

```
订单创建事件 → 库存预留 → 信用额度扣减
     │
     ├── 支付事件 → 账务记账 → 银行回调
     │
     └── 发货事件 → 物流下单 → WMS同步 → 客户通知
```

**设计决策**：
- 订单状态作为"单一真相源"，其他系统通过事件同步
- 不一致时可以补偿（对账机制+人工介入），但不能丢失事件
- 消息队列选型：金融级用RocketMQ（事务消息），一般用RabbitMQ/Kafka

## 第四章：关键技术决策框架

本章是面试高频考点——当面试官问"你为什么这么设计"，你需要一个清晰的决策框架。

### 4.1 同步还是异步？

| 场景 | 选择 | 原因 |
|------|------|------|
| 撮合匹配 | 同步 | 毫秒级响应，错失=损失 |
| 订单创建 | 同步 | 用户需要即时反馈 |
| 库存扣减 | 同步 | 防超卖 |
| 支付确认 | 异步 | 银行回调不可控 |
| 短信通知 | 异步 | 非核心链路 |
| 数据同步 | 异步(Canal) | 解耦，不影响主流程 |
| 审批流转 | 异步 | 审批人可能不在线 |

### 4.2 强一致还是最终一致？

| 场景 | 选择 | 原因 |
|------|------|------|
| 撮合结果 | 强一致 | 一单不能多卖 |
| 订单-库存 | 强一致 | 超卖=资金损失 |
| 支付-账务 | 最终一致 | 银行回调有时间差 |
| 订单-物流 | 最终一致 | 物流系统异步确认 |
| 订单-发票 | 最终一致 | 发票可事后补开 |

**核心原则**：涉及"钱"和"货"的用强一致，涉及"通知"和"同步"的用最终一致。

### 4.3 自研还是外采？

| 模块 | 建议 | 原因 |
|------|------|------|
| 撮合引擎 | 自研 | 核心竞争力，买不到 |
| 价格引擎 | 自研 | 行业特殊定价逻辑，通用产品覆盖不了 |
| WMS/TMS | 外采+适配 | 成熟产品，集成即可 |
| 电子签章 | 外采API | 合规成本高，接入费用远低于自研 |
| 企业征信 | 外采API | 自建数据源不现实 |
| OA/审批 | 外采/集成 | 非核心能力 |

## 第五章：面试叙事框架

### 5.1 一句话自我介绍

> "我是B2B大宗贸易供应链的技术负责人，主导了[C语言撮合引擎+Java微服务]异构架构的设计和落地，核心负责交易撮合、履约保证、价格引擎和生态对接四大模块。"

### 5.2 三分钟架构陈述模板

**第一段（30秒）：业务背景和规模**
"我们做的是XX品类的大宗商品B2B交易平台，年交易额XX亿，服务XX家企业客户。核心挑战是：撮合延迟要求高（行情波动秒级变化）、交易模式复杂（协议价/基差/信用价多套定价体系）、履约链路长（从合同到结算十几步）、外部系统多（银行/物流/税务等9+系统对接）。"

**第二段（90秒）：架构设计核心决策**
"基于这些挑战，我们做了四个关键决策。第一，撮合引擎用C语言单线程内存撮合——因为Java的GC停顿对撮合不可接受，我们实测过GC时的几十毫秒停顿会导致行情错失。第二，业务中台用Java微服务——12+服务需要快速迭代，Java生态和团队能力匹配。第三，中间加了一层防腐层（DS数据中心）——用Hessian协议对接C引擎，确保两个技术栈不互相污染。第四，数据同步用Canal+独立缓存服务——读写分离，Web访问走缓存，不碰主库。"

**第三段（60秒）：个人价值**
"我作为技术经理，在这套架构中的角色不是写撮合引擎代码——那是C程序员的活。我的价值是：定义C和Java的边界（什么逻辑放哪里）、设计防腐层的协议和容错策略、保证交易链路的数据一致性、以及带团队在12+微服务的复杂性中保持迭代速度。"

### 5.3 常见追问的准备

**Q: 为什么不把撮合引擎也用Java写？**
> "试过。GC停顿即使优化到几十毫秒，在行情激烈波动时这几十毫秒的延迟累积会导致撮合结果偏离。大宗商品一单动辄几十上百万，这是不能接受的。C语言单线程无锁设计，确定性很高。"

**Q: 异构架构怎么保证数据一致性？**
> "C引擎只管撮合，撮合结果通过Socket异步推给DS，DS写入MySQL后再通过Canal同步到缓存。这个链路上任何节点挂了都有补偿机制：C引擎有本地日志，DS有重试，MySQL有事务，Canal有断点续传。我们不做分布式事务，用事件驱动+最终一致性+对账补偿。"

**Q: 你们团队多少人？你怎么分工的？**
> "核心团队XX人。C引擎3个人（资深C程序员），DS桥接层2个人（Java），交易核心5个人，其他微服务按模块拆分。我直接review DS和交易核心的代码——DS是连接两个世界的枢纽，出了问题两边都受影响。这也是为什么防腐层的代码质量我盯得最紧。"

**Q: 如果从头再来，你会改什么？**
> "我会更早引入防腐层的概念，而不是让C协议直接透传到业务层。早期我们让交易服务直接调C的Socket，导致C协议的变更影响面太大。现在DS层做了一层隔离，两边独立演进，是个正确的决定。"

**Q: 你的AI/大模型在业务中怎么落地？**
> "正在探索三个方向。第一，智能报价——基于历史成交数据+市场行情，辅助生成报价建议。第二，合同智能审查——RAG+大模型辅助审核合同条款的合规性。第三，交易规则问答——用RAG让客户自助查询交易规则和流程。这些方向还在POC阶段，但B2B+AI是确定的趋势。"

## 附录：B2B架构常见反模式

### 反模式1：用B2C思维做B2B
- 表现：把订单当购物车设计，价格只有一口价，账号是单用户
- 后果：第一期上线后发现80%的客户需求覆盖不了
- 解法：从第一天就用企业账户、多价格体系、审批流来建模

### 反模式2：微服务拆分过度
- 表现：一个B2B交易系统拆成50+微服务
- 后果：一个询价要跨8个服务，分布式事务满天飞，排查一个bug要查5个服务的日志
- 解法：按业务边界拆分，不是按数据表拆分。客户中心、商品中心、交易中心、履约中心——5-8个核心服务就够了

### 反模式3：外部系统直连核心业务
- 表现：银行接口异常导致订单创建失败
- 后果：外部系统的SLA远低于你，却绑架了你的核心流程
- 解法：所有外部依赖必须异步化+熔断+降级。银行回调失败？订单照下，支付信息异步补。

### 反模式4：把撮合当简单匹配
- 表现：select * from order where price >= ? and qty >= ? limit 1
- 后果：并发上来后数据库锁竞争，撮合延迟从毫秒变秒
- 解法：撮合是独立子系统，设计时就要考虑并发模型和内存数据结构

# B2B系统：从原型到优秀平台的建设框架

> **编写背景**：你已经把自己的系统解剖到了根因层——"副本式架构"的七个痛点高度收敛于同一个系统性缺陷。现在反过来想：如果从头设计一套优秀的B2B系统，原型阶段应该做什么、怎么做、做到什么程度才算"过了"。

---

## 一、先纠正一个认知：B2B原型 ≠ 画界面

B2C创业可以做个Figma高保真原型拿给用户点一点、测转化率。B2B不行。

**B2B原型的核心目的不是"好不好看"，是"对不对"——领域模型对不对，交易链路通不通，数据一致性能不能保证，异常情况下系统行为是否符合业务预期。**

| | B2C原型 | B2B原型 |
|---|---|---|
| 验证什么 | 用户体验、转化漏斗 | 领域模型、交易闭环、数据一致性 |
| 谁来看 | 终端消费者 | 业务专家、交易运营、风控 |
| 可接受的错误 | 按钮位置不对、颜色不喜欢 | 订单状态丢了一步、金额对不上、货权归属错误 |
| 原型载体 | Figma/可交互页面 | 领域模型图 + 核心链路可运行骨架 + 事件时序图 |
| "过了"的标志 | 用户愿意点下一步 | 业务专家看完说不出"这不符合实际流程" |

**你做原型的第一个动作不是打开设计工具，是拿一张白纸画领域模型。**

---

## 二、原型之前：三个必须先回答的问题

在你写一行代码、画一个框之前，把这三件事想清楚。它们决定了你后面所有技术决策的边界。

### 问题1：你的系统本质上是什么？

不是"一个交易平台"，那太泛了。要精确到一句话：

> **这是一个以 [核心撮合机制] 为引擎、以 [履约保证] 为信任基石、以 [供应链金融] 为增值引擎的 [垂直品类] B2B交易系统。**

按你的实际情况填空：
- 核心撮合机制：挂牌/竞价/协议/基差 四种模式
- 履约保证：合同→仓单→交收→结算 闭环
- 增值引擎：交易数据 → 信用评价 → 供应链融资
- 垂直品类：钢铁（可扩展）

**这句话是你原型阶段所有取舍的判断标准。** 任何跟这句话无关的功能，原型阶段都不做。

### 问题2：你的第一个客户是谁？

不是"所有大宗贸易商"。第一个人必须具体到一家公司、一个人。

从你之前的五类目标客户分析里选一个作为原型验证对象：

| 客户类型 | 原型验证重点 | 为什么选它 |
|---|---|---|
| 垂直行业平台运营商 | 多租户配置引擎 | 一个平台服务多个垂直品类 |
| 大型产业集团 | 私有化部署 + 深度定制 | 企业内部供应链数字化 |
| 地方政府/产业园 | 交易大屏 + 监管合规 | 政策驱动，快速立项 |
| 行业协会/商会 | 会员共享平台 | 轻量级起步 |
| 金融机构 | 供应链金融风控引擎 | 数据变现路径最短 |

**建议原型阶段选"垂直行业平台运营商"中的一家中型贸易商**——它既有真实交易场景帮你验证领域模型，又不像钢厂那样要求私有化部署。

### 问题3：一条交易从头走到尾，最少需要哪几个系统？

不要一上来就想12个微服务。原型阶段只做"最小可行骨架"——

```
                    ┌──────────────┐
                    │   用户/认证    │  ← 谁在用
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ▼                  ▼                  ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│   商品中心    │  │   交易引擎    │  │   合同中心    │
│ (有什么可买卖) │  │ (怎么成交)    │  │ (怎么锁定)    │
└──────────────┘  └──────┬───────┘  └──────────────┘
                          │
                          │ 成交后
                          ▼
                 ┌──────────────┐
                 │   履约中心    │  ← 仓单过户 + 交收 + 结算
                 └──────────────┘
```

**原型阶段的六个系统**（刚够让一笔交易跑通）：
1. **用户与权限** — 谁在用、看到什么
2. **商品中心** — 品类编码、商品主数据
3. **交易引擎** — 挂牌/摘牌/撮合（核心）
4. **合同中心** — 成交后生成合同
5. **履约中心** — 仓单过户、交收确认、资金结算
6. **通知服务** — 状态变更推送

不需要支付网关（原型阶段用模拟）、不需要风控引擎、不需要数据分析、不需要供应链金融。那些是血肉，骨架先搭对。

## 三、原型四阶段

### Phase 0：纸上建模（2-3天，不写代码）

**目标**：让业务专家看完说不出"不对"。

**做法**：拿出白纸（或Miro/Excalidraw），跟最懂业务的人一起画三张图。

#### 图1：领域模型图

画出核心聚合根和它们之间的关系。只画主干，不画枝叶。

```
客户(Customer)
  │
  ├── 拥有多个 商品(Product) ── 属于 ── 品类(Category)
  │
  ├── 发布 挂牌(Listing)
  │       │
  │       └── 成交后生成 合同(Contract)
  │               │
  │               └── 关联 仓单(WarehouseReceipt)
  │                       │
  │                       └── 触发 交收(Delivery)
  │                               │
  │                               └── 完成 结算(Settlement)
  │
  └── 有 账户(Account) ── 记录 资金流水(FundTransaction)
```

**关键原则**：
- 每个聚合根只在一个地方"出生"（唯一写入源）
- 其他系统通过ID引用，不走数据副本
- 聚合根之间的事件传递是异步的

#### 图2：一笔交易的事件时序图

以最简单的"挂牌→摘牌→成交"为例，画出每个事件在六个系统之间的流动：

```
买方         交易引擎        合同中心       履约中心       通知服务
 │              │              │              │              │
 │  摘牌请求     │              │              │              │
 │─────────────>│              │              │              │
 │              │ 验证挂牌状态   │              │              │
 │              │ 生成成交记录   │              │              │
 │              │ 发布"已成交"事件│             │              │
 │              │─────────────>│              │              │
 │              │              │ 生成合同      │              │
 │              │              │ 发布"合同已生成"│             │
 │              │              │─────────────>│              │
 │              │              │              │ 创建履约单    │
 │              │              │              │ 发布"待交收"  │
 │              │              │              │─────────────>│
 │              │              │              │              │ 推送给双方
 │  <──────────────────────────────────────────────────────  "合同已生成"
 │  <──────────────────────────────────────────────────────  "待交收确认"
```

**这张图的价值**：它暴露了所有"数据该从哪里来"的问题。如果某一步事件断了，后续步骤全卡住——这就是你现有系统"副本式同步"的根因可视化。

#### 图3：领域事件目录

列出一笔交易从生到死所有会产生的事件：

| 事件 | 产生方 | 消费方 | 关键数据 |
|---|---|---|---|
| ListingPublished | 交易引擎 | 通知服务 | 挂牌ID、商品、价格、数量、卖方 |
| ListingAccepted | 交易引擎 | 合同中心、通知服务 | 挂牌ID、摘牌方、成交价、成交量 |
| ContractCreated | 合同中心 | 履约中心、通知服务 | 合同ID、双方、商品、价格、数量 |
| DeliveryRequested | 履约中心 | 仓单系统、通知服务 | 履约单ID、合同ID、仓单ID |
| DeliveryCompleted | 履约中心 | 结算、通知服务 | 履约单ID、交收时间、验收结果 |
| SettlementCompleted | 履约中心 | 通知服务 | 结算单ID、金额、时间 |

**这张图是你系统的事件骨架。原型阶段的代码就是让这些事件按顺序正确发生。**

#### Phase 0 验收标准
- [ ] 业务专家看了领域模型图，没有说"我们实际不是这样的"
- [ ] 事件时序图覆盖了你的核心交易模式（挂牌成交 + 至少一个变体如竞价）
- [ ] 事件目录没有遗漏"钱"和"货"的任何一个状态变更
- [ ] 每个事件都能回答"谁产生、谁消费、携带什么数据"

---

### Phase 1：核心骨架（2-3周，最小可运行）

**目标**：让一笔虚拟交易从头跑到尾，事件全部正确触发。

**做什么**：
1. 六个系统各自的最简实现——每个系统只实现Phase 0定义的核心聚合根
2. 系统间通过**领域事件**通信（Kafka或内存消息队列，原型阶段后者更简单）
3. 每个系统有自己的数据库，不共享
4. 所有数据变更通过事件通知，不做同步RPC调用链

**不做**：
- 不做前端完整UI——只做一个极简操作界面或直接API调用
- 不做权限精细控制——只有"买方/卖方"两个角色
- 不接真实支付、不接真实短信、不接任何外部系统
- 不做性能优化、不做缓存、不做高可用

#### 原型阶段的数据架构：从第一天就避免"副本式"

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   商品中心    │    │   交易引擎    │    │   合同中心    │
│              │    │              │    │              │
│ 商品表(权威)  │    │ 挂牌表       │    │ 合同表(权威)  │
│              │    │ 商品ID(引用)  │    │ 挂牌ID(引用)  │
└──────────────┘    └──────────────┘    │ 买卖方ID(引用) │
                                        └──────┬───────┘
                                               │ 合同ID(权威)
                                        ┌──────▼───────┐
                                        │   履约中心    │
                                        │              │
                                        │ 履约单表(权威)│
                                        │ 合同ID(引用)  │
                                        └──────────────┘
```

**核心规则**：
- 每个数据只有一个"出生地"（权威源）
- 其他系统存**引用**（ID），不存**副本**（完整数据）
- 如果需要展示关联数据（如履约单上显示商品名称），查询时通过ID去权威源获取，不在履约表里存商品名称副本

#### Phase 1 验收标准
- [ ] 挂牌→摘牌→成交→合同生成→履约单创建，整条链路跑通
- [ ] 每个状态变更都有对应的事件发出
- [ ] 任何一个中间系统宕机，不影响已完成的步骤（事件可重放）
- [ ] 数据库中不存在"同一份客户数据存在两个不同版本"的情况
- [ ] 可以用一个查询把"合同→挂牌→商品→履约"串起来

---

### Phase 2：血肉填充（2-4周，可演示）

**目标**：让业务专家可以实际操作，能跑通真实业务场景。

**做什么**：

#### 2.1 前端可操作界面

不是完整产品，是够用的操作界面：
- 卖方：发布挂牌、查看我的挂牌、确认成交
- 买方：浏览挂牌、摘牌、查看我的合同
- 双方：查看履约进度、确认交收

每个页面聚焦一件事。不做dashboard、不做数据统计、不做管理后台。

#### 2.2 业务角色区分

从原型第一天就做角色区分，不要等到后面重构：
- 买方登录 → 看到的是"找货"视图
- 卖方登录 → 看到的是"卖货"视图
- 同一账号可以同时是买方和卖方（大宗贸易商天然双向），但切换模式时有清晰的视图切换

#### 2.3 用真实业务场景跑一遍

从你的钢铁交易场景故事集中挑3个最有代表性的：
1. **标准挂牌成交**：卖方挂牌→买方摘牌→签合同→仓单过户→交收→结算（最基础链路）
2. **竞价成交**：卖方发起竞价→多方出价→最高价成交→后续同标准链路
3. **异常场景**：买方摘牌后反悔→合同取消→挂牌恢复（验证状态回滚）

每个场景走完，记录三件事：
- 哪里跟业务专家说的不一样？
- 哪个状态转换业务专家觉得"不对"？
- 少了什么数据？

#### Phase 2 验收标准
- [ ] 三个场景全部跑通，业务专家能自己操作
- [ ] 角色切换流畅，买方/卖方看到的内容正确隔离
- [ ] 异常场景的状态回滚符合业务预期
- [ ] 业务专家不再说"这里跟我们实际不一样"

---

### Phase 3：弹性验证（1-2周，边界条件）

**目标**：在原型阶段就暴露系统设计的薄弱点，避免生产事故。

#### 3.1 事件断链恢复

模拟消息中间件宕机、某个服务重启：
- 事件是否可重放？
- 重放后状态是否一致？
- 消费端是不是幂等的？

#### 3.2 并发冲突

两个买方同时摘同一个挂牌：
- 谁先到谁成交？
- 后来者看到什么提示？
- 会不会出现"两个人都以为自己成交了"？

#### 3.3 状态机完整性

画出交易引擎的完整状态机：

```
挂牌发布 ──→ 待摘牌 ──→ 已摘牌 ──→ 合同已生成 ──→ 履约中 ──→ 已完成
                │                                    │
                └──→ 已过期                          └──→ 已取消（需双方确认?）
```

**检查每条边**：从当前状态出发，哪些操作是合法的？哪些是非法的？
**检查每个状态**：有没有"死状态"（进去了出不来）？

#### Phase 3 验收标准
- [ ] 事件断链后系统可自动恢复，无需人工介入
- [ ] 并发场景下不会出现数据不一致
- [ ] 状态机没有死状态、没有非法转换路径
- [ ] 所有异常场景都有明确的错误信息和恢复路径

---

## 四、原型阶段就要做对的五件事（你现有系统的血泪教训）

### 1. 商品编码从第一天就统一

你现有系统最大的痛：仓单用大类ID，挂牌用细分品种ID，配货靠人工对名称。

**原型做法**：设计三层品类编码（大类→品种→规格），所有系统引用同一个商品ID。哪怕原型阶段只有10个商品，编码体系也要完整。

### 2. 客户主数据只有一个源

你现有系统第二大痛：客户数据通过消息队列"复制"到N个系统，同步断了就乱。

**原型做法**：客户只在"用户系统"创建。其他系统存`customer_id`（引用），展示时通过ID去用户系统查。不做任何形式的客户数据副本。

### 3. 事件驱动，不做同步调用链

你现有系统的履约流程是高耦合的——一个环节调用下一个，链条中断需要人工排查。

**原型做法**：每个系统只做两件事——处理本域业务逻辑 + 发布领域事件。谁消费这个事件、怎么处理，发布方不关心。这让你后续加新业务模式时不需要改现有代码，只需要加新的事件消费者。

### 4. 状态机先画全再写代码

很多系统的状态机是"写着写着补出来的"，导致边界情况没覆盖。

**原型做法**：Phase 0就把交易核心的状态机画完整（包括所有异常路径），Phase 1按状态机实现。宁可原型阶段多画几个状态，也不要上线后补。

### 5. 配置化而不是硬编码

你现有系统的第三个大问题：新增一个交易模式要在多个系统里改代码。

**原型做法**：挂牌规则、合同模板、履约流程用配置驱动。原型阶段不需要完整的规则引擎，但架构上留出"策略可替换"的口子——用策略模式或简单的配置表，不要`if 挂牌 else if 竞价`写死在业务逻辑里。

---

## 五、原型之后的过渡：怎么从原型到生产

原型通过验收后，最大的陷阱是"原型代码直接上线"。不要这么做。

| | 原型代码 | 生产代码 |
|---|---|---|
| 目标 | 验证模型对不对 | 稳定运行、可运维 |
| 数据库 | 可能单机、无备份 | 主从、备份策略、迁移脚本 |
| 消息队列 | 可能内存实现 | Kafka集群、持久化、监控 |
| 服务通信 | 可能直连 | 网关、服务发现、熔断 |
| 错误处理 | "先跑通再说" | 全面的异常分类和降级策略 |

**过渡策略**：
1. **保留领域模型和事件目录**（Phase 0的产出是永久资产）
2. **保留状态机定义**（直接翻译成生产代码的状态机）
3. **重写基础设施层**（数据库切换为生产配置、消息队列切换为Kafka、加网关）
4. **逐个替换业务逻辑**（一个聚合根一个聚合根迁移，不要大爆炸式切换）
5. **上线前跑一遍Phase 3的弹性验证**（在生产环境配置下重跑）

---

## 六、贯穿始终的核心原则

### 原则1：领域模型是唯一真相源

代码可以重写、框架可以换、数据库可以迁移——但领域模型是系统对业务的"理解"。只要模型对了，换什么技术实现都只是工程问题。模型错了，技术再牛也是在一个错误的方向上加速。

### 原则2：事件是系统的血液

在B2B系统中，一笔交易生成了什么事件、谁消费了这些事件，比"用了什么数据库""用了什么框架"重要十倍。事件目录是你系统最核心的设计文档。

### 原则3：从第一天就拒绝数据副本

"先复制一份数据过去，后面再统一"是B2B系统最常见的慢性自杀。原型阶段的代价很小——就六个系统、几十条数据——此时把引用关系做对几乎零成本。等到100个客户、几十万条数据时再改，代价是原型阶段的100倍。

### 原则4：业务专家是原型阶段的第一用户

不是CEO、不是投资人、不是测试工程师。是那个每天在Excel里手动对账的人。他能在5分钟内告诉你"这个状态不对""实际流程不是这样的""少了这个字段我会死"。

---

## 七、你现在就可以做的第一件事

不用等任何条件成熟。拿一张纸，画你的**领域事件目录**。

把你最熟悉的"挂牌→成交→合同→履约→结算"拆成事件序列，每个事件写清楚：谁发出的、内容是什么、谁需要知道。

画完之后问自己一个问题：**如果合同系统挂了，挂牌成交还能不能正常发生？**

你能回答这个问题，就说明你已经开始用"事件驱动"而不是"同步调用链"的方式思考了。这就是优秀的B2B系统和"能跑的B2B系统"的分界线。

# 优秀B2B系统：完整技术选型与设计方案

> **设计原则**：每一项选型都回答四个问题——选什么、为什么选它而不是替代品、这个选择在B2B场景下的价值是什么、有什么代价。

---

## 一、架构总览：模块化单体 + 事件驱动

### 核心决策：原型到中期用"模块化单体"，不定"微服务"

这是整个方案里最重要的一个决策，放最前面说清楚。

```
┌─────────────────────────────────────────────────────────┐
│                      API Gateway                        │
│                 (Spring Cloud Gateway)                  │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│   │ 用户模块  │ │ 商品模块  │ │ 交易模块  │ │ 合同模块  │  │
│   │ user     │ │ product  │ │ trade    │ │ contract │  │
│   └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘  │
│        │            │            │            │         │
│   ┌────┴─────┐ ┌────┴─────┐ ┌────┴─────┐ ┌────┴─────┐  │
│   │ 履约模块  │ │ 结算模块  │ │ 通知模块  │ │ 配置模块  │  │
│   │ delivery │ │ settle   │ │ notify   │ │ config   │  │
│   └──────────┘ └──────────┘ └──────────┘ └──────────┘  │
│                                                         │
│   ─ ─ ─ ─  跨模块通信：Spring Events  ─ ─ ─ ─ ─ ─     │
│                                                         │
│   ┌──────────────────────────────────────────────────┐  │
│   │              共享内核 (Shared Kernel)              │  │
│   │   领域事件定义 / 基础工具类 / 通用异常 / ID生成     │  │
│   └──────────────────────────────────────────────────┘  │
│                                                         │
├─────────────────────────────────────────────────────────┤
│                   数据层                                 │
│   ┌──────────┐  ┌──────────┐  ┌──────────────────────┐  │
│   │ MySQL 8  │  │  Redis   │  │  MinIO (对象存储)     │  │
│   └──────────┘  └──────────┘  └──────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

#### 为什么是模块化单体而不是微服务？

| 维度 | 模块化单体 | 微服务 | B2B系统的判断 |
|------|-----------|--------|--------------|
| 事务一致性 | 本地事务，天然ACID | 分布式事务，Seata/Saga | **B2B对数据一致性要求极高**，交易/合同/资金不容出错 |
| 部署复杂度 | 一个包，一个进程 | N个包，N个进程 | 初期团队规模小，微服务的运维开销远超收益 |
| 调试排查 | 一个调用栈走到头 | 跨服务追踪依赖SkyWalking | B2B业务链路长，排查问题频繁，单体调用栈一目了然 |
| 领域边界稳定性 | 允许试错，模块边界易调整 | 拆分后改边界代价极高 | **原型阶段领域边界在探索中**，急着拆服务会拆错 |
| 未来拆分 | 模块间已有明确接口，拆分是部署方式变化 | - | 代码结构按DDD限界上下文组织，需要时一个模块一个模块拆出去 |

**关键认知**：模块化单体 ≠ 大泥球。区别在于模块间是否通过**接口+事件**通信，而不是直接调对方的Service/读对方的表。代码结构上已经按微服务的方式组织了，只是部署时还是一个进程。

#### 什么时候拆？

三个触发条件，满足任意一个就拆：
1. 某个模块的流量需要独立扩缩容（比如交易引擎QPS是其他模块的10倍）
2. 某个模块需要独立的发布节奏（比如配置模块改一个规则不想重启整个系统）
3. 团队拆分，一个团队负责一个模块

## 二、逐层技术选型

### 2.1 语言与运行平台

| 选型 | 版本 | 为什么 |
|------|------|--------|
| **Java** | JDK 17 LTS | 团队主语言；Spring生态最成熟；JDK 17的Record/Sealed Class对DDD值对象建模极友好；ZGC在JDK 17已生产可用，大堆内存低延迟适合撮合场景 |
| **Vue 3** | 3.4+ | 团队已有Vue经验；Composition API让复杂B2B表单逻辑可复用（一个挂牌表单可能有30+字段和动态校验规则） |
| **TypeScript** | 5.x | B2B前端数据结构复杂（挂牌/合同/仓单各有几十个字段），类型系统是第一道防线 |

**JDK 17 特别说明**：
- Record类型天然适合DDD中的值对象（如`Money`、`Quantity`、`CommodityCode`），不可变、自带equals/hashCode，比Lombok更干净
- Sealed Class适合定义状态机的合法状态集合，编译期检查状态转换的完备性
- 选17不选21的原因：21的Virtual Thread虽然诱人，但生态工具（SkyWalking/Arthas等）对21的支持还在追赶中，稳字当头

---

### 2.2 后端框架

| 选型 | 版本 | 为什么 |
|------|------|--------|
| **Spring Boot** | 3.2+ | 事实标准，团队熟悉。3.x原生支持GraalVM Native Image（留后路）、Observability API（Micrometer集成） |
| **Spring Security** | 6.x | RBAC+业务角色双模型 |
| **MyBatis-Plus** | 3.5+ | B2B系统SQL复杂（多维筛选挂牌、跨表聚合统计），MyBatis的SQL可控性远超JPA。Plus版在单表CRUD上又能省掉大量重复代码 |
| **Springdoc OpenAPI** | 2.x | API文档自动生成，配合Knife4j |

#### 为什么是 MyBatis-Plus 而不是 JPA/Hibernate？

| | MyBatis-Plus | JPA/Hibernate |
|---|---|---|
| 复杂查询 | SQL写清楚，DBA能review | JPQL/HQL，复杂查询难调优 |
| 多表关联 | JOIN写明白，执行计划可控 | 懒加载N+1陷阱，Fetch策略容易踩坑 |
| 报表统计 | 原生SQL直接写 | Criteria API可读性差 |
| 学习成本 | 团队已在用 | 概念多（EntityManager/Session/一级缓存/二级缓存） |
| B2B适配度 | **高**——B2B的查询维度多、条件组合复杂 | 中——适合CRUD为主的系统 |

**但是**：JPA在领域建模的表达力上更强（`@Embedded`、`@OneToMany`的级联等），建议在聚合根内部的实体关系上用JPA注解辅助建表，复杂查询用MyBatis。两者可以共存——Spring Data JPA做领域持久化，MyBatis做查询。

---

### 2.3 数据库

| 选型 | 版本 | 为什么 |
|------|------|--------|
| **MySQL** | 8.0+ | 团队最熟悉；B2B系统强事务需求，MySQL的InnoDB在事务成熟度上仍是开源首选；8.0的窗口函数/CTE对报表统计有用 |
| **HikariCP** | Spring Boot默认 | 连接池事实标准，性能无需调优即可用 |

#### 为什么是 MySQL 而不是 PostgreSQL？

| | MySQL 8.0 | PostgreSQL 16 |
|---|---|---|
| 生态 | 国内B2B/金融行业绝对主流 | 在国内处于追赶态势 |
| DBA资源 | 好找 | 相对稀缺 |
| 运维工具 | 成熟（gh-ost/PT工具/Arthas） | PG工具链在国内不够普及 |
| 分区表 | 支持，够用 | 更强大（声明式分区） |
| JSON支持 | JSON类型+函数 | JSONB，查询性能更强 |
| 地理空间 | 弱 | PostGIS是杀手级 |
| **判断** | **选MySQL**——B2B不需要JSONB的强大查询，不需要地理空间，最需要的是团队熟、DBA好招、运维工具全 |

#### 数据库架构设计

```
┌─────────────────────────────────────────────┐
│                MySQL 双实例                   │
│                                              │
│  ┌─────────────────┐  ┌─────────────────┐   │
│  │   Master (读写)  │  │  Slave (只读)    │   │
│  │                 │  │                 │   │
│  │ user_db         │  │ 半同步复制       │   │
│  │ product_db      │  │                 │   │
│  │ trade_db        │  │ 报表查询        │   │
│  │ contract_db     │  │ 数据导出        │   │
│  │ delivery_db     │  │ 对账任务        │   │
│  │ settle_db       │  │                 │   │
│  └─────────────────┘  └─────────────────┘   │
│                                              │
│  分库策略：按限界上下文垂直分库                │
│  不分表（初期数据量不需要）                    │
└─────────────────────────────────────────────┘
```

**每个模块独立数据库**——这是"模块化单体"在数据层的核心实践。即使部署是单体，数据库已经按微服务的方式拆了，未来拆服务时数据库不需要动。

**为什么垂直分库而不是水平分表**：
- 初期一个垂直行业几十万条交易数据，单表撑得住
- 垂直分库保证每个模块的事务在自己的数据库内完成，不需要分布式事务
- 只有交易明细表未来可能水平分表，届时按`trade_date`分区即可

---

### 2.4 缓存

| 选型 | 为什么 |
|------|--------|
| **Redis** | 不仅仅是缓存，B2B系统中承担四重角色 |

Redis在B2B系统中的四重角色：

| 角色 | 数据结构 | 场景 | 为什么不能丢 |
|------|---------|------|-------------|
| 热点缓存 | String/Hash | 商品详情、客户信息、挂牌列表首页 | 减少DB压力，Cache-Aside模式 + Canal兜底 |
| 分布式锁 | String + Redisson | 摘牌竞抢、日终结算、大额资金操作 | B2B交易涉及资金和货权，并发冲突不允许发生 |
| 延迟队列 | ZSet | 挂牌自动过期、合同超时提醒 | 时间驱动的业务动作不需要额外引入定时任务框架 |
| 去重/幂等 | String(SETNX) | 事件消费去重、支付回调幂等 | 事件驱动架构的"安全带"，防重复消费 |

**部署模式**：初期哨兵模式（1主2从3哨兵），够用；中后期集群模式。不推荐单机。

---

### 2.5 消息队列

| 选型 | 为什么 | 替代方案与对比 |
|------|--------|--------------|
| **Kafka** | 团队已有经验；高吞吐、持久化、多消费者组天然适合事件驱动架构 | 对比见下表 |

#### Kafka vs RocketMQ：B2B场景的深度对比

| 维度 | Kafka | RocketMQ | B2B选型判断 |
|------|-------|----------|------------|
| 事务消息 | 需要自己实现（outbox pattern） | **原生支持** | RocketMQ优势明显——"合同生成"和"通知发送"要么都成功要么都失败 |
| 顺序消息 | 分区内有序 | **全局有序（队列级）** | B2B中订单状态变更必须按序消费，Kafka靠分区+key保证，RocketMQ更直接 |
| 延迟消息 | 需要自己用ZSet实现 | **原生18个延迟级别** | 挂牌过期、合同超时这类场景RocketMQ更简单 |
| 吞吐量 | **极高**（百万条/秒） | 高（十万条/秒） | B2B交易量远达不到Kafka的吞吐上限 |
| 运维复杂度 | 依赖ZK，组件多 | 相对简单 | 团队已有Kafka运维经验，这点不存在 |
| 生态 | **更大**（Connector生态丰富） | 主要在阿里系 | Kafka的Canal/ES/Flink Connector可直接用 |
| 社区 | Apache顶级，全球活跃 | 阿里主导，中文社区好 | 两个社区都健康 |

**结论：选Kafka。** 虽然RocketMQ在事务消息和延迟消息上更省心，但团队已经在用Kafka，运维经验是最重的砝码。事务消息用outbox pattern + 本地消息表来补，延迟消息用Redis ZSet来实现。

#### Kafka Topic 规划设计

| Topic | 用途 | 分区数 | 消费者组 |
|-------|------|--------|---------|
| `trade-event` | 交易事件（挂牌/摘牌/成交/取消） | 3 | 合同服务、通知服务、风控 |
| `contract-event` | 合同事件（生成/签署/变更/终止） | 3 | 履约服务、结算服务、通知服务 |
| `delivery-event` | 履约事件（交收开始/质检/完成） | 3 | 结算服务、通知服务 |
| `master-data-change` | 主数据变更（客户/商品/品类） | 1 | 缓存刷新 |

**分区数原则**：初期从3开始，每个消费者组一个分区够用，后续根据消费延迟加分区。不要一上来设32个分区——分区越多，Kafka的故障恢复越慢。

---

### 2.6 服务发现与配置管理

| 选型 | 为什么 |
|------|--------|
| **Nacos** | 服务发现+配置管理一体化 |

#### 为什么是 Nacos？

| 对比 | Nacos | Consul | Eureka | Apollo |
|------|-------|--------|--------|--------|
| 服务发现 | ✅ | ✅ | ✅(已停维) | ❌ |
| 配置管理 | ✅ | ✅(KV) | ❌ | ✅(纯配置) |
| 中文社区 | **极强** | 一般 | - | 强 |
| 阿里云兼容 | **原生** | 需适配 | - | 需适配 |
| 配置灰度 | ✅ | ❌ | - | ✅ |
| 运维复杂度 | 低（单机即可） | 中 | 低 | 中（需MySQL+Portal） |

**选Nacos的关键原因**：
1. 服务发现和配置管理一个组件解决，减少运维负担
2. B2B系统有大量业务配置（交易规则、合同模板、风控参数），配置的灰度发布能力是刚需
3. 初期模块化单体阶段Nacos只当配置中心用，将来拆微服务时服务发现直接启用，零迁移成本

### 2.7 API 网关

| 选型 | 为什么 |
|------|--------|
| **Spring Cloud Gateway** | 基于Reactor非阻塞，性能远超Zuul 1.x；与Spring生态无缝集成 |

#### 为什么是 Spring Cloud Gateway 而不是自研？

你的现有系统midservice是Java Web自研网关，这个选择在当时有合理性（业务逻辑耦合深）。但新建系统有两个变化：

1. **业界标准已经成熟**：Spring Cloud Gateway的过滤器链机制足够灵活，路由/限流/鉴权/日志都是配置驱动，不需要写代码
2. **自研的隐性成本**：midservice的经验告诉你，自研网关的所有功能（限流规则、路由策略、监控面板）都要自己实现和长期维护

**结论**：用Spring Cloud Gateway。把团队宝贵的开发时间花在B2B业务逻辑上，不要花在造网关轮子上。

| 网关功能 | 实现方式 |
|---------|---------|
| 路由转发 | 配置文件/注册中心驱动 |
| 认证鉴权 | 全局过滤器 + JWT解析 |
| 限流 | Redis令牌桶（RequestRateLimiter） |
| 日志采集 | 全局过滤器 + 异步写入 |
| 跨域处理 | 配置驱动 |
| 灰度路由 | 自定义过滤器（按用户标签路由到不同版本） |

### 2.8 分布式事务

**核心原则：能用本地事务绝不用分布式事务。**

在模块化单体架构下，大部分操作在同一个数据库事务内完成：
- 挂牌成交 → 生成合同：同一个数据库事务
- 交收完成 → 更新结算单：同一个数据库事务

真正需要分布式事务的场景只有两类：

#### 场景1：跨数据库的写操作

模块化单体下，一个HTTP请求通常只操作一个模块的数据库。如果确实需要跨库（如通知服务记录写入通知库的同时，交易库更新状态），用**本地消息表 + 事件最终一致性**：

```
1. 交易服务在本地事务中：
   - 更新交易状态
   - 写入本地消息表（同一事务！）
2. 后台定时任务扫描消息表，发送Kafka
3. 通知服务消费Kafka，生成通知
4. 有问题走定时对账补偿
```

#### 场景2：涉及外部系统的长事务

比如成交后调用银行支付接口。用**Saga编排**：

| Saga模式 | 做法 | 适用场景 |
|---------|------|---------|
| 编排式(Choreography) | 事件驱动，每个服务自己决定下一步 | 简单流程 |
| 协调式(Orchestration) | 中央协调器控制流程 | 复杂流程，需要补偿逻辑 |

**B2B推荐协调式Saga**——履约流程复杂（合同→仓单→交收→质检→结算），需要一个明确的流程协调器。初期用状态机枚举实现，不做重框架。

| 选型 | 使用条件 |
|------|---------|
| 本地事务 | 首选，模块化单体下90%场景 |
| 本地消息表 + Kafka | 跨服务异步通知 |
| 协调式Saga（自研轻量） | 涉及外部系统 + 需要补偿的长流程 |

**为什么不用Seata**：Seata AT模式需要全局锁，对数据库有侵入；Seata Saga需要额外部署Seata Server。模块化单体拆服务前，Seata的收益小于运维成本。

### 2.11 工作流引擎

| 选型 | 为什么 |
|------|--------|
| **Flowable 7.x** | BPMN 2.0标准；审批流+履约流双场景 |

#### 工作流引擎在B2B中的两个战场

| 战场 | 典型流程 | 特点 |
|------|---------|------|
| 审批流 | 挂牌审核、放款审批、合同变更审批 | 人工决策节点多、需要会签/转办/加签 |
| 履约流 | 仓单过户→质检→交收确认→结算 | 系统自动流转为主、与业务状态机联动 |

#### Flowable vs Camunda vs 自研状态机

| | Flowable | Camunda 7 | 自研状态机 |
|---|---|---|---|
| BPMN标准 | 完整支持 | 完整支持 | 不支持 |
| 中文文档 | **较多** | 少 | 自产 |
| 可视化流程设计 | Modeler内置 | Modeler独立部署 | 需要自己画 |
| 审批流能力 | 完整（会签/转办/加签/退回） | 完整 | 需要全自研 |
| 学习成本 | 中 | 中高 | 低（但有天花板） |
| 推荐场景 | 审批流多、流程会变 | 审批流多、偏国外团队 | 履约流程（系统自动流转） |

**结论——分场景用**：
- **审批流 → Flowable**：审批流是B2B系统的高频场景，Flowable的BPMN能力是成熟方案，不要自研
- **履约流（系统自动流转） → 自研状态机 + 事件驱动**：履约是系统自动执行的流程，不自带人工审批节点，状态机更轻量。事件驱动天然支持流程编排（事件触发下一步）

两者通过**业务事件**桥接——审批流完成后发布事件，履约状态机监听到事件后自动流转。

两者都是优秀的企业级组件库，差距不大。选Ant Design Vue的理由：

| | Ant Design Vue | Element Plus |

**但**：如果你团队已经在用Element Plus而且封装了很多业务组件，继续用Element Plus完全没问题。切换成本不值得。

#### 前端架构要点

```
src/
├── views/           # 页面：按限界上下文分
│   ├── trade/       # 交易：挂牌列表、挂牌详情、竞价大厅
│   ├── contract/    # 合同：合同列表、合同详情
│   └── delivery/    # 履约：交收进度、质检报告
├── components/      # 业务组件：可跨页面复用
│   ├── CommoditySelector    # 商品选择器
│   ├── ContractStatusTag    # 合同状态标签
│   └── DeliveryTimeline     # 履约时间轴
├── composables/     # Composition API 逻辑复用
│   ├── usePriceCalculate    # 价格计算（含税/不含税/基差）
│   └── useTradeStatus       # 交易状态机转换
├── stores/          # Pinia Store
│   ├── user.ts             # 用户信息、角色、权限
│   └── commodity.ts        # 品类树缓存
└── router/          # 路由
    └── index.ts            # 按业务角色动态路由
```

**关键设计**：
- **按角色动态路由**：采购商登录不加载销售端路由（连代码都不下载），这是你现有系统"两套UI同时加载"问题的根治方案
- **Composables封装业务逻辑**：价格计算（含税/不含税/基差换算）、状态转换规则放在composable里，不散落在组件中
- **组件按业务粒度封装**：`CommoditySelector`而不是`Table + Filter + Pagination`的机械组合

## 三、关键决策专题

### 3.1 为什么不用DDD的完整战术模式？

DDD战术模式（Aggregate/Entity/ValueObject/Repository/DomainService/DomainEvent/Factory/Specification）概念多、学习曲线陡。在B2B系统中：

| 概念 | 要不要 | 理由 |
|------|--------|------|
| Aggregate（聚合根） | **要** | 这是DDD最核心的概念，交易/合同/履约三个聚合根的边界决定了数据一致性边界 |
| ValueObject（值对象） | **要** | `Money`、`CommodityCode`、`TradeQuantity`，用JDK Record实现，零成本 |
| DomainEvent（领域事件） | **要** | 事件驱动架构的灵魂，整个系统的通信骨架 |
| Repository（仓储） | **建议要** | 隔离领域层和持久化层，方便单元测试替换 |
| DomainService | **适度用** | 当逻辑不属于任何一个聚合根时用，不要什么逻辑都往DomainService塞 |
| Factory | 可选 | 聚合根创建逻辑复杂时才需要 |
| Specification | 可选 | 复杂查询条件组合用，简单查询直接写SQL |
| ApplicationService | **要** | 事务边界、权限校验、编排调用 |

**结论**：用DDD的**战略模式**（限界上下文、上下文映射、通用语言），战术模式**挑着用**。不要为了"纯DDD"而增加不必要的复杂度。

### 3.2 读写分离的时机

| 阶段 | 做法 | 理由 |
|------|------|------|
| 原型~上线初期 | 单库 | 流量不够触发读写分离的必要性 |
| 日活破千/报表查询明显拖慢主库 | 开启读写分离 | 从库专用于报表/对账/导出 |

**不要过早优化**。读写分离带了一个隐性成本——主从延迟导致读到旧数据。这对于B2B系统是致命的（用户刚摘牌，从库还没同步，刷新页面发现挂牌还在）。

如果一定要读从库，规则是：
- **查询可读从库**：挂牌列表、商品搜索、历史合同
- **写后立刻读必须走主库**：成交后跳转的合同详情、刚发布的挂牌详情

---

### 3.3 分库分表的时机

**垂直分库（按模块）——原型阶段就做**，因为这是架构决策，不是性能优化。

**水平分表——等到不得不做的时候再做**。

判断标准：单表数据量超过1000万行，且查询/写入开始出现明显的性能下降。

B2B系统的数据量增长是有规律的：
- 钢铁行业中等规模平台，日均成交1000笔
- 一年36万笔交易，即使20年也就720万笔
- 加上挂牌、合同、履约等关联表，核心表3-5年内很难超过1000万行

**结论**：水平分表在你的规模下是"过度设计"。

## 五、选型背后的三条铁律

### 铁律1：团队经验权重大于技术先进性

RocketMQ的事务消息比Kafka优雅，但选Kafka——因为团队已经在用。PostgreSQL的JSONB比MySQL强，但选MySQL——因为DBA好招。一项技术选型的"先进性"只占决策权重的20%，团队经验、生态成熟度和运维成本占了80%。

### 铁律2：越靠近业务核心，越要用团队最熟悉的技术

交易引擎、履约流程、合同管理——这些是你的核心战场。用你最熟的技术栈（Java + MyBatis + MySQL），把认知资源留给业务建模，不要留给新框架的学习和踩坑。前端的组件库、API网关这类"非核心"领域可以适当引入新技术。

### 铁律3：每个选型都要考虑"将来换掉它的代价"

MySQL → PostgreSQL？应用代码改SQL方言，迁移成本中高。
Nacos → Consul？配置文件和注解改一改，迁移成本低。
自研网关 → Spring Cloud Gateway？全重写，迁移成本极高。

**所以自研的东西一定要想清楚——它解决的是不是只有你能解决的问题？如果不是，就不要自研。**

## 一、MySQL

### 部署

MySQL 双实例，主从架构，半同步复制。主库承接所有写入（交易/支付/合同），从库分担读负载（报表/分析/导出）。

### 核心数据域

| 数据域 | 核心内容 | 存储特征 |
|--------|---------|---------|
| **交易域** | 订单、成交、挂牌、竞价记录 | 写入密集、Q4 冬储流量暴增，金融级精度（`DECIMAL`） |
| **财务域** | 支付流水、结算单、发票、对账记录 | 不可丢、不可改、日终对账强依赖 |
| **用户域** | 客户、企业、交易员、权限 | 读多写少，变更低频 |
| **合同域** | 合同结构化字段 + MinIO 文件引用 | 与电子签章 SDK 联动，状态机驱动 |
| **仓单域** | 电子仓单、质押记录、货权变更 | 防篡改、状态机驱动（入库→在库→质押→解押→出库） |
| **配置域** | 规则配置、审批模板、租户参数 | 读多写少，热加载前置 |

### 读写分离

| 场景 | 走主/从 | 原因 |
|------|:-----:|------|
| 下单 / 支付 / 签约 / 资金操作 | **主库** | 强一致性，不容读到过期数据 |
| 历史订单查询 | 从库 | 允许秒级延迟 |
| 报表生成 / 数据导出 | 从库（专用） | 大查询不阻塞交易链路 |
| 行情 / 挂牌浏览 | **Redis 缓存** | 不直接打库 |

### 分库分表（策略，非确认具体数字）

- **决策前提**：订单表持续增长 → 单表过大时索引维护成本过高、范围查询退化。
- **分片键选择**：`customer_id`（客户 ID）——B2B 场景下绝大多数查询天然带客户维度，避免跨分片查询。
- **为什么不用时间分片**：冬储期单月数据暴增会造成热点分片，按客户 ID 分保证负载均匀。
- **路由层**：Sharding-JDBC 或自研路由中间件，应用层透明。

> ⚠️ 具体分片数（如 N 库 × M 表）属于实施细节，未在本文确认。面试话术聚焦**"为什么按 customer_id 分、不按时间分"**的 trade-off 即可。

## 二、Redis

### 部署形态

Redis 封装为**独立 Java 缓存服务**（Cache Service），不裸调。好处：统一缓存策略管理（TTL / 淘汰 / 一致性）、统一监控（命中率 / 热 Key / 大 Key）、统一降级切换。

> ⚠️ Redis 底层部署形态（Cluster / Sentinel / 单机）未在本文确认。

### 五大场景

#### 场景 1：热点缓存（String / Hash）

| 缓存内容 | 结构 | 典型 TTL | 说明 |
|---------|:---:|:------:|------|
| 实时行情价格 | String | 5s | 价格频繁变动，短 TTL 保新鲜 |
| 交易员权限 | Hash | 30min | `HGETALL` 一次取全部字段，省多次往返 |
| 商品/挂牌详情 | Hash | 10min | 读多写少，字段可单独更新 |
| 客户基础信息 | String(JSON) | 1h | 高频读取，低频变更 |

**缓存策略**：Cache-Aside + Canal binlog 兜底。写：先更新 DB 再删缓存；读：先查缓存，miss 则查 DB 回填。万一删缓存失败，Canal 监听到 DB 变更后异步刷新缓存，保证最终一致。

#### 场景 2：分布式锁（Redisson + SETNX）

| 锁场景 | 实现方式 | 为什么必须 |
|--------|---------|----------|
| 防重复提交 | `SETNX + UUID + TTL` | 大额交易不能重复创建订单 |
| 库存/保证金操作 | Redisson 看门狗（自动续期） | 并发场景下防止超卖和重复冻结 |
| 日终结算防重跑 | Redisson RLock + 较长 TTL | 多节点部署，结算只能跑一次 |

> ⚠️ Redisson 看门狗为通用方案描述。资金类关键操作可能升级为 ZooKeeper 临时顺序节点保证强一致——取决于具体场景的容忍度。

#### 场景 3：延迟队列（ZSet）

`score` = 处理时间戳，定时任务按 `score` 范围拉取到期任务。典型场景：超时未付保证金自动取消、竞价截止自动触发撮合、超时未确认收货自动划款。

**为什么用 ZSet 而非 MQ 延迟消息**：ZSet score 可精确到秒级任意时间点；支持随时查询"还有多少待处理"；不依赖特定 MQ 的延迟级别限制。

#### 场景 4：实时排行（ZSet）

`ZINCRBY` 原子更新分数，`ZREVRANGE` 取 Top N。典型场景：近 24h 交易量 Top 10（风控监控）、品种涨跌幅排行（大屏实时）、供应商履约率排行（买方选商参考）。

#### 场景 5：限流（String 滑动窗口）

`INCR + EXPIRE` 实现分钟级计数滑动窗口，超阈值拒绝。典型场景：防止单客户高频刷行情、防止恶意下单。

## 三、Kafka

### 定位

> **已确认（2026-07-18）**：系统使用 Kafka 作为统一消息中间件。

单集群靠 Topic + Partition + Consumer Group 隔离不同业务场景，运维简单、学习成本集中。

### 核心消息域

| 消息域 | 典型事件 | 生产者 | 消费者 |
|--------|---------|--------|--------|
| **交易事件** | 订单状态变更、撮合成交、履约状态变更 | 交易服务 / DS 转发 | 仓储消费组(备货/出库)、财务消费组(记账/开票)、风控消费组(额度调整)、通知消费组(Push) |
| **行情数据** | 撮合结果（价格/量/时间） | 交易核心(DS 转发) | 行情聚合服务(生成 K 线 → 推送大屏/移动端) |
| **外部回调** | 银行放款通知、仓储入库回执、物流状态、电子签章回调 | midservice 网关(接收后转发) | 各业务服务异步消费 |

> ⚠️ 具体 Topic 名称、Partition 数量、Replication Factor 均属实施细节，本文未逐项确认。面试聚焦"为什么用 Kafka 统一承载三类场景"即可。

### 可靠性设计

- **消息不丢**：Producer `acks=all` + Consumer 手动提交 offset（处理完再 ACK）
- **消息不重**：消费者幂等处理（业务唯一键 / 状态机前置判断）
- **消费失败**：死信队列兜底 + 人工补偿通道

### 事件驱动全链路

```
挂牌成功  → [LISTING_CREATED]
买方下单 → [ORDER_CREATED]   → 风控冻结额度 · 仓储预占库存
支付保证金 → [DEPOSIT_PAID]  → 财务记账 · 通知卖方备货
卖方发货 → [GOODS_SHIPPED]   → 物流创建运单 · 通知买方
买方收货 → [GOODS_RECEIVED]  → 触发质检流程
质检完成 → [INSPECTED]       → 释放尾款
尾款支付 → [FULLY_PAID]      → 开发票
发票开具 → [INVOICED]        → 通知买方
结算完成 → [SETTLED]         → 更新客户信用评级
```

## 四、ZooKeeper

### 两大核心职责

#### 职责 1：Kafka 集群协调（强依赖）

Kafka 2.x 依赖 ZK 管理：
- **Broker 注册与发现**（临时节点，Broker 下线自动清除）
- **Controller 选举**（集群唯一 Controller 负责 Partition Leader 选举）
- **Topic / Partition / ISR 元数据存储**

> 注：Consumer Group offset 新版本已迁至 Kafka 内部 Topic `__consumer_offsets`，不再依赖 ZK。

#### 职责 2：分布式锁（金融级强一致）

当 Redis 分布式锁的"主从切换锁丢失"风险不可接受时，升级为 ZK 临时顺序节点：

- **原理**：竞争者创建临时顺序节点 → 序号最小者获得锁 → 释放时删除节点 → 触发下一等待者的 Watcher 回调
- **保证**：ZAB 协议（CP）——主节点写入需半数以上 Follower 确认才返回
- **适用场景**：日终结算（绝不能重复执行）、大额资金操作互斥

> ⚠️ ZK 分布式锁在系统中的实际使用范围（哪些场景用 ZK 锁、哪些用 Redis 锁）待确认。

### 配置管理（若有）

如系统未单独部署 Nacos 等配置中心，ZK 持久节点 + Watch 机制可承担全局配置动态下发（降级开关、灰度路由等）。**此角色取决于系统实际配置治理方案。**

## 五、Hessian

### 协议边界（关键）

> **2026-07-18 校准**：
> - C ↔ Java = **TCP + 自定义二进制报文**（非 Hessian）
> - Java ↔ Java = **Hessian**（服务间 RPC）

```
C 撮合引擎 ←─TCP+自定义报文─→ DS 数据中心 (Java)
                                    │
                     ┌──────────────┼──────────────┐
                     │ Hessian      │ Hessian      │ Hessian
                     ▼              ▼              ▼
                交易服务        风控服务        财务服务
                    │              │              │
                    └──────────────┼──────────────┘
                                   │ Hessian
                     ┌─────────────┼─────────────┐
                     ▼             ▼             ▼
                合同服务       账本服务       用户服务
```

### 使用场景

12+ Java 微服务间的所有 RPC 调用走 Hessian：二进制序列化（比 JSON 体积小、解析快）、Spring 原生集成、团队已有沉淀。

### 典型调用链

```
浏览器 → midservice(网关) → 交易服务
                              │
          ┌───────────────────┼───────────────────┐
          │ Hessian           │ Hessian           │ Hessian
          ▼                   ▼                   ▼
    风控服务.checkLimit   库存服务.lock      合同服务.create
   ("客户额度是否够？")  ("锁定500吨库存")  ("生成电子合同")
          │                   │                   │
          └───────────────────┼───────────────────┘
                              │ Hessian
                              ▼
                        DS 数据中心
                   (Java对象 → 二进制报文
                    → TCP → C 撮合引擎)
```

### DS 的双协议角色

DS 数据中心是系统中最关键的"翻译官"节点——**向下对 C 讲二进制报文（性能优先），向上对 Java 服务讲 Hessian（生态友好）**。所有异构通信复杂度收敛在这一层。

## 六、Socket（TCP + 自定义二进制报文）

### 定位

专门服务于 **C 撮合引擎 ↔ DS 数据中心** 之间的高性能通信。不是通用 Socket API，是**基于 TCP 的自定义二进制报文协议**。

### 为什么自定义而不用 Protobuf / Thrift

- C 撮合引擎追求极致简单：无框架依赖、零运行时开销、字节级控制
- 报文极简（通常几十字节），解析零开销
- C 语言无 GC，延迟 100% 确定性
- 代价：协议变更需人工同步 C ↔ Java 两端 → **这恰好是契约治理的价值**，DS 作为协议转换层负责维护这份契约

### 两种通信模式

| 模式 | 场景 | 流程 |
|------|------|------|
| **同步请求-响应** | 提交撮合指令 → 等待成交回报 | DS 发报单指令，C 引擎内存撮合，纳秒级返回结果 |
| **异步落库** | 撮合结果持久化 | C 引擎撮合完成后写入内存队列，独立线程异步批量写 MySQL，不阻塞撮合主路径 |

### 报文协议（示意）

```
┌──────────┬──────────┬──────────┬──────────┐
│ 报文类型   │ 报文长度   │ 有效载荷   │  校验码   │
│ 固定偏移   │ 固定偏移   │ 变长      │ 固定偏移   │
│ 标识操作   │ 边界判定   │ 撮合指令   │ 完整性校验  │
└──────────┴──────────┴──────────┴──────────┘
```

> ⚠️ 上图仅为协议设计思路示意，具体字节偏移、字段定义、校验算法均属实施细节，未在本文确认。

### C 引擎的设计边界

C 引擎只做两件事：①接收报文指令 ②返回撮合结果。不关心 Java 任何业务逻辑，不引入 Java 运行时依赖。这是"让性能层纯粹、让业务层灵活"的架构决策。

## 七、Elasticsearch

### 索引的数据

| 索引内容 | MySQL 来源 | 搜索需求 |
|---------|-----------|---------|

### ES vs MySQL：为什么不用 LIKE

| 搜索需求 | MySQL 的困境 | ES 的优势 |
|---------|------------|----------|
| 合同全文搜索 | `LIKE '%关键词%'` 全表扫描 | 倒排索引 → "词条→文档列表" 直接定位 |
| 多条件仓单筛选 | 12 条件 + 4 表 join + 百万数据 | filter 不参与打分，位图直接命中 |
| 多维挂牌检索 | 多字段排序 + 聚合超出 B+Tree 能力 | Aggregation 一行搞定分桶 + 指标 |
| 成交聚合分析 | 多个复杂 GROUP BY | 分桶聚合 + 指标聚合一次完成 |

```
MySQL binlog → Canal → Kafka → ES Consumer → Elasticsearch
                 │
                 └──→ 缓存服务(Redis) [已确认]
```

> ⚠️ `Canal → Kafka → ES` 为基于架构合理推演的链路，具体是否走 Kafka 中转、或 Canal 直写 ES、或 Canal Adapter 方式，待确认。

### 分治架构

**ES 只存搜索需要的字段**（正文 / 标签 / 筛选维度），完整结构化数据仍在 MySQL。ES = 搜索引擎，MySQL = 真相源。

## 八、Flowable

### 驱动的流程

#### 审批流

| 流程 | 典型节点 | 多租户差异 |
|------|---------|----------|
| 挂牌审核 | 提交 → 风控 → 运营 → 上架 | 单级（中小客户）/ 三级（大客户）/ 超额加签 CEO |
| 放款审批 | 提交 → 业务经理 → 风控总监 → 总经理 | 金额阈值决定分支（如 >500 万加签） |
| 合同变更 | 提交 → 法务 → 双方确认 | 需电子签章回调 |

#### 履约流

| 流程 | 典型节点 | 关键设计 |
|------|---------|---------|
| 质检交收 | 发货 → 抽样 → 报告 → 买方确认 / 异议 | 异议处理分支，含超时自动确认 |
| 结算流程 | 收货确认 → 对账单 → 买方确认 → 财务审核 → 结算 | 跨多角色，支持自动划款 |
| 保证金退还 | 结算完成 → 风控复核 → 退款 → 到账确认 | 资金类操作，需强一致 |

### Flowable vs Saga 的分工

| | Flowable | Saga 状态机 |
|---|---------|-----------|
| 管什么 | **人**的流转（审批人、超时催办、条件分支） | **系统**的流转（微服务间数据一致性） |
| 典型场景 | "业务经理审批通过 → 流转到风控总监" | "订单已发货 → 仓储出库 + 物流创建 + 通知买方" |
| 协作方式 | 审批通过 → 触发 Saga 事件 → 推进微服务链路 |

## 面试叙事：一笔交易穿越全部组件

> "我给你讲一笔挂牌交易从发起到结算，全部组件如何协作：
>
> 买方在 Vue 前端搜索螺纹钢 → 请求走 **midservice 网关**做鉴权限流 → **Elasticsearch** 多维筛选返回挂牌列表。
>
> 选中下单 → 交易服务用 **Hessian** 调风控查额度、调仓储查库存——热点数据走 **Redis** 缓存，不直接打库。
>
> 下单请求进入 **DS 数据中心**，DS 把 Java 对象转成二进制报文，通过 **TCP Socket** 发给 **C 撮合引擎**。C 在内存中完成纳秒级撮合，异步落 **MySQL**。
>
> 撮合结果回来，DS 发 **Kafka** 事件 `ORDER_CREATED`。仓储消费组备货、财务消费组记账、风控消费组扣额度——全异步互不阻塞。
>
> 订单进入履约阶段，**Flowable** 启动质检交收流程——质检→出报告→买方确认，自动分配处理人、超时催办。
>
> 整条链路涉及多次保证金冻结/释放，**ZooKeeper** 临时顺序节点做金融级分布式锁，保证资金操作万无一失。
>
> 交易完成后，**MySQL binlog** 通过 **Canal** 同步到 **Redis** 缓存服务（加速页面访问）和 **ES**（更新历史成交索引）。
>
> ——这就是全部组件在一笔交易里的完整协作。"
