01 基础认知与数据类型

1.1 Redis 是什么？主要应用场景有哪些？高频

Redis 是一个基于 内存 的键值对 NoSQL 数据库（Remote Dictionary Server），由 C 语言编写，单机 QPS 可达 10万+。既是数据库，也是缓存，还是消息中间件。

典型场景：

  • 缓存：热点数据加速，扛住读并发（最主流）。
  • 分布式锁：SET NX EX 实现互斥，见第 10 章。
  • 排行榜：ZSet 按分数排序。
  • 计数器/限流：INCR、滑动窗口、令牌桶。
  • 消息队列：List / PubSub / Stream。
  • 社交关系：Set 做关注/粉丝/共同好友。
  • 统计类：Bitmap 签到、HyperLogLog UV、GEO 附近的人。
💡 加分点：Redis 不是"缓存"这么简单——它凭借丰富数据结构 + 原子命令 + Lua 脚本，承担了大量"在线逻辑"。

1.3 String 的三种编码：int / embstr / raw进阶
  • int：value 是整数且能用 long 表示 → 直接用 long 存，节省内存。
  • embstr：长度 ≤ 44 字节（3.2 之前是 39）→ 一次 malloc 分配 redisObject + sdshdr 连续内存，只读优化。
  • raw：长度 > 44 字节 → 两次分配，普通 SDS。
  • 一旦对 embstr 执行修改（APPEND 等），会转成 raw。
💡 追问：为什么是 44？因为 embstr 需要一次性分配 64 字节（jemalloc 分配单元），减去 redisObject(16B) 和 sdshdr8(3B) + 结束符(1B)，剩余 44 字节可存数据。
1.4 ZSet 为什么既能排序又能快速查分？进阶

ZSet 底层是 skiplist + dict 双结构：

  • skiplist：按 score 排序，支持 ZRANGE 范围查询、ZRANK 排名（O(logN)）。
  • dict：member → score 映射，支持 ZSCORE O(1) 精确查分。
  • 两者通过指针共享同一份元素，不冗余存储数据。
💡 追问：什么时候用 ziplist/listpack？元素数量 < 128 且 value 长度 < 64 字节时用 listpack 紧凑存储，超过后升级为 skiplist+dict。
1.5 高级类型：Bitmap / HyperLogLog / GEO / Stream高频
  • Bitmap：位图，基于 String 按位操作。签到（SETBIT 1 表示签）、在线状态、布隆过滤器。
  • HyperLogLog：基数统计（UV）。12KB 内存即可统计 2^64 个不同值，误差约 0.81%，不可精确回读元素。
  • GEO：经纬度地理信息，底层就是 ZSet（GeoHash 编码作 score）。附近的人：GEORADIUS。
  • Stream（5.0 引入）：可持久化的消息队列，支持消费者组、消息 ACK、Pending 列表、死信处理，是 Redis 最接近专业 MQ 的形态。
1.6 单机默认 16 个数据库，为什么通常只用 0 号库？基础

select 0~15 切换。但生产环境几乎只用 db0：

  • 多库不便于管理、难排查。
  • 集群模式下只有 db0（Cluster 不支持多库）。
  • 语义隔离应通过 key 前缀/命名空间（如 user:1001:profile）而非多库。
💡 加分点：3.x 就有人提出废弃多库；现在官方推荐用前缀隔离 + 不同 Redis 实例隔离不同业务。

02 底层数据结构

2.1 SDS（简单动态字符串）比 C 字符串强在哪？高频

SDS 结构：len + alloc + flags + buf[]，相比 C 字符串：

  1. O(1) 获取长度：C 字符串要 O(n) 遍历。
  2. 杜绝缓冲区溢出：修改前检查空间，不足自动扩容（预分配：<1MB 翻倍，≥1MB 加 1MB）。
  3. 二进制安全：以 len 判断结束而不是 \0，可存图片、序列化对象等任意二进制。
  4. 惰性空间释放：缩短字符串不立即释放，避免频繁重分配。
  5. 兼容 C 字符串函数：末尾保留 \0，能直接复用 strlen/strcat 等。
2.2 dict 字典的渐进式 rehash 怎么工作？高频

dict = 两个哈希表 ht[0]、ht[1] + rehashidx。

  • 触发扩容：used/size ≥ 1（允许扩容时）触发翻倍扩容；used/size ≥ 5 时强制扩容。
  • 触发缩容：used/size < 0.1 时缩容。
  • 渐进式：不一次性迁移所有键（会阻塞），而是 rehash 期间每次增删查改顺带迁移一个桶，直到 rehashidx 走完 ht[0] 全部桶。
  • rehash 期间：新键一律加 ht[1]；读操作先查 ht[0] 再查 ht[1]；删除两表都查。
  • 负载因子：默认 1；做 BGSAVE/BGREWRITEAOF 时（子进程 fork 期间）提高到 5，避免写时复制扩大内存。
💡 加分点：渐进式 rehash 是 Redis"单线程不能长时间阻塞"哲学的典型体现。
2.3 ziplist 是什么？为什么 7.0 被 listpack 淘汰？进阶

ziplist 是一块连续内存，按"前一个节点长度 + 编码 + 数据"紧凑排列，省内存且 cache 友好。

  • 代价：连锁更新——某节点长度变化导致后续所有节点的 prevlen 字段连锁扩容，最坏 O(n²)。
  • listpack（7.0）：每个节点只记录自身长度，不再记录前驱长度 → 彻底消除连锁更新，同时保持紧凑。
2.4 quicklist 与 linkedlist进阶
  • 3.2 前：List 元素少用 ziplist，多则 linkedlist（每个节点一个独立内存，碎片化 + 指针开销大）。
  • 3.2 起：quicklist = 双向链表 + 每节点一段 ziplist/listpack，兼顾内存紧凑与两端 O(1) 操作。
  • 配置：list-max-listpack-size（节点容量，默认 128 或 8KB）、list-compress-depth（两端外中间节点压缩，0 不压缩）。
2.5 跳表 skiplist：为什么 ZSet 用它而不是红黑树？高频

跳表 = 有序链表 + 多层索引，查找 O(logN)。

选跳表而非红黑树/AVL 的原因：

  1. 实现简单：区间/范围查询（ZRANGE）实现远比平衡树容易——跳表天然有序遍历。
  2. 增删改简单：无需复杂的旋转/染色，调整层级即可。
  3. 内存局部性可控：按需随机建层，常数因子适中（Redis 层高上限 32，概率 p=0.25）。
  4. 红黑树在单点查、内存占用上略优，但 Redis 高频操作是范围查询，跳表更合适。
💡 加分点：skiplist 的层高用随机数生成（类似抛硬币），Redis 通过 ZSKIPLIST_MAXLEVEL=32 限制层数，期望层高 ≈ 4。
2.6 intset 整数集合基础
  • 只存整数的 Set 用 intset：连续数组，按编码 int16/int32/int64 递增升级存储。
  • 升级条件：元素个数 > 512（set-max-intset-entries）或插入非整数 → 转 hashtable。
  • 升级不可逆：一旦升级为 int64 编码，删回小整数也不会降级。

03 持久化

3.1 RDB 持久化原理与触发方式高频

RDB = 内存数据的二进制快照。

触发方式：

  • 手动：SAVE（阻塞主线程）、BGSAVE（fork 子进程）。
  • 自动：配置 save 900 1 / 300 10 / 60 10000（900 秒内 ≥1 次写、300 秒内 ≥10 次、60 秒内 ≥1 万次，满足任一即 BGSAVE）。
  • 其他：主从全量同步、SHUTDOWN（无 AOF 时）也会触发。

流程（BGSAVE）：

  1. fork 子进程（此时内存几乎翻倍风险，见 3.7）。
  2. 子进程写临时 RDB 文件（利用 COW 快照内存页）。
  3. 写完后 rename 原子替换 旧 RDB。

优缺点：

  • ✅ 文件紧凑、加载快、适合备份/灾备。
  • ❌ 丢数据窗口大（两次快照间的写入全丢）。
3.2 fork + COW（写时复制）的细节进阶

fork 出的子进程与父进程共享内存页表。子进程读共享页写 RDB；父进程收到写请求时，被写的页先复制一份再修改（COW），子进程看到的仍是 fork 时刻的旧页。

  • 好处：子进程不阻塞父进程，能"瞬间"拿到一致性快照。
  • 风险：写越多，复制页越多，内存占用越高（极端可能 2 倍）；大实例 fork 本身也耗时。
  • 优化：vm.overcommit_memory=1 允许超量内存；避免 fork 期间大量写；主从的从库开 RDB 可降低主库负担。
3.3 AOF 原理与三种刷盘策略高频

AOF = 追加写命令日志（类似 binlog，存的是 Redis 协议文本）。

三种策略（appendfsync）：

策略刷盘时机性能最多丢数据
always每条命令 fsync最慢1 条命令
everysec每秒 fsync折中1 秒
no交给操作系统最快数十秒~更多
  • 默认 everysec，兼顾性能与安全。
  • fsync 调用是同步 IO，always 会显著拖慢吞吐；no 依赖内核 pdflush 策略，崩溃丢数据不可控。
3.4 AOF 重写（rewrite）原理高频

AOF 无限追加会膨胀。重写 = 用当前数据集生成最小命令集（如对 100 万次 INCR 只写 SET key 1000000）。

流程：

  1. fork 子进程，根据当前内存快照生成新 AOF（写临时文件）。
  2. 重写期间父进程把新写命令同时追加到 AOF rewrite buffer。
  3. 子进程完成后，父进程把 rewrite buffer 追加进新 AOF，rename 原子替换。
  • 触发：手动 BGREWRITEAOF 或 auto-aof-rewrite-percentage 100（AOF 增长 100%）+ auto-aof-rewrite-min-size 64mb。
  • 注意：重写期间大量写入时，rewrite buffer 也可能膨胀。
3.5 混合持久化（4.0+）进阶

aof-use-rdb-preamble yes（默认开启）：

  • AOF 重写后的文件 = RDB 快照 + 增量 AOF。
  • 加载时先快速加载 RDB 部分，再回放增量命令。
  • ✅ 兼得 RDB 的加载速度和 AOF 的丢数据窗口小；❌ 文件不再是纯文本，无法直接人肉编辑。
3.6 RDB vs AOF 怎么选？恢复流程？高频
维度RDBAOF
文件二进制快照命令文本
大小小大（重写可缩小）
恢复速度快慢
丢数据多少（everysec 丢 1s）
适用备份/灾备/冷启动数据安全要求高
  • 生产推荐：两者都开（AOF 保安全，RDB 做备份）；纯缓存场景可只开 RDB 甚至都不开。
  • 启动恢复：优先加载 AOF（数据更全），无 AOF 才加载 RDB。
  • 文件损坏：AOF 用 redis-check-aof --fix，RDB 用 redis-check-rdb。
3.7 fork 阻塞与持久化风险排查进阶
  • INFO stats 看 latest_fork_usec；INFO persistence 看 rdb/aof 状态。
  • 现象：fork 期间主线程停顿（大实例可达秒级），命令延迟飙升。
  • 优化：
  • 控制实例内存（单实例 ≤ 10GB 量级，或改用多实例）。
  • 关闭 THP（透明大页），避免 COW 页分裂放大。
  • 错峰 BGSAVE；主从都开持久化；从库开启 RDB 减少主库压力。

04 过期删除与内存淘汰

4.1 过期键的删除策略高频

Redis 采用 惰性删除 + 定期删除 结合：

  • 惰性删除：key 过期后不立即删，访问时才检查是否过期，过期则删。省 CPU，但过期 key 会残留占内存。
  • 定期删除：每 100ms 随机抽 20 个带过期时间的 key，删除其中过期的；若过期比例 > 25%，继续抽下一轮（每轮最多执行 1ms 限制，防阻塞）。
  • 为什么不用定时器逐 key 删？key 太多，扫描成本高；纯惰性又占内存 → 两者互补。
💡 追问：CPU 与内存权衡——定期删除有 hz 配置（默认 10，即每秒 10 次任务循环）。
4.2 过期键在主从复制 / 持久化中的特殊处理进阶
  • 主从：从库不主动删除过期 key（避免主从时钟不一致导致删错），等主库发 DEL 命令同步删除；但读从库时仍会按本地时间判断"逻辑过期"，返回 nil。
  • RDB：生成时过滤已过期的 key；加载时（主库）忽略过期 key。
  • AOF：删除时追加一条 DEL；AOF 重写时过滤过期 key。
4.3 内存淘汰策略（maxmemory-policy）高频

maxmemory 达到上限后按策略淘汰：

策略作用范围说明
noeviction-不淘汰，写直接报错（默认，适合对一致性敏感的缓存）
allkeys-lru所有 key最近最少使用
allkeys-lfu所有 key最不经常使用（4.0+）
allkeys-random所有 key随机淘汰
volatile-lru设置了过期时间的 key最常用
volatile-lfu设置了过期时间的 key
volatile-random设置了过期时间的 key
volatile-ttl设置了过期时间的 key剩余寿命最短的先淘汰
  • 无过期时间的 key 不受 volatile-* 影响（可能被"饿死"内存）。
  • 缓存场景建议 allkeys-lru（或 lfu）；有明确 TTL 语义用 volatile-lru。
4.4 LRU 与 LFU 的区别？Redis 为什么用"近似 LRU"？进阶
  • LRU：按"最近访问时间"淘汰；问题：一次冷数据大量读取也能把热点挤出去（如全表扫描缓存），且维护精确时间成本高。
  • LFU：按"访问频率"淘汰，兼顾频次与时间衰减（计数器随时间减半），更抗突发扫描。4.0 引入。
  • 近似 LRU：不维护全局链表，抽样 maxmemory-samples（默认 5）个 key，淘汰其中最久未用的。代价是精度略降，换来 O(1) 且无内存开销。
  • 配置：maxmemory-samples 越大越接近精确 LRU，但淘汰耗时略增。
4.5 淘汰是阻塞的吗？淘汰流程基础
  • 近似 LRU/LFU：主线程内执行，但只抽样几个 key，耗时极小。
  • 若剩余候选都不满足（无过期 key 且策略是 volatile-*），则不淘汰，写命令返回 OOM 错误。
  • 大 key 淘汰删除也会阻塞 → Redis 4.0 起支持 unlink（异步删除），淘汰默认走异步删除通道（lazyfree-lazy-eviction yes 可配）。

05 主从复制

5.1 主从复制的作用与拓扑基础
  • 作用：读写分离（主写从读）、数据冗余、故障时从库晋升、为哨兵/集群提供基础。
  • 拓扑：一主一从、一主多从、主从链（从库再挂从库，缓解主库全量同步压力）。
  • 命令：REPLICAOF host port（7.0 前为 SLAVEOF）；取消：REPLICAOF no one。
  • 复制是异步的：主库执行写命令后立即返回，通过传播给从库。
5.2 全量复制的完整流程（PSYNC）高频

触发：从库首次连接、或增量同步不可用（backlog 不够）。

从库 → 主库: PSYNC ? -class="num">1
主库: 生成 replid，启动 BGSAVE，写入 repl backlog
主库 → 从库: +FULLRESYNC <replid> <offset>
主库: 发送 RDB 快照（期间新写命令进 backlog）
主库 → 从库: 发送 backlog 中的增量命令
从库: 清空旧数据 → 加载 RDB → 追加重放增量 → 建立连接持续收增量

关键点：

  • 同步期间从库清空自身数据，期间对外读可能返回空（replica-serve-stale-data 可配是否允许读旧数据）。
  • RDB 传输/加载阶段从库阻塞，大实例全量同步耗时可观。
  • 主库 fork 做 BGSAVE 也有阻塞与内存翻倍风险（见 3.7）。
5.3 增量复制与复制积压缓冲区（backlog）高频
  • 断线重连后，从库发 PSYNC <replid> <offset>。
  • 主库检查 offset 是否仍在 repl_backlog（默认 1MB，环形缓冲区）内：
  • 在 → +CONTINUE，只补发断线期间的增量命令。
  • 不在（断线太久，数据被覆盖）→ 退化为全量同步。
  • backlog 大小建议按 重连耗时 × 每秒写量 估算，太小的后果是频繁全量同步。
💡 追问：主从切换后如何继续增量？Redis 用 replid 与 replid2：主库切换后从库拿 replid2 匹配新主库，只要 backlog 里还有数据就能增量续传，避免全量。
5.4 主从数据不一致与延迟怎么处理？进阶
  • 根因：复制异步，从库有网络/加载延迟；INFO replication 可看 master_repl_offset 与从库 offset 差值。
  • 缓解：
  • repl-disable-tcp-nodelay no：小包立即发送（牺牲一点带宽换低延迟）。
  • 从库本地读缓存写放大：replica-read-only yes（默认，从库只读）。
  • 强一致场景不要走 Redis 主从读：业务上对一致性敏感的操作必须打主库或加缓存版本号校验。
  • 配置 min-replicas-to-write + min-replicas-max-lag：从库落后过多时主库拒绝写入（牺牲可用性换一致性）。
5.5 读写分离有哪些坑？高频
  1. 读到旧数据：主从延迟 → 刚写就读从库可能读不到 → 一致性敏感操作读主。
  2. 从库宕机/延迟飙升：客户端要具备故障转移和延迟降级。
  3. 缓存场景放大写放大：热点更新频繁时，把"缓存更新"也复制到从库，从库内存/CPU 白白翻倍。
  4. 主库 BGSAVE 全量同步期间，从库短暂不可服务。
  5. 只适合读多写少、容忍秒级延迟的业务。

06 哨兵 Sentinel

6.1 Sentinel 解决什么问题？基础

主从复制本身不能自动故障转移：主库挂了，从库不会自己上位，客户端也不知道新主是谁。

Sentinel（哨兵）提供：

  1. 监控：持续检查主从健康。
  2. 通知：故障通知运维/系统。
  3. 自动故障转移：选从库晋升为新主，并让其他从库重新指向新主。
  4. 配置中心：客户端通过哨兵拿当前主库地址。
6.2 主观下线（sdown）与客观下线（odown）进阶
  • 主观下线 sdown：单个哨兵发现主库 down-after-milliseconds 内无响应（PING 超时），标记"疑似下线"。
  • 客观下线 odown：≥ quorum 个哨兵都认为主库 sdown，才确认主库真的挂了，进入故障转移。
  • 防止网络分区误判：单哨兵可能因自身网络抖动误判，需要多哨兵"投票"确认。
6.3 故障转移（failover）完整流程高频
  1. 判定 odown：哨兵 A 发现主库 sdown，向其他哨兵广播"我认为主库挂了"，收到 ≥ quorum 个确认 → odown。
  2. 选举 leader 哨兵：故障转移由一个哨兵执行。候选哨兵向其他哨兵要选票，获得半数以上（超过 quorum） 即成为 leader（Raft 类似算法）。每个哨兵一个配置纪元只能投一票。
  3. leader 选新主：筛选在线且数据最新的从库，按优先级排序：
  • replica-priority 越小越优先；
  • 复制偏移量越大（数据越新）越优先；
  • 再相同按 runid 字典序。
  1. 切换：向新主发送 SLAVEOF NO ONE → 其他从库 SLAVEOF 新主 → 通知客户端更新主库地址 → 旧主恢复后变成新主的从库。
💡 加分点：Sentinel 至少部署 3 个（奇数）——quorum 机制要求多数派才能决策，2 个哨兵时恰好一个分区各占一个，谁都凑不齐 quorum，故障转移瘫痪。
6.4 脑裂（split-brain）问题进阶

脑裂场景：主库与哨兵网络隔离，但主库仍活着 → 哨兵选出新主 → 旧主继续接收写入 → 恢复后旧主降级为从库，这部分写入全部丢失。

解决：

  • min-replicas-to-write 1 + min-replicas-max-lag 10：主库发现从库失联超过阈值就拒绝写入，把"被隔离期间的写入"挡在门外。
  • 本质：用牺牲可用性换取一致性，丢失窗口被压缩到不可接受范围之外。
6.5 客户端如何感知主从切换？基础
  • 客户端先向哨兵查询：SENTINEL get-master-addr-by-name <name>。
  • 客户端订阅哨兵频道 +switch-master 事件，主库变更时自动刷新连接。
  • 主流客户端（如 Jedis Sentinel / Lettuce / Redisson）内置此逻辑。

07 集群 Cluster

7.1 Cluster 的槽位（slot）机制高频
  • 数据分片：整个 key 空间划分为 16384 个槽，slot = CRC16(key) % 16384。
  • 每个节点负责一段槽区间（CLUSTER ADDSLOTS），读写只路由到对应节点。
  • 客户端缓存"槽 → 节点"映射表；连接错误节点时返回 MOVED 重定向。
  • 每个主节点可挂从节点做高可用（哨兵逻辑内嵌）。
7.2 为什么槽数量定 16384 而不是 65536？进阶

官方解释（Redis 作者 antirez）：

  1. 心跳包体积：节点间 gossip 用 bitmap 表示槽分布，16384 槽 = 2KB 的 bitmap；65536 槽 = 8KB，节点多时网络开销翻 4 倍。
  2. 集群规模上限：16384 槽配合每节点承载上千槽，已足够支撑千节点级集群（实际生产几十上百节点）。
  3. 设计权衡：槽是静态的，节点少时 65536 反而浪费；传输、计算成本都高于收益。
7.3 MOVED 与 ASK 重定向的区别高频
  • MOVED：槽已经迁移完成，目标节点明确。客户端收到后更新本地槽映射缓存，下次直连新节点（持久性）。
  • ASK：槽正在迁移中（源节点只剩部分 key，目标节点已有部分 key）。仅对当前请求临时重定向，客户端不更新缓存（一次性）。
  • 两者都是返回给客户端的错误/提示，客户端需正确处理并重试。
7.4 集群节点间通信：gossip 协议进阶
  • 节点间用独立的 集群总线端口（16379），与客户端端口（6379）分离。
  • 每个节点定期与其他节点交换状态：MEET（握手加入）、PING/PONG（心跳 + 携带节点状态信息）。
  • 通过 gossip 传播：节点故障检测、槽分配变更、配置纪元。
  • 故障判定类似哨兵：半数以上主节点认为某节点不可达 → 标记 FAIL，触发从节点提升。
7.5 扩容/缩容与数据迁移进阶
  • 新增节点：CLUSTER MEET 加入集群 → CLUSTER RESHARD 从其他节点迁槽。
  • 迁移以 slot 为粒度、key 为单位：源节点对目标节点执行 MIGRATE 命令，逐 key 搬运。
  • 迁移中该槽处于 migrating/importing 状态 → 客户端访问触发 ASK 逻辑。
  • 缩容：迁走节点的所有槽后 CLUSTER FORGET 移除。
💡 加分点：cluster-require-full-coverage（默认 yes）：部分槽没有节点覆盖时整个集群拒绝服务；改为 no 可让集群降级可用（部分数据访问失败）。
7.6 Cluster 的使用限制与踩坑高频
  1. 多键操作必须同槽：MSET、Lua、事务涉及多个 key 时，必须用 hash tag（{user1001}:cart 按 {} 内内容算槽）保证落在同一节点。
  2. 不支持跨节点事务。
  3. pipeline 跨节点会被打散，需按节点分组发送。
  4. 只有 db0。
  5. 小数据量别上集群：单机 10 万 QPS 足够时，集群反而引入路由、迁移、运维复杂度。

08 缓存三大问题与一致性

8.1 缓存穿透（cache penetration）高频

现象：查询一个必然不存在的数据，缓存和数据库都查不到 → 每次请求都打数据库，DB 压力被放大。

原因：恶意攻击或代码漏洞，构造大量不存在的 key。

解决：

  1. 缓存空值：查不到也缓存 key → null，TTL 设短（如 5 分钟），并加随机防止同时失效。
  2. 布隆过滤器：请求先过布隆，判定"一定不存在"直接拒绝，不查缓存和 DB。
  3. 接口层参数校验：非法 ID（负数、超范围）直接拦截。
  4. 监控空值命中率异常波动。
8.2 缓存击穿（cache breakdown / hot key expire）高频

现象：某一个热点 key 在过期瞬间，大量并发请求同时打到 DB。

解决：

  1. 互斥锁：缓存失效后，只有一个线程去查 DB 重建缓存，其余线程等待或返回旧值（注意死锁与超时）。
  2. 逻辑过期：value 里存逻辑过期时间，过期后异步重建缓存，请求先返回旧数据——不阻塞读。
  3. 热点永不过期：后台定时刷新（不设物理过期，用逻辑过期控制）。
  4. 热点 key 预热 + 多副本分散。
8.3 缓存雪崩（cache avalanche）高频

现象：

  • 大量 key 同一时刻过期 → 同时打 DB；
  • 或 Redis 整体宕机 → 请求全部打到 DB，DB 被压垮。

解决：

  1. 过期时间加随机：基础 TTL + random(0~300s)，避免集中失效。
  2. 多级缓存：本地缓存（Caffeine）+ Redis，Redis 挂了本地还能扛。
  3. Redis 高可用：主从 + 哨兵 + 集群，避免单点宕机。
  4. 限流降级：DB 侧限流、熔断、降级返回兜底数据。
  5. 提前预热：大促前把热点数据刷进缓存并分散过期时间。
8.4 缓存与数据库一致性方案高频

主流方案 Cache Aside（旁路缓存）：

  • 读：先读缓存，未命中读 DB → 写回缓存。
  • 写：先更新 DB，再删除缓存（不是更新缓存）。

为什么"先删缓存再更新 DB"不行：删除后、更新 DB 前，并发读会把旧值写回缓存 → 缓存里长期是脏数据。

为什么"更新缓存"不行：写频繁时缓存被反复无效更新，且与 DB 更新非原子。

一致性增强：

  1. 延迟双删：更新 DB 后删缓存，等 ~1s 再删一次，兜住中间窗口的脏回写。
  2. binlog 订阅（canal）：应用只写 DB，canal 监听 binlog 异步删缓存——解耦、可靠、主流。
  3. 版本号/时间戳：缓存带 version，回写时校验，旧的写不进去。
💡 结论：缓存一致性只能做到最终一致；强一致场景不应依赖缓存（直接读 DB 或用分布式事务）。
8.5 缓存粒度与更新策略选型进阶
  • 缓存粒度：对象级（整个 user 对象）vs 字段级。对象级实现简单、命中率高；字段级内存省但逻辑复杂。一般对象级 + 序列化。
  • 写策略对比：
  • Cache Aside：实现简单，适合读多写少。
  • Write Through / Write Behind：强一致/异步写回，实现复杂，Redis 场景少用。
  • 缓存命中率目标：> 95%，用 INFO stats 的 keyspace_hits/keyspace_misses 监控。

09 事务与 Lua

9.1 Redis 事务的组成与原理高频

命令：MULTI（开启）→ 命令入队（不执行）→ EXEC（批量执行）/ DISCARD（取消）。

  • 原子性：EXEC 时队列中命令连续执行完，期间不穿插其他客户端的命令（单线程 + 整体执行）。
  • WATCH：乐观锁。WATCH 的 key 在 EXEC 前被其他客户端修改，则 EXEC 直接返回空（事务作废），配合重试实现 CAS。
  • 隔离性：事务执行期间不会被其他命令打断 → 天然串行。
💡 加分点：Redis 事务更像"批量执行 + 乐观锁"，而不是关系数据库的事务——它没有回滚、没有隔离级别概念。
9.2 Redis 事务为什么不支持回滚？进阶

官方设计取舍：

  1. 命令错误在入队阶段就能发现（语法错误/命令不存在），此时整批拒绝，不存在"执行到一半失败"的语法问题。
  2. 运行时错误（如对 String 执行 LPUSH）本质是编程错误，回滚也无法恢复业务语义。
  3. 回滚会增加实现复杂度，违背 Redis"简单高效"的哲学。
  • 注意：EXEC 时某条命令运行失败，其他命令照常执行，不会整体回滚。
9.3 Lua 脚本：为什么能保证原子性？高频

Redis 2.6 引入 Lua：EVAL script numkeys key... arg...。

  • 原子性：Lua 脚本在服务端一次性执行，执行期间 Redis 不处理任何其他命令 → 读改写无竞态。
  • 减少网络往返：复杂逻辑一次 RTT 完成。
  • 典型应用：秒杀扣库存（GET → 判断 → DECR）、分布式锁续期、限流计数。
  • 脚本可以用 redis.call() / redis.pcall() 调用命令；redis.call 出错会中断脚本。
💡 追问：Lua 与事务的区别？事务=命令批量排队执行，无逻辑判断；Lua=在服务端执行一段程序，可读改写、可判断，原子性更强更灵活。7.0 的 Redis Functions 可把 Lua 函数化部署管理，替代 EVAL 散落的脚本。
9.4 pipeline 与事务、Lua 的区别基础
  • pipeline：客户端批量发送命令减少 RTT，不保证原子（命令之间可能插入其他请求）。
  • 事务：服务端排队 + EXEC 原子执行，但不减少"入队"那次的 RTT 开销。
  • Lua：服务端执行，既原子又少 RTT，是三者中"功能最强"的。
  • 组合用法：pipeline + 多条独立命令 提升吞吐；关键一致性操作用 Lua。

10 分布式锁

10.1 分布式锁的基本实现高频

最简：SET lock:order key value NX PX 30000

  • NX：key 不存在才设置成功（互斥）。
  • PX：自动过期，防死锁（加锁进程崩溃也不怕）。
  • 一定要 SET 一条命令原子完成，不能用 SETNX + EXPIRE 两步（中间崩溃就死锁）。

value 存什么？客户端唯一标识（UUID/请求 ID），用于解锁时校验"只能解自己的锁"。

10.2 误删锁与安全解锁高频

问题：A 拿到锁，业务执行超时，锁自动过期；B 拿到锁；A 执行完去 DEL，把 B 的锁删了 → 互斥失效。

解决：解锁前校验 value 是自己的，且校验+删除必须原子（Lua）：

-- KEYS[1]=lock key, ARGV[1]=clientId
if redis.call(class="st">"get", KEYS[class="num">1]) == ARGV[class="num">1] then
return redis.call(class="st">"del", KEYS[class="num">1])
else
return class="num">0
end
10.3 Redisson 看门狗（WatchDog）续期机制进阶
  • 默认锁有效期 30 秒；持有锁的线程业务没执行完怎么办？
  • Redisson 启动一个后台定时任务（看门狗）：锁剩余时间 < 1/3 有效期时自动续期到 30s，直到业务显式解锁。
  • 客户端崩溃 → 看门狗随进程消失 → 锁到期自动释放，不会死锁。
  • 实现基于 Lua（可重入 Hash + 过期 + 续期）。
10.4 RedLock 多节点锁与争议进阶

背景：单主 Redis 锁在主从切换时会丢：A 在旧主加锁 → 旧主没同步就挂了 → 新主没有锁记录 → B 也能加锁成功 → 互斥失效。

RedLock 思想：在 N 个独立 Redis 节点（通常 5）上都加锁，成功 ≥ N/2+1 个才算持有。

  • 用途：对一致性要求极高（如金融扣款、幂等控制）时。
  • 争议（Martin Kleppmann vs antirez）：
  • Kleppmann：RedLock 依赖时钟，GC 停顿/时钟跳跃仍可能破功；分布式锁的正确姿势是 Fencing token（锁携带单调递增令牌，写入时校验，旧令牌拒绝）。
  • antirez：工程上 RedLock 已足够，配合足够短的有效期，可把风险降到可接受。
  • 实践结论：绝大多数业务用单节点 Redis 锁 + 看门狗就够；要绝对安全请用 ZooKeeper/etcd（顺序节点 + 会话超时）或带 fencing token 的落库校验。
10.5 分布式锁还有哪些细节考点？进阶
  1. 可重入：同一线程重复加锁不阻塞（Redisson 用 Hash：field=线程 ID，计数 +1）。
  2. 锁粒度：尽量细（按订单/用户维度），避免全局一把锁拖垮并发。
  3. 加锁失败处理：自旋重试（带超时上限）或快速失败返回。
  4. 业务执行时间 > 锁有效期：看门狗续期，或预估最长执行时间设置合理 PX。
  5. 等锁时间与最大持有时间分开设置，防线程池耗尽。
  6. 锁与业务操作同一事务边界，避免"加锁后 DB 操作失败锁不释放"。

11 高性能机制

11.1 Redis 为什么是单线程模型？单线程为什么还这么快？高频

Redis 命令执行是单线程（网络 IO 与命令处理主体为单线程；6.0 起网络 IO 可多线程）。

为什么快：

  1. 纯内存操作：数据都在内存，无磁盘 IO（持久化异步）。
  2. 单线程避免上下文切换与锁竞争：无锁、无竞态，天然原子。
  3. IO 多路复用：epoll 监听大量连接，非阻塞处理网络。
  4. 高效数据结构：SDS、跳表、压缩结构针对场景优化。
  5. 代码路径短：核心命令都是简单 C 实现，无复杂调度。

为什么坚持单线程：

  • 多线程带来的锁竞争、上下文切换、缓存失效开销可能大于收益；
  • 单线程让原子性天然成立（事务/Lua/分布式锁都受益）；
  • 瓶颈在内存与网络带宽，不在 CPU。
11.2 IO 多路复用：select / poll / epoll进阶
  • Redis 通过 aeEventLoop 封装 epoll（Linux）/kqueue（macOS）/select（兜底）。
  • epoll 优势：epoll_create + 内核事件表；O(1) 获取就绪事件（select/poll 是 O(n) 扫描）；水平触发/边缘触发；避免每次调用重新拷贝 fd 集合。
  • Redis 对每个事件：读事件 → 解析命令 → 执行 → 写事件回包。
  • 单线程事件循环让上万个连接共享一个线程而不互相阻塞。
11.3 文件事件与时间事件进阶
  • 文件事件：客户端连接/读写就绪，回调处理。
  • 时间事件：定期任务（serverCron，每 100ms）——过期键清理、AOF 刷盘、主从心跳、统计信息、集群检查等。
  • 事件循环：优先处理文件事件，时间事件按到期时间执行，两者共享单线程。
11.4 Redis 6.0 引入多线程 IO，为什么？进阶

背景：瓶颈不在 CPU，而在网络读写（read/write 系统调用 + 协议解析的 memcpy），大流量时单线程处理网络 IO 成为瓶颈。

6.0 方案：

  • 默认关闭；io-threads 4、io-threads-do-reads yes 开启。
  • 读/写 socket 用多个 IO 线程并行（把数据从内核缓冲搬入/搬出），命令执行仍由主线程串行 → 保持原子性与无锁。
  • 收益：网络吞吐提升明显（尤其多客户端、大 value）；对纯计算型负载无增益。
💡 加分点：Redis 7.0 继续优化：共享 IO 线程任务、减少锁竞争；7.2 引入异步 socket 写等。永远记住：执行模型仍是单线程，这是所有原子性保证的根基。
11.5 慢查询与延迟排查进阶
  • 慢日志：slowlog-log-slower-than 10000（微秒，默认 10ms）、slowlog-max-len 128；SLOWLOG GET 查看。
  • 常见慢命令：KEYS *（全量扫描，O(N) 阻塞）→ 用 SCAN 游标迭代替代；SMEMBERS/HGETALL/LRANGE 大集合；SORT；大 value 的 GET/SET。
  • 延迟监控：redis-cli --latency、INFO commandstats（各命令耗时统计）、latency monitor。
  • 排查顺序：慢日志 → 大 key（--bigkeys）→ 网络/内核参数 → fork/持久化阻塞 → 内存碎片。

12 大 Key / 热 Key / 内存治理

12.1 大 Key 的危害与发现高频

定义（经验值）：String value > 10KB；集合元素 > 5000 个或整体 > 10KB。

危害：

  1. 阻塞：删除（DEL）、序列化（SAVE/迁移）、HGETALL 等耗时飙升，阻塞主线程。
  2. 网络：一次大 value 传输占用带宽、拖慢其他命令。
  3. 内存：倾斜（分片不均）、内存碎片。

发现：

  • redis-cli --bigkeys（按类型抽样扫描）。
  • MEMORY USAGE key 精确查看单个 key 内存。
  • SCAN + 类型命令（LLEN/SCARD/HLEN/STRLEN）自研巡检脚本。
  • 结合监控：节点内存不均、慢查询命令为集合类时重点怀疑。
12.2 大 Key 怎么治理？进阶
  1. 拆分：大 value 拆成多个小 key（如 hash 按字段拆、list 按页拆），或大集合拆多个。
  2. 压缩/降级：大对象压缩后存储；图片等二进制放 OSS，Redis 只存 URL。
  3. 异步删除：UNLINK key（4.0+，后台线程回收），或开启 lazyfree-lazy-* 系列配置，DEL 自动异步化。
  4. 避免产生：写库层限制单 key 大小、定期清理过期大集合（EXPIRE + 后台扫描）。
12.3 热 Key 的发现与处理高频

发现：

  • 客户端本地计数（访问频率最高的 key 上报）。
  • redis-cli --hotkeys（需开启 LFU 策略）。
  • MONITOR 抽样（线上慎用，有性能开销）。
  • 代理层（如 Codis/Twemproxy/自研网关）统计。

处理：

  1. 本地缓存（Caffeine）：热 key 直接命中 JVM，Redis 只做兜底——最有效。
  2. 多副本 / 读写分离：热 key 拆成 key:0~key:N 多个副本分散到不同节点，读随机选一个。
  3. 热点限流：对单 key 访问频率限流，保护下游。
  4. 避免把全部流量打到单节点（集群下热 key 所在节点会成为瓶颈）。
12.4 内存碎片与内存分析进阶
  • INFO memory：used_memory（数据）、used_memory_rss（进程实际占用）、mem_fragmentation_ratio（RSS/used，>1.5 表示碎片高）。
  • 碎片来源：频繁增删改、大 key 删除后空间未归还。
  • 处理：CONFIG SET activedefrag yes（自动整理）；重启（不推荐）；MEMORY PURGE（整理 jemalloc 缓存）。
  • 内存分析工具：redis-rdb-tools（rdb 转 CSV 分析各 key 占用）、MEMORY DOCTOR 诊断。

13 高频场景题

13.1 秒杀系统如何防超卖？高频

链路：限流 → 预扣库存 → 异步下单 → 对账回补。

  • Lua 原子预扣（关键）：
-- KEYS[1]=stock:sku, ARGV[1]=userId
local stock = tonumber(redis.call(class="st">"get", KEYS[class="num">1]) or class="num">0)
if stock <= class="num">0 then return class="num">0 end
redis.call(class="st">"decr", KEYS[class="num">1])
redis.call(class="st">"sadd", class="st">"users:" .. KEYS[class="num">1], ARGV[class="num">1]) -- 幂等：一人一单
return class="num">1
  • 预扣成功 → 发 MQ 异步下单（削峰）→ DB 幂等兜底（订单号唯一索引）。
  • 回补：订单超时未支付/取消 → 库存 +1（同样走 Lua）。
  • 防超卖本质：把"读-判断-写"变成原子条件更新，杜绝并发窗口。
13.2 排行榜怎么实现？高频

ZSet：ZADD rank:game1 100 userA，分数即分值。

  • 实时更新：ZINCRBY rank:game1 10 userA。
  • TopN：ZREVRANGE rank:game1 0 99 WITHSCORES（O(logN+M)）。
  • 排名：ZREVRANK；同分排序规则：ZREVRANGEBYSCORE 按成员字典序。
  • 分页：ZREVRANGE WITHSCORES 配合 limit。
  • 千万级用户也毫无压力（skiplist 保证 O(logN)）。
13.3 用 Redis 实现消息队列高频

三种方案对比：

方案可靠性消费者组适用
List（LPUSH+BRPOP）一般（BRPOPLPUSH 可确认）无简单任务队列
PubSub不持久（发布即焚，离线收不到）无实时广播/通知
Stream（5.0+）持久化 + ACK + Pending✅生产级轻量 MQ

Stream 关键概念：XADD（追加消息）、XREADGROUP（消费者组消费）、XACK（确认）、XPENDING（未确认列表）、死信处理 XCLAIM。

💡 加分点：Stream + 消费者组 + Pending + ACK，可以做到"至少一次"投递；业务要求强顺序/事务性时仍建议专业 MQ（Kafka/RocketMQ）。
13.4 分布式限流方案高频
  • 固定窗口：INCR key + 首次 EXPIRE（简单，有临界突刺问题：窗口交界可双倍流量）。
  • 滑动窗口：ZSet 记录时间戳，ZREMRANGEBYSCORE 清窗口外 + ZCARD 计数（精确，内存随请求量增长）。
  • 令牌桶（Lua 原子实现）：按速率补令牌，突发可控，最常用：
-- KEYS[1]=bucket, ARGV[1]=capacity, ARGV[2]=rate, ARGV[3]=now
local t = tonumber(redis.call(class="st">"get", KEYS[class="num">1] .. class="st">":ts") or ARGV[class="num">3])
local tokens = tonumber(redis.call(class="st">"get", KEYS[class="num">1] .. class="st">":tk") or ARGV[class="num">1])
tokens = math.min(tonumber(ARGV[class="num">1]), tokens + (tonumber(ARGV[class="num">3]) - t) * tonumber(ARGV[class="num">2]))
redis.call(class="st">"set", KEYS[class="num">1] .. class="st">":ts", ARGV[class="num">3])
if tokens < class="num">1 then return class="num">0 end
redis.call(class="st">"set", KEYS[class="num">1] .. class="st">":tk", tokens - class="num">1)
return class="num">1
  • 网关层（Nginx + Lua / Sentinel）做全局限流，应用层做业务维度限流。
13.5 布隆过滤器进阶

原理：bitmap + k 个 hash 函数。写入把 k 个位全置 1；查询 k 个位不全为 1 → 一定不存在；全为 1 → 可能存在（有误判率）。

  • 误判率公式：p ≈ (1 - e^(-kn/m))^k，m=位数组大小，n=元素数，k=hash 数。
  • 支持删除的变体：Counting Bloom Filter（计数位）。
  • Redis 原生 bitmap 可手写；生产用模块 RedisBloom（支持 BF.ADD / BF.EXISTS，含误判率参数）。
  • 应用：缓存穿透防护、黑名单、爬虫去重、推荐系统去重。
13.6 附近的人 GEO基础
  • 存：GEOADD city:users 116.39 39.90 userId（底层 ZSet，score=GeoHash 编码）。
  • 查：GEORADIUS city:users 116.39 39.90 5 km WITHDIST（5 公里内，带距离）。
  • GEOSEARCH（6.2+）支持更灵活的范围/形状查询。
  • 注意：GEO 精确度约米级（GeoHash 球面编码），足够 LBS 场景；高精度需求需专业地理位置服务。
13.7 签到与 Bitmap基础
  • 签到：SETBIT sign:2026-08 userId 1（按年/月建 key，bit 位=日期）。
  • 查询连续签到：BITFIELD GET u31 0（取 31 位）→ 位运算数末尾连续 1。
  • 统计本月签到天数：BITCOUNT sign:2026-08。
  • 优点：一个用户一年才 365bit≈46 字节，千万用户也只需几十 MB。
13.8 UV 统计 HyperLogLog基础
  • PFADD page:uv:0815 userA userB ...，PFCOUNT 得基数。
  • 内存固定 ~12KB（无论统计多少），误差约 0.81%，无法回读具体用户。
  • 适用：UV、独立访客、搜索词去重等只关心"有多少个不同值"的场景。
  • 精确统计小规模（如 <1000）用 Set；超大规模用 HLL 近似。
13.9 延迟队列（定时任务）进阶

方案：ZSet，score = 下次执行时间戳。

  • 入队：ZADD delay_queue now+5s taskId。
  • 消费（轮询 + 重投）：
local item = redis.call(class="st">"zrangebyscore", KEYS[class="num">1], class="num">0, ARGV[class="num">1], class="st">"limit", class="num">0, class="num">1)
if item[class="num">1] then
redis.call(class="st">"zrem", KEYS[class="num">1], item[class="num">1]) -- 原子取出：先查再删（lua 保证）
return item[class="num">1]
end
  • 到期任务投递到工作队列（List/Stream）异步执行；执行失败重新入队（带重试次数）。
  • 应用：订单超时关闭、优惠券到期提醒、异步对账。
💡 加分点：多消费者竞争时用 Lua 保证"取出+删除"原子，避免重复消费；或用 Stream 的 XREADGROUP + XACK 更稳。

14 进阶与生态

14.1 Redis vs Memcached高频
维度RedisMemcached
数据类型5 大类型 + 高级类型仅 String
持久化RDB / AOF无
集群Cluster 原生分片客户端分片（一致性哈希）
线程模型单线程事件循环多线程
内存管理jemalloc + 多种编码优化slab 分配
功能事务/Lua/发布订阅/Stream/分布式锁纯缓存
适用缓存 + 业务逻辑 + 中间件极简 KV 缓存

结论：Redis 功能全面替代 Memcached；Memcached 仅在"极致简单、多线程大吞吐"的纯缓存场景还有价值。

14.2 Redis vs 本地缓存（Caffeine/Guava）进阶
维度本地缓存Redis
访问速度纳秒级（JVM 堆内）微秒级（网络 RTT）
一致性多实例各自为政，容易不一致全局唯一
容量受单机 JVM 内存限制可横向扩展（集群）
失效通知无发布订阅/版本号可做
适用热点 key 二级缓存、防击穿全局共享缓存

最佳实践：本地缓存 + Redis 两级缓存——本地扛热点（命中率 90%+），Redis 做全局一致层，本地过期走 Redis 兜底。注意两级缓存的一致性：本地 TTL 尽量短或用版本号失效。

14.3 Redis 7.0 重要变化进阶
  1. listpack 全面替代 ziplist，消除级联更新；配置项改名 *-max-listpack-entries。
  2. Redis Functions：Lua 函数化注册管理（FUNCTION LOAD），替代散落 EVAL，支持权限控制。
  3. ACL v2：key 权限支持通配符与更细粒度。
  4. Sharded Pub/Sub：集群下广播只发到相关分片，解决广播风暴。
  5. 命令维度 TLS、lazy free 增强、内存效率提升（大 value 场景更省）。
  6. Redis 8.0（2025）进一步聚焦 AI：内置 Vector Set（向量集）、Redis Data Integration（RDI）数据管道、LLM 缓存等，原生支持 AI 应用缓存与向量检索。
14.4 Redis 安全加固高频
  1. ACL：按用户分配命令/key 权限（Redis 6+），最小权限原则。
  2. 禁用危险命令：rename-command KEYS ""、FLUSHALL、CONFIG、DEBUG、EVAL（按需）。
  3. 网络隔离：bind 内网IP、protected-mode yes、不暴露公网；必要时走专用网络/VPC、SSL。
  4. 认证：requirepass 强密码；生产用 ACL 用户更细粒度。
  5. 其他：升级版本修 CVE、监控慢命令、限制 maxmemory 防 OOM 拖垮机器。
14.5 Redis 线上故障排查思路进阶

按现象定位：

  • 延迟飙升：SLOWLOG → 大 key（--bigkeys）→ fork/持久化 → 网络/内核 → 内存碎片。
  • 内存暴涨：MEMORY USAGE + redis-rdb-tools 分析 → 无效 key（过期策略没触发）→ 大 value → 连接数（buffer）。
  • 连接数打满：客户端连接池配置（maxTotal）、慢命令占线程、timeout 配置、连接泄漏。
  • OOM/淘汰：maxmemory + 淘汰策略不当 → 调整策略、扩容、治理大 key。
  • 主从不同步：INFO replication 看 offset 差距 → 网络带宽 → backlog 过小导致频繁全量。
  • 集群数据倾斜：CLUSTER INFO / CLUSTER NODES 看槽分布与内存 → 热 key 分片、hash tag 使用不当。
  • 监控指标：INFO stats/commandstats/memory/replication + Redis Exporter + Grafana。
14.6 单机性能与容量估算基础
  • 单机 QPS：读 10w+、写 8w+（受 value 大小、网络、机器影响）。
  • 单机内存：建议 ≤ 10GB（fork 成本、全量同步时间、RDB 加载时长可控）。
  • 容量规划：总数据量 × (1 + 索引/编码开销 20~50%)；集合类按元素估算。
  • 压测：redis-benchmark -t set,get -n 1000000 -c 100，关注 P99 延迟（< 1ms 为佳）。
  • 部署：主从 + 哨兵是标配；数据量大/写入高再上 Cluster；核心链路加本地缓存兜底。
