# B2B平台参数组合爆炸问题 — 架构级治理方案分析

> 面向技术经理的架构决策文档 | 2026-07-22

---

## 一、问题诊断：这不是技术问题，是"产品治理"缺位

你描述的现象非常经典，但根因比表面看到的更深。让我们先做一层根因分析：

### 1.1 表面症状

```
客户A要特殊逻辑 → 加参数 enable_a_feature
客户B要不同逻辑 → 加参数 enable_b_logic  
客户C要特殊流程 → 加参数 switch_c_process
```

代码变成：
```java
if (enableA && enableB && !enableC) { ... }
else if (!enableA && enableB) { ... }
```

### 1.2 真正的三层根因

| 层次 | 根因 | 表现 |
|------|------|------|
| **产品层** | 缺乏"能力抽象"。每个客户需求直接映射到一个参数，没有抽象出可复用的能力单元 | 参数数量 = 客户需求数量 |
| **架构层** | 参数与客户直接耦合，没有"能力→套餐→客户"的中间层 | A的参数影响B的行为 |
| **流程层** | 缺少参数生命周期管理。谁加的？为什么加？能否删？都不知道 | 参数只增不减，成为历史债务 |

### 1.3 最关键的一点（方案里没点透）

**"为A客户加的参数，B客户也能用"——这个不是Bug，是你们缺少"参数作用域"的概念。**

参数的真正问题不是"太多"，而是：
- **没有归属**：这个参数属于哪个能力？谁批准的？
- **没有边界**：谁能用？在什么场景下生效？
- **没有约束**：参数A和参数B能同时开吗？互斥吗？依赖吗？

---

## 二、方案评估：能力集+套餐+场景规则的可行性

你分享的那套方案（以下称"三层模型"）方向正确，但有几个关键点需要补充和警惕：

### 2.1 方案核心逻辑（已验证有效的部分）

```
客户 → 套餐 → 能力集 → 参数（受控）
                ↓
            场景规则（同一能力在不同场景的不同表现）
```

**这个模型的本质是什么？**

是把"参数的自由组合"变成了"能力的受控组合"。类比：
- 旧模式 = 给每个客户一个工具箱，里面什么零件都有，客户自己拼
- 新模式 = 给客户预制好的功能模块，模块内部的参数是封装好的，只暴露有限的可配置项

### 2.2 方案中隐含但没说透的三个关键设计

#### 关键设计1：能力之间的"兼容性契约"

方案提到"能力之间是兼容设计的"，但**没说怎么保证**。这恰恰是最难的部分。

实际做法：
- 每个能力必须声明**依赖**（开A必须先开B）
- 每个能力必须声明**互斥**（开A就不能开C）
- 每个能力必须声明**副作用**（开A会影响D的行为）

**这需要一个"能力兼容性矩阵"**，不是你拍脑袋定的，是要在代码层面有约束的。

#### 关键设计2：参数的"三层优先级"

```
场景规则 > 客户覆盖 > 能力默认值 > 全局默认值
```

这个优先级链一定要在引擎里写死，否则又是混乱的根源。

#### 关键设计3：灰度与回滚

每个能力的开关必须支持：
- **租户级灰度**：先给A客户开，验证没问题再给B开
- **快速回滚**：关掉一个能力，所有相关参数同时失效，不能残留
- **影响面评估**：关掉能力前，系统能告诉你有多少客户、多少场景会受影响

## 三、映射到你的异构系统：C引擎 + Java微服务

这是整个分析最有价值的部分——方案再好，得能落到你的系统里。

### 3.1 你的系统架构回顾

```
外部客户(PC/移动/大屏)
    ↓
midservice1/2/3 (Java网关)
    ↓
业务中台(Java微服务集群)
    ↓
DS数据中心 (Java桥接层/ACL) ← TCP+自定义报文 → C撮合引擎
    ↓
MySQL双实例 + MinIO + Redis缓存
```

### 3.2 参数治理在你这的"分界点"

**关键判断：C引擎内部有没有客户级参数？**

| 场景 | C引擎角色 | 治理策略 |
|------|----------|----------|
| C引擎是"纯撮合"（只管价格/数量/时间优先匹配） | 无状态黑盒 | 参数治理全放在Java层，C不受影响 |
| C引擎已有客户级配置（如不同客户的撮合规则不同） | 有状态 | **这是最棘手的情况**——需要评估能否把客户配置从C提到Java层 |

根据你之前确认的：C引擎是"单线程内存撮合+异步落库"，大概率是第一种。如果是这样，**参数治理完全可以在Java层闭环，不需要动C**。

### 3.3 能力引擎应该放哪一层？

**推荐：放在DS数据中心层（或独立的能力服务）**

理由：
1. **DS数据中心已经是"防腐层"**——它负责协议转换，天然适合做"能力翻译"
2. C引擎不感知客户概念，DS在转发前做"能力→参数→报文"的映射
3. Java微服务之间通过Hessian调用能力服务，性能开销可控

```
请求流：
客户请求 → midservice → 业务服务 
    → 能力引擎(查询该客户套餐→能力集→参数) 
    → DS数据中心(将参数注入报文) 
    → C引擎(无感知，纯撮合)
```

### 3.4 对现有系统的影响评估

| 改动点 | 影响范围 | 风险等级 |
|--------|----------|----------|
| 新建能力引擎微服务 | 新增，不影响现有 | 🟢 低 |
| 新建5张配置表 | 新增，与现有参数表并行 | 🟢 低 |
| 业务代码中if-else替换为能力查询 | 逐步替换，可灰度 | 🟡 中 |
| C引擎报文格式变更 | **不需要**，DS做翻译 | 🟢 低 |
| 旧参数迁移 | 一次性，需要数据脚本 | 🟡 中 |

## 四、迁移策略：不可能一夜重构，必须"绞杀"

你不可能停下来把所有参数重构一遍。必须走"绞杀者模式"（Strangler Fig Pattern）。

### 4.1 四阶段迁移路线

#### 阶段1：止血（1-2周）——先别让问题恶化

- **冻结新参数**：任何新参数必须先登记到能力表
- **参数盘点**：把现有所有参数列出来，标注：归属哪个客户？影响什么功能？
- **建立参数审批流程**：加参数需要技术经理审批

#### 阶段2：抽象能力（2-4周）——从现有参数中"提取"能力

- 把现有参数按功能域归类（交易模式、支付、审批、通知、合同...）
- 每一组相关参数打包成一个能力
- 先不要改代码，只是建立"能力清单"

#### 阶段3：灰度替换（4-8周）——新老并行

- 选1-2个低风险功能域（如短信通知、合同格式），先做能力化改造
- 能力引擎上线，与旧参数并行运行
- 新客户直接走能力引擎，老客户逐步迁移
- **关键：每个能力独立灰度，出问题只回滚那个能力**

#### 阶段4：清理（持续）——删除旧参数

- 老参数标记为deprecated
- 所有客户迁移完成后，删除旧参数代码
- 这个阶段可能持续数月，但每删掉一个旧参数，系统就干净一分

### 4.2 迁移中最容易踩的坑

| 坑 | 表现 | 预防 |
|----|------|------|
| **参数语义漂移** | 同一个参数在不同客户那含义不同 | 抽象能力时，宁可拆成两个能力，不要复用歧义参数 |
| **隐式依赖** | 关了一个参数，某个不相关的功能坏了 | 能力间依赖关系必须在代码层面声明（不是文档） |
| **迁移不彻底** | 新旧两套参数都在跑，更乱了 | 每个能力迁移完必须删除旧代码，不留尾巴 |
| **C引擎的隐藏参数** | DS报文中的某些字段其实是客户级参数 | 盘点时要覆盖协议层，不能只看Java代码 |

## 五、向老板/面试官怎么讲这个故事

### 5.1 用老板能听懂的话

> "我们现在的问题本质上是'产品化能力不足'。每接一个新客户就要改代码、加开关，这不是个性化的服务，这是技术债务。
>
> 我们要做的是把系统变成'乐高'——底座是统一的，但可以给不同客户拼不同的功能模块。改一个模块不影响其他客户，新客户对接直接选套餐就行，不需要动代码。
>
> 这样做的结果是：接客户的速度快3倍，线上事故少80%，测试成本降一半。"

### 5.2 面试场景的标准话术

**Q：你们系统怎么管理多租户的个性化需求？**

> "我们采用了能力集+套餐的三层模型。核心思路是：不允许参数直接挂在客户上，必须先抽象成能力，能力再打包成套餐，客户只能选套餐。
>
> 这样做的关键收益有三点：
> 1. **组合爆炸被消除**：能力之间有兼容性契约，不会出现A开了B就炸的情况
> 2. **测试成本骤降**：测的是能力组合，而不是N个客户的N种参数排列
> 3. **可规模化**：接100个客户和接10个客户，复杂度增长是线性的而非指数的
>
> 另外我们的系统是C语言撮合引擎+Java微服务的异构架构，能力引擎放在DS数据中心的防腐层，C引擎完全不感知客户概念，改动范围可控。"

**Q：迁移过程中最大的挑战是什么？**

> "最大的挑战不是技术，是'语义梳理'。我们发现很多参数在不同客户那含义不一样，抽象能力时不能简单归类。
>
> 我们的做法是：先冻结新参数，再做全量盘点，按功能域归并，每组参数抽象成一个能力。每个能力独立灰度上线，新老并行跑一段时间再切。这样即使出问题也只影响单个能力，可以快速回滚。"

### 5.3 面试官可能会追问的深度问题

| 追问 | 你的回答要点 |
|------|-------------|
| "能力之间怎么保证兼容？" | 能力元数据里声明依赖/互斥/副作用关系，引擎在开通时做校验，运行时不校验（性能考虑） |
| "性能开销多大？" | 能力+参数在客户登录时一次性加载到本地缓存（Redis），运行时只是内存HashMap查询，纳秒级 |
| "如果客户要的能力套餐里没有怎么办？" | 走定制套餐流程：评估→开发→测试→加入能力库。关键是新能力加入后所有客户都能用，不是一次性交付 |
| "旧参数怎么处理？" | 不删，标记deprecated，用绞杀者模式逐步替换。每个能力迁移完才删对应旧代码 |

# B2B大宗贸易平台 — 租户·商品·业务模式·基础模块 层次化架构设计

> 核心诉求：建立"租户→业务模式→统一服务→基础模块"四层架构体系，支持通过配置快速搭建新业务模式
> 设计原则：上层定义规则、中层定义能力、底层提供原子服务；层层解耦，逐级依赖

---

## 一、架构总览：四层层次化体系

```
┌─────────────────────────────────────────────────────────────┐
│  L1 租户层 (Tenant Layer)                                    │
│  多租户注册 · 数据隔离策略 · 角色模板绑定 · 业务模式授权        │
├─────────────────────────────────────────────────────────────┤
│  L2 业务模式层 (Business Model Layer)                        │
│  现货挂摘牌 · 竞价拍卖 · 长协合同 · 仓单融资 · 供应链金融 · ...│
│  [每一层都是"配置 + 编排"，不是"新建代码分支"]                  │
├─────────────────────────────────────────────────────────────┤
│  L3 统一服务层 (Unified Service Layer) — 三大支柱             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
│  │ 统一商品管理  │  │ 统一仓单管理  │  │ 统一资金管理  │       │
│  │ Product      │  │ Warehouse    │  │ Fund         │       │
│  └──────────────┘  └──────────────┘  └──────────────┘       │
├─────────────────────────────────────────────────────────────┤
│  L4 基础模块层 (Base Module Layer)                            │
│  认证 · 工作流 · 消息 · 规则 · 审计 · 报表 · 文件 · 配置 · 事件 │
└─────────────────────────────────────────────────────────────┘
```

**关键架构约束**：
- L2 只能调用 L3，不能跨层直接调 L4（L4 由 L3 聚合后暴露）
- L1 是横切关注点，通过拦截器/网关注入到每一层
- 服务间不直接 RPC 调用，全部通过事件总线异步解耦
- 每个模块对 L1 完全无感——租户上下文由网关层在请求入口注入

---

## 二、L1 租户层设计

### 2.1 租户数据隔离策略：三级混合方案

B2B金融级场景下，"一刀切"的隔离策略不可行。采用**分级隔离**：

| 数据类别 | 隔离级别 | 实现方式 | 适用原因 |
|---------|:-------:|---------|---------|
| **资金/账户/交易核心** | Schema级 | 每租户独立Schema（MySQL） | 金融数据强隔离要求，任何租户间数据泄露都是合规事故 |
| **商品/品类/质检标准** | 行级 (tenant_id) | 共享Schema + tenant_id过滤 | 品类等主数据需要跨租户共享和统一维护，平台统一定义 |
| **合同/仓单/履约单据** | Schema级 | 每租户独立Schema | 业务核心单据，虽不如资金敏感但涉及商业机密 |
| **操作日志/审计记录** | 行级 + 分区 | 共享表 + tenant_id分区 | 日志量大、读少写多，共享存储降低成本，分区保证隔离查询 |
| **基础配置/字典** | 行级 (tenant_id可选NULL) | NULL=平台全局默认，有值=租户覆盖 | 支持"平台提供默认值，租户可按需覆盖"的模式 |

**Schema命名规范**：`{tenant_code}_{module}`，如 `trader_a_fund`、`trader_a_contract`。

```
租户注册时的自动化流程：
1. 创建租户记录 (tenant_master表，共享库)
2. 按策略创建对应Schema (Flyway自动执行DDL)
3. 初始化角色模板 (从role_template表复制)
4. 分配默认权限矩阵
5. 激活基础模块的MQ Consumer Group (按tenant_id路由)
```

### 2.2 租户上下文注入机制

所有业务请求在Gateway层拦截，从JWT Token中提取tenant_id，写入`TenantContext`（ThreadLocal）：

```
请求链路：
  Client Request
    → API Gateway (JWT解析 → 提取 tenant_id)
    → TenantFilter (写入 TenantContext.setCurrentTenant())
    → 业务服务 (所有SQL自动追加 WHERE tenant_id = ?)
    → 响应返回后 TenantContext.clear()
```

**横切注入点**：
- **数据库层**：MyBatis Interceptor / JPA TenantListener 自动追加tenant_id
- **缓存层**：Redis Key前缀 `{tenant_id}:business_key`
- **消息队列**：每条消息Header携带 `tenant_id`，Consumer按需过滤
- **文件存储**：MinIO Bucket / 路径前缀 `{tenant_id}/`

## 三、L3 统一服务层 — 三大支柱

这是整个架构的"共享内核"。所有业务模式都复用这三套服务，不做分支。

### 3.1 统一商品管理

**要解决的痛点**：不同业务模式下商品定义各自为政——现货交易按"牌号+规格"、仓单融资按"品类+产地"、长协合同按"国标编号"——导致同一批螺纹钢在三个系统里是三个"不同"商品。

**设计思路**：引入**SPU（标准产品单元）+ SKU（库存保有单元）**两层模型。

```
┌──────────────────────────────────────────────┐
│              SPU (Standard Product Unit)      │
│  ┌─────────┐  ┌──────────┐  ┌──────────────┐ │
│  │ 品类树   │  │ 品牌/产地 │  │ 质检标准模板  │ │
│  │Category │  │Brand     │  │Quality Std   │ │
│  └─────────┘  └──────────┘  └──────────────┘ │
│         SPU ID = "STEEL_REBAR_HRB400E"        │
├──────────────────────────────────────────────┤
│              SKU (Stock Keeping Unit)         │
│  ┌──────────┐  ┌──────────┐  ┌─────────────┐ │
│  │ 规格属性  │  │ 仓库/货位 │  │ 价格/库存    │ │
│  │Spec Attr │  │Location  │  │Price/Stock  │ │
│  └──────────┘  └──────────┘  └─────────────┘ │
│      SKU = SPU + 仓库 + 规格 + 批次            │
└──────────────────────────────────────────────┘
```

**核心能力**：

| 模块 | 功能 |
|------|------|
| 品类管理 | 多级品类树，支持平台级（全局）+ 租户级（扩展）双轨维护 |
| 属性模板 | 每品类绑定动态属性Schema（如钢材有"抗拉强度"，煤炭有"热值"），支持JSON Schema定义 |
| 质检标准库 | 国标/厂标/自定标准，与SPU绑定，仓单自动引用 |
| 定价模型 | 支持"固定价/期货联动/指数浮动"三种模式，对接行情数据源 |
| 可售量引擎 | 对接仓单服务，实时计算"在库-已挂单-已锁定"后的可售量 |
| SPU-SKU映射 | 同一个SPU在不同仓库/不同批次下自动生成对应SKU |

**对外接口（RESTful API）**：

```
GET    /api/v1/products/{spu_id}                   # SPU详情
GET    /api/v1/products/search?keyword=&cat=&attr=  # 多条件组合搜索
POST   /api/v1/products                            # 新建SPU（含属性Schema）
PUT    /api/v1/products/{spu_id}/price              # 调价
GET    /api/v1/categories/tree                      # 品类树
GET    /api/v1/skus?spu_id=&warehouse_id=           # 查SKU及可售量
POST   /api/v1/quality-standards                     # 新建质检标准模板
```

**发布领域事件**：
- `ProductCreated` — SPU新建，仓单和业务模式订阅以做后续绑定
- `ProductPriceChanged` — 价格变动，资金服务/行情大屏订阅
- `InventoryChanged` — 可售量变化，挂牌/竞价模块订阅以刷新前端展示

### 3.2 统一仓单管理

**要解决的痛点**：仓库管理分散（每个仓库有自己的系统）、仓单不统一（纸质/Excel/邮件）、货权流转不透明（一货多押风险）。

**核心模型**：仓库 → 仓单 → 货权 + 区块链存证。

```
仓单生命周期状态机：

  入库登记 → 在库(可挂牌) → 被锁定(已挂单) → 已出库
                ↓               ↓
             质押(融资)      货权转移(转卖)
                ↓               ↓
             解押 ←──────────────┘
```

**核心能力**：

| 模块 | 功能 |
|------|------|
| 仓库管理 | 多仓库统一注册，WMS适配器模式对接异构仓库系统 |
| 入库/出库 | 标准API，支持PDA扫码/过磅数据自动回传 |
| 仓单生命周期 | 入库→在库→锁定→解除→出库，全程状态机管控 |
| 货权流转 | 仓单背书转让，每次流转记录不可篡改的权属链 |
| 质押管理 | 电子仓单质押/解押，对接资金服务的冻结/解冻 |
| 区块链存证 | 仓单创建、质押、转移、销毁等关键节点上链存证 |
| 盘点对账 | 周期盘点差异自动生成调整单 |
| IoT对接 | 对接仓库摄像头/电子围栏，质押期间货物异动自动告警 |

**对外接口**：

```
POST   /api/v1/warehouse/register               # 注册仓库
POST   /api/v1/warehouse/stock-in               # 入库
POST   /api/v1/warehouse/stock-out              # 出库
GET    /api/v1/warehouse/{id}/inventory         # 实时库存
POST   /api/v1/receipt/create                   # 生成电子仓单
POST   /api/v1/receipt/pledge                   # 仓单质押
POST   /api/v1/receipt/release                  # 仓单解押
POST   /api/v1/receipt/transfer                 # 仓单转让(货权变更)
GET    /api/v1/receipt/{id}/chain               # 仓单流转链(含区块链存证hash)
```

**发布领域事件**：
- `StockInCompleted` — 入库完成，商品服务更新可售量，资金服务判断是否满足解冻条件
- `ReceiptPledged` — 仓单质押，资金服务匹配授信并放款
- `ReceiptReleased` — 仓单解押，恢复挂牌/出库能力
- `OwnershipTransferred` — 货权转移，合同域记录履约进度

**与商品服务的接口关系**：

```
仓单入库时必须绑定SPU：
  POST /api/v1/receipt/create
  Body: {
    "spu_id": "STEEL_REBAR_HRB400E",     ← 引用商品服务SPU
    "warehouse_id": "WH_SH_001",
    "quantity": 500.0,
    "quality_report": { ... }             ← 引用SPU绑定的质检标准模板
  }
  
仓单生成后：
  → 商品服务自动创建对应SKU（spu_id + warehouse_id + 批次号）
  → 商品服务更新可售量（available_qty += 500）
```

### 3.3 统一资金管理

**要解决的痛点**：不同业务模式下的资金规则不同——现货是"款到发货"、长协是"保证金+进度款+尾款"、仓单融资是"质押放款+还本付息"——如果每套模式自己管钱，财务对账是噩梦。

**设计思路**：三层资金模型（资金计划→结算账单→支付工具），履约域不感知支付方式。

```
三层模型（参考 p001_1033_contract 架构）：

第一层：资金计划 (Fund Plan) — 履约域
  决定"什么时候付、付多少钱"
  示例：PlanA(保证金20%) + PlanB(发货款70%) + PlanC(尾款10%)

第二层：结算账单 (Settlement Bill) — 结算域
  应对溢短装、质检扣罚
  示例：合同500吨，实收498吨，含水超标扣2000元
  → 最终结算金额 = 498×单价 - 2000

第三层：支付工具 (Payment Instrument) — 支付域
  决定"这笔钱怎么付"
  银行直连 / 虚拟子账户 / 线下汇款核销 / 票据 / 信用证
  → 全部输出统一的 PaymentCompleted 事件
```

**核心能力**：

| 模块 | 功能 |
|------|------|
| 账户体系 | 虚拟子账户（平台存管模式），支持冻结/解冻/划拨 |
| 支付网关 | 适配器模式，统一对接多银行、多支付通道 |
| 资金冻结引擎 | 按履约节点自动冻结/解冻，防止"货发了钱没扣" |
| 清结算引擎 | 多批次发货→多批次结算→尾款轧差，自动生成结算单 |
| 对账中心 | 日终自动拉取银行流水，与平台流水匹配，差异标红 |
| 退款/逆向 | 独立的逆向资金单模型，不跟正向单混用 |
| 授信模块 | 对接风控规则，按租户/客户分配额度 |

**对外接口**：

```
POST   /api/v1/account/open                     # 开立虚拟子账户
GET    /api/v1/account/{id}/balance             # 查询余额
POST   /api/v1/payment/order                    # 发起支付
POST   /api/v1/fund/freeze                      # 冻结资金
POST   /api/v1/fund/unfreeze                    # 解冻资金
POST   /api/v1/settlement/reconcile             # 触发结算
GET    /api/v1/settlement/daily-reconciliation   # 日对账结果
```

**发布领域事件**：
- `PaymentCompleted` — 支付成功，履约服务推进状态机 / 解锁发货
- `FundFrozen` — 资金冻结，履约服务标记"资金已就绪"
- `FundUnfrozen` — 资金解冻，仓单服务解除质押
- `SettlementCompleted` — 结算完成，合同域判断是否完结

## 四、L2 业务模式层 — 配置驱动的快速接入

这是整个架构**最能体现"平台化"价值**的一层。

### 4.1 核心设计思想

**业务模式 ≠ 代码分支。业务模式 = 配置 + 编排。**

每一套业务模式，本质上是对 L3 三大服务和 L4 基础模块的一次"组合声明"。新增模式不需要建新项目、不需要写Service层代码，只需定义一份配置JSON。

### 4.3 新增业务模式的完整流程（以"竞价拍卖"为例）

**Step 1：定义模式配置JSON（核心工作量，1-2天）**

填写一份如上的配置JSON，声明：
- 激活哪些统一服务、哪些功能
- 流程编排（状态机/工作流）
- 规则引擎规则
- 前端菜单和仪表盘
- 数据库表（只定义本模式特有的表，如`auction_session`、`bid_record`）

**Step 2：系统自动组装（零人工）**

```
配置提交 → 配置中心(Nacos/Apollo)热加载 →
  ├── 前端壳应用读取 ui_config → 动态注册路由/菜单
  ├── RBAC服务读取 button_permissions → 注入权限矩阵
  ├── 工作流引擎读取 workflow_definition → 部署流程定义
  ├── 规则引擎读取 rule_engine_config → 热加载规则
  ├── 事件总线读取 event_subscriptions → 注册Consumer Group
  └── 数据库执行 mode_specific_tables DDL → 新建表
```

**Step 3：少量定制开发（如需要，1-2天）**

只有以下情况需要写代码：
- 业务模式有**特有的前端页面**（如竞价大厅的实时出价组件）
- 业务模式有**特有的外部对接**（如对接某交易所的报价API）
- 业务模式有**复杂的计算逻辑**（如竞价中的价格发现算法）

**传统方案 vs 配置驱动方案对比**：

| 维度 | 传统方案（新开代码分支） | 配置驱动方案 |
|------|----------------------|------------|
| 新建业务模式周期 | 4-6周 | 1-3天（配置）+ 1-2天（少量定制） |
| 需要改动的代码量 | 全栈（前端+后端+DB） | 仅特有组件 |
| 统一服务改动 | 每套模式自己实现 | 零改动 |
| 基础模块改动 | 每套模式自己封装 | 零改动 |
| 复用程度 | 代码复制粘贴 | 配置+编排复用 |
| 维护成本 | N套模式 × M个模块 = N×M | 1套代码 + N份配置 |
| 大客户定制 | 开分支 → 合并地狱 | 新增或覆盖一份配置JSON |

## 五、L4 基础模块层设计

基础模块是L4的"原子能力池"。每个模块独立部署、独立扩展、通过标准API和事件总线被上层调用。

### 5.1 模块清单与职责

| 模块 | 核心职责 | 与上层接口方式 |
|------|---------|--------------|
| **认证授权 (Auth)** | 统一登录/SSO/RBAC/数据权限 | REST API + JWT Token |
| **工作流引擎 (Workflow)** | 流程定义/实例管理/任务分配 | REST API + 回调 |
| **规则引擎 (Rule Engine)** | 业务规则热加载/实时决策 | REST API + 事件订阅 |
| **消息通知 (Notification)** | 邮件/短信/站内信/钉钉/企微 | REST API + 事件订阅 |
| **操作审计 (Audit Log)** | 全量操作留痕/Diff对比/防篡改 | 事件订阅(被动收集) |
| **报表引擎 (Report)** | 报表模板/数据源/定时生成/导出 | REST API |
| **文件服务 (File)** | 上传/下载/预览/OCR/水印 | REST API + MinIO |
| **分布式ID (ID Gen)** | Snowflake/号段模式 | SDK嵌入 |
| **任务调度 (Scheduler)** | 定时任务/延迟任务/分布式调度 | REST API |
| **配置中心 (Config)** | 热配置/灰度发布/租户级覆盖 | SDK + 长轮询 |
| **事件总线 (Event Bus)** | 领域事件发布订阅/outbox 消息表/死信 | SDK + Kafka |

### 5.2 模块可复用性设计原则

每个基础模块必须满足：

1. **无状态**：模块本身不存储租户相关会话状态，租户上下文由调用方传入
2. **接口标准化**：所有模块暴露统一的RESTful风格API + 领域事件，不暴露内部实现
3. **配置外置**：模块行为由配置中心驱动，不在代码中硬编码任何业务规则
4. **可独立部署**：每个模块独立的Docker镜像、独立的数据库/存储、独立的扩缩容策略
5. **优雅降级**：每个模块必须在依赖不可用时提供降级方案（如审计服务挂了不影响交易）

### 5.3 示例：规则引擎的可扩展设计

规则引擎是"配置驱动"最核心的基础模块，因为它承载了不同业务模式之间的差异：

```
规则引擎架构：

  业务模式层              规则引擎                 规则存储
  ┌──────────┐      ┌──────────────────┐      ┌──────────┐
  │ 模式配置  │─────→│ RuleLoader        │←────│ MySQL    │
  │ JSON     │      │ 热加载/版本管理    │     │ rule_def │
  └──────────┘      └────────┬─────────┘      └──────────┘
                             │
                    ┌────────┴─────────┐
                    │ RuleExecutor      │
                    │ DSL解析/条件匹配   │
                    └────────┬─────────┘
                             │
            ┌────────────────┼────────────────┐
            ▼                ▼                 ▼
      ┌──────────┐    ┌──────────┐     ┌──────────┐
      │执行动作A  │    │执行动作B  │     │执行动作C  │
      │拦截+告警  │    │标记+人工  │     │自动放行   │
      └──────────┘    └──────────┘     └──────────┘

每个业务模式在配置JSON中声明自己的规则集(RuleSet)：
  mode_id = "AUCTION" → rules: [竞价延时规则, 起拍价校验, 加价幅度校验]
  mode_id = "SPOT"    → rules: [价格偏离检查, 大单审批, 新买家限额]
  mode_id = "FINANCE" → rules: [质押率上限, 风险敞口控制, 逾期预警]
```

## 六、模块间接口与数据流转全景

### 6.1 核心原则

1. **同步走API，异步走事件** —— 查询类请求直接RESTful API；状态变更类操作通过事件总线通知下游
2. **事件即契约** —— 每个事件有明确的Schema（JSON Schema定义），版本化管理，向后兼容
3. **消费方容错** —— 事件消费方必须幂等 + 有死信队列兜底
4. **跨模块关联不用Join，用事件物化** —— 需要跨服务联查的数据，通过监听事件在本地构建物化视图

### 6.2 典型数据流转链路

以"现货挂摘牌：买方支付成功 → 自动触发发货 → 收货后自动结算"为例：

```
时间轴 ──────────────────────────────────────────────────────────→

买方支付：
  [前端] 点击"支付"
    → [资金服务] POST /payment/order (同步)
        ├─ 调用银行接口完成扣款
        ├─ 更新 payment_order.status = PAID
        └─ 发布事件 PaymentCompleted { contractId, amount, channel }
            │
            ▼ (MQ异步)
  [履约服务] 监听 PaymentCompleted
    ├─ 推进状态机：CONTRACT_SIGNED → PAID
    ├─ 生成发货任务单 shipment_task
    └─ 发布事件 PaymentConfirmed { contractId }

卖方发货：
  [前端] 点击"发货"
    → [仓单服务] POST /warehouse/stock-out (同步)
        ├─ 校验可出库量 ≥ 发货量
        ├─ 扣减库存、更新仓单状态
        └─ 发布事件 StockOutCompleted { receiptId, qty, logisticsNo }
            │
            ▼ (MQ异步)
  [履约服务] 监听 StockOutCompleted
    ├─ 推进状态机：PAID → SHIPPED
    └─ 发布事件 ShipmentCompleted { contractId, shipmentId }

买方收货：
  [前端] 点击"确认收货"
    → [履约服务] 记录收货 (同步)
        ├─ 推进状态机：SHIPPED → RECEIVED
        └─ 发布事件 ReceiptConfirmed { contractId, actualQty, qualityDeduction }
            │
            ▼ (MQ异步)
  [资金服务] 监听 ReceiptConfirmed
    ├─ 计算结算金额 = actualQty × 单价 - qualityDeduction
    ├─ 执行清分（解冻卖方应得部分 → 划拨）
    └─ 发布事件 SettlementCompleted { contractId, settlementAmount }
        │
        ▼ (MQ异步)
  [履约服务] 监听 SettlementCompleted
    ├─ 推进状态机：RECEIVED → SETTLED
    ├─ 检查所有Plan是否都结算完 → 如果是，推进到 COMPLETED
    └─ 发布事件 ContractCompleted { contractId }
        │
        ▼ (MQ异步)
  [审计服务] 监听所有事件 → 生成操作日志时间轴
  [通知服务] 监听关键事件 → 推送消息给相关角色
```

### 6.3 跨模块关联查询策略

**问题**：用户想看"某个合同涉及的所有资金流水 + 所有仓单流转记录"——这些数据分散在三个不同的服务/数据库中。

**方案分级**：

| 方案 | 适用场景 | 实现方式 |
|------|---------|---------|
| **方案A：事件物化视图**（推荐）| 高频联查、需要聚合统计 | 查询服务监听所有相关事件，在本地构建"合同全息视图"宽表 |
| **方案B：API聚合层** | 低频联查、实时性要求一般 | BFF层并行调用多个服务API，前端聚合展示 |
| **方案C：CQRS查询端** | 复杂报表、多维分析 | 独立查询数据库，通过Canal/CDC同步各服务数据 |

**方案A（推荐）详细设计**：

## 八、数据一致性保障

### 8.1 三级一致性策略

| 场景 | 一致性要求 | 技术方案 |
|------|:--------:|---------|
| **资金扣款** | 强一致 | 数据库行锁（UPDATE...WHERE balance >= amount）；单库事务 |
| **支付→通知履约→推进状态** | 最终一致 | 本地消息表（outbox）+ Kafka + 幂等消费 |
| **商品调价→刷新大屏/挂牌** | 最终一致 | MQ普通消息 + Redis缓存失效 |
| **多服务间结算** | 最终一致 | Saga编排（正操作+补偿操作） |
| **对账（平台 vs 银行）** | 日终强一致 | T+1批处理 + 差异标红人工处理 |

### 8.2 资金场景的防并发设计（最核心）

银行金融级资金操作，并发控制是底线：

```
// 资金冻结 —— 必须用数据库行锁，不能用Redis分布式锁
UPDATE fund_account 
SET frozen_balance = frozen_balance + #{amount},
    available_balance = available_balance - #{amount},
    version = version + 1
WHERE account_id = #{accountId}
  AND tenant_id = #{tenantId}
  AND available_balance >= #{amount}
  AND version = #{currentVersion}    ← 乐观锁

// 如果 affected_rows = 0：
//   → version不匹配：并发冲突，重试
//   → balance不足：拒绝操作，返回余额不足

// 所有资金操作的事件发布都走 outbox（本地消息表）+ Kafka：
@Transactional
public void processPayment(PaymentRequest req) {
    // 1. 扣款（数据库行锁）
    fundAccountMapper.deduct(req.getAccountId(), req.getAmount());
    
    // 2. 写本地消息表（与扣款在同一本地事务）
    outboxMapper.insert(
        new OutboxEvent("payment.completed", req.getContractId(), req.getAmount())
    );
    
    // 3. 事务提交后，定时任务扫描消息表投递到 Kafka（幂等 key 去重）
}
```

## 九、关键技术决策对比

| 决策点 | 方案A | 方案B | 选择 | 理由 |
|-------|-------|-------|:--:|------|
| 租户数据隔离 | Schema级 | 行级(tenant_id) | **混合** | 资金/合同用Schema级（合规要求），品类/日志用行级（运维成本低） |
| 服务间通信 | RPC直连 | 事件总线 | **事件总线** | B2B场景业务耦合度高，RPC会导致"改一处联动一片"，事件解耦后扩展零影响 |
| 业务模式实现 | 多代码分支 | 配置驱动 | **配置驱动** | 3天 vs 6周的上线速度差异是核心竞争壁垒 |
| 跨模块查询 | 实时Join/API聚合 | 事件物化视图 | **事件物化** | 查询频率高的"合同全息视图"值得冗余存储；低频用API聚合即可 |
| 资金并发控制 | Redis分布式锁 | 数据库行锁 | **数据库行锁** | 资金操作不允许任何并发窗口，数据库行锁的原子性保障是金融级底线 |
| 分布式事务 | XA/2PC | Saga+补偿 | **Saga** | 大宗交易跨月长事务，XA锁时间不可接受；Saga配合业务补偿更贴合实际 |
