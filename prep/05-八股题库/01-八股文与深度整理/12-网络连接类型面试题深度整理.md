## 01 连接的本质与分类

### 1.1 什么是"网络连接"？物理连接与逻辑连接的区别？【基础】
**网络连接**是通信双方在传输数据前建立的一种"通路"概念，但必须区分两个层面：

- **物理连接**：真实存在的硬件链路，如网线、光纤、交换机端口之间的电气/光信号通路。它是"线"的存在。
- **逻辑连接**（软件连接）：在物理链路上，由协议栈软件维护的一条"虚拟通路"状态，如 TCP 连接（四元组 + 状态机）、HTTP 连接（请求/响应会话）、VPN 隧道。它是"状态"的存在。

> 加分点：物理连接是共享的，逻辑连接是复用的——成千上万条 TCP 连接可能共享同一根光纤（分组交换），这正是"逻辑连接"存在的意义：在共享介质上抽象出隔离的会话。

### 1.2 面向连接 vs 无连接：TCP 与 UDP 的本质差异【高频】

| 维度 | 面向连接（TCP） | 无连接（UDP） |
|---|---|---|
| 连接建立 | 三次握手建立连接 | 无握手，直接发包 |
| 状态维护 | 两端维护连接状态机 | 无状态 |
| 可靠性 | 确认、重传、排序、去重 | 尽最大努力交付 |
| 流量/拥塞控制 | 有（滑动窗口 + 拥塞控制） | 无 |
| 报文边界 | 字节流，无边界（粘包） | 保留报文边界 |
| 首部开销 | 20 字节 | 8 字节 |
| 典型场景 | HTTP、数据库、文件传输 | DNS、音视频、游戏、QUIC |

> 加分点：口语化的"TCP 要连接、UDP 不要连接"并不精确——**"连接"的本质是两端协同维护的会话状态**，TCP 用握手 + 序号 + 窗口 + 重传把不可靠的 IP 网络抽象成可靠字节流；UDP 只是 IP 之上加了一个 8 字节端口复用层，其他一律不管。

### 1.3 单播、广播、组播（多播）、任播的区别【基础】
这是按**目的地址的寻址范围/接收者数量**划分的"连接/通信类型"：

- **单播（Unicast）**：一对一，发送方与唯一接收方通信。TCP、绝大多数 HTTP 都是单播。
- **广播（Broadcast）**：一对全部，发给本网段所有主机（目的地址 `255.255.255.255` 或子网广播地址）。只存在于 IPv4，IPv6 用组播取代。
- **组播（Multicast）**：一对多，只发给"订阅了该组地址"的主机（IPv4 的 `224.0.0.0/4`，IPv6 的 `FF00::/8`）。直播、IPTV、路由协议（OSPF 用 224.0.0.5/6）。
- **任播（Anycast）**：一对最近，多个主机共享同一地址，路由器把报文送给"最近"的一个。DNS（8.8.8.8、1.1.1.1）、CDN、Anycast TCP 常用于抗 DDoS。

> 加分点：面试升级点——**TCP 只能单播**（因为需要端到端状态与确认），UDP 天然支持广播/组播/任播；但任播 + TCP 在 CDN/DNS 场景大量使用（多台服务器共享 IP，靠 BGP 路由到最近节点），这不矛盾：连接是建立在"被路由选中的那一台"上的。

### 1.4 电路交换 vs 分组交换；虚电路 vs 数据报【进阶】
- **电路交换（Circuit Switching）**：通信前先建立**独占物理通路**（如老式电话），期间独占带宽，线路利用率低，建立慢，但时延稳定。连接 = 物理通路本身。
- **分组交换（Packet Switching）**：数据拆成分组独立路由转发，链路共享，利用率高，但可能乱序/丢失。互联网本质是分组交换。

分组交换再分两种"连接形态"：
- **虚电路（Virtual Circuit）**：发送前先建立逻辑通路（如 ATM、MPLS、X.25），分组沿同一路径走，网络层有状态。**"面向连接"的分组交换**。
- **数据报（Datagram）**：每个分组独立选路（IP 就是这样），无连接、无状态、可能乱序。

> 加分点：经典面试点——**TCP 是"端到端的有状态协议"，但跑在"无状态的数据报网络层(IP)"之上**，这正是"端到端原则"（End-to-End Principle）的体现：把可靠性放在终端实现，网络只管转发，这是互联网能够大规模扩展的根本原因。

### 1.5 "连接"在 OSI/TCP-IP 各层分别是什么形态？【进阶】

| 层级 | 连接形态 | 典型协议 |
|---|---|---|
| 应用层 | 应用会话/逻辑连接 | HTTP Keep-Alive、WebSocket、TLS Session |
| 传输层 | 端到端连接（四元组+状态机） | TCP、SCTP |
| 网络层 | 无连接数据报（或有虚电路） | IP、MPLS LSP |
| 数据链路层 | 点到点/局域网连接（MAC、VLAN） | 以太网、PPP、Wi-Fi 关联 |
| 物理层 | 物理链路/信道 | 铜缆、光纤、无线电波 |

> 加分点：一条"浏览器打开网页"的链路，从上到下同时存在 5 层连接：TLS 会话（应用）→ TCP 连接（传输）→ IP 路由（网络）→ 以太网链路（链路）→ 光纤信道（物理），面试能把这 5 层对应关系讲清楚，说明真懂网络。

## 02 TCP 连接的建立：三次握手

### 2.1 三次握手的过程与每个报文的作用【高频】
1. **客户端 → 服务器：SYN=1, seq=x**（SYN_SENT 状态）。含义："我想建立连接，我的起始序号是 x"。
2. **服务器 → 客户端：SYN=1, ACK=1, seq=y, ack=x+1**（SYN_RCVD 状态）。含义："收到你的 SYN，我同意，我的起始序号是 y，期望你下次从 x+1 发"。
3. **客户端 → 服务器：ACK=1, seq=x+1, ack=y+1**（ESTABLISHED）。含义："收到你的 SYN+ACK，连接建立"。

> 加分点：三次握手本质是**同时确认双方的收发能力与序号同步**——第 1 次后服务器知道客户端能发、自己能收；第 2 次后客户端知道双方都能收发；第 3 次后服务器确认客户端能收（否则服务器会认为自己的 SYN+ACK 可能丢了，直接进入 ESTABLISHED 会有隐患）。

### 2.2 为什么是三次握手，而不是两次或四次？【高频】
- **为什么不能两次**：核心是**防止失效的历史连接请求突然到达服务器**。客户端发了 SYN，但因网络拥塞超时重传，重传的 SYN 建立成功了，而**旧的失效 SYN 才到达**——如果两次握手，服务器收到旧 SYN 就会建立连接并分配资源，但客户端根本不会理它（客户端没有这个连接），造成服务器资源浪费，甚至可能把客户端已确认的连接序号搞乱。三次握手时，服务器收到旧 SYN 回 SYN+ACK，客户端发现序号对不上/不是自己期望的连接，直接发 RST 拒绝，服务器才能识别出这是失效连接。
- **为什么不需要四次**：三次已经完成了"客户端→服务器、服务器→客户端"双向的收发能力确认与序号同步，第四次是冗余的。

> 加分点：另一个角度——**两次握手无法避免"半连接"状态下的资源浪费，也无法在服务器侧区分新旧 SYN**；三次握手让**服务器在收到客户端最后的 ACK 前不进入 ESTABLISHED**，从而把"确认对方还活着"的成本前置给了先发起的一方。

### 2.3 SYN Flood 攻击原理与防护【高频】
- **原理**：攻击者伪造大量源 IP 发送 SYN 包，服务器收到后回 SYN+ACK，但伪造 IP 永远不会回 ACK，导致**半连接队列（SYN 队列）被占满**，后续正常客户的 SYN 无法入队，服务不可用。
- **危害**：服务器每接收一个 SYN 都要分配控制块，内存与 CPU 被耗尽；真正的目的是让**全连接队列/半连接队列溢出**。

防护手段：
1. **SYN Cookie**（最核心）：不分配半连接资源，把序号用哈希（源/目的 IP 端口 + 时间 + 密钥）计算出来作为 SYN+ACK 的序号，客户端回 ACK 时校验序号即可直接建立连接。Linux 默认 `net.ipv4.tcp_syncookies=1`。
2. **缩短 SYN 超时**：`tcp_synack_retries` 从 5 次降到 1~2 次，快速回收半连接。
3. **限速/黑白名单**：网关层识别并丢弃攻击流量（DDoS 清洗）。
4. **tcp_max_syn_backlog 调大**：扩容半连接队列，缓解但不治本。

> 加分点：SYN Cookie 的代价是**放弃了一些 TCP 特性**（如窗口缩放、SACK 等选项无法在 SYN 阶段协商，需要通过"TFO/时间戳回填"补偿），所以它是"溢出时才启用"的兜底机制（Linux 中队列满时自动触发）。

### 2.4 TCP 初始序列号（ISN）为什么不能固定？【进阶】
- 如果 ISN 固定（如恒为 0），攻击者可**预测并伪造**带合法序号的报文，实施会话劫持（TCP Spoofing）。
- 固定的 ISN 还会导致**新旧连接的序号冲突**——前一个连接遗留的旧报文（网络中延迟到达）可能与新连接的序号区间重叠，干扰新连接。
- 现代实现（RFC 1948）：ISN ≈ 时钟（4µs 粒度）+ 四元组相关的随机哈希（防预测）。

> 加分点：Linux 生成 ISN 用 `secure_tcp_seq()`，是**四元组 + 加密密钥的哈希函数**，同一连接每次建立得到的 ISN 都不同且不可预测；这也解释了为什么**TIME_WAIT 2MSL 之后旧报文必然消失**——ISN 随机化 + 时间窗双重保障新连接不被污染。

### 2.5 三次握手可以携带数据吗？为什么？【进阶】
- **第一次 SYN 不能携带数据**：此时服务器还没确认客户端身份，若携带数据会放大 SYN Flood 攻击面（伪造 SYN 也能让服务器缓存数据）。
- **第二次 SYN+ACK 不能携带数据**：同理，服务器还不能确认客户端可达。
- **第三次 ACK 可以携带数据**：此时客户端已确认服务器可达，是"捎带数据"（piggyback）的合法时机，如 HTTP 场景可把首个请求直接捎带在第三次握手上，省一个 RTT。

> 加分点：**TCP Fast Open（TFO）** 打破了"首次 SYN 不能带数据"的限制——首次连接用 Cookie 认证后，后续连接的 SYN 可携带数据，实现**0-RTT 建连 + 首包数据**，Chrome/HTTP 场景收益明显，但需防重放，因此 Cookie 有有效期。

### 2.6 同时打开（Simultaneous Open）会发生什么？【进阶】
双方同时向对方发 SYN：
- 客户端 A 发 SYN → A 进入 SYN_SENT；B 同时发 SYN → B 也进入 SYN_SENT。
- A 收到 B 的 SYN（不是 SYN+ACK），A 进入 **SYN_RCVD** 并回 SYN+ACK；B 同样处理。
- 各自收到对方的 SYN+ACK 后进入 ESTABLISHED。
- 结果是**双方都成为主动连接方，各自建立一条完整连接（两倍的状态）**，RFC 793 允许，但实际几乎不发生（因为客户端/服务器角色通常固定）。

> 加分点：同时打开在 P2P 场景（双方同时拨号到对方）理论上有意义，但现代 NAT 环境下几乎不可能真正同时发出；NAT 穿透一般用 UDP 打洞而非 TCP 同时打开，因为 NAT 对 SYN 的映射策略不可控。

## 03 TCP 连接的释放：四次挥手

### 3.1 四次挥手的过程【高频】
1. **主动方 A → B：FIN=1, seq=u**（A 进入 FIN_WAIT_1）。含义："我这边数据发完了，我要关闭发送方向"。
2. **B → A：ACK=1, ack=u+1**（B 进入 CLOSE_WAIT，A 进入 FIN_WAIT_2）。含义："收到你的 FIN，但我还有数据要发"。
3. **B 数据发完后 → A：FIN=1, seq=w**（B 进入 LAST_ACK）。含义："我这边也发完了，关闭"。
4. **A → B：ACK=1, ack=w+1**（A 进入 TIME_WAIT，B 收到后 CLOSED）。A 等待 2MSL 后 CLOSED。

> 加分点：**FIN 只表示"发送方向关闭"**，TCP 是双工协议，两个方向独立关闭——这就是为什么需要 4 次而不是 2 次。主动关闭方发 FIN 后仍能接收数据（半关闭），直到对方也发 FIN。

### 3.2 为什么挥手要四次，而握手只要三次？【高频】
- **握手时**：服务器的 SYN 和 ACK 可以**合并**（SYN+ACK 一个报文），因为服务器没有"必须先等业务数据"的约束。
- **挥手时**：B 收到 A 的 FIN 后，**先回 ACK 表示"收到关闭请求"**，但此时 B 可能还有业务数据要发送，**不能立即发 FIN**，必须等数据发完。所以 FIN 和 ACK 分开发，天然需要 4 次。
- 只有在"B 恰好也没有数据要发"的特殊情况下，FIN 和 ACK 才能合并（3 次挥手）。

> 加分点：本质是**被动关闭方需要一段时间处理完剩余数据**，这段时间里 A 处于 FIN_WAIT_2。如果 B 一直不 close（应用层 Bug），A 会一直停在 FIN_WAIT_2，最终由 `tcp_fin_timeout`（默认 60s）兜底关闭——线上排查时 FIN_WAIT_2 堆积通常指向"对端应用不关连接"。

### 3.3 TIME_WAIT 是什么？为什么是 2MSL？【高频】
- **TIME_WAIT**：主动关闭方在发送最后一个 ACK 后进入的状态，等待 **2MSL**（Maximum Segment Lifetime，报文最大生存时间）后才 CLOSED。Linux 中 MSL≈30s（`tcp_fin_timeout` 相关），即 TIME_WAIT 约 60s。
- 两个作用：
  1. **保证最后一个 ACK 能可靠到达**：如果第 4 次 ACK 丢失，B 会重发 FIN，A 需要留在 TIME_WAIT 以便重发 ACK；如果 A 直接关闭，B 会一直收不到确认而反复重传 FIN，甚至误判。
  2. **让本连接的所有旧报文在网络中消亡**：2MSL 覆盖了"报文去 + ACK 回"的最长往返时间，确保旧连接的延迟报文不会污染下一个使用相同四元组的新连接。

> 加分点：TIME_WAIT 是**主动关闭方的专利**，被动关闭方不会进入（B 收到 FIN 回 ACK 后走 CLOSE_WAIT → LAST_ACK → CLOSED）。所以高并发短连接服务（如 Nginx 作为客户端、爬虫、网关）会出现大量 TIME_WAIT，这是**正常且必要的**，不要一味"清零"。

### 3.4 TIME_WAIT 过多怎么处理？【高频】
先确认原因：短连接高频建连/断连（如 HTTP/1.0、服务间 RPC 短连接、大量客户端连完就关）。

处理手段（按优先级）：
1. **连接复用**（治本）：开启 HTTP Keep-Alive / 连接池，让连接建立后持续复用，从源头减少"建-断"次数。
2. **调整内核参数**（缓解）：
   - `net.ipv4.tcp_tw_reuse=1`：**客户端**视角允许复用处于 TIME_WAIT 的连接（必须配合时间戳选项；对服务器端无效）。
   - `net.ipv4.tcp_timestamps=1`：tcp_tw_reuse 的前提。
   - 调小 TIME_WAIT 时长（改 MSL 不推荐，破坏协议语义）。
3. **服务器主动关闭改被动**：让对端（客户端）主动断开，把 TIME_WAIT 转移出去。
4. **负载均衡**：分摊到多台机器，稀释单机 TIME_WAIT。

> 加分点：**强烈不推荐 `tcp_tw_recycle`（已废弃）**——它会在 NAT 环境下因为时间戳倒置而误杀正常连接，Linux 4.12 起已删除该参数。面试主动说"我不用 tcp_tw_recycle，因为 NAT 下时间戳回退会导致新连接被拒"是明显加分项。

### 3.5 CLOSE_WAIT 堆积的原因与排查【高频】
- **CLOSE_WAIT**：被动关闭方收到 FIN 回 ACK 后，**等待应用层调用 close()** 的状态。只要应用不 close，连接就卡在 CLOSE_WAIT。
- **堆积原因**（几乎都是应用层 Bug）：
  1. 代码只处理了读事件，没处理连接关闭事件（没调用 close）。
  2. 处理逻辑抛异常/超时，close 语句没走到。
  3. 长连接场景下游不关闭，服务器自己也不主动关。
  4. 线程池耗尽，处理线程全部阻塞，无法执行 close。
- **排查**：`netstat -ant | grep CLOSE_WAIT | wc -l` 看数量；`ss -antp | grep CLOSE_WAIT` 定位进程；用 jstack 看线程是否卡死；检查代码里 socket 是否在 finally 中关闭。

> 加分点：CLOSE_WAIT 堆积是"服务器资源泄漏"的典型信号——连接没释放，fd 耗尽后新连接直接失败。**它与 TIME_WAIT 正好相反：TIME_WAIT 是正常的协议状态，CLOSE_WAIT 几乎都是代码 Bug**。一句话记忆：TIME_WAIT 多找网络层/架构，CLOSE_WAIT 多查应用代码。

### 3.6 半关闭（shutdown）与 close 的区别【进阶】
- **close(fd)**：引用计数 -1，当引用计数归零时**立即**发送 FIN，并且**释放整个连接**（两个方向都关闭）。若还有数据在途，close 会直接丢弃并可能发 RST。
- **shutdown(fd, SHUT_WR / SHUT_RD / SHUT_RDWR)**：**只关闭指定方向**，不释放资源：
  - `SHUT_WR`：发 FIN，关闭发送方向，仍可接收（半关闭）。
  - `SHUT_RD`：关闭接收方向。
  - `SHUT_RDWR`：相当于两个方向都 shutdown，但**不释放 fd**（仍需 close）。
- 适用场景：协议要求"发完请求后关闭发送，但仍要读响应"（如某些 RPC、FTP）。

> 加分点：多线程共享同一 socket 时，一个线程 close 会让其他线程无法使用；正确做法是用 shutdown 通知对方"我要关发送"，等数据收完再 close。这也是"优雅关闭"（Graceful Shutdown）的协议层实现基础。

## 04 TCP 状态机与连接队列

### 4.1 TCP 11 种状态全解【进阶】

| 状态 | 含义 | 进入条件 |
|---|---|---|
| CLOSED | 初始状态，无连接 | — |
| LISTEN | 服务器监听 | bind+listen 后 |
| SYN_SENT | 已发 SYN，等待 SYN+ACK | 主动连接方 |
| SYN_RCVD | 收到 SYN，已回 SYN+ACK | 服务器半连接态 |
| ESTABLISHED | 连接建立，可传数据 | 握手完成 |
| FIN_WAIT_1 | 已发 FIN，等待 ACK | 主动关闭方第一步 |
| FIN_WAIT_2 | 已收 ACK，等待对方 FIN | 主动关闭方第二步 |
| CLOSE_WAIT | 已收 FIN，回 ACK，等应用 close | 被动关闭方 |
| LAST_ACK | 应用 close 后已发 FIN，等最终 ACK | 被动关闭方收尾 |
| TIME_WAIT | 发完最后 ACK，等 2MSL | 主动关闭方收尾 |
| CLOSING | 双方同时发 FIN（罕见） | 同时关闭 |

> 加分点：把状态机串成一条线——**服务端视角**：LISTEN → (收到SYN) SYN_RCVD → (收到ACK) ESTABLISHED → (收到FIN) CLOSE_WAIT → (应用close) LAST_ACK → CLOSED；**客户端视角**：SYN_SENT → ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED。面试画这条线比背表强得多。

### 4.2 半连接队列与全连接队列【高频】
TCP 服务器有两个队列配合握手：
- **半连接队列（SYN 队列 / syn queue）**：收到 SYN、还没完成三次握手的连接（SYN_RCVD 状态）。大小受 `net.ipv4.tcp_max_syn_backlog`（默认 1024/4096）限制。
- **全连接队列（accept 队列）**：三次握手完成、等待应用 accept() 的连接（ESTABLISHED 但未被 accept）。大小 = `min(listen(fd, backlog), net.core.somaxconn)`（somaxconn 默认 4096）。

建立流程：SYN 到达 → 入半连接队列 → 回 SYN+ACK → 收到 ACK → **从半连接队列移入全连接队列** → 应用 accept() 取走。

> 加分点：**`listen(backlog)` 的 backlog 只控制全连接队列，控制不了半连接队列**（那是 tcp_max_syn_backlog 的事）。很多面试者误以为调大 backlog 能防 SYN Flood，实际防的是"accept 不及时"的场景。

### 4.3 连接队列溢出：tcp_abort_on_overflow 与 backlog【进阶】
- **全连接队列满**时新完成的连接怎么处理？由 `net.ipv4.tcp_abort_on_overflow` 决定：
  - `0`（默认）：**静默丢弃** ACK 报文，客户端以为握手成功（它已发 ACK），实际服务端没建连接。客户端发数据时服务器回 RST，客户端报错。
  - `1`：直接发 **RST** 拒绝，客户端立刻感知"连接被拒绝"。
- 日志标志：`dmesg` 中出现 `"TCP: request_sock_TCP: Possible SYN flooding on port xxx"` 说明半连接队列溢出；`ss -lnt` 中 `Send-Q` 大于 `Recv-Q` 且不断增长说明 accept 队列溢出。

> 加分点：`ss -lnt` 读法——`Recv-Q` 是当前 accept 队列长度，`Send-Q` 是队列上限；`Recv-Q` 接近 `Send-Q` 且持续不降，说明**应用 accept 速度跟不上**，优先排查应用线程/epoll 处理，而不是调内核参数。

### 4.4 三次握手与两个队列的交互（Linux 实现细节）【进阶】
1. 客户端 SYN 到达 → 服务器在 **inet_csk_reqsk_queue**（半连接队列）创建一个 request_sock，回 SYN+ACK。
2. 若收到重传的 SYN（半连接已存在）→ 重新回 SYN+ACK。
3. 收到 ACK → 校验通过后从半连接队列**移除**，创建 sock，**插入全连接队列**。
4. 应用 accept() 从全连接队列取出 sock → 完成。
5. **SYN Cookie 模式**下：不创建 request_sock（半连接队列零占用），把"握手信息"编码进 ISN，收到 ACK 时现场校验、直接建立全连接——这也是为什么溢出时 Linux 自动启用 Cookie。

> 加分点：半连接队列的满溢判断是"**入队前检查**"，而 SYN Cookie 是"**溢出后才触发**"的兜底（`tcp_syncookies=1` 时队列满则改用 Cookie）。所以**防 SYN Flood 的第一道防线永远是队列容量，第二道才是 Cookie**。

### 4.5 如何排查连接队列溢出？【进阶】
1. `ss -lnt`：对比 `Recv-Q` 与 `Send-Q`。
2. `netstat -s`：看 `SYNs to LISTEN sockets dropped`、`times the listen queue of a socket overflowed` 等计数器。
3. `dmesg`：SYN flooding 告警。
4. 性能计数器：`nstat -az | grep -i listen`。

定位到溢出后对症处理：
- 半连接队列溢出 → 大概率 SYN Flood 或被 DDoS，检查源 IP 分布、开 syncookies、限速。
- 全连接队列溢出 → 应用 accept 慢，查线程池、阻塞 I/O、epoll 配置，再考虑调大 backlog/somaxconn。

> 加分点：排查顺序应该是"**先看是哪个队列满**"，因为两个队列的根因完全不同——半连接满通常是网络层攻击，全连接满通常是应用层瓶颈。答出这一层，面试官会认为你有真实排障经验。

## 05 TCP 可靠性机制

### 5.1 TCP 如何保证可靠传输？【高频】
六大机制协同：
1. **序号与确认**：每个字节一个序号，ACK 告知对方"期望的下一个字节号"，实现有序重组与去重。
2. **确认与重传**：超时未确认（RTO）或收到重复 ACK → 重传。
3. **滑动窗口/流量控制**：按接收方 rwnd 调整发送量，防止接收方缓冲区溢出。
4. **拥塞控制**：按网络状态调整 cwnd，防止压垮网络。
5. **校验和**：首部+数据校验，损坏即丢弃（触发重传）。
6. **连接管理**：握手/挥手保证会话正确建立与释放。

> 加分点：一句话总结——**TCP 用"序号 + 确认 + 重传"对抗丢包，用"窗口"对抗双方速度差（流控）与网络容量差（拥塞控制），用"校验和"对抗损坏**。IP 层只保证"尽力而为"，所有可靠性都在传输层补上。

### 5.2 超时重传与快速重传【高频】
- **超时重传**：发送方启动 RTO（Retransmission Timeout）定时器，超时未收到 ACK 就重传。RTO 动态估算：`RTO = SRTT + 4×RTTVAR`（RFC 6298），超时后 RTO **指数退避**（×2）。连续超时 15 次（`tcp_retries2`）后放弃连接。
- **快速重传**：不等超时——发送方**收到 3 个重复 ACK**（即第 4 次收到相同 ack 号）就立即重传，避免傻等 RTO。原理：重复 ACK 说明"你发的下一个包丢了，且后续包陆续到了"。

> 加分点：快速重传触发条件是"**3 个重复 ACK**"不是 1 个——因为 1~2 个重复 ACK 可能只是乱序（后到的包先到），只有连续 3 个才能判定大概率真丢包。这是面试高频细节。

### 5.3 SACK 与 D-SACK【进阶】
- **SACK（Selective Acknowledgment）**：传统 ACK 只能确认"连续收到的最大序号"，如果中间丢了包（如收到 1-1000、3000-4000），发送方不知道 1000-3000 之外哪些已到，只能重传全部。SACK 选项允许接收方**精确报告已收到的非连续区间**，发送方只重传真正丢失的段，显著提升效率。
- **D-SACK（Duplicate-SACK）**：SACK 的增强，用于**报告重复收到的段**——让发送方判断"是重传导致重复，还是报文绕路迟到"，据此调整重传策略与 RTO 估算。

> 加分点：SACK 需要双方在握手时协商（选项），Linux 默认开启（`tcp_sack=1`）。高带宽高延迟链路（BDP 大）上 SACK 收益最明显；而 SYN Cookie 场景下 SACK 选项可能丢失，Linux 用"时间戳回填"补偿。

### 5.4 滑动窗口与流量控制（rwnd）【高频】
- **滑动窗口**：发送方维护 [已确认 | 已发送未确认 | 可发送 | 不可发送] 的窗口，窗口内可连续发送，无需逐包等待 ACK（累积确认），提升吞吐。
- **流量控制**：由**接收方**主导——接收方在 ACK 中携带 `rwnd`（接收窗口），告知"我还能收多少"。发送方窗口 = `min(swnd, rwnd, cwnd)`。若 rwnd=0，发送方停止发送并启动**窗口探测（persist timer）**。
- **零窗口死锁**：rwnd=0 后，若接收方恢复的"窗口更新报文"丢失，双方互等 → 用窗口探测（发送 1 字节探测包）打破。

> 加分点：流量控制（rwnd，防止"我收不过来"）与拥塞控制（cwnd，防止"网络受不了"）是**两个独立窗口**，发送量取两者较小值——这是高频区分点：**流控是端到端的接收方反馈，拥塞控制是发送方对网络状态的推测**。

### 5.5 拥塞控制：慢启动 / 拥塞避免 / 快速恢复【高频】
- **慢启动（Slow Start）**：连接建立时 cwnd 从 1（实际 10）个 MSS 开始，每收到一个 ACK 就翻倍（**指数增长**），直到 ssthresh（慢启动阈值）。
- **拥塞避免（Congestion Avoidance）**：超过 ssthresh 后 cwnd **线性增长**（每 RTT +1），探测可用带宽。
- **快速恢复（Fast Recovery）**：触发快速重传（3 个重复 ACK）时，cwnd 减半而非清零，配合快速重传快速恢复吞吐（区别于超时重传的直接降到 1 重新慢启动）。
- **超时重传**：视为严重拥塞，cwnd 重置为 1，ssthresh 减半，重新慢启动。

> 加分点：**AIMD（加性增、乘性减）** 是拥塞控制的灵魂——加法增窗口（温和探测），乘法减窗口（丢包即砍半/清零）。Linux 默认算法是 **CUBIC**（适合高带宽长链路），新内核还支持 BBR（基于带宽时延积，不靠丢包判断拥塞）。

### 5.6 CUBIC 与 BBR【进阶】
- **CUBIC**（Linux 默认，2008 起）：用**三次函数**控制窗口增长，与 RTT 无关——在长肥管道上窗口恢复快，适合数据中心/骨干链路，但对"浅缓冲队列"场景不够灵敏。
- **BBR**（Google，2016）：**不把丢包当作拥塞信号**，而是持续探测"带宽 × 时延"（BDP）——先用最大带宽增长，再找到最小时延，把 cwnd 稳定在 BDP 附近。在丢包率高但带宽富余的链路上吞吐远超 CUBIC（YouTube 从 CUBIC 切 BBR 后吞吐提升 2~25 倍）。

| 维度 | CUBIC | BBR |
|---|---|---|
| 拥塞信号 | 丢包 | 带宽×时延（BDP） |
| 窗口策略 | 三次函数 AIMD | 按 BDP 定窗口 |
| 适用场景 | 通用、大带宽 | 高丢包、长时延链路 |
| 代价 | 丢包误判拥塞 | 会挤占排队缓存，公平性有争议 |

> 加分点：BBR 的争议在于**会"吃掉"瓶颈路由器的排队缓存**（因为它不主动退让），多流竞争时对其他 TCP 流不友好；内核 5.9+ 提供 `bbr2` 改进了公平性。面试说出"BBR 靠测量不靠丢包、bbr2 修复公平性"就已超出平均水准。

### 5.7 粘包与拆包：TCP 是字节流协议【高频】
- **为什么有粘包**：TCP 是**面向字节流的传输**，只保证字节顺序，不保留应用消息边界。发送方多次 send 的数据可能被合并（Nagle 算法、缓冲区合并）一次交付；一次 send 的大数据也可能被拆成多次交付。
- **现象**：接收方把多条消息粘在一起（粘包），或一条消息被拆开（拆包/半包）。
- **解决方案**（4 选 1 或组合）：
  1. **定长消息**：每条消息固定长度，按长度切分（简单但浪费）。
  2. **分隔符**：消息以 `\n` 等特殊字符结尾（如 Redis RESP、行协议；需处理转义）。
  3. **长度前缀（最常用）**：消息头 4 字节长度 + 载荷，按长度字段切分（如 HTTP/2 帧、Netty LengthFieldBasedFrameDecoder）。
  4. **自定义协议**：头部含魔数+版本+长度等（如 Dubbo、MQ 协议）。

> 加分点：粘包/拆包**不是 TCP 的 Bug**，而是"流协议没有消息边界"的必然结果；UDP 是数据报协议，天然保留边界，所以**不会粘包**。Nagle 算法（小包合并）是粘包的重要诱因，实时性要求高的场景可 `TCP_NODELAY` 关闭。

## 06 长连接保活与连接数量

### 6.1 TCP KeepAlive 机制与三个内核参数【高频】
TCP KeepAlive 是内核层面的保活探测：
- 连接空闲 `tcp_keepalive_time`（默认 **7200s**，2 小时）后开始探测。
- 每隔 `tcp_keepalive_intvl`（默认 **75s**）发送一个探测包。
- 连续 `tcp_keepalive_probes`（默认 **9** 次）无响应 → 判定连接死亡并关闭。

即：默认情况下，一条空闲连接最长要 `7200 + 75×9 ≈ 2.2 小时` 才能被内核发现"对方死了"。应用可在 socket 上设置 `SO_KEEPALIVE` 并用 `TCP_KEEPIDLE/KEEPINTVL/KEEPCNT` 覆盖默认值。

> 加分点：**默认 2 小时才探测**意味着 TCP KeepAlive 主要防"长期空闲的连接被僵尸化"，对实时性场景（如 IM 检测用户掉线）完全不够——必须用**应用层心跳**。另外 KeepAlive 只保活**已建立的连接**，不能防断线重连。

### 6.2 应用层心跳 vs TCP KeepAlive【高频】

| 维度 | TCP KeepAlive | 应用层心跳 |
|---|---|---|
| 实现层 | 内核协议栈 | 应用代码 |
| 默认探测间隔 | 2 小时（太慢） | 可按需，如 30s |
| 探测粒度 | 只知道"连接死没死" | 可携带业务数据/确认业务存活 |
| 可靠性 | 依赖系统参数 | 完全可控 |
| 典型场景 | 防僵尸连接、NAT 映射回收 | IM 在线状态、长连接健康检测 |

**实践结论**：IM/长连接系统通常两者都用——TCP KeepAlive 兜底清理僵尸连接，应用层心跳做真正的活跃度检测（心跳超时 → 标记掉线 → 触发重连与状态广播）。

> 加分点：心跳报文要轻（一个 ping 帧即可），**心跳超时判定要防抖动**（连续 N 次未收到才判死）；另外 NAT 网关会回收长时间无流量的映射，所以心跳间隔一般要小于 NAT 映射超时（常见运营商 NAT 超时约 30~120s），**30s 心跳是工程经验值**。

### 6.3 长连接与短连接的对比与选择【高频】

| 维度 | 短连接 | 长连接 |
|---|---|---|
| 建连成本 | 每次请求都 3 次握手+4 次挥手 | 首次建连后复用 |
| 时延 | 每请求多 1~2 RTT | 无额外握手 RTT |
| 资源占用 | 频繁 TIME_WAIT、SYN/ACK 开销 | 常驻 fd、内存、保活开销 |
| 适用场景 | 低频、服务端集群大、无状态 | 高频交互、实时推送、内部 RPC |

选择原则：
- **B/S 高频 Web** → HTTP Keep-Alive / HTTP/2 长连接复用。
- **服务间 RPC、DB/Redis/MQ 客户端** → 连接池长连接。
- **低频一次性请求**（如发送一次邮件通知）→ 短连接更省资源。
- 长连接要考虑：连接数上限、心跳、断线重连、负载均衡（粘性会话）。

> 加分点：真正的工程结论是"**短连接的性能瓶颈在握手 RTT，长连接的性能瓶颈在连接管理与保活**"。HTTP 时代用 Keep-Alive、HTTP/2 把多路复用做到单连接内，本质上都是在"驯服建连成本"。

### 6.4 一台服务器最多能建立多少 TCP 连接？【高频】
理论极大，实际受多重约束：
- **四元组上限**：源 IP×源端口×目的 IP×目的端口 = 2^32 × 2^16 × 2^32 × 2^16 ≈ 2^96，理论上无穷。
- **实际瓶颈**：
  1. **文件描述符 fd**（最直接）：`ulimit -n`，每连接至少 1 个 fd。百万连接需要 ≥ 100w+ fd。
  2. **内存**：每个 TCP 连接内核态约 3~4KB（sock + 缓冲区），百万连接约 3~4GB 内核内存，加上用户态缓冲区、线程栈，轻松吃掉几十 GB。
  3. **端口**：作为**服务端**监听同一端口可接受海量连接（四元组靠客户端端口区分）；作为**客户端**单 IP 最多约 6.5 万端口（2^16，含保留端口），需要多 IP/端口复用突破。
  4. **中断/CPU**：每连接收发包都触发软中断，CPU 是隐藏瓶颈。

> 加分点：经典数字——**单机 C10K 早已过时，现代 Linux + epoll 单机可支撑百万连接（C10M 靠内核旁路如 DPDK/XDP 或用户态协议栈）**。面试常用话术："百万连接的瓶颈不是内核能不能 hold，而是 fd、内存、CPU 中断的工程化调配。"

### 6.5 TCP 连接为什么用四元组标识？【基础】
四元组 = **源 IP + 源端口 + 目的 IP + 目的端口**，唯一确定一条连接：
- IP 定位主机，端口定位主机上的进程/服务，四元组精确定位"哪台机器的哪个进程 ↔ 哪台机器的哪个进程"。
- 同一条连接的两端各有一个（IP, 端口），双向复用同一四元组。
- 服务器 listen 一个端口（如 80），可以同时服务百万条连接——因为每条连接的**客户端四元组不同**，内核靠四元组哈希找到对应 sock。

> 加分点：补充两个变体——**五元组** = 四元组 + 协议（区分 TCP/UDP）；**七元组** = 五元组 + 进出接口 + 会话 ID（防火墙/负载均衡常用）。答出这个递进关系，显示对网络栈的完整理解。

### 6.6 C10K / C10M 问题与 epoll【高频】
- **C10K**：单机并发 1 万连接。老方案（进程/线程 per 连接）在 1 万连接时线程切换、内存爆炸。核心解法是 **I/O 多路复用**：
  - **select/poll**：内核每次把全部 fd 拷给用户态，O(n) 遍历，fd 上限 1024/无上限但低效。
  - **epoll**（Linux）：**事件驱动 + 就绪回调**，只返回"就绪的 fd"，O(1) 处理，无数量上限。配套 **ET（边缘触发）** 与 **LT（水平触发）** 模式。
  - macOS/BSD 用 **kqueue**，Windows 用 **IOCP**（真正的异步 I/O）。
- **C10M**：单机千万连接。纯 epoll 也难，需要 **DPDK/XDP（内核旁路，用户态收包）**、多队列网卡（RSS）、无锁编程。

> 加分点：epoll ET vs LT——**LT**（默认）只要缓冲区有数据就持续通知，编程简单；**ET** 只在状态变化时通知一次，必须一次性读完（配合非阻塞 I/O 循环读），否则丢数据。Netty 默认 LT（对 Java 友好），Redis/Node 的 libuv 默认 **ET**——答出 Redis 用 ET 是加分项。

## 07 UDP 连接与可靠 UDP

### 7.1 UDP 为什么"无连接"？UDP 头部 8 字节【基础】
- UDP 头部只有 **4 个字段 × 16 bit = 8 字节**：源端口、目的端口、长度、校验和。**没有序号、没有确认、没有窗口、没有状态**——所以不需要连接。
- "无连接"的三层含义：
  1. **无需握手**：发数据前不建立会话。
  2. **无状态**：两端不保存对方信息，内核里没有连接表。
  3. **无保证**：不保证送达、不保证有序、不保证不重复。

> 加分点：正因为 UDP 头只有 8 字节，**QUIC 才能在用户态把"连接状态"搬到应用层实现**——UDP 是"裸奔"的传输层，什么都能在它上面自己造，这是 QUIC/KCP 能落地的前提。

### 7.2 UDP 报文最大多大？MTU 分片【进阶】
- **理论最大**：UDP 长度字段 16 bit，最大 65535 字节，减 IP 头 20 + UDP 头 8，**载荷最大 65507 字节**。
- **实际限制**：IP 层 MTU（以太网 1500 字节），超过 MTU 会触发 **IP 分片**——分片包只要丢一片，整个报文作废（IP 层不重传），所以**大 UDP 报文可靠性极差**。
- **最佳实践**：UDP 载荷控制在 **MTU 内**（以太网建议 ≤ 1472 字节，减去 IP+UDP 头），或做应用层分片 + 序号重组（QUIC 就是这么干的，还带重传）。

> 加分点：**PMTUD（路径 MTU 发现）** 通过探测避免分片；但某些网络会静默丢弃 DF 置位的大包，导致"小包通、大包不通"的诡异故障——面试能举这个排障案例很加分。IPv6 路由器不再分片（只有源端可分片），更依赖 PMTUD。

### 7.3 如何基于 UDP 实现可靠传输？【高频】
在 UDP 之上补 TCP 的能力（自研 RUDP）：
1. **序号**：给报文编号，接收方检测丢包/乱序/重复。
2. **确认 ACK + 重传**：NACK（否定确认，丢了哪些）比纯 ACK 更高效；超时重传 + 快速重传。
3. **缓冲与排序**：接收方重排乱序报文。
4. **流量控制**：滑动窗口（发送窗口、接收窗口）。
5. **拥塞控制**：可选（游戏场景常简化或不做）。
6. **连接标识**：用连接 ID 代替四元组（可支持连接迁移）。

> 加分点：RUDP 的意义在于**按需裁剪**——"既要 UDP 的低时延，又要 TCP 的可靠"，但把拥塞控制做对很难（很多自研 RUDP 在网络拥塞时会打爆路由器），所以业界更倾向直接用成熟的 **QUIC 或 KCP**，而不是从零造轮子。

### 7.4 QUIC：基于 UDP 的可靠连接【进阶】
QUIC（Quick UDP Internet Connections，Google，HTTP/3 的传输层）核心特性：
1. **0-RTT / 1-RTT 建连**：首次 1-RTT，复用会话 0-RTT（缓存密钥），比 TCP+TLS（2~3 RTT）快得多。
2. **连接 ID 与连接迁移**：连接不再绑定 IP:端口四元组，**换 Wi-Fi/换网络 IP 变化连接不断**（手机切网不重连）。
3. **无队头阻塞**：多路复用多个 stream，**一个 stream 丢包只重传该 stream**，不影响其他 stream（HTTP/2 在 TCP 上做不到）。
4. **TLS 1.3 内嵌**：加密握手与传输握手合一，无明文阶段。
5. **用户态实现**：迭代快（TCP 改进要改内核），且**无需 NAT 打洞**（UDP 天然可穿越 NAT）。

> 加分点：面试高频对比——**HTTP/2 的队头阻塞在 TCP 层**（丢一个包，整个 TCP 连接上的所有 stream 都要等重传）；**QUIC 把"可靠传输"按 stream 隔离**，把队头阻塞限制在单 stream 内。这是 HTTP/3 选择 QUIC 的根本原因。

### 7.5 KCP 与其他 RUDP 方案对比【进阶】

| 方案 | 定位 | 特点 |
|---|---|---|
| QUIC | 通用可靠传输（HTTP/3 基座） | 标准、全特性、拥塞控制完备 |
| KCP | 游戏加速可靠 UDP | **牺牲带宽换低延迟**：快速重传、非退避重传、可配置拥塞，适合弱网实时对战 |
| WebRTC SCTP | 浏览器实时通信数据通道 | 基于 SCTP over DTLS over UDP，内置有序/无序两种模式 |
| 自研 RUDP | 私有业务 | 灵活但易踩坑 |

> 加分点：KCP 的核心思想是"**用更多重传换取更快到达**"——它的快速重传阈值可配置（默认 2 个重复 ACK 就重传），重传间隔不按 RTO 退避，还支持"跳过确认"（收到乱序包就提前重传疑似丢失的包）。弱网游戏用它，因为它不在乎多吃带宽。

### 7.6 TCP 与 UDP 如何选择？【高频】
决策模型（按业务诉求）：
1. **需要可靠 + 有序 + 通用** → TCP（HTTP、数据库、文件、RPC）。
2. **容忍少量丢失但要求低时延** → UDP（音视频、游戏操作指令、实时监控——丢一帧无所谓，等重传反而卡顿）。
3. **要求可靠但又要低时延/连接迁移** → QUIC（HTTP/3、弱网移动端）。
4. **广播/组播/任播** → 只能 UDP。
5. **DNS** → UDP 为主（单包小、快），超时重试才切 TCP。

> 加分点：一句话——**"TCP 用时间换可靠，UDP 用不可靠换时间，QUIC 想两个都要"**。面试被问"视频会议为什么不用 TCP"，标准答案是：TCP 丢包后的重传与队头阻塞会造成画面卡顿与声音滞后，实时媒体宁可丢旧帧也要及时渲染新帧，所以 RTP/QUIC 这类"部分可靠"才是正解。

## 08 HTTP 连接模型演进

### 8.1 HTTP/1.0 vs HTTP/1.1：短连接到长连接【高频】
- **HTTP/1.0**：**默认短连接**，每个请求/响应后 TCP 连接即关闭，下一个请求重新三次握手。请求频繁时建连开销巨大（多 RTT + 系统资源）。
- **HTTP/1.1**：**默认持久连接（Keep-Alive）**，同一 TCP 连接上串行传输多个请求/响应，直到客户端或服务器主动关闭。响应头带 `Connection: keep-alive`（默认，可显式）；`Connection: close` 表示用完即关。

> 加分点：Keep-Alive 让**一个 TCP 连接处理多个请求**，省去重复握手；但 HTTP/1.1 仍然**串行**——同一连接上的请求必须排队（队头阻塞在 HTTP 层），浏览器为突破限制只能开 6 个并发连接（同域名）。这两个痛点（串行 + 连接数限制）正是 HTTP/2 要解决的。

### 8.2 Keep-Alive 与 Connection 头【高频】
- `Connection: keep-alive`：要求复用连接（HTTP/1.1 默认，可不写）。
- `Connection: close`：请求/响应完成后关闭连接。
- **HTTP/2 禁止 Connection 头**（连接管理交给协议层，多路复用天然复用）。
- 服务器侧超时参数：`keepalive_timeout`（Nginx 默认 75s）、`keepalive_requests`（Nginx 默认 1000，单连接最大请求数，防长连接被单个慢客户端长期占住）。

> 加分点：**长连接也不是无限长**——服务器要限制单连接的请求数和空闲超时，否则慢客户端会占着连接不释放（连接耗尽攻击的一个变种）。Nginx 的 keepalive_requests=1000 就是为平衡"复用收益"与"占用成本"。

### 8.3 HTTP 管线化（Pipelining）为什么失败？【进阶】
HTTP/1.1 曾引入**管线化**：一个连接上连续发送多个请求，不必等前一个响应——理论上提高并发。但它失败了：
1. **队头阻塞仍在**：服务器**必须按序响应**（协议要求），第一个响应慢，后面全堵住。
2. **兼容性问题**：代理、服务器实现不统一，很多不遵守规则。
3. **无多路复用语义**：响应无法标识对应哪个请求（没有流 ID）。
- 结果：主流浏览器与服务器**普遍禁用/从未支持**管线化，等于废弃，直到 HTTP/2 用真正的多路复用解决。

> 加分点：管线化的教训是"**半吊子的并发比不做更糟**"——按序响应约束让管线化在慢响应场景反而更慢（HoL blocking at HTTP layer），HTTP/2 的核心突破就是**给每个请求独立流 ID，允许乱序响应**。

### 8.4 HTTP/2 多路复用：一个连接多个流【高频】
HTTP/2 的关键机制：
1. **二进制分帧**：把请求/响应拆成帧（HEADERS / DATA / RST_STREAM / SETTINGS 等），帧携带 **流 ID（Stream ID）**。
2. **多路复用**：**一个 TCP 连接上并发多个流**（Stream），帧交错发送，**响应可以乱序到达**（按流 ID 重组），彻底消除 HTTP 层的队头阻塞。
3. **头部压缩 HPACK**：静态表+动态表+哈夫曼编码，头部体积平均下降 80%+。
4. **服务端推送（Server Push）**：服务器可主动推送资源（已逐渐被弃用，因缓存问题）。
5. 浏览器不再需要 6 连接并发——**单连接承载所有请求**。

> 加分点：HTTP/2 解决了 **HTTP 层**的队头阻塞，但**TCP 层的队头阻塞还在**——TCP 丢一个包，重传期间该连接上所有流的数据都得等（接收缓冲按序交付）。这个"残留问题"只有 HTTP/3 能治，这是面试必须能接上的下一句。

### 8.5 HTTP/2 的队头阻塞问题【进阶】
- **TCP 层队头阻塞**：HTTP/2 所有流共享一个 TCP 连接。若一个流的一个包丢失，TCP 接收方只能按序缓冲，**整个连接上的所有流都被阻塞**，直到重传到达。
- **触发场景**：弱网、高丢包链路（丢包率 > 1% 时 HTTP/2 可能比 HTTP/1.1 还慢——因为 HTTP/1.1 多个连接互相独立，一个连接丢包不影响其他连接）。
- **缓解**：部分实现做"多 TCP 连接分摊流"（Chrome 曾尝试 QUIC 前用多连接），但治本方案就是 HTTP/3。

> 加分点：量化记忆——**丢包率 0.1% 时 HTTP/2 仍优于 HTTP/1.1；丢包率超过 1~2% 时 HTTP/2 反而劣于多连接的 HTTP/1.1**。这个"临界点"结论经常被面试官用来验证你是否真的理解队头阻塞。

### 8.6 HTTP/3 QUIC：连接迁移与 0-RTT【进阶】
HTTP/3 = HTTP 语义 + QUIC 传输：
1. **无 TCP 层队头阻塞**：每个流独立可靠传输（QUIC 内部按流管理序号与重传），一个流丢包不影响其他流。
2. **0-RTT 建连**：复用缓存的连接参数与 TLS 密钥，首个请求随握手一起发出（有重放风险，仅用于幂等请求）。
3. **连接迁移**：连接 ID 不随 IP 变化——手机从 Wi-Fi 切 4G，QUIC 连接不断，HTTP 会话无需重连（TCP 做不到，IP 变了连接就断）。
4. **基于 UDP**：UDP 头 + 自实现可靠传输，便于用户态升级迭代。

> 加分点：HTTP/3 的握手是"**TLS 1.3 + 传输握手合并**"——TCP+TLS1.3 需要 1 RTT（TLS）+ 1 RTT（TCP）≈ 2 RTT，HTTP/3 首次 1 RTT、复用 0 RTT。移动端弱网场景收益最大（连接迁移 + 无队头阻塞），2023 年起 Chrome/Firefox/Safari 默认启用。

### 8.7 HTTP 连接池如何复用连接？【高频】
- **为什么需要连接池**：HTTP 客户端（OkHttp、Apache HttpClient、Go 的 Transport、JDK HttpClient）内部维护连接池，把 Keep-Alive 连接缓存复用，避免每次请求建连。
- **核心机制**：
  1. **缓存**：按 (scheme, host, port) 分组保存空闲连接。
  2. **复用**：新请求优先从池中取空闲连接，超时未取到才新建。
  3. **驱逐**：空闲超时（如 OkHttp 默认 5 分钟 keepAlive）、连接数上限（maxIdleConnections）、过期清理。
  4. **健康检查**：取出时校验连接是否仍可用（如 TCP 探测、HTTP/2 ping），失效则废弃重建。
- **参数**：最大空闲连接数、keep-alive 时长、连接获取超时、每路由最大连接数。

> 加分点：连接池与数据库连接池同理——**池的本质是"以空间换时间 + 复用昂贵的建连成本"**。HTTP/2 时代连接池的"路由"从连接粒度细化为"连接上的流"，连接数需求大幅下降（单连接多流），池的参数模型也随之变化。

## 09 WebSocket 与实时双向连接

### 9.1 WebSocket 握手过程【高频】
WebSocket 通过 **HTTP Upgrade** 建立：
1. 客户端发 HTTP 请求：
```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```
2. 服务器计算 `Sec-WebSocket-Accept = Base64(SHA1(Sec-WebSocket-Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))`，返回：
```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```
3. 之后连接升级为 **全双工双向** 数据通道，不再走 HTTP 语义。

> 加分点：**Sec-WebSocket-Key 是随机 16 字节 base64，防缓存代理**（保证请求新鲜）；握手成功后**连接不复用给普通 HTTP**（协议已切换），网关/负载均衡需要开启 WebSocket 透传（`upgrade` 头部放行），否则连接会被代理截断。

### 9.2 WebSocket 与 HTTP 长轮询 / SSE 对比【高频】

| 维度 | HTTP 轮询 | HTTP 长轮询 | SSE | WebSocket |
|---|---|---|---|---|
| 方向 | 单向（客户端拉） | 单向 | 服务器→客户端单向 | **全双工双向** |
| 协议 | HTTP | HTTP | HTTP（text/event-stream） | 独立帧协议 |
| 实时性 | 差 | 较好 | 好 | 最好 |
| 开销 | 高（高频请求） | 中 | 低（长连接复用） | 低 |
| 自动重连 | 无 | 无 | **内置（Last-Event-ID）** | 需自己实现 |
| 典型场景 | 旧系统 | 弱网兜底 | 通知流、行情推送 | 聊天、游戏、协同编辑 |

> 加分点：**SSE 比 WebSocket 简单得多且自带重连**（服务端断线可基于 Last-Event-ID 续传），只做"服务器单向推送"时优先 SSE；需要客户端主动发消息/真正双向交互才上 WebSocket。面试说"不是所有实时场景都该用 WebSocket"是成熟的表现。

### 9.3 WebSocket 帧结构与掩码【进阶】
WebSocket 帧格式（RFC 6455）：
- **FIN**（1 bit）：是否最后一帧（分片控制）。
- **RSV**（3 bit）：扩展位。
- **opcode**（4 bit）：0x1 文本、0x2 二进制、0x8 关闭、0x9 Ping、0xA Pong、0x0 续帧。
- **MASK**（1 bit）：**客户端 → 服务器必须置 1**，服务器 → 客户端必须为 0。
- **Payload len**（7 bit / 扩展 16 bit / 64 bit）：载荷长度。
- **Masking-Key**（4 字节）：仅客户端发帧时存在，用于载荷异或混淆。

> 加分点：**掩码机制是为了防止"缓存投毒攻击"**——早期代理会缓存内容，攻击者通过 WebSocket 伪造 HTTP 响应头注入缓存，掩码让载荷对中间代理不可预测，破坏这种注入。这是 RFC 6455 中"客户端必须掩码、服务端禁止掩码"不对称设计的真实原因，答出这一点非常加分。

### 9.4 WebSocket 心跳与断线重连【高频】
- **心跳**：协议自带 **Ping/Pong** 帧（opcode 0x9/0xA）。客户端定时发 Ping，服务器必须回 Pong；N 次无 Pong 判定断线。也可用应用层 JSON 心跳报文（可携带业务信息，但会污染业务协议，一般优先 Ping/Pong）。
- **断线重连策略**：
  1. **立即重连**：检测到断开马上重连。
  2. **指数退避 + 随机抖动**：1s、2s、4s… 上限 30s，加 ±随机抖动防止"惊群"（大量客户端同时重连打爆服务器）。
  3. **重连后状态恢复**：重新鉴权、恢复订阅、补发断线期间的消息（结合消息序号）。
  4. **服务端重连限流**：记录最近断连频次，频繁断连要求等待更久，防客户端死循环打爆服务。

> 加分点：重连抖动（jitter）是工程细节——**纯指数退避会导致 N 个客户端在同一时刻集体重连（雷群效应）**，加抖动后分散到时间轴上。云厂商 SDK 普遍用"退避 + 抖动 + 上限"三段式，面试能主动提 jitter 是加分项。

### 9.5 WebSocket 与 HTTP/2 的关系【进阶】
- HTTP/2 本身支持**双向流**（客户端发起的 server push 是单向推送，且仅限服务器→客户端；WebSocket 是真正的双向）。
- HTTP/2 提供了 **RFC 8441（Extended CONNECT）**：允许 WebSocket 在 HTTP/2 连接上复用（在 HTTP/2 之上承载 WebSocket），解决"HTTP/2 场景下 WebSocket 只能另开 TCP 连接"的问题。
- **本质上 WebSocket 与 HTTP/2 是不同层的复用**：WebSocket 提供"应用层双向消息通道"，HTTP/2 提供"传输层多路复用"；两者可以组合。

> 加分点：一个易混点——**HTTP/2 的 Server Push 与 WebSocket 是两回事**：Push 是"服务器预判客户端需要的资源并提前推送"（单向、一次性、易缓存错配），WebSocket 是"建立后任意时刻双向自由收发"。HTTP/3 时代 WebSocket over QUIC 也已有草案（WebTransport 的补充）。

## 10 连接池原理与参数

### 10.1 为什么需要连接池？【基础】
- **建连成本高**：数据库/Redis/MQ 等每次建立 TCP 连接 = 三次握手 + 鉴权 + 初始化会话（MySQL 还要做认证、权限校验、建临时表等），动辄数十 ms。
- **无池的痛点**：每请求建连 → 高并发下握手风暴、TIME_WAIT 爆炸、数据库端连接建立风暴，QPS 上不去。
- **池化收益**：
  1. **复用**：连接建好反复用，摊薄建连成本。
  2. **限流**：池有上限，天然保护下游（数据库连接数可控）。
  3. **预热与监控**：启动时预建连接（预热），空闲/泄漏可观测。

> 加分点：连接池的本质是**"对象的昂贵初始化与高频使用解耦"**——同理还有线程池、HTTP 连接池、内存对象池。池化三要素：**容量上限、空闲回收、生命周期管理**，任何池都逃不出这三件事。

### 10.2 数据库连接池核心参数（以 HikariCP 为例）【高频】
HikariCP（Spring Boot 默认）关键参数：

| 参数 | 默认值 | 作用 |
|---|---|---|
| maximumPoolSize | 10 | 池中**最大连接数**（含使用中） |
| minimumIdle | 10 | 最少空闲连接数（维护下限） |
| connectionTimeout | 30000ms | **获取连接超时**，超时抛异常 |
| idleTimeout | 600000ms | 空闲连接**回收**时长（仅当空闲 > minimumIdle 时生效） |
| maxLifetime | 1800000ms | 连接**最大存活时间**（必须小于数据库 wait_timeout） |
| connectionTestQuery | 无 | 连接健康检查 SQL（如 `SELECT 1`） |
| leakDetectionThreshold | 0（关闭） | 连接泄漏检测阈值 |

> 加分点：**maxLifetime 必须 < 数据库的 wait_timeout**（MySQL 默认 8 小时，连接被服务端空闲断开后，池内"僵尸连接"会导致报错），这是连接池与数据库之间最容易踩的坑；`leakDetectionThreshold` 开启后，连接持有超过阈值会**强制归还并打日志**，是排查泄漏的利器。

### 10.3 连接池如何维护连接？获取/归还/驱逐【进阶】
生命周期状态机：
1. **创建**：池空且未达上限 → 新建连接（可**预热**，启动时预建 minimumIdle 条）。
2. **获取（borrow）**：优先取空闲连接；空闲不足且未达上限 → 新建；达上限 → **等待**（connectionTimeout 内等归还）。
3. **归还（release）**：使用完放回空闲队列（注意：必须**释放事务/重置状态**，否则下个用户拿到脏状态）。
4. **驱逐（evict）**：空闲超时（idleTimeout）、存活超时（maxLifetime）、健康检查失败（testQuery）→ 关闭并移除，再按需补充。
5. **泄漏防护**：持有超阈值（leakDetectionThreshold）→ 警告并强制回收。

> 加分点：**连接归还 ≠ 关闭连接**，归还是把连接"重置并放回池"，关闭是销毁——连接池 bug 多出在"归还时没重置（autocommit 被改、临时表残留、字符集被改）"，导致连接状态污染，这类问题极难排查，面试提"连接状态重置"是资深信号。

### 10.4 连接泄漏与 leakDetectionThreshold【高频】
- **泄漏场景**：代码拿了连接没归还（异常未 finally 释放、连接被线程持有不放、ThreadLocal 传递导致跨线程占用）→ 池被耗尽 → 后续请求全部超时/报"connection pool exhausted"。
- **排查手段**：
  1. `leakDetectionThreshold=5000`：连接持有超 5s 未归还 → HikariCP 打印完整**调用栈堆栈**（能定位到具体代码行）→ 开启后定位泄漏精确到行。
  2. 监控：池使用率曲线、活跃连接数、等待获取超时次数。
  3. 代码审查：try-with-resources / finally 中归还。
- **根治**：规范编码（Java 用 try-with-resources；Python 用 with/contextmanager）+ 压测 + 泄漏检测阈值全开。

> 加分点：**泄漏检测只能"事后发现"**（连接被借出超过阈值才报警），无法阻止泄漏；更本质的防线是**编码规范 + 代码评审 + 超时兜底**（connectionTimeout 保证请求不会无限等）。另外注意：`leakDetectionThreshold` 必须小于 `connectionTimeout` 才有意义（否则等待方先超时了）。

### 10.5 连接池大小怎么设置？【高频】
- **误区**：连接越多吞吐越高？错——连接是**串行执行 SQL** 的资源，CPU 核数是真实上限。**过大的连接池反而降低吞吐**（线程切换、锁竞争、数据库端连接风暴）。
- **经验公式**：`连接数 = CPU核数 × 2 + 有效磁盘数`（HikariCP 作者 Brett Wooldridge 给出的公式，机械硬盘场景；SSD/高并发 IO 场景可乘 4~8）。
- 关键权衡：
  - 池太小 → 等待获取超时，吞吐受限。
  - 池太大 → 数据库连接数爆炸、上下文切换开销、GC 压力。
- **正确姿势**：按"**P99 延迟达标 + 池使用率 30~60%**"为目标调参，配合压测（如 50/100/200 连接三档对比吞吐曲线）。

> 加分点：公式背后的原理——**数据库查询是 CPU+IO 密集的串行操作，一个活跃连接同一时刻只能跑一个查询，并发收益上限 ≈ CPU 核数 × (1/IO 等待占比)**。池的"最优大小"是让 CPU 刚好饱和、连接不排队，而不是越大越好——这是与"线程池大小"完全一致的建模逻辑。

### 10.6 连接预热与连接健康检查【进阶】
- **预热（Warm-up）**：应用启动时提前创建 minimumIdle 条连接并执行轻量查询（如 `SELECT 1`），避免"上线第一波流量全部卡在建连上"——常见于发布扩容后的流量尖峰。
- **健康检查**：
  - **惰性校验**：借出时校验（多一次 RTT，只对"可疑连接"做）。
  - **定期校验**：后台线程用 connectionTestQuery 探测空闲连接，失败即淘汰（HikariCP 默认每 30s 检查空闲连接）。
  - **建连时校验**：新连接必须通过校验才能入池（防 DNS/权限变更后建出"哑连接"）。
- 典型故障：数据库重启、网络闪断、防火墙超时 → 池内连接变僵尸 → 不校验则首次使用必报错（"Communications link failure"），健康检查后自动淘汰重建，业务无感。

> 加分点：**"僵尸连接"检测的经典坑**——如果连接是"空闲状态被服务端断开"，借出时才知道（惰性校验命中）；连接池推荐组合是"**惰性校验 + 后台定期校验**"，仅靠定期校验会漏掉"刚被断开、还没到检查周期"的连接。这也是 HikariCP 用 `aliveBypassWindow`（200ms 内刚借出的连接跳过重复校验）做性能优化的原因。

## 11 连接问题排查与场景题

### 11.1 线上大量 TIME_WAIT 怎么排查处理？【高频】
**排查**：
```bash
# 统计 TIME_WAIT 数量
ss -ant | awk '{print $1}' | sort | uniq -c | sort -rn
# 看哪些目标端口（对端）堆积
ss -ant state time-wait | awk '{print $4}' | sort | uniq -c | sort -rn
```
**根因判断**：谁主动断开谁产生 TIME_WAIT——大量 TIME_WAIT 说明**本机是主动关闭方**，且连接"建了即断"（短连接、代理转发、健康检查等）。

**处理**（按收益排序）：
1. 业务层开启**连接复用**（Keep-Alive/连接池）——治本。
2. 确认 TIME_WAIT 数量是否真的影响可用性（**< 几万通常无感**，端口耗尽才致命）。
3. 必要时 `tcp_tw_reuse=1`（仅客户端角色）+ `tcp_timestamps=1`；禁用 tcp_tw_recycle。
4. 架构层：客户端集中断连改为服务端断开/负载均衡分摊。

> 加分点：**TIME_WAIT 本身不是故障，端口耗尽才是**。TCP 连接四元组中源端口只有 6.5 万，若高 QPS 短连接且 TIME_WAIT 占用 60s，理论上每秒新建超 1000 连接就可能耗尽端口——所以"量大不大"要看"每秒新建速率 × 60s"是否接近 6.5 万，而不是看绝对值。

### 11.2 线上大量 CLOSE_WAIT 怎么排查处理？【高频】
**排查**：
```bash
ss -antp | grep CLOSE_WAIT | head -20   # 定位进程 PID
# 数量统计
ss -ant | grep -c CLOSE_WAIT
# 对端是谁
ss -ant state close-wait | awk '{print $5}' | sort | uniq -c | sort -rn
```
**根因**：被动关闭方收到 FIN 后**应用没调用 close()**。锁定进程后：
1. `jstack <pid>` 看线程是否阻塞在 IO/锁上（线程池耗尽 → 无法处理关闭事件）。
2. 检查代码：读循环里是否处理了 `read()==-1/0` 并 close；异常分支是否漏 close。
3. 检查连接管理：是否有第三方库/网关吞掉了关闭事件。
4. 兜底：调整 `tcp_keepalive_time` 让僵尸连接更快被回收（治标）。

> 加分点：CLOSE_WAIT 排查的"三板斧"：**ss 定位进程 → jstack 找阻塞线程 → 代码审计 close 路径**。大多数线上 CLOSE_WAIT 堆积是"线程池被慢下游占满，处理线程没机会执行 close"，所以**先看线程池状态**比先看代码更高效——面试答这个顺序比答原理更值钱。

### 11.3 连接超时：connect timeout / read timeout 区别【高频】
- **connect timeout（连接超时）**：从发起 TCP 连接到**握手完成**的等待上限。超时原因：目标不可达、防火墙丢包（SYN 无响应）、半连接队列满。设置建议：**局域网 1~3s，公网 3~5s**，不宜太长（否则故障感知太慢）。
- **read timeout（读超时/响应超时）**：连接建立后，**等待响应数据**的时限。超时原因：服务端处理慢、死锁、网络拥塞、服务端崩溃（连接悬挂）。设置建议：**按业务 P99 延迟 × 3~5**。
- **write timeout**：发送缓冲区满时等待写入。

> 加分点：超时设置的核心原则——**"connect 要短（快速失败），read 要按业务容忍度（给足余量）"**。另外一个高频细节：**read timeout 超时只是"放弃等待"，连接本身未必失效**，多数框架会**直接关闭连接**（防止读到错位数据），所以 read timeout 之后连接不可复用。

### 11.4 断线重连策略：指数退避与抖动【高频】
- **目标**：断线后快速恢复，同时不把服务器打挂。
- **标准策略（指数退避 + 随机抖动 + 上限）**：
  ```
  delay = min(base * 2^attempt, max_delay)
  delay = delay + random(0, jitter)   # 抖动，防雷群
  ```
  例：base=1s，max=60s，attempt=0,1,2… → 1s、2s、4s、8s…60s。
- **细节**：
  1. **成功连接后重置计数**。
  2. **连续失败阈值**：达到上限后进入"长等待"，避免死循环空转。
  3. **状态恢复**：重连后重放订阅/鉴权/断点续传（消息序号）。
  4. **服务端视角**：记录每客户端重连频率，超频拒绝（防被 client 循环打）。

> 加分点：抖动（jitter）的存在理由——**N 个客户端同时断网恢复时，若无抖动会在同一秒集体重连（惊群/雷群效应），把刚恢复的服务器再次打挂**；加 ±50% 随机抖动后重连均匀散开。真实分布式系统（如 Kafka 消费者、云 SDK）全部内置该策略。

### 11.5 NAT 穿透与 UDP 打洞【进阶】
- **问题**：内网主机（如手机在 WiFi 后）没有公网 IP，公网对端无法直接连它——NAT 为出站连接建立"映射表"，只允许"从内部发起的会话"反向回包。
- **NAT 类型**（按限制从松到严）：
  1. **全锥形（Full Cone）**：映射后任意公网主机都能往该端口发包。
  2. **受限锥形（Restricted Cone）**：只有"本机曾经通信过的目标 IP"能发包进来。
  3. **端口受限锥形（Port Restricted）**：限定目标 IP+端口。
  4. **对称 NAT（Symmetric）**：**每个目标地址/端口都建立独立映射**——最难穿透。
- **UDP 打洞原理**：A、B 同时向对方公网地址发 UDP（各自 NAT 建立映射），**利用"受限锥形允许已通信 IP 反向发包"的规则**，双方互相"踩通"映射后即可互发。
- **TCP 打洞**：更难（SYN 时序与 NAT 映射策略不可控），P2P 一般用 UDP 打洞 + 上层可靠协议（QUIC/自研）。

> 加分点：**对称 NAT 下 UDP 打洞必然失败**，业界兜底方案是 **TURN（中继转发）**——由公网服务器中转所有流量（WebRTC 就是这么设计的：先尝试 P2P，失败降级 TURN）。面试能完整说出"打洞适用受限锥形、对称 NAT 必须 TURN 中继"就达到专家线。

### 11.6 负载均衡的连接保持（粘性会话）【进阶】
- **问题**：无状态化后请求会被分发到不同后端，但**有状态会话**（登录态、购物车、WebSocket 长连接）要求后续请求仍落到同一台后端。
- **方案**：
  1. **Cookie 粘性**：LB 种下 Cookie 记录后端选择。
  2. **IP Hash**：按客户端 IP 哈希到固定后端（Nginx ip_hash）。
  3. **一致性哈希**：带虚拟节点，后端增减时**仅少量会话迁移**（Redis 集群分片同款思想）。
  4. **会话外部化**（治本）：把 Session 放 Redis/DB，彻底不依赖粘性（现代分布式系统的正解）。
- **长连接场景**：WebSocket/HTTP/2 的连接与后端绑定，LB 需保证"同连接同后端"（HTTP/2 一个连接上的所有流必须去同一后端，否则流状态错乱）。

> 加分点：粘性会话是**"局部优化"**，会话外部化才是**"全局正解"**——面试升级话术："粘性只是过渡方案，它的代价是后端扩容/缩容时的会话抖动与单点热点；生产上优先把会话下沉到分布式缓存（Redis），让任意后端都能服务任意请求。"（Nginx ip_hash 的经典坑：源 IP 哈希在后端增减时几乎全量迁移，一致性哈希才平滑。）

### 11.7 百万长连接网关架构（IM 场景）【进阶】
经典设计（微信/钉钉类 IM 的接入层）：
1. **接入层（Connection Gateway）**：无状态集群，每台用 epoll 支撑 **10万~百万级** WebSocket/TCP 长连接，**连接只在本机，业务状态外置**。
2. **会话路由**：Redis 记录"userId → 网关节点"，消息投递先查路由再转发到对应网关（或经消息总线）。
3. **水平扩展**：新网关上线自动注册（服务发现），客户端重连路由到新节点。
4. **心跳与踢人**：30s 心跳，超时判离线；同账号新登录踢旧连接（连接管理）。
5. **消息可靠性**：客户端 ack + 服务端消息序号 + 离线消息存 MQ/DB。
6. **瓶颈点**：单机 fd 上限（调 ulimit）、每连接内存（压缩到 2~4KB）、CPU 软中断（多队列+RSS）、GC 停顿（Netty 用堆外内存/池化）。

> 加分点：IM 架构的**核心原则是"连接与状态分离"**——连接是"瞬态资源"（哪台网关都能收），状态是"持久资产"（必须落 Redis/DB），这样网关可以随意扩缩容而不丢会话。面试常追问"网关挂了连接断了怎么办"——答案就是：客户端重连 → 新网关 → 路由表查 userId → 状态从 Redis 恢复，用户无感知。这就是"**连接可丢、状态不丢**"的设计哲学。
