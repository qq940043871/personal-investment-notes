# 竞价页面突然变慢 — 全链路分层排查实录

> **文档定位**：典型故障排查实录（基于真实架构的代表性场景），回答"页面突然变慢这类问题怎么定位"。核心方法：**自上而下逐层定界，用数据把瓶颈收敛到一层**。讲排障方法论 + 治乱能力。

---

## 1. 问题描述

### 1.1 竞价页面的数据链路（排查的地图）

```
浏览器（Vue3，2 秒轮询）                          ┌──────────────┐
   │  HTTPS                                    │ Kafka        │
   ▼                                           │（出价事件、  │
midservice 网关 × N（鉴权/租户路由/限流）         │ 状态变更）   │
   │  Hessian over HTTP                        └──────┬───────┘
   ▼                                                  │
自由竞价服务 ────────────┬──────────────┬────────────┤
   │                     │              │            ▼
   │ ①行情/挂牌列表       │ ②最新出价    │ ③标的详情   下游消费（仓储/财务/风控）
   ▼                     ▼              ▼
独立缓存服务（封装 Redis） DS 数据中心    MySQL 双实例
   ▲（Canal 监听 binlog    │（防腐层）    （读写分离）
     同步高频读数据）       ▼
                        C 撮合引擎（单线程内存撮合）
```

- 竞价页面高频读两类数据：**行情/挂牌列表**（走 Canal→Redis 缓存加速）、**最新出价/成交**（走 DS→C 撮合引擎）；标的详情等走 MySQL。
- 出价写入：竞价服务落库 + outbox 发 Kafka，撮合指令经 DS 下发 C 引擎。

### 1.2 故障现象

| 维度 | 描述 |
|------|------|
| **故障表现** | 竞价专场（密集出价、多轮次）开市 15 分钟后，页面卡顿、报价确认慢、倒计时刷新延迟 |
| **监控特征** | 竞价查询接口 P99 从 150ms 升到 3.2s、P99.9 8s；**成功率仍 100%——慢而不报错** |
| **影响范围** | 全部租户、全部地域/运营商（排除线路问题，见 08 号文档对照结论） |
| **触发条件** | 与开市时间强相关：开市前页面完全正常 |
| **复现率** | 开市时段必现，闭市后自行缓解 |

### 1.3 关键差异条件

| 对比维度 | 开市前 | 开市后（密集出价期） |
|----------|:-----:|:------------------:|
| 竞价查询接口 P99 | 150ms | 3.2s |
| 出价写入接口 | 正常 | 偶发超时重试（事务链路排队） |
| 静态资源 / 登录 / 其他页面 | 正常 | 正常 |
| C 撮合引擎 TPS / 队列深度 | 正常 | **正常** |

### 1.4 已排除的假设

| 假设 | 根因方向 | 排除依据 |
|------|---------|---------|
| 网络/线路问题 | 接入层 | 全地域全运营商一致变慢，08 号文档四步定位法对照正常 |
| 流量突增 / 攻击 | 入口层 | 网关 QPS 与昨日同时段持平，限流未触发 |
| C 撮合引擎变慢 | 撮合链路 | 撮合 TPS、积压队列深度、P99 全部正常，DS 心跳正常 |
| Full GC / JVM 内存问题 | 服务运行时 | GC 日志正常，老年代占用平稳，无 Full GC |
| 发布/变更导致 | 版本 | 故障窗口无发布记录 |
| Kafka 积压 | 异步链路 | 消费组 lag 正常，出价事件落库正常 |

## 2. 排查过程：自上而下逐层定界

> 性能问题排查的第一原则：**不要猜，先把耗时拆到每一层，瓶颈收敛到唯一一层之后再深挖。**

### 2.1 第一层：前端定界 — 慢在接口还是静态资源

浏览器 DevTools Network 看 waterfall：

- 静态资源（JS/CSS/图片）：5ms 级，正常；
- 轮询接口 `/api/bid/list`、`/api/bid/quote`：单个耗时 3s+，排队串行放大成页面卡顿；
- 多客户同时反馈、换浏览器无效 → **服务端问题**。

### 2.2 第二层：网关层 — 用 traceId 把总耗时拆开

midmon 按 traceId 拆解一次典型慢请求：

```
traceId=7f3a9c…  total=3210ms
  ├─ midservice 网关（鉴权 + 租户路由 + 限流）        20ms   ✅
  ├─ 自由竞价服务 doQuery                          3180ms   ← 时间都花在这
  │    ├─ Redis 缓存 GET（未命中，miss）             12ms   ⚠️ 命中率崩了
  │    ├─ MySQL SELECT t_listing …                2950ms   ❌ 瓶颈在这
  │    └─ DS → C 最新出价查询                       45ms   ✅
  └─ 响应序列化                                      13ms   ✅
```

网关自身 CPU/线程池正常、QPS 平稳 → 入口层清白，瓶颈在竞价服务及其下游。

### 2.3 第三层：竞价服务 — 两个关键排除

- **排除 GC**：GC 日志正常、无 Full GC（如果这里看到 Full GC 频繁，转 10 号文档的 JVM 排查路径）；
- **排除撮合链路**：Hessian 调 DS→C 的耗时 45ms 正常，撮合引擎 TPS/队列深度平稳——**竞价"慢"不是撮合"慢"**，是查询"慢"。这两条排除是本案的关键分叉点。

观测到：服务工作线程池打满、DB 连接池等待 200+——线程都在等数据库。

### 2.4 第四层：缓存层 — 命中率崩塌

| 指标 | 平时 | 故障时 | 判读 |
|------|------|--------|------|
| Redis 命中率 | 98% | **31%** | 大量请求绕过缓存回源 |
| 热点 key（挂牌列表/行情） | TTL 内常驻 | 大批过期未重建 | 缓存更新流中断 |
| Canal 消费位点 | 实时 | **停滞 22 分钟** | binlog 没有被消费 |

### 2.5 第五层：MySQL — 回源打爆主库

```sql
SHOW FULL PROCESSLIST;          -- 大量 t_listing / t_quote 查询排队
SELECT * FROM information_schema.innodb_trx\G   -- 长事务/锁等待排查
-- 慢查询日志 Top：挂牌/行情列表查询（原本走缓存，回源后大范围扫描）
```

主库 CPU 97%、慢查询堆积；从库反而很闲（业务把列表读也配在了主库强一致读上）。

**收敛**：缓存失效 → 流量回源 → 主库打满 → 查询变慢 → 页面变慢。往下追"缓存为什么失效"。

### 2.6 根因追查：Canal 为什么停滞

- Canal 日志：`parse binlog event failed` 后消费线程退出，**无自动恢复、无告警**；
- 追溯 binlog：开市前 30 分钟，运营对竞价标的表执行了一次 **DDL（加字段）**，且未走变更流程、未通知下游；
- Canal 版本对该 DDL 事件解析异常退出，位点停在 DDL 之前 → 缓存更新流中断；
- 同时热点 key 陆续 TTL 过期，过期后**未命中直接回源、无并发保护**（缓存击穿），请求量叠加开市峰值 → 主库 CPU 97%。

## 3. 根本原因总结

### 3.1 直接根因

> **Canal 消费 binlog 在一次未走流程的 DDL 后解析失败中断（位点停滞 22 分钟、无告警），缓存更新流断掉；热点 key 过期后未重建，大量请求击穿缓存回源 MySQL，主库 CPU 打满、慢查询排队，竞价服务等 DB 连接池导致接口 P99 从 150ms 涨到 3.2s，页面变慢。**

### 3.2 深层根因

1. **缓存架构单点**：高频读数据的更新完全依赖 Canal 单链路，中断即"静默失效"，没有对账兜底；
2. **变更管理失控**：DDL 未走变更流程、未避开交易时段、未通知下游；
3. **可观测性缺口**：只有 Redis 服务存活告警，没有"Canal 位点停滞/消费延迟"告警和"缓存命中率水位"告警——故障发现靠客户体感。

### 3.3 根因因果链

```
开市前运营执行 DDL（未走变更流程）
  → Canal 解析该 binlog 事件失败，消费线程退出（无自动恢复）
    → 缓存更新流中断，热点 key 过期后未重建（缓存击穿）
      → 流量回源 MySQL，叠加开市峰值
        → 主库 CPU 97%、慢查询排队、连接池耗尽
          → 竞价查询接口 P99 150ms → 3.2s
            → 页面卡顿、报价确认慢（客户投诉）
```

## 4. 处置经过与改进措施

### 4.1 应急处置（30 分钟内恢复）

| 序号 | 措施 | 说明 |
|:---:|------|------|
| S-1 | 重启 Canal 并校正消费位点 | 恢复缓存更新流 |
| S-2 | 执行热点缓存预热脚本 | 挂牌列表/行情 key 主动重建，命中率 5 分钟内回到 95% |
| S-3 | 网关对非核心查询降级限流 | 历史成交、导出类接口返回兜底数据/排队 |
| S-4 | 列表查询临时切读从库 | 释放主库压力（确认这类读可容忍秒级延迟） |
| S-5 | 观察 30 分钟后解除降级 | P99 回到 150ms，主库 CPU 回落 40% |

### 4.2 中期技术改进（1-2 周）

| 序号 | 措施 | 优先级 | 说明 |
|:---:|------|:-----:|------|
| M-1 | **Canal 消费监控告警**：位点停滞 > 1 分钟 / 消费延迟 > 30 秒即告警 | **P0** | 补上"静默失效"的观测盲区 |
| M-2 | **缓存命中率水位告警**：核心业务 key 命中率 < 90% 告警 | **P0** | 击穿发生时秒级感知 |
| M-3 | 热点 key 二级缓存：本地缓存（Caffeine，30s）+ Redis，回源加 singleflight/信号量并发保护 | P1 | 即使 Redis/Canal 全挂，本地缓存扛 30s |
| M-4 | 读路径梳理：明确"哪些读必须主库、哪些读从库"，列表类读全部走从库 | P1 | 慢查询与强一致读范围治理 |
| M-5 | Canal 异常自动拉起 + 位点校验脚本 | P1 | 解析失败可恢复，而不是停在原地 |

### 4.3 长期预防（流程与规范）

| 序号 | 措施 | 层面 | 说明 |
|:---:|------|------|------|
| L-1 | **变更流程红线**：DDL 必须走流程、避开交易时段（开市/竞价专场）、提前通知下游消费方 | 流程 | 本次故障的第一因 |
| L-2 | 缓存对账兜底：定时任务（XXL-Job）全量校验缓存与 DB 一致性，发现偏差自动重建 | 架构 | Canal 挂了也能在分钟级自愈 |
| L-3 | 开市前预案：专场开市前跑缓存预热 + 关键指标巡检 checklist | 运维 | 把"开市"当大促对待 |
| L-4 | 全链路压测 + 缓存击穿演练 | 测试 | 验证二级缓存与限流降级真实有效 |
| L-5 | "慢而不报错"类故障纳入 SLO：分段耗时（网关/服务/缓存/DB）进看板 | 可观测 | 成功率 100% 不等于没故障 |

### 4.4 改进优先级路线图

```
当天              1 周内               2 周内              持续
┌──────────┐   ┌───────────────┐   ┌───────────────┐   ┌──────────┐
│ 恢复 Canal│ → │ M-1 Canal 告警│ → │ M-3 二级缓存  │ → │ L-1~L-5  │
│ 预热+降级 │   │ M-2 命中率告警│   │ M-4 读路径治理│   │ 流程/演练 │
```

## 5. 附录

### 5.1 性能问题分层排查清单（可复用）

| 层 | 看什么 | 工具 | 本案观测 |
|----|--------|------|---------|
| 前端 | 静态资源 vs XHR 耗时、是否串行 | DevTools waterfall | XHR 3s+，静态正常 |
| 网关 | QPS、线程池、限流触发、网关自身耗时 | midmon 看板 | 网关 20ms，平稳 |
| 业务服务 | 线程池、连接池等待、GC 日志、下游调用耗时 | traceId 拆解、jstack | 等 DB 连接 200+，GC 正常 |
| 撮合链路 | DS 心跳、C 引擎 TPS/队列深度 | midmon 撮合看板 | 正常 → 排除 |
| 缓存 | 命中率、Canal 位点/延迟、热点 key TTL | 缓存服务监控 | 命中率 98%→31%，位点停滞 |
| DB | CPU、慢查询、连接数、锁等待、主从延迟 | PROCESSLIST / slow log | 主库 CPU 97% |
| 异步 | Kafka 消费组 lag | Kafka 监控 | 正常 → 排除 |

### 5.2 分段计时与链路拆解示例

```bash
# 前端侧把"网络"和"服务端"分开：tcp 正常而 ttfb 大 = 服务端慢
curl -o /dev/null -s -w 'tcp=%{time_connect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  https://trade.example.com/api/bid/list
```

midmon 链路拆解见 2.2 节 traceId 示例——**排性能问题必须拿到一条完整 trace，而不是只看总耗时**。

### 5.3 术语说明

| 术语 | 说明 |
|------|------|
| 缓存击穿 | 热点 key 过期瞬间大量请求直接打到 DB |
| Canal | 阿里开源的 MySQL binlog 增量订阅/消费组件，本架构用于同步数据到 Redis 缓存服务 |
| 消费位点 | Canal 消费 binlog 的进度坐标，停滞 = 更新流中断 |
| P99 / P99.9 | 99% / 99.9% 的请求耗时上限，比平均值更能反映用户体感 |
| singleflight | 相同 key 的并发回源合并为一次查询，防止击穿 |
| 强一致读 | 必须读主库的场景（写后读、资金类），范围要明确收敛 |

### 5.4 面试速答（90 秒版）

> "竞价专场开市 15 分钟后客户反馈页面变慢，成功率还是 100%，典型的'慢而不报错'。我按**自上而下逐层定界**：先用 traceId 把一次慢请求拆开——网关 20ms、撮合链路 45ms、Redis 未命中、MySQL 查询 2950ms，瓶颈收敛到 DB。同时排除了 GC 和撮合引擎两个关键嫌疑：GC 日志正常，C 引擎 TPS 和队列深度平稳，所以'竞价慢'其实是'查询慢'。再往上看缓存层：命中率从 98% 崩到 31%，Canal 消费位点停滞 22 分钟——开市前有人对标的表加字段走了 DDL，没走变更流程，Canal 解析失败线程退出、无告警。缓存更新流一断，热点 key 过期后击穿回源，开市峰值叠加，主库 CPU 97%，接口 P99 从 150ms 涨到 3.2s。应急是重启 Canal 校正位点 + 热点缓存预热 + 非核心查询降级，30 分钟恢复。治本三件事：Canal 位点停滞和缓存命中率告警、热点 key 二级缓存加回源并发保护、DDL 变更红线——交易时段冻结变更、通知下游。"

**追问预案**：

| 追问 | 回答要点 |
|------|---------|
| 怎么确定不是撮合引擎慢？ | traceId 拆解里 DS→C 只占 45ms，撮合 TPS/队列深度全程平稳；竞价页面的"慢"在查询路径不在撮合路径 |
| 怎么排除 JVM 问题？ | GC 日志无 Full GC、老年代平稳；如果 GC 异常会看到线程等 GC，走 10 号文档的 JVM 路径 |
| Canal 挂了为什么是"变慢"而不是"数据错"？ | Canal 只负责缓存更新，过期后回源 DB 数据仍正确，只是慢；如果同步的是搜索/索引数据才会表现为"数据错" |
| 缓存整体失效怎么扛？ | 三级防线：本地缓存 30s 逃生 + 回源 singleflight/限流保护 DB + 从库分流；再加定时对账兜底自愈 |
| 为什么不重启 MySQL？ | 根因在缓存更新流中断，重启 DB 只是把打满的 CPU 清零，几分钟内会被回源流量再次打爆，先断根因 |
