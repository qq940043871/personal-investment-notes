# 网关横向扩容打穿数据库 — 高并发性能开发规范

> **文档定位**：一问一文——"中间件网关横向扩容后，流量直接把后端数据库打死了，怎么处理？"由真实场景沉淀出可复用的**性能开发规范**：五层防线（限流 / 隔离 / 削峰 / 缓存 / DB 保护）+ 精到数值的配置基线（限流多少、线程池多少、连接池多少、缓存策略）+ 上线红线 checklist。讲**治乱能力**：扩容是放大器，出口容量不变时必须先加闸门。

---

## 1. 场景还原

### 1.1 故障链路（排查的地图）

```
客户端（峰值 2500 并发会话）
   │
   ▼
中间件网关（midservice）横向 ×5          ← 扩容后并发"跟得上"了
   │  鉴权 / 租户路由 / 转发
   ▼
后端服务（同步处理，直连 DB）             ← 慢接口拖住网关工作线程
   │  无隔离 / 无队列 / 无缓存
   ▼
MySQL（连接被瞬间占满，慢查询排队）        ← 出口是单通道，被打死
```

### 1.2 故障演进

| 阶段 | 现象 | 说明 |
|------|------|------|
| 扩容前 | 网关某些接口慢，整体并发数跟不上 | 慢接口占用网关工作线程，队头阻塞拖垮整机吞吐 |
| 扩容后 | 网关横向扩到 5 个，可支撑 2500 并发 | 入口容量 ×5，**流量放大器就位** |
| 扩容后几分钟 | 后端 DB 被直接拖死，全站不可用 | 流量全部打穿到后端直连 DB，出口容量没变 |

### 1.3 本质：瓶颈后移

```
网关能横向扩展 = 入口无限放大
后端直连 DB   = 出口是单通道
                → 中间没有任何闸门，放大器直接把 DB 炸掉
```

**核心结论一句话**：扩容解决的是"入口并发跟不上"，制造的是"出口流量放大"。必须在 **网关 → 后端 → DB** 之间加"限流、排队、缓存、隔离"，让扩容后的流量安全落地。

---

## 2. 容量模型：数值从哪来（Little's Law）

> 所有限流值、线程池、连接池都不是拍脑袋，用两个公式反推：

```
① 利特尔法则：在途并发 = QPS × RT
② DB 吞吐上限：安全 QPS ≈ 连接数 ÷ SQL 平均 RT × 利用率(0.7)
```

**参考基线（示例数字，实际以全链路压测为准）**：

| 模型输入 | 参考值 | 说明 |
|---------|--------|------|
| 网关实例数 | 5 | 横向扩容后 |
| 慢接口 RT（DB 直连） | ≈ 300ms | 重查询拖到 500ms~1s |
| DB 连接预算 | 100 | 5 实例 × 20 连接（见 4.4） |
| DB 安全吞吐 | 100 ÷ 0.3 × 0.7 ≈ **230 QPS** | 再取整留余量 → 放行 200 QPS |

**推导链条**（这就是"精确到数值"的算法）：

1. 未限流时：2500 并发会话哪怕只有 10% 同时在途慢请求 = 250 在途 → 需要 250 个 DB 连接 → 连接池瞬间耗尽 → 线程全部阻塞在等连接 → 网关工作线程跟着占满（这就是"并发数跟不上"的真身）；
2. DB 出口容量是硬约束：200 QPS 放行（= 230 × 0.6 水位）；
3. 全局限流 200 QPS ÷ 5 实例 = 40 QPS/实例；
4. 在途并发 = 40 × 0.3s = 12/实例 → 慢接口独立线程池 core 15 / max 30 / queue 100；
5. 连接池 20/实例（合计 100）＜ max_connections 200（含运维余量 100）；
6. 缓存命中率 ≥ 90% 后，实际回源 ≤ 20 QPS → DB 真实负载极低，余量留给突发。

## 3. 五层防线总览

```
第一层 网关    限流 / 熔断 / 降级          —— 不让超过 DB 承受能力的流量进来
   ↓
第二层 后端    线程池隔离 / 队列削峰 / SQL 红线 —— 慢接口不拖垮快接口，消费速度可控
   ↓
第三层 缓存    本地 + Redis 多级缓存       —— 90% 请求不进 DB
   ↓
第四层 DB      连接数限制 / 慢查询治理 / 读写分离 —— 只承受安全流量
   ↓
第五层 架构    网关扩容多少倍，DB 都不崩     —— 规范与流程兜底
```

---

## 4. 第一层：入口控制（网关层，最优先最有效）

### 4.1 全局限流

| 限流维度 | 建议值 | 推导 |
|---------|--------|------|
| 按接口（慢接口） | **200 QPS** | DB 上限 230 × 60% 水位 |
| 按应用（后端服务总并发） | 200~300 并发 | 在途 = 200 × 0.3s = 60，再留突发余量 |
| 单实例分摊 | 40 QPS | 全局 ÷ 5 实例（集中式令牌桶或分片令牌桶） |

超过阈值直接返回"系统繁忙，请稍后重试"（HTTP 429 + 兜底文案），**目的只有一个：不让超过 DB 承受能力的流量进入后端**。

### 4.2 熔断降级

| 参数 | 建议值 |
|------|--------|
| 慢调用判据 | RT > 500ms |
| 熔断触发 | 慢调用比例 ≥ 50% 或异常比例 ≥ 50%（滑动窗口 10s / 20 请求） |
| 熔断时长 | 5s，半开探针放 3 个请求试探 |
| 降级行为 | 直接返回降级页/兜底数据，不放流量过去 |

**目的**：防止一个慢接口拖死整个后端线程池 → 进而拖死 DB。

### 4.3 超时分层（必须逐层递减）

```
网关 1000ms ＞ 后端入口 800ms ＞ 服务内 DB 调用 500ms ＞ JDBC socket 400ms
```

**红线**：下游超时必须小于上游。反过来配 = 上游已放弃、下游还在耗资源，超时重试会把故障放大成流量风暴。

### 4.4 服务熔断、降级与排队

- 慢接口超过容量：排队（队列 100，≈2.5s 容忍）→ 超时拒绝；
- 快接口（纯缓存/内存路径）用**信号量隔离**（50）而不是线程池，避免无谓线程切换。

---

## 5. 第二层：后端应用层（最关键）

### 5.1 绝对禁止"同步直连 DB 无隔离"，必须加线程池/队列

**方案 A：线程池隔离（Bulkhead，最简单有效）**——慢接口单独建池：

| 参数 | 慢接口独立池 | 推导 |
|------|------------|------|
| 核心线程 | 15 | 稳态在途 12（40 QPS × 0.3s） |
| 最大线程 | 30 | 突发 2 倍余量 |
| 队列 | 100 | ≈2.5s 排队容量，超时 1s 拒绝 |

超过直接拒绝，**不占用通用线程池**——慢接口再慢，不影响其他正常接口。

**方案 B：异步化 + 内存队列削峰（高并发写入必用）**：

1. 请求进来丢内存队列（`LinkedBlockingQueue`）；
2. 后台线程池以受控速度消费；
3. **消费速度 = DB 安全阈值**（如 200 QPS 恒速消费）。

流量再大也只是排队，打不崩 DB。查询类接口不能异步化（同步语义），用方案 A + 缓存解决。

### 5.2 接口 SQL 红线（慢接口 90% 是这四件事）

| 禁止 | 强制 |
|------|------|
| `select *` | 只查需要的列 |
| 一次查 10000 条 | **单次查询最多 100~200 条**，分页必须带 `limit` |
| 大事务、长 SQL | 长事务拆短（> 5s / > 1000 行即大事务） |
| 全表扫描 | 必须走索引，慢 SQL 上线前过审核 |

### 5.3 连接池严格卡死（非常重要）

Druid / HikariCP 基线：

| 参数 | 建议值 | 说明 |
|------|--------|------|
| 最大连接数 | **20/实例（绝对不能大）** | 5 实例 × 20 = 100，DB 安全 |
| 最小空闲 | 5 | |
| 连接超时 | 1s | 拿不到连接快速失败，别排队到天荒地老 |
| 慢 SQL 监控 | 开启 | 阈值 1s |

反面教材：不限制时 5 实例 × 200 连接 = 1000 连接，直接打挂 MySQL——**连接数多 ≠ 吞吐高**，DB 的 CPU/IO 是硬上限，连接多了只是上下文切换更慢、排队更长。

---

## 6. 第三层：DB 前必须加缓存（扛量核心）

**原则：凡能缓存的，绝不让请求走到 DB。**

| 层 | 组件 | 参数 |
|----|------|------|
| L1 本地缓存 | Caffeine / Guava | 热点 key TTL 30s，maximumSize 10000 |
| L2 分布式缓存 | Redis | 通用 TTL 5~30min |
| 预热 | 缓存预热脚本 | 高峰期（开市/大促）前主动加载 |

三类问题的防线：

| 问题 | 防线 |
|------|------|
| 穿透 | 空值缓存 60s / 布隆过滤器 |
| 击穿 | singleflight（同 key 并发回源合并为一次）/ 逻辑过期 / 分布式锁 |
| 雪崩 | TTL 加 ±10% 随机抖动 + 多级缓存 + 熔断兜底 |

**目标：90% 请求在缓存返回，完全不进 DB。**

---

## 7. 第四层：数据库本身保护

| 措施 | 建议值 |
|------|--------|
| `max_connections` | = Σ连接池 + 运维余量 = 5×20 + 100 = **200**（严禁默认无限） |
| 慢查询 kill | > 1s 自动 kill（pt-kill） |
| 长事务 | > 5s 告警 + kill，禁止大事务 |
| 读写分离 | 读（列表/报表）走从库，写与写后读走主库 |

读写分离是最终兜底：网关扩容再多读流量，也打不垮主库。

---

## 8. 第五层：架构最终形态与规范红线

### 8.1 目标形态

```
网关（限流 200 QPS / 熔断 / 降级）
   ↓
后端服务（慢接口独立线程池 15/30/100 + 写入队列削峰）
   ↓
Redis 多级缓存（命中率 ≥ 90%，挡掉 90% 流量）
   ↓
DB（连接池 100、max_connections 200，只承受安全流量）

→ 网关扩容多少倍，DB 都不会崩。
```

### 8.2 上线红线 checklist（性能开发规范）

1. **容量申报**：新接口上线前申报 QPS 预估、RT 预算、SQL 条数预算，压测过再上；
2. **SQL 红线**：禁止 `select *`、分页必须 `limit`（≤ 200 条）、禁止大事务（> 5s / > 1000 行）、慢 SQL 过审核；
3. **隔离红线**：预计 RT > 200ms 的接口必须独立线程池 + 独立限流，禁止与快接口共池；
4. **连接配额**：单实例连接池 ≤ 30，总量变更需评审；
5. **缓存红线**：读接口 QPS > 100 必须有缓存层，命中率进看板；
6. **超时红线**：调用链超时逐层递减，禁止下游比上游长；
7. **扩容红线**：任何横向扩容前先核 DB 出口容量（新增实例 × 连接池 ≤ max_connections 配额；放行 QPS ≤ DB 上限 × 60%），写进扩容 SOP；
8. **可观测**：限流触发数、线程池水位、连接池等待数、缓存命中率、慢 SQL 条数进看板并告警。

### 10.2 术语说明

| 术语 | 说明 |
|------|------|
| 利特尔法则 | 在途并发 = QPS × RT，容量规划的基础公式 |
| 瓶颈后移 | 前端扩容后压力转移到下游，故障点跟着搬家 |
| 舱壁隔离（Bulkhead） | 慢接口独立线程池，仿船舱水密隔板，一舱进水不沉船 |
| 信号量隔离 | 限制并发数但不限线程，适合快速接口 |
| singleflight | 相同 key 并发回源合并为一次查询，防缓存击穿 |
| 逻辑过期 | 缓存值带过期标记但不删 key，异步重建，防击穿 |
| 半开探针 | 熔断恢复期放少量请求试探下游是否恢复 |
| 出口容量 | 下游（DB）安全吞吐 QPS，扩容前必须核对的硬约束 |

### 10.3 面试速答（90 秒版）

> "我们中间件网关某些接口慢，整体并发上不去，横向扩到 5 个实例后能扛 2500 并发——结果几分钟后后端数据库被打死了。这是典型的**瓶颈后移**：网关扩容是流量放大器，后端直连 DB 是单通道出口，中间没有任何闸门。我用利特尔法则算了账：2500 并发哪怕 10% 同时在途慢请求就是 250 个 DB 连接需求，远超连接池，连接耗尽线程阻塞、网关线程跟着占满。治理分四层：**入口**网关给慢接口限流 200 QPS——这个数是反推的，DB 100 连接、SQL 300ms，安全吞吐 230 QPS，取 60% 水位；**应用层**慢接口独立线程池 15/30/100 舱壁隔离，写入走内存队列恒速削峰；**缓存**本地 30s + Redis，命中率做到 90%；**DB** 连接池每实例卡 20、max_connections 200、慢查询 1 秒 kill、列表读走从库。当晚四步急救：限流、独立线程池、卡连接池、热点缓存，DB 立刻恢复。再往后固化成规范：新接口容量申报、SQL 红线、扩容前先核出口容量——网关再怎么扩，DB 都是安全的。"

**追问预案**：

| 追问 | 回答要点 |
|------|---------|
| 为什么网关扩容反而把 DB 打死？ | 瓶颈后移：入口容量 ×5，出口容量不变，中间无闸门；扩容是放大器不是解药，先加限流再扩容 |
| 限流 200 QPS 是怎么定的？ | 反推法：DB 安全吞吐 = 连接数 ÷ SQL RT × 利用率 = 100 ÷ 0.3 × 0.7 ≈ 230，取 60% 水位；上线后按压测和命中率逐步校准 |
| 为什么不直接把连接池调大？ | 连接数多 ≠ 吞吐高：DB CPU/IO 是硬上限，连接多了只是排队更长、上下文切换更慢，反而更慢 |
| 线程池隔离和信号量隔离怎么选？ | 慢接口/独立下游用线程池隔离（Bulkhead）；快接口、纯缓存路径或不能切线程的调用用信号量隔离 |
| 缓存击穿/雪崩怎么防？ | 击穿 singleflight/逻辑过期/分布式锁；雪崩 TTL 加随机抖动 + 多级缓存；穿透空值缓存/布隆过滤器 |
| 怎么保证下次扩容不再出事？ | 扩容 SOP 红线：扩容前先核出口容量（新增实例 × 连接池 ≤ max_connections 配额、放行 QPS ≤ DB 上限 60%），全链路压测常态化 |
| 查询接口能异步化削峰吗？ | 不能，查询是同步语义；查询类靠"隔离 + 限流 + 缓存"，异步削峰只适用写入/通知类 |
