# B2B 现货交易供应链 - 难点与解决方案手册（速查 + 深挖）

> **范围**：聚焦"现货交易"全链路（区别于期货/远期），从商流、物流、资金流、信息流**四流**视角拆解。
> **形式**：第一部分痛点→方案→真实模块→话术一一对应，速查表为主；第二部分每个难点给出业务场景 / 技术难点 / 面试讲法 / 深挖问题预案。

## 0.1 一句话总览（电梯版）

> **B2B 现货交易供应链的本质难点是「让陌生对手方在「金额大、频次低、履约长、价格波动剧烈」的条件下完成可信交易」**——平台用「四流合一 + 履约保证 + 信用体系 + 生态对接」系统性解决信任问题，用「异构架构 + 规则配置 + 数据中台」解决扩展性问题。

面试开场可直接用这一句。后面任何展开都围绕"信任"和"扩展"两个根因。

# 第一部分：现场速查

## 1. 现货 vs 期货 / 远期：先讲清定位

| 维度 | 现货 | 期货 | 远期 |
|------|------|------|------|
| **交割** | 即时/短期（T+0~T+7）实物交割 | 标准化合约，到期交割 | 定制化合约，到期交割 |
| **价格** | 当下市场价（一单一价） | 期货所公开竞价 | 双方议价 |
| **核心痛点** | **实物交付**（货权/物流/质检）+ 信任 | **价格风险**（保证金/对冲/结算） | 履约信用（违约无保证金兜底） |
| **金融属性** | 弱 | 强 | 中 |
| **平台核心能力** | 仓储+物流+仓单+质检 | 撮合+清算+风控 | 合同+履约跟踪 |
| **典型平台** | 找钢网、欧冶云商、你的现货平台 | 大商所、郑商所、文华财经 | 银行间 OTC |

> **⚠️ 易混淆点（必须讲清）**：现货的**交割**是即时的（T+0~T+7 实物交割），但**结算账期**可以是 30-90 天。这两件事不矛盾——货交得快、钱收得慢，正是「账期长、回款慢」痛点（`05 痛点 17`）的来源。期货则是"交割也在未来，但有保证金 + 每日盯市兜住风险"。

> **面试金句**：「现货的核心是「货」，期货的核心是「钱」——所以现货平台的难点是物理世界的复杂，期货平台的难点是金融世界的复杂。**两个系统的设计哲学完全不同**：现货系统是「商流+物流+资金流+信息流」**四流合一**，期货系统是「风控+清算+对冲」三件套。」

## 2. 现货供应链全链路：四流视角

```
                  ┌────────────────┐
                  │   需求/供给     │  ← 起点：买家/卖家入场
                  └────────┬───────┘
                           │
            ┌──────────────┴──────────────┐
            ▼              ▼              ▼
       ┌─────────┐    ┌─────────┐    ┌─────────┐
       │ 信息流  │    │ 商流    │    │ 物流    │  ← 三流并行
       │ 行情/资讯│    │ 询价/签约│    │ 仓储/运输│
       └────┬────┘    └────┬────┘    └────┬────┘
            │              │              │
            └──────────────┼──────────────┘
                           ▼
                    ┌─────────────┐
                    │   资金流     │  ← 结算/融资/对账
                    └──────┬──────┘
                           ▼
                  ┌────────────────┐
                  │   交收/履约     │  ← 终点：货权转移
                  └────────────────┘
```

**四流合一的价值**：
- **商流**：合同/订单/发票（权属凭证）
- **物流**：仓单/运单/签收（实物凭证）
- **资金流**：付款/收款/融资（资金凭证）
- **信息流**：行情/数据/审计（合规凭证）

> **核心洞察**：四流割裂是传统贸易所有痛点的根因。平台的核心价值 = **让四流在同一个系统里闭环**，所以"票货一致""四流可追溯"成为税务合规/反洗钱/审计的硬性要求。

> **合约、仓单、发票、对账单都可以电子化（电子签章 + 电子凭证效力），但资金不能电子化**——这是现货平台与纯信息平台最本质的区别。

## 4. 五大架构决策（决策结论 + 话术 ⭐ 面试高频）

> 面试中常被问"为什么这么设计"，不是问"怎么实现"。本节只保留**决策结论与话术**。
> **完整技术展开**：决策 1/2 见 `05 痛点 4/5` 及本文件第二部分第 14 节（难点六）；决策 3 见 `05 能力 2` 及第二部分第 9 / 13 节（难点一 / 难点五）；决策 4 见 `05 能力 3` 及第二部分第 12 节（难点四）；决策 5 见 `05 能力 4` 及第二部分第 11 节（难点三）；分布式事务框架见 `01-架构方法论与选型设计手册.md` 第 2.8 节。

### 决策 1：为什么 C + Java 异构架构（而不是统一 Java）

**结论**：业务倒逼分层——撮合要微秒级用 C 单线程内存撮合，业务要灵活用 Java 微服务，**DS 数据中心做防腐层**（C 只暴露二进制协议，DS 翻译为 Hessian，Java 侧无感）。

**话术**：
> 「**业务的自然分层倒逼了技术的分层**。我们不是「为了异构而异构」——C 引擎是性能极致，Java 中台是业务灵活，DS 是我能 review 的治理抓手。**这正是技术经理的价值：管住 DS 就管住了整个异构链路的稳定性**。」

### 决策 2：为什么异步落库（而不是同步等 MySQL ACK）

**结论**：撮合的核心职责是成交不是存储——内存订单簿（微秒级）→ 后台线程池写 MySQL → 失败写 WAL 回放；代价"内存有但库无"用「内存为准 + 异步回放 + 幂等补偿 + 定时对账」兜底。

**话术**：
> 「如果撮合完要等 MySQL ACK 确认，撮合性能就被数据库写入能力绑死了。**异步落库换来的是撮合吞吐量和确定时延**，代价是引入数据一致性复杂度——这部分我们用「内存为准 + WAL 回放 + 定时对账」来兜底。」

### 决策 3：为什么用 outbox 事务消息而不是 Seata/XA（保证金场景）

**结论**：银行冻结接口耗时 3 秒，全局事务持锁 3 秒会拖垮履约吞吐；MQ 统一 **Kafka**，事务语义由 **outbox 本地消息表 + 消费幂等 + 定时扫表兜底** 实现（不用半消息），再叠加状态机禁止非法跳转。

**话术**：
> 「金融场景下，Seata 的全局锁是「正确但不可用」——3 秒锁持有时间会拖垮履约吞吐。我们的 MQ 统一是 Kafka，事务语义不用半消息，而是用 **outbox 本地消息表 + 消费幂等 + 定时扫表兜底** 落地，再叠加状态机约束：**分布式系统设计的第一原则是「让系统可恢复」而不是「让系统不出错」**。」

### 决策 4：为什么用 Canal + 缓存服务（而不是直接 Redis Cluster）

**结论**：缓存服务不是简单 Redis 封装，而是「行记录 → KV 转换 + 三端推送分发」的中间层——前端只关心 Redis 最终态，不关心数据怎么来，Canal 直推前端会让前端耦合 binlog 格式。

**话术**：
> 「**缓存服务是「数据结构转换 + 推送分发」的中间层**。前端只关心 Redis 里的最终态，不关心数据怎么来。Canal 挂了不影响交易（不影响 C 撮合主流程），缓存服务挂了不影响撮合，只影响行情展示——**降级边界清晰**。」

### 决策 5：为什么用规则配置中心（而不是写死业务逻辑）

**结论**：B2B 业务规则多变（不同品类/客户/模式的保证金比例、审批流、计费规则都不同）；改代码 1 周上线，改配置 1 分钟生效且可回滚，元能力是让业务人员自助驱动业务变化。

**话术**：
> 「**B2B 业务最贵的成本是「每开一个新业务就要改一次代码」**。规则配置中心的本质是「把业务策略从代码中抽出来」——业务人员通过配置就能定义「A 类客户用 X 保证金比例 + Y 审批流」，技术团队不再被业务变更打断。」

## 5. 痛点 → 真实系统模块 映射（架构视角）

把第 3 节的 10 个痛点反向映射到真实异构系统：

```
痛点 1 (货权)  →  仓单服务 + 第三方存证接口
痛点 2 (信任)  →  资金服务 + 银行存管 + 履约状态机
痛点 3 (价格)  →  套保引擎 + CTRM 外部接口
痛点 4 (资金)  →  银行/支付/供应链金融 9+ 外部接口
痛点 5 (质量)  →  质检服务 + 合约模板引擎
痛点 6 (物流)  →  物流追踪 + 仓储服务
痛点 7 (行情)  →  缓存服务 + Canal + 三端推送
痛点 8 (流程)  →  7 大交易模式 + 合同中心 + 规则配置
痛点 9 (税务)  →  发票服务 + 对账引擎
痛点 10 (风控) →  风控引擎 + 履约状态机 + 风控 ODS

通用底座：
- DS 数据中心：所有异构通信（C↔Java、外部接口↔Java）
- midservice 网关：所有客户端请求的统一入口
- midmon 监控：所有服务健康度和链路追踪
- MySQL 双实例：交易/管理/数据中心分离
- MinIO：合同/凭证/质检报告等文件存储
```

> **架构洞察**：9+ 外部接口（银行/物流/CTRM/开票/咨询/企查查/供应链金融/证书/短信）不是"对接外部"，而是**把行业能力外包给生态**——银行做资金、物流做运输、CTRM 做风控数据、企查查做征信。**平台的核心是「连接器 + 编排器」，不是「全功能闭环」**。
> 逐项模块清单见 `05` 第 10 节（22 个核心模块）。

## 6. 面试话术 10 条（按出现频率排序）

### Q1：请用 2 分钟介绍你们平台
> 「我们做的是 B2B 大宗商品现货交易平台，覆盖**能源、煤炭、金属、农产品**等十几个行业，**撮合引擎用 C 写**（单线程内存撮合、毫秒级延迟），**业务中台用 Java 微服务**（12+ 业务服务），**接入层走 midservice 自研网关**，三端覆盖大屏、PC、移动。**关键点是异构系统之间的桥接层——DS 数据中心**——把 C 引擎的二进制协议翻译成 Java 对象，是我作为 Java 技术经理能直接 review 代码的地方，**管住 DS 就管住了整个异构系统的稳定性**。」

### Q2：你们平台解决了什么核心问题？
> 「**一句话：解决「陌生对手方在大宗场景下的可信交易」**。具体是四件事——**让四流合一**（商流/物流/资金流/信息流在系统内闭环）、**让违约有代价**（履约保证+信用体系）、**让价格可对冲**（点价/基差/套保三件套）、**让数据可决策**（行情中心+数据中心反哺）。**根因是信任，所有方案都围绕信任构建**。」

### Q3：现货和期货系统的区别是什么？
> 「**现货的核心是「货」，期货的核心是「钱」**。现货系统的难点是物理世界的复杂——仓单、物流、质检、货权；期货系统的难点是金融世界的复杂——保证金、对冲、结算价。**所以两套系统的设计哲学完全不同**：现货是「商流+物流+资金流+信息流」**四流合一**，期货是「风控+清算+对冲」三件套。
> 补充一点：现货**交割**是即时的，但**结算账期**可以很长——货交得快、钱收得慢，这正是 B2B 的典型特征。」

### Q4：你们最大技术挑战是什么？
> 「**是「让 C 撮合引擎和 Java 业务中台在异构条件下保持一致」**。C 单线程撮合性能极致但只暴露二进制协议，Java 微服务灵活但 GC 不可控。**DS 数据中心做防腐层**——同步走 Hessian over HTTP，异步走 Socket——**让两侧各自演进但保持契约**。**作为技术经理，我管住 DS 就管住了整个链路**。」

### Q5：怎么保证数据一致性？
> 「**分级一致性，不要一刀切**。撮合主链路用 C 内存 + 异步落库，**最终一致**；履约单状态变更用 outbox 事务消息（Kafka），**最终一致**；资金冻结用同步调用 + 幂等 + 补偿，**强一致**。**该强的地方强，该弱的地方弱**——分布式系统设计的第一原则是「让系统可恢复」而不是「让系统不出错」。」

### Q6：怎么防止超卖？
> 「**三道防线**。第一道：C 撮合引擎单线程内存撮合 + CAS 扣减库存，**内存里就挡住了**。第二道：DS 数据中心超时熔断 + 幂等校验，**C 超时不重试**。第三道：Java 业务层 MySQL 用 `resource_id + version` 乐观锁，**数据库兜底**。**三道防线独立演进、互不依赖，任何一道失守都不会全局崩盘**。」

### Q7：你们 9+ 外部接口怎么管理？
> 「**作为连接器和编排器，不是全功能闭环**。银行做资金、物流做运输、CTRM 做风控数据、企查查做征信——**行业能力外包给生态**。**DS 数据中心统一做协议适配**——银行/物流/CTRM 都是异构系统，DS 是「外部异构 + C 引擎异构」的双重防腐层。**新增一个外部接口 = 在 DS 加一个适配器，业务侧无感**。」

### Q8：客户最在意什么？
> 「**信任和效率**。信任层面：货是不是真的？钱会不会丢？违约有没有代价？效率层面：流程是不是能线上化？资金是不是能 T+0 到账？信息是不是实时？**信任是 P0（没有就不来），效率是 P1（有了才留下），增值是 P2（留下才付费）**。」

### Q9：如果重做一次，你会改什么？
> 「**统一主数据中心，而不是用 MQ 同步副本**。我们吃过亏——客户、商品、订单各业务系统都维护自己的副本，靠消息中间件同步，**MQ 挂了数据就不一致**。**正确做法是「1 份权威数据 + N 个系统引用」**——业务系统走 API 查主数据中心，不维护副本。**这是架构范式的转变，从「烟囱式」走向「平台化」**。」

### Q10：你的技术管理价值是什么？
> 「**不在「能写代码解决某个 Bug」**，而在四件事——**能识别根因**（不是头痛医头）、**能给渐进式方案**（不搞大拆大建）、**能复用现有资产**（DS/Canal/midservice 都有定位）、**能管住异构系统**（C 是黑盒但 DS 是我手里的抓手）。**技术经理的价值 = 驾驭复杂度 + 让团队少走弯路**。」

## 7. 常见追问与应对（防被问倒）

| 追问 | 简短回答 |

## 9. 难点一：银行资金存管的资金流一致性

### 业务场景

客户在平台下单 → 平台向银行存管系统发送扣款指令 → 银行执行资金划付 → 平台更新订单状态。**资金在银行侧，交易状态在平台侧，两者必须最终一致，不能出现"钱扣了订单没成"或"订单成了钱没扣"的情况。**

### 技术难点

```
平台交易系统 ──(扣款指令)──→ 银行存管系统
     │                              │
     │ ←──(扣款结果)─────┘
     │
     ├── 成功 → 更新订单为"已支付"
     ├── 失败 → 订单回滚
     └── 超时 → ??? (最棘手的情况)
```

**核心挑战**：

| 问题 | 难点说明 |
|------|---------|
| **网络超时** | 银行接口超时，不知道钱到底扣了没扣，需要主动查询对账 |
| **幂等性** | 重试机制下，同一笔扣款不能执行两次 |
| **状态机一致性** | 订单状态、资金流水、银行回单三方状态必须一致 |
| **T+1 对账** | 银行按日结算，平台实时交易，存在跨日对账差异 |
| **多银行适配** | 每家银行接口协议不同（上海银行/兴业/中原/平安/工行），需要适配层 |

### 面试讲法（建议话术）

> "我们对接了 5 家银行的存管系统，核心难点是**平台交易状态与银行资金状态的最终一致性**。银行接口存在超时、重试、异步回调等不确定性，我们采用了**本地消息表 + 定时补偿 + 银行对账文件核对**的三层保障机制。每笔资金操作先写本地消息表（保证与业务事务同库），异步投递到银行，超时后主动查询银行接口，T+1 再用银行对账文件做全量核对。所有资金操作设计了**幂等键**（订单号+操作类型），确保重试不会重复扣款。"

### 深挖问题预案

| 面试官追问 | 你的回答要点 |
|-----------|-------------|
| "超时了怎么办？" | 主动查询银行接口（queryByReqId），根据查询结果决定继续/回滚 |
| "查询也超时了呢？" | 标记为"不确定状态"，进入人工对账队列，T+1 对账文件兜底 |
| "幂等怎么设计的？" | 幂等键 = 会员ID + 订单号 + 操作类型 + 日期，银行侧也用 reqId 去重 |
| "多银行怎么适配？" | 适配器模式，定义统一的 BankGateway 接口，每家银行一个实现类 |
| "一致性保证了，性能呢？" | 异步化+批量处理，非核心链路异步补偿，TPS 受限于银行接口（通常 50-200 TPS） |

### 与你背景的关联

你在 Agent Harness 中用 FastAPI 做 MainLoop 编排，本质上也是**多步骤状态机的一致性管理**。可以这样桥接：

> "这和我做 Agent Harness 时的任务状态管理很像——每个 Agent 步骤也有超时、重试、补偿的需求，我用了类似的状态机+补偿机制来保证 Agent 任务流的最终一致性。"

## 10. 难点二：区块链 + 物联网 + WMS 三层仓单可信链

### 业务场景

大宗商品仓单融资中，最大的风险是**虚假仓单**——同一批货物开多张仓单、货物根本不存在、货物被偷偷运走。用三层架构解决：

```
┌─────────────────────────────────────────┐
│  区块链层：仓单上链，不可篡改，可溯源       │
│  ← 解决"仓单数据是否可信"                  │
├─────────────────────────────────────────┤
│  WMS 层：入库→质检→注册仓单→在库→出库     │
│  ← 解决"仓单与货物是否对应"                │
├─────────────────────────────────────────┤
│  物联网层：视频监控+温湿度+RFID+出入库管控  │
│  ← 解决"货物是否真实存在"                  │
└─────────────────────────────────────────┘
```

### 技术难点

| 层 | 技术难点 | 说明 |
|----|---------|------|
| **物联网层** | 多源异构数据实时采集 | 视频（RTSP）、温湿度（Modbus/MQTT）、RFID、门禁系统，协议各异，需要统一接入网关 |
| **物联网层** | 边缘计算 vs 云端处理 | 视频流不能全上云（带宽成本），需要在边缘做行为检测（如异常搬货），只上事件 |
| **WMS 层** | 仓单生命周期状态机 | 仓单状态：待注册→已注册→已质押→部分解押→已提货，状态流转需严格防非法跳转 |
| **WMS 层** | 仓单与物理货物映射 | 货物可能分批入库、合并堆放、分批出库，仓单-货物映射是 N:M 关系 |
| **区块链层** | 链上链下数据同步 | 区块链写入有延迟（秒级~分钟级），不能阻塞交易流程，需要异步上链+回执确认 |
| **区块链层** | 仓单拆分与合并 | 融资场景需要仓单拆分（一张拆多张）或合并（多张合一），链上状态变更复杂 |
| **跨层** | 三层数据一致性 | WMS 注册仓单 → 物联网验证货物存在 → 区块链上链，任一环节失败需要跨层回滚 |

### 面试讲法

> "仓单可信链是我认为最有技术含量的一块。难点不在于单独某一层，而在于**三层之间的数据一致性**。物联网层采集到货物入库事件后，WMS 才能注册仓单，仓单注册后才能上链。但物联网数据可能误报（比如摄像头误识别）、WMS 可能操作回滚、区块链上链可能延迟。我们设计了**事件驱动的跨层编排**：每层操作都是幂等的，通过事件溯源（Event Sourcing）记录所有状态变更，上链失败时通过补偿事件回滚 WMS 状态。物联网层用边缘网关做预处理，只把结构化事件（入库/出库/异常）上传，避免视频流直传云端的带宽问题。"

### 深挖问题预案

| 面试官追问 | 你的回答要点 |
|-----------|-------------|
| "区块链上链慢怎么办？" | 异步上链，先返回"上链中"状态，后台轮询确认，交易流程不阻塞 |
| "物联网数据怎么保证可信？" | 多传感器交叉验证（视频+RFID+称重），异常告警人工复核 |
| "仓单拆分怎么实现？" | 原仓单状态置为"已拆分"，生成 N 张子仓单上链，链上记录拆分关系 |
| "三层回滚怎么做？" | Saga 模式，每步有补偿动作：区块链标记无效→WMS 回滚仓单→物联网标记误报 |

## 11. 难点三：七种交易模式的可插拔引擎

> 速查结论与"为什么配置驱动"的决策话术见第一部分第 4 节决策 5。

### 业务场景

支持 7 种交易模式：协议交易、挂牌交易、竞价交易、预售交易、点价交易、提单交易、现货通。每种模式的**交易流程、结算规则、风控规则、合同模板**都不同，但会员管理、资金管理、仓储管理是共享的。

### 技术难点

```
                    ┌──────────────┐
                    │  交易引擎核心  │
                    └──────┬───────┘
                           │
          ┌────────┬───────┼───────┬────────┐
          ▼        ▼       ▼       ▼        ▼
      ┌──────┐┌──────┐┌──────┐┌──────┐┌──────┐
      │挂牌模式││竞价模式││点价模式││预售模式││ ...  │
      └──┬───┘└──┬───┘└──┬───┘└──┬───┘└──────┘
         │       │       │       │
         ▼       ▼       ▼       ▼
    ┌─────────────────────────────────┐
    │      共享服务层                    │
    │  会员 │ 资金 │ 仓储 │ 物流 │ 风控  │
    └─────────────────────────────────┘
```

**核心挑战**：

| 问题 | 难点 |
|------|------|
| **模式差异大** | 点价需要实时期货行情，竞价需要定时撮合，挂牌是实时摘牌，流程完全不同 |
| **可扩展性** | 新增交易模式不能影响现有模式，需要开闭原则 |
| **配置化 vs 硬编码** | 过度配置化会导致复杂度爆炸，过度硬编码无法复用 |
| **风控规则差异** | 不同模式的风控阈值、保证金比例、涨跌停规则不同 |

### 面试讲法

> "7 种交易模式如果每个写一套，代码量爆炸且无法维护。我们用了**策略模式 + 模板方法模式**的组合：定义交易流程骨架（挂单→撮合→成交→结算→交收）作为模板方法，每种模式实现自己的策略类。风控规则用**规则引擎**（Drools/自研 DSL）外部化，不同模式绑定不同规则集。新增交易模式只需要实现策略接口+配置规则集，不动核心引擎。这和我在 Agent Harness 里做节点编排的思路一致——MainLoop 是骨架，每个 Agent 是可插拔的策略。"

### 架构设计要点

```python
# 面试时可以画的简化代码
class TradeMode(ABC):
    @abstractmethod
    def create_order(self, req: OrderRequest) -> Order: ...
    @abstractmethod
    def match(self, order: Order) -> TradeResult: ...
    @abstractmethod
    def settle(self, result: TradeResult) -> Settlement: ...

class ListingMode(TradeMode):  # 挂牌交易
    def create_order(self, req): ...  # 实时摘牌
    def match(self, order): ...       # 即时匹配
    def settle(self, result): ...     # T+0 结算

class PricingMode(TradeMode):  # 点价交易
    def create_order(self, req): ...  # 需要期货行情
    def match(self, order): ...       # 点价时点匹配
    def settle(self, result): ...     # 当日结算
```

## 12. 难点四：点价交易的期现实时联动

> 速查结论与"为什么 Canal + 缓存服务"的决策话术见第一部分第 4 节决策 4。

### 业务场景

点价交易中，挂牌方报价 = **期货实时价格 ± 升贴水**，摘牌方选择某个时点的价格摘牌。这意味着系统需要**实时获取期货行情、动态计算现货价格、在毫秒级窗口内锁定价格**。

### 技术难点

```
期交所行情源 ──(WebSocket/FAST协议)──→ 行情接入网关
                                          │
                                    ┌─────┴─────┐
                                    │ 行情分发   │
                                    └─────┬─────┘
                    ┌─────────────────┼─────────────────┐
                    ▼                 ▼                  ▼
              ┌──────────┐    ┌──────────┐      ┌──────────┐
              │ 点价引擎  │    │ 前端推送  │      │ 风控监控  │
              │ 价格计算  │    │ WebSocket │      │ 波动告警  │
              └──────────┘    └──────────┘      └──────────┘
```

| 挑战 | 难点 | 量化指标 |
|------|------|---------|
| **行情接入延迟** | 期交所行情推送频率高（每秒数百 tick），需要低延迟接入 | 行业标准：<10ms |
| **价格锁定原子性** | 摘牌时必须锁定当时的期货价格，不能出现"摘牌时看到的价格和成交价格不一致" | 需要时间戳+版本号 |
| **行情分发性能** | 同时有数千交易商查看实时行情，需要高效广播 | 需支持万级并发推送 |
| **白盘/夜盘切换** | 期货有日盘和夜盘，行情源切换不能中断服务 | 需要无缝热切换 |
| **基差监控** | 期现价差（基差）实时计算+预警 | 数据延迟从 2-5 分钟降至 10 秒 |

### 面试讲法

> "点价交易最核心的技术挑战是**价格的实时性和锁定原子性**。期货行情通过 WebSocket 接入，每秒数百个 tick，我们在行情接入层做了**背压控制**防止行情风暴打爆下游。摘牌时用'行情快照+版本号'机制——摘牌请求携带当前版本号，如果引擎当前版本号已更新则摘牌失败，需要重新确认价格，保证价格锁定的原子性。前端推送用 WebSocket 批量合并（100ms 窗口聚合成一帧），减少推送次数同时保持实时性。"

## 13. 难点五：全流程模块化的数据一致性

> 速查结论与"为什么 outbox 而不是 Seata/XA"的决策话术见第一部分第 4 节决策 3。

### 业务场景

郑大 B2B 平台有 8 个核心模块（会员、交易、资金、结算、风控、合同、仓储、运输），一笔交易涉及**全部 8 个模块的状态联动**。比如：下单→冻结资金→生成合同→锁定仓单→调度物流→风控审核→结算→解冻资金。

### 技术难点

| 问题 | 难点 |
|------|------|
| **跨服务事务** | 8 个微服务，一个交易流程跨全部服务，不能用数据库本地事务 |
| **部分失败处理** | 资金冻结成功但仓单锁定失败，需要回滚资金冻结 |
| **事件顺序保证** | 合同生成必须在交易成交之后，物流调度必须在仓单锁定之后 |
| **状态查询性能** | 交易全链路状态查询不能查 8 个服务，需要聚合视图 |
| **幂等+补偿** | 每个步骤都可能重试，必须幂等；失败必须可补偿 |

### 面试讲法

> "8 个模块的状态联动，如果用分布式事务（如 Seata）性能太差，我们用了**事件驱动 + Saga 编排**的方案。核心交易流程定义为一个 Saga，每个步骤有对应的补偿动作。比如'冻结资金'的补偿是'解冻资金'，'锁定仓单'的补偿是'释放仓单'。事件通过 Kafka 传递，保证顺序性。状态查询用 CQRS 模式——写库用各服务本地库，读库用一个聚合视图（ElasticSearch/Redis），异步同步。"

### Saga 编排示意

```
下单成功
  ├─→ 冻结资金 ──(失败)──→ 回滚订单
  ├─→ 生成合同 ──(失败)──→ 解冻资金 → 回滚订单
  ├─→ 锁定仓单 ──(失败)──→ 作废合同 → 解冻资金 → 回滚订单
  ├─→ 调度物流 ──(失败)──→ 释放仓单 → 作废合同 → 解冻资金 → 回滚订单
  └─→ 风控审核 ──(失败)──→ 取消物流 → 释放仓单 → 作废合同 → 解冻资金 → 回滚订单
```

### 与你背景的关联

> 这和你 Agent Harness 中的**6 节点流水线**高度一致——微信公众号流水线（采集→清洗→生成→配图→排版→发布）也是多步骤、可补偿的 Saga 流程，可以直接用来类比。

## 14. 难点六：高并发交易撮合与流式风控

> 速查结论见第一部分第 4 节决策 1 / 决策 2 与第 6 节 Q4 / Q6（C+Java 异构、异步落库、防超卖三道防线）。

### 业务场景

竞价交易模式下，多个买方同时出价，系统需要**实时撮合 + 实时风控**——每笔出价都要检查保证金是否充足、是否触发涨跌停、是否异常交易。

### 技术难点

| 挑战 | 方案 |
|------|------|
| **内存撮合** | 撮合引擎纯内存操作（类似交易所撮合），订单簿用红黑树/优先队列 |
| **流式风控** | 每笔订单实时过风控规则引擎，延迟 <5ms |
| **熔断降级** | 风控服务不可用时，交易是"拒绝"还是"放行"？需要熔断策略 |
| **峰值应对** | 竞价截止前集中出价，峰值可达日常 10-50 倍 |
| **数据持久化** | 内存撮合结果需要异步落库，宕机不能丢数据（WAL 机制） |

### 面试讲法

> "撮合引擎参考了交易所的设计——订单簿维护在内存中，买单按价格降序、卖单按价格升序，撮合是 O(log N) 的红黑树操作。风控用流式处理，每笔订单过规则引擎，单次 <5ms。为了防风控故障导致交易中断，设计了**熔断+降级**策略：风控服务超时率超阈值时，切换到本地规则缓存（宽松模式），同时告警人工介入。撮合结果用 WAL（Write-Ahead Log）先写日志再撮合，宕机可恢复。"
