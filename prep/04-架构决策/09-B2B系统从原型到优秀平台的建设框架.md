# B2B系统：从原型到优秀平台的建设框架

> **拆分来源**：原 `04-架构决策/01-架构方法论与选型设计手册.md`（三份材料拼接），2026-10-11 第二十一轮独立成篇。
> 姊妹篇：`04-架构决策/01`（架构方法论）、`04-架构决策/10`（完整技术选型与设计方案）。

> **编写背景**：你已经把自己的系统解剖到了根因层——"副本式架构"的七个痛点高度收敛于同一个系统性缺陷。现在反过来想：如果从头设计一套优秀的B2B系统，原型阶段应该做什么、怎么做、做到什么程度才算"过了"。

---

## 一、先纠正一个认知：B2B原型 ≠ 画界面

B2C创业可以做个Figma高保真原型拿给用户点一点、测转化率。B2B不行。

**B2B原型的核心目的不是"好不好看"，是"对不对"——领域模型对不对，交易链路通不通，数据一致性能不能保证，异常情况下系统行为是否符合业务预期。**

| | B2C原型 | B2B原型 |
|---|---|---|
| 验证什么 | 用户体验、转化漏斗 | 领域模型、交易闭环、数据一致性 |
| 谁来看 | 终端消费者 | 业务专家、交易运营、风控 |
| 可接受的错误 | 按钮位置不对、颜色不喜欢 | 订单状态丢了一步、金额对不上、货权归属错误 |
| 原型载体 | Figma/可交互页面 | 领域模型图 + 核心链路可运行骨架 + 事件时序图 |
| "过了"的标志 | 用户愿意点下一步 | 业务专家看完说不出"这不符合实际流程" |

**你做原型的第一个动作不是打开设计工具，是拿一张白纸画领域模型。**

## 二、原型之前：三个必须先回答的问题

在你写一行代码、画一个框之前，把这三件事想清楚。它们决定了你后面所有技术决策的边界。

### 问题1：你的系统本质上是什么？

不是"一个交易平台"，那太泛了。要精确到一句话：

> **这是一个以 [核心撮合机制] 为引擎、以 [履约保证] 为信任基石、以 [供应链金融] 为增值引擎的 [垂直品类] B2B交易系统。**

按你的实际情况填空：
- 核心撮合机制：挂牌/竞价/协议/基差 四种模式
- 履约保证：合同→仓单→交收→结算 闭环
- 增值引擎：交易数据 → 信用评价 → 供应链融资
- 垂直品类：钢铁（可扩展）

**这句话是你原型阶段所有取舍的判断标准。** 任何跟这句话无关的功能，原型阶段都不做。

### 问题2：你的第一个客户是谁？

不是"所有大宗贸易商"。第一个人必须具体到一家公司、一个人。

从你之前的五类目标客户分析里选一个作为原型验证对象：

| 客户类型 | 原型验证重点 | 为什么选它 |
|---|---|---|
| 垂直行业平台运营商 | 多租户配置引擎 | 一个平台服务多个垂直品类 |
| 大型产业集团 | 私有化部署 + 深度定制 | 企业内部供应链数字化 |
| 地方政府/产业园 | 交易大屏 + 监管合规 | 政策驱动，快速立项 |
| 行业协会/商会 | 会员共享平台 | 轻量级起步 |
| 金融机构 | 供应链金融风控引擎 | 数据变现路径最短 |

**建议原型阶段选"垂直行业平台运营商"中的一家中型贸易商**——它既有真实交易场景帮你验证领域模型，又不像钢厂那样要求私有化部署。

### 问题3：一条交易从头走到尾，最少需要哪几个系统？

不要一上来就想12个微服务。原型阶段只做"最小可行骨架"——

```
                    ┌──────────────┐
                    │   用户/认证    │  ← 谁在用
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ▼                  ▼                  ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│   商品中心    │  │   交易引擎    │  │   合同中心    │
│ (有什么可买卖) │  │ (怎么成交)    │  │ (怎么锁定)    │
└──────────────┘  └──────┬───────┘  └──────────────┘
                          │
                          │ 成交后
                          ▼
                 ┌──────────────┐
                 │   履约中心    │  ← 仓单过户 + 交收 + 结算
                 └──────────────┘
```

**原型阶段的六个系统**（刚够让一笔交易跑通）：
1. **用户与权限** — 谁在用、看到什么
2. **商品中心** — 品类编码、商品主数据
3. **交易引擎** — 挂牌/摘牌/撮合（核心）
4. **合同中心** — 成交后生成合同
5. **履约中心** — 仓单过户、交收确认、资金结算
6. **通知服务** — 状态变更推送

不需要支付网关（原型阶段用模拟）、不需要风控引擎、不需要数据分析、不需要供应链金融。那些是血肉，骨架先搭对。

## 三、原型四阶段

### Phase 0：纸上建模（2-3天，不写代码）

**目标**：让业务专家看完说不出"不对"。

**做法**：拿出白纸（或Miro/Excalidraw），跟最懂业务的人一起画三张图。

#### 图1：领域模型图

画出核心聚合根和它们之间的关系。只画主干，不画枝叶。

```
客户(Customer)
  │
  ├── 拥有多个 商品(Product) ── 属于 ── 品类(Category)
  │
  ├── 发布 挂牌(Listing)
  │       │
  │       └── 成交后生成 合同(Contract)
  │               │
  │               └── 关联 仓单(WarehouseReceipt)
  │                       │
  │                       └── 触发 交收(Delivery)
  │                               │
  │                               └── 完成 结算(Settlement)
  │
  └── 有 账户(Account) ── 记录 资金流水(FundTransaction)
```

**关键原则**：
- 每个聚合根只在一个地方"出生"（唯一写入源）
- 其他系统通过ID引用，不走数据副本
- 聚合根之间的事件传递是异步的

#### 图2：一笔交易的事件时序图

以最简单的"挂牌→摘牌→成交"为例，画出每个事件在六个系统之间的流动：

```
买方         交易引擎        合同中心       履约中心       通知服务
 │              │              │              │              │
 │  摘牌请求     │              │              │              │
 │─────────────>│              │              │              │
 │              │ 验证挂牌状态   │              │              │
 │              │ 生成成交记录   │              │              │
 │              │ 发布"已成交"事件│             │              │
 │              │─────────────>│              │              │
 │              │              │ 生成合同      │              │
 │              │              │ 发布"合同已生成"│             │
 │              │              │─────────────>│              │
 │              │              │              │ 创建履约单    │
 │              │              │              │ 发布"待交收"  │
 │              │              │              │─────────────>│
 │              │              │              │              │ 推送给双方
 │  <──────────────────────────────────────────────────────  "合同已生成"
 │  <──────────────────────────────────────────────────────  "待交收确认"
```

**这张图的价值**：它暴露了所有"数据该从哪里来"的问题。如果某一步事件断了，后续步骤全卡住——这就是你现有系统"副本式同步"的根因可视化。

#### 图3：领域事件目录

列出一笔交易从生到死所有会产生的事件：

| 事件 | 产生方 | 消费方 | 关键数据 |
|---|---|---|---|
| ListingPublished | 交易引擎 | 通知服务 | 挂牌ID、商品、价格、数量、卖方 |
| ListingAccepted | 交易引擎 | 合同中心、通知服务 | 挂牌ID、摘牌方、成交价、成交量 |
| ContractCreated | 合同中心 | 履约中心、通知服务 | 合同ID、双方、商品、价格、数量 |
| DeliveryRequested | 履约中心 | 仓单系统、通知服务 | 履约单ID、合同ID、仓单ID |
| DeliveryCompleted | 履约中心 | 结算、通知服务 | 履约单ID、交收时间、验收结果 |
| SettlementCompleted | 履约中心 | 通知服务 | 结算单ID、金额、时间 |

**这张图是你系统的事件骨架。原型阶段的代码就是让这些事件按顺序正确发生。**

#### Phase 0 验收标准
- [ ] 业务专家看了领域模型图，没有说"我们实际不是这样的"
- [ ] 事件时序图覆盖了你的核心交易模式（挂牌成交 + 至少一个变体如竞价）
- [ ] 事件目录没有遗漏"钱"和"货"的任何一个状态变更
- [ ] 每个事件都能回答"谁产生、谁消费、携带什么数据"

### Phase 1：核心骨架（2-3周，最小可运行）

**目标**：让一笔虚拟交易从头跑到尾，事件全部正确触发。

**做什么**：
1. 六个系统各自的最简实现——每个系统只实现Phase 0定义的核心聚合根
2. 系统间通过**领域事件**通信（Kafka或内存消息队列，原型阶段后者更简单）
3. 每个系统有自己的数据库，不共享
4. 所有数据变更通过事件通知，不做同步RPC调用链

**不做**：
- 不做前端完整UI——只做一个极简操作界面或直接API调用
- 不做权限精细控制——只有"买方/卖方"两个角色
- 不接真实支付、不接真实短信、不接任何外部系统
- 不做性能优化、不做缓存、不做高可用

#### 原型阶段的数据架构：从第一天就避免"副本式"

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   商品中心    │    │   交易引擎    │    │   合同中心    │
│              │    │              │    │              │
│ 商品表(权威)  │    │ 挂牌表       │    │ 合同表(权威)  │
│              │    │ 商品ID(引用)  │    │ 挂牌ID(引用)  │
└──────────────┘    └──────────────┘    │ 买卖方ID(引用) │
                                        └──────┬───────┘
                                               │ 合同ID(权威)
                                        ┌──────▼───────┐
                                        │   履约中心    │
                                        │              │
                                        │ 履约单表(权威)│
                                        │ 合同ID(引用)  │
                                        └──────────────┘
```

**核心规则**：
- 每个数据只有一个"出生地"（权威源）
- 其他系统存**引用**（ID），不存**副本**（完整数据）
- 如果需要展示关联数据（如履约单上显示商品名称），查询时通过ID去权威源获取，不在履约表里存商品名称副本

#### Phase 1 验收标准
- [ ] 挂牌→摘牌→成交→合同生成→履约单创建，整条链路跑通
- [ ] 每个状态变更都有对应的事件发出
- [ ] 任何一个中间系统宕机，不影响已完成的步骤（事件可重放）
- [ ] 数据库中不存在"同一份客户数据存在两个不同版本"的情况
- [ ] 可以用一个查询把"合同→挂牌→商品→履约"串起来

---

### Phase 2：血肉填充（2-4周，可演示）

**目标**：让业务专家可以实际操作，能跑通真实业务场景。

**做什么**：

#### 2.1 前端可操作界面

不是完整产品，是够用的操作界面：
- 卖方：发布挂牌、查看我的挂牌、确认成交
- 买方：浏览挂牌、摘牌、查看我的合同
- 双方：查看履约进度、确认交收

每个页面聚焦一件事。不做dashboard、不做数据统计、不做管理后台。

#### 2.2 业务角色区分

从原型第一天就做角色区分，不要等到后面重构：
- 买方登录 → 看到的是"找货"视图
- 卖方登录 → 看到的是"卖货"视图
- 同一账号可以同时是买方和卖方（大宗贸易商天然双向），但切换模式时有清晰的视图切换

#### 2.3 用真实业务场景跑一遍

从你的钢铁交易场景故事集中挑3个最有代表性的：
1. **标准挂牌成交**：卖方挂牌→买方摘牌→签合同→仓单过户→交收→结算（最基础链路）
2. **竞价成交**：卖方发起竞价→多方出价→最高价成交→后续同标准链路
3. **异常场景**：买方摘牌后反悔→合同取消→挂牌恢复（验证状态回滚）

每个场景走完，记录三件事：
- 哪里跟业务专家说的不一样？
- 哪个状态转换业务专家觉得"不对"？
- 少了什么数据？

#### Phase 2 验收标准
- [ ] 三个场景全部跑通，业务专家能自己操作
- [ ] 角色切换流畅，买方/卖方看到的内容正确隔离
- [ ] 异常场景的状态回滚符合业务预期
- [ ] 业务专家不再说"这里跟我们实际不一样"

---

### Phase 3：弹性验证（1-2周，边界条件）

**目标**：在原型阶段就暴露系统设计的薄弱点，避免生产事故。

#### 3.1 事件断链恢复

模拟消息中间件宕机、某个服务重启：
- 事件是否可重放？
- 重放后状态是否一致？
- 消费端是不是幂等的？

#### 3.2 并发冲突

两个买方同时摘同一个挂牌：
- 谁先到谁成交？
- 后来者看到什么提示？
- 会不会出现"两个人都以为自己成交了"？

#### 3.3 状态机完整性

画出交易引擎的完整状态机：

```
挂牌发布 ──→ 待摘牌 ──→ 已摘牌 ──→ 合同已生成 ──→ 履约中 ──→ 已完成
                │                                    │
                └──→ 已过期                          └──→ 已取消（需双方确认?）
```

**检查每条边**：从当前状态出发，哪些操作是合法的？哪些是非法的？
**检查每个状态**：有没有"死状态"（进去了出不来）？

#### Phase 3 验收标准
- [ ] 事件断链后系统可自动恢复，无需人工介入
- [ ] 并发场景下不会出现数据不一致
- [ ] 状态机没有死状态、没有非法转换路径
- [ ] 所有异常场景都有明确的错误信息和恢复路径

## 四、原型阶段就要做对的五件事（你现有系统的血泪教训）

### 1. 商品编码从第一天就统一

你现有系统最大的痛：仓单用大类ID，挂牌用细分品种ID，配货靠人工对名称。

**原型做法**：设计三层品类编码（大类→品种→规格），所有系统引用同一个商品ID。哪怕原型阶段只有10个商品，编码体系也要完整。

### 2. 客户主数据只有一个源

你现有系统第二大痛：客户数据通过消息队列"复制"到N个系统，同步断了就乱。

**原型做法**：客户只在"用户系统"创建。其他系统存`customer_id`（引用），展示时通过ID去用户系统查。不做任何形式的客户数据副本。

### 3. 事件驱动，不做同步调用链

你现有系统的履约流程是高耦合的——一个环节调用下一个，链条中断需要人工排查。

**原型做法**：每个系统只做两件事——处理本域业务逻辑 + 发布领域事件。谁消费这个事件、怎么处理，发布方不关心。这让你后续加新业务模式时不需要改现有代码，只需要加新的事件消费者。

### 4. 状态机先画全再写代码

很多系统的状态机是"写着写着补出来的"，导致边界情况没覆盖。

**原型做法**：Phase 0就把交易核心的状态机画完整（包括所有异常路径），Phase 1按状态机实现。宁可原型阶段多画几个状态，也不要上线后补。

### 5. 配置化而不是硬编码

你现有系统的第三个大问题：新增一个交易模式要在多个系统里改代码。

**原型做法**：挂牌规则、合同模板、履约流程用配置驱动。原型阶段不需要完整的规则引擎，但架构上留出"策略可替换"的口子——用策略模式或简单的配置表，不要`if 挂牌 else if 竞价`写死在业务逻辑里。

## 五、原型之后的过渡：怎么从原型到生产

原型通过验收后，最大的陷阱是"原型代码直接上线"。不要这么做。

| | 原型代码 | 生产代码 |
|---|---|---|
| 目标 | 验证模型对不对 | 稳定运行、可运维 |
| 数据库 | 可能单机、无备份 | 主从、备份策略、迁移脚本 |
| 消息队列 | 可能内存实现 | Kafka集群、持久化、监控 |
| 服务通信 | 可能直连 | 网关、服务发现、熔断 |
| 错误处理 | "先跑通再说" | 全面的异常分类和降级策略 |

**过渡策略**：
1. **保留领域模型和事件目录**（Phase 0的产出是永久资产）
2. **保留状态机定义**（直接翻译成生产代码的状态机）
3. **重写基础设施层**（数据库切换为生产配置、消息队列切换为Kafka、加网关）
4. **逐个替换业务逻辑**（一个聚合根一个聚合根迁移，不要大爆炸式切换）
5. **上线前跑一遍Phase 3的弹性验证**（在生产环境配置下重跑）
