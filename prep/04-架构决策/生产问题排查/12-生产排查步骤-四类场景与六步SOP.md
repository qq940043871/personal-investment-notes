# 生产排查步骤 — 四类场景地图与六步排查 SOP

> **文档定位**：本系列**方法论总纲**（一问一文）——回答两个高频问题："你们日常排查的都是什么问题？"（四类场景地图）和"线上出问题，你的排查步骤是什么？"（六步 SOP）。`06/08/09/10/11` 五篇实录讲"一个案子怎么破"，本篇讲"所有案子通用的破案流程"，并给出四类问题到实录的对照索引。

## 1. 四类场景全景地图：日常排查的都是什么问题

Java 高级架构师日常排查的问题，本质上可以分为**四类场景**：线上正在发生的故障、周期性/突发性性能问题、隐蔽的架构与代码缺陷、以及跨团队的疑难杂症。先认清问题属于哪一类，排查策略完全不同。

### 1.1 线上故障类（优先级最高）

这类问题特点是**正在影响用户，必须快速止损**——排查与止损并行，不允许"查清楚再动手"。

| 问题类型 | 典型现象 | 排查切入点 |
|---|---|---|
| CPU 飙高 | 单核 100%、Load 持续攀升 | `top -H -p pid` 找线程 → `jstack` 看栈 → 定位死循环/正则回溯/GC |
| 内存泄漏 / OOM | 频繁 Full GC、堆越来越大 | `jmap -histo` 看对象分布 → `jmap -dump` + MAT 分析支配树 |
| 线程池打满 | 接口超时、请求排队 | `jstack` 看线程状态、阻塞点；检查拒绝策略和队列长度 |
| 连接池耗尽 | 获取连接超时、DB 连接报错 | 监控连接池活跃数、等待数、慢 SQL |
| 死锁 | 线程互相等待、接口挂起 | `jstack` 直接能看出 `Found one Java-level deadlock` |
| 服务不可用 | 大量 5xx、熔断触发 | 看网关日志、下游依赖、链路追踪 |

**核心工具链**：`top / vmstat / iostat` → `jstack / jmap / jstat / arthas` → `MAT / JProfiler` → 链路追踪（SkyWalking / Jaeger）。

### 1.2 性能与容量类

特点是**不报错但变慢**（或周期性发作），用户体感差、投诉常常先于告警到达。

- **接口 RT 毛刺**：偶发慢请求，通常是 GC 停顿、锁竞争、批量任务抢占资源。
- **慢 SQL**：`explain` 执行计划、索引失效、大表 join、深分页。这是最高频问题之一。
- **缓存问题**：缓存击穿（热点 key 失效）、穿透（查不存在数据）、雪崩（大批 key 同时过期）。
- **Full GC 频繁**：堆参数不合理、大对象、内存泄漏、元空间（Metaspace）膨胀。
- **消息积压**：消费能力不足、消费逻辑阻塞、分区不均衡。
- **数据库连接被打满**：慢查询拖垮整个池。

（实录对照：页面突变慢见 `09`，扩容后流量打穿 DB 见 `11`。）

### 1.3 架构与中间件类

特点是**故障面大、责任边界模糊**，往往要拉着 DBA / 运维 / 中间件团队一起看。

| 组件 | 常见排查问题 |
|---|---|
| **MySQL / PG** | 主从延迟、锁等待、事务隔离级别问题、连接数打满 |
| **Redis** | 大 key / 热 key、内存碎片、持久化阻塞、集群脑裂、慢查询 |
| **Kafka / RocketMQ** | 消息丢失、重复消费、顺序性、消费者 group rebalance、堆积 |
| **注册中心 Nacos/Consul** | 服务下线不及时、实例状态不一致、健康检查误判 |
| **网关 / Nginx** | 502/504、连接数、超时配置、后端健康检查 |
| **分布式事务** | 数据不一致、补偿未执行、TCC 悬挂/空回滚 |
| **分布式锁** | 锁失效、锁续约、死锁、误删他人锁 |

### 1.4 隐蔽缺陷与跨团队问题

特点是**低频、难复现、日志常常是干净的**，最考验推理能力与证据链。

- **并发问题**：可见性、原子性、指令重排导致的偶发数据错误，极难复现。
- **时序/竞态**：分布式环境下日志时间不一致，需要对时、看链路 traceId。
- **版本/配置不一致**：多环境、多机房配置漂移导致的"在我这儿是好的"。
- **三高场景下的连锁故障**：一个下游抖动引发全链路雪崩（需从依赖拓扑整体看）。
- **数据一致性问题**：缓存与 DB 不一致、分库分表后跨库 join、主键冲突。

（实录对照：日志干净的"进程消失"见 `10` 的判定树；认证偶发失败的 5Why 推理见 `06`。）

## 2. 生产排查步骤：六步 SOP

不管哪一类问题，通用流程都是六步。核心顺序不能乱：**先止损，再定位；先定界，再下钻；用数据说话，用固化收尾**。

```
第 1 步   第 2 步     第 3 步     第 4 步       第 5 步     第 6 步
  止损 → 看大盘 →  缩小范围 → 逐层下钻 →   数据实证 → 复盘固化
（分钟级）（定性质） （二分定界）（逐层收敛）  （锁根因）  （防再发）
```

### 第 1 步：先止损，再定位（分钟级，与排查并行）

**做什么**：熔断、降级、扩容、回滚、限流优先——回滚最近变更（发布/配置/DDL/网络）、打开预案开关、切流量到备用。原则：**恢复用户可用性优先于查明原因**；30 分钟未定位必须升级拉人，不允许单人闷头查。

**注意**：止损前先**留证**——监控截图、`jstack` / `jmap` / GC 日志落盘，避免"重启把现场销毁了"。实在来不及就先止损，事后用监控数据回溯。

### 第 2 步：看监控大盘，定问题性质

**看什么**：CPU / 内存 / GC / RT / QPS / 错误率——先确定**拐点时间**，把故障窗口和变更窗口对齐（发布、促销、定时任务、上下游故障）。

**判定出口**（决定走哪条排查路径）：

| 大盘特征 | 问题性质 | 走向 |
|---|---|---|
| 错误率上升 | 线上故障类 | §1.1 路径 |
| 错误率不涨、RT 上升 | "慢而不报错" | §1.2 路径（见 `09`） |
| 数据错 / 不一致 | 隐蔽缺陷 | §1.4 路径 |

### 第 3 步：缩小范围（二分定界）

回答四个问题，把范围砍掉一半以上：

1. **单机还是集群？**——只有某台坏 → 查该机（CPU/磁盘/网络/邻居进程）；全部坏 → 查公共依赖。
2. **特定接口还是全局？**——单接口 → 该接口链路；全局 → 网关 / JVM / DB / 公共中间件。
3. **本服务还是下游？**——traceId 拆分段耗时，把瓶颈收敛到一层（见 `09` 五层定界）。
4. **变更前还是变更后？**——故障窗口内的发布/配置/DDL/流量变化是第一嫌疑。

### 第 4 步：自上而下逐层下钻

```
网关 / 入口  →  应用服务  →  缓存 / 中间件  →  DB
```

每层只问三个问题：**这层的耗时正常吗？这层的容量指标正常吗？这层有变更吗？**——任何一层"明显不对"就先停在该层深挖，不跳层。多机房多线路场景先做接入层定界（四步定位法见 `08`）。

### 第 5 步：用数据说话（锁死根因）

| 怀疑方向 | 取证工具 |
|---|---|
| CPU / 死循环 / 锁竞争 | `top -H -p` → `jstack`（多次采样对比）→ 火焰图 |
| 内存 / GC | GC 日志、`jstat -gcutil`、`jmap -histo`、dump + MAT 支配树 |
| 慢 SQL | 慢查询日志、`explain`、PROCESSLIST、锁等待 |
| 链路 | traceId 分段耗时（SkyWalking / Jaeger） |
| 进程消失 / 被杀 | 退出码、hs_err、内核 dmesg / cgroup 日志（见 `10` 判定树） |

**标准**：根因必须能用**一条证据链**解释全部现象（包括"为什么别的机器没事"），解释不了就说明还没到底。

### 第 6 步：复现并固化（防再发）

- **复现**：预发回放 / 压测用例复现根因；复现不了就补埋点等下一次。
- **固化四件套**：补监控指标（覆盖盲区）、补告警规则（阈值 + 分级）、补压测用例（进回归）、写复盘（根因 / 改进项 / 完成时间）。
- **落地为规范**：能写进 checklist / 红线的（如"DDL 禁止在交易时段"），就不依赖人的记忆。**故障不可怕，可怕的是同一个问题重复发生。**

## 3. 工具链速查（按层）

| 层 | 常用工具 | 关键动作 |
|---|---|---|
| 系统层 | `top -H -p` / `vmstat` / `iostat` / `free` / `ss` | 先看 CPU、IO、网络是否异常，再进 JVM |
| JVM 层 | `jstack` / `jmap -histo` / `jmap -dump` / `jstat -gcutil` / Arthas | 线程栈看阻塞点，堆分布看泄漏，Arthas 在线定位（trace/watch 热方法） |
| 堆分析 | MAT / JProfiler | 支配树找"谁占着内存不放" |
| 链路追踪 | SkyWalking / Jaeger / 自研 trace | 一次请求分段耗时，瓶颈收敛到层 |
| DB | `explain` / 慢日志 / PROCESSLIST / `show engine innodb status` | 索引失效、锁等待、连接数、主从延迟 |
| 中间件 | Redis slowlog / bigkeys；Kafka lag；Nacos 实例状态 | 大 key / 热 key、积压、注册状态不一致 |

## 5. 附录

### 5.1 排查常见误区（反面清单）

| 误区 | 后果 | 正确做法 |
|---|---|---|
| 先重启再查 | 现场销毁，根因永远找不到 | 先留证（堆栈/dump/监控截图）再止损 |
| 只看平均值 | 毛刺被平均掉 | 看 P99 / P99.9 分位 + 最慢 TopN |
| 只盯自己服务 | 下游抖动被忽略 | traceId 分段，先把瓶颈收敛到层 |
| 定位到就收工 | 同一问题重复发生 | 必须固化四件套（监控/告警/压测/复盘） |
| 全凭经验猜 | 互相甩锅、来回拉扯 | 用数据说话，每一步有证据 |

### 5.2 术语说明

| 术语 | 说明 |
|------|------|
| 止损 | 优先恢复用户可用性（回滚/限流/降级/扩容），不等根因查清 |
| 定界 / 下钻 | 先把故障收敛到某一层/某台机，再在该范围内深挖，不跳层 |
| 拐点时间 | 监控指标突变的时刻，用来和变更窗口对齐 |
| P99 / P99.9 | 99% / 99.9% 的请求耗时上限，比平均值更能反映用户体感 |
| traceId | 一次请求全链路的唯一标识，用于分段拆解耗时 |
| 支配树 | MAT 堆分析视图，找"谁占着内存不放" |
| 慢而不报错 | 成功率 100% 但 RT 恶化的故障形态，投诉先于告警到达 |

### 5.3 面试速答（90 秒版）

> "我日常排查的问题分四类：正在影响用户的线上故障、慢而不报错的性能问题、隐蔽的架构缺陷和跨团队疑难。流程上我坚持六步：**先止损再定位**——熔断、降级、扩容、回滚优先，但动手前先留证，堆栈和监控截图先落盘；**第二步看大盘**定性质，找拐点时间跟变更窗口对齐，区分是报错、变慢还是数据错；**第三步缩小范围**，单机还是集群、特定接口还是全局、本服务还是下游、变更前还是变更后，四个问题把范围砍一半；**第四步自上而下逐层下钻**，网关 → 应用 → 中间件 → DB，每层只问耗时、容量、变更三个问题，不跳层；**第五步用数据说话**锁根因——CPU 问题拿线程栈，内存问题拿 GC 日志和 MAT，慢 SQL 拿 explain，链路问题拿 traceId 分段耗时，根因要能用一条证据链解释全部现象；**最后一步复现并固化**，补监控、补告警、补压测用例、写复盘，能进 checklist 的不依赖记忆。我的原则是：故障不可怕，可怕的是同一个问题重复发生。"

**追问预案**：

| 追问 | 回答要点 |
|------|---------|
| 止损和留证冲突怎么办？ | 不冲突：留证只要几十秒（截图、`jstack` 两次采样、GC 日志落盘），实在来不及就先止损，事后用监控数据回溯；保用户永远第一 |
| 怎么快速判断是单机问题？ | 同接口在其他机器正常 + 该机 CPU/IO/网络异常 → 单机；反之查公共依赖。监控按实例维度拆分看 |
| 一个"偶发慢 500ms"怎么查？ | 先分位数确认毛刺频率和时间分布（是否与定时任务/GC 周期相关）→ traceId 拆分段耗时定位层 → 毛刺时刻的 GC 日志 / 锁竞争 / 慢 SQL 三对照 |
| 线上 CPU 100% 的完整命令序列？ | `top` 定位进程 → `top -H -p` 定位线程 → 线程 ID 转十六进制 → `jstack pid` 找 nid 对应栈 → 死循环 / 正则回溯 / 频繁 GC 三类收尾 |
| 为什么强调"拐点和变更窗口对齐"？ | 生产故障第一嫌疑永远是变更（发布/配置/DDL/网络）；时间对齐能用最快速度排除或坐实一半假设 |
| 复现不了的问题怎么办？ | 补埋点、留快照、加告警等下一次；低频并发问题靠 code review 抓可见性/原子性/时序问题，同时用压力手段提高触发概率 |
