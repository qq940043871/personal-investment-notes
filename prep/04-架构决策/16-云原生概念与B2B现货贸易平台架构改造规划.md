# 第一部分 · 云原生概念底座

## 1. 云原生（Cloud Native）到底指什么

### 1.1 权威定义（CNCF）

> 云原生技术有利于各组织在**公有云、私有云、混合云**等动态环境中，构建和运行**可弹性扩展**的应用。代表技术包括：**容器、服务网格、微服务、不可变基础设施和声明式 API**。

拆开看三层含义：

| 层次 | 含义 | 关键词 |
|------|------|--------|
| **环境层** | 面向动态、弹性、可编排的基础设施 | 公有/私有/混合云、K8s |
| **方法层** | 用工程化手段把「运维」变成「代码」 | 声明式、不可变、自动化 |
| **技术层** | 容器、微服务、服务网格、Serverless 等具体载体 | Docker、Istio、Knative |

### 1.2 三个最常见的误区

| 误区 | 纠正 |
|------|------|
| 「用了 Docker 就是云原生」 | Docker 只是**门票**。没有编排、没有声明式交付、没有可观测性，只是「把 jar 换成了镜像」，是**容器化**而非云原生 |
| 「上 K8s 等于云原生」 | K8s 是**底座**。若仍靠人工 `kubectl` 部署、无 GitOps、无弹性策略、无统一可观测，则只是「把部署脚本搬进了集群」 |
| 「云原生 = 微服务」 | 微服务是**选项不是前提**。模块化单体 + 容器化 + 声明式交付同样是云原生实践（见 `10` 的「模块化单体」结论） |

> **判据（本人口径）**：判断一套系统「云原生成熟度」的高低，不看用了多少组件，看三件事——**能不能声明式地描述期望状态、能不能自动收敛、能不能被观测**。

### 1.3 四大核心支柱

```
┌─────────────────────────────────────────────────────────────┐
│                    云原生四大支柱                             │
├───────────────┬───────────────┬───────────────┬─────────────┤
│  ① 容器化      │  ② 微服务      │  ③ DevOps /   │ ④ 声明式API  │
│  Container     │  Microservice │  持续交付      │  + 不可变    │
│               │               │  CI/CD        │  基础设施     │
│  一致性打包    │  独立部署演进  │  自动化流水线  │ 期望态收敛   │
│  环境无差异    │  边界清晰      │  小步快跑      │ 重建而非修改  │
└───────────────┴───────────────┴───────────────┴─────────────┘
```

- **① 容器化**：把「应用 + 依赖 + 运行时」打包成一个不可变镜像，消除「我本地能跑」的环境差异。
- **② 微服务**：按业务边界拆分、独立部署、独立伸缩。**它是手段不是目的**——拆错的微服务比单体更痛。
- **③ DevOps / 持续交付**：CI/CD 流水线把「提交到上线」压缩成分钟级，配合灰度与回滚降低发布风险。
- **④ 声明式 API + 不可变基础设施**：只描述「我要什么状态」，由控制器不断 reconcile；基础设施**不原地修改，而是重建替换**——这是云原生最容易被忽视、却最本质的一条。

### 1.4 12-Factor App 速查（云原生应用的基本纪律）

| # | 要素 | B2B 场景的对应 |
|---|------|---------------|
| 1 | 基准代码（Codebase） | 一库一服务，多环境同一份代码 + 不同配置 |
| 2 | 依赖（Dependencies） | 显式声明依赖，打进镜像，不依赖宿主机 |
| 3 | 配置（Config） | **配置外置**到 Nacos / ConfigMap / Secret，代码里不写死环境参数 |
| 4 | 后端服务（Backing services） | MySQL/Redis/Kafka 视为可替换资源，通过配置连接而非硬编码 |
| 5 | 构建/发布/运行（Build/Release/Run） | 三阶段严格分离：镜像构建一次，配置决定发布 |
| 6 | 进程（Processes） | 服务**无状态化**，会话外置到 Redis |
| 7 | 端口绑定（Port binding） | 服务自包含端口，不依赖外部注入 Web 容器 |
| 8 | 并发（Concurrency） | 靠**水平扩展进程**而非加大单进程线程来扩容 |
| 9 | 易处置（Disposability） | 能快速启动、能**优雅停机**（见下文 K8s 优雅下线） |
| 10 | 开发/生产一致性（Dev/prod parity） | 环境差异最小化，杜绝「测试能跑生产挂」 |
| 11 | 日志（Logs） | 日志是**事件流**，打到 stdout 由平台统一采集，不自己管文件切割 |
| 12 | 管理进程（Admin processes） | 一次性任务（迁移、对账）作为独立进程运行 |

> **本人现状对照**：`3/4/7` 已基本做到（Nacos 配置中心 + 连接池）；`6/9/11` 是**改造重点**——会话无状态化、优雅停机、日志 stdout 化，这三条是上弹性伸缩前的**前置条件**。

### 1.5 CNCF 技术全景（分层速查）

| 分层 | 代表项目 | 在 B2B 现货平台的可能位置 |
|------|---------|--------------------------|
| 编排与调度 | Kubernetes、Karmada（多集群） | 底座（现状：自建 K8s） |
| 容器运行时 | containerd、CRI-O、Kata | 底座（Docker → containerd） |
| 网络 CNI | Calico、Cilium | **NetworkPolicy 多租户隔离**（规划） |
| 入口/网关 | Envoy Gateway、Traefik、Ingress-Nginx | **midservice 之上的 L7 入口**（规划） |
| 服务网格 | Istio、Linkerd | Java 中台东西向流量治理（**规划，慎选**） |
| 存储 CSI | Rook/Ceph、Longhorn、MinIO | 对象存储（现状：MinIO） |
| 可观测 | Prometheus、Grafana、OpenTelemetry、Loki、Jaeger | **统一可观测（规划重点）** |
| CI/CD & GitOps | GitLab CI、ArgoCD、Tekton、Argo Rollouts | **交付流水线（规划重点）** |
| 安全与策略 | Trivy、Falco、OPA/Kyverno、Vault、cert-manager | 镜像扫描 + Secret 管理 + 策略准入（规划） |
| 中间件 Operator | Strimzi（Kafka）、Redis Operator、MySQL Operator | 数据层自愈（规划） |
| 应用定义 | Helm、Kustomize | 打包与多环境渲染（规划） |

> **现实提醒**：CNCF 全景是「超市货架」不是「采购清单」。**能用 5 个组件解决的问题，不要引入 15 个**——每引入一个组件，就多一份运维与故障面（见 `10` 的「铁律 1：团队经验权重大于技术先进性」）。

### 1.6 关键概念速查

| 概念 | 一句话解释 | 适用 / 代价 |
|------|-----------|------------|
| **Service Mesh** | 把流量治理（mTLS、重试、熔断、灰度、可观测）从业务代码下沉到**基础设施数据平面**（Sidecar 或 Ambient） | 适用：多语言、服务多、治理规则复杂的场景；代价：**资源开销 + 一跳延迟 + 运维复杂度**，中小规模常「不值」 |
| **Serverless** | 事件驱动、按需伸缩到 0、按用量计费（FaaS + BaaS） | 适用：突发/低频/无状态/短任务；不适用：长时、有状态、低延迟确定性任务 |
| **GitOps** | 以 **Git 为唯一事实源**，声明式描述期望态，由 Agent **拉取并自动收敛**（ArgoCD / Flux） | 适用：环境一致性、可审计、可回滚；代价：密钥管理、仓库权限是新的风险点 |
| **Operator** | **CRD + 控制器**，把运维专家的知识编码成软件，实现中间件的自愈、备份、扩缩容 | 适用：有状态中间件；代价：Operator 质量参差，升级需谨慎 |
| **Sidecar** | 与主容器同 Pod 的辅助容器，代办网络/日志/代理等横切能力 | 适用：无侵入增强；代价：每 Pod 一份资源开销 |
| **不可变基础设施** | 不原地改机器，**重建替换**；镜像按 digest 固定，禁止 `latest` | 适用：杜绝「配置漂移」；代价：需配套镜像仓库与流水线 |
| **渐进式交付** | 蓝绿 / 金丝雀 / 灰度，配合指标自动分析并回滚（Argo Rollouts / Flagger） | 适用：高风险发布；代价：需完整可观测指标做「自动判断」的依据 |
| **声明式 API** | 只描述期望状态，控制器负责收敛（Reconciliation Loop） | 云原生的**方法论内核** |
| **SRE / 错误预算** | 用 SLI/SLO 量化可靠性，错误预算决定「能否继续发布」 | 适用：稳定性与迭代速度的平衡器 |
| **混沌工程** | 主动注入故障（Chaos Mesh / Litmus）验证系统韧性 | 适用：常态化的故障演练；代价：需先在预发环境跑通 |

### 1.7 云原生的边界：哪些工作负载「不该」云原生化

> **这一节比「用哪些组件」更重要**——云原生不是信仰，是工具。以下负载要**谨慎或例外处理**：

| 负载类型 | 为什么不照搬云原生 | 处理方式 |
|---------|-------------------|---------|
| **低延迟内存撮合（本项目 C 引擎）** | 要求**纳秒级确定性时延**：CPU 绑核、HugePages、NUMA 亲和、无 GC；容器网络多一层 NAT、弹性调度会带来抖动 | **专用裸金属节点池 + 有限容器化**，**绝不参与弹性伸缩**（详见 §5.1） |
| 有状态数据库 | 数据在本地盘、扩容涉及数据重分布 | **StatefulSet + Operator**，或直接用托管服务 |
| 强依赖特定硬件的负载 | GPU / FPGA / 加密卡 | 设备插件 + 节点亲和 + 污点隔离 |
| 极低频的内部工具 | 云原生化收益 < 容器与流水线成本 | 保持虚拟机/脚本直装 |

## 2. 现状：已经「容器化」，尚未「云原生」

### 2.1 现状架构

```
┌──────────────────────────────────────────────────────────────┐
│  外部系统 9+：5 家银行 · 物流 WMS · 税务 · 电子签章 …          │
└──────────────────────────────────────────────────────────────┘
                    ↑↓ 统一外联网关适配层
┌──────────────────────────────────────────────────────────────┐
│  midservice 自研网关 × N（Java Web）+ midmon 监控              │
│  三端接入：外部大屏 / 普通客户 / 机构客户                       │
└──────────────────────────────────────────────────────────────┘
                    ↑↓ HTTP + traceId
┌──────────────────────────────────────────────────────────────┐
│  Java 微服务业务中台（12+ 服务）                               │
│  交易 · 支付结算 · 合同履约 · 仓单 · 物流 · 税务 · 供应链金融   │
└──────────────────────────────────────────────────────────────┘
                    ↑↓ Hessian over HTTP（同步）/ Kafka（异步）
┌──────────────────────────────────────────────────────────────┐
│  自研 DS 数据中心（防腐层）：协议转换 · 可靠性 · 可观测性       │
└──────────────────────────────────────────────────────────────┘
                    ↑↓ TCP Socket 自定义二进制协议
┌──────────────────────────────────────────────────────────────┐
│  C 语言内存撮合引擎（单线程 · 内存撮合 · 低延迟）               │
│  挂牌 · 竞价 · 询价 · 招标 · 基差点价                          │
└──────────────────────────────────────────────────────────────┘
   基础设施：Docker 镜像交付 · 公司自建 K8S 集群 · GitLab CI/CD
   数据/中间件：MySQL · Redis/Redisson · Kafka · ES · MinIO · Nacos
```

### 2.2 云原生成熟度自评（0–5 级）

| 维度 | 现状级别 | 说明 |
|------|:-------:|------|
| 容器化 | **3** | 镜像化交付 + K8s Deployment/Service/探针/滚动更新；**无镜像 digest 固化、无供应链扫描** |
| 编排与命名空间 | **2** | 有集群与 Namespace，但**无 NetworkPolicy 隔离、无资源配额精细化** |
| 持续交付 | **2** | GitLab CI/CD 流水线可用；**手动灰度 + 快速回滚**，无 GitOps、无自动金丝雀 |
| 弹性伸缩 | **1** | **手动扩缩容 + 压测保障**；无 HPA/VPA/KEDA |
| 可观测性 | **2** | Prometheus/Grafana + ELK + midmon + C 侧自采；**链路割裂、无统一端到端 Trace** |
| 配置与密钥 | **2** | Nacos 配置中心已用；**Secret 管理薄弱（存在明文/半明文风险）** |
| 安全与合规 | **2** | 等保整改项已落网关（见 `11`）；**无镜像扫描/SBOM/策略准入** |
| 数据层自动化 | **1** | MySQL/Redis/Kafka 自建自运维；**无 Operator，故障恢复靠人** |
| 容灾与多活 | **1** | 单集群 + 备份恢复；**无同城/异地多活** |

> **一句话结论**：**容器化到位、交付及格、弹性与治理缺位**——下一步不是「推倒重来」，而是**补齐云原生的「声明式 + 自动化 + 可观测」三条腿**。

### 2.3 六个核心痛点（改造要解决的问题）

| # | 痛点 | 现象 | 归属维度 |
|---|------|------|---------|
| ① | **异构边界发版互锁** | C 撮合、DS、Java 中台三方联调/发版靠人力协同，任一侧变更都牵动全局 | 交付 + 边界 |
| ② | **弹性靠人工** | 冬储高峰靠人工扩容 + 压测；无自动扩缩，容量决策滞后 | 弹性 |
| ③ | **可观测割裂** | 网关 midmon、Java 侧 Prometheus、C 侧自采日志**各自为政**，一个订单跨四层却无端到端 Trace | 可观测 |
| ④ | **发布治理弱** | 手动灰度、回滚靠人；多租户共用集群，一次发布可能波及全部客户 | 交付 |
| ⑤ | **中间件自建运维重** | MySQL/Redis/Kafka 主从切换、扩容、备份均为人工，**故障恢复慢** | 数据层 |
| ⑥ | **安全纵深不足** | 镜像未扫描、Secret 管理弱、Pod 间无网络策略，等保/信创要求尚需加固 | 安全合规 |

# 第三部分 · 目标架构（To-Be）

## 3. 目标架构：三层声明式 + 一条端到端可观测链路

### 3.1 目标架构图

```
┌───────────────────────────────────────────────────────────────────┐
│  边缘层：CDN / WAF / 高防（通用方案，非本人主导）                    │
└───────────────────────────────────────────────────────────────────┘
                    ↓ HTTPS
┌───────────────────────────────────────────────────────────────────┐
│  K8s 集群 · 入口层                                                  │
│  Ingress / Gateway API（Envoy Gateway）—— 纯 L7 流量入口             │
│  midservice 自研网关 Deployment + HPA（业务耦合治理：租户/权限/限流） │
│  midmon（观察者，独立部署，不参与放行）                              │
└───────────────────────────────────────────────────────────────────┘
                    ↓ HTTP + traceId（OTel 贯穿全程）
┌───────────────────────────────────────────────────────────────────┐
│  K8s 集群 · 业务池（通用节点池）                                     │
│  Java 业务中台 12+ 微服务：Deployment + HPA + PDB + 三探针            │
│  Namespace 按「环境 + 租户域」隔离 + NetworkPolicy                    │
│  ┌─ 无状态化：会话外置 Redis；日志 stdout 化                        │
│  └─ 优雅停机：preStop + terminationGracePeriod                       │
└───────────────────────────────────────────────────────────────────┘
                    ↓ Hessian over HTTP / Kafka（Strimzi）
┌───────────────────────────────────────────────────────────────────┐
│  K8s 集群 · 交换池                                                   │
│  DS 数据中心：Deployment（无状态转发）+ 待发送表持久化（StatefulSet） │
└───────────────────────────────────────────────────────────────────┘
                    ↓ TCP Socket（无人化抖动预算）
┌───────────────────────────────────────────────────────────────────┐
│  裸金属 / 专用节点池（内存计算池，打污点，不参与弹性）               │
│  C 撮合引擎：CPU Manager static + 绑核 + HugePages + NUMA 亲和       │
└───────────────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────────────────────────┐
│  数据与中间件层（Operator 化 / 或托管）                              │
│  MySQL Operator · Redis Operator · Strimzi(Kafka) · Nacos · MinIO   │
└───────────────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────────────────────────┐
│  平台能力层                                                          │
│  可观测：Prometheus + Grafana + Loki + OTel Collector + SkyWalking   │
│  交付：GitLab CI → Harbor → ArgoCD(GitOps) → Argo Rollouts(金丝雀)   │
│  安全：Trivy/SBOM + Kyverno/OPA + External Secrets/Vault + cert-mgr  │
└───────────────────────────────────────────────────────────────────┘
```

### 3.2 模块划分与职责边界

| 层 | 模块 | 云原生形态 | 弹性策略 | 边界纪律 |
|----|------|-----------|---------|---------|
| 入口 | Ingress/Gateway API | Deployment | 跟随网关 | **只做 L7 入口**，不抢 midservice 的业务治理 |
| 入口 | midservice 自研网关 | Deployment + HPA | CPU/QPS 双指标 | **保留自研**（业务耦合治理，见 `11`） |
| 业务 | Java 中台 12+ 服务 | Deployment + HPA + PDB | CPU/QPS/Kafka lag | 无状态化、日志 stdout 化 |
| 交换 | DS 数据中心 | Deployment + StatefulSet | 低弹性 | 不动协议内核（见 `15`） |
| 撮合 | C 撮合引擎 | 裸金属节点池 | **不弹性** | 绑核 + HugePages，见 §5.1 |
| 数据 | MySQL/Redis/Kafka/Nacos | Operator / 托管 | 存储扩容为主 | 有状态用 StatefulSet |
| 平台 | 可观测 / 交付 / 安全 | 集群级组件 | — | 平台能力与业务解耦 |

### 3.3 数据流（含改造后新增的观测面）

```
用户请求
  → [Ingress/Gateway]  ← ① L7 入口日志
  → [midservice 网关]   ← ② 鉴权/限流/契约校验（midmon 采集）
    └─ 注入 traceId（OTel 起点）
  → [Java 中台服务]     ← ③ 业务编排（Prometheus 指标 + OTel Span）
    ├─ 同步 → [DS] → [C 撮合]   ← ④⑤ 跨语言 Span 透传（改造重点）
    ├─ 异步 → [Kafka 事件]      ← 消费 lag 作为 KEDA 扩容信号
    └─ 落库 → MySQL → Canal → ES（搜索/缓存刷新）
  → 全程 traceId 汇聚到 SkyWalking / Jaeger，指标汇聚到 Prometheus
```

> **改造后新增的能力**：一条订单从「网关 → Java → DS → C」**四层跨语言的端到端链路**可被一个 traceId 串起——这是痛点③的根治，也是痛点①（异构边界发版互锁）的**观测基础**。C 侧需配合输出结构化日志并透传 traceId（见 `02` §3.1 的「可观测层」）。

### 3.4 部署方式与集群规划

| 规划项 | 方案 |
|--------|------|
| 集群形态 | **自建 K8s（信创环境）+ 可选公有云托管混合**；起步单集群多节点池 |
| 节点池划分 | `通用池`（业务微服务）/ `中间件池`（数据组件）/ `内存计算池`（C 撮合，裸金属，打污点） |
| 命名空间 | `platform`（可观测/入口）、`dev`/`test`/`prod`、`prod-tenant-a`/`prod-tenant-b`（大客户隔离） |
| 隔离手段 | Namespace + ResourceQuota + LimitRange + **NetworkPolicy** |
| 存储 | 动态 CSI（块存储给数据库）/ MinIO（对象）；数据库优先本地 SSD |
| 版本策略 | K8s 版本与 CNI/CSI 版本对齐维护窗口，**升级先在预发集群演练** |

# 第四部分 · 改造路线图（P1 → P4）

> **编排原则**：**先立标准，再上能力；先做可观测，再做自动化**。理由——没有统一可观测，「自动金丝雀」「自动扩缩容」都失去判断依据（渐进式交付的 analysis 模板要消费指标）。**顺序错了会返工。**

## 4.1 P1 · 标准化与容器化深化（打地基）

| 项 | 内容 |
|----|------|
| **目标** | 让「一套流水线能可复现地部署任意服务到任意环境」 |
| **关键动作** | ① 统一 Dockerfile 多阶段构建与基础镜像（JRE 基础镜像统一、非 root 运行）；② **镜像 tag 用 Git commit + digest，禁用 `latest`**；③ 资源 requests/limits + LimitRange/ResourceQuota 标准化；④ 三探针（startup/liveness/readiness）标准化；⑤ 配置外置到 Nacos/ConfigMap，**Secret 迁出代码**；⑥ 日志统一到 stdout，禁止应用自己切分文件；⑦ **优雅停机（preStop + 信号处理）**；⑧ Namespace/标签规范（app/version/tenant） |
| **验收标准** | 同一份代码经流水线可部署到 test；镜像可复现；滚动更新无 5xx 毛刺；无明文密钥进代码库 |
| **风险** | 存量服务改造工作量分散、易遗漏 → 用**规范 + 模板 + CI 卡点**（不合规不放行） |
| **成本** | 以人力为主，无新增组件成本 |
| **替代方案** | 若不改存量，仅对新建服务立规范——**会导致新旧两套标准并存**，不建议 |

## 4.2 P2 · 统一可观测 + GitOps（立「事实源」）

| 项 | 内容 |
|----|------|
| **目标** | 端到端可观测 + 环境一致性（Git 为唯一事实源） |
| **关键动作** | ① 引入 **OpenTelemetry Collector**，Java 侧 OTel Java Agent（零侵入）+ 网关 traceId 注入，落 **SkyWalking/Jaeger**；② 日志统一 **Loki/EFK**，与 trace 关联；③ 指标统一 **Prometheus + Grafana**，覆盖网关/Java/DS/C 四层（C 侧指标经 exporter 接入）；④ **Helm/Kustomize** 打包应用；⑤ **ArgoCD** 落地 GitOps，dev/test 自动同步，prod 人工审批 |
| **选型对比** | 可观测「自建 Prom+Grafana+Loki+OTel」vs「托管 SaaS」：自建可控、成本取决于人力，托管省运维、有数据出境顾虑 |
| **验收标准** | 一个订单可用一个 traceId 串起网关→Java→DS→C；一次 Git 提交自动同步到 test；prod 变更留痕可回滚 |
| **风险** | 采集体量与存储成本；OTel Agent 对低延迟服务的影响需评估 |
| **替代方案** | 只上 SkyWalking 不做 OTel 统一——**多语言（C 侧）接入会受阻** |

## 4.3 P3 · 弹性伸缩 + 渐进式交付（上自动化）

| 项 | 内容 |
|----|------|
| **目标** | 高峰自动扩容；发布自动化灰度与回滚 |
| **关键动作** | ① **HPA**（CPU/QPS/自定义指标）+ **KEDA**（以 Kafka 消费 lag、定时冬储窗口为信号）；② VPA 或资源画像辅助调参；③ **Argo Rollouts** 金丝雀 + analysis 模板（错误率/延迟达标才晋级，否则自动回滚）；④ 多租户发布隔离（大客户独立 Namespace，先小客户灰度）；⑤ **PDB** 保证滚动更新时不中断 |
| **验收标准** | 冬储高峰核心链路自动扩容、指标达标；一次发布灰度失败可自动回滚；滚动更新期间无用户可感知中断 |
| **风险** | 扩容把压力传导到 DB → 需与 `生产问题排查/11`（网关扩容打穿 DB）的**限流与连接池防线**配套；**弹性 ≠ 无脑扩容** |
| **成本** | 需预留弹性资源水位；自动回滚依赖完善的可观测（P2 已建） |
| **替代方案** | 定时（Cron）扩缩容 + 手动灰度——成本最低，但应对不了突发；可作为 P3 的中间态 |

## 4.4 P4 · 纵深演进（可选、按需）

| 方向 | 内容 | 前置条件 |
|------|------|---------|
| **数据层 Operator 化** | MySQL/Redis Operator、Strimzi（Kafka）：自愈、备份、扩缩自动化 | P1/P2 稳定 |
| **多活/单元化** | 从同城双活起步，按租户/地域做单元化路由（网关承载路由） | 需解决跨单元数据一致性 |
| **Service Mesh** | 仅当**东西向治理规则复杂 + 多语言服务多**时才上 Istio/Linkerd | 需评估延迟与资源开销，**中小规模通常不值** |
| **非核心 Serverless 化** | 对账、报表导出、通知等**突发/低频/可延迟**任务用 Knative/函数计算 | P1 无状态化完成 |
| **混沌工程** | Chaos Mesh 常态化故障演练（先在预发） | P2 可观测完备 |
| **成本治理** | 自建 vs 云托管 ROI 复盘、资源画像与规格优化 | 持续 |

# 第五部分 · 关键专题

## 5.1 C 撮合引擎的容器化适配（本文最需谨慎的一节）

> **背景**：C 撮合引擎是资金链路的「心脏」，要求**纳秒级确定性时延**（见 `02` §2.1）。**把它简单塞进容器 + 弹性伸缩，是绝对不能犯的错。**

| 方案 | 做法 | 适用 | 优点 | 缺点 / 风险 | 成本 |
|------|------|------|------|------------|------|
| **A. 裸金属 + K8s 混合调度（推荐）** | C 引擎跑在**专用裸金属节点**，打污点；仅 C 相关 Pod 带 toleration 调度；启用 CPU Manager `static` 策略绑核 + HugePages + NUMA 亲和；**不进 HPA** | 延迟极敏感、已有 K8s 底座 | 保留确定性时延；仍享受统一部署/观测/网段 | 需裸金属资源；节点调度策略复杂 | 中高 |
| **B. 完全容器化（不推荐用于撮合）** | C 引擎做成镜像跑普通节点池 | 中小撮合、时延要求宽松 | 部署统一、最简单 | 容器网络多一跳、CPU 不独占、**弹性调度带来抖动** | 低但风险高 |
| **C. 保持物理机直装** | 完全不进 K8s，独立运维 | 最低风险、无 K8s 意愿 | 时延最稳 | 无法复用统一交付与观测，运维孤岛 | 低 |

**决策建议**：**选 A**——C 引擎「借 K8s 的布网与观测，不借 K8s 的弹性」。要落实的三件套：

1. **CPU 独占**：CPU Manager `static` 策略 + `guaranteed` QoS（requests=limits），把核绑给撮合线程；
2. **大页内存**：HugePages 预分配，减少 TLB miss；
3. **禁弹性 + 保副本**：C 引擎用**固定副本**（或热备），节点故障切换靠**主备/热备机制**（见 `13` C 核心一致性设计），而非 K8s 自动重建。

> **反模式警示**：给 C 引擎配 HPA = 用「抖动」换「弹性」，在资金链路里这笔账**必亏**。

## 5.2 多租户隔离的云原生化

| 隔离层级 | 手段 | 强度 | 备注 |
|---------|------|:----:|------|
| 命名空间 | Namespace + RBAC | 中 | 逻辑隔离，起步够用 |
| 资源配额 | ResourceQuota + LimitRange | 中 | 防「嘈杂邻居」抢占 |
| 网络隔离 | **NetworkPolicy**（Calico/Cilium） | 强 | 阻断跨租户 Pod 直连 |
| 数据隔离 | 独立库 / schema + 应用层租户路由 | 强 | 大客户独立库 |
| 强隔离 | 虚拟集群（vCluster）/ 独立集群 | 最强 | 成本最高，仅超大户 |

> **与网关呼应**：租户维度的路由、限流配额本就是 midservice 的强项（见 `11` §1.3）；云原生侧要做的是**把租户边界再下沉一层到网络与资源**，形成「网关规则 + Namespace 配额 + NetworkPolicy」的三重隔离。

## 5.3 云原生安全与合规（等保 / 信创）

| 环节 | 手段 |
|------|------|
| **供应链安全** | 镜像构建即扫描（Trivy）、输出 **SBOM**、基础镜像最小化、非 root 运行、只读根文件系统 |
| **密钥管理** | **禁止明文 Secret**；用 Sealed Secrets / External Secrets + Vault 注入 |
| **准入控制** | **Kyverno/OPA Gatekeeper** 策略：禁止 `latest`、强制资源配额、强制标签、禁特权容器 |
| **运行时安全** | Falco 检测异常行为；NetworkPolicy 收敛东西向流量 |
| **合规对齐** | 等保 2.0 的审计留痕、分区分域、双因子（网关侧已落，见 `11`）+ 信创环境的组件适配层 |
| **证书治理** | cert-manager 自动化证书轮换 |

## 5.4 数据层：自建 Operator 化 vs 云托管

| 维度 | 自建 + Operator | 云托管（RDS/Redis/Kafka 云服务） |
|------|----------------|-------------------------------|
| 可控性 | 高（版本、参数、网络全控） | 中（受服务能力约束） |
| 运维成本 | 中（Operator 降低但非归零） | 低 |
| 数据合规 | 满足「数据不出内网 / 信创」 | 需评估数据出境与合规 |
| 成本结构 | 硬件 + 人力 | 按量/包年费用 |
| **本平台判断** | **信创与商业秘密要求下，核心库倾向自建 + Operator**；非核心组件可评估托管 | — |

## 5.5 成本治理

| 项 | 做法 |
|----|------|
| 资源画像 | 用 VPA 推荐值 / 历史指标反推真实 requests，消除「拍脑袋申请」 |
| 弹性水位 | 预留缓冲而非长期满载；峰谷用 KEDA 定时伸缩 |
| 组件瘦身 | 每个新增组件都要回答「解决什么独有问题」，避免 CNCF「采购上瘾」 |
| 自建 vs 托管 | 按「核心度 × 数据敏感度 × 团队人力」三维决策 |

# 第六部分 · 风险 / 成本 / 替代方案汇总

| 改造项 | 收益 | 主要成本 | 核心风险 | 替代方案 |
|--------|------|---------|---------|---------|
| P1 标准化 | 交付可复现、隐患前置 | 人力 | 存量改造遗漏 | 仅新服务立规（不推荐） |
| P2 可观测 + GitOps | 端到端定位、环境一致 | 采集体量 + Agent 开销 | 低延迟服务受 Agent 影响 | 仅 SkyWalking（C 侧难接） |
| P3 弹性 + 金丝雀 | 高峰无忧、发布安全 | 资源水位 + 观测量 | 扩容打穿 DB | 定时扩缩容 + 手动灰度 |
| P4 Operator 化 | 中间件自愈、降运维 | Operator 学习与升级 | Operator 质量风险 | 继续自建人工运维 |
| Service Mesh | 治理下沉、多语言 | 延迟 + 资源 + 复杂度 | 中小规模收益为负 | 保持 SDK 治理（Nacos/Sentinel） |
| C 引擎混合调度 | 保时延 + 复用底座 | 裸金属资源 | 调度策略复杂度 | 物理机直装 |

> **总体判断**：本项目**应当推进 P1–P3**（收益明确、风险可控）；**P4 按需**——尤其 **Service Mesh 与本项目的 ROI 需谨慎评估**，在「12+ 服务、Java 为主、已有自研网关与 Nacos/Sentinel」的前提下，Mesh 的边际收益有限。

# 第七部分 · 与面试叙事的衔接（真实 vs 规划的话术边界）

> 本库纪律（见 `../00-资料库总览.md`）：**不把规划包装成战绩，也不把行业知识说成大厂标准答案**。本文内容在面试中的安全表述：

| 话题 | ✅ 可以这样说（真实） | ⚠️ 不可这样说（越界） |
|------|---------------------|---------------------|
| 容器化 | 「我负责 Java 微服务的镜像构建与交付、K8s 部署配置与滚动更新」 | 「我主导了云原生改造 / 落地了 Service Mesh」 |
| 弹性 | 「我用压测 + 人工扩容保障过连续两季冬储高峰的容量」 | 「我做了 HPA 自动弹性伸缩」 |
| 交付 | 「我用 GitLab CI/CD 落地了多模块流水线、手动灰度与快速回滚」 | 「我落地了 GitOps + Argo Rollouts 自动金丝雀」 |
| 云原生概念 | 「云原生的四大支柱是…；本项目下一步规划是…」（**说明这是规划**） | 「我们已经完成了云原生改造」 |
| C 引擎容器化 | 「我判断 C 撮合**不应**参与弹性伸缩，方案是裸金属 + K8s 混合调度」（**这是方案判断，可讲**） | 「我把 C 引擎容器化并弹性扩容了」 |

> **加分点**：能讲清「**为什么 C 引擎不适合云原生弹性**」「**为什么 12 个服务的规模上 Service Mesh 不划算**」这两条**判断**，比堆砌组件名更能体现架构取舍能力——**这正是本文的写作目的**。
