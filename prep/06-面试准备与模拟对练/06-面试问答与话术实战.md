**第四层，接入层加外部生态。** PC端、移动端、机构客户三端接入，同时对接9大外部系统——银行、短信、证书、物流、CTRM、开票、企查查、供应链金融等。

## 三、3 分钟版（CTO/VP 面用）

> 这个版本适合对方想深入了解你全貌的场景。可以分段讲，配合对方点头反馈调整节奏。

我叫XXX，XX公司技术经理，B2B大宗贸易线上交易平台技术负责人。

先说说我们平台是做什么的。大宗贸易听起来离互联网很远，但实际上它是一套完整的线上交易市场——钢铁、煤炭、化工等大宗商品，买卖双方在我们的平台上挂单、询价、撮合、签约、结算、物流交付。这个业务链条比普通电商复杂得多，因为每笔交易金额大、履约周期长、涉及的外部系统多。

所以我们系统的架构挑战是双重的：**交易核心要快，业务逻辑要灵活**。

快速过一下我们的架构全景——

**第一层，撮合引擎。** 我直接说结论：用C语言，单线程，纯内存撮合，异步写库。为什么不用Java？因为大宗交易的撮合逻辑是CPU密集型的——买卖盘口的匹配、价格优先时间优先的排序、复杂的撮合规则计算——这些在Java里会因为GC产生不可预测的停顿。对交易系统来说，每一次停顿都可能导致不公平。C语言的确定性执行是我们选择它的核心原因。

**第二层，DS数据服务中心。** 这是我个人最看重的一层，也是我在面试中最愿意展开讲的部分。它本质上是一个**防腐层（Anti-Corruption Layer）**——C引擎对外暴露的是TCP+自定义二进制协议，对Java团队来说就是黑盒。DS的职责就是把这种异构通信的脏活封装起来：下层解析二进制报文，上层转换成标准的Java服务接口，中间还要处理连接管理、心跳保活、协议版本兼容。有了DS之后，所有上层Java服务对C引擎的访问就像调用本地方法一样简单。**这一层的设计让异构系统之间的边界变得可控。**

**第三层，业务中台。** Java微服务体系，包括交易核心服务、管理中心、以及12+垂直业务服务。服务间通过Hessian做RPC调用。我们用Canal监听MySQL binlog，把变更同步到独立的缓存服务（封装Redis），专门加速Web端的查询访问。

**第四层，接入层加外部生态。** 大屏/PC/移动端三端接入，同时对接9大外部系统——银行支付、短信通知、电子签章、物流追踪、CTRM风控、开票系统、企查查企业验证、供应链金融等等。

（稍停，转入管理叙事）

再聊聊我在这个体系中的角色。我管一支XX人的Java团队，直接负责业务中台层和DS数据服务层。虽然我不写C代码，**但我能通过DS这层桥接管住异构通信的全链路**，这意味着整个交易核心链路都在我的掌控范围内。

我个人深度参与的模块四个方面：

**第一，交易模式。** 我们不是只有简单的买和卖。大宗贸易有挂牌交易、竞价拍卖、招标采购、基差点价等多种模式，每种模式的撮合规则、定价逻辑、结算流程都不一样。我主导了交易模式的可配置化设计，通过规则引擎把业务差异抽象成可组合的规则项，避免了"每增加一种交易模式就要开发一套新代码"的困境。

**第二，履约保证体系。** 大宗交易的履约风险比B2C大得多。我们设计了保证金阶梯、信用额度动态计算、风控预警触发等多层保障机制，确保买卖双方在交易链条上的每个环节都有安全保障。

**第三，数据服务。** 大宗贸易的数据维度非常丰富——价格指数、成交统计、库存变化、物流时效——这些数据对平台运营和客户决策都很有价值。我主导了数据中心从"被动查询"到"主动分析"的演进。

**第四，生态对接。** 10+外部系统的对接，涉及银行、物流、税务、征信等多种异构协议。我建立了统一的网关适配层和对接规范，把对接一个新系统的周期从两周压缩到三天。

## 四、5 分钟版（深度技术面用）

我来讲一下我参与的这个大宗商品 B2B 电商平台项目。

**背景**：大宗商品行业（钢材、化工、农产品等）传统交易都是线下的，存在三个核心痛点：一是客户不信任平台，不愿资金在平台过夜，担心平台挪用资金；二是仓单造假频发，同一批货开多张仓单骗贷；三是交易模式复杂，远比 B2C 电商复杂，涉及挂牌、竞价、点价、预售等七种模式。

**我的角色**：后端架构+核心模块开发，主要负责交易引擎、资金存管、仓单可信链三块。

**技术架构**：整体微服务架构，8 个核心模块。业务中台是 Java 微服务（Spring Cloud 自研网关 midservice/midmon），前端 Vue3，消息中间件 Kafka，缓存 Redis，搜索引擎 ES；交易撮合是 C 语言单线程内存引擎，通过 DS 数据中心（Hessian + Socket）与 Java 层桥接。区块链用 Hyperledger Fabric，物联网网关用 MQTT+边缘计算。

**核心难点一：资金存管一致性**。我们对接了 5 家银行，资金存在银行存管账户，平台只有指令权。难点是平台交易状态和银行资金状态的最终一致性——银行接口可能超时、重试、异步回调。我的方案是：每笔资金操作先写本地消息表（和业务事务同库），异步投递银行，超时主动查询，T+1 对账兜底。幂等键设计为"会员ID+订单号+操作类型+日期"，银行侧也用 reqId 去重。多银行适配用适配器模式。

**核心难点二：可插拔交易引擎**。7 种交易模式如果每个写一套，维护成本爆炸。我用策略模式+模板方法定义交易流程骨架（挂单→撮合→成交→结算→交收），每种模式实现自己的策略类。风控规则用规则引擎外部化。新模式 2 天上线，不影响现有模式。

**核心难点三：仓单可信链**。三层架构——物联网层验证货物真实存在（视频+RFID+称重交叉验证），WMS 层管理仓单生命周期状态机，区块链层做不可篡改存证。跨层一致性用事件溯源+Saga，每步有补偿动作。

**成果**：平台服务数百家客户，撮合延迟 <10ms，风控延迟 <5ms，资金对账差异率从 8% 降到 0.1% 以下。

这个项目和我在 Agent Harness 上的经验高度互补——Agent 的多步骤编排本质上也是一种 Saga，我在两边互相借鉴了很多设计思路。

## 二、常见追问及应答话术

### Q1: "你们为什么用C语言写撮合引擎，不用Go/Rust？"

> 这是一个好问题，我们当时评估过几个选项。Go的GC虽然比Java轻，但仍然是STW的，C的确定性执行是交易公平性的刚需。Rust在安全性和性能上确实优秀，但当时团队没有Rust储备，而且C的生态系统在金融交易领域非常成熟。权衡下来，C是最务实的选择。另外我补充一点——虽然引擎是C写的，但它只做撮合这一件事，代码量不大，维护成本可控。

### Q2: "DS这层不会成为性能瓶颈吗？"

> 不会，因为DS主要做的是协议转换和连接管理，不涉及业务逻辑计算。TCP二进制报文的解析是纯IO操作，Java NIO完全可以胜任。真正的性能瓶颈在撮合引擎内部，而那部分我们放在了C层。DS的延迟一般在微秒到毫秒级别，对交易体验没有影响。

### Q3: "你说你管Java团队，那C层的代码你怎么管？"

> 我不管C代码本身，但我管C层和Java层的接口协议。DS数据服务中心就是我的抓手——C引擎对外的二进制报文格式、TCP连接的握手与保活、协议的版本兼容，这些都在DS层体现。我能review DS的代码，能定义协议规范，就等于管住了异构通信的全链路。技术上这叫防腐层，管理上这叫边界治理。

### Q4: "你提到了12+微服务，服务治理怎么做的？"

> 我们用的是Hessian做RPC，相对传统但不复杂。服务发现和配置管理通过自研的midservice网关层统一管理，监控通过midmon。因为我们不是互联网级别的高并发场景，大宗交易的请求量相对稳定，所以没有上Spring Cloud或Dubbo全家桶，选择了更轻量的方案。

> 下方"3 道系统设计题"为本文件独有内容，不在权威版本范围内。

## 难点一：银行资金存管的资金流一致性

- **结论**：资金不过平台账户——客户在银行开立存管子账户，平台只有交易指令权，没有资金支配权。
- **链路**：平台下单 → 带幂等键 `reqId` 发扣款指令 → 银行买方子账户扣款划入卖方子账户 → 异步回调更新订单。
- **关键数字**：超时后 3 秒带同reqId 重试 → 再 `queryByReqId` 主动查询 → 仍不确定则标记"资金状态不确定"进人工对账，T+1 用银行对账文件兜底（差异率从行业 8% 降到 0.1% 以下）。
- **追问方向**：银行接口超时怎么确认扣没扣？幂等键怎么设计、银行不支持去重怎么办？5 家银行接口差异怎么管理（适配器模式 + 配置中心）？

## 难点二：区块链 + 物联网 + WMS 三层仓单可信链

- **结论**：三层各解决一层信任——物联网证明"货在"，WMS 证明"仓单与货对应"，区块链证明"数据不可篡改"；单做任何一层都不成立。
- **关键数字**：视频流不上云（8 路 1080P 约 2TB/天），边缘网关只上传 AI 事件截图 + 结构化数据，带宽成本降 95% 以上。
- **一致性**：Saga 处理跨层，上链异步不阻塞 WMS 主流程；仓单设"待上链"中间态，上链失败仓单不可交易/融资。
- **追问方向**：三层数据不一致（WMS 注册成功但上链失败）怎么办？仓单拆分（1000 吨拆 5 张 200 吨分别融资）链上链下怎么处理？

## 难点三：七种交易模式的可插拔引擎

- **结论**：策略模式 + 模板方法组合——模板方法定流程骨架（挂单→撮合→成交→结算→交收），策略类只实现差异步骤，符合开闭原则。
- **风控**：自研轻量规则 DSL（`mode` + `rules` + `condition`/`action`），规则存DB 热加载，不用 Drools。
- **关键数字**：不涉及新外部系统对接时，新增一种交易模式约 2 天（Day1 实现 TradeMode 5 个方法 + 风控规则配置；Day2 联调上线）；涉及新外部系统再加 2-3 天。
- **追问方向**：为什么不用 if-else？风控规则硬编码还是配置化？新增模式的成本？

## 难点四：点价交易的期现实时联动

- **结论**：行情快照 + 版本号保证摘牌价格锁定——行情更新即递增 version，摘牌请求携带 version，版本不一致则拒绝并提示"价格已变动"。
- **关键数字**：期交所 → 行情服务商 → 行情网关 → 交易引擎，端到端延迟 <10ms；高频 tick 做背压控制，丢中间 tick 只保留最新价。
- **白盘夜盘**：多行情源连接，新连接 ready 后再断旧连接（优雅切换）；切换窗口期禁止摘牌（风控规则）。
- **追问方向**：行情延迟多少？摘牌价格错位怎么防？夜盘切换断连怎么处理？

## 难点五：全流程 8 模块数据一致性

- **结论**：不用 Seata AT（8 服务全局事务锁资源性能不可接受，且管不了银行外部接口），用编排式 Saga——本地事务 + 逆序补偿 + 最终一致。
- **关键设计**：Saga 协调器维护执行状态，宕机可从实例表恢复继续补偿；补偿动作本身必须幂等。
- **事件顺序**：Kafka 按交易 ID 做 partition key保证单交易内有序，跨交易并行；失败事件进死信队列不阻塞 partition。
- **状态查询**：CQRS——写库各服务本地库，读库聚合视图（Redis + ES），一次查询返回全链路 steps。
- **追问方向**：为什么不用 Seata？补偿顺序怎么保证？8 服务事件顺序怎么保证？全链路状态怎么查？

## 难点六：高并发撮合与流式风控

- **结论**：撮合纯内存，买卖盘红黑树（价格 + 时间优先），O(log N)；先写 WAL 再内存撮合，宕机可恢复；集合竞价按"最大成交量原则"批量撮合。
- **风控两层**：实时风控 <5ms（规则预编译成内存决策树）+ 深度风控异步（Flink 流式检测对敲、自买自卖）；实时风控故障熔断降级为"宽松模式"，绝不让风控故障中断交易。
- **峰值应对**：竞价截止前 5 分钟出价峰值可达日常 10-50 倍 → 引擎无状态 + K8s HPA 弹性扩容、Kafka 队列缓冲、集合竞价批量撮合、单会员出价频控（10 次/分钟）。
- **追问方向**：撮合数据结构怎么设计？风控凭什么 <5ms？竞价峰值怎么扛？

# 第四部分：3 道系统设计面试题

## 系统设计题一：设计一个大宗商品 B2B 资金存管系统

**题目**：假设你要设计一个对接多家银行的 B2B 交易资金存管系统，要求：
- 客户资金存在银行，平台不碰资金
- 支持冻结、解冻、划转、退款等操作
- 保证平台交易状态和银行资金状态最终一致
- 支持 T+1 对账

**考察点**：

| 维度 | 考察内容 |
|------|---------|
| 架构设计 | 适配器模式多银行对接、存管子账户体系 |
| 一致性 | 分布式事务方案、幂等设计、补偿机制 |
| 可靠性 | 超时处理、重试策略、对账兜底 |
| 可扩展性 | 新增银行如何扩展 |

**参考回答框架**：

1. **架构分层**：交易服务 → 资金服务 → 银行网关（适配器）→ 各银行接口
2. **子账户设计**：每个客户在每家银行有独立子账户，主账户是银行的汇总账户
3. **一致性方案**：本地消息表 + 异步投递 + 超时查询 + T+1 对账
4. **幂等设计**：reqId = 会员ID + 订单号 + 操作类型 + 日期
5. **对账流程**：拉银行对账文件 → 逐笔比对 → 差异处理 → 报告生成

## 系统设计题二：设计一个仓单可信链系统

**题目**：设计一个大宗商品仓单管理系统，要求：
- 保证仓单对应的货物真实存在
- 仓单不可伪造、不可重复质押
- 支持仓单的创建、拆分、合并、转让
- 支持金融机构基于仓单放款

**考察点**：

| 维度 | 考察内容 |
|------|---------|
| 多源数据融合 | 物联网+WMS+区块链三层架构 |
| 状态机设计 | 仓单生命周期状态流转 |
| 跨系统一致性 | Saga 跨层补偿 |
| 防篡改 | 区块链存证设计 |

**参考回答框架**：

1. **三层架构**：物联网（货物验证）→ WMS（仓单管理）→ 区块链（不可篡改存证）
2. **仓单状态机**：待注册→已注册→已上链→可交易→已质押→部分解押→已提货
3. **防重复质押**：质押时仓单状态锁定，链上标记，全网可查
4. **拆分合并**：原仓单作废+子仓单上链，链上记录溯源关系
5. **跨层一致性**：事件驱动 Saga，每步补偿

## 系统设计题三：设计一个多模式交易撮合引擎

**题目**：设计一个支持挂牌、竞价、点价三种交易模式的撮合引擎，要求：
- 三种模式可独立运营也可组合运营
- 点价模式需要实时期货行情联动
- 竞价模式支持集合竞价
- 风控实时拦截，延迟 <10ms

**考察点**：

| 维度 | 考察内容 |
|------|---------|
| 设计模式 | 策略+模板方法、开闭原则 |
| 实时性 | 行情接入、价格锁定原子性 |
| 性能 | 内存撮合、风控低延迟 |
| 高并发 | 峰值应对、限流降级 |

**参考回答框架**：

1. **引擎设计**：TradeMode 抽象接口 + 模板方法流程骨架 + 3 个策略实现类
2. **行情接入**：WebSocket 行情网关 + 背压控制 + 版本号锁价
3. **撮合引擎**：内存红黑树订单簿 + WAL 持久化 + 集合竞价算法
4. **风控引擎**：预编译规则决策树 + 熔断降级 + 异步深度风控
5. **峰值应对**：Kafka 队列缓冲 + K8s 弹性扩容 + 频率限流
