## 一、消息队列（RocketMQ / Kafka / RabbitMQ）

> ⚠️ **口径提示（重要）**：本节是**知识储备**，用于回答"各家 MQ 有什么区别、事务消息怎么实现"。
> 但**我们项目实际用的是 Kafka**，事务语义用 **outbox 本地消息表 + 消费幂等 + 定时扫表兜底**实现，不用 RocketMQ 半消息。
> 被追问"你们项目用的哪个"时，答案永远是：**Kafka**，理由是团队已有运维经验 + 高吞吐 + 多消费者组，详见 `../03-架构决策与问题排查/01-架构方法论与选型设计手册.md` 第 2.5 / 2.8 节。

**一句话定位**：异步化、解耦、削峰、事件驱动的事实标准。

**B2B 业务场景**
- 订单状态流转发事件（挂牌→摘牌→签约→付款→履约），下游结算/风控/数据服务异步消费。
- 日终对账文件生成（大数据量，削峰）。
- 生态对接异步回调（银行放款通知、仓储入库回执）。

**深度解析**
- **RocketMQ**：Java 生态、事务消息原生支持、低延迟、堆积能力强 → B2B 国内首选。事务消息 = 半消息 + 本地事务 + 回查，天然解决"本地写 DB 成功但发消息失败"的不一致。
- **Kafka**：高吞吐、持久化、流处理友好 → 日志/埋点/数仓 ingress；但事务消息弱、运维重。
- **RabbitMQ**：协议丰富(AMQP)、路由灵活、延迟低 → 中小规模、复杂路由；集群堆积与水平扩展弱于前两者。

**选型对比（面试必答）**

| 维度 | RocketMQ | Kafka | RabbitMQ |
|------|----------|-------|----------|
| 吞吐量 | 高 | 极高 | 中 |
| 事务消息 | ✅ 原生 | ⚠️ 弱 | ❌ |
| 堆积能力 | 极强 | 强 | 较弱 |
| 延迟 | 毫秒 | 毫秒~秒 | 微秒~毫秒 |
| B2B 适用 | ★★★★★ | ★★★（数仓） | ★★★（路由复杂小场景） |

**高频追问**
- Q：消息重复/丢失怎么办？→ A：生产者确认 + 消费者幂等（唯一键/状态机）+ 死信队列兜底。
- Q：如何保证顺序？→ A：同一业务键（如订单号）哈希到同一队列，单队列有序。
- Q：和你模块的连接？→ 交易状态机每步发领域事件，履约保证流程靠事件驱动推进，生态对接靠异步回调削峰。

## 二、Redis（缓存 / 分布式锁 / 计数器 / 限流）

**一句话定位**：内存数据结构存储，B2B 高并发的"减压阀"。

**数据结构业务映射（你曾薄弱，重点背）**

| 结构 | B2B 场景 | 为什么用它 |
|------|----------|-----------|
| String | 库存余量、验证码、限流计数 | 原子 incr/decr，单值高性能 |
| Hash | 商品/挂牌详情、用户画像字段 | 部分更新，省内存 |
| List | 询价队列、操作日志流 | 双向队列，LPUSH/RPOP |
| Set | 标签去重、已读消息、黑名单 | 交集/去重 O(1) |
| **ZSet(有序集合)** | 行情排行榜、竞价价格档位、延迟任务 | 按 score 排序，范围查询 |
| Stream | 交易事件流、削峰写缓冲 | 类 Kafka，消费组+ACK |

**深度解析**
- 单线程模型 + IO 多路复用 → 天然无锁，命令原子；但大 key / 热 key 会阻塞。
- 持久化：RDB（快照，快但丢窗口）/ AOF（追加，安全但重）/ 混合。
- 集群：槽位分片(16384)，扩缩容靠 reshard。

**高频追问**
- Q：缓存一致性？→ A：先更 DB 再删缓存（Cache-Aside）+ 延时双删 / binlog 订阅兜底。
- Q：缓存击穿/雪崩/穿透？→ 击穿：互斥锁/逻辑过期；雪崩：随机 TTL；穿透：布隆过滤器。
- Q：和你模块连接？→ 挂牌库存用 String 原子扣减；竞价档位用 ZSet；行情榜单用 ZSet；限流用 String+过期。

## 三、分布式锁（Redisson / RedLock / ZooKeeper）

**一句话定位**：分布式下"同一时刻只一个人干活"的互斥原语。

**B2B 业务场景**
- 防超卖：挂牌库存扣减临界区。
- 幂等：同一笔付款回调只处理一次。
- 定时任务防重：多节点调度同一任务只跑一次。

**深度解析**
- **Redisson 看门狗**：加锁默认 30s，后台续期，防业务未跑完锁过期 → 生产首选。
- **RedLock**：多独立 Redis 节点多数派获取 → 理论安全但运维复杂、时钟假设有争议，多数业务用单集群 + 看门狗足够。
- **ZooKeeper 临时顺序节点**：强一致、无时钟问题、但写性能低于 Redis → 适合对一致性极度敏感的场景。

**高频追问**
- Q：锁过期但业务没跑完？→ Redisson 看门狗自动续期。
- Q：Redis 宕机锁丢了？→ 用 RedLock 或降级到 DB 乐观锁 + 业务幂等兜底。
- Q：和你模块连接？→ 交易撮合扣库存、付款回调幂等、竞价同一标的串行处理。

## 四、分布式事务（Seata / Saga / 本地消息表）

**一句话定位**：跨服务/跨库的数据一致，B2B 的"命门"。

**B2B 业务场景**
- 下单同时扣库存、生成应收账款、记履约单 → 跨交易/结算/金融。
- 你之前文档提到的"跨月长事务一致性"：一笔国际贸易可能跨数十天，不能占用锁。

**深度解析（四种模式对比）**

| 模式 | 原理 | 适用 | B2B 适配 |
|------|------|------|----------|
| AT(Seata) | 自动补偿，无侵入 | 短事务 | ★★★★ 内部服务 |
| TCC | Try/Confirm/Cancel 三阶段 | 强一致、高价值 | ★★★★ 资金类 |
| **Saga** | 长事务拆步骤+补偿 | **长周期** | ★★★★★ 履约/国际贸易 |
| 本地消息表 | 本地事务+消息重试 | 最终一致 | ★★★★ 生态对接 |

**关键判断**：B2B 大宗走**最终一致性 + Saga 补偿**，而非强一致 2PC（锁资源太久、吞吐量崩）。资金类用 TCC 保准确，履约长流程用 Saga。

**高频追问**
- Q：2PC 为什么不用？→ 阻塞、单点、锁资源，B2B 长周期不可接受。
- Q：空回滚/悬挂/幂等？→ TCC 三问题，靠事务状态表 + 防重 key 解决。
- Q：和你模块连接？→ 交易模式落单 → 履约保证生成 → 数据服务记账，全链路 Saga。

## 五、Elasticsearch（检索 / 聚合）

**B2B 业务场景**：商品/挂牌检索、企业库（买方卖方）搜索、行情多维筛选、合同全文检索。

**深度解析**
- 倒排索引 + 分片(shard)/副本(replica)；近实时(refresh 1s)。
- 深度分页用 search_after 而非 from/size。
- 写入用 bulk，避免单条；mapping 设计决定检索质量。

**高频追问**
- Q：和 DB 一致性？→ CDC（Canal）订阅 binlog 同步，最终一致。
- Q：和你模块连接？→ 数据服务的"行情/挂牌检索"底层；生态对接的企业资质检索。

## 六、任务调度（XXL-JOB）

**B2B 业务场景**：日终对账、账单生成、利息计提、报表推送、履约超时扫描。

**深度解析**：调度中心 + 执行器分离；失败重试、分片广播（大批量数据分片处理）、告警。替代 crontab 的分布式痛点（单点、无可视、无重试）。

**高频追问**：如何避免重复执行？→ 分片参数 + 执行器路由策略 + 分布式锁兜底。

---

## 七、API 网关（Spring Cloud Gateway / Kong）

**B2B 业务场景**：多租户路由（不同客户不同入口）、统一鉴权、限流、生态对接（银行/仓储 API 转发）、灰度。

**深度解析**：Gateway 基于 WebFlux 响应式，过滤器链做鉴权/限流/日志；Kong 基于 Nginx+Lua，性能更高、插件生态。B2B 多租户靠网关层路由 + 租户上下文透传。

**高频追问**：网关挂了怎么办？→ 网关集群 + 下游服务降级；关键生态对接走重试+对账兜底。

---

## 八、注册中心 / 配置中心（Nacos / ZooKeeper）

**B2B 业务场景**：微服务发现；规则配置热更新（改计费规则不重启）→ 直连你"规则配置"模块。

**深度解析**：Nacos 同时支持注册+配置，AP/CP 可切；ZK 强一致 CP，适合协调。配置中心让"规则配置模块"实现业务规则运行时生效。

---

## 九、规则引擎（Drools / 自研 DSL）

**B2B 业务场景**：计费规则、风控规则、促销/返点、履约校验 → 你"规则配置"模块的核心。

**深度解析**：把 if-else 业务规则外置为可执行规则，运营可配；Drools 用 Rete 算法做模式匹配；自研 DSL 更贴合业务但需维护。权衡：规则多且变 → 上引擎；规则少且稳 → 配置表足够。

**高频追问**：为什么不用硬编码？→ 规则变更频率高、需业务人员参与，硬编码导致发版慢、耦合深。

---

## 十、CDC 数据同步（Canal / Debezium）

**B2B 业务场景**：DB binlog → 消息队列 → 数仓/ES/缓存，实现读写分离、数据服务解耦。

**深度解析**：伪装 MySQL 从库拉 binlog；保证"数据服务"模块不直连交易主库，减轻压力。和你"数据服务"模块强相关。

---

## 十一、对象存储（MinIO / FastDFS）

**B2B 业务场景**：合同 PDF、仓单扫描件、质检报告、发票影像 → 你"履约保证"模块的凭证存证。

**深度解析**：MinIO S3 兼容、自建私有；FastDFS 轻量分布式。关注：防篡改（哈希/区块链存证）、权限隔离、生命周期。

---

## 十二、工作流引擎（Flowable / Activiti）

**B2B 业务场景**：审批流（挂牌审核、放款审批）、履约流程编排（多角色串联：卖方→仓储→物流→买方）。

**深度解析**：BPMN 流程定义 + 状态持久化；长周期履约用流程引擎保证"走到哪、谁卡住、超时提醒"。和你"履约保证"模块强相关。

## 关键选型对比速查（面试连环追问 TOP 10）

1. **RocketMQ vs Kafka？** → 事务消息/业务事件选 RocketMQ，日志流选 Kafka。
2. **Redis 为什么单线程还快？** → 内存 + IO 多路复用 + 无锁，瓶颈在内存带宽非 CPU。
3. **缓存一致性怎么保？** → Cache-Aside + 延时双删 + binlog 兜底。
4. **分布式锁用 Redis 还是 ZK？** → 性能选 Redis(看门狗)，强一致选 ZK。
5. **2PC 为什么不适合 B2B？** → 阻塞锁资源，长周期不可接受 → 用 Saga/TCC。
6. **Saga 怎么处理补偿失败？** → 重试 + 人工干预通道 + 对账兜底。
7. **消息不丢不重？** → 确认机制 + 消费幂等 + 死信。
8. **ES 深度分页？** → search_after，禁 from/size 深翻。
9. **规则引擎值不值？** → 规则多变/需业务自助 → 值；稳且少 → 配置表。
10. **网关限流算法？** → 令牌桶(允许突发) vs 漏桶(平滑)，B2B 用令牌桶。

## 与你熟悉模块的连接矩阵（面试串联话术）

> "在我们的 B2B 平台里，中间件不是孤立的：一笔挂牌交易，Redis(ZSet)撑竞价档位、分布式锁防超卖、Kafka 发领域事件驱动下游（outbox 本地消息表 + 消费幂等保证不丢）、Saga 保证交易-履约-记账最终一致、规则引擎实时算费、CDC 把数据同步给数据服务、ES 提供检索——我用这套组合解决'高并发撮合 + 长周期一致 + 业务规则热更'三件最难的事。"
