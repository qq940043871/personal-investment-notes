第一部分：提问框架优化

1.1 原始九问的问题

原始九问是：产品是什么 → 目标客户 → 客户特点 → 解决什么问题 → 行业痛点 → 产品如何解决 → 产品现存痛点 → 技术经理怎么解决 → 技术经理解决了什么问题。

毛病：九个问题里有三组重叠（"解决什么问题"≈"行业痛点"≈"产品如何解决"），且叙事顺序是"产品→痛点→自己"，听着像产品发布会后临时加了个个人述职。面试官真正想听的是一条线：你懂业务 → 你知道痛在哪 → 你干了什么 → 你还能干什么。

第二部分：七问标准答案底稿

以下内容全部基于本项目实际内容整理，可直接背练，标 ⭐ 的是必须脱口而出的部分。

Q1. 产品是什么（60-90秒电梯陈述）

⭐ 一句话版本："我们做的是大宗商品合同履约与供应链产业电商平台——覆盖从交易撮合、合同签约、履约交收、仓单物流、结算发票，到供应链金融和期货套保风控的全链路闭环。一句话概括：让大宗贸易里'签了合同之后的事'全部线上化、可信化、金融化。"

展开版本（结构：定位 → 覆盖范围 → 差异点）：

  • 定位：垂直于大宗商品现货贸易（铁矿石/煤炭/钢铁/农产品/能源）的产业电商 + 供应链协同平台
  • 覆盖范围：四层架构 24 个子系统——顶层设计层（产品全景/技术底座/决策驾驶仓）、产业电商管理层（SaaS运营端/管理端/机构协同）、产业电商门户层（农产品/工业/能源三大门户 + 会员中心 + 移动端 + 企微协同）、供应链服务层（智慧物流/智慧云仓/供应链金融/CTRM/ERP/期货套保风控）
  • 差异点：不是做"信息撮合"就完事，而是深入履约层——把交收、资金、票据、仓单这些最容易扯皮和造假环节做成了系统化能力，这也是供应链金融能做起来的前提

避坑：不要报菜名式地数 24 个子系统。先讲链路闭环，子系统作为佐证一笔带过。

Q2. 目标客户是谁（90秒）

⭐ 四类客户 + 一句话特征：

客户类型典型画像核心诉求决策特征
贸易商（核心客户）区域性钢材/煤炭/农产品贸易公司，年流水几千万到几十亿快进快出赚价差，需要比价、锁价、快速回款、垫资老板拍板，对"资金效率"极度敏感
核心企业/工厂钢厂、煤矿、大型加工企业稳定销路、应收账款管理、获得供应链金融工具采购/财务双部门决策，流程重
生态服务方仓储方、物流承运商、资金方（银行/保理）、质检机构接入平台获得业务流量，标准化的作业与结算对接看平台单量和结算确定性
平台运营方（B端自用）产业电商平台的运营团队会员管理、交易监管、风控处置、门户运营内部客户，看运营效率

客户特点总结（⭐必须能说）：

  1. 交易金额大、决策链长——单笔合同几十万到几千万，客户对"信任"的敏感度远高于对"价格"的敏感度
  2. 高度依赖线下关系链——传统上靠电话+微信+饭圈做生意，数字化意愿有但习惯迁移难
  3. 资金敏感——账期、垫资、融资成本是他们的命门，所以供应链金融是留客杀手锏
  4. 参与方多、单据杂——一笔交易涉及买卖双方+仓库+物流+银行+质检，任何一方掉链子全链卡壳
加分句："我们平台上一个小采购经理的真实处境是：打四个电话比价，问到第四家时第一家的价格已经作废了——这就是我们要服务的人和我们要解决的场景。"

4.2 核心架构设计一：合同域与履约域解耦 ⭐

"我们把合同域（商业契约：谁、什么、多少、什么价）和履约域（执行：付款、发货、收货、开票）彻底解耦。为什么？因为大宗贸易中合同变更极其频繁——补充协议、数量增减、交期调整是家常便饭，如果把履约状态耦合在合同上，每次变更都是一场数据迁移事故。解耦后，合同是版本链（原合同+N个补充协议），履约是独立的计划与任务流，两者通过事件总线联动。核心表设计：contract / contract_item / contract_party / fulfillment_plan / payment_order / shipment_order / receipt_settlement / fund_pool / invoice / refund_order。"

4.3 核心架构设计二：双轨履约引擎 ⭐⭐（必须讲透）

"大宗贸易的履约没有统一节奏，我们抽象出双轨引擎，由合同上的 delivery_mode 决定走哪条轨：
  • 顺序交收（Sequential）——状态机/工作流引擎强制有序（先款后货类），强一致，适合标准化、风险高的交易
  • 自由交收（Free-form）——事件驱动+规则引擎并行流转，动态条件判定，适合长期合作客户的灵活交收
  • 两轨共用同一套底层履约任务数据结构，监控和风控视角统一
  • 之上再叠加五种交收模式：款到发货、货到付款、定金+尾款、分期付款、信用证

加分点：主动讲 trade-off——"顺序轨用状态机换确定性，自由轨用事件驱动换灵活性，代价是自由轨的异常补偿逻辑复杂得多，我们用规则引擎把补偿策略配置化，而不是硬编码。"

4.4 支撑底座（一笔带过即可）：技术底座 126 页设计：统一身份 IAM、主数据 MDM、低代码、事件总线 eventhub、规则引擎、中间服务 midservice、数据中心、监控，以及 DDD + EDA + FSM 的整体方法论。

Q5. 产品现存痛点 + 技术经理解决思路（2-3分钟）

⭐ 诚实但有策略地讲。选真实存在、且你的解法有亮点的痛点：

现存痛点现状我的解决思路
1. 原型与生产的鸿沟：1300 页静态原型，页面间大量复制粘贴模板（抽屉/toast/分页无公共组件库），mock 数据硬编码验证业务模型有效，但离可交付差得远分层收敛：抽公共组件库（表格/抽屉/状态徽章）→ mock 数据层抽象为 schema 驱动 → 前后端契约先行（OpenAPI），原型页即验收用例
2. 图表库不统一：Chart.js 3.9 为主，部分外围页面是 Chart.js 4.x 或 ECharts，未收敛视觉与维护成本双输制定图表组件规范，统一封装一层 chart adapter，业务页只声明数据不声明实现
3. 履约自由轨的复杂度：事件驱动+规则引擎灵活但调试难、异常补偿路径多排障靠人肉追事件链引入履约链路 trace（事件溯源轻量版），每个履约单可回放完整事件时间线；异常策略从规则配置中可视化审计
4. 跨端导航与集成的脆弱性：shell+iframe 架构，postMessage 兜底，file:// 与 http:// 行为不一致演示能跑，集成两行泪中期把 iframe shell 演进为微前端（qiankun/wujie 或模块联邦），统一路由与状态；短期先统一 postMessage 协议为带版本号的 message schema
5. 数据一致性：资金预检 2PC 已设计，但跨域（合同-履约-结算-仓单）最终一致性的事务边界需要落地验证设计完备，实施待验证按域划分事务边界，跨域走事件+对账兜底，建立每日自动对账任务
话术要点：先说"哪些已经验证是对的"（业务模型、双轨引擎、域解耦），再说"哪些是技术债"，最后收在"我的优先级判断"——体现的不是完美，而是判断力。

Q6. 技术经理解决了哪些问题（STAR 故事库）

⭐ 每个案例按 S情境-T任务-A行动-R结果 打磨，90秒讲完。以下素材来自实际工作，选择 2-3 个最匹配目标岗位的深练：

  • 故事 1：河南能源双平台交付（主战故事 ⭐两个平台均为我方承建，唯一完整案例）
    • S：河南能源集团（世界 500 强级能源化工国企）需要同时解决销售端和采购端的数字化——煤炭/化工品销售要发现价格、创造溢价，采购端要阳光合规、国资审计留痕
    • T：作为技术负责人承建大宗商品交易平台（竞价/挂牌/长协/邀约专场，交易/物流/资金/仓单/融资模块）与中原云商阳光采购平台（电子招投标+电子签约）
    • A：销售端以竞价引擎为核心设计多模式交易状态机与异常出价风控；采购端以全流程留痕、电子签约、审批链为主线；两端共用会员/资金/物流底座
    • R：平台累计成交 1.1 亿吨、673 亿元，竞价溢价增收累计 8 亿元（对国企即净利润）；阳光采购成为河南省国资委试点，采购周期 20 天→7 天，成交项目破万；平台甲醇/1,4-丁二醇成交价成为行业风向标；客户 2026 年启动的"电商+物流+供应链金融"产业互联网转型与我们的四层架构判断一致
    • 加分句："一个客户、销售采购两端、两套系统，我完整走过了大宗产业电商'卖'与'买'两侧的数字化。"
  • 故事 2：ICC 系统重构——配置文件到 HTTP 实时获取
    • S：原系统参数靠读取本地配置文件，发布配置需重启/分发文件，多环境不一致且故障排查困难
    • T：主导将参数获取迁移为通过 HTTP 接口基于 deviceId 实时获取
    • A：设计设备维度的参数下发接口与缓存策略，保证接口故障时的降级回退（本地缓存兜底），分环境灰度切换
    • R：配置生效从"重启级"降到"秒级"，多环境配置一致性有保障，排障时间大幅缩短
    • 加分句："这个改造教会我一件事：任何去中心化方案都必须先设计好降级路径，否则就是把一个稳定性问题换成一个可用性问题。"
  • 故事 3：Postman 接口资产自动化（工程效率故事）
    • S：870 个业务请求/244 个文件夹靠手工维护，接口文档与实际实现漂移严重，跨脚本约定不一致
    • T：把接口资产变成可自动生成的工程资产
    • A：编写 Python 自动生成工具，统一请求模板与跨脚本一致性；解决 new.demo（客户端展开参数）→ demo（后端中间件 directives 包装）的格式转换
    • R：接口集合从"手工维护的负债"变成"一键重建的资产"，联调成本显著下降
  • 故事 4：期货套保风控子系统（业务深度故事）
    • S：大宗贸易客户有期现结合需求，套保头寸、风险敞口缺乏系统化管理
    • T：设计期货套保风控管理子系统（strategy/risk/balance/config/report）
    • A：套保策略与现货合同挂钩，敞口实时计算，风险限额与预警分级
    • R：期现联动从"Excel 手工台账"升级为系统化管控（可衔接石油期现联动交易方案，体现业务深度）
  • 故事 5：AI 工程化能力（差异化故事，视岗位选用）
    • LangChain/LangGraph 微信公众号 6 节点流水线、Agent Harness 架构（FastAPI+Vue3+PyQt6+MainLoop）、自动绘本生成智能体——"我不只是在传统 B 端做技术管理，同时在做 AI 工程化落地，知道 LLM 能力和工程约束的边界在哪"
STAR 使用提醒：R 必须有数字或可感知的变化；A 里必须有一个"我拍板的关键决策"——面试官在验证是"你带队"还是"你参与"。

Q7. 三个月/半年优先级（2分钟）

⭐ 给出排序逻辑而非清单："我会按'先止血、再还债、后增值'排：
  1. 第 1 个月（止血）：统一图表库与公共组件库，建立前后端契约（OpenAPI）和自动化对账——这些不解决，后面每加一个功能都在放大技术债
  2. 第 2-3 个月（还债+补关键短板）：履约链路 trace 与事件回放、跨端架构从 iframe 向微前端演进的技术验证；司机端（目前仅占位）补齐最小闭环
  3. 第 4-6 个月（增值）：基于可信履约数据把供应链金融能力做深（这是平台的商业护城河）；试点 AI 能力接入（智能推荐、单据识别、风控辅助），利用 LLM 工程化上的积累

收尾句："优先级的底层逻辑只有一个：先保证平台数据可信（履约/结算/仓单），再谈金融增值——信任是这个行业的货币。"

第三部分：面试训练计划

3.1 总体安排：5 天冲刺训练

天主题任务自检标准
D1叙事链打底背熟 Q1 电梯陈述（60秒版+90秒版各一遍）；通读 Q2-Q4 底稿，把七环痛点表抄写一遍对镜 60 秒讲完 Q1 不卡壳；痛点七环能默写环节名
D2架构深度深练 Q4：合同履约域解耦 + 双轨引擎，动手画架构图（域划分/状态机/事件流各一张）；准备 trade-off 问答白纸手画双轨引擎图 3 分钟内完成；能说出每条轨的代价
D3自我批判与规划精练 Q5/Q7：现存痛点表逐条准备追问预案；写出一版自己的"三个月优先级"并录音每个痛点能顶住两轮追问不露怯
D4STAR 故事打磨从五个故事选 3 个，写成 200 字卡片，各录音 90 秒；互相交叉检查是否有数字结果和关键决策听录音：S/A/R 比例约 1:4:2，没有流水账
D5全链模拟找人或用 AI 扮演面试官，按追问库随机轰炸 30 分钟；复盘录音，标记卡壳点七问全部能在总 15 分钟内完成主线陈述

3.2 每日微训练（碎片时间）

  • 晨间 10 分钟：随机抽一个 Q，脱稿口述并录音，回听检查"嗯/然后/就是说"的次数
  • 电梯测试：每次换一种身份讲 Q1——对 CEO 讲（价值/收入）、对 CTO 讲（架构/技术债）、对业务总监讲（客户/场景），三种版本都要顺
  • 痛点抽卡：把七环痛点做成卡片，随机抽一环，30 秒内说出"痛点场景 + 产品方案 + 对应子系统"三连

3.3 高频追问库（模拟面试必练）

业务类追问：

  1. 大宗商品和普通 B2B 电商的本质区别是什么？（答：非标/大额/长周期履约/价格波动风险/信任成本，履约和金融是重心）
  2. 你们和找钢网/欧冶这类平台的差异？（答：对标项目里的《客户案例与行业对标手册》，强调履约层深度和金融闭环）
  3. 五种交收模式为什么要做成系统而不是配置模板？
  4. 顺序交收和自由交收，客户怎么选？选错了怎么办？（答：引擎支持轨间切换策略 + 追问预案）
  5. 平台怎么解决"鸡生蛋"问题——没有买家卖家不来？（答：先从核心企业/园区切入 + 金融服务作为钩子）

架构类追问：

  1. 双轨引擎共用数据结构，怎么避免互相污染？
  2. 事件驱动那套，消息丢了/重复了怎么办？（答：幂等键 + 对账兜底 + 履约 trace 回放）
  3. 资金预检 2PC 具体怎么做的，和 TCC/Saga 的取舍？
  4. 电子签章、CA、存证的合规链路怎么设计？（答：契约锁/e签宝/法大大方案分析在 01-design/signauth/）
  5. 仓单防造假怎么做的技术保障？（答：电子仓单 + 货权流转留痕 + 质检报告扫码追溯批次 + 监控风控中心）

管理类追问：

  1. 你的团队多大？怎么分工？怎么做代码评审和技术债管理？
  2. 讲一次你和技术骨干的意见冲突，怎么解决的？
  3. 怎么估算工期？延期了怎么处理？
  4. 你怎么平衡业务需求的紧急性和架构重构的长期性？
  5. 为什么离开现在的公司/团队？（提前准备，落在"追求更大的业务纵深"而非抱怨）

3.4 面试现场执行清单

  • 开场 60 秒定调：Q1 电梯陈述务必背熟，第一印象不可重来
  • 白板/纸笔：主动要求画图讲双轨引擎——技术经理面试中"能画图"本身就是加分信号
  • 数字钩子：至少准备 5 个数字（24 个子系统、5 种交收模式、2 条履约轨、15 个角色、870 个接口请求），陈述中自然植入
  • 自我批判的度：痛点讲 3-5 个即可，每个必须带解法；只说痛点不给方案等于自曝
  • 反问环节（体现层次）："这个岗位接手的系统当前最大的技术债是什么？""团队现在最缺的能力是业务深度还是工程规范？""未来一年产品和技术的优先级排序是怎样的？"
