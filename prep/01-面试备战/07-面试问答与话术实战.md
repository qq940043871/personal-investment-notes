## 四、5 分钟版（深度技术面用）

我来讲一下我参与的这个大宗商品 B2B 电商平台项目。

**背景**：大宗商品行业（钢材、化工、农产品等）传统交易都是线下的，存在三个核心痛点：一是客户不信任平台，不愿资金在平台过夜，担心平台挪用资金；二是仓单造假频发，同一批货开多张仓单骗贷；三是交易模式复杂，远比 B2C 电商复杂，涉及挂牌、竞价、点价、预售等七种模式。

**我的角色**：后端架构+核心模块开发，主要负责交易引擎、资金存管、仓单可信链三块。

**技术架构**：整体微服务架构，8 个核心模块。后端 FastAPI，前端 Vue3，消息中间件 Kafka，缓存 Redis，搜索引擎 ES。区块链用 Hyperledger Fabric，物联网网关用 MQTT+边缘计算。

**核心难点一：资金存管一致性**。我们对接了 5 家银行，资金存在银行存管账户，平台只有指令权。难点是平台交易状态和银行资金状态的最终一致性——银行接口可能超时、重试、异步回调。我的方案是：每笔资金操作先写本地消息表（和业务事务同库），异步投递银行，超时主动查询，T+1 对账兜底。幂等键设计为"会员ID+订单号+操作类型+日期"，银行侧也用 reqId 去重。多银行适配用适配器模式。

**核心难点二：可插拔交易引擎**。7 种交易模式如果每个写一套，维护成本爆炸。我用策略模式+模板方法定义交易流程骨架（挂单→撮合→成交→结算→交收），每种模式实现自己的策略类。风控规则用规则引擎外部化。新模式 2 天上线，不影响现有模式。

**核心难点三：仓单可信链**。三层架构——物联网层验证货物真实存在（视频+RFID+称重交叉验证），WMS 层管理仓单生命周期状态机，区块链层做不可篡改存证。跨层一致性用事件溯源+Saga，每步有补偿动作。

**成果**：平台服务数百家客户，撮合延迟 <10ms，风控延迟 <5ms，资金对账差异率从 8% 降到 0.1% 以下。

这个项目和我在 Agent Harness 上的经验高度互补——Agent 的多步骤编排本质上也是一种 Saga，我在两边互相借鉴了很多设计思路。

## 二、常见追问及应答话术

### Q1: "你们为什么用C语言写撮合引擎，不用Go/Rust？"

> 这是一个好问题，我们当时评估过几个选项。Go的GC虽然比Java轻，但仍然是STW的，C的确定性执行是交易公平性的刚需。Rust在安全性和性能上确实优秀，但当时团队没有Rust储备，而且C的生态系统在金融交易领域非常成熟。权衡下来，C是最务实的选择。另外我补充一点——虽然引擎是C写的，但它只做撮合这一件事，代码量不大，维护成本可控。

### Q2: "DS这层不会成为性能瓶颈吗？"

> 不会，因为DS主要做的是协议转换和连接管理，不涉及业务逻辑计算。TCP二进制报文的解析是纯IO操作，Java NIO完全可以胜任。真正的性能瓶颈在撮合引擎内部，而那部分我们放在了C层。DS的延迟一般在微秒到毫秒级别，对交易体验没有影响。

### Q3: "你说你管Java团队，那C层的代码你怎么管？"

> 我不管C代码本身，但我管C层和Java层的接口协议。DS数据服务中心就是我的抓手——C引擎对外的二进制报文格式、TCP连接的握手与保活、协议的版本兼容，这些都在DS层体现。我能review DS的代码，能定义协议规范，就等于管住了异构通信的全链路。技术上这叫防腐层，管理上这叫边界治理。

### Q4: "你提到了12+微服务，服务治理怎么做的？"

> 我们用的是Hessian做RPC，相对传统但不复杂。服务发现和配置管理通过自研的midservice网关层统一管理，监控通过midmon。因为我们不是互联网级别的高并发场景，大宗交易的请求量相对稳定，所以没有上Spring Cloud或Dubbo全家桶，选择了更轻量的方案。

# 第三部分：6 大技术难点完整面试 Q&A

## 难点一：银行资金存管的资金流一致性

### Q1：能详细说说资金存管的架构吗？资金是怎么流转的？

**A：** 核心原则是**资金不过平台账户**。客户在银行开立存管子账户，资金直接在银行体系内流转。平台只有交易指令权，没有资金支配权。

资金流转链路：
1. 客户在平台下单 → 平台生成交易单号
2. 平台向银行发送扣款指令（带幂等键 reqId）
3. 银行从买方子账户扣款，划入卖方子账户
4. 银行异步回调平台，通知扣款结果
5. 平台根据结果更新订单状态

关键技术点：每笔指令带 reqId（幂等键），银行侧去重；本地消息表保证"发指令"和"记录"是原子操作；超时主动查询银行接口。

### Q2：银行接口超时了怎么办？你怎么知道钱到底扣没扣？

**A：** 这是最常见也最棘手的情况。分三步处理：

1. **即时重试**：超时后等待 3 秒重试一次（带相同 reqId，银行会幂等处理）
2. **主动查询**：如果重试也超时，调银行的 queryByReqId 接口，查这笔 reqId 到底有没有成功
3. **标记不确定**：如果查询也超时（极端情况），标记订单为"资金状态不确定"，进入人工对账队列，T+1 用银行对账文件兜底

关键设计：**永远不要假设结果**。要么确认成功，要么确认失败，不确定就等对账文件。宁可慢，不能错。

### Q3：幂等怎么设计的？如果银行侧没有去重怎么办？

**A：** 幂等键 = `会员ID + 订单号 + 操作类型 + 日期`，拼成 reqId 发给银行。

如果银行侧支持 reqId 去重（大多数银行存管接口支持），直接利用银行去重。如果银行不支持，我们在**本地做请求锁**——同一 reqId 在本地有一张"请求登记表"，发银行前先 INSERT，利用唯一约束保证同一 reqId 只发一次。银行回调时也按 reqId 更新登记表状态。

### Q4：5 家银行接口都不一样，怎么管理复杂度？

**A：** 适配器模式。定义统一的 `BankGateway` 接口：

```python
class BankGateway(ABC):
    @abstractmethod
    def freeze(self, req: FreezeRequest) -> FreezeResponse: ...
    @abstractmethod
    def transfer(self, req: TransferRequest) -> TransferResponse: ...
    @abstractmethod
    def query(self, req_id: str) -> QueryResponse: ...
    @abstractmethod
    def reconcile(self, date: str) -> ReconcileFile: ...
```

每家银行一个实现类（ShanghaiBankGateway、XingyeBankGateway...），内部处理各家协议差异。上层业务代码只面向 BankGateway 接口编程。银行配置（接口地址、证书、超时）放配置中心，可动态切换。

### Q5：T+1 对账具体怎么做的？

**A：** 每天凌晨 2 点（银行出对账文件后），拉取银行 T-1 日的对账文件，和本地资金流水逐笔比对：

- **本地有、银行有**：状态一致，跳过
- **本地有、银行无**：本地多记账，可能是银行处理延迟或本地误记，标记异常
- **本地无、银行有**：银行多记账，可能是回调丢失，根据银行记录补记
- **金额不一致**：标记异常，人工介入

对账结果生成差异报告，差异率监控告警。上线后差异率从行业平均 8% 降到 0.1% 以下。

## 难点二：区块链+物联网+WMS 三层仓单可信链

### Q1：为什么需要三层？一层不行吗？

**A：** 每层解决不同层面的信任问题：

- **只做区块链**：数据上链不可篡改，但如果上链的数据本身就是假的（货物不存在），区块链只是"可信地记录了谎言"
- **只做 WMS**：仓单管理系统记录了仓单，但 WMS 是中心化系统，可以被篡改，也无法证明货物物理存在
- **只做物联网**：监控到了货物存在，但没有仓单体系和防篡改存证，无法支撑融资场景

三层叠加才能形成完整的信任链：物联网证明"货在"→WMS 证明"仓单与货对应"→区块链证明"数据不可篡改"。

### Q2：物联网数据怎么接入的？视频流全传云端吗？

**A：** 不全传。视频流直传云端带宽成本太高（一个仓库 8 路摄像头，24 小时 1080P 约 2TB/天）。我们的方案是**边缘计算+事件上传**：

- 仓库部署边缘网关（ARM 设备），接入摄像头、RFID 读卡器、温湿度传感器、地磅
- 视频在边缘端做 AI 行为检测（异常搬货、人员闯入），只上传事件截图+结构化数据
- 温湿度/RFID/称重数据本身就是结构化的，直接 MQTT 上传
- 视频流保留在本地 NVR，云端按需调阅（事件触发时拉取对应时段视频）

这样带宽成本降低 95% 以上，同时关键事件不遗漏。

### Q3：三层数据不一致怎么办？比如 WMS 注册了仓单但区块链上链失败？

**A：** 用 Saga 模式处理跨层一致性：

```
WMS 注册仓单（本地事务）
  └─→ 物联网验证货物存在（调用边缘网关查询）
        └─→ 区块链上链（异步）
              ├─ 成功 → 仓单状态置为"已上链"
              └─ 失败 → 重试 3 次
                    └─ 仍失败 → 标记"上链失败"，人工介入
```

关键设计：
- 每层操作都**幂等**，重试安全
- 区块链上链**异步**，不阻塞 WMS 主流程
- 仓单状态有"待上链"中间态，只有上链成功才是"有效仓单"
- 上链失败的仓单不能用于交易和融资

### Q4：仓单拆分怎么实现？链上怎么处理？

**A：** 仓单拆分是融资场景的常见需求（一张 1000 吨的仓单拆成 5 张 200 吨分别融资）。

链下处理：
1. 原仓单状态置为"已拆分"（不可再交易）
2. 生成 N 张子仓单，每张记录数量、对应原仓单 ID
3. WMS 校验子仓单总量 ≤ 原仓单数量

链上处理：
1. 原仓单的链上记录标记为 SPLITTED
2. 铸造 N 张子仓单的链上 token（每张一个唯一 ID）
3. 链上记录拆分关系（子仓单 → 原仓单的引用）
4. 后续溯源可以追溯到原仓单

## 难点三：七种交易模式的可插拔引擎

### Q1：为什么用策略模式？直接 if-else 不行吗？

**A：** 7 种模式如果用 if-else，交易引擎核心代码会有 7 个分支 × 每个分支上百行，维护时改一个模式可能影响其他模式。策略模式把每种模式的差异隔离到独立的策略类中，符合开闭原则——新增模式不改现有代码。

但纯策略模式有个问题：7 种模式有大量**公共逻辑**（都是挂单→撮合→成交→结算→交收）。所以用**策略模式+模板方法**组合：模板方法定义流程骨架，策略类只实现差异化的步骤。

### Q2：风控规则怎么做的？硬编码还是配置化？

**A：** 用规则引擎外部化。不同交易模式的风控规则差异大——点价模式要监控基差波动，竞价模式要控制出价频率，挂牌模式要检查库存。

我们自研了一个轻量规则 DSL，类似：

```yaml
mode: pricing
rules:
  - name: 基差波动限制
    condition: "basis_change > 5%"
    action: reject
    message: "基差波动超过5%，禁止摘牌"
  - name: 保证金检查
    condition: "available_margin < order_amount * 0.1"
    action: reject
    message: "保证金不足"
  - name: 涨跌停检查
    condition: "price > yesterday_close * 1.1 || price < yesterday_close * 0.9"
    action: reject
    message: "触发涨跌停限制"
```

规则文件存在 DB 里，运营人员可配置，热加载生效。不用 Drools 那么重，但对我们的场景够用。

### Q3：新增一种交易模式大概要多久？

**A：** 如果新模式不涉及新的外部系统对接，大概 2 天：
- Day 1：实现 TradeMode 接口的 5 个方法（create_order、match、settle、cancel、query），编写风控规则配置
- Day 2：联调测试+上线

如果涉及新的外部系统（比如新模式需要对接期货公司接口），再加 2-3 天对接。

## 难点四：点价交易的期现实时联动

### Q1：期货行情怎么接入的？延迟多少？

**A：** 通过期交所授权的行情服务商接入，协议是 WebSocket（也有 FAST 二进制协议的）。行情接入层单独部署，和交易引擎分开。

延迟链路：期交所 → 行情服务商 → 我们的行情网关 → 交易引擎，端到端延迟 <10ms。

行情推送频率高时（每秒数百 tick），行情网关做**背压控制**——如果下游消费速度跟不上，丢弃中间 tick 只保留最新价，避免行情堆积打爆内存。

### Q2：摘牌时怎么保证价格锁定的原子性？

**A：** 这是点价交易最核心的问题——用户看到的期货价格是 4500，摘牌后不能变成 4501。

设计：**行情快照+版本号**机制。

1. 行情每次更新生成一个递增版本号（version）
2. 前端展示行情时携带当前 version
3. 摘牌请求携带 version
4. 引擎收到摘牌请求，检查当前 version 是否变化
   - 版本号一致 → 成交，锁定价格
   - 版本号已变化 → 摘牌失败，返回"价格已变动，请重新确认"

这样虽然不能 100% 成交（极端行情波动时可能需要重试几次），但**绝不会出现价格错位**。

### Q3：白盘夜盘切换怎么处理？

**A：** 期货有日盘（9:00-15:00）和夜盘（21:00-次日凌晨），切换时行情源会断开重连。

处理：
- 行情网关维护多个行情源连接，白盘/夜盘各有独立连接
- 切换时新连接 ready 后再断开旧连接（**优雅切换**，不断服务）
- 切换期间行情可能有 1-2 秒空窗，前端展示"行情切换中"提示
- 点价交易在切换窗口期内禁止摘牌（风控规则）

## 难点五：全流程 8 模块数据一致性

### Q1：为什么不用 Seata 这种分布式事务框架？

**A：** 考虑过 Seata AT 模式，但两个问题：

1. **性能**：Seata AT 模式要锁资源，8 个服务参与一个全局事务，锁定时间长，高并发下性能不可接受
2. **银行接口**：银行存管接口是外部系统，Seata 管不了，还是需要补偿机制

所以用 **Saga 模式**——每步本地事务+补偿动作，不锁资源，最终一致。性能远优于 2PC。

### Q2：Saga 的补偿顺序怎么保证？

**A：** Saga 的补偿必须**逆序执行**。如果执行顺序是 A→B→C→D，D 失败了，补偿顺序是 C'→B'→A'。

实现上用**编排式 Saga**（Orchestration），有一个 Saga 协调器维护执行状态：

```
执行：A(成功) → B(成功) → C(成功) → D(失败)
补偿：C' → B' → A'
```

每步的执行状态和补偿动作记录在 Saga 实例表中。如果协调器宕机重启，从表中恢复，继续执行补偿。

补偿动作也必须幂等——因为补偿本身也可能失败重试。

### Q3：8 个服务之间的事件怎么保证顺序？

**A：** 不是所有事件都需要全局有序，只有**同一交易内**的事件需要有序。

用 Kafka，按交易 ID 做 partition key，同一交易的事件发到同一 partition，保证单 partition 内有序。不同交易之间无序，可以并行处理，性能不受影响。

如果某个服务消费失败，不阻塞 partition（失败的事件进死信队列，人工处理），不影响其他交易。

### Q4：状态查询怎么做的？用户要看交易全链路状态。

**A：** 用 CQRS 模式。写库是各服务的本地数据库，读库是一个聚合视图（Redis + ES）。

每步执行完后发事件，一个聚合服务消费事件更新读库视图：

```json
{
  "trade_id": "T20250723001",
  "status": "物流调度中",
  "steps": [
    {"name": "下单", "status": "done", "time": "10:00:00"},
    {"name": "资金冻结", "status": "done", "time": "10:00:01"},
    {"name": "合同生成", "status": "done", "time": "10:00:02"},
    {"name": "仓单锁定", "status": "done", "time": "10:00:03"},
    {"name": "物流调度", "status": "processing", "time": "10:00:04"},
    {"name": "风控审核", "status": "pending"},
    {"name": "结算", "status": "pending"}
  ]
}
```

前端一次查询拿到全链路状态，不用调 8 个服务。

## 难点六：高并发撮合与流式风控

### Q1：撮合引擎具体怎么实现的？

**A：** 参考交易所撮合设计，纯内存操作。

核心数据结构：
- **买盘**：红黑树，按价格降序+时间优先
- **卖盘**：红黑树，按价格升序+时间优先
- 新订单进来，和对手盘最优价格撮合

撮合复杂度 O(log N)。撮合结果异步落库（先写 WAL 再内存撮合，宕机可恢复）。

竞价模式下，撮合在竞价结束时批量执行（集合竞价），算法是**最大成交量原则**——找一个价格使成交量最大。

### Q2：风控怎么做到 <5ms 的？

**A：** 风控分两层：

- **实时风控**（<5ms）：纯内存计算，检查保证金、涨跌停、频率限制。规则预编译成内存中的决策树，订单过一遍决策树即可
- **深度风控**（异步）：异常交易模式检测（如对敲、自买自卖），用流式计算（Flink）异步分析，不影响交易延迟

实时风控如果故障，熔断降级到"宽松模式"（只检查保证金），同时告警。**绝不让风控故障导致交易完全中断**，但也不能完全放行——宽松模式仍保留最基本的资金检查。

### Q3：竞价截止前的峰值怎么应对？

**A：** 竞价模式的特点是截止前 5 分钟集中出价，峰值可达日常 10-50 倍。

应对：
- **弹性扩容**：撮合引擎无状态，K8s HPA 根据 QPS 自动扩容
- **队列缓冲**：出价请求先进 Kafka 缓冲，消费端按能力消费，防止打爆
- **集合竞价**：竞价期间不实时撮合，只记录出价，截止后批量撮合，降低实时压力
- **限流**：单会员出价频率限制（如 10 次/分钟），防止恶意刷单
