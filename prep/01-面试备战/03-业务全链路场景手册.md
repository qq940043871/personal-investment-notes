## 场景1：挂牌与报价 — 交易的第一公里

### 业务是什么

卖方（钢厂/贸易商）把货挂到平台上，标明品种、规格、数量、价格、交货地。买方浏览选货。

**B2B 大宗跟淘宝的区别**：不是"一口价加购物车"。钢材价格每天甚至每小时都在变（跟着期货走），同一个规格不同钢厂的价格不同，同一个钢厂不同交货地的运费差几百块。

### 业务痛点

| 痛点 | 为什么痛 | 技术能做什么 |
|------|---------|------------|
| 价格变动频繁 | 一天调价十几次，靠 Excel 群发，客户收到已经是旧价格 | 实时行情接入 + 自动调价规则 |
| 库存不实时 | 卖方挂了 500 吨，实际仓库只剩 300 吨，成交后才发现超卖 | 与 WMS/ERP 库存实时同步 |
| 报价不可比 | 客户要比 5 家供应商，每家 Excel 格式不一样，人工对齐很痛苦 | 标准化产品编码 + 比价功能 |
| 信用不透明 | 跟新供应商交易，不知道靠不靠谱 | 供应商评级 + 历史交易数据展示 |

### 技术怎么解决

```
上海期货交易所行情 → 数据中台清洗 → Redis 实时价格缓存 → 前端轮询展示

供应商 ERP/WMS → API 对接 → 库存数据实时同步 → 挂单时自动校验可售量

供应商历史交易数据 → 数据仓库 → 评级模型 → 平台展示信用分
```

### 面试话术

> "大宗商品跟零售不一样，价格跟着期货实时波动。我们的报价系统接入了期货交易所行情，通过 Redis 缓存毫秒级推送给前端，保证交易员看到的是最新价。同时对接了卖方的 WMS 系统做实时库存校验，挂单时自动检查可售量，防止超卖。这是 B2B 最基础的'真实可靠'——价格真实、库存真实。"

## 场景2：合同签约 — 从口头到法律效力

### 业务是什么

买卖双方谈妥后签订电子合同，确定品种、规格、数量、单价、总金额、交货期、质量标准、结算方式。大宗合同金额动辄千万，每一行条款都有法律后果。

### 业务痛点

| 痛点 | 为什么痛 |
|------|---------|
| 条款复杂 | 大宗合同十几页，涉及质量标准（国标/厂标）、计量方式（过磅/理计）、异议处理条款 |
| 审批链条长 | 内部要过法务、风控、业务总监，外部要对方确认，一个合同来回改七八版 |
| 签约效率低 | 纸质合同要邮寄、盖章、回传，异地签约从发起到完成可能一周 |
| 履约跟踪难 | 合同签完后丢一边，到了交货期才发现卖方根本没备货 |

### 技术怎么解决

```
合同模板库 → 智能填充（品种/价格/条款从订单自动带入）→ 在线协同编辑

审批流引擎 → 多级审批（法务→风控→业务总监）→ 审批记录上链/时间戳

电子签章（e签宝/法大大） → 双方在线签署 → 存证平台存证 → 合同归档到ES
```

### 面试话术

> "合同是我们的核心环节。大宗合同条款复杂、金额大，我们做了三件事：第一，智能合同模板，80%的标准条款自动生成，业务员只需改品种数量和价格；第二，审批流引擎，法务、风控、业务总监按规则自动流转，改一版推送一次，不用微信群来回@；第三，集成电子签章，签约从一周缩短到一天，签完后合同自动归档到 ES，支持'去年跟 XX 钢厂签的所有含质量异议条款的合同'这种全文搜索。"

## 场景3：支付结算 — 资金安全是底线

### 业务是什么

大宗交易支付比零售复杂得多：不是支付宝一键付款。涉及保证金（签约时付）、进度款（发货前付）、尾款（验收后付），还可能涉及信用证、银行承兑汇票。

### 业务痛点

| 痛点 | 为什么痛 |
|------|---------|
| 支付方式多 | 保证金/进度款/尾款/信用证/银承，每种规则不同 |
| 金额巨大 | 一笔支付错误几百万，人工操作风险极高 |
| 银行对接难 | 不同银行接口规范不同，银企直连对接成本高 |
| 账务复杂 | 一笔交易分多次付款，还要匹配发票，财务对账头疼 |

### 技术怎么解决

```
支付计划引擎 → 签约后自动生成支付计划（保证金X日付→进度款Y日付→尾款Z日付）

银企直连接口 → 统一支付网关 → 适配多银行接口 → 自动记账

RocketMQ事务消息 → 支付成功 → 通知风控调额度 + 通知财务记账 + 通知仓储备货
```

### 面试话术

> "支付是资金安全红线。我们的支付引擎签约后自动生成支付计划——什么时候付保证金、什么时候付进度款、什么时候付尾款，系统自动提醒，逾期自动预警。支付环节接了银企直连，通过统一支付网关适配不同银行接口。支付成功后通过 RocketMQ 事务消息通知风控调额度、财务记账、仓库备货，保证多系统数据一致——绝不能出现'钱付了但额度没扣'这种事故。"

## 场景4：仓储物流 — 货在哪里、什么状态

### 业务是什么

大宗商品的仓储物流跟快递不一样。钢材在仓库里是一捆一捆的，按吨计价，出库要过磅。仓单（仓库出具的权利凭证）可以在贸易商之间流转——你可能买了一批螺纹钢，但在提货之前把它转卖给了下家，这中间货没动，仓单变了。

### 业务痛点

| 痛点 | 为什么痛 |
|------|---------|
| 仓单造假 | 一货多押、假仓单，供应链金融最大风险 |
| 库存不准 | 仓库报的库存跟实际对不上，原因可能是出库没记账、损耗没核销 |
| 物流不透明 | 货发出去后，买方不知道到哪了，司机联系不上 |
| 多仓库管理 | 一个贸易商同时在 5 个仓库有货，各自系统不通 |

### 技术怎么解决

```
WMS系统对接 → 入库/出库/盘点数据实时同步 → 平台库存实时可见

仓单电子化 → 区块链存证 → 仓单流转记录不可篡改 → 杜绝一货多押

GPS/物联网 → 运输车辆轨迹实时回传 → 买方能看到"货到哪了"
```

### 面试话术

> "仓储物流在 B2B 大宗里特别重要——因为货值大。我们对接了合作仓库的 WMS 系统，入库出库数据实时同步到平台，库存不准的问题基本解决了。仓单这块，我们做了电子化，通过区块链存证保证流转记录不可篡改，杜绝一货多押。物流环节接了 GPS 轨迹，买方在平台上能看到货物运输的实时位置，不用不停打电话问司机。"

## 场景5：质检与异议处理 — 大宗交易最头疼的事

### 业务是什么

买方收到货后发现质量不达标（比如螺纹钢含碳量超标、煤炭热值不够），发起异议。双方协商：退货、降价、还是赔偿。这在大宗交易中非常普遍，处理不好就是客户流失+法律纠纷。

### 业务痛点

| 痛点 | 为什么痛 |
|------|---------|
| 证据难收集 | 质检报告、现场照片、往来邮件分散在各处 |
| 处理周期长 | 从异议发起到最终解决平均 2-4 周，期间资金冻结 |
| 责任界定难 | 是出厂质量就不行？还是运输中受损？还是买方自己存坏了？ |
| 缺少赔付标准 | 每次异议都像第一次处理，没有历史案例参考 |

### 技术怎么解决

```
异议工单系统 → 买方提交（照片+质检报告+描述）→ 
自动分配给对应业务员 → 升级路径（未24小时处理自动升级）

历史异议案例库 → ES全文搜索 → "类似的质量问题历史上怎么赔付的"
```

### 面试话术

> "大宗交易的异议处理是个高频痛点。我们建了一套异议工单系统：买方在 App 上提交——拍照、传质检报告、写描述，系统自动分配给对应业务员，24 小时内未处理自动升级给主管。所有沟通记录留在系统里，不会出现'电话里说的不算'。我们还把历史异议案例存在 ES 里，处理新的异议时可以搜'类似的质量问题之前怎么赔的'，让赔付有据可依，不是每次都是拍脑袋。"

## 场景6：风控系统 — 每一笔交易背后的"安检"

### 业务是什么

B2B 大宗的风控是**事前+事中+事后**三层。事前：对新客户进行信用评估，给授信额度；事中：实时监控交易行为，异常交易拦截；事后：逾期催收、坏账核销。

### 业务痛点

| 痛点 | 为什么痛 |
|------|---------|
| 信用评估依赖人工 | 授信靠业务员"感觉"，没有标准化模型 |
| 风险发现滞后 | 等发现客户有问题时，已经欠了 500 万 |
| 规则硬编码 | 风控策略写在代码里，改一条规则要发版 |
| 关联风险不可见 | 看起来不相关的多家公司实际是同一控制人 |

### 技术怎么解决

```
风控引擎 → 规则引擎（Drools/Easy Rules）→ 规则热更新，不用发版

实时计算 → 客户维度聚合（近7天交易额/退款率/逾期次数）→ 
超过阈值自动触发：预警/限额/冻结

关联关系图谱 → 企业工商数据 → 识别同一控制人/关联公司 → 合并计算授信
```

**用 Redis ZSet 的风控场景**（接上篇的技术点）：
```
每笔交易完成 → redisTemplate.opsForZSet()
    .incrementScore("risk:volume:24h", customerId, amount);
// 定时任务检查 Top N 大户，异常波动自动预警
```

### 面试话术

> "风控在供应链金融里是命门。我们做了三层：事前信用评估——对接工商数据+历史交易，自动计算授信额度；事中实时监控——用规则引擎（Drools），交易量/退款率/逾期次数任一超标自动预警或冻结；事后催收——逾期自动生成催收任务，分级处理。关键是把风控策略从代码里抽出来，改规则不用发版，因为市场变化太快了——今天螺纹钢价格暴跌，必须立刻调保证金比例，不能等一个迭代。"

## 场景7：发票与税务 — B2B 逃不掉的合规

### 业务是什么

每笔大宗交易都要开增值税专用发票。发票信息（品名、规格、数量、单价、金额、税率）必须跟合同和实际交货完全一致。错了要冲红重开，平均周期 2-3 周，影响买方抵扣。

### 业务痛点

| 痛点 | 为什么痛 |
|------|---------|
| 开票信息不一致 | 合同写的"螺纹钢HRB400"，发票写的"螺纹钢"，税务不认 |
| 开票慢 | 财务每月集中开票，买方等发票抵扣等到月底 |
| 三单匹配难 | 合同、发票、入库单匹配，全靠 Excel 人工比对 |
| 税务合规风险 | 虚开发票是刑事责任，但信息不一致可能是无意的 |

### 技术怎么解决

```
订单完成 → 自动触发开票申请 → 财务审核（一键确认）→ 
税务系统开票 → 电子发票回传平台 → 买方下载

三单匹配引擎 → 合同行 vs 发票行 vs 入库行 → 自动比对 → 
不一致自动标红 → 人工处理
```

### 面试话术

> "大宗贸易的发票管理跟 C 端不一样——都是增值税专票，信息必须跟合同和实物完全一致，不然税务不认。我们做了自动开票：订单完成后自动生成开票申请，品名规格从合同自动带入，财务只需要一键确认。还做了三单匹配引擎——合同、发票、入库单自动比对，不一致的自动标红，把原来财务 3 天的工作量压缩到 2 小时。"

## 场景8：供应链金融 — 从贸易服务到金融服务

### 业务是什么

这是 B2B 大宗平台的核心变现模式之一。三种典型产品：

| 产品 | 业务逻辑 | 谁需要 |
|------|---------|--------|
| **应收账款融资** | 卖方交货但买方没付钱 → 平台/银行先付给卖方 → 买方到期还给平台/银行 | 卖方（缺周转资金） |
| **存货质押** | 货在仓库 → 以货为抵押物借钱 → 还钱后解押提货 | 贸易商（货压着没钱周转） |
| **预付款融资** | 买方想买货但钱不够 → 平台垫付部分货款 → 买方分期还 | 买方（有好机会但缺钱） |

### 业务痛点

| 痛点 | 为什么痛 |
|------|---------|
| 确权难 | 应收账款是"真的吗"？买方认不认这笔债？ |
| 货权不清 | 仓库里的货到底是谁的？有没有被重复质押？ |
| 风控数据不足 | 银行做供应链金融最大的顾虑：看不懂大宗贸易，不敢放款 |
| 资金流向难追踪 | 钱放出去了，买方有没有真的用来买货？ |

### 技术怎么解决

```
应收账款融资：
  平台交易数据 → 自动生成应收账款凭证 → 
  区块链存证（买方确权记录不可篡改）→ 资金方看到确权后放款

存货质押：
  电子仓单 + 物联网（仓库摄像头/AI识别）→ 
  质押期间货物异动自动告警 → 解押后才能出库

预付款融资：
  受托支付 → 钱不经过买方手 → 直接打给卖方 → 
  货物入库后自动转为存货质押
```

### 面试话术

> "供应链金融是平台从'交易撮合'到'金融服务'的关键一跳。我们的核心优势是有交易数据——应收账款融资，我们用平台上的真实交易记录生成电子凭证，买方在线确权，资金方看到确权后放款，解决了传统供应链金融最头疼的'确权难'。存货质押这块，我们做电子仓单加物联网监控，质押期间货物有任何异动自动告警。这就是 B2B 平台的数据壁垒——没有交易数据，做不了金融。"

## 场景9：客户运营 — 买了产品之后

### 业务是什么

B2B 的客户运营跟 C 端完全不同。不是你让用户"每天打开 App 打卡"他就来的。企业客户的核心诉求就一个：**"你的系统帮我多赚钱了，还是少亏钱了？"**

### 客户运营全流程

```
售前（1-2周）          售中（1-2月）          售后（持续）
──────────────────────────────────────────────────
需求调研              系统培训               日常问题响应
Demo演示              数据迁移               新功能推送
ROI测算               灰度上线               健康度监控
商务谈判              正式切换               续费/增购
签约                  验收交付               流失预警
```

### 业务痛点

| 痛点 | 为什么痛 |
|------|---------|
| 上线慢 | 客户数据格式各不相同，导入导出反复折腾，平均 2 个月才用起来 |
| 用不起来 | 功能上线了，但客户团队没人会用，打开率不到 30% |
| "沉默客户" | 签了年费，用了两周就不用了，到期肯定不续 |
| 客户成功团队缺数据 | 不知道谁用得好、谁快流失了，全凭感觉 |

### 技术怎么解决

```
客户健康度评分模型：
  登录频率 × 0.2 + 核心功能使用率 × 0.4 + 
  交易完成率 × 0.3 + 问题响应满意度 × 0.1
  → 低于 60 分触发客户成功经理介入

客户数据导入工具 → 
  模板下载（标准格式）→ 批量导入 → 自动校验 → 
  异常数据标红 → 人工修正 → 一键入库
```

### 面试话术

> "客户的运营是我们最薄弱的但正在加强的环节。现在我们做了客户健康度模型——登录频率、核心功能使用深度、交易完成率、问题响应满意度四个维度加权打分。低于 60 分的客户自动触发客户成功经理介入，在客户自己说'不续了'之前，我们已经知道谁有风险。客户数据导入我们也从原来的人工一个个录入做成了模板批量导入加自动校验，新客户从签约到用起来的时间压缩了一半。"

## 场景10：多角色权限体系 — 一个客户账户，N 类人在用

### 业务是什么

B2B 产品的用户比 C 端复杂太多。签合同的是一个公司，但实际用系统的是公司里不同角色的人：

| 角色 | 核心需求 | 不能让他看/做的 |
|------|---------|---------------|
| 采购经理 | 找货、比价、下单 | 不能看财务数据 |
| 财务 | 对账、开票、付款审批 | 不能下单 |
| 风控 | 看交易数据、设额度 | 不能操作交易 |
| 老板 | 看全局报表 | 不能改数据 |
| 仓库管理员 | 入库/出库/盘点 | 不能看价格 |

### 技术怎么解决

```
RBAC权限模型：
  用户 → 角色 → 权限 → 资源

数据权限：
  同一个"订单列表"页面，A 只能看他部门的，B 能看到全公司的
  
菜单权限：
  财务看到的菜单跟采购看到的完全不同
```

### 面试话术

> "B2B 的权限比 C 端复杂得多。同一个客户公司，采购、财务、风控、老板看到的界面和能做的操作完全不同。我们用 RBAC 做菜单级和按钮级权限控制，采购看不到财务价格，财务不能下订单。数据权限上，同一个查询页面，区域经理只能看他负责区域的客户，总部能看到全部。"

## 全场景串联：面试 5 分钟业务叙事模板

面试官：**"你们产品到底做什么的？讲一下业务流程。"**

> "我们是做大宗商品交易和供应链服务的 B2B 平台。核心客户是大宗贸易商和终端工厂，品类以钢材为主。
>
> **业务全链路是这样的**：卖方在平台挂牌报价——我们实时对接期货行情，价格是活的；买方在线询价比价——标准化产品编码让他能一键对比五家供应商。
>
> **成交后进入签约环节**：智能合同模板 80% 自动生成，在线协同编辑、审批流自动流转、电子签章一键签署。签完签约一周变成一天。
>
> **然后是履约**：平台自动生成支付计划——什么时候付保证金、什么时候付尾款，系统自动提醒。银企直连接口适配多银行，支付走 RocketMQ 事务消息，保证资金、额度、账务三系统数据一致。
>
> **仓储物流方面**：对接了合作仓库的 WMS，库存实时同步；电子仓单区块链存证；运输 GPS 轨迹客户实时可查。
>
> **金融服务是我们的差异化**：基于平台积累的交易数据做应收账款融资和存货质押——资金方敢放款，因为我们有不可篡改的交易记录和仓单流转数据。
>
> **售后服务**：质检异议走工单系统，自动分配、超时升级、历史案例可查；客户健康度模型做流失预警。
>
> 整个平台覆盖了从询价到售后的完整闭环，技术团队不到 X 人，核心挑战是如何在高客单价、长链条、多方协作的 B2B 场景下，保证数据一致性和系统稳定性。"
