## 一、Redis — 不止是缓存，是"快"的答案

### 场景1：交易页面数据缓存（String）

**业务场景**：大宗商品价格实时波动，交易员每次刷新行情页面都要查数据库，数据库扛不住。

**技术方案**：
```
期货实时价格 → Redis String → 前端轮询
KEY: "price:RB2410:realtime"
VALUE: "3750"
TTL: 5秒（价格5秒更新一次）
```

**为什么是 Redis String？**
- O(1) 读写，毫秒级响应
- 设置 TTL 自动过期，不担心脏数据堆积
- 单线程模型天然原子性，并发读价格不会出现不一致

**追问："你们价格缓存怎么保证跟数据库一致？"**

→ Cache Aside 模式：更新数据库时删缓存，下次查询重建。关键：**先删缓存再更新数据库**（避免并发读写入旧缓存）。极端场景用延迟双删：删缓存→更新DB→等500ms→再删一次。

---

### 场景2：防止重复提交（String + SETNX）

**业务场景**：大宗交易金额巨大，用户手抖点两次"确认下单"，千万不能创建两笔订单。

**技术方案**：
```java
String lockKey = "order:submit:" + orderNo;
Boolean locked = redisTemplate.opsForValue()
    .setIfAbsent(lockKey, "1", 30, TimeUnit.SECONDS);
if (!locked) {
    throw new BizException("请勿重复提交");
}
// 执行业务逻辑...
redisTemplate.delete(lockKey); // 处理完释放
```

**为什么用 SETNX 而不是数据库唯一约束？**
- 数据库唯一约束只能防"存进去"，不能防"业务逻辑执行两遍"
- SETNX 在业务入口就拦截，减少无效的数据库操作和第三方调用

**追问："SETNX 有什么坑？"**
- 锁过期时间设置：设太短业务没执行完锁就释放了（→ 用 Redisson 看门狗自动续期）
- 误删别人的锁：A 的锁过期，B 获取了锁，A 执行完删了 B 的锁（→ value 存 UUID，删之前比较）

---

### 场景3：交易员操作权限缓存（Hash）

**业务场景**：每次操作都要查"这个交易员能不能做这笔交易"（额度限制、品种权限、合同范围），权限表 join 了 5 张表，查一次 200ms。

**技术方案**：
```
KEY: "trader:permission:10023"
HASH:
  "credit_limit" → "50000000"     (授信额度)
  "allowed_products" → "螺纹钢,热卷,铁矿石"  (可交易品种)
  "counterparty_list" → "1001,1002,1005"     (可交易对手方)
```

**为什么是 Hash 而不是多个 String？**
- 一次 HGETALL 拿到所有权限字段，不用多次网络往返
- 修改单个字段（如额度调整）只需 HSET 一条，不用重建整个对象
- 内存占用比多个 String key 小（共用 key 的元数据开销）

---

### 场景4：延迟队列处理超时订单（ZSet）

**业务场景**：大宗交易中，买家确认合同后 30 分钟内必须支付保证金，超时自动取消。

**技术方案**：
```java
// 创建订单时
long cancelTime = System.currentTimeMillis() + 30 * 60 * 1000;
redisTemplate.opsForZSet().add("order:timeout:queue", orderNo, cancelTime);

// 定时任务每秒轮询
Set<String> timeoutOrders = redisTemplate.opsForZSet()
    .rangeByScore("order:timeout:queue", 0, System.currentTimeMillis());
// 逐个取消...
```

**为什么是 ZSet 而不是 RocketMQ 延迟消息？**
- ZSet 的 score 就是取消时间，自然排序
- 如果延迟消息量大，RocketMQ 延迟级别有限（18个级别），30分钟这种自定义延迟不好做
- ZSet + 轮询实现简单，业务可控

---

### 场景5：排行榜/风控预警（ZSet）

**业务场景**：风控系统要实时展示"近 24 小时交易量最大的前 10 个客户"，监控异常交易。

```java
// 每笔交易完成时
redisTemplate.opsForZSet().incrementScore("risk:volume:24h", customerId, amount);

// 查询 Top 10
Set<ZSetOperations.TypedTuple<String>> top10 = redisTemplate.opsForZSet()
    .reverseRangeWithScores("risk:volume:24h", 0, 9);
```

## 二、MySQL — 数据的"保险柜"

### 场景1：订单表设计 — 聚簇索引 vs 二级索引

**业务场景**：订单表每天新增 10 万条，需要按"下单时间"范围查询，又要按"客户 ID"查他的所有订单。

**建表决策**：
```sql
-- 主键：自增 bigint → 聚簇索引
-- 顺序插入，不会页分裂
CREATE TABLE t_order (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 聚簇索引，叶子存整行
    order_no VARCHAR(32) NOT NULL,
    customer_id BIGINT NOT NULL,
    product_code VARCHAR(20),
    amount DECIMAL(18,2),
    status TINYINT,
    create_time DATETIME,
    
    UNIQUE KEY uk_order_no (order_no),
    INDEX idx_customer_time (customer_id, create_time)  -- 联合索引
);
```

**面试要说清楚**：
- **聚簇索引（id）**：叶子节点存完整行数据，按 id 顺序排列。好处是按 id 范围查直接扫叶子链表；代价是二级索引要回表。
- **二级索引（idx_customer_time）**：叶子节点只存 (customer_id, create_time, id)，查到 id 后回表取完整行。如果 `SELECT id, customer_id, create_time FROM t_order WHERE customer_id=1001` — 覆盖索引，不用回表。

---

### 场景2：联合索引的最左前缀原则 — 为什么这个查询慢了？

**业务场景**：客服查"客户 1001 在 2026 年 7 月的订单"，索引 `(customer_id, create_time)`

```sql
-- ✅ 走索引（等值查 customer_id + 范围查 create_time）
EXPLAIN SELECT * FROM t_order 
WHERE customer_id = 1001 AND create_time >= '2026-07-01';

-- ✅ 走索引（从最左 customer_id 开始）
EXPLAIN SELECT * FROM t_order WHERE customer_id = 1001;

-- ❌ 不走索引（跳过了 customer_id）
EXPLAIN SELECT * FROM t_order WHERE create_time >= '2026-07-01';

-- ⚠️ 只走 customer_id（create_time 用了函数，索引失效）
EXPLAIN SELECT * FROM t_order 
WHERE customer_id = 1001 AND DATE(create_time) = '2026-07-01';
```

**面试标准回答**："联合索引遵循最左前缀原则，查询条件必须从索引定义的第一列开始连续匹配。遇到范围查询（>、<、BETWEEN、LIKE 'xx%'）之后，后续列不再走索引。另外，对索引列用函数会导致索引失效，应该改成范围查询。"

---

### 场景3：为什么 InnoDB 推荐自增主键？

**业务场景**：订单表用雪花算法生成的随机 ID vs 自增 ID，插入性能差多少？

**答案**：B+Tree 的叶子节点是按主键顺序存储的。自增主键每次插入都在最后面，几乎不会触发页分裂。随机主键插入位置不可预测，频繁引起页分裂 → 磁盘碎片 → 性能下降。

**追问："雪花算法就不行吗？"**

→ 可以，但要在业务层做优化：用"节点号+时间戳"保证趋势递增。或者用一个自增 ID 做聚簇索引，雪花 ID 做二级唯一索引。

---

### 场景4：慢查询优化实战

**业务场景**：财务对账页面，一个 SQL 查 30 秒。

**排查流程（面试要能讲出这个流程）**：
```
1. SHOW FULL PROCESSLIST → 找到卡住的 SQL
2. EXPLAIN 看执行计划：
   - type=ALL → 全表扫描，没走索引
   - rows=200万 → 扫描行数太大
   - Extra=Using filesort → 排序没有用索引
3. 加联合索引 (company_id, settle_time, order_status)
4. 加完后 EXPLAIN 验证 type=range，rows 降到几千
5. 上预发布环境压测确认
```

## 三、消息队列 — 解耦的"神经系统"

### 场景1：订单状态同步多个下游系统（RabbitMQ）

**业务场景**：一笔大宗交易的订单状态变更（待确认→已确认→已付款→已发货→已收货→已结算），需要同步通知：仓储系统（备货/出库）、财务系统（记账/开票）、风控系统（额度调整）、客户 APP（推送通知）。

如果同步调用：
```
交易服务 → 仓储服务（等3秒）
         → 财务服务（等5秒）
         → 风控服务（等2秒）
         → 客户通知（等1秒）
总耗时 11秒，任何一个挂了整个链路崩
```

改成异步：
```java
// 订单状态变更后
rabbitTemplate.convertAndSend("order.exchange", "order.status.changed", event);
// 各个下游服务自己订阅，独立消费
```

**面试要说清楚**：
- **解耦**：交易服务不关心谁在消费，只管发消息
- **削峰**：冬储期日均订单量暴增 5 倍，消息队列缓冲住，下游慢慢消费
- **最终一致性**：B2B 场景允许秒级延迟，不允许丢消息（→ 手动 ACK + 死信队列 + 补偿表）

---

### 场景2：哪些场景用 RocketMQ 而不是 RabbitMQ？

| 场景 | 选型 | 原因 |
|------|------|------|
| 订单状态同步 | RabbitMQ | 业务消息，量不大，topic 少，RabbitMQ 够用且运维简单 |
| 交易流水上报监管 | RocketMQ | 不能丢（同步刷盘），高吞吐（日千万级），RocketMQ 的事务消息保证发消息和本地事务原子性 |
| 日志采集、用户行为埋点 | Kafka | 纯高吞吐场景，允许少量丢失，Kafka 的零拷贝和顺序写磁盘是王者 |

**追问："RocketMQ 事务消息怎么保证一致性？"**

→ 两阶段：①发 half 消息（消费者不可见）→ ②执行本地事务 → ③根据本地事务结果 commit 或 rollback half 消息。如果第③步失败（生产者挂了），RocketMQ 会定时回查本地事务状态。

---

### 场景3：消息丢了怎么办？

**面试三连问的标准答案**：

```
生产者丢 → RocketMQ 事务消息 / RabbitMQ confirm 模式
Broker丢  → 同步刷盘 + 主从同步（降吞吐换可靠性）
消费者丢 → 手动 ACK，处理完再确认，不能自动 ACK
```

B2B 金融场景：**宁可慢，不可丢**。用同步刷盘 + 手动 ACK + 死信队列 + 补偿表四重保障。

## 四、Elasticsearch — 搜索不是"LIKE"

### 场景1：合同全文搜索

**业务场景**：法务要找"去年跟 XX 钢铁厂签的含'质量异议'条款的所有合同"。MySQL LIKE？5 亿条合同文本，查到天荒地老。

**技术方案**：
```
合同创建 → MySQL 存结构化字段（金额、日期、状态）
         → ES 存全文（合同正文、条款内容）
         
搜索时：ES 返回合同 ID 列表 → MySQL 查完整信息
```

**为什么用 ES？**
- 倒排索引：先把文档切词成"词条→文档ID"的映射表，搜索时直接翻字典，O(1)定位
- 不用扫全表，不用 like '%质量异议%'

**追问："ES 为什么快？MySQL 为什么慢？"**

→ MySQL B+Tree 索引最左前缀匹配，`LIKE '%质量异议%'` 无法利用索引必须全表扫描。ES 倒排索引是"词条→文档列表"的映射，"质量异议"这个词直接定位到包含它的所有文档。

---

### 场景2：仓单/提单结构化搜索

**业务场景**：运营要筛选"上海仓库的螺纹钢仓单，库存>100吨，入库时间在最近30天"。

MySQL 能做，但 12 个筛选条件 + 4 张表 join + 百万级数据 → 慢。ES 的 filter 不参与打分，直接跳转到位图命中，毫秒级返回。

## 五、分布式事务 — B2B 绕不开的坎

### 场景：下单扣库存 + 扣额度 + 创建合同

**业务场景**：大宗交易下单涉及三个操作：

```
1. 库存服务：锁定 500 吨螺纹钢
2. 风控服务：扣减客户授信额度 200 万
3. 合同服务：生成电子合同
```

**必须同时成功或同时失败**。

### 方案演进（面试要能讲出这个思考过程）

**阶段1：本地事务** → 不行。三个服务三个数据库。

**阶段2：Seata AT 模式** → 自动回滚，但性能损耗大（两阶段提交，锁时间长），B2B 高并发交易扛不住。

**阶段3：Saga 模式（推荐）** → 每个服务执行成功调下一个，失败则调上一个的补偿接口：
```
下单成功 → 锁库存成功 → 扣额度成功 → 创建合同成功 ✅

如果"扣额度"失败：
下单补偿（释放库存）→ 释放库存（补偿）✅
```

**为什么 B2B 供应链适合 Saga？**
- 操作之间有几秒的时间差是可接受的（不像支付秒级）
- 补偿逻辑天然存在（锁库存→释放库存，扣额度→恢复额度）
- 不用全局锁，并发性能好

**追问："Saga 有什么问题？"**
- 隔离性问题：A→B→C 执行中，B 还在进行时，另一个事务已经读到了 A 的结果。B2B 供应链场景一般用"状态机"解决——状态未到达终态前，下游不认。

## 六、API 网关 / Nginx — 流量入口

### 场景：Q4 冬储期流量骤增，后端服务压力大

**Nginx 限流**：
```nginx
# 限制交易接口每秒 200 次请求
limit_req_zone $binary_remote_addr zone=trade:10m rate=200r/s;
location /api/trade/ {
    limit_req zone=trade burst=50 nodelay;
}
```

**网关统一鉴权**：
```java
// JWT Token 校验，不用每个服务都写一遍鉴权逻辑
// 网关校验 Token → 解析出用户 ID/角色 → 透传给下游
```

**面试一句话**："API 网关做三件事：限流防刷、统一鉴权、请求路由。B2B 系统的外部对接方（银行、交易所、客户 ERP）都从网关进来，我们在这里做统一的流量管控和安全校验。"

## 七、分布式锁 — 多节点下的"排队"

### 场景：每日结算任务只能跑一次

**业务场景**：每天凌晨 2 点跑日终结算，生产环境部署了 3 个节点，如果三个节点同时跑，账就乱了。

```java
// Redisson 分布式锁
RLock lock = redisson.getLock("settle:daily:20260716");
try {
    if (lock.tryLock(0, 30, TimeUnit.MINUTES)) {
        // 执行结算逻辑
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

**追问："Redis 分布式锁有什么缺陷？主从切换怎么办？"**

→ 主节点刚写入锁，还没来得及同步到从节点，主挂了，从升级为新主——锁丢了。RedLock 算法：向多个（5个）独立 Redis 节点依次获取锁，超过半数成功才算加锁成功。但 RedLock 有争议（Martin Kleppmann 认为它不保证安全性），B2B 金融场景建议用 ZooKeeper 的临时顺序节点做分布式锁（依靠 ZAB 协议保证一致性）。

## 第二部分之网关层（midservice + midmon，Java Web 自研）

### Q1：你们网关是自研的？为什么不用 Nginx / Spring Cloud Gateway / Kong？

**答题框架**：

| 维度 | 你的回答要点 |
|------|------------|
| 背景 | 平台有 3 类租户（外部大屏/普通客户/机构客户），并发等级、鉴权重、限流策略差异极大 |
| 挑战 | 通用网关要么太重（Kong插件多但二次开发难），要么太轻（Nginx L7能力弱），通用方案难匹配多租户分级路由 |
| 方案 | 基于 Java Web（Servlet + Netty）自研：① 租户维度路由（不同客户隔离域）② 多级限流（机构客户配额远高于普通）③ 灰度发布与流量染色 |
| 收益 | 一次请求路由效率比通用网关高 30%；租户故障隔离能力是 Kong 没有的 |
| midmon | 同套技术栈，监控/告警/链路追踪，**不是独立产品而是网关的一部分** |

> **避坑**：不要贬低开源（"它们不够好"），而是说"我们的业务场景更匹配自研"。

### Q2：midservice 多实例怎么做会话一致？

**答题要点**：① 无状态化（Session 抽到 Redis）② 路由策略：一致性 Hash（同一用户落同一实例）+ 健康检查剔除 ③ 写操作走 MQ 异步（避免实例间数据不一致）。

> 关键不是"怎么做"，是"为什么这种做法在你的场景最划算"。

### Q3：网关挂了怎么办？3 道防线讲清楚

**三层防线**（按时间序）：
1. **接入层** → midservice 多实例 + 健康检查 + 自动剔除（**实例级容错**）
2. **熔断层** → midmon 触发熔断、限流、降级（**故障级容错**）
3. **兜底层** → 静态兜底页 + 关键读操作降级到缓存服务（**业务级容错**）

## 第二部分之业务中台（Java 微服务，12+ 集群）

### Q4：12+ 个微服务怎么治理？不会拆得太细吗？

**答题框架（重点题）**：
- **拆分原则**：**按业务能力垂直切**（不是按技术层水平切），每个服务对应一个完整的"业务动作"（如下单服务 = 订单生成 + 校验 + 持久化的全流程）
- **避免过度拆分**：判断标准 = 5 人以下团队维护的不要拆（拆了反而增加协作成本）
- **服务通信**：同步 = Hessian over HTTP；异步 = 内部 MQ
- **数据归属**：每个服务拥有自己的库表，跨服务走 API 或领域事件，**禁止直接 join 别人的库**（这是关键纪律）

> **加分点**：主动提"演进式拆分"——早期单体，按业务成熟度逐步拆，而不是一开始就上 12 个。

### Q5：微服务的链路追踪怎么做？

**答题框架**（基于实际栈）：
- 入口：midservice 生成 traceId，注入请求头
- 传递：HTTP 用 Header 透传；Socket 用协议字段透传
- 落点：DS 桥接层是**关键转换点**（Hessian 二进制里要预留 traceId 字段）
- 聚合：midmon 收集 + ES 存储 + 可视化
- 价值：定位一笔交易从下单→撮合→落库→缓存刷新的全链路耗时

> **杀手追问**："Hessian 协议怎么加 traceId？"——答：自定义 Hessian 序列化器扩展字段，或在协议头加固定偏移字段。
> ⚠️ 如果你团队还没做完整链路追踪，别提"全链路"，提"关键节点"更稳。

### Q6：服务间调用超时怎么设？雪崩怎么防？

**答题框架**：
- **超时分级**：核心交易 200ms / 一般业务 1s / 后台异步不设超时
- **三件套**：超时 + 重试（2次）+ 熔断（Resilience4j）
- **雪崩防线**：① 线程池隔离（不同服务不同池）② 快速失败（达到阈值直接返回兜底）③ 降级（返回缓存/默认值）
- **B2B 特殊点**：大宗交易**不能降级**（涉及钱），所以宁可拒绝也不返回错值——这是和电商最大的区别

## 第二部分之DS 数据中心（Java 防腐层，Hessian + Socket）⭐ 核心杀手锏

### Q7：DS 是什么？为什么需要它？（必问，**最该背熟**）

**满分答题框架**（5段式）：
1. **背景**：C 撮合引擎是单线程内存撮合 + 异步落库，性能极强但只暴露二进制协议；Java 业务层要的是标准 POJO/RPC 语义
2. **挑战**：如果让 Java 直接调 C，要么 Java 团队必须懂 C 协议（团队分裂），要么 C 团队被迫实现业务接口（性能被拖累）
3. **方案**：**DS 数据中心（Java）做协议转换的"翻译官"**——把 C 的二进制协议翻译成 Java 业务服务能消费的标准接口和领域事件（C 不感知业务，业务不感知 C）
4. **同步/异步双通道**：
   - 同步 = **Hessian over HTTP**（请求-响应，Java 业务调 C 撮合）
   - 异步 = **Socket 长连接**（C 撮合产生的事件反向推给 Java 业务，Java 消费做下游）
5. **我的角色**：作为 Java 技术经理，我**不需要写 C 代码，但能直接 review DS 桥接层**——这就是我"管住异构系统"的抓手

> **杀手级收尾**："异构系统的复杂度收敛在 DS 一层，C 团队和 Java 团队各自独立演进、互不阻塞——这是我们最巧妙的设计。"

### Q8：为什么序列化用 Hessian 不用 JSON / Protobuf？

**答题框架**（讲清权衡）：

| 方案 | 优势 | 劣势 | 你的选择 |
|------|------|------|---------|
| JSON | 跨语言最通用、可读 | 体积大、解析慢、字段错位不报错 | 排除（性能+稳定性） |
| Protobuf | 体积小、强 schema | 需预生成代码、调试难、跨团队维护成本高 | 排除（团队协作成本） |
| **Hessian** | Java 生态成熟、跨语言、字节紧凑、调试比 PB 简单 | 比 PB 略大 | **采用**（团队已选） |

> **加分点**："选型要看团队成本——Hessian 学习成本最低、IDE 友好、自定义序列化器扩展 traceId 也方便。"

### Q9：Socket 异步通信怎么保证消息不丢不重？

**答题框架**（4层可靠性）：

```
业务层     → 幂等消费（业务侧去重）
可靠传输层 → ACK + 重试 + 去重 + offset
连接管理层 → 心跳 + 重连 + 熔断
        ↕ Socket 长连接
        ↕ Redis 集群（去重表 + offset + 会话状态）
```

> **关键铁律**：先落地（写库/写Redis）再回 ACK，反过来就丢消息。

### Q10：DS 高可用怎么设计？（C 撮合挂了怎么办）

**答题框架**（**异构系统必问题**）：
- **熔断降级**：DS 检测 C 不可用 → 立即熔断 → 业务请求走**降级队列暂存** → C 恢复后**回放**
- **请求排队**：DS 限流（不把 C 打爆）+ 排队（让 C 按自己的节奏消费）
- **数据兜底**：关键交易状态在 DS 侧**镜像一份**，C 挂了 Java 也能查询
- **应急开关**：极端情况下，业务方允许"只接单不撮合"，先保业务可用

> **B2B 核心原则**：**钱的事绝对不能错，宁可慢也不能乱**——这是 C 引擎 + DS 设计的第一约束。

## 第二部分之交易核心（C 语言单线程内存撮合）⭐ 差异化

### Q11：为什么撮合引擎用 C 不用 Java？必问加分题

**满分答题框架**：
- **延迟确定性**：C 单线程无 GC 停顿，纳秒级；Java 即使调优也有 GC 抖动（10-100ms 不可控）
- **内存可控**：C 手动内存管理，撮合订单簿可用自定义内存池；Java 受 GC 影响不可控
- **CPU 亲和性**：C 可绑核、单线程无锁，CPU 缓存命中率高
- **行业对标**：郑商所、大商所、LME 等核心撮合都是 C/C++

> **避坑**：别说"Java不行"——要说"在这个特定场景下，延迟确定性的要求让 C 是更优选"。
> **加分收尾**："我作为 Java 技术经理，不写 C，但我通过 DS 桥接层和监控仪表盘管住它的'健康'——飞行员不需要修发动机，但要读懂每个仪表。"

### Q12：你不懂 C，怎么管交易核心？（诚实但不失分）

**答题框架**（**BOUNDARY 框架简版**）：
1. **承认边界**："我的深度领域是 Java 业务层和异构桥接层，C 撮合核心是 C 团队的领域"
2. **守住接口**："但我守三件事：① C 的输入输出协议（业务怎么调它、它回什么）② 异常行为的契约（C 出错怎么回、Java 怎么接）③ 全链路可观测（traceId 跨异构打通）"
3. **量化管控**："通过 DS 桥接层的熔断/限流/重试，把 C 的爆炸半径控制在它自己域内"
4. **协作机制**："每周 15 分钟对齐会 + 接口契约 Review 我审批 + 事故联合复盘"

### Q13：异步落库怎么做？数据一致性怎么保证？

**答题框架**（技术深度题）：
- **设计**：撮合完成 → 内存订单簿更新 → 异步队列 → 落库
- **一致性**：撮合是"主"，落库是"影子"——落库失败不能回滚撮合（会阻塞后续撮合），而是**记异常 + 重试 + 对账兜底**
- **故障恢复**：进程崩了，从内存订单簿 + 落库增量 offset 恢复状态
- **面试话术**："异步落库是典型的**最终一致**模型，靠对账兜底保数据正确性——这是分布式系统的基本功。"

### Q14：C 撮合怎么扩多模式？（挂牌/竞价/询价/代采/预售）

**答题框架**：
- 撮合核心 = **撮合算法可插拔**（策略模式）
- 模式 = 算法（价格优先时间优先 / 数量优先 / 全量成交 / 部分成交）
- 新增模式 = 加算法实现 + 在 DS 侧加模式路由
- 关键设计：**撮合核心不感知业务模式名，只接收结构化指令**

> **加分**：提"规则配置驱动"——业务模式变化不改代码，只改规则配置。

## 第二部分之数据层（MySQL 双实例 + MinIO + 缓存服务）

### Q15：MySQL 双实例是主从还是双主？一致性怎么保证？

**答题框架**：
- **大概率是主从**（双主易脑裂，中小公司慎用）
- **同步策略**：半同步复制（保证至少一从落盘）+ binlog 校验 + 定期全量对账
- **业务分流**：写主读从（读写分离）+ 关键交易强制读主（避免主从延迟导致资损）
- **C 撮合落库**：写主库（强一致需求），缓存同步走 Canal（异步最终一致）

> ⚠️ **如果你不确定是不是双主**——面试时说"读写分离 + 半同步"是较安全的回答。

### Q16：Canal 同步到缓存服务是为什么？Redis 不是吗？

**答题框架**（**已确认的事实**）：
- **架构**：Canal 监听 MySQL binlog → 推送到**独立 Java 缓存服务**（封装 Redis，对外暴露统一 API）
- **为什么包一层**：
  ① **业务隔离**：业务不直接调 Redis，统一通过缓存服务（接入门槛低、调用规范统一）
  ② **读写加速**：高频读（行情/挂牌列表）走缓存，不打 MySQL
  ③ **协议屏蔽**：未来换缓存（Redis → Memcached → 本地缓存）业务无感
- **数据流**：MySQL → Canal → 缓存服务 → Redis → 业务读

> **加分**："独立缓存服务是**B2B 场景特有的'读多写少'优化**——行情刷新、挂牌列表这些高频读场景，没缓存会把 MySQL 打死。"

### Q17：缓存一致性问题怎么解决？（cache aside 还是其他？）

**答题框架**（标准答案 + 你的场景化）：
- **基础模式**：Cache Aside（读时 cache miss 查 DB 写缓存；写时先更新 DB 再失效缓存）
- **你的特殊点**：大宗交易**不能用"先失效缓存再写 DB"**（可能写 DB 失败但缓存已失效，下次读 cache miss 又回源 DB → 数据未更新）→ **先写 DB，成功后异步失效缓存**（通过 Canal 触发）
- **进阶**：缓存击穿（热点 key 永不过期 + 后台异步刷新）/ 雪崩（过期时间加随机扰动）/ 穿透（布隆过滤器）

## 第二部分之生态接口（9+ 外部对接）

### Q18：9 个外部接口怎么统一治理？（重点题）

**答题框架**（**必答，体现架构成熟度**）：
1. **统一接入层**：所有外部接口进同一 SDK（限流/重试/熔断/超时/签名统一）
2. **适配器模式**：每个外部接口一个 Adapter，业务只调统一接口
3. **异步回调 + 状态机**：外部接口**必然是异步的**（银行打款不可能秒回）→ 状态机跟踪：已请求→处理中→成功/失败
4. **日终对账兜底**：实时异步 + 日终批量对账是**双保险**（金融场景必须）
5. **失败重试策略**：对账不一致 → 人工介入 / 自动补单

> **杀手追问**："如果银行接口挂了 2 小时你怎么办？"
> 答：① 立即熔断（不让请求堆积）② 业务侧提示"支付延迟"③ 失败的请求进死信队列 ④ 银行恢复后批量回放 ⑤ 仍失败的进人工对账。

### Q19：供应链金融接口怎么对接？和普通支付的区别？

**答题框架**（体现行业理解）：
- **本质区别**：供应链金融是**多方信任 + 资金路径长**（核心企业/银行/供应商/资金方）
- **关键能力**：授信管理 / 应收账款流转 / 资金清结算 / 风险预警
- **技术要点**：
  ① 强事务（涉及钱）→ 用可靠消息 + 幂等 + 对账
  ② 协议多变（不同银行不同接口）→ 适配器层必须灵活
  ③ 监管合规（数据留痕 / 反洗钱）→ 操作日志全审计
- **B2B 特色**：与"撮合引擎 + 履约保证"强耦合——金融的"放款"必须以"履约"为前提

## 第二部分之跨层综合题（拉开差距）

### Q20：描述一笔挂牌交易从下单到落库的全链路（**必考压轴题**）

**答题框架**（按 8 步讲清全链路）：

```
[1] 用户下单（Vue PC/移动）
   ↓
[2] midservice 网关：鉴权 + 限流 + 路由
   ↓
[3] 业务服务：参数校验 + 业务规则（规则引擎）
   ↓
[4] DS 桥接层：Hessian 序列化 → 调 C 撮合引擎
   ↓
[5] C 撮合引擎：单线程内存撮合（价格优先时间优先）
   ↓
[6] 撮合结果：① 同步返回 DS → 业务响应用户
            ② 异步 Socket 推领域事件 → DS → 业务订阅
   ↓
[7] 异步落库：撮合结果进 MQ → 落库服务写 MySQL
   ↓
[8] Canal 监听 binlog → 同步到缓存服务 → Redis 缓存刷新 → 用户看到行情
```

> **核心讲清两件事**：
> ① **同步/异步边界**：用户感知的是同步（步骤 6①），系统内部是异步（步骤 6② + 7 + 8）
> ② **异构协同点**：DS 在第 4 步（Java→C）和第 6 步（C→Java）双向翻译
>
> **加分收尾**："全链路每一段都能独立容错，单点故障不会让整笔交易失败——这就是**异构架构的工程化成熟度**。"

### Q21：双 11 / 大促流量 10 倍，怎么扛？

**答题框架**（5 招全用上）：
1. **网关层**：midservice 水平扩 + 限流 + 排队
2. **读链路**：缓存前置（行情/挂牌列表 90% 走缓存）
3. **撮合层**：C 引擎限流保护（不被打爆）+ 关键交易走快路径
4. **DB 层**：读写分离 + 慢 SQL 提前优化 + 必要时降级非关键写
5. **应急**：业务分级（核心交易保证 / 非核心功能降级 / 营销活动延后）

> **加分**："大宗 B2B 流量比 C 端电商低，但**单笔资损大**——大促设计要'稳'优先，不是'快'优先。"

### Q22：项目里最大的技术挑战是什么？你做了什么？（开放式压轴）

**答题方向**（挑你最熟的）：

| 候选挑战 | 角度 |
|---------|------|
| **异构桥接层稳定性** | DS 的熔断降级 + 全链路 traceId 打通 |
| **9 个外部接口统一治理** | 适配器 + 状态机 + 对账兜底 |
| **技术债治理** | 业务奔跑期如何不踩雷 / 用绞杀者模式渐进重构 |
| **团队管理转型** | 从"自己救火"到"团队救火 + 业务上游" |

> **答题公式**：`背景（业务复杂度）→ 挑战（具体卡点）→ 我的方案（架构+管理双管齐下）→ 量化收益（故障率↓/效率↑）→ 反思（哪里还能更好）`
