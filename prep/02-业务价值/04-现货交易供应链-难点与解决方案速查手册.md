## 0. 一句话总览（电梯版）

> **B2B 现货交易供应链的本质难点是「让陌生对手方在「金额大、频次低、履约长、价格波动剧烈」的条件下完成可信交易**——平台用「四流合一+履约保证+信用体系+生态对接」系统性解决信任问题，用「异构架构+规则配置+数据中台」解决扩展性问题。

面试开场可直接用这一句。后面任何展开都围绕"信任"和"扩展"两个根因。

## 1. 现货 vs 期货 / 远期：先讲清定位

| 维度 | 现货 | 期货 | 远期 |
|------|------|------|------|
| **交割** | 即时/短期（T+0~T+7）实物交割 | 标准化合约，到期交割 | 定制化合约，到期交割 |
| **价格** | 当下市场价（一单一价） | 期货所公开竞价 | 双方议定 |
| **核心痛点** | **实物交付**（货权/物流/质检）+ 信任 | **价格风险**（保证金/对冲/结算） | 履约信用（违约无保证金兜底） |
| **金融属性** | 弱 | 强 | 中 |
| **平台核心能力** | 仓储+物流+仓单+质检 | 撮合+清算+风控 | 合同+履约跟踪 |
| **典型平台** | 找钢网、欧冶云商、你的现货平台 | 大商所、郑商所、文华财经 | 银行间 OTC |

> **面试金句**：「现货的核心是「货」，期货的核心是「钱」——所以现货平台的难点是物理世界的复杂，期货平台的难点是金融世界的复杂。**两个系统的设计哲学完全不同**：现货系统是「物流+商流+资金流」三流融合，期货系统是「风控+清算+对冲」三件套。」

## 2. 现货供应链全链路：四流视角

```
                  ┌────────────────┐
                  │   需求/供给     │  ← 起点：买家/卖家入场
                  └────────┬───────┘
                           │
            ┌──────────────┴──────────────┐
            ▼              ▼              ▼
       ┌─────────┐    ┌─────────┐    ┌─────────┐
       │ 信息流  │    │ 商流    │    │ 物流    │  ← 三流并行
       │ 行情/资讯│    │ 询价/签约│    │ 仓储/运输│
       └────┬────┘    └────┬────┘    └────┬────┘
            │              │              │
            └──────────────┼──────────────┘
                           ▼
                    ┌─────────────┐
                    │   资金流     │  ← 结算/融资/对账
                    └──────┬──────┘
                           ▼
                  ┌────────────────┐
                  │   交收/履约     │  ← 终点：货权转移
                  └────────────────┘
```

**四流合一的价值**：
- **商流**：合同/订单/发票（权属凭证）
- **物流**：仓单/运单/签收（实物凭证）
- **资金流**：付款/收款/融资（资金凭证）
- **信息流**：行情/数据/审计（合规凭证）

> **核心洞察**：四流割裂是传统贸易所有痛点的根因。平台的核心价值 = **让四流在同一个系统里闭环**，所以"票货一致""四流可追溯"成为税务合规/反洗钱/审计的硬性要求。

## 3. 十大核心痛点 + 对应方案（速查表 ⭐ 最重要）

| # | 痛点 | 根因 | 平台方案 | 真实系统模块 | 难度 | 优先级 |
|---|------|------|---------|------------|------|--------|
| **1** | **货权不真/一货多卖** | 仓单无统一标准，靠人工登记 | 电子仓单 + 区块链存证 + 唯一码 | 仓单服务 + 第三方存证接口 | 高 | P0 |

| **8** | **流程线下化、合同非标** | 各签各版本、靠人盯 | 标准化电子合同 + 7 大交易模式 + 工作台 | 合同中心 + 规则配置 + 工作流 | 中 | P1 |
| **9** | **税务合规断点（票货不一）** | 商流/物流/资金流割裂 | 四流合一闭环 + 发票自动化 + 进项抵扣 | 发票服务 + 对账引擎 | 高 | P1 |

## 4. 五大架构决策（决策框架 ⭐ 面试高频）

> 面试中常被问"为什么这么设计"，不是问"怎么实现"。下面是 5 个核心架构决策。

### 决策 1：为什么 C + Java 异构架构（而不是统一 Java）

- **业务倒逼分层**：撮合要微秒级 → C 单线程内存撮合；业务要灵活 → Java 微服务
- **不要为了统一而统一**：Java GC 停顿不可控，大宗撮合场景下 0.1% 的 500ms 毛刺 = 价格窗口失效
- **关键：DS 数据中心做防腐层**——C 黑盒只暴露二进制协议，DS 翻译为 Hessian，Java 侧无感

**话术**：
> 「**业务的自然分层倒逼了技术的分层**。我们不是「为了异构而异构」——C 引擎是性能极致，Java 中台是业务灵活，DS 是我能 review 的治理抓手。**这正是技术经理的价值：管住 DS 就管住了整个异构链路的稳定性**。」

### 决策 2：为什么异步落库（而不是同步等 MySQL ACK）

- **撮合的核心职责是成交，不是存储**：撮合成功的关键路径上不能有数据库
- **异步落库架构**：内存订单簿（微秒级）→ 后台线程池写 MySQL → 失败写 WAL 回放
- **代价**：极端情况下出现"内存有但库无"——通过"以内存为准、异步回放、幂等补偿"解决

**话术**：
> 「如果撮合完要等 MySQL ACK 确认，撮合性能就被数据库写入能力绑死了。**异步落库换来的是撮合吞吐量和确定时延**，代价是引入数据一致性复杂度——这部分我们用「内存为准 + WAL 回放 + 定时对账」来兜底。」

### 决策 3：为什么用事务消息而不是 Seata/XA（保证金场景）

- **全局锁是性能毒药**：银行冻结接口耗时 3 秒，全局事务持有锁 3 秒 → 履约流程被阻塞
- **最终一致性 > 强一致性**：宁可短暂不一致，不要长期不可用
- **状态机约束做兜底**：履约单 `transition(事件)` 禁止非法跳转，编译期防呆

**话术**：
> 「金融场景下，Seata 的全局锁是「正确但不可用」——3 秒锁持有时间会拖垮履约吞吐。我们选「事务消息 + 最终一致 + 状态机约束」：**分布式系统设计的第一原则是「让系统可恢复」而不是「让系统不出错」**。」

### 决策 4：为什么用 Canal + 缓存服务（而不是直接 Redis Cluster）

- **异构数据同步是核心难点**：C 撮合→MySQL→前端三端，链路长、节点多
- **缓存服务不是简单 Redis 封装**：是「行记录 → KV 转换 + 三端推送分发」两件事的合集
- **解耦推送逻辑**：如果 Canal 直推前端，前端要懂 binlog，要懂数据格式，乱套

**话术**：
> 「**缓存服务是「数据结构转换 + 推送分发」的中间层**。前端只关心 Redis 里的最终态，不关心数据怎么来。Canal 挂了不影响交易（不影响 C 撮合主流程），缓存服务挂了不影响撮合，只影响行情展示——**降级边界清晰**。」

### 决策 5：为什么用规则配置中心（而不是写死业务逻辑）

- **B2B 业务规则多变**：不同品类、不同客户、不同模式的保证金比例/审批流/计费规则都不同
- **改代码 vs 改配置**：改代码 1 周上线 + 回测 + 上线审批；改配置 1 分钟生效 + 可回滚
- **元能力**：让运营/产品能自助配置，业务人员驱动业务变化

**话术**：
> 「**B2B 业务最贵的成本是「每开一个新业务就要改一次代码」**。规则配置中心的本质是「把业务策略从代码中抽出来」——业务人员通过配置就能定义「A 类客户用 X 保证金比例 + Y 审批流」，技术团队不再被业务变更打断。」

## 5. 痛点 → 真实系统模块 映射（架构视角）

把第 3 节的 10 个痛点反向映射到用户的真实异构系统：

```
痛点 1 (货权)  →  仓单服务 + 第三方存证接口
痛点 2 (信任)  →  资金服务 + 银行存管 + 履约状态机
痛点 3 (价格)  →  套保引擎 + CTRM 外部接口
痛点 4 (资金)  →  银行/支付/供应链金融 9+ 外部接口
痛点 5 (质量)  →  质检服务 + 合约模板
痛点 6 (物流)  →  物流追踪 9+ 外部接口
痛点 7 (行情)  →  缓存服务 + Canal + 三端推送
痛点 8 (流程)  →  7 大交易模式 + 合同中心 + 规则配置
痛点 9 (税务)  →  发票服务 + 对账引擎
痛点 10 (风控) →  风控引擎 + 信用中心

通用底座：
- DS 数据中心：所有异构通信（C↔Java、外部接口↔Java）
- midservice 网关：所有客户端请求的统一入口
- midmon 监控：所有服务健康度和链路追踪
- MySQL 双实例：交易/管理/数据中心分离
- MinIO：合同/凭证/质检报告等文件存储
```

> **架构洞察**：用户的 9+ 外部接口（银行/物流/CTRM/开票/咨询/企查查/供应链金融/证书/短信）不是"对接外部"，而是**把行业能力外包给生态**——银行做资金、物流做运输、CTRM 做风控数据、企查查做征信。**平台的核心是「连接器 + 编排器」，不是「全功能闭环」**。

## 6. 面试话术 10 条（按出现频率排序）

### Q1：请用 2 分钟介绍你们平台
> 「我们做的是 B2B 大宗商品现货交易平台，覆盖**能源、煤炭、金属、农产品**等十几个行业，**撮合引擎用 C 写**（单线程内存撮合、毫秒级延迟），**业务中台用 Java 微服务**（12+ 服务），**接入层走 midservice 自研网关**，三端覆盖大屏、PC、移动。**关键点是异构系统之间的桥接层——DS 数据中心**——把 C 引擎的二进制协议翻译成 Java 对象，是我作为 Java 技术经理能直接 review 代码的地方，**管住 DS 就管住了整个异构系统的稳定性**。」

### Q2：你们平台解决了什么核心问题？
> 「**一句话：解决「陌生对手方在大宗场景下的可信交易」**。具体是四件事——**让四流合一**（商流/物流/资金流/信息流在系统内闭环）、**让违约有代价**（履约保证+信用体系）、**让价格可对冲**（点价/基差/套保三件套）、**让数据可决策**（行情中心+数据中心反哺）。**根因是信任，所有方案都围绕信任构建**。」

### Q3：现货和期货系统的区别是什么？
> 「**现货的核心是「货」，期货的核心是「钱」**。现货系统的难点是物理世界的复杂——仓单、物流、质检、货权；期货系统的难点是金融世界的复杂——保证金、对冲、结算价。**所以两套系统的设计哲学完全不同**：现货是「物流+商流+资金流」三流融合，期货是「风控+清算+对冲」三件套。」

### Q4：你们最大技术挑战是什么？
> 「**是「让 C 撮合引擎和 Java 业务中台在异构条件下保持一致」**。C 单线程撮合性能极致但只暴露二进制协议，Java 微服务灵活但 GC 不可控。**DS 数据中心做防腐层**——同步走 Hessian over HTTP，异步走 Socket——**让两侧各自演进但保持契约**。**作为技术经理，我管住 DS 就管住了整个链路**。」

### Q5：怎么保证数据一致性？
> 「**分级一致性，不要一刀切**。撮合主链路用 C 内存 + 异步落库，**最终一致**；履约单状态变更用事务消息，**最终一致**；资金冻结用同步调用 + 幂等 + 补偿，**强一致**。**该强的地方强，该弱的地方弱**——分布式系统设计的第一原则是「让系统可恢复」而不是「让系统不出错」。」

### Q6：怎么防止超卖？
> 「**三道防线**。第一道：C 撮合引擎单线程内存撮合 + CAS 扣减库存，**内存里就挡住了**。第二道：DS 数据中心超时熔断 + 幂等校验，**C 超时不重试**。第三道：Java 业务层 MySQL 用 `resource_id + version` 乐观锁，**数据库兜底**。**三道防线独立演进、互不依赖，任何一道失守都不会全局崩盘**。」

### Q7：你们 9+ 外部接口怎么管理？
> 「**作为连接器和编排器，不是全功能闭环**。银行做资金、物流做运输、CTRM 做风控数据、企查查做征信——**行业能力外包给生态**。**DS 数据中心统一做协议适配**——银行/物流/CTRM 都是异构系统，DS 是「外部异构 + C 引擎异构」的双重防腐层。**新增一个外部接口 = 在 DS 加一个适配器，业务侧无感**。」

### Q8：客户最在意什么？
> 「**信任和效率**。信任层面：货是不是真的？钱会不会丢？违约有没有代价？效率层面：流程是不是能线上化？资金是不是能 T+0 到账？信息是不是实时？**信任是 P0（没有就不来），效率是 P1（有了才留下），增值是 P2（留下才付费）**。」

### Q9：如果重做一次，你会改什么？
> 「**统一主数据中心，而不是用 MQ 同步副本**。我们吃过亏——客户、商品、订单各业务系统都维护自己的副本，靠消息中间件同步，**MQ 挂了数据就不一致**。**正确做法是「1 份权威数据 + N 个系统引用」**——业务系统走 API 查主数据中心，不维护副本。**这是架构范式的转变，从「烟囱式」走向「平台化」**。」

### Q10：你的技术管理价值是什么？
> 「**不在「能写代码解决某个 Bug」**，而在四件事——**能识别根因**（不是头痛医头）、**能给渐进式方案**（不搞大拆大建）、**能复用现有资产**（DS/Canal/midservice 都有定位）、**能管住异构系统**（C 是黑盒但 DS 是我手里的抓手）。**技术经理的价值 = 驾驭复杂度 + 让团队少走弯路**。」

## 7. 客户汇报话术 5 条（场景化）

### 给老板汇报（3 分钟）
> 「咱们平台解决的是**大宗贸易「信任缺失、效率低下、资金难」三个老问题**。传统模式靠人脉、Excel、电话，**20% 的订单因为信息不对称或信任问题流失**。我们用**线上化 + 履约保证 + 供应链金融**三板斧，把成交率提升 30%、资金周转提速 50%、违约率降到 1% 以下。**核心壁垒是 9+ 生态对接 + 异构架构 + 12+ 业务中台**——这是后来者 3 年内追不上的。」

### 给技术客户介绍（5 分钟）
> 「我们做的是**异构四层架构**——C 撮合引擎 + Java 微服务中台 + midservice 自研网关 + 三端接入。**异构的关键问题是协议桥接**，我们用 **DS 数据中心**做防腐层。**性能关键路径用 C 保证速度，业务复杂度用 Java 保证可维护性**。这背后是 12+ 业务服务集群，**可水平扩展、可独立演进**。」

### 给业务客户介绍（5 分钟）
> 「简单讲就是三件事——**帮你把货卖出去、把货买进来、把资金周转起来**。卖货：你挂牌我们撮合，找钢网/欧冶云商都这么干。买货：你想锁定未来价格我们提供点价服务，怕亏。资金：你货压在仓库里我们做仓单质押融资。**所有操作在一个平台完成，不用换系统**。」

### 给风控/合规部门介绍（5 分钟）
> 「平台做了**事前-事中-事后三层风控**。事前：信用评级 + 额度授信 + 实名认证。事中：实时保证金监控 + 大额交易拦截 + 关联账户检测。事后：逐日盯市 + 风险敞口报告 + 异常追溯。**所有操作留痕存证、关键事件可一键回溯**——满足监管对「四流合一」和「可追溯」的硬性要求。」

### 给银行/资金方介绍（5 分钟）
> 「我们做的是**用真实贸易背景给中小企业输血**。应收账款融资、仓单质押融资、预付款融资——每一笔融资都有**真实的合同 + 真实的仓单 + 真实的物流轨迹**做支撑，**银行敢放款**。**平台沉淀的交易数据本身就是中小企业的信用画像**——融资客户在我们平台有 N 笔履约记录、有 M 吨库存、有 K 万流水，这就是银行最缺的「数据抓手」。」

## 8. 常见追问与应对（防被问倒）

| 「你的角色是？」 | 「**管住 DS 这个 Java 桥接层 + 主导规则配置和数据中台建设 + 推动业务中台的渐进式重构**」 |
