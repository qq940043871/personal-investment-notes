一、一句话定位（自我介绍 3.0 版，60 秒）

"我是一个把业务当第一需求文档的技术经理。大宗商品这个行业，技术方案错一点，客户丢的是真金白银——所以我们团队的文化是：先搞懂客户怎么赚钱，再决定代码怎么写。我带队承建过河南能源的大宗商品交易平台和中原云商阳光采购平台，销售端帮客户累计做出 8 亿溢价，采购端把周期从 20 天压到 7 天；现在主导的供应链产品覆盖了从国企交易中心、政府资源平台、国有要素交易场所到民营贸易商五类客户。技术上我的主线是领域驱动的架构设计——合同域和履约域解耦、双轨履约引擎——同时我也在做 AI 工程化落地，知道 LLM 能力和工程约束的边界在哪。"

结构拆解：定位金句（10s）→ 交付战绩（20s）→ 技术主线（20s）→ 差异化（10s）。全程没有一句"我精通 Java/微服务"这种废话——技术细节留给追问。

技术架构版的四档开场（30 秒 / 1-2 分钟 / 3 分钟 / 5 分钟 × 版本 A/B）以 06-面试话术与背诵手册.md 第一部分为权威版本。

二、业务理解力：五层进阶模型（自证体系）

面试官验证你"懂不懂业务"的方式不是问概念，而是看你能聊到第几层。每往下一层，竞争力指数级上升：

层次能力描述你的证据（能脱口而出的话）
L1 知道流程说得出交易→签约→履约→结算链路"大宗交易七环：询价、看货、签约、付款、履约、结算、融资"
L2 知道痛点每一环的真实麻烦和后果"比价差两分钟价就没了；合同晚三天 400 万的单子飞了"
L3 知道赚钱逻辑每类客户靠什么赚钱、在哪流血⭐ 见下方"五方盈利逻辑速查表"
L4 知道角色 KPI客户方每个用系统的人考核什么"销售总监看溢价率，财务看回款账期，风控看敞口，仓管看货权清不清晰"
L5 能预判演进客户明年会要什么"五个客户都在殊途同归走向'交易+物流+金融'的产业互联网——河南能源 2026 年的转型招标、林控从卖活立木扩到融资中心/发票税务/物流，都是证据"

L5 是技术经理的分水岭：L1-L3 是高级工程师也能有的认知，L4/L5 只有真正对客户结果负责的人才有。面试中主动展示 L4/L5，直接和其他候选人拉开身位。

三、技术把控力：四个维度（自证体系）

业务理解让你"说得上话"，技术把控让你"拍得了板"。四个维度，每个都备好"决策故事"：

3.1 架构判断力——三个代表作

每个架构决策按"业务问题 → 备选方案 → 取舍逻辑 → 代价"讲，这是技术经理和架构师的通用语言。完整技术底稿（表设计、五种交收模式等）见下篇 Q4：

  • 代表作 1：合同域与履约域解耦——业务问题：大宗合同变更极其频繁（补充协议/数量增减/交期调整是日常），履约状态如果耦合在合同上，每次变更都是数据迁移事故。备选方案：一张大宽表全搞定 vs 域解耦+事件联动。取舍：解耦后读写路径变长，但换来合同版本链清晰、履约独立演进——变更频率决定了解耦是必选项。代价：跨域一致性要靠事件+对账兜底，不能靠数据库事务。
  • 代表作 2：双轨履约引擎——业务问题：交收节奏没有统一标准——交易所类客户要强顺序（先款后货），长期合作客户要灵活并行。备选方案：一个万能流程引擎硬扛 vs 双轨（状态机轨 + 事件规则轨）。取舍：顺序轨用状态机换确定性，自由轨用事件驱动换灵活性，底层共用任务数据结构，监控视角统一。代价：自由轨的异常补偿逻辑复杂，用规则引擎配置化补偿策略，不硬编码。
  • 代表作 3：支付渠道适配器——业务问题：平台不能碰资金池（二清是红线），但每个客户的银行/持牌支付通道都不一样。取舍：统一适配器接口 + 渠道插件化（银行直连/银企直联/第三方），资金预检用两阶段提交思路。代价：渠道间能力差异要在适配层抹平（到账时效、回单格式），对账逻辑每渠道一份。

3.2 关键 Trade-off 清单（高概率被考 ⭐）

追问你的回答框架
为什么不用分布式事务跨域保一致？"跨域（合同-履约-结算-仓单）我选事件驱动+每日对账兜底，不用 2PC/TCC——因为大额资金场景宁可慢不可锁，同步事务把可用性押上去了；但资金预检这一跳我反而用了 2PC 思路，因为钱的事不能有中间态"
为什么履约用状态机+事件双轨而不是纯工作流引擎（Activiti/Flowable）？"工作流引擎擅长'人审批'，但大宗履约的核心是'货款票三轨的状态推进'，人工节点只占三成。状态机+事件让机器节点毫秒级推进，人只处理异常"
为什么原型阶段不用 Vue/React 组件化？"1300 页原型的诉求是'快验证业务模型'，静态 HTML+CDN 让任何一页都能双击打开给客户演示。但我知道它的边界——所以现在做组件收敛和契约先行的转型规划"（顺势引出技术债管理）
套保系统为什么自研而不是买现成的？"敞口计算和现货合同强耦合——点价量、在途量、已点未发、期货头寸要实时轧差，通用风控软件拿不到这些一手数据。自研才能把'现货合同→敞口→期货头寸'做成一条链"

3.3 工程治理力——两个真故事

下篇 Q6 另有 STAR 版（故事 2 / 故事 3），两者同源：本节给"讲点"，Q6 给"S/T/A/R 结构 + 数字"。

  • 故事 A：接口资产化——870 个业务请求、244 个文件夹的手工 Postman 集合，写 Python 工具一键生成，统一客户端参数展开和后端 directives 包装两种格式，跨脚本一致性由工具保证。讲点："接口文档漂移是团队协作的第一隐性成本，我把它从负债变成资产。"
  • 故事 B：ICC 系统重构——参数从本地配置文件迁到 HTTP 接口按 deviceId 实时获取，设计降级路径（本地缓存兜底），分环境灰度。讲点："任何去中心化方案必须先设计好降级路径，否则是把稳定性问题换成可用性问题。"

3.4 技术债与优先级管理（管理成熟度的直接证据）

主动讲这套方法论："我把技术债分三类排优先级——

  1. 流血债（影响正确性/资金安全，如对账兜底缺失）→ 本迭代必须还
  2. 放血债（拖慢交付速度，如无组件库、接口无契约）→ 排进季度规划，按"每新增一页放大多少成本"量化给老板听
  3. 美容债（风格不统一如图表库混用）→ 顺手还，不立项
⭐ 金句："技术经理的价值不是消灭所有技术债，是让团队知道哪些债在吃利息、哪些债可以先欠着。"

四、杀手锏：业务语言 → 技术方案翻译表

这是"业务×技术"双能力最直观的自证形式——客户说的每句人话，你都能接住并翻译成架构。面试中主动展示这张表的能力，面试官会记住你：

客户的原始话术（业务语言）背后的业务实质我的技术翻译
"价格天天变，报价跟不上"期现联动定价，人工调价永远滞后行情跟盘调价规则引擎（挂牌价=期货主力+升水），四种定价模式（固定/浮动/基差点价/公式）
"钱打过去了，对方不认账"支付到账不可见，信任死结收付款单+资金池核销记账+到账状态实时同步给履约状态机卡点

"这货到底是谁的？"货权不清，一女二嫁电子仓单 + 货权流转留痕 + 质检报告扫码溯源批次

"领导要看数据，我攒一周报表"数据分散在各子系统决策驾驶仓 + 上帝视角，四流数据一屏透视
"老供应商靠谱，新面孔不敢碰"信任成本高，陌生人交易难履约率/成交记录/客户评价的信用档案体系
⭐ 使用方法：面试中被问任何业务问题时，先用这张表的逻辑回答——"客户说 X，背后的实质是 Y，我们用 Z 解决"——三段式，每一段都同时在证明业务理解和技术能力。

五、高光问答设计（预演 Q&A）

Q1："你怎么定位技术经理这个角色？"
"三个词：翻译、拍板、兜底。翻译——把客户生意语言翻成架构语言，把技术约束翻成老板听得懂的成本收益；拍板——方案分歧时敢做决定并为结果负责，我的原则是'两条路都对时选可回退的那条'；兜底——出了问题技术经理站在最前面，先恢复业务再复盘根因，不甩锅给环境或某个人。"
Q2："业务方需求很急但架构不允许，怎么办？"
"先问一句：急的是什么？大多数'急'是业务想要结果而不是想要功能。回答框架：①确认业务截止时间的真实约束；②给分层方案——先用 80% 方案快速上线，同时明确技术代价记账；③把这次妥协变成下次重构的输入。妥协可以，但必须被记录、被定价——无意识的妥协才叫技术债失控。"
Q3："你怎么让技术团队懂业务？"
"三个机制：①新人下现场——没有跟客户开过会不许写核心模块；②需求评审讲钱——每个需求先回答'这帮客户多赚钱还是少亏钱'，答不上来的需求降级；③业务术语表进代码——领域模型、变量命名和客户的行业黑话一一对应（仓单就是仓单不是 inventory_doc），看代码就是在看业务。"
Q4："举一个你业务判断救了技术方案的例子？"（⭐最出区分度的问题）
"最早设计履约系统时，技术方案是纯流程引擎。但我看了太多客户的真实交收——国企要强管控顺序交收，民营贸易商两笔货可能今天发货明天才补合同。是业务判断告诉我：履约节奏不存在行业标准，所以必须有双轨。这个判断不是从技术博客来的，是看客户怎么干活来的。"
Q5："AI 都这么火了，你怎么看技术经理要不要 all in？"
"我的原则是场景成熟度决定投入度。我自己在做 Agent 工程化，知道 LLM 的能力边界——产品里 AI 的落点选的是智能推荐、单据识别、风控辅助，这些是'AI 提效、人兜底'的场景；资金操作、合同生效这类强一致性场景，AI 只做提示不做决策。用 AI 的前提是你知道它什么时候不可靠。"

第一部分：提问框架优化

1.1 原始九问的问题

原始九问是：产品是什么 → 目标客户 → 客户特点 → 解决什么问题 → 行业痛点 → 产品如何解决 → 产品现存痛点 → 技术经理怎么解决 → 技术经理解决了什么问题。

毛病：九个问题里有三组重叠（"解决什么问题"≈"行业痛点"≈"产品如何解决"），且叙事顺序是"产品→痛点→自己"，听着像产品发布会后临时加了个个人述职。面试官真正想听的是一条线：你懂业务 → 你知道痛在哪 → 你干了什么 → 你还能干什么。

4.2 核心架构设计一：合同域与履约域解耦 ⭐

"我们把合同域（商业契约：谁、什么、多少、什么价）和履约域（执行：付款、发货、收货、开票）彻底解耦。为什么？因为大宗贸易中合同变更极其频繁——补充协议、数量增减、交期调整是家常便饭，如果把履约状态耦合在合同上，每次变更都是一场数据迁移事故。解耦后，合同是版本链（原合同+N个补充协议），履约是独立的计划与任务流，两者通过事件总线联动。核心表设计：contract / contract_item / contract_party / fulfillment_plan / payment_order / shipment_order / receipt_settlement / fund_pool / invoice / refund_order。"

4.3 核心架构设计二：双轨履约引擎 ⭐⭐（必须讲透）

"大宗贸易的履约没有统一节奏，我们抽象出双轨引擎，由合同上的 delivery_mode 决定走哪条轨：
  • 顺序交收（Sequential）——状态机/工作流引擎强制有序（先款后货类），强一致，适合标准化、风险高的交易
  • 自由交收（Free-form）——事件驱动+规则引擎并行流转，动态条件判定，适合长期合作客户的灵活交收
  • 两轨共用同一套底层履约任务数据结构，监控和风控视角统一
  • 之上再叠加五种交收模式：款到发货、货到付款、定金+尾款、分期付款、信用证

加分点：主动讲 trade-off——"顺序轨用状态机换确定性，自由轨用事件驱动换灵活性，代价是自由轨的异常补偿逻辑复杂得多，我们用规则引擎把补偿策略配置化，而不是硬编码。"（自证角度的取舍框架见上篇 §3.1 代表作 2。）

4.4 支撑底座（一笔带过即可）：技术底座 126 页设计：统一身份 IAM、主数据 MDM、低代码、事件总线 eventhub、规则引擎、中间服务 midservice、数据中心、监控，以及 DDD + EDA + FSM 的整体方法论。

3.1 总体安排：5 天冲刺训练

天主题任务自检标准
D1叙事链打底背熟 Q1 电梯陈述（60秒版+90秒版各一遍）；通读 Q2-Q4 底稿，把七环痛点表抄写一遍对镜 60 秒讲完 Q1 不卡壳；痛点七环能默写环节名
D2架构深度深练 Q4：合同履约域解耦 + 双轨引擎，动手画架构图（域划分/状态机/事件流各一张）；准备 trade-off 问答白纸手画双轨引擎图 3 分钟内完成；能说出每条轨的代价
D3自我批判与规划精练 Q5/Q7：现存痛点表逐条准备追问预案；写出一版自己的"三个月优先级"并录音每个痛点能顶住两轮追问不露怯
D4STAR 故事打磨从五个故事选 3 个，写成 200 字卡片，各录音 90 秒；互相交叉检查是否有数字结果和关键决策听录音：S/A/R 比例约 1:4:2，没有流水账
D5全链模拟找人或用 AI 扮演面试官，按追问库随机轰炸 30 分钟；复盘录音，标记卡壳点七问全部能在总 15 分钟内完成主线陈述

3.2 每日微训练（碎片时间）

  • 晨间 10 分钟：随机抽一个 Q，脱稿口述并录音，回听检查"嗯/然后/就是说"的次数
  • 电梯测试：每次换一种身份讲 Q1——对 CEO 讲（价值/收入）、对 CTO 讲（架构/技术债）、对业务总监讲（客户/场景），三种版本都要顺
  • 痛点抽卡：把七环痛点做成卡片，随机抽一环，30 秒内说出"痛点场景 + 产品方案 + 对应子系统"三连

3.3 高频追问库（模拟面试必练）

业务类追问：

  1. 大宗商品和普通 B2B 电商的本质区别是什么？（答：非标/大额/长周期履约/价格波动风险/信任成本，履约和金融是重心）
  2. 你们和找钢网/欧冶这类平台的差异？（答：对标项目里的《客户案例与行业对标手册》，强调履约层深度和金融闭环）
  3. 五种交收模式为什么要做成系统而不是配置模板？
  4. 顺序交收和自由交收，客户怎么选？选错了怎么办？（答：引擎支持轨间切换策略 + 追问预案）
  5. 平台怎么解决"鸡生蛋"问题——没有买家卖家不来？（答：先从核心企业/园区切入 + 金融服务作为钩子）

架构类追问：

  1. 双轨引擎共用数据结构，怎么避免互相污染？
  2. 事件驱动那套，消息丢了/重复了怎么办？（答：幂等键 + 对账兜底 + 履约 trace 回放）
  3. 资金预检 2PC 具体怎么做的，和 TCC/Saga 的取舍？
  4. 电子签章、CA、存证的合规链路怎么设计？（答：契约锁/e签宝/法大大方案分析在 01-design/signauth/）
  5. 仓单防造假怎么做的技术保障？（答：电子仓单 + 货权流转留痕 + 质检报告扫码追溯批次 + 监控风控中心）

管理类追问：

  1. 你的团队多大？怎么分工？怎么做代码评审和技术债管理？
  2. 讲一次你和技术骨干的意见冲突，怎么解决的？
  3. 怎么估算工期？延期了怎么处理？
  4. 你怎么平衡业务需求的紧急性和架构重构的长期性？
  5. 为什么离开现在的公司/团队？（提前准备，落在"追求更大的业务纵深"而非抱怨）

3.4 面试现场执行清单

  • 开场 60 秒定调：Q1 电梯陈述务必背熟，第一印象不可重来
  • 白板/纸笔：主动要求画图讲双轨引擎——技术经理面试中"能画图"本身就是加分信号
  • 数字钩子：至少准备 5 个数字（24 个子系统、5 种交收模式、2 条履约轨、15 个角色、870 个接口请求），陈述中自然植入
  • 自我批判的度：痛点讲 3-5 个即可，每个必须带解法；只说痛点不给方案等于自曝
  • 反问环节（体现层次）："这个岗位接手的系统当前最大的技术债是什么？""团队现在最缺的能力是业务深度还是工程规范？""未来一年产品和技术的优先级排序是怎样的？"

3.5 自评分表（每次模拟后打分）

维度满分自评
电梯陈述流畅度（60秒内、无填充词）10
客户画像具体度（有人物有场景有数字）10
痛点叙事感染力（有故事有后果）15
架构讲解深度（能画图、有 trade-off）20
自我批判分寸（有痛点必带解法）10
STAR 故事可信度（有决策有数字）20
追问抗压（两轮追问不卡壳）15
总分100
