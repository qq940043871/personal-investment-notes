## 第一部分：先做认知校准——你到底缺什么

### 1.1 别把"角色界"和"能力界"搞混

你说"AI 是我的薄弱部位"——这句话里混了两个完全不同的东西：

| 维度 | 你的真实状态 | 面试里的价值 |
|------|------------|------------|
| **AI 项目管理 / 落地角色** | 弱（只参与选型和前期原型） | 别吹，吹了必翻车 |
| **AI 工程机制层（架构）** | **强**（只是没用 AI 的术语说过） | **这是你的真实卖点** |
| **AI 算法 / 模型层** | 弱（RAG 检索策略、微调、训练） | 诚实划界即可，岗位也不要 |

**结论**：JD 招的是"把 AI **接进企业系统**"的架构师，不是算法工程师。你缺的是**术语对齐 + LLM 特有的物理约束认知**，不是能力本身。

### 1.2 传统后端 vs LLM 应用：差在哪

这是整本手册的地基，看懂这张表，后面全是它的推论。

| 维度 | 传统后端（你熟的） | LLM 应用（要补的） | 工程后果 |
|------|-----------------|-----------------|---------|
| **输入** | 结构化参数，确定 | 自然语言，模糊、有歧义 | 必须做输入理解/分类/抽取 |
| **输出** | 确定、可校验 | **概率生成，同样输入可不同输出** | 必须评测 + 兜底 + Schema 校验 |
| **正确性** | 由代码保证（100%） | 由概率保证（"大概率对"） | 需要"确定性逻辑"与"AI 能力"分层 |
| **成本** | CPU/内存/带宽 | **按 token 计费，随文本长度线性涨** | 需要上下文预算 + 成本护栏 |
| **延迟** | 毫秒级 | **首字延迟 + 逐 token 生成，秒级** | 需要流式输出 + 异步化 |
| **状态** | 会话/事务显式管理 | 模型本身**无状态**，上下文要自己拼 | 上下文工程 + 状态外置 |
| **可测性** | 单元测试断言相等 | 输出是开放文本，**没法断言相等** | 需要评测集 + 指标 |

> 一句话记住：**LLM 应用的一切工程复杂度，都来自"模型是不确定的、按 token 收费的、无状态的、会说谎的"这四件事。** 后面每一节，都是在对付这四件事之一。

### 1.3 你的定位一句话版

> "我在 AI 侧是**架构视角**——选型怎么选、AI 怎么接进业务系统、权限怎么收口、怎么评测和兜底；模型算法层的细节我不装懂，但我能把 AI 从 demo 做成可控的生产系统。"

<a id="二"></a>
## 第二部分：三条物理约束——所有 AI 工程手段的源头

面试里真正的高手，都是**从约束反推方案**，而不是背手段。掌握这三条，你就能自己推导答案。

### 约束一：上下文窗口有限 → 上下文工程

- **是什么**：模型单次能"看到"的文本总量（prompt + 历史 + 检索内容 + 输出）上限，常见 8K / 32K / 128K / 200K token。
- **衍生问题**：放不下 → 塞什么？怎么塞？→ **上下文工程**（第三部分）。
- **反直觉点**：**窗口大 ≠ 效果好**。"大海捞针"研究表明，信息放在长上下文中间容易被忽略（Lost in the Middle）；上下文越长，成本越高、延迟越大、噪音越多。所以 **RAG 不是"窗口小才用"，而是"永远该用"**。

### 约束二：按 token 计费 & 逐 token 生成 → 成本 + 延迟工程

- **是什么**：输入输出双向按 token 计费；输出是一个一个 token 生成的，所以文本越长越慢。
- **衍生手段**：
  - 成本：上下文预算、缓存（相同问题命中缓存）、小模型路由（简单问题走便宜模型）、输出 `max_tokens` 上限；
  - 延迟：流式输出（先出字，改善体感）、异步任务化（长任务转后台 + 轮询/推送）、并行调用。
- **你的对应物**：这本质上就是**接口耗时与资源预算治理**——和"网关扩容打穿 DB"里"先算容量再放量"是同一套思维。

### 约束三：概率生成 → 幻觉 + 评测 + 兜底

- **是什么**：模型目标是"生成像样的文本"，不是"说真话"。没有的事实它会流畅地编（**幻觉**）。
- **衍生机制**：
  - 输入层：RAG 注入可信知识 + 要求引用来源；
  - 指令层：Prompt 明确"只在资料里找，没有就说不知道"；
  - 输出层：结构化输出 + Schema 校验 + 规则校验（金额、日期、枚举）；
  - 兜底层：**敏感结论不采信模型**，走规则/人工卡点。
- **你的对应物**：这就是你在 B2B 里天天干的**"关键路径不允许非确定来源"**——报价、资金计算绝不交给一个可能出错的组件。

<a id="三"></a>
## 第三部分：上下文工程（Context Engineering）

> 这是 JD 任职要求 5 明确点名的词，也是你现在 gap 清单里的第 2 条。

### 3.1 一句话定义

**上下文工程 = 在有限的 token 预算里，决定"这一刻给模型看什么、按什么顺序看、以什么形式看"。**

它比 Prompt Engineering 大一圈：Prompt 工程管"怎么写指令"，上下文工程管"把哪些信息、以什么结构放进模型的视野"。

### 3.2 核心动作：预算 → 选择 → 排序 → 压缩 → 结构化

**① 上下文预算管理**（把它当成一张"内存预算表"）

| 预算项 | 内容 | 典型占比思路 |
|--------|------|------------|
| System / 指令 | 角色、规则、输出格式 | 固定小块 |
| 检索内容 | RAG 召回的片段 | 大头，按 score 截断 |
| 对话历史 | 多轮上下文 | 滚动窗 + 摘要 |
| 输出预留 | `max_tokens` | 必须留够，否则被截断 |
| **合计** | ≤ 模型窗口 − 安全余量 | 超了要主动裁剪 |

**② 选择**：不是"能找到的都塞"，是"只塞回答了当前问题的"——这就是 RAG 的 top-k 与阈值过滤。

**③ 排序**：重要信息放**开头和结尾**（避开中间衰减区）；检索片段按相关度降序，最强的放最前。

**④ 压缩**：长对话 → 滚动窗口 + 摘要（把前 N 轮压成一段"背景摘要"）；长文档 → 分段摘要再汇总（Map-Reduce）。

**⑤ 结构化**：把上下文按固定模板拼装（如 `<背景>\n<检索结果>\n<用户问题>\n<输出格式>`），比一堆散文本更可控。

### 3.3 长上下文 vs RAG：别迷信 128K

| 方案 | 优点 | 缺点 | 什么时候用 |
|------|------|------|----------|
| 全文塞上下文 | 实现简单、无检索损失 | 贵、慢、中间信息衰减、易跑题 | 单文档、短、必须全文理解 |
| RAG 检索注入 | 便宜、快、可溯源、可扩展到海量知识 | 依赖检索质量，漏召回就答不对 | **绝大多数企业场景** |

> **金句级观点**："RAG 是上下文工程的一个子集——它的职责是'在正确的时刻，把正确的知识片段，放进预算里'。窗口再大也替代不了检索，因为成本和精度都受不了。"

### 3.4 你已有的同构经验

- **上下文预算 ≈ 接口报文裁剪 + JVM 内存预算**：都是"资源有限，先定配额，再决定装什么"。
- **滚动窗口 + 摘要 ≈ 日志滚动 + 归档**：老数据不全留，压成摘要/冷存。
- **结构化拼装 ≈ 你统一接口契约时的报文模板**：让内容可预期、可校验。

### 3.5 面试怎么问 / 怎么答

**Q：多轮对话里历史很长怎么办？**
> "三招：滑动窗口保留最近 N 轮；把更早的对话压成一段摘要挂在前面；把确定性的会话状态（用户是谁、当前订单号）从对话里剥出来，放到外部状态里按需注入——模型无状态，状态是我们自己管理的。"

<a id="四"></a>
## 第四部分：RAG——把外挂知识库接进模型

> 这是 AI 应用最主流的落地形态，也是超聚变 JD 优先条件里的"AI 应用落地"。

### 4.1 为什么需要 RAG（先讲清动机，再讲链路）

模型有四个先天不足，RAG 就是补这四个：

1. **知识有截止日期**（训练完就冻结）→ RAG 现查现用；
2. **不知道你的私有知识**（内部文档、合同、政策）→ RAG 外挂知识库；
3. **爱编**（幻觉）→ RAG 提供"有据可查"的答案 + 引用来源；
4. **改不了**（重新训练太贵）→ RAG 改文档即可，秒级生效。

### 4.2 全链路（离线 + 在线两条线）

```
【离线：建库】
文档接入 → 解析 → 切块(chunk) → 向量化(embedding) → 存入向量库
（原始文件：PDF/Word/Excel/网页/数据库）

【在线：问答】
用户问题 → 向量化 → 检索(top-k) → [可选]关键词检索 → 融合 → 重排(rerank)
        → 拼进上下文 → 交给 LLM 生成 → 返回 + 引用来源
```

### 4.3 每一环的工程细节与坑（重点：知道"为什么这么选"）

**① 解析（把文档变成文本）**
- PDF：文字层 vs 扫描件（要 OCR）；多栏、表格、图表是重灾区；
- 表格：结构化表格抽成 Markdown/JSON 比纯文本更适合检索；
- **结论**：解析质量决定了 RAG 的天花板——垃圾进，垃圾出。

**② 切块（chunking）——最容易踩坑的一环**

| 策略 | 说明 | 取舍 |
|------|------|------|
| 固定长度 | 按 token 数切（如 512），带重叠（overlap 10~20%） | 简单，但会切断语义 |
| 按结构切 | 按标题/段落/章节切 | 保住语义，依赖文档结构 |
| 父子块 | 小块用于检索（精准），大块用于生成（完整） | 效果最好，实现复杂 |
| 语义切 | 按语义相似度找断点 | 成本高 |

- **关键认知**：**切块大小是"检索精度"和"上下文完整度"的权衡**——块太小检索准但上下文碎，块太大上下文全但检索发虚。
- 一般从 **256~1024 token、overlap 10~20%** 起步，再用评估集调。

**③ 向量化（Embedding）**
- 把文本映射成高维向量（常见 768/1024/1536/3072 维），语义近的向量距离近；
- 选型看：中文效果、维度（影响存储与检索成本）、是否支持多语言、能否私有化部署；
- **注意**：检索用的 embedding 模型和生成用的 LLM 是**两回事**，可以分别选。

**④ 向量库选型**

| 选项 | 定位 | 适合 |
|------|------|------|
| pgvector | 挂在 PostgreSQL 上 | 已有 PG、数据量中小、想少一个组件 |
| Milvus / Qdrant / Weaviate | 专业向量数据库 | 亿级向量、高并发、要独立扩容 |
| Chroma / Faiss | 轻量库 | 原型、单机、小数据量 |

**⑤ 检索：向量 vs 关键词 vs 混合**
- **向量检索**：懂语义（"报销流程"能命中"费用审批"），但对专有名词/编号不敏感；
- **关键词检索（BM25）**：精确匹配强，但不懂同义；
- **混合检索**：两者结果用 RRF 等算法融合——**生产环境大多数走混合**。

**⑥ 重排（Rerank）——为什么必要**
- 向量检索是"粗筛"（快但不够准），只保证"大致相关"；
- Rerank 用更重的 cross-encoder 模型对 top-k 结果**精排**，把真正最相关的顶上来；
- 类比：**向量检索 = 一级排序（宽召回），Rerank = 二级排序（精排序）**。

**⑦ 效果评估（离线）**
- **Hit Rate / Recall@k**：标准答案有没有被召回（检索层）；
- **MRR / NDCG**：正确结果排得够不够前（排序层）；
- **人工/模型打分**：答案质量（生成层）。

### 4.4 RAG 效果不好的排查树（面试高频）

```
问效果差 → 先分层定位：
├─ 检索层：标准答案根本没被召回？
│   ├─ 切块太碎/太大 → 调 chunk
│   ├─ Embedding 不适配中文/领域 → 换模型
│   ├─ 只有向量、没关键词 → 上混合检索
│   └─ top-k 太小 → 放大候选
└─ 生成层：召回对了但答错？
    ├─ 上下文没拼好/被截断 → 查预算
    ├─ Prompt 没约束"只用资料" → 改指令
    └─ 模型太小/幻觉 → 换模型 or 加 Schema 校验
```
> **方法论点**（这是你能讲出水平的点）：**先建评估集，再谈优化**。没有评估集，调参就是盲人摸象。

### 4.5 你已有的同构经验

- **RAG 链路 ≈ 你的"读库 + 组装 + 输出"分离**：检索层负责"取对数据"（像索引/分库分表设计），生成层负责"组装成答案"（像聚合服务）。
- **Rerank ≈ 二级排序**：跟你做搜索结果/竞价排序的"粗排+精排"是同一模式。
- **评估集先行 ≈ 你的对账兜底**：先有"正确答案"，才能判断系统对不对。
- **文档切块 ≈ 分表分片**：颗粒度设计决定查询效率，颗粒度错了上层全废。

### 4.6 你的真实 AI 锚点：MinerU 文档解析改造（这是你能讲的真东西）

**MinerU 是什么**：开源的 PDF → Markdown/JSON 解析工具（OpenDataLab 出品）。它把 PDF 里的版式、表格、公式（转 LaTeX）、图片、阅读顺序还原成结构化 Markdown——**它的输出质量，直接决定 RAG 知识库的天花板**（对应 4.3① 的“解析”环节）。

**它在 AI 架构里的位置**：

```
PDF/Word 等原始文档 → 【MinerU 解析 → Markdown】→ 切块 → 向量化 → 向量库 → 检索 → 生成
                      ↑ 你参与的就是这一环（离线建库第一步）
```

**为什么这一环值得你讲**（三个真实、可展开的点）：

1. **它是 RAG 的入口，垃圾进垃圾出**——解析错了，后面切块/检索/生成全白搭；
2. **它的难度不在模型，在工程**：批量调度、GPU/CPU 资源、超时重试、失败兜底、结构化输出校验、与入库链路的衔接——**全是你的主场**；
3. **它天然是“技术改造”而非“算法研发”**——你改造的是“怎么用它、怎么接进流水线”，这正是“AI 应用工程”。

**能说出口的口径（诚实版）**：

> “AI 这块我在公司参与的是**文档解析这一环**——用 MinerU 把多格式文档统一解析成 Markdown，再往向量库里落。我做的是**技术改造**：怎么把它接进建库流水线、怎么处理批量解析的资源和失败、怎么保证输出格式能让下游切块入库稳定消费。模型算法不是我的活，但‘让 AI 数据链路跑得稳’是我的活。”

**可能的追问与答法**：

- **Q：MinerU 解析质量怎么保证？** → 结构化输出校验（标题层级、表格完整性）+ 抽检 + 解析失败降级（换解析器/人工处理）+ 用检索指标反向验证解析质量。
- **Q：为什么选 MinerU 而不是别的（PyMuPDF / 商业 OCR）？** → 开源可私有化（数据不出域）、公式/表格还原强、输出 Markdown 可直接喂 RAG；商业 API 有数据外流风险。
- **Q：解析环节的坑？** → 扫描件要 OCR、复杂表格易错行、多栏版式阅读顺序乱、超长文档耗时——所以要批量调度 + 失败兜底 + 质量抽检。

> **一句话定位**：你的 AI 经验值 = “**AI 数据链路的工程化**”，不是“模型算法”。这个定位诚实、具体，且正好命中 JD 要的“AI 接入企业系统”。

<a id="五"></a>
## 第五部分：Agent 与 Agent Harness 六机制

> 这是超聚变 JD 任职要求 5 的**点名内容**，也是你 gap 里的第 1 条。好消息：**六机制里五个是你的主场**，只是换了马甲。

### 5.1 从"问答"到"智能体"

- **普通 LLM 应用**：一问一答，模型只输出文本；
- **Agent（智能体）**：模型能**调用工具**（查数据库、调 API、写文件）、能**多步规划**、能**根据结果决定下一步**——从"说"变成"做"。

**工具调用（Function Calling）原理**：你把可用工具用 JSON Schema 描述给模型（工具名、参数、说明），模型判断"这个任务该调哪个工具、参数是什么"，返回结构化的调用请求；你的程序真正执行工具，把结果再喂回模型，循环直到任务完成。**模型不执行代码，它只是"决定调用"——执行权在你手里。**（这点很重要：安全边界在你这，不在模型。）

### 5.2 Agent 执行循环

```
感知(输入/工具结果) → 规划(下一步做什么) → 行动(调用工具) → 观察(拿到结果) → 回到感知...
                      ↑______________________ 直到任务完成 or 触发终止条件 ______________________|
```
这就是 **ReAct 模式的工程化版**，也是 JD 说的"任务执行循环"。

### 5.3 六机制逐条：原理 + LLM 特有难点 + 你的同构经验

| # | JD 术语 | 原理（讲人话） | LLM 特有的难点 | **你的同构经验** |
|---|---------|--------------|--------------|----------------|
| 1 | **任务执行循环** | 感知→规划→行动→观察的循环，直到完成或触发终止 | 模型会"跑飞"、死循环、越绕越远 | **工作流编排 / Saga 编排器 / 状态机**——你早就在管"多步流程的推进与终止" |
| 2 | **状态管理** | 会话与任务状态放在外部（Redis/DB），每步可恢复、可回放 | 模型本身**无状态**，上下文要自己拼；长任务中途失败要能续 | **outbox 事件表 / 幂等 / 会话外置**——你做过"状态不丢、可恢复" |
| 3 | **权限控制** | 工具分级：只读 / 写 / 高危；高危需显式授权 | 模型不会"自己守规矩"，**鉴权绝不能跟着 Agent 走，必须跟着用户身份走** | **鉴权收口中台 / RBAC**——你的主场，AI 只是新增一个"旁路"风险 |
| 4 | **异常恢复** | 工具失败重试 + 降级 + 补偿；输出不合法 → 带错误反馈重试；循环失败熔断转人工 | 出错不是"抛异常"而是"返回了一段胡说八道" | **重试 / 降级 / 补偿 / 熔断**——Saga 补偿你这套最熟 |
| 5 | **人工介入（HITL）** | human-in-the-loop 卡点：写操作前审批、低置信度转人工、操作留可撤销窗口 | 需要设计"什么时候必须停下来问人" | **审批流 / 双人复核 / 灰度发布**——B2B 审批你天天做 |
| 6 | **评测观测** | 每步 trace 落日志；指标：成功率/步数/工具错误率/成本/时延；离线评测集回归 | 输出是开放文本，指标比传统系统难定义 | **On-call / 监控 / 对账 / 双跑比对**——你的运维体系直接迁移 |

### 5.4 为什么需要"Harness"（框架）而不是裸模型

**Harness（挽具）= 套在模型外面的那层工程骨架**——它把上面六个机制实现出来，让"一个会说人话的模型"变成"一个可靠、可管、可观测的执行体"。

> **这是你最该记住的一句面试话**："Agent 的可靠性不来自模型，来自 Harness——循环上限、状态外置、权限分级、失败补偿、人工卡点、评测观测。这六个机制我在企业级系统里都做过同构版本，AI 版的差异我清楚在哪。"

### 5.5 防失控三闸门（面试爱问"死循环怎么防"）

1. **步数上限**：最多循环 N 步；
2. **预算上限**：最多烧 X token / Y 金额；
3. **重复检测**：连续相同动作/相同工具参数 → 判定卡死，中止。

→ 触发任一 → **熔断 + 转人工兜底**。

### 5.6 面试怎么问 / 怎么答

**Q：你们 Agent 的权限怎么设计？**
> "工具的鉴权**不跟着 Agent 走，跟着发起请求的用户身份走**。Agent 只是一个执行通道，它没有自己的人格化权限。高危写操作要显式授权 + 人工确认节点。这条是硬约束——否则 AI 就成了系统里的一个新权限旁路。"

<a id="六"></a>
## 第六部分：评测与可观测——把 AI 当生产系统

> gap 清单第 5 条：方法你都会，缺一个自己的量化案例。

### 6.1 为什么 AI 必须评测

传统系统"对了就是对了"，AI 是概率输出——**没有评测，你连"这次改动到底变好还是变坏"都不知道**。评测是 AI 从 demo 到生产的唯一桥梁。

### 6.2 三层评测

| 层 | 评什么 | 指标 | 怎么建 |
|----|--------|------|--------|
| **检索层** | 知识有没有找对 | Hit Rate、Recall@k、MRR | 标注"问题→应召回片段" |
| **生成层** | 答得对不对 | 准确率、忠实度（有没有编）、格式合规率 | 标注"问题→标准答案" |
| **端到端** | 用户满不满意 | 解决率、人工转接率、满意度、坏例率 | 线上埋点 + 人工抽检 |

### 6.3 离线 vs 在线

- **离线**：固定评测集（N 题），每次改动前后各跑一遍 → 防止"改好了 A 场景、改坏了 B 场景"（**回归测试的 AI 版**）。
- **在线**：A/B 分流对比、用户反馈（👍/👎）、**badcase 回流**（把线上错例补进评测集，集子越用越准）。

### 6.4 可观测指标与成本护栏

- **指标**：QPS、首字延迟（TTFT）、端到端时延、token 消耗、成本、工具调用错误率、**幻觉率（人工抽检）**；
- **成本护栏**：上下文预算、输出上限、缓存命中、小模型路由、按部门/租户的 **token 计量与限额告警**（← 这块正好接你中台的计量能力）。

### 6.5 你已有的同构经验（这是你能讲出彩的地方）

- **离线评测集 ≈ 自动化测试 + 回归测试**；
- **badcase 回流 ≈ 生产事故复盘进排查手册**（你已经这么干了：事故 → 防再发措施 → 进手册）；
- **Online 监控指标体系 ≈ 你的 On-call + 四维考核**；
- **对账兜底 ≈ 忠于事实的校验**：你的三流对账就是"数据一致性"域的极致实践。

### 6.6 面试话术（补上数字口径）

> "智能客服上线前我们建了评测集——**按团队目标口径，上线前 N 道题跑基线，准确率从 X 提到 Y，badcase 按周回流进评测集**，每次 Prompt/知识库改动前后各跑一遍做回归。指标上盯首字延迟、token 成本和人工转接率。"

（面试前把 N/X/Y 填成你自己认可且经得起追问的数字；口径一律标"团队目标"。）

<a id="七"></a>
## 第七部分：生产化集成——你的主场

> 前面六节是"补课"，这一节是"收割"：AI 接入企业系统的**集成层**，全是你的老本行。面试时把重音放在这里。

| AI 集成的工程问题 | 本质 | 你的现成答案 |
|-----------------|------|------------|
| **流式输出** | 逐 token 生成，要边生成边推给前端 | SSE / WebSocket 长连接，**转发不改语义**，断线重连要幂等 |
| **鉴权收口** | AI 网关不该自带权限语义 | 身份穿透传递，**校验永远在中台侧执行**，避免"AI 旁路"成为新权限边界 |
| **幂等** | 用户可能重发、网络可能重试 | 会话/请求 ID 幂等键，写操作幂等——你中台的老本行 |
| **异步长任务** | Agent 多步执行可能几十秒 | 转后台任务 + 事件回调/轮询，超时可控 |
| **超时/重试/降级** | 模型服务会超时、会限流 | 超时设上限、重试带退避、**降级到缓存答案或转人工** |
| **多租户隔离** | 不同客户数据不能串 | 数据源隔离 + 上下文隔离，**防绕过**（不能让用户用 Prompt 越权取数） |
| **不直连业务库** | 模型/编排平台不应直连 DB | 只通过中台暴露的受控工具/API 访问 |
| **审计留痕** | 合规要求可追溯 | 业务操作日志 + AI 调用日志用 **trace_id 关联** |

> 三条硬约束（来自你的选型复盘，直接可说）：**① 权限校验永远在中台侧，不把数据过滤交给 Prompt；② 编排平台不直连业务数据库；③ 工作流里不写复杂业务逻辑，只做路由/拼装/调用/格式化。**

**这就是"确定性业务逻辑与 AI 能力分层"（JD 任职要求 6）的落地版本**——跟钱、合规、状态强相关的走确定性逻辑，AI 只负责非结构化理解、检索汇总、草稿建议。

<a id="八"></a>
## 第八部分：速记卡与应答模板

### 8.1 十个"一句话定义"（睡前扫一遍）

1. **Token**：模型处理文本的最小单位，按它计费、按它算延迟。
2. **上下文窗口**：单次能塞进去的 token 上限，**大不等于好**。
3. **上下文工程**：在预算内决定"给模型看什么、怎么排、怎么压"。
4. **RAG**：外挂知识库——检索相关片段注入上下文，解决时效/私域/幻觉/可溯源。
5. **切块**：拿检索精度换上下文完整度，256~1024 token 起步。
6. **Embedding**：把文本变向量，语义近则向量近；和生成模型是两回事。
7. **Rerank**：向量检索后的精排（二级排序）。
8. **工具调用**：模型只"决定调用"，**执行权在你手里**。
9. **Harness**：套在模型外的工程骨架（循环/状态/权限/恢复/人工/观测）。
10. **幻觉**：模型按概率续写、目标是"像"不是"真"；靠 RAG+指令+校验+兜底四层压制。

### 8.2 三套应答模板（弱化 AI 版）

**模板 A：被问"你的 AI 项目经历"**（诚实 + 有料，不吹）
> "AI 这块我在公司是**前期选型和原型阶段**的参与者：主导了 AI 平台底座的选型复盘（Dify vs 自研），做了 **MinerU 文档解析（PDF→Markdown）这一环的技术改造**，也验证了多格式文档落向量库这条链路。**落地执行主要由团队推进，我后期参与得少了——这点我不夸大。**我个人还在做 Agent Harness 相关的技术储备，对任务循环、状态管理、权限这些机制有一线的体感。"

**模板 B：被问"AI 融合架构怎么设计"**（把重音放到你的主场）
> "我的切入点不是模型本身，是**AI 怎么接进企业系统**：模型按数据敏感度划通道，权限收口在业务中台，编排平台不直连业务库，写操作走事务和幂等，全链路用 trace_id 串起来做审计和观测。这些不是 AI 的新问题，是企业集成的老问题——我在 B2B 平台做了 13 年这类事。"

**模板 C：被问到你不会的 AI 细节**（BOUNDARY 诚实划界）
> "模型侧的细节我不装懂——这块的深度我不是专家。我能讲清的是**工程机制层**：循环上限、状态外置、权限分级、失败补偿、人工卡点、评测观测，这些在企业系统里有同构的成熟做法。**架构判断力我能给，算法细节我诚实说不会。**"

### 8.3 "弱化 AI"的操作要点

1. **自我介绍里 AI 只占 1/3 或更少**，且用"选型/集成架构"角度，不用"算法能力"角度；
2. **主线永远是架构 + 实施 + 管理**（你的 13 年）；
3. **AI 只在被问到时展开**，且展开的是"融合架构"不是"模型技术"；
4. **个人项目必须明确标注"个人储备"**，绝不能与公司项目混淆——这是四轮追问下最容易翻车的地方。

## 第九部分：边界与诚实话术

### 9.1 你必须"诚实地不会"的清单

| 主题 | 你的状态 | 应对话术 |
|------|---------|---------|
| 模型训练 / 微调 | 不会 | "训练和微调不是我的领域，我做的是用模型、不是训模型。" |
| 检索算法调优（向量索引参数、召回策略） | 了解概念，无深度实战 | "检索链路我懂原理和排查方向，但做到索引级调参不是我的一线经验。" |
| 上下文工程的一线实现 | 未亲自做过 | "这块是我的补强项——原理我讲得清，实战细则我在补。" |
| 生产级 Agent 落地 | 个人储备 | "Agent 机制我有个人项目的体感，公司级的我没有，这两者我不会混着讲。" |

### 9.2 BOUNDARY 句式（黑盒诚实 + 边界内可靠）

> "**行业/技术的 X 不是我不装懂的部分**——我做过功课的是它的架构位置和工程约束；我的判断是：**方法论（边界划分、能力复用、实施落地、集成治理）跨领域成立**，细节我可以很快补，但架构判断力补不出来。"

### 9.3 心态（最后一句真话）

你不擅长 AI 算法——**这没关系，这个岗位要的也不是这个**。面试官真正在筛的是：你是不是一个**能用 AI 把企业系统重构好**的架构师。你 13 年干的就是"把复杂系统管住、把能力复用起来、把落地兜住"，这套东西在 AI 时代只会更值钱。

**你要补的只有两样：术语 + LLM 特有的物理约束。这两样，这本手册就是为了给你补的。**
