## 0. 两版开场（背这两段就够，其余都是追问用的弹药）

### 30 秒版

> 这是一个大宗商品线上交易平台，服务煤炭、钢铁、矿石、农产品的产业链买卖双方，客单价从几十万到上千万，覆盖挂牌、竞价、询价、招标、基差点价五种交易模式，后面接支付结算、合同履约、仓单、物流、税务和供应链金融。
> 我是技术经理 / Java 侧负责人，带 20 人团队，负责 Java 业务中台的整体方案与交付，并且是 C 撮合团队和 Java 团队之间的技术接口人。
> 投时间最多的是两件事：一是 C 单线程撮合引擎和 Java 中台之间的异构桥接与一致性，二是跨系统调用的最终一致。这两块我可以展开讲。

### 3 分钟版（顺序：背景 → 模块与主链路 → 我的职责 → 一个有证据的难点）

> 平台的业务死结有三个：陌生人大额交易谁先付款谁先发货、比价与履约效率、买方囤货缺现金流。对应产品能力是资金监管与货权控制、五种交易模式加全链路履约、供应链金融。
>
> 系统是异构的：底层 C 语言单线程内存撮合引擎保撮合延迟，上层 12+ 个 Java 微服务承载业务编排和外部集成，中间夹一层自研的 DS 数据中心做防腐，外部还有统一外联网关接 5 家银行、WMS、税务、电子签章共 9 个以上系统。
>
> 一次下单走这样一条链路：客户端进中间件网关（做鉴权、协议号校验、参数形状与压力参数校验、限流），进交易服务后在一个本地事务里写单据并写待发送表，提交后由派发器认领批次投给 DS，DS 用 Hessian over HTTP 同步调 C 撮合，撮合结果再经回写队列落库，最后用 Kafka 事件驱动履约、结算、仓单、物流。
>
> 我负责 Java 侧全部方案，最花力气的是网关治理和跨系统一致性。举一个具体的：网关横向扩容到 5 个实例后，流量放大把后端数据库打死了——瓶颈只是从网关后移到了 DB。
> 【推演/实证混合，见 §5.4】我们用利特尔法则反推慢接口的安全吞吐，网关给慢接口限流 200 QPS、慢接口独立线程池做舱壁、连接池每实例卡 20、热点数据本地加 Redis 两级缓存，当晚把 DB 救回来，之后固化成"新接口容量申报 + SQL 红线 + 扩容前先核出口容量"三条规范。

## 3. 请求链路（画图就画这条）

### 3.1 主链路：一次下单

```
客户端
  │ HTTPS
  ▼
中间件网关 ── 十道关（按拦截成本从低到高）
  │  ① 鉴权  ② 协议号校验（协议号 = 接口唯一编码）
  │  ③ 入参形状校验（白名单制）  ④ 压力参数强制校验
  │     · 分页默认 100，超限显式拒绝而不是静默截断
  │     · 单次扫描 SQL 行数红线 ≤ 200
  │  ⑤ 分级限流 / 黑名单  ⑥ 等保拦截（含文件上传）  ⑦ 响应脱敏
  ▼
Java 交易服务 ── 一个本地事务内做两件事：
  │   · 写业务单据（订单 / 挂牌 / 竞价出价）
  │   · 写「待发送第三方表」（Outbox，记欠账，不在这里发网络调用）
  │   COMMIT
  ▼
派发器 ── 一条 UPDATE 原子认领整批（batchNo 全局唯一，禁单机自增）
  │          → 多实例不需要分布式锁，谁认领到谁发
  ▼
DS 数据中心 ── Hessian over HTTP（同步、要应答）
  │   统一报文 header / body / signature / traceId
  ▼
C 撮合引擎 ── 单线程串行处理，内存订单簿撮合
  │   · 内存状态变更 → 先生成「回写待办」，再出内存（核心不变量）
  ▼
回写待办队列 ── 阶梯重试 1s → 2s → 4s … 上限 N
  │   成功 → 落 DB；失败到上限 → 熔断 + 运营短信 → 死信队列
  ▼
Kafka ── 履约 / 结算 / 仓单 / 物流 / 税务，消费端按业务键幂等去重
```

**三个必须自己先讲清的边界（面试官最爱在这里挖）**：

- **待发送表 ≠ 待回写队列**。前者是 Java 发**下游/外部**的欠账（`12`），后者是 C 内存发**DB** 的欠账（`13`）。两条链路方向不同，别混着说。
- **Outbox 保证的是"写库与发消息"原子，不是"调用成功"**。调用失败靠重试与兜底，不靠事务。
- **协议号是接口唯一编码**，不是消息 ID。它决定契约注册表里白名单、限流配额、脱敏策略、监控维度挂在哪一行。

### 3.2 失败链路（必须能单独讲一条）

**C 回写数据库失败**（内存状态已变、库里没有）：

1. 现象：撮合成交在内存生效，但 DB 里订单状态没变，或金额与持仓对不上。
2. 处置：内存变更落「回写待办」→ 队列阶梯重试 → 超上限熔断 + 运营短信 → 死信队列。
3. 人工重试的**语义边界**：只重放**回写**，幂等 upsert；**绝不重新撮合**——重新撮合会二次成交，是资损级事故。
4. C 进程崩溃：镜像文件三段各自承担不同责任 → 启动重放**输入**（命令日志）恢复，不重放结果。

**Java 调用外部失败**（如银行支付回执）：

- 本地事务已提交、待发送记录在 → 派发器重试 → 熔断转人工介入界面 → 界面重试只重置该条记录，不重跑整个单据。

## 4. 技术选型（每条都要能说"候选 / 否决理由 / 代价"）

| 选型 | 当前方案 | 候选与否决理由 | 付出的代价 |
|---|---|---|---|
| 撮合引擎 | C 单线程 + 内存订单簿 | **否决"用 Java 重写统一技术栈"**：GC 停顿对资金链路不可接受，重写带来数月的性能倒退与业务中断风险 | 异构双栈：C 团队独立、协议层复杂、排障要跨语言 |
| 两栈之间 | 自研 DS 数据中心（防腐层） | 否决直接 RPC（Dubbo / gRPC）：C 侧无成熟客户端，且需要定长头 + TLV 极致控帧 | 自己维护序列化、背压、连接管理；多一跳排查成本 |
| 同步 / 异步通道 | Hessian over HTTP（同步要应答）+ Socket 长连接（异步批量） | 一刀切用长连接会把"要应答"的语义做复杂；全走 HTTP 则批量吞吐上不去 | 两套通道两套排障路径，监控要成对做 |
| C↔Java 可靠投递 | 待发送表 + 批次号认领 + 阶梯重试 + 熔断转人工 | 否决 2PC / XA：外部系统（银行 / 税务）根本不支持，跨月长事务也撑不住 | 最终一致：必须配重试、对账、人工兜底三件套 |
| 跨月长事务 | Saga 编排 + 状态机 + 事件溯源 | 否决"大事务包住"：合同→备货→发运→验收→结算跨月跨服务 | 补偿逻辑要逐场景写；状态机维护成本 |
| 服务间数据同步 | Kafka + 本地消息表（Outbox）+ 消费幂等 | 否决点对点同步调用：耦合重、丢消息、重复投递无解 | 重复消费必须靠业务键去重；事件有序性要按分片键保 |
| 多租户差异 | Drools 规则引擎 + 策略模式 + 配置化模板 | 否决"每客户定制开发"：上线周期长、代码分叉 | 规则可视化与调试成本；配置错比代码错更难查 |
| 网关 | 自研（不是买 API 网关） | 通用网关管不了"协议号契约 + 压力参数红线 + 等保项"这套业务级约束 | 自研运维；midmon 这类可观测要自己建 |

**如果被问"重新做会怎么改"**（JavaGuide 提示社招必问）：

- 网关的契约注册表想更早落地——早期接口各自为政的历史债，后面靠注册表收敛代价很高。
- DS 的编解码我会更早抽成独立模块 + 明确"业务线程只做纯内存操作"的铁律，避免后来在 IO 线程里写序列化。

## 5. 难点或故障（每个都按"现象→约束→排查→方案比较→实施→验证→遗留"讲）

### 5.1 难点一：C 单线程内存一致性（讲"单线程不是银弹"）

- **现象/约束**：单线程只解决"内存内"的串行化，风险全在**内存外**三类：易失（崩溃丢内存）、时滞（内存先进、DB 落后）、回写失败（重试也失败）。
- **方案比较**：同步双写（性能不可接受）｜纯 WAL（恢复慢）｜镜像文件三段 + 异步回写队列 + 死信（选中）。
- **实施**：命令日志记输入、快照记状态、待办记欠账；回写走阶梯重试；死信只重放回写。
- **验证**：崩溃恢复矩阵——按"失败落在哪一段"逐格给恢复方式；热备切换六步 + 仲裁防脑裂。
- **遗留**：仲裁者失联时整体停摆是**正确**行为（设计目标是安全不是可用），这条要敢说。

### 5.2 难点二：跨系统调用一致性（讲"本地事务与网络调用不能混"）

- 四条核心不变量 + 待发送表字段规则 + 批次号全局唯一（一条 UPDATE 认领整批，不需要分布式锁）。
- 失败矩阵按"失败发生在哪一段"给处置，而不是笼统说"重试"。

### 5.3 难点三：网关限流误伤与分级处置

- 三级配额而不是一刀切；触发源四类（不只 QPS 过高）；处置阶梯先轻后重且可回退。
- 误伤防护不做，第一个投诉的就是真客户——这是业务视角，不是技术视角。

### 5.4 故障一：网关横向扩容打穿数据库 `【推演·基于真实架构与实录】`

- **现象**：某接口慢、整体并发上不去 → 扩容到 5 实例能扛 2500 并发 → 几分钟后 DB 被打死（连接耗尽、线程阻塞）。
- **约束**：扩容是流量放大器，后端直连 DB 是单通道出口，中间没有闸门。
- **排查**：用利特尔法则算账——2500 并发若 10% 同时在途慢请求就是 250 个 DB 连接需求，远超连接池。
- **方案**：入口限流反推（DB 100 连接 × SQL 300ms → 安全吞吐约 230 QPS，取 60% 水位 = 200 QPS）｜慢接口独立线程池 15/30/100 舱壁隔离｜写入走内存队列恒速削峰｜本地 30s + Redis 两级缓存做到 90% 命中｜连接池每实例 20、`max_connections` 200、慢查询 1s kill、列表读走从库。
- **验证**：当晚四步急救后 DB 恢复；后续固化为"新接口容量申报 + SQL 红线 + 扩容前先核出口容量"。
- **遗留**：数值是特定机器与数据量下的反推值，换环境要重算——这句话要说，别把 200 QPS 当普适常数。

### 5.5 故障二：竞价页面突然变慢 `【推演·实录】`

- **现象**：竞价页 2 秒轮询，接口 P99 从 150ms 涨到 3.2s。
- **排查**：先定界再深挖——网络（全地域一致 → 排除）→ 流量（网关 QPS 持平、限流未触发 → 排除）→ 撮合（TPS / 积压 / DS 心跳正常 → 排除）→ JVM（无 Full GC → 排除）→ 缓存 / DB。
- **根因**：Canal 消费 binlog 在**一次未走流程的 DDL** 后解析失败退出（位点停滞 22 分钟、无告警）→ 缓存更新流断 → 热点 key TTL 过期后未命中直接回源、无并发保护（缓存击穿）→ 主库 CPU 97%，竞价服务等连接池，P99 3.2s。
- **验证与遗留**：补 Canal 位点延迟监控 + 缓存击穿保护（互斥重建 / 逻辑过期）+ DDL 变更流程纳入发布管控。
- **一句话版本**：慢在 DB，根因在变更流程和监控缺口。

### 5.6 故障三：下载 PDF 导致 JVM 进程消失 `【推演·实录】`

- **方法铁律**：先定性质（谁杀的）再定根因（为什么）。
- **判定树三问**：① 退出码（137 = SIGKILL，排除 JVM 自身崩溃与 Java OOM）② 有无 `hs_err_pid*.log`（无 → 不是 JVM 崩）③ 内核日志 / dmesg。
- **结论**：容器内存超限被内核 OOM Killer 杀掉；诱因是批量勾选 120 份 PDF 打 ZIP 下载，堆外/直接内存或流式处理未做限制。
- **修复**：改流式下载 + 分页打包 + 限制单次份数，堆外内存与容器 limit 对齐，补 `-XX:MaxDirectMemorySize` 与 OOM 告警。
