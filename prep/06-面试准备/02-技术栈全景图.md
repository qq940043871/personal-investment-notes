## 一、Redis — 不止是缓存，是"快"的答案

### 场景1：交易页面数据缓存（String）

**业务场景**：大宗商品价格实时波动，交易员每次刷新行情页面都要查数据库，数据库扛不住。

**技术方案**：
```
期货实时价格 → Redis String → 前端轮询
KEY: "price:RB2410:realtime"
VALUE: "3750"
TTL: 5秒（价格5秒更新一次）
```

**为什么是 Redis String？**
- O(1) 读写，毫秒级响应
- 设置 TTL 自动过期，不担心脏数据堆积
- 单线程模型天然原子性，并发读价格不会出现不一致

**追问："你们价格缓存怎么保证跟数据库一致？"**

→ Cache Aside 模式：更新数据库时删缓存，下次查询重建。关键：**先删缓存再更新数据库**（避免并发读写入旧缓存）。极端场景用延迟双删：删缓存→更新DB→等500ms→再删一次。

---

### 场景2：防止重复提交（String + SETNX）

**业务场景**：大宗交易金额巨大，用户手抖点两次"确认下单"，千万不能创建两笔订单。

**技术方案**：
```java
String lockKey = "order:submit:" + orderNo;
Boolean locked = redisTemplate.opsForValue()
    .setIfAbsent(lockKey, "1", 30, TimeUnit.SECONDS);
if (!locked) {
    throw new BizException("请勿重复提交");
}
// 执行业务逻辑...
redisTemplate.delete(lockKey); // 处理完释放
```

**为什么用 SETNX 而不是数据库唯一约束？**
- 数据库唯一约束只能防"存进去"，不能防"业务逻辑执行两遍"
- SETNX 在业务入口就拦截，减少无效的数据库操作和第三方调用

**追问："SETNX 有什么坑？"**
- 锁过期时间设置：设太短业务没执行完锁就释放了（→ 用 Redisson 看门狗自动续期）
- 误删别人的锁：A 的锁过期，B 获取了锁，A 执行完删了 B 的锁（→ value 存 UUID，删之前比较）

---

### 场景3：交易员操作权限缓存（Hash）

**业务场景**：每次操作都要查"这个交易员能不能做这笔交易"（额度限制、品种权限、合同范围），权限表 join 了 5 张表，查一次 200ms。

**技术方案**：
```
KEY: "trader:permission:10023"
HASH:
  "credit_limit" → "50000000"     (授信额度)
  "allowed_products" → "螺纹钢,热卷,铁矿石"  (可交易品种)
  "counterparty_list" → "1001,1002,1005"     (可交易对手方)
```

**为什么是 Hash 而不是多个 String？**
- 一次 HGETALL 拿到所有权限字段，不用多次网络往返
- 修改单个字段（如额度调整）只需 HSET 一条，不用重建整个对象
- 内存占用比多个 String key 小（共用 key 的元数据开销）

---

### 场景4：延迟队列处理超时订单（ZSet）

**业务场景**：大宗交易中，买家确认合同后 30 分钟内必须支付保证金，超时自动取消。

**技术方案**：
```java
// 创建订单时
long cancelTime = System.currentTimeMillis() + 30 * 60 * 1000;
redisTemplate.opsForZSet().add("order:timeout:queue", orderNo, cancelTime);

// 定时任务每秒轮询
Set<String> timeoutOrders = redisTemplate.opsForZSet()
    .rangeByScore("order:timeout:queue", 0, System.currentTimeMillis());
// 逐个取消...
```

**为什么是 ZSet 而不是 MQ 延迟消息（Kafka）？**
- ZSet 的 score 就是取消时间，天然按时间排序，`rangeByScore` 一把捞到期订单
- Kafka **没有原生延迟消息**（不像 RocketMQ 有固定延迟级别），要自己做时间轮/延时 topic，30 分钟这种自定义延迟反而更麻烦
- ZSet + 轮询实现简单，业务可控，量级不大时是最性价比的方案

---

### 场景5：排行榜/风控预警（ZSet）

**业务场景**：风控系统要实时展示"近 24 小时交易量最大的前 10 个客户"，监控异常交易。

```java
// 每笔交易完成时
redisTemplate.opsForZSet().incrementScore("risk:volume:24h", customerId, amount);

// 查询 Top 10
Set<ZSetOperations.TypedTuple<String>> top10 = redisTemplate.opsForZSet()
    .reverseRangeWithScores("risk:volume:24h", 0, 9);
```

## 二、MySQL — 数据的"保险柜"

### 场景1：订单表设计 — 聚簇索引 vs 二级索引

**业务场景**：订单表每天新增 10 万条，需要按"下单时间"范围查询，又要按"客户 ID"查他的所有订单。

**建表决策**：
```sql
-- 主键：自增 bigint → 聚簇索引
-- 顺序插入，不会页分裂
CREATE TABLE t_order (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 聚簇索引，叶子存整行
    order_no VARCHAR(32) NOT NULL,
    customer_id BIGINT NOT NULL,
    product_code VARCHAR(20),
    amount DECIMAL(18,2),
    status TINYINT,
    create_time DATETIME,
    
    UNIQUE KEY uk_order_no (order_no),
    INDEX idx_customer_time (customer_id, create_time)  -- 联合索引
);
```

**面试要说清楚**：
- **聚簇索引（id）**：叶子节点存完整行数据，按 id 顺序排列。好处是按 id 范围查直接扫叶子链表；代价是二级索引要回表。
- **二级索引（idx_customer_time）**：叶子节点只存 (customer_id, create_time, id)，查到 id 后回表取完整行。如果 `SELECT id, customer_id, create_time FROM t_order WHERE customer_id=1001` — 覆盖索引，不用回表。

---

### 场景2：联合索引的最左前缀原则 — 为什么这个查询慢了？

**业务场景**：客服查"客户 1001 在 2026 年 7 月的订单"，索引 `(customer_id, create_time)`

```sql
-- ✅ 走索引（等值查 customer_id + 范围查 create_time）
EXPLAIN SELECT * FROM t_order 
WHERE customer_id = 1001 AND create_time >= '2026-07-01';

-- ✅ 走索引（从最左 customer_id 开始）
EXPLAIN SELECT * FROM t_order WHERE customer_id = 1001;

-- ❌ 不走索引（跳过了 customer_id）
EXPLAIN SELECT * FROM t_order WHERE create_time >= '2026-07-01';

-- ⚠️ 只走 customer_id（create_time 用了函数，索引失效）
EXPLAIN SELECT * FROM t_order 
WHERE customer_id = 1001 AND DATE(create_time) = '2026-07-01';
```

**面试标准回答**："联合索引遵循最左前缀原则，查询条件必须从索引定义的第一列开始连续匹配。遇到范围查询（>、<、BETWEEN、LIKE 'xx%'）之后，后续列不再走索引。另外，对索引列用函数会导致索引失效，应该改成范围查询。"

---

### 场景3：为什么 InnoDB 推荐自增主键？

**业务场景**：订单表用雪花算法生成的随机 ID vs 自增 ID，插入性能差多少？

**答案**：B+Tree 的叶子节点是按主键顺序存储的。自增主键每次插入都在最后面，几乎不会触发页分裂。随机主键插入位置不可预测，频繁引起页分裂 → 磁盘碎片 → 性能下降。

**追问："雪花算法就不行吗？"**

→ 可以，但要在业务层做优化：用"节点号+时间戳"保证趋势递增。或者用一个自增 ID 做聚簇索引，雪花 ID 做二级唯一索引。

---

### 场景4：慢查询优化实战

**业务场景**：财务对账页面，一个 SQL 查 30 秒。

**排查流程（面试要能讲出这个流程）**：
```
1. SHOW FULL PROCESSLIST → 找到卡住的 SQL
2. EXPLAIN 看执行计划：
   - type=ALL → 全表扫描，没走索引
   - rows=200万 → 扫描行数太大
   - Extra=Using filesort → 排序没有用索引
3. 加联合索引 (company_id, settle_time, order_status)
4. 加完后 EXPLAIN 验证 type=range，rows 降到几千
5. 上预发布环境压测确认
```

## 三、消息队列 — 解耦的"神经系统"

> ⚠️ **对齐真实栈**：自家 MQ 统一是 **Kafka**。本节以 Kafka 为主线讲 MQ 的解耦 / 削峰 / 最终一致，RocketMQ / RabbitMQ 仅作为"为什么没选它们"的选型对比出现，别报成自家栈。事务语义一律落到 **outbox 本地消息表 + 消费幂等**（见 [`02-2-技术栈深度面试题库.md`](02-2-技术栈深度面试题库.md) 避坑指南）。

### 场景1：订单状态同步多个下游系统（Kafka）

**业务场景**：一笔大宗交易的订单状态变更（待确认→已确认→已付款→已发货→已收货→已结算），需要同步通知：仓储系统（备货/出库）、财务系统（记账/开票）、风控系统（额度调整）、客户 APP（推送通知）。

如果同步调用：
```
交易服务 → 仓储服务（等3秒）
         → 财务服务（等5秒）
         → 风控服务（等2秒）
         → 客户通知（等1秒）
总耗时 11秒，任何一个挂了整个链路崩
```

改成异步，一个 topic 多个消费组各取所需：
```java
// 订单状态变更后，发一条领域事件到 Kafka（key=orderNo 哈希分区，保证同订单分区内有序）
kafkaTemplate.send("order.status.changed", orderNo,
        OrderStatusChangedEvent.of(orderNo, from, to));

// 仓储 / 财务 / 风控 / 通知各自起一个消费组订阅同一 topic，
// 各自维护自己的 offset，独立消费、互不影响、互不抢消息
```

**面试要说清楚**：
- **解耦**：交易服务只发一个 topic，谁消费、消费几次由下游自己声明消费组，交易服务不感知
- **削峰**：冬储期日均订单量暴增 5 倍，Kafka 靠磁盘顺序写先把消息囤下来，下游按自己速度消费（消费组多实例并行 + 分区水平扩展）
- **最终一致性**：B2B 场景允许秒级延迟，不允许丢消息（→ `acks=all` + 消费幂等 + 死信 topic / 补偿表）
- **为什么这条链路用 Kafka 而不是 RabbitMQ**：同一份订单事件要被 4 个下游重复消费，Kafka 的"一个 topic 多个消费组各自维护 offset"天然适配；RabbitMQ 一条消息消费完即删，多下游要么多队列扇出、要么再抄一份，扩展成本高

---

### 场景2：为什么我们选 Kafka 而不是 RocketMQ / RabbitMQ？

| 维度 | Kafka（自家选型） | RocketMQ | RabbitMQ |
|------|------------------|----------|----------|
| 定位 | 高吞吐分布式日志 / 流平台 | 业务消息 + 事务消息 | 轻量业务消息 |
| 吞吐 | 单机十万级+（顺序写 + 零拷贝 + 攒批） | 十万级 | 万级 |
| 多下游消费 | 一个 topic 多消费组天然扇出 | 支持，但 offset 模型不如 Kafka 顺手 | 靠多队列扇出，较重 |
| 顺序性 | 分区内有序（key 哈希分区） | 队列内有序 | 队列内有序 |
| 事务消息 | 无原生 half-message，用 outbox 本地消息表补 | 有原生事务消息 | confirm 机制 |
| 生态 | 流处理 / 数据管道 / 大数据一体 | 中小规模业务系统 | 简单业务解耦 |

**自家选型理由**：
- 大宗商品交易的事件量级 + 数据管道需求（行情、成交、履约凭证流的落库与分析）本来就要 Kafka，**一套 MQ 同时覆盖业务异步 + 数据管道**，不引入第二套中间件
- 一个事件被多下游重复消费是常态（订单事件同时喂仓储 / 财务 / 风控 / 通知），Kafka 多消费组模型最省心
- 团队只维护一套 MQ，学习成本和故障面都小

**追问："Kafka 没有事务消息，发消息和本地事务的一致性怎么保证？"**

→ 用 **outbox 本地消息表**：把业务操作和"待发送消息"写进同一个本地库的同一个事务（要么都成功、要么都回滚），再由独立线程 / 定时扫表把消息投递到 Kafka，投递成功打标。消费侧靠**幂等**（业务唯一键去重表 / 状态机判重）兜住重复投递。它比原生事务消息多一次轮询，但把一致性责任握在自己手里，也避免 MQ 不可用拖垮主链路。

---

### 场景3：Kafka 消息丢了 / 重复了怎么办？

**面试三连问的标准答案（按 Kafka 讲）**：

```
生产者丢 → acks=all（等 ISR 中所有副本确认）+ retries 重试 + enable.idempotence=true（幂等生产者防重）
Broker丢  → replication.factor>=3 + min.insync.replicas>=2（至少 2 副本落盘才算成功），关闭 unclean.leader.election
消费者丢 → 关闭自动提交，业务处理完再手动 commit offset；异常不提交，交给重试 / 投递到死信 topic
重复消费 → 消费幂等：业务唯一键去重表 / 状态机判重，offset「至少一次」+ 幂等 = 业务上「恰好一次」
```

B2B 金融场景：**宁可慢，不可丢**。生产端 `acks=all` + 幂等生产者，Broker 多副本同步落盘，消费端手动提交 offset + 死信 topic + 补偿表，四重保障。

## 四、Elasticsearch — 搜索不是"LIKE"

### 场景1：合同全文搜索

**业务场景**：法务要找"去年跟 XX 钢铁厂签的含'质量异议'条款的所有合同"。MySQL LIKE？5 亿条合同文本，查到天荒地老。

**技术方案**：
```
合同创建 → MySQL 存结构化字段（金额、日期、状态）
         → ES 存全文（合同正文、条款内容）
         
搜索时：ES 返回合同 ID 列表 → MySQL 查完整信息
```

**为什么用 ES？**
- 倒排索引：先把文档切词成"词条→文档ID"的映射表，搜索时直接翻字典，O(1)定位
- 不用扫全表，不用 like '%质量异议%'

**追问："ES 为什么快？MySQL 为什么慢？"**

→ MySQL B+Tree 索引最左前缀匹配，`LIKE '%质量异议%'` 无法利用索引必须全表扫描。ES 倒排索引是"词条→文档列表"的映射，"质量异议"这个词直接定位到包含它的所有文档。

### 场景2：仓单/提单结构化搜索

**业务场景**：运营要筛选"上海仓库的螺纹钢仓单，库存>100吨，入库时间在最近30天"。

MySQL 能做，但 12 个筛选条件 + 4 张表 join + 百万级数据 → 慢。ES 的 filter 不参与打分，直接跳转到位图命中，毫秒级返回。

## 五、分布式事务 — B2B 绕不开的坎

### 场景：下单扣库存 + 扣额度 + 创建合同

**业务场景**：大宗交易下单涉及三个操作：

```
1. 库存服务：锁定 500 吨螺纹钢
2. 风控服务：扣减客户授信额度 200 万
3. 合同服务：生成电子合同
```

**必须同时成功或同时失败**。

### 方案演进（面试要能讲出这个思考过程）

**阶段1：本地事务** → 不行。三个服务三个数据库。

**阶段2：Seata AT 模式** → 自动回滚，但性能损耗大（两阶段提交，锁时间长），B2B 高并发交易扛不住。

**阶段3：Saga 模式（推荐）** → 每个服务执行成功调下一个，失败则调上一个的补偿接口：
```
下单成功 → 锁库存成功 → 扣额度成功 → 创建合同成功 ✅

如果"扣额度"失败：
下单补偿（释放库存）→ 释放库存（补偿）✅
```

**为什么 B2B 供应链适合 Saga？**
- 操作之间有几秒的时间差是可接受的（不像支付秒级）
- 补偿逻辑天然存在（锁库存→释放库存，扣额度→恢复额度）
- 不用全局锁，并发性能好

**追问："Saga 有什么问题？"**
- 隔离性问题：A→B→C 执行中，B 还在进行时，另一个事务已经读到了 A 的结果。B2B 供应链场景一般用"状态机"解决——状态未到达终态前，下游不认。

## 七、分布式锁 — 多节点下的"排队"

### 场景：每日结算任务只能跑一次

**业务场景**：每天凌晨 2 点跑日终结算，生产环境部署了 3 个节点，如果三个节点同时跑，账就乱了。

```java
// Redisson 分布式锁
RLock lock = redisson.getLock("settle:daily:20260716");
try {
    if (lock.tryLock(0, 30, TimeUnit.MINUTES)) {
        // 执行结算逻辑
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

**追问："Redis 分布式锁有什么缺陷？主从切换怎么办？"**

→ 主节点刚写入锁，还没来得及同步到从节点，主挂了，从升级为新主——锁丢了。RedLock 算法：向多个（5个）独立 Redis 节点依次获取锁，超过半数成功才算加锁成功。但 RedLock 有争议（Martin Kleppmann 认为它不保证安全性），B2B 金融场景建议用 ZooKeeper 的临时顺序节点做分布式锁（依靠 ZAB 协议保证一致性）。

## 十、面试场景串联：完整参考话术

面试官：**"介绍一下你们的技术架构。"**

参考回答（控制在 4-5 分钟）：

> "我们服务的是大宗商品供应链，核心链路是询价→签约→支付→发货→结算。系统是**异构四层架构**，我按"接入 → 业务 → 桥接 → 撮合"的顺序讲。
>
> **① 接入与网关层**：三端接入——外部大屏看行情和运营监控、普通客户端面向中小贸易商、机构客户端面向大客户，都覆盖 PC 和移动。入口是我们 **Java Web 自研的网关 midservice（多实例）**，承担统一鉴权、限流、租户路由和请求日志；midmon 做监控告警和链路追踪。为什么自研？因为三类租户的限流配额和鉴权策略差异极大，通用网关难做租户级分级路由。
>
> **② Java 业务中台**：管理系统 10+ 模块（客户、超级账本、商品类目、交易、合同、门户、权限、交易风控）+ 业务服务集群 12+ 微服务（认证、用户、账本、合同、资金、运力、创新挂牌、自由竞价），按**业务能力垂直切**而不是按技术层切。同步调用走 Hessian over HTTP，异步统一用 **Kafka**，事务语义用 **outbox 本地消息表 + 消费幂等 + 定时扫表兜底**。
>
> **③ DS 数据中心**：这一层是我最想讲的，也是异构架构的关键——它是 Java 写的**防腐层（ACL）**，把 C 撮合引擎的 TCP 二进制报文翻译成 Java 业务能消费的标准接口和领域事件。同步走 Hessian over HTTP，异步走 Socket 长连接；连接管理、心跳、重连、熔断降级、请求排队、traceId 跨异构透传全在这里。**异构复杂度收敛在 DS 一层，C 团队和 Java 团队各自独立演进、互不阻塞。**
>
> **④ C 撮合引擎**：单线程纯内存撮合 + 异步落库，选 C 换的是**延迟确定性**——Java 的 GC 抖动在这个场景不可接受。它只暴露"标准化指令输入 / 撮合事件输出"，撮合算法对业务团队是黑盒。
>
> **⑤ 底座与生态**：MySQL 双实例做读写分离和容灾，MinIO 存合同 PDF、仓单扫描件、质检报告等履约凭证；Canal 监听 binlog 同步到独立缓存服务（封装 Redis），加速行情和挂牌列表的高频读。右侧对接银行、物流、CTRM、开票、企查查、供应链金融等 9+ 外部系统，每个接口都是**熔断降级 + 异步回调 + 日终对账**兜底。
>
> **我在其中的角色**：我不写 C，但 DS 是 Java 写的、正好在我的技术栈覆盖范围内——我用『接口契约治理 + DS 协议转换逻辑 review + 可观测性（撮合 TPS / 积压队列 / P99 延迟）』管住交易核心。**你能管住的边界，就是你能负责的边界。**"

> **自检**：如果这段里出现了 Nginx / RabbitMQ / RocketMQ / Spring Cloud，说明你在讲"教科书架构"而不是"自家架构"——自家是 **midservice 自研网关 + Kafka + 异构四层**。深度追问见 [`02-2-技术栈深度面试题库.md`](02-2-技术栈深度面试题库.md)。
