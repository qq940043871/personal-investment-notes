二、2 分钟版（第二击 · 技术面 / 总监面）
〔锚点 + 团队 · 25s〕我做技术 13 年，前 2 年在金融清算系统打底，练的是"数据精确性大于一切"；后 11 年一直在这家 B2B 现货贸易平台，从 0 到 1 参与核心交易系统，现在带 20 人研发团队——3 个 C 做撮合内核、6 个 Java 做业务中台、5 个 Vue 做前端、5 个测试做质量，向总经理汇报。
〔① 产品做什么 · 15s〕产品做一件事：把大宗现货的找货、签约、付款、交收、结算、开票全链路搬到线上，做成一个可交易、可履约、可融资的数字化市场。不是信息撮合网站，是把"签了合同之后的事"也线上化。
〔② 解决什么问题 · 35s〕客户买单有四个死结：不敢买——跟陌生人做几百万的生意，先款怕不发货、先货怕不给钱；找不准——打五个电话比价，问到一半价格就变了；跑断腿——合同邮寄改四版、跑银行打款、月底三个人对三天账；缺钱——看到低价货没钱吃，货压仓库占资金。解法一句话：把"对人的信任"换成"对系统的信任"，把"人跑"换成"数据跑"。
〔④ 行业特点 · 20s〕这四个死结不是产品没做好，是行业决定的。大宗现货有五个"不一样"：单笔大、周期长（一笔 1-3 个月、十几个状态）；非标、交收差异大；价格跟着行情走；金融属性强；参与方和单据多。这五个特点直接决定了系统怎么搭。
〔⑤ 四层架构 · 40s · 边说边画〕所以技术分四层，从上往下：
接入层
PC / 移动 / 大屏 + 机构 API只干一件事：把终端差异收敛掉——统一登录、权限、租户隔离。
▼
网关层
midservice（业务网关）+ midmon（监控网关）一句话分工：一个管"请求怎么进"（鉴权/限流/路由/协议适配），一个管"系统怎么样"（指标/健康度/告警）。分两个是因为关注点不同，混在一起改一个就波及另一个。
▼
数据
交换层
DS 数据中心 · Kafka · Canal+缓存 · 外部生态适配整套架构的核心。① DS 做异构桥接：C 内核只认 TCP 自定义二进制，上层是 Hessian 标准接口，协议解析/连接管理/心跳保活/版本兼容全收在这；② Kafka 做异步与最终一致；③ Canal+缓存做读加速；④ 银行/仓储/物流/税务/签章/企查查的统一适配也收在这层。不设这层，协议解析会散落到 12+ 服务里，出错率高、没法维护。
▼
业务层
Java 微服务业务中台 + C 撮合内核交易 / 合同 / 履约保证 / 资金结算 / 仓单 / 物流 / 规则配置 / 会员；交易域背后挂 C 单线程内存撮合内核（先写 WAL 再内存撮合、异步落库）。业务逻辑一行都不放进 C——这层要"改得快"，C 要"算得准"，混在一起两个优点都没了。
收口一句：四层各自能被单独替换——这就是我判断边界切得对不对的标准。C 负责快、Java 负责稳、DS 负责翻译、网关负责守门。
〔⑥ 我的职责 · 15s〕我的职责也是三条：架构决策（四层边界怎么切、异构怎么治、复用还是新建、排期取舍）、机制建设（评审、On-call、技术债台账、接口契约治理）、疑难兜底（团队接住 80% 现场问题，我只介入疑难和跨系统）。业务纵深上，合同复杂交收和履约保证是我最熟的两块。

收尾："我的产出不是代码行数，是团队的可预测性和系统的边界。"
三、3 分钟版：六点 + STAR 两个场景
六点部分直接复用 2 分钟版，不要重背。这里只加两个场景——一个业务向、一个技术向，别都讲技术，也别都讲管理。
STAR 场景一（业务向）· 交收场景化改造
S（10s）平台早期客户差异全靠参数开关实现。光合同交收就有先合同后款、先款后合同两大类，每个客户节奏还不一样，于是不断加开关去凑。加到后来改一个参数不知道波及哪条链路，新客户上线要先配几百个参数，平均排 2 个月——销售签回来的客户在排队等系统。
T（8s）我负责收敛，目标两个：新客户上线压到 1 周以内；主链路不留客户定制分支。
A（20s）四步：① 盘点存量参数，按"交收节奏"归并成场景——先款后货、先货后款、定金+尾款、分批提货；② 场景里封装参数组合、校验规则和状态流转，运营按场景选，不裸调参数；③ 不变的部分抽成统一引擎（策略模式 + 规则配置）；④ 老客户迁移时三条链路双跑对账，签约、付款、交收逐笔比对，一致再切。
R（7s）新客户上线 2 个月 → 1 周；参数从几百个收敛成十几个场景；主链路无定制分支，回归范围固定。
判断客户要的不是一百个开关，是"先款后合同"这句话背后的完整交收场景。
STAR 场景二（技术向）· 跨月长事务一致性
S（10s）一笔交易跨 1-3 个月、十几个状态：签约、保证金、备货、发货、质检、结算、开票。每个状态要同步 4-6 个系统。早期是点对点调用，一次超时就出现"钱扣了单没成""货发了账没记"，排查要跨四五个系统翻日志。
T（8s）把一致性做成可解释、可补偿、可对账，硬指标是资金零差错。
A（22s）四层机制：① 状态机——每个状态定义前置条件、触发事件、副作用、超时处理，不允许隐式状态；② Saga——每个正向动作配补偿动作，补偿必须幂等；③ 事件驱动——跨系统不直连，Kafka + 本地消息表，业务事务与消息同库落盘再异步投递；④ 对账兜底——T+1 拉银行/仓储对账文件逐笔比对，差异进人工。
R（7s）运行三年零资金差错；对账差异率从行业 8% 降到 0.1% 以下；出问题能定位到"哪一步没成、补哪一步"。
判断能跑的状态机一个月够，不会出事的状态机要两年——因为你要见过所有异常，才知道补偿路径怎么写。
收尾（15s）：这两个场景一个是把业务复杂度收敛，一个是把技术风险收敛，本质是同一件事——在正确的边界上做决策。我这次看的是技术经理岗，想把"产业互联网 + 中小团队机制建设"这套经验用到更复杂的场景里。
四、5 分钟版：深挖 + 选型取舍
背景：大宗商品传统交易在线下，三个核心痛点：客户不信任平台、不愿资金过夜；仓单造假频发（同一批货多张开仓单骗贷）；交易模式复杂（挂牌/竞价/询价/基差等多类模式）。
可加的第三段——多模式交易引擎：多类模式每个写一套维护成本爆炸；用策略模式 + 模板方法定义流程骨架（挂单→撮合→成交→结算→交收），各模式只实现差异步骤；风控规则外部化成轻量 DSL，存库热加载。不涉及新外部对接时，新模式 2 天上线。
选型取舍（最能体现判断力的一段，必背）
为什么保留 C 不改写 Java：撮合是 CPU 密集的强确定性场景，GC 停顿就是不公平；重写等于拿最不能出事的部分换"看起来整齐"。
为什么单独一个数据交换层：不设这层，协议解析散落 12+ 服务，出错率高、没法维护；收敛在一层，上层调 C 就像调本地方法。
为什么不上微服务全家桶：大宗交易请求量相对稳定，Hessian + 自研网关够用，轻量方案少一层运维负担。
结论句：架构选型不是选最先进的，是选约束下风险最小的。能讲清楚"为什么不做什么"，比讲做了什么更体现判断力。
互补（收尾）：这套经历和我做 Agent 编排的经验是互通的——多步骤编排本质上也是一种 Saga，两边互相借鉴。

② 解决什么问题：客户买单的四个死结
死结一
不敢买 — 信任
靠熟人关系做生意，人脉圈就是天花板；先款怕不发货，先货怕不给钱
平台担保 + 资金存管（钱不过对方手）+ 履约信用档案
本质：把"对人的信任"变成"对系统的信任"
死结二
找不准 — 信息
打五个电话比价，问到一半价格就变了；说有货，下单后没货
实时行情 + 一键比价 + 标准编码 + 库存与 WMS 实时校验
下单即校验，杜绝"说有货其实没货"
死结三
跑断腿 — 效率
合同邮寄改四版、跑柜台打款、月底三个人对三天账
电子签章 + 银企直连 + 物流轨迹 + 全链路自动勾稽
交易 5~7 天 → 1.5 天；对账 3 人天 → 2 小时；签约 1 周 → 1 天
死结四
缺钱 — 资金
看到低价货没钱吃，银行审批 2 周；货压仓库就是死钱
预付融资 / 仓单质押（货值 70%）/ 应收融资（80% 变现）
让钱不够的买方也能成交，直接提高成交率
收口：四个死结一句话串起来——把"对人的信任"换成"对系统的信任"，把"人跑"换成"数据跑"。为什么银行做不了、我们能做？平台有真实交易数据，银行才敢放款。没数据的人做金融是在猜，我们是在算。

高频追问速答（技术 7 问 + 管理 6 问）
技术类
Q1 为什么用 C 写撮合，不用 Go / Rust？
评估过：Go 的 GC 比 Java 轻但仍会停顿，撮合要的是确定性；Rust 性和能都好，但团队没储备、招聘交付风险大；C 在金融交易生态最成熟。另外引擎只做撮合这一件事，代码量不大，维护成本可控。
Q2 数据交换层不会成为瓶颈吗？
不会。这层只做协议转换、连接管理和事件转发，不做业务计算；TCP 二进制解析是纯 IO，Java NIO 完全胜任。真正的瓶颈在撮合内部，那部分在 C 层。DS 延迟在微秒到毫秒级。
Q3 你管 Java 团队，C 层代码怎么管？
不管 C 代码本身，但管 C 和 Java 之间的契约。抓手就是数据交换层——报文格式、握手保活、协议版本兼容都在这层落地；能 review DS、能定义协议规范，就等于管住异构通信全链路。技术上叫防腐层，管理上叫边界治理。
Q4 12+ 微服务，服务治理怎么做？
Hessian 做 RPC，服务发现和配置由自研 midservice 统一管理，监控走 midmon。我们不是互联网级高并发，大宗交易请求量相对稳定，所以没上 Spring Cloud / Dubbo 全家桶——少一层运维负担，团队也 hold 得住。
Q5 你做过什么关键架构决策？为什么？
最有代表性的是"要不要把 C 内核重写成 Java、统一技术栈"。我否决了：一来撮合是 CPU 密集的强确定性场景，GC 停顿是硬伤；二来撮合是资金链路的心脏，重写等于拿最不能出事的部分换"看起来整齐"。我选的是保留 C、用数据交换层把异构边界管住，两边团队互不阻塞。架构选型不是选最先进的，是选约束下风险最小的。
Q6 你踩过什么坑？怎么复盘的？
早期客户注册后要同步到交易、合同、结算、风控，当时点对点直连。某模块超时就出现"注册成功但下游没收到"——商户看不到商品、下不了单，排查跨四五个模块翻日志。5 Whys 根因是把跨模块同步当 RPC 设计、没当事件设计。改成 Kafka 事件 + 本地消息表 + 消费幂等 + 对账兜底，并留制度：跨模块必须走事件、排查手册加标准处置、新模块必须订阅标准事件。只讲事故是报告，讲到规则沉淀才是复盘。
Q7 四个死结里哪个最难解？
缺钱最难，因为它不是技术问题，是信任定价问题。前三个死结本质是流程线上化，能做就能解；缺钱要靠数据说话——平台有真实交易、仓储、履约数据，银行才敢放款，所以它是数据飞轮的产物。这也是我们做仓单可信链的原因：没有可信的货权数据，金融就是空的。
管理类（答法统一：机制 + 动作 + 证据）
Q8 你怎么做团队管理和项目把控？
流程线：需求收口评审、设计/技术评审、QA 验收、发布评审、移交评审，关键节点强制过审，不通过不流转。进度线：需求池/已评审/开发中三态看板 + 排期表，多项目并行可视化，优先保关键路径。一句话：我不只是管进度，更管研发过程的确定性。
Q9 怎么提升团队技术氛围？
三个抓手：① 周技术分享轮流主讲，讲项目里的真问题（CPU 飙高怎么定位、接口失败怎么排查）；② 结对辅导定向带教，明确核心储备成员目标；③ 调研沉淀——低代码、可视化规范、UI 规范都落成文档进知识库。氛围是让成员从"只写业务代码"长出"关注架构、性能、规范和效率"。
Q10 线上故障怎么处理？
先止损再定位：保留日志、监控、操作记录；恢复后复盘，明确根因、责任人、改进措施，形成故障报告并跟踪闭环；最后把问题转成规范或自动化检查项，进排查手册和告警规则。故障不可怕，可怕的是同一个问题重复发生——产出永远是"防再发"。
Q11 复杂业务与开发冲突怎么处理？
冲突多源于"业务一句话、开发一大坑"。做法是把不确定性前置：先出原型和交互，再写需求规格说明书，组织需求评审和技术评审，把边界、状态、异常流程明确后再开发。反复返工的根源不是能力，是需求在开发阶段还在变形。变更不设单独流程，靠评审前置控制。
Q12 做过哪些架构优化？
三类：复用化（登录/开户/认证/签章组件化）、配置化/低代码（流程编排、表单设计器、界面装修设计器）、治理化（信创改造方案、外联网关统一收口）。目标不是"更先进"，是交付更快、复用更多、风险更小。
Q13 怎么保证系统稳定性？
三层。目标层：重大故障 ≤1 次/年、中等 ≤3 次/年、首页 <1.5 秒、核心并发 ≥1000/秒（当时设定的考核指标）；机制层：上线评审、性能压测、监控告警、On-call 轮值；闭环层：故障报告 + 复盘，重复问题必须转成规范或自动化检查项。稳定性不是测出来的，是用制度把每次事故变成防线。

难点一 · 银行资金存管的资金流一致性
结论：资金不过平台账户——客户在银行开存管子账户，平台只有指令权。
链路：下单 → 带幂等键 reqId 发扣款指令 → 买方子账户扣款划入卖方 → 异步回调更新订单。
数字：超时 3 秒带同 reqId 重试 → queryByReqId 主动查询 → 仍不确定标记"资金状态不确定"进人工对账，T+1 银行对账文件兜底（差异率行业 8% → 0.1% 以下）。
追问：超时怎么确认扣没扣？幂等键设计 / 银行不支持去重怎么办？5 家银行差异怎么管（适配器 + 配置中心）。
难点二 · 区块链 + 物联网 + WMS 三层仓单可信链
结论：物联网证明"货在"、WMS 证明"仓单与货对应"、区块链证明"不可篡改"，单做任一层都不成立。
数字：视频流不上云（8 路 1080P 约 2TB/天），边缘网关只传 AI 事件截图 + 结构化数据，带宽降 95%+。
一致性：Saga 跨层，上链异步不阻塞 WMS；仓单设"待上链"中间态，上链失败不可交易/融资。
追问：WMS 成功但上链失败怎么办？仓单拆分（1000 吨→5×200 吨）链上链下怎么处理。
难点三 · 多交易模式的可插拔引擎
结论：策略模式 + 模板方法——模板定流程骨架（挂单→撮合→成交→结算→交收），策略类只实现差异步骤。
风控：自研轻量规则 DSL（mode / rules / condition / action），规则存 DB 热加载，不用 Drools。
数字：不涉及新外部对接时新增一种模式约 2 天；涉及新外部系统再加 2-3 天。
追问：为什么不用 if-else？风控硬编码还是配置化？新增成本？
难点四 · 点价交易的期现实时联动
结论：行情快照 + 版本号锁价——行情更新递增 version，摘牌带 version，不一致则拒绝并提示"价格已变动"。
数字：期交所 → 行情服务商 → 行情网关 → 交易引擎，端到端 <10ms；高频 tick 背压，丢中间 tick 只留最新价。
白盘夜盘：多行情源，新连接 ready 后再断旧连接（优雅切换）；切换窗口禁摘牌。
追问：行情延迟多少？摘牌价格错位怎么防？夜盘断连怎么处理？
难点五 · 全流程 8 模块数据一致性
结论：不用 Seata AT（8 服务全局锁资源不可接受，且管不了银行外部接口），用编排式 Saga——本地事务 + 逆序补偿 + 最终一致。
设计：协调器维护执行状态，宕机可从实例表恢复继续补偿；补偿动作必须幂等。
顺序：Kafka 按交易 ID 做 partition key 保单交易内有序；失败事件进死信队列不阻塞 partition。
查询：CQRS——写库各服务本地库，读库聚合视图（Redis + ES），一次查询返回全链路 steps。
追问：为什么不用 Seata？补偿顺序？8 服务事件顺序？全链路状态怎么查？
难点六 · 高并发撮合与流式风控
结论：撮合纯内存，买卖盘红黑树（价格+时间优先）O(log N)；先写 WAL 再内存撮合，宕机可恢复；集合竞价按"最大成交量原则"批量撮合。
风控两层：实时 <5ms（规则预编译成内存决策树）+ 深度风控异步（Flink 检测对敲/自买自卖）；实时风控故障熔断降级为"宽松模式"，绝不中断交易。
峰值：竞价截止前 5 分钟可达日常 10-50 倍 → 引擎无状态 + K8s HPA + Kafka 缓冲 + 批量撮合 + 单会员频控（10 次/分钟）。
追问：撮合数据结构？风控凭什么 <5ms？竞价峰值怎么扛？

五个成果（挑 2-3 个讲）
成果一
数据交换层 — 驾驭 C+Java 异构架构
问题C 内核是黑盒，只暴露 TCP 二进制；上层 12+ Java 服务无法直连
方案防腐层：Java NIO 收二进制帧 → 协议解析/版本路由 → 上层 Hessian 标准 DTO
结果异构复杂度收敛在一层，C 与 Java 各自独立演进
"我不写 C 代码，但我设计了这一层让 C 和 Java 能对话。技术经理的价值不是写了多少代码，是在正确的边界上做了正确的决策。"
成果二
交收场景化改造 — 参数收敛成场景（STAR 场景一）
问题客户差异全靠参数开关，参数越加越多、组合失控，新客户先配几百个参数
方案收敛成场景（先款后货/先货后款/定金尾款/分批提货）+ 场景内封装校验与状态流转 + 统一引擎 + 老客户双跑对账
结果新客户上线 2 个月 → 1 周，主链路无定制分支
"客户要的不是一百个参数开关，而是'先款后合同'这句话背后的完整交收场景。"
成果三
跨月长事务一致性 — 三年零资金差错（STAR 场景二）
问题一笔交易跨 1-3 个月、十几个状态，每状态同步 4-6 个系统
方案状态机 + Saga（正向 + 幂等补偿）+ Kafka 事件 + 本地消息表 + T+1 对账
结果运行三年 零资金差错，对账差异率 8% → 0.1% 以下
"能跑的状态机一个月够，不会出事的状态机要两年——因为你要见过所有异常。"
成果四
管理三件套 — 从救火队长到技术领导者
①On-call 轮值：主副双岗，P0-P3 四级 SLA；凌晨被叫起月均 8 次 → 2 次
②技术债台账：债务项/风险/成本/优先级可视化，隐性 → 显性 → 可控
③20% 带宽：每迭代固定产能还债，被动响应 45% → 15%
"临时方案不可怕，没有退路、没有记录、没有终点的临时方案才可怕。"
成果五
场景化工作台 — 从"功能菜单"到"任务向导"
问题左侧几十个入口，客户不知道点哪里，培训要半天
方案按任务组织：我要买货/卖货/发货/对账，一条线性引导流 + 角色视图过滤
结果培训 半天 → 30 分钟，客服咨询量下降 60%
"客户是带着任务来的，不是来'逛'的。按功能堆菜单，等于把说明书甩给他自己研究。"
