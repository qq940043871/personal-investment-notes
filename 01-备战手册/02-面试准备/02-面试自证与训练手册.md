## 第一篇 · 策略与心态

### 一、心态建设 — 先破心魔

#### 1.1 你不需要什么都懂

技术 Leader 面试焦虑的三个来源，以及为什么它们不成立：

| 焦虑来源 | 为什么不用怕 |
|---------|------------|
| "他会不会问我没听过的技术？" | 你是技术 **Leader**，不是技术 **专家**。Leader 面试的核心考察点是**决策力、治理能力、业务理解、团队管理**。你不懂 C 语言细节，但你管得住 C 引擎。 |
| "万一问到盲区怎么办？" | 面试是双向选择，不是考试。敢于说"这块我不深，但我有另一种思路"比硬撑强 100 倍。 |
| "需要准备的东西太多了" | 实际上你只需要准备好**三个主场**——剩下的都是客场，客场不需要赢，不丢分就行。 |

> **核心心法**：Leader 面试不是"回答所有问题"，是"把 80% 的面试时间花在自己最强的 3 个主场上"。

```
不慌 = 知道什么不必准备（减负）
     + 把必准备的主场练到肌肉记忆（聚焦）
     + 有不会的问题时的兜底话术（安全感）
     + 相信不是审判而是双向选择（心态）
```

#### 1.2 你的三个主场（画清楚边界）

基于你的真实经验，你的不可替代性集中在三个方向。凡不在这三个方向上的问题，都是客场，及格即可。

#### 主场一：驾驭异构架构（技术决策力）

**为什么这是你的主场**：
市面上 90% 的 Java 技术经理只会 Spring Boot 全家桶。你能同时面对 C 撮合引擎 + Java 业务中台 + Vue 前端三套异构系统——这是跨语言、跨范式的治理能力。

**必须脱口而出**：
- 四层架构：接入 → 网关(midservice自研) → 业务中台(DS+交易核心+12微服务) → 数据层
- 双核驱动：C 撮合引擎（单线程内存撮合，纳秒级确定性）+ DS 数据中心（Java 防腐层）
- C↔Java 通信：TCP + 自定义二进制报文；Java↔Java 通信：Hessian
- DS 数据中心的价值：收敛异构复杂度到单一桥接点，业务层完全不感知 C

#### 主场二：技术+业务双修（商业思维）

**为什么这是你的主场**：
大多数技术经理说不清自己做的产品到底解决了什么客户问题。你能从挂牌讲到交收、从资金讲到税务、从仓单讲到供应链金融。

**必须脱口而出**：
- 五大业务模块：交易模式 / 履约保证 / 数据服务 / 规则配置 / 生态对接
- 客户价值三层：效率（5天→1.5天）/ 风险（三年零差错）/ 增长（供应链金融）
- 竞争壁垒：数据飞轮 / 配置化引擎 / 外部集成深度 / 行业复合人才 / 信任资产

**快问快答训练**：
- "你们平台解决什么问题？" → "大宗贸易线下交易效率低、风险高，我们让交易周期从5天降到1.5天、三年零资金差错"
- "客户为什么用你？" → "不是因为我们数字化，是因为我们钻进了线下做不了、做不好、做不快的缝隙"
- "和找钢网/1688有什么区别？" → "他们是轻量撮合，我们是重度垂直——一个订单几百万，履约全闭环"

#### 主场三：从救火队长到技术操盘手（领导力）

**必须脱口而出**：
- 管理哲学：靠制度管人、靠台账管债、靠流程管风险
- 技术债治理：台账 + 还债比例（每迭代20%时间）+ 向上沟通公式
- 团队机制：On-call 轮值、事故复盘不追责、Code Review 卡债
- 契约治理：跨团队接口SLA、决策权三档（做/建议/知晓）

**必准备的故事**：
> "我刚接手的时候是个救火队长。后来做了三件事：建了 On-call 轮值，逼团队成长也逼系统暴露真问题；建了技术债台账，把隐性的坑全部显性化；推了事故复盘不追责文化。半年后救火时间降了一大截，冬储期一整季零 P0。"

#### 1.3 客场生存法则

面试中大概 30% 的问题不在你的三个主场上。客场不需要赢，及格就行。

| 问题类型 | 识别标志 | 策略 |
|---------|---------|------|
| **知识盲区** | 问一个你没用过/不了解的技术 | "这块我不深，但根据我的经验，类似场景下核心考量是 X 和 Y……" |
| **假设性开放题** | "如果你从零设计这个系统……" | 用你已有的经验框架去套：先分层、再定边界、再讲 trade-off |
| **行为面试** | "你有没有遇到过 XX 情况……" | 永远用 PEARL 框架，讲真实发生过的事 |
| **压力题** | "你觉得你最大的弱点是什么？" | 诚实但策略性——讲一个真实弱点 + 你已经在做的改进 |

**不会就说不懂，但给一个"平移思路"**：
> "这个技术我没直接用过，但如果类比到我们平台的情况，核心问题应该是 X 和 Y 之间的 trade-off。我们之前处理过类似的场景，当时的思路是……"

**把客场问题引导回主场**：
> 面试官："你们怎么做的 A/B 测试？"
> 你："我们没做 A/B 测试。但我们在多租户场景下，通过规则引擎 + 场景化配置实现了客户的个性化需求——光合同交收就有先合同后款、先款后合同两大类，100 多个客户各有不同的计费规则和风控阈值，5 分钟改规则生效。这个跟 A/B 测试的底层逻辑类似。"

#### 2.3 PEARL 回答框架（STAR 升级版）

| 字母 | 含义 | 你的打法 |
|------|------|---------|
| **P**roblem | 问题是什么 | 用具体数字："冬储期交易量从日均 1000 笔暴增到 8000 笔" |
| **E**vidence | 有多严重 | "撮合引擎 CPU 冲到 92%，有一次差点崩，所有交易挂起 5 分钟" |
| **A**lternatives | 做过什么比较 | "我们比较了三个方案：加机器（不管用）、拆服务（风险大）、分层降级（可行）" |
| **R**easoning | 为什么这么选 | "C 撮合引擎是单线程的，加机器没用。核心思路是把非关键链路降级" |
| **L**esson | 收获和沉淀 | "事后我们建了冬储预案 SOP，第二年零 P0" |

**PEARL 比 STAR 更锋利的原因**：多了 E（严重性）→ 让面试官感受到真实；多了 A（方案对比）→ 展示决策思维；多了 R（推理过程）→ 展示 trade-off 能力；多了 L（收获）→ 证明有复盘能力。

#### 2.4 三个必杀问题

#### 必杀 1：为什么 C 撮合引擎不迁移到 Java？

**第一层（技术事实）**：
> "C 撮合引擎是单线程内存撮合，没有 GC 停顿，延迟是纳秒级且确定性的。Java 做撮合，GC 会在不可预测的时间点暂停所有线程，对于金融交易来说，这个不确定性不可接受。"

**第二层（决策思维）**：
> "我们评估过要不要迁。不是不能迁，是不值得迁。C 撮合引擎跑了多年，稳定、零事故。迁移到 Java 不仅可能引入 GC 延迟，还要重新验证所有撮合逻辑——测试成本巨大，收益为零。"

**第三层（管理智慧）**：
> "我一个 Java 技术经理管 C 引擎，听起来矛盾对吧？但恰恰因为我不懂 C 代码，我才更关注它的可观测性——日志、监控、告警。我建了 DS 数据中心做防腐层，把 C 的二进制协议封装成 Java 对象。我不是管 C 代码，是管 C 引擎的健康。"

#### 必杀 2：你们的平台和找钢网/1688 有什么本质区别？

> "两个本质区别。第一，我们是重度垂直，不是通用平台。1688 做轻量撮合，品类极多但每个品类很浅。我们做大宗交易，一个订单几百万，履约链条极长——从挂牌到签合同到支付到质检到仓储到物流到开票。"
> "第二，我们的壁垒不是技术本身，是数据和集成深度。五年的交易数据形成的定价模型和风控画像，100 多个客户磨合出来的配置化规则引擎，9 个外部系统的技术适配和商务关系——这些不是写代码能解决的，是时间垒出来的护城河。"

#### 必杀 3：你最大的失败是什么？

> "第一年冬储期系统崩了一次，撮合引擎挂了 5 分钟。这不是技术问题——是我作为技术负责人没有提前做容量规划和应急预案。"
> "我学到的不是'怎么修 bug'，是'怎么建体系'。事故之后我做了三件事：建了冬储预案 SOP、推了 On-call 轮值机制、推了技术债台账。第二年冬储，零 P0。"

#### 2.5 三个专用框架（BOUNDARY / SCOPE / PEARL 的分工）

全库只保留这一节定义三套框架的分工，其余文件一律引用，不再各自复述。

| 框架 | 什么时候用 | 权威定义 |
|------|-----------|---------|
| **PEARL** | 主框架，所有经历类/技术深挖类问题的默认答法 | 本文件 §2.3 |
| **BOUNDARY** | 面试官问到你**不熟悉的模块**（C撮合、财务清结算、物流执行） | 本小节 |
| **SCOPE** |纯技术选型/ Trade-off 类问题（为什么选A不选B） | 本小节 |

#### BOUNDARY 边界框架（答"我不熟的模块"）

遇到陌生模块，按 BOUNDARY 四步走：

| 步骤 | 动作 | 示例话术 |
|------|------|---------|
| **B**oundary | 坦诚边界，说清深度区与治理区 | "撮合引擎的撮合算法不是我的深度区，我负责的是它与 Java 层的协作边界" |
| **O**wnership | 说明你 nonetheless 承担的责任 | "但它的可观测性、协议契约、故障演练是我的 Owner 职责" |
| **M**echanism | 给出你建的机制（不是靠个人盯） | "我建了 DS 防腐层统一收口二进制协议，并推动补齐了指标与告警" |
| **R**esult | 落到可量化结果 | "接入方从直连 TCP 的 N 个变为统一走 DS 的 1 个口子，协议变更从改N 处降到改 1 处" |

**一句话模板**：
> "这不是我的深度领域，但我通过 **XX 机制** 保障了该模块与整体的协同——我是这个模块的**接口Owner**，不是它的**代码Owner**。"

#### SCOPE 取舍框架（答技术选型题）

拿到一个"为什么这么选"的问题，内心默念五个词，然后开口：

| 字母 | 含义 | 你开口说的 |
|------|------|----------|
| **S**ituation | 问题发生的场景 | "在我们平台，这个问题的典型场景是……" |
| **C**onstraint | 当时有什么约束 | "受限条件是我们只有 XX 资源和 YY 时间窗口" |
| **O**ptions | 考虑过哪些方案 | "当时我们比较了 A/B/C 三个方案" |
| **P**ick | 选了哪个、为什么 | "我们选了 B，因为……"（展示 trade-off 思维） |
| **E**ffect | 结果和收获 | "最终结果是……，这件事教会我……" |

### 二、业务理解力：五层进阶模型（自证体系）

面试官验证你"懂不懂业务"的方式不是问概念，而是看你能聊到第几层。**每往下一层，竞争力指数级上升**：

| 层次 | 能力描述 | 你的证据（能脱口而出的话） |
|------|---------|------------------------|
| **L1 知道流程** | 说得出交易→签约→履约→结算链路 | "大宗交易七环：询价、看货、签约、付款、履约、结算、融资" |
| **L2 知道痛点** | 每一环的真实麻烦和后果 | "比价差两分钟价就没了；合同晚三天 400 万的单子飞了" |
| **L3 知道赚钱逻辑** | 每类客户靠什么赚钱、在哪流血 | ⭐ 见下方"五方盈利逻辑速查表" |
| **L4 知道角色 KPI** | 客户方每个用系统的人考核什么 | "销售总监看溢价率，财务看回款账期，风控看敞口，仓管看货权清不清晰" |
| **L5 能预判演进** | 客户明年会要什么 | "五个客户都在殊途同归走向'交易+物流+金融'的产业互联网——河南能源 2026 年的转型招标、林控从卖活立木扩到融资中心/发票税务/物流，都是证据" |

### 三、技术把控力：四个维度（自证体系）

业务理解让你"说得上话"，技术把控让你"拍得了板"。四个维度，每个都备好"决策故事"：

#### 3.1 架构判断力——三个代表作

每个架构决策按"**业务问题 → 备选方案 → 取舍逻辑 → 代价**"讲，这是技术经理和架构师的通用语言。完整技术底稿（表设计、五种交收模式等）见第三篇 Q4：

##### 代表作 1：合同域与履约域解耦
- **业务问题**：大宗合同变更极其频繁（补充协议/数量增减/交期调整是日常），履约状态如果耦合在合同上，每次变更都是数据迁移事故
- **备选方案**：一张大宽表全搞定 vs 域解耦+事件联动
- **取舍**：解耦后读写路径变长，但换来合同版本链清晰、履约独立演进——变更频率决定了解耦是必选项
- **代价**：跨域一致性要靠事件+对账兜底，不能靠数据库事务（见 3.2）

##### 代表作 2：双轨履约引擎
- **业务问题**：交收节奏没有统一标准——合同和款项的先后就有两大类：先合同后款（签合同锁价再按节点走款，适合信用好的长期客户）、先款后合同（款到才出合同，适合新客户/高风险交易）；再加上国企类客户要强顺序、贸易商客户要灵活并行
- **备选方案**：一个万能流程引擎硬扛 vs 双轨（状态机轨 + 事件规则轨）
- **取舍**：一个引擎看似省事，实际是两边都不好用——顺序轨用状态机换确定性，自由轨用事件驱动换灵活性，底层共用任务数据结构，监控视角统一
- **代价**：自由轨的异常补偿逻辑复杂，用规则引擎配置化补偿策略，不硬编码

##### 代表作 3：支付渠道适配器
- **业务问题**：平台不能碰资金池（二清是红线），但每个客户的银行/持牌支付通道都不一样
- **取舍**：统一适配器接口 + 渠道插件化（银行直连/银企直联/第三方），资金预检用两阶段提交思路
- **代价**：渠道间能力差异要在适配层抹平（到账时效、回单格式），对账逻辑每渠道一份

#### 3.2 关键 Trade-off 清单（高概率被考 ⭐）

| 追问 | 你的回答框架 |
|------|------------|
| 为什么不用分布式事务跨域保一致？ | "跨域（合同-履约-结算-仓单）我选事件驱动+每日对账兜底，不用 2PC/TCC——因为大额资金场景宁可慢不可锁，同步事务把可用性押上去了；但**资金预检这一跳**我反而用了 2PC 思路，因为钱的事不能有中间态" |
| 为什么履约用状态机+事件双轨而不是纯工作流引擎（Activiti/Flowable）？ | "工作流引擎擅长'人审批'，但大宗履约的核心是'货款票三轨的状态推进'，人工节点只占三成。状态机+事件让机器节点毫秒级推进，人只处理异常" |
| 为什么原型阶段不用 Vue/React 组件化？ | "1300 页原型的诉求是'快验证业务模型'，静态 HTML+CDN 让任何一页都能双击打开给客户演示。但我知道它的边界——所以现在做组件收敛和契约先行的转型规划"（顺势引出技术债管理） |
| 套保系统为什么自研而不是买现成的？ | "敞口计算和现货合同强耦合——点价量、在途量、已点未发、期货头寸要实时轧差，通用风控软件拿不到这些一手数据。自研才能把'现货合同→敞口→期货头寸'做成一条链" |

#### 3.3 工程治理力——两个真故事

> 下方两故事在**第三篇 Q6** 另有 STAR 版（故事 2 / 故事 3），两者同源：本节给"讲点"，Q6 给"S/T/A/R 结构 + 数字"，按场合取用。

**故事 A：接口资产化**——870 个业务请求、244 个文件夹的手工 Postman 集合，写 Python 工具一键生成，统一客户端参数展开和后端 directives 包装两种格式，跨脚本一致性由工具保证。**讲点**："接口文档漂移是团队协作的第一隐性成本，我把它从负债变成资产。"

**故事 B：ICC 系统重构**——参数从本地配置文件迁到 HTTP 接口按 deviceId 实时获取，设计降级路径（本地缓存兜底），分环境灰度。**讲点**："任何去中心化方案必须先设计好降级路径，否则是把稳定性问题换成可用性问题。"

#### 3.4 技术债与优先级管理（管理成熟度的直接证据）

主动讲这套方法论："我把技术债分三类排优先级——
1. **流血债**（影响正确性/资金安全，如对账兜底缺失）→ 本迭代必须还
2. **放血债**（拖慢交付速度，如无组件库、接口无契约）→ 排进季度规划，按"每新增一页放大多少成本"量化给老板听
3. **美容债**（风格不统一如图表库混用）→ 顺手还，不立项"

⭐ **金句**："技术经理的价值不是消灭所有技术债，是让团队知道哪些债在吃利息、哪些债可以先欠着。"

### 五、高光问答设计（预演 Q&A）

**Q1："你怎么定位技术经理这个角色？"**

"三个词：**翻译、拍板、兜底**。翻译——把客户生意语言翻成架构语言，把技术约束翻成老板听得懂的成本收益；拍板——方案分歧时敢做决定并为结果负责，我的原则是'两条路都对时选可回退的那条'；兜底——出了问题技术经理站在最前面，先恢复业务再复盘根因，不甩锅给环境或某个人。"

**Q2："业务方需求很急但架构不允许，怎么办？"**

"先问一句：**急的是什么**？大多数'急'是业务想要结果而不是想要功能。上个月（举真实例子）式回答框架：①确认业务截止时间的真实约束；②给分层方案——先用 80% 方案快速上线，同时明确技术代价记账；③把这次妥协变成下次重构的输入。**妥协可以，但必须被记录、被定价**——无意识的妥协才叫技术债失控。"

**Q3："你怎么让技术团队懂业务？"**

"三个机制：①**新人下现场**——没有跟客户开过会不许写核心模块；②**需求评审讲钱**——每个需求先回答'这帮客户多赚钱还是少亏钱'，答不上来的需求降级；③**业务术语表进代码**——领域模型、变量命名和客户的行业黑话一一对应（仓单就是仓单不是 inventory_doc），看代码就是在看业务。我自己先做到：我能给客户财务讲对账、给风控讲敞口、给老板讲溢价，团队才会相信懂业务是硬要求。"

**Q4："举一个你业务判断救了技术方案的例子？"**（⭐最出区分度的问题）

用双轨引擎回答："最早设计履约系统时，技术方案是纯流程引擎，一条道跑到黑。但我看了太多客户的真实交收——国企要强管控顺序交收，民营贸易商两笔货可能今天发货明天才补合同。是业务判断告诉我：**履约节奏不存在行业标准**，所以必须有双轨。这个判断不是从技术博客来的，是看客户怎么干活来的。反过来，如果我当时只从技术优雅出发做一个万能引擎，现在大概率在给两种客户打补丁。"

**Q5："AI 都这么火了，你怎么看技术经理要不要all in？"**

"我的原则是**场景成熟度决定投入度**。我自己在做 Agent 工程化（LangChain/LangGraph 流水线），知道 LLM 的能力边界——所以我们产品里 AI 的落点选的是：智能推荐（撮合）、单据识别（OCR 结构化）、风控辅助（异常模式发现），这些是'AI 提效、人兜底'的场景；而资金操作、合同生效这类强一致性场景，AI 只做提示不做决策。**用 AI 的前提是你知道它什么时候不可靠**——这是工程化能力，不是追热点能力。"

## 第三篇 · 七问底稿与训练计划


> 源自原 `14-面试训练框架与计划`：基于 p001_b2b_supply_chain（大宗商品合同履约与供应链产业电商平台）项目整理。

### 第一部分：提问框架优化

#### 1.1 原始九问的问题

你的原始九问是：产品是什么 → 目标客户 → 客户特点 → 解决什么问题 → 行业痛点 → 产品如何解决 → 产品现存痛点 → 技术经理怎么解决 → 技术经理解决了什么问题。

**毛病**：九个问题里有三组重叠（"解决什么问题"≈"行业痛点"≈"产品如何解决"），且叙事顺序是"产品→痛点→自己"，听着像产品发布会后临时加了个个人述职。面试官真正想听的是一条线：**你懂业务 → 你知道痛在哪 → 你干了什么 → 你还能干什么**。

#### 1.2 优化后的七问叙事链

按"业务 → 痛点 → 方案 → 自己 → 未来"重排，每问给出考察意图、回答时长和弹药位置：

| # | 优化后的问题 | 考察意图 | 建议时长 | 弹药出处 |
|---|-------------|---------|---------|---------|
| Q1 | **用一分钟介绍你们的产品：它是什么、服务谁、核心价值一句话是什么？** | 抽象概括能力、业务理解高度 | 60-90秒 | §2.1 |
| Q2 | **你们的目标客户是谁？他们有什么典型的业务特征和决策特征？** | 用户画像颗粒度、是否真懂客户 | 90秒 | §2.2 |
| Q3 | **这个行业本身有哪些痛点？请按业务链路讲，最好有真实场景。** | 行业纵深、是否有实战认知而非 PPT 认知 | 2-3分钟 | §2.3（客户故事集） |
| Q4 | **针对这些痛点，你们的产品是怎么解决的？请讲核心架构和关键设计。** | 技术方案与业务痛点的映射能力 | 3分钟 | §2.4（双轨引擎/合同履约域解耦） |
| Q5 | **产品现在还遗留哪些问题？你作为技术经理的解决思路是什么？** | 技术判断力、诚实务实、规划能力 | 2-3分钟 | §2.5 |
| Q6 | **你作为技术经理，实际解决了哪些关键问题？请用具体案例讲。** | STAR 验真、技术领导力 | 每案例90秒×2-3个 | §2.6（STAR 故事库） |
| Q7 | **如果给你三个月/半年，你会优先做什么？为什么是这个优先级？** | ROI 思维、优先级判断、管理视角 | 2分钟 | §2.7 |

**记忆口诀**：**"一客户二痛点三方案，四战绩五规划"**——Q1/Q2 讲清"是谁"，Q3/Q4 讲清"值不值"，Q5/Q6/Q7 讲清"你行不行"。

#### 1.3 面试官的潜台词对照表

| 你以为他在问 | 他其实在问 |
|-------------|-----------|

### 第二部分：七问标准答案底稿

#### Q1. 产品是什么（60-90秒电梯陈述）

>开场白的四档时长版本（30 秒 / 1-2 分钟 / 3 分钟 / 5 分钟）以 `01-面试话术与背诵手册.md` 第一部分为权威版本；本Q 只练"产品是什么"这条叙事线。

⭐ **一句话版本**：
"我们做的是**大宗商品合同履约与供应链产业电商平台**——覆盖从交易撮合、合同签约、履约交收、仓单物流、结算发票，到供应链金融和期货套保风控的**全链路闭环**。一句话概括：让大宗贸易里'签了合同之后的事'全部线上化、可信化、金融化。"

- **定位**：垂直于大宗商品现货贸易（铁矿石/煤炭/钢铁/农产品/能源）的产业电商 + 供应链协同平台

- **差异点**：不是做"信息撮合"就完事，而是**深入履约层**——把交收、资金、票据、仓单这些最容易扯皮和造假环节做成了系统化能力，这也是供应链金融能做起来的前提

#### Q2. 目标客户是谁（90秒）

⭐ **四类客户 + 一句话特征**：

**客户特点总结（⭐必须能说）**：
1. **交易金额大、决策链长**——单笔合同几十万到几千万，客户对"信任"的敏感度远高于对"价格"的敏感度
2. **高度依赖线下关系链**——传统上靠电话+微信+饭圈做生意，数字化意愿有但习惯迁移难

**加分句**："我们平台上一个小采购经理的真实处境是：打四个电话比价，问到第四家时第一家的价格已经作废了——这就是我们要服务的人和我们要解决的场景。"

##### 4.2 核心架构设计一：合同域与履约域解耦 ⭐

"我们把**合同域**（商业契约：谁、什么、多少、什么价）和**履约域**（执行：付款、发货、收货、开票）彻底解耦。为什么？因为大宗贸易中合同变更极其频繁——补充协议、数量增减、交期调整是家常便饭，如果把履约状态耦合在合同上，每次变更都是一场数据迁移事故。解耦后，合同是版本链（原合同+N个补充协议），履约是独立的计划与任务流，两者通过事件总线联动。核心表设计：contract / contract_item / contract_party / fulfillment_plan / payment_order / shipment_order / receipt_settlement / fund_pool / invoice / refund_order。"

（自证角度的"业务问题 → 备选 → 取舍 → 代价"框架见上篇 §3.1 代表作 1。）

##### 4.3 核心架构设计二：双轨履约引擎 ⭐⭐（必须讲透）

"大宗贸易的履约没有统一节奏，最先是**合同和款项谁先谁后**就分两大类——**先合同后款**（签合同锁价、再按节点走款，适合信用好的长期客户）和**先款后合同**（款到才出合同，适合新客户和高风险交易）。我们抽象出**双轨引擎**，由合同上的 `delivery_mode` 决定走哪条轨：
- **顺序交收（Sequential）**——状态机/工作流引擎强制有序，强一致，承接先款后合同这类高风险交易
- **自由交收（Free-form）**——事件驱动+规则引擎并行流转，动态条件判定，承接先合同后款的长期合作客户
- 两轨**共用同一套底层履约任务数据结构**，监控和风控视角统一
- 交收节奏之上再叠加**五种交收模式**：款到发货、货到付款、定金+尾款、分期付款、信用证"

**加分点**：主动讲 trade-off——"顺序轨用状态机换确定性，自由轨用事件驱动换灵活性，代价是自由轨的异常补偿逻辑复杂得多，我们用规则引擎把补偿策略配置化，而不是硬编码。"

（自证角度的取舍框架见上篇 §3.1 代表作 2。）

1. 大宗商品和普通 B2B 电商的本质区别是什么？（答：非标/大额/长周期履约/价格波动风险/信任成本，履约和金融是重心）
2. 你们和找钢网/欧冶这类平台的差异？（答：对标项目里的《客户案例与行业对标手册》，强调履约层深度和金融闭环）
3. 交收差异早期用参数配置实现，为什么要改造成场景化？参数爆炸怎么界定？（答：参数开关越加越多、组合失控，改一个不知道波及哪条链路；场景 = 参数组合+校验规则+状态流转的封装，运营按场景选、不裸调参数——主动讲"参数→场景化"的演进，这是我负责的改造）
4. 顺序交收和自由交收，客户怎么选？选错了怎么办？（答：引擎支持轨间切换策略 + 追问预案）
5. 平台怎么解决"鸡生蛋"问题——没有买家卖家不来？（答：先从核心企业/园区切入 + 金融服务作为钩子）

**架构类追问**：

7. 事件驱动那套，消息丢了/重复了怎么办？（答：幂等键 + 对账兜底 + 履约 trace 回放）
8. 资金预检 2PC 具体怎么做的，和 TCC/Saga 的取舍？
9. 电子签章、CA、存证的合规链路怎么设计？（答：契约锁/e签宝/法大大方案分析在 `01-design/signauth/`）
10. 仓单防造假怎么做的技术保障？（答：电子仓单 + 货权流转留痕 + 质检报告扫码追溯批次 + 监控风控中心）

### 3.3 面试前 10 分钟速查卡

#### 业务
- 三层价值：效率(5天→1.5天) / 风险(零事故) / 增长(供应链金融)
- 四种价值：信任中介 / 信息聚合 / 交易效率 / 金融服务
- 五大壁垒：数据飞轮 / 配置引擎 / 外部集成 / 复合人才 / 信任资产

#### 架构
- 四层：接入(三端) / 网关(midservice多实例) / 中台(DS+交易核心双核) / 数据(MySQL×2+MinIO)
- 双核：C撮合(纳秒级) + DS数据中心(Java桥接/防腐层，Hessian+Socket)
- 9+外部：银行/短信/证书/物流/CTRM/开票/咨询/企查查/供应链金融

#### 技术
- Redis：String→价格 / Hash→权限 / ZSet→延迟队列+排行
- MySQL：B+Tree / 聚簇+二级 / 最左前缀 / EXPLAIN
- MQ：本项目统一 Kafka（outbox 本地消息表 + 消费幂等；延迟消息用 Redis ZSet）
- 事务：Saga+状态机+补偿（不用 2PC/Seata：全局锁 3 秒不可接受 + 侵入 + 运维成本）
- 锁：SETNX→Redisson→RedLock→ZK

#### 管理
- 三件套：On-call轮值 / 技术债台账 / 接口契约治理
- BOUNDARY：坦诚深度区 → 契约治理 → 风险地图 → 用机制替代亲力亲为

### 3.5 面试当天心态指南

1. **你不是去乞求一份工作，你是去跟一个潜在合作伙伴探讨你能创造什么价值**
2. **面试官问的不是你的 JD，是"你来了之后发生了什么变化"**
3. **诚实比完美重要**——不知道就说"这块是我需要补的，我目前正在通过 XX 方式学习"
4. **B2B 是你的差异化优势**——能驾驭异构系统+懂大宗贸易的人远比只会 Spring Boot 的人稀缺
5. **每个回答都要有结构**——先说结论，再说原因，最后给数据
