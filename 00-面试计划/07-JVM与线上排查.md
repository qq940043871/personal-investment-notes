# 07 · JVM 与线上排查（P0 主场 · 真实实录）

> **排期**：D12（JVM + 线上排查）
> **本件定位**：这是**别人只有八股、你有真实实录**的那一档。答题顺序永远是：**先给方法论（六步）→ 再给一个案子（证据链）→ 最后给治本三件事**。

---

## 0. 答题主线（三句话定场）

1. **先止损，再定位；先定界，再下钻**；根因必须能用**一条证据链**解释全部现象（含"为什么别的机器没事"）。
2. 排查分**四类场景**：线上故障（要快）／性能容量（慢而不报错）／架构中间件（责任边界模糊）／隐蔽缺陷（日志干净）。
3. 定位一律**自上而下逐层**：网关 → 应用 → 缓存/中间件 → DB，任何一层"明显不对"就停在该层深挖，不跳层。

---

## 1. 90 秒速答

### 1.1 被问"线上出问题你的排查步骤"

> 六步，顺序不能乱。**第一步先止损**：熔断、降级、扩容、回滚优先，回滚最近变更（发布 / 配置 / DDL / 网络）；止损前先**留证**——监控截图、`jstack`/`jmap`/GC 日志落盘，别让重启把现场销毁了；30 分钟定位不了必须升级拉人。
>
> **第二步看大盘定性质**：CPU / 内存 / GC / RT / QPS / 错误率，先找拐点时间，把故障窗口和变更窗口对齐。三个出口：错误率涨 → 故障类；错误率不涨但 RT 涨 → "慢而不报错"；数据错 → 隐蔽缺陷。
>
> **第三步二分定界**：单机还是集群、特定接口还是全局、本服务还是下游（traceId 拆分段耗时）、变更前还是变更后。
>
> **第四步逐层下钻**：网关 → 应用 → 缓存/中间件 → DB，每层只问三件事：耗时正常吗、容量指标正常吗、这层有变更吗。
>
> **第五步用数据锁根因**：CPU 用 `top -H` + `jstack` 多次采样；内存用 GC 日志 + `jmap -histo` + dump + MAT 支配树；慢 SQL 用慢日志 + `explain`；进程消失看退出码 + `hs_err` + `dmesg`/cgroup。
>
> **第六步复现并固化**：补监控、补告警、补压测用例、写复盘；能写进 checklist 红线的就不靠人的记忆——**故障不可怕，同一个故障重复发生才可怕**。

### 1.2 四个实录（各 60~90 秒，按岗位挑一个深讲）

**A. 竞价页面突然变慢（慢而不报错）**
> 竞价专场开市 15 分钟后客户反馈慢，成功率还是 100%——典型的"慢而不报错"。我先用 traceId 把一次慢请求拆开：网关 20ms、DS→C 撮合链路 45ms、Redis 未命中、MySQL 查询 2950ms，瓶颈收敛到 DB。同时排掉两个嫌疑：GC 日志正常、C 引擎 TPS 与队列深度平稳，所以"竞价慢"其实是"查询慢"。
> 往上看缓存层：命中率从 98% 崩到 31%，**Canal 消费位点停滞 22 分钟**——开市前有人对标的表加字段走了 DDL，没走变更流程，Canal 解析失败线程退出且无告警。缓存更新流一断，热点 key 过期后击穿回源，叠加开市峰值，主库 CPU 97%，P99 从 150ms 涨到 3.2s。
> 应急：重启 Canal 校正位点 + 热点缓存预热 + 非核心查询降级，30 分钟恢复。治本三件：Canal 位点停滞与命中率告警、热点 key 二级缓存 + 回源并发保护、**DDL 变更红线（交易时段冻结）**。

**B. 批量下载 PDF 导致 JVM 进程消失**
> 客户反馈下载中断，进程**没有任何日志就消失了**，Exit Code 137。137 = SIGKILL，先按"被杀"而不是"崩溃"定性质：查 K8s 事件发现 `oom_kill`，容器 limit 6Gi。
> 根因链：批量下载把 MinIO 的 PDF **全量读入堆**再 ZIP 打包，8 路并发时堆内大对象 + 堆外（线程栈 / direct / 压缩缓冲）总和突破 6Gi → cgroup OOM Killer 强杀，捕获不了、写不了日志。深层还有两条：`-Xmx4g` 与 limit 6Gi 只留 2G 给堆外且无人评审；**没有 RSS / 堆外 / cgroup OOM 事件监控**，`memory.events` 的 oom_kill 计数无人看。
> 治本：P0 改 **MinIO 预签名 URL 直连下载**，文件字节完全不过 JVM；剩余场景流式化（8KB 缓冲 + ZIP 逐文件写）；大批量转异步导出；**limit = Xmx + 堆外预算** 一起评审；下载并发信号量限流。

**C. 多机房多线路访问异常（传输层定界）**
> 客户反馈部分地区慢，服务端指标干净。四步定位：**定域**——按地域×运营商×机房拼故障矩阵，只有"联通→主机房"一格异常；**对照**——同机房电信 VIP 正常、联通 VIP 丢包 12%，联通走灾备机房又正常，同宿异线、同线异宿两个对照钉死是我方联通这根线；**逐跳**——`mtr` 显示丢包从"机房联通出口"开始，运营商骨干全程 0 丢包；**取证**——入口 SYN 到达率仅 70%，交换机端口 CRC 误码持续增长，光模块收光 -19.8dBm 已越过 -18dBm 灵敏度，根因是**光模块老化光衰**。
> 处置：GSLB 把联通切灾备 BGP 入口恢复，换模块后回切。治本：补"从外向内分运营商"的多点拨测 + 分线路告警（以前只能靠客户报障发现）。

**D. Cookie 认证偶发失败（5Why 推理型）**
> 现象是**偶发**未登录、日志干净。5Why 逐层：为什么失败 → 服务端 Redis 查不到 Token → 为什么查不到 → 到达的 Token 与存储值不一致 → 为什么不一致 → 传输中被改写 → 谁改的 → **公司出口的 DLP / WAF / 上网行为管理对出站 Cookie 做深度包检测，把长 base64 的 Token 误判成敏感数据**，做了截断/改写。
> 深层根因：**认证方案把 Token 的唯一载体绑在 Cookie 上**，而 Cookie 正是企业网络设备的重点监控对象，缺少对复杂网络环境的容错。改进：短期给安全设备加白名单/改走 Header，中期支持 Header 携带 + 双通道兼容。

## 2. 四类场景地图（被问"你们日常都排查什么"）

| 类 | 特征 | 典型 | 切入点 |
|---|---|---|---|
| ① 线上故障 | 正在影响用户，止损与排查并行 | CPU 飙高、OOM、线程池打满、连接池耗尽、死锁、服务不可用 | `top -H` → `jstack`；`jmap -histo`/dump；连接池活跃与等待 |
| ② 性能容量 | **不报错但变慢**，投诉先于告警 | RT 毛刺、慢 SQL、缓存击穿/穿透/雪崩、Full GC 频繁、MQ 积压 | 先定性质（错误率不涨）→ traceId 分层 |
| ③ 架构中间件 | 故障面大、责任边界模糊 | MySQL 主从延迟/锁等待、Redis 大 key/热 key、MQ 顺序与 rebalance、注册中心、网关 502/504、分布式事务与锁 | 拉 DBA / 运维 / 中间件一起看，先对齐"哪一层" |
| ④ 隐蔽缺陷 | 低频、难复现、日志干净 | 并发可见性/原子性、时序竞态、多环境配置漂移、连锁雪崩、缓存与 DB 不一致 | 证据链推理 + 对时 + traceId |

## 3. 六步 SOP（背这张表就够）

| 步 | 动作 | 要点 / 坑 |
|:--:|---|---|
| 1 | **止损**（分钟级，与排查并行） | 回滚最近变更（发布/配置/DDL/网络）、预案开关、切流量；**先留证再重启**；30 分钟未定位就升级 |
| 2 | **看大盘定性质** | 找拐点时间，对齐变更窗口；错误率涨→①，RT 涨错误率不涨→②，数据错→④ |

## 4. 三类高频现象的排查顺序（命令级，被追到底就靠它）

### 4.1 CPU 飙高

```bash
top -c                 # ① 定位 PID
top -H -p PID          # ② 定位 TID
printf "%x\n" TID      # ③ 转十六进制
jstack PID > /tmp/j.txt && grep -A 30 "nid=0x3048" /tmp/j.txt
# 或用 Arthas：thread -n 3 / thread -n 3 -i 1000
```

| 栈顶特征 | 判断 |
|---|---|
| `Pattern$Curly.match` | 正则回溯 |
| `MessageDigest / Base64` | 大文件加解密 |
| jackson 反序列化 | 超大 JSON |
| `GC task thread` | 是 GC 引起 → 转 4.2 |
| 业务方法 | 死循环 / 全表遍历 |

阈值：Load ≈ 核数 = 满负荷；Load ≫ 核数且 `wa` 高 → 先查 IO（`iostat -x 1`）。

### 4.2 Full GC 频繁 / 老年代不降

```bash
jstat -gcutil PID 1000 10    # S0 S1 E O M / YGC YGCT / FGC FGCT
jmap -histo:live PID | head -30
jmap -dump:live,format=b,file=/tmp/heap.hprof PID   # 线上慎用（STW）
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/   # 提前埋
```

判断树：
```
Full GC 后老年代是否下降？
├── 降   → 对象创建太快 → 减对象 / 增大堆 / 调新生代
└── 不降 → 内存泄漏 → dump + MAT（Leak Suspects → Dominator Tree → Path to GC Roots）
Young GC 太频繁？   → Eden 太小 / 短命对象多
单次 STW 过长？     → 堆过大 / GC 器不当 → G1 / ZGC
```

常见泄漏源：静态 Map 无上限缓存（换 Caffeine + 淘汰）、`ThreadLocal` 未 remove、监听器未反注册、连接未关闭、CGLIB/反射类累积（Metaspace OOM）。

### 4.3 进程消失（比 OOM 更难，因为**没有日志**）

判定顺序：**先定性质，再定根因**——"崩溃"（有 hs_err / OOM 栈）还是"被杀"（SIGKILL，无日志）。

| 证据 | 指向 |
|---|---|
| Exit Code **137** | SIGKILL，几乎一定是**容器内存超限**被 cgroup OOM Killer 杀 |
| `dmesg` / `memory.events` 的 `oom_kill` 计数 | 确认是内核杀的，不是 K8s 探针或人工 |
| `-Xmx` 与 `limits.memory` 的差值 | 堆外预算不足（线程栈 + direct + CodeCache + GC 结构） |
| RSS 曲线 | 尖峰型 → 大对象/批量操作；锯齿上升 → 泄漏 |

**纪律**：`limits.memory = Xmx + 堆外预算`，容器与 JVM **一起评审**，不允许只配一个。

## 5. 四个实录的浓缩对照（被问哪个就取哪行）

| 案子 | 一句话根因 | 治本三件 |
|---|---|---|
| 竞价变慢 | DDL 绕过变更流程 → Canal 线程退出无告警 → 缓存更新流断 → 热点击穿回源打满主库 | 位点停滞与命中率告警 / 二级缓存 + 回源并发保护 / DDL 交易时段冻结 |
| PDF 进程消失 | 批量下载全量读入堆打包，堆内+堆外超容器 6Gi → cgroup SIGKILL（137），无日志无监控 | 预签名直连（字节不过 JVM）/ 流式化 + 异步导出 / limit 与 Xmx 一起评审 |
| 多机房线路 | 出口光模块老化，收光 -19.8dBm 越过 -18dBm 灵敏度 → 联通线路丢包 12% | 光功率与误码纳管 / 多点拨测 + 分线路 SLO / 双上联 + 自动切换预案 |
| Cookie 认证 | 出口 DLP/WAF 深度包检测把 base64 Token 误判改写；Token 只走 Cookie 单一载体 | 安全设备白名单 / 支持 Header 承载 + 双通道 / 认证链路监控 |

### 追问通用预案

| 追问 | 答 |
|---|---|
| 怎么确定不是服务端问题 | B2B：同机房其他运营商正常 + 内网直连 0 丢包 + 网关 QPS/RT/错误率平稳，三条同时指向传输层 |
| `mtr` 中间跳丢包算故障吗 | 不一定，中间设备 ICMP 限速常见；看**边界跳之后是否持续到底** |
| 为什么不定点重启 DB | 重启只清零 CPU，几分钟内被回源流量重新打爆——先断根因 |
| 缓存整体失效怎么扛 | 本地缓存 30s 逃生 + singleflight/限流保护 DB + 从库分流 + 定时对账兜底 |
| 怎么保证不再发生 | 故障三件套：监控补盲区、告警带分级、压测进回归；能进 checklist 的不靠记忆 |
