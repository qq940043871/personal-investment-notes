## 1. 按层次｜网关十道关如何平衡性能损耗与安全

> **定调**：安全和性能是假命题，真矛盾是把安全放在错误的层级——我按"拦截成本从低到高"分四层讲。
>
> **第一，入口层零 IO 拒绝最便宜。** 协议号防伪（首尾 16 位 + 中间 MD5）本地算完就拒，不碰磁盘不碰网络——所以它能排最前不是因为最重要，是因为最便宜。
>
> **第二，配置层一处定义四处生效。** `api.json` 一处定义 + 反射路由，加协议不用发版；`PUB/FRM/CLI` 三级缓存命中后不进反射，安全校验的开销被摊薄。
>
> **第三，风控层可灰度可回退。** 20 道校验走"全局开关 + 协议级 Map"，出问题按协议秒级回退，不用全站改代码。
>
> **第四，可观测层兜底。** 十道关的拒绝原因全落 `1018_MONITOR_DATA`，哪个关卡频繁拒绝找得到——**看不见的安全等于没有安全**。
>
> **收口**：所以平衡的本质是"把便宜的拒绝放前面、把贵的放后面、每道都可回退"。您想展开哪一层？

## 2. 按语义｜C↔DS 协同机制（那道低分题，重答）

> **定调**：我一句话定位——Java 侧负责人 + C/Java 技术接口人，定边界、定契约、定一致性，不写 C 代码。协同机制我按"谁→做什么→凭什么保证"三句讲。
>
> **第一，DS 做双向翻译官。** C 只认私有 TCP 二进制帧、Java 只认 Hessian 对象，DS 让两边互不迁就——这是防腐层的价值。
>
> **第二，两条通道都是同步指令，区别在协议。** Hessian over HTTP 对接 Java 侧接口、Socket 私有帧对接 C 引擎，都是请求-响应、阻塞等应答。（"一条同步一条异步"是设计目标不是现状，别讲反。）
>
> **第三，我主导的是 Java 桥接 SDK + 边界契约 + 排障体系。** SDK 屏蔽连接/心跳/重连/熔断，契约双方评审我拍板，桥接日志是第一排查依据——这就是接口人的抓手。
>
> **收口**：所以我管的是"连线"不管"黑盒内部"，守住接口、SLA、爆炸半径。您想先听哪块？

## 3. 按时间｜高频爬虫把服务器负载打高

> **定调**：识别爬虫是安全层、扛住负载是容量层——真正把服务器打挂的不是"它是爬虫"，是流量超过 DB 出口。**先止血再抓虫**，我按四步讲。
>
> **第一，现象**：网关横扩到 5 实例后慢查询涨、DB 连接池打满——扩容是流量放大器，瓶颈只是从网关后移到 DB。
>
> **第二，定位**：用利特尔法则反推慢接口的安全吞吐，确认瓶颈在 DB 写入不在网关；同时用协议号防伪 + `RiskProcessor` 四维（频率/地域/设备/行为）判是不是真爬虫。
>
> **第三，止血**：当晚四步——慢接口限流 200 QPS（示例基线）、热点缓存 30s 命中率≥90%、独立线程池 core15/max30/queue100 做舱壁、连接池每实例卡 20。
>
> **第四，防复发**：固化成"新接口容量申报 + SQL 红线 + 扩容前先核出口容量"三条规范。
>
> **收口**：所以高频≠爬虫（机构批量对账合法冲高），处置靠双信号不靠拍脑袋。您想听容量侧还是识别侧？

## 4. 按对比｜仓储视频监控网关选型

> **定调**：我最终选了 FFmpeg + ZLMediaKit 做通用流媒体网关，否决了另外三条路——决定因素是"适配矩阵做不完"和"周期"。
>
> **第一，否决 NVR SDK**：按路授权 + 绑死客户端，换浏览器版本就播不了——早期一家摄像头一个插件的灾难正是这个。
>
> **第二，否决海外 SaaS**：视频出域 + 跨境延迟，合规和体验都过不了。
>
> **第三，否决纯自研**：从零做流媒体服务器周期不可接受。
>
> **第四，选 FFmpeg + ZLM**：摄像头只认 RTSP/ONVIF，一路 RTSP 只拉一次，连接数与观众数无关（嵌入式摄像头并发个位数，10 人直连就打死）——这是整套架构的命门。三档出口 WebRTC <500ms → FLV 1–2s → HLS 3–5s 逐级降级兜底。
>
> **收口**：代价是出口带宽成新瓶颈（1000+ 并发单机千兆网卡打不住，属推演）。您想听选型还是容量？

## 5. 按矛盾｜竞价状态延迟跨团队推动

> **定调**：我们没在对错上扯皮，而是把问题拆成两段——状态口径和推送通道，我组织双方评审拍板边界。
>
> **第一，状态口径归谁**：6 条根因（时序竞争/倒计时口径/WS 假活/断线无补偿/消息乱序/数据源不统一）逐条对号入座，口径问题归 Java、延迟问题归 C，按"C 管快 Java 管稳"定责。
>
> **第二，推送通道归谁**：定推拉分离——C 直推独立 WS 只发不取、查询走网关、不复用 dataShare；C 侧有界队列非阻塞投递、绝不反压撮合线程、seq 防乱序。
>
> **第三，怎么验收**：契约评审拍板，各方用同一组例子复述、边界/状态/异常无歧义才算对齐；效果 5s→1s（库内口径，题面 2s 是客户感知现象）。
>
> **收口**：我主导的是契约/边界/评审，**不写 C 代码**；订阅和状态副本补齐是设计态未落地。您想听冲突处理还是技术方案？

## 6. 按价值｜系统不足与重新设计排期

> **定调**：不足我不逃避，但按层次讲；重新设计不是推倒重写，是"把基础设施更早落地"；排期按价值/风险排序——先止血、再固本、后优化。
>
> **第一，安全合规**：MD5 混淆、AES-CBC 的 IV 不合规、SQL contains 误判——这是 P0 止血，因为踩的是合规红线。
>
> **第二，资金安全**：硬编码审计协议号、catch Throwable——资金零差错是红线，紧随其后。
>
> **第三，稳定性**：无自动熔断/限流/舱壁、三处全局锁——排 P1，且限流熔断必须排在舱壁**之后**（无线程隔离时熔断触发慢请求照样占线程池）。
>
> **第四，可维护性与性能**：2581 行单类、配置不热更、路由 O(n)——排 P2 优化。
>
> **收口**：重做两条——契约注册表更早落地、DS 编解码更早抽模块并钉死"业务线程只做纯内存操作"（目标态）。排期表人日是面试方案示例非真实台账。您想听哪一层？

## 7. 按机制｜如何向团队传达缓存最佳实践

> **定调**：我不靠发文档开会，靠三层机制——规范、工具、人工，缺一层就退化成形式主义。
>
> **第一，规范文档层（应该怎样）**：缓存使用规范写进仓库，早会只过阻塞点、周分享只讲真问题，技术常见坑表把教训变成可勾选清单。
>
> **第二，工具门禁层（必须怎样）**：Sonar + 自研 jar 包检测四项（事务注解/Redis 锁/日志完善/**幂等**）——规范不能被工具强制就只是文档。CI 门禁是规划中，别讲成已在跑。
>
> **第三，人工评审层（是否合理）**：Code Review 看设计是否合理，复述检验看是否真掌握——不查资料讲清链路、追问三个为什么、说出 2 个坑+监控指标+何时会挂。
>
> **收口**：三层缺一不可——文档管认知、工具管底线、评审管合理。您想听传达还是掌握度检查？
