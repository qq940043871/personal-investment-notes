# 04 · 识别滥用特征后，主要依据哪些指标或数据来判断

> **性质**：AI 面试复盘沉淀件（一问一文件）。2026-11-26 收录，同日按真实项目经历改造。
> **原题**：识别滥用特征后，主要依据哪些指标或数据来判断？比如访问频率、访问时间、访问内容。

> **证据等级（先分清再说）**
> - 【实证·现状】可从 `HandlerController` 源码回查的：① 协议号防伪（首尾 16 位 + 中间 MD5）② 防重放（时间戳 SHA256 + `security.difftime` 默认 60s）③ `RiskProcessor` 四维拦截（频率 / 地域 / 设备 / 行为）④ `valide()` + `Validate.isSafe` 参数与注入校验 ⑤ 授权维度（`USERFLAG`、`checkPowers` 代理关系、`3002_API_AUTH_LIST`）⑥ 审计流 `1018_APP_LOG`（`KEYID/USERID/OPERTIME/API/NOTE/ISOK/OPERIP`）⑦ 监控上报 `1018_MONITOR_DATA`（`STARTTIME/ENDTIME/API/RESULT/MSG/COST_TIME/MACHINE_IP`）。
> - 【设计态】11 号文档的"触发源四类"、midmon 六块看板、契约健康度看板、非法编码请求数、相对劣化判据——是目标态治理模型，**现状还没有这些看板**（现状是 Redis 监控队列 + 外部监控消费，见 14 号 §八）。
> - 【通用方案】无明显外部内容，本篇主体是项目实证 + 设计态两层。

---

## 0. 一句话口径（先背这句）

> 我们识别滥用靠**四层实证数据**：访问频率走 `RiskProcessor` 频率维度、访问时间走防重放时间窗与地域/行为维度、访问内容走协议号防伪 + `valide()` 注入校验、身份来源走 `USERFLAG` 与机构代理关系校验；全部落 `1018_APP_LOG` 审计流和 `1018_MONITOR_DATA` 监控队列。体系上归成触发源四类、配 midmon 看板做双信号判定——但**看板与双信号闸门是设计态**，现状有数据和钩子，没有那套完整看板。

---

## 1. 实证层：现状真正采集的四个维度

### 1.1 ① 访问频率（现状：风控钩子维度）

- 【实证】`RiskProcessor.process()` 拿到解密后指令集 + 登录态，含**频率维度**拦截；
- 【设计态】三级配额（租户 / 应用 / 接口）、令牌桶计数——方案有，现状没完整落地；
- 判据：**高 QPS 不等于恶意**（机构批量对账合法），必须分租户档位，这是设计态配额分层的理由。

### 1.2 ② 访问时间（现状：防重放窗口 + 风控行为维度）

- 【实证】防重放：`sha256(curtime + "czzdit")` 验签 + `|now - curtime| ≤ security.difftime`（默认 **60000ms**）——时间窗超差直接拒；
- 【实证】`RiskProcessor` 的地域 / 设备 / 行为维度——这是"同账号异地并发、间隔规律"的真实落点；
- 【设计态】窗口按服务端时间归集（NTP）、相对劣化（同比/环比）——治理规范，现状监控队列用服务端时间但无完整同比看板。

### 1.3 ③ 访问内容（现状：校验最厚的一层）

| 信号 | 实证实现 | 拒绝码 |
|------|---------|--------|
| 协议号枚举 / 篡改 | 长度 > 32 时 `首16位+尾16位 == md5(中间)` | `API不正确，非授权访问` |
| SQL 注入 / XSS | `Validate.isSafe` | 拦截 |
| 敏感词 | `SensitivewordFilter`（按协议开关） | `信息中包含敏感词` |
| 参数形状 | `valide()`：`VALIDATE/LENGTH/TYPE/ISREQUIRE` 全在 `api.json` | 参数校验失败 |
| 批量超限 | `Security.Api.maxMultiApiCount` | `超过最大执行量` |

> ⚠️ **头号误判陷阱**：参数校验失败突增，八成是调用方字段没同步 `api.json`（配置变更未同步），**不是攻击**。先查配置，别先封人。

### 1.4 ④ 身份与来源（现状：授权体系最完整）

| 信号 | 实证实现 |
|------|---------|
| 用户类型 | `USERFLAG=1` 管理员 / `=2` 机构 / `=3` 第三方；`DF_` 协议强制管理员、`SF_` 强制机构 |
| 机构越权代客 | `checkPowers` 查 Redis `1001_AGENTFIRM_USERID` 代理客户列表，`AGENTFIRMID` 不在列表即拒 |
| 协议授权 | `checkApiAuth` 查 `3002_API_AUTH_LIST`；`noAuthApis` 白名单跳过 |
| 登录强度 | `LOGINTYPE` 映射 1/2/3 级，查询密码、交易证书（GB2013/GB2014） |
| IP 记录 | `MODU_ID=1036` 自动注入客户端 IP；审计流记 `OPERIP` |

> 撞库和越权的单请求长得完全合法，只有**身份维度关联**才暴露——我们这层实证最厚。

## 2. 设计态层：触发源四类 + 双信号闸门

11 号文档 §6.3 把信号归成四类：**频率超限 / 高频错误 / 扫描特征 / 行为异常**，并配 midmon 六块看板（全局大盘、慢协议榜、调用量榜、限流与封禁、契约健康度、容量水位）。

| 机制 | 状态 |
|------|------|
| 双维度校验（两个信号成立才自动封禁） | 【设计态】 |
| 契约健康度看板（失败率突增 = 调用方变更未同步） | 【设计态】思路可借，**现状靠人工查 `api.json` 变更** |
| midmon 各看板 | 【设计态】现状是 `1018_MONITOR_DATA` 队列 + 外部监控消费，无这六块 |

> 面试讲法：先用 §1 的实证数据说"我们采什么"，再用 §2 说"体系上怎么归类判定"，最后补一句"看板是设计态"。

## 3. 项目版 90 秒速答

> 识别滥用我们靠四层数据，而且都能落到源码：**频率**走 `RiskProcessor` 钩子，它拿解密后的指令集和登录态做频率维度拦截；**时间**靠防重放的时间窗——`sha256(curtime + salt)` 加 60 秒容差，超差直接拒，加上风控的地域、设备、行为维度；**内容**靠协议号防伪（首尾 16 位拼中间 MD5）、`Validate.isSafe` 注入防护、`valide()` 按 `api.json` 逐参数校验、批量上限；**身份来源**靠 `USERFLAG` 分级、`checkPowers` 查机构代理客户列表、`checkApiAuth` 查授权列表——撞库和越权单请求都合法，靠这层关联才看得出来。
>
> 数据全部落两处：`1018_APP_LOG` 安全审计流记谁、何时、调了什么协议、结果、IP；`1018_MONITOR_DATA` 队列上报耗时、协议、结果码、机器 IP 给外部监控消费。
>
> 体系上我们把它归成四类触发源——频率超限、高频错误、扫描特征、行为异常，配 midmon 看板做双信号判定，但那套看板是设计态，现状有数据和钩子，没那么完整。还有一条纪律：参数校验失败突增先查是不是调用方改了字段没同步 `api.json`，别急着当攻击。

## 4. 追问预案（带证据等级）

| 追问 | 回答要点 |
|------|---------|
| 你们靠什么识别扫描？ | 【实证】协议号防伪 + `Validate.isSafe` + `valide()` 连续失败 |
| 防重放怎么做？ | 【实证】`sha256(curtime + "czzdit")` + 60s 时间窗，超差拒 |
| 撞库怎么识别？ | 【实证】`RiskProcessor` 行为维度 + `USERFLAG` + 代理关系校验关联 |
| 有 midmon 看板吗？ | 【设计态】现状是 `1018_MONITOR_DATA` 队列，六块看板是设计方案 |
| 失败率突增怎么判？ | 先查调用方是否改了字段没同步 `api.json`，不是先当攻击 |
| 有双信号自动封禁吗？ | 【设计态】现状风控按协议灰度拦截，双信号闸门是方案 |
