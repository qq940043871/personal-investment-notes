# 12 · 外部系统接口超时与熔断降级：从四层防护到人工闭环

> **性质**：AI 面试复盘沉淀件（一问一文件）。2026-11-26 收录，由两道连环追问合并而成——① 外部系统接口频繁超时 / 不稳定如何处理；② 完整的熔断、降级与人工介入闭环机制。两题同属"外部依赖治理"一条链，合并成一篇从防护到闭环的完整答案。
> **原题**：外部系统接口频繁超时或不稳定时，你的系统如何处理？／请描述完整的熔断、降级与人工介入闭环机制。
> **角色**：Java 侧负责人 —— 接口治理、跨系统一致性、兜底闭环的机制设计是我定的；具体编码归对应团队。

> **证据等级（先分清再说，否则就是背教材）**
> - 【实证】= 库内标注来自真实架构与源码的事实：外接 9+ 系统（5 家银行 + 税务 / 物流仓储 / CA / 开票）、统一 SDK 收口、同步段只写本地事务 + 待发送表、跨系统通知阶梯退避 1s→2s→4s、超限转人工、人工全站熔断开关（`SysPara 40310`）、批量协议数量上限、按目标系统分派运营、日终对账、On-call 主副双岗 + 四级 SLA + 六步应急作业单 + 48 小时复盘。
> - 【目标态】= 设计蓝图，**源码尚未实现**：网关自动熔断三态（CLOSED/OPEN/HALF_OPEN + 半开探针）、慢调用/异常比例判定、QPS 限流、舱壁线程池隔离、五层防线 + 四支柱。⚠️ 讲成"已实现"就是过度声明。
> - 【口径限定】= 数字为内部口径或示例基线：**9+ 外部接口 / 5 家银行 / 3 年零资金差错** 是内部口径，被追问统计口径就如实说"需回查"；不是实测的性能数值不要报成压测结果。

> **讲法纪律**：先用【实证】讲"我怎么设计、怎么兜底"；碰到三态熔断 / QPS 限流必须主动加"这是目标态、现状只有人工开关"；对外数字带限定语。

## 0. 一句话口径（先背这句）

> 外部系统不可靠是常态——外接 9+ 系统、5 家银行，它一定会超时、一定会抖。所以设计目标不是"让它不出问题"，是**它出问题时我的系统不被拖垮、每一笔业务有最终交代**。处理分四层：统一 SDK 护住每次调用 → 异步化 + 状态机不让用户等下游 → 可靠送达（**异步通知才重试、同步查询不重试**）→ 日终对账兜底。熔断/降级/人工闭环要拆成三套：网关三态熔断是**目标态**保护、降级是体验、跨系统"熔断转人工"是重试超限后的状态跃迁 + 闭环，核心是**绝不静默丢失**。

---

## 1. 先拆概念：题面里的"熔断"其实有两套（这题的第一得分点）

> 很多人把熔断/降级/人工介入讲成一锅粥，面试官一句"两种熔断有什么区别"就卡住。先把概念拆开：

| 机制 | 属于哪层 | 本质 | 状态 |
|---|---|---|---|
| **网关/调用侧熔断器** | 实时保护 | 三态 CLOSED→OPEN→HALF_OPEN，专识别"慢"而非"错"，fail-fast 释放资源 | 【目标态】源码只有人工全站熔断开关 |
| **跨系统"熔断转人工"** | 待发送表状态机 | 重试次数超限后的一个跃迁：不再自动重试、转人接管 | 【实证】已实现 |
| **降级** | 熔断时同步生效 | fail-fast 兜底 + 推拉分离 + 热点读本地缓存 | 部分【实证】/ 部分【目标态】 |
| **人工闭环** | 组织 + 状态机 | 通知到人 → 两条出路 → 不允许悬浮 | 【实证】已实现 |

**⚠️ 现状红线（背下来，讲错就是过度声明）**：源码里只有**人工全站熔断开关**（`SysPara 40310`，发版维护用）+ **批量协议数量上限**，**没有**单协议自动熔断、没有三态/半开探针、没有 QPS 限流。三态熔断是目标态设计。

## 2. 第一问：外部系统超时的四层防护

### 2.1 先区分调用性质——答错这一条就是硬伤

> 面试最阴的坑是一律"加重试"。**同步查询**和**异步通知**的重试策略完全相反：

- **异步通知类**（通知资金 / 仓单）：带幂等键做阶梯退避重试——这是可靠送达。
- **同步查询类超时：不自动重试**——重试会把已经喘不过气的下游放大成流量风暴，靠幂等卡 + 对账兜底。

### 2.2 四层防护（从"护住调用"到"最后兜底"）

**① 统一 SDK / 适配器 —— 护住每一次调用。** 外部接口不走散兵游勇，统一 SDK 收口**限流、超时、熔断、降级、签名、fail-fast**。两个关键细节：
- **超时逐层递减**：网关 1s > 后端 800ms > DB 500ms。反过来（外层比内层短）会造成"外层已超时、内层还在打 DB"的白干。
- **舱壁隔离**【目标态】：慢的、独立的下游用线程池隔离（一舱进水不沉船），不能让它占住公共线程池把全站拖死。

**② 异步化 + 状态机 —— 不让用户等下游。** 同步段只做**本地事务（业务表 + 待发送表）**，远程调用一律挪到事务提交之后；用户侧事务提交即返回"受理成功"，状态由异步段推进。**事务里只写自己库里的表，绝不出现 HTTP/RPC。**

**③ 可靠送达 —— 只有异步通知才重试，且必须带幂等键。**
- 阶梯退避 **1s→2s→4s…** ±20% 抖动防重试风暴，上限 N 次，超限熔断转"待人工"。
- **前提是每次带业务幂等键（业务单号 + 目标系统 + 业务动作）、下游按幂等键去重**——否则重试就是重复入账 / 重复过户。
- "超时≠没执行"是分布式最危险的不确定失败——不盲目重试，靠幂等键 + 主动查状态 / 对账确认真实结果。

**④ 日终对账 + 失败转人工 —— 最后兜底。** 实时异步 + 批量对账双保险；对不平就告警 + 运营工单，按目标系统分派（资金问题→资金运营，仓单问题→仓储运营）。**"待人工"不能是终态**。这是"3 年零资金差错"的底气——不是不出问题，是**出了问题一定有人知道、有一笔能对上**。

## 3. 第二问：完整的熔断 / 降级 / 人工闭环

### 3.1 熔断（网关侧三态，目标态设计）

- `CLOSED` 正常放行 → 慢调用 / 异常比例 **≥50%（滑动窗口 10s / 20 请求）** → `OPEN`：**fail-fast，熔断 5s，不放流量过去**，直接返回兜底页 / 兜底数据 → 5s 后 `HALF_OPEN`：放 **3 个探针**请求，成功回 CLOSED、失败回 OPEN。
- 判据用 `slowCallRate + slowCallDuration`，**专识别"慢"而不是"错"**。
- ⚠️ **现状**：只有人工全站熔断开关 + 数量上限，三态 / 半开探针 / QPS 限流都是目标态（五层防线 + 四支柱）。

### 3.2 降级（熔断时同步生效的三板斧）

1. **fail-fast 兜底**：不放流量过去，返回兜底页 / 兜底数据，而不是让请求堆着把下游打更惨；
2. **推拉分离**：竞价推送通道故障时，**查询通道仍可用**——这是降级生效的前提（推拉分离当初就是这么设计的）；
3. **热点读走本地缓存 30s**：Redis 或 Canal 全挂时，本地缓存是逃生层，给告警和降级争取时间。

### 3.3 "熔断转人工" + 人工闭环（跨系统通知侧，这是主体）

**待发送表六态流转**：

```
待发送 →(批次号原子认领)→ 发送中 →(阶梯退避 1s→2s→4s…)→ 待重试 →(≥N 次)→ 待人工
   ↑                                                                    │
   └──────────────(手动/自动重启派发，只重置记录)────────────────────────┘
   成功 → 归档
```

**进入待人工的判定要点**：
- **该重试的错**（网络超时、5xx、限流、明确"稍后重试"）才走阶梯；**不该重试的错**（4xx、业务码拒绝）**不占 N 次额度**，直接转人工附原因；
- **告警阈值低于熔断阈值**——重试到一半就该有人知道，不是等熔断才喊；
- "超时≠没执行"，不确定时按幂等键重试、绝不"猜"。

**人工闭环三要素（缺一就不是闭环）**：

1. **通知到人**：按目标系统分派（资金→资金运营，仓单→仓储运营）；告警内容带**业务单号 + 目标系统 + 已重试次数 + 最近失败原因**，让运营一眼判断、**不用再查库**。
2. **两条出路**：运营线下处理完标记"**已闭环**"；或判断是系统问题，点"**重启派发**"回到"待发送"——**只重置记录，不产生第二笔业务**（幂等键不变）。界面端重试是兜底不是主路径，要有权限控制和操作留痕（谁、何时、对哪条重试过）。
3. **不允许悬浮**："待人工"不是终态，**有超时提醒**；要么重试回去、要么人工闭环；成功记录要有归档清理策略，否则表无限膨胀。

**部分成功的处理**：资金成功、仓单失败时，**只对失败的那条记录重试**，已成功的不动——这就是"一条下游一条记录"的价值。

### 3.4 组织侧闭环（故障管理的完整闭环）

- 机制层：**On-call 主副双岗 + 四级 SLA + 六步应急作业单**。P1（如竞价报价看不到 = 核心功能不可用）要求 2h 响应、当日修复。
- 闭环层：故障报告 → 复盘 → **转成规范或自动化检查项**。复盘的产出永远是**防再发**，不是事故报告。

## 3.5 实战例子：被要求"举个限流/熔断/降级的例子"时讲哪个

> 通用例子（秒杀限流、电商熔断、朋友圈降级）谁都能背三个，面试官听腻了。要讲**自己系统里能报出数值、能说清当时场景**的。举例前先按"谁不行了"归位，别把兜底（资源不存在）讲成降级：
>
> | 谁不行了 | 归到哪类 |
> |---|---|
> | 流量太大（系统还活着但扛不住） | 限流 |
> | 下游服务失败率高 / 慢调用多 | 熔断 |
> | 资源压根不存在（404） | 兜底 fallback，**不是降级** |
> | 用户没登录 / 没权限 | 认证拦截，**不是降级** |

### 3.5.1 限流——管"来的人太多"

**① 慢接口全局 200 QPS / 单实例 40 QPS（最硬，能讲出推导链）。**
场景：网关横扩后怕再把 DB 打穿，设了慢接口全局 200 QPS、单实例 40 QPS（全局 ÷ 5 实例）。反推链用利特尔法则：`DB 连接预算 100 ÷ SQL RT 0.3s × 利用率 0.7 ≈ 230 QPS`，取 60% 水位 → 放行 200。⚠️ **这是反推的示例基线，不是压测实测**——被问"数怎么来的"就把这条链讲出来，别说成生产实测值。

**② 压力参数拒绝（最容易讲清，因为具体）。**
`pageSize>100` 拒、时间跨度>31 天拒、批量>200 拒、数组元素>100 拒、排序字段走白名单。设计决策是**默认拒绝、不做静默截断**——超了就明确返回让调用方感知，不悄悄砍掉（静默截断 = 埋雷 + 参数注入风险）。这是**我们定的红线口径**，讲"我们定的"即可。

**③ 处置阶梯（安全侧，【目标态】）。**
告警 → 429 → 临时封禁 15 分钟（自动解封）→ 黑名单（人工解封 + 申诉）。触发源四类识别：频率超限 / 高频错误 / 扫描特征（非法编码、参数连续失败、路径穿越）/ 行为异常（同 IP 切多账号、异地并发、脚本特征）。防误伤靠白名单（内部互调、健康检查、监控探针）+ 机构客户触发同步通知值班。⚠️ 自动封禁是目标态，别讲成已全量上线。

### 3.5.2 熔断——管"对方不行了"

**① 网关横扩打穿 DB（你最有画面感的例子）。**
场景：网关横扩 5 实例，入口容量 ×5、出口容量没变、中间没闸门，几分钟后 DB 被直接拖死。本质是**瓶颈后移**——扩容是放大器不是解药，先限流再扩容。⚠️ 口径：库里写"真实发生过"，但保守讲法是"**基于真实架构的代表性场景**"，被问"你当时在场吗"如实答，别硬认亲历。

**② 三态熔断【目标态，务必标清】。**
慢调用/异常比例 ≥50%（10s/20 请求）→ OPEN 熔断 5s、fail-fast → 3 个探针半开试探。**现状只有人工全站熔断开关**（`SysPara 40310`，发版维护用），没有自动三态、没有探针、没有 QPS 限流。

### 3.5.3 降级——管"给个能用的"

**① 全站一键降级（前后台都能感知，不是静默）。**
发版维护时开全站熔断开关、返回提示语，提示语在系统参数里可配、不用改代码发版。

**② 单协议失败不阻断整体 + DB 异常统一兜底（组合加分点）。**
某协议初始化失败不影响其他协议；DB 异常统一回"处理失败"，SQL 关键字脱敏成"数据库异常"，连接池耗尽降噪成 `RST_GB9999` "系统异常，可忽略"——**降级的同时还防信息泄露**，这是三层信息泄露防护的一部分。

**③ 推拉分离 + 本地缓存 30s 逃生（最体现架构远见，首推）。**
竞价推送通道挂了，**查询通道仍可用**——降级生效的前提是当初架构就把"推"和"拉"分开了；热点读还能走本地缓存 30s 当逃生层，给告警和降级争取时间。这个例子比"返回兜底页"更能说明你懂架构。

### 3.5.4 怎么挑着讲（面试官问哪类就报哪个）

| 面试官问 | 首选例子 | 关键限定语 |
|---|---|---|
| 举个限流的例子 | 慢接口 200 QPS + 利特尔法则推导链 | 示例基线非实测 |
| 举个熔断的例子 | 扩容打穿 DB（瓶颈后移）+ 补三态是目标态 | 代表性场景，别硬认亲历 |
| 举个降级的例子 | 推拉分离 + 本地缓存 30s 逃生（首推）；全站开关当补充 | 说清是架构设计的前提 |
| 问压力参数怎么防 | pageSize≤100 / 批量≤200 / 默认拒绝不静默截断 | 我们定的红线口径 |

> **本节三条红线**：① 200 / 230 / 50–100 这些数全是反推示例基线，**别说成实测**；② 三态熔断、QPS 限流、舱壁是**目标态**，现状只有人工开关 + 数量上限；③ 扩容打穿 DB 讲"基于真实架构的代表性场景"，被问是否在场如实答。

## 4. 项目版 90 秒速答（直接背）

> 外界接口不可靠是常态，外接 9+ 系统、5 家银行，它一定超时一定抖。我的目标不是让它不出问题，是**它出问题时我的系统不被拖垮、每笔业务有最终交代**。
>
> 处理分四层：第一层**统一 SDK**，把限流、超时、熔断、降级、签名收口，超时逐层递减（网关 1s > 后端 800ms > DB 500ms），慢下游做舱壁隔离；第二层**异步化 + 状态机**，同步段只写本地事务和待发送表，远程调用提交后，用户不用等下游；第三层**可靠送达**，这里要分清——**异步通知**带幂等键做阶梯退避 1s→2s→4s、超限转人工，**同步查询超时不自动重试**，否则把故障放大成流量风暴；第四层**日终对账兜底**，对不平告警转运营，不留静默丢失。
>
> 完整的熔断降级闭环我拆三块：第一块**熔断**，网关侧三态 CLOSED→OPEN→HALF_OPEN，慢/异常比例 ≥50% 就 fail-fast 熔断 5s、放 3 个探针试探恢复——但要讲清这是目标态，现状只有人工全站熔断开关；第二块**降级**，熔断时 fail-fast 返回兜底、推拉分离保证查询通道仍可用、热点读走本地缓存 30s；第三块**转人工闭环**，跨系统通知走待发送表状态机，超限转"待人工"，三要素——通知到人（按系统分派、告警带业务单号不用查库）、两条出路（线下处理标已闭环，或重启派发回待发送且不产生第二笔业务）、不允许悬浮（超时提醒 + 操作留痕 + 成功归档）。
>
> 收口：**熔断是保护、降级是体验、人工闭环是兜底，三者拼起来才叫完整机制——核心是任何一笔业务都有最终交代，绝不静默丢失。**

## 5. 追问预案（带证据等级）

| 追问 | 回答要点 |
|---|---|
| 超时了到底重不重试？ | **分性质**：异步通知带幂等键重试、阶梯退避；同步查询不重试（放大成风暴），靠幂等卡 + 对账兜底【实证】 |
| 两种"熔断"有什么区别？ | 网关三态是实时保护（fail-fast 释放资源，目标态）；跨系统"熔断转人工"是重试超限后的状态跃迁，指不再自动重试、转人接管【实证】 |
| 重试会不会重复扣款/过户？ | 不会——每次派发带业务幂等键（业务单号+目标系统+业务动作），下游按幂等键去重；不幂等的下游先加去重表+状态查询层再谈重试【实证】 |
| "超时≠没执行"怎么处理？ | 分布式最危险的不确定失败——不盲目重试，靠幂等键 + 主动查状态 / 对账确认真实结果【实证】 |
| 待人工之后呢？ | 两条出路：线下处理标"已闭环"或重启派发回"待发送"；有超时提醒，不允许悬浮【实证】 |
| 手动重试会不会产生第二笔业务？ | 不会——只重置记录状态重新入队，幂等键不变【实证】 |
| 部分成功怎么补？ | 只对失败的那条下游记录重试，已成功的不动（一条下游一条记录）【实证】 |
| 告警什么时候发？ | 告警阈值低于熔断阈值，重试到一半就通知，不等熔断【实证】 |
| 熔断怎么配？ | 慢调用/异常比例 ≥50%（10s/20 请求）触发，熔断 5s + 半开探针 3 个，fail-fast 不放流量过去【目标态】 |
| 下游一直挂怎么办？ | 阶梯重试超限转"待人工"，按目标系统分派运营；界面端手动重试是兜底不是主路径，重置回"待发送"不产生第二笔业务【实证】 |
| 限流/熔断是现状还是规划？ | **现状是短板**：只有人工全站熔断开关 + 批量数量上限，自动熔断/舱壁/QPS 限流是目标态（五层防线+四支柱），讲时别把目标当现状【目标态】 |
| 超时时间怎么定？ | 逐层递减，外层 > 内层：网关 1s > 后端 800ms > DB 500ms，避免外层超时内层还在打 DB【实证】 |
