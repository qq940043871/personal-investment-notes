# 10 · 主导冲突的案例：竞价标状态延迟（报价成功另一方 2s 才看到）如何协调解决

> **性质**：AI 面试复盘沉淀件（一问一文件）。2026-11-26 收录，按真实项目经历口径撰写。
> **原题**：主导这种冲突的案例有吗？分享当时的情况和处理——客户端访问竞价标的状态延时，客户报价成功后另一方看不到最新价格，延迟约 2s 才看到。

> **证据等级（先分清再说）**
> - 【实证·真实方案沉淀】问题场景真实：竞价详情页状态/最优价延迟、三端不同步（库里记为"大屏看到价格上涨，PC 没刷新，移动端更慢——交易决策错位"，客户投诉）；根因经 2026-10-28 竞价系统改造技术讨论沉淀为 **6 条**（时序竞争/倒计时口径/WS 假活/断线无补偿/消息乱序/数据源不统一）。处理方案是真实讨论产物：`06-竞价状态不一致`（状态口径与补偿规则）+ `09-竞价详情页轮询改造`（推拉分离通道设计）+ 痛点 21（Canal+缓存写时通知读时拉取）。
> - 【实证·效果口径】库里的实测口径是**行情同步延迟 5 秒压到 1 秒内、推送与数据强一致**（痛点 21）；题面"2s"是题干给的现象值，库里**没有单独标注 2s 的逐笔事故记录**——讲的时候用"客户感知约 2 秒级延迟"，效果引用库里"5s→1s"口径，不要把 2s 说成我的实测。
> - 【设计态 / 未落地】推拉分离方案里"订阅功能上线后实施（需后台配合）"、购房情接口做状态副本补齐——原文明确标注未实施；直推独立 WS 服务的事件可靠性（有界队列满即丢、seq+快照自愈）是设计取舍，讲的时候说"方案定的是……"，不冒充已全量上线。
> - 【角色边界】我作为 Java 侧负责人 / C↔Java 技术接口人**主导契约与方案评审、拍板边界**，C 引擎编码与推送通道实现归对应团队；"我主导"指主导协调与决策，不是我亲手写了 C 代码或 WS 服务。

## 0. 一句话口径（先背这句）

> 有，竞价详情页延迟是典型一例。先说清楚我的角色：我是 Java 侧负责人兼 C/Java 技术接口人，这类冲突我主导的是**契约、边界和方案评审**，不是去写 C 代码。当时的现象是客户报价成功后，另一方要等约 2 秒才看到最新价格，三端还不同步，客户投诉。我们没在对错上扯皮，而是把问题拆成两段——**状态口径**（06 号定了 6 条根因和补偿规则）和**推送通道**（09 号定推拉分离），我组织双方评审拍板边界：C 只管快、只发不取，核心推送绝不阻塞撮合线程；查询仍走网关；页面从轮询改成事件驱动。效果按库里口径是行情同步从 5 秒压到 1 秒内。有几处（订阅、状态副本补齐）方案里写着上线后实施，我不会说成都落地了。

## 1. STAR · S 情境（当时的情况）

**业务场景**：大宗商品竞价交易，客单价几十万到上千万，价格实时波动，交易员盯盘出价。

| 维度 | 内容 |
|------|------|
| 现象 | 客户报价成功后，**另一方看不到最新价格，约 2 秒后才刷新出来**；同时三端不同步——大屏看到价格上涨，PC 没刷新，移动端更慢 |
| 影响 | 交易决策错位、客户投诉（库里记为 P1-高优："报价看不到，2h 响应当日修复"） |
| 冲突点 | 前端说"推送慢/丢消息"，C 侧说"我已经推了"，Java 侧说"库里状态还没到"——**三方各执一词，没有公共事实** |
| 我的角色 | Java 侧负责人 + C↔Java 技术接口人：**主导把三方拉到同一份事实和契约上**，定边界、组织评审、拍板方案 |

> 讲法要点：冲突不是"谁技术差"，是**异构链路上每段都觉得自己在标准内，端到端却慢了/对不上**。这正是接口负责人该出场的时刻。

---

## 2. STAR · T 任务（要解决的真问题）

不是"把 2 秒调成 0"，而是三个层次：

1. **先有公共事实**：把端到端链路切段，用桥接日志/序列号定位延迟到底落在推送段、推送通道段还是查询段——延续 09 号案例里"桥接 SDK 日志第一排查依据"的方法；
2. **再定口径边界**：竞价状态怎么定义、倒计时基准、断线怎么补——这是 C/Java/前端三方必须签死的契约；
3. **最后定技术方案并推动落地**：谁改什么、发布顺序、灰度与回滚、不能一次做完的怎么排期。

---

## 3. STAR · A 行动（我怎么主导的，分四步）

### 第一步：组织定位，拆成"状态口径"和"推送通道"两个问题【实证·方法】

- 把三方争议拆成两个互不重叠的议题，避免混着吵：
  - **状态口径** → `06-竞价状态不一致` 负责（6 条根因 + 补偿规则）；
  - **推送通道** → `09-竞价详情页轮询改造` 负责（推拉分离 + 稳定性）。
- 这一步本身就是协调动作：**用"分而治之 + 明确每份文档的职责边界"终止了互相甩锅**——06 只讲状态口径不重复通道设计，09 只讲通道不重复状态口径。

### 第二步：定根因清单，让争议变成"对号入座"【实证】

06 号沉淀的 6 条根因：

| # | 根因 | 现象 |
|---|------|------|
| 1 | 页面打开时序竞争 | 推送早于连接建立 / 库状态异步未更新 → 首屏落后 |
| 2 | 倒计时口径不一 | 手机/PC 不一致；凌控只在进页面取一次服务器时间，放久偏差几分钟 |
| 3 | WebSocket 假活 | "链接还在但消息收不到"，静默丢消息 |
| 4 | 断线无补偿 | 断线期间状态变化丢失，重连后不补 |
| 5 | 消息乱序 | 旧消息晚到覆盖新状态 |
| 6 | 详情页数据源不统一 | 交易中/结束后查不同源，结束后靠 WS 动态确认，与库对不上 |

> 三方争议逐条对号入座后，"谁的责任"变成了"哪条根因"——**这是冲突协调的关键一转**。

### 第三步：拍板边界与方案（我作为接口人的核心动作）【实证·方案】

| 决策 | 拍板内容 | 为什么这么定 |
|------|---------|-------------|
| **推拉分离** | 推送 = C 核心直推独立 WS 服务（只发不取）；查询 = 仍走 midservice 网关 → dataShare → DB/C | 两条通道独立扩容/发布/故障；推送不被 DS 发布窗口绑架 |
| **不复用 dataShare 中继** | 放弃原设想的 C→dataShare→网关→客户端，改 C 直推 WS 服务，链路缩为两跳 | 竞价事件语义极简、延迟敏感，不值得拉通用数据中心中转；代价是事件可靠性责任转移给 WS 服务 |
| **C 侧硬约束** | 事件出口必须有界队列 + 非阻塞投递，队列满丢最旧，**绝不反压撮合线程** | 撮合是资金心脏，推送不能阻塞它；丢的是高频可覆盖事件，下个事件/快照自愈 |
| **状态口径** | 核心推送"标的号+状态+阶段结束时间戳"，前端只更新对应标的；前端算倒计时并持续对服务器时间校准 | 统一口径，解决三端倒计时不一致 |
| **防乱序** | 推送与补偿都带序列号（状态/出价/时间变化 seq+1），前端只接收更新的 seq | 旧消息不覆盖新状态；补偿只拿最新快照 |
| **查询数据源统一** | 交易中查核心 `2457`，结束后查库，结束即最终、需手动刷新 | 消除"库/核心/WS 三源打架" |

### 第四步：推动落地与降级兜底【实证 + 设计态】

- 断线补偿：断线期间每秒查核心 `24b0`（**只查详情不查大厅**，核心承受不住大厅级频率），重连后再查一次确认；
- 稳定性三层：心跳发现假活连接 → 退避重连 → 拉快照/校时钟/重订阅；连任意一台 WS 中间件都能收，**4 台做性能压测**；
- 降级：推送通道故障时查询通道仍可用（推拉分离生效的前提）；
- **诚实标注**：订阅功能、购房情接口做状态副本补齐，方案原文写"上线后实施/暂未处理"——讲的时候说明是后续项。

## 4. STAR · R 结果（效果按库里口径讲）

| 结果 | 口径 |
|------|------|
| 行情同步延迟 | 库里实测口径：**5 秒 → 1 秒内**，推送与数据强一致（痛点 21） |
| 后端压力 | 移除详情页实时轮询（500ms~1s、每次 5 跳穿透），改为事件推送——空轮询与随在线人数线性放大的 QPS 消失 |
| 三端一致性 | Redis 唯一数据源 + 大屏 WS 全量推 / PC SSE 增量推 / 移动端轮询+ETag，三端读同一份缓存 |
| 组织成果 | 冲突从"三方甩锅"变成"两份文档分域定责 + 契约评审拍板"，可复用（对应 D1 异构题锚点） |

> **数字纪律**：效果引用库里"5s→1s"实测口径；题面"2s"只作为客户感知现象描述，**不说成我的实测基线**。

## 6. 项目版 90 秒速答

> 有，竞价详情页延迟是典型一例。当时客户报价成功后另一方约 2 秒才看到最新价，三端还不同步、客户投诉——前端说推送慢、C 侧说已经推了、Java 侧说库状态没到，各执一词。
>
> 我作为 C/Java 技术接口人，主导的不是写 C 代码，是**建公共事实 + 拍板边界**。第一步把争议拆成两个议题：状态口径交给一份文档、推送通道交给另一份，避免混着吵；第二步定了 6 条根因（时序竞争、倒计时口径、WS 假活、断线无补偿、消息乱序、数据源不统一），三方对号入座，争议从"谁的锅"变成"哪条根因"。
>
> 第三步拍板方案：推拉分离——C 核心直推独立 WebSocket 服务只发不取，查询仍走网关；不复用 dataShare 中继；C 侧硬约束是有界队列非阻塞投递、绝不反压撮合线程；状态带序列号防乱序、前端算倒计时并对服务器时间校准；查询统一数据源。断线期间每秒查核心详情兜底，重连拉快照自愈。
>
> 效果按我们库里的口径是行情同步从 5 秒压到 1 秒内、三端用 Redis 唯一数据源保持一致。有几项像订阅功能方案里写着上线后实施，我不会说成都落地了。**我主导的是契约和评审、边界拍板，C 代码和 WS 服务实现归对应团队。**
