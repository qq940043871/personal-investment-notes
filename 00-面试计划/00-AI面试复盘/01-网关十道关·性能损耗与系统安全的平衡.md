# 01 · 网关十道关：如何平衡性能损耗与系统安全性

> **性质**：AI 面试复盘沉淀件（一问一文件）。2026-11-26 收录，同日按真实项目经历改造。
> **原题**：在网关设计中，如何平衡十道关卡带来的性能损耗与系统安全性？

> **证据等级（先分清再说，否则就是背教材）**
> - 【实证·现状】=`midservice-1.1.188.228.5`（模块 `1018_S`）的 `HandlerController`：**20 道校验**、`api.json` 配置化、`RiskProcessor` 风控钩子、三级缓存、用户维度锁、幂等卡、`1018_MONITOR_DATA` 监控上报——源码可回查（详见 `midservice/14-HandlerController-网关功能详解.md`）。
> - 【设计态】= **"十道关"本身是 11 号设计文档对网关职责的目标态抽象**（原文明确"十道关为目标态抽象；现状实现见 14 号（20 道校验）"）；令牌桶限流、处置阶梯、midmon 六块看板、全链路 traceId 均属设计态或未实施。
> - 【通用方案】= 外部知识对照，本人无实战。
>
> **讲法纪律**：先用现状讲"我做了什么"，再用设计态讲"体系上应该怎么做"，**绝不把设计目标说成已落地战绩**。

## 0. 一句话口径（先背这句）

> 我们真实网关是配置驱动的 `HandlerController`，20 道校验按"拒绝要早、要便宜"串成漏斗——协议号防伪、防重放、参数校验这些本地判定先把脏流量榨干，执行器级缓存命中直接不进反射调用，最贵的反射调用与下游连接只留给干净流量。**"十道关"是我们对这套职责的目标态抽象**，用来讲清排序逻辑；性能不靠少做安全，靠把拦截成本前低后高排，再用纵深、配置化、可观测把安全加码变成可控成本。

## 2. 核心论述：排序逻辑与设计目标（【设计态】为主）

> 这一节讲"体系上为什么这么排"。11 号文档把网关职责抽象成十道关，**它不是现状清单，是目标态模型**——面试里要说清这一层，否则就是把蓝图当大楼卖。

### 2.1 排序本身就是最大的性能优化

| 目标态关卡 | 成本 | 作用 | 现状对应 |
|------|:--:|------|---------|
| ① 契约校验 | 本地 Map、零 IO | 协议不存在直接拒 | 【实证】`api.json` 路由表 + 协议号防伪（首尾 16 位 + 中间 MD5） |
| ② 身份 | 一次会话读 | 后面判断的前提 | 【实证】Token 解析 + 四套认证体系 + 登录强度分级 |
| ③④ 参数 / 压力参数 | 零 IO | 形状不对、超限就拒 | 【实证】`valide()` 逐参数校验 + `Validate.isSafe` 注入防护 + 批量上限 |
| ⑤⑥ 授权 / 限流 | 缓存读 | 合法身份的高频消耗挡在转发前 | 【实证】`checkApiAuth`/`checkPowers` + `RiskProcessor`；【设计态】三级令牌桶 |
| ⑦ 合规安全 | 一次签名计算 | 防重放 / 签名 / 越权 | 【实证】SHA256 时间戳 + AppKey 验签 + 混合加密 |
| ⑧ 协议缓存 | 一次缓存读 | 命中直接返回 | 【实证】执行器级 `PUB/FRM/CLI` 三级缓存 |
| ⑨ 转发 | 一次网络调用（最贵） | 只处理榨干后的干净流量 | 【实证】反射调用 + DS 桥接 |
| ⑩ 响应治理 | 回程本地处理 | 脱敏 + 信封 + 审计 | 【实证】字段级出参脱敏 + `1018_APP_LOG` 安全审计流 |

**为什么 ① 最前**：不是最基础的安全关，是**最便宜**的关——成本排序压倒逻辑排序。现状里协议号防伪就是这一思想的落地：不合法的协议号在本地就被拒，连 Token 都不用查。

### 2.2 纵深防御，不是重复防御

"网关 pageSize 上限 100、后端 SQL 硬红线 200"看着像重复，其实是【设计态】的纵深：网关拦常规流量 → 白名单提额到 200 卡住后端红线（**申报 + 评审的例外**，不是默认放宽）→ DAO 强制 `limit` 兜内部调用绕过。**注意**：pageSize 100 / 提额 200 是设计文档基线，现状 20 道校验里能确认的是"批量上限"开关（`Security.Api.maxMultiApiCount`），不要硬报 100 是线上现值。

### 2.3 配置化，把每请求成本压成 O(1)

【实证】`api.json` 一处定义、`HandlerRouter` 多处生效（路由 / 鉴权 / 参数校验 / 日志 / 脱敏，共五类元数据）。入参按 `PARAMS` 元数据校验、出参按 `encodeMap` 字段清单脱敏——两侧都靠配置兜住，业务执行器不用反复自证清白。加一个接口不用发版，是这套网关最核心的设计目标。

> ⚠️ **口径区分（别背串）**：11 号文档 §3.3 的「**一处定义、四处生效**」是**设计态契约注册表**的说法，四处 = 校验规则 / 接口文档 / 监控维度 / 限流脱敏配置；本段讲的是**现状 `api.json`** 里封装进 `HandlerRouter` 的五类元数据（路由 / 鉴权 / 参数校验 / 日志 / 脱敏）。两者不是同一件事——面试官问「四处是哪四处」，答设计态那四件，别拿本段五项去凑数。

### 2.4 用可观测和灰度把"安全过严"的代价关进笼子

【实证】每道校验「全局开关 + 协议级 Map」双控支持灰度，风控有 `Security.Risk.enable` 开关，一键熔断有 `SysPara["40310"]`——**配置驱动让策略调整不用发版**。
【设计态】处置阶梯、灰度观察期、midmon 观察者与执行者分离、容量红线反推（DB 安全吞吐 ≈ 230 QPS → 放行 200 → ÷5 实例 = 40 QPS/实例）都是目标态设计，**不要说成线上已完整落地**。

## 3. 项目版 90 秒速答（改真实术语，别背十道关编号）

> 我们的入口是 Java Web 自研的 `midservice` 网关，核心实现是 `HandlerController`——配置驱动，协议元数据全在 `api.json`，加协议和改校验都不用发版。
>
> 性能与安全的平衡靠三件事：**第一，按成本排校验链**。20 道校验里协议号防伪、防重放、参数形状校验都是本地判定，扫描器和不合法请求在前面就被拒，连最贵的反射调用和下游连接都碰不到；执行器级三级缓存命中直接不返回反射，QPS 承载能力差一个量级。**第二，纵深**。网关校验、后端 SQL 红线、DAO 强制 limit 各管一段，不把成本叠在一次请求上。**第三，配置化 + 可观测**。每道校验都有全局开关加协议级 Map，能灰度、能按渠道差异化；监控走 `1018_MONITOR_DATA` 上报耗时与结果码，P95 看慢协议。
>
> 我们内部把网关职责抽象成"十道关"用来讲排序逻辑，但那是目标态模型；现状是 20 道校验，全链路 traceId 也还是设计态没上。真出过的事是网关横扩到 5 实例把 DB 打穿——那是流量放大器问题，靠限流、隔离、卡连接池、缓存四步止血，再固化成扩容前核出口容量的规范。一句话收口：**安全与性能的矛盾是假命题，真矛盾是把安全放在错误的层级。**

## 4A. 「一处定义、四处生效」专项追问链（四层，逐层深挖）

> **为什么要单独备**：这句话简历上写着漂亮，但它横跨**设计态**与**现状实证**两套口径，面试官从"哪四处"一路能追到"落地了吗""有什么问题"。按下面四层背，每层都能接住，不会串场。
>
> **定调句**（被追问先抛这句）：本质是**把不变收敛到底座、把变化交给配置**——契约是接口语义的单一事实源，校验、文档、监控、限流脱敏都从它派生。

### 4A.1 定义层（开场必追）

**Q1：你说"四处生效"，具体哪四处？**
> 分两套讲，别串：① **设计态**（11 号 §3.3 契约注册表）= 校验规则 / 接口文档 / 监控维度 / 限流脱敏配置；② **现状实证**（`api.json` → `HandlerRouter`）= 路由 / 鉴权 / 参数校验 / 日志 / 脱敏五类元数据。面试官问"四处"答①，问"你们线上配了什么"答②，并主动点明两者不是一回事。【设计态 + 实证】

**Q2：协议号是什么？跟消息 ID 有什么区别？**
> 协议号 = **接口唯一编码**，不是消息 ID、不是流水号。它决定契约注册表里白名单、限流配额、脱敏策略、监控维度**挂在哪一行**。消息 ID 标识一次调用，协议号标识一类接口。【实证】

**Q3：编码怎么编的？**
> 分段编址 `服务段-模块段-接口段@版本`；一生一码、编码不回收（下线后永久保留）、兼容性变更不升版本、破坏性变更（删字段/改语义/改类型）才升版本且新旧并行。灰度、下线都以编码为单位，不按 URL 模糊匹配。【设计态】

### 4A.2 机制层（怎么落地的，最容易被打假）

**Q4：为什么要收口到网关？以前什么样？**
> 改造前参数校验、压力参数、脱敏分散到各业务服务各写一遍 → 同一字段三个服务三种校验、新增接口必漏、改一处改 N 处。网关收口后这些横切能力只维护一份，"一处定义、处处生效"。【设计态·改造前痛点】

**Q5：这份契约在你们系统里到底存在哪？**
> **现状**是 `api.json` 配置表，启动时反射预解析成 `HandlerRouter`（协议 → 类#方法 + 元数据），支持外置配置目录覆盖 classpath；**设计态**才是独立建表的契约注册表，统一发放编码、状态机管控（草稿·生效·灰度·下线）。别说成线上已经有注册表。【实证 + 设计态】

**Q6：加一个接口要不要发版？**
> 加协议 / 改校验 / 调脱敏字段都不发版，改 `api.json` 即可——这是这套网关最核心的设计目标。**但要主动补短板**：现状是启动加载、不热更新，改配置要重启；热更新（配置中心 + 文件 Watcher）是重做时的改进项。【实证 + 设计态】

**Q7：未定义字段为什么是"拒绝"而不是"忽略"？**
> 忽略 = 埋雷（前端改了字段名没人知道）；透传 = 参数注入（攻击者塞 `isAdmin=true`、`tenantId=别家`）；**拒绝是唯一安全选项**。同样，类型严格（声明 int 就不收 "123"）、枚举封闭、长度必有上限。【设计态·入参白名单】

**Q8：为什么入参和输出都要白名单？**
> **对称**：入参白名单挡注入与越权赋值，出参白名单让泄露面不随开发增长（只输出契约声明过的字段）。两侧都靠契约兜住，中间的业务代码就不必反复自证清白。【设计态 + 实证 `encodeMap`】

### 4A.3 边界层（考你分不分得清）

**Q9：契约注册表就是配置中心吗？**
> 不是。契约是**接口语义的单一事实源**（一个接口有哪些字段、什么类型、谁能调、限多少）；配置中心管的是运行时参数与开关注入。现状 `api.json` 走外置目录覆盖，不是配置中心，也不热更新。混为一谈是概念错误。【设计态 + 实证】

**Q10：网关只做横切，那业务校验放哪？**
> 判据一句话：**网关只做与业务无关、横切、可配置的事**。需要问"这个客户是谁、这笔业务合不合法"才能做的判断（库存、授信、状态机），一律下沉业务层。【设计态】

**Q11：这套设计还有什么问题？**（主动自曝题）
> 挑能讲出根因和改法的三件事：① 配置**启动加载不热更新** → 接 Apollo/Nacos + Watcher；② 审计协议号**硬编码** 6 个 → `api.json` 加 `AUDIT_FLAG` / `SECURITY_LEVEL`；③ 路由 `for` 遍历 List 是 O(n) → `Map<api, router>` 双索引。再加一条最重的：**契约注册表本身是设计态，早期接口各自为政，靠协议号逐一收敛，地基阶段就该建**。【实证·短板 + 设计态】

**Q12：如果重做会怎么改？**
> 不是推翻重写：**契约注册表在地基阶段就建**（否则后面所有限流/监控/授权都无处挂），配置热更新 + 审计字段配置化 + 路由双索引。收口一句——"先跑起来没错，但地基要一开始留好位置"。【设计态·演进】

### 4A.4 治理层（跨团队场景）

**Q13：跨团队对数据格式有分歧，契约怎么起作用？**
> 先问一句：**这个字段在契约里定义过吗？** 定义过 = 有人绕过评审，按变更闸门补评审；没定义过 = 契约缺失，双方评审后补进去、在 DS 做映射，不动 C 核心。最后用同一组例子让双方复述，边界/状态/异常三处无歧义才算对齐。【实证·02A + 09 号】

**Q14：契约变更怎么保证兼容？**
> 新增字段可空、不改语义、保留旧字段过渡期、发布顺序写进评审单；破坏性变更才升版本、新旧并行一段时间。契约里带责任人 / 变更时间 / 容量申报，变更以编码为单位灰度。【设计态 + 实证·评审闸门】

> **追问链收口**：定义 → 编码规则 → 落地形态 → 白名单理由 → 边界判据 → 短板与演进 → 跨团队治理。**每一层都要能落回 `11` 号（设计态）或 `14` 号（现状实证），落不回去的就是教材话，别说。**
