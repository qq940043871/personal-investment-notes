# 03 · 白名单 IP 的安全性和有效性如何确保，被滥用怎么办

> **性质**：AI 面试复盘沉淀件（一问一文件）。2026-11-26 收录，同日按真实项目经历改造。
> **原题**：白名单 IP 的安全性和有效性是如何确保的？如果某个 IP 被滥用或者被恶意利用应该怎么应对？

> ⚠️ **先纠正题面与项目的错位（这篇最重要的改造）**
> 全库核查结论：**我们项目里真实存在的"白名单"是协议白名单 / 配置白名单，不是 IP 白名单**。
> - 【实证·现状】`rsaAllowMap`（明文通道协议白名单）、`noAuthApis`（授权跳过白名单）、`dapingMap`（大屏协议白名单）、`WhiteApi.apis`（配置白名单）、`APISTYLE=inner`（内部协议禁止外呼）、`MODU_ID=1036` 自动注入客户端 IP——见 14 号文档 §二/§四。
> - 【设计态】11 号文档 §6.5 那句"内部互调 / 健康检查拨测 / 监控探针 / 办公出口 IP 不参与自动封禁"是**目标态误伤防护**，现状没有 IP 白名单配置。
> - 【通用方案】"IP 白名单被滥用怎么应对"整套（裸 IP 不够 / 三元组条目 / mTLS / 降级豁免）**是外部通用知识，本人无实战**。
>
> **讲法纪律**：如果面试官问的是"你们白名单怎么管"，**先答协议白名单**（有实证）；如果问题明确是 IP 白名单，老实说"那是通用方案，我们现状 IP 主要用于审计与风控维度，不是白名单准入"。**千万别把协议白名单偷换成 IP 白名单战绩**。

---

## 0. 一句话口径（先背这句）

> 我们项目里真实的白名单是**协议级**的——明文协议要进 `rsaAllowMap`、内部分组走 `APISTYLE=inner` 禁外呼、大屏协议走 `dapingMap`，全是配置驱动、一处定义处处生效；IP 在现状里进审计日志和风控维度，不是白名单准入。**IP 白名单的滥用应对是通用方案**（IP + 身份 + 接口三元组、叠加应用层凭证、先降级豁免再吊销隔离），我讲的时候会标清楚是设计/通用，不冒充已实现。

---

## 1. 项目里真实存在的白名单（【实证·现状】）

| 白名单 | 作用 | 不做的后果 | 出处 |
|--------|------|-----------|------|
| `rsaAllowMap` | 明文模式必须每个 api 在白名单，否则 `no auth` | 加密通道被绕过 | 14 号 §三阶段 2 |
| `noAuthApis` | `checkApiAuth` 时跳过授权列表 | 机构用户协议授权失控 | 14 号 §四第 19 关 |
| `dapingMap` | 大屏协议需登录且 `userId == is.daping.user` | 大屏只读接口被普通用户调 | 14 号 §四第 13 关 |
| `WhiteApi.apis` | 全局白名单配置，`initRouter` 时加载 | — | 14 号 §2.3 |
| `APISTYLE=inner` | 内部协议禁止从网关外呼（`mid.server.style=custom` 时生效） | 内部接口暴露到公网 | 14 号 §4.5 |
| `rsaAllowMap` / 业务白名单 | 协议级、配置驱动，改配置不发版 | — | 14 号 §九 |

**有效性怎么确保（实证）**：

- **白名单是配置源不是硬编码**：全在 `api.json` / `ServiceConst` 里，`initRouter` 启动加载，单条脏配置只打日志不中断（可用性设计）；
- **纵深不靠单一白名单**：明文白名单 + 混合加密（RSA 传 AES Key + AES-CBC）+ AppKey 验签 + 登录强度分级（查询密码、交易证书）四层叠加；
- **有据可查**：审计流 `1018_APP_LOG` 记 `KEYID/USERID/OPERTIME/API/NOTE/ISOK/OPERIP`，白名单内调用一样留痕。

> 这就是"有记录的例外"在我们系统里的真实形态——**不是口头放行，是配置留痕 + 审计留痕**。

## 2. "IP 白名单"的滥用应对（【通用方案】/【设计态】，非本人实战）

> ⚠️ 以下不是我们系统现状。面试官若追"你们真这么做了吗"，如实答"这是通用做法，我们现状 IP 走风控与审计，不做白名单准入"。

### 2.1 根因认知：IP 是网络层标识，不是身份证明

内网沦陷、NAT 出口共享、VPN 劫持都能让"可信 IP"里跑出恶意流量——所以白名单 IP 只能是第一道门，必须叠加应用层凭证（AppKey 签名 / 服务证书 / mTLS）。我们项目里**恰好有这套凭证层的实证**（AppKey 验签 + 混合加密 + 登录强度分级），可以借它来讲"为什么光靠 IP 不够"。

### 2.2 处置阶梯（通用方案，非现状）

```
异常信号 → 降级豁免权回普通通道 → 吊销应用层凭证 + 熔断接口限爆炸半径 → 走安全事件流程
```

### 2.3 长效机制（通用方案）

三元组条目（IP + 身份 + 接口范围）、带有效期定期复核、变更留痕、白名单流量不退出监控。

---

## 3. 项目版 90 秒速答

> 我们项目里真实的白名单是**协议级**而不是 IP 级：`api.json` 里的 `rsaAllowMap` 管明文通道准入，`noAuthApis` 管授权跳过，`dapingMap` 管大屏协议，`APISTYLE=inner` 让内部协议禁止外呼——全是配置驱动，改白名单不发版。有效性靠三点：白名单是配置源不是硬编码，单条脏配置不阻断启动；它只是第一层，后面还叠着 RSA + AES 混合加密、AppKey 验签、登录强度分级，查询类密码登录、交易类证书登录；所有调用进 `1018_APP_LOG` 审计流，包括 IP，白名单内也一样留痕。
>
> 如果你问的是 IP 白名单被滥用——那是我们设计文档和行业通用方案里的东西，不是我们现状：我们 IP 主要进审计和风控维度，不做白名单准入。通用打法是别把 IP 当身份，叠加应用层凭证，出事先降级豁免权再吊销凭证隔离，条目做三元组加定期复核。我能讲这套思路，但得说清楚它是方案不是战绩。

## 4. 追问预案（带证据等级）

| 追问 | 回答要点 |
|------|---------|
| 你们白名单是怎么配的？ | 【实证】协议级配置：`rsaAllowMap`/`noAuthApis`/`dapingMap`/`WhiteApi.apis`，改配置不发版 |
| 有没有 IP 白名单？ | **没有**——IP 进 `1018_APP_LOG` 的 `OPERIP` 审计字段与风控维度，不做准入 |
| 白名单协议被滥用怎么办？ | 【实证】后面还有加密 + 验签 + 登录分级 + 审计；【设计态】`RiskProcessor` 可按协议灰度拦截 |
| 光靠白名单够吗？ | 不够，我们现状就是"白名单 + 混合加密 + AppKey 验签 + 登录强度分级"纵深 |
| IP 被冒用怎么应对？ | 【通用方案】三元组 + 应用层凭证 + 降级豁免 + 吊销隔离，非本人实战，明说 |
| 内部协议会被外部调到吗？ | 【实证】`APISTYLE=inner` + `mid.server.style=custom` 时直接拒（§4.5） |
