# 02 · 某个关卡频繁触发拒绝（如某 IP 频繁调用触发风控限流）

> **性质**：AI 面试复盘沉淀件（一问一文件）。2026-11-26 收录，同日按真实项目经历改造。
> **原题**：某个关卡频繁触发拒绝操作，比如某个 IP 频繁调用调至风控限制，怎么处理？

> **证据等级（先分清再说）**
> - 【实证·现状】`HandlerController` 有 `RiskProcessor.process()` 风控前置钩子（阶段 5），拿到**原始请求 + 解密后完整指令集 + 登录态**，可做**频率 / 地域 / 设备 / 行为**维度拦截；`Security.Risk.enable` 全局开关；`SysPara["40310"]` 全站一键熔断；20 道校验每道「全局开关 + 协议级 Map」可灰度。源码可回查 14 号文档 §三阶段 5 / §四 / §九。
> - 【设计态】"触发源四类 / 处置阶梯（告警→降速→临时封禁 15 分钟→黑名单）/ 双维度校验 / 灰度观察期 / 令牌桶"全部出自 11 号设计文档 §6，**是目标态治理方案，不是现状已逐条实现**。
> - ⚠️ **"IP 频繁调用触发风控"这个题面本身要修正**：现状风控有频率维度，但**没有"按 IP 自动封禁"的实证**；IP 在现状里主要进审计日志（`1018_APP_LOG` 的 `OPERIP`），不是封禁主体。面试别把题面当自己的系统行为照单全收。

---

## 0. 一句话口径（先背这句）

> 频繁拒绝不等于有攻击——先定位是哪道校验在拒、拒的什么信号，再决定处置。我们现状是 `RiskProcessor` 做频率 / 地域 / 设备 / 行为四维拦截 + 每道校验可灰度开关；体系上把触发源归成四类（频率超限 / 高频错误 / 扫描特征 / 行为异常），处置走先轻后重可回退的阶梯，双信号才自动封禁，误伤申诉大于零就复盘。**阶梯与令牌桶是设计态**，讲的时候要分清。

---

## 1. 第一步：定位——哪道校验在拒（【实证】框架 + 【设计态】映射）

| 拒绝飙升的位置 | 最可能的根因 | 现状能查什么 |
|------|------|------|
| 协议层校验 | 非法协议号、协议号伪造（首尾 16 位 + 中间 MD5 不匹配）、RESTful 路径无法识别 | `HandlerRouter` 表 / 协议号防伪校验 |
| 安全校验层 | 防重放时间窗超差（`security.difftime` 默认 60s）、签名错误、敏感词命中 | 时间戳 SHA256 校验 / `SensitivewordFilter` |
| 身份授权层 | `checkLoginType` 等级不足、`checkApiAuth` 未授权、`checkPowers` 机构无代理权限 | `AuthTypeMap` / `3002_API_AUTH_LIST` / `1001_AGENTFIRM_USERID` |
| 参数校验层 | `valide()` 失败、`Validate.isSafe` 注入拦截、批量超上限 | `api.json` 的 `VALIDATE/LENGTH/TYPE` / `Security.Api.maxMultiApiCount` |
| 风控层 | `RiskProcessor` 四维拦截命中 | `Security.Risk.enable` 开关 + 风控处理 |

> **关键纪律**：不同位置的拒绝信号含义完全不同——**参数校验失败突增，八成是调用方改了字段没同步 `api.json`，不是攻击**。先查配置变更，别先封人。

---

## 2. 第二步：判性质——四类触发源（【设计态】）

11 号文档 §6.3 归纳的四类是**治理模型**，用来组织话术：

| 触发源 | 特征信号 | 现状对应 |
|------|---------|---------|
| ① 频率超限 | QPS 超租户 / 应用 / 接口配额 | 【实证】`RiskProcessor` 频率维度；【设计态】三级令牌桶 |
| ② 高频错误 | 滑窗内 4xx/5xx 占比超阈值 | 【设计态】midmon 错误率看板 |
| ③ 扫描特征 | 大量"编码不存在"、参数连续失败、路径穿越 | 【实证】协议号防伪 + `Validate.isSafe` 注入防护 |
| ④ 行为异常 | 同 IP 切多账号、异地并发、间隔极规律 | 【实证】`RiskProcessor` 地域 / 设备 / 行为维度 |

- **光 QPS 高不算恶意**：机构客户批量对账、内部批量协议可能合法冲高；
- **双维度校验**（【设计态】）：至少两个信号成立才自动封禁，单信号只告警；
- **白名单豁免**（【设计态】）：内部互调 / 拨测 / 探针 / 办公出口 IP 不参与自动封禁；注意现状项目里的白名单是**协议白名单**（`noAuthApis`、`rsaAllowMap`、`WhiteApi.apis`），不是 IP 白名单，详见 `03` 号文件。

---

## 3. 第三步：处置措施——现状能做的 vs 设计态规划

| 层级 | 【实证·现状】 | 【设计态】 |
|------|-------------|-----------|
| 单请求拦截 | `RiskProcessor` 返回 false → `HandlerException("该请求已被拦截！")`；各道校验拒绝码（GB2013~GB2021 等） | 429 + 可读文案 |
| 策略灰度 | 每道校验「全局开关 + 协议级 Map」；`Security.Risk.enable` | 新阈值先告警后拦截的灰度观察期 |
| 全局止血 | `SysPara["40310"]` 全站一键熔断（发版维护用，提示语可配） | 慢调用比例 ≥ 50% 自动熔断 |
| 主体处置 | IP 进审计日志 `OPERIP`，**无自动封禁实证** | 告警 → 降速 → 临时封禁 15 分钟自动解封 → 黑名单人工 + 申诉 |
| 计数一致性 | — | 集中式 / 分片令牌桶；判据"限流保护什么决定精度"，计量计费走独立通道 |

> 面试被问"你们真按 IP 自动封禁吗"：**如实说——风控有多维拦截，IP 进审计，但自动封禁阶梯是设计态**。编"我们封了"一旦被追配置就露馅。

---

## 4. 项目版 90 秒速答

> 遇到某类请求被频繁拦，我先定位是哪一道在拒——我们的 `HandlerController` 有 20 道校验，协议号防伪、防重放、身份授权、参数校验、风控各管一段，拒绝码都不一样。参数校验失败突增通常是调用方改了字段没同步 `api.json`，先查配置变更，别当攻击封人。
>
> 风控这一层是 `RiskProcessor` 前置钩子，拿到原始请求和解密后的指令集，做频率、地域、设备、行为四个维度的拦截，有全局开关能按协议灰度。体系上我们把触发源归成四类——频率超限、高频错误、扫描特征、行为异常，处置走先轻后重：告警、降速、临时封禁自动解封、最重才黑名单人工加申诉，至少两个信号成立才自动封禁。真要全局止血我们有 `SysPara["40310"]` 一键熔断。
>
> 但有一条我得说清楚：**按 IP 自动封禁那套阶梯是我们设计文档里的目标态，现状 IP 主要进审计日志，不是自动封禁主体**。限流令牌桶同理，是设计方案。我不会把设计目标说成已经上线。

## 5. 追问预案（带证据等级）

| 追问 | 回答要点 |
|------|---------|
| 你们真有 IP 自动封禁吗？ | **没有实证**——风控四维拦截是现状，IP 进审计 `OPERIP`；封禁阶梯是设计态 |
| 频繁拒绝一定是攻击吗？ | 参数失败突增八成是调用方字段没同步 `api.json`，先查配置变更 |
| 风控能拦什么？ | 【实证】`RiskProcessor` 频率 / 地域 / 设备 / 行为四维，全局开关 + 协议级灰度 |
| 一键熔断和自动封禁区别？ | 一键熔断是现状全局止血（`40310`）；自动阶梯是设计态主体级处置 |
| 多实例计数怎么一致？ | 【设计态】集中式 / 分片令牌桶；判据"限流保护什么决定精度"，计量计费走独立通道 |
| 误封了怎么办？ | 【设计态】临时封禁 15 分钟自动解封 + 黑名单人工申诉；现状靠配置开关快速回退 |
