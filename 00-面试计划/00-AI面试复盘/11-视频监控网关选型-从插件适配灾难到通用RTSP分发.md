## 0. 一句话口径（先背这句）

> 早期方案是**一家摄像头配一个浏览器插件，换个浏览器版本就播不了**——本质是"N 家设备 × M 个浏览器"的适配矩阵做不完。我拍板做一层**通用流媒体网关**：底层 FFmpeg + ZLMediaKit，摄像头侧只认 RTSP/ONVIF 标准协议，**新设备只要给一个 RTSP 地址就能接入**；服务端一次拉流转码、一次输入产出 WebRTC / FLV / HLS 三档出口，浏览器按能力降级，适配问题被网关一次吃掉。两个关键收益：**多浏览器适配从此不用管**，以及**一路 RTSP 只拉一次、摄像头连接数不随观众数增长**。代价是服务端成了流量汇聚点，出口带宽变成新瓶颈。

## 1. 先落项目锚点：这个决策解决的是哪个层次的问题

| 项 | 真实情况 | 口径 |
|---|---|---|
| 起点 | 客户现场存量几十上百个 RTSP 摄像头，看画面要回机房开 NVR 客户端；一家摄像头配一个浏览器插件，换浏览器版本就播不了 | 【底稿】 |
| 行业约束 | 园区/工地/仓储/门店存量摄像头几乎全是 RTSP / ONVIF；商用监控平台按路授权 | 【底稿】 |
| 角色 | 流媒体方案技术负责人（选型 + 落地），"这个决策是我做的"指拍板方案与边界，不是我写了全部编码 | 【底稿】 |
| 顶点 | 单机 50–100 路（4C8G / 720P / 1–2 Mbps）、1000+ 并发观看 | 【底稿】，口径见 §4 |

**这不是"换一个播放器"的小改进，是消灭一整个适配矩阵的架构决策。** 口述里"采用一种通用的、适配多家摄像头和多浏览器的方案"——这句话的方向对，但面试要把"通用"具体化成一句话：**把设备侧的私有协议收敛到 RTSP/ONVIF 一个标准入口，把浏览器侧的兼容收敛到 Web 协议三档出口，中间用一层网关隔开，两侧各自独立演进。**

## 2. 选型：四条路线对比与"我否决了什么"

> 面试官真正想听的不是你选了什么，是**你否掉了什么、为什么**。这题的含金量全在否决理由。

| 路线 | 授权成本 | 延迟可控 | 数据归属 | 设备兼容 | 结论 |
|---|---|---|---|---|---|
| 商用 NVR 厂商 SDK | 按路授权，几十上百路持续计费 | 好（私有协议） | 客户内网 | 仅厂商设备 | ❌ 否决 |
| 海外 SaaS 中转 | 按流量/路数订阅 | **不可控**（跨境链路） | 视频流出域 | 好 | ❌ 否决 |
| 纯自研（自己写 RTSP 解析 + RTP 打包 + WebRTC） | 零授权 | 最好 | 自控 | 最好 | ❌ 周期不可接受 |
| **开源底座 + 自建分发（FFmpeg + ZLMediaKit）** | **零授权** | 好（同机房） | 自控 | RTSP/ONVIF 通吃 | ✅ **选定** |

**三条否决口径（背下来）**：

1. **否决商用 NVR SDK**：两个理由——**按路授权**是持续成本（几十上百路不是小数目），**绑死客户端**（只能局域网、只能在指定系统）。客户要的是"手机能看、领导远程看、出事按事件回溯调录像"，厂商客户端给不了。口述里只讲了"插件换版本就播不了"，这是兼容性理由；商业上的按路授权理由更不能漏。
2. **否决海外 SaaS 中转**：视频流出域 + 跨境链路延迟不可控。监控数据是客户现场的生产资料，不是能随便交第三方的流量。
3. **否决纯自研**：把 RTSP 解析、RTP 打包、WebRTC 全自己写，技术上最可控，但周期不可接受——项目要的是快速交付可用能力，不是造轮子。

**为什么是 ZLMediaKit 而不是 SRS / MediaMTX**【推演】：本场景权重是"同一路流要多协议出口 + 按需拉流 + 低资源"，ZLM 匹配度最高（一次输入 → WebRTC/FLV/HLS 同源、单二进制 C++ 资源占用低）；SRS 社区更大作为备选，MediaMTX 适合极简场景。讲的时候标"这是选型评估口径"，别讲成压测过的结果。

## 3. 两个核心收益（口述漏讲、但最值钱的部分）

### 3.1 收益一：多浏览器适配问题被网关一次吃掉

口述说"视频网关建立后再也不用考虑多浏览器适配了"——对，但要说清机制：**浏览器只认 Web 协议，RTSP 是设备侧的事，插件是被淘汰的旧形态**。网关把协议转换做在服务端，前端只消费三档标准 Web 流：

| 出口 | 延迟 | 适用 |
|---|---|---|
| WebRTC | < 500ms | PC 有 RTCPeerConnection |
| FLV（flv.js） | 1–2s | PC 无 WebRTC、flv.js 可用 |
| HLS（hls.js） | 3–5s | 手机 / 兜底，兼容性最好 |

**逐级降级，HLS 是终点——只要它还在，用户就不会看到黑屏。** 口述只讲了"FLV 实时性好、HLS 有延时"两档，漏了 WebRTC 这档低延迟的，会把方案讲成"实时 vs 延时"二选一，实际是有梯度的三档自适应。另外"为什么不全用 WebRTC"要能答：WebRTC 延迟最低但兼容性最脆（Safari、部分安卓浏览器、企业代理不支持）。

### 3.2 收益二：一路 RTSP 只拉一次（整套架构的命门）

> 这是口述里完全没提、但面试官一定追问的一块。

**否决方案**：每个观看者直连摄像头，或每 N 个观看者起 N 个 FFmpeg。
**理由**：摄像头是**嵌入式设备，并发连接数通常只有个位数**——10 个人直连同一路就能把它拖死。
**做法**：服务端**一路只拉一次**，ZLM 向多客户端分发，**摄像头侧连接数只跟"正在被拉流的设备数"有关，与观众数无关**。
**代价**：服务端成为流量汇聚点，**出口带宽成为新瓶颈**（见 §5）。

## 4. 容量口径（最容易被追死的地方，务必带限定语）

| 指标 | 口径 | 讲法 |
|---|---|---|
| 单机 50–100 路 | 【底稿】4C8G / 720P / 1–2 Mbps | ⚠️ **【待确认】源材料未区分"接入注册路数"还是"并发转码路数"**。面试主动说清：如果这个数是并发转码，4C8G 的 CPU 账算不过来；它成立的唯一方式是"接入路数 + 按需拉流 + 源是 H.264/AAC 时优先 `-c copy` 直转" |
| 1000+ 并发观看 | 【底稿】指标卡 | 【推演】单机千兆网卡打不住（1000 × 1.5 Mbps = 1.5 Gbps），不是单机能交付的指标，需多节点/CDN 或降码率档 |
| WebRTC <500ms / FLV 1–2s / HLS 3–5s | 【底稿】 | 直接报，带"目标"口径 |
| 首帧 ≤1s | 【底稿】依赖 GOP 缓存 | 可报 |

> **红线（原话保留）**：**"50–100 路"按"100 路同时软件转码"报容量，现场 CPU 一定打满、方案必然翻车。** 三档出口、按需拉流、直转优先这三条必须一起讲，否则报出来的容量是错的。

## 5. 代价与技术债（诚实清单，讲出来反而加分）

| 项 | 状态 | 内容 |
|---|---|---|
| 出口带宽成新瓶颈 | 【推演】 | 服务端汇聚所有流，16 分屏还会成倍放大；后面要做多档清晰度 + 分发节点/CDN |
| 单机无 HA | 【推演】 | ZLM / 转码全挂则全站断流，生产版需双实例 + 按设备分片 + 重连备用 |
| 断点续传示例 bug | 【推演·审阅发现】 | 代码用 `resp.getHeader("Range")` 取了**响应头**（应为请求头），206 分支永不触发、续传实际不生效 |
| `Runtime.exec` 拼命令 | 【推演·审阅发现】 | 字符串拼接，路径含空格即失败、有注入风险、无超时退出码校验；应改 `ProcessBuilder` + 参数数组 |
| 元数据与文件一致性 | 【推演】 | 文件被清理但记录还在 → 时间轴有段、播放 404，需一致性巡检 |

> 面试官问"这套方案的技术债"时，主动报前两条代码级发现最见功力——**这说明你不是只会画架构图，是真去看过代码**。

## 6. 项目版 90 秒速答（直接背，已修正口误）

> 这个决策的起点是一次适配灾难：早期是一家摄像头配一个浏览器插件，换个浏览器版本就播不了；而且商用 NVR SDK 按路授权、绑死局域网客户端，客户要的手机能看、领导能远程看都满足不了。所以我拍板做一层通用的流媒体网关。
>
> 选型上我否决了三条路：商用 NVR SDK（按路授权 + 绑死客户端）、海外 SaaS 中转（视频出域 + 跨境延迟不可控）、纯自研 RTSP/RTP/WebRTC（周期不可接受）。选的是 **FFmpeg + ZLMediaKit 开源底座 + 自建分发**。
>
> 做法是：摄像头侧只认 RTSP/ONVIF 标准协议，**新摄像头只要给一个 RTSP 地址就能接入，不用改代码**；FFmpeg 按需拉流转码，ZLM 一次输入产出三档 Web 出口——**WebRTC 500 毫秒内、FLV 1–2 秒、HLS 3–5 秒**，前端按能力逐级降级、HLS 兜底。
>
> 两个收益：**第一，多浏览器适配问题从此不用管**——浏览器只消费 Web 协议，RTSP 和插件的事全被网关吃掉；**第二，一路 RTSP 只拉一次**，ZLM 向多观众分发，摄像头是嵌入式设备、并发连接个位数，直连十个人就能把它打死，现在连接数只跟被拉流的设备数有关、跟观众数无关。
>
> 代价说清楚：服务端成了流量汇聚点，**出口带宽变成新瓶颈**，所以后面要做多档清晰度和分发节点。还有个容量口径要讲准——**"单机 50–100 路"指的是接入注册路数，不是同时转码路数**，这个分不清、按 100 路同时转码报容量，现场 CPU 一定打满。

## 7. 追问预案（带证据等级）

| 追问 | 回答要点 |
|---|---|
| "西瓜浏览器"是什么？ | ⚠️ 口误，没有这种浏览器。前端 Vue3 + **flv.js / hls.js**；西瓜视频开源的是播放器 xgplayer，不是浏览器 |
| ffmpget 是哪个组件？ | **FFmpeg**，口误；负责拉流与转码，参数 `-preset ultrafast -tune zerolatency -g 25`【底稿】 |
| 为什么不直接用厂商 SDK？ | 按路授权持续成本 + 绑死客户端；客户要手机看、远程看、按事件回溯，厂商给不了【底稿】 |
| 三档为什么不全用 WebRTC？ | WebRTC 延迟最低但兼容性最脆；按终端能力降级，HLS 是兜底终点，永不黑屏【底稿】 |
| 100 人看会不会把摄像头打死？ | 不会，一路只拉一次、ZLM 分发；摄像头连接数与观众数无关；真正撞墙的是出口带宽【底稿 + 推演瓶颈】 |
| 50–100 路怎么算出来的？ | 【待确认】源材料未区分接入/并发转码；成立条件是"接入路数 + 按需拉流 + `-c copy` 直转优先"，按 100 路并发转码算 CPU 不够 |
| 为什么不选 SRS / 自建？ | SRS 是备选（社区大、资料多），ZLM 在多协议出口 + 按需拉流 + 低资源上匹配度最高【推演选型评估】；纯自研周期不可接受【底稿】 |
| 这套方案的技术债？ | 出口带宽瓶颈、单机无 HA、续传 `Range` 头取错、`Runtime.exec` 拼命令、元数据-文件一致性【推演，诚实报】 |
| "适配多家摄像头"就只要 RTSP 地址吗？ | 看直播/回放是的；**云台 PTZ 还要 ONVIF 能力探测**，标准动作 `ContinuousMove / Stop`，换品牌不改代码，但要做能力探测和按型号兜底【底稿 D3】 |
