# 06 · 高频爬虫导致服务器负载过高，应该如何处理

> **性质**：AI 面试复盘沉淀件（一问一文件）。2026-11-26 收录，按真实项目经历口径撰写。
> **原题**：高频爬虫导致服务器负载过高，应该如何处理？

> **证据等级（先分清再说）**
> - 【实证·现状】识别层：`HandlerController` ① 契约关协议号防伪（`API不正确，非授权访问`，扫描器零 IO 就被榨干）+ 阶段 5 `RiskProcessor.process()` 四维拦截（频率/地域/设备/行为，拒绝 `该请求已被拦截！`）；处置层：`SysPara["40310"]` 一键熔断、慢接口独立线程池、审计流 `1018_APP_LOG`。可回查 14 号现状文档。
> - 【真实事故闭环】网关横扩 5 实例扛 2500 并发 → 流量放大打穿 DB → 当晚四步急救（限流 200 QPS + 超时 1s、热点缓存 30s、独立线程池 core15/max30/queue100、每实例连接池卡 20）→ 中期熔断降级与慢 SQL 治理 → 长期容量申报与扩容 SOP。**按真实架构的代表性场景，数值是利特尔法则反推的示例基线，非实测**；是否被问及在场如实答。
> - 【设计态】令牌桶三级配额（租户/应用/接口）、429 + "系统繁忙"兜底文案、midmon 三级预警、自动熔断参数（慢调用 ≥50%、5s、半开探针 3 个）、按协议分域线程池（方案二，暂不排期）、全链路 traceId——是方案与规范，不是现状逐条实现。
> - 【通用方案】验证码 / 人机校验、UA 指纹、JS 挑战、IP 信誉库、WAF、robots 遵从——**本人项目没有专项反爬组件**，库里也无对应实证，只作外部知识对照，不许讲成战绩。

---

## 0. 一句话口径（先背这句）

> 这题是两件事，别混成一件：**识别爬虫是安全层，扛住负载是容量层**。多数人上来就说"封 IP"，但真正把服务器打挂的不是"它是爬虫"，是"流量超过了 DB 的出口容量"。我们的处理顺序是**先止血再抓虫**——先用限流、缓存、隔离、熔断把负载摁在 DB 承受线以内（这是真事故里验证过的四步），再用 `RiskProcessor` 四维信号 + 协议号防伪把爬虫从合法高频里挑出来。项目里没有专门的反爬产品，验证码、UA 指纹那套是通用方案，我不会说成自己做过。

---

## 1. 先止血：负载过高优先保容量（真实事故闭环）

**核心判断：爬虫只是流量来源，负载过高是容量问题。先问"DB 能扛多少"，再问"谁在打"。**

当年真出过的事：网关横扩 5 个实例扛 2500 并发，入口容量 ×5 但出口（DB）容量没变，中间没闸门，几分钟就把 DB 拖死——**扩容是放大器，不是解药**。

```
网关横扩 5 实例扛 2500 并发 → 瓶颈后移，流量打穿 DB
   ↓ 当晚四步急救（实证）
① 慢接口限流 200 QPS + 超时 1s + 兜底文案  ← 断洪水
② 热点缓存本地 30s + 预热，命中率 ≥90%     ← 回源 ≤20 QPS
③ 慢接口独立线程池 core15/max30/queue100   ← 舱壁隔离
④ 每实例连接池卡 20（5×20=100 < max_conn 200）← 护 DB
   ↓
DB 立刻恢复 → 中期熔断降级 + Top10 慢 SQL 治理 + 读写分离
   ↓ 长期规范
容量申报 + SQL 红线 + 扩容前先核出口容量
```

| 防线 | 手段 | 防的是什么 |
|------|------|-----------|
| 入口 | 全局限流 200 QPS、超时 1s（网关 1s > 后端 800ms > DB 500ms） | 超过 DB 承受力的流量根本不进后端 |
| 缓存 | L1 本地 30s + L2 Redis 5~30min + 预热，命中 ≥90% | 爬虫重复的读请求全在缓存层死掉，不打 DB |
| 隔离 | 慢接口独立线程池；快接口用信号量隔离（50） | 一只爬虫拖死一个接口，不拖死全站线程池 |
| DB | 连接池 20/实例、慢查询 1s kill、列表读走从库 | 最后一道兜底，连接耗尽是全站不可用的真因 |

> **压强口径**：2500 并发哪怕只有 10% 在途慢请求就是 250 个 DB 连接需求，连接池瞬间耗尽 → 线程全阻塞在等连接 → 网关工作线程跟着占满。所以"服务器负载过高"的真身往往是**连接耗尽 + 线程阻塞**，不是 CPU。

---

## 2. 再抓虫：把爬虫从合法高频里挑出来

**头号陷阱：高频 ≠ 爬虫。** 机构客户批量对账、内部服务互调都会合法冲高。只按 QPS 封，封掉的必然是大客户。判据是**多维信号 + 行为特征**，不是单一阈值。

| 维度 | 【实证·现状】 | 【设计态 / 通用方案】 |
|------|-------------|---------------------|
| 契约 / 内容 | ① 协议号不存在直接拒（`API不正确，非授权访问`）——扫描器狂扫不存在的编码，一次本地 Map 查询就归零，**零 IO、连身份都不用问** | 路径穿越、未声明字段、参数连续失败 |
| 频率 | `RiskProcessor` 可做频率维度拦截；三级配额（租户/应用/接口）为设计态 | 令牌桶分级计数、429 超限 |
| 地域 / 设备 | `RiskProcessor` 地域 + 设备维度拦截 | 同 IP 切多账号、异地并发、IP 信誉库（通用） |
| 行为 | `RiskProcessor` 行为维度拦截；重复提交靠 `ReentrantLock(api_tokenId)` + Greencard 幂等卡（≤4 次复用） | **请求间隔毫秒级等距**（脚本特征，真人不会）——设计态行为信号 |
| 专项反爬 | **无**，项目里没有专项组件 | 验证码、UA 指纹、JS 挑战、WAF（通用方案，本人无实战） |

**两条保命纪律**：

1. **参数校验失败率突增先查自己人**——契约健康度看板的典型判读是"前端/调用方变更未同步"，不是攻击。上来就封爬虫，很可能封的是刚改了字段名的自家前端。
2. **单信号只告警，双信号同时成立才自动处置**（设计态）；现状的"可回退"是每道校验的**全局开关 + 协议级 Map**，能按协议快速关掉，不是自动解封那套。

## 3. 隔离与兜底：不让一只爬虫拖垮全站

| 措施 | 【实证·现状】 | 【设计态】 |
|------|-------------|-----------|
| 全站止血 | `SysPara["40310"]=1` 一键熔断（发版维护用，提示语 `40311` 可配） | midmon 🟡观察→🟠预警→🔴熔断；慢调用 ≥50%（10s/20 请求）触发，熔断 5s + 半开探针 3 个 |
| 舱壁隔离 | 慢接口独立线程池（当晚四步之一）；`APISTYLE=inner` 内部协议隔离 | 按协议分域线程池（方案二，暂不排期）：一域一池一连接一分配额，域之间不借线程 |
| 降级行为 | 系统升级统一提示页 | 降级页 / 兜底数据，不放流量过去 |
| 留痕 | `1018_APP_LOG` 记谁/何时/什么协议/结果/IP | 误伤申诉数 > 0 即复盘、灰度观察期、阈值按实测校准 |

> **纪律**：midmon 只报告不执行，动作全由 midservice 落——监控挂了不影响交易，限流策略永远只有一个执行点。

---

## 4. 防复发：把止血手法固化成红线

面试官问"怎么保证下次爬虫再来不出事"，答案在规范层：

- **容量申报**：新接口上线前报 QPS 预估、RT 预算、SQL 条数预算，压测过再上；
- **缓存红线**：读接口 QPS > 100 必须有缓存层，命中率进看板（爬虫重复读的天然解药）；
- **扩容红线**：任何横向扩容前先核 DB 出口容量——新增实例 × 连接池 ≤ `max_connections` 配额，放行 QPS ≤ DB 上限的 60%，写进 SOP；
- **全链路压测常态化**：扩容 / 高峰前必跑，限流数值按压测和命中率逐步校准。

## 5. 项目版 90 秒速答

> 我先把问题拆成两件：抓爬虫是安全层，负载过高是容量层。真把服务器打挂的都是容量问题——我们出过一次网关横扩 5 个实例把 DB 打穿，入口 ×5 出口没变也没闸门。当晚四步止血：慢接口限流 200 QPS 加 1s 超时、热点缓存 30s 做到 90% 命中、慢接口独立线程池做舱壁、每实例连接池卡 20。数值是利特尔法则反推的示例基线，不是实测。
>
> 识别爬虫这层，我们现状靠两样：一是协议号防伪，扫描器扫不存在的编码在契约关一次本地查询就被拒，零 IO；二是 `RiskProcessor` 做频率、地域、设备、行为四维拦截，重复提交靠幂等卡和锁。**高频不等于爬虫**，机构客户批量对账也可能冲高，所以靠多维信号不靠单一 QPS。
>
> 兜底有 `SysPara["40310"]` 一键熔断，发版维护时切提示页；每道校验有全局开关加协议级 Map，能按协议灰度回退。验证码、UA 指纹、IP 信誉库这些专项反爬我们没做，是通用方案，我不会说成自己做过。

## 6. 追问预案（带证据等级）

| 追问 | 回答要点 |
|------|---------|
| 你们有专门的反爬系统吗？ | 【通用方案】没有；现状是协议号防伪 + `RiskProcessor` 四维，专项反爬属外部知识对照 |
| "高频"怎么定阈值？ | 【设计态】三级配额按租户/应用/接口分层，实测分布校准；【实证】不给单一 QPS 阈值，机构客户合法冲高必须留余量 |
| 封 IP 会不会误伤？ | 【设计态】双信号才处置、白名单豁免、误伤数 > 0 即复盘；【实证】现状靠配置开关灰度回退 |
| 限流的 200 QPS 怎么来的？ | 利特尔法则反推：DB 安全吞吐 ≈230 QPS，按 60% 水位放行 200；**示例基线非实测**，以压测为准 |
| 爬虫专打一个慢接口怎么办？ | 【实证】当晚四步里的慢接口独立线程池 + 200 QPS 限流；【设计态】按协议分域池与连接池（方案二，暂不排期） |
| 缓存会不会被爬虫打穿？ | 【实证】热点缓存 30s + 预热、命中 ≥90% → 回源 ≤20 QPS；穿透用空值缓存 + 布隆过滤器（通用） |
| 限流放不进来的请求怎么回？ | 【设计态】429 + "系统繁忙，请稍后重试"；【实证】现状走 `HandlerException` + 统一错误码信封，不做 429 文案 |
| 多实例计数不准怎么办？ | 【设计态】集中式令牌桶准但每请求一次 Redis 往返，分片桶省 Redis 但故障要重分片；判据是**限流保护什么**——保护 DB 可容误差，计量计费走独立高精度通道 |
