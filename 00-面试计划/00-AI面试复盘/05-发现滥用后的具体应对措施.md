# 05 · 发现滥用行为后，采取的具体应对措施有哪些

> **性质**：AI 面试复盘沉淀件（一问一文件）。2026-11-26 收录，同日按真实项目经历改造。
> **原题**：发现滥用行为后，采取的具体措施/应对措施有哪些？

> **证据等级（先分清再说）**
> - 【实证·现状】`HandlerController` 现状能做的处置：① 20 道校验逐道拒绝（各有拒绝码 GB2013~GB2021 等）② `RiskProcessor` 拦截 → `HandlerException("该请求已被拦截！")` ③ `SysPara["40310"]` **全站一键熔断**（发版维护用，提示语 `40311` 可配）④ 用户维度 `ReentrantLock(api_tokenId)` 防重复提交 ⑤ Greencard 幂等卡（失败重试发卡、≤4 次复用）⑥ 审计流 `1018_APP_LOG` 留痕 ⑦ 每道校验「全局开关 + 协议级 Map」可灰度回退。
> - 【设计态】11 号文档的处置阶梯（告警→降速→临时封禁→黑名单）、midmon 三级预警、自动熔断参数（慢调用 ≥50%、5s、半开探针 3 个）、Sentinel/Resilience4j 熔断降级、429 兜底文案——**是方案与规范，不是现状逐条实现**。（生产排查 11 号把熔断列为"中期改进 M1"，说明不是当晚就有的东西。）
> - 【真实事故闭环】网关横扩 5 实例打穿 DB → **当晚四步急救**（限流 200 QPS + 超时 1s、热点缓存 30s、慢接口独立线程池 15/30/100、连接池卡 20）→ 中期熔断降级与 SQL 治理 → 长期规范。这是按真实架构的代表性场景，数值是反推示例基线非实测。

---

## 0. 一句话口径（先背这句）

> 我们现状的处置是四层：**校验层逐道拒绝 + 风控钩子拦截 + 一键熔断止血 + 审计留痕**，每道校验都能按协议灰度开关快速回退；体系上规划的是处置阶梯（告警、降速、临时封禁自动解封、黑名单人工申诉）加 midmon 三级预警与自动熔断——但那套是设计态。真出过的事故是扩容打穿 DB，靠四步急救止血再固化成规范，这个闭环是实证。

---

## 1. 第一层：请求级拒绝（【实证·现状】）

20 道校验各自拒绝，拒绝码可回查：

| 校验 | 拒绝动作 / 拒绝码 |
|------|---------|
| 防重放 | `时间戳为空` / `签名信息错误` / `请求时间与服务器时间差值过大` |
| 协议号防伪 | `API不正确，非授权访问` |
| 身份授权 | `GB2013` 需手机验证码 / `GB2014` 需证书 / `GB2016`/`GB2021` 需认证 / `GB2015` 需签协议 / `GB2017` 会员过期 |
| 机构越权 | `外部机构没有代理该客户的权限` |
| 状态 / 批量 | `客户状态已挂起` / `超过最大执行量` |
| 风控 | `RiskProcessor` 返回 false → `该请求已被拦截！` |

> 现状拒绝走 `HandlerException` + 统一错误码信封，**不做 429 + "系统繁忙"文案**（那是设计态）。

---

## 2. 第二层：主体级处置（现状有限 + 设计态完整）

| 措施 | 【实证·现状】 | 【设计态】 |
|------|-------------|-----------|
| 拦截主体 | `RiskProcessor` 四维（频率/地域/设备/行为），协议级灰度 | IP / 账号 / AppKey 三维度 |
| 降速 / 排队 | 用户维度 `ReentrantLock` 串行化；无专门排队队列 | 队列 100（≈2.5s 容忍） |
| 重复提交 | Greencard 幂等卡（≤4 次复用，超次废弃） | — |
| 临时封禁 | 无自动封禁实证 | 429 + 临时封禁 15 分钟自动解封 |
| 黑名单 | 无 | 人工解封 + 申诉 + 留痕 |
| 防误伤 | 每道校验全局开关 + 协议级 Map，可按协议快速回退 | 双维度信号、白名单豁免、大客户通知值班 |

> 面试被问"封禁阶梯上线了吗"：**没有**，直说设计态；现状的"可回退"体现为配置开关灰度，不是封禁自动解封。

---

## 3. 第三层：全局止血（一键熔断实证 + 自动熔断设计态）

| 措施 | 【实证·现状】 | 【设计态】 |
|------|-------------|-----------|
| 全站降级 | `SysPara["40310"]=1` 一键熔断，提示语 `40311` 可配，**发版维护用** | — |
| 自动熔断 | 无 | midmon 🟡观察→🟠预警→🔴熔断；慢调用比例 ≥ 50%（10s/20 请求）；熔断 5s + 半开探针 3 个 |
| 降级行为 | 系统升级统一提示页 | 降级页 / 兜底数据，不放流量过去 |
| 隔离 | 慢接口独立线程池（当晚四步之一）；`APISTYLE=inner` 内部协议隔离 | 按协议分域线程池（方案二，暂不排期） |
| 超时红线 | 网关 1s > 后端 800ms > DB 500ms（规范） | 同上，设计基线 |

**真实事故闭环（代表性场景，按 05 §5 口径讲）**：

```
网关横扩 5 实例扛 2500 并发 → 流量放大打穿 DB（瓶颈后移）
   ↓ 当晚四步急救
① 慢接口限流 200 QPS + 超时 1s + 兜底文案
② 热点缓存 30s + 预热
③ 慢接口独立线程池 core15/max30/queue100（舱壁隔离）
④ 每实例连接池卡 20
   ↓ 中期
熔断降级（Sentinel/Resilience4j）+ Top10 慢 SQL 治理 + 读写分离
   ↓ 长期规范
容量申报 + SQL 红线 + 扩容前核出口容量
```

> 数值全部是**利特尔法则反推的示例基线，非实测**，以全链路压测为准；被问是否在场如实答（按真实架构复盘 vs 亲自在场）。

## 5. 项目版 90 秒速答

> 发现滥用后我们现状有四层处置：**第一层各道校验逐道拒**，防重放、协议号防伪、身份授权、参数校验都有明确拒绝码；**第二层风控拦截**，`RiskProcessor` 做频率/地域/设备/行为四维拦截，重复提交靠 Greencard 幂等卡；**第三层全局止血**，有 `SysPara["40310"]` 一键熔断，发版维护时直接切提示页；**第四层审计留痕**，`1018_APP_LOG` 记谁、何时、调了什么协议、结果、IP。每道校验都有全局开关加协议级 Map，能按协议灰度快速回退。
>
> 体系上我们规划了完整的处置阶梯——告警、降速、临时封禁自动解封、最重黑名单人工申诉，加 midmon 三级预警和慢调用过半触发自动熔断。但那部分是设计态，我不会说成已经上线。
>
> 真出过的事是网关横扩 5 个实例把 DB 打穿，当晚四步止血：限流、热点缓存、独立线程池、卡连接池，后面固化成容量申报和扩容前核出口容量的规范。这个闭环我是亲历的，**数值是反推的示例基线，不是实测数字**。
