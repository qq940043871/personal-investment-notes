# 13 · 系统现有不足与重新设计：从"哪里不够"到"怎么改、怎么排期"

> **性质**：AI 面试复盘沉淀件（一问一文件）。2026-11-26 收录。这道题是三段式连环追问——① 目前系统存在哪些不足；② 如果重新设计会怎么做；③ 待办任务（改进项）的排期表。三段同属"技术债治理 + 架构演进"一条链，合一篇讲透。
> **原题**：目前系统存在的不足之处，如何重新设计会怎么做？待办任务的排期表。
> **角色**：Java 侧负责人 / 后期技术经理 —— 改进项的设计与排期我是主导者；讲"不足"要诚实、讲"重做"要有取舍、讲"排期"要有优先级依据。

> **证据等级（先分清再说，否则就是背教材）**
> - 【实证·源码级】= `14-HandlerController` §十一 列出的 11 条改进点、`安全防护与熔断限流汇总` 第二部分"现状 vs 目标"的短板：路由 O(n)、2581 行单类、MD5 防伪是混淆非认证、AES-CBC 用 Key 当 IV、硬编码协议号、`lockMap` 无淘汰、`catch(Throwable)`、SQL 关键字 contains 判断、配置不热更新、DS 协议号魔法值；现状只有人工全站熔断开关（`SysPara 40310`）+ 批量数量上限，**无自动熔断 / 无 QPS 限流 / 无舱壁**。
> - 【设计口径·已整改】= `04-技术管理/01-技术整改十一项与落地.html`：我主导的 11 项专项整改（统一开放网关、等保+信创、数据契约、开发规范脚手架+AI 提效等），每项按"背景问题→方案设计→落地效果"三段式——**这是已做的事，不是待办**。
> - 【规划·重做假设】= `02-项目叙事-B2B.md` §"重新做会怎么改"的两条：契约注册表更早落地、DS 编解码更早抽独立模块 + "业务线程只做纯内存操作"铁律。**面试说"我会怎么改"时用，别说成已改**。
> - 【口径限定】= 排期表的"人日/工期/优先级"是**面试里的方案示例，不是真实项目台账**；被追问就说"这是按价值/风险排序的改进计划口径，不是我当时的实际排期表"。

> **讲法纪律**：讲不足**主动分层**（安全合规 / 稳定性 / 可维护性 / 性能），别散着列举；讲重做要讲"更早做 X"而不是"推倒重来"；讲排期必须给**优先级依据**（安全合规 > 资金安全 > 稳定性 > 可维护性 > 性能），否则就是拍脑袋。

## 0. 一句话口径（先背这句）

> 系统的不足我不逃避，但**按层次讲**——安全合规（MD5 防伪是混淆、AES-CBC 的 IV 用法不合规）、稳定性（无自动熔断/QPS 限流/舱壁，慢协议会横向扩散）、可维护性（2581 行单类、硬编码协议号、配置不热更新）、性能（路由 O(n)、SQL 关键字 contains 误判）。重新设计不是推倒重来，是**把当初"先跑起来"欠下的债按价值补上**：契约注册表更早落地、编解码更早抽离成模块并钉死"业务线程只做纯内存操作"铁律。排期按"安全合规 > 资金安全 > 稳定性 > 可维护性 > 性能"分 P0/P1/P2——**先止血、再固本、后优化**。

## 1. 先定调：怎么答"系统不足"才不翻车

> 两个极端都不能踩：**"我们系统挺好的没什么不足"**（面试官直接判定你没反思）；**"一堆问题如数家珍"**（暴露你维护的系统千疮百孔，或者显得在甩锅）。正确姿势：**承认不足 + 说清当时为什么这么取舍 + 给出演进路径**。三句话结构：

> "这些不足大部分是**特定阶段的取舍**——早期要快速交付可用能力，先把契约、隔离这些'底座'往后放；业务跑起来后，我按价值/风险排序逐步补。**不是没意识到，是分阶段还债。**"

### 1.1 不足分层（这是这题的骨架，散着列会显得没结构）

| 层 | 具体不足 | 为什么当初这么取舍 | 风险等级 |
|---|---|---|---|
| **安全合规** | MD5 首尾拼接防伪是"混淆"非"认证"；AES-CBC 用 `aesKey.getBytes()` 同时当 Key 和 IV（不符合 CBC 语义）；SQL 关键字用 `contains` 判断（误判+漏判） | 早期快速上线，用了简单实现 | 高（合规/攻击面） |
| **资金安全** | 硬编码审计协议号（MT1100 等 6 个）；`catch(Throwable)` 吞 `Error` | 审计点少时硬编码可接受 | 高（漏审/吞错） |
| **稳定性** | 无自动熔断/三态探针、无 QPS 限流、无舱壁隔离；慢协议与快协议共享 Tomcat 线程池 + 三处全局锁，`DSUtils.getClient()` 是 `static synchronized`（135 个调用点） | 早期流量小，共享资源够用 | 高（故障横向扩散） |
| **可维护性** | 2581 行单类、`handle()/execute()` 过长；DS 协议号是 `byte[]` 魔法值（如 `{1,114,16,5}`）；配置启动加载、不热更新；`lockMap` 无淘汰（内存泄漏风险） | 单体起步成本最低 | 中（迭代成本/内存泄漏） |
| **性能** | 路由查找 `for` 遍历 List O(n)；`StringUtils.notEmpty(new String[]{...})` 反编译产物 | 数据量小时 O(n) 无感 | 中低（千级才成瓶颈） |

**讲法要点**：先抛这张分层表（5 层），再挑 2–3 个展开，**展开的一定是"我能讲出根因和改法"的**，别每层都点到为止。

## 2. 第二问：如果重新设计会怎么做

> 面试官问"重新做会怎么改"，考的是**你能不能分清"当初的合理取舍"和"真正该早点做的基础设施"**。答案不是"全部重写"——那是最差答案，既否定了自己又显得不计成本。

### 2.1 库里的两条权威答案（先背这两条，这是"标准答案"）

1. **网关契约注册表想更早落地**——早期接口各自为政，靠协议号逐一收敛；契约注册表应该在地基阶段就建，后期靠它收敛历史债代价很高。
2. **DS 编解码更早抽成独立模块 + 钉死铁律**——明确"业务线程只做纯内存操作、编解码固定在 IO 线程"，避免后来在 IO 线程里写序列化、也避免业务线程被序列化拖慢。

### 2.2 按层给出"重做时我会更早做"的清单（这是加分展开）

| 层 | 如果重来我会更早做 | 解决哪个不足 |
|---|---|---|
| 安全合规 | 用 HMAC-SHA256 对 whole-body 签名替代 MD5 混淆；IV 随机生成并随报文传输；SQL 关键字判定改用 JSQLParser 或持久层异常类型 | MD5 混淆、IV 不合规、contains 误判 |
| 资金安全 | 审计协议号在 `api.json` 加 `AUDIT_FLAG` / `SECURITY_LEVEL` 配置化；`catch (Exception)` 而非 `Throwable`，`Error` 单独处理 | 硬编码审计点、吞 Error |
| 稳定性 | 一开始就把**舱壁 + 熔断 + 异步化**作为地基（四支柱），不让慢协议和快协议共享线程池与全局锁 | 故障横向扩散 |
| 可维护性 | 网关按 `ProtocolDecoder / SecurityFilterChain / ParamValidator / ResponseAssembler / AuditLogger` 拆分，校验用**责任链 + 注解配置**；接配置中心（Apollo/Nacos）+ 文件 Watcher 做热更新；DS 协议号抽枚举/常量类 | 单类过大、配置不热更新、魔法值 |
| 性能 | 路由用 `Map<api, router>` + `Map<restfull, router>` 双索引 O(1)；`lockMap` 改 `ConcurrentHashMap` + 过期清理或 Caffeine | 路由 O(n)、内存泄漏 |

### 2.3 一句收口（把"重做"讲成演进，不是否定过去）

> "所以'重新设计'不是推翻重写——那些底座（契约注册表、编解码分层、舱壁隔离）**在早期做成本最低、越晚补代价越高**。我的反思是：**先跑起来没错，但地基要一开始留好位置。**"

## 3. 第三问：待办任务排期表（P0 / P1 / P2）

> **排期依据**（这是这题的命门，必须讲出来）：不是按"哪个容易改"，是按 **价值 / 风险排序**——`安全合规 > 资金安全 > 稳定性 > 可维护性 > 性能`。债务按"先止血、再固本、后优化"三期还。
>
> ⚠️ **口径**：下表是**面试里的改进计划示例**，工期是人日量级估算，不是真实项目台账；被追问就如实说"这是方案口径，不是我当时的实际排期表"。

### 3.1 P0 · 止血期（安全 + 资金，最高优先级）

| 改进项 | 所属层 | 动作 | 估时 |
|---|---|---|---|
| 审计协议号配置化 | 资金安全 | `api.json` 加 `AUDIT_FLAG` / `SECURITY_LEVEL`，替换 6 个硬编码 | 2–3 人日 |
| `catch(Throwable)` → `catch(Exception)` | 资金安全 | `Error` 单独处理，防吞致命错误 | 1 人日 |
| AES-CBC 的 IV 修正 | 安全合规 | IV 随机生成并随报文传输，Key/IV 分离 | 2–3 人日 |
| HMAC-SHA256 whole-body 签名 | 安全合规 | 替代 MD5 首尾拼接防伪 | 3–5 人日 |
| SQL 判定改造 | 安全合规 | JSQLParser 或持久层异常类型替代 contains | 2–3 人日 |

### 3.2 P1 · 固本期（稳定性 + 可维护性地基）

| 改进项 | 所属层 | 动作 | 估时 |
|---|---|---|---|
| 慢接口独立线程池 + 舱壁隔离（规划，未落地） | 稳定性 | 待实施：core 15 / max 30 / queue 100，与快协议隔离；受 Tomcat 共享线程池约束，需先评估异步化，否则以接口限流 + 连接池隔离替代 | 5–8 人日 |
| 自动熔断三态 + 半开探针 | 稳定性 | CLOSED/OPEN/HALF_OPEN，`slowCallRate + slowCallDuration` 判"慢" | 5–8 人日 |
| 每协议 QPS 令牌桶限流 | 稳定性 | 慢接口全局 200 QPS（利特尔法则反推），单实例 40 | 3–5 人日 |
| 网关按职责拆类 + 责任链校验 | 可维护性 | 拆 5 个组件，校验关卡责任链 + 注解配置 | 10–15 人日 |
| 契约注册表 + 配置中心热更新 | 可维护性 | Apollo/Nacos + 文件 Watcher，改协议免重启 | 8–12 人日 |
| DS 编解码抽独立模块 + 铁律入规约 | 可维护性 | 明确"业务线程只做纯内存操作"并写进 Code Review 清单 | 5–8 人日 |
| `lockMap` 淘汰机制 | 可维护性 | `ConcurrentHashMap` + 过期清理或 Caffeine | 1–2 人日 |

### 3.3 P2 · 优化期（性能，数据量上来才做）

| 改进项 | 所属层 | 动作 | 估时 |
|---|---|---|---|
| 路由双索引 O(1) | 性能 | `Map<api, router>` + `Map<restfull, router>`，千级数据再启动 | 2–3 人日 |
| DS 协议号魔法值抽枚举 | 可维护性 | `{1,114,16,5}` → 常量类 / 枚举 | 2–3 人日 |
| 反编译产物代码清理 | 可维护性 | `StringUtils.notEmpty(new String[]{...})` 改回 varargs | 1 人日 |

### 3.4 排期表的三条讲法（面试官追"为什么这个先做"）

1. **为什么安全/资金排 P0？** 平台是资金链路，一次资损/合规事故的代价远高于性能问题；且这几项改动面小、风险可控，先做性价比最高。
2. **为什么限流熔断排 P1 不是 P0？** 它们依赖隔离做基础——**没有接口级限流与连接池隔离，熔断触发时慢请求照样占着连接池与共享线程**，所以先做接口限流 + 连接池隔离，再做熔断，有依赖顺序。
3. **为什么路由 O(1) 排最后？** 现在协议量级下 O(n) 无感，到千级才是瓶颈；**没有证据就优化是浪费**，等数据量上来再启动。

## 4. 项目版 90 秒速答（直接背）

> 系统不足我按四层讲：安全合规——MD5 防伪是混淆不是认证、AES-CBC 的 IV 用法不合规、SQL 关键字用 contains 判断会误判漏判；稳定性——没有自动熔断、QPS 限流和舱壁，慢协议和快协议共享线程池，会横向扩散；可维护性——2581 行单类、硬编码协议号、配置不热更新；性能——路由 O(n)。这些大部分是早期快速交付的取舍，不是没意识到，是分阶段还债。
>
> 重新设计我不会推倒重写，而是把当初该早点做的基础设施补上：**契约注册表更早落地**、**DS 编解码更早抽独立模块并钉死"业务线程只做纯内存操作"的铁律**，再往上加 HMAC 签名、接口级限流 + 连接池隔离、配置中心热更新。核心是"先跑起来没错，但地基要一开始留位置"。
>
> 排期按价值/风险分三期：**P0 止血**——审计配置化、catch 改 Exception、IV 修正、HMAC 签名、SQL 判定改造；**P1 固本**——接口级限流 + 连接池隔离（舱壁线程池列为规划备选、未落地）、自动熔断三态、QPS 限流、网关拆类、契约注册表+热更新；**P2 优化**——路由双索引、协议号枚举、清理反编译产物。**排序依据是安全合规 > 资金安全 > 稳定性 > 可维护性 > 性能，先止血再固本后优化**——限流熔断必须排在隔离之后，因为没有接口级限流与连接池隔离，熔断触发时慢请求照样占着共享资源。
>
> 收口：**讲不足要诚实但分层，讲重做要讲"更早做 X"而不是推翻，讲排期要给优先级依据——否则就是要么甩锅、要么拍脑袋。**
