## 0. 一句话口径（先记「四分类 + 五句口径」）

### 0.1 网关职责四分类（十道关全收进这四条）

> 记忆口诀：**定规矩 → 验形状 → 挡坏人 → 看得见**

| 分类 | 一句话 | 关键词 |
|------|--------|--------|
| ① **契约**（先定规矩） | 每个接口先有唯一编码 + 入参/出参白名单，全写进契约注册表，**一处定义、四处生效** | 分段编址 `SVC-MOD-IF@版本` |
| ② **校验**（只验形状） | 只验参数"长什么样"，不碰业务；**未定义字段拒绝**；压力参数**显式拒绝不静默截断** | 分页 100 · 跨度 31 天 · 批量 200 |
| ③ **防护**（挡住坏人） | 认证 → 授权 → 三级限流黑名单 → 等保 → 响应兜底脱敏 | 处置阶梯 · 越权防护 · 文件三重校验 |
| ④ **可观测**（看得见） | midmon 多实例：慢协议**看 P95 不看平均**，告警落四元组 | 实例标签 · 请求标识去重 |

**十道关挂靠四分类**（被追问时对号入座，十道关全收）：

| 四分类 | 挂靠的关 | 记忆锚 |
|--------|---------|--------|
| ① 契约 | ① 契约校验 | 接口存在吗 · 入参定义过吗 |
| ② 校验 | ③ 参数预校验 · ④ 压力参数校验 | 形状对不对 · 会不会打疼后端 |
| ③ 防护 | ② 身份 · ⑤ 授权 · ⑥ 限流黑名单 · ⑦ 等保 · ⑩ 响应脱敏 | 谁 → 有权吗 → 恶意吗 → 合规吗 → 别裸奔 |
| ④ 可观测 | 平行维度（midmon 全程采集，不在十道关内） | P95 · 四元组 |
| 转发本职（非治理四分类） | ⑧ 协议缓存 · ⑨ 转发 | 能不打后端就不打 · 送过去要隔离熔断 |

## 1. 90 秒速答（两版，按面试官第一问选一个）

### 1.1 被问"你们的网关是怎么设计的"

> 我们的入口是**自研的 midservice 网关（多实例）+ midmon 监控**。核心原则是**拒绝要早、要便宜**——十道关按拦截成本排序，本地能判的绝不留到远程。
>
> 具体六件事：
>
> 1. **接口（内部叫协议）统一编码**：分段编址 `服务段-模块段-接口段@版本`，一接口一编码、编码不回收、只有破坏性变更才升版本；编码由网关的**契约注册表**统一发放，契约里定义入参、压力参数标记、权限、限流配额、脱敏字段——**一处定义、四处生效**（校验、文档、监控、限流脱敏都从契约读）。
> 2. **入参白名单**：只接收契约定义过的入参，未定义字段**拒绝**而不是忽略，这挡住参数注入和越权赋值。
> 3. **压力参数强制校验**：分页默认上限 100、时间跨度 31 天、批量 200、排序字段白名单；原则是**显式拒绝不做静默截断**——静默截断会让调用方以为拿到全量。
> 4. **限流与黑名单**：租户级/应用级/接口级三级配额，触发源不只是 QPS，还有高频错误、扫描特征、行为异常；处置阶梯是告警→限流→临时封禁 15 分钟（自动解封）→黑名单（人工解封），并做了防误伤。
> 5. **等保侧**：防重放（时间戳 5 分钟窗口 + nonce）、签名防篡改、越权防护（请求里的租户 ID 不可信，只信会话）、文件上传做扩展名 + MIME + 魔数三重校验、服务端重命名、隔离存储、下载走一次性令牌。
> 6. **响应侧**：网关做兜底脱敏，业务层做基于角色的精确脱敏；关键是**输出白名单**——只输出契约声明过的字段，让泄露面不随开发增长。
>
> midmon 解决**多实例可观测**：指标带实例标签、预警看全局聚合、按请求唯一标识去重（traceId 去重属设计态，见 §3）；慢协议预警看 **P95 不看平均值**，告警必须落到**接口编码 + 实例 + 租户 + 下游**四元组，否则不可行动。
>
> 最后一条纪律：**网关只做与业务无关的、横切的、可配置的事**——库存、授信、状态机这些要领域知识的判断，一律下沉业务层。

### 1.2 被问"你们线上出过什么高并发事故"

> 我们中间件网关某些接口慢，整体并发上不去，横向扩到 5 个实例后能扛 2500 并发——**结果几分钟后后端数据库被打死了**。这是典型的**瓶颈后移**：网关扩容是流量放大器，后端直连 DB 是单通道出口，中间没有任何闸门。
>
> 我用利特尔法则算了账：2500 并发哪怕只有 10% 同时在途慢请求就是 250 个 DB 连接需求，远超连接池，连接耗尽 → 线程全部阻塞在等连接 → 网关工作线程跟着占满。
>
> 治理分四层：**入口**给慢接口限流 200 QPS（这个数是反推的，不是拍的）；**应用层**接口级 200 QPS 限流 + 连接池每实例 20 + 快速失败（Tomcat 是共享线程池，做不到按接口独立线程池），写入走 Kafka 削峰；**缓存**Redis 单层缓存（TTL + 随机抖动）做到 90% 命中；**DB** 每实例连接池卡 20、`max_connections` 200、慢查询 1 秒 kill、列表读走从库。
>
> 当晚四步急救：限流、卡连接池 + 快速失败、列表读走从库、热点缓存（Redis 单层），DB 立刻恢复。之后固化成规范：新接口容量申报、SQL 红线、**扩容前先核出口容量**——网关再怎么扩，DB 都是安全的。

## 2. 追问链（每条都要能追到第二层）

### 2.1 十道关的顺序凭什么这样排

| 关 | 拦什么 | 拦截成本 | 为什么在这个位置 |
|:--:|---|---|---|
| ① 契约校验 | 接口存在吗？入参定义过吗 | **本地内存**（注册表本地缓存，零 IO） | 最便宜，**扫描器在这一关就被榨干** |
| ② 接入与身份 | 身份是谁（会话/Token/AppKey 签名） | 一次会话读 | 后面所有判断都要"对谁" |
| ③ 参数预校验 | 形状对不对（类型/长度/格式/枚举） | 本地内存 | 同上，纯本地 |
| ④ 压力参数强制校验 | 会不会打疼后端（分页/跨度/批量） | 本地内存 | 同上，但规则要按接口定制 |
| ⑤ 授权 | 有无权力调这个接口 | 本地计数 + 一次缓存读 | 比 ②③④ 贵，但比转发便宜 |
| ⑥ 频率与信誉 | 恶意/高频（限流 + 黑名单） | 本地计数 + 缓存读 | 要在转发前挡住"合法身份的高频消耗" |
| ⑦ 合规与安全 | 等保要求（防重放/签名/越权/上传） | 一次签名/时间戳计算 | 计算型，放在确定要放行之后 |
| ⑧ 协议缓存 | 能不能不打扰后端 | 一次缓存读 | 命中直接返回，**完全不打后端** |
| ⑨ 转发 | 超时/熔断/隔离/租户路由 | **一次网络调用** | 最贵，前面的关必须把脏流量榨干 |
| ⑩ 响应治理 | 脱敏/统一信封/审计留痕 | 一次序列化 | 出口统一，业务不用各写一遍 |

**一句话收益**：一个扫描器狂扫不存在的接口编码，在 ② 就被拒（连鉴权都不做），一次请求的代价是"查一次本地 Map"。

**改造前痛点（必答）**：早期把参数校验、压力参数、脱敏分散到各业务服务各写一遍 → 同一字段三个服务三种校验、新增接口必漏、改一处改 N 处。网关的意义是**一处定义、处处生效**。

### 2.2 限流数值是怎么定出来的（Little's Law 反推六步）

```
① 在途并发 = QPS × RT
② DB 安全 QPS ≈ 连接数 ÷ SQL 平均 RT × 利用率
```

| 步骤 | 推导 | 结果 |
|:--:|---|---|
| 1 | 未限流时 2500 并发 × 10% 在途慢请求 = 250 在途 | 需 250 个 DB 连接 → 连接池瞬间耗尽 → 线程阻塞 → 网关线程占满（"并发跟不上"的真身） |
| 2 | DB 100 连接 ÷ 0.3s ≈ 333 QPS 理论上限；×0.7 利用率 ≈ 230 QPS 安全吞吐 | **取理论值 60% 水位，放行 200 QPS**（200＜230，再留一档余量） |
| 3 | 200 ÷ 5 实例 | **40 QPS/实例** |
| 4 | 在途 = 40 × 0.3s = 12 | 接口级限流 **40 QPS/实例 + 连接池 20**（Tomcat 共享池，不做独立线程池） |
| 5 | 5 实例 × 20 连接 = 100 ＜ `max_connections` 200（留运维余量 100） | **连接池 20/实例** |
| 6 | 缓存命中率 ≥ 90% → 回源 ≤ 20 QPS | DB 真实负载极低，余量留给突发 |

**必须说的一点**：这是**示例基线，以全链路压测为准**；但推导方法本身就是答案——面试官问"这个数哪来的"，答"利特尔法则 + DB 安全吞吐反推"，比答"经验值"高一个层级。

### 2.3 多实例下限流怎么保证准确

| 方案 | 准确性 | 代价 | 用在 |
|---|---|---|---|
| 集中式令牌桶（Redis） | 准确 | 每次 Redis 往返 | **计量计费必须精确**的场景走独立通道 |
| 分片令牌桶（本地 + 配额分片） | 有误差（约 ±实例数） | 省调用 | **保护 DB** 这类"可容误差"的场景 |

判据一句话：**先问"限流在保护什么"，再选精度**——保护 DB 可容误差，计量计费不能。

### 2.4 三个"为什么不"（标准答案）

| 追问 | 答 |
|---|---|
| 未定义入参为什么拒绝而不是忽略 | 忽略埋雷（前端改字段无人知）；透传是参数注入（`isAdmin`、`tenantId`）；**拒绝是唯一安全选项** |
| 分页 100 是怎么定的 | 入口闸门；与后端 SQL 红线（≤200，白名单接口审批提额）形成**纵深**，不是重复 |
| 为什么不静默截断 | 静默截断 = 数据静默丢失，调用方以为拿到全量；显式拒绝让问题在联调期暴露 |

### 2.5 熔断与隔离的细节

- **熔断参数**：慢调用判据 RT > 500ms；触发条件 = 慢调用比例 ≥ 50% 或异常比例 ≥ 50%（滑动窗口 10s / 20 请求）；熔断 5s，半开探针放 3 个请求试探；降级直接返回兜底页/兜底数据，**不放流量过去**。
- **隔离手段（本系统）**：midservice 跑在内置/外置 Tomcat 的 Servlet 同步模型上，工作线程是共享池，**做不到按接口独立线程池**；实际隔离靠**接口级 200 QPS 限流 + 出向连接池每实例 20 + 快速失败**，再叠加从库分流。
- **通用选型知识（非本系统现状）**：线程池隔离（Bulkhead，一舱进水不沉船）适合能切线程的慢下游；信号量隔离适合快接口、纯缓存路径、不能切线程的调用——这是理论选型，我们受 Tomcat 共享池约束没有落地独立线程池。
- **超时必须逐层递减**：网关 1s ＞ 后端 800ms ＞ DB 500ms。反过来（外层比内层短）会造成"外层已超时、内层还在打 DB"。
- **查询接口不能异步削峰**：查询是同步语义，只能靠"隔离 + 限流 + 缓存"；异步削峰只适用于写入/通知类。

### 2.6 缓存三兄弟（一句话各答一句）

| 问题 | 处置 |
|---|---|
| 穿透（查不存在的数据） | 空值缓存 + 布隆过滤器 |
| 击穿（热点 key 过期瞬间） | singleflight 合并回源 / 逻辑过期异步重建 / 分布式锁 |
| 雪崩（大批 key 同时过期或 Redis 挂） | TTL 加 ±10% 随机抖动 + 限流/熔断兜底（本系统 Redis 单层，无本地多级缓存） |

### 2.7 体系性短板：网关不区分协议（知识按模块划分，资源按平权分配）

> 这是**主动自曝**的一条。被问"你们这套设计还有什么问题"就直接抛它 —— 先说问题（2.7）、再说两个方案（2.8）、最后给触发条件。可信度远高于"我们没有问题"。

**问题一句话**：**编排维度是模块，执行维度是平权**。协议（接口）按 `SVC-MOD-IF@版本` 分段编址、按模块归属治理，系统知识天然是**按模块划分**的；但网关转发侧的**通道连接（工作线程 + 到后端的连接）是一个共享池，不区分协议快慢**，契约里那些分类信息在执行层完全没用上。

**故障形态（慢协议拖死快协议）**：

| 环节 | 现状 | 后果 |
|---|---|---|
| 契约层 | 每个协议都知道自己属于哪个模块、什么语义、什么配额 | 治理粒度是"模块"，**信息是有的** |
| 执行层 | 所有协议共用一个默认线程池 + 连接池 | 执行粒度是"平权"，**信息没用上** |
| 表现 | 慢协议（长事务写入 / 大导出 / 等第三方回执）把共享池占满 | 快协议（查询、开单）排到队尾 → **毫不相关的接口莫名超时** |
| 定位难度 | 单接口监控看全是正常的 | 必须看「实例线程池水位 + 慢协议 RT 分布」才能发现，midmon 的 P95 在这里才有用 |

**和 1.2 那次事故是同一类错误的两层**：那次是**出口（DB）没闸门**，这次是**通道（执行资源）没分区**。共同点——扩容只会把共享资源的争抢放大，所以两者都必须在**扩容之前**先加闸门。

#### 现状：共享的"通道"具体是哪两样东西

先明确部署现实：**midservice 是跑在内置/外置 Tomcat 里的普通 Web 应用，Servlet 同步阻塞模型**，没有 Reactor 事件循环可用。所以"通道"具体是两个共享实体：

| 共享资源 | 传统 Tomcat 下的实体 | 谁控制它 |
|---|---|---|
| 请求通道（线程） | Tomcat 工作线程 `http-nio-*-exec-*`，全协议共用 | `server.tomcat.threads.max` / `accept-count` |
| 出向连接 | 转发用的 `CloseableHttpClient` 全局连接池 | `PoolingHttpClientConnectionManager.setMaxTotal` |

慢协议占满的就是这两样：Tomcat 线程全卡在等下游 → `accept-count` 队列满 → 新请求被拒，现象是"网关整体不响应"，而不是"某个接口慢"。

**Tomcat 侧必说的取舍**：`maxThreads` 才是那张"共享通道"，异步化只是把"占 Tomcat 线程"换成"占业务池线程"，`maxConnections` 仍被慢连接占着。所以真隔离 = **Tomcat 线程池（收请求）+ 业务域池（执行）+ 出向连接池（下游）三层一起分域**；只分一层，只是把瓶颈从 A 挪到 B。

#### 设计中的兜底（未落地）：点对点舱壁五步（治标，不是分区）

> **口径**：以下是**设计稿/规划**，未在现网落地。现网 Tomcat 是共享线程池，做不到按接口独立线程池；本节作为"若将来触发条件命中"的演进方案记录，面试里必须说清"设计了、没实施"。

设想做法：只给"被投诉慢的接口"挂独立线程池—— **L1 池隔离 → L2 线程切换 → L3 连接分域 → L4 拒绝与超时 → L5 指标**。

**L1 池注册表**（配置驱动，未配置落 `default`）：

```java
public final class BizPools {
    static final String DEFAULT = "default";
    private static final Map<String, ThreadPoolExecutor> POOLS = new ConcurrentHashMap<>();

    public static ThreadPoolExecutor of(String group) {
        return POOLS.computeIfAbsent(group == null || group.isBlank() ? DEFAULT : group, BizPools::build);
    }

    private static ThreadPoolExecutor build(String group) {
        PoolCfg c = PoolCfg.load(group);                        // core / max / queue / timeout
        return new ThreadPoolExecutor(
                c.core(), c.max(), 60L, TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(c.queue()),           // 必须有界，否则无限排队 → OOM
                new NamedThreadFactory("biz-" + group + "-"),
                new ThreadPoolExecutor.AbortPolicy());          // 满了显式拒；不用 CallerRuns（会把压力反压回 Tomcat 线程）
    }
}
```

> 同一套手法在设计上规划了后端服务进程内也复制一份（配置基线里那个 `core 15 / max 30 / queue 100` 是设计稿里的慢接口池，**未落地**）——网关侧还要多一层"出向连接池"一起分域。

**L2 网关 Servlet 内切线程 + `AsyncContext` 归还 Tomcat 线程**（关键：切线程放在网关自己的 Servlet 里做完整转发；**不要跨线程继续 `chain.doFilter`**，那在 Tomcat 上属非规范用法，容易出现 `IllegalStateException` / 响应已提交）：

```java
String code  = ProtocolCode.parse(req);                     // SVC-MOD-IF@版本
String group = ContractRegistry.poolGroupOf(code);           // 查不到 → "default"，这就是缺口的来源
ThreadPoolExecutor pool = BizPools.of(group);

AsyncContext ctx = req.startAsync(req, res);
ctx.setTimeout(PoolCfg.load(group).timeoutMs());             // 必须 < 网关对外超时，否则 Tomcat 默认 30s 才回收
CtxSnapshot snap = CtxSnapshot.capture();                    // traceId(MDC) / 租户 / 身份，池化线程必须手工搬运

try {
    pool.execute(() -> {
        snap.restore();
        try { Proxy.forward(req, res, group); }              // 同步调下游，用本域 HttpClient
        catch (Throwable e) { Responses.error(res, e); }
        finally { snap.clear(); ctx.complete(); }            // 成败都要归还，否则连接泄漏
    });
} catch (RejectedExecutionException rejected) {
    res.setHeader("Retry-After", "1");
    Responses.error(res, 503, "SYS_BUSY");                   // 显式拒绝，不静默排队
    ctx.complete();
}
```

**L3 出向连接分域**，否则隔离只做了一半：**每个域一个 `PoolingHttpClientConnectionManager`**，`setMaxTotal` + `setDefaultMaxPerRoute` 按域配额；socket timeout 逐层递减（网关 1s ＞ 后端 800ms ＞ DB 500ms）。只分线程池不分连接池，慢协议仍在抢同一条下游连接。

**L4 拒绝与超时语义**：`AbortPolicy` + 503/`Retry-After`；`AsyncListener.onTimeout` 写 504；真正能掐断阻塞的是业务线程的下游 socket timeout（`future.cancel(true)` 对阻塞 IO 无效）。

**L5 指标**（2.8 的触发条件就靠它，按池名打标签）：

```java
BizPools.all().forEach((group, p) -> {
    midmon.gauge("gw.bizpool.active_pct", p.getActiveCount() * 100L / p.getMaximum(), "pool", group);
    midmon.gauge("gw.bizpool.queue",      p.getQueue().size(),                        "pool", group);
    midmon.counter("gw.bizpool.rejected", rejectedOf(group),                          "pool", group);
});
```

#### 为什么这仍是"点对点"而不是分区方案

三个缺口全是人治：

1. **池名靠人配**：`poolGroup` 在配置里手工填，忘填就落 `default`，新协议默认没人管；
2. **粒度是单协议**：一协议一池，池数随接口数线性涨、线程总量不可控，所以只敢给"被投诉过的那几个"挂池；
3. **判据是热度不是语义**：挂池依据是"有人投诉慢"，而不是"该协议类别本就是批处理/导出"。

所以它是**治标**：够用，但不体系——完备方案见 2.8（演进成本极低，改一个缺省值即可，见方案二的「落地成本低」）。

### 2.8 两个方案：先消除慢，再隔离慢

#### 方案一：慢协议异步化（先受理、后通知）—— 消除慢

- **适用**：语义上允许"先受理、后通知"的协议 —— 批量导入、导出、报表生成、对账文件、对外通知回调。
- **做法**：契约里给协议加 `executionMode = SYNC | ASYNC`；ASYNC 走**受理通道**：契约校验 → 鉴权 → 落任务表（带幂等键）→ **立即返回 202 + taskId**；业务侧由独立消费组执行，完成后回调 / 站内信 / 前端轮询"查任务结果"协议。请求通道只做"受理"这一件 10ms 级的事。
- **收益**：慢协议**不再占用请求通道**，分钟级 RT 塌缩为受理级；顺带白得一份可重试、可审计、可限速的任务台账。
- **代价**：**语义变更**——调用方与前端要改成轮询或回调；要补任务状态机 + 幂等去重；网关要新增任务查询协议。
- **红线**：**查询类永远不能异步**（同步语义，只能靠"隔离 + 限流 + 缓存"，见 2.5 节）；异步只给写入 / 通知 / 批处理。

#### 方案二：按协议分域线程池（真舱壁）—— 隔离慢

- **做法**：契约里给协议打 `协议类别`（查询 / 写入 / 批处理 / 对外回调），网关按类别路由到**各自的线程池 + 各自的后端连接池**；每域独立配额、独立队列、独立超时、独立熔断，**域之间不借线程**。
- **收益**：慢协议最坏情况只打满自己那一域，快协议域不受影响，**爆炸半径从"全站"缩到"一个域"**；容量可以按域用 Little's Law 分域算（2.2 节的方法直接复用）。
- **代价**：池子数 × 实例数，线程总量上升（内存 + 上下文切换）；域间静态切配额会碎片化（一域闲、一域饱和）；每域 core / max / queue 要重新压测校准。
- **落地成本低**：把 `poolGroupOf()` 从"查配置、缺省 `default`"改成"**按契约里的 `协议类别` 派生**（查询→query 域 / 写入→write 域 / 批处理→batch 域），配置只做覆盖"，再按域重压校准 core/max/queue——是改一个缺省值，不是重构。
- **折中**：**只分 3~4 类，不是一协议一池**；未分类协议统一进"兜底域"，防止池子爆炸。

| 维度 | 方案一 异步化 | 方案二 分域池 |
|---|---|---|
| 解决什么 | **消除**慢请求对通道的占用 | **隔离**慢请求的影响范围 |
| 改动面 | 大（契约 + 调用方 + 前端 + 任务台账） | 中（网关路由 + 契约打标 + 压测重校） |
| 见效 | 慢协议 RT 从分钟级降到受理级 | 快协议不再被拖，爆炸半径缩小 |
| 前提 | 语义允许"先受理后通知" | 能接受线程总量与配额碎片化 |
| 顺序 | **先做这个** | 异步覆盖不到的兜底 |

**顺序不能反**：**先异步消灭慢，再分域隔离剩下的慢**——分域只是隔离，异步才是消除。语义上不允许异步的（同步查询、必须同步返回的写入）才靠分域兜。

**什么时候必须做（三条可量化触发条件，命中任一再排期）**：

1. 共享池水位 P95 > 60%，或线上出现"线程池拒绝/队列满"的错误码（靠 2.7 的 L5 指标）；
2. 快协议 RT 与慢协议 QPS 出现**正相关**（说明已经在互相踩）；
3. 批处理 / 导出类协议超过 5 个，或单实例线程占用 > 50%。

**当下的口径**：**已知短板、方案明确、暂不排期**——现有体量下慢协议占比低、默认池水位常态远未打满，先记账进容量申报清单，等触发条件命中再动。面试里这句比"我们很完美"强得多：它证明你能**自己发现体系缺陷、量化它、给它定优先级**，而不是等故障来教你。

## 3. 全链路追踪方案（traceId：网关生成 → 全链路透传 → 按 traceId 查询）

> **口径说明**：需求里的 `traeId` 即业界通用的 `traceId`（拼写差异），全文统一 `traceId`。
> **本件定位**：这是**设计过、P0 未实施**的能力。现状是"**有指标、没链路**"——能说出哪类协议慢，说不出这一笔慢在谁身上。

### 3.1 现状盘点：先划清边界（别把"已有"说成"已实现"）

| 能力 | 现状 | 缺口 |
|---|---|---|
| traceId 生成 | **无**。`HandlerController.execute` 只在 `startTime/endTime` 处算 `COST_TIME`，上报 `1018_MONITOR_DATA`（STARTTIME / ENDTIME / API / RESULT / MSG / COST_TIME / MACHINE_IP） | 一笔请求没有唯一标识 |
| 响应信封 | 已设计 `code / message / data / timestamp / traceId` | 字段在、值没落地 |
| 指标（midmon） | 按 **协议 × 实例 × 窗口** 聚合，已有多实例聚合与 P95 预警 | 聚合是"维度视图"，不是"单笔视图" |
| 日志 | 各服务各写，文本格式，无统一字段 | 无 traceId 列、无法跨机器关联 |
| 异步 / 异构 | Kafka 削峰、DS→C 撮合桥接 | traceId 在消息边界与 IPC 边界**断链** |
| 查询 | 只能按接口 + 时间去 Redis / 日志文件里捞 | 不能用一笔请求反查全链路 |

**一句话判据**：**指标回答"哪类接口慢"，追踪回答"这一笔慢在哪一跳"** —— 现在只有前者。

### 3.2 生成、表示与透传（要求 ①）

#### 三 ID 分工（只有一个 traceId 是拼不出调用树的）

| 字段 | 长度 | 谁生成 | 生命周期 | 作用 |
|---|---|---|---|---|
| `traceId` | 32 hex | **网关入口唯一生成** | 全链路不变 | 串联同一笔请求的所有日志 |
| `spanId` | 16 hex | 每一跳（含网关、每个服务） | 单跳 | 标识"一跳" |
| `parentSpanId` | 16 hex | 上游 spanId 传下来 | 单跳 | 还原调用树、算自身耗时 |
| `bizNo` | 业务单号 | 业务层 | 业务生命周期 | 反向查询（订单号 / 合同号 → traceId） |

> 只有 traceId 时你知道"这 20 行属于同一笔"，但不知道"谁调谁、谁慢"；`parentSpanId` 才能拼瀑布图。**span 不需要引入完整 APM，只要"进出成对"。**

#### 格式：兼容 W3C Trace Context（别自造协议）

```
traceparent: 00-{traceId 32hex}-{spanId 16hex}-01
             版本            父 ID          采样标记（01 采样 / 00 不采样）
```

同时**冗余**一个 `X-Trace-Id`（纯 traceId）：因为客服工单、第三方、老系统只会贴一个 ID，且 ES 里聚合时不用解析前缀。**双写是迁移期成本最低的做法**，后续可只留 `traceparent`。

#### 生成规则（含防伪造）

```java
// 网关第一关（放在契约校验之前，任何拒绝都要能带回 traceId）
public static TraceCtx start(HttpServletRequest req) {
    String tp = req.getHeader("traceparent");
    boolean trusted = TrustedApp.isInternal(req);          // 只信内部/白名单来源
    TraceCtx ctx = (trusted && tp != null) ? TraceCtx.parse(tp) : null;
    if (ctx == null) ctx = TraceCtx.root();                // 无 / 非法 / 不可信 → 重新生成
    MDC.put("traceId", ctx.traceId());
    MDC.put("spanId",  ctx.spanId());
    return ctx;                                            // 调用方 finally 必清
}
```

- **算法**：`时间戳(48bit) + 实例IP(32bit) + 序列号(16bit) + 随机(32bit)` 拼 32 hex。好处是**能从 traceId 反推大致时间与实例**，日志缺段时救命；`UUID` 去横线更简单但丢了信息。
- **必须重新生成的两类**：① 来源不可信却带了 traceparent —— 防伪造串链、防日志注入（与"租户 ID 只信会话"同一条纪律）；② 格式非法 / 缺 spanId。
- **生成点唯一**：只在网关生成。业务服务**只继承不生成**（无 traceId 时才补一个并打 `orphan=true` 标记，用于自查漏透传）。

#### 四条透传通道（缺一条就断链）

| 通道 | 载体 | 落地方式 |
|---|---|---|
| HTTP 同步调用 | `traceparent` + `X-Trace-Id` + `X-Span-Id` | 网关转发处注入；服务间用 `RestTemplate`/`HttpClient` **拦截器自动注入**，禁止手写 |
| 线程内 | MDC：`traceId / spanId / tenantId / protocolCode` | Servlet Filter `MDC.put` → `finally` 必清（线程池复用会串日志） |
| 线程池 / 异步 | 任务包装时捕获 + 还原 | 复用 2.7 的 `CtxSnapshot`，**不要写两套上下文搬运** |
| Kafka 消息 | 消息 header `traceparent` | 生产端 `ProducerInterceptor` 写入；消费端 `RecordInterceptor` 取出再 `MDC.put` |

**异构段单独说（最容易被追问）**：C 撮合没有 MDC / 线程上下文概念，改造成本高，所以只要求两件事——① 报文头扩展位带 traceId 并**原样回传**；② C 侧日志模板加一列 `[trace=...]`。做不到就退化成"**时间窗 + 会话号 + 业务单号**"三要素关联，并在查询页显式标注该段为"**弱关联**"。诚实标弱，比假装全链路强。

### 3.3 落点、采集、聚合与关联（要求 ②）

**先定落点：traceId 本身不落库，落的是"关于它的三类记录"**

| 记录 | 存储 | 保留 | 用途 |
|---|---|---|---|
| 网关访问日志 | Kafka → ES `gw-access-*` | 90 天 | 全链路根记录，条数最全（含被拒绝的请求） |
| 服务 span 进出对 | Kafka → ES `app-trace-*` | 30 天 | 拼瀑布图 |
| 链路索引表 | MySQL `trace_index`（traceId, bizNo, protocol, tenant, start, status, totalMs, spanCount） | 1 年 | 快查 + 按业务单号反查，**不让 ES 承担主键查询** |

**采集链路**：应用 → 异步 appender 落本地 JSON → Filebeat/Vector → Kafka（**按 traceId hash 分区**）→ 消费者批量 bulk 写 ES。

| 设计点 | 做法 | 理由 |
|---|---|---|
| 分区键 | 按 `traceId` hash | 同一笔的所有日志进同一分区，消费侧可流式算 span 数、总耗时、**是否缺段**；代价是大 trace 热点，靠"Kafka 只做 3~5 分钟缓冲、不做长期存储"化解 |
| 时间基准 | 统一 NTP，`@timestamp` 用**服务端时间** | 客户端时间不可信，窗口一错瀑布图就成倒挂 |
| ES mapping | `traceId/spanId` 必须 `keyword` | `text` 会分词，精确查询与聚合全部失效（最常见的翻车点） |
| 索引 | 按天滚动 `app-trace-2026.11.23` | 冷热分层、按需删、限时间范围查询 |
| 写入路由 | `_routing = traceId` | 同链路落同一 shard，按 traceId 查只打 **1 个 shard**，这是查询快的根因 |
| 关联三要素 | 同一 traceId（串联）+ spanId/parentSpanId（还原树）+ 服务端时间（排序） | 只靠"日志都在一个库"是关联不了的 |

**三档分离，别把日志当指标用**：

| 数据 | 采样 | 用途 |
|---|---|---|
| 指标（midmon 聚合） | **全量，不采样** | 发现异常：哪类协议、哪个实例、什么水位 |
| 链路 span | 入口 **10%** + 错误/慢请求整条打标 | 定位单笔 |
| 业务日志 | 不采样，但按级别控量（INFO ≤ 5 条/请求） | 还原现场 |

> **采样铁律**：采样决策在**入口一次定**并写进 `traceparent` 最后两位，下游无条件跟随。中途各采各的，链路必然缺段。慢/错请求的"全采"只能在网关自己这层保证（下游已经发生的没采就回不来），所以口径是"**入口 10% + 慢/错请求整条打标并强制保留网关段**"。

### 3.4 日志规范与埋点标准（要求 ③）

**统一 JSON、一行一条**（禁止多行堆栈、禁止字符串拼接拼接出非结构化文本）：

```json
{"ts":"2026-11-23T10:12:33.412+08:00","level":"INFO","service":"order-center","instance":"10.0.0.21:8080",
 "traceId":"4f2a9c...","spanId":"a1b2c3d4e5f60718","parentSpanId":"0f1e2d3c4b5a6978",
 "protocolCode":"ORD-MOD-IF@1","tenantId":"T1001","userId":"U88","bizNo":"HT202611230001",
 "event":"db.query","costMs":182,"result":"OK","errCode":null,"msg":"select contract by id"}
```

| 字段 | 必填 | 规范 |
|---|:--:|---|
| `ts / level / service / instance` | ✓ | `instance` 必带 `IP:端口`，**与 midmon 实例维度同名同值**，否则两边对不上 |
| `traceId / spanId` | ✓ | 根 span 的 `parentSpanId` 用全 0 |
| `protocolCode` | ✓ | 契约编码，与限流 / 脱敏 / 监控用**同一个 key** |
| `tenantId / userId` | ✓ | 只信会话（与越权防护同一条） |
| `event` | ✓ | 枚举：`req.in / req.out / db.query / cache.get / mq.send / mq.recv / rpc.call / biz.step` |
| `costMs / result / errCode` | 出参必填 | `result` 取 `OK / FAIL / TIMEOUT` 三值 |
| `bizNo` | 关键链路必填 | 用于"订单号 → traceId"反查 |

**五条硬规则**：

1. **只允许从 MDC 取** traceId/spanId，禁止业务代码手写 —— 写错一次，链路永久缺一段，而且查不出来。
2. **进出必成对**：每个服务入口 `req.in`、出口 `req.out`（带 costMs），靠 Filter/AOP 自动打，不靠人记。
3. **敏感字段禁落**：与网关脱敏同一套规则（日志是最大的泄露源，等保必查）。
4. **级别语义固定**：ERROR = 要告警 / WARN = 要人看 / INFO = 业务里程碑 / DEBUG = 生产关闭。
5. **埋点三层，能自动不手工**：网关（零埋点）＞ 框架（Filter / Interceptor / AOP）＞ 业务节点（手工只允许 5 类：状态流转、外部调用、慢 DB、缓存未命中、重试）。

### 3.5 查询能力（要求 ④）

**三个入口**：

1. **按 traceId 精确查**（第一入口）：前端报障 / 客服工单 → 信封里的 `traceId` → 时间轴。ES `keyword` + routing，目标 **P99 < 1s**。
2. **按业务单号反查**：`bizNo → traceId` 走 MySQL `trace_index`，再拉 ES 明细（避免全表扫 ES）。
3. **按条件搜**：租户 + 协议 + 时间 + `costMs > X` + `result=FAIL`，回答"这一批失败请求长什么样"。

**展示形态（瀑布图 + 最慢一跳标红）**：

```
traceId 4f2a9c...   总耗时 1423ms   [慢]   FAIL
├─ midservice  gateway          12ms   preHandle / 契约 / 限流
│  └─ order-center  req.in    1180ms
│     ├─ db.query  select ...   182ms
│     ├─ rpc.call  inventory    903ms   ← 最慢一跳（Top1 自动标红）
│     └─ req.out               1181ms
└─ DS→C 段  missing span（弱关联，时间窗兜底）
```

- **先看最慢那一跳**：追踪的价值不是"看到全部日志"，是"不用逐个看日志"。
- **与 midmon 联动**：慢协议预警点进去 → 直接列该协议最近 10 条慢 trace。**从"哪类接口慢"下钻到"这一笔慢在哪"**，这才是闭环。
- 查询优化：按 `startTime` 限定索引范围，别查全部 `app-trace-*`；跨天链路用 `trace_index` 拿准确时间再定位索引。

### 3.6 落地步骤与优先级（要求 ⑤，现状未实现）

| 期 | 内容 | 工期 | 为什么这个优先级 |
|:--:|---|---|---|
| **P0** | 网关生成 traceId → 响应信封回填 → HTTP 全链路透传 → 各服务 Filter 打 MDC + `req.in/req.out` → 日志 JSON 化 → Kafka + ES → 按 traceId 查询 | **2 周** | **这一层就解决 80% 定位问题**；改动全在框架层，业务零侵入 |
| **P1** | Kafka 消息透传、DS→C 弱关联、`bizNo` 索引、瀑布图 + Top1 标红、慢 SQL 加 `/*traceId*/` 注释 | 3~4 周 | 补齐断链点；异构改造成本最高、收益中等，必须放第二 |
| **P2** | 采样与成本治理、日志冷热分层、与 midmon 告警联动下钻、OpenTelemetry 标准化（以后接 SkyWalking / Jaeger 不白做） | 1~2 月 | 规模与成本问题，等量上来再做 |

**排序四条判据**（被问"凭什么这么排"就答这四条）：

1. **先"能查"再"好看"**：traceId 不透传，瀑布图画得再好也是空壳。
2. **先同构再异构**：12 个 Java 服务改一个 Filter 全生效；C 撮合要改报文格式，评审周期就吞掉一个月。
3. **先自动再手工**：埋点一旦靠自觉，三个月后必缺一半。
4. **先全量再采样**：先看清日志量级（GB/天）再定采样率，且采样只在入口定一次。

**成本与边界（诚实补一句）**：全链路追踪 70% 的成本在**存储与运维**（ES 集群 + 索引治理），不在开发。所以口径是"**P0 先做、验证价值再投**"；C 撮合段明确接受"弱关联"，**不承诺 100% 无断点**。

**一句收口**：现状是"有指标、没链路"；方案是**网关一次生成 traceId、四条通道全透传、日志统一 JSON 进 ES、按 traceId 出瀑布图**；落地按"先同构后异构、先自动后手工"排三期，P0 两周见效。
