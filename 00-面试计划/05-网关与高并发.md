## 0. 一句话口径（先记这三句）

1. 入口 = **Java Web 自研 `midservice`（多实例）+ `midmon`**；Nginx / Spring Cloud Gateway / Kong 只是"为什么没选"的对比，**不要说成自家组件**。
2. 设计原则 = **拒绝要早、要便宜**：十道关按"拦截成本"从低到高排，本地能判的绝不留到远程。
3. 扩容 = **流量放大器**，不是解药。出口（DB）容量不变时，**先加闸门再扩容**。

## 1. 90 秒速答（两版，按面试官第一问选一个）

### 1.1 被问"你们的网关是怎么设计的"

> 我们的入口是**自研的 midservice 网关（多实例）+ midmon 监控**。核心原则是**拒绝要早、要便宜**——十道关按拦截成本排序，本地能判的绝不留到远程。
>
> 具体六件事。第一，**接口（内部叫协议）统一编码**：分段编址 `服务段-模块段-接口段@版本`，一接口一编码、编码不回收、只有破坏性变更才升版本；编码由网关的**契约注册表**统一发放，契约里定义入参、压力参数标记、权限、限流配额、脱敏字段——**一处定义、四处生效**（校验、文档、监控、限流脱敏都从契约读）。第二，**入参白名单**：只接收契约定义过的入参，未定义字段**拒绝**而不是忽略，这挡住参数注入和越权赋值。第三，**压力参数强制校验**：分页默认上限 100、时间跨度 31 天、批量 200、排序字段白名单；原则是**显式拒绝不做静默截断**——静默截断会让调用方以为拿到全量。第四，**限流与黑名单**：租户级/应用级/接口级三级配额，触发源不只是 QPS，还有高频错误、扫描特征、行为异常；处置阶梯是告警→限流→临时封禁 15 分钟（自动解封）→黑名单（人工解封），并做了防误伤。第五，**等保侧**：防重放（时间戳 5 分钟窗口 + nonce）、签名防篡改、越权防护（请求里的租户 ID 不可信，只信会话）、文件上传做扩展名 + MIME + 魔数三重校验、服务端重命名、隔离存储、下载走一次性令牌。第六，**响应侧**：网关做兜底脱敏，业务层做基于角色的精确脱敏；关键是**输出白名单**——只输出契约声明过的字段，让泄露面不随开发增长。
>
> midmon 解决**多实例可观测**：指标带实例标签、预警看全局聚合、按 traceId 去重；慢协议预警看 **P95 不看平均值**，告警必须落到**接口编码 + 实例 + 租户 + 下游**四元组，否则不可行动。
>
> 最后一条纪律：**网关只做与业务无关的、横切的、可配置的事**——库存、授信、状态机这些要领域知识的判断，一律下沉业务层。

### 1.2 被问"你们线上出过什么高并发事故"

> 我们中间件网关某些接口慢，整体并发上不去，横向扩到 5 个实例后能扛 2500 并发——**结果几分钟后后端数据库被打死了**。这是典型的**瓶颈后移**：网关扩容是流量放大器，后端直连 DB 是单通道出口，中间没有任何闸门。
>
> 我用利特尔法则算了账：2500 并发哪怕只有 10% 同时在途慢请求就是 250 个 DB 连接需求，远超连接池，连接耗尽 → 线程全部阻塞在等连接 → 网关工作线程跟着占满。
>
> 治理分四层：**入口**给慢接口限流 200 QPS（这个数是反推的，不是拍的）；**应用层**慢接口独立线程池做舱壁隔离 + 写入走内存队列恒速削峰；**缓存**本地 30s + Redis 做到 90% 命中；**DB** 每实例连接池卡 20、`max_connections` 200、慢查询 1 秒 kill、列表读走从库。
>
> 当晚四步急救：限流、独立线程池、卡连接池、热点缓存，DB 立刻恢复。之后固化成规范：新接口容量申报、SQL 红线、**扩容前先核出口容量**——网关再怎么扩，DB 都是安全的。

## 2. 追问链（每条都要能追到第二层）

### 2.1 十道关的顺序凭什么这样排

| 关 | 拦什么 | 拦截成本 | 为什么在这个位置 |
|:--:|---|---|---|
| ① 接入与身份 | 身份是谁（会话/Token/AppKey 签名） | 一次会话读 | 后面所有判断都要"对谁" |
| ② 契约校验 | 接口存在吗？入参定义过吗 | **本地内存**（注册表本地缓存，零 IO） | 最便宜，**扫描器在这一关就被榨干** |
| ③ 参数预校验 | 形状对不对（类型/长度/格式/枚举） | 本地内存 | 同上，纯本地 |
| ④ 压力参数强制校验 | 会不会打疼后端（分页/跨度/批量） | 本地内存 | 同上，但规则要按接口定制 |
| ⑤ 授权 | 有无权力调这个接口 | 本地计数 + 一次缓存读 | 比 ②③④ 贵，但比转发便宜 |
| ⑥ 频率与信誉 | 恶意/高频（限流 + 黑名单） | 本地计数 + 缓存读 | 要在转发前挡住"合法身份的高频消耗" |
| ⑦ 合规与安全 | 等保要求（防重放/签名/越权/上传） | 一次签名/时间戳计算 | 计算型，放在确定要放行之后 |
| ⑧ 协议缓存 | 能不能不打扰后端 | 一次缓存读 | 命中直接返回，**完全不打后端** |
| ⑨ 转发 | 超时/熔断/隔离/租户路由 | **一次网络调用** | 最贵，前面的关必须把脏流量榨干 |
| ⑩ 响应治理 | 脱敏/统一信封/审计留痕 | 一次序列化 | 出口统一，业务不用各写一遍 |

**一句话收益**：一个扫描器狂扫不存在的接口编码，在 ② 就被拒（连鉴权都不做），一次请求的代价是"查一次本地 Map"。

**反面清单（必答）**：早期把参数校验、压力参数、脱敏分散到各业务服务各写一遍 → 同一字段三个服务三种校验、新增接口必漏、改一处改 N 处。网关的意义是**一处定义、处处生效**。

### 2.2 限流数值是怎么定出来的（Little's Law 反推六步）

```
① 在途并发 = QPS × RT
② DB 安全 QPS ≈ 连接数 ÷ SQL 平均 RT × 利用率
```

| 步骤 | 推导 | 结果 |
|:--:|---|---|
| 1 | 未限流时 2500 并发 × 10% 在途慢请求 = 250 在途 | 需 250 个 DB 连接 → 连接池瞬间耗尽 → 线程阻塞 → 网关线程占满（"并发跟不上"的真身） |
| 2 | DB 100 连接 ÷ 0.3s × 0.7 ≈ 230 QPS，取 60% 水位 | **放行 200 QPS** |
| 3 | 200 ÷ 5 实例 | **40 QPS/实例** |
| 4 | 在途 = 40 × 0.3s = 12 | 线程池 **core 15 / max 30 / queue 100** |
| 5 | 5 实例 × 20 连接 = 100 ＜ `max_connections` 200（留运维余量 100） | **连接池 20/实例** |
| 6 | 缓存命中率 ≥ 90% → 回源 ≤ 20 QPS | DB 真实负载极低，余量留给突发 |

**必须说的一点**：这是**示例基线，以全链路压测为准**；但推导方法本身就是答案——面试官问"这个数哪来的"，答"利特尔法则 + DB 安全吞吐反推"，比答"经验值"高一个层级。

### 2.3 多实例下限流怎么保证准确

| 方案 | 准确性 | 代价 | 用在 |
|---|---|---|---|
| 集中式令牌桶（Redis） | 准确 | 每次 Redis 往返 | **计量计费必须精确**的场景走独立通道 |
| 分片令牌桶（本地 + 配额分片） | 有误差（约 ±实例数） | 省调用 | **保护 DB** 这类"可容误差"的场景 |

判据一句话：**先问"限流在保护什么"，再选精度**——保护 DB 可容误差，计量计费不能。

### 2.4 三个"为什么不"，答错就露馅

| 追问 | 答 |
|---|---|
| 未定义入参为什么拒绝而不是忽略 | 忽略埋雷（前端改字段无人知）；透传是参数注入（`isAdmin`、`tenantId`）；**拒绝是唯一安全选项** |
| 分页 100 是怎么定的 | 入口闸门；与后端 SQL 红线（≤200，白名单接口审批提额）形成**纵深**，不是重复 |
| 为什么不静默截断 | 静默截断 = 数据静默丢失，调用方以为拿到全量；显式拒绝让问题在联调期暴露 |

### 2.5 熔断与隔离的细节

- **熔断参数**：慢调用判据 RT > 500ms；触发条件 = 慢调用比例 ≥ 50% 或异常比例 ≥ 50%（滑动窗口 10s / 20 请求）；熔断 5s，半开探针放 3 个请求试探；降级直接返回兜底页/兜底数据，**不放流量过去**。
- **线程池隔离 vs 信号量隔离**：慢接口 / 独立下游用**线程池隔离**（Bulkhead，一舱进水不沉船）；快接口、纯缓存路径、不能切线程的调用用**信号量隔离**。
- **超时必须逐层递减**：网关 1s ＞ 后端 800ms ＞ DB 500ms。反过来（外层比内层短）会造成"外层已超时、内层还在打 DB"。
- **查询接口不能异步削峰**：查询是同步语义，只能靠"隔离 + 限流 + 缓存"；异步削峰只适用于写入/通知类。

### 2.6 缓存三兄弟（一句话各答一句）

| 问题 | 处置 |
|---|---|
| 穿透（查不存在的数据） | 空值缓存 + 布隆过滤器 |
| 击穿（热点 key 过期瞬间） | singleflight 合并回源 / 逻辑过期异步重建 / 分布式锁 |
| 雪崩（大批 key 同时过期或 Redis 挂） | TTL 加 ±10% 随机抖动 + 多级缓存 + 熔断限流兜底 |

## 3. 配置基线（一张表背完，被追问数值就靠它）

| 层 | 参数 | 值 | 推导 |
|---|---|---|---|
| 网关 | 慢接口全局限流 | **200 QPS** | DB 上限 230 × 60% 水位 |
| 网关 | 单实例限流 | **40 QPS** | 全局 ÷ 5 实例 |
| 网关 | 接口超时 | **1s** | ＞ 后端 800ms ＞ DB 500ms |
| 网关 | 熔断 | 慢调用/异常 ≥ 50%，熔断 5s | 滑动窗口 10s / 20 请求 |
| 网关 | 压力参数默认值 | 分页 100（白名单 200）/ 时间跨度 31 天 / 导出 5000 / 批量 200 / IN 元素 100 / 关键词 50 字符 / 树深 5 | 入口闸门，显式拒绝 |
| 网关 | 上传 | 单据 10MB / 图片 5MB | 扩展名 + MIME + 魔数三重校验 |
| 后端 | 慢接口线程池 | core 15 / max 30 / queue 100 | 在途 = 40 × 0.3 = 12 |
| 后端 | 写入削峰队列 | `LinkedBlockingQueue` + 恒速消费 | 消费速度 = DB 安全 QPS |
| 后端 | 连接池 | max 20 / min 5 / timeout 1s | 5 × 20 = 100 |
| 后端 | 单查询条数 | ≤ 200 条，必须 limit | SQL 红线（慢接口 90% 是这四件事之一） |
| 缓存 | L1 本地 | TTL 30s，size 10000 | 热点逃生层 |
| 缓存 | L2 Redis | TTL 5~30min ± 10% 抖动 | 防雪崩 |
| 缓存 | 命中率目标 | ≥ 90% | 回源 ≤ 10% |
| DB | `max_connections` | 200 | Σ连接池 + 运维余量 100 |
| DB | 慢查询 kill | > 1s（pt-kill） | 只承受安全流量 |
| DB | 长事务 | > 5s 告警 + kill | 同上 |

## 5. 翻车红线（说错这三句，前面全白讲）

1. **不要说"我们用的是 Spring Cloud Gateway / Kong / Nginx"** ——会与架构图对不上。正确说法：自研 midservice；通用网关只出现在"为什么没选"的对比里。
2. **不要把秒杀说成自己做的** ——`电商/04` 里写明"通用方案 / 本人无秒杀实战"；要讲就用"如果让我设计"的假设语气。
3. **不要报"平均值"** ——耗时一律 P95/P99，说平均值等于自曝没看过线上大盘。
