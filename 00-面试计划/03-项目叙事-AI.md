## 0. 两版开场

### 30 秒版

> 这是在已有的大宗商品交易平台上加的一层企业级 AI 能力底座，输出智能客服、知识检索、政策解读三类应用，政策解读还有一个电力垂直版。
> 架构是三层：Dify 做智能层（工作流、RAG 管道、Agent），自研业务中台做业务层（统一身份、鉴权、工具网关、审计、token 计量），底层是模型和知识资产。
> 我是前期技术选型和数据链路负责人：做了六路底座选型复盘，主责复杂 PDF 解析改造和文档落向量库这条链路。最近在补的是解析成功率和检索命中率的度量。

### 3 分钟版（背景 → 三层与三个死结 → 我的四件交付 → 一个还能继续追问的难点）

> 业务侧抱怨集中在三件事：政策看不懂甚至看错（政策不是追加新版，而是失效 / 被替代，极易抓到已废止版本）；同一个问题打三次电话（"我的单子到哪一步""这个月用了多少"答案只在业务系统里）；知识散在十几个老员工脑子里。
>
> 这三件事其实对应三类问题：文档类、数据类、混合类。所以架构上必须先分清哪类问题走查文档、哪类走查业务系统——这一步走错，后面 RAG 再准也答不对。
>
> 我负责四件具体的事：一是六路底座选型（Dify / LangChain / 百炼 / FastGPT / RAGFlow / n8n），定出"智能层 + 业务层"分工；二是 MinerU 复杂 PDF 解析改造，四层增强输出统一 Markdown 中间态；三是批量解析的调度与失败兜底，解析失败不能静默丢文档；四是分块与元数据跟向量库对齐，让下游能按文号、章节、页码、有效期过滤。
>
> 最难的一块是政策解读的确定性部分。时效、效力位阶、权限边界、引用真伪这四件事全有法定规则，必须用代码算，不能交给模型猜。比如行政规范性文件有效期一般不超过 5 年、暂行试行不超过 3 年、届满未延续自动失效；还有"已公布尚未施行"这第三种状态，不建模必错。我们做了两道纯代码闸门卡在生成前后。
> 【★ 这里可以主动收一句】编排调优和微调由团队推进，我讲的是我亲手做的那条数据链路。

## 3. 请求链路

### 3.1 主链路：一次政策问答

```
用户提问
  ▼
接入层 ── 身份 / 租户 / 角色权限（权限校验在中台，不在 Prompt 里）
  ▼
意图与范围判定 ── 知识类 / 数据类 / 混合类三分
  │                 · 数据类（"我的单子到哪一步"）直接走中台工具网关，不进 RAG
  ▼
检索侧 ── 第一层：知识库级（向量 / 关键词 / 混合）
  │        第二层：元数据过滤（地域 · 行业 · 文号 · 有效期 · 密级）
  │        → Rerank → 候选池（宁窄勿宽，宽了就是给模型编造的机会）
  ▼
生成侧（Dify Workflow）── 上下文注入 + 强制条款级引用（第 X 条第 Y 款）
  ▼
★ 闸门一（生成前 / 纯代码）── 时效闸门：文件是否废止、是否"已公布尚未施行"
★ 闸门二（生成后 / 纯代码）── 位阶与权限闸门：下位不得否定上位；征求意见稿/内部件不得外发
  ▼
输出 ── 结论 + 依据条款 + 生效状态 + 免责与"以原文为准"
```

**三个必须主动讲清的边界**：

- **确定性的事不交给模型**：有效期、效力位阶、密级权限、引用真伪 —— 全是代码算。只有"翻译成人话"交给模型。看到哪个环节在"让模型自己判断"，那就是事故起点。
- **Dify 不直连业务数据库**：所有数据访问走中台受控工具；权限永远在中台执行，不把过滤责任交给 Prompt。
- **工作流内不写复杂业务逻辑**：只做路由、拼装、调用与格式化。这三条是写进架构规范的硬约束。

### 3.2 失败链路（两条，都要能单独讲）

**A. 解析失败不能静默丢文档**（我负责的这一环）

- 现象：某批政策 PDF 解析超时或产出空 Markdown，文档在库里"消失"却没人知道——这是最坏的一种失败，因为它安静。
- 处置：失败入待办表 + 告警；按类型降级：换后端（pipeline ↔ VLM）/ 转 OCR / 人工处理；保留原文件可重跑；大批量导入可续跑、可重入。
- 验证：抽取集（多栏 / 嵌套表 / 扫描件各若干份）逐份人工比对结构与表格还原。

**B. 检索空结果 / 证据不足**

- 允许"我不知道"：空结果或引用校验失败时，输出"未找到有效依据"并给检索路径，而不是让模型补一段。
- 客服场景则转人工，且交接包带上下文（客户不用重讲一遍）。

## 4. 技术选型（每条都要"候选 / 否决理由 / 代价"）

| 选型 | 当前方案 | 候选与否决理由 | 付出的代价 |
|---|---|---|---|
| 智能层底座 | Dify（社区版私有化二开） | 六路对比：LangChain 自由度高但工程量大、无编排界面；百炼绑定云厂商、私有化受限；FastGPT 做客服问答强但不适合多应用平台；RAGFlow 解析强但编排弱；n8n 是自动化工具不是 LLM 平台 | 社区版二开要跟版本；复杂编排能力有边界；升级需回归 |
| 智能层 / 业务层分工 | Dify 管智能，中台管门禁与总线 | 否决"全交给 Dify"：权限、审计、计量、业务数据访问它管不住；否决"全自研"：编排、RAG 管道、Prompt 管理重造轮子 | 两套系统之间的 API 契约要持续维护；排障跨两套 |
| PDF 解析 | MinerU + 四层增强 | 否决"直接调大模型做 OCR"：成本与稳定性不可控；否决"只换更强模型"：误差分布在图像质量 → 版面检测 → 元素识别 → 顺序还原每一环 | 四层增强引入调参与维护成本；双后端要判页 |
| 解析产物格式 | 统一 Markdown 中间态 | 否决"各解析器产各自格式直入向量库"：换解析器就要动分块与索引 | 中间态有信息损失（表格转 HTML 表、图存对象存储），需保证能回溯原文 |
| 页级路由 | 原生电子版走 pipeline（快）、扫描件/复杂版式走 VLM | 全走 VLM 太慢太贵；全走 pipeline 复杂版式错得多 | 判页错误会两头不讨好（该慢的没慢、该准的不准） |
| 客服答案来源 | 直击库（L0/L1/L2 三层已验证问答）+ RAG + 工具调用 | 否决"纯 RAG"：近一半问题答案不在文档里，纯 RAG 会一本正经地编 | 直击库要持续维护与清洗；三层命中判断增加链路 |
| 政策确定性规则 | 纯代码闸门（Dify Code 节点） | 否决"写进 Prompt 让模型遵守"：模型不保证遵守，且不可回归测试 | 规则要随法规变化维护；规则误杀会挡住正常问题 |

**如果被问"重新做会怎么改"**：

- 解析评测集会从第一天就建。先有基线（哪一类文档成功率多少），后面每改一版才知道是变好还是变坏——没有评测集的优化都是猜。
- 元数据字段会在入库前就定死（文号、章节路径、有效期、密级），而不是等下游要过滤时才补。
- 六路对比会先写"硬约束清单"（私有化、二开、审计、成本）再评分，避免被功能列表带跑。

## 5. 难点（AI 项目没有"故障"就先讲难点，但要给证据链）

### 5.1 难点一：复杂 PDF —— 误差分布在整条链路，不能靠换模型

| 难点类型 | 典型表现 | 我的对策（四层增强） |
|---|---|---|
| 多栏排版 | 左右栏串行、跨栏大图切断文流、页眉页脚混入正文 | 第 3 层：XY-cut + 规则修复阅读顺序 |
| 嵌套表格 | 表头语义丢失、合并单元格错位、跨页续表拆断 | 第 3 层：表格二次识别，输出 HTML 表 |
| 图文混排 | 图注与图错配、嵌图内文字丢失 | 第 4 层：图存对象存储 + 位置锚点 |
| 公式 | 长公式/多行公式错、α→a、上标丢失 | 第 3 层：公式增强 + 低置信度回填 |
| 扫描件 | 低分辨率、摩尔纹、倾斜 → OCR 错误率飙升 | 第 1 层：超分、去噪、倾斜矫正 |

四层是：① 图像预处理 ② 双后端页级路由 ③ 专项增强（表格/公式/多栏） ④ 统一 Markdown 中间态。

**必须说出口的取舍**：中间态统一是为了让解析器可替换——换解析器不动向量库和分块逻辑。这跟 C 与 Java 之间放一层 DS 数据中心是同一个思路：**用一层协议把两侧解耦**。

### 5.2 难点二：政策解读的"确定性"必须从模型手里拿走

- 五个独有约束：时效敏感、效力分层、条款级溯源、解读 ≠ 立法、权限与密级。
- 三条硬规则（写进代码）：① 有效期一般 ≤5 年、暂行/试行 ≤3 年，届满未延续自动失效 ② 公布日 ≠ 施行日，存在"已公布尚未施行"第三种状态 ③ 上位优于下位、特别优于一般（限同一机关）、新法优于旧法；"工作方案""会议纪要"不构成行政管理依据。
- 为什么值得当难点讲：正确答案有时是**如实告知"这不构成依据"**，而不是硬凑一段解读。这是产品判断，不是模型能力。

### 5.3 难点三：智能客服的"一半问题不是知识问题"

- 两个分岔：知识类 / 数据类 / 混合类 —— 走错必然答错。
- 命中校验四关 + 转人工七条件 + 交接包 + 数据类 API 白名单（九个动作）。
- 上下文串线会把 A 的资料说给 B，属重大事故 → 会话隔离与并发上下文管理。
- **口径提醒**：客服工作流编排是团队推进的，我讲的是数据链路与解析侧如何喂给它干净的语料。

### 5.4 难点四：RAG 的静默故障（升级完悄悄失效）

- 索引侧决定天花板、检索侧决定命中率、生成侧决定敢不敢用、运维侧决定能不能持续变好。
- 静默故障最要命：换了 embedding 模型或解析器版本，召回悄悄下降，但没人报错。
- 对策：固定评测集 + 定期召回测试 + 版本升级前后对比。

## 6. 项目指标（AI 项目的诚实答案：能讲的与暂时没有的）

**可讲的（方法可验证）** `【设计】`：

| 指标 | 度量口径（要能说清分母） | 现状 |
|---|---|---|
| 解析成功率 | 按文档类型分桶（电子版 / 扫描件 / 多栏 / 嵌套表），成功 = 产出结构可用的 Markdown 且表格未破损 | `【待实测】` 有抽取集，缺基线数字 |
| 页级路由判定 | 抽样人工标注 100 页，看 pipeline / VLM 判定与实际最优后端的一致率 | `【待实测】` |
| 元数据完备率 | 入库文档中 文号/章节路径/页码/有效期 四字段齐全的比例 | `【设计】` 字段已定义 |
| 检索命中率 | 固定问答集 Top-K 命中率 + 空结果率 | `【待实测】` 评测集待建 |
| 转人工率与首解率 | 客服侧：转人工比例、一次解决比例 | `【待实测】` 团队口径 |
| token 成本 / 会话 | 中台计量，按应用与租户拆分 | `【设计】` 计量点已在业务层 |

**不能讲的（必须明确"没有"）**：

- 没有任何"效率提升 X%""成本下降 Y%""准确率 95%"这类数字，因为**没有生产实测**。被问就直接说：*"这个阶段还在验证，我能给的是度量口径和验证方法，数字要等 POC 跑完。"*
- 凡是简历或页面上的量化表述，一律标 `待实测`，不让它们变成面试雷。

## 9. AI 工程理解层（三条物理约束 → RAG 排查树 → Agent 六机制）

> 这一节解决"**被问到 AI 工程细节时，能自己推导**"——不是背手段，而是从约束反推。

### 9.1 三条物理约束（所有 AI 手段的源头）

| 约束 | 是什么 | 衍生手段 | 你的同构经验 |
|---|---|---|---|
| **上下文窗口有限** | 单次可见 token 上限（8K/32K/128K/200K） | **上下文工程**：预算 → 选择 → 排序 → 压缩 → 结构化 | 读库 + 组装分离；分页与投影 |
| **按 token 计费 + 逐 token 生成** | 输入输出双向收费；输出是逐 token 生成，越长越慢 | 成本：预算、缓存、小模型路由、`max_tokens`；延迟：流式、异步任务化、并行调用 | **接口耗时与资源预算治理**——和"先算容量再放量"同一套思维 |
| **概率生成** | 目标是"生成像样的文本"，不是"说真话" → 幻觉 | 输入层 RAG + 引用；指令层"没有就说不知道"；输出层 Schema + 规则校验；兜底层敏感结论不采信模型 | **关键路径不允许非确定来源**（报价、资金计算绝不交给可能出错的组件） |

> **反直觉点（加分）**：**窗口大 ≠ 效果好**。"大海捞针"研究表明信息在长上下文中间易被忽略（Lost in the Middle），越长越贵越慢噪音越多 → **RAG 不是"窗口小才用"，而是永远该用**。

### 9.2 RAG 效果不好的排查树（高频）

```
问效果差 → 先分层定位：
├─ 检索层：标准答案根本没被召回？
│   ├─ 切块太碎/太大 → 调 chunk
│   ├─ Embedding 不适配中文/领域 → 换模型
│   ├─ 只有向量、没关键词 → 上混合检索
│   └─ top-k 太小 → 放大候选
└─ 生成层：召回对了但答错？
    ├─ 上下文没拼好/被截断 → 查预算
    ├─ Prompt 没约束"只用资料" → 改指令
    └─ 模型太小/幻觉 → 换模型或加 Schema 校验
```

**方法论点**：**先建评估集，再谈优化**——没有评估集，调参就是盲人摸象。（`16` 风险清单里"AI 段口径"的解法也是这句：先有基线，才敢报数。）
> 注意：**索引侧决定天花板**（解析/切块/元数据），**检索侧决定命中率**，**生成侧决定敢不敢用**，**运维侧决定能不能持续变好**——面试按这四层归因，比笼统说"调参"高一个层级。

### 9.3 Agent 六机制（JD 术语 → 你的同构经验）

| # | 机制 | 讲人话 | LLM 特有难点 | 你的同构经验 |
|:--:|---|---|---|---|
| 1 | 任务执行循环 | 感知→规划→行动→观察，直到完成或触发终止 | 模型会"跑飞"、死循环、越绕越远 | 工作流编排 / Saga 编排器 / 状态机 |
| 2 | 状态管理 | 会话与任务状态外置（Redis/DB），每步可恢复可回放 | 模型本身无状态，上下文要自己拼；长任务中断要能续 | Outbox 事件表 / 幂等 / 会话外置 |
| 3 | 权限控制 | 工具分级：只读 / 写 / 高危，高危显式授权 | 模型不会自己守规矩，**鉴权不能跟 Agent 走，必须跟用户身份走** | 鉴权收口中台 / RBAC |
| 4 | 异常恢复 | 工具失败重试 + 降级 + 补偿；输出不合法带错误反馈重试 | 出错不是"抛异常"，而是"返回一段胡说八道" | 重试 / 降级 / 补偿 / 熔断 |
| 5 | 人工介入（HITL） | 写操作前审批、低置信转人工、留可撤销窗口 | 要设计"什么时候必须停下来问人" | 审批流 / 双人复核 / 灰度发布 |
| 6 | 评测观测 | 每步 trace 落日志；成功率/步数/工具错误率/成本/时延 | 输出是开放文本，指标难定义 | On-call / 监控 / 对账 / 双跑比对 |

**防失控三闸门**（问"死循环怎么防"就答这个）：**步数上限 / 预算上限（token 或金额）/ 重复检测**（连续相同动作或相同参数 → 判定卡死）→ 触发任一即**熔断 + 转人工**。

**最该背的一句**：
> "Agent 的可靠性不来自模型，来自 **Harness**——循环上限、状态外置、权限分级、失败补偿、人工卡点、评测观测。这六个机制我在企业级系统里都做过同构版本，AI 版的差异我清楚在哪。"

## 10. AI 段诚实口径（D9 的唯一任务：主动收窄，不硬撑）

| 场景 | 说法 |
|---|---|
| 被问"你的角色" | "我是**前期选型与数据链路负责人**：六路底座选型、MinerU 解析改造、批量调度兜底、入库元数据契约；**编排调优与微调由团队推进**" |
| 被问"上线了吗、效果如何" | "选型与解析链路已交付，编排由团队推进；**效果指标还在验证，我给的是度量口径与验证方法，数字要等 POC 跑完**" |
| 被问"准确率多少" | 绝不给 95% 这类数字。改为："按文档类型分桶的解析成功率 + 固定问答集 Top-K 命中率，两个口径已定义" |
| 被问"你会微调吗" | "参与可行性判断与数据侧准备，训练由团队执行" |
| 被问"跟 LangChain 比" | 讲六路对比的**硬约束清单**（私有化 / 二开 / 审计 / 成本），不讲功能列表 |
| 被问"AI 和 B2B 什么关系" | "同一平台加的一层能力底座，B2B 主链路仍是 Java 中台 + C 撮合；AI 是旁路，不承接交易" |

**三条硬约束（写进架构规范的原话）**：① **确定性的事不交给模型**（时效 / 位阶 / 权限 / 引用真伪全用代码算）② **Dify 不直连业务库**（数据访问走中台受控工具，权限在中台执行，不交给 Prompt）③ **工作流内不写复杂业务逻辑**（只做路由、拼装、调用、格式化）。
