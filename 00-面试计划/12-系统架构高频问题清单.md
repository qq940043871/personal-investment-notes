## 二、异构架构与 C 撮合（最高频）

| # | 问题 | 回答要点 | 出处 |
|:--:|---|---|---|
| B1 | 你们的撮合系统怎么设计的？ | C 撮合引擎（单线程内存撮合、O(logN) 排序树）+ Java 桥接 SDK（协议封装/连接管理/熔断限流）；C 保延迟确定性，Java 保业务编排灵活性 | §4.1 |
| B2 | 为什么不全部用 Java 微服务？ | GC 停顿 + JVM 预热让撮合延迟不可控；这是用可维护性换确定性的明确取舍 | §4.1 |
| B3 | Java 和 C 怎么通信？ | TCP Socket + 自定义二进制协议；Java 侧桥接 SDK 管连接池/超时/熔断/重试；撮合结果**异步落库** | §4.1 |
| B4 | 你怎么管一个你不熟的 C 模块？ | 不读 C 代码也能控局：接口契约 + 技术尽调框架 + 桥接层日志指标（飞行员不必会修发动机，但要读懂仪表盘） | §4.1 |
| B5 | DS 数据中心和交易核心什么关系？ | DS = Java 桥接 / 防腐层（ACL），把 C 的二进制协议翻译成 Java 能消费的接口与领域事件；异构复杂度全部收敛在 DS | 2.1 第三层 / 第四部分 #6 |
| B6 | 为什么用 Hessian 不用 JSON？ | 撮合是高频二进制交互，Hessian 序列化/解析开销远低于文本协议，跨语言友好、体积小 | 2.1 第三层 |
| B7 | 多模式交易的撮合一致性怎么保证？ | Java 侧规则配置引擎把挂牌/竞价/询价/基差规则翻译成 C 引擎标准指令序列，新增模式不改 C 代码 | 3.2 难题一 |
| B8 | 这种异构架构的竞争优势在哪？ | 别人会 Spring Cloud，我经历过"为什么有些东西不能用 Java 做"；并管过 C 团队 + Java 团队的异构协作 | §4.3 |

## 三、分层细节追问（一层一坑）

| # | 问题 | 回答要点 | 出处 |
|:--:|---|---|---|
| C1 | 为什么分三类终端？ | B2B 客户差异极大：中小企业要"快速下单"，机构要"资金风险 + 数据决策"，混在一起必臃肿 | 2.1 第一层 |
| C2 | 网关用什么技术？ | midservice1/2/3 自研 Java Web（鉴权/限流/租户路由/请求日志）+ midmon 自建监控面板，多实例部署 | 2.1 第二层 |
| C3 | 网关挂了怎么办？ | 多实例 + DNS 轮询 + 下游服务降级 | 第四部分 #3 |
| C4 | MySQL 双实例怎么保证一致？ | 主从复制 + 半同步 + 应用层幂等兜底；一主一从做读写分离与容灾 | 2.1 第四层 / 第四部分 #2 |
| C5 | MinIO 存了什么？ | 合同 PDF、仓单扫描件、质检报告、发票影像——全是履约凭证；另有文件服务统一管上传下载与权限 | 第四部分 #5 |
| C6 | 外部接口超时怎么处理？ | 熔断器（连续失败 3 次切备用通道）+ 调用异步化（MQ 回调）+ 每日凌晨全量对账告警 | 3.2 难题二 / 第四部分 #4 |
| C7 | 创新挂牌和自由竞价的区别？ | 挂牌 = 明盘报价、先到先得；竞价 = 价格优先、时间优先撮合 | 第四部分 #7 |
| C8 | 缓存服务怎么设计的？ | 独立 Java 服务封装 Redis；Canal 监听 binlog 实时刷新；专门加速网页读请求（读多写少），实质是卸 DB 压力 | 3.2 难题三 / 第四部分 #10 |
| C9 | 多租户数据隔离怎么做的？ | 网关做租户路由（不同客户打到对应隔离空间），DS 侧兼顾隔离与读性能 | 2.1 第二层 / 3.2 难题三 |
| C10 | 可观测性怎么做的？ | 连接数、消息积压、去重命中率、P99 延迟必须监控，否则故障都发现不了 | §二 |

## 四、Socket 长连接接入（由 2 分钟话术反推的题面）

| # | 问题 | 回答要点 | 出处 |
|:--:|---|---|---|
| D1 | 异构系统 Socket 长连接怎么分层设计？ | 三层：传输层可靠投递 / 连接层断线自愈 / 一致性走最终一致 + 对账 | §二 |
| D2 | 怎么保证消息不丢不重？ | 唯一 msgId + 接收方先落地再回 ACK + 指数退避重发 + Redis SETNX 去重 | §二 |
| D3 | 断线怎么自愈？ | Netty IdleStateHandler 双向心跳；指数退避 + 随机抖动重连防惊群；按 Redis 里的 offset 断点续传 | §二 |
| D4 | 为什么不做强一致？ | 异构系统强一致代价太高；ACK + 幂等解决 99.9%，定时对账 + 日终全量对账兜底 0.1% | §二 |
| D5 | 对端挂了怎么办？ | 熔断降级 + 消息暂存待发队列 + 恢复后回放；服务无状态化（状态存 Redis）可水平扩展 | §二 |
