## 1. Java 基础与集合

| 问 | 一句话结论 | 追问层（第二层） |
|---|---|---|
| HashMap 底层结构 | 数组 + 链表 + 红黑树（JDK8+），链表长度 ≥8 且容量 ≥64 才树化 | 为什么先扩容再树化：容量小于 64 时树化后还要扩容，代价大；退化阈值 6 防抖动 |
| 扩容机制 | 默认 16，负载因子 0.75，扩容 2 倍；JDK8 用高低位拆分，**无需重算 hash** | 为什么 0.75：空间与冲突的折中；为什么容量是 2 的幂：`(n-1)&hash` 位运算取模 |
| 为什么线程不安全 | JDK8 头插改尾插，不再成环，但并发 put 仍会**丢数据 / size 错乱** | 并发场景用什么：`ConcurrentHashMap`（JDK8 用 CAS + synchronized 锁桶头） |
| ConcurrentHashMap JDK8 的锁 | 锁单个桶头节点（synchronized），空桶用 CAS 放 | 为什么不用段锁：JDK7 段锁粒度粗、并发度固定 16；size 用 baseCount + CounterCell 分散热点 |
| String 为什么不可变 | final char[]/byte[] + 类 final；不可变才能做常量池缓存与线程安全 | 字符串拼接：循环里用 `StringBuilder`（非线程安全）/`StringBuffer`；`+` 在循环里会反复建对象 |
| equals 与 hashCode | 重写 equals 必须重写 hashCode，否则散列容器找不到 | 只重写 equals 的后果：两个"相等"对象落到不同桶，`contains` 返回 false |
| 重载与重写 | 重载编译期定（静态分派），重写运行期定（动态分派） | 为什么重载不能按返回类型区分：方法签名不含返回值 |
| 泛型擦除 | 编译期擦除到上界，运行期无泛型信息 | 后果：不能 `new T[]`、`instanceof List<String>` 非法；反射可绕过类型检查 |

## 2. JVM

| 问 | 一句话结论 | 追问层（第二层） |
|---|---|---|
| 内存区域 | 线程私有：程序计数器、虚拟机栈、本地方法栈；共享：堆、方法区（元空间） | 哪块会 OOM：堆（对象）、元空间（类）、栈（递归过深会 StackOverflowError） |
| 对象创建与分配 | 类加载检查 → 分配内存（TLAB）→ 零值初始化 → 设对象头 → 执行 `<init>` | 为什么用 TLAB：避免多线程分配同一块内存的指针碰撞竞争 |
| 对象何时进老年代 | 大对象直接进、动态年龄判定（Survivor 同龄总和 > 一半）、年龄达阈值（默认 15） | 为什么不是"熬过 N 次就晋升"：动态年龄判定优先，避免 Survivor 溢出 |
| GC  Roots 有哪些 | 栈上引用、静态属性、常量、JNI 引用、同步锁持有对象 | 为什么不用引用计数：无法解决循环引用 |
| 分代回收与收集器 | 新生代复制（Eden:S0:S1=8:1:1），老年代标记-整理/标记-清除 | G1 的 Region 与可预测停顿：`MaxGCPauseMillis` 是按 Region 收益排序回收；ZGC 用染色指针 + 读屏障，停顿 < 1ms |
| 类加载过程 | 加载 → 验证 → 准备 → 解析 → 初始化 | 准备阶段赋**零值**，`static final` 常量在准备阶段就赋值；初始化才执行 `<clinit>` |
| 双亲委派 | 先委派父加载器，父加载不了才自己加载 | 为什么：避免核心类被篡改；打破场景：SPI（`Thread.contextClassLoader`）、Tomcat 应用隔离、热部署 |
| 线上 OOM 怎么查 | `jstat -gcutil` 看老年代 → `jmap -histo:live` 看对象 → dump + MAT 支配树 | 详见主线件 `07` §4.2（含判断树与常见泄漏源） |

## 3. 并发

| 问 | 一句话结论 | 追问层（第二层） |
|---|---|---|
| JMM 三大特性 | 原子性、可见性、有序性；`volatile` 保可见 + 有序（禁重排），**不保原子** | `i++` 用 volatile 为什么还错：读-改-写三步，中间可被覆盖 |
| happens-before | 程序次序、锁、volatile、线程 start/join、传递性 | 作用：判断"一个线程的写对另一个线程是否可见"的唯一标准 |
| synchronized 与 ReentrantLock | 前者 JVM 层（monitor）、自动释放、非公平；后者 API 层、可中断/超时/公平/多条件 | 锁升级：偏向 → 轻量（CAS 自旋）→ 重量（OS 互斥）；JDK15 后偏向锁默认关闭 |
| AQS 原理 | 一个 `volatile int state` + CLH 双向队列，`tryAcquire/tryRelease` 交由子类实现 | 为什么用队列：抢不到锁的线程排队等待，避免自旋耗尽 CPU |
| 线程池核心参数 | core / max / queue / keepAlive / 拒绝策略 / 线程工厂 | 执行顺序：core → 队列 → max → 拒绝。**队列满了才扩到 max**，这是最常答错的一点 |
| 线程池参数怎么定 | CPU 型 ≈ 核数+1；IO 型 ≈ 核数 ×(1+等待/计算)；**实际按下游容量与压测定** | 队列选择：`LinkedBlockingQueue` 无界会导致 max 永远不生效；有界队列 + 明确拒绝策略 |
| 拒绝策略 | Abort（抛异常）/ CallerRuns（回压）/ Discard / DiscardOldest | 生产建议：自定义——落库或降级，并打点计数 |
| ThreadLocal 原理与坑 | 每线程一个 `ThreadLocalMap`，key 是弱引用、value 强引用 | 为什么会泄漏：key 被回收后 value 仍挂在 Entry 上；线程池复用线程必须 `finally remove()` |
| CAS 与 ABA | 比较并交换，无锁；ABA 用版本号（`AtomicStampedReference`）解决 | 缺点：自旋耗 CPU、只能保证一个变量、ABA |

## 4. MySQL

| 问 | 一句话结论 | 追问层（第二层） |
|---|---|---|
| InnoDB 索引结构 | B+ 树：非叶子只存键、叶子存数据且成链，**三层可存约千万级** | 为什么不用 B 树：B+ 树矮胖、IO 次数少、叶子链表利于范围与排序；为什么不用 Hash：不支持范围 |
| 聚簇与二级索引 | 主键索引叶子存整行；二级索引叶子存主键值 → 回表 | 覆盖索引：查询列都在索引里就不用回表；`explain` 的 `Using index` |
| 最左前缀 | 联合索引 (a,b,c) 只能从 a 开始连续用 | 范围查询后面的列失效（`a=? and b>? and c=?` 中 c 用不上索引的有序性） |
| 索引失效常见原因 | 函数/表达式、隐式转换、前缀通配 `%x`、OR 连接非索引列、区分度太低 | 隐式转换为什么失效：字符串列用数字比较会转成 double，索引失去可比性 |
| 事务隔离级别 | 读未提交 / 读已提交 / 可重复读（默认）/ 串行化 | 各解决什么：脏读 / 不可重复读 / 幻读（RR 下靠间隙锁在**当前读**才挡住幻读） |
| MVCC 实现 | 隐藏列（trx_id、roll_pointer）+ undo log 版本链 + ReadView | RC 与 RR 的差别：ReadView **生成时机**——RC 每次快照读新建，RR 首次快照读建立并复用 |
| 间隙锁与死锁 | RR 下范围当前读会加 Next-Key（记录 + 间隙）锁 | 死锁怎么排查：`show engine innodb status` 看 LATEST DETECTED DEADLOCK；预防：定序访问、短事务、必要索引避免锁全表 |
| redo / undo / binlog | redo 保证崩溃恢复（物理，循环写）；undo 保证回滚与 MVCC；binlog 用于复制与归档（逻辑） | 两阶段提交：redo prepare → binlog → redo commit，解决主从与恢复一致 |
| 慢 SQL 怎么优化 | 先看 `explain` 的 type / key / rows / Extra（filesort、临时表）→ 改 SQL 或加索引 | 深分页：`limit 100000,20` 用"延迟关联"或"记住上次最大 id"；`type` 至少要 range，ALL 要警惕 |

## 5. Redis

| 问 | 一句话结论 | 追问层（第二层） |
|---|---|---|
| 为什么快 | 内存 + 单线程无锁 + IO 多路复用 + 高效数据结构 | 6.0 的多线程：只用于**网络 IO 读写**，命令执行仍单线程 |
| 数据结构与底层编码 | String（SDS）/ Hash（listpack、hashtable）/ List（quicklist）/ Set（intset、listpack、hashtable）/ ZSet（listpack、skiplist） | ZSet 为什么用跳表不用红黑树：范围查询简单、实现易、并发友好 |
| 持久化 | RDB（快照，恢复快、可能丢数据）+ AOF（追加，安全、文件大）；4.0+ 混合持久化 | AOF 刷盘策略：always / everysec（默认，最多丢 1s）/ no |
| 过期与淘汰 | 惰性删除 + 定期删除；淘汰策略 8 种，生产常用 `allkeys-lru` / `volatile-ttl` | 为什么不用定时删除：海量 key 时定时器扛不住 |
| 缓存穿透 / 击穿 / 雪崩 | 穿透 = 查不存在（空值缓存 + 布隆）；击穿 = 热点 key 失效（互斥重建 / 逻辑过期）；雪崩 = 大批同时过期（TTL 抖动 + 多级缓存） | 逻辑过期与互斥重建的区别：前者不阻塞读、返回旧值；后者阻塞、保证只回源一次 |
| 缓存与 DB 一致性 | 先更新 DB 再删缓存（Cache Aside），失败重试/订阅 binlog 补偿；**资金类不允许缓存为准** | 为什么是删不是改：并发下改缓存可能写入旧值；延迟双删针对主从延迟 |
| 分布式锁 | `SET key value NX PX`，value 放唯一标识，释放用 Lua 比对删除 | 为什么要 PX：防持有者崩溃导致死锁；续期用看门狗（Redisson） |
| 大 key / 热 key | 大 key 拆分成多 key 或用 Hash 分片；热 key 本地缓存 + 多副本分散 | 危害：大 key 阻塞单线程、网络拥塞；热 key 打爆单个分片 |

## 6. Spring

| 问 | 一句话结论 | 追问层（第二层） |
|---|---|---|
| IoC 与 DI | 容器管理对象生命周期与依赖注入，解耦 | 三种注入方式：构造器（推荐，可测且不可变）、setter、字段（不推荐） |
| Bean 生命周期 | 实例化 → 属性填充 → Aware → BeanPostProcessor 前置 → 初始化（`@PostConstruct` / `afterPropertiesSet` / init-method）→ 后置 → 使用 → 销毁 | 循环依赖：三级缓存（单例池 / 早期引用 / 工厂），**只解决单例 setter/字段注入**，构造器注入无法解决 |
| AOP 原理 | 动态代理：JDK Proxy（接口）或 CGLIB（子类），Spring Boot 2.x 默认 CGLIB | 为什么同类方法自调用切面失效：走的是 `this`，不是代理对象 |
| 事务传播 | REQUIRED（默认，加入现有）/ REQUIRES_NEW（挂起新建）/ NESTED（保存点）/ SUPPORTS / NOT_SUPPORTED / MANDATORY / NEVER | REQUIRED 下内层抛异常会一起回滚（同一物理事务），REQUIRES_NEW 才是独立事务 |
| 事务失效的几种情况 | ①同类自调用 ②非 public ③异常被吞 ④异常类型不是 RuntimeException（默认）⑤数据库/存储引擎不支持 ⑥多线程调用 | 最常被问：自调用与"异常被 catch 掉"；解决：注入自身代理或拆类 |
| Spring Boot 自动配置 | `@EnableAutoConfiguration` → `AutoConfigurationImportSelector` → `spring.factories` / `AutoConfiguration.imports` → 条件装配 | 条件注解：`@ConditionalOnClass/OnMissingBean/OnProperty`；自定义 starter 就是"自动配置类 + 条件 + 配置元数据" |

## 7. 网络（高频 5 题，够用即可）

| 问 | 一句话结论 | 追问层（第二层） |
|---|---|---|
| TCP 三次握手 | SYN → SYN+ACK → ACK；目的是**双向确认收发能力 + 同步初始序号** | 为什么不是两次：无法确认客户端收包能力，且历史连接请求会造成服务端资源浪费 |
| 四次挥手与 TIME_WAIT | FIN → ACK → FIN → ACK；主动关闭方等 2MSL | 为什么等 2MSL：保证最后 ACK 到达 + 让旧报文在网络中消亡；TIME_WAIT 过多的处置：连接池复用、`tcp_tw_reuse`（不能盲调） |
| TCP 与 UDP | TCP：可靠、有序、拥塞控制、面向字节流；UDP：无连接、不可靠、低开销 | 什么时候选 UDP：实时音视频、DNS、QUIC 在 UDP 上自建可靠传输 |
| HTTP/1.1 vs 2 vs 3 | 1.1 长连接但队头阻塞；2 多路复用（仍受 TCP 层阻塞）；3 基于 QUIC（UDP）解决 TCP 层队头阻塞 | 2 的队头阻塞在哪：丢一个 TCP 段会阻塞该连接上所有流 |
| HTTPS 握手 | 非对称换对称：证书验证 + 密钥协商，之后用对称密钥通信 | 为什么不全程非对称：性能差 1~2 个数量级；证书链校验的是"身份"，不是"加密强度" |

## 8. Kafka（选型题常客，4 题）

| 问 | 一句话结论 | 追问层（第二层） |
|---|---|---|
| 为什么快 | 顺序写 + 页缓存 + 零拷贝（sendfile）+ 批量与压缩 + 分区并行 | 零拷贝省了什么：省掉内核态到用户态的两次拷贝与上下文切换 |
| 怎么保证不丢 | 生产端 `acks=all` + 重试；broker `replication.factor≥3` + `min.insync.replicas≥2`；消费端手动提交 offset | 三种丢法：生产端（未确认）、broker（未刷盘/副本不足）、消费端（先提交后处理） |
| 怎么保证不重 | 幂等生产者（PID + 序列号）+ 事务；消费端**业务幂等**（唯一键 + 状态机） | 为什么业务幂等必须有：跨系统重试、rebalance 重复消费无法靠 Kafka 单独解决 |
| 顺序性 | 同一分区内有序；要保序就按业务键选分区 | 扩分区会破坏顺序：key→分区映射变化；顺序性要求高时慎扩 |
