# 06 · 一致性与异构（P0 主场）

> **排期**：D8（跨系统一致性 + 异构 + 容量）
> **本件定位**：一致性与异构是面试第三层追问最密集的主题。本卡按三个工程的真实代码重写：**MidService**（网关）、**midmon-ds**（DS 管理台 + midmon 监控）、**dataShare**（DS 数据交换中心）。每个结论都标注证据等级，被问到数字时只报对应等级允许的口径。
> **答题主线**：先讲系统真实是什么，再讲异构点在哪、一致性靠什么守，最后给出容量的诚实数字和改造路径。

## 1. 系统真实的一致性模型

**一句话**：同步调用链 + 无分布式事务 + 局部串行锁 + 尽力投递的 MQ。跨系统的正确性不是系统自动修复的，而是**调用方拿到失败结果后自己决定怎么处理**。

| 环节 | 当前机制 | 证据等级 | 位置 |
|---|---|---|---|
| 网关 → DS → 后端 | 同步请求-响应，失败或超时直接返回调用方 | 【代码证实】 | `HandlerController`；DS 超时 3000ms 【配置证实】 |
| 跨系统事务 | 未发现 2PC、Saga、本地消息表或补偿编排 | 【代码证实】（三工程中未找到） | — |
| 单用户单接口串行 | `lockApi / unLockApi` 按 `api + tokenId` 取 `ReentrantLock`，由开关 `is.open.syncLock=Y` 控制 | 【代码证实】开关逻辑；生产开关值【未核实】 | `HandlerController.java:1744-1790` |
| 分布式业务锁 | 用 `setnx` + `expire` 两条独立命令加锁 | 【代码证实】（缺陷分析引用） | `T00010040` |
| MQ 投递 | 发布在 Kafka 确认前即返回成功；消费失败会取消订阅；offset 固定 60 秒刷库 | 【代码证实】（缺陷分析 B6–B8） | `T00010033`、`T00010040` 相关逻辑 |
| 幂等 | 三工程中未见统一的业务幂等键机制 | 【未核实】 | — |

**对外口径**：关键交易动作放在同步链路上，失败即时返回，调用方可感知；异步通道目前是尽力投递，可靠化的改造路径见 §4。

## 2. 异构点：五段协议，多种序列化

请求方向的真实链路：

```
调用方（HTTP + JSON 报文）
  → midservice 网关（Tomcat 线程；入口 /api/<协议号>、/toBack/<协议号>）
  → DS 客户端 SDK（自研 Socket 长连接，ansyKey 复用）
  → dataShare 服务端（IO 线程接收，按协议号路由，协议参数来自 TB_DS_PROTOCOL）
  → 后端，按 connType 分两路：
       connType=1 → Hessian over HTTP（业务服务）
       connType=2 → TCP 二进制帧（C 撮合引擎）
旁路：dataShare ↔ Redis（分片池）、dataShare → Kafka（MQ）
监控：midservice → midmon TalkerServer（socket，端口 9999）
```

| # | 边界 | 两侧 | 协议与序列化 | 当前风险点 |
|---|---|---|---|---|
| 1 | 外部入口 | 调用方 ↔ midservice | HTTP + JSON，统一响应结构 `{result, api, msg, data, timestamp, appresult}` | 业务成败靠报文内 `result` 区分；舱壁拒绝也是 HTTP 200 + 同结构报文 |
| 2 | 网关 ↔ DS | midservice ↔ dataShare | 自研 Socket 长连接（DSClientAPI） | 客户端池 `maxCon=200`【配置证实】；池耗尽等待 5000ms 为 SDK 硬编码【反编译证实】 |
| 3 | DS ↔ 业务后端 | dataShare ↔ Java 服务 | Hessian over HTTP（connType=1） | JVM 默认 `http.maxConnections=5`/主机，长 RT 下吞吐受限 |
| 4 | DS ↔ C 撮合 | dataShare ↔ C 引擎 | TCP 二进制帧（connType=2），协议细节由 C 团队定义 | 撮合协议的 `SOCKET_MAX/INIT/TIMEOUT` 从 DB 读取，无代码默认值 |
| 5 | Java ↔ Redis / Kafka | dataShare、midservice ↔ 中间件 | 分片 Redis 客户端；Kafka 生产者 | 全局锁与 MQ 语义见 §1、§3 |
| 6 | 网关 ↔ 监控 | midservice ↔ midmon | 私有 Socket（9999） | `mon.maxConn=5`【配置证实】；监控不在交易数据面上 |

**定位澄清**：midmon-ds 是一个合并工程（Spring Boot 2.7，JDK 8），内含 DS 管理台与 midmon 监控，属于**管理与监控面**，不在交易请求的数据面上。真正做协议翻译与路由的是 **dataShare**。

**为什么要有 DS 这一层**：两侧独立演进。C 侧只说 Socket 二进制帧，Java 侧说 Hessian 与 HTTP，协议翻译和路由集中在 dataShare，业务服务不需要懂撮合引擎的内存布局，C 团队也不需要懂 Java 的 RPC 语义。

## 4. 改造路径（按改动量从小到大）

> 完整的并发需求推导、逐跳判据、分阶段验收见 `02-项目底稿/b2b-project/midservice/达成目标的改造路线-5万QPS与1000TPS.md`。核心是 Little 定律：所需并发 = 目标吞吐 × RT；写 1000 TPS 在 RT 60ms 下需约 60 并发（余量后 120），读 5 万 QPS 加权 RT 约 1.1ms 时需约 55 并发（余量后 110）。逐跳核对后，真正卡住的是 DS 处理模型、归还全局锁、Hessian 连接数、读路径依赖 DS 与串行锁，而不是 Tomcat 线程。

| 步骤 | 动作 | 解决的问题 | 改动量 |
|---|---|---|---|
| 1 | 核实并固化配置：`is.open.syncLock` 生产取值、舱壁协议级参数、`ds.maxCon` 生产值、JVM `http.maxConnections` | 配置层天花板与池大小 | 低 |
| 2 | 读链路：三级缓存接线 + Redis 直连（不经 DS） | 读不再受 dataShare 单 IO 约束 | 低 |
| 3 | 去全局锁：归还锁按 `clientFlag` 分段；Redis 借连接移出全局锁；热路径 `static synchronized` 去锁 | 串行点 | 低至中 |
| 4 | dataShare 业务 worker 线程池：`HandlerImpl.run` 解析后移交线程池 | 打破 TPS ≈ 1/RT 的上限 | 中 |
| 5 | MQ 可靠化：发布等待 Kafka 确认；消费失败不取消订阅；offset 按批提交 | 尽力投递 → 可补偿 | 中 |
| 6 | 送达型一致性：本地消息表 + 批次号 + 阶梯重试（1s→2s→4s）+ 超限转人工，用于通知类动作 | 异步通知可靠送达 | 中；设计见 `12`，落地工程待确认 |
| 7 | 超时分级 + 熔断 + 撮合不自动重试（幂等与对账兜底） | 慢协议不拖垮快协议 | 低 |

> 撮合侧的内存一致性与热备设计见 `13`，编码由 C 团队实现；DS 的协议内核与容量测算设计见 `15`。

## 5. 90 秒速答（三段，按题选段）

### 5.1 "你们跨系统调用怎么保证一致？"

> 先讲清边界。网关到 DS 到后端是**同步调用**，关键交易动作失败时即时返回调用方，系统不做分布式事务，也不做自动补偿。一致性靠三件事：一是同一用户同一接口的串行锁，防止同一用户并发写乱序，开关可配置；二是交易动作放在同步链路上，失败可感知，不产生"静默丢失"；三是异步通道（MQ）目前是尽力投递，我们把它列为第一批改造项，改成等待 Kafka 确认加消费失败回流。对"只需送达"的通知类动作，设计上用本地消息表加批次号加阶梯重试兜底，超限转人工，方案已成文，落地顺序是先 MQ 再推广到通知类动作。

### 5.2 "你们怎么和 C 撮合对话？"

> 网关用自研 Socket 长连接访问 dataShare，dataShare 按协议的 connType 分两路：请求-响应类后端走 Hessian over HTTP，撮合类走 TCP 二进制帧直连 C 引擎。协议参数、连接池和超时都配在 DB 协议表里，由 dataShare 统一翻译与路由，两侧独立演进。撮合引擎的编码由 C 团队负责，我这边定义 Java 侧的契约与一致性要求。

### 5.3 "系统能扛多少？"

> 我不报没有实测的数字。按代码和配置推算，当前写链路大约在 10 到 100 TPS，取决于后端响应时间，有效并发个位到十几。瓶颈不在配置上限，而在结构：同用户串行、DS 同步阻塞调用模型、归还全局锁。目标是 1000 TPS 写、5 万 QPS 读，路径是读走缓存和 Redis 直连、dataShare 加 worker 池、去掉全局锁，写目标的前提是撮合引擎能扛 1000 撮合每秒。压测方案和拐点判据已经有了，结果出来后再报数字。

## 6. 追问链

### 6.1 一致性

| 追问 | 答 |
|---|---|
| 两次调用都成功怎么办？ | 同步链路上任一步失败都即时返回，调用方感知并决定处理。系统内不做自动补偿，这是当前边界；送达型场景用 `12` 的方案补齐 |
| 为什么不用 2PC / XA？ | 跨库加外部撮合引擎不支持 XA，全程持锁，可用性和性能代价大；交易动作本身也不需要跨系统原子提交 |
| 同用户串行锁是干什么的？ | 防止同一用户同一接口并发导致重复提交或写乱序，代价是单用户并发上限为 1。生产是否开启以现场配置为准 |
| MQ 发出去为什么不一定到？ | 当前发布不等 Kafka 确认，消费失败会取消订阅，属于尽力投递。改造是等待确认加失败回流 |
| 分布式锁有什么风险？ | `setnx` 与 `expire` 是两条命令，中间崩溃会留下永不过期的锁。改为单条原子的 `SET NX PX` 即可消除 |
| 怎么发现数据不一致？ | 目前没有对账闭环的代码证据，这是待补的一环；方案层面用内存态、DB 态、下游态三方比对，见 `13` |

### 6.2 异构

| 追问 | 答 |
|---|---|
| 为什么 Hessian 不用 JSON？ | 请求-响应链路上的序列化开销直接进入时延预算，Hessian 是二进制，比 JSON 省；JSON 保留给配置与人读场景 |
| 为什么 Hessian 路径是瓶颈？ | JVM 默认每主机 5 个 HTTP 连接，长 RT 下吞吐约等于 5 / RT；把 `http.maxConnections` 调大是最直接的缓解 |
| 为什么 DS 单独做一层？ | 防腐层：两侧协议与语言各自独立演进；协议翻译与路由集中在一处，业务服务与撮合引擎互不侵入 |
| midmon 在交易链路上吗？ | 不在。它是管理与监控面，midservice 通过 9999 端口的监控通道上报，不影响交易数据面 |

### 6.3 容量

| 追问 | 答 |
|---|---|
| 你们能扛多少？ | 见 §5.3：按代码推算约 10～100 TPS，目标 1000 TPS 写与 5 万 QPS 读，均未压测 |
| 怎么判断瓶颈在哪一层？ | 压测阶梯加压，找吞吐拐点；拐点时 `jstack` 看 dataShare 的 IO 线程数，若只有一个 reactor 线程在跑 `HandlerImpl.run`，即单 IO 线程模型成立；同时看各层 RT 的 P95/P99 |
| 5 万 QPS 怎么来的？ | 约 90% 命中三级缓存，10% 走 Redis 直连，2～3 台网关；这是设计目标，需要压测确认缓存命中率 |
| 1000 TPS 怎么来的？ | 64 个 worker 线程 ÷ 撮合 RT 50ms ≈ 1280 TPS/台；前提是 C 撮合引擎能扛 1000 撮合/秒，这一条必须先实测 |
