# 06 · 一致性与异构（P0 主场）

> **排期**：D8（跨系统一致性 + 分布式事务）
> **本件定位**：一致性是最容易被追问到第三层的主题。**先分类再选型**，是这份卡唯一的答题主线。

---

## 0. 三分法（先分类，再答题——这是你的差异化）

> 面试官问"你们怎么保证一致性"，**先切三类再选**。切完再选，气场完全不同。

| 需求类型 | 典型场景 | 用什么 | 一句话理由 |
|---|---|---|---|
| **只需"送达"** | 确认收货要通知资金 + 仓单 | 本地消息表（Outbox）+ 批次号原子认领 + 阶梯重试（`12`） | 两个动作**可以独立完成**，本就不需要强一致 |
| **必须"补偿"** | 跨月长事务、下游不支持 XA | Saga 编排器（`05`） | 用"反向操作"换"不锁资源" |
| **以内存为准** | C 核心撮合 | 镜像落盘（WAL）+ 异步回写 + 死信兜底 + 定时对账（`13`） | 确定性重放，DB 只是最终一致的副本 |
| **跨语言互译** | C（Socket 帧）↔ Java（Hessian） | DS 数据交换中心 = 防腐层（`15`） | 两侧独立演进，谁也别把对方逻辑写进自己 |

**一句话口径**：**`12` 管送达、`05` 管补偿、`13` 管内存、`15` 管互译——一件管一段，拼成完整防线。**

## 1. 90 秒速答（三段，按题选段）

### 1.1 "跨系统调用一致性怎么做的"（D8 主问题）

> 我们不追求"两次调用都成功"，只保证**最终被确认**。做法是**本地消息表**：在业务本地事务里，把"单据要变更"和"要通知谁（欠账记录）"写在同一个事务里，原子提交。然后独立的派发器扫描待发送表，**先取一个全局唯一批次号，用一条带批次号的 UPDATE 把整批记录原子认领**（改状态、打号、记认领时间同一条 SQL），这一批就共享同一个号。派发失败按 1s→2s→4s 阶梯重试，超上限熔断进死信、发运营短信。下游用业务幂等键去重，所以**超时了不知道成功没成功，也不需要知道——重试是幂等的**。
>
> 关键设计是"一条下游一条记录"：资金成功、仓单失败时，只重试失败那条，部分成功就从"灾难"降级为"两个独立进度"。集群部署也靠批次号：多实例各管自己的批次，**既不重复派发也不互相覆盖**，宕机还能按批次号整批回收。
>
> 为什么不用 2PC：本地事务跨不了库，XA 要全程持锁，可用性和性能都赔不起；而这个场景两个动作本来就可以独立完成。

### 1.2 "C 核心单线程怎么保证一致性"（架构深潜）

> 单线程保证的是**内存内**——串行、无锁、可复现（输入序列定则输出定）。**内存外**要靠三段兜：镜像文件（write-ahead，防丢）、异步回写 + 阶梯重试（追 DB）、死信队列 + 运营重试（收敛卡死）。
>
> 次序不变量是"**先落地、再改内存**"：如果先改内存后写日志，那个窗口崩溃 → 这笔成交彻底蒸发（不在内存、不在日志、不在 DB）。镜像落三种东西：命令日志（记输入，用于重放）、定期快照（记状态，加速恢复）、回写待办（记还欠 DB 什么）。
>
> 同步落库不能用——那等于把撮合速度绑死在 DB 写入能力上，一次 DB 抖动就变成撮合停顿。异步的代价是"内存有、库无"的时滞，用"内存为准 + 异步回放 + 幂等补偿 + 定时对账"兜住。**对账是兜底的兜底**：前面都在"尽量不出错"，对账保证"出错了也一定被发现"。

### 1.3 "C 和 Java 怎么对话"（异构桥接）

> DS 数据交换中心是 C 撮合与 Java 中台之间的**防腐层**：C 只会说 Socket 二进制帧，Java 只说 Hessian / HTTP，DS 互译成统一报文，让两个团队各自独立演进。原则是**不把 Java 写进 C 引擎，也不把 C 逻辑外泄到 Java 层**。
>
> 通道跟着语义走：请求-响应要结果 → Hessian over HTTP（状态码、超时、重试现成）；高频回执和行情要吞吐 → Socket 长连接（省建连和头部开销，C 侧本来只会 Socket）。**不是追潮流，是各取所长。**

## 2. 追问链（每条都备有第二层）

### 2.1 送达型（`12`）

| 追问 | 答 |
|---|---|
| 怎么保证两次调用都成功 | **不保证"都成功"，只保证"最终被确认"**——把"要通知谁"写成本地数据，异步派发 + 阶梯重试 + 超限熔断转人工 |
| 超时了到底成功没有 | 不知道，也**不需要知道**：幂等键 + 下游去重，让"不确定"变成可以放心重试的问题 |
| 资金成功、仓单失败了 | 只重试失败那条，已成功的不动——"一条下游一条记录"把部分成功降级为两个独立进度 |
| 为什么重试要有上限还转人工 | "发不出去"（等下游恢复）与"发出去被拒"（参数错/业务不允许）是**两类问题**，后者代码解决不了，必须交人 |
| 批次号为什么不能单机自增 | 多实例会撞号；全局唯一才能"一条 UPDATE 原子认领整批"，避免分布式锁 |
| 界面重试和异步重试什么关系 | 异步重试是主路径，界面重试是兜底：只把记录重置成"待发送"重新入队，**不产生第二笔业务** |
| 为什么不用 2PC / TCC | 本地事务跨不了库；XA 全程持锁，可用性与性能赔不起；本场景不需要强一致。TCC 要写三个接口，收益不抵成本 |

### 2.2 内存型（`13`）

| 追问 | 答 |
|---|---|
| 单线程怎么保证一致 | 保证的是**内存内**串行、无锁、可复现；内存外用镜像 + 异步回写 + 死信三段兜 |
| 为什么不同步落库 | 等于把撮合速度绑死在 DB 上，一次抖动就停顿；异步换吞吐与确定时延，代价用幂等 + 对账吸收 |
| 先落地镜像是落什么 | write-ahead 三样：命令日志（重放）、定期快照（加速恢复）、回写待办（欠账）；常用组合是日志 + 快照 |
| 先改内存后写文件会怎样 | 窗口内崩溃 → 这笔成交彻底蒸发；"先落地"这条不变量不能破 |
| 回写失败 N 次怎么办 | 不能闷头重试（解决不了"发不出去"）；熔断进死信 + 运营短信，短信必须带**单号 + 原因 + 次数** |
| 运营点重试是不是重新撮合 | **绝对不是**。只重放"回写 DB"，按业务单号幂等 upsert。**撮合只发生一次，回写可以重放无数次** |
| 内存和 DB 不一致怎么发现 | 定时对账（内存态 / DB 态 / 下游态三方比对，差异报警） |
| 仲裁者自己挂了怎么办 | **整体停摆是正确行为**：无法区分"主挂了 / 主卡顿 / 网络分区"，三种情况动作相反 → 宁可停不可双主。正解不是让它永不挂，而是**做多数派**（3 容 1、5 容 2，每节点只维护任期号 + 租约）或复用 etcd / DB 租约表。两个硬细节：**任期号必须持久化**、**下游必须校验栅栏令牌**（"主会自觉停服"是假设，"下游拒绝旧令牌"才是事实） |
| 怎么做热备 | **不复制结果、只复制输入**：备机收命令日志自己重放（撮合确定 → 重放必得同一内存）；切换从已完整落盘的 LSN 续位点；回写靠幂等吸收重复。**RPO 由"对外应答前是否已同步到备"决定**，不由"改内存前是否同步"决定 |

### 2.3 异构型（`15`）

| 追问 | 答 |
|---|---|
| 怎么支持高并发 | 四件事：**IO 模型**（epoll / Netty Reactor，一连接一线程是自杀）、**背压**（有界队列 + 高水位三级，宁可明确拒收不堆到 OOM）、**并行**（按业务单号分片，同键保序异键并行）、**批量**（小包合并、批量落库）；再加对 C 单线程的适配：DS→C 只写**无锁 SPSC 队列**，绝不让撮合线程等我们 |
| 大概能扛多少 | 分三层：**连接数** 10 万级（内部实际几十~几百条，免测）；**接入吞吐** 10 万级 QPS（小报文）；**端到端 1~3 万 TPS，瓶颈在下游 DB 不在 DS**；生产 3 节点基线 |
| 怎么保证不丢不重 | 复用 `12` 范式（待发送表 + 批次号 + 阶梯重试 + 死信）；去重三层：帧序号保通道内、requestId 保窗口内、**业务幂等键保永久** |
| 队列打爆怎么办 | 有界 + 高水位三级：60% 告警、80% 明确拒绝或转落盘。**丢一条是事故，OOM 是全站停摆**——与网关"显式拒绝不做静默截断"同一条纪律 |
| 为什么 Hessian 不用 JSON | 高频二进制交互，序列化开销直接进时延预算；JSON 留给配置和人看的场合；Protobuf 更快但存量迁移成本 > 收益，不推倒重来 |

### 2.4 选型题（会被单独问）

| 对比 | 结论 |
|---|---|
| Saga vs 本地消息表（Outbox） | **Saga 管"必须补偿"**（跨月长事务、外部系统不支持 XA）；**Outbox 管"只需送达"**。二者互补、常嵌套：Saga 的某一步内部就用待发送表派发 |
| Choreography vs Orchestration | 事件驱动（Choreography）耦合低但链路不可见；编排器（Orchestration）链路显式、便于补偿与观测，**长事务选编排器** |
| 补偿的四大黄金原则 | 幂等、可重试、可交换（顺序不敏感）、必须记录；补偿失败走阶梯：自动重试 → 人工介入 → 挂账对账 |
| C 核心这套 vs ZooKeeper + Kafka | 同一形态的两个平面：ZK/仲裁者管"谁当主"（协调平面），Kafka/主备管"数据怎么复制"（数据平面）。**栅栏令牌 = leader epoch**、**"应答前同步到备" = ISR + acks=all**、**幂等 upsert = 幂等生产者**；KRaft 的启示是"**角色分离 ≠ 进程分离**"，所以 C 核心**倾向外部协调**（撮合线程不能阻塞，别把共识塞进去），外部可复用 etcd / DB 租约表 |
