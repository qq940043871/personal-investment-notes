# 原型与事故报告审查方法论手册

---

## 使用说明

不带框架看大量材料=白看。用下面这套透镜，看完能产出三样东西：场景补全清单、缺陷热力图、优先修复队列。

---

## 一、阅读前的准备工作（花5分钟，别跳过）

### 1.1 先在脑子里锚定三个问题

开始翻第一份材料之前，把这3个问题写在一张纸上放在旁边：

> 1. **这个原型/事故让我对"客户真实怎么用系统"多知道了什么？**
> 2. **这个原型/事故暴露了哪个"设计时没想到"的边界？**
> 3. **如果我只修一件事，从这里面选什么？**

### 1.2 准备一个记录表

用Excel或飞书表格，建三张sheet：

```
Sheet 1：原型审查记录
Sheet 2：事故报告审查记录
Sheet 3：交叉发现（最重要的一张）
```

---

## 二、原型怎么看——四个透镜

不要看"长什么样"，要看"暴露了什么"。

### 2.1 透镜一：设计 vs 现状 的偏差

拿原型页面跟线上实际页面做对比（能做多少做多少）：

| 对比维度 | 原型设计 | 线上现状 | 偏差原因追问 |
|---------|---------|---------|------------|
| 功能是否上线 | | | 砍了？搁置了？做了一半？问产品为什么 |
| 交互流程 | | | 简化了？复杂化了？谁改的？为什么？ |
| 数据字段 | | | 原型有但线上没有=数据被砍了 / 原型没有但线上有=后来临时加的 |
| 角色权限 | | | 原型假设了哪些角色操作？线上实际谁在用？ |

**重点关注：原型里有但线上没有的功能。** 这是最有价值的信息——说明当时的业务假设没有被验证，或者优先级被调整了，但**场景本身可能还在**。

### 2.2 透镜二：场景覆盖的空白

看原型时，问自己：

> - 这个流程假设用户已经知道什么？假设的前提合理吗？
> - 有没有"用户做到一半发现缺信息，必须退出"的断点？
> - 异常路径画了吗？（网络超时、数据不存在、权限不够——原型往往只画正常路径）
> - 多角色协作的场景画了吗？（交易不是一个角色完成的）

**重点关注：原型里只有一条"Happy Path"的流程。** 大宗贸易从来不走Happy Path——价格会变、质检会出问题、资金会延迟。异常路径才是真实世界。

### 2.3 透镜三：被放弃的设计——为什么？

如果发现某个原型设计了但没做（或做了但下线了），问产品：

> - "这个当时为什么没做？是技术原因还是业务原因？"
> - "现在回头看，这个需求还成立吗？"
> - "客户有没有再提过这个场景？"

**被放弃的设计往往藏着两个东西：①当时的架构没能力支撑（现在可能有了）②当时的市场没到这个阶段（现在可能到了）。**

### 2.4 透镜四：原型里埋的术语表

翻原型的时候顺手整理**业务术语**：

> 原型里叫"调拨"，客服嘴里叫"转库"，客户叫"划转"——这是同一个东西吗？

记下来，这直接影响你和商务/客服对话时的"解码"效率。

## 三、事故报告怎么看——四个透镜

事故报告是最诚实的文档。它告诉你系统**真正的弱点**在哪——不是压测报告里的，是真实打到客户身上的。

### 3.1 透镜一：分类计数→画热力图

每看完一份事故报告，给它在下面两个维度打分：

**维度A：根因类型**

| 类型 | 标记 | 例子 |
|------|------|------|
| 代码Bug | 🐛 | 空指针、边界条件、并发问题 |
| 设计缺陷 | 🏗️ | 流程设计本身就有漏洞、状态机不完备 |
| 配置/数据问题 | ⚙️ | 规则配错、数据迁移遗漏、缓存不同步 |
| 外部依赖故障 | 🔗 | 银行接口超时、物流回传失败、证书过期 |
| 容量/性能 | 📈 | 撮合峰值打满、数据库连接池耗尽、内存泄漏 |
| 操作失误 | 👤 | 运维误操作、客服误删、客户传错数据 |

**维度B：影响范围**

| 级别 | 标记 | 定义 |
|------|------|------|
| S级 | 🔴 | 交易中断/资金差错 |
| A级 | 🟠 | 核心功能不可用（报价、签约、履约） |
| B级 | 🟡 | 非核心功能异常（报表延迟、页面展示错误） |
| C级 | 🟢 | 体验问题/内部可见 |

看完所有报告后，做一个统计表：

```
根因类型分布：
🐛 代码Bug：   ████████░░ 8次
🏗️ 设计缺陷：  ██████░░░░ 6次
⚙️ 配置/数据： ████░░░░░░ 4次
🔗 外部依赖：  ██████████ 10次  ← 最高！
📈 容量/性能： ██░░░░░░░░ 2次
👤 操作失误：  ███░░░░░░░ 3次

影响范围分布：
🔴 S级：██ 2次
🟠 A级：██████ 6次
🟡 B级：████████████ 12次
🟢 C级：████ 4次
```

**热力图一眼就能告诉你：钱该花在哪。** 如果外部依赖事故最多，那是你该推动熔断/降级/监控建设；如果代码Bug最多但都是C级，那是工程规范问题，不是架构问题。

### 3.2 透镜二：时间轴聚类

把所有事故按发生时间排序，看：

> - 事故是不是集中在上线后1-3天？（= 发布质量有问题）
> - 有没有某个时间段事故密度突然升高？（= 当时可能在做大重构或赶进度）
> - 同类事故的间隔在缩短还是在拉长？（= 在恶化还是在收敛）
> - 有没有"一个事故引发连锁反应"的？（= 耦合太紧，隔离不够）

### 3.3 透镜三：发现方式统计

每个事故是谁发现的：

| 发现方式 | 数量 | 说明 |
|---------|------|------|
| 客户投诉发现 | | 监控没覆盖的点 |
| 客服巡检发现 | | 靠人肉，不可靠 |
| 监控告警发现 | | 监控覆盖到位 |
| 技术自查发现 | | 偶然发现，更可怕 |

**客户投诉发现的比例越高，说明监控盲区越大。** 你能靠人肉传感器（商务/客服）补一部分，但不能靠他们当监控。

### 3.4 透镜四：修复质量回看

对于已经关闭的事故，快速看两点：

> - **修复方式**：是改了代码（治本）、改了配置（治标）、还是加了监控就关了（只监测不修复）？
> - **是否复发**：同一个事故后来有没有再出现过？

**加了监控就关了的事故 = 技术债，迟早会回来。**

## 四、交叉分析：原型和事故报告一起看

这是最有价值的一步。把两份审查结果放一起：

### 4.1 事故是否暴露了原型没考虑的场景？

> 案例：事故报告显示"客户在基差交易中修改了定价公式导致结算异常"。
> 对照原型：基差交易的原型里，定价公式修改有没有被设计成关键操作？有没有二次确认？有没有权限控制？

**这类交叉发现直接产出"功能加固清单"。**

### 4.2 原型中反复出现但线上事故频发的模块

> 原型里"履约管理"模块设计了很复杂的流程，迭代了5版原型。
> 事故报告里"履约状态不一致"出现了3次。
>
> → 信号：这个模块的业务复杂度超过了当时的架构设计能力。需要重新审视数据一致性方案。

### 4.3 原型里没出现、但事故里暴露了真实使用方式的场景

> 原型假设客户单品种交易。
> 事故报告显示客户在"一单多品种"操作时导致拆分逻辑错误。
>
> → 信号：真实业务场景比原型假设的更复杂。需要跟商务确认"客户是不是经常一单多品种"。

## 五、执行步骤（按顺序来）

### 第一步：分类堆放（10分钟）

把所有材料分成三堆：

```
堆A：功能原型（业务流程设计）
堆B：页面原型（UI/交互设计）  
堆C：事故报告
```

先看堆C——事故报告是你最缺的真相。原型可以慢慢看。

### 第二步：快速扫描堆C，填分类表（30-45分钟）

每份事故报告只提取6个字段，不需要读完：

| 字段 | 从哪里找 |
|------|---------|
| 日期 | 第一页 |
| 模块 | 标题/概述 |
| 根因一句话 | 根因分析/结论 |
| 根因类型 | 你判断（🐛🏗️⚙️🔗📈👤六选一） |
| 影响级别 | 你判断（🔴🟠🟡🟢四选一） |
| 谁发现的 | 报告里一般会写 |

**不要陷进细节。** 目标是把所有事故做完分类统计，不是把每一份读透。

### 第三步：统计→画两张图（10分钟）

1. 根因类型分布柱状图——哪类最高？
2. 影响级别分布——S+A级占比多少？

这两张图就是你跟老板/团队沟通的弹药。

### 第四步：挑3份重点读（20分钟）

- 挑1份S级（最严重）——完整读，关注根因和修复措施
- 挑1份根因类型最多的那种——理解这类问题的典型模式
- 挑1份"客户投诉发现"的——理解监控盲区长什么样

### 第五步：扫原型，只看"差异"（30-45分钟）

不读每个页面。只找：

1. 原型有、线上没有的功能 → 记下来，标注"为什么没做？现在还成立吗？"
2. 原型和你知道的线上流程明显不一样的地方 → 记下来，标注"谁改了？为什么？"
3. 原型里业务流程的"Happy Path"旁边用红笔画一笔——"异常路径画了吗？"

### 第六步：填交叉发现表（15分钟）

把第四步和第五步的发现放一起，看有没有能交叉验证的。

花5分钟填完这张表，你的"看一遍"就值了：

```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━

一、事故报告的三个核心发现：
1. [根因类型]最高的是______，占___%
2. S+A级事故共___次，集中在______模块
3. 客户投诉发现的事故占___%，监控盲区在______

二、原型的三个核心发现：
1. 有___个功能原型设计了但没上线，其中最值得重新评估的是______
2. 有___个流程的原型和线上不一致，原因是______
3. 有___个流程只画了正常路径，漏了异常处理

三、交叉发现的三个关键信号：
1. [模块名]：原型设计复杂 + 事故频率高 → 建议重新审视架构
2. [场景]：原型假设A + 事故暴露B → 建议跟商务确认真实业务流
3. [外部依赖]：事故集中在XX接口 → 建议优先建设熔断/监控
```

## 附：事故报告快速分类速查卡

打印出来放在旁边，每看一份打一个标签：

```
这份事故报告：

根因类型：□🐛代码Bug  □🏗️设计缺陷  □⚙️配置/数据  □🔗外部依赖  □📈容量/性能  □👤操作失误
影响级别：□🔴S级(交易中断/资金)  □🟠A级(核心功能)  □🟡B级(非核心)  □🟢C级(体验)
发现方式：□客户投诉  □客服巡检  □监控告警  □技术自查  □外部通知
修复方式：□代码修复  □配置修改  □加监控  □未修复/降级
是否复发：□是（第___次）  □否  □不确定

一句话根因：_________________________________
```
