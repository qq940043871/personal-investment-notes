区块链项目 总览 节点部署 钱包与充提 余额对账

数字资产充提与对账 · 项目总览

Crypto Deposit & Withdrawal — 自建 BTC / ETH 节点 + 钱包对接 + 日终余额校合，让平台能安全地收发数字资产并算得清账。

后端开发（节点与钱包） BTC / Omni / ETH JSON-RPC 按区块高度对账

项目背景：平台要支持数字资产充值 / 提币，但当时既没有现成的托管服务，也找不到能覆盖「多币种 + 对账」的通用组件。自建这套东西真正的难点是三处：① 币种异构——BTC、Omni-USDT、ETH 是三套完全不同的 RPC 与地址 / 私钥格式，余额语义也不一样（UTXO vs 账户模型）；② 到账语义——链上「已广播」不等于「已到账」，必须等确认数，还要考虑分叉回滚；③ 账要算得平——系统里的余额是按业务流水累加出来的，链上余额是节点给的，两者必须每天对得上，对不上要能定位到哪一笔。

我的角色：后端开发，负责节点侧与钱包侧的全部对接：节点编译部署与运维、JSON-RPC 封装、地址与私钥处理、区块监听与入账、提币广播与状态回写、日终余额校合。关键判断有两个：① 不依赖第三方托管接口，自己跑全节点——托管方一旦停服，用户的币就取不出来，这是不能接受的单点；② 账务推进只认「区块高度游标」，不认「轮询时的时间窗」——按时间窗扫会漏块，按高度推进才能保证「一块都不丢」，且重启后能精确续扫。

四个能力模块

1. 节点部署与运维

BTC 从源码编译（依赖 Berkeley DB 4.8 单独编译、指定 prefix），ETH 用 Geth，都先在测试网跑通再上主网；节点以无图形界面的服务端模式常驻。

我的关注点：BTC 编译最容易卡在 BDB 4.8 上——系统自带的是 5.x/6.x，钱包功能必须用 4.8，所以要单独下载编译并用 --with-incompatible-bdb 指定。这类环境问题在文档里往往一句带过，但实际会卡掉一整天。

2. 地址、私钥与钱包

为每个用户生成独立充值地址；私钥以 WIF（Base58Check） 形式保存，兼容压缩 / 非压缩公钥；ETH 侧对应用户地址与 keystore。

我的关注点：地址与私钥的版本前缀决定一切：0x00 是主网地址（1 开头）、0x05 是 P2SH（3 开头）、0x6F 是测试网（m/n 开头）、0x80 是私钥 WIF（5 / K / L 开头）。测试网私钥误用于主网、或压缩标记漏写，产出的地址就是「钱打进去取不出来」的地址。

3. 充值监听与提币

监听线程按区块高度逐块扫描，命中平台地址即生成充值流水；确认数达标后才上账。提币走节点广播，状态与手续费回写核心系统。

我的关注点：监听线程必须带 while 循环重试——调 JSON-RPC 取区块时网络抖动很常见，一次失败就退出的话，这个高度就永远漏了。另外 Omni 与 BTC 共用同一条链，扫块时如果不把 Omni 的交易过滤掉，会被误判成一笔普通 BTC 充值。

4. 日终余额校合

账户余额按「地址 + 区块高度」记账；每天用「期初 + 充值 − 提现 − 手续费 = 期末」对链上余额校一遍，差额不为 0 即不通过，再按明细逐笔定位。

我的关注点：余额必须带高度维度，否则「多少高度时的余额」说不清，链上一回滚就对不上。对账不是「跑个总账看平不平」，而是用明细重算一遍系统余额，再和链上余额比——只有这样才能在差额出现时直接指到具体交易。

实现：按高度推进的区块游标

整个系统的「正确性锚点」就是一件事：扫到哪个高度了，必须持久化。有了这个游标，重启能续扫、漏块能补扫、对账能复算——所有后续逻辑都建立在它上面。 

/**
 * 区块监听：从游标高度逐块推进，RPC 失败不退出、只重试
 * 关键约束：游标只在「本块处理完」之后才前移，否则会漏块
 */
public void listen(String chain) {
    long cursor = cursorRepo.get(chain);          // 已处理到的区块高度，持久化

    while (running) {
        try {
            long tip = rpc.call("getblockcount", Long.class);
            while (cursor < tip) {
                String hash  = rpc.call("getblockhash", String.class, cursor + 1);
                Block  block = rpc.call("getblock", Block.class, hash, 2);

                for (Tx tx : block.getTx()) {
                    // Omni 与 BTC 同链：先按协议层过滤，避免把 Omni 交易当成 BTC 充值
                    if (isOmniTx(tx) && !"OMNI".equals(chain)) continue;
                    for (Out out : tx.getVout()) {
                        if (isPlatformAddress(out.getScriptPubKey())) {
                            depositService.record(chain, out, cursor + 1);   // 幂等：按 txid + vout 去重
                        }
                    }
                }

                cursorRepo.save(chain, ++cursor);      // 本块处理完才前移
            }
        } catch (Exception e) {
            log.warn("区块拉取失败，稍后重试: {}", e.getMessage());
        }
        sleepQuietly(3000);                            // 不退出循环，避免该高度永久丢失
    }
}

日终校合

闭环里最容易漏掉的是倒数第二环：状态与手续费的「回写」。提币的最终状态（成功 / 失败）与真实手续费都不是平台自己算出来的，而是从链上查回来的——不回写，系统余额就会和链上余额慢慢裂开一条缝，最后变成对不上账的差额。

  • 地址：一用户一地址，私钥 WIF 加密保存，版本前缀严格区分网络；
  • 到账：按高度逐块扫，txid + vout 幂等去重，确认数达标才上账；
  • 提币：广播后起独立线程查状态，把 results 与 fee 回写核心；
  • 对账：明细重算系统余额，按高度与链上余额比对，差额落到交易级。

行业背景（一句话）

数字资产充提在这个行业里的地位很微妙：它不是核心业务，但一旦出错就是「钱」的事故。所以主流方案只有两条——接第三方托管（省事但受制于人）或自建节点（可控但要自己扛运维与对账）。我这段经历走的是后者。
