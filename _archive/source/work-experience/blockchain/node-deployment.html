节点部署与运维

Node Deployment — 从源码把 BTC 编出来、把 ETH 跑起来，先在测试网验证，再上主网

Ubuntu / CentOS Berkeley DB 4.8 JSON-RPC 测试网先行

场景背景：要让平台能收发链上资产，第一步不是写业务代码，而是先有一台自己能完全掌控的节点。这一步的坑几乎全在环境上：BTC 的钱包功能依赖 Berkeley DB 4.8（系统源里的版本太新，必须单独编译），编译参数、依赖包、Qt / 无界面模式的选择都会决定后面能不能正常开钱包；ETH 侧则是 Geth 的同步模式与 RPC 开放范围。这些都不是「写代码」的问题，但任何一步错了，后面所有业务逻辑都无从谈起。

我的角色：节点的编译、部署与 RPC 封装。方法论很简单但很有效：测试网跑通再上主网——测试网可以随便发币、随便失败，主网一次错误的地址生成就是真金白银。RPC 层我封成一个薄客户端，业务代码只调方法名、不关心 HTTP 细节，换币种只换配置。

四个模块

1. BTC 源码编译

准备 build-essential / libtool / autoconf / libssl / boost / Qt 等依赖，单独编译 BDB 4.8 到独立 prefix，再用它作为钱包数据库编译 BTC 本体。

我的关注点：BDB 必须是 4.8 且装在独立 prefix，编译时用 --with-incompatible-bdb --with-gui=no 指过去。不这么做，要么编不过，要么编过了但钱包功能不可用——而「钱包不可用」在启动时才暴露，排查成本远高于一开始就配对。

2. 服务端模式常驻

生产环境跑无图形界面的服务端模式（daemon），配 bitcoin.conf 的 RPC 用户密码、数据目录与监听端口；本机开发时可用图形界面模式排查。

我的关注点：RPC 端口绝不暴露到公网——节点 RPC 一旦可被外部调用，等于把钱包交出去。只允许本地或内网访问，跨机访问走 SSH 隧道或内网网关，这是一条不需要讨论的红线。

3. JSON-RPC 封装

统一的 rpcClient.invoke(method, params, Type) 入口，业务侧只关心「查余额」「发交易」这类语义，不写 HTTP 与序列化。

我的关注点：封装层要统一超时与错误语义。节点在同步、钱包在加密锁定时返回的都是不同错误码，如果业务侧各自 catch，很快就会演变成「有的地方重试、有的地方直接失败」。重试策略收敛在封装层，上层只管拿结果。

4. 测试网验证与节点健康检查

上线前在测试网完整走一遍：建地址、领测试币、发交易、查确认、查余额；上线后用 getinfo / getmininginfo 之类的接口做节点健康探活。

我的关注点：健康检查要看「区块高度有没有在涨」而不是「进程还在不在」。节点进程活着但停止同步（磁盘满、对等节点掉光）是最常见的故障形态，只看进程存活会把这种「假活」判成正常。

实现：BDB 4.8 与 RPC 封装

左边是那段「必须先做对」的编译步骤，右边是业务代码真正会碰到的那一层封装。前者决定节点能不能用，后者决定业务代码写起来干不干净。 

# 1) 单独编译 Berkeley DB 4.8（系统源里的版本过新，钱包不能用）
BDB_PREFIX=$(pwd)/db4 && mkdir -p $BDB_PREFIX
wget https://download.oracle.com/berkeley-db/db-4.8.30.NC.tar.gz
tar -xzvf db-4.8.30.NC.tar.gz && cd db-4.8.30.NC/build_unix
../dist/configure --enable-cxx --disable-shared --with-pic --prefix=$BDB_PREFIX
make && make install

# 2) 用这份 BDB 编译 BTC（无图形界面，服务端模式）
./autogen.sh
./configure --with-gui=no --with-incompatible-bdb \
            BDB_LIBS="-L${BDB_PREFIX}/lib -ldb_cxx-4.8" \
            BDB_CFLAGS="-I${BDB_PREFIX}/include"
make -j$(nproc)

# 3) 服务端起节点（RPC 只监听内网/本地）
./src/bitcoind -daemon -conf=/etc/bitcoin/bitcoin.conf
/** RPC 薄封装：业务侧只关心「查余额 / 发交易」，超时与重试收敛在这里 */
public class RpcClient {

    public <T> T invoke(String method, Object[] params, Class<T> type) {
        for (int i = 0; i < 3; i++) {
            try {
                JsonNode resp = post(buildRequest(method, params));   // HTTP Basic Auth
                if (resp.has("error") && !resp.get("error").isNull()) {
                    throw new RpcException(resp.get("error").toString());
                }
                return mapper.convertValue(resp.get("result"), type);
            } catch (IOException e) {
                if (i == 2) throw new RpcException("RPC 连续失败: " + method, e);
                sleepQuietly(1000L << i);                            // 1s / 2s / 4s
            }
        }
        return null;
    }
}

健康探活

这条链上真正花时间的不是「编译成功」，而是把环境差异消掉：Ubuntu 与 CentOS 的依赖包名不同、Java 路径不同、libtool 缺失的报错方式也不同。我把这些差异整理成了步骤化笔记（见侧边栏「技术笔记」），下次换机器照着走，而不是重新踩一遍。

  • 编译：BDB 4.8 独立 prefix，钱包能力才可用；
  • 运行：daemon 模式常驻，RPC 只对内网开放；
  • 验证：测试网走完建址 / 发币 / 确认 / 查余量全流程；
  • 运维：以「区块高度是否推进」作为健康判据。

行业背景（一句话）

自建节点的门槛几乎全在「环境」而不是「代码」：同一条链，不同发行版、不同依赖版本编出来的节点行为可能不一样。所以行业里做节点运维的团队，沉淀下来的从来不是代码，而是一份逐条验证过的部署清单。
