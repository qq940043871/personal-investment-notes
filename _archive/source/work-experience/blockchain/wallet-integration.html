钱包与充提

Wallet & Deposit/Withdraw — 一用户一地址、私钥严格编码、扫块入账、确认数达标才上账

WIF / Base58Check Omni 代币 充值监听 提币广播

场景背景：钱包这一层看起来只是「生成地址、发交易」，但它是整个系统里一旦出错就不可逆的地方。地址生成错一个字节，用户打进去的币就永远取不出来；私钥编码时压缩标记漏写，导出的 WIF 在别的钱包里会推导出另一个地址；扫块时没做好去重，同一笔充值会重复上账。这些错误都不会立刻报错，只会在几周后的对账里变成一个查不清的差额。

我的角色：钱包与充提链路的设计与实现。三条硬约束：① 地址与私钥的编码必须显式带网络参数，不做「默认主网」这种隐式假设；② 入账幂等键是 txid + vout，同一笔输出只允许上账一次；③ 提币状态与手续费以链上结果为准回写，平台自己算的手续费只能当预估值。

四个模块

1. 地址与私钥（WIF 编码）

每个用户分配一个独立充值地址；私钥以 WIF（Base58Check）形式导出，兼容压缩公钥（末尾补 0x01）。ETH 侧对应 keystore 与地址。

我的关注点：Base58Check 的结果由版本前缀决定：0x00 → 主网地址（1 开头）、0x05 → P2SH（3 开头）、0x6F → 测试网（m/n 开头）、0x80 → 私钥 WIF（5 / K / L 开头）、0x0142 → BIP38 加密私钥（6P 开头）。前缀错了不会报错，只会生成一个别的网络上的合法地址。

2. Omni 代币（USDT 那一类）

代币发行、查询属性、查余额、发起转账都通过 Omni 的 RPC 完成（如 omni_sendissuancefixed、omni_getbalance、omni_listproperties），底层仍是 BTC 交易。

我的关注点：Omni 的资产靠 property id 区分：1 是 Omni 本体、2 是测试 Omni，2147483651 对应 BTC，自建测试代币用的是 2147483652。查余额必须同时给地址和 property id——只给地址会拿到默认资产，看起来「余额是对的」，其实查错了币。

3. 充值监听与入账

扫块时把输出脚本与平台地址表比对，命中即生成「待确认」充值；确认数达到阈值再转为「已上账」，用户余额才变。

我的关注点：「广播成功」和「到账」必须分成两个状态。0 确认就上账，遇到链上重组（回滚）时用户已经拿这笔钱去交易了，平台只能自担损失。确认数阈值就是用来买这段时间的安全边际的。

4. 提币、归集与状态回写

提币签名并广播后写回 txid；散落在各用户地址上的币按策略归集到主钱包；最终状态与真实手续费从链上查回来再更新。

我的关注点：回写是一个独立线程干的事，不能挂在提币请求里等。一笔提币从广播到确认可能几分钟也可能几小时，请求线程等不起；而状态不回写，系统余额就会和链上余额慢慢裂开。

实现：私钥编码与幂等入账

两段代码对应两个最容易出错的点：私钥编码（压缩标记不能漏）与入账幂等（同一 txid + vout 只能成功一次）。 

/** WIF 编码：32 字节私钥 + 压缩标记(0x01) + 版本前缀(0x80)，再做 Base58Check */
private static byte[] encode(byte[] keyBytes, boolean compressed) {
    Preconditions.checkArgument(keyBytes.length == 32, "私钥必须是 32 字节");
    if (!compressed) return keyBytes;               // 非压缩：原样 32 字节

    byte[] out = new byte[33];                      // 压缩：末尾补 0x01
    System.arraycopy(keyBytes, 0, out, 0, 32);
    out[32] = 1;
    return out;
}

/** 导出 WIF：网络参数显式传入，绝不用「默认主网」 */
public DumpedPrivateKey exportWif(ECKey key, NetworkParameters params) {
    return new DumpedPrivateKey(params, key.getPrivKeyBytes(), key.isCompressed());
}
/**
 * 充值入账：幂等键 = txid + vout
 * 同一笔输出无论被扫到几次（重扫、补扫、重启后重叠），只会成功一次
 */
public void record(String chain, TxOut out, long height) {
    String key = chain + ":" + out.getTxid() + ":" + out.getN();

    if (!dedupRepo.tryLock(key)) return;             // 已处理过，直接跳过

    Deposit d = Deposit.builder()
        .chain(chain).txid(out.getTxid()).vout(out.getN())
        .address(out.getAddress()).amount(out.getValue())
        .height(height).status(DepositStatus.PENDING)   // 待确认，不是已到账
        .build();
    depositRepo.save(d);
}

闭环：一笔充值从链上到账上

用户充值到专属地址

扫块命中地址

待确认（等 N 个块）

确认达标上账

归集到主钱包

这条链上「待确认」这个状态不是多余的中间态，而是整条资金链路的安全垫：它把「链上已经发生但还可能被回滚」的时间窗，和「平台已经认账」这件事严格隔开。

  • 地址：一用户一址，私钥 WIF 加密存储，网络参数显式；
  • 入账：txid + vout 幂等，重复扫到不重复记；
  • 确认：PENDING → CREDITED 由确认数驱动，不由时间驱动；
  • 归集：零散余额汇入主钱包，为提币提供流动性。

行业背景（一句话）

钱包对接在行业里的分工很明确：能自己控制的只有私钥，其余的都要以链上为准。平台算的余额、预估的手续费、以为的状态，都只是「本地视图」，最终解释权在链上——这也是所有对账工作存在的原因。
