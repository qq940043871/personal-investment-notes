余额对账

Balance Reconciliation — 用明细重算一遍系统余额，再跟链上余额比，差额要能落到具体那笔交易

地址 + 高度记账 期初 + 充值 − 提现 − 手续费 差值必须为 0 历史数据修复

场景背景：数字资产的对账比法币难得多，因为「账」有两本，而且其中一本不受你控制：一本是平台按业务流水累加出来的余额，另一本是节点返回的链上真实余额。两本账只要有一条记录错位，差额就会永远存在——而差额不会自己说明原因。更麻烦的是链上余额随时间变化（有手续费、有归集、有待确认），不比同一时刻的数据，比出来的差额毫无意义。

我的角色：对账模型的设计与实现。两个关键设计：① 余额带高度维度——记成「地址 + 区块高度 → 余额」，这样任何一笔对账都能说清「比的是哪个时刻的链上状态」；② 对账分两层——先比总额（快、能发现问题），再用明细逐笔重算系统余额（慢、能定位问题）。只做第一层等于只知道「账不对」，做不了第二层等于永远修不好。

四个模块

1. 余额快照（地址 + 高度）

链上余额按「地址 + 区块高度」落快照，例如某地址在高度 1003 时余额为 220。对账时取同一高度的两侧数据比，而不是「现在」跟「昨天」比。

我的关注点：没有高度维度的余额是不可对账的余额——链上余额每几分钟就变一次，你拿今天 10:00 的链上余额和昨天 23:59 的系统余额比，差额里混着「时间差」而不是「差错」。这是对账做不准的第一个根因。

2. 按明细重算系统余额

拉出「币种 / 地址 / 交易 hash / 高度 / 收支类型 / 金额 / 手续费」的明细，从零累加一遍，得到「系统本该是多少」。这一步不信任任何缓存余额。

我的关注点：明细里必须有手续费字段，而且必须是链上真实值。缺这一列，重算结果就永远比链上多出「手续费之和」——这不是差错，是模型缺陷，但表现出来和差错一模一样，会浪费大量排查时间。

3. 平衡关系校验

每个币种每天一行：期初 → 充值 → 提现 → 手续费 → 期末 → 链上余额 → 差值 → 平衡结果。差值不为 0 直接判「不通过」，并锁定该币种当天的明细。

我的关注点：公式要写死成一条：期末 = 期初 + 充值 − 提现 − 手续费，差值 = 链上余额 − 期末。「平衡结果」是一列显式字段而不是靠人看——对账的价值就在于把判断交给规则，而不是交给盯着表格的眼睛。

4. 差额定位与历史修复

对不平时先看差额形态：等于某几笔手续费之和 → 手续费没回写；等于某笔金额 → 漏记或重复记。历史差额用「独立线程重查所有提现状态 → 回写核心 → 修正状态与手续费」的方式补齐。

我的关注点：修复绝不能直接改余额。正确做法是补齐缺失的明细记录（尤其手续费与最终状态），让「重算」自然算出正确结果——直接改余额会把差错从「可解释」变成「不可解释」，下次对账更查不清。

对账表长什么样

一张表就是一套校验规则。下面用一组示意数据说明结构（真实数据按币种、按日跑）：

币种 期初 充值 提现 手续费 期末（算） 链上余额 差值 结果
ETH 300 0 50 0.3 249.7 249.7 0 通过
BTC 2.0 0.5 0.2 0.0004 2.2996 2.2990 -0.0006 不通过

BTC 那行的差额 −0.0006 大于本日手续费 0.0004，说明除了「手续费漏回写」之外还有别的缺口（例如某笔提现的状态未更新）。差额的绝对值与形态本身就是线索：和手续费同量级先查回写，和某笔金额同量级先查重复入账。

实现：一次对账就是一次重算

对账代码刻意不读「余额表」，只读明细：明细是真事实，余额表是派生物。派生物出错可以重建，事实出错才是事故。 

/**
 * 日终对账：期初 + 充值 - 提现 - 手续费 = 期末，再与同高度链上余额比
 * 注意：手续费取自「链上真实值」，不是平台预估值
 */
public ReconciliationRow reconcile(String coin, LocalDate day, long height) {
    BigDecimal opening  = snapshotRepo.balanceAt(coin, day.minusDays(1), height);
    BigDecimal deposits = detailRepo.sumIn(coin, day);       // 类型 = 入
    BigDecimal withdraw = detailRepo.sumOut(coin, day);      // 类型 = 出
    BigDecimal fee      = detailRepo.sumFee(coin, day);      // 链上真实手续费

    BigDecimal closing = opening.add(deposits).subtract(withdraw).subtract(fee);
    BigDecimal onChain = chainRepo.balanceAt(coin, height);   // 同一高度，可比
    BigDecimal diff    = onChain.subtract(closing);

    return ReconciliationRow.builder()
        .coin(coin).day(day).height(height)
        .opening(opening).deposits(deposits).withdraw(withdraw).fee(fee)
        .closing(closing).onChain(onChain).diff(diff)
        .passed(diff.signum() == 0)                            // 结果由规则判定，不由人看
        .build();
}

/** 历史差额修复：补齐明细，而不是直接改余额 */
public void repair(String coin) {
    for (Withdraw w : withdrawRepo.findAllUncertain(coin)) {
        ChainTx tx = rpc.call("gettransaction", ChainTx.class, w.getTxid());
        withdrawRepo.updateStatusAndFee(w.getId(), tx.getStatus(), tx.getFee());  // 回写真相
    }
    // 下一轮对账会自然算出正确余额
}

闭环：快照 → 重算 → 比对 → 修复

同高度快照

明细重算

比对定差值

差额下钻

补明细 / 再对账

这条闭环的终点不是「差额清零」，而是「每一笔差额都能被解释」。人工改平余额可以骗过当天的报表，但会让下一次对账失去所有线索——所以修复动作永远只做在明细层。

  • 快照：按地址 + 高度取链上余额，保证两侧同一时刻；
  • 重算：只信明细，不读余额表（余额是派生物，可重建）；
  • 比对：一条公式 + 一列显式结论，差值非 0 即拦截；
  • 修复：补齐缺失的手续费与状态，让重算自然回到平衡。

行业背景（一句话）

在资金类系统里，对账不是财务的收尾动作，而是系统的最后一道正确性验证：它用一条独立的路径（明细累加）去校验主路径（余额更新）的结果。凡是不能对账的资金系统，本质上都只是「看起来在正常跑」。

关键点与结果

两侧同一时刻

地址 + 高度快照，剔除时间差干扰

只信明细

从零累加重算，不信任缓存余额

结论由规则给

差值非 0 即不通过，不靠人眼判断

差额有形态

按量级反推：手续费未回写 / 重复入账

修复在明细层

补真相不改余额，下次对账自然平
