视频下载

Download — 把录像「拿走」的最后一公里：批量、转码、断点续传、签名链接

批量打包 格式转换 断点续传 签名有效期

场景背景：下载这个动作的触发方往往不是值班员，而是公安、保险、法务、上级单位——他们要的是「一段指定时间、指定摄像头、能直接播放的文件」，而且经常一次要好几段。所以下载功能真正的难点不是「给个链接」，而是：大文件不能把服务器拖住、格式要能对上对方电脑里的播放器、手机弱网断了要能续、链接不能被到处转发。

我的角色：下载链路的方案设计与实现。核心判断是把下载定性为异步任务而不是同步接口：转码要跑 FFmpeg、打包要写 ZIP，都是分钟级操作，一旦放在 HTTP 请求里，连接会被网关超时掐断，用户只看到失败。所以设计成「提交任务 → 轮询进度 → 拿带签名的结果链接」三步。

四个模块

1. 单文件与批量打包

选中一段直接下；选中多段则后台打成 ZIP 一次下完，避免「点十次、十次弹窗、十次找路径」。任务列表里能看到每个任务的状态。

我的关注点：批量不是循环调用单文件下载——那样会并发起 N 个转码进程把 CPU 吃干。批量走一条任务 + 串行打包，进度按「已完成段数 / 总段数」上报，资源占用可控、进度也真实。

2. 格式转换（MP4 / AVI / MKV）

默认给 MP4（兼容性最好），可要求转 AVI / MKV 以适配收件方指定的播放器或编辑软件。

我的关注点：能只换容器不重编码就绝不重编码——-c copy 是秒级操作，重编码是分钟级且画质有损。只有当目标格式与源编码不兼容时才降级为真转码，这个判断必须在任务提交时就做完。

3. 断点续传与大文件传输

小时级录像动辄几百 MB 到几 GB，手机或弱网环境断线是常态。响应头声明 Accept-Ranges: bytes，按 Range 分块续传，断了接着下。

我的关注点：分块读取必须边读边 flush且严格按 Content-Range 的起止发完就停，多发一个字节客户端就会判定文件损坏——这种问题在本地测试永远复现不了，只有大文件 + 弱网才暴露。

4. 签名链接与任务管理

下载地址带 token 与有效期（24 小时），过期即失效；任务列表展示 PENDING / PROCESSING / COMPLETED / FAILED 四态与实时进度。

我的关注点：任务状态机只有四个态、单向流转，失败可重试但必须新建任务——不原地改状态。这样「这个文件到底有没有成功下过」永远有记录可查，事后不会被问住。

实现：异步任务 + Range 续传

两个关键片段：① 提交即返回 taskId，真正的转码 / 打包在异步线程里跑，进度写进进度表供轮询；② 大文件出口按 Range 分块，客户端断线重连能接着下。 

@Service
public class DownloadService {

    /** 只换容器就 -c copy（秒级）；不兼容才重编码（分钟级） */
    private String convert(String in, String format, String taskId) throws Exception {
        String out = in.replace(".mp4", "." + format);
        Process p = Runtime.getRuntime().exec(
            String.format("ffmpeg -i %s -c copy %s", in, out));   // 不重编码
        p.waitFor();
        return out;
    }

    /** 大文件出口：声明可续传，按 Range 起止精确发完即停 */
    public void stream(String path, HttpServletResponse resp) throws Exception {
        File f = new File(path);
        resp.setHeader("Accept-Ranges", "bytes");
        resp.setHeader("Content-Type", "application/octet-stream");

        long start = 0, end = f.length() - 1;
        String range = resp.getHeader("Range");     // 由容器解析后传入
        if (range != null && range.startsWith("bytes=")) {
            String[] parts = range.substring(6).split("-");
            if (!parts[0].isEmpty()) start = Long.parseLong(parts[0]);
            if (parts.length > 1 && !parts[1].isEmpty()) end = Long.parseLong(parts[1]);
            resp.setStatus(206);                    // Partial Content
            resp.setHeader("Content-Range", "bytes " + start + "-" + end + "/" + f.length());
        }

        try (RandomAccessFile raf = new RandomAccessFile(f, "r");
             OutputStream os = resp.getOutputStream()) {
            raf.seek(start);
            byte[] buf = new byte[8192];
            long left = end - start + 1;
            int n;
            while (left > 0 && (n = raf.read(buf, 0, (int) Math.min(buf.length, left))) != -1) {
                os.write(buf, 0, n);
                os.flush();
                left -= n;
            }
        }
    }
}

这条链的设计原则只有一句：HTTP 请求只负责「下单」，不负责「干活」。一旦把 FFmpeg 塞进请求线程，等待时间必然超过网关超时，功能在演示时正常、在真实大文件上必坏。

  • 下单：校验录像存在 + 判断要不要真转码，立刻返回 taskId；
  • 干活：线程池执行，进度写表，失败落错误信息；
  • 取件：完成后发带 token 的链接，24 小时有效；
  • 传输：支持 Range 续传，手机断网不重下。

行业背景（一句话）

监控录像在多数行业里是「证据」而不是「内容」：它要能被交出去、能在别人的电脑上播放、能证明没被篡改。所以下载功能本质上是一次合规交付，稳定性与可追溯性比速度重要得多。
