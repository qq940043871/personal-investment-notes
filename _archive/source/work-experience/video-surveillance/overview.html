视频监控平台 · 项目总览

Video Surveillance Platform — 用 FFmpeg + ZLMediaKit 搭一层流媒体底座，把存量 RTSP 摄像头变成 Web 端「可看、可回、可取证」的能力。

流媒体方案负责人 单机 50–100 路 WebRTC < 500ms PC / 手机同源

项目背景：客户现场已经装了几十上百个 RTSP 摄像头，但看画面还得回机房打开 NVR 客户端——装软件、配 IP、只能在局域网。手机看不了、领导远程看不了、出事调录像只能按文件名一个个拖。自研一套 Web 端监控，真正的难点不在「能播」，而在四件事：一路摄像头要被 N 个人同时看（直连摄像头必死）、浏览器不认 RTSP、弱网 / 手机 / 大屏三类终端对延迟与兼容的要求互相打架、录像要按事件回溯而不是按文件翻。我用 FFmpeg + ZLMediaKit 搭了一层流媒体底座，把这四件事收敛成一套入口。

我的角色：流媒体方案的技术负责人（选型 + 落地）。选型上否决了「商用 NVR 厂商 SDK 按路授权」和「海外 SaaS 中转」两条路——前者按路收费、绑死客户端，后者把视频流交给第三方且延迟不可控；最终定下开源底座 + 自建分发。负责推流 / 录制链路设计、多协议降级策略，并把「摄像头侧、流媒体侧、业务库侧」三条线的边界划清。下文先讲四个能力模块，再讲它们如何汇入「接入 → 分发 → 观看 → 回溯 → 取证」这一条闭环。

四个能力模块

1. 实时直播

值班室盯屏的核心场景：多路画面同时预览（1/4/9/16 分屏）、云台 PTZ 上下左右与缩放、一键截图留证，PC 与手机都能看。看的是「此刻正在发生什么」。

我的关注点：一路 RTSP 只拉一次，由 ZLMediaKit 向多客户端分发——否则 10 个人看同一路摄像头就会把摄像头的并发连接打满甚至拖死。云台控制走 ONVIF 标准指令而不是厂商私有 SDK，换品牌不用重写。协议按终端能力自动选：PC 走 WebRTC，手机走 HLS。

2. 录像回放

事情发生之后要「倒回去看」：按日期与时间轴定位、0.5x–8x 倍速、快进快退 30 秒、告警片段在时间轴上高亮，随时截图。

我的关注点：录像「文件」与录像「记录」分开存——元数据（设备、起止时间、存储路径、是否告警）进 MySQL，MP4 文件进 NAS / OSS。检索永远查元数据，绝不去扫目录。播放地址用 OSS 预签名 URL（1 小时有效），不把存储桶直接暴露给前端。

3. 视频下载

取证与上报要「把文件拿走」：单个录像下载、多段录像打包成 ZIP、格式转换（MP4 / AVI / MKV）、断点续传、任务进度实时可见。

我的关注点：转码和打包都是分钟级长任务，全部丢进异步线程池 + 任务表，HTTP 线程绝不等 FFmpeg 跑完；大文件下载走 Accept-Ranges: bytes + Range 分块，手机断网重连能接着下，而不是从头再来一遍。

4. 流媒体底座（FFmpeg + ZLMediaKit）

不做业务、只做「把流搬对」：FFmpeg 从摄像头拉 RTSP 并转码，ZLMediaKit 一次输入产出 WebRTC / FLV / HLS 三种出口，业务层只拿 URL。

我的关注点：转码参数定死 -preset ultrafast -tune zerolatency -g 25，牺牲一点压缩率换实时性；开启 GOP 缓存让新观众一秒内出画（而不是等下一个关键帧）；码率与分辨率相同的流复用同一个转码进程，避免每来一个观看者就复制一份 CPU 开销。

实现：一套代码三档协议，按终端自动降级

四类终端的兼容性差异是最大的坑：Safari 不认 FLV、部分安卓浏览器 WebRTC 不可用、老设备只吃 HLS。与其做四套播放器，不如把「选协议」做成一条能力探测 + 逐级降级的链：能 WebRTC 就用 WebRTC，不能就 FLV，再不能就 HLS，手机直接 HLS。 

/**
 * 协议选择器：按「终端类型 + 浏览器能力」逐级降级
 * 手机：HLS（兼容优先，延迟 3-5s 可接受）
 * PC  ：WebRTC（<500ms）→ FLV（1-2s）→ HLS（兜底）
 */
const pickProtocol = (stream, ua = navigator.userAgent) => {
  const isMobile = /Android|iPhone|iPad|iPod/i.test(ua);
  if (isMobile) return { protocol: 'hls', url: stream.hlsUrl };

  if (window.RTCPeerConnection) return { protocol: 'webrtc', url: stream.webrtcUrl };
  if (flvjs.isSupported())      return { protocol: 'flv',    url: stream.flvUrl };
  return { protocol: 'hls', url: stream.hlsUrl };   // 最后一道兜底
};

/**
 * 播放器挂载：一次只持有一个实例，切协议前必须销毁旧实例
 * 否则同一个 <video> 上会叠加多个解码器，表现为内存暴涨 / 画面花屏
 */
const mount = (el, stream) => {
  destroyPlayer();                       // 幂等清理
  const { protocol, url } = pickProtocol(stream);
  if (protocol === 'webrtc') return playWebRTC(el, url);
  if (protocol === 'flv')    return playFLV(el, url);
  return playHLS(el, url);
};

闭环：接入 → 分发 → 观看 → 回溯 → 取证

摄像头接入

FFmpeg 拉流 / 转码

ZLMediaKit 分发

观看（三档协议）

录制归档

回放 / 下载取证

闭环的关键在于：「看直播」和「看录像」共用同一份归档。录像不是直播之外的另一条链路，而是同一条流的落盘结果，所以回放和下载永远不会「和刚才看到的不一样」。

  • 接入 → 分发：RTSP 只拉一次，分发给 N 个观看者，摄像头连接数恒定；
  • 分发 → 观看：按终端能力选 WebRTC / FLV / HLS，失败自动降级不黑屏；
  • 观看 → 归档：录制按时间段切片成 MP4，元数据入库并打上告警标记；
  • 归档 → 取证：回放按时间轴定位，下载可打包、转码、断点续传，链接带签名有效期。

行业背景（一句话）

园区、工地、仓储、门店的存量摄像头几乎全是 RTSP / ONVIF，出厂配套的客户端只在局域网能用，商用监控平台大多按路授权——几十上百路就是一笔持续的授权成本。开源自建的价值，就是把这笔「按路付费」变成「一台服务器的固定成本」。
