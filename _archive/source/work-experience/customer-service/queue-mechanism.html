排队机制

Queue Mechanism — 用一条 Redis ZSet 同时解决「优先级插队」「同优先级先来先服务」「按技能分队列」

ZSet 优先级队列 5 分钟超时提醒 按会话数负载均衡 第三方派单

场景背景：排队是客服系统里唯一一个「用户能实时感受到不公平」的地方。高峰时在线用户几百人、客服十几人，谁先被接、谁被跳过、等了多久，用户全盯着那个「前面还有 3 人」的数字。这里做错两件事会立刻出事：一是 VIP 插队把普通用户无限后推（体验崩塌），二是队列在内存里（服务一重启，所有排队的人凭空消失）。所以队列必须持久、顺序必须可解释。

我的角色：排队机制的设计与实现。核心设计是把「排队」压缩成一个 Redis ZSet + 一条 score 公式：score = (100 - 优先级) × 10¹² + 入队毫秒。高位放优先级、低位放时间戳，于是「优先级高者在前」和「同级先来先服务」用一次排序同时满足，不需要任何额外比较逻辑，也不怕并发插入。

四个模块

1. 按技能分队列 + 优先级排序

咨询按业务领域拆成多条队列（如「通用」「技术」「财务」），用户按问题标签入对应队列；同一队列内 VIP 优先、同级按入队时间先后。

我的关注点：队列 key 用 queue:{skill} 而不是一个全局队列——一条全局队列会让「懂技术的人」被迫接「财务问题」，接了也答不了，只能再转一次。分队列 + 技能标签是让「第一次就派对人」的前提。

2. 智能分配与负载均衡

用户入队后立刻尝试分配：在「在线 + 还有空位 + 技能匹配」的客服里，挑当前会话数最少的那个。

我的关注点：排序键是「当前会话数」而不是「谁先上线」。按上线顺序分配会把人累死在同一批客服身上——最先上线的那几个永远满负荷，后面的闲着。按会话数升序是最便宜也最有效的均衡策略，不需要引入权重算法。

3. 超时提醒与位次通知

定时任务每 30 秒扫一遍所有队列，等待超过 5 分钟的用户收到「已等待 N 分钟，请耐心等待」的实时提醒；用户随时可查自己前面还有几人。

我的关注点：位次用 ZRANK + 1 现算，不维护「位次」字段——队列每出一个人，全网所有人的位次都变，维护字段等于每次出队都要批量更新几百条记录，这是典型的自我制造的写热点。

4. 手动接入与第三方派单

客服可以越过队列直接接入某个排队用户；外部系统（如工单、订单系统）可通过带 API Key 的接口直接派单到指定客服。

我的关注点：手动接入和第三方派单都必须再校验一次客服剩余能力。绕开队列不等于绕开限制——否则「手动接入」会变成压垮某个客服的快捷方式，而且这种超载在监控里很难看出来。

实现：一条 score 公式撑起整个队列

入队只写两处：ZSet 定顺序、Hash 存用户信息（技能、入队时间、优先级）。出队时取 score 最小的那个，分配成功才真正移除——先分配、后出队，避免「人已经出队但分配失败」造成用户彻底失踪。 

@Service
public class QueueService {

    /** score 高位放优先级、低位放入队毫秒：一次排序同时满足插队与先来先服务 */
    private double score(int priority, long ts) {
        return (100 - priority) * 1_000_000_000_000L + ts;
    }

    public String enqueue(String userId, String skill, int priority) {
        String queueId = UUID.randomUUID().toString();
        String qKey = "queue:" + skill;

        redisTemplate.opsForZSet().add(qKey, queueId, score(priority, System.currentTimeMillis()));
        redisTemplate.opsForHash().putAll("queue_user:" + queueId, Map.of(
            "userId", userId, "skill", skill,
            "joinTime", System.currentTimeMillis(), "priority", priority));

        tryAssign(skill);                 // 入队即尝试分配，空闲客服不空转
        return queueId;
    }

    /** 分配：在线 + 有空位 + 技能匹配 三者交集，按当前会话数升序取人 */
    public void tryAssign(String skill) {
        List<CsUser> cs = capacityService.available(skill);
        if (cs.isEmpty()) return;

        Set<String> head = redisTemplate.opsForZSet().range("queue:" + skill, 0, 0);
        if (head == null || head.isEmpty()) return;

        String queueId = head.iterator().next();
        assign(queueId, cs.get(0).getCsId());            // 先建会话、再加计数
        redisTemplate.opsForZSet().remove("queue:" + skill, queueId);   // 成功后才出队
    }

    /** 位次现算，不维护字段（维护字段 = 每次出队批量更新，自造写热点） */
    public long position(String queueId, String skill) {
        Long rank = redisTemplate.opsForZSet().rank("queue:" + skill, queueId);
        return rank == null ? 0 : rank + 1;
    }
}

闭环：从入队到开始服务

用户入队

按 score 排序

挑空闲客服

建会话开始服务

出队并留记录

整条链上只有一处必须严格守序：「先建会话成功，再把人从队列里摘掉」。反过来做，一旦建会话失败，用户既不在队列里也没有客服——这是排队系统最典型的丢单方式，而且极难排查。

  • 入队：写 ZSet 定顺序 + 写 Hash 存上下文，立即尝试分配；
  • 等待：位次现算、30 秒巡检、5 分钟超时提醒；
  • 分配：三条件交集 + 会话数最少优先，避免偏科与偏载；
  • 兜底：手动接入与第三方派单同样校验剩余能力。

行业背景（一句话）

排队理论里有个残酷的结论：用户对「等待」的容忍度取决于「是否知道要等多久」，而不是等多久本身。所以大多数排队系统的优化重点不是缩短队列，而是让位次、预计时间、超时提醒变得可信。
