在线客服系统 · 项目总览

Customer Service System — Spring Boot + Netty + Redis，把「用户提问 → 智能首答 → 人工排队 → 会话归档」做成一条不丢消息的链路。

后端负责人 Netty WebSocket Redis 全量存储 RAG 智能首答

项目背景：交易类业务的咨询有明显的时间潮汐——下单高峰与故障期间咨询量会瞬间放大几倍，其余时间人力大量闲置；同时用户的主入口在微信，但客服用的却是另一套企业内网系统。想做自研客服，要解的不是「有个聊天框」，而是四个问题：用户身份怎么统一（微信 / 第三方认证）、消息怎么实时送达且不丢（长连接而不是轮询）、人力怎么排队不浪费（技能匹配 + 优先级 + 超时提醒）、重复问题怎么不占人力（先让知识库答，答不了再转人工）。我用 Netty + Redis 把这条链路搭起来，把「能用」变成「扛得住高峰」。

我的角色：后端负责人（架构 + 核心链路实现）。两个关键技术决策：① 通信层不用 HTTP 轮询，直接用 Netty 做 WebSocket 长连接——轮询在高峰期的请求放大会把服务器压垮，而长连接是「有多少在线用户就有多少连接」的可预期成本；② 数据层不引入 MySQL 做在线态，在线用户、排队队列、会话消息、客服能力全部收敛到 Redis 的合适数据结构上，在线态天然带 TTL，不用写清理任务。下文先讲四个能力模块，再讲它们如何汇入「提问 → 首答 → 排队 → 接待 → 归档」这一条闭环。

四个能力模块

1. 接待客户（实时会话）

用户从微信进来，消息经过敏感词过滤后实时送达客服；客服可转接、可发文件；断线后自动重连，重连上还能看到之前的上下文。

我的关注点：长连接的难点从来不是「连上」，而是「断了之后怎么办」——客户端 3 秒自动重连、服务端用 Redis 里的在线表判定真实在线态，不以 Connection 对象是否存在为准（连接假死时对象还在，消息发出去就丢了）。消息先落 Redis 再转发，保证「存住的」和「发出的」是同一份。

2. 排队机制（谁先接谁）

无空闲客服时用户进入队列，实时告知「前面还有几人」；VIP 走优先级插队；排队超 5 分钟自动提醒；客服可手动接入，也支持外部系统直接派单。

我的关注点：队列用 Redis ZSet，score = (100 - 优先级) × 10¹² + 入队毫秒——这一条公式同时解决了「优先级高者在前」和「同优先级先到先服务」，不需要额外的排序逻辑。分配时按客服当前会话数升序挑人，天然是负载均衡。

3. 客服管理（能力与身份）

客服不单独建账号体系，直接对接企业已有的 LDAP / OAuth / SSO；每人配最大接待数、技能标签、在线状态；下线时会话自动转接，不把用户挂在空气里。

我的关注点：「能力」不是一个人数上限，而是「在线 + 还有空位 + 技能匹配」三个条件的交集。三个条件缺一个就不该派单，否则会出现「把财务问题派给只会查物流的客服」。下线转接也要做，不然客服一关页面，用户就永远等在那里。

4. 智能首答（先机器后人工）

用户发问先查知识库：命中就直接答（附带「回复转人工」提示），没命中才把用户推进人工队列。重复度最高的那些问题根本不占人力。

我的关注点：智能首答必须有「答不了」的明确出口。做不好这件事的系统会陷入更糟的体验：机器人反复打太极，用户被迫打「转人工」三个字。所以设计成精确匹配 → 相似度匹配（阈值 0.7）→ 直接转人工，宁可早转，不要瞎答。

实现：消息进 Redis 与转发的顺序

一段代码说清一件事：消息的处理顺序是「过滤 → 落库 → 转发」。落库在前是因为客服可能刚好断线——先存后发，重连后能补；先发后存在断线时消息就永久丢了。 

@Component
public class WebSocketServer {

    /** userId -> Channel：只代表「连接对象」，不代表「用户在线」，在线态以 Redis 为准 */
    private static final Map<String, Channel> CHANNELS = new ConcurrentHashMap<>();

    public void onMessage(String userId, String payload) {
        ChatMessage msg = JSON.parseObject(payload, ChatMessage.class);

        // 1. 敏感词过滤（Trie，内置 + 可选第三方）
        msg.setContent(sensitiveWordService.filter(msg.getContent()));

        // 2. 先落 Redis 再转发：断线重连后能补，不会因发送失败而丢
        redisTemplate.opsForList()
            .rightPush("chat_messages:" + msg.getSessionId(), msg);

        // 3. 智能首答：命中即答，未命中的自然进入人工排队流程
        if (msg.getType() == MessageType.USER) {
            String answer = ragService.getAnswer(msg.getContent());
            if (answer != null) send(msg.getFrom(), answer);
        }

        // 4. 转发给对话方（客服或用户）
        send(msg.getTo(), payload);
    }

    private void send(String userId, String payload) {
        Channel ch = CHANNELS.get(userId);
        if (ch != null && ch.isActive()) ch.writeAndFlush(new TextWebSocketFrame(payload));
    }
}

闭环：提问 → 首答 → 排队 → 接待 → 归档

人工接待

会话归档 / 统计

闭环的关键在于：用户从头到尾只有一个入口，中间换了几次「谁在答」他都不用知道。机器人答、人工答、客服转接，对用户来说都是同一个会话窗口；系统侧则靠 sessionId 把消息、记录、统计串起来。

  • 提问 → 首答：微信 OAuth 拿身份，消息同步落 Redis；
  • 首答 → 排队：未命中知识库则按技能入队，告知当前位次；
  • 排队 → 接待：按「在线 + 有空位 + 技能匹配」挑人，超时提醒；
  • 接待 → 归档：会话结束写记录与满意度，沉淀为可统计的数据。

行业背景（一句话）

客服系统的成本结构很特殊：按峰值配人一定浪费，按均值配人在峰值一定崩。所以这个行业的正解一直是「用机器扛住重复问题，用排队把人力削峰」，而不是单纯加人。

关键点与结果

长连接替代轮询

Netty WebSocket，高峰请求量不随刷新放大

在线态天然过期

Redis 承载在线表 / 队列 / 消息，靠 TTL 自清理

一条公式定排队

优先级 × 入队时间合成 score，VIP 插队且不乱序

重复问题不占人

知识库命中即答，阈值 0.7 未命中直接转人工

不新建账号体系

LDAP / OAuth / SSO 三种 Provider 可插拔

敏感内容可控

Trie 树实时过滤，内置词库 + 第三方检测双保险
