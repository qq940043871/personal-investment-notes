# 技术管理常遇问题与应答（需求沟通 · 代码质量）

> **定位**：本文件装的是**面试官高频追问的两类管理场景**——「需求评审」和「代码质量保障」。它不是话术稿，是把口述答案拆成**可判定的规则 + 落地点 + 口径护栏**的速查件：每题按「挑战拆解 → 处理策略（判定规则）→ 口径护栏 → 追问预案 → 权威指针」五段组织。
> **使用顺序**：先扫本文件拿骨架 → 讲通用管理口径回 `00-技术管理索引.md` → 被追问工具链细节翻 `02A-技术管理补充件.md` 第二部分 → 需要权威出处按文末指针表走。
> ⚠️ **口径纪律**：指标带限定语 / 脱敏类别名 / 20 人·13 年 / 技术栈不混——**全库只在 `00-技术管理索引.md` §六 维护一份**，本文件不复述，只引用。⚠️ 注意：索引 §六第 5 条仍写「CI 门禁 / Code Review 讲规划 + 在推」，其中 **Sonar 扫描与自研 jar 包检测已于本人 2026-11-26 确认「已实现」**，仅 **CI（持续集成）仍在规划**；本文件按新口径讲，遇到冲突以本文件护栏 3 为准。本文件额外钉死三条本题专属护栏，见 §三末。

## 一、需求评审类

### 问题 1：参与需求评审过程中，你遇到的最大挑战是什么？

#### 挑战拆解

口述里其实藏了两类完全不同的挑战，答的时候**必须拆开讲**，不然显得没结构：

| # | 挑战 | 本质 | 拆开讲的价值 |
|---|---|---|---|
| ① | 业务目标 vs 实现成本冲突（"一周上线" vs "按原方案一个月"） | **资源与范围的矛盾** | 考的是优先级判断和"给选择题而不是否决"的能力 |
| ② | 需求理解不到位、全链路不能闭环 | **信息不对称** | 考的是把模糊需求收敛成可验收事实的能力 |

> 一句话开场：**最大的挑战不是"做不完"，是"目标、成本、理解三者对不齐"——我的工作是先把它们对齐，再谈实现。**

---

#### 挑战① 业务目标 vs 实现成本冲突

**处理策略（四步判定，按顺序走，不跳步）：**

```
第 1 步：先问"能不能分期"
        ├─ 能分期 → 拆阶段，排优先级，先交最高价值切片
        └─ 不能分期（业务要的是完整能力，拆开没意义）
                   ↓
第 2 步：确认"是不是真有硬截止"
        └─ 有（展会 / 客户签约节点 / 政策窗口）→ 不能靠延期解决
                   ↓
第 3 步：做简化版（满足暂时使用），并列明后续补齐计划
                   ↓
第 4 步：红线校验 → 简化版 ≠ 半成品
```

**"简化版"的判定规则（关键，防止被追问打脸）：**

| 维度 | 简化版必须满足 | 半成品（禁止） |
|---|---|---|
| 核心闭环 | 主流程端到端可用，用户能完成一次真实业务 | 功能做一半，按钮点了报错 |
| 边界与异常 | 关键异常有兜底（失败可重试、有明确提示） | 只跑 happy path，异常直接崩 |
| 数据 | 数据结构可扩展，后续补齐不要求客户重录 | 临时字段、临时表，上线后要洗数据 |
| 后续计划 | **有补齐排期 + 责任人 + 时间点**，进技术债台账 | "以后再说"，无排期 |

> **红线（原话保留，别丢）**：**绝不出现"功能开发一半就发布给客户"**——简化版是"完整的小"，不是"残缺的大"。

**输出物三件套**（讲的时候甩出来，显得不是空谈）：分期方案 / 简化版范围清单 / 后续补齐排期。

**方法论落点**：这是 `../00-面试计划/10-面试训练手册.md` §3 三套框架的现场版——**先给边界，再给替代路径与代价，让业务方做选择题**，不是技术方单方面说"做不了"。分期后发现欠下的账，按技术债三分法登记（流血债 / 放血债 / 美容债，见同文件 §4.5）。

---

#### 挑战② 需求理解不到位、链路不能闭环

**处理策略（三步收敛，重点是"举例"）：**

| 步 | 动作 | 要点 |
|---|---|---|
| 1 | 先和产品沟通 | **把自己的疑问点举例列出来**，不是泛泛说"不清楚" |
| 2 | 举例要具体到可复述 | 每个疑问带**场景 + 输入 + 预期输出 + 异常分支**，举到具体单据 / 状态 / 角色 |
| 3 | 拉客户相关负责人开短会 | 对齐的是**业务事实**，不是文档措辞；目标是把整条链路走通、闭环 |

**"对齐了"的判定标准**（避免"会开完了但没人真懂"）：各方能用**同一组例子**复述同一流程，且**边界 / 状态 / 异常**三处无歧义。做不到就是没对齐，继续举例。

**落回闸门**：这一步不是额外流程，是 `00-技术管理索引.md` §三 ②「六道评审闸门」里**需求收口评审**的前置动作——把"需求不清"的返工挡在开发之前，与 `02A-技术管理补充件.md` 第一部分难点三（多租户非标定制 → 配置化主线）同源。

---

#### 追问预案（问题 1）

| 追问 | 应答骨架 |
|---|---|
| 简化版会不会变成永久版？ | 简化版必须带补齐排期 + 责任人，并进技术债台账；没有排期的简化版我不允许上——那不是简化，是埋雷 |
| 客户就是不同意分期怎么办？ | 给边界 + 替代路径 + 各自代价，让业务方做选择题；技术方不单方面否决，但"开发一半就发"这条底线不松 |
| 怎么判断是需求没讲清，还是产品能力真不足？ | 用"举例复述测试"：各方举同一场景，能复述一致 = 沟通问题；复述不出来且产品侧也无案例 = 能力缺口，走简化版或分期 |
| 分期会不会破坏跨月长事务的完整性？ | 分期按**业务闭环**切，不按技术模块切；跨月状态机的完整性在评审里单独盯（见 `02A` 第一部分难点四） |

### 问题 2：在技术管理过程中，你是如何审查同事的代码的？有哪些策略保证代码正确性？

> ⚠️ **开场先纠一个口误**：口述里说的是"审查客户的代码"——这是口误，正确说法是**审查同事 / 团队的代码**（内部 code review）。对客户交付的环节叫**检测 / 验收**，不存在"审客户代码"这回事。现场说错会被追问，务必改过来。

#### 挑战拆解

这两问其实是同一套体系的**两个面**：第一问答"怎么审"（范围、分层、顺序），第二问答"怎么保正确"（三道防线 + 可判定规则）。

**审查范围界定**：聚焦**本次需求的修改点（diff）**，不在全量代码的海洋里捞针；但**涉及资金的改动，审查范围要扩大到调用链上下游**（资金零差错是首要 KPI，见 `02A` 第一部分难点二）。

---

#### 一、怎么审：分层 + 顺序

| 环节 | 规则 | 落地点 |
|---|---|---|
| **分层** | 普通改动 → 模块 owner 主审；**涉及资金 → 核心资深工程师 + 技术经理共同 review**（双人审） | `02A` §9.2 评审人数；§9.3 P0 优先级 |
| **顺序** | ① 先按「技术常见坑表」逐项排查 → ② 再进入真正的 code review | 坑表 = `02A` §9.6 检查清单（通用 / Java 后端 / 数据库 / 前端 / 测试五组） |
| **前置** | 作者自查 → 静态扫描（Sonar + jar 检测，**已实现**）→ 人工评审 → 合并；CI 门禁仍在规划 | `02A` §9.2 / §9.5；护栏 3 |
| **评论分级** | `[blocking]` / `[suggest]` / `[question]` / `[nit]`；`[nit]` 不得阻塞合并 | `02A` §9.4 |

> "技术常见坑表"不是口头禅——它对应 `02A` §9.6 那份可勾选清单，现场被追问"坑表长啥样"直接翻那一节。

---

#### 二、怎么保正确：三道防线 + 四项可判定规则

**三道防线（口述原意保留，措辞校准）：**

| 防线 | 内容 | 状态口径 |
|---|---|---|
| ① 人 | 核心资深工程师 code review；资金改动双人审 | 按团队实践讲，不包装成平台能力 |
| ② 静态分析 | Sonar 静态代码分析（空指针 / 资源泄漏 / SQL 拼接 / 圈复杂度等） | ✅ **已实现** |
| ③ 自研规范扫描 | 自研扫描工具（jar 包扫描）：扫事务、**Redis 锁**、日志、幂等 | ✅ **已实现**；持续集成（CI）规划中，见护栏 3 |

**四项扫描项 → 判定规则（把"扫一下"变成"扫什么、怎么算合格"）：**

| 扫描项 | 合格判定 | 权威源 |
|---|---|---|
| **事务** | 该原子的操作在同一事务内（写库 + 本地消息表 Outbox 原子）；跨服务调用不在事务内、事务内不做远程 IO | `../02-现货贸易/03-架构决策/一致性与异构/12-跨系统调用一致性方案.md` |
| **锁** | 资金业务操作**必须加 Redis 锁**；扫描工具逐笔检查是否按规范加了 Redis 锁（资金操作很少用数据库锁） | 用户 2026-11-26 确认；`02A` 第一部分难点二（⚠️ 该处旧稿写"不用 Redis 锁"，已废弃，见护栏 1） |
| **日志** | 级别合理，含关键业务标识（订单号 / 客户号 / traceId），**不含敏感信息** | `02A` §9.6 通用 |
| **幂等** | 重复提交 / 重试 / 消息重投**不会**导致重复扣款、重复发货 | `02A` §9.6 Java 后端；`12-跨系统调用一致性方案.md` |

#### 三、口径护栏（本题专属，三条红线）

> 通用纪律只在 `00-技术管理索引.md` §六 维护一份，此处只补本题特有的三条。

1. ✅ **资金业务操作用 Redis 锁（本人 2026-11-26 确认，以此为准）**：所有资金业务操作都用 Redis 锁，很少用数据库锁。扫描工具逐笔检查资金操作是否加了 Redis 锁——这是原稿的正确表述，不是口误。⚠️ **注意全库仍有大量旧稿写"资金用 DB 行锁、不用 Redis 锁"**（`02A` 第一部分难点二、`03A-平台化治理与多租户架构手册.md` §8.2/§9、招聘件 B3、`12-跨系统调用一致性方案.md` §3.3、`06-Redis八股文追问链.md` 链 09、`04-MySQL八股文追问链.md` 等），**这些是待纠正的历史口径**，在被逐份修正前，面试现场若被追问请统一按"资金用 Redis 锁"答，并说明"数据库锁是早期通用方案对照，不是本人系统现状"。
2. ✅ **"审查同事的代码"**（原稿"客户"是口误已修正）；**交付给客户的功能属于"验收环节"**，不是 code review。
3. ✅ **Sonar 静态扫描 + 自研 jar 包检测 = 目前已实现**；⚠️ **持续集成（CI）目前是正在规划**，两者状态必须分开讲——工具已落地，CI 是规划中。静态扫描问题处置按 `02A` §5.1：P0 阻断合并、P1 记录限期整改（试运行阶段先告警校准误报率再转强制）。
