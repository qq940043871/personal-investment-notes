# 第一部分 · 技术情报收集

> 核心命题：商务、产品、客服是你最便宜的"人肉传感器"——他们每天都在客户现场和生产环境里泡着，但信息不会自动流向你。你需要设计一套**提取机制**。

## 1.1 为什么你听不到真话？——三层过滤衰减

```
客户真实场景 ──→ 商务转述（砍掉80%细节，只留"能不能做"）──→ 产品翻译（再砍50%，变成PRD需求）──→ 技术接收（只剩10%原始信息）
```

你不是没数据，你是**被过滤了**。每个角色都在用自己的语言框架重写原始信息：

| 角色 | 他们把信息扭曲成什么 | 你真正需要的是什么 |
|------|---------------------|-------------------|
| 商务 | "客户想要XX功能" | 客户为什么觉得现有系统做不了这件事？他现在的线下流程到底是什么？ |
| 产品 | "下个版本要做XX" | 哪个设计假设被现实打脸了？哪个功能上线后没人用？ |
| 客服 | "XX模块有个Bug" | 这个Bug是代码缺陷、设计缺陷、还是场景未覆盖？频率和趋势是什么？ |

**你要做的是"反过滤"——绕过他们的语言框架，直接抓原始信号。**

## 1.2 对商务：挖"客户不买的原因"和"真实业务流程"

商务是你触达**真实终端用户**最便宜的通道。但商务跟你说话时，已经在脑内做了两道翻译：

1. "客户抱怨系统慢" → "技术能不能优化一下性能"
2. "客户说竞品有个XX功能我们没有" → "我们也做一个XX功能吧"

你需要的是**原始对话**，不是商务的翻译结论。

### 1.2.1 商务脑子里有、但不会主动跟你说的四类情报

| 情报类型 | 商务的原始信息 | 你的技术解码 |
|---------|-------------|------------|
| **竞品杀伤点** | "客户说XX平台做这个特别快" | 快在哪里？流程少几步？预填了数据？异步化了？——你的系统能不能做到？ |
| **使用断点** | "客户说做到一半就不知道该点哪里了" | 哪些业务流程在系统里是断裂的？是不是规则配置没覆盖这种场景？ |
| **线下补救** | "客户说他们自己做了个Excel辅助" | 系统漏了什么数据/报表/操作？为什么客户宁可用Excel？ |
| **放弃原因** | "客户试用后没签" | 是功能不够？性能不行？操作太复杂？还是根本就不匹配他们的业务模式？ |

### 1.2.2 钩子问题（问"客户抱怨了什么"）

要这样问：

> ✅ "最近哪个客户试用后没签？他说的是什么原因？你感觉他说的原因是真心的还是借口？"
>
> ✅ "有没有客户说过'这个竞品做得比我们好'？他说的是哪个功能？他怎么描述的？"
>
> ✅ "客户演示的时候，你在旁边看到客户皱眉头或者反复操作的地方是哪里？"
>
> ✅ "有没有客户说过'要是你们系统能像XX那样就好了'？这个XX是我们竞品还是他们之前用的老系统？"

**关键技巧：追问细节，追到具体事实。**

> 商务说："客户觉得我们交易流程太长。"
>
> 你追问："哪一步长？下单那一步，还是确认那一步，还是等待响应那一步？客户跟谁比的？竞品要几步？我们几步？"

### 1.2.3 最有效的一招：跟访 / 旁听

如果条件允许，**每季度跟商务出去见一次客户**。不是去讲技术方案，是去听。

你只需要带一个笔记本，记录：

- 客户说到什么的时候语气变了（兴奋 / 抱怨 / 犹豫）
- 客户拿出了什么纸质单据 / Excel（= 系统没有覆盖的数据流）
- 客户反复问"能不能……"（= 系统能力边界）

跟访一次，比你读 100 份 PRD 都有用。

## 1.3 对产品：挖"设计假设的崩塌点"和"没人用的功能"

产品知道的信息，比商务离你近一步——他们已经做过一轮翻译了。但他们的翻译也有盲区。

### 1.3.1 产品脑子里有、但不会主动跟你说的三类情报

| 情报类型 | 产品的原始信息 | 你的技术解码 |
|---------|-------------|------------|
| **僵尸功能** | "XX功能上线后没什么人用" | 是设计问题还是实现问题？入口太深？操作太复杂？还是这个需求本身就不对？ |
| **设计打脸** | "客户老是在XX操作上犯错" | 是不是交互反直觉？字段命名客户理解不了？流程顺序不符合业务逻辑？ |
| **场景漂移** | "最近XX品种的交易变多了" | 撮合规则是否跟得上？数据模型能不能承载新品种？外部接口（质检 / 物流）有对应关系吗？ |

### 1.3.2 钩子问题（问"上个版本做错了什么"）

要这样问：

> ✅ "上次上线的XX功能，现在每天有多少人用？跟预期比差多少？你猜为什么？"
>
> ✅ "最近有没有你当初拍板做的功能，现在回头看觉得不该做？为什么？"
>
> ✅ "有没有客户投诉说'你们这个设计不合理'，但你心里觉得客户说得对？"
>
> ✅ "你最近看竞品更新了什么功能，觉得他们想得比我们深？"

### 1.3.3 需求溯源：问三次"这个场景是什么"

每个需求背后都有一个业务场景。但你收到的需求描述往往已经丢失了场景：

> 产品说："客户想要一个批量导入合同的功能。"
>
> 你问第一层："他们一次要导入多少份？" → 产品："大概几十份吧。"
>
> 你问第二层："这些合同从哪来的？是另一个系统的导出文件还是纸质合同？" → 产品："……我去问问。"
>
> 你问第三层："为什么不能在我们的系统里直接生成？是什么逼他们必须用导入？" → 这才是真正的问题。

**原则：需求是症状，场景是病因。追问到场景层面，你才知道该治哪里。**

## 1.4 对客服：挖"系统真实故障热力图"和"用户操作变形"

客服是你离**线上真实运行状态**最近的人。但他们给你反馈的信息格式通常是最糟糕的——"XX功能坏了，赶紧修"。

你需要把客服变成**系统健康度的仪表盘**。

### 1.4.1 客服脑子里有、但不会主动跟你说的四类情报

| 情报类型 | 客服的原始信息 | 你的技术解码 |
|---------|-------------|------------|
| **高频痛点** | "最近好多人问怎么XX" | 是帮助文档缺失？还是交互设计反直觉？还是这个功能本身就设计错了？ |
| **使用变形** | "客户老绕路做XX操作" | 客户在绕过你的系统设计，说明设计不符合他们的真实工作流 |
| **数据异常** | "客户说数据不对，但刷新又好了" | 缓存延迟？Canal 同步有延迟？数据一致性问题？ |
| **操作黑话** | "客户说做了'调拨'，但我们查不到" | 客户口中的业务术语跟系统里的概念对不上——术语表不对齐 |

### 1.4.2 钩子问题（问"什么在反复出现"）

要这样问：

> ✅ "最近哪个问题被不同客户反复提过三次以上？把最早一次和最近一次的时间给我。"
>
> ✅ "有没有客户说'之前还好好的，突然不行了'的事情？是哪天开始出现的？"
>
> ✅ "你接到的最让你无语的客户操作是什么？就是那种你会想'怎么会有人这么用'的？"（这种往往是系统设计问题，不是客户傻）
>
> ✅ "如果你只能让技术团队修一个东西，你选什么？为什么？"

### 1.4.3 建立"客服工单 → 技术缺陷"的翻译管道

你定一个简单的标记规则，客服照着打标即可：

| 客服标记 | 含义 | 你的动作 |
|---------|------|---------|
| 🔴 同一客户反复提 | 可能是数据问题或权限问题 | 查该客户数据状态 |
| 🟡 不同客户都提 | 大概率是 Bug 或设计缺陷 | 优先排查，可能是通用问题 |
| 🟢 第一次出现 | 可能是偶发或客户环境问题 | 记录，观察趋势 |
| ⚪ 客户说"之前好好的" | 可能是最近上线引入的回归 | 查最近一次部署的变更清单 |

### 1.4.4 最被低估的一招：看客服的屏幕

不需要天天看。**一个月花半小时坐在客服旁边，看他们处理三个工单。**

你会看到：

- 他们在哪一步卡住了（= 系统排查工具不好用）
- 他们反复复制粘贴了什么（= 缺少批量操作或模板）
- 他们打开了很多个页面来回切换（= 信息分散，缺少聚合视图，说明你的系统信息架构有问题）

这些不是 Bug，是你作为技术经理应该修但不知道的**系统体验债**。

## 1.5 建立持续的信息回流机制（不是一次性的）

靠偶发聊天获取信息不可靠。你需要低摩擦的常态化机制。

### 1.5.1 每周 15 分钟"三问制"

分别找三个部门的关键人，每周固定时间，只问三个问题（固定格式）：

**对商务（每周一，5 分钟，问最近一周见到的客户）：**

> 1. "这周见客户时，有没有客户说了让你意外的话？"
> 2. "有没有客户提到竞品的某个点让你觉得我们确实不如？"
> 3. "有没有一个快谈成的单子突然凉了？你知道真实原因吗？"

**对产品（每周五，5 分钟，回顾本周迭代）：**

> 1. "这周有没有人反馈了你没想到的问题？"
> 2. "哪个功能上线后跟你想的不一样？"
> 3. "你下周最纠结要做的那个需求，纠结的点是什么？"

**对客服（每周三，5 分钟，看过去一周的工单趋势）：**

> 1. "这周跟上周比，哪类问题明显变多了？"
> 2. "有没有客户说的词你听不懂？"（= 业务术语没对齐）
> 3. "有没有一个你特别想让技术知道但不知道怎么描述的事情？"

### 1.5.2 你的个人"信号日志"

建一个简单的笔记，每次跟三个角色聊完，只记三类东西：

```
【商务信号-2024.XX.XX】
- 客户A说竞品X的XX功能比我们快 → 待验证：快在异步化还是流程简化？
- 客户B试用后流失，理由是"操作太复杂" → 待跟产品确认：哪个步骤？

【产品信号-2024.XX.XX】
- XX功能上线后DAU只有预期的30% → 待分析：入口问题还是需求本身有问题？
- 最近贸易商开始做XX品种 → 提醒自己：规则配置是否支持新品种？

【客服信号-2024.XX.XX】
- "数据不对"类工单本周增加40% → 重点查：Canal同步延迟？缓存失效？
- 多个客户问同一个操作 → 不是Bug，是设计/文档问题
```

**三个信号交叉验证时，就是真正的系统缺陷。**

比如：商务说"客户觉得我们慢" + 客服说"数据不对的工单在涨" + 产品说"用户活跃度在降" → 不是单一 Bug，可能是**数据链路的系统性性能退化**。

> **纪律**：日志里每条信号必须带一个"待验证"动作。只记感受、不落验证动作的信号，一个月后就是废纸。

# 第二部分 · 跨部门沟通框架

> 适用场景：日常协作 / 需求对接 / 面试话术准备
> 行业背景：大宗商品撮合交易平台（C 语言撮合引擎 + Java 微服务中台 + 多端接入）；技术栈口径见 `00-技术管理索引.md` §六 第 4 条。

## 2.1 先看清三个部门的利益地图

沟通低效的根本原因是**不知道对方在意什么**。先对齐利益诉求：

| 维度 | 商务（BD/Sales） | 产品（PM） | 客服（CS/Ops） |
|------|-----------------|-----------|---------------|
| **核心 KPI** | 签单量、GMV、客户数 | 功能上线质量、用户满意度 | 问题解决率、响应时效 |
| **对你的期待** | "帮我拿下这个客户" | "帮我想清楚怎么做" | "帮我快速解决问题" |
| **怕什么** | 技术瓶颈影响签单 | 技术说了算、需求被砍 | 客户投诉找不到人、问题石沉大海 |
| **对你的误解** | "你们技术能不能快点？" | "这个需求很简单吧？" | "找技术他们总说查一下就没下文" |
| **你需要让他们懂什么** | 技术复杂度 = 交付周期的真实约束 | 系统现状 = 方案可行性的边界 | 问题分类 = 响应优先级和 SLA |

## 2.2 与商务沟通：从"接需求"到"一起打单"

### 2.2.1 售前阶段（客户来询，还没签约）

**必问 5 个问题：**

| 序号 | 问题 | 为什么问这个 | 你的系统锚点 |
|------|------|-------------|-------------|
| 1 | 这个客户做什么品种？大致年交易量多少？ | 评估撮合引擎峰值吞吐是否匹配 | C 撮合引擎（单线程内存撮合）的容量上限 |
| 2 | 客户现有系统是什么？有没有 CTRM / ERP？ | 判断是需要做接口对接还是独立使用 | 已有 9+ 外部接口（银行 / 物流 / CTRM / 企业征信等），能复用哪些 |
| 3 | 客户在意的核心痛点是什么？一句话说清楚 | 避免技术过度设计，对准真实价值点 | 交易模式 / 履约保证 / 数据服务的契合点 |
| 4 | 有没有竞品也在跟？对方主打什么？ | 了解竞争态势，准备技术优势话术 | C 引擎撮合延迟确定性（无 GC 停顿）vs 竞品 Java 撮合的差异点 |
| 5 | 这个单子的时间窗口有多紧？有没有硬 deadline？ | 评估是否能走标准交付流程还是需要特殊排期 | 涉及外部接口对接的最低交付周期（银行证书等不可压缩环节） |

**话术模板（售前支持）：**

> "这个客户我们技术上可以做，但有三个点需要我们一起对齐：第一，XXX 品种的撮合规则是否和现有规则库兼容；第二，如果对接客户现有 ERP，接口联调至少需要 X 周；第三，建议分批交付——先跑通交易闭环，再上数据服务。这样既能快速签单，也不会给交付埋坑。"

### 2.2.2 签约后阶段（合同已签，进入交付）

**必问 4 个问题：**

| 序号 | 问题 | 风险点 |
|------|------|--------|
| 1 | 合同中约定的功能边界在哪里？有没有模糊表述？ | 防止交付范围蔓延（scope creep） |
| 2 | 验收标准是什么？谁说了算？ | 防止"客户觉得不好用"变成无限返工 |
| 3 | 商务侧承诺的交付时间表，有没有和客户沟通过第三方依赖（如银行接口）的不可控性？ | 银行证书申请、银企直连开通不归你管 |
| 4 | 客户侧的技术对接人是谁？有没有决策权？ | 对接错人 = 传话筒，沟通效率低 |

**核心原则：承诺由商务出口，你负责让商务知道每项承诺的代价。**

## 2.3 与产品沟通：从"需求翻译官"到"技术合伙人"

### 2.3.1 需求评审阶段

**必问 6 个问题：**

| 序号 | 问题 | 目的 | 关联你懂的模块 |
|------|------|------|---------------|
| 1 | 这个需求解决谁的什么问题？不做会怎样？ | 判断优先级（是真痛点还是伪需求） | — |
| 2 | 有没有看过现有系统的实现？为什么不能复用或改造？ | 避免重复造轮子 | 12+ 业务服务集群中可能已有类似能力 |
| 3 | 这个功能涉及哪些外部接口 / 第三方依赖？ | 评估技术风险和交付周期 | 银行 / 短信 / 证书 / 物流 / CTRM 等 9+ 接口 |
| 4 | 数据一致性的要求是什么？强一致还是最终一致？ | 决定架构方案（同步 / 异步 / 补偿） | C 异步落库 + Canal + Redis 缓存的数据链路 |
| 5 | 并发量预估是多少？峰值在什么场景下出现？ | 决定是否需要走撮合引擎，还是普通业务服务 | 单线程 C 引擎 vs Java 微服务的吞吐差异 |
| 6 | 这个需求对现有交易规则配置体系有没有冲击？ | 规则引擎的扩展性评估 | 规则配置模块是核心，改动影响面大 |

**核心原则：产品定"做什么"，你定"能不能做"和"怎么做最稳"。**

### 2.3.2 方案设计阶段

与产品沟通时，你最需要对齐的 4 个技术约束：

| 约束 | 怎么跟产品说明白 |
|------|-----------------|
| **撮合引擎是 C 单线程** | "撮合这层不能加太多业务逻辑，它会拖慢整个交易。你提的 XXX 校验应该放在 Java 业务层做。" |
| **C ↔ Java 走 TCP 二进制协议** | "跨语言通信有时间开销。如果这个功能需要撮合引擎实时返回结果，延迟预算要留 X ms。" |
| **DS 数据中心是桥接层** | "你的数据看板如果要从撮合引擎取实时数据，走 DS 做协议转换会有延迟，建议走缓存服务（Redis）那一路。" |
| **外部接口不可控** | "银行 / 物流这些不在我们 SLA 范围内，这个功能如果强依赖外部接口，要做熔断和降级。" |

## 2.4 与客服沟通：从"救火队"到"问题管理体系"

### 2.4.1 问题接收阶段

**必问 5 个问题（要求客服在提工单时就有答案）：**

| 序号 | 问题 | 目的 |
|------|------|------|
| 1 | 影响范围：几个客户？是否为核心客户？ | 定 P0/P1/P2 优先级 |
| 2 | 能否复现？操作路径是什么？ | 减少排查时间 |
| 3 | 问题发生时间？有没有截屏 / 录屏 / 客户账号？ | 定位日志时间窗口 |
| 4 | 是功能缺陷还是客户不会用？ | 分流：修 Bug vs 补文档 / 培训 |
| 5 | 客户情绪状态？有没有升级风险？ | 决定是否需要技术直接出面安抚 |

**你给客服的承诺（当时的团队约定，不是对外 SLA 条款）：**

> "客服提单后，P0 问题 30 分钟内有人响应，P1 问题 2 小时内，P2 问题下一个工作日。每次响应我会告诉你查到了什么、下一步做什么、预计什么时间给结论。"

### 2.4.2 建立问题分类与 SLA 矩阵

| 级别 | 定义 | 例子 | 技术响应 | 客服话术 |
|------|------|------|---------|---------|
| **P0-紧急** | 交易中断 / 资金风险 | 撮合引擎挂掉、支付失败、数据丢失 | 30min 响应，2h 内修复或降级 | "技术团队已介入排查，预计 X 点前恢复" |
| **P1-高优** | 核心功能不可用 | 报价看不到、合同签不了、履约状态不对 | 2h 响应，当日修复 | "已定位原因，正在修复中，预计今日完成" |
| **P2-普通** | 非核心功能异常 | 报表数据延迟、页面显示异常 | 下一工作日响应，72h 内修复 | "已记录，预计 X 个工作日内修复" |
| **P3-优化** | 体验问题 / 建议 | 操作不便、希望加个导出功能 | 纳入需求池，不承诺修复时间 | "已转产品评估，有进展同步您" |

> ⚠️ 讲这套矩阵时说明它是**团队内部的响应约定**，只说机制与分级逻辑，不承诺具体分钟数给外部客户。

### 2.4.3 常见问题的技术排查指南（给客服的自助手册骨架）

你不需要让客服懂技术，但要让他们知道什么信息对你有用：

| 客户报什么 | 客服应该问什么 | 你应该查什么 |
|-----------|--------------|-------------|
| "交易报错了" | 客户账号？什么品种？什么时间？截图？ | 撮合引擎日志 + DS 数据中心日志 + 业务服务日志 |
| "数据不对" | 哪个页面？期望值 vs 实际值？ | Canal 同步延迟 → Redis 缓存 → 数据库直查对比 |
| "页面打不开 / 慢" | 什么浏览器？网络环境？是所有页面还是某个？ | 网关日志 → 对应 Java 服务响应时间 |
| "对接失败" | 哪个外部接口？什么时候开始？有报错码吗？ | 外部接口调用日志 + 证书有效期 + 银行通道状态 |

# 第三部分 · 向上沟通：要资源、要决策、要保护

> 索引 §四 把本册定位为答"怎么拿资源 / 怎么对齐业务"。前两部分解决"平级对齐"，这一部分解决"向上争取"——**没有资源的对齐，只是一张好看的图。**

## 3.1 先弄清上级在看哪三张账

向副总（或任何上级）汇报，他脑子里同时在算三笔账，你说的话必须能落到其中一笔，否则就是噪音：

| 账 | 上级在问 | 你该怎么呈现 |
|---|---|---|
| **交付确定性账** | 这个季度能不能按时交？哪些会滑？ | 只讲关键路径 + 滑动幅度 + 可选项，不讲完成百分比 |
| **风险敞口账** | 最坏会发生什么？谁兜底？ | 先给最坏场景，再给止损手段和触发阈值 |
| **产能账** | 这块地还能种多少东西？加人会怎样？ | 用人天 / 迭代容量说话，不讲"大家很忙" |

**原则：向上沟通不是"汇报进度"，是"让上级用最少信息做出一个决策"。** 每次开口前先问自己：我要他做什么决定？

## 3.2 报忧三段式：事实 → 影响 → 选项

坏消息的正确结构，永远比好消息更需要格式：

```
1. 事实（不超过两句，不含情绪、不含归因）
   "XX 客户的对账数据从 11 月 18 日起出现 T+1 延迟，已定位到 Canal 同步积压。"

2. 影响（说范围和量级，不说形容词）
   "影响 3 家客户、日均约 X 笔对账；资金安全不受影响，但客户侧会有人工补账工作量。"

3. 选项（给 2–3 个，标代价，标你的建议）
   "方案 A 调大同步并发 + 慢查询治理，2 天，风险低，建议选它；
     方案 B 加中间表临时兜底，半天，但要还债；
     方案 C 只监控不处理，本周客户会继续投诉。"
```

**三个禁忌：**

- ❌ 只说事实不给选项 → 上级被迫替你做技术决策，且会怀疑你的判断力
- ❌ 说"已经在处理了" → 等于没汇报，上级无法判断是否需要介入
- ❌ 把归因放在第一句 → 听起来像甩锅，事实会被情绪盖住

## 3.3 要资源的四步法

**Step 1 · 换成上级的语言**

把技术诉求换算成他账本上的单位。技术债不是"代码烂"，是"每新增一个履约场景的交付成本"；性能优化不是"要重构"，是"高峰期每分钟的丢单风险"。

| 你想说 | 换成 |
|---|---|
| "要重构一下老模块" | "现在每加一个定制场景要改 5 处代码，配置化之后同类需求从 X 人天降到 Y 小时" |
| "服务器不够了" | "并发到 X 会出现响应抖动，直接影响下单成功率" |
| "人手不够" | "按当前排期，交付窗口内只能保 3 个必须项，砍哪两个由业务定" |

**Step 2 · 单点试点，不要一次要全部**

先要最小的一块：一个模块、一个客户、一个迭代。用小成本跑出可比数据，下一次要资源时你手里有账本，不是靠说服。

**Step 3 · 给止损承诺（这是最容易被忽略的一步）**

要资源时主动给上级一个"什么时候你可以叫停"的信号：试点一个迭代内看不到 X 效果就收手。**愿意设止损的人，才拿得到第二次资源。**

**Step 4 · 复盘复用**

做完就出结论：省了多少、快了多少、还剩什么没解决。这一步决定了下次要资源是"再谈一次"还是"直接批"。

## 3.4 一页周报骨架（五分钟能写完）

```markdown
## 本周（第 N 周）
- 交付：关键路径推进到 __；风险项 __（滑动 __ 天）
- 稳定：P0 __ 起 / P1 __ 起；重复问题 __ 条（已转规范 / 检查项 __ 条）
- 情报：来自商务 __ 条、产品 __ 条、客服 __ 条；交叉验证成立 __ 条
- 需要决策：__（选 A / B / C，建议 __，最晚 __ 前定）
```

**只报"变化"和"需要决策"，不复述已完成的事。** 上级要的是差异视图，不是流水账。

## 3.5 三种高频场景的话术

**场景一 · 要人（编制或借调）**

> "现在这条线有 3 个必须项在同一个交付窗口，按人天核算差 X 人月。我有两个方案：借调 1 人两个月，或者砍掉其中 1 项。我建议借调——砍掉的那项是验收条款里的，砍了后面要返工。"

**场景二 · 要预算（工具 / 压测环境 / 监控）**

> "不是要一套新系统，是要一次压测窗口。目标是把并发目标下的瓶颈提前暴露，而不是等上线后由客户发现。预算是一次性投入，收益是上线评审有数据可依。"

**场景三 · 要推迟**

> "这个功能按现有方案要 Y 周，但质量会打折。我建议推一个迭代，把外部接口的降级路径补上——否则上线后每逢银行通道异常就要人工介入。要不要推，请您定，我今晚就能出降级方案的具体工作量。"

## 3.6 向上沟通的四条纪律

1. **同一个问题只提一次**：提了没结论就自己定，定完告知——反复请示会消耗信任。
2. **带方案不带问题**：至少两个选项，且明确推荐哪个。
3. **不在公开场合暴露未定的分歧**：对齐后再开会，会上不制造意外。
4. **承诺的东西一定回执**：说了"今晚给方案"，当晚就给，哪怕方案很粗——**回执本身就是可信度**。

# 第四部分 · 从情报到动作：转化闭环

> 情报最大的浪费不是没收到，而是**收到了没进流程**。这部分是把前面三部分的输出接进本目录的整改与技术债体系。

## 4.1 信号分诊表

每条信号落到下面某一格，才算处理完毕：

| 信号特征 | 归类 | 落点 | 时间尺度 |
|---|---|---|---|
| 影响正确性 / 资金安全 | **流血债** | 本迭代必还，进 P0/P1 修复 | 当迭代 |
| 让每次交付都更慢（每加一个场景改多处） | **放血债** | 排季度规划，进十一项整改的对应主线 | 季度 |
| 只是不顺手、不影响交付与正确性 | **美容债** | 顺手还，不立项 | 有空 |
| 需求本身错了 / 场景不成立 | **不立项** | 回写产品，讲清为什么不做 | 立即 |
| 信息不足，无法判断 | **待验证** | 回给传感器角色，指定验证动作与时限 | 一周内 |

**原则：一条信号如果两周内没有落点，就默认丢弃并说明原因——挂在日志里的信号会污染判断。**

## 4.2 与技术债三分法对接

三分法的权威口径在 `../00-面试计划/10-面试训练手册.md` §4.5，本册只讲**怎么用情报给它喂料**：

- **流血债**来源最多的是客服的⚪标记（"之前好好的"）和⚫数据异常——这类是回归与一致性问题，优先级最高。
- **放血债**来源最多的是产品的"僵尸功能"和商务的"使用断点"——它们不报错，但持续抬高每个新需求的成本。
- **美容债**来源最多的是 1.4.4 看客服屏幕时发现的操作摩擦——成本低、体感强，是团队士气的便宜投入。

## 4.3 与十一项整改对接

`01-技术整改十一项与落地.html` 的十一个项目，本质上都是**同一类情报反复出现后收敛成机制的产物**。典型对应关系：

| 反复出现的情报 | 收敛成的机制 |
|---|---|
| 每个客户都要改代码做定制（商务端持续反馈） | 配置化 / 低代码，规则与表单可配 |
| 对接方各自一套接口（实施与客服共同痛点） | 统一开放网关 |
| 支付渠道各自实现（资金类问题反复） | 统一支付 |
| 交收场景每次都要改（业务侧场景漂移） | 交收场景化改造 |
| 客服排查时看不到一致数据（数据异常高频） | 缓存服务改革 + 数据链路口径统一 |

**讲法提示：不要平铺十一个项目，先讲"哪类情报反复出现"，再说"所以收敛成哪个机制"——这是管理判断，不是项目清单。**

## 4.4 一条信号的完整生命周期（示例）

```
D1  客服："3 家客户说对账数据有时差一小时。"（🟡不同客户都提）
D1  技术侧：查 Canal 同步延迟 → 定位为高峰期消费积压，非数据错误
D2  回执客服：已定位，不是数据错误，是同步延迟；给临时方案（对账前手动触发补偿）
D3  信号日志：归类【放血债】——每逢高峰期都会复现，客服每周要人工解释
D5  评审：不是单点修 Bug，而是进「缓存服务改革 / 数据链路一致性」主线
W2  落地：同步并发调整 + 积压告警 + 对账页面加"数据截止时间"标识
W3  回访客服：同类工单量下降，客服不再需要人工解释
W4  沉淀：把"积压告警"写进监控基线，下次上线评审必查项
```

**这条链路的价值不在技术，在于它证明了：情报 → 判断 → 机制 → 验证，是一个闭环而不是一次性救火。**

# 第五部分 · 边界与红线

方法用过头会变成另一种问题，这四条边界讲的时候要主动说：

1. **情报不替代数据**：人肉传感器提供"假设"，监控、日志、埋点提供"证据"。**只用情报做决策，等于用传闻做架构。**
2. **不做人肉监控**：不追问个人工作细节、不评价个人能力，只问"客户说了什么 / 系统发生了什么"。情报的对象是系统，不是人。
3. **客户信息脱敏**：客户名、金额、合同细节进日志前按类别名处理（银行 / 仓储 / 税务 / 监管），与 `00-技术管理索引.md` §六 第 2 条一致。
4. **不越位承诺**：情报里听到的客户诉求，不由技术直接对客户承诺交付时间——**承诺由商务出口**（见 2.2.2 核心原则）。

# 第六部分 · 面试速用

## 6.1 两条主线（先选一条，别混着讲）

**主线 A · 情报侧（被问"你怎么了解真实业务和系统问题"）——30 秒版：**

> "我不靠测试报告和需求文档，我靠三组人肉传感器——商务、产品、客服，每周各 5 分钟、只问三个固定问题。
> 商务告诉我客户为什么不买，我追问到具体场景；产品告诉我哪个设计假设被打脸，僵尸功能比缺失功能更浪费；客服是我的系统健康度仪表盘，我给工单定了标记规则，同一客户反复提查数据、不同客户都提查通用问题、'之前好好的'查最近变更。
> 三路信号交叉验证时我才动手——那不是偶发 Bug，是系统级缺陷。"

**主线 B · 沟通侧（被问"你怎么和商务、产品、客服协作"）——90 秒版（STAR）：**

> **S**：平台是 C 撮合引擎 + Java 微服务中台 + DS 桥接，三个业务团队每天和技术打交道，但对技术约束的理解程度不同。
> **T**：我的角色是让三方和技术的信息对齐——技术方案支撑业务目标，业务团队理解技术真实约束。
> **A**：对商务，我参与售前，问品种、量级、现有系统、痛点、竞品，然后翻译成"能做 / 不能做 / 有条件做"，尤其讲清外部接口的最低交付周期；对产品，我追问需求在架构里的落点——走撮合实时链路还是缓存一路，延迟预算多少，我会把"能不能做 / 要改架构才能做"的边界说清楚；对客服，我建了分级响应约定，要求提单带"谁、什么时间、做了什么、什么结果、有没有截图"，并把高频问题转成 FAQ 与排查指南。
> **R**：三方对技术的信任度提升了——商务敢带技术去见客户，产品提需求前会先想走哪个数据通道，客服的问题描述质量明显提高。

## 6.2 常见追问与应答

| 追问 | 应答骨架 |
|---|---|
| "你怎么保证不是靠拍脑袋？" | 情报出假设，监控 / 日志 / 埋点出证据；三路信号交叉才动手，单路信号只进日志 |
| "这套机制落地了吗？" | 讲**已发生的动作**（固定周节奏、工单标记规则、FAQ 与排查指南），不吹制度文件 |
| "部门不配合怎么办？" | 先给对方价值：给客服排查指南减少重复答疑、给商务售前话术减少空转、给产品架构边界减少返工；**先给再要** |
| "情报收集会不会侵犯隐私 / 合规？" | 见第五部分四条边界：只问系统不问人、客户信息脱敏、不越位承诺 |
| "资源要不到怎么办？" | 单点试点 + 止损承诺 + 复盘账本；要不来就自己定范围并告知，不反复请示 |

## 6.3 一屏速查卡（面试前 5 分钟）

```
【定位】  技术经理 = 翻译器 + 接收器，不是传话筒
【三传感器】商务(为什么不买) / 产品(什么被打脸) / 客服(什么在反复)
【追问口诀】问三遍"这个场景是什么" → 症状是需求，病因是场景
【回流机制】每周各 5 分钟 × 3 问；信号日志必带"待验证动作"
【交叉验证】三路指向同一问题 = 系统级缺陷，不是单点 Bug
【向上】事实两句 → 影响说量级 → 给 2–3 个选项 + 建议
【要资源】换算式 → 单点试点 → 止损承诺 → 复盘复用
【分诊】流血债(当迭代) / 放血债(季度) / 美容债(顺手) / 不立项(讲清为什么)
【红线】情报不替代数据 · 不做人肉监控 · 客户脱敏 · 承诺由商务出口
【数字】20 人(3C/6Java/5Vue/5测试)、9+ 外部接口、12+ 微服务 —— 均为简历口径；
        SLA 分钟数、覆盖率、并发目标带"当时设定的目标 / 团队约定"限定语
```
