# 08 · 技术经理能力模型（技术 / 业务 / 管理 + 沟通贯穿层）

> **定位**：本文件答一类「总纲题」——「技术经理的能力主要体现在哪些方面」。01–07 各答一类具体管理追问，本件只给**骨架与取舍**：先定能力域，再把每域的证据指回既有文档。
> **收录**：2026-11-27，口述框架 + 两轮对照修订。
> **口径**：所有数字与限定语以 `00-技术管理索引.md` §六为准，**本件不另立数字、不复述正文**；指针走 `00` 号 §四（全库唯一一份）。
> **关系**：技术深度 → `../02-现货贸易/03-架构决策/`；沟通落地 → 本目录 `05`、`07`；成长路径 → 本目录 `02B`；带人证据 → `00` 号 §二 / §三。

> **证据等级（先分清再说）**
> - 【实证】本人系统现状：网关十道关、Java 业务中台 + C 撮合 + 自研 DS 桥接、资金操作用 Redis 锁、六道评审闸门、Sonar 静态扫描 + 自研 jar 包检测、早会 / 周分享 / 技术常见坑表。
> - 【目标线 · 非达成值】覆盖率、人月、故障次数等考核线——见 `00` 号 §六第 1 条，本件不引数字。
> - 【规划 · 在推】CI 门禁 / CD 自动检测 / 制品库全链路——见 `07` 号护栏，不包装成已落地。
> - 【通用方法 · 非本人系统实证】DDD / 限界上下文 / 聚合根：**只在架构方法论手册里作选型推演**，本人项目叙事中没有 DDD 落地表述。讲成「我们业务层用 DDD」会被追问到翻车。

## 0. 一句话口径（先背这句）

> **技术决定下限，业务决定方向，管理决定能不能复制，沟通决定前三样有没有人买账。**
> 技术经理的价值 = 技术判断 × 业务价值 × 研发效能，三者靠沟通协作传导到团队与业务方——乘积关系，任何一项为零，整体归零。

## 1. 全图：三域 + 一个贯穿层

| 域 | 回答的问题 | 落脚点 | 权威出处 |
|---|---|---|---|
| **技术** | 关键节点能不能拍板 | 深度 / 广度 / 高度 | `../02-现货贸易/03-架构决策/` |
| **业务** | 技术投入值不值 | 全链路 / 核心模块 / 翻译 | `02B` 第二部分、`05` 第一部分 |
| **管理** | 能力能不能复制 | 流程（质量）/ 开发（人） | `00` 号 §二 / §三、`07` |
| **沟通协作（贯穿）** | 前三样有没有人买账 | 横向 / 向上 / 向下 | `05`、`07` |

**为什么沟通是贯穿层，不是并列的第四域**：技术判断要让人点头、业务认知要跟业务方对上、管理动作要推动别人执行，全靠它。如果并列成第四块，权重立刻掉成「软技能附录」；实际上它是让前三域**生效**的乘数。技术经理与架构师的分水岭也在这——架构师靠技术影响力，技术经理靠**通过别人拿结果**。

## 2. 技术能力（硬实力：关键节点能拍板）

> 原口述是「网关层 / 业务层 / 设计层」。⚠️ 这三者不是同一刀切出来的：网关层、业务层是**系统的横向分层**，设计层是**工程活动**。把组件和动作并列，被追问「划分维度是什么」就会散架。下面改为三个正交维度，原三项全部有落点。

### 2.1 深度 —— 关键路径能下沉拍板

- **网关层（架构入口与边界）**：网关是系统唯一入口，承载流量治理、统一鉴权、服务路由与输出白名单。【实证】对应十道关处理链路——拒绝要早要便宜、入参白名单、分页默认 100 / SQL 红线 ≤200、显式拒绝不静默截断、分级限流。
- **业务层（系统实现与稳定性）**：【实证】Java 业务中台承载从挂牌到结算的核心流程；资金操作用 Redis 锁、幂等、状态机与待发送表构成正确性底座；C 单线程内存撮合内核与 DS 桥接构成异构主链路。
- **判定**：这三处出问题，技术经理必须能亲自下场定位到命令级，而不是只转派。

### 2.2 广度 —— 异构系统视野

- 【实证】C + Java + Vue3 异构栈、自研 DS 桥接（Hessian 与 Socket 双通道）、MySQL / Redis / Elasticsearch / MinIO 四件套——能讲清各组件在哪一层、为什么是它、替换代价是什么。
- ⚠️ 技术栈不混：FastAPI / Python 只属个人 Agent Harness 储备，**不进平台技术栈**（`00` 号 §六第 4 条）。
- ⚠️ MongoDB 从未在业务系统使用；出现相关内容一律标「通用原理对照，非项目实证」。

### 2.3 高度 —— 架构规划与演进

- 【实证】技术债三分法：流血债本迭代必还、放血债排季度规划并量化、美容债顺手还不立项；十一项整改收束成一条主线——**把每次定制改代码，变成配置与契约**。
- 高可用与容灾、容量规划与压测、演进节奏取舍（什么时候上什么、为什么先不上）——依据指针见 `../02-现货贸易/03-架构决策/`。
- ⚠️ DDD 只作【通用方法 · 非本人系统实证】：方法论手册里把它列为模块化单体的代码组织方式与 JDK 17 选型的适配理由，**不是本人系统的落地战绩**。要讲就讲「代码结构按限界上下文组织，需要时一个模块一个模块拆出去」这个**决策**，别讲成「我们做了完整 DDD 落地」。

## 3. 业务能力（软着陆：价值导向）

### 3.1 全链路业务视角（全局观）

- 【实证】从挂牌到结算 8 环节，上游流量从哪来、下游数据到哪去、商业逻辑与盈利模式是什么——详见 `../02-现货贸易/01-业务与价值/02-业务全链路场景手册.md`。
- **判定**：技术决策要算投入产出比，不是追酷炫技术。被问「这个功能值不值得做」时，能说出它卡在哪个环节、影响哪类客户、不做的代价是什么。

### 3.2 核心模块精通（专业度）

- 技术权威性的来源是**关键模块能亲自下场**。团队遇到棘手难题或性能瓶颈时，你能给出方案而不只是分派——这直接建立信任。
- 【实证】排障六步 SOP 与生产问题实录走 `../02-现货贸易/04-生产问题排查/`，篇数按该目录实际文件数，不报固定数。

### 3.3 业务翻译（原框架缺项，补上）

- 双向翻译：**用业务语言向业务方讲技术投入的 ROI**，**用技术方案解决业务方自己都说不清的痛点**。【实证出处】`02B-技术经理成长手册.md` 第二部分「业务深度 × 技术深度」交叉栏。
- 反过滤机制：商务、产品、客服是「人肉传感器」，但信息会经三层过滤衰减；靠钩子问题与跟访抓原始信号——见 `05` 号第一部分。

## 4. 管理能力（生产力：降本增效，把个人经验变成团队能力）

> 一句话口径见 `00` 号 §一：**机制 × 证据 × 杠杆**；交付只是底线，机制与资产才是 leader 的产出。

### 4.1 流程管理 —— 提高产品质量

- 【实证】六道评审闸门：需求收口 → 设计 → 技术 → QA 验收 → 发布 → 移交，**不通过不流转**。把需求不清、设计不足、测试遗漏的返工挡在开发之前。
- 标准化 SOP 覆盖需求评审、Code Review、测试准入准出、发布流程，目的是**减少不确定性**，避免人肉运维。关键节点留表单（评审表 / 发布记录 / 移交记录）。
- ⚠️ 工具层分清现状：Sonar 静态扫描 + 自研 jar 包检测**已实现**；CI 门禁 / CD 自动检测 / 制品库全链路**在推**。把「规划 + 在推」讲成「已在跑」就是过度声明。

### 4.2 开发管理 —— 提高团队能力

- 【实证】三层机制：规范文档写「应该怎样」、工具门禁强制「必须怎样」、人工评审判断「是否合理」，缺一层就退化成形式主义——见 `07` 号 §1。
- 【实证】日常三节奏：早会只过阻塞点、周技术分享只讲真问题且轮流主讲、技术常见坑表把教训变成可勾选项。
- 【实证】带人配套：师徒制、主链路强制代码评审、调研沉淀进知识库。
- 【目标线 · 非达成值】节省人月、团队整体自动化覆盖率、核心模块单测门禁起始线——数字见 `00` 号 §六第 3 条与 §五追问链，本件不复述。

## 5. 沟通协作（贯穿层：让前三域生效）

> 不是「会说话」，是**信息传导 + 资源调度 + 影响力**的工程化能力。三个方向各有现成弹药，不要混讲。

### 5.1 横向 —— 跨部门 / 跨公司疑难推动

- 【实证】利益地图 + 商务 / 产品 / 客服各自的必问清单与 SLA，把模糊需求收敛成可验收事实——见 `05` 号第二部分。
- 跨公司（客户 / 供应商 / 监管）场景沿用脱敏类别名，现场不补真名（`00` 号 §六第 2 条）。
- **判定标准**：项目能不能在没有行政授权的情况下跨部门推动——靠的是把对方利益翻译成可交付条件。

### 5.2 向上 —— 要资源、报忧、争取支持

- 【实证】上级的三张账 + 报忧三段式 + 要资源四步法——见 `05` 号第三部分。
- **判定标准**：能不能把技术问题翻译成老板听得懂的「风险 / 成本 / 收益」，并把资源要回来。

### 5.3 向下 —— 规范传达与团队赋能

- 【实证】`07` 号三层落地机制 + 日常三节奏；`00` 号 §三第 ⑤ 牌（技术债与整改）与 §二第 4 件（带人）。
- **判定标准**：你不在场时，团队能不能按同一套规范做对——这就是「把经验变成团队能力」。

## 6. 常见误区与未采纳项（防止术语回流）

| 误区 | 为什么要避 | 正确说法 |
|---|---|---|
| 把「网关 / 业务 / 设计」当三个并列能力域 | 前两个是系统分层，第三个是工程活动，划分维度不统一 | 深度 / 广度 / 高度，原三项分别落进深度与高度 |
| 把沟通协作写成「软技能附录」或直接删掉 | 它是前三域生效的乘数，也是技术经理区别于架构师的关键 | 贯穿层：横向 / 向上 / 向下 |
| 把「业务层对应 DDD 落地能力」写成个人实证 | 本人项目叙事无 DDD 落地表述，追问限界上下文会答不上 | 【通用方法 · 非本人系统实证】，只讲代码组织决策 |
| 把 CI/CD 自动化讲成「已在跑」 | 实际是规划 + 在推 | Sonar + 自研 jar 包检测已实现，CI 门禁在推 |
| 把目标线讲成达成值 | 混淆运行结果与考核线 | 一律带限定语，见 `00` 号 §六第 1 条 |
| 把 FastAPI / Python 写进平台技术栈 | 个人储备与平台栈混讲是红线 | 平台 = Java + C + DS 桥接 + Vue3，FastAPI 只属个人 Harness |

## 7. 口播速用

**30 秒版**
> 技术经理的能力我分三块加一层：技术看深度、广度、高度——关键节点能拍板、异构栈能讲清、演进节奏能定；业务看全链路视角、核心模块精通和双向翻译；管理看流程保质量、开发提能力。这三块靠沟通协作传导——横向跨部门推动、向上要资源、向下做赋能。技术决定下限，业务决定方向，管理决定能不能复制，沟通决定有没有人买账。

**90 秒版**
> 在 30 秒版基础上，每域甩一个证据：技术讲网关十道关与资金 Redis 锁；业务讲从挂牌到结算 8 环节与业务语言翻译 ROI；管理讲六道闸门不通过不流转、规范 + 工具 + 人工三层缺一不可；沟通讲跨部门必问清单与 SLA、要资源四步法、早会周分享坑表三节奏。收束一句：**我不只是自己能解决，而是让团队在没有我的时候也能做对。**

**换题取用**：被问「技术和管理怎么平衡」→ 只讲 §1 全图 + §0 乘积关系；被问「你凭什么当技术经理」→ 讲 §2 + §3.2；被问「怎么带团队」→ 讲 §4 + §5.3；被问「跨部门怎么推动」→ 只讲 §5.1 并甩 `05` 号。
