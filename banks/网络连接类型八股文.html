01 连接的本质与分类

1.1 什么是网络连接？物理连接与逻辑连接的区别？基础

标准答案（三步法）：

  1. 物理连接：真实的硬件链路（网线、光纤、交换机端口），是"线"的存在。
  2. 逻辑连接：协议栈维护的虚拟通路状态（TCP 四元组+状态机、HTTP 会话、VPN 隧道），是"状态"的存在。
  3. 关系：逻辑连接建立在物理连接之上，物理连接共享、逻辑连接复用——千条 TCP 连接可共享一根光纤（分组交换）。
💡 记忆口诀："物理是线、逻辑是状态；线共享、状态复用。" 答出"分组交换让逻辑连接在共享介质上抽象出隔离会话"是加分句。
1.2 TCP 与 UDP 的本质区别？高频

标准答案（六维对比表）：

维度TCPUDP
连接面向连接，三次握手无连接，直接发包
可靠性确认/重传/排序/去重尽最大努力
流量/拥塞控制有无
报文边界字节流（粘包）保留边界
首部20 字节8 字节
场景HTTP、DB、文件、RPCDNS、音视频、游戏、QUIC
💡 记忆口诀："TCP 是可靠的双向管道，UDP 是 IP 上加 8 字节端口复用层，其他一概不管。" "连接的本质 = 两端协同维护的会话状态"。
1.3 单播、广播、组播、任播的区别？基础

标准答案：

  1. 单播：一对一（TCP、绝大多数 HTTP）。
  2. 广播：一对本网段全部，IPv4 独有（IPv6 用组播代替）。
  3. 组播：一对订阅了组地址的多个主机（直播、IPTV、OSPF 用 224.0.0.5）。
  4. 任播：多机共享一地址，路由送到最近的一台（DNS 8.8.8.8、CDN）。
💡 记忆口诀："TCP 只能单播（要端到端状态），UDP 能播组任；任播+TCP 在 CDN 里是'路由先选中一台，再和那一台建连'，不矛盾。"
1.4 电路交换 vs 分组交换；虚电路 vs 数据报？进阶

标准答案：

  1. 电路交换：先建立独占物理通路（老电话），带宽独占、利用率低、时延稳定。
  2. 分组交换：分组独立路由转发，链路共享、利用率高、可能乱序（互联网本质）。
  3. 分组交换分两种连接形态：
  • 虚电路：发前建逻辑通路，分组同路径（ATM、MPLS、X.25），网络层有状态。
  • 数据报：每包独立选路（IP），无连接无状态可能乱序。
💡 记忆口诀："TCP 是端到端有状态，跑在无状态的数据报 IP 之上——这就是端到端原则：可靠性放终端，网络只管转发。"
1.5 "连接"在 OSI/TCP-IP 各层分别是什么形态？进阶

标准答案（五层对照）：

  • 应用层：应用会话/逻辑连接（HTTP Keep-Alive、WebSocket、TLS Session）。
  • 传输层：端到端连接（四元组+状态机，TCP/SCTP）。
  • 网络层：无连接数据报（IP、MPLS LSP）。
  • 链路层：点到点/局域网连接（以太网、PPP、Wi-Fi）。
  • 物理层：物理链路/信道（铜缆、光纤）。
💡 记忆口诀："一条网页请求从上到下五层连接：TLS 会话 → TCP → IP 路由 → 以太网 → 光纤。"能一口气对应完 = 真懂网络。

02 TCP 三次握手

2.1 三次握手的过程与每个报文的作用？高频

标准答案（三步背法）：

  1. 客户端 → 服务端：SYN=1, seq=x（客户端进 SYN_SENT）。含义：我想连，起始序号 x。
  2. 服务端 → 客户端：SYN=1, ACK=1, seq=y, ack=x+1（服务端进 SYN_RCVD）。含义：同意，我的起始序号 y，期望你从 x+1 发。
  3. 客户端 → 服务端：ACK=1, seq=x+1, ack=y+1（双方 ESTABLISHED）。含义：收到，连接建立。
💡 记忆口诀："SYN 我来了，SYN+ACK 我同意你来了，ACK 我确认你也收到了我。"本质是双向确认收发能力 + 序号同步。
2.2 为什么是三次握手，不是两次或四次？高频

标准答案（防失效历史连接）：

  1. 为什么不是两次：防失效的历史 SYN 突然到达。客户端超时重传的 SYN 已建立成功，旧 SYN 才到达——两次握手时服务器会为旧 SYN 分配资源，而客户端根本不认，白占资源。三次握手时服务器回 SYN+ACK，客户端发现不是自己期望的连接，回 RST 拒绝，服务器识别出失效连接。
  2. 为什么不用四次：三次已完成双向收发能力确认 + 序号同步，第四次冗余。
💡 记忆口诀："两次握手防不了旧包诈尸；第三次 ACK 是给服务器'确认客户端还活着'的机会，把确认成本前置给发起方。"
2.3 SYN Flood 攻击原理与防护？高频

标准答案：

  1. 原理：伪造大量源 IP 发 SYN，服务器回 SYN+ACK 后等不到 ACK，半连接队列被占满，正常客户连不上。
  2. 防护（四板斧）：
  • SYN Cookie（核心）：不分配半连接资源，把握手信息哈希进 ISN，收到 ACK 现场校验建连。
  • 缩短 SYN 超时：tcp_synack_retries 降到 1~2。
  • 网关限速/黑白名单：DDoS 清洗。
  • 调大 tcp_max_syn_backlog：扩容缓解不治本。
💡 记忆口诀："Cookie 是溢出时的兜底，队列容量是第一道防线。"代价：SYN Cookie 下窗口缩放/SACK 等选项无法协商。
2.4 三次握手可以携带数据吗？进阶

标准答案：

  1. 第一次 SYN：不能带（服务端未确认客户端身份，带数据会放大 SYN Flood 攻击面）。
  2. 第二次 SYN+ACK：不能带。
  3. 第三次 ACK：可以带（已确认服务器可达，捎带首包数据省一个 RTT）。
💡 记忆口诀："前两次不带防伪造，第三次捎带是合法操作。TCP Fast Open 更进一步：Cookie 认证后 SYN 直接带数据，实现 0-RTT。"
2.5 TCP 初始序列号（ISN）为什么不能固定？进阶

标准答案：

  1. 固定 ISN 可被预测伪造，实施会话劫持（TCP Spoofing）。
  2. 固定 ISN 会让旧连接遗留报文与新连接序号重叠污染。
  3. 现代实现（RFC 1948）：ISN = 时钟 + 四元组相关随机哈希（Linux secure_tcp_seq()）。
💡 记忆口诀："ISN 随机化防预测、防新旧串扰；也解释了 TIME_WAIT 2MSL 后旧报文必然消亡——随机序号+时间窗双重保险。"

03 TCP 四次挥手

3.1 四次挥手的过程？高频

标准答案（A 主动关闭）：

  1. A → B：FIN=1, seq=u（A 进 FIN_WAIT_1）。我发完了，关发送方向。
  2. B → A：ACK=1, ack=u+1（B 进 CLOSE_WAIT，A 进 FIN_WAIT_2）。收到，我还有数据。
  3. B → A：FIN=1, seq=w（B 进 LAST_ACK）。我也发完了。
  4. A → B：ACK=1, ack=w+1（A 进 TIME_WAIT，等 2MSL；B 收到即 CLOSED）。
💡 记忆口诀："FIN 只关发送方向，TCP 双工两方向独立关——所以四次。主动方发 FIN 后仍能收（半关闭）。"
3.2 为什么挥手四次、握手三次？高频

标准答案：

  • 握手：服务器的 SYN 和 ACK 可合并（没有"等业务数据"的约束）。
  • 挥手：B 收到 FIN 后先回 ACK，但可能还有数据要发，不能立刻发 FIN——FIN 与 ACK 必然分开，天然四次。
  • 只有 B 恰好没数据时 FIN+ACK 可合并成三次。
💡 记忆口诀："握手是'我有话说'，挥手是'我说完了'——对方说完了我还得把话说完，所以多一次。"FIN_WAIT_2 堆积 = 对端应用不 close。
3.3 TIME_WAIT 是什么？为什么 2MSL？高频

标准答案：

  1. TIME_WAIT：主动关闭方发完最后一个 ACK 后等待 2MSL 的状态（Linux MSL≈30s，共约 60s）。
  2. 两个作用：
  • 保证最后一个 ACK 可靠到达（丢了还能重发，配合对方重传 FIN）。
  • 让旧连接的延迟报文在 2MSL 内消亡，不污染新连接。
💡 记忆口诀："TIME_WAIT 是主动关闭方的专利，被动方不进。'量大不是病，端口耗尽才致命'——每秒新建×60s 接近 6.5 万才是危险线。"
3.4 TIME_WAIT 过多怎么处理？高频

标准答案（按优先级）：

  1. 连接复用（治本）：Keep-Alive/连接池，减少"建-断"次数。
  2. 内核参数（缓解）：tcp_tw_reuse=1（仅客户端角色）+ tcp_timestamps=1。
  3. 架构调整：让对端主动断开，把 TIME_WAIT 转移出去；负载均衡分摊。
💡 记忆口诀："禁用 tcp_tw_recycle——NAT 下时间戳倒置会误杀正常连接，Linux 4.12 已删除。主动说这句话是明显加分项。"
3.5 CLOSE_WAIT 堆积的原因与排查？高频

标准答案：

  1. 原因：被动关闭方收到 FIN 回 ACK 后应用没调用 close()——代码 Bug（没处理关闭事件、异常漏 close、线程池耗尽）。
  2. 排查三板斧：
  • ss -antp | grep CLOSE_WAIT 定位进程。
  • jstack <pid> 找阻塞线程（先看线程池！）。
  • 代码审计 close 路径（finally/异常分支）。
💡 记忆口诀："TIME_WAIT 多找网络层/架构，CLOSE_WAIT 多查应用代码——两者正好相反。"CLOSE_WAIT 堆积 = fd 泄漏信号。

04 TCP 状态机与连接队列

4.1 TCP 11 种状态怎么背？进阶

标准答案（两条主线）：

  • 服务端主线：LISTEN → SYN_RCVD → ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED。
  • 客户端主线：SYN_SENT → ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED。
  • 另有：CLOSED（初始）、CLOSING（双方同时 FIN，罕见）。
💡 记忆口诀："画两条线比背表强：服务端从听(倾听)到收，客户端从发到等。"面试现场画出状态迁移线 = 稳。
4.2 半连接队列与全连接队列？高频

标准答案：

  • 半连接队列（SYN 队列）：收到 SYN、未完成握手（SYN_RCVD），大小受 tcp_max_syn_backlog 限制。
  • 全连接队列（accept 队列）：握手完成、等应用 accept()，大小 = min(listen(fd, backlog), somaxconn)。
  • 流程：SYN 入半连接 → 回 SYN+ACK → 收 ACK 移入全连接 → accept() 取走。
💡 记忆口诀："backlog 只管全连接队列，管不了半连接队列——调大 backlog 防的是'accept 不及时'，不是 SYN Flood。"
4.3 连接队列溢出怎么处理？进阶

标准答案：

  1. 全连接队列满：由 tcp_abort_on_overflow 决定——0（默认）静默丢 ACK，客户端发数据时才被 RST；1 直接回 RST。
  2. 半连接队列满：dmesg 出现 Possible SYN flooding on port，大概率被攻击。
  3. 排查：ss -lnt 看 Recv-Q（当前队列）vs Send-Q（上限），Recv-Q 顶满不降 = 应用 accept 太慢。
💡 记忆口诀："先判断是哪个队列满：半连接满=网络层攻击，全连接满=应用层瓶颈。根因完全不同。"
4.4 连接队列与三次握手的交互细节？进阶

标准答案：

  1. SYN 到达 → 半连接队列建 request_sock，回 SYN+ACK。
  2. 收到 ACK → 校验后移出半连接队列，建 sock 入全连接队列。
  3. accept() 取走 → 完成。
  4. SYN Cookie 模式：不建 request_sock，握手信息编码进 ISN，收 ACK 现场校验直接建连。
💡 记忆口诀："Cookie 是'溢出才触发'的兜底，队列是'入队前检查'的第一道防线。"

05 TCP 可靠性机制

5.1 TCP 如何保证可靠传输？高频

标准答案（六大机制）：

  1. 序号+确认：每字节一个序号，ACK 报"期望的下一个字节号"，有序重组去重。
  2. 超时重传：RTO 超时未确认即重传。
  3. 滑动窗口/流量控制：按接收方 rwnd 调发送量。
  4. 拥塞控制：按网络状态调 cwnd。
  5. 校验和：损坏即丢弃触发重传。
  6. 连接管理：握手/挥手保证会话正确。
💡 记忆口诀："序号确认重传打丢包，窗口打速度差（流控）和容量差（拥塞），校验和打损坏。"
5.2 超时重传与快速重传的区别？高频

标准答案：

  • 超时重传：RTO 定时器（RTO = SRTT + 4×RTTVAR），超时未收到 ACK 重传，超时后指数退避（×2），连续 15 次放弃（tcp_retries2）。
  • 快速重传：不等超时，收到 3 个重复 ACK 立即重传。原理：重复 ACK 说明下一个包丢了且后续包陆续到了。
💡 记忆口诀："快速重传阈值是 3 个重复 ACK 不是 1 个——1~2 个可能只是乱序，3 个才能判定真丢包。高频细节！"
5.3 SACK 与 D-SACK？进阶

标准答案：

  • SACK（选择确认）：精确报告已收到的非连续区间，只重传真正丢的段（传统 ACK 只能确认连续部分）。
  • D-SACK（重复 SACK）：报告重复收到的段，让发送方区分"重传导致重复"还是"绕路迟到"，优化 RTO 估算。
💡 记忆口诀："SACK 治'中间丢了一截'，D-SACK 治'我重复收到'。高带宽高延迟链路收益最大。"
5.4 滑动窗口与流量控制（rwnd）？高频

标准答案：

  • 滑动窗口：发送方维护窗口连续发送、累积确认，不必逐包等待。
  • 流量控制：接收方在 ACK 里带 rwnd（我还能收多少），发送窗口 = min(swnd, rwnd, cwnd)。
  • 零窗口：rwnd=0 停发，用窗口探测（persist timer 发 1 字节）打破死锁。
💡 记忆口诀："流控（rwnd）防'我收不过来'，拥塞控制（cwnd）防'网络受不了'——两个独立窗口，取小者。"
5.5 拥塞控制四阶段？高频

标准答案：

  1. 慢启动：cwnd 从 1（实为 10）个 MSS 指数增长，到 ssthresh 停止。
  2. 拥塞避免：超过 ssthresh 后线性增长（每 RTT +1）。
  3. 快速恢复：3 个重复 ACK 触发，cwnd 减半而非清零，配合快速重传。
  4. 超时重传：视为严重拥塞，cwnd 归 1、ssthresh 减半，重新慢启动。
💡 记忆口诀："AIMD 灵魂：加性增、乘性减。重复 ACK 减半、超时清零——区别必考。"Linux 默认 CUBIC，新内核支持 BBR。
5.6 CUBIC 与 BBR 的区别？进阶

标准答案：

  • CUBIC（Linux 默认）：三次函数控制窗口增长，与 RTT 无关，适合大带宽长链路；用丢包当拥塞信号。
  • BBR（Google）：不靠丢包，持续探测带宽×时延（BDP），把窗口稳定在 BDP 附近；高丢包高带宽链路吞吐远超 CUBIC（YouTube 提升 2~25 倍）。
💡 记忆口诀："CUBIC 靠丢包判拥塞，BBR 靠测量定窗口。BBR 的争议：会吃掉瓶颈路由器排队缓存，bbr2 才修公平性。"
5.7 粘包与拆包的原因和解决？高频

标准答案：

  1. 原因：TCP 是字节流协议，不保留应用消息边界——多次 send 可能合并交付（Nagle、缓冲区），一次 send 可能拆开发送。
  2. 解决四选一：
  • 定长消息：固定长度切分（浪费）。
  • 分隔符：\n 结尾（Redis RESP；要处理转义）。
  • 长度前缀（最常用）：4 字节长度头 + 载荷（HTTP/2 帧、Netty）。
  • 自定义协议：魔数+版本+长度（Dubbo、MQ）。
💡 记忆口诀："粘包不是 TCP 的 Bug，是流协议没有消息边界的必然。UDP 是数据报天然不粘包。实时场景可关 Nagle（TCP_NODELAY）。"

06 长连接保活与连接数量

6.1 TCP KeepAlive 的三个内核参数？高频

标准答案：

  • tcp_keepalive_time（默认 7200s）：空闲多久开始探测。
  • tcp_keepalive_intvl（默认 75s）：探测包间隔。
  • tcp_keepalive_probes（默认 9）：连续几次无响应判定死亡。
💡 记忆口诀："7200+75×9≈2.2 小时才能发现对方死了——太慢，所以实时场景必须应用层心跳。"KeepAlive 只保活已建立连接。
6.2 应用层心跳 vs TCP KeepAlive？高频

标准答案：

  • TCP KeepAlive：内核实现，间隔 2 小时太慢，只知道"连接死没死"，防僵尸连接。
  • 应用层心跳：应用代码实现，间隔可控（如 30s），可携带业务数据，真正检测活跃度。
  • 实践：两者都用——TCP KeepAlive 兜底清理僵尸，应用心跳做活跃检测（连续 N 次未收到才判死，防抖动）。
💡 记忆口诀："30s 是工程经验值——要小于运营商 NAT 映射超时（约 30~120s），否则映射被回收连接被掐。"
6.3 长连接 vs 短连接怎么选？高频

标准答案：

  • 短连接：每次 3 次握手+4 次挥手，时延多 1~2 RTT，产生大量 TIME_WAIT；适合低频一次性请求。
  • 长连接：首次建连后复用，无额外握手 RTT，常驻 fd/内存/保活开销；适合高频交互、实时推送、内部 RPC。
  • 选择：B/S 高频 → Keep-Alive/HTTP/2；RPC/DB/Redis/MQ → 连接池长连接；低频一次性 → 短连接。
💡 记忆口诀："短连接瓶颈在握手 RTT，长连接瓶颈在连接管理与保活——HTTP/2 多路复用本质是驯服建连成本。"
6.4 一台服务器最多能建立多少 TCP 连接？高频

标准答案（四重约束）：

  1. fd（最直接）：每连接至少 1 个 fd，ulimit -n 决定。
  2. 内存：每连接内核态约 3~4KB，百万连接 3~4GB+，加用户态轻松几十 GB。
  3. 端口：服务端监听同一端口可接受海量连接（靠客户端端口区分）；客户端单 IP 最多约 6.5 万源端口。
  4. CPU 中断：每连接收发包触发软中断，隐藏瓶颈。
💡 记忆口诀："C10K 过时了，现代 epoll 单机百万连接；C10M 要靠 DPDK/XDP 内核旁路。瓶颈不是内核，是 fd/内存/中断的工程调配。"
6.5 C10K / C10M 与 epoll？高频

标准答案：

  • C10K 解法 = I/O 多路复用：
  • select/poll：全量 fd 拷用户态，O(n) 遍历，低效。
  • epoll（Linux）：事件驱动+就绪回调，只返回就绪 fd，O(1)。ET（边缘触发）vs LT（水平触发）。
  • macOS 用 kqueue，Windows 用 IOCP。
  • C10M：epoll 不够，需 DPDK/XDP 内核旁路、多队列网卡（RSS）、无锁编程。
💡 记忆口诀："LT 有数据就通知（编程简单），ET 只通知一次必须读干净（配非阻塞循环）。Redis/Node 用 ET，Netty 默认 LT。"

07 UDP 与可靠 UDP

7.1 UDP 为什么"无连接"？基础

标准答案：

  • UDP 头仅 8 字节：源端口、目的端口、长度、校验和——没有序号/确认/窗口/状态，所以不需要连接。
  • "无连接"三层含义：无需握手、无状态（内核无连接表）、无保证（不保证送达/有序/不重复）。
💡 记忆口诀："UDP 头短到只有 8 字节，才能让 QUIC 在用户态把连接状态搬上来自造——这是 QUIC/KCP 能落地的前提。"
7.2 UDP 报文最大多大？MTU 分片？进阶

标准答案：

  • 理论最大：长度字段 16 bit，载荷最大 65507 字节（减 IP 头 20 + UDP 头 8）。
  • 实际限制：超过 MTU（以太网 1500）触发 IP 分片，丢一片整个报文作废（IP 不重传）。
  • 最佳实践：载荷 ≤ 1472 字节（1500-20-8），或应用层分片+序号重组（QUIC）。
💡 记忆口诀："1472 是安全线。PMTUD 防分片，但某些网络静默丢大包——'小包通、大包不通'就是 PMTUD 失效的经典故障。"
7.3 如何基于 UDP 实现可靠传输？高频

标准答案（自研 RUDP 六要素）：

  1. 序号：检测丢包/乱序/重复。
  2. ACK/NACK + 重传：NACK（报丢哪些）比纯 ACK 高效；超时+快速重传。
  3. 缓冲排序：重排乱序报文。
  4. 流量控制：滑动窗口。
  5. 拥塞控制：可选（游戏常简化）。
  6. 连接 ID：代替四元组，支持连接迁移。
💡 记忆口诀："RUDP = 把 TCP 的能力挑着抄到 UDP 上。别从零造轮子——直接用 QUIC 或 KCP，拥塞控制做对太难。"
7.4 QUIC 的核心特性？进阶

标准答案（五点）：

  1. 0-RTT/1-RTT 建连：首次 1-RTT，复用会话 0-RTT（比 TCP+TLS 的 2~3 RTT 快）。
  2. 连接 ID 与连接迁移：不绑 IP:端口，换网不断连。
  3. 无队头阻塞：按 stream 独立可靠传输，一个 stream 丢包不影响其他。
  4. TLS 1.3 内嵌：加密与传输握手合一。
  5. 用户态实现：迭代快，无需 NAT 打洞。
💡 记忆口诀："HTTP/2 的队头阻塞在 TCP 层——丢一个包整条连接上的流全等；QUIC 把它隔离到单 stream，这是 HTTP/3 选 QUIC 的根本原因。"
7.5 TCP 与 UDP 如何选择？高频

标准答案（决策模型）：

  1. 要可靠+有序+通用 → TCP（HTTP、DB、文件、RPC）。
  2. 容忍少量丢失但要低时延 → UDP（音视频、游戏指令）。
  3. 要可靠又要低时延/连接迁移 → QUIC。
  4. 广播/组播/任播 → 只能 UDP。
  5. DNS → UDP 为主，超时重试切 TCP。
💡 记忆口诀："TCP 用时间换可靠，UDP 用不可靠换时间，QUIC 两个都要。视频会议不用 TCP：丢包重传+队头阻塞会卡顿，宁可丢旧帧渲染新帧。"

08 HTTP 连接模型演进

8.1 HTTP/1.0 与 HTTP/1.1 连接的区别？高频

标准答案：

  • HTTP/1.0：默认短连接，每请求响应后关闭，重复握手开销大。
  • HTTP/1.1：默认持久连接（Keep-Alive），同一 TCP 连接串行多请求；Connection: close 显式关闭。
💡 记忆口诀："Keep-Alive 解决了重复握手，但 HTTP/1.1 仍串行+浏览器单域 6 连接上限——这两个痛点正是 HTTP/2 要解决的。"
8.2 HTTP/2 多路复用是什么？高频

标准答案：

  1. 二进制分帧：请求响应拆成帧，帧带 Stream ID。
  2. 多路复用：一个 TCP 连接并发多个流，帧交错发送，响应可乱序（按流 ID 重组），消除 HTTP 层队头阻塞。
  3. HPACK 头部压缩：体积降 80%+。
  4. Server Push：服务端主动推资源（已渐弃用）。
💡 记忆口诀："HTTP/2 解决了 HTTP 层的队头阻塞，但 TCP 层还在——丢一个包，整条连接所有流都等。这句接不上就露怯了。"
8.3 HTTP/2 为什么还有队头阻塞？进阶

标准答案：

  • 所有流共享一个 TCP 连接，一个流的包丢失 → TCP 接收缓冲按序交付 → 整条连接所有流阻塞，直到重传到达。
  • 量化：丢包率 0.1% 仍优于 HTTP/1.1；超过 1~2% 反而更慢（HTTP/1.1 多连接互相独立）。
💡 记忆口诀："临界点：丢包率 1~2% 是 HTTP/2 与 HTTP/1.1 的胜负手——答出这个量化结论，面试官会认为你真懂。"
8.4 HTTP/3 相对 HTTP/2 的改进？进阶

标准答案：

  1. 无 TCP 层队头阻塞：QUIC 按流独立可靠传输，一个流丢包不影响其他流。
  2. 0-RTT 建连：复用缓存参数与 TLS 密钥（有重放风险，仅幂等请求）。
  3. 连接迁移：连接 ID 不随 IP 变，Wi-Fi 切 4G 不断连。
  4. 基于 UDP：用户态实现，迭代快。
💡 记忆口诀："TCP+TLS1.3 约 2 RTT，HTTP/3 首次 1 RTT、复用 0 RTT。移动端弱网收益最大，2023 起三大浏览器默认启用。"
8.5 HTTP 连接池如何复用连接？高频

标准答案（池化四机制）：

  1. 缓存：按 (scheme, host, port) 分组存空闲连接。
  2. 复用：优先取池中空闲连接，超时未取到才新建。
  3. 驱逐：空闲超时、连接数上限、过期清理。
  4. 健康检查：取出时校验可用性，失效废弃重建。
💡 记忆口诀："连接池=以空间换时间+复用昂贵建连成本。HTTP/2 时代池的'路由'从连接细化到流，连接需求大降。"

09 WebSocket

9.1 WebSocket 握手过程？高频

标准答案：

  1. 客户端发 HTTP Upgrade 请求：Upgrade: websocket + Sec-WebSocket-Key（随机 16 字节 base64）+ Sec-WebSocket-Version: 13。
  2. 服务器算 Sec-WebSocket-Accept = Base64(SHA1(Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))，回 101 Switching Protocols。
  3. 升级为全双工双向数据通道。
💡 记忆口诀："Key 防缓存代理伪造。握手后连接不复用给普通 HTTP——网关/负载均衡必须放行 upgrade 头，否则被截断。"
9.2 WebSocket 与轮询、SSE 的对比？高频

标准答案：

  • 轮询：客户端定时拉，单向，开销高。
  • 长轮询：挂起请求直到有数据，单向，弱网兜底。
  • SSE：服务器→客户端单向流，HTTP 协议，内置重连（Last-Event-ID）。
  • WebSocket：全双工双向，独立帧协议，实时性最好，重连需自实现。
💡 记忆口诀："只做服务器单向推送优先 SSE（简单+自带重连）；要双向交互才上 WebSocket。不是所有实时场景都该用 WS——成熟话术。"
9.3 WebSocket 帧结构与掩码的作用？进阶

标准答案：

  • 帧字段：FIN（最后帧）、opcode（0x1 文本/0x2 二进制/0x8 关闭/0x9 Ping/0xA Pong）、MASK、Payload len、Masking-Key。
  • 掩码规则：客户端→服务器必须置 MASK=1，服务器→客户端必须为 0。
💡 记忆口诀："掩码的真实目的是防'缓存投毒攻击'——让载荷对中间代理不可预测，破坏向缓存注入伪造 HTTP 响应的攻击。答出这点非常加分。"
9.4 WebSocket 心跳与断线重连策略？高频

标准答案：

  • 心跳：优先用协议自带 Ping/Pong 帧；N 次无 Pong 判定断线。
  • 重连：立即重连 → 指数退避+随机抖动（1s/2s/4s…上限 30s）→ 重连后恢复鉴权/订阅/补消息 → 服务端限流防死循环。
💡 记忆口诀："纯指数退避会导致'雷群效应'（N 个客户端同时重连打爆服务器），必须加抖动分散。云厂商 SDK 全是'退避+抖动+上限'三段式。"

10 连接池

10.1 为什么需要连接池？基础

标准答案：

  1. 建连成本高：三次握手+鉴权+初始化（MySQL 认证、权限校验），动辄数十 ms。
  2. 无池痛点：高并发下握手风暴、TIME_WAIT 爆炸、数据库连接风暴。
  3. 池化收益：复用摊薄成本、限流保护下游、预热与监控。
💡 记忆口诀："池的本质 = 昂贵初始化与高频使用解耦。池化三要素：容量上限、空闲回收、生命周期管理——所有池都逃不出这三件事。"
10.2 数据库连接池核心参数（HikariCP）？高频

标准答案（必背参数）：

参数默认作用
maximumPoolSize10池最大连接数
minimumIdle10最少空闲连接
connectionTimeout30s获取连接超时
idleTimeout10min空闲回收（仅当空闲>minimumIdle）
maxLifetime30min连接最大存活
leakDetectionThreshold0泄漏检测阈值
💡 记忆口诀："maxLifetime 必须 < 数据库 wait_timeout（MySQL 8h），否则'僵尸连接'报错——最经典的坑。"
10.3 连接池大小怎么设置？高频

标准答案：

  • 误区：连接越多吞吐越高？错！连接是串行执行 SQL 的资源，CPU 核数是真实上限，池过大反而降吞吐。
  • 经验公式：连接数 = CPU核数 × 2 + 有效磁盘数（HDD；SSD 场景乘 4~8）。
  • 调参目标：P99 延迟达标 + 池使用率 30~60%，配合压测三档对比。
💡 记忆口诀："一个活跃连接同一时刻只能跑一个查询，并发收益上限≈CPU 核数×（1/IO 等待占比）——和线程池大小是同一套建模逻辑。"
10.4 连接泄漏怎么排查？高频

标准答案：

  1. 现象：拿连接没归还（异常未 finally、线程持有不放）→ 池耗尽 → "connection pool exhausted"。
  2. 排查：leakDetectionThreshold=5000（持有超 5s 打印完整调用栈，定位到代码行）+ 监控池使用率。
  3. 根治：try-with-resources / with 语法 + 代码评审 + connectionTimeout 兜底。
💡 记忆口诀："泄漏检测只能事后发现，防不了泄漏；更本质的是编码规范+超时兜底。leakDetectionThreshold 必须 < connectionTimeout 才有意义。"

11 排障与场景题

11.1 线上大量 TIME_WAIT 怎么排查处理？高频

标准答案：

# 统计各状态数量
ss -ant | awk '{print $class="num">1}' | sort | uniq -c | sort -rn
# 看对端端口堆积
ss -ant state time-wait | awk '{print $class="num">4}' | sort | uniq -c | sort -rn
  1. 根因：本机是主动关闭方 + 短连接高频建断。
  2. 处理：连接复用（治本）→ 确认数量是否影响可用性（几万内无感）→ tcp_tw_reuse=1（仅客户端）+ 时间戳 → 架构调整让对端断开。
💡 记忆口诀："TIME_WAIT 不是故障，端口耗尽才是：每秒新建×60s 接近 6.5 万才危险。别急着清零，先看每秒新建速率。"
11.2 线上大量 CLOSE_WAIT 怎么排查处理？高频

标准答案：

ss -antp | grep CLOSE_WAIT | head -class="num">20 # 定位进程
jstack <pid> # 找阻塞线程
  1. 根因：被动关闭方收到 FIN 后应用没 close()。
  2. 排查顺序：ss 定位进程 → jstack 找阻塞线程（先看线程池！）→ 代码审计 close 路径。
  3. 兜底：调 tcp_keepalive_time 加速回收（治标）。
💡 记忆口诀："CLOSE_WAIT 三板斧：ss 定位 → jstack 查线程池 → 审计 close。大多数堆积是'线程池被慢下游占满，没机会 close'，先看线程池比先看代码高效。"
11.3 connect timeout 与 read timeout 的区别？高频

标准答案：

  • connect timeout：握手完成的等待上限。原因：目标不可达、防火墙丢 SYN、半连接队列满。建议：局域网 1~3s，公网 3~5s。
  • read timeout：连接建立后等响应数据的时限。原因：服务端慢、死锁、拥塞。建议：业务 P99 × 3~5。
💡 记忆口诀："connect 要短（快速失败），read 要按业务容忍度给足余量。read 超时后多数框架直接关连接——连接不可复用。"
11.4 断线重连策略？高频

标准答案：

delay = min(base * class="num">2^attempt, max_delay) + random(class="num">0, jitter)
# 例：base=1s, max=60s → 1s,2s,4s,8s…60s
  1. 成功连接后重置计数。
  2. 连续失败达上限进入长等待，防死循环。
  3. 重连后恢复状态：重放订阅/鉴权/断点续传。
  4. 服务端记录重连频率，超频拒绝。
💡 记忆口诀："jitter 的理由：N 个客户端同时断网恢复时，无抖动会集体重连（惊群）把刚恢复的服务器再次打挂。Kafka 消费者、云 SDK 全内置。"
11.5 NAT 穿透与 UDP 打洞？进阶

标准答案：

  1. NAT 四类型（松→严）：全锥形 → 受限锥形 → 端口受限锥形 → 对称 NAT。
  2. UDP 打洞：双方同时向对方公网地址发 UDP，利用"受限锥形允许已通信 IP 反向发包"互相踩通映射。
  3. 对称 NAT 下打洞必失败 → 兜底 TURN 中继（WebRTC：先 P2P 后降级 TURN）。
💡 记忆口诀："打洞适用受限锥形，对称 NAT 必须 TURN。TCP 打洞更难（SYN 时序不可控），P2P 一般 UDP 打洞+上层可靠协议。"
11.6 百万长连接网关架构怎么设计（IM 场景）？进阶

标准答案（六层设计）：

  1. 接入层无状态集群：epoll 支撑十万~百万级连接，连接只在本机。
  2. 会话路由：Redis 记录 userId → 网关节点。
  3. 水平扩展：服务发现自动注册，客户端重连路由新节点。
  4. 心跳与踢人：30s 心跳判离线，同账号踢旧连接。
  5. 消息可靠性：客户端 ack + 服务端序号 + 离线消息落 MQ/DB。
  6. 瓶颈点：fd 上限、每连接内存（压到 2~4KB）、CPU 软中断（多队列 RSS）、GC 停顿（Netty 堆外内存）。
💡 记忆口诀："IM 核心哲学：连接与状态分离——连接可丢、状态不丢。网关挂了 = 客户端重连新网关 + 从 Redis 恢复状态，用户无感知。"
