01 Kafka 核心概念与架构

1.1 Kafka 是什么？核心角色与定位？【必背】

答案骨架：

  • Kafka 是 LinkedIn 开源（2011 年进 Apache）的分布式消息队列 / 流处理平台，Scala + Java 编写。
  • 三大核心能力：发布订阅（Pub/Sub）、数据存储（可回溯）、流处理（Kafka Streams）。
  • 四大角色：
  • Producer（生产者）：发消息。
  • Broker（服务端）：存消息，集群由多个 Broker 组成。
  • Consumer（消费者）：拉消息。
  • ZooKeeper / KRaft：协调器（早期管元数据与选举，KRaft 时代被替代）。

口诀： P 发、B 存、C 拉、ZK 管 —— 一条链路，四个角色。

加分点： 区别于"用完即走"的 MQ，Kafka 本质是日志系统：消息落盘可重复消费、可回溯（offset 不删除消息），所以它能同时当"队列"和"流数据平台"。

追问： Kafka 消息会被消费后删除吗？—— 不会，按 retention.ms（默认 7 天）或分区大小保留，消费者各自记录自己的 offset。

1.2 Topic / Partition / Offset 三件套？【必背】

答案骨架：

  • Topic（主题）：消息的逻辑分类，一个 Topic 下可以有很多分区。
  • Partition（分区）：物理分片，每个分区是一个有序的日志文件（append-only）；分区内有序、跨分区无序。
  • Offset（位移）：分区内每条消息的递增编号（从 0 开始），是消息的唯一位置标识，也是消费者消费进度的游标。
  • 消息归属：partition = hash(key) % 分区数（无 key 则轮询/粘性分区）。

口诀： Topic 分类、Partition 分片、Offset 编号 —— 分区内有序，全局只保证这个。

加分点： 分区数决定并行度（并发上限 = min(分区数, 消费者数)）；但分区不是越多越好：文件句柄、rebalance 时间、元数据都会膨胀。

追问： 为什么 Kafka 只在分区内有序？—— 全局有序就要单分区，牺牲并行度；业务上按 key 分区即可保证"同一 key 有序"。

1.3 Kafka 为什么快？核心六板斧【必背】

答案骨架：

  1. 顺序写盘：消息 append-only 追加写，磁盘顺序写接近内存速度（600MB/s+）。
  2. Page Cache：读写都优先走操作系统的页缓存，避免 JVM GC 与对象开销。
  3. 零拷贝：消费走 sendfile（内核态直接搬数据），生产走 mmap，省去用户态拷贝。
  4. 批量 + 压缩：生产者攒批（batch）、服务端按批存储、消费者按批拉取，消息压缩（lz4/zstd/snappy）降网络 IO。
  5. 稀疏索引：日志配 index 文件，二分查找定位，不逐条扫。
  6. 无状态 Broker + 分区并行：Broker 不维护消费状态（offset 在消费者侧），天然易水平扩展。

口诀： 顺序写、页缓存、零拷贝、批压、稀疏索引、无状态 —— 六板斧砍出百万 TPS。

加分点： 面试亮点：Kafka 的"快"本质是 用磁盘换性能（顺序 IO），把传统 MQ 的"内存+随机 IO"换成"Page Cache + 顺序 IO"，再叠加"批量"把 IO 次数降到最低。

追问： Page Cache 会不会导致丢消息？—— 不会主动丢，但断电/宕机会丢（页缓存未刷盘），生产用 log.flush.interval.messages/fsync 参数权衡性能与安全。

1.4 AR / ISR / OSR 三兄弟？【必背】

答案骨架：

  • AR（Assigned Replicas）：分区的所有副本集合。
  • ISR（In-Sync Replicas）：同步中的副本集合（与 Leader 保持同步、存活），写入只认 ISR。
  • OSR（Out-of-Sync Replicas）：落后/失联的副本（= AR - ISR）。
  • 副本同步判定：Follower 持续向 Leader 拉数据，落后超过 replica.lag.time.max.ms（默认 30s）就会被踢出 ISR；追上了再加回来（ISR 是动态伸缩的）。

口诀： AR 全员、ISR 在岗、OSR 掉队 —— 写入只问 ISR。

加分点： ISR 是 Kafka 高可用与一致性的枢纽：HW（高水位）只推进到 ISR 里最慢的那个，ISR 收缩过小说明副本健康堪忧，是排查丢数据的第一站。

追问： ISR 可以变成空吗？—— 极端情况可能，此时 Leader 可自行推进 HW（取决于 min.insync.replicas 与 unclean 配置），也可能触发"未同步副本竞选"。

1.5 Kafka vs RabbitMQ vs RocketMQ？【中频】

答案骨架：

维度KafkaRabbitMQRocketMQ
模型Topic 分区日志Exchange/QueueTopic/Queue
吞吐百万级万级十万级
顺序性分区内严格单队列队列内严格
消息回溯支持（offset 重放）不支持支持（时间点）
消费模式拉 Pull推 Push/拉推拉结合
事务幂等+事务弱分布式事务强
典型场景日志、大数据、削峰业务消息、低延迟金融、事务消息

口诀： Kafka 要吞吐、RabbitMQ 要轻快、RocketMQ 要事务 —— 按需点单。

加分点： 面试常问"为什么选 Kafka"：日志类高吞吐 + 可回溯 + 生态（Flink/Spark）最顺；但业务级强事务/死信/延迟队列 RabbitMQ/RocketMQ 更顺手。

追问： Kafka 是推还是拉？—— 拉（Pull）：消费者主动拉取，服务端无状态、可批量、可控速；缺点是有延迟（可长轮询缓解）。

02 生产者原理

2.1 生产消息完整流程？【必背】

答案骨架： 一条消息的旅程：

Producer 拦截器(interceptor) → 序列化器(serializer) → 分区器(partitioner)
→ 攒批进缓冲区(accumulator, 默认 32MB)
→ Sender 线程按批次取出（满足 batch.size 或 linger.ms）
→ 发送到 Leader → 等待 acks → 回调(callback) 通知成功/失败
  • 关键：异步 + 批量 —— 主线程只负责往缓冲区塞，真正发送是后台 Sender 线程。

口诀： 拦截 → 序列化 → 分区 → 进缓冲区 → 批量发 → 等 ack → 回调。

加分点： max.block.ms 控制"缓冲区满时等待"；batch.size（默认 16KB）与 linger.ms（默认 0）决定攒批策略；buffer.memory 默认 32MB。

追问： linger.ms 调大会怎样？—— 吞吐↑（攒更多批）但延迟↑；追求低延迟设 0~5，追求吞吐设 10~100。

2.2 分区选择策略？高频

答案骨架：

  1. 指定 partition：直接发指定分区（最高优先级）。
  2. 指定 key：hash(key) % 分区数 → 同一 key 永远进同一分区（顺序性）。
  3. 无 key（新版本默认）：Sticky Partition（粘性分区）—— 一批消息粘在一个分区，攒够再换，减少请求次数，提升吞吐（旧版是轮询）。

口诀： 指定分区 > 按 key 哈希 > 粘性轮询。

加分点： 粘性分区是 2.4+ 的优化点，问"生产者为什么吞吐高"可以扯到它：消息尽量粘在同一分区攒批，减少跨分区请求。

追问： key 哈希能保证稳定吗？—— 分区数不变则稳定；扩容分区数会打乱映射，所以需要顺序性的场景扩容要谨慎（或按"业务 id 子分区"设计）。

2.3 acks 三种可靠性语义？【必背】

答案骨架：

acks含义可靠性场景
0不等确认，发完就算成功最差（可能丢）日志、监控（可丢）
1Leader 写成功即确认（默认）中（Leader 挂了丢）大多数业务
-1/allISR 全部写成功才确认最好（配合 min.insync.replicas）金融、关键数据

口诀： 0 不回头、1 认 Leader、all 等全员 —— 可靠性按需加钱。

加分点： acks=all 必须配合 min.insync.replicas（如 =2）才有意义：否则 ISR 只剩 Leader 时 all 也退化成 1。三者组合：acks=all + min.insync.replicas=2 + retries 才是生产推荐。

追问： acks=all 一定不丢吗？—— 还受 retries、unclean.leader.election 影响；若允许"非 ISR 副本竞选 Leader"，仍可能丢数据。

2.4 生产者重试与顺序性冲突？进阶

答案骨架：

  • retries：发送失败重试次数（默认 Integer.MAX，配合 delivery.timeout.ms 限总时长）。
  • max.in.flight.requests.per.connection（默认 5）：同一连接上未确认的请求数。
  • 重试 + 乱序的坑：第一批发送失败重试，第二批已发出，若重试成功晚到，则消息顺序颠倒（0、1、2 → 0、2、1）。
  • 解法：① 置 max.in.flight=1（保顺序但掉吞吐）；② 开启幂等（enable.idempotence=true，默认开），Broker 端按序去重，允许 >1。

口诀： 重试会乱序，幂等来兜底；要不就 in.flight=1 锁死。

加分点： 2.8+ 默认 enable.idempotence=true 且 max.in.flight=5 也保证顺序 —— 因为幂等生产者的 seq 校验会让重试批次按序落盘。

追问： 幂等如何保证顺序？—— 见 2.5，Broker 按 (PID, Partition, seq) 校验，seq 必须连续递增，乱序批次被拒绝/等待。

2.5 幂等生产者原理？【必背】

答案骨架：

  • 开启 enable.idempotence=true 后，每条消息带 PID（生产者 ID）+ Sequence Number（序号，分区内自增）。
  • Broker 端为每个 (PID, 分区) 维护一个 已接收的最大序号：
  • 新消息序号 = 上一条 + 1 → 正常接收。
  • 序号 ≤ 已接收 → 重复，直接丢弃。
  • 序号 > 上一条 + 1 → 乱序/缺号，拒绝（等重试）。
  • 结果：单生产者、单分区内的消息不重复、不丢失、有序。

口诀： PID + seq，Broker 查重 —— 重复丢、乱序拒、断号等。

加分点： 幂等只能保证单会话单分区的 exactly-once；跨分区/多会话要用事务（2.6）。

追问： PID 什么时候失效？—— 生产者重启 PID 会变（或旧 PID 过期），所以"崩溃重启后"的重复仍可能发生，幂等不是跨进程的。

2.6 Kafka 事务与 exactly-once？进阶

答案骨架：

  • 事务 = 把多个分区的写入（可跨 Topic）做成原子操作：要么全部成功、要么全部回滚。
  • 核心组件：Transaction Coordinator（事务协调器，在 Broker 内） + 事务日志（内部 Topic __transaction_state）。
  • 流程：
  1. 生产者向 Coordinator 发起事务（initTransactions）。
  2. 写消息前标记分区（AddPartitionsToTxn），消息带事务 id。
  3. 提交时 Coordinator 写 PREPARE_COMMIT → 各分区写 COMMIT 标记（LSO 后的控制消息） → 完成。
  • 消费端配合 isolation.level=read_committed 才能只读到已提交的消息。

口诀： Coordinator 记账，分区写标记，提交才可见 —— 多分区原子提交。

加分点： 事务实现真正 exactly-once（端到端）：事务写 + read_committed 消费 + 幂等消费（offset 去重），是 Kafka 精确一次的完整链路。

追问： 事务性能开销大吗？—— 有额外 RTT（标记分区、提交协调），追求极致吞吐的业务一般不用；且事务不能跨 Kafka 集群（可用消息最终一致性代替）。

03 消费者原理

3.1 消费流程与位移（offset）管理？【必背】

答案骨架：

  • 消费者是拉模式：poll() 批量拉取（默认 max.poll.records=500），处理完后提交 offset 表示"这段我消费完了"。
  • offset 存哪：内部 Topic __consumer_offsets（50 个分区，按 groupId hash），老版本存 ZK。
  • 消费进度 = 消费者自己提交的 offset，Broker 不记录谁消费到哪 —— 这就是"无状态 Broker"。

口诀： poll 拉、处理完、提交 offset —— 进度在消费者手里。

加分点： enable.auto.commit（默认 true）每 auto.commit.interval.ms（5s）自动提交；手动提交更可控（commitSync 同步阻塞 / commitAsync 异步回调）。

追问： offset 提交太早/太晚会怎样？—— 早提交：处理中途崩溃 → 消息丢失（offset 已提交但没处理完）；晚提交：处理完未提交崩溃 → 重复消费（重启从头拉）。

3.2 消费组与分区分配策略？【必背】

答案骨架：

  • Consumer Group（消费组）：组内消费者共同分担一个或多个 Topic 的所有分区；一个分区同一时刻只能被组内一个消费者消费（互斥）。
  • 三大分配策略（partition.assignment.strategy）：
  1. Range（范围，默认）：按 Topic 逐个分配，分区数/消费者数整除 —— 不均时前几个消费者多分。
  2. RoundRobin（轮询）：所有分区排好队轮流分，整体均衡。
  3. Sticky（粘性，2.4+）：在轮询基础上尽量保持上次的分配（rebalance 时少挪动），3.x 默认。

口诀： Range 按 Topic 割、RoundRobin 轮流发、Sticky 尽量不搬家。

加分点： 组内消费者数 > 分区数时，多出的消费者空转（拿不到分区）；最大消费并行度 = 分区数。

追问： 一个消费者能消费多个分区吗？—— 能，一个消费者默认可以持有多个分区；分区是组内唯一持有单元。

3.3 offset 提交的四种姿势？高频

答案骨架：

组合说明风险
自动提交5s 定时提交，poll 之前先提交上次易丢/易重
同步提交 commitSync处理完提交，失败会重试，阻塞吞吐低
异步提交 commitAsync提交回调，失败不重试可能漏提交
同步+异步组合关键位置同步兜底，日常异步生产推荐

口诀： 自动省事有风险、sync 稳但慢、async 快但飘、组合拳最优。

加分点： 推荐模式：循环内 commitAsync（快），循环退出前（或优雅关闭时）补一次 commitSync 兜底 —— 兼顾吞吐与可靠。

追问： commitAsync 失败会怎样？—— 失败但没回调重试，offset 停留在旧值 → 下次重启重复消费；所以"至少一次"靠"手动提交 + 处理完再提交"保证。

3.4 Rebalance 机制与协调器？【必背】

答案骨架：

  • Rebalance（再平衡）：消费者加入/退出/崩溃或分区变化时，组内重新分配分区。期间全体停止消费（stop-the-world）。
  • 触发条件：① 消费者加入/离开；② 消费者崩溃（session.timeout.ms 未心跳）；③ 分区数变化（扩分区）。
  • 协调器：Group Coordinator（某个 Broker 承担），消费者心跳 + offset 提交都找它。
  • 流程（2.4+ 新版）：
  1. 消费者向 Coordinator 发 JoinGroup。
  2. Coordinator 选 Leader 消费者，Leader 用分配策略算出分配方案。
  3. 所有消费者收 SyncGroup 结果，rebalance 完成。

口诀： 有变动就全员重排、期间停摆；心跳断了就被踢出局。

加分点： 新版优化：max.poll.interval.ms（默认 5min）代替"处理超时踢人"；静态成员（static membership） 用 group.instance.id 避免"宕机秒踢+重平衡"风暴。

追问： 消费慢会被踢吗？—— 超过 max.poll.interval.ms 没 poll 就会被判定失联踢出组 → 触发 rebalance；解法：调大该参数、减少单次 poll 记录数、或并发消费。

3.5 消息不丢 / 不重 / 有序，消费端怎么保证？【必背】

答案骨架：

  • 不丢（至少一次 At-Least-Once）：处理完业务再提交 offset（手动提交、先处理后提交）；enable.auto.commit=false。
  • 不重（幂等消费）：业务侧幂等 —— 用业务唯一键（订单号/消息 ID）去重（Redis setNX / DB 唯一索引 / 记录消费表）。
  • 有序：① 生产按 key 分区（同一 key 进同一分区）；② 消费端单分区单线程处理（max.poll.records=1 或并发队列按 key 哈希到单线程）。

口诀： 先处理再提交防丢；唯一键去重防重；按 key 分区 + 单线程保序。

加分点： 经典总结：Kafka 默认是"至少一次"，既可能重复消费（可幂等处理），也可能丢（offset 乱提交/acks=1）。要 exactly-once 必须 幂等 + 事务 + 业务幂等三方配合。

追问： 消费端怎么"优雅关闭"？—— 实现 ConsumerRebalanceListener：在 onPartitionsRevoked 里做"处理完再提交 offset"，再退出 poll 循环，避免 rebalance 丢位移。

04 存储与日志机制

4.1 日志分段存储结构？【必背】

答案骨架：

  • 每个分区一个目录：/data/topic-0/；内部按段（Segment） 切分，默认 log.segment.bytes=1GB 或 log.roll.hours 到达即滚动。
  • 一个 Segment = 三个文件（同 baseOffset 命名）：
  • 00000000000000000000.log —— 消息数据（顺序追加）。
  • ...index —— 偏移量索引（相对 offset → 物理位置）。
  • ...timeindex —— 时间索引（时间戳 → 相对 offset）。
  • 活跃段（active segment）：正在写的最后一个段，不可删除。

口诀： 一分区一目录，段切三件套：log 存数据、index 查偏移、timeindex 查时间。

加分点： 段是有序的：全局 offset = 段 baseOffset + 段内相对 offset；删除/过期按段整段删除（所以消息删除是"整段删"，粒度是段）。

追问： 为什么消息删除慢？—— 删除是删除整个 Segment 文件（顺带清理 index），不是逐条删；磁盘回收取决于段大小与 retention。

4.2 稀疏索引与二分查找？高频

答案骨架：

  • index 是稀疏索引：不是每条消息都建索引，而是每隔 log.index.interval.bytes（默认 4KB）记录一条（offset → 文件物理位置）。
  • 查找消息流程：按目标 offset 定位所属 Segment → 在 index 二分查找最近 <= 目标 offset 的条目 → 从该物理位置顺序扫到目标消息。
  • 好处：索引文件小（内存友好）、查找快（O(logN) + 少量顺序扫描）。

口诀： 稀疏索引 + 二分定位 + 顺序扫描 —— 不逐条建索引，也不逐条扫。

加分点： 面试亮点：Kafka 没有为每条消息建索引（那样索引比数据还大），用"稀疏索引 + 粗定位 + 细扫描"在内存占用与查找速度间取平衡。

追问： index 怎么保证 index 文件本身有序？—— 追加写天然有序（按 offset 递增），所以能二分。

4.3 日志清理策略：delete 与 compact？【必背】

答案骨架：

  • delete（默认）：按 时间（retention.ms，默认 7 天）或 大小（retention.bytes，按分区）删除过期段。
  • compact（日志压缩）：按 key 合并 —— 相同 key 只保留最新一条（value 最新），用于"状态快照"类数据（如配置、用户最新状态）。
  • 触发：log.cleanup.policy=compact 或 delete,compact 混合。
  • cleaner 线程：后台线程扫描日志，保留每个 key 的最新记录，删除旧记录（用布隆过滤器加速）。

口诀： delete 按时间/大小删，compact 按 key 留最新 —— 一个清历史，一个留状态。

加分点： 经典场景：消费者组 offset 用的内部 Topic __consumer_offsets 就是 compact 策略 —— 只留每个 group+分区的最新 offset；KV 状态存储（Kafka Streams changelog）也是 compact。

追问： compact 一定能压缩到很小吗？—— 不能保证，依赖 key 的分布与 cleaner 时机；且活跃段不参与压缩。

4.4 刷盘机制与消息安全性？高频

答案骨架：

  • Kafka 写消息先到 Page Cache，再由操作系统异步刷盘（log.flush.interval.messages 默认 Long.Max、log.flush.interval.ms 默认无）。
  • 可控刷盘参数（log.flush.scheduler.interval.ms、每 Broker 的 flush 配置）可强制 fsync，但大幅降低吞吐。
  • 生产不主动刷盘：靠 acks=all + ISR 多副本 保证"至少存了一份"，单机宕机依赖副本恢复 —— 即"用副本冗余替代磁盘同步"。

口诀： 写缓存、靠副本、不硬刷 —— 副本冗余换性能。

加分点： 面试高频：Kafka 保证持久性不是靠 fsync，而是靠 ISR 多副本 + acks=all；单副本 + 断电会丢 Page Cache 里未刷盘的数据。

追问： 为什么日志目录建议用独立磁盘？—— 避免与 OS 日志/其他应用 IO 竞争；且顺序写需要整块盘，RAID 无缓存场景注意掉电保护。

4.5 零拷贝细节（sendfile / mmap）？【必背】

答案骨架：

  • 消费方向（Broker → 消费者）：sendfile —— 数据从磁盘 → 内核 socket 缓冲区 → 网卡，不经过用户态，2 次拷贝（DMA + CPU）。
  • 生产方向（生产者 → Broker）：mmap —— 消息缓冲区映射到内存，写消息 = 写内存，由内核回写磁盘。
  • 对比传统 read/write：数据要"磁盘 → 内核 → 用户态 → 内核 → 网卡"，4 次拷贝 + 多次上下文切换。

口诀： 消费 sendfile 内核对内核搬，生产 mmap 当内存写 —— 都不进 JVM 用户态。

加分点： 关键：Kafka 的零拷贝把数据链路压缩到"磁盘缓冲直发网卡"，配合 Page Cache（热数据直接在内存）实现高吞吐。

追问： 传输大对象（>1MB）零拷贝还生效吗？—— 零拷贝对网络发送生效，但跨 Broker 复制、消费者大批量场景仍涉及内存缓冲；大消息会额外消耗页缓存。

05 副本与一致性

5.1 副本同步（Leader 与 Follower）细节？【必背】

答案骨架：

  • 每个分区有 1 个 Leader + N 个 Follower（replication.factor 决定）。
  • 读写都只走 Leader；Follower 主动拉取（fetch） 同步数据，不对外服务。
  • Follower 同步路径：Follower 向 Leader 发 FetchRequest（带自己的 offset）→ Leader 返回新消息 → Follower 写入本地日志。
  • ISR 判定：Follower 的 LEO 落后 Leader 的 HW 超过 replica.lag.time.max.ms（默认 30s，注意是时间阈值不是条数）→ 踢出 ISR。

口诀： 读写认 Leader，Follower 自己来拉，30 秒不跟就踢出 ISR。

加分点： Kafka 副本是"异步复制"（Leader 不等 Follower 就能 ack，除非 acks=all）→ 所以天然可能丢；ISR + acks=all 把窗口缩到最小。

追问： Follower 同步慢会被踢吗？—— 会，但按时间判断：只要 Follower 持续拉（哪怕每次很少）就不算掉队；卡住 30s 才踢。

5.2 高水位 HW 与 LEO？【必背】

答案骨架：

  • LEO（Log End Offset）：每个副本本地日志下一条要写的偏移（最新）。
  • HW（High Watermark）：ISR 中所有副本 LEO 的最小值；offset < HW 的消息对所有副本"已提交"（消费者可见）。
  • 消费者只能消费 < HW 的消息；Leader 会把自己的 HW 发给 Follower，Follower 也截断到 HW。
  • Leader Epoch（0.11+）：记录 Leader 任期，Follower 截断时以 Leader Epoch 判断该截多少，修复旧版 HW 不一致导致的丢/重。

口诀： LEO 是队尾，HW 是集体最矮 —— 低于 HW 才算数。

加分点： 面试拔高：旧版 HW 机制在"Leader 切换 + 副本截断"时可能丢数据（截断过头），Leader Epoch 通过"带任期号向新 Leader 问"精确截断，是 0.11 的重要修复。

追问： HW 谁推进？—— Leader 推进自己 HW（看 ISR 最慢 LEO），并把 HW 广播给 Follower；Follower 收到后推进自己的 HW。

5.3 Leader 选举与 Controller？【必背】

答案骨架：

  • Controller（控制器）：集群中唯一的"管家"Broker，负责分区 Leader 选举、分区分配、Broker 上下线处理。
  • Controller 选举：依赖 ZK（早期）—— 多个 Broker 抢建 /controller 临时节点，抢到的就是 Controller；失败者监听该节点，Controller 挂了自动再抢。KRaft 时代用 Raft 协议在控制器节点间选举。
  • 分区 Leader 选举：分区 Leader 挂了，Controller 从 ISR 中选一个新 Leader（优先选副本在位的）；unclean 选举允许从 OSR 选（会丢数据，默认关闭）。

口诀： Controller 是管家，分区挂了从 ISR 里挑新 Leader，unclean 是保命不是保数据。

加分点： 元数据缓存：Controller 维护所有分区/副本状态，变更通过 RPC 通知各 Broker 更新元数据；Controller 是单点，但切换是秒级。

追问： unclean.leader.election.enable 开不开？—— 默认 false（宁可分区不可用也不丢数据）；开 true 保可用性但可能丢消息，二选一。

5.4 丢数据场景大盘点？【必背】

答案骨架： 从生产到消费四个环节：

  1. 生产端：acks=0/1（没等 ISR 全落）、生产者异常未重试 → 丢。
  2. Broker 端：Leader 挂了、Follower 未同步完成就接盘（ISR 无/未同步）、unclean 选举 → 丢。
  3. 存储端：Page Cache 未刷盘断电 → 丢。
  4. 消费端：先提交 offset 后处理（自动提交/同步提交过早）→ 丢。

口诀： 生产不等 ack、Broker 抢脏 Leader、缓存没落盘、消费先提交 —— 四处漏水的四个窟窿。

加分点： 生产级防丢清单：acks=all + min.insync.replicas=2 + retries（大）+ unclean.leader.election.enable=false + 消费先处理再提交 + 合理刷盘/副本数（3）。

追问： 副本数 3 就万无一失吗？—— 不是：如果 ISR 只剩 Leader（两个 Follower 都掉队），此时 Leader 挂 → 无同步副本可选 → 要么不可用、要么 unclean 丢数据。所以要监控 ISR 收缩。

06 高可用与集群管理

6.1 Kafka 集群元数据存什么？高频

答案骨架：（ZK 时代）Kafka 在 ZK 上存储/注册：

  • Broker 注册：/brokers/ids/{id}（临时节点，Broker 下线自动消失）。
  • Topic 元数据：/brokers/topics/{topic}（分区数、副本分配）。
  • Controller 节点：/controller（临时节点，谁建谁当 Controller）。
  • 消费者组 offset（老版本）/ 分区 ISR 变化等。

口诀： ZK 管四样：Broker 名册、Topic 配置、Controller 宝座、老版位移。

加分点： 注意：消息数据本身不存 ZK，ZK 只存元数据；且 0.9+ 消费位移已迁到 Kafka 内部 Topic，ZK 只管协调类元数据。

追问： ZK 挂了 Kafka 还能用吗？—— 能用：元数据已缓存到各 Broker，但无法创建 Topic、无法处理 Broker 上下线、无法选举 Controller，等于集群"瘫痪但还活着"。

6.2 Controller 的角色细讲？进阶

答案骨架：

  • Controller 做的事：
  1. 分区 Leader 选举（分区挂、Broker 挂触发）。
  2. Broker 上下线管理：新 Broker 注册 → 分配分区副本；Broker 下线 → 副本转移、Leader 重选。
  3. 分区重分配（扩缩容/迁移）。
  4. ISR 变更通知、元数据分发（通知所有 Broker 更新缓存）。
  • 实现：Controller 内存维护 元数据缓存（全量 Topic/分区/副本状态），变更时把事件广播（LeaderAndIsr、UpdateMetadata 请求）。

口诀： 选举、上下线、重分配、广播元数据 —— Controller 是集群的神经中枢。

加分点： Controller 挂了的恢复：其他 Broker 监听 /controller，ZK 会话超时后重新竞选；恢复期间集群只读（不能建 Topic、不能迁分区），但存量消费/生产仍可用。

追问： Controller 会不会成为瓶颈？—— 元数据量巨大（几万分区）时，Controller 处理元数据变更和广播会有压力；分区数建议控制在合理范围（经验 < 5 万）。

6.3 分区副本怎么分配与扩容？进阶

答案骨架：

  • 初始分配：分区副本尽量均匀分布到不同 Broker，且每个分区的副本错开 Broker（同机架还要错机架，rack.aware）。
  • 扩容：新增 Broker → 用 kafka-reassign-partitions.sh 迁移分区（把部分分区副本搬过去），期间数据复制、服务不中断。
  • 分区数扩容：kafka-topics.sh --alter --partitions N，但已存在消息的 key 路由会变（hash 基数变了）。

口诀： 新 Broker 搬分区、分区数扩容要谨慎 —— 副本跟机架走，key 路由会翻车。

加分点： 迁移用"增量副本 + 完成即删旧副本"，避免瞬时双写压力；生产推荐"分区数一次性规划够"，别频繁扩。

追问： 扩分区后同一 key 还在同一分区吗？—— 不一定！hash(key) % N 变成 % M（M>N），历史数据重路由 → 需要顺序性的 topic 扩容会破坏顺序。

6.4 Kafka 高可用部署架构？高频

答案骨架：

class="num">3+ Broker（副本 factor=class="num">3，副本错机架）
↕ 元数据协调
class="num">3+ ZK 节点（ZK 时代）或 class="num">3 控制器（KRaft）
  • 副本 factor=3：单 Broker 挂不丢数据、ISR 仍 ≥2。
  • ZK 集群：奇数节点（3/5），过半可用；ZK 不存数据只存元数据。
  • 监控：ISR 收缩、UnderReplicatedPartitions、Controller 切换、消费组 lag 是四大黄金指标。

口诀： Broker 三副本错机架，ZK 奇数过半 —— 挂了也能转。

加分点： 生产者侧 acks=all、消费端 read_committed 按需；客户端配 bootstrap.servers 多地址（只用于发现，任意一个能连即可）。

追问： ZK 集群本身怎么不挂？—— 奇数节点 + 独立磁盘 + 监控告警；ZK 会话超时（session.timeout.ms）设置过短会导致 Broker 被误判下线，引发大面积 rebalance。

07 性能优化与排障

7.1 生产端调优参数清单？【必背】

答案骨架：

  1. acks=all + min.insync.replicas=2（可靠）。
  2. batch.size=32K~64K + linger.ms=10~100（攒批，提吞吐）。
  3. compression.type=lz4/zstd（压缩省带宽，CPU 换带宽）。
  4. buffer.memory=64MB、max.block.ms（缓冲不足不阻塞主线程）。
  5. max.in.flight.requests.per.connection=5 + enable.idempotence=true（高吞吐还保序）。
  6. retries 大 + delivery.timeout.ms（重试窗口）。

口诀： acks 保命、batch+linger 攒批、压缩省带宽、幂等保序 —— 六件套。

加分点： 调优依据：先看瓶颈 —— 带宽受限就加压缩，CPU 受限就减压缩，延迟敏感就小 batch + linger=0。

追问： 压缩在哪个环节发生？—— 生产者压缩（攒批后），Broker 存压缩态，消费者拉取后解压 —— 端到端压缩，磁盘/网络都省。

7.2 消费端调优参数清单？【必背】

答案骨架：

  1. fetch.min.bytes（默认 1，攒够才返回）+ fetch.max.wait.ms（最多等多久）→ 减少空轮询。
  2. max.poll.records=500 → 控制单次处理量，防"处理超时被踢"。
  3. max.poll.interval.ms=5min → 处理慢的业务调大。
  4. enable.auto.commit=false + 手动提交 → 精确控制位移。
  5. isolation.level=read_committed → 事务消息只读已提交。
  6. 并发：分区数 = 消费者数（并行度上限），处理用线程池 + 按 key 哈希到线程保序。

口诀： 攒批拉取、限量处理、手动提交、并发对齐分区数。

加分点： 高性能消费架构：单消费者 + 多线程 + 内部队列按 key 分桶 —— 既保持单分区有序，又突破"单消费者单线程"的瓶颈。

追问： 消费者数 > 分区数会怎样？—— 多余消费者闲置（join 但没分区），白占资源；所以扩容消费者要先扩分区。

7.3 消息积压（lag）怎么办？【必背】

答案骨架：

  1. 先诊断：kafka-consumer-groups.sh --describe 看各分区 lag；定位是生产暴增还是消费变慢（消费耗时、日志、GC、DB 慢查询）。
  2. 应急扩容：增加消费者数量 —— 但并行度受分区数限制，分区数不够先扩分区（注意 key 路由影响）。
  3. 加速消费：批量处理（攒批写 DB）、异步化（先入本地缓冲/下一级 MQ）、去重降计算。
  4. 如果积压到快过期：临时加 Topic + 增加消费者机器，或换更大的消费组分流。
  5. 根治：定位生产端瓶颈 / 消费端慢查询、死锁、外呼慢。

口诀： 先看 lag 哪来的，扩容消费者、加分区、批量加速 —— 治标再治本。

加分点： 注意消费积压 ≠ 系统挂了：Kafka 消息不丢（保留期内），滞后消费是可恢复的；关键是不让 lag 超过 retention 导致消息被删。

追问： 消费者处理不过来，能多开几个消费者进程吗？—— 能，但同一组内多进程分到的还是那些分区；换组则各消费各的（相当于复制一份全量数据，慎用）。

7.4 常见故障排查清单？高频

答案骨架：

症状排查方向
消费 lag 暴涨消费端慢、rebalance 频繁、分区热点
rebalance 风暴心跳超时、session.timeout.ms 过短、处理超 max.poll.interval.ms、GC 停顿

口诀： 积压看消费、风暴看心跳、发送看缓冲、漂移看元数据、磁盘看保留、副本看同步。

加分点： 万能第一步：kafka-topics.sh --describe（分区/ISR/Leader）+ 消费组 describe（lag）+ Broker 日志，三查定位。

追问： rebalance 风暴怎么根治？—— ① 调大 session.timeout.ms / heartbeat.interval.ms；② 处理逻辑提速，别超 max.poll.interval.ms；③ 静态成员（group.instance.id）；④ 关掉不必要的心跳风暴源（GC 长停顿、网络抖动）。

7.5 延迟与吞吐指标速记？进阶

答案骨架：

  • 吞吐：TPS（每秒消息数）/ MBps；关键参数 batch、linger、压缩、并发。
  • 延迟：end-to-end latency（生产到消费可见）；producer latency（发出到 ack）；fetch latency。
  • 关系：高吞吐与低延迟互相矛盾 —— 攒批越大延迟越高；链路延迟 = 网络 RTT + 攒批等待 + 消费 poll 间隔。
  • 常用工具：JMX 指标（kafka.server:type=BrokerTopicMetrics）、kafka-run-class kafka.tools.GetOffsetShell、Prometheus + Grafana。

口诀： 吞吐靠攒批，延迟怕攒批 —— 先定业务目标再调。

加分点： 长轮询（fetch）默认等待 fetch.max.wait.ms；生产加 linger.ms=0 可降延迟；消费 poll 间隔 = max.poll.interval.ms 内的一次循环，积压时延迟自然升高。

追问： 怎么测 Kafka 极限吞吐？—— 用 kafka-producer-perf-test.sh 压生产、kafka-consumer-perf-test.sh 压消费；观察是否是磁盘/网卡/GC 瓶颈。

08 高频场景题

8.1 消息丢失，完整排查链路？【必背】

答案骨架： 四段式排查（见 5.4）：

  1. 生产端：确认 acks 是否 0/1、是否重试尽、发送是否抛异常未处理。
  2. Broker 端：确认 min.insync.replicas、unclean 是否开、ISR 是否收缩、副本数。
  3. 消费端：确认 offset 提交时机（是否先提交后处理）。
  4. 链路：看监控（Producer error rate、UnderReplicatedPartitions、lag 变化）倒推。

口诀： 生产问 acks、Broker 问 ISR、消费问提交、全程看监控。

加分点： 面试答法：先定性"哪一段可能丢"，再逐个给证据（配置、日志、指标），最后给修复方案（acks=all、先处理再提交、副本 3、监控 ISR）。

追问： 如果已经发生了，怎么恢复？—— 生产侧：从源头重发（保留原始数据）；消费侧：offset 回退到丢失点重放（kafka-consumer-groups.sh --reset-offsets）；Broker 已删的消息无法找回，只能靠备份。

8.2 消息重复消费怎么解决？【必背】

答案骨架：

  • 重复的根源：Kafka 是至少一次 —— 重试、rebalance、offset 提交失败都会导致重复。
  • 解决三板斧（幂等消费）：
  1. 唯一键去重：消息带业务唯一 ID（订单号），消费端查 Redis SETNX / DB 唯一索引 / 幂等表。
  2. 状态机幂等：处理逻辑本身幂等（如"更新账户余额为 X"而非"余额+X"）。
  3. 事务兜底：消费 + 写库放同一事务（DB 唯一约束冲突回滚）。

口诀： 重复不可怕，幂等来消化 —— 唯一键去重、接口幂等、事务兜底。

加分点： 最常用："消息 ID + Redis SETNX"（value 为消费结果，TTL 覆盖业务时间窗），或 DB 建唯一索引（消息 id 作为唯一键），简单可靠。

追问： 重复窗口有多长？—— 可能跨越很久（offset 回退重放），所以幂等键不要设太短 TTL；极端场景（删库重放）要靠 DB 唯一索引永久兜底。

8.3 怎么保证消息顺序消费？【必背】

答案骨架：

  • 生产端：同一业务 key → 同一分区（key.hashCode() % partitions）。
  • Broker 端：分区内天然有序（append-only）。
  • 消费端：单分区内单线程消费（一个分区不会被组内两个消费者同时消费；但一个消费者可多线程，需要按 key 哈希路由到固定线程）。
  • 极端可靠：max.in.flight=1 + 幂等（防止重试乱序）。

口诀： key 进同分区、分区内单线程、重试不乱序 —— 三关守序。

加分点： 面试追问点：顺序与吞吐的平衡 —— 可以"每个分区一个线程"或"按 key 哈希分到 N 个桶线程"，桶内有序、桶间并行。

追问： rebalance 会乱序吗？—— rebalance 后分区换消费者处理，新消费者从提交的 offset 继续，若旧消费者还有消息处理中未提交，可能乱序/重复 → 用 8.2 的幂等兜底。

8.4 大消息（>10MB）怎么处理？进阶

答案骨架：

  1. 不推荐直接塞：Kafka 单条默认 message.max.bytes=1MB，大消息占内存、拖慢 GC、消费网络慢。
  2. 方案一：消息传引用 —— 大文件/大对象存 OSS/MinIO/DB，Kafka 只传 URL + 元数据（最常用）。
  3. 方案二：拆分成多条（块）+ 消费端组装。
  4. 方案三：调大 message.max.bytes / max.request.size / fetch.message.max.bytes（万不得已，影响性能）。

口诀： 大对象进对象存储，Kafka 只跑元数据 —— 引用式消息。

加分点： 面试亮点：大消息对页缓存杀伤力大（挤掉热数据），还会让零拷贝失效；正确做法永远是"消息瘦身"。

追问： 必须传大 JSON 呢？—— 压缩（snappy/zstd）后再放，或拆成多条 + 顺序号 + 消费端 join。

8.5 百万/千万级消息积压怎么抢救？【必背】

答案骨架：

  1. 扩容消费者（先扩到分区数上限）。
  2. 扩分区（并行度不够时；注意 key 路由变化）。
  3. 消费加速：批量写库、异步落库、下游削峰（加中间层）。
  4. 如果只是临时大流量：允许 lag 存在（保留期内可追），监控不要误判为故障。
  5. 极端情况：临时"重放方案" —— 另开消费者把积压消息转存到更大的集群/其他 MQ 慢慢处理。

口诀： 先加消费者、再加分区、批量加速 —— 让 lag 先停涨，再慢慢消化。

加分点： 面试常考"消费能力跟不上"：瓶颈往往在下游 DB/外呼而不是 Kafka 本身；真正的解法是异步化 + 削峰填谷（MQ 的本质用途）。

追问： 积压期间消息会丢吗？—— 不会（保留期内）；但超时 retention 的消息会被清掉，所以优先处理接近过期窗口的数据，或临时调大 retention。

8.6 快问快答 15 连高频

Q1. Kafka 吞吐为什么高？ 顺序写 + 页缓存 + 零拷贝 + 批量压缩 + 稀疏索引。

Q2. 分区和消费者的关系？ 一分区一消费者互斥，并行度 = 分区数。

Q3. 消息会丢失吗？ 默认至少一次；acks=all+ISR 缩小丢窗口；unclean 会丢。

Q4. 重复消费怎么办？ 幂等（唯一键去重）。

Q5. 顺序消费怎么保证？ 同 key 同分区 + 单线程消费。

Q6. acks=0/1/all？ 不等/Leader/ISR 全确认。

Q7. HW 和 LEO？ LEO 队尾，HW 是 ISR 最矮，消费者只看 <HW。

Q8. ISR 是什么？ 与 Leader 保持同步的副本集合。

Q9. offset 存哪？ 内部 Topic __consumer_offsets（老版 ZK）。

Q10. 幂等原理？ PID + seq，Broker 查重。

Q11. 事务谁协调？ Transaction Coordinator + __transaction_state。

Q12. 消费组重平衡触发？ 增删消费者、分区数变化、心跳超时。

Q13. 消息积压怎么办？ 扩消费者/分区 + 批量 + 异步。

Q14. Controller 干什么？ 选举、上下线、重分配、广播元数据。

Q15. 为什么移除 ZK？ ZK 是性能/运维瓶颈，KRaft 自管元数据。

8.7 送命题：Kafka 和 Flink 怎么配合？进阶

答案骨架：

  • Flink 作为消费者：从 Kafka 拉流式计算（窗口、聚合、状态），结果写回 Kafka/DB/下游。
  • 精确一次：Flink checkpoint 把 Kafka offset 存进 state，恢复时从 checkpoint 的 offset 续消费 → 端到端 exactly-once。
  • Kafka 当缓冲层：削峰 + 解耦 + 可重放（Flink 出错了能回放修复）。

口诀： Kafka 当蓄水池，Flink 当水厂，checkpoint 记水位 —— 可回溯可恢复。

加分点： 面试：Kafka + Flink 是流处理黄金组合，难点是"端到端精确一次" = 源端（offset 进 state）+ 计算（checkpoint）+ 汇端（两阶段提交/幂等写）。

09 ZooKeeper 核心概念

9.1 ZooKeeper 是什么？数据模型？【必背】

答案骨架：

  • ZooKeeper 是 Apache 的分布式协调服务（源自 Hadoop 生态），为分布式系统提供一致性协调：配置管理、命名、锁、Leader 选举。
  • 数据模型：树形 ZNode 结构（类似文件系统），每个节点存数据（<1MB）+ 元数据（版本号、ACL、时间戳）。
  • 核心承诺：强一致（ZAB 协议）、顺序性、原子性 —— 写操作全走 Leader，过半写入才算成功。

口诀： ZK = 分布式系统的"注册中心 + 文件系统"，树形节点，强一致。

加分点： 经典组合：ZK 是 Kafka、HBase、Dubbo、Hadoop HA 的底层协调者 —— 它们都用 ZK 解决"谁当主、谁在哪、配置是什么"。

追问： 为什么 ZK 不适合存大数据？—— 节点默认 1MB 限制、全量加载内存、写是串行的；它是"协调状态机"，不是数据库。

9.2 ZNode 四种类型？【必背】

答案骨架：

类型特点场景
持久节点（PERSISTENT）手动删除才消失配置、元数据
持久顺序节点名字带递增序号，持久公平锁排队
临时节点（EPHEMERAL）会话结束自动删除Broker/服务注册（挂了自动摘除）
临时顺序节点临时 + 序号分布式锁、Leader 选举

口诀： 持久靠手动删，临时跟会话走，顺序自带编号 —— 四种节点组合出所有玩法。

加分点： 临时节点是 ZK 做"心跳探活"的关键：客户端会话（session）通过心跳维护，断连超过 session.timeout 节点即被删 → 服务故障自动摘除。

追问： 临时节点能带子节点吗？—— 可以带，但临时节点下不能建持久子节点（临时节点的生命周期随会话，子节点会失联）。

9.3 Watch 机制原理？【必背】

答案骨架：

  • Watch（监听）：客户端注册一次在节点上的监听（读操作可附带 watch）。
  • 触发：节点数据变化（set）、节点删除、子节点变化时，ZK 通知客户端（异步回调）。
  • 一次性：watch 触发一次后失效，要持续监听需重新注册（"watch 是一次性的"）。
  • 保证：客户端能先收到通知再读到新数据（通知语义），但通知可能延迟，需配合重查。

口诀： 注册一次、变化通知、通知完失效 —— 要监听就得重新绑。

加分点： 面试亮点：watch 是 Push 通知，比轮询高效；但不能依赖 watch 拿数据，它只是"变化提示"，事件驱动的标准写法是"收到通知 → 重新 getData 带 watch"。

追问： 羊群效应（惊群）和 watch 的关系？—— 大量客户端 watch 同一节点，节点一变全部被唤醒（如抢锁失败者都监听同一把锁）→ 用顺序节点 + 只监听前一个节点规避（见 11.3）。

9.4 ZK 典型应用场景？高频

答案骨架：

  1. 命名服务：节点路径当唯一 ID（/services/user-service/node1）。
  2. 配置管理：配置放节点，客户端 watch 变更即时感知（老牌方案，现在多用 Apollo/Nacos）。
  3. 分布式锁：临时顺序节点实现公平锁（见 11 章）。
  4. Leader 选举：多个候选抢建临时节点，建成功的当 Leader；Leader 挂了节点消失，触发再选（Kafka Controller、HBase HMaster）。
  5. 注册中心：服务上线注册、下线自动摘除（Dubbo 早期方案）。
  6. 集群元数据/协调：Kafka、Hadoop HA 都靠它。

口诀： 命名、配置、锁、选举、注册 —— ZK 五虎将。

加分点： 面试对比：Nacos 是"ZK + 配置中心"的升级版（AP 模式、自带控制台）；ZK 定位是通用协调原语，写强一致、读可扩展性弱。

追问： 注册中心选 ZK 还是 Nacos？—— 高可用优先（可用性 > 一致性，容忍短暂不一致）选 Nacos（AP）；强一致元数据场景选 ZK（CP）。

10 ZK 一致性原理

10.1 ZAB 协议两阶段？【必背】

答案骨架：

  • ZAB（ZooKeeper Atomic Broadcast） = 崩溃恢复 + 消息广播两个阶段。
  1. 崩溃恢复（选举）：Leader 挂了，集群进入选举，选出新 Leader，新 Leader 同步日志（把未提交的提案补齐/丢弃），收敛到一致状态。
  2. 消息广播（主从复制）：Leader 写请求 → 生成提案（Proposal，带 ZXID） → 广播给 Follower → 过半 ack → Leader 提交并通知 Follower 提交。
  • 保证：已提交的提案不丢、未提交的不能出现在新 Leader 上（ZAB 的核心正确性）。

口诀： 先选主补齐账，再广播过半提交 —— ZAB 两阶段。

加分点： 与 Raft 对比：ZAB 强调恢复后不能出现"已提交被丢弃"（丢弃旧 Leader 未提交日志要交给新 Leader 决定）；Raft 是"任期 + 日志匹配"。

追问： 过半提交为什么能保证强一致？—— 两个过半集合必有交集（quorum 数学性质），所以任何已提交的提案一定被"存活多数"记住，新 Leader 从多数派恢复日志必含已提交项。

10.2 Leader 选举流程与 ZXID？【必背】

答案骨架：

  • ZXID（事务 ID）：64 位 = 纪元（epoch，高 32 位）+ 事务计数（低 32 位）；每次 Leader 换届 epoch+1，提案计数从 0 重来。
  • Fast Leader Election 流程：
  1. 每个 Follower 投自己（(epoch, zxid, myid)）。
  2. 收到投票，比较 (epoch, zxid)，大的赢，改投对方并广播。
  3. 某节点收到过半同意的投票 → 当选 Leader。
  4. 新 Leader 向其他节点发"成为 Leader"消息，旧 Leader 退位，Follower 同步日志。
  • 优先级：epoch 高 > zxid 高（数据新）> myid 大。

口诀： 先比纪元、再比日志新、最后比 id —— 数据新者当老大。

加分点： 选 Leader 的核心逻辑：谁的数据最新谁当主（zxid 最大），避免新 Leader 还得倒数据；选举期间集群不可写（只读旧数据），是 ZK 的"短暂不可用窗口"。

追问： 选举会永远选不出来吗？—— 不会：超过半数节点在线就一定能选出（quorum 定理）；少于半数在线 → 集群整体不可用（ZAB 的牺牲可用性保一致性）。

10.3 脑裂与过半机制？【必背】

答案骨架：

  • 脑裂：网络分区把集群分成两半，两边各自选 Leader → 数据分裂。
  • 解决：过半（quorum）机制 —— 只有拿到 N/2+1 票的 Leader 才有效；分区后只能有一半有资格（多数派），少数派再选也凑不齐票，自动作废。
  • 例：5 节点集群，分区成 3+2 → 3 的一方选 Leader 成功，2 的一方永远选不出来 → 没有双主。

口诀： 过半才称王，分裂必一边 —— 少数派翻不了天。

加分点： 这是"CP 系统"（如 ZK）的经典取舍：宁可牺牲可用性，也不允许双主写脏数据；对比 Redis 主从（AP 系）需要额外哨兵/仲裁处理脑裂。

追问： 机器数必须奇数吗？—— 建议奇数：5 台能扛 2 台故障，6 台也只扛 2 台（多数 = 4），奇数用更少的机器获得同样的容错。

10.4 ZK 读性能和顺序性细节？进阶

答案骨架：

  • 读请求：任意节点（Leader/Follower）都能直接返回本地数据（主从分离读）→ 读性能可扩展。
  • 写请求：全部转发 Leader，串行处理（单线程事务队列）→ 写性能有上限（几千~上万 TPS）。
  • 顺序性保证：① 全局有序（同一 Leader 串行提案）；② 因果有序（客户端会话内先发先生效）；③ 读可能读到旧数据（Follower 读未同步）→ 强一致性读要走 sync() 或读 Leader。
  • ZXID 保证 watch 通知顺序与事务提交顺序一致。

口诀： 读扩散、写串行 —— 读可能旧，写一定新。

加分点： 面试亮点：ZK 是"读写不对称"系统：读强一致只是"最终一致 + 顺序一致"（Follower 可能滞后），要线性一致性读需加 sync。这也是"ZK 不适合当缓存"的原因之一。

追问： ZK 能当缓存用吗？—— 不合适：读是"过半无写冲突"的本地读还行，但节点容量小、内存型、写串行，缓存该用 Redis。

11 ZK 分布式锁与实战

11.1 分布式锁三方案对比？【必背】

答案骨架：

方案原理优点缺点
Redis SETNX内存加锁 + 过期快、简单主从切换丢锁（RedLock 复杂）、看门狗
ZK 临时顺序节点最小序号拿锁强一致、天然防死锁（会话断开自动释放）、公平性能低（写串行）、重
DB 唯一索引/悲观锁数据库行锁简单、可靠性能差、单点

口诀： Redis 快但可能抖，ZK 稳但慢，DB 兜底最朴素。

加分点： 面试结论：业务量小/要绝对正确选 ZK（Curator），高并发低延迟选 Redis（可接受极小概率的锁失效）；DB 锁只做兜底。

追问： Redis 锁为什么会失效？—— 主从异步复制：加锁在 Master，Master 挂了 Slave 顶上但锁数据没复制过去 → 新主上没有锁 → 两个客户端同时持锁。ZK 因"过半同步"无此问题。

11.2 ZK 实现分布式锁（临时顺序节点）？【必背】

答案骨架：

  • 加锁：在锁节点下创建临时顺序节点 /locks/lock_0000000010。
  • 判断：序号最小的节点 = 持锁者。
  • 等待：非最小者 watch 前一个节点（只监听比它小的最近一个），前一个删除 → 自己被唤醒 → 再判断是否最小。
  • 释放：删除自己的节点（或会话断开自动删）。
  • 优点：公平（按申请顺序）、无死锁（临时节点随会话消亡）、避免惊群（只 watch 前一个）。

口诀： 排号叫号 —— 建临时顺序节点排队，最小号拿锁，只看前面一个。

加分点： 这是羊群效应的经典解法：如果所有等待者都 watch 锁根节点，锁一释放全被唤醒（羊群效应/惊群）；"watch 前驱"把唤醒面收敛到 O(1)。

追问： 持锁者挂了会怎样？—— 会话超时 → 临时节点被 ZK 自动删除 → 前驱消失 → 后继被唤醒抢锁，不需要超时续租（对比 Redis 要看门狗）。

11.3 羊群效应（惊群）详解？进阶

答案骨架：

  • 羊群效应：很多客户端同时等待同一事件，事件触发时全部被唤醒去竞争，但只有 1 个能赢，其余白忙 + 产生大量请求。
  • ZK 场景：① 大量客户端 watch 同一锁节点 → 锁释放时全员唤醒；② 大量客户端 watch Leader 节点 → Leader 挂全员抢选举。
  • 解法：只监听自己关心的最小对象 —— 锁场景"只 watch 前驱节点"、选举场景"只 watch 比自己小的节点"，把 O(n) 唤醒降为 O(1)。

口诀： 惊群 = 一石惊起千鸟飞；对症下药 = 只盯眼前那一个。

加分点： Curator 的 InterProcessMutex 就是"临时顺序节点 + watch 前驱"实现；面试说出"避免羊群效应"就是加分项。

追问： 还有别处见过羊群效应吗？—— 有：缓存失效后多线程同时回源（缓存击穿）、Kafka 多消费者抢分区、Redis 分布式锁释放后多客户端自旋 —— 解法思路一致：收窄竞争面 + 退避。

11.4 Curator 框架速记？【中频】

答案骨架：

  • Curator = ZK 客户端封装（Netflix 开源），比原生 API 好用太多。
  • 常用 API：
  • CuratorFramework 连接管理（重试策略 RetryNTimes/ExponentialBackoffRetry）。
  • InterProcessMutex（排他锁）/ InterProcessReadWriteLock（读写锁）。
  • LeaderLatch / LeaderSelector（Leader 选举）。
  • PathChildrenCache（子节点监听，替代手写 watch）。
  • 使用注意：必须自己维护会话与重试，超时时间、连接串配置好。

口诀： Curator 是瑞士军刀 —— 锁、选举、缓存监听一套齐。

加分点： 面试答"用过 ZK 吗"→ 用 Curator 实现过分布式锁/注册中心，是常见项目题；记得提"ZK 强一致所以锁可靠，但吞吐受限"。

12 Kafka 与 ZK 的关系及演进

12.1 Kafka 到底用 ZK 干什么？【必背】

答案骨架：（2.8 之前）

  1. Broker 注册/发现：Broker 启动注册 /brokers/ids/{id}，下线自动消失。
  2. Topic 元数据：分区数、副本分配方案存 /brokers/topics/{topic}。
  3. Controller 选举：/controller 临时节点，谁建谁当 Controller。
  4. 消费者组/offset（0.9 之前）：旧版消费位移也存 ZK（后迁到 Kafka 内部 Topic）。
  5. ISR 变化通知（老版本）：Broker 上报 ISR 变更，Controller 通过 ZK watch 感知。

口诀： 注册、元数据、Controller、老位移 —— ZK 是 Kafka 的"总台账"。

加分点： 面试重点：消息数据不进 ZK，ZK 只存元数据；且 Kafka 对 ZK 是重度依赖 —— ZK 挂 → 元数据无法变更，集群"只能消费存量"。

追问： 为什么后来的 Kafka 要摆脱 ZK？—— 见 12.2：ZK 成为性能/运维瓶颈，且 Kafka 社区想要"一组件架构"。

12.2 为什么 Kafka 要移除 ZK（KRaft）？【必背】

答案骨架：

  1. 运维复杂度：多一套 ZK 集群要部署、监控、调优，故障面翻倍。
  2. 元数据扩容瓶颈：分区数巨大时（几万分区）ZK 的元数据读写、watch 压力大，成为上限。
  3. 故障恢复慢：ZK 会话超时触发 Controller 切换、大面积 rebalance 风暴。
  4. 架构简洁：Kafka 自己用 Raft 协议管元数据（KRaft，KIP-500），Broker 同时当"控制器节点"。
  5. 可演进：支持元数据自己管理后，Kafka 能独立演进（如更细粒度权限、topic 级故障域）。

口诀： 少一套 ZK、快一点恢复、扛更大集群 —— 自己当家做主（KRaft）。

加分点： KRaft：Quorum Controller（奇数个） 用 Raft 管理元数据，元数据日志存自己的磁盘；3.0+ 支持、4.0 起 ZK 模式移除。

追问： KRaft 和 ZK 模式有啥区别？—— 部署从"Kafka + ZK"变"纯 Kafka"；Controller 从"ZK 抢临时节点"变"Raft 选主"；其余 Producer/Consumer 协议完全不变，迁移透明。

12.3 ZK 模式 → KRaft 迁移注意？进阶

答案骨架：

  1. 工具：kafka-storage.sh random-uuid（生成 cluster id）→ kafka-storage.sh format（格式化元数据目录）→ 配 process.roles=broker,controller。
  2. 兼容：2.8~3.x 支持混合模式（ZK 与 KRaft 共存迁移）。
  3. 迁移影响：滚动重启，老 Broker 用 ZK、新节点用 KRaft，逐步切换。
  4. 生产建议：新集群直接上 KRaft（3.x 稳定版），老集群规划低峰迁移。

口诀： 新装用 KRaft，老集群滚动切，broker 和 controller 一肩挑。

加分点： 面试如果聊到"最新的 Kafka 架构"，提 KRaft 就是加分项；能说出"4.0 彻底移除 ZK"更好。

追问： KRaft 还是单 Controller 吗？—— 不是：奇数个控制器节点组成 quorum（如 3），Raft 选主，Leader 挂自动切换，天生高可用。

12.4 Kafka + ZK 经典面试连环问？高频

Q1. ZK 挂了 Kafka 会怎样？ 元数据不能变更（建 Topic/上下线/选举停摆），存量消费生产继续。

Q2. Controller 挂了谁顶？ 其他 Broker 重新竞选（ZK 模式抢 /controller，KRaft Raft 选主）。

Q3. 为什么 Kafka 不用 Redis 做协调？ 需要强一致 + 持久化 + 有序，ZK/ZAB/Raft 是专门设计。

Q4. ZK 节点是 CP 还是 AP？ CP（强一致，牺牲可用性）。

Q5. 消费 offset 现在存哪？ Kafka 内部 Topic __consumer_offsets（早先存 ZK）。

13 综合快问快答与送命题

13.1 综合快问快答 20 连高频

Kafka 篇：

Q1. 一个分区最多被几个消费者消费？ 同一消费组内 1 个。

Q2. Topic 分区数怎么定？ 吞吐目标 + 消费者并行度 + 扩容成本，别贪多。

Q3. 消息格式是什么？ 二进制的 RecordBatch（带 CRC、压缩、时间戳、key/value）。

Q4. 消费者组 offset 提交失败会怎样？ 重复消费（至少一次）。

Q5. __consumer_offsets 怎么分区？ 按 groupId 哈希到 50 个分区。

Q6. Kafka 能当缓存吗？ 不适合：无随机读、无 TTL 语义，是日志不是 KV。

Q7. 为什么拉模式而不是推模式？ 消费者控速、批量、服务端无状态。

Q8. 分区数和副本数啥区别？ 分区是并行度，副本是冗余度。

Q9. Leader 读写，Follower 干嘛？ 备份 + 随时顶班。

Q10. 消息时间戳存哪？ 每条消息带 timestamp，配 timeindex 按时间查。

ZK 篇：

Q11. ZK 节点数据大小限制？ 默认 1MB。

Q12. ZK 是 AP 还是 CP？ CP（过半机制，可用性让位一致性）。

Q13. 临时节点什么时候删？ 会话超时/关闭。

Q14. Watch 是一次性的吗？ 是，触发即失效。

Q15. 选举怎么保证数据最新者当选？ ZXID（epoch + 计数）最大者。

Q16. 脑裂怎么防？ 过半 quorum，少数派选不出主。

Q17. ZK 为什么不适合高并发写？ 写全走 Leader 串行。

Q18. 分布式锁公平吗？ 临时顺序节点版是公平锁。

Q19. Curator 是什么？ ZK 的高层封装客户端。

Q20. ZK 写请求必须走 Leader？ 是，Follower 收到会转发给 Leader。

13.2 送命题：设计一个消息中间件，怎么答？进阶

答案骨架： 从 Kafka 抄作业：

  1. 存储：append-only 日志 + 分段（Segment）+ 稀疏索引 + 顺序写磁盘。
  2. 高吞吐：批量（攒批）+ 压缩 + 零拷贝（sendfile/mmap）+ 页缓存。
  3. 分布式：Topic 分区 + 副本（ISR 思想：维护同步副本集合）+ 控制器选举。
  4. 消费模型：拉模式 + 消费组 + offset 管理（内部 Topic 存位移）。
  5. 可靠性：acks 分级 + 幂等（序号去重）+ 事务（协调器 + 提交标记）。
  6. 一致性：元数据用 Raft（KRaft 思路）或 ZK。

口诀： 日志存储 + 批量压缩 + 分区副本 + 拉消费 + 幂等事务 —— 一套 Kafka 从零到一。

加分点： 面试官要听的不是"背 Kafka 参数"，而是设计取舍：为什么顺序写快、为什么 ISR 不全部同步、为什么拉不推 —— 答出权衡就是高分。

追问： 如果要你优化 Kafka，改哪里？—— ① 元数据与数据面分离（已做 KRaft）；② 分区数膨胀问题（共享日志/Tiered Storage 分层存储）；③ 大消息处理（对象存储引用）；④ 跨集群事务（可参考各开源方案）。

13.3 面试高频坑与避坑指南【必背】

答案骨架：

  1. "Kafka 消息不会丢" ❌ —— 默认至少一次，不同配置下会丢，要说清楚条件。
  2. "ISR 就是所有副本" ❌ —— ISR 是"同步中"的副本（AR 才是全部）。
  3. "顺序保证 = 全局有序" ❌ —— 只有分区内有序。
  4. "offset 存 ZK" ❌ —— 0.9+ 存 __consumer_offsets（ZK 时代已过去）。
  5. "ZK 存了 Kafka 的消息" ❌ —— ZK 只存元数据。
  6. "幂等 = exactly-once" ❌ —— 幂等只管单分区单会话；exactly-once 要事务 + 幂等消费。
  7. "ZAB 就是 Raft" ❌ —— 类似但不同：ZAB 有"恢复后不丢已提交"的强保证细节。
  8. "ZK 读也强一致" ❌ —— 读可走 Follower（可能旧），要线性读需 sync。

口诀： 丢不丢看配置、序不序看分区、offset 在 Kafka 不在 ZK、幂等不是万能的 —— 八个坑，背完不踩。

加分点： 面试说"至少一次 + 幂等消费 = 业务级不重不丢"是被普遍认可的落地方案；能主动指出坑说明你真懂。
