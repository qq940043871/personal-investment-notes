3 🔥 追问链 01｜一条 SQL 的执行链路

L0 · 主问题：一条 SELECT 语句的完整执行流程？

答：客户端 → 连接器 → 分析器 → 优化器 → 执行器 → 存储引擎。连接器做 TCP 握手、鉴权、权限缓存；分析器做词法/语法分析生成语法树；优化器决定执行计划（选哪个索引、连接顺序）；执行器调用存储引擎接口取数；存储引擎真正读写数据。

L1 · 追问：8.0 为什么把查询缓存移除了？

答：查询缓存以 SQL 文本为 key 缓存结果集，只要表有任何更新，该表所有缓存整体失效；高并发下命中率低，且缓存维护、失效加锁反而成为瓶颈。缓存应由应用层（Redis）按业务语义来做，而不是数据库按 SQL 文本做。

L2 · 追问：优化器怎么决定走哪个索引？

答：基于代价模型（Cost Model），不是规则：根据统计信息（innodb_stats_*、表行数、索引区分度/基数 cardinality）估算不同执行计划的 CPU + IO 代价，选代价最小的。这也是为什么 rows 是估算值、统计信息失真会导致"明明有索引却走全表扫描"。

L3 · 追问：执行器和存储引擎是怎么交互的？

答：通过统一的 handler 抽象接口。Server 层不直接碰数据文件，只调用 handler 的 open/read_first/read_next/index_read 等方法，具体读写由各引擎实现。这就是"插件式存储引擎"能换引擎的原因。

L4 · 追问：权限到底在哪里检查？为什么不是连接器一次查完？

答：连接器阶段先读一次权限并缓存到连接会话；执行器在打开表时再校验一次（在优化器之后）。注意顺序：优化器不检查权限，执行器才检查。若连接建立后权限被修改，需重连或用 FLUSH PRIVILEGES 才生效。

L5 · 追问：如果这是一条 UPDATE，流程会多出什么？

答：多出日志与两阶段提交：定位行加锁（当前读）→ 改内存页 → 写 undo（用于回滚/MVCC）→ 写 redo(PREPARE) → 写 binlog → redo(COMMIT) → 返回，脏页延迟刷盘。核心是 redo 与 binlog 用两阶段提交保证崩溃恢复时二者一致。详见追问链 08。

4 🔥 追问链 02｜为什么是 B+ 树

L0 · 主问题：MySQL 为什么用 B+ 树做索引？

答：索引要同时支持等值、范围、排序查询，且要减少磁盘 IO。B+ 树非叶子只存键+指针、叶子存数据并双向链表相连，扇出大、树矮、范围查询快、查询路径等长，完美契合磁盘场景。

L1 · 追问：哈希表、红黑树、B 树为什么不行？

答：哈希表等值 O(1) 但不支持范围/排序/前缀匹配；红黑树/AVL 是二叉树，千万级数据 20+ 层 = 20+ 次随机磁盘 IO；B 树非叶子也存数据，扇出小、树更高，范围查询要中序遍历。

L2 · 追问：说"3 层就能存 2000 万"，具体怎么算的？

答：InnoDB 一页 16KB。非叶子节点每项 = 主键 8B + 指针 6B ≈ 14B，一页约装 16KB/14B ≈ 1170 个分叉。叶子节点假设一行 1KB，一页约 16 行。三层 B+ 树：1170 × 1170 × 16 ≈ 2190 万行，即最多 3 次磁盘 IO（根页常驻内存时实际 2 次）。

L3 · 追问：主键为什么推荐自增？不自增会怎样？

答：自增主键是顺序追加写，新记录总是落在最右叶子，几乎不引发页分裂；UUID/随机主键无序，插入时频繁页分裂，产生碎片、随机 IO，且二级索引要冗余存主键，主键越宽，二级索引越占空间。可答：雪花算法/号段生成趋势递增的 bigint 是生产常用折中。

L4 · 追问：页分裂具体发生了什么？

答：当叶子页写满还要插入时，InnoDB 申请一个新页，把原页约一半数据搬过去，再更新父节点指针，插入新值。主键有序时新页追加在尾部，几乎不搬数据；主键随机时插入点落在中间，频繁搬一半数据，产生大量碎片和随机 IO。

L5 · 追问：那为什么不用跳表（Skip List）？Redis 不是用跳表吗？

答：跳表也是 O(log n)，但它是内存数据结构：节点靠多层随机指针串联，指针跳转在内存里很快，但在磁盘上是随机 IO，且跳表节点不按页对齐、扇出小、树高，无法像 B+ 树那样把连续键紧凑塞进一页实现顺序预读。一句话：跳表为内存优化，B+ 树为磁盘优化，介质决定结构。

5 🔥 追问链 03｜聚簇·回表·覆盖索引

L0 · 主问题：聚簇索引、二级索引、回表、覆盖索引分别是什么？

答：聚簇索引（主键）叶子存整行数据；二级索引叶子存"索引列 + 主键值"；用二级索引查到主键后、再回聚簇索引查整行叫回表；查询所需列全部在索引里、不用回表叫覆盖索引。

L1 · 追问：表没有主键怎么办？

答：InnoDB 按优先级选：① 第一个非空唯一索引；② 都没有则生成隐藏的 6 字节 ROW_ID 作聚簇索引。所以最好显式建主键，避免依赖隐藏 row_id（不可控、不能复用）。

L2 · 追问：二级索引为什么存主键值，而不是存行指针（MyISAM 那样）？

答：因为聚簇索引的数据会随主键变更/页分裂而移动。若二级索引存物理地址，数据一移动所有二级索引都要更新；存主键值（逻辑地址），数据移动时二级索引不用动，代价只是多一次回表。这是 InnoDB 与 MyISAM 的核心差异。

L3 · 追问：EXPLAIN 里怎么看出是覆盖索引、还是用了 ICP？

答：Extra 列。Using index = 覆盖索引（不回表，最优）；Using index condition = 索引下推 ICP（引擎层先过滤，减少回表）；Using where = Server 层过滤；Using filesort/Using temporary 是警告信号。

L4 · 追问：回表的代价是什么？MRR 怎么优化？

答：回表是随机 IO——二级索引叶子里的主键是无序的，回聚簇索引读整行时磁盘寻道频繁。MRR（Multi-Range Read） 把二级索引查到的主键先排序，再按主键顺序回表，把随机读变成近似顺序读，减少磁盘寻道。可通过 optimizer_switch 的 mrr=on 控制。

6 🔥 追问链 04｜最左前缀原则

L0 · 主问题：什么是最左前缀原则？

答：联合索引 (a,b,c) 按 (a,b,c) 整体排序，查询必须从最左列开始连续匹配才能走索引。等效于建了 a、(a,b)、(a,b,c) 三个索引。

L1 · 追问：WHERE a=1 AND c=3 会怎样？

答：a 能走索引，c 因为跳过了 b 无法直接定位，只能靠索引下推（ICP）在遍历 a=1 的行时顺带过滤 c=3，比全表回表好，但不如 (a,c) 高效。

L2 · 追问：WHERE a>1 AND b=2，为什么 b 失效？

答：因为索引按 (a,b) 排序，a>1 是范围，范围内 a 各不相同的行，其 b 是无序的，无法用 b 继续二分定位。范围列之后的列都失效——这是最左前缀最常见的坑。

L3 · 追问：为什么不能跳过 a 直接查 b？

答：B+ 树叶子按 (a,b,c) 整体字典序排列：先比 a，a 相同再比 b。若只按 b 查，索引里 b 是全局无序的，无法用 b 定位，只能全索引扫描。这就是"最左前缀"的物理本质。

L4 · 追问：怎么设计才能既查 a 又按 b 排序？

答：把排序列也纳入联合索引。如 WHERE a=? ORDER BY b 需要 (a,b)；WHERE a=? AND b>? ORDER BY c 需要 (a,b,c) 才能排序也不 filesort。核心口诀：等值在前、范围在后、排序列紧随其后，让排序也能"吃"到索引的有序性。

7 🔥 追问链 05｜事务隔离与 MVCC

L0 · 主问题：四个隔离级别分别解决什么问题？

答：RU 什么也不解决（脏读）；RC 解决脏读，但可能不可重复读、幻读；RR（MySQL 默认）解决脏读+不可重复读，基本解决幻读；Serializable 全解决（靠串行化）。

L1 · 追问：MVCC 是怎么实现"不加锁读"的？

答：靠隐藏字段 + undo 版本链 + ReadView。每行有 DB_TRX_ID（最近修改的事务 id）、DB_ROLL_PTR（指向 undo 里的历史版本）；读时沿版本链找到"本事务可见"的版本，通过版本判断而非加锁实现一致性快照。

L2 · 追问：ReadView 的可见性判断规则是什么？

答：ReadView 记录 m_ids（当前活跃事务集合）、min_trx_id、max_trx_id、creator_trx_id。对某版本的事务 id trx_id：

trx_id == creator_trx_id → 自己改的，可见
trx_id < min_trx_id → 已提交，可见
trx_id >= max_trx_id → 视图之后的事务，不可见
trx_id ∈ m_ids → 仍在活跃，不可见
否则 → 已提交，可见
L3 · 追问：RR 和 RC 的 MVCC 差在哪？

答：ReadView 生成时机不同。RC：每次快照读都生成新 ReadView，所以能读到别的事务新提交的数据（不可重复读）；RR：事务内第一次快照读生成 ReadView 并复用，全程同一快照，所以可重复读。

L4 · 追问：MySQL 为什么默认 RR，而不是像 Oracle 用 RC？

答：历史原因——5.7 之前 binlog 默认 STATEMENT 格式，主从复制靠 SQL 回放，若用 RC 会出现"主库事务执行顺序与 binlog 回放结果不一致"的幻读风险；RR + 间隙锁能保证 STATEMENT 复制下主从一致。5.7.7 后 binlog 默认 ROW，才逐渐有公司切 RC 提并发。能答出这条"历史包袱"是明显加分。

L5 · 追问：undo log 会被清理吗？什么时候？

答：会，由后台 purge 线程异步清理。判断依据是：某 undo 版本不再被任何活跃事务的 ReadView 引用时才可回收。长事务会拖着 purge 无法推进，导致 undo 空间暴涨、版本链变长、查询变慢——这就是长事务危害的底层原因。

8 🔥 追问链 06｜幻读与 next-key lock

L0 · 主问题：什么是幻读？和不可重复读有何区别？

答：不可重复读是同一行被改（读到的值变了）；幻读是多出/少了行（同样的范围查询，结果集的行数变了）。幻读本质是插入/删除造成的。

L1 · 追问：RR 是怎么解决幻读的？

答：两条腿。快照读靠 MVCC（读的是事务开始时的快照，别人插入看不到）；当前读靠 next-key lock（记录锁 + 间隙锁），把查询范围锁住，阻止其他事务插入，从根上消除幻读。

L2 · 追问：为什么间隙锁只在 RR 及以上才有？

答：间隙锁锁的是"记录之间的空隙"，代价是降低并发。RC 没有间隙锁（只有记录锁），因为它容忍幻读；RR 为了基本消除幻读才引入。这也是 RC 并发更高、RR 更容易死锁的原因。

L3 · 追问：RR 能 100% 避免幻读吗？边界在哪？

答：不能严格 100%。经典反例：事务 A 先快照读（SELECT * WHERE id>5，MVCC 不加锁），此时事务 B 插入一条 id=10 并提交；A 再当前读（SELECT ... FOR UPDATE 或 UPDATE）时会看到这条新插入的行，产生"幻影"。所以严格说 RR 只是"基本解决"，能主动点出这个边界是加分项。

L4 · 追问：InnoDB 的加锁规则是什么？

答：丁奇总结的四原则 + 两优化：① 加锁基本单位是 next-key lock（前开后闭）；② 访问到的对象才加锁；③ 等值查询向右遍历到第一个不满足等值条件的值，退化为间隙锁；④ 唯一索引等值命中，退化为记录锁。另有已知现象：唯一索引范围查询会锁到第一个不满足条件的值。

9 🔥 追问链 07｜锁分类与死锁

L0 · 主问题：MySQL 有哪些锁？

答：按粒度分全局锁、表级锁、行级锁。表级含 MDL 元数据锁、意向锁；行级含记录锁、间隙锁、临键锁。另外还有自增锁 AUTO-INC。

L1 · 追问：意向锁（IS/IX）是干什么的？

答：解决"表锁与行锁的冲突判断"。事务加行锁前先给表加意向锁；别人要加表锁时，只需看表上有没有意向锁，就知道有没有行锁，而不用逐行扫描。它是表级标记、不阻塞、只用于快速判断兼容性。

L2 · 追问：MDL 锁是什么？为什么大表 DDL 会阻塞 DML？

答：MDL（元数据锁）保护表结构：增删改查自动加 MDL 读锁，DDL 需要 MDL 写锁，读写互斥。一个未提交的长事务持有 MDL 读锁，后面的 ALTER TABLE 拿不到写锁就一直排队，而后续新来的 DML 又排在 DDL 后面——造成"DDL 阻塞 DML、进而雪崩"。这是 Online DDL 与 pt-osc/gh-ost 要解决的问题。

L3 · 追问：死锁怎么检测？怎么处理？

答：InnoDB 维护锁等待图，发现环路即判定死锁，自动回滚事务量最小（undo 最少）的那个，抛 1213 错误，让应用重试。查看 SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 定位是哪两条 SQL 互相持有对方要的锁。

L4 · 追问：工程上怎么避免死锁？

答：① 按固定顺序访问多行/多表（不同事务锁序一致）；② 尽量缩小锁范围（精确索引、少用范围）；③ 控制事务粒度，事务内不穿插远程调用/长查询；④ 高并发热点可降级 RC（无间隙锁）或用锁等待超时 innodb_lock_wait_timeout 兜底；⑤ 应用侧捕获 1213 自动重试。

10 🔥 追问链 08｜redo·binlog·两阶段提交

L0 · 主问题：redo log 和 binlog 有什么区别？

答：redo log 是 InnoDB 层物理日志（记录页的修改），循环写，用于崩溃恢复；binlog 是 Server 层逻辑日志（SQL 或行变更），追加写，用于主从复制和数据恢复。

L1 · 追问：为什么需要两阶段提交？

答：因为 redo 和 binlog 分属两层、独立写入，若一个成功一个失败，就会不一致：redo 成功 binlog 失败 → 主库有数据、从库没有（主从不一致）；binlog 成功 redo 失败 → 从库有、主库没有。两阶段提交让二者"要么都成功、要么都失败"。

L2 · 追问：两阶段提交的具体流程？

答：

class="num">1. 写 redo log，状态 = PREPARE
class="num">2. 写 binlog
class="num">3. 写 redo log，状态 = COMMIT，事务提交成功
L3 · 追问：崩溃后怎么判断该提交还是回滚？

答：扫描 redo 里的 PREPARE 事务，再比对 binlog：

  • redo 是 PREPARE + binlog 不存在 → 回滚（redo 未提交，binlog 也没写，主从都无）
  • redo 是 PREPARE + binlog 存在 → 提交（binlog 已写，从库会执行，主库必须提交保持一致）
  • redo 是 COMMIT → 直接提交
L4 · 追问：组提交（Group Commit）是什么？为什么能提性能？

答：两阶段提交里最贵的操作是 fsync 刷盘（redo 和 binlog 各一次）。组提交把并发事务的 fsync 合并成一次——多个事务的日志一起刷，分摊 fsync 开销，大幅提升写入吞吐。开启 binlog_group_commit_sync_delay 可进一步攒批。

L5 · 追问：要"数据绝对不丢"，三个刷盘参数怎么配？

答：① innodb_flush_log_at_trx_commit=1（每次提交 fsync redo）；② sync_binlog=1（每次提交 fsync binlog）；③ innodb_doublewrite=1（防部分页写）。即"双 1 + 双写"最安全，代价是写入性能下降，通常用组提交 + 批量刷盘平衡。

11 🔥 追问链 09｜主从复制与延迟

L0 · 主问题：主从复制的原理？

答：主库把变更写 binlog → 从库 IO 线程拉取 binlog 到本地 relay log → 从库 SQL 线程回放 relay log 更新数据。8.0 引入 GTID，事务有全局唯一 id，切换从库无需找位点。

L1 · 追问：为什么会有主从延迟？

答：主库并发写（多线程），从库 SQL 线程是单线程串行回放，跟不上主库吞吐；大事务、DDL、从库自身负载也会放大延迟。监控指标 Seconds_Behind_Master。

L2 · 追问：怎么解决主从延迟？

答：并行复制——5.7 按库并行（DATABASE），8.0 用 writeset（WRITESET）按事务冲突关系并行，同库不冲突的事务也能并行回放；配合拆分大事务、一主多从分流、只读从库。

L3 · 追问：GTID 是什么？解决了什么问题？

答：GTID = server_uuid:transaction_id，为每个事务分配全局唯一编号。传统基于位点的复制在切换主从时要手动找 File+Position，容易错位；GTID 让从库能自动跳过已执行的事务、续传未执行的，主从切换和故障恢复更可靠。

L4 · 追问：异步、半同步、MGR 分别什么场景？脑裂怎么办？

答：异步不等确认、延迟小但可能丢数据；半同步等至少一个从库 ACK 才返回，降低丢数据风险（从库故障需降级异步避免阻塞）；MGR 用 Paxos 共识实现强一致+自动选主，需 3 节点。脑裂靠"过半仲裁"解决：网络分区后只有多数派能写，少数派自动降级只读，配合 fencing 强制旧主下线。

12 🔥 追问链 10｜分库分表

L0 · 主问题：什么时候需要分库分表？

答：分库——单库连接数/IO 打满或按业务域拆分；分表——单表千万~亿级或 >10GB，B+ 树加深、Buffer Pool 命中率下降、DDL 阻塞。先做减法（归档、加索引、优化 SQL、升级硬件），垂直优先、水平次之。

L1 · 追问：垂直拆分和水平拆分怎么选？

答：垂直分库按业务域（用户库/订单库/库存库），垂直分表拆大字段到扩展表；水平分表是同结构拆多张，靠路由定位。垂直解决"表太宽/库太杂"，水平解决"行太多"。

L2 · 追问：分片键怎么选？基因法是什么？

答：分片键选最频繁的等值条件（如 user_id），保证均匀、避免时间热点。基因法：订单号末尾嵌入 user_id 的哈希后缀，使订单既能按订单号直接路由、也能按 user_id 路由，解决"按 user_id 查订单却要全库扫"的痛点（电商经典）。

L3 · 追问：跨库的 join、事务、分页怎么办？

答：join——应用层组装 / 字段冗余 / 宽表 / ES；事务——XA（刚性慢）/ TCC / 本地消息表 + MQ（最终一致，最常用）/ Saga；分页——各分片 limit 后归并，深分页用游标翻页。中间件：ShardingSphere-JDBC（客户端）/ Proxy、MyCat（服务端）。

L4 · 追问：怎么平滑扩容？

答：双写 + 全量迁移 + 校验 + 灰度切换：新老分片同时写，用 canal 订阅 binlog 追增量，pt-table-checksum 校验一致后灰度切读、再停旧库。取模分片翻倍扩容只迁一半数据，是常见低成本方案。

13 🔥 追问链 11｜缓存一致性

L0 · 主问题：更新数据时，更新缓存还是删除缓存？

答：删除缓存（Cache Aside）。因为"更新缓存"在并发下可能写脏、且缓存未必马上被读，不如"失效后按需回源"，配合"先更新 DB 再删缓存"。

L1 · 追问：先删缓存还是先更新 DB？为什么都有不一致窗口？

答：先删缓存：删完、DB 未更新前，旧请求把旧值写回缓存 → 读到旧值；先更新 DB 后删缓存：更新完、删缓存前，读请求可能命中旧缓存 → 短暂读到旧值。二者窗口不同，主流是先更 DB 再删缓存，窗口更短。

L2 · 追问：延迟双删是解决什么的？怎么用？

答：解决"先更 DB 后删缓存"仍可能出现的脏缓存：更新 DB 后删一次，延时（如 1~2 秒）再删一次，把并发写回的脏值二次清掉。是简单可靠的兜底，但不是银弹。

L3 · 追问：生产里更推荐什么方案？

答：canal 订阅 binlog 删缓存：应用只写 DB，canal 解析 binlog 变更后异步删缓存。解耦、可靠、可重放，是主流大厂做法。核心思想：一致性交给"数据库变更事件"驱动，而不是应用手动维护。

L4 · 追问：缓存穿透、击穿、雪崩分别怎么防？

答：穿透（查不存在的 key 打穿到 DB）——布隆过滤器 / 缓存空值；击穿（热点 key 过期瞬间集中打 DB）——互斥锁重建 / 逻辑过期 / 热点不过期；雪崩（大量 key 同时过期/缓存宕机）——过期时间加随机抖动 / 多级缓存 / 限流降级。

14 🔥 追问链 12｜Buffer Pool 与内存

L0 · 主问题：Buffer Pool 是什么？

答：InnoDB 的内存缓存区，缓存数据页。读写都先经过它——命中即内存操作，未命中才磁盘 IO，是 MySQL 性能的核心。大小 innodb_buffer_pool_size，建议物理内存 60%~75%。

L1 · 追问：Buffer Pool 的 LRU 有什么特殊设计？

答：冷热分区（冷区约占 37%）：新读入的页先放冷区头部，只有被再次访问且停留时间 > innodb_old_blocks_time（默认 1000ms）才晋升热区。这样全表扫描的一次性页不会挤掉热点数据。

L2 · 追问：脏页什么时候刷回磁盘？

答：不是每次更新都刷，而是由后台线程按需刷：redo log 空间水位触发的 checkpoint、脏页比例超过 innodb_max_dirty_pages_pct、Buffer Pool 空闲页不足、MySQL 空闲/关闭时。脏页过多会导致刷盘风暴、IO 抖动。

L3 · 追问：怎么衡量 Buffer Pool 是否够用？

答：看命中率：Innodb_buffer_pool_read_requests / (read_requests + read_ahead)，命中率应 >99%。若命中率低且 Innodb_buffer_pool_reads（磁盘读）高，说明池太小或数据量超内存，需扩容或分库分表。

L4 · 追问：为什么大表全表扫描会让系统变卡？

答：全表扫描会不断把新页读入 Buffer Pool，若无冷热分区保护，会把热点页全部挤出，导致后续热点查询全部落盘、整体变慢。冷热分区正是为此设计；也可用 innodb_buffer_pool_size 多 instance 降低争用。

15 🔥 追问链 13｜一条 UPDATE 的完整链路（压轴）

L0 · 主问题：完整描述一条 UPDATE 从执行到落盘的全过程？

答：执行器定位行（当前读 + X 锁/next-key lock）→ 数据页读入 Buffer Pool → 写 undo（版本链，供回滚/MVCC）→ 修改内存页（变脏页）→ 写 redo(PREPARE) → 写 binlog → redo(COMMIT) → 返回成功，脏页由后台延迟刷盘。

L1 · 追问：UPDATE 加的是快照读还是当前读？为什么？

答：当前读。UPDATE 必须基于最新数据修改，且要加锁防止并发修改冲突；快照读（MVCC）读的是历史快照，不能用于更新基础，否则会丢更新。

L2 · 追问：没有索引的 WHERE 条件下 UPDATE 会怎样？

答：InnoDB 行锁是加在索引记录上的，无索引时无法定位具体行，会退化为全表扫描 + 锁全表所有行（实际上锁住所有记录和间隙），并发极差、极易死锁。这是"WHERE 条件必须走索引"的根因。

L3 · 追问：redo log 满了会怎样？checkpoint 是干嘛的？

答：redo log 是循环写，write pos 追上 checkpoint 即"满了"，此时必须停下写入、强制把脏页刷盘以推进 checkpoint 腾出空间，导致写入卡顿。checkpoint 标记"哪些脏页已刷盘、对应 redo 可覆盖"，是 redo 循环复用的关键。

L4 · 追问：从提交到"数据真正落盘"中间发生了什么？

答：事务提交只保证 redo 落盘（持久性），数据页仍在 Buffer Pool 是脏页，由后台线程异步刷盘。这就是 WAL（先写日志）的威力——提交快，因为只刷顺序的 redo，而非随机写数据页。

L5 · 追问：崩溃重启后，这条 UPDATE 怎么恢复？

答：重放 redo log 前滚已提交事务（redo 是 COMMIT 或 PREPARE+binlog 存在的），再用 undo log 回滚未提交事务（redo 是 PREPARE 但 binlog 不存在），最终回到崩溃前的一致状态。

16 新增高频题（现有题库缺失的补充）

补01 · 为什么索引列不建议用 NULL？

答：NULL 值参与比较需额外处理（IS NULL / 不等判断），优化器处理更复杂、部分场景索引失效；占用额外字节标志位。规范上建表 NOT NULL DEFAULT，把"空"语义用默认值表达。

补02 · EXPLAIN 的 key_len 有什么用？

答：key_len 是实际用到的索引字节数。通过它判断联合索引"用了几列"：如 (name VARCHAR(20) utf8mb4, age INT)，只匹配 name 时 key_len ≈ 20×4+2=82，再命中 age 会 +4。是验证最左前缀、定位索引没吃满的利器。

补03 · 索引的区分度/选择性怎么算？低于多少不建议建索引？

答：区分度 = COUNT(DISTINCT col) / COUNT(*)，越接近 1 越好。区分度极低的列（如性别、状态位）走索引收益小，优化器可能直接全表扫。经验：低于 20% 一般不单独建索引，可作为联合索引的辅助列。

补04 · 自适应哈希索引（AHI）是什么？

答：InnoDB 观察高频等值查询模式，自动在内存为热点索引页建哈希索引，等值查询 O(1)。无需人工干预，但只对等值、热点、重复模式有效，范围查询用不上。SHOW ENGINE INNODB STATUS 可看 AHI 使用情况。

补05 · 为什么 MySQL 不用跳表、也不把 B 树换成"更好的"结构？

答：见追问链 02 L5——介质决定结构。B+ 树把连续键紧凑塞进 16KB 页实现顺序预读 + 高扇出 + 矮树高，是为磁盘随机 IO 贵而生的最优解；跳表/红黑树等为内存设计，在磁盘上会退化为大量随机 IO。

补06 · 当前读 vs 快照读，最常见的"踩坑"场景？

答：RR 下，事务先 SELECT（快照读，看到旧值）再 UPDATE（当前读，基于最新值修改），改完再 SELECT 仍显示旧值——因为快照读复用同一 ReadView。业务判断若依赖"我刚读到的值"，必须用 SELECT ... FOR UPDATE（当前读），否则会基于过期数据做决策。

补07 · undo log 空间一直涨怎么办？

答：定位长事务——information_schema.innodb_trx 查 trx_started 最早、trx_rows_modified 最大的事务；SHOW PROCESSLIST 找执行时间长的会话。根治：缩短事务、及时 COMMIT、事务内不做远程调用/大查询、设置 max_execution_time、监控 undo 使用率告警。

补08 · MDL 锁写锁的"雪崩"是怎么发生的？怎么避免？

答：长事务持 MDL 读锁 → DDL 申请写锁排队 → 后续所有 DML 申请读锁排在 DDL 后 → 业务读写全阻塞。避免：大表 DDL 用 Online DDL（INSTANT/INPLACE + LOCK=NONE） 或 pt-osc/gh-ost（影子表 + binlog 同步，不长时间持锁）。

补09 · InnoDB 为什么没有"锁升级"（lock escalation）？

答：InnoDB 行锁存在内存哈希表里，内存开销可控，无需像 Oracle/SQL Server 那样"行锁太多时升级成表锁省内存"。代价是可能锁大量行，但换来更细粒度的并发，这与其"行锁+MVCC 高并发"的设计目标一致。

补10 · 锁等待超时 和 死锁，有什么区别？

答：锁等待超时是单边等待超过 innodb_lock_wait_timeout（默认 50s），报 1205；死锁是互相等待成环，被死锁检测立即识别并回滚，报 1213。死锁是"等不到头"，超时是"等太久"；处理上死锁靠重试，超时靠排查慢事务。

补11 · redo log 为什么要设计成循环写、固定大小？

答：redo 只需保证"崩溃能恢复最近未刷盘的修改"，一旦脏页刷盘、对应 redo 就无用了，可覆盖复用。固定大小 + 循环写既省空间又性能稳定（顺序写、无需扩容），checkpoint 推进即可复用。

补12 · binlog 里的 XID event 是干什么的？

答：XID 是事务提交标识，用于两阶段提交时在 binlog 中标记事务边界。崩溃恢复时，redo 的 PREPARE 事务通过 XID 去 binlog 里查找对应事务是否存在，从而决定提交还是回滚——XID 是 redo 与 binlog 关联的桥梁。

补13 · 8.0 的 writeset 并行复制为什么比 5.7 强？

答：5.7 按库并行（不同库可并行，同库串行），单库热点无法并行；8.0 的 WRITESET 记录每事务改动的行集合，只要两个事务改的行不冲突就能并行回放，同库内也能并行，大幅提升单库从节点吞吐。

补14 · 半同步复制从库挂了会怎样？怎么兜底？

答：主库等不到从库 ACK，写入会阻塞直到超时（rpl_semi_sync_master_timeout），超时后自动降级为异步，从库恢复后再自动升回半同步。避免单点故障拖垮主库，是半同步的常见保护机制。

补15 · 怎么校验主从数据是否一致？

答：pt-table-checksum 对主库分块计算校验和，与从库对比定位不一致的表/块；不一致用 pt-table-sync 回补。预防：binlog 用 ROW 格式、启用 GTID、禁止在从库手工写数据、定期巡检。

补16 · 订单超时未支付自动取消，数据库层面怎么做？

答：不要靠"实时扫描全表"。主流：延迟队列/RocketMQ 延迟消息投递超时事件，或定时任务扫"已创建且超时"的订单（状态 + 过期时间建索引，分批游标扫描），配合状态机流转 + 幂等取消 + 库存回补。核心：按过期时间索引、增量处理、幂等。

补17 · 排行榜/点赞数这种场景，MySQL 合适吗？

答：高频写、实时排序、读多写多，MySQL 压力大。更优：Redis ZSet（天然有序、O(log N) 写、实时 rank）。MySQL 做持久化兜底，Redis 做实时榜单，异步落库。能答出"不同数据结构选不同存储"是加分。

补18 · 热点行高并发更新（如库存/余额）怎么优化？

答：① 把单行拆成多行（如库存拆 10 份，随机取一行扣减，再汇总）；② 排队削峰（MQ 串行化）；③ 合并批量更新；④ 适当降级 RC、关死锁检测、锁超时兜底；⑤ 余额类用流水表 + 汇总替代单行频繁 UPDATE。核心：分散热点，避免单行串行成为瓶颈。

补19 · 读写分离下，写完立刻读主从延迟导致读到旧数据怎么办？

答：一致性敏感场景强制走主库（如"写后立即读"）；或用路由标记（会话内写后 N 秒内读主）；或读从库+版本号校验；长期靠降低主从延迟（并行复制、拆分大事务）。核心原则：能容忍延迟的读才走从库。

补20 · 分库分表后，唯一性约束（如手机号唯一）怎么保证？

答：分片后单库唯一索引失效，需全局唯一：① 用唯一列作为分片键（按手机号哈希分片，天然唯一）；② 若不能，用全局唯一表/Redis 预占（先抢唯一性再写）；③ 应用层先查后写 + 唯一表兜底。能指出"分片键选择与唯一性约束冲突"这一根本矛盾是加分。

补21 · 账户余额并发扣减，怎么保证不超扣、不丢更新？

答：UPDATE balance = balance - ? WHERE id=? AND balance >= ? 条件更新，受影响行数=0 则重试/拒绝（乐观锁思路，本质是"读-判断-写"变原子条件更新）；或用行锁 SELECT ... FOR UPDATE。绝不能先 SELECT 判断再 UPDATE（非原子，并发下超扣）。

补22 · 为什么金额字段要用 DECIMAL 而不是 FLOAT/DOUBLE？

答：FLOAT/DOUBLE 是二进制浮点，无法精确表示十进制小数（如 0.1），运算有误差；DECIMAL 是定点精确存储，适合金额。金额用 DECIMAL(18,2)，运算在应用层用 BigDecimal 或整数分，避免浮点误差。

补23 · DATETIME 和 TIMESTAMP 怎么选？

答：TIMESTAMP 是 4 字节、带时区、范围到 2038 年（2038 问题）；DATETIME 是 8 字节、范围大、不含时区。需要精确记录到远未来或不受时区转换影响时用 DATETIME，需要毫秒用 DATETIME(3)。8.0 后默认推荐 DATETIME。

补24 · 一条 SQL 为什么"时快时慢"？

答：可能原因：① 缓冲池命中波动（冷数据第一次查慢，热了变快）；② 脏页刷盘/checkpoint 导致的 IO 抖动；③ 锁等待（被别的事务阻塞）；④ 执行计划变化（统计信息更新后换了索引，甚至走错索引）；⑤ 网络/连接池抖动。排查：SHOW PROCESSLIST 看状态，EXPLAIN 对比执行计划，慢日志看是否同一条 SQL 波动。

补25 · MySQL 的 IO 是同步还是异步的？

答：8.0 之前 InnoDB 用原生 AIO（异步 IO），可并发发起多个磁盘请求；Windows 等平台用模拟 AIO。异步 IO 让多个页的读写并行，减少等待。能答出"IO 模型"层面属于进阶加分。

补26 · 为什么说"不要用 SELECT *"？

答：① 多读无用列，大字段会触发 off-page 额外 IO；② 破坏覆盖索引，导致回表；③ 增加网络与内存开销；④ 表结构变更时结果集列数变化，代码脆弱。应只 SELECT 必要列，最好走覆盖索引。
