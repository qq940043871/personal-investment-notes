### Q1: 如何进行微服务拆分？拆分的原则和边界是什么？

**考察点：** 服务拆分方法论、领域驱动设计、实际项目经验

**参考答案：**

微服务拆分应遵循以下原则：

```
┌─────────────────────────────────────────────────────────┐
│                  微服务拆分原则                          │
├─────────────────────────────────────────────────────────┤
│  1. 单一职责：一个服务只做一件事                          │
│  2. 高内聚低耦合：服务内部紧密，服务间松散                │
│  3. 独立部署：每个服务可独立开发、测试、部署              │
│  4. 业务边界：按业务领域拆分，而非技术层                  │
│  5. 数据独立：每个服务有自己的数据库                      │
└─────────────────────────────────────────────────────────┘
```

**拆分策略：**

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| 按业务域拆分 | 用户、商品、订单、支付 | 电商、SaaS |
| 按子域拆分 | DDD限界上下文 | 复杂业务系统 |
| 按团队拆分 | 康威定律 | 大型团队 |

**实际经验（电商项目）：**

```
电商系统拆分示例：
├── 用户服务（user-service）     → 用户注册、登录、会员等级
├── 商品服务（product-service）  → 商品CRUD、SKU管理、库存查询
├── 订单服务（order-service）    → 下单、状态流转、拆单合单
├── 支付服务（payment-service）  → 支付渠道、回调、对账
├── 库存服务（inventory-service）→ 库存扣减、预占、回滚
├── 营销服务（marketing-service）→ 优惠券、活动、积分
└── 搜索服务（search-service）   → ES索引、搜索、推荐
```

**拆分粒度权衡：**
- 太粗：失去微服务意义，部署效率低
- 太细：运维复杂度高，服务间调用链长
- 建议：从粗粒度开始，根据实际需要逐步拆分

### Q6: 如何设计分布式锁？有哪些实现方案？

**考察点：** 分布式锁原理、实现方案对比、实际应用

**参考答案：**

**实现方案对比：**

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| Redis SETNX | 性能高、实现简单 | 需处理超时、主从切换 | 高并发场景 |
| Redisson | 功能完善、可重入 | 依赖Redis | 生产推荐 |
| ZooKeeper | 强一致、可靠性高 | 性能较低 | 强一致性要求 |
| 数据库 | 简单可靠 | 性能差 | 低并发 |

**Redisson 实现：**

```java
// 1. 引入依赖
// implementation 'org.redisson:redisson-spring-boot-starter:3.23.4'

// 2. 使用分布式锁
@Autowired
private RedissonClient redisson;

public void processOrder(String orderId) {
    RLock lock = redisson.getLock("order:lock:" + orderId);
    try {
        // 尝试获取锁，等待3秒，锁定10秒
        boolean acquired = lock.tryLock(3, 10, TimeUnit.SECONDS);
        if (acquired) {
            // 执行业务逻辑
            doProcess(orderId);
        } else {
            throw new BusinessException("获取锁失败");
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}

// 3. 看门狗机制（自动续期）
// Redisson默认启用watchdog，每10秒续期一次
```

**锁的注意事项：**

```
┌────────────────────────────────────────────────────┐
│               分布式锁注意事项                       │
├────────────────────────────────────────────────────┤
│ 1. 设置超时时间，防止死锁                            │
│ 2. 释放锁时验证所有权（Lua脚本原子操作）             │
│ 3. 主从切换可能导致锁丢失（RedLock解决）             │
│ 4. 可重入锁需要记录持有计数                          │
│ 5. 业务执行时间不能超过锁超时时间                    │
└────────────────────────────────────────────────────┘
```

### Q7: 限流算法有哪些？如何实现分布式限流？

**考察点：** 限流算法原理、实现方案、实际应用

**参考答案：**

**限流算法对比：**

```
┌─────────────────────────────────────────────────────────────┐
│                      限流算法对比                            │
├───────────┬─────────────┬─────────────┬─────────────────────┤
│   算法    │    原理     │    特点     │      适用场景        │
├───────────┼─────────────┼─────────────┼─────────────────────┤
│ 固定窗口   │ 时间窗口内计数│ 实现简单    │ 精度要求不高        │
│ 滑动窗口   │ 细粒度时间窗口│ 精度高      │ 需要精确限流        │
│ 令牌桶     │ 固定速率放令牌│ 允许突发    │ API限流（推荐）     │
│ 漏桶       │ 固定速率流出  │ 严格平滑    │ 流量整形            │
└───────────┴─────────────┴─────────────┴─────────────────────┘
```

**令牌桶算法实现（Redis + Lua）：**

```lua
-- Lua脚本实现令牌桶
local key = KEYS[1]
local capacity = tonumber(ARGV[1])  -- 桶容量
local rate = tonumber(ARGV[2])      -- 放入速率
local requested = tonumber(ARGV[3]) -- 请求数量
local now = tonumber(ARGV[4])       -- 当前时间

local lastRefill = redis.call('hget', key, 'lastRefill')
local tokens = redis.call('hget', key, 'tokens')

if lastRefill == false then
    tokens = capacity
    lastRefill = now
end

-- 计算补充的令牌
local delta = math.max(0, now - lastRefill)
local filledTokens = math.min(capacity, tokens + delta * rate)

if filledTokens >= requested then
    local newTokens = filledTokens - requested
    redis.call('hmset', key, 'tokens', newTokens, 'lastRefill', now)
    return 1  -- 允许
else
    return 0  -- 拒绝
end
```

### Q9: 如何保证分布式事务一致性？有哪些方案？

**考察点：** 分布式事务方案、CAP权衡、实际应用

**参考答案：**

**分布式事务方案对比：**

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|----------|
| 2PC | 强一致 | 低 | 高 | 传统系统 |
| TCC | 最终一致 | 中 | 高 | 金融交易 |
| Saga | 最终一致 | 高 | 中 | 长流程业务 |
| 本地消息表 | 最终一致 | 高 | 低 | 简单场景 |
| 事务消息 | 最终一致 | 高 | 低 | 异步场景 |

**TCC实现示例（订单+库存）：**

```java
// TCC事务接口
public interface InventoryTccService {
    
    // Try: 预扣库存
    @TwoPhaseBusinessAction(name = "inventoryDeduct", 
                            commitMethod = "commit", 
                            rollbackMethod = "rollback")
    boolean tryDeduct(@BusinessActionContextParameter(paramName = "orderId") String orderId,
                      @BusinessActionContextParameter(paramName = "skuId") String skuId,
                      @BusinessActionContextParameter(paramName = "quantity") int quantity);
    
    // Confirm: 确认扣减
    boolean commit(BusinessActionContext context);
    
    // Cancel: 回滚预扣
    boolean rollback(BusinessActionContext context);
}

// Try实现
public boolean tryDeduct(String orderId, String skuId, int quantity) {
    // 1. 检查库存是否充足
    // 2. 冻结库存（inventory_frozen表）
    // 3. 记录事务日志
    return inventoryMapper.freezeStock(skuId, quantity, orderId);
}

// Cancel实现
public boolean rollback(BusinessActionContext context) {
    String orderId = context.getActionContext("orderId").toString();
    // 释放冻结库存
    return inventoryMapper.releaseFrozenStock(orderId);
}
```

### Q10: CAP理论是什么？如何在架构设计中权衡？

**考察点：** CAP理论、BASE理论、架构决策

**参考答案：**

**CAP理论：**

```
┌─────────────────────────────────────────────────────┐
│                     CAP 理论                        │
├─────────────────────────────────────────────────────┤
│  C (Consistency)  : 一致性 - 所有节点数据一致        │
│  A (Availability) : 可用性 - 每个请求都有响应        │
│  P (Partition)    : 分区容错 - 网络分区时系统可用    │
│                                                     │
│  定理：分布式系统中，CAP最多只能同时满足两个         │
└─────────────────────────────────────────────────────┘

         ┌───────────┐
         │     CA     │ ← 单机数据库（MySQL单机）
         └───────────┘
              ╱ ╲
             ╱   ╲
┌───────────┐     ┌───────────┐
│    CP     │     │    AP     │
└───────────┘     └───────────┘
  ZooKeeper         Cassandra
  Redis集群         Eureka
```

**实际架构权衡：**

| 场景 | 选择 | 原因 |
|------|------|------|
| 银行转账 | CP | 一致性优先，可接受短暂不可用 |
| 商品展示 | AP | 可用性优先，短暂不一致可接受 |
| 订单创建 | CP | 库存一致性必须保证 |
| 用户评论 | AP | 可用性优先，最终一致即可 |

**BASE理论（AP的补充）：**

```
BA (Basically Available)  : 基本可用 - 允许部分降级
S (Soft State)            : 软状态 - 允许中间状态
E (Eventually Consistent) : 最终一致 - 一定时间后一致
```

```python
# 混合检索实现
def hybrid_search(query, k=10):
    # 1. 语义检索
    semantic_results = vector_db.search(
        embedding(query), 
        top_k=k*2
    )
    
    # 2. 关键词检索 (BM25)
    keyword_results = elasticsearch.search(
        query,
        top_k=k*2
    )
    
    # 3. 融合排序 (RRF)
    merged = reciprocal_rank_fusion(
        semantic_results, 
        keyword_results
    )
    
    # 4. 重排
    reranked = reranker.rerank(
        query, 
        merged[:k*2]
    )
    
    return reranked[:k]
```

### Q18: vLLM的PagedAttention原理是什么？为什么能提升推理性能？

**考察点：** 模型推理优化、显存管理

**参考答案：**

**传统推理 vs PagedAttention：**

```
传统推理（连续内存）：
┌─────────────────────────────────────────────────────┐
│ Request 1: [████████████████████]                   │
│ Request 2: [██████████░░░░░░░░░░]  ← 预分配但未用完 │
│ Request 3: [████████████░░░░░░░░]                   │
│                                                     │
│ 问题：内存碎片、预分配浪费、无法共享                 │
└─────────────────────────────────────────────────────┘

PagedAttention（分页内存）：
┌─────────────────────────────────────────────────────┐
│ Block Pool: [■][■][■][■][■][■][■][■][■][■][■][■]... │
│              ↑     ↑     ↑                          │
│ Request 1: Block 0,1,2,3 (动态分配)                 │
│ Request 2: Block 4,5 (按需分配)                     │
│ Request 3: Block 6,7,8 (共享前缀 Block 0,1)         │
│                                                     │
│ 优势：按需分配、共享前缀、零碎片                     │
└─────────────────────────────────────────────────────┘
```

**核心优化：**

| 优化点 | 说明 | 收益 |
|--------|------|------|
| PagedAttention | KV Cache分块管理 | 显存利用率提升2-4x |
| Continuous Batching | 动态批处理 | 吞吐提升2-3x |
| 前缀缓存 | 共享Prompt前缀 | 延迟降低30-50% |
| Tensor Parallelism | 多卡并行 | 支持更大模型 |

### Q20: 向量检索原理

**标准答案：**

**HNSW (Hierarchical Navigable Small World) 算法：**

```
原理:
- 构建多层图结构
- 上层稀疏(快速跳跃)、下层稠密(精确搜索)
- 搜索时从上层入口点开始，逐层向下找最近邻

图结构示意:

Layer 2:     ●───────────────●        (稀疏)
             │               │
Layer 1:     ●───────●───────●        (中等)
             │       │       │
Layer 0:     ●───●───●───●───●        (稠密)
             ↑
          查询点

搜索过程:
1. 从Layer 2入口点开始
2. 在当前层找最近邻
3. 进入下一层继续搜索
4. 直到Layer 0返回结果
```

**关键参数：**

| 参数 | 说明 | 影响 |
|------|------|------|
| M | 每层最大连接数 | 越大召回率越高、索引越大 |
| efConstruction | 构建时搜索范围 | 越大索引质量越好、构建越慢 |
| efSearch | 搜索时搜索范围 | 越大召回率越高、搜索越慢 |

**性能指标：**

```
召回率: Recall@K = 命中真实Top-K / K
QPS: 每秒查询数
延迟: P50 / P99

典型配置:
- M = 16
- efConstruction = 200
- efSearch = 100

性能参考 (Qdrant, 100万向量):
- Recall@10: 98%+
- QPS: 5000+
- P99延迟: <50ms
```

### Q22: LoRA 微调原理

**标准答案：**

**原理详解：**

```
原始模型权重: W (冻结)

LoRA添加: ΔW = B × A
- A: (d × r) 降维矩阵
- B: (r × d) 升维矩阵
- r: 秩 (通常 r << d)

最终权重: W' = W + B × A

参数量对比:
- 原始: d × d
- LoRA: 2 × d × r
- 当 r=8, d=4096: 参数量减少 99.6%
```

**训练过程：**

```python
from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM

# 加载基础模型

    "Qwen/Qwen2.5-7B-Instruct",
    torch_dtype=torch.bfloat16,
)

# LoRA配置

    r=16,                    # 秩
    lora_alpha=32,           # 缩放因子
    target_modules=[         # 应用层
        "q_proj", "k_proj", 
        "v_proj", "o_proj"
    ],
    lora_dropout=0.05,
    task_type="CAUSAL_LM",
)

# 应用LoRA
model = get_peft_model(model, lora_config)

# 训练
trainer.train()
```

### Q24: ROI 评估方法

**标准答案：**

**成本计算：**

```
成本 = 硬件成本 + 推理成本 + 人力成本

硬件成本:
├── GPU服务器: 4×A100 80G ≈ 40万/年(租赁)
├── 存储: 10TB SSD ≈ 2万/年
└── 网络: 内网带宽 ≈ 1万/年

推理成本:
├── API模式: Token单价 × 日均Token数
└── 私有部署: 电费 + 运维人力

人力成本:
├── 开发: 2人 × 30万/年 = 60万
└── 运维: 1人 × 20万/年 = 20万
```

**收益计算：**

```
收益 = 效率提升 + 转化提升 + 成本节约

智能客服案例:
├── 原人工客服: 20人 × 15万/年 = 300万
├── AI客服替代: 60%问题自动解决
├── 节约人力: 12人 × 15万 = 180万
└── 扣除AI成本: 180万 - 60万 = 120万/年

知识库问答案例:
├── 原查询效率: 30分钟/次
├── AI后效率: 3分钟/次
├── 效率提升: 10倍
├── 日均查询: 1000次
└── 年节约时间: 1000 × 27分钟 × 250天 = 112500小时
```

**ROI 公式：**

```
ROI = (收益 - 成本) / 成本 × 100%

案例计算:
- 年收益: 180万
- 年成本: 60万(开发) + 40万(硬件) + 20万(运维) = 120万
- ROI = (180 - 120) / 120 × 100% = 50%

考虑长期:
- 第2年起开发成本下降
- ROI可提升至 100%+
```

```
│                                                     │
└─────────────────────────────────────────────────────┘

```
