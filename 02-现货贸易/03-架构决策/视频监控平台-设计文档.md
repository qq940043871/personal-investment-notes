# 视频监控平台 · 完整设计文档

> **定位**：用 **FFmpeg + ZLMediaKit** 自建一层流媒体底座，把客户现场存量的 RTSP 摄像头变成 Web 端「**可看、可回、可取证**」的能力。本文覆盖选型、架构、数据模型、四条主链路、容量测算、故障矩阵与已知缺陷。
> **角色**：流媒体方案技术负责人（选型 + 落地）。
> **适用场合**：方案评审 / 面试追问 / 交付交接。
> **口径约定**：`【底稿】`= 源页面已写明；`【推演】`= 本文补充的推导与测算（CPU/带宽/存储账、缺陷清单），**不得当作已实现事实引用**；`【待确认】`= 源材料缺失或需实测。

---

## 零、三句话（被问到时先答这三句）

1. **这件事的难点不在「能播」，而在四件事**：一路摄像头要被 N 个人同时看（直连必死）、浏览器不认 RTSP、弱网/手机/大屏三类终端对延迟与兼容的要求互相打架、录像要按事件回溯而不是按文件翻。
2. **解法是「开源底座 + 自建分发」**：否决商用 NVR 厂商 SDK（按路授权、绑死客户端）与海外 SaaS 中转（把视频流交给第三方、延迟不可控）；用 FFmpeg 一次拉流转码、ZLMediaKit 一次输入产出 WebRTC/FLV/HLS 三档出口，业务层只拿 URL。
3. **闭环的关键是「直播与录像同源」**：录像不是另一条链路，而是同一条流的落盘结果——所以回放和下载永远不会「和刚才看到的不一样」。

## 二、问题定义

### 2.1 业务背景

客户现场已装几十上百个 **RTSP** 摄像头，但看画面要回机房开 NVR 客户端：装软件、配 IP、只能局域网。手机看不了、领导远程看不了、出事调录像只能按文件名一个个拖。

行业约束（这是选型的真正起点）【底稿】：园区/工地/仓储/门店的存量摄像头几乎全是 RTSP / ONVIF；出厂客户端只在局域网可用；商用监控平台大多**按路授权**——几十上百路就是一笔持续成本。**开源自建的价值就是把「按路付费」变成「一台服务器的固定成本」。**

### 2.2 四个真问题

| # | 问题 | 不解决的后果 | 对应设计 |
|---|---|---|---|
| Q1 | **一路摄像头要 N 个人看** | 10 个人看同一路 → 把摄像头并发连接打满甚至拖死 | 服务端**一路只拉一次**，ZLM 向多客户端分发（D1） |
| Q2 | **浏览器不认 RTSP** | 只能退回「装客户端」 | 协议转换：WebRTC / FLV / HLS 三档出口（D2） |
| Q3 | **三类终端要求互相打架** | 一套播放器覆盖不了，做四套维护成本爆炸 | 能力探测 + **逐级降级**，HLS 兜底（D2） |
| Q4 | **录像要按事件回溯，不是按文件翻** | 定位一件事从分钟级退化到小时级 | 元数据/文件分离 + 时间轴片段模型（D4、§7.5） |

### 2.3 目标与非目标

| 类型 | 内容 |
|---|---|
| **目标** | ① 存量 RTSP 零改造接入；② 单路多客户端分发、摄像头连接数恒定；③ PC/手机同源、协议自动降级不黑屏；④ 录像可按时间轴定位、按告警收敛；⑤ 取证下载可批量、可转码、可断点续传、链接可控 |
| **非目标** | ① 不做智能分析（人形/车牌识别），只做「告警标记」的承接与展示；② 不做多级联网/上级平台级联（GB/T 28181）本期不实现；③ 不做云原生弹性伸缩（单机/小集群起步）；④ 不做视频内容检索（语义搜索） |

### 2.4 验收指标

| 类别 | 指标 | 目标 | 来源 |
|---|---|---|---|
| 接入 | 单机注册路数 | 50 ~ 100 路（4C8G / 720P / 1–2 Mbps） | 底稿 |
| 观看 | 并发观看连接 | 1000+（不放大摄像头侧连接） | 底稿 |
| 延迟 | PC WebRTC / FLV / HLS | < 500ms / 1–2s / 3–5s | 底稿 |
| 首帧 | 新观众出画时间 | ≤ 1s（依赖 GOP 缓存） | 底稿 |
| 播放 | 降级成功率 | 100%（HLS 兜底，不黑屏） | 底稿 |
| 检索 | 定位一段告警录像的耗时 | 分钟级（原为小时级） | 底稿 |
| 下载 | 断点续传 | 弱网断线可续，不重下 | 底稿 |

## 三、总体架构

```
┌──────────────┐   RTSP over TCP    ┌──────────────────────────────────────┐
│ 存量摄像头     │◄──────────────────│ ① 接入 / 转码层（FFmpeg 进程池）      │
│ (RTSP/ONVIF)  │   ONVIF 控制        │  · 按需拉流（观看/录制时才拉）         │
└──────┬───────┘◄──────────────────│  · -preset ultrafast -tune zerolatency│
       │ PTZ 指令                   │  · -g 25，同参数复用同一转码进程       │
       │                            └──────────────┬───────────────────────┘
       │                                           │ 一路输入
       │                            ┌──────────────▼───────────────────────┐
       │                            │ ② 分发层 ZLMediaKit                    │
       │                            │  · 一次输入 → WebRTC / FLV / HLS 三出口 │
       │                            │  · GOP 缓存（新观众秒出画）             │
       │                            │  · 录制落盘（与直播同源）                │
       │                            └──────┬─────────────────┬─────────────┘
       │                                   │ 播放 URL         │ MP4 切片
       │                    ┌──────────────▼──────┐   ┌──────▼──────────────┐
       │                    │ ③ 播放层（浏览器）    │   │ ④ 存储层             │
       │                    │  协议探测 + 逐级降级  │   │  MP4 → NAS / OSS     │
       │                    │  分屏实例生命周期     │   └──────┬──────────────┘
       │                    └──────────┬──────────┘          │
       │                               │                     │
       │                    ┌──────────▼─────────────────────▼──────────────┐
       └───────────────────►│ ⑤ 业务层（Java/Spring）                        │
         PTZ 转发            │  设备管理 · 时间轴检索 · 下载任务 · 预签名 · 告警 │
                            │  MySQL：camera / recording / download_task     │
                            └───────────────────────────────────────────────┘
```

### 3.1 三条线的边界（这块决定了系统能不能演进）

| 线 | 管什么 | 不管什么 |
|---|---|---|
| **摄像头侧** | RTSP 地址、ONVIF 能力（PTZ/预置位）、在线状态 | 不直连浏览器、不承担多观众 |
| **流媒体侧** | 拉流、转码、分发、GOP 缓存、录制落盘 | **不碰业务语义**（谁有权限看、这段算不算告警） |
| **业务库侧** | 设备主数据、录像元数据、告警标记、下载任务、鉴权与签名 | 不搬流、不转码 |

> 这条边界的价值：换流媒体实现（ZLM → SRS / MediaMTX / 云厂商）时，业务层只改「URL 生成」与「拉流控制」两处；业务侧改权限模型时，流媒体侧不动。

## 四、技术选型

### 4.1 四条路线对比

| 路线 | 授权成本 | 延迟可控 | 数据归属 | 设备兼容 | 结论 |
|---|---|---|---|---|---|
| **商用 NVR 厂商 SDK** | 按路授权，几十上百路持续计费 | 好（私有协议） | 客户内网 | 仅厂商设备 | ❌ 否决 |
| **海外 SaaS 中转** | 按流量/路数订阅 | **不可控**（跨境链路） | 视频流出域 | 好 | ❌ 否决 |
| **纯自研（自己写 RTSP 解析 + RTP 打包 + WebRTC）** | 零授权 | 最好 | 自控 | 最好 | ❌ 周期不可接受 |
| **开源底座 + 自建分发（FFmpeg + ZLMediaKit）** | **零授权** | 好（同机房） | 自控 | RTSP/ONVIF 通吃 | ✅ **选定** |

### 4.2 为什么是 ZLMediaKit 而不是 SRS / MediaMTX【推演】

| 维度 | ZLMediaKit | SRS | MediaMTX |
|---|---|---|---|
| WebRTC 输出 | 原生支持（含 WHIP/WHEP 演进） | 支持但配置重 | 支持 |
| 多协议一次输入多出口 | 强项（RTSP/RTMP/FLV/HLS/WebRTC 同源） | 强（偏直播场景） | 中 |
| 按需拉流 / 无人观看关闭 | 支持（`on_demand` + 延迟关闭） | 需外部触发 | 支持 |
| 与 FFmpeg 协作 | 可直接收 FFmpeg 推流，也可自己拉 RTSP | 同 | 同 |
| 生态与部署 | 单二进制、C++、资源占用低 | 文档最全、社区最大 | 最轻量 |

结论：本场景的权重是「**同一路流要多协议出口 + 按需拉流 + 低资源**」，ZLM 匹配度最高；SRS 作为备选（社区更大、排障资料多），MediaMTX 适合极简场景。

## 五、关键技术决策（决策 / 备选 / 代价）

### D1 一路 RTSP 只拉一次，服务端分发

**否决**：每个观看者直连摄像头，或每路 N 个观看者就起 N 个 FFmpeg。
**理由**：摄像头是**嵌入式设备**，并发连接数通常只有个位数；10 个人看同一路就能把它拖死。
**代价**：服务端成为流量汇聚点，**出口带宽成为新瓶颈**（§8.2），需要多节点/CND 分流。

### D2 协议三档自适应 + 逐级降级

```
手机（Android/iOS）           → HLS（兼容优先，3–5s 可接受）
PC 有 RTCPeerConnection       → WebRTC（< 500ms）
PC 无 WebRTC 且 flv.js 可用    → FLV（1–2s）
其余                          → HLS（最后一道兜底，永不黑屏）
```

**理由**：Safari 不认 FLV、部分安卓浏览器 WebRTC 不可用、老设备只吃 HLS。做四套播放器不如做一条降级链。
**代价**：三档延迟不统一，UI 必须**告诉用户当前档位**（否则「为什么手机上慢 3 秒」会被当成 bug）；HLS 的切片延迟与 GOP 长度耦合。

### D3 云台走 ONVIF 标准，不接厂商私有 SDK

**理由**：`ContinuousMove / Stop` 是标准动作，换品牌不改代码。
**代价**：ONVIF 能力探测要做（不是所有设备支持预置位/变焦）；不同厂商对 `ContinuousMove` 速度参数的解释有差异，需按型号兜底。
**必须做对的一件小事**：「松手即停」要真的发一条 **Stop**。网络抖动丢了停止指令，镜头会一直转到限位——这是现场最容易出的事故。

### D4 元数据与文件分离

| 存哪 | 存什么 | 为什么 |
|---|---|---|
| **MySQL** | 录像记录：设备、起止时间、存储路径、存储类型、`hasAlarm` | 检索永远查元数据，**绝不扫目录** |
| **NAS / OSS** | MP4 本体 | 大对象、按生命周期清理，不占数据库 |

**代价**：元数据与文件可能不一致（文件被清理但记录还在）→ 需要一致性巡检（§12 缺陷 6）。

### D5 播放地址不直连存储，发预签名 URL

- 云上：OSS 预签名，**1 小时有效**；本地：走应用代理 `/api/recordings/play/{id}`。
- **理由**：一旦把桶路径透给前端，URL 会被复制外传，录像就变成公开资源。预签名把「谁能看、能看多久」交给签名表达，过期自动失效，**也不必为播放再造一套鉴权**。
- **代价**：1 小时窗口内链接可被转发 → 需水印与访问日志兜底（§10）。

### D6 下载定性为「异步任务」，不是同步接口

```
提交（校验 + 判断是否需要真转码）→ 立刻返回 taskId
              ↓ 线程池
      FFmpeg 转码 / ZIP 串行打包 → 进度写表
              ↓
      轮询进度 → COMPLETED 后发带 token 的链接（24h）
```

**理由**：转码要跑 FFmpeg、打包要写 ZIP，都是分钟级操作，塞进 HTTP 请求必然被网关超时掐断——**演示时正常，真实大文件上必坏**。
**代价**：多一套任务表与状态机；用户要二次操作（看进度再取件）。

### D7 分屏数即实例数（解码器生命周期）

`screenCount` 是唯一状态源，`watch(screenCount)` 同步 `playerPool.resize(n)`——**多出来的 `close()`**。
**理由**：16 路同时硬解会把中低端显卡打满；「演示能跑」和「值班能盯 8 小时」的差别就在这一条。
**代价**：切分屏时有短暂重连与首帧等待（可接受，用 GOP 缓存与占位图缓解）。

### D8 直播与录像同源

录像不是「另起一路去拉流」，而是**同一路输入的落盘结果**。于是回放/下载的内容与直播看到的一致，也不额外增加摄像头连接数。

## 六、数据模型

### 6.1 MySQL 表

```sql
-- 设备
camera(
  id, name, rtsp_url, onvif_url,
  manufacturer, model,
  ptz_supported, preset_supported,
  status,              -- ONLINE / OFFLINE / UNKNOWN
  last_heartbeat_at,
  region_id, created_at
)  KEY idx_region_status(region_id, status)

-- 录像记录（时间轴的最小单元）
recording(
  id, camera_id,
  start_time, end_time,          -- 绝对时间，非文件内偏移
  duration_s,                    -- 冗余，便于统计
  file_path,                     -- NAS 相对路径 / OSS object key
  storage_type,                  -- NAS / OSS
  file_size,                     -- 字节
  has_alarm,                     -- 告警标记随记录落库（不依赖告警系统在线）
  alarm_type, alarm_event_id,
  created_at
)  KEY idx_cam_start(camera_id, start_time)   -- 时间轴检索主索引

-- 下载任务（四态单向流转）
download_task(
  id, camera_id,
  recording_ids,                 -- 多段入库 JSON 或子表
  target_format,                 -- MP4 / AVI / MKV
  need_transcode,                -- 提交时判定：能否 -c copy
  status,                        -- PENDING/PROCESSING/COMPLETED/FAILED
  progress,                      -- 0~100（按已完成段数/总段数）
  result_path, error_msg,
  created_by, created_at, finished_at
)

-- 告警事件（可选，回放只读 has_alarm 冗余字段）
alarm_event(id, camera_id, occurred_at, type, payload, created_at)
```

### 6.2 存储路径规范【推演】

```
{camera_id}/{yyyy}/{MM}/{dd}/{HHmmss}_{duration}s_{alarm|normal}.mp4
例：1024/2026/11/23/140500_600s_alarm.mp4
```

好处：按设备+日期即可前缀列举做对账；**但检索仍只查 MySQL**——路径规范是给运维和一致性巡检用的，不是给查询用的。

### 6.3 为什么 `has_alarm` 要冗余进 `recording`

告警系统挂了，历史标记照样能查。**「事后回溯」与「实时告警」必须解耦**——这是回放模块最容易被做错的一处（用 join 实时查告警表，告警表一清理，时间轴上的高亮就消失了）。

## 七、核心链路

### 7.1 直播播放

```
前端选路 → 取流地址（业务层按设备+协议能力生成）
        → pickProtocol(终端 + 能力)：hls / webrtc / flv
        → destroyPlayer()（幂等清理，切协议前必须销毁旧实例）
        → 挂载播放器
ZLM 侧：若该路无人观看 → 按需拉流（FFmpeg 起进程 / ZLM 直拉）
        若该路已在播 → 直接复用输入流（不重复拉摄像头）
```

**顺序不可换的是「先销毁再挂载」**：同一个 `<video>` 上叠加两个解码器，表现为内存暴涨、画面花屏，且极难归因。

### 7.2 云台 PTZ

```
按下 → 前端持续发 ContinuousMove（方向 + 速度）  → 业务层 → ONVIF → 设备
松开/失焦/页面隐藏 → 必须发 Stop（且要有超时兜底：N 秒无新指令自动 Stop）
```

### 7.3 实时截图

`video` → `canvas.drawImage` → `toDataURL('image/png')` → 下载或上传。

**必须满足**：视频源与页面**同源或允许 CORS**，否则 `toDataURL` 抛安全异常、拿到空白图。服务端必须对流地址响应头放开跨域（`Access-Control-Allow-Origin`），否则这个功能在真实环境里 100% 失败。

### 7.4 录制与切片

```
同一路输入 → ZLM/FFmpeg 按固定时长切片（如 10 分钟）
          → 每片落 NAS/OSS，回调写 recording 一行
          → 若该片段内有告警 → has_alarm = true（写入时定死）
```

切片长度是**权衡**：片太长 → 单文件大、下载/回放定位粒度粗、失败重传成本高；片太短 → 记录行数暴涨、时间轴碎片化、OSS 小对象多。10 分钟是常用折中【推演】。

### 7.5 时间轴检索

```
选设备 + 选日期
   ↓ 一次查询（主索引 idx_cam_start）
片段列表：[{recordingId, startTime, endTime, hasAlarm}]   ← 前端唯一渲染输入
   ↓ 时间轴着色：有录像上色 / 无录像留空 / 告警高亮
点选 → 播放地址（预签名 or 代理）
```

**关键**：时间轴数据是**「片段列表」而不是「文件列表」**，且不含任何存储细节。切片规则以后改了，前端不用动。

**跨片段的绝对时间**：进度必须按**绝对时间**算而不是**文件内偏移**，否则一换文件时间轴就跳回 0，用户以为录像丢了。这是回放体验里最容易被忽略的一处。

### 7.6 下载任务

```
提交：校验 recording 存在 → 判定 need_transcode（目标容器 vs 源编码）
     → 建 task（PENDING）→ 返回 taskId
处理：线程池取任务 → PROCESSING → 逐段处理（进度=已完成段/总段）
     → 成功写 result_path → COMPLETED；异常 → FAILED + error_msg
取件：生成带 token 的下载链接（24h）
传输：Accept-Ranges: bytes → 206 Partial Content → Content-Range 精确起止
```

**状态机四态、单向流转、失败可重试但必须新建任务**——不原地改状态，这样「这个文件到底有没有成功下过」永远有记录可查。

## 八、容量与资源测算【推演 · 必须实测替换】

### 8.1 CPU：为什么「50–100 路」不能是「并发转码 50 路」

| 模式 | 单路 CPU 成本（720P25，4C8G） | 4C8G 可用约 3 核 → 并发能力 |
|---|---|---|
| 软件转码（`ultrafast`，H.264→H.264） | 约 0.5 ~ 1.5 核/路 | **2 ~ 6 路** |
| 直转 / 不转码（`-c copy`） | ≈ 0（只做协议封装） | 数十路（受网络与 fd 约束） |
| 硬件转码（QSV/NVENC，若有） | 约 0.1 ~ 0.3 核/路等效 | 20 ~ 50 路 |

**结论（重要）**：「单机 50–100 路」在本场景下的**唯一成立方式**是：

1. 「50–100 路」指**接入/注册路数**，不是同时转码路数；
2. 观看采用**按需拉流**（无人看就不拉、无人看延迟关闭）；
3. 源本身是 H.264/AAC 时**优先 `-c copy` 直转**，只有编码不兼容或多档输出时才真转码。

> 这三条必须写进交付文档，否则按「100 路同时转码」报容量的方案在现场必然翻车。`【待确认】` 源页面未区分这两种口径。

### 8.2 带宽：出口是比 CPU 更早撞墙的资源

| 项 | 计算 | 结果 |
|---|---|---|
| 单路码率 | 720P @ 1.5 Mbps（区间 1–2） | 0.19 MB/s |
| 1000 并发观看（1 路/人） | 1000 × 1.5 Mbps | **1.5 Gbps** ❌ 单机千兆网卡打不住 |
| 16 分屏 × 100 人 | 100 × 16 × 1.5 Mbps | **2.4 Gbps** ❌ 分屏会成倍放大 |
| 500 并发 + 部分 4 分屏 | 假设 400×1 + 100×4 = 800 路 | 1.2 Gbps |

**结论**：**「1000+ 并发观看」不是单机能交付的指标**（除非走多节点前置/CDN 或降码率档）。工程上必须：① 按并发路数（含分屏放大）而不是人数报容量；② 出多档清晰度（如 720P/480P）让弱网与大并发自动降档；③ 超过单机出口时前置多台分发节点或 CDN 回源。

### 8.3 存储：录像成本才是长期成本

| 码率 | 单路日增（86400s） | 100 路日增 | 100 路 30 天 |
|---|---|---|---|
| 1 Mbps | 10.8 GB | 1.08 TB | **32 TB** |
| 1.5 Mbps | 16.2 GB | 1.62 TB | **49 TB** |
| 2 Mbps | 21.6 GB | 2.16 TB | **65 TB** |

**结论**：存储是持续成本，必须定三件事：**留存期**（30/90 天）、**分层**（近 7 天热存 + 更早冷存/低频 OSS）、**告警片段单独长期保留**（证据价值高、体积小）。这一条常常比服务器采购更影响报价。

### 8.4 连接与 fd

| 项 | 估算 |
|---|---|
| 单实例 ZLM 播放连接 | 数千（受 fd 与内存约束，需 `ulimit -n` 调至 10 万+） |
| 摄像头侧连接 | **= 注册且正在拉流的设备数**（与观众数无关，这是 D1 的收益） |
| 转码进程数 | = 正在观看且需转码的路数（复用后不随观众数增长） |

## 九、故障矩阵与降级

| 故障 | 表现 | 根因 | 动作 |
|---|---|---|---|
| **摄像头离线 / 网络抖动** | 某路黑屏、卡顿 | RTSP 断流、丢包 | RTSP 走 **TCP** 而非 UDP（UDP 丢包直接花屏）；ZLM 断流回调 → 置 `OFFLINE` + 定时重连（指数退避）；UI 显示「设备离线」而非静默黑屏 |
| **转码进程崩溃 / 卡死** | 观众一直转圈 | FFmpeg 异常退出、进程僵死 | 进程守护（退出即重启，带熔断）；**无输出超时**（如 10s 无帧）杀掉重建；单路连续失败 N 次标记不可用 |
| **ZLM 单点故障** | 全站断流 | 进程/机器挂 | 单机版只能重启（要承认）；生产版需双实例 + 按设备分片 + 设备重连到备用节点【推演】 |
| **协议不支持** | 握手失败/黑屏 | 企业代理、Safari 不认 FLV | 逐级降级 → HLS 兜底；降级要有**终点**，不能无限尝试 |
| **OSS 不可用** | 回放/下载 403/超时 | 云侧故障、签名错误 | NAS 与 OSS 走同一接口（`playbackUrl` 分支），可临时切 NAS 代理；签名失败返回明确错误码而非空白 |
| **NAS 满盘** | 录制中断、写入失败 | 无生命周期策略 | 容量水位告警（70%/85%）；按留存期自动清理；**告警片段不参与自动清理** |
| **元数据与文件不一致** | 时间轴有段但播放 404 | 文件被清理、录制回调丢失 | 一致性巡检（按日期前缀对账）+ 播放前存在性校验 + 前端降级提示 |
| **时钟漂移** | 时间轴整体偏移、跨片段跳变 | 服务器/设备 NTP 未同步 | 统一 NTP；`start_time` 以录制侧为准并记录时区；跨片段用绝对时间 |
| **长任务拖死请求** | 下载 502/超时 | 同步转码 | 异步任务化（D6），HTTP 只负责「下单」 |
| **慢客户端** | 单连接拖慢分发 | 移动端弱网 | ZLM 侧发送缓冲与丢帧策略（保关键帧）；播放端降档 |

## 十二、已知缺陷与技术债（诚实清单）

> 前 2 条是**代码级审阅发现**（源页面示例代码里的真实 bug），第 3 条起是架构/交付缺口。

| # | 缺陷 | 影响 | 建议动作 |
|---|---|---|---|
| 1 | 续传代码用 `resp.getHeader("Range")` 取 **响应头** | `Range` 是**请求头**（应为 `request.getHeader("Range")`），按此实现永远拿不到范围 → **206 分支永不触发，断点续传实际不生效** | 改 `HttpServletRequest`；补「大文件 + 断网重连」用例，本地小文件测不出来 |
| 2 | `Runtime.getRuntime().exec("ffmpeg -i " + in + " ...")` 字符串拼接 | 路径含空格/特殊字符即失败；外部可控输入时有**命令注入**风险；且无超时、无进度、无退出码校验 | 改 `ProcessBuilder` + 参数数组；加超时与输出解析（`-progress`）；进程收敛到受管线程池 |
| 3 | 单机无 HA | ZLM/转码全挂则全站断流 | 双实例 + 按设备分片 + 设备重连到备用 |
| 4 | 「50–100 路」口径未区分接入/转码 | 按错误口径报容量，现场 CPU 打满 | 明确并按 §8.1 三条（按需拉流/直转优先/资源账）交付 |
| 5 | 1000+ 并发观看缺带宽方案 | 单机网卡打不住（§8.2） | 多档清晰度 + 分发节点/CDN |
| 6 | 元数据与文件无一致性校验 | 时间轴有段、播放 404 | 按日期前缀对账 + 播放前存在性校验 |
| 7 | 预签名 URL 可外传 | 1h 窗口内链接泄露 | 水印 + 调阅日志 + 关键设备缩短有效期 |
| 8 | 批量打包串行无优先级 | 大任务排队久、取证场景（法务/公安）无法加急 | 任务优先级 + 分组队列 |
| 9 | PTZ 无指令防重放/频率限制 | 恶意高频指令可损耗云台电机 | 前端限流 + 服务端按会话限速 |
| 10 | 无录像完整性校验（checksum） | 取证时无法证明文件未被篡改 | 落盘时记 hash，下载时校验并在交付清单中给出 |

## 十四、高频追问预案

**Q1：为什么不用商用 NVR 厂商的方案？**
两条：**按路授权**（几十上百路是持续成本，开源自建变成一次性服务器成本）与**绑死客户端**（只能在局域网、只能在指定系统）。客户要的是「手机能看、领导能远程看」，这个诉求厂商客户端满足不了。

**Q2：一路摄像头 10 个人看，怎么不把摄像头打死？**
服务端**一路只拉一次**，ZLM 向多客户端分发。摄像头侧连接数只跟「正在被拉流的设备数」有关，与观众数无关。这是整套架构最重要的一条收益，代价是出口带宽变成新瓶颈。

**Q3：WebRTC / FLV / HLS 为什么不全用 WebRTC？**
WebRTC 延迟最低但兼容性最脆（Safari 支持、部分安卓浏览器/企业代理不支持）。所以按「终端能力」降级，**HLS 作为终点兜底**——它延迟最高但几乎什么浏览器都认，只要它还在，用户就不会看到黑屏。

**Q4：分屏 16 路会不会把浏览器卡死？**
会，如果 16 个播放器同时活着。所以**分屏数就是实例数**：切到 4 屏时立刻 `close()` 另外 12 路的解码器。这是「演示能跑」和「值班能盯 8 小时」的分界。

**Q5：云台为什么不接厂商 SDK？**
接 SDK 就等于绑死品牌。ONVIF 的 `ContinuousMove / Stop` 是标准动作，换设备不用改代码。代价是要做能力探测，且不同厂商对速度参数解释有差异。

**Q6：录像为什么不全放数据库？**
MP4 是几百 MB 到几 GB 的大对象，放数据库会让备份、迁移、清理全部失控。**元数据进 MySQL（可检索），文件进 NAS/OSS（可分层）**，检索永远只查元数据，绝不扫目录。

**Q7：播放地址为什么不能直接给存储路径？**
一给就等于公开：URL 会被复制、外传、贴到群里。预签名 URL 把「谁、多久」编码进签名，1 小时自动失效，也不用为播放再造一套鉴权。代价是窗口内仍可能被转发，所以还要水印 + 调阅日志。

**Q8：下载为什么要做成异步任务？**
转码跑 FFmpeg、打包写 ZIP 都是分钟级。塞进 HTTP 请求必然被网关超时掐断——**演示正常、真实大文件必坏**。所以是「提交拿 taskId → 轮询进度 → 取件」，HTTP 只负责下单不负责干活。

**Q9：转码参数为什么用 ultrafast？画质不是很差？**
牺牲压缩率换实时性：`-tune zerolatency` 去 B 帧与前瞻，`-g 25`（1 秒一个关键帧）配合 **GOP 缓存**让新观众一秒内出画。监控场景**看得实时比看得精致重要**，而且录像质量可以由录制链路单独保证。

**Q10：100 个人同时看，CPU 怎么办？**
不是「100 个人 = 100 次转码」。同参数（码率/分辨率/编码）的流**复用同一个转码进程**，观众增加只增加分发连接，不增加 CPU。真正的 CPU 压力来自「多少路不同参数需要转」，所以还要优先 `-c copy` 直转。

**Q11：录像回放怎么做到「分钟级定位」？**
靠三件事叠加：**时间轴**（有录像上色、缺口可见）→ **告警高亮**（先看有事的）→ **倍速 + ±30s**（几倍速扫一遍再微调）。关键是把「几十小时」的搜索空间收敛到「有告警的几分钟」，而不是换个更好的播放器。

**Q12：跨片段播放时间轴会跳，怎么解决？**
进度按**绝对时间**算，不按文件内偏移算。按偏移算，一换文件就归零，用户以为录像丢了——这是回放里最容易被忽略的一处。

**Q13：这套系统的技术债是什么？**
最实在的两条：① 续传示例代码取错了 `Range` 头（拿的是响应头），按原样写**断点续传不生效**；② `Runtime.exec` 拼接命令有注入与进程失控风险。架构层面还有单机无 HA、并发观看带宽缺口、元数据与文件无一致性校验（§12）。
