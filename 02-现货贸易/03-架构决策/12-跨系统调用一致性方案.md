# 跨系统调用一致性方案（本地事务 + 异步派发 + 阶梯重试）

> **一句话**：用一个**本地事务**把"要通知下游"这件事记成一条**本地数据**，剩下的跨系统调用全部交给**异步线程**去重试。本方案不追求强一致，追求的是——**最终一定会通知到；通知不到，就一定有人知道**。

## 0 一句话总览

| 问题 | 本方案的答案 |
|---|---|
| 一次业务要同时通知资金 + 仓单，怎么保证都通知到？ | 不保证"同时成功"，只保证**每条通知最终被确认**；确认不了就报警交给人 |
| 本地事务和远程调用怎么兼得？ | 本地事务只管本地（业务表 + 待发送表），**远程调用一律挪到事务提交之后** |
| 远程调用失败怎么办？ | **阶梯退避重试**（1s→2s→4s…），上限 **N** 次，超限即**熔断为"待人工"** |
| 用户要不要等？ | 不等。事务提交即返回"受理成功"，业务状态由异步段推进 |
| 重试会不会重复扣款 / 重复过户？ | 不会——前提是**每次派发都带业务幂等键**，下游按幂等键去重（这是本方案的地基） |
| 多实例集群会不会重复派发同一条记录？ | 不会——派发线程先取**全局唯一批次号**，用**一条带批次号的 UPDATE 原子认领整批**，此后回写只认自己批次内的记录（见 §3.3） |

**适用边界**：可以由"回调/重试"补救、允许分钟级最终一致的跨系统通知。若监管要求强一致（如资金扣划必须与账务同秒一致），本方案不适用，要走 TCC 或由下游提供可对冲接口。

## 1 场景与三个假想敌

**样例：合同中心「确认收货」**。一次确认收货要同时通知两个模块：

- **资金模块**——买方货款解付 / 卖方可用余额增加；
- **仓单模块**——仓单过户 / 释放质押。

最朴素的写法是"两次 RPC 串行调，都成功才算成功"。这个写法会撞上三堵墙：

| 坑 | 具体表现 | 为什么不能硬扛 |
|---|---|---|
| **① 本地事务跨不了库** | 合同状态在合同库，资金在资金库，仓单在仓单库 | 2PC/XA 代价高、可用性差，且下游未必支持；把三个库塞进一个事务，等于让整条链路被最慢最不稳的那个拖死 |
| **② 超时 ≠ 没执行** | 资金接口超时，但它其实已经入了账 | 直接重试 → 重复入账；不重试 → 状态不一致。**分布式调用里"不确定的失败"比"确定的失败"危险得多** |
| **③ 部分成功** | 资金成功了、仓单失败了 | 资金已入账不能回滚，业务已经"半只脚"迈出去，只能往前走（重试），不能往后退（补偿） |

> ⚠️ 坑 ③ 是这条链路真正的命门。**本方案因此把"重试"当作一等公民而不是异常分支**——只要重试是幂等的，部分成功就只是一个"还没重试到"的中间态。

## 2 方案骨架：三段式

| 段 | 触发时机 | 参与者 | 一致性要求 | 失败应对 |
|---|---|---|---|---|
| **同步段** | 用户点击"确认收货" | 界面端 / 合同中心 / 本地库 | **强一致**（单库本地事务） | 事务回滚，直接把错误抛回界面 |
| **异步段** | 本地事务提交之后 | 异步派发线程 / 资金 / 仓单 | **最终一致** | 阶梯退避重试，≤ N 次 |
| **兜底段** | 重试次数超限 | 派发线程 / 运营 / 界面端 | 人工兜底 | 告警推送运营 + 界面端手动重试 |

### 核心不变量（四条，缺一不可）

1. **业务数据变更**与**待发送记录写入**在**同一个本地事务**里——要么都在，要么都不在；
2. **远程调用一律发生在事务提交之后**——事务里不出现任何 HTTP / RPC / MQ 发送；
3. **远程调用必须带业务幂等键**，且下游按幂等键去重——这是重试能被允许的**唯一前提**；
4. **每次派发先取一个全局唯一批次号**，整批记录共享该号，认领、回写、回收一律以批次号为范围——这是多实例不打架、宕机可整批恢复的前提（见 §3.3）。

> 第 3 条不成立时，前两条做得再漂亮也白搭：重试会把资金重复入账。所以**接入任何新下游前，先确认它幂等**；不幂等的下游，先在中间加一层"去重表 + 状态查询"，再谈重试。
>
> 第 4 条不成立时（比如拿单机内存自增当批次号），**单实例看不出问题，一上集群就撞号、就重复派发**——这类问题最贵，因为它只在生产扩容那一刻才暴露。

## 3 关键机制细则

### 3.1 本地事务边界（判定清单）

**必须进同一个本地事务：**

- [x] 业务主表的状态与数量变更（合同状态、已收货数量）；
- [x] 「待发送第三方表」的记录写入（**一条下游 = 一条记录**）；
- [x] 与本次业务同源的本地流水 / 操作日志。

**绝不能进事务：**

- [ ] 任何远程调用（HTTP / RPC / MQ 发送）；
- [ ] 依赖下游返回值才能确定的字段（"下游单号"这类字段只能回填，不能在同步段写死）；
- [ ] 通知类副作用（短信、站内信、消息推送）——它们是异步段的产物，不是业务的前置条件。

**一句话判据：事务里只写自己库里的表。**

### 3.2 「待发送第三方表」字段规则表

| 字段 | 作用 | 规则 |
|---|---|---|
| 业务单号 | 与业务主表关联、幂等键组成部分 | 必须，且建索引 |
| 目标系统 | 资金 / 仓单 / … | **一条下游一条记录**，不要一条记录里塞两个下游 |
| 业务动作 | 确认收货 / 解付 / 过户 | 决定下游做什么，与目标系统共同构成语义 |
| **幂等键** | 下游去重依据 | 全局唯一，建议 `业务单号 + 目标系统 + 业务动作` |
| 状态 | 待发送 / 发送中 / 成功 / 待重试 / 待人工 / 已闭环 | 见配套 **图 2** |
| 重试次数 | 已尝试次数 | 每次失败 +1，用于熔断判定 |
| 下次可派发时间 | 阶梯退避的落地点 | 失败后写 `当前时间 + 本次退避时长`；扫描器只捞"≤ 当前时间"的 |
| 最近失败原因 | 排障与告警内容 | 保留下游返回码 + 报文摘要，别只留一句"失败" |
| 认领标识 / 认领时间 | 多实例互斥 + 宕机回收 | 认领超时按"未认领"重新可捞 |
| **派发批次号** | 一次派发周期的身份、统一批次的凭据 | 每次扫描/认领生成一个**全局唯一**批次号，整批共享；回写、回收都以它为范围（细则见 §3.3） |

**设计要点（踩过的三类坑）：**

- **一条下游一条记录**——两个下游进度互不阻塞。如果合并在一条记录里，资金成功、仓单失败时，这条记录到底是成功还是失败？
- **必须有"状态 + 下次可派发时间"的联合索引与批量上限**——否则扫描会退化成全表扫，量一大就把库拖垮。
- **成功记录要归档**——这张表是"写多读多"的表，不做清理会无限膨胀；归档策略要在设计时就写进方案。

### 3.3 派发批次号（batchNo）：统一批次 + 多实例安全

**一句话**：异步线程每扫描一批，先**取一个全局唯一批次号**，再**用它一次性把整批记录认领下来**——这一批就构成一个**统一批次**；此后所有回写、重试、回收都以这个批次号为范围。

**为什么需要它（四个理由）**

| 理由 | 说明 |
|---|---|
| **多实例不重复派发** | 集群里多个实例同时扫同一张表。没有批次号，认领只能逐条竞争——A 实例捞了记录 1、3，B 实例捞了 2、4，谁发了谁没发就说不清。有了批次号，认领变成**一次批量 UPDATE**，天然互斥：一条记录只会落进某一个批次 |
| **宕机可整批恢复** | 实例挂了，记录卡在「发送中」。按**批次号**可以整批定位并回收（这一批正是它这次认领的），比「按认领时间一条条猜」精确得多 |
| **回写有明确边界** | 一次派发周期结束时，回写「成功 M 条 / 失败 K 条 / 耗时」直接按批次号聚合，不用额外关联 |
| **可观测、可对账** | 日志、埋点、对账都以批次号为线索串起来——**这个批次发了什么、结果如何**，一眼可查 |

**怎么生成（规则表）**

| 项 | 规则 |
|---|---|
| 唯一性 | **全局唯一**、跨实例不撞号。用数据库序列 / 雪花 ID；**不要用单机内存自增**——单实例看不出问题，一上集群必撞号 |
| 含实例标识 | 推荐把机器号 / 实例 ID 编进批次号（或另存一列），便于定位「这批是哪台机器处理的」 |
| 生成时机 | **在认领之前取号**——因为认领语句本身要用它做归属标记 |
| 粒度 | **一次扫描一个号**（例如一次捞 100 条，共享一个号），不是一条记录一个号 |

**怎么用（保证「统一批次」的关键动作）**

认领必须是**一条带批次号条件的批量 UPDATE**：

1. **取号**：`batchNo = 取全局唯一序号()`；
2. **批量认领**——同一条 SQL 完成「改状态 + 打号 + 记认领时间」，它影响的行就是本批次：
   - 条件：`状态 = 待发送` 且 `下次可派发时间 ≤ 当前时间`；
   - 动作：`状态 = 发送中`、`batch_no = 本批次号`、`认领时间 = 当前时间`；
   - 带批量上限（如 `LIMIT 100`），避免一次捞太多把库拖住。
3. **后续写操作只认自己的号**：回写成功、累加重试次数、记录失败原因，条件里都带 `batch_no = 本批次号`（可与幂等键叠加）。

> **判据**：认领是不是原子的，取决于「改状态」和「打批次号」是不是**同一条 SQL**。拆成两条做，等于把并发窗口重新打开——这是最容易踩的一个坑。

**批次号的收尾与继承**

| 场景 | 处理 |
|---|---|
| 批次内全部结束 | 记一条**批次执行摘要**（成功 / 失败 / 耗时）供观测，批次结束 |
| 批次内仍有未结束记录 | 批次保持「进行中」，未结束的记录按各自状态继续流转 |
| 实例宕机 | 按**认领超时**判定：超过「下游最大超时」仍未结束，就把该批次的「发送中」记录**整批回收**为「待重试」 |
| 重试时 | **重试是一次新的派发动作 → 取新批次号**；记录上只保留「当前批次号」（覆盖），历史批次另存批次流水，需要时可按业务单号串起来 |

**与分布式锁的关系**：批次号认领靠的是数据库的**条件更新 + 行锁**，它本身就是一次原子互斥操作，**不需要再引入 Redis / ZooKeeper 分布式锁**。只有在库不支持可靠条件更新时，才退回「分布式锁 + 批量认领」——而那时锁会成为新的单点，只作降级方案。

**单实例 → 集群的迁移路径**：**即使现在只跑一个实例，也先按批次号来做**（取号 → 带号认领 → 回写只认自己的号）。这样将来加实例就是「直接加」，派发逻辑一行不用改——批次号是**提前为集群买好的保险**。

### 3.4 派发器怎么工作（决策树）

- **多实例同时扫同一张表怎么办？**
  - 记录能被原子地「改状态 + 打批次号」→ 用**带批次号的批量认领**（`待发送 → 发送中` 并在同一条 SQL 里写入 `batch_no`），天然互斥，**首选**（细则见 §3.3）；
  - 库不支持可靠条件更新、又想简单 → 用**分布式锁 + 批量认领**，但锁本身成了新的单点，只作降级方案。
- **认领了但线程挂了怎么办？**
  - **不要**把「发送中」当终态 → 扫描器按**认领超时**把僵死记录回收成「待重试」（可结合批次号整批定位，见 **图 2**，状态机里因此没有独立的「僵死」态）；
  - 认领超时时间要 **大于** 下游接口的最大超时时间，否则会出现"还在重试中就被别人抢走"。
- **事务提交后要不要主动踢一脚线程？**
  - 要。**定时扫描兜底 + 提交后主动唤醒**：主动唤醒负责"快"（秒级），定时扫描负责"不漏"（进程重启、唤醒丢失都能捞回来）。

### 3.5 幂等（规则表）

| 层级 | 做法 | 说明 |
|---|---|---|
| 幂等键怎么选 | `业务单号 + 目标系统 + 业务动作` | 不要用时间戳、不要用自增 ID 拼随机数——同一笔业务重试必须算出同一个键 |
| 下游已支持幂等 | 直接带键调用 | 最省事，接入新下游时优先确认这一点 |
| 下游不支持幂等但支持查询 | 调前先查状态，已处理则跳过 | 存在"查完还没处理、调过去已处理"的竞态窗口，只能缩小不能消除 |
| 下游既不幂等也不能查 | **先在合同中心加一层去重表**（键 + 处理结果） | 用本地去重表兜住重试；同时推动下游改造，这是技术债不是方案 |

> **判据**：一个下游如果说不清"同一笔请求重复发一次会怎样"，那它就不具备接入本方案的条件。

### 3.6 阶梯重试（规则表）

| 项 | 规则 |
|---|---|
| 退避方式 | 阶梯递增：**1s → 2s → 4s → 8s → …**（按已重试次数取 2 的幂，可设单次上限如 1 分钟） |
| 重试上限 | **N 次**（N 由业务容忍时长倒推，本方案不写死；写死的是"必须有上限"这件事） |
| 超限动作 | **不再自动发送**，状态置"待人工"，推送运营（站内信 / 工单） |
| 哪些错误**该**重试 | 网络超时、下游 5xx、下游限流、下游明确返回"稍后重试" |
| 哪些错误**不该**重试 | 参数校验失败（4xx / 业务码拒绝）、下游明确返回"业务不允许"——**这类错误重试 N 次也只是浪费 N 次**，应直接置"待人工"并附上原因 |
| 是否需要抖动 | 需要。同一批记录同时失败时会形成"重试风暴"，退避时长加 ±20% 随机抖动 |
| 是否要告警 | 要。**告警阈值应低于熔断阈值**：重试到一半就该有人知道，而不是等熔断才喊 |

> **为什么用阶梯而不是固定间隔**：阶梯退避在"下游抖动几秒"时能快速自愈（第 1、2 次就成功），在"下游真挂了"时又不会把请求量堆成雪崩（后期间隔拉长）。

### 3.7 人工介入与界面重试（规则表）

| 项 | 规则 |
|---|---|
| 触发条件 | 重试次数 ≥ N，状态置"待人工" |
| 通知谁 | 相关运营人员（按目标系统分派：资金问题给资金运营，仓单问题给仓储运营） |
| 通知内容 | 业务单号 + 目标系统 + 已重试次数 + 最近失败原因（**够运营一眼判断，不用再查库**） |
| 运营能做什么 | ① 线下处理后标记"已闭环"；② 判断是系统问题 → 点"重启派发"回到"待发送" |
| 界面端重试 | **是兜底，不是主路径**：把记录重置回"待发送"重新入队，**不产生第二笔业务** |
| 防滥用 | 手动重试要有权限控制与操作留痕（谁、什么时候、对哪条记录重试过） |
| 必须闭环 | "待人工"不是终态——要么被重试回"待发送"，要么被人工置"已闭环"，**不允许长期悬浮**（做超时提醒） |

### 3.8 订阅消息：同一个范式的入站版本

订阅消息（入站）与派发调用（出站）**共用一套范式**，只是方向相反（见配套 **图 3**）：

| 维度 | 出站：派发调用 | 入站：订阅消息 |
|---|---|---|
| 触发 | 本地业务动作（用户确认收货） | 外部事件到达（到货通知 / 支付结果） |
| 第一步 | 业务表 + 待发送表，**同一个本地事务** | 消息**先落本地库**（订阅落库表），再 ACK |
| 第二步 | 异步线程扫描待发送表 | 异步线程扫描订阅落库表 |
| 幂等依据 | 业务幂等键 | **消息 ID 唯一索引**（天然去重） |
| 失败处理 | 阶梯重试 → 熔断 → 人工 | 同样的阶梯重试（**不阻塞 MQ 位点**，否则一条坏消息会卡死整个消费组） |
| 为什么先落库 | 保证"要发的一定发得出去" | 保证"收到的一定不丢、重复的一定不重" |

> **两条通道的共同点**：都用**一次本地事务**换掉**一次跨系统动作**，把分布式问题收敛成单库问题。这也是本方案能被复用到"发布 / 撤销 / 退款 / 结算"等其它链路的原因。

## 4 失败矩阵（失败发生在哪一段，怎么处置）

| 发生位置 | 典型表现 | 处置 | 用户可见结果 |
|---|---|---|---|
| 同步段 · 本地事务内 | 写库失败、并发冲突 | 事务回滚，报错返回 | 明确失败，可重试（不会产生半成品数据） |
| 同步段 · 事务已提交、异步未派发 | 进程宕机 | 无需处理——记录还在"待发送"，扫描器自然捞起 | 受理成功，稍后完成 |
| 异步段 · 下游返回失败 | 资金拒绝、仓单校验不过 | 阶梯重试 → ≤ N 次 → 熔断"待人工" | 受理成功，但状态停在"处理中"，运营介入 |
| 异步段 · 调超时 | 不确定是否已执行 | **按幂等重试**，不许"猜" | 同上 |
| 异步段 · **部分成功** | 资金成功、仓单失败 | **只对失败的那条记录重试**，已成功的记录不动（这是"一条下游一条记录"的价值） | 同上 |
| 异步段 · 线程宕机 | 记录卡在「发送中」 | 认领超时回收 → 「待重试」（按批次号可整批定位） | 同上 |
| 异步段 · 多实例并行 | 两个实例同时扫同一批记录 | **批次号 + 批量认领天然互斥**：一条记录只归一个批次，不会重复派发 | 无影响 |
| 兜底段 | 重试超限 | 告警运营 + 界面端可手动重试 | 用户可在页面看到"待处理"并提供重试入口 |

> **部分成功为什么不需要补偿**：因为两个下游的动作在业务语义上是**可独立完成**的（资金解付 ≠ 必须与仓单过户原子绑定）。判断标准是：**这两个动作里，有没有哪一个单独完成会造成业务上不可接受的后果**。有 → 别用本方案，去用 Saga 编排 + 显式补偿；没有 → 本方案最省事。

## 5 方案选型对比

| 方案 | 一致性 | 对下游的要求 | 复杂度 | 适用 |
|---|---|---|---|---|
| 2PC / XA | 强一致 | 必须支持 XA、必须能长期持锁 | 高 | 同构数据库间、强一致刚需场景 |
| **TCC** | 强一致（业务级） | 每个下游都要实现 Try/Confirm/Cancel | 很高 | 资金扣划这类不容忍中间态的场景 |
| **Saga 编排** | 最终一致 + 显式补偿 | 每个环节都要有**可对冲**的补偿动作 | 高 | 多步骤、且其中某步不做完业务上不可接受 |
| **本地事务 + 异步派发（本方案）** | 最终一致，**无补偿** | 下游**幂等**即可 | 低 | 多下游通知、动作可独立完成、允许分钟级延迟 |
| 最大努力通知 | 弱 | 下游自己回调确认 | 最低 | 通知类、丢了也勉强能接受 |

**选型判据（三连问）：**
1. 下游动作之间**必须原子**吗？→ 必须 → 排除本方案，走 Saga / TCC。
2. 每个下游**幂等**吗？→ 不幂等 → 先解决幂等，再谈本方案。
3. 业务能容忍**分钟级延迟**吗？→ 能 → 本方案落地成本最低、最不容易在生产上出事。

> 本方案与 Saga **不是竞争关系**：Saga 处理"必须补偿"的长事务，本方案处理"不需要补偿、只需送达"的通知。真实系统里常常两者并存——**Saga 的某一步内部，用的就是本方案**。

## 6 落地检查清单（自查表）

**同步段**
- [ ] 业务变更与待发送记录确实在同一个本地事务里（不是"先提交业务、再插记录"）
- [ ] 事务里没有任何远程调用
- [ ] 事务提交完成后才返回"受理成功"（不是提交前）

**异步段**
- [ ] 一条下游一条记录，没有"一条记录多个下游"
- [ ] 幂等键 = 业务单号 + 目标系统 + 动作，且重试时**算出的是同一个键**
- [ ] 扫描走"状态 + 下次可派发时间"索引，且有批量上限
- [ ] 每次派发先取**全局唯一批次号**（跨实例不撞号），且「改状态 + 打批次号」在同一条 UPDATE 里完成
- [ ] 回写、重试计数、僵死回收都带 `batch_no` 条件，不越界改别的批次
- [ ] 批次号包含（或另存）实例标识，能定位「这批是哪台机器处理的」
- [ ] 多实例下有原子认领，且认领超时 > 下游最大超时
- [ ] 定时扫描兜底 + 提交后主动唤醒，两条路都在
- [ ] 退避是阶梯 + 有抖动 + 有上限 N
- [ ] "不该重试的错误"被单独识别，不占用 N 次额度

**兜底段**
- [ ] 熔断会上报运营，且告警阈值低于熔断阈值
- [ ] 告警内容自带业务单号与失败原因，运营不用再查库
- [ ] 界面端有重试入口，且**只重置记录、不新建业务**
- [ ] "待人工"有超时提醒，不允许长期悬浮
- [ ] 成功记录有归档/清理策略

**验证**
- [ ] 用"下游人造超时"验证过不会重复入账（幂等真的生效）
- [ ] 用"杀进程"验证过宕机后记录能被回收重派
- [ ] 用「起两个实例并发跑」验证过同一条记录不会被两个批次重复派发
- [ ] 用"关掉下游"验证过熔断与告警真的会来
