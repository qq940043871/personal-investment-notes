# DS 数据交换中心设计说明书 —— C↔Java 异构协议桥接与高并发

> **一句话**：DS 数据交换中心（内部俗称"数据交换 / data exchange"）是 **C 撮合引擎与 Java 业务中台之间的防腐层与翻译官**——把 C 侧的 TCP Socket 二进制帧和 Java 侧的 Hessian over HTTP 互译成一套统一报文，让两种语言、两种进程模型各自演进；高并发的答案不是"堆连接"，而是**IO 模型 + 有界背压 + 分片并行 + 批量落库**四件事，端到端天花板在下游 DB（单机 1~3 万 TPS），接入层可到 10 万级 QPS。

> **口径**：本文属**公司项目轨道**，与 `11-midservice网关职责与治理设计.md`（入口侧）、`12-跨系统调用一致性方案.md`（Java 侧出口）、`13-C核心单线程内存一致性设计.md`（C 侧心脏）构成**「公司项目一致性四件套」**——11 管"谁能进"、12 管"必须送达"、13 管"内存一致"、**本文管"两种语言怎么对上话"**。术语口径见 §1.2。

## 0 一句话总览

| 问题 | 本设计的答案 |
|---|---|
| C 说 Socket、Java 说 Hessian+HTTP，谁迁就谁？ | **谁都不迁就**——DS 做双向适配，C 团队与 Java 团队各自独立演进（§1） |
| 两条通道怎么分工？ | **同步指令走 Hessian over HTTP**（要结果），**异步交换走 Socket 长连接**（要吞吐），共用一套协议内核（§1.2） |
| 高并发第一课是什么？ | **先算账再选型**：先估峰值业务量，再定单节点能力与节点数，不过度设计（§3） |
| 单机能扛多少并发连接？ | 10 万级（epoll / Netty 上限），但内部交换场景**实际只有几十~几百条**——连接数从来不是瓶颈（§5.1） |
| 单机能扛多少吞吐？ | 小报文 10~30 万条/秒；含落库的端到端 **1~3 万条/秒**（§5.2） |
| 集群能扛多少？ | 3~5 节点：接入层 30~100 万 QPS，端到端 3~10 万 TPS（§5.4） |
| 瓶颈通常在哪？ | **下游 DB 写入**，不是 DS 本身——接入层扩容治不好 DB 打穿（§5.3，呼应 `生产问题排查/11`） |
| 怎么保证消息不丢不重？ | ACK + 序号 + 去重 + **本地待发送表 + 批次号认领** + 阶梯重试 + 死信人工兜底（§6，与 12 号同范式） |
| C 是单线程撮合，DS 会把它堵死吗？ | **不会**——DS→C 只写无锁队列，C 按自己节奏消费；DS 读 C 的 Socket 用独立 IO 线程（§4.2） |
| 流量突增怎么办？ | **有界队列 + 高水位三级处置**（正常 / 告警 / 拒绝或转落盘）——宁可明确拒收，不堆到 OOM（§4.4） |

**适用边界**：内部系统间（C 撮合 ↔ Java 中台）的中等规模交换。日均消息量百万级以下、峰值 QPS 万级以内，3~5 节点覆盖。若目标是互联网 C 端海量长连接（百万级），需另做接入层专项（连接网关 + 无状态扇出），本文的协议内核与可靠性机制仍可复用。

## 1 定位与边界：这个"翻译官"到底在翻译什么

### 1.1 两边说的是什么"方言"

| 维度 | C 侧（撮合引擎） | Java 侧（业务中台） |
|---|---|---|
| 通信方式 | **TCP Socket 长连接**，自研二进制帧 | **Hessian over HTTP**（同步调用） |
| 序列化 | 紧凑二进制（定长头 + TLV） | Hessian 二进制 RPC |
| 进程模型 | **单线程事件循环**（撮合线程绝不阻塞，见 13 号 §3） | 多线程微服务（12+ 服务） |
| 擅长 | 确定性时延、纳秒级撮合 | 业务编排、生态丰富 |
| 短板 | 没有 RPC 框架、没有对象模型 | GC 停顿、时延不确定 |
| 对对方的期待 | "别让我等你" | "别让我懂你的内存布局" |

> **核心矛盾**：C 的世界里**没有"调用"只有"消息"**，Java 的世界里**万物都是对象与方法**。直接对接 = 让业务开发懂 C 的内存布局，或让 C 团队懂 Java 的 RPC 语义——两边都被对方绑死。**DS 的存在就是把"异构"收敛到一个点**：业务侧看到的是标准 Java 服务，C 侧看到的永远是它熟悉的 Socket 帧。

### 1.2 两条通道：线上同步调用 vs 线下异步交换（术语口径）

本文按"要不要结果"把交换分成两条通道——**这也是回答"线下数据交换"是什么的口径**：

| | **线上同步调用** | **线下数据交换**（本文重点） |
|---|---|---|
| 方向 | Java → C（指令为主） | C → Java（回执 / 行情 / 对账 / 批量）为主，双向都有 |
| 通道 | **Hessian over HTTP** 请求-响应 | **Socket 长连接**（异步、可补传） |
| 典型报文 | 下单 / 撤单 / 查订单簿 | 成交回执、行情快照、日终对账、批量同步 |
| 语义 | 调用方**等结果**，超时要明确 | 发送方**不等结果**，靠 ACK 与补传保证送达 |
| 时延要求 | 毫秒级（P99 < 20ms） | 秒级~分钟级（批量窗口 50~200ms） |
| 失败处理 | 同步返回错误，调用方决定重试 | 本地待发送表 + 阶梯重试 + 死信（§6） |
| 一致性依据 | 接口幂等（引用 11 号入参契约） | **12 号待发送表范式**（§6.2） |

> **口径说明**：本文"线下数据交换"指**面向异步、批量、可补偿的内网交换通道**（与"线上同步调用"对偶）。若团队内部"线下"另有确指（如某条具体业务线），以团队口径为准——本文的协议设计、并发手段、容量测算与命名无关，机制部分全部适用。
>
> **为什么同步用 Hessian over HTTP、异步用 Socket**：请求-响应语义 HTTP 天生具备（状态码、超时、重试都现成）；高频回执 / 行情走 Socket 长连接，省掉反复建连与 HTTP 头开销，且 C 侧本来就"只会说"Socket。**选型跟着语义走，不是跟着潮流走。**

### 1.3 DS 的四件事

1. **协议转换**：C 二进制帧 ⇄ Hessian 对象 ⇄ 统一报文（§2）
2. **路由分发**：按接口编码 / 租户 / 品种路由到目标服务或 C 实例，按分片键保序（§4.7）
3. **可靠性落地**：ACK、去重、待发送表、重试、死信——把"不可靠的网络"包成"可追责的交付"（§6）
4. **可观测**：连接、队列深度、时延、重试率全量上报（§8）

### 1.4 边界清单（DS 不做什么）

| DS **做** | DS **不做**（谁做） |
|---|---|
| 协议互译、统一报文封装 | 业务规则校验（网关 11 号 + 各业务服务） |
| 路由与分片 | 事务编排（Saga 编排器，见 `05-Saga编排器详细介绍.md`） |
| 交换侧可靠性（送达保证） | 撮合与内存一致性（C 核心，13 号） |
| 内部通道限流与隔离 | 三端入口治理（midservice 网关，11 号） |
| 交换审计与 traceId 透传 | 持久化权威（各业务库；DS 只写待发送类本地表） |

> **一句话边界**：DS 是**翻译官 + 邮差**，不是**法官**（不判业务对错）也不是**账房**（不做权威账本）。

## 2 协议设计：让两种语言对上话

### 2.1 C 侧 Socket 帧格式（定长头 + TLV body）

帧 = **定长头（固定 32 字节）** + **TLV Body**。定长头让 C 侧一次读满即可解析；TLV 让字段增删不破坏兼容。

**定长头字段表**：

| 字段 | 长度 | 说明 |
|---|---|---|
| 魔数 magic | 2B | 帧起始校验，错位立即断开（防脏数据污染流） |
| 版本 version | 1B | 帧格式版本，升级期双版本并存 |
| 帧类型 type | 1B | 指令 / 回执 / 行情 / 心跳 / ACK / 对账 |
| 负载长度 length | 4B | Body 字节数，**上限强制校验**（如 8MB），超限拒绝——防内存攻击的第一道关 |
| 报文序号 seq | 8B | 连接内单调递增，ACK 与去重都靠它 |
| 时间戳 ts | 8B | 发送方毫秒时间戳，用于时延统计与乱序检测 |
| 业务编码 bizCode | 4B | 接口唯一编码（与 11 号"接口编码 = 协议唯一编码"口径一致） |
| 分片键 hash | 2B | 路由用（§4.7） |
| 保留 reserved | 2B | 对齐与扩展 |

**Body 用 TLV**：Type(2B) + Length(4B) + Value。好处是**加字段不用改版本**——老解析器跳过不认识的 T，新解析器照常读。

> **判据**：字段会频繁增删（业务在长）用 TLV；字段永久固定（协议内核）才用定长。

### 2.2 Java 侧 Hessian over HTTP

| 设计点 | 规则 |
|---|---|
| 连接管理 | **长连接池 + keep-alive**，按目标 C 实例分组；禁止每次调用新建连接（建连成本 ≈ 一次调用本身） |
| 超时 | 分级：连接超时 < 读超时；读超时按接口重要度设（指令类 1~3s，查询类 500ms） |
| 序列化 | Hessian2（二进制，体积小、编解码快，见 §4.9） |
| 错误映射 | 网络错 / 超时错 / 业务错**三类分开返回**——调用方要知道"该不该重试"（网络错可重试，业务错重试无意义） |
| 幂等键 | 每次调用带 requestId，C 侧与 DS 双重去重（§6.1） |

### 2.3 统一内部报文（header + body + signature + traceId）

所有通道进来先译成**统一报文**再路由——这是"一次对接、处处可用"的本体：

| 段 | 字段 | 说明 |
|---|---|---|
| header | requestId / source / target / version | 请求 ID（幂等键）、来源、目标、接口版本 |
| header | traceId | **全链路透传**（网关 → DS → C → 回执），排障时一把串联（§8） |
| body | action + data | 业务动作 + 数据（TLV / Hessian Map 承载） |
| signature | 签名 | 内网也要签：防内部误连、防重放（时间窗校验） |

> **版本兼容规则**：接口编码 + 版本号唯一确定一份契约（引用 11 号"一处定义、四处生效"）；升级期**双版本并行**，按 version 字段路由到不同处理器，观察一个周期再下掉老版本。

### 2.4 编解码放在哪一层

**铁律：编解码在 IO 线程完成，业务处理才进业务线程池。**

理由：编解码是纯 CPU 活，放 IO 线程可以与网络等待重叠；若落到业务线程，等于每条消息多两次调度切换。**代价**：IO 线程不能做任何可能阻塞的事（查库、调下游）——阻塞一个 IO 线程 = 阻塞一组连接。

### 2.5 与外部 9+ 接口的关系（一句带过）

DS 同时适配银行 / 物流 / CA 等外部系统（适配器模式隔离每家）。那些是**外网边界**，治理规则以 11 号网关与等保要求为准；本文只讲 **C↔Java 内网交换内核**——两者共用适配器框架，但安全等级不同（§7）。

## 3 高并发设计总纲：先算账，再选型

### 3.1 容量估算三步法

| 步骤 | 动作 | 产出 |
|---|---|---|
| ① 估业务量 | 日均消息量 × 集中度系数（开盘 30 分钟占全天 40~60%） | **峰值 QPS** |
| ② 定单节点能力 | 按瓶颈件取最小：min(CPU 编解码, 网卡, DB 写入)（§5.3） | **单节点天花板** |
| ③ 定节点数 | ⌈峰值 QPS × 安全系数 2 ÷ 单节点天花板⌉ | **集群规模** |

> **反模式警告**：跳过①直接选型 = 用互联网 C 端的标准（百万连接、分库分表）设计一个内部交换系统——**过度设计比设计不足更贵**（复杂度本身就是故障源）。大宗 B2B 的真实峰值通常只有几百~几千 QPS，留 2 倍余量足够。

### 3.2 三个数字先行

| 数字 | 量级 | 依据 |
|---|---|---|
| 并发连接 | 内部场景 **几十~几百条**长连接（双方实例数 × 通道数） | 这是系统间交换，不是 C 端接入 |
| 峰值吞吐 | **千级 QPS** 常见，万级需专项 | 日成交几千~几万笔 × 开盘集中度 |
| 端到端时延 | 同步 P99 < 20ms；异步 < 100ms | 交易指令不能等，回执可以等 |

### 3.3 五条总原则

1. **IO 线程不阻塞，业务线程有边界**（§4.1 / §4.2）
2. **队列必须有界，满了要明确处置**（§4.4）
3. **能批量就不单条**（§4.5）
4. **同键保序、异键并行**（§4.7）
5. **扩容治接入，治不了 DB**（§5.3）

## 4 高并发设计手段逐条展开

每条按 **手段 / 解决什么 / 代价 / 判据** 说清——**没有免费午餐，选型就是选代价**。

### 4.1 IO 模型：epoll + Reactor

| 手段 | 解决什么 | 代价 | 判据 |
|---|---|---|---|
| C 侧 epoll 事件驱动；Java 侧 Netty 主从 Reactor（boss 组 accept、worker 组 IO + 编解码） | 单线程管万级连接；连接海啸不崩 | 代码复杂度高（事件状态机） | **一连接一线程是自杀**——线程数随连接线性涨，上下文切换吃掉 CPU |

### 4.2 线程模型：对 C 单线程撮合的适配（本节是重点）

| 环节 | 做法 | 为什么 |
|---|---|---|
| DS → C | **无锁 SPSC 队列**（单生产者单消费者环形队列），DS 写、C 撮合线程读 | C 的命门是"撮合线程绝不阻塞"（13 号 §3）——**绝不能让它等 DS 的锁或等 DS 的处理** |
| C → DS | C 写输出队列，DS 用**独立 IO 线程**读 Socket | 读的动作在 DS 侧，C 只做"投递"，不等确认 |
| DS 内部 | IO 线程（编解码）→ 有界业务队列 → 业务线程池 | 编解码与业务处理分离，任一环慢不互拖 |
| 线程池 | **同步指令池与异步回执池隔离** | 回执洪水（开盘行情爆发）不能挤占指令通道 |

> **一句话**：DS 对 C 的所有动作都收敛成"**往一个无锁队列里放消息**"——这是 DS 能"管住"异构系统的前提，也呼应 02 号文档"不把 Java 写进 C 撮合引擎"的边界。

### 4.3 连接管理

- **长连接复用**：Hessian over HTTP 用连接池；Socket 长连接保活（心跳 30s，3 次无响应摘除）
- **空闲回收**：超过阈值（如 10 分钟）无报文的连接半关闭，防僵尸连接占 fd
- **慢连接隔离**：读缓冲区积压超限的连接单独标记、降速或断开，防一颗老鼠屎拖垮 IO 线程
- **fd 上限**：系统级调优（ulimit）+ 使用率 80% 预警

### 4.4 背压：有界队列 + 高水位三级处置

| 水位 | 现象 | 处置 |
|---|---|---|
| 正常（< 60%） | 消费速度 ≥ 生产速度 | 正常流转 |
| 告警（60%~80%） | 消费开始滞后 | 告警 + 记录滞后时长，人工关注 |
| 拒绝 / 转落盘（> 80%） | 持续积压 | **明确拒绝**（返回"系统忙"，让上游重试）或**转落盘**（可补偿消息走本地表） |

> **铁律：宁可明确拒收，不可无限堆内存。** 无界队列的结局是 OOM——**丢一条消息是事故，OOM 是全站停摆**。这也呼应 11 号网关"显式拒绝不做静默截断"的同一条纪律。

### 4.5 批量：小包合并 + 批量落库

| 场景 | 做法 | 收益 |
|---|---|---|
| 高频小报文（行情 / 回执） | 按时间窗（如 5ms）或条数（如 200 条）**合并发送** | syscall 次数与网络包数降一个量级 |
| 落库 | 多值插入 / 批量提交，**一个事务一批** | DB 往返从 N 次降到 1 次，TPS 提升数倍 |
| 判据 | 时延敏感报文（指令）不批量；吞吐敏感报文（回执 / 行情）才批量 | **批量换时延，时延换吞吐**，按报文类型分策略 |

### 4.6 内存与零拷贝

- **池化缓冲区**：网络缓冲区走池化分配（Netty ByteBuf 池 / C 侧环形缓冲复用），编解码路径**零临时对象**——GC 抖动是高并发的大敌
- **减少拷贝次数**：报文在 IO 线程解出头 → 直接路由 → 尽量不做"字节数组 → 对象 → 字节数组"的往返；只有需要落业务库的才转对象
- **堆外内存**：大报文缓冲区用堆外，避免大对象直接进老年代

### 4.7 分片并行：同键保序、异键并行

- **分片键**：业务单号 / 账户 / 品种 hash（与 §2.1 帧头 hash 字段联动）
- **规则**：同一分片键的消息**永远进同一个队列、同一个线程**——顺序性天然成立；不同分片键并行处理
- **分片数经验值**：2 × CPU 核数（够并行又不至于调度抖动）
- **路由一致性**：分片表在 DS 集群内一致（启动时加载 + 变更推送），保证同一键永远落到同一分片

### 4.8 无锁结构

- 入口队列用 **MPSC / SPSC 环形队列**替代锁队列（锁在争用时退化严重）
- 计数器、统计用 CAS 或线程本地累加后合并
- **判据**：只有争用极低的场景才用锁；队列这种热点必须无锁

### 4.9 序列化选型：为什么是 Hessian

| 协议 | 体积 | 编解码速度 | 跨语言 | 可读性 | 结论 |
|---|---|---|---|---|---|
| **Hessian（二进制）** | 小 | 快 | ✅ | ❌ | **跨语言边界主力**——撮合高频交互，开销低于文本协议 |
| JSON | 大 | 慢 | ✅ | ✅ | 只用于配置 / 低频 / 需人看的场合 |
| Protobuf | 最小 | 最快 | ✅（需 schema） | ❌ | 新系统可选；**存量 Hessian 不推倒**——迁移成本 > 收益 |

> **口径**：选 Hessian 不用 JSON，是因为**撮合是高频二进制交互**，序列化开销直接进时延预算（02 号文档同口径）。

### 4.10 隔离与限流

- **按租户 / 接口配额**（引用 11 号分级限流）：单个租户刷爆不能影响别人
- **线程池隔离**：指令池、回执池、对账池分开——不同报文类型的洪峰互不传染
- **慢下游隔离**：对下游（DB / 外部接口）的调用必须带超时与熔断，慢下游不能占满业务线程（引用 12 号熔断转人工）

### 4.11 JVM 与系统层

| 项 | 基线 |
|---|---|
| GC | G1 或 ZGC，目标停顿 < 50ms；编解码路径零临时对象（§4.6） |
| 堆 | 按连接数 × 每连接缓冲区估算，宁小勿大（大堆 = 长 GC） |
| 网卡 | 千兆 ≈ 小报文 10 万+/秒；万兆 ≈ 1 GB/s——**先算带宽再算并发** |
| sysctl | 连接数相关（backlog、tcp_tw_reuse、本地端口范围）按连接规模调 |

## 5 容量测算：到底能扛多少并发

> **先给结论**：这个系统**连接数从来不是瓶颈，吞吐的瓶颈在下游 DB**。接入层按 10 万级 QPS 设计都绰绰有余，端到端（含落库）单机天花板是 **1~3 万条/秒**——要更高就分片 + 批量 + 加节点，而不是优化 DS 本身。
>
> ⚠️ **数值口径**：本节所有数字为**设计基准经验值**（同机房内网、单节点、主流硬件），用于选型与面试陈述；**上线前以实测压测数据替换**（方法见 §5.6）。

### 5.1 并发连接数

| 场景 | 单机上限 | 本系统实际 |
|---|---|---|
| epoll（C 侧） | 10 万级长连接（受 fd 与内存约束） | 双方实例 × 通道 ≈ **几十~几百条** |
| Netty（Java 侧） | 10 万级长连接 | 同上 |
| Hessian HTTP 池 | 每目标实例数十条 | 同上 |

> **结论：连接数免测。** 内部系统间交换，连接数是常量不是变量——为它做任何专项设计都是浪费。

### 5.2 单节点吞吐分档（同机房内网）

| 档位 | 报文特征 | 单节点能力 | 瓶颈件 |
|---|---|---|---|
| A 纯转发 | ≤1KB，只编解码 + 路由 | **10~30 万条/秒** | CPU（单核约 5~10 万条/秒编解码） |
| B 含业务处理 | 1~10KB，进业务线程池 | **3~10 万条/秒** | 线程池 + 内存分配 |
| C 含落库 | 上述 + MySQL 写入 | **1~3 万条/秒** | **DB 写入（单机天花板）** |
| D 广播扇出 | 行情推多订阅方 | 5~10 万条/秒 | 网卡 + 订阅方最慢者 |

### 5.3 下游瓶颈表（端到端的真正天花板）

| 组件 | 单机天花板 | 说明 |
|---|---|---|
| **MySQL 写入** | **1~3 万 TPS** | 批量 + 多值插入可逼近 5 万，但受事务与索引影响；**这是端到端的墙** |
| Redis | 8~10 万 QPS | 去重 / offset 的承载，不是瓶颈 |
| 网卡 | 千兆 ~ 小报文 10 万+/秒 | 先算带宽：并发数 × 报文大小 × 每秒 = 带宽需求 |
| DS 自身 | 10 万级 QPS（§5.2 A 档） | 几乎不可能是瓶颈 |

> **血泪教训（库内有案）**：`生产问题排查/11-网关扩容打穿DB-性能开发规范.md`——**接入层扩容治不好 DB 打穿**。DS 集群加节点前，先确认下游 DB 的写入余量；否则只是把排队从 DS 挪到 DB。

### 5.4 集群规模与节点数公式

**节点数 N = ⌈峰值 QPS × 2（安全系数）÷ 单节点瓶颈能力⌉**

| 规模 | 接入层能力（A 档） | 端到端能力（C 档） | 适用 |
|---|---|---|---|
| 单节点 | 10~30 万 QPS | 1~3 万 TPS | 日常 |
| 3 节点 | 30~90 万 QPS | 3~9 万 TPS | 生产基线（1 节点维护时仍双活承载） |
| 5 节点 | 50~150 万 QPS | 5~15 万 TPS | 大促 / 开盘高峰预案 |

> **注意公式里的"单节点瓶颈能力"取 C 档（含落库），不是 A 档。** 用 A 档算节点数 = 造出一个被 DB 打穿的集群。

### 5.5 时延预算

| 链路 | P50 | P99 | 预算去向 |
|---|---|---|---|
| 纯转发（同机房） | < 0.5ms | < 2ms | 编解码 + 队列 + 路由 |
| 同步指令（Java→DS→C→回） | 2~5ms | < 20ms | + Hessian 编解码 + C 撮合 |
| 异步交换端到端 | 50ms 内 | < 100ms | + 批量窗口（50~200ms） |

### 5.6 压测方法与瓶颈判定树

**阶梯加压**：1k → 5k → 1万 → 5万 QPS，每档稳态 5 分钟，看哪个指标先翘：

| 先翘的指标 | 瓶颈 | 处置 |
|---|---|---|
| CPU 100% | 编解码瓶颈 | 加节点 / 降单条成本（批量、零拷贝） |
| 业务队列深度持续上涨 | 业务池不足 | 扩线程池 / 优化单条处理 |
| DB 连接池打满、慢 SQL 涨 | **落库瓶颈** | 批量合并 / 分库 / 降级非核心写入 |
| 网卡带宽饱和 | 网络瓶颈 | 升级网卡 / 压缩报文 / 就近部署 |
| GC 停顿陡增 | 内存瓶颈 | 修临时对象（§4.6）/ 调堆与 GC |
| 队列满触发拒绝 | 已达设计上限 | 按 §4.4 处置，这是**预期行为不是故障** |

### 5.7 面试口径（一句话答案）

> "**连接数 10 万级但内部场景根本用不满；接入层 10 万级 QPS；端到端 1~3 万 TPS，瓶颈在下游 DB。** 我们的做法是先按业务峰值算账（日均 × 开盘集中度），再按 min(CPU, 网卡, DB) 定单节点能力、留 2 倍余量定节点数——生产 3 节点基线，峰值远未触及设计上限。**不过度设计，但背压、限流、死信这些'满了怎么办'的机制一样不能少。**"

## 6 可靠性：不丢、不重、不乱

> DS 的交换可靠性**完全复用 12 号文档的范式**（本地待发送表 + 异步派发 + 阶梯重试 + 人工兜底），区别只在对象：12 号是 Java 侧业务系统之间，本文是 **C↔Java 异构通道**。02 号文档早已给出加固方向："给现有 Socket 加 ACK 层、用 Redis 做去重和 offset、加 Netty 心跳"——本节就是它的落地。

### 6.1 三层防重：ACK + 序号 + 去重

| 层 | 机制 | 说明 |
|---|---|---|
| 传输层 | **帧序号 + ACK** | 发送方未收到 ACK 按序号补传；连接内单调递增（§2.1） |
| 应用层 | **requestId 去重** | Redis SETNX（窗口内）+ 本地去重表（兜底 Redis 故障） |
| 业务层 | **幂等键** | 下游按业务单号 + 操作类型去重（引用 12 号核心不变量③） |

> **判据**：三层都要——传输层保"通道内不重"，应用层保"窗口内不重"，业务层保"永久不重"（补传可能跨天）。

### 6.2 待发送本地表 + 批次号认领（照搬 12 号 §3.3）

| 环节 | 规则 |
|---|---|
| 落 | 消息进入 DS **先写本地待发送表**（与发送动作同一事务边界），提交后才上通道 |
| 认领 | 派发前**先取全局唯一批次号**，一条带批次号的 UPDATE 原子认领整批（改状态 + 打号 + 记认领时间在同一条 SQL） |
| 范围 | 回写、重试计数、僵死回收**一律以 batch_no 为范围**；多实例各管各的批次，宕机可按批次整批回收 |
| 唯一 | 批次号全局唯一（序列 / 雪花 ID，**禁用单机内存自增**） |

### 6.3 顺序性：要序与不要序的判据

| 报文类型 | 要序吗 | 手段 |
|---|---|---|
| 同一订单的状态流转 | **要** | 同分片键 → 同队列（§4.7） |
| 成交回执之间 | 不要 | 乱序无害，下游按业务时间戳排序 |
| 行情快照 | 不要（只认最新） | 覆盖写，旧值自然废弃 |

> **判据一句话**：**同一业务单号的状态变化必须有序；不同单号之间、快照类数据可以不保序。** 为不需要序的消息保序 = 白白牺牲并行度。

### 6.4 阶梯重试与死信（同 12 / 13 号口径）

- **重试**：1s → 2s → 4s → …上限 N（N 不写死，只描述有上界），带抖动
- **熔断**：连续失败达阈值 → 熔断该通道，转人工 + 告警
- **死信**：N 次全失败 → 死信队列 + **运营界面重试**（只重放"发送"这一步，不重新生成业务——同 13 号"只重放回写、不重新撮合"的纪律）
- **对账**：定时（日终）比对 C 侧输出与 Java 侧落库，差异标红——**兜底的兜底**

## 7 安全与治理（内部通道的精简关）

内部可信 ≠ 不设防，但**关要比网关少**（11 号十道关的裁剪版）：

| 关 | 规则 |
|---|---|
| 接入认证 | 通道级证书 / 预共享密钥；陌生来源直接拒 |
| 签名与防重放 | 统一报文签名 + 时间窗（§2.3） |
| 负载长度硬限 | 帧长度上限强制校验（§2.1），超限即拒 |
| 限流 | 按租户 / 接口配额（§4.10） |
| 审计 | 全量 traceId + 关键操作留痕（§8） |
| 脱敏 | **DS 不做业务脱敏**——那是出口侧（网关 / 业务服务）的职责（11 号输出白名单） |

**密码算法选型（与 11 号 §7.3 同口径）**：

> 内部通道可信 ≠ 不设防，但**算法选型与 11 号网关保持一致**：等保三级优先国密，RSA 兼容外部/存量。

| 用途 | 国际算法（兼容） | 国密算法（合规主选） | 内部通道落点 |
|------|----------------|---------------------|-------------|
| 通道认证 / 签名 | RSA | **SM2** | §2.3 signature、通道级证书 |
| 哈希 / 摘要 | SHA-256 | **SM3** | 报文防篡改摘要 |
| 对称加密 | AES-GCM | **SM4** | 敏感报文加密（如需） |

> 签名验签由密码设备完成，私钥不进 DS 实例；DS 只持"用哪个密钥"的索引，密钥由 **KMS / 密码机（HSM）** 托管——同 11 号密钥管理口径。

## 8 可观测性：看什么指标

| 指标 | 告警线 | 说明 |
|---|---|---|
| 连接数 / fd 使用率 | 80% | 逼近上限前扩容或回收 |
| 队列深度（各分片） | 持续 > 60% 水位 | 消费滞后（§4.4） |
| 端到端时延 P50 / P99 | P99 超预算（§5.5） | 慢协议预警（呼应 midmon 双条件：值 + 持续性） |
| 重试率 / 死信增量 | 死信 > 0 即告警 | 死信必须有人看，不能静默 |
| ACK 超时率 | > 1% | 通道质量劣化 |
| DB 写入 TPS / 慢 SQL | 逼近 §5.3 天花板 | **端到端瓶颈的先行指标** |
| traceId 串联 | — | 排障主线：网关 → DS → C → 回执一把串 |
