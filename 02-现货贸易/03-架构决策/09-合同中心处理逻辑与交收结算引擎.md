# 09 · 合同中心处理逻辑与交收结算引擎

> **用途**：回答"合同中心到底怎么处理一笔交易的履约与结算"。这是大宗交易平台区别于普通电商最硬的一块，也是追问最深、最容易露馅的一块。
> **口径标注**：`【源文档】` = 源自项目设计源文档 `01-design/scenarios/`（合同中心 / 业务场景分析，15 个 HTML）；`【总纲口径】` = 与顶层 `CLAUDE.md` / `README.md` 一致；`【归纳】` = 本文对源文档的整理，非独立发明。
> **一句话定位**：合同中心 = **合同容器 + 履约编排 + 结算引擎 + 风控网关**；其核心是「**合同域（商业契约）与履约域（执行）解耦**」，交收模式决定节点顺序，结算渠道决定资金如何流转。

---

## 0. 先记住三句话（被问"合同中心复杂在哪"就答这三句）

1. **合同是"容器"，不是"订单"**：一个合同对应 N 批发货计划，每批有独立的物流、质检、结算子流程；B2C 订单是"原子"（一次下单 = 一次物流 = 一次支付），B2B 合同是"容器"。
2. **交收模式决定节点先后，结算渠道决定资金流动**：先付款还是先发货，是交收模式的职责；资金"实际划转还是仅冻结"，是结算渠道的职责。两者正交，不能混谈。
3. **合同域与履约域解耦**：合同只记录商业契约（谁、什么、多少、什么价），履约按交收模式动态生成执行计划。新增一种交收模式时，合同核心代码无需改动，只新增一个履约策略实现。

---

## 1. 为什么大宗商品的合同管理是最复杂的环节（十大痛点）

> 源文档 `contract-pain-points.html`。一份典型铁矿石进口合同涉及品质条款 10+ 指标、定价机制（指数/基差/一口价）、交收模式、付款条件、运输条款、滞期费、争议解决……合同本身就是系统工程。

**十大核心痛点**（面试挑 2-3 个能展开的记）：

| # | 痛点 | 系统能力落点 |
|:--:|---|---|
| 1 | 合同模板管理混乱（几十个模板、版本分散、法务改了业务还在用旧版） | 模板版本管理 · 条款库 · 模板审批 |
| 2 | 合同签署效率低（纸质打印→盖章→扫描→回传 3-7 天） | 电子签章 · U-Key · 签署流程引擎 |
| 3 | 品质条款复杂与争议（Fe/SiO₂ 等 10+ 指标，每项有基准值/上下限/拒收值） | 品质指标库 · 品质差价公式 · 第三方质检对接 |
| 4 | 交收模式选择与匹配困难（买卖双方对"款到发货"理解不一致） | 交收模式匹配引擎 · 履约计划引擎 |
| 5 | 履约过程不可视（合同签完"进抽屉"，只有问经办人才知道进度） | 履约状态机 · 节点跟踪 · 合同看板 · 预警 |
| 6 | 变更管理缺乏规范（口头变更、变更后履约/付款/物流计划不同步） | 变更流程 · 变更审批 · 履约计划联动 |
| 7 | 链式合同权责不清（A→B→C→D 转卖，最终品质问题责任在谁） | 链式合同引擎 · 权责链条追溯 · 背对背条款匹配 |
| 8 | 违约处理与纠纷解决机制缺失 | 违约认定 · 违约金计算 · 纠纷调解 · 仲裁支持 |
| 9 | 合同与结算脱节（品质/数量差异导致结算金额变化，两套系统人工核对） | 合同-结算联动 · 品质差价公式 · 自动结算引擎 |
| 10 | 合规与监管风险（制裁筛查、KYC、出口管制、反洗钱） | 制裁筛查 · KYC · 合规检查引擎 · 监管报告 |

**复杂度分层模型（L1→L5，面试画这张表最有说服力）**：

| 层级 | 描述 | 系统能力 |
|---|---|---|
| L1 合同创建 | 模板选择、条款填写、价格与品质录入 | 模板管理 · 条款库 · 智能填充 |
| L2 合同签署 | 电子签章、签署流程、签署状态 | 电子签章 · 签署流程引擎 · 多方式认证 |
| L3 履约执行 | 履约计划生成、节点跟踪、付款/发货/收货联动 | 履约状态机 · 节点跟踪 · 异常预警 |
| L4 变更与违约 | 变更管理、违约认定、纠纷处理、违约金 | 变更流程 · 违约引擎 · 纠纷调解 |
| L5 结算与归档 | 品质差价结算、合同-结算联动、归档 | 结算联动 · 差价公式 · 自动归档 |

## 2. 合同域与履约域的解耦（最根本的一处设计）

`【总纲口径】` 核心设计原则：**合同域（商业契约：谁、什么、多少）与履约域（执行：付款、发货、收货、发票）解耦**。

- **为什么解耦**：大宗贸易中合同变更极其频繁——补充协议、数量增减、交期调整是家常便饭。若把履约状态耦合在合同上，每次变更都是一场数据迁移事故。
- **解耦后**：合同是**版本链**（原合同 + N 个补充协议），履约是**独立的计划与任务流**，两者通过**事件总线**联动。
- **核心表** `【源文档】` `system-design-with-tables.md`：
  - `contract`（主合同）、`contract_item`（合同行项：商品/数量/单价/质量标准）、`contract_party`（参与方）
  - `fulfillment_plan`（履约计划，批次拆分）、`payment_order`（收付款资金单）、`shipment_order`（发货单）、`receipt_settlement`（收货 + 质检结算）
  - `fund_pool`（预付池/已结池核销记账）、`invoice`（开票/收票）、`refund_order`（超付款退款单）

**一句话**：合同是"商业契约"，履约是"执行计划"，中间用 `delivery_mode`（交收模式）和事件总线连起来。

## 3. 交收模式：5 种口径 × 7 种架构视角（务必分清层次，这是最高频的追问点）

> **关键**：项目里"交收模式"有两个层次，面试时先说清层次，才不会自相矛盾。

### 3.1 付款节奏层（顶层口径：五种交收模式）

`【总纲口径】` `CLAUDE.md` 顶层定义**五种交收模式 (Five Delivery Modes)**：

| 交收模式 | 先后次序 | 风险主要在谁 | 典型场景 |
|---|---|---|---|
| 款到发货 | 先付款，后发货 | 买方（怕卖方不发货） | 陌生客户、大额单、信用不足 |
| 货到付款 | 先发货，后付款 | 卖方（怕买方不付款） | 长期老客户、有账期额度 |
| 定金+尾款 | 先付定金，发货/验收后付尾款 | 两边分担 | 预售、长协、价格波动大 |
| 分期付款 | 按节点分批付（发货前/到港后/验收后） | 两边分担、按节点释放 | 大额单，需分段保障 |
| 信用证 | 银行替买方承诺，单证相符后付款 | 银行承担付款信用 | 跨境或陌生方，需银行背书 |

> 面试点破：**款到发货和货到付款不是两种功能，而是同一个"付款节点"在时间轴上的两个位置**。把付款节点的位置和比例做成参数，五种模式就是参数组合。

### 3.2 结算×配货通道层（架构视角：七种交收模式）

`【源文档】` `fulfillment-workflow-modes.html` 把「结算（资金）场内/场外」和「配货（货物）场内/场外」两个维度引入后，得到**七种交收模式**：

| 模式 | 履约顺序 | 结算 | 配货 | 平台掌控力 |
|---|---|:--:|:--:|---|
| ① 先款后货担保 | 先款后货 | 场内 | 场内 | 最强（全流程管控） |
| ② 先货后款 | 先货后款 | 场内 | 场内 | 中等（发货后平台被动） |
| ③ 付款交割 | 款货同步 | 场内 | 场内 | 强（款到发货） |
| ④ 自主交收 | 自主安排 | 场外 | 场外 | 弱（仅首尾确认） |
| ⑤ 自由交收 | 任意顺序 | 场外 | 场外 | 无（不限制） |
| ⑥ 场内结算+场外交收 | 先款后货 | 场内 | 场外 | 较强（控资金不控货） |
| ⑦ 场外结算+场内交收 | 先款后货 | 场外 | 场内 | 较强（控货不控资金） |

> **层次关系（归纳，务必说清）**：`5 种` 回答"**钱分几次付、什么时候付、谁担保**"（付款节奏）；`7 种` 回答"**钱和货各自走场内还是场外、谁管控**"（结算与配货通道）。两者是正交的两个抽象维度，不是"5 种升级成 7 种"。
> - 7 种里的 ①②③ 本质都是「场内结算 + 场内交收」，差异仅在付款与发货的先后顺序；④⑤ 是场外场景（④ 场外+场外的简化版、⑤ 纯场外无约束）；⑥⑦ 是真正把两个维度交叉出的模式。
> - 5 种里的「定金+尾款 / 分期付款 / 信用证」属于**付款节奏**，在 7 种这套体系里没有独立对应项——它们是正交维度，面试别硬套。

### 3.3 三维决策框架（画图就用这个）

`【源文档】` `fulfillment-workflow-modes.html` 把完整履约方案拆成三个独立决策维度：

1. **履约顺序**（先款后货 / 先货后款 / 款货同步 / 自由自主）
2. **结算方式**（场内结算——平台支付网关；场外结算——平台外流转，仅登记）
3. **货物方式**（场内配货——电子仓单/平台过户/质押解押；场外配货——实物运输/物流单据/仅记录）

> 架构结论：应把「**履约顺序引擎、支付通道适配器、货物系统**」设计为**三个可插拔的独立模块**，通过合同签订时的模式选择动态启用/禁用，而不是为每种模式维护一套代码。

### 3.4 2×2 结算配货矩阵（Q1-Q4）

`【源文档】` `settlement-fulfillment-modes.html`：

| | 场内结算（资金走平台） | 场外结算（资金走平台外） |
|---|---|---|
| **场内配货（货物走平台）** | **Q1 全场内**：平台全闭环，掌控力 ★★★★★ | **Q2 场外结+场内配**：控货不控资金 ★★★★☆ |
| **场外配货（货物走场外）** | **Q3 场内结+场外配**：控资金不控货 ★★★★☆ | **Q4 纯场外**：仅合同+记录 ★★☆☆☆ |

- 技术实现：**配置驱动**。签约时选模式，系统自动加载对应的支付通道、货物规则、对账策略（Q1 启用支付网关+货物系统+2PC+自动对账；Q4 全不启用，全人工对账）。
- 红线 `【源文档】`：**无支付牌照严禁资金池模式，资金池 + 二清 = 刑事风险**——这就是为什么要做银行存管、把资金控制力外包给持牌机构。

## 4. 履约引擎：双轨驱动（顺序交收 vs 自由交收）

`【总纲口径】` 由合同上的 `delivery_mode` 决定走哪条轨，两轨**共用同一套底层履约任务数据结构**：

| 轨 | 机制 | 特点 | 承接场景 |
|---|---|---|---|
| **顺序交收 (Sequential)** | 状态机/工作流引擎强制有序步骤 | 强一致，先款后货 | 高风险交易（新客户、大额、先款后合同） |
| **自由交收 (Free-form)** | 事件驱动 + 规则引擎并行流转 | 灵活，动态条件判定 | 长期合作客户（先合同后款） |

> 加分点（trade-off）：**顺序轨用状态机换确定性，自由轨用事件驱动换灵活性**，代价是自由轨的异常补偿逻辑复杂得多——用规则引擎把补偿策略配置化，而不是硬编码。

## 5. 付款规则：三大资金类型 + 两类保证金 + 216 条组合

`【源文档】` `payment-rule-scenarios.html` + `payment-rule-combinations.html`。

### 5.1 资金分类（一笔合同涉及的五类钱）

| 资金类型 | 说明 |
|---|---|
| **履约金 Deposit** | 买方缴纳的保证金，担保交易履约 |
| **货款 Goods Payment** | 货物对价，主要结算金额 |
| **手续费 Service Fee** | 平台服务费、资金通道费 |
| **卖方保证金 Seller Bond** | 卖方缴纳，担保开票/交付 |
| **开票保证金 Invoice Bond** | 货款中锁定部分，开票后释放 |

### 5.2 付款规则 = 5 维度决策空间（3×4×3×3×2 = 216 条组合）

| 维度 | 取值 |
|---|---|
| 履约金去向 | 冻结在买方账户 / 支付给卖方（自由）/ 支付给卖方（冻结） |
| 冲抵货款方式 | 不冲抵 / 按交收比例冲抵 / 延迟冲抵 / 交收到一定比例冲抵完 |
| 卖方收款节点 | 买方付款时 / 买方收货时 / 卖方收款确认时 |
| 卖方保证金释放 | 买方收货时 / 卖方收款时 / 卖方开票时 |
| 开票保证金冻结 | 冻结在买方账户 / 冻结在卖方账户 |

### 5.3 九种资金动作（看清每笔钱的来龙去脉）

`【源文档】` `fund-movement-matrix.html`，五大资金类型 × 六大业务事件（合同生效/发货/收货确认/收票确认/合同完结/违约处罚）→ 九种资金动作：

`FreezeDeposit`（冻结履约金）、`FreezePayment`（冻结货款）、`OffsetDeposit`（履约金冲抵）、`ReleasePayment`（释放货款）、`FreezeInvoiceBond`（截留开票保证金）、`ReleaseInvoiceBond`（释放开票保证金）、`DeductFee`（扣手续费）、`Refund/补款`（多退少补）、`Penalty`（罚没）。

> 关键动作语义：**收货确认时，货款同时发生三件事**——核销给卖方 + 截留开票保证金（约 10%）+ 扣手续费。

## 6. 资金池模型与轧差（合同履约状态与资金联动的核心）

`【源文档】` `funds-flow.html`。大宗资金链路 = 建立资金池（资金计划）→ 发生业务 → 逐步核销 → 多退少补 → 冻结与解冻。

- **三大资金池**：
  - `Paid_Pool`（买方已付）——履约计划级的虚拟账户
  - `Settled_Pool`（应结应付账单）
  - `Clearing Job`（核销机器人）
- **轧差公式**：`应退/补 = Paid_Pool − ΣSettled_Pool`
- **收货与质检**（核心环节）：生成 `receipt_settlement_order`（"真理账单"），例如实收 498 吨、扣罚 2000 元，应付 99.4 万——**按实收数量结算，多退少补**。
- **开票保证金 10%**：收货核销时从货款截留 10% 冻结，卖方开票且买方确认收票后解冻（90% 可提现 + 10% 冻结）。
- **联动价值**：`Paid_Pool` 有钱可自动解锁卖方"发货"按钮——**合同履约状态与资金池联动**，而不是靠人工确认。

> 面试点破：资金池是"履约计划（Plan）"级的虚拟账户，不是平台自己的沉淀池——这正是规避"二清"的关键：**钱在银行存管子账户，平台只记虚拟账**。

## 7. 结算渠道与对账补偿（4 种渠道 × 3 层补偿）

`【源文档】` `settlement-scenarios.html` + `fund-processing-matrix.html`。

### 7.1 四种结算模式

| 模式 | 资金控制力 | 特点 |
|---|---|---|
| 线下支付 | 最弱（无冻结能力） | 资金流与信息流完全脱节，纯人工核对，适合超大额 |
| 余额支付·无需再次授权 | 强 | 一次授权后平台后台 API 动账（freeze/transfer/split），无二清风险 |
| 余额支付·动账授权 | 最强 | 每笔冻结/划转客户显式授权（H5 密码/短信/U盾），安全性最高、阻力最大 |
| 银行订单支付 | 弱（一事一结） | B2B 网关，企业内审批流，异步回调驱动状态机 |

### 7.2 对账补偿三层次

- **L1 在线补偿**：本地消息表 + 定时重试（每 30 秒）
- **L2 定时巡检补偿**：每 5 分钟查 `PRE_FROZEN/FROZEN` 超时
- **L3 日终对账批处理**：凌晨 02:00 全量对账

> 幂等关键：`request_id(UUID)` 作为唯一键，保证同一资金操作重试多次只执行一次。

## 8. 四大特殊场景（合同中心处理逻辑的"深水区"）

`【源文档】` 这些是追问到极致时能救命的场景，各记一句核心逻辑即可。

### 8.1 链式合同（chain-string-sales）——从实物交割变为单据交割
- A→B→C→D→E 共 4 笔背靠背买卖合同 + 1 条物理物流线 + 1 条单据流转线 + 4 段资金清算链。
- 中间商交收 = 物权凭证（海运提单 B/L）的买卖与转移；支持**换单（Switch B/L）**、指示提单背书。
- 资金采用"**资金不过夜 + DVP 货银对付**"：货权先行确权 → 生成确定交割单 → DVP 扣款秒级分账 → 日终 16:30 零余额清扫。
- 三大痛点：单据流转比船慢、连环违约（多米诺）、贸易真实性审查。

### 8.2 代理销售（agent-sales）——商流与物权分离
- 合同卖方是中型贸易商 M，但货和仓单主体在终端工厂 F 手里。
- 解法"**条件预货转**"：名义货转（满足交收合规）+ 逻辑锁死（满足风控）+ 资金到账瞬间全解。
- 锁定规则：预货转后仓单**不可质押、不可转卖、不可提货**（系统硬阻断）；超时 24 小时自动撤单回滚。
- 原子化交收：资金到位与货权解押**同一毫秒同步**，任一方失败全部回滚。

### 8.3 托盘融资（pallet-financing）——链路断裂时引入托盘方救场
- 原 A→B→C→D→E 变异为 A→B→C→D→**P(托盘方)**→E(分批赎货)。
- 托盘方核心原则：**出钱前提是绝对控制货权，买方付清全款前碰不到货**。
- 最关键一步（货权拦截）：提单抬头**必须变更为托盘方 P**，绝不能再背书给 E；系统 OCR 识别收货方，收货方仍为 E 则**报错并阻断付款**。
- 分批赎货：赎货金额 = 货值 + 资金占用利息 + 仓储费 + 服务费。

### 8.4 违约处置（default-scenarios）——8 大违约场景 + 逆向单据
- 系统价值观：**违约发生时，让钱和货按契约自动流向该去的地方**。
- 三把利器：解耦的单据、冻结机制、逆向财务单（`penalty_order` / `refund_order` / `dispute_ticket`）。
- 8 大场景：买方逾期不付款（定金罚没）、拖延不确认收货（强制过账）、卖方卷款/不发货（资金熔断+强制过户）、卖方不开票（保证金划扣）、货不对板（质检扣罚）、质量严重拒收（单据作废）、虚假仓单（异议冻结）、隐性债务/仓储欠费（智能分账）。
- 关键设计：**正向单据（receipt_order / shipment_order / settlement_order）与逆向单据（penalty_order / refund_order / dispute_ticket）解耦**，保证单个环节出问题不卡死全链；冻结机制让系统掌握物理控制权。

## 9. 六大贸易场景（合同中心服务的业务全貌）

`【源文档】` `scenarios.html`，围绕「货、钱、权」三大核心要素：

| 场景 | 核心逻辑 | 典型交收 |
|---|---|---|
| 生产企业直采 | 钢厂/化工厂向上游资源方采购原材料，货期匹配生产 | 长协 + 30% 预付 + 70% 货到付款 |
| 贸易商中间分销 | 批量采购后拆分销售，赚批零差价/时间差 | 信用证采购 + 货到付款分销 |
| 跨境进出口 | 国际物流、外汇、清关 | 即期信用证 + CIF |
| 仓储质押融资 | 以仓单质押向银行融资 | 场内配货（货权控制） |
| 长协锁价 | 1-3 年长协锁定供需与价格 | 定金+尾款、月结 |
| 期货套保 | 现货期货反向操作对冲 | 场内结算（轧差需同一体系） |

> 三大核心要素：**货**（货物真实可溯）、**钱**（资金安全高效）、**权**（风险全面可控）。无论哪种场景，最终都收敛到这三个字。

## 10. 高频追问预案（合同中心专项）

| 追问 | 怎么答 |
|---|---|
| 为什么叫"合同中心"不叫"订单中心"？ | B2B 是"签约"（商业行为），B2C 是"买单"（消费行为）。合同是容器（一合同 N 批发货），订单是原子。详见 `07-B2B合同中心vsB2C订单中心-区别分析.md` |
| 你们有几种交收模式？ | 先分两层：付款节奏层是**五种**（款到发货/货到付款/定金+尾款/分期/信用证）；再往深一层，结算×配货通道是**七种**组合（引入场内/场外维度）。两层是正交的。 |
| 顺序交收和自由交收怎么选？ | 由合同 `delivery_mode` 决定；顺序轨用状态机换确定性，自由轨用事件驱动换灵活性，两轨共用底层履约任务结构。 |
| 收货时资金怎么动？ | 收货质检生成"真理账单"，货款同时三件事：核销给卖方 + 截留 10% 开票保证金 + 扣手续费；多退少补按 `Paid_Pool − ΣSettled_Pool` 轧差。 |
| 资金池是不是二清？ | 不是。钱在银行存管子账户，平台只记虚拟账（Paid_Pool/Settled_Pool），无支付牌照绝不碰资金池——资金池+二清=刑事红线。 |
| 链式合同怎么处理权责？ | 从实物交割变为单据交割，中间商交收的是提单；上游状态变更自动通知下游；支持换单；四流合一验证。 |
| 新增一种交收模式要改代码吗？ | 不用。合同域与履约域解耦，新增模式 = 新增履约策略实现 + 配置结算/配货通道，合同核心代码零改动。 |
