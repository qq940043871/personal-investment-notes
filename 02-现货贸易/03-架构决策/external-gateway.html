一、项目背景与要解决的问题

平台要把交易向资金侧、仓储物流侧、税务侧、签章侧延伸，就必须对接大量外部系统。5 家银行（支付、资金监管、对账）、物流 WMS、税务、电子签章等，累计 9+ 个外部系统。这些系统天生异构：通信方式、报文格式、签名算法、同步/异步回调机制都不一样，每家对接都要把认证、重试、幂等、对账重写一遍。

协议千差万别

银行多为专线 + 自定义报文 + 签名；WMS/税务/签章多为 HTTP 或异步回调，格式各不相同。

重复投递与资金风险

银行回调可能重复到达，若处理不幂等，极易造成重复入账、重复发货等资金差错。

对接周期长

每接一家新系统都要两三周，认证、重试、对账逻辑反复重造，拖慢业务上线。

核心定位：建立统一的外部系统集成网关适配层，把「对接一个外部系统」抽象为「实现一个适配器」。适配层统一承担防腐（隔离外部变化）、协议转换、幂等处理、对账兜底，外部系统差异被收敛在适配器内部，业务代码只面向统一抽象编程。

四、统一适配层设计

防腐（Anti-Corruption）

外部系统的字段、错误码、异常不泄漏进业务域；适配器负责翻译为平台内部的统一模型，外部变更被挡在适配器之内。

协议与报文转换

专线自定义报文、HTTP、异步回调统一转换为内部标准报文；签名/验签、编码、加解密差异全部封装在适配器内。

幂等处理

以「业务单号 + 外部流水号」为幂等键，重复的支付回调、重复的 WMS 回执一律去重，确保资金与货权动作只执行一次。

对账兜底

同步回执之外，定时以对账文件/对账接口做双向核对，主动发现并修复不一致，作为异步场景的最终一致性兜底。

五、关键决策与踩坑

决策一 · 用适配器模式统一异构渠道

为每一类外部系统定义统一接口（如下单、查询、回调处理），具体系统实现各自适配器，新增系统只加适配器、不动业务。收益：新系统对接 2-3 周 → 3-5 天。

决策二 · 回调必须幂等 + 只信对账，不信单次回执

踩坑：银行支付回调因网络重发被处理两次，险些重复入账。修复：以「业务单号 + 外部流水号」幂等去重，并在回调之上叠加定时对账兜底，把「单次回执」降级为参考、把「对账一致」作为权威结论。

决策三 · 超时、重试与补偿分离

查询类可安全重试；支付/发货类动作不盲目重试，超时后进入「待确认」状态交由对账与人工兜底，避免重试引发的重复资金动作。

决策四 · 外部不可用时业务要能降级不阻塞

签章、发票等非关键路径外部系统短时不可用时，主交易链路降级放行并记录待补办任务，避免「外部抖动导致交易中断」。同时对外部接口可用率做监控告警。

六、关键实现

渠道适配器 + 统一注册（以银行为例）

每类外部系统定义一个适配器契约，具体系统实现之；业务侧通过渠道编码调用统一入口，实现「一次对接，处处可用」。

// 统一渠道适配器契约
public interface ChannelAdapter {
    PayResult pay(PayRequest request);          // 下单/支付
    PayResult query(String bizNo);              // 主动查询
    void handleCallback(CallbackMessage msg);   // 异步回调
}

// 适配器注册中心：按渠道编码路由
@Service
public class ChannelRegistry {

    private final Map<String, ChannelAdapter> adapters = new ConcurrentHashMap<>();

    public void register(String channel, ChannelAdapter adapter) {
        adapters.put(channel, adapter);
    }

    public ChannelAdapter get(String channel) {
        ChannelAdapter adapter = adapters.get(channel);
        if (adapter == null) {
            throw new BizException("未支持的渠道: " + channel);
        }
        return adapter;
    }
}

// 5 家银行的实现（专线自定义报文，差异封装在适配器内）
@Service
public class BankAAdapter implements ChannelAdapter {
    @Override public PayResult pay(PayRequest req) { /* 签名 + 组包 + 发送 */ return null; }
    @Override public PayResult query(String bizNo)  { /* 查询交易状态 */ return null; }
    @Override public void handleCallback(CallbackMessage msg) { /* 幂等 + 入账 */ }
}

回调幂等 + 对账兜底

重复回调去重后入库；定时对账以外部账为基准核对，主动发现并修复差异。

// 回调处理：幂等键 = 业务单号 + 外部流水号
@Service
public class CallbackHandler {

    @Autowired private IdempotentService idempotent;
    @Autowired private ReconService reconService;

    public void onBankCallback(CallbackMessage msg) {
        String idemKey = msg.getBizNo() + ":" + msg.getExternalNo();
        if (!idempotent.tryAcquire(idemKey)) {
            return;   // 重复回调，直接丢弃
        }
        // 完成入账/货权动作（同一本地事务）
        // ...
    }
    // 定时任务：以银行对账单为准，双向核对并修复差异（最终一致性兜底）
}

@Service
public class ReconService {
    @Scheduled(cron = "0 0 2 * * ?")   // 每日凌晨对账
    public void dailyRecon() { /* 拉取对账文件 → 逐笔核对 → 差异告警/自动修复 */ }
}
