# 10 · Drools 规则引擎与交收模式

> **用途**：回答两类问题。一是"你们为什么用规则引擎，它在系统里管什么"；二是"先付款后发货、先发货后付款、定金尾款、分期、信用证，这些交收方式在系统里怎么表达"。
> **口径标注**：【底稿口径】= 项目底稿里已写明的用途；【源文档口径】= 手册中的描述，未独立核验；【设计推演】= 本文为交收模式做的设计，**不代表项目已按此实现**，面试时必须说成"设计思路"。

---

## 0. 三句话先记住

1. **规则引擎管"判断"，状态机管"推进"，策略管"怎么执行"。** 三者分开，任何一处变化只动一处。
2. 交收方式本质是**资金和货物的先后次序**。先付款还是先发货，决定了谁承担违约风险。这个次序由规则决定，由状态机执行。
3. 规则只产出一份**结算计划**，本身不调用银行、不改库存、不发消息。这样规则可以测试、回放和审计。

---

## 1. 项目里 Drools 做什么（真实用途）

【底稿口径】Drools 在项目中解决的是"多客户差异"问题。平台面向上百家客户，每家的计价、结算、违约、审批和表单校验规则都不同。如果写死在代码里，每个客户都要分叉一套代码。项目的做法是"一套引擎加每客户一套配置"，差异由规则表达。

具体的落点有四处：

| 位置 | 规则管什么 | 来源 |
|---|---|---|
| 合同条款 | 计价、结算、违约条款的客户差异 | 合同管理系统设计（电商指南 25） |
| 审批流 | 金额条件分支，决定走哪一级审批 | 工作流与审批流（电商指南 26） |
| 表单与授信 | 授信额度、计价规则、联动校验 | 表单与模板配置（电商指南 27） |
| 事中风控 | 交易量、退款率、逾期次数任一超标，自动预警或冻结 | 业务全链路场景手册（业务价值 02） |

【底稿口径】效果是：新客户上线周期从 2 个月缩短到 1 周（项目口径）。

**注意**：以上四处都是"判断类"规则。底稿里没有写明"五种交收模式的选择由 Drools 完成"，这一点在第 6 节"待核对"里单列。

## 2. 交收方式：谁先付、谁先发、风险在谁身上

平台的五种交收模式见总纲（【源文档口径】），下面按"资金和货物的先后"重新排列：

| 交收模式 | 先后次序 | 风险主要在谁 | 典型场景 |
|---|---|---|---|
| 款到发货 | 先付款，后发货 | 买方（怕卖方不发货） | 陌生客户、大额单、信用不足 |
| 货到付款 | 先发货，后付款 | 卖方（怕买方不付款） | 长期老客户、有账期额度 |
| 定金加尾款 | 先付定金，发货或验收后付尾款 | 两边分担 | 预售、长协、价格波动大 |
| 分期（进度款） | 按节点分批付，如发货前、到港后、验收后 | 两边分担，按节点逐步释放 | 大额单，需要分段保障 |
| 信用证或银行担保 | 银行替买方承诺，单证相符后付款 | 银行承担付款信用 | 跨境或陌生方，需要银行背书 |

另外还有两个在业务手册里出现的变体：保证金（竞价时支付）和进度款（发货前支付）。它们本质上都是"定金"和"分期"的组合，可以用同一套节点模型表达。

面试时可以这样点破：**款到发货和货到付款不是两种功能，而是同一个"付款节点"在时间轴上的两个位置**。把付款节点的位置和比例做成参数，五种模式就只是参数组合。

## 3. 设计：规则、状态机、策略的分工【设计推演】

整个交收链路分四层，每层只做一件事：

```
交易事件（挂牌成交）
   │
   ▼
① 规则层（Drools，无状态）
   输入：交易事实 + 客户事实 + 品类事实
   输出：结算计划 SettlementPlan（模式 + 付款节点 + 比例 + 账期 + 是否需担保）
   │
   ▼
② 状态机（有状态，持久化）
   按计划推进：PLANNED → 首笔付款到账 → 可发货 → 已发货 → 已验收 → 尾款结清 → 已完结
   发货动作的守卫条件：计划中"发货前应付金额"是否已到账
   │
   ▼
③ 策略（按模式执行）
   款到发货策略、货到付款策略、分期策略……各自决定"何时发起支付、何时放行发货"
   │
   ▼
④ 事件（付款到账、发货完成、验收完成）
   触发状态机推进；必要时重新跑规则（例如延期、改价）
```

**为什么规则层必须无状态、无副作用。** 规则只读输入、只写计划。它不查数据库，不调银行，不改库存。这样做有三个好处：

1. **可测**：给一组交易事实，断言计划是否正确，不需要起任何外部服务。
2. **可回放**：用历史订单跑新规则，对比新旧计划的差异，上线前就能发现误配。
3. **可审计**：每份计划记录命中的规则编号和规则版本，事后能解释"为什么这笔订单被要求先付款"。

**为什么长流程不交给规则引擎。** 款到发货要等付款到账，可能要几天。这类等待、超时、补偿属于状态机和 Saga 的职责（见 `05-Saga编排器详细介绍.md`）。规则引擎适合一次性判断，不适合长时间持有状态。

## 4. 规则示例（示意代码，非项目源码）

下面用 DRL 写三条规则，只为说明"规则决定什么、不决定什么"。阈值是示意值，不是项目参数。

```drl
package settlement.rules

import settlement.fact.TradeFact
import settlement.fact.CustomerFact
import settlement.fact.SettlementPlan

// 规则一：大额单或高风险客户，先付款后发货
rule "先付款后发货：大额或高风险"
salience 100
when
    $t : TradeFact( amount >= 5000000 || riskLevel == "HIGH" )
    $p : SettlementPlan( mode == null )
then
    $p.setMode("PREPAY_FULL");
    $p.addNode("SHIP_GATE", 1.00, "BEFORE_SHIP");
    $p.setRuleId(drools.getRule().getName());
end

// 规则二：授信足够、无逾期，允许先发货后付款
rule "货到付款：授信充足且无逾期"
salience 90
when
    $t : TradeFact( amount <= $c.creditLimit )
    $c : CustomerFact( overdueCount == 0, creditLimit >= amount )
    $p : SettlementPlan( mode == null )
then
    $p.setMode("CREDIT_AFTER_DELIVERY");
    $p.setPeriodDays(30);
    $p.addNode("FINAL_PAY", 1.00, "AFTER_ACCEPT");
    $p.setRuleId(drools.getRule().getName());
end

// 规则三：兜底，不自动放行，转人工
rule "兜底：无匹配则转人工"
salience -100
when
    $p : SettlementPlan( mode == null )
then
    $p.setMode("MANUAL_REVIEW");
    $p.setRuleId(drools.getRule().getName());
end
```

几点设计说明：

- **互斥靠 `mode == null` 加 salience。** 一旦某条规则写入模式，后续规则不再覆盖。这是最常见的写法，但它隐含"规则顺序即优先级"，所以优先级必须有文档。
- **兜底规则采用失败关闭（fail-closed）。** 没有规则命中时，不自动放行，转人工审核。宁可慢，不可错放。这个选择要说明理由，因为大宗单笔资金损失大。
- **保证金比例不在规则里算。** 参考业务手册的公式"保证金 = 客户信用 × 品类风险系数 × 交易模式系数 × 行情波动"（【源文档口径】，05 业务痛点手册）。规则只负责选择系数表，乘法在 Java 里做。这样规则保持简单，计算逻辑可以单测。
- **规则只产出计划，发货动作的放行是状态机的守卫条件。** 规则说"要先付款"，状态机才是那个真正拒绝发货的地方。

## 5. 复杂支付方式怎么表达【设计推演】

下面用同一套"付款节点"模型，描述几种复杂的支付场景。每个场景都是规则产出的一份计划，区别只在节点的位置和比例。

| 场景 | 计划里的节点 | 规则要判断什么 |
|---|---|---|
| 定金加尾款 | 定金（签约时，比例 X%）；尾款（验收后） | 价格波动大时定金比例是否上调；品类是否允许尾款期 |
| 分期进度款 | 第一期（发货前）、第二期（到港后）、第三期（验收后） | 大额单是否必须分期；每期比例与节点的对应关系 |
| 信用证 | 银行承诺付款（单证相符后释放） | 是否需要银行介入；跨境或陌生方是否强制信用证 |
| 账期加担保 | 发货后 N 天付款，由担保方兜底 | 账期天数由授信决定；担保条件是否满足 |

**一个容易被问倒的点**：分期付款的第二期，何时触发？答案是**事件**，不是规则。规则只决定"第二期在到港后付"。到港这件事由物流事件通知，状态机收到后推进，并调用付款策略。规则不关心"到港"是怎么发生的。

## 6. 追问链

| 追问 | 怎么答 |
|---|---|
| 为什么不用状态机写 if-else 处理所有交收方式？ | 状态机管流程推进，不管同一流程在不同客户下参数不同。客户差异是参数问题，用规则表达比在状态机里写分支更可维护。 |
| 为什么不把整个交收流程都交给 Drools？ | Drools 适合一次性判断。款到发货要等几天付款到账，长时间持有状态、等待超时，应交给状态机和 Saga。 |
| 规则怎么保证不冲突？ | 通过 salience 排优先级，`mode == null` 保证只写一次，最后加兜底规则。上线前用历史订单回放，看新旧计划差异。 |
| 规则改了，已经下单的订单怎么办？ | 计划在下单时生成并快照，规则版本号写进计划。规则更新只影响之后新下的单，已生成的计划不因规则改动而变化。 |
| 规则配错怎么办？ | 配置错误比代码错误更难查，这是选 Drools 的代价之一（见 `00-面试计划/02-项目叙事-B2B.md` 的取舍表）。应对方式：灰度生效、回放对比、规则版本审计、兜底转人工。 |
| 规则会不会拖慢下单？ | 规则是无状态的一次执行，源文档中风控场景的单笔规则执行延迟约 5ms 以内（【源文档口径】，04 现货手册）。规则本身不做 IO，耗时主要在输入数据的准备上。 |
| 为什么原型阶段不用完整规则引擎？ | 架构方法论手册的建议是：原型阶段用策略模式或配置表，但留出"策略可替换"的接口，等规则复杂度上来再引入 Drools（【源文档口径】，01 架构方法论）。 |
