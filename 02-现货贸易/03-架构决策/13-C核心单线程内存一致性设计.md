# C 核心单线程内存一致性设计（镜像落盘 + 异步回写 + 死信兜底）

> **一句话**：单线程内存撮合**天生串行、无需加锁**，它的一致性风险从来不在"内存内部"，而在"内存之外"——**掉电即全丢**、**内存与 DB 有回写时滞**。所以这套设计用三段把"内存外"也变成可恢复问题：**镜像文件**保证丢不掉、**异步回写 + 阶梯重试**保证追得上、**死信队列 + 运营重试**保证发不出去也有人知道。

> **口径**：本文属**公司项目轨道**（C 撮合引擎），与 `11-midservice网关职责与治理设计.md`（入口侧）、`12-跨系统调用一致性方案.md`（Java 侧跨系统）构成"公司项目一致性三部曲"——三者**对象不同、范式同构**（见 §9）。

## 0 一句话总览

| 问题 | 本设计的答案 |
|---|---|
| 单线程还需要操心并发一致性吗？ | **不需要**操心"内存内并发"（队列单线程天然串行 + CAS 兜底）；要操心的是"内存外"的三件事（§1） |
| 进程崩溃 / 机器掉电，内存订单簿怎么办？ | 关键动作**先落地镜像文件**（write-ahead），重启后按镜像**回放重建**内存 |
| 内存已成交、DB 还没写进去，算不算事故？ | **不算**。口径是**内存为准**，DB 是"最终一致的副本"，靠异步回写追上 |
| 回写失败了怎么办？ | 进「待回写队列」，**阶梯重试 N 次**；N 次全失败 → 熔断 → 进**死信队列** + **发运营短信** |
| 死信了谁来救？ | 运营**登录后台界面点"重试"**，记录重置回队列，**只重放回写、不重新撮合** |
| 这样最终能一致吗？ | 靠四件套：**内存为准 + 异步回放 + 幂等补偿 + 定时对账**（§6） |
| 整机（硬件 / 机房）不可用怎么办？ | **热备**——备机重放主的命令日志保持一致，仲裁判死后由备接管（§8） |
| **仲裁者自己挂了怎么办？** | **宁可全停，不可双主**——仲裁失联时无法区分“主挂了 / 主只是卡 / 网络分区”，只能拒绝服务；正解不是让它永不挂，而是**做成多数派仲裁组**（3 / 5 节点）+ **任期号持久化** + **栅栏令牌**（§8.5） |
| 这套“仲裁者 + 主备”像什么？ | **ZooKeeper + Kafka 的形态**——一个管“谁来当主”（协调平面），一个管“数据怎么复制”（数据平面）；硬对应如 **fencing ↔ leader epoch**、**ISR / `acks=all` ↔ RPO 判定点**、**幂等生产者 ↔ 幂等 upsert**（§8.6） |

**适用边界**：允许"内存为准、DB 最终一致"的撮合 / 行情 / 订单簿场景。若监管要求**成交即持久化强一致**（每笔成交必须等落库确认才算成交），本设计不适用，要走同步落库 + 双写确认。**判据**：这笔成交晚 1 秒落库，业务上能不能接受？能 → 本设计；不能 → 另议。

## 1 先厘清：单线程内存撮合，风险到底在哪

**一个必须先破除的误解**：单线程 ≠ 自动一致。单线程只免掉了一把锁，没免掉"崩溃"和"异步"。真正的做法是——**用单线程把"内存内"收敛成确定性问题，再用三段兜底把"内存外"也变成可恢复问题**。

风险分三类，边界清楚：

| 风险 | 场景 | 根因 | 对应防线 | 本文位置 |
|---|---|---|---|---|
| **① 易失性** | 进程崩溃 / 机器掉电 / 被 OOM Kill | 内存数据随进程结束即消失，且无痕迹 | **镜像文件**（写前落盘） | §2 |
| **② 内存与 DB 时滞** | 撮合已改内存、回写还没到 DB | 异步回写的天生时滞（换来的是撮合吞吐） | **内存为准 + 异步回写 + 定时对账** | §3 / §5 |
| **③ 回写永久失败** | DB 挂了 / 数据脏 / 唯一键冲突 | 重试无法自动收敛，需要人判断 | **死信队列 + 运营人工重试** | §4 |

> **三类风险互不相同，不能用一个机制兜**：镜像解决"丢"，异步回写解决"慢"，死信解决"卡死"。少任何一段，链路都有个宽度不等的裂缝。

### 1.1 单线程"能保证什么、不能保证什么"（边界表）

| 维度 | 单线程 + 内存 **能**保证 | **不能**保证（要靠别的机制） |
|---|---|---|
| 同一时刻两个操作改同一笔订单 | ✅ 不可能发生（串行） | — |
| 超卖 | ✅ 内存内 CAS 扣减就挡住了 | — |
| 撮合结果的可复现性 | ✅ 输入序列确定 → 输出确定 | — |
| 掉电后内存还在 | ❌ | 镜像文件（§2） |
| 内存改动一定到 DB | ❌ | 异步回写 + 重试（§3） |
| DB 永久写不进去时不静默 | ❌ | 死信 + 告警 + 人工（§4） |

## 2 第一段：镜像文件 —— 崩溃恢复的地基

### 2.1 为什么必须"先落地"：write-ahead 次序

**次序不变量（不可违背）**：任何会改变内存状态的操作，必须**先写入镜像文件并落盘（fsync 成功）**，才允许施加到内存。

反面推演：如果顺序反了（先改内存、后写文件），在"改完内存、写文件前"崩溃 → **内存改动没了，而且没有任何记录能说明它发生过**。这笔成交既不在内存（已丢）、也不在日志（没写）、也不在 DB（还没回写）——**彻底蒸发**。

> **一句话判据**：**"记下来"必须永远早于"改内存"。** 这是整套设计唯一一条绝对不能破的次序。

### 2.2 "镜像文件"到底记什么——三种概念先分清

用户口中的"镜像文件"是个统称，落地上要分三种，角色不同、别混用：

| 名称 | 记什么 | 作用 | 恢复时怎么用 | 本平台用法 |
|---|---|---|---|---|
| **命令日志 / 重做日志（WAL）** | "收到了**什么请求**"（输入指令） | 崩溃后从**确定性输入回放**，重建内存 | 从头（或从最近快照）**重放** | ✅ **主用**——撮合确定性高，回放即可复原 |
| **内存快照（snapshot / checkpoint）** | "**此刻内存长什么样**"（全量状态） | 加速恢复，不必从头重放 | 先载入快照，再补快照之后的日志 | ✅ **辅用**——定期打点，压缩恢复时间 |
| **回写待办（回写队列的持久化）** | "**哪些变更还没写进 DB**"（待办事项） | 保证"该回写的不会因崩溃而漏" | 重启后继续把待办写完 | ✅ 见 §3 |

> **三者的分工口诀**：**WAL 记"做了什么"、快照记"现在怎样"、回写待办记"还欠什么"。** 前两者服务于"重建内存"，第三者服务于"补齐 DB"。
>
> 实践组合：**命令日志 + 定期快照**。快照把恢复时间从"重放全部历史"压到"载入快照 + 重放一小段"，日志保证快照之后的增量不丢。

### 2.3 镜像落在哪里（决策树）

- **单机自用、只求"进程崩溃不丢"** → **本地磁盘顺序追加**。顺序写 + fsync，是这套方案里最便宜的一环。
- **要求"整机掉电也不丢"** → 本地磁盘 fsync 即可（关键在 fsync 真落盘，不是 write 到页缓存）；再叠加**主备/热备**，把单点消掉。
- **要求"机房级不丢"** → 日志同步到**备用机 / 共享存储**，但**不能同步等远端 ACK 才改内存**（那等于把撮合速度绑在网络 RTT 上，退回同步落库的老问题）。
- **判据**：**"先落地"的"地"越远，代价越高，撮合越慢。** 默认落在本地 + fsync，用热备兜机房级故障，不要为了极端场景牺牲主链路时延。

### 2.4 恢复流程（启动时）

| 步骤 | 动作 | 说明 |
|---|---|---|
| 1 | 载入**最近的快照** | 若启用快照；无快照则从日志头开始 |
| 2 | **重放**快照之后的命令日志 | 按原顺序、原输入重放，内存状态被确定性地重建 |
| 3 | 校验重放结果 = 快照指针 + 日志水位 | 确认无中间断档（日志有 gap 说明写入有洞，要报警） |
| 4 | **接管回写待办** | 把"还没写进 DB"的待办继续回写（不重放撮合，只补 DB，见 §3.5） |
| 5 | 与 DB 做**一次对账** | 内存重建完、待办补完后，与 DB 比对一次，差异报警（§6） |

> **恢复的核心纪律**：**重放的是"输入"，不是"结果"。** 只重放"收到过哪些订单"，由撮合逻辑自己再跑一遍得出结果——这样"内存 = 重放出来的内存 = 当时的那个内存"，天然自洽，不依赖任何落库状态的正确性。

## 3 第二段：内存处理 —— 单线程的无锁串行

### 3.1 "单线程"是怎么成立的：串行化入口

外部请求（订单、撤单）是多连接、多来源进来的，天然并发。所以"单线程"不是"世界上只有一条线程"，而是：

| 环节 | 做法 | 为什么 |
|---|---|---|
| 入口 | 所有请求**排进一条队列**（无锁队列 / Ring Buffer） | 把"多来源并发"收敛成"一个输入序列" |
| 处理 | **单线程事件循环**依次取出、依次撮合 | 序列确定 → 撮合结果确定 → 可回放 |
| 输出 | 撮合结果写入回写待办 + 推送下游 | 出口是"写待办"，不是"写 DB" |

> **关键**：单线程的价值不在"省了锁"，而在**把并发问题转成了排序问题**——只要输入序列定了，内存状态就是输入的函数，可复现、可回放。这是 §2 能用"重放命令日志"恢复内存的前提。

### 3.2 内存里的一致性靠什么

| 机制 | 保证什么 | 说明 |
|---|---|---|
| **队列单线程** | 内存改动的原子性 | 同一时刻只有一处改内存，无竞态 |
| **CAS 扣减** | 不超卖 | 库存 / 持仓扣减用 CAS；即便存在旁路访问，也不会扣穿 |
| **只读快照出内存** | 读不污染写 | 行情 / 查询走的是一份只读视图，绝不改内存结构 |
| **确定性撮合** | 可回放 | 价格优先、时间优先，规则纯函数化，无随机、无外部依赖 |

> **反面提醒**：单线程最大的敌人是**"顺手在里面做别的"**——比如在撮合线程里调外部接口、写日志文件、做重计算。**任何可能阻塞的操作都必须挪出撮合线程**（这正是 §2.3 里"不能同步等远端 ACK"的原因，也是库里"撮合主路径不引入 Java 服务、避免 GC 毛刺"的同一条纪律）。

### 3.3 内存变更必须先转成"回写待办"再出内存（核心不变量）

**不变量**：内存在改动的**同一个处理周期内**，必须把对应变更**追加进回写待办**——不允许"改了内存就完事"。

- **待办记的是"结果"**（这笔成交改成什么样），不是"输入"——因为回写 DB 要的是最终态；
- **待办的持久化位置**与镜像文件同源（见 §2.2 第三种"镜像"），保证"内存变了"和"待办记了"在崩溃语义上绑在一起；
- 出内存之后，回写由**独立线程**完成，撮合线程不等它。

## 4 第三段：待回写 DB 队列 —— 异步 + 阶梯重试 + 熔断告警

### 4.1 队列与回写器结构（规则表）

| 项 | 规则 | 理由 |
|---|---|---|
| **一条变更一条记录** | 一笔成交 / 一次撤单 = 一条回写记录，不合并 | 失败时只重试坏的那条，不牵连好数据 |
| **回写并发度** | 撮合单线程，**回写可多线程** | 撮合的确定性只需在撮合线程内保证；回写是 IO 密集，可并行 |
| **同一业务单的次序** | **同一笔业务的多条回写必须有序** | 否则 DB 里可能出现"先平仓、后开仓"，状态错乱 |
| **批量与上限** | 批量回写要有**条数上限** | 防止单次大批量把 DB 打满（与 `11-midservice` 网关的分页上限是同一纪律） |
| **失败不阻塞** | 单条回写失败**只影响该条**，不阻塞队列其余记录 | 一条坏数据拖死整条回写线程是典型事故 |

### 4.2 回写器工作方式（决策树）

- **同一业务单的次序怎么保？**
  - 按**业务单号哈希分片**，同一单固定落到同一回写线程 → 天然有序，首选；
  - 或**串行单写线程**（简单但吞吐低）→ 只作降级。
- **内存里 DB 已经是最新的了，还回写吗？**
  - 要回写。**内存为准不是"DB 可有可无"**——DB 是审计、对账、跨系统读取的依据；
  - 但**回写可以做"最终态覆盖"**：若同一条记录被后续变动覆盖，只回写最新态（幂等 upsert），减少无效写入。
- **回写要不要主动踢一脚？**
  - 要：**定时扫描兜底 + 变更后主动唤醒**并存。主动唤醒负责"快"，定时扫描负责"不漏"（线程重启、唤醒丢失都能捞回）。

### 4.3 阶梯重试（规则表）

沿用 `12-跨系统调用一致性方案.md` §3.6 的口径，**不另立一套**：

| 项 | 规则 |
|---|---|
| 退避方式 | 阶梯递增：**1s → 2s → 4s → 8s → …**（按次数取 2 的幂，设单次上限如 1 分钟） |
| 重试上限 | **N 次**（N 由业务容忍时长倒推；写死的不是 N 的值，而是"必须有上限"这件事） |
| 抖动 | 需要，±20% 随机——避免同批记录同时失败形成**回写风暴** |
| **该重试的错** | DB 连接断、超时、死锁回滚、主从切换中 |
| **不该重试的错** | 唯一键冲突（说明已写过，直接判成功）、字段越界 / 约束不满足（**重试 N 次也只是浪费 N 次**）→ 直接进死信 |
| 告警阈值 | **低于熔断阈值**：重试到一半就该有人知道，而不是等死信才喊 |

### 4.4 熔断 → 运营短信（规则表）

| 项 | 规则 |
|---|---|
| 触发条件 | 某条回写记录**重试达 N 次仍失败** → 移入**死信队列**（§5） |
| 短信发给谁 | 相关运营（按业务域分派：交易 / 资金 / 仓单） |
| 短信内容 | **单号 + 业务类型 + 已重试次数 + 最近失败原因**——够运营一眼判断，不必再登系统查库 |
| 为什么要短信而非只告警面板 | 撮合是**资金相关**的 P0 链路，**被动等运营看板 = 可能几小时没人发现**；短信是"主动捅醒" |
| 降噪 | 短信要**按类型聚合 / 限频**，避免"DB 整体挂了"时一次爆几千条短信（那是告警风暴，不是告警） |

> **熔断的语义**：熔断不是"放弃这笔数据"，而是**把"机器重试不动的"交给"人能判断的"**。所以熔断的那一刻必须**信息完整**（单号、原因、次数），否则运营拿到短信也不知道该干什么。

## 5 第四段：死信队列 + 运营人工重试

### 5.1 死信队列表（字段规则表）

| 字段 | 作用 | 规则 |
|---|---|---|
| 业务单号 | 关联撮合结果、供运营定位 | 必须，且建索引 |
| 业务动作 | 成交 / 撤单 / 行情快照 | 决定这张记录本该写进哪张表 |
| **重试次数** | 显示"试了多少次" | 达到 N 才进来；进来后不再自动重试 |
| **最近失败原因** | 排障关键 | 保留下游返回 / DB 报错全文 + 报文摘要，**别只留一句"失败"** |
| 首次失败时间 / 最后失败时间 | 判断"卡了多久" | 用于超时提醒 |
| **失败分类** | 可重试 / 需人工判断 / 数据本身错 | 决定运营是"点重试"还是"线下处理" |
| 处理人 / 处理时间 / 处理动作 | 操作留痕 | 谁、何时、对哪条做了什么 |
| 状态 | 待处理 / 处理中 / 已重试成功 / 已人工闭环 | 见 §5.4，不含"永久悬挂"态 |

### 5.2 运营界面（能看什么 / 能做什么）

| 能力 | 说明 |
|---|---|
| **看得见** | 死信列表（按业务域 / 时间 / 次数筛），详情含**单号 + 完整失败原因 + 关联的原始变更** |
| **点重试** | 一键把记录**重置回待回写队列**，重新入队（**不新建业务、不重新撮合**） |
| **批量重试** | DB 恢复后一键"全部重试"（有权限控制） |
| **标记闭环** | 判断是数据本身错（如上游给了非法值）→ 线下处理后标"已闭环"，不再重试 |
| **筛选与告警联动** | 死信积压能触发看板红点 / 二次短信 |

### 5.3 重试的语义边界（最容易搞错的地方）

| 动作 | 正确语义 | 错误做法（要避免） |
|---|---|---|
| 运营点"重试" | **只重放"回写 DB"这一步** | ❌ 重新撮合一遍——会算出第二笔业务，资金重复变动 |
| 重试的对象 | **死信表里那条待办** | ❌ 从原始订单重新走全流程 |
| 重试的幂等 | 按业务单号 upsert，重复重试结果一致 | ❌ 每次重试都 insert 一条新记录 |

> **判据**：**撮合只发生一次，回写可以重放无数次。** 重试针对的是"持久化"（可以重复做）这一环，绝不动"撮合"（只能做一次）那一环。

### 5.4 死信状态机（简述，配套图可参考 `12-图-待发送表状态机.html` 的画法）

```
待回写 ──失败──▶ 待重试 ──重试N次仍失败──▶ 死信（待处理）
  ▲                 │                          │
  │                 │重试成功                   │运营点"重试"
  └─────────────────┴──────────────────────────┘
                                                 │运营标"已闭环"
                                                 ▼
                                              已闭环（终态）
```

- **死信不是终态**——它要么被重试回"待回写"，要么被人工标"已闭环"；**不允许长期悬浮**（做超时提醒）。
- 与 `12-图-待发送表状态机.html` 的"待人工"态相比，语义一致、对象不同（那边是"发给下游"，这边是"写进 DB"），可按需统一成同一套状态命名。

## 6 四层兜底总览：C 核心一致性的"全貌"

库内既有口径「**内存为准 + 异步回放 + 幂等补偿 + 定时对账**」四件套，与用户口述四段一一对应：

| 兜底层 | 对应本文 | 兜住什么 |
|---|---|---|
| **内存为准** | §3 | 定义"谁说了算"——内存是权威，DB 是副本；避免"内存已成交、DB 没写"被误判成事故 |
| **异步回放** | §2 镜像 + §4 回写 | 崩溃后能重建内存（回放日志），崩溃后能补齐 DB（回放待办） |
| **幂等补偿** | §4.3 + §5.3 | 回写可安全重放；重放不产生第二笔业务（业务单号 upsert） |
| **定时对账** | §2.4 步骤5 + 本节 | 定期比对 **内存态 ↔ DB 态 ↔ 下游态**，差异报警——**兜底的兜底** |

> **对账为什么是"兜底的兜底"**：前面的机制都是"尽量不出错"，对账是"出错了也必须发现"。**没有对账，前面所有机制都是"相信它没坏"**。对账频率与撮合吞吐成反比，通常走低峰批量扫描。

## 7 崩溃恢复矩阵（失败落在哪一段，怎么恢复）

| 崩溃位置 | 内存 | 镜像文件 | DB | 恢复动作 | 数据后果 |
|---|---|---|---|---|---|
| **写镜像前** | 未改 | 已记 | 未写 | 无需恢复——内存本来就没改 | **无损失**（这是次序不变量买来的） |
| **写镜像后、改内存前** | 未改 | 已记 | 未写 | 重放日志 → 重建内存 | 无损失（重放即复原） |
| **改内存后、回写前** | 已丢（重启后重建） | 已记 | 未写 | 重放日志 → 内存复原 → 待办继续回写 | 无损失（DB 稍后追上） |
| **回写中、DB 已写部分** | 重建可得 | 已记 | 部分 | 待办继续回写，幂等 upsert 去重 | 无损失（重复写被幂等吸收） |
| **回写失败达 N 次** | 正常 | 已记 | 缺该条 | 进死信 → 运营重试 | **有缺口，但可见、可控、可补** |
| **镜像文件本身损坏** | 可重建但输入源坏 | ❌ | 完整 | 从 DB + 快照 + 原始订单流交叉重建 | **最坏情况**——需人工介入，故镜像要**多副本** |

> **矩阵的读法**：从上到下"内存是否已改"逐渐不可知，恢复手段逐渐从"无需动作"退到"人工介入"。**整张表的设计目标就是——让绝大多数崩溃落在前四行**（即镜像文件写成功之后的任何点，都能自动恢复）。

## 8 热备部署改造：从"单机可恢复"到"整机可接管"

> 前七节解决的是**单机内**的不丢不重——进程崩溃能恢复、回写失败能收敛。但**整机（硬件 / 机房 / 网络）不可用**时，单机再稳也没有意义。热备要补的是**整机级**的接管能力。改造的妙处在于：它几乎不新增"机制"，只是把既有机制**复制到第二个节点**上——因为本节要复用的，正是第 2 节那条"重放输入"的纪律。

### 8.1 核心思路：复制"输入"，不复制"结果"

热备最省事的做法，恰恰是 §2.2 那条纪律的直接延伸——**备机不接收"内存快照"、不接收"撮合结果"，只接收主的命令日志，自己重放一遍**。

| 复制对象 | 备机要做什么 | 代价 | 结论 |
|---|---|---|---|
| **命令日志（输入）** | 收到后**自己重放一遍撮合** | 备机要跑撮合（CPU），但**数据量小** | ✅ **首选**——与 §2 的 write-ahead / 重放纪律完全同构 |
| 内存快照（状态） | 直接载入内存 | 传输量大、频率高、易错位 | ❌ 只作"抢占式全量对齐"的兜底 |
| 撮合结果（输出） | 直接应用结果 | 要求状态机可序列化 + 顺序严格 | ❌ 复杂度高，且**撮合的确定性已能保证重放一致** |

> **判据**：既然 §3 已经保证"输入定则输出定"（撮合无随机、无外部依赖），那么**备机重放同一串输入，必然得到同一个内存**——传结果纯属多此一举。这正是热备能做"轻"的根本原因，也是"**确定性撮合**"的价值在可用性上的兑现。

### 8.2 架构改造：从单机到"三件套 + 一个仲裁"

| 角色 | 职责 | 与既有设计的关系 |
|---|---|---|
| **主节点（Active）** | 接命令、落镜像、内存撮合、回写 DB、发死信 | 就是 §3–§5 的原样，**逻辑不改** |
| **备节点（Standby）** | 收日志、落**本地镜像副本**、**重放内存**；**不接单、不回写、不推行情** | 复用 §2 的重放逻辑，只是"输入源"从本地日志换成主推来的日志 |
| **日志复制通道** | 把主的命令日志**有序、可断点续传**地推给备 | 新增；日志必须带**单调序号（LSN）** |
| **仲裁者** | 裁定"谁是主"，防止主备各自称主（脑裂） | 新增；**这是热备唯一不能省的外部依赖** |

**改造点清单（对照单机版，逐条看哪些变、哪些不变）：**

| 单机版的机制 | 热备要改成什么 | 为什么 |
|---|---|---|
| 镜像文件落"本地磁盘" | 落本地 **+ 推给备机**（备机也"先落盘、再重放"） | 备机接管后要有一份完整日志 |
| 命令日志 | 增加**单调序号（LSN）** | 备机要知道自己重放到哪、从哪续传 |
| 内存撮合 | **不变** | 确定性是热备能"靠重放对齐"的前提 |
| 回写队列 | **必须持久化** + **回写权单点** | 主挂了、内存里的待办不能丢；任一时刻只能一处回写 DB |
| 回写幂等 | **不变** | 切换瞬间"主写了半截、备又写一遍"靠它兜住 |
| 死信与人工 | **不变** | 与主备无关 |

### 8.3 切换流程（六步）

| 步 | 动作 | 要点 / 判据 |
|---|---|---|
| 1 | **故障检测** | 心跳超时；阈值要 **> 一次卡顿 / GC 的最坏时长**，否则把"慢"误判成"死" |
| 2 | **仲裁判死** | 备**不能自己宣布**主挂了——必须由仲裁者确认（主可能只是网络抖动，其实还活着） |
| 3 | **备晋升** | 备转主：接命令队列、开回写权、恢复对外服务 |
| 4 | **位点衔接** | 从"**已完整重放且已落盘的 LSN**"继续；**丢弃未完整接收的尾部日志** |
| 5 | **回写接管** | 从**持久化的回写待办**继续写 DB，用**幂等 upsert** 吸收"主已写一半" |
| 6 | **对外切换** | 网关 / DS 把流量指向新主；**这一步必须在新主"能服务"之后** |

> ⚠️ 第 4 步是热备最容易被忽略的一步：**"日志有 gap 就不许接管到 gap 之后"**。日志是 fsync 落盘的，**落盘的那条必然完整**；只收了一半的那条必须丢弃、从上一个完整位点续——**重复的输入会被幂等吃掉，但缺失的输入会造成错单**。

### 8.4 脑裂防护：为什么必须有仲裁者

- **最坏的场景**：主备都以为"对方死了、自己还活着" → **双主** → 都能接单 → 双份成交、双份回写 → 灾难。
- **纪律**：**"是不是主"这件事，不能由主备自己投票决定**。常见实现：
  - 独立**仲裁节点**（轻量，只投票）；
  - 共享存储 / 分布式锁的**租约**——主必须持有有效租约才有权服务，**租约到期即自动丧失服务权**；
  - 同机房双机用**直连心跳**，跨机房则**必须有第三方**。
- **红线**：**拿不到租约 / 票的主，必须立刻停止服务**——**宁可停，不可双主**。

> 但仲裁者**自己也会挂**——它挂了怎么办？**见 §8.5**。

### 8.5 仲裁者自身故障：把"一个点"做成"一个多数派"

§8.4 说"仲裁者不能省"，那**仲裁者自己挂了怎么办**？先把结论说死：

> **仲裁者失联 = C 核心整体停摆。这是正确行为，不是缺陷。**

原因只有一个：仲裁者缺席时，系统**无法区分三种情况**——① 主真的挂了；② 主只是卡顿 / GC 停顿；③ 网络分区（主其实活着，只是通信断了）。这三者要求的动作**恰好相反**（① 应当晋升，②③ 绝不能），而仲裁者恰恰是唯一能分辨它们的角色。分辨不出，就只剩一个安全选项：**拒绝服务**。

**所以仲裁者的设计目标不是"高可用"，而是"永不给出两个互相矛盾的答案"。** 宁可全体停摆，也不允许双主——这是 safety 优先于 availability 的典型取舍（CAP 里选 C）。对"多撮一笔就是真金白银"的交易场景，没有第二种选择。

#### 解法一（首选）：仲裁者不是一个点，而是一个多数派

| 方案 | 形态 | 容错 | 代价 | 适用 |
|---|---|---|---|---|
| **A · 单点仲裁** | 一个进程 / 一台机器（或一把 DB 锁） | **0**——它挂即全停 | 最轻 | 可接受"短时全停"的场景 |
| **B · 多数派仲裁组** | 3 / 5 个节点，**多数派投票**（本质就是 Raft / Paxos 的仲裁集合） | 3 节点容 1 挂；5 节点容 2 挂 | 多几台机器，但**节点极轻** | 要求整机 / 机房级容灾（推荐） |
| **C · 复用已有 HA 组件** | etcd / ZooKeeper / Consul 的租约与选主 | 同上（它们内部就是 Raft） | 引入一个外部依赖 | 团队已有该基础设施（最务实） |

**关键：仲裁节点必须"极轻"。** 它**不存业务数据、不跑撮合、不接交易、不推行情**，只维护三样东西——**任期号 + 谁持有租约 + 租约到期时间**。正因为它轻，做 3 个副本的成本远低于做主备本身。这与 §8.1"备机只重放"是同一个思路：**把这个角色要承载的状态压到最小**，冗余才做得便宜。

**方案 C 往往是最优解**：与其自己造一个仲裁者（等于再造一个单点），不如**复用架构里已有的高可用组件**——例如用 DB 的租约表（`UPDATE lease SET owner = me, expire_at = now + ttl WHERE owner = me OR expire_at < now`，**谁 UPDATE 成功谁就是主**），而 DB 本身通常已有主从 + 故障自动切换。**复用已有 HA 组件，比新造一个单点更划算。**

> ⚠️ **最需要避免的伪解法**：为了"防一个单点"而新造一个**没有冗余**的仲裁者——那只是把单点从 A 搬到了 B，总单点数没变，还多了一份要维护的代码和一条新的故障路径。

#### 两个必须写死、否则一定出事的细节

| 细节 | 不做的后果 | 纪律 |
|---|---|---|
| **任期号（term / epoch）必须持久化** | 仲裁者重启后**遗忘自己上次授权给了谁**，可能在**同一任期**内再授权给另一个候选 → **一个任期两个主** | 每次授权**先落盘 fsync 再回复**；任期号**全局单调递增**、永不回退 |
| **栅栏令牌（fencing token）必须由下游校验** | 光靠"主自己停服"不够——**僵尸主**（进程卡死、根本没执行到停服那几行）仍可能继续写 DB / 发指令 | 每次授权递增任期号；主写 DB / 发指令时**带上令牌**，下游**拒绝旧令牌**的写入 |

第二条比第一条更关键：

> **"主会自觉停服"是一个假设，"下游拒绝旧令牌"是一个事实。** 前者依赖对方行为正确（而进程卡死时它恰恰不正确），后者不依赖任何对手方行为。所以 fencing 才是最后一道硬保险——它把"防双主"从**信任主**变成**信任下游的校验**。
>
> 这与 §4 的"回写权单点"是一对：**回写权单点管正常时序**（任一时刻只有一处回写），**fencing 管异常时序**（旧主的写入必然被拒）。

#### 恢复与降级

- **恢复路径**：仲裁组恢复多数派 → 重新选主 → 新主按 §8.3 的六步接管（从**已完整落盘的 LSN** 续位点）。**失联期间已对外应答的成交不会丢**（§8.7 半同步保证：应答前已复制到备）；未应答的按下游重试正常补发。
- **降级取舍（可选）**：仲裁失联时，主可保留**只读 / 查询**（行情、持仓查询），只关闭**写**（下单 / 撤单）。但必须清楚：此时主**也不能确定自己还是不是主**，只读可能读到**陈旧状态**——仅适用于"能容忍略旧"的场景，且客户端必须走**统一的"当前主"发现**，不能各自直连。
- **一句话纪律**：**仲裁失联时，写一定要停；读停不停，看业务对"略旧数据"的容忍度。**

### 8.6 与 ZooKeeper + Kafka 的对照：协调平面与数据平面

"仲裁者 + 主备"不是新发明——它在大规模分布式系统里早有一个人人都在用的形态：**ZooKeeper + Kafka**。把这个形态拆开，它恰好就是本文 §8 的两个平面。

#### 两个平面，逐一对上

| ZooKeeper + Kafka | 仲裁者 + C 核心 |
|---|---|
| **ZK = 协调平面**（选主、集群成员、配置、ISR 元数据） | **仲裁组 = 协调平面**（选主、任期、租约、谁持有写权） |
| **Kafka = 数据平面**（partition log、leader 单写、follower 复制） | **C 核心主备 = 数据平面**（镜像 WAL、主单写、备机重放） |
| ZK 的 **ephemeral node + session 超时** | **租约**（lease）+ **任期号**（心跳失效即让位） |
| Kafka **controller 唯一**（单写元数据） | **回写权单点**（任一时刻只一处写 DB） |
| **ISR + `acks=all`**（等副本确认才算提交） | **"对外应答前同步到备"**（RPO 的判定点，§8.7） |
| Kafka **幂等生产者**（PID + 序号去重） | **幂等 upsert**（按业务单号去重） |

#### 几条可以"画等号"的硬对应

不是"看着像"，是**同一个问题的同一招**：

- **栅栏令牌（fencing）↔ Kafka 的 leader epoch**（KIP-101）——Kafka 当年解决的正是"脑裂后旧 leader 继续写"：新 leader 上任即抬升 epoch，**副本拒绝低 epoch 的写入**。这与 §8.5 的 fencing 一字不差。
- **"对外应答前同步到备" ↔ ISR + `acks=all`**——Kafka 的"已提交"= 高水位之下、已被 ISR 全部复制的部分；这正是 §8.7 那句"RPO 由对外应答前是否已同步到备决定"的同构表述。
- **幂等 upsert ↔ 幂等生产者**——Kafka 靠 `(PID, 序号)` 让重发不产生重复消息；C 核心靠业务单号让重放不产生第二笔业务。

#### 更有价值的是演化：Kafka 后来把 ZK"干掉了"

> Kafka 从 2.8 起（**KIP-500**）引入 **KRaft**，3.3 生产可用，4.0 彻底移除 ZK 依赖。

为什么移除？**不是"协调"这个角色多余了，而是"为协调角色多跑一套不同系统"不划算**——两套软件、两份运维，ZK 还成了额外的单点与瓶颈。**注意：KRaft 里 Kafka 依然有独立的 controller quorum**，角色没消失，只是换成同一套软件来跑。

所以这个类比给出的**真正设计轴**是：

> **协调层：外部独立系统（ZK 式）↔ 内嵌共识（KRaft 式）——但无论哪种，角色都必须先独立。** 一句话：**角色分离 ≠ 进程分离。**

#### 对 C 核心的推论：这一层的答案是"别内嵌"

顺着这条轴，对 C 核心的结论是**倾向外部协调**，理由和 Kafka 相反、但更硬：

- Kafka 内嵌共识的动机是"省一套运维"，它的 broker 本就是多线程异步的，背得动；
- **C 核心的命门是"撮合线程内绝不阻塞"（§3）**。一旦把共识代码塞进撮合进程，就多了一条"共识慢 → 撮合被拖"的路径，直接侵蚀它的根。**为省一套运维去动最不该动的纯度纪律，不划算。**

但"外部"≠"必须引入 ZK"。§8.5 的方案 C——**复用已有的 etcd / DB 租约表**——本质就是"用现成的小 ZK"。**协调是一个独立角色，但不是非得是一个独立系统。**

#### 类比在哪里断掉

| 维度 | ZooKeeper + Kafka | 仲裁者 + C 核心 |
|---|---|---|
| **并行度** | 分区并行（每个 partition 各有 leader，靠分区数换吞吐） | **全局串行**（单线程 + 单主）→ C 核心 ≈ **只有一个 partition 的 Kafka** |
| **一致性语义** | `at-least-once` + 幂等生产者拼出 exactly-once | **确定性重放**直接得到，语义更强 |

> 配套对照图：`13-图-协调平面与数据平面对照图.html` / `.png`（左 ZK + Kafka、右 仲裁者 + C 核心，两平面逐条对应 + 一条「外部协调 ↔ 内嵌共识」的演化轴，含 KRaft 这一步）。

### 8.7 RPO / RTO：同步复制 vs 异步复制的取舍

| 复制方式 | RPO（丢多少） | RTO（停多久） | 代价 | 适用 |
|---|---|---|---|---|
| **异步复制** | 可能丢最后若干条（备尚未收到） | 秒级 | 主链路几乎无感 | 能容忍"最后几笔成交回滚 / 补录" |
| **同步复制** | **0**（主等备确认才算数） | 秒级 | 每次应答多一个**网络往返**，时延上升 | 成交即承诺、一笔都不能丢 |
| **半同步**（推荐权衡） | ≈0——**已对外应答的必然已复制** | 秒级 | 应答等复制确认，但**撮合本身不阻塞** | 多数资金相关场景 |

**关键区分**：「**改内存**」和「**对外应答**」是两件事，可以分开对待——

- 主先**落本地日志 fsync**（保证本机不丢）→ **立即改内存**（保证撮合快）→ **推日志给备** → **备确认后才对外应答**（保证整机不丢）。
- 这样**撮合吞吐不被网络拖累**，而"**已经告诉客户的成交**"保证在两个节点都有。

> **综合判据**：RPO 由"**对外应答前是否已同步到备**"决定，**不由"改内存前是否已同步"决定**。这正是热备能做到"既快又不丢"的关键。也顺带澄清 §2.3 中"不能同步等远端 ACK 才改内存"那句话——它说的是**改内存**这一步，**不代表**"对外应答"也可以不等。

### 8.8 热备下"不变的五条"（守住，否则越改越乱）

1. **撮合的确定性不变**——正因为确定，备机才能靠重放对齐；一旦撮合引入随机 / 对当前时间的依赖，热备立即失效。
2. **回写的幂等不变**——正因为幂等，切换后"主写了半截、备重写一遍"才无害。
3. **"先落盘再改内存"的次序不变**——**主机如此，备机重放时也如此**。
4. **回写权单点不变**——任一时刻只有主能写 DB；备只在**晋升之后**才有回写权。
5. **仲裁权威的唯一性不变**——任何时刻只有一个**有效任期**，任期号只能**单调递增**，旧任期的令牌一律无效（§8.5）。**哪怕仲裁者重启、扩容、换机房，这条都不许破**——它是"宁可停不可双主"最后的承重墙。

## 附：设计自查清单

**镜像段**
- [ ] 次序不变量落实：所有改内存的操作都"先写日志 + fsync"再改内存
- [ ] 命令日志能完整重放出一个确定性的内存（撮合逻辑无随机、无外部依赖）
- [ ] 有定期快照，恢复时间可接受
- [ ] 镜像文件有多副本（防"最坏情况"）
- [ ] 日志有水位/指针校验，能发现写入断档

**内存段**
- [ ] 入口是单线程串行队列（无锁或 Ring Buffer）
- [ ] 撮合线程内**没有任何阻塞操作**（不调外部接口、不同步写文件、不做重计算）
- [ ] 库存/持仓扣减走 CAS，不超卖
- [ ] 查询/行情走只读快照，不污染内存

**回写段**
- [ ] 一条变更一条记录；同一业务单的回写有序
- [ ] 批量回写有上限，不把 DB 打满
- [ ] "该重试"与"不该重试"的错误明确区分
- [ ] 阶梯退避 + 抖动 + 上限 N
- [ ] 告警阈值低于熔断阈值
- [ ] 回写幂等（业务单号 upsert），重放结果一致

**兜底段**
- [ ] 达 N 次进死信队列，短信带单号 + 原因 + 次数
- [ ] 运营界面能看详情、能点重试（**只重放回写**）、能标闭环
- [ ] 死信不是永久态，有超时提醒
- [ ] 有定时对账，比对内存态 / DB 态 / 下游态
- [ ] 短信有聚合 / 限频，防告警风暴

**热备段**
- [ ] 备机只重放日志：**不接单、不回写、不推行情**；日志带**单调 LSN**
- [ ] 有**仲裁者**防脑裂；拿不到租约 / 票的主**立即停服**
- [ ] 回写待办**已持久化**，切换后能被备接管（幂等 upsert）
- [ ] 明确了 **RPO 目标**（对外应答前是否已同步到备）与 **RTO 目标**
- [ ] 故障检测阈值 **> 一次卡顿的最坏时长**，不把“慢”误判成“死”
- [ ] 仲裁者**不是单点**：要么多数派仲裁组（3 / 5 节点），要么**复用已有 HA 组件**（etcd / DB 租约表）
- [ ] 仲裁者的**任期号已持久化**（先落盘 fsync 再回复），重启后**不会投出矛盾票**
- [ ] 主写 DB / 发指令**带栅栏令牌**，下游**拒绝旧令牌**（防"僵尸主"，不依赖主自觉停服）
- [ ] 若采用外置协调，已明确它是“独立角色”而非“多引入的一套系统”（可复用 etcd / DB 租约表）；且**共识代码不进撮合进程**

- [ ] 用"DB 人造失败"验证过重试与熔断真的会来
- [ ] 用"重复重放"验证过幂等真正生效（不产生第二笔业务）
- [ ] 用"制造内存与 DB 差异"验证过对账能发现
