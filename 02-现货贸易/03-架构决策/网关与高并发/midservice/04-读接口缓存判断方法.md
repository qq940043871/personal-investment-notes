# 读接口缓存判断方法（midservice 三级缓存落地）

> 背景：midservice 有几千协议，不可能全加缓存。如何判断哪些读接口值得加缓存？
> 结论先行：**按「缓存收益 = QPS × 命中率 × (后端 RT − 缓存 RT)」排序，只给「高频读 + 变更慢 + 穿透贵」的协议加缓存。**

---

## 一、现有缓存机制（配置驱动，加缓存 = 加一条配置）

三级缓存不是代码硬编码，而是声明式配置：

```
配置源（MonService.java:580 加载）→ ServiceConst.ApiCacheMap
  每条 = { API_ID, CACHE_KEY, CACHE_TYPE(PUB/FRM/CLI), CACHE_EXPIRE }
HandlerController.java:717
   containsKey(api_protocol) → 命中走缓存，未命中 callable.call() 后回填，TTL = CACHE_EXPIRE×1000ms
```

**三级缓存语义**（`HandlerController.java:823-833`）：

| 类型 | redisKey | 隔离维度 | 命中率 | 适用 |
|---|---|---|---|---|
| **PUB** | `CACHE_KEY` | 全用户共享 | 最高 | 行情、公告、公共配置、字典 |
| **FRM** | `CACHE_KEY + FIRM_ID` | 按机构隔离 | 高 | 费率、机构配置 |
| **CLI** | `CACHE_KEY + MD5(params)` | 按请求参数 | 低（参数空间决定） | 客户资产、个性化查询 |

> 结论：加缓存只需在配置源里给协议加一条 `{API_ID, CACHE_KEY, CACHE_TYPE, CACHE_EXPIRE}`，**零代码**。所以真正的活儿是「从几千协议里筛出该加的」。

---

## 二、判断公式

```
缓存收益 = QPS × 命中率 × (后端RT − 缓存RT) − 失效一致性风险
```

四个因子，逐一判断即可。

---

## 三、五个判据（逐个筛）

| # | 判据 | 判断方法 | 结论 |
|---|---|---|---|
| 1 | **是读还是写** | 协议语义 / 是否触发后端写（撮合/下单/支付/资金） | 写协议**绝不缓存**（一致性）；只考虑读 |
| 2 | **QPS 高不高** | 流量埋点 `ClientRequestCount.incrementAndGet(commandStr)` 聚合，或访问日志按协议号排 QPS | 低频读加缓存收益低，只处理 **Top N 高频** |
| 3 | **命中率高不高** | 数据变更频率 + 参数空间 | 变更慢 + 参数空间小 → 命中率高 → 值得；变更快/参数空间巨大 → 不划算 |
| 4 | **穿透贵不贵** | 后端 RT（DB 慢查询 vs Redis 快查） | 后端是 DB/撮合（贵）→ 缓存收益高；后端已是 Redis（便宜）→ 收益低 |
| 5 | **一致性能不能容忍** | 业务能否接受秒级/分钟级旧值 | 配置/公告能容忍 → 可缓存；资金余额/持仓强一致 → 不做或极短 TTL |

---

## 四、三级缓存类型怎么选

| 数据特征 | 选型 | 理由 |
|---|---|---|
| 全用户相同（行情、公告、公共字典） | **PUB** | 命中率最高，一份缓存服务所有人 |
| 同一机构内相同（费率、机构配置） | **FRM** | 按 `FIRM_ID` 隔离，机构内共享 |
| 随参数变化、但参数空间小且热点集中（某热门品种快照） | **CLI** | 热点参数才命中，冷参数穿透 |
| 随参数变化、参数空间巨大（每个请求都不同） | **不加** | 命中率趋近 0，缓存反而浪费内存 |

---

## 五、落地三步

1. **拉排行**：用流量埋点 / 访问日志，按协议号聚合 QPS 和平均 RT，取 **Top 50~100**。
2. **打分**：对 Top N 逐个过上面五个判据，剔除写协议、低频、强一致、参数空间大的。
3. **配置 + 灰度**：给命中的协议加 `{API_ID, CACHE_KEY, CACHE_TYPE, CACHE_EXPIRE}`，先灰度观察「命中率 + 数据一致性 + 后端 QPS 下降」，达标再放量。

---

## 六、典型对照表

| 协议类型 | 是否缓存 | 级别 | TTL 建议 |
|---|---|---|---|
| 公共配置 / 字典 / 合约模板 | ✅ | PUB / FRM | 60~300s |
| 公告 / 资讯 | ✅ | PUB | 60s |
| 挂牌品种 / 交货地 / 行情模板（GP9xxx） | ✅ | PUB | 60s |
| 费率（按机构） | ✅ | FRM | 300s |
| 行情快照（实时） | ⚠️ 短 TTL 或推送 | PUB | 1~5s |
| 客户资产 / 持仓 | ⚠️ 强一致 | CLI（短 TTL）或不做 | 1s |
| 资金余额 | ❌ | — | 不做 |
| 撮合 / 下单 / 支付（写） | ❌ | — | 不做 |

---

## 七、两个关键提醒

1. **`PubConfigCache`（5s TTL）已实现但未接线**——配置类读当前每请求一次 JDBC（`PubConfigServiceImpl`）。先把这类「变更慢 + 全用户共享 + 后端查 DB」的配置接口接上 PUB 缓存，是性价比最高的一步。
2. **失效一致性**：加缓存的协议必须有对应的**失效/刷新机制**（写操作后主动删缓存，或依赖 TTL 自然过期）。FRM/CLI 维度多，失效比 PUB 复杂，优先做 PUB。

## 八、③④⑤ 快速判断速查（不逐个人工看）

### ③ 命中率 → 看「参数空间 + 数据源」

| 信号 | 判断 |
|---|---|
| 入参无用户/账户/品种维度 | PUB / FRM，命中率高 |
| 入参含 `FIRM_ID`/用户/账户/品种等维度 | CLI，命中率看热点集中度 |
| 数据来自 DB 配置表（字典/配置/模板） | 变更慢 → TTL 60~300s |
| 数据来自撮合/实时行情 | 变更快 → TTL 1~5s 或不做 |

### ④ 穿透成本 → 看 handler 调用的 DSUtils 方法

| 调用 | 穿透到 | 成本 |
|---|---|---|
| `callSocket` / `callHession` | 撮合 / 微服务 / DB | 贵 → 值得缓存 |
| `getRedisInfo` | Redis | 便宜 → 收益低 |
| 纯本地计算 / 静态返回 | 无后端 | 不需要缓存 |

### ⑤ 一致性 → 看协议名/字段关键词

| 关键词 | 结论 |
|---|---|
| `balance` / `fund` / `position` / `order` / `margin` / `risk`（余额/资金/持仓/订单/保证金/风控） | 强一致，**不缓存** |
| `config` / `dict` / `template` / `notice` / `announce` / `fee`（配置/字典/模板/公告/费率） | 弱一致，**可缓存** |

### 批量自动筛（用已有数据源，脚本分类）

```
协议元数据（api.json / TB_DS_PROTOCOL）→ ① 读/写 + ④ connType/后端类型
流量埋点（ClientRequestCount）           → ② QPS
访问日志                                  → ④ 后端 RT
```

三条规则串起来，脚本自动分类，人工只复核「交易决策相关」的边界协议（如风控、保证金查询这类名字像读、实际影响交易决策的）。
