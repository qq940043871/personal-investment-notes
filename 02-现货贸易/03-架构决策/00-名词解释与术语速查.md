> **维护约定**：一个名词一张卡；先找已有分组，没有就新建（`##`）；卡片之间空一行。**只加名词卡片不动索引**；只有改文件名 / 移动位置时，才需同步三处（根 `index.html` 的 `PREP_CATEGORIES.arch`、`04-备战手册/index.html` 的 `04-架构决策.files`、`04-备战手册/00-资料库总览.md` 文件树）。

## 分布式一致性与事务

### WAL（Write-Ahead Log · 预写日志）

> **一句话**：改数据之前，先把「要做的动作」写进日志并落盘，崩溃后靠重放日志恢复状态。

| 维度 | 内容 |
|------|------|
| 核心思想 | **先记日志、后改数据**。日志记的是「意图 / 输入」，不是「结果」 |
| 为什么需要 | 内存状态易失、日志持久；只要日志在，崩溃后重放就能回到一致状态 |
| 本项目关联 | 13 号 C 核心的「镜像文件」三段兜底：**命令日志记输入 / 快照记状态 / 待办记欠账，恢复靠重放输入**——就是 WAL 思想 |
| 面试速答 | "WAL 用持久化日志换崩溃可恢复：先落日志再改内存，恢复时重放日志" |
| 易混 | WAL 是**增量**（记动作），快照是**全量**（记状态），两者配合用，不是二选一 |

### 死信队列（Dead Letter Queue · DLQ）

> **一句话**：重试到上限仍失败的消息 / 任务，移入一个隔离队列等待人工介入，而不是无限重试或直接丢弃。

| 维度 | 内容 |
|------|------|
| 核心思想 | **兜底**：不丢（留痕可查）、不无限重试（防故障放大）、不阻塞主链路（隔离） |
| 为什么需要 | 无限重试会占满资源、放大故障；直接丢弃会丢数据——死信是两者之间的第三条路 |
| 本项目关联 | 12 号「熔断转人工」；13 号死信队列**只重放回写、幂等 upsert，绝不重新撮合**；15 号死信 + 运营界面重试 |
| 面试速答 | "重试 N 次仍失败的消息进死信队列，由人工兜底，重放时只重放落库那一步、幂等执行" |
| 易混 | 死信 ≠ 丢弃：死信留痕可重放，丢弃是不可逆的数据丢失 |

### Saga（长事务补偿模式）

> **一句话**：把一个长事务拆成一串本地事务，每个都配一个逆向补偿操作，失败时逆序执行补偿，保证最终一致。

| 维度 | 内容 |
|------|------|
| 核心思想 | **正向操作 + 逆向补偿**；不追求强一致，追求**最终一致** |
| 为什么需要 | 跨服务长事务既不能包在一个本地事务里，也不能用 2PC 阻塞——Saga 用补偿换不阻塞 |
| 本项目关联 | `05-Saga编排器详细介绍.md`；12 号分工口径：**Saga 管"必须补偿"，12 号管"只需送达"**；个人储备 Harness 多步骤流水线与 Saga 同构（`02-AI智能体/01-认知框架` §4.5） |
| 面试速答 | "Saga 把长事务拆成 N 步本地事务 + 每步一个补偿，失败逆序补偿，最终一致" |
| 易混 | 补偿是**新写一段业务**，不是自动 undo；补偿本身也要幂等、可重试、失败转人工 |

### 2PC（Two-Phase Commit · 两阶段提交）

> **一句话**：协调者先问所有参与者"能不能提交"（准备阶段），再统一通知"提交 / 回滚"（提交阶段）。

| 维度 | 内容 |
|------|------|
| 核心思想 | **强一致**：要么全提交、要么全回滚 |
| 为什么不用 | 同步阻塞、协调者单点、参与者挂起时事务悬挂、性能差——不适合高并发 |
| 本项目关联 | 12 号选型对比：本项目**不选 2PC**，因为它阻塞且协调者是单点，与"只需送达 + 补偿"的目标不匹配 |
| 面试速答 | "2PC 两阶段保证强一致，代价是同步阻塞 + 协调者单点 + 性能差，所以高并发用 Saga/TCC" |
| 易混 | 2PC 是强一致（阻塞），Saga/TCC 是最终一致（不阻塞）；XA 是 2PC 的规范实现 |

### TCC（Try-Confirm-Cancel）

> **一句话**：每个操作拆成 Try（预留资源）/ Confirm（确认提交）/ Cancel（取消回滚），是 Saga 的一种"资源预留"风格实现。

| 维度 | 内容 |
|------|------|
| 核心思想 | **先预留、再确认、失败取消**；三个操作都要幂等 |
| 为什么需要 | Try 提前冻结资源，避免"Saga 正向都成功、补偿时资源已被别人抢走"的尴尬 |
| 本项目关联 | 12 号选型对比：与 Saga 同属补偿系，TCC 强调**资源预留（冻结）**，适合资金 / 库存类强资源语义 |
| 面试速答 | "TCC 把操作拆成 Try/Confirm/Cancel 三步，Try 预留资源，失败走 Cancel 回滚，三步都幂等" |
| 易混 | TCC 是 Saga 的特化（强调预留），比通用 Saga 多两个坑：**空回滚**（Cancel 时发现 Try 没执行，直接返回成功）、**悬挂**（Cancel 先于 Try 到达） |
