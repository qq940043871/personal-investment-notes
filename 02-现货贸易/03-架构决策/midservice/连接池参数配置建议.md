# B2B 连接池参数配置建议

> 建议值均为**压测基线**，最终以压测拐点实测为准；标注「改代码」的是当前硬编码、需改源码或加参数化。

---

## 一、配置总览（一句话结论）

| 层 | 池 | 建议压测基线 | 关键风险 |
|---|---|---|---|
| 网关 | DS 客户端池（→dataShare） | **200~300** | 第 2 跳硬顶，池耗尽关整池雪崩 |
| 网关 | 21 个后端业务池 | 核心 100~200 / 查询 50 | 部分池无默认值 → NPE |
| 网关 | Tomcat 线程 | 200~500 | 同步阻塞模型下是硬顶 |
| 数据中心 | 后端 socket 池（DB） | 撮合 200~300 / 查询 50~100 | `maxWaitMillis=5000` 硬编码 |
| 数据中心 | Redis 池（服务端） | MaxTotal 300 | 全局锁内借连接，耗尽归零 |
| 数据中心 | Redis 池（客户端 SDK） | MaxIdle 5→50 | MaxIdle 偏小 |
| 数据中心 | Hessian HTTP 连接 | `-Dhttp.maxConnections=200` | 最隐蔽的硬约束 |

## 二、网关侧（midservice）

### 2.1 DS 客户端池（网关 → dataShare，第 2 跳硬顶）

| 参数 | 建议值 | 依据 |
|---|---|---|
| `maxCon` | **200（撮合密集 300）** | 同步 BIO 下 1 连接=1 请求，`maxCon` = 第 2 跳并发上限；先核实生产值，再按 dataShare 实测并发能力定 |
| `initCon` | **20（maxCon 的 10%）** | 预热可消除首包毛刺 |
| `timeOut` | **3000** | 撮合短超时 + 不自动重试（幂等/对账兜底） |
| `maxWaitMillis` | 保持 5000，或按 RT P99 设 | **不要盲目改小**：它是「池耗尽时的快速失败护栏」不是「排队窗口」。前提是 `maxCon` 先匹配容量（正常不耗尽），否则改小 = 把排队变成「拿不到连接」 |

> ⚠️ 必须显式 `setUserPswd()`，否则登录 DS 失败。

### 2.2 21 个后端业务连接池

| 池类型 | `maxCon` | `initCon` | `timeOut` |
|---|---|---|---|
| 核心撮合/资金（`bd/bp/cnjy_trade/fundsV2/xht` 等） | 100~200 | 20 | 1000~2000 |
| 查询类（`xhtQuery/plzgQuery/cxgp` 等） | 50 | 10 | 3000~5000 |

> 无默认值的池（`Cxgp`/`Xht`/`Plzg`/`PLZBzg`/`XhtV5`/`Xydls`）**必须逐一显式配置**，这是压测环境搭建的必查项。

### 2.3 Tomcat 线程池

- **Tomcat**：`conf/server.xml` 的 `<Connector maxThreads=...>`，建议 **200~500**（配合 AsyncContext 异步化后可保持小）。

## 三、数据中心侧（dataShare）

### 3.1 后端 socket 池（`TB_DS_PROTOCOL`，第 4 跳硬顶）

| 协议类型 | `SOCKET_MAX` | `SOCKET_INIT` | `SOCKET_TIMEOUT` |
|---|---|---|---|
| 撮合类（connType=2 主链路） | 200~300 | MAX 的 20% | 1000（不自动重试） |
| 查询/报表类 | 50~100 | MAX 的 20% | 3000 |

```sql
-- 压测前核实并修正
UPDATE TB_DS_PROTOCOL SET SOCKET_MAX=200, SOCKET_INIT=40, SOCKET_TIMEOUT=1000
WHERE CONN_TYPE=2 AND MAIN_HIGH='撮合协议主号';   -- 按实际协议号
```

> `maxWaitMillis=5000` 硬编码：**不要直接改小**。正确的组合拳是——① `SOCKET_MAX` 先匹配「峰值并发 × RT」（尤其撮合/DB 类长 RT 协议）；② 池耗尽改成「只销毁坏连接 + 熔断」而非「关整池递归重建」；③ 加 `testOnBorrow=true`。在 ①②③ 到位后，`maxWaitMillis` 才可作为异常快速失败护栏，且取值应 **≥ 后端 RT 的 P99**（如 DB RT P99=2s，则至少 2000~3000，而非 500），否则正常慢查询也会被误伤成「拿不到连接」。

### 3.2 Redis 池（服务端 `redis.properties`）

```properties
# redis.properties（COMMON 段）
REDIS_LIST=10.0.0.1:6379,10.0.0.2:6379
MaxTotal=300
MaxIdle=50
MaxWaitMillis=1000
AUTH=******
```

> ⚠️ `MaxTotal` 要大于「后端并发 × Redis 往返占比」，且借连接务必移出全局锁（改造项）。

### 3.3 客户端 SDK Redis 池

`MAXIDLE` 从 5 调到 **50**（当前偏小，高并发下频繁建/销连接）；`MAXTOTAL` 保持 200 或按客户端直连场景调大。

### 3.4 Hessian HTTP 连接（最隐蔽的硬约束，查 DB 场景尤其关键）

1. JVM 启动参数 `-Dhttp.maxConnections=200`（JDK8 为 `sun.net.http.maxConnections`）——先把连接数从 5 放开。
2. 按「峰值并发 × DB RT」评估 Hessian 需要的有效连接数，`http.maxConnections` 要 ≥ 该值。
3. Hessian 本身是同步阻塞 HTTP RPC，长 RT（查 DB）会长期占用连接/线程；要彻底解决需异步化或走 connType=2 TCP 协议（见《网关百万并发与协议隔离设计》§六）。

## 四、配置示例汇总

```bash
# 1) JVM（网关 & 数据中心）
JAVA_OPTS="$JAVA_OPTS -Dhttp.maxConnections=200"   # Hessian 连接数

# 2) server.xml（Tomcat）
<Connector protocol="org.apache.coyote.http11.Http11NioProtocol"
           maxThreads="300" acceptCount="2000" maxConnections="30000" connectionTimeout="20000" />

# 3) redis.properties（dataShare）
REDIS_LIST=host1:6379,host2:6379
MaxTotal=300
MaxIdle=50
MaxWaitMillis=1000
AUTH=******

# 4) TB_DS_PROTOCOL（撮合协议）
UPDATE TB_DS_PROTOCOL SET SOCKET_MAX=200, SOCKET_INIT=40, SOCKET_TIMEOUT=1000 WHERE <撮合协议>;
```
