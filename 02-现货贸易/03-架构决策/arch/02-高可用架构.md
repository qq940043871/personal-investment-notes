# 02 - 高可用架构



> 如何保证交易系统 7x24 小时稳定运行

---

## 📖 概述

高可用（High Availability）是交易系统的生命线。一次宕机可能造成可观损失。本章介绍高可用的通用方案，并标注本人已落地与未落地的部分。

---

## 🏗️ 一、高可用架构设计

### 1.1 什么是高可用

**可用性指标**：
```
可用性 = MTBF / (MTBF + MTTR) × 100%

MTBF (Mean Time Between Failures)：平均故障间隔时间
MTTR (Mean Time To Repair)：平均修复时间
```

| 可用性 | 年故障时间 | 适用场景 |
|--------|-----------|----------|
| 99% | 3.65天 | 普通系统 |
| 99.9% | 8.76小时 | 企业级 |
| 99.99% | 52分钟 | 电商核心 |
| 99.999% | 5分钟 | 金融级 |

### 1.2 高可用架构原则

```
1. 消除单点故障 (Single Point of Failure)
2. 冗余设计 (Redundancy)
3. 故障隔离 (Fault Isolation)
4. 快速故障转移 (Failover)
5. 优雅降级 (Graceful Degradation)
```

## 🔄 二、故障转移机制

### 2.1 数据库故障转移

```
┌─────────┐      自动切换       ┌─────────┐
│  主库   │ ─────────────────► │  从库   │
│(读写)   │                    │(只读)   │
└─────────┘                    └─────────┘
     ▲                             │
     │     自动选主                 │
     └─────────────────────────────┘
```

### 2.2 缓存故障转移

```
正常情况：
┌─────────┐  写入   ┌─────────┐
│ 应用    │ ──────►│ Redis主 │
└─────────┘        └─────────┘

故障时自动切换：
┌─────────┐  写入   ┌─────────┐
│ 应用    │ ──────►│ Redis从 │
└─────────┘        └─────────┘
```

**Sentinel 故障检测**：
```yaml
# Sentinel 配置
sentinel monitor mymaster 127.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 30000
```

## 🔥 三、熔断与降级

> 限流算法实现、分层限流与 L1-L4 降级策略统一以 `./04-高并发处理策略.md` 为准（§二 流量控制、§三 熔断降级），本节只留定位。

### 3.1 熔断器模式

熔断器三态流转：关闭（Closed，正常放行）→ 失败次数超限 → 打开（Open，拒绝请求）→ 静默期后进入半开（Half-Open，放行探测请求），探测成功回到关闭，失败则重回打开。

### 3.2 降级策略

降级按影响面分级执行：L1 关闭非核心功能 → L2 简化流程 → L3 返回缓存数据 → L4 返回默认值，详见 `./04-高并发处理策略.md` §三。

### 3.3 限流策略

限流以令牌桶等算法在接入层/网关/应用层/数据层分层实施，算法实现与分层限流详见 `./04-高并发处理策略.md` §二。
