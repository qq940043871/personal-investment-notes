# 07 - 数据库选型与分库分表

## 个人经验锚点

> 本章为**通用方案 + 真实实践(B2B)**。分库分表（ShardingSphere/Sharding-JDBC、按用户/单据分片、读写分离）属于**通用方法储备**；本人 **B2B 大宗平台（2020 至今）** 实际落地的是**共用 MySQL 实例、按领域垂直分 schema（逻辑分库）+ 读写分离（主写从读）**，未做物理分库分表。分片扩容一致性 Hash 属于**通用方案 / 行业知识**，本人核心业务库为 MySQL。

> 数据库选型与水平扩展

---

## 📖 概述

数据库是交易系统的核心数据存储。本章介绍数据库选型策略和分库分表方法；分库分表为通用方案储备，本人 B2B 大宗平台实际落地的是垂直分 schema（逻辑分库）。

---

## 🗄️ 一、数据库选型

### 1.1 电商数据库需求

| 需求 | 说明 |
|------|------|
| **事务强一致** | 订单、支付必须ACID |
| **高并发读写** | 商品查询、订单创建 |
| **海量数据存储** | 历史订单、用户行为 |
| **复杂查询** | 多维度筛选、报表 |

### 1.2 选型对比

> 本人核心业务库为 MySQL；下表其余选项为通用选型参考。

| 数据库 | 优势 | 劣势 | 适用场景 |
|--------|------|------|----------|
| **MySQL** | 成熟、事务、运维 | 并发有限 | 核心业务 |
| **PostgreSQL** | 功能强、扩展性 | 生态稍弱 | 复杂查询 |

## 📊 二、分库分表

### 2.1 分片策略

```yaml
# ShardingSphere 分片配置
spring:
  shardingsphere:
    rules:
      sharding:
        tables:
          t_order:
            # 按用户ID分片
            databaseStrategy:
              standard:
                shardingColumn: user_id
                shardingAlgorithmName: database_inline
            tableStrategy:
              standard:
                shardingColumn: order_id
                shardingAlgorithmName: order_inline
```

### 2.2 分片算法

| 算法 | 公式 | 特点 |
|------|------|------|
| **Hash** | `id % n` | 均匀分布 |
| **Range** | `id BETWEEN` | 范围查询优 |
| **时间** | `DATE(created)` | 历史数据分离 |

## 🔄 三、读写分离

### 3.1 架构

```
┌────────────┐
│  应用服务  │
└─────┬──────┘
      │
      ├──► 写 ──► Master (主库)
      │
      └──► 读 ──► Slave1 / Slave2 (从库)
```

## ⚠️ 四、常见问题

| 问题 | 解决方案 |
|------|----------|
| 跨分片Join | ES替代/数据冗余（本人用 Elasticsearch 承接跨库检索） |
| 分布式ID | Snowflake/UUID |
| 分片扩容 | 一致性Hash（通用方案） |

## 💡 五、本人数据层实践

- **B2B 大宗平台（2020 至今）**：共用一个 MySQL 实例、按领域垂直分 schema（交易/订单/合同/结算等逻辑分库），读写分离（主写从读），配合 Snowflake 分布式 ID；跨域检索交给 Elasticsearch；历史数据按时间归档，缓解单表膨胀。物理分库分表为通用方案储备，未在本项目落地。
