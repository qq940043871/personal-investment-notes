一致性分流红线

弱一致（可旧、可延迟）→ Redis 直返，不穿透 │ 强一致（金额 / 持仓 / 成交）→ 绝不过缓存，穿透到服务层。
缓存只能承载「旧值」，不能承载「错值」—— 这条线画错，上面所有优化都只是放大器。

分流 缓存命中 ⇢ 直接返回客户端（短路，不进后端） 未命中 / 强一致读 → 协议转发至数据交互层

一致性兜底三件套

镜像文件防内存易失 │ 待回写队列防回写失败（阶梯重试 + 熔断转人工） │ 死信队列只重放回写、幂等 upsert，绝不重新撮合

① 为什么用 WebSocket 替掉强一致数据轮询：轮询的延迟下界 = 轮询周期，且「客户端数 × 1/周期」是一个恒定打向网关的 QPS，成交高峰时纯属给自己加戏。改成服务端推送后，"发现变化"的成本从 N 个客户端收敛为服务端 1 次事件。

② 分协议线程池为什么必须做：慢协议不隔离会占满共享池 → 快协议排队 → 表现为「下单偶发超时」，且在总维度监控上完全看不出元凶。按协议族分池后，慢的只拖死自己。

③ midmon 的三个观测位：协议调用量（发现异常放大与刷接口）、调用时长 P99（定位是哪条协议慢）、缓存命中率与失效（判断缓存到底有没有在干活）。

④ 一致性分层是这张图的题眼：弱一致可缓存、可延迟、可降级；强一致不缓存、不重试、不猜测。两层之间靠「协议号 + 数据语义」判定归属，而不是靠开发同学的心情。
