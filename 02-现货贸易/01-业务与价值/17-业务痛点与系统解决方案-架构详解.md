## 2. 客户/账户环节（3 个痛点）

### 痛点 1：客户开户审核慢、人工繁琐

| 维度 | 内容 |
|------|------|
| **业务痛点** | 企业开户需要营业执照、法人身份证、对公账户验证、经办人授权等，传统人工审核 1-3 天 |
| **业务影响** | 客户首次体验差，竞争对手 10 分钟开户，我们 3 天开户 → 客户流失 |
| **根因** | 资质核验依赖人工 + 多系统重复录入 + 跨部门审批 |
| **系统模块** | 客户中心 + 9+ 外部接口（企查查/银行/证书服务）|
| **解决机制** | **自动化核验流水线**——企查查接口核验工商信息、银行接口核验对公账户、OCR 识别证件信息，机器先审，人工复核兜底 |
| **关键设计** | **异步并行核验**——3 路核验并行（不串行），总耗时从分钟级压到秒级；**结果缓存**——重复核验不调外部接口 |
| **解决效果** | 开户从 1-3 天压到 10-30 分钟，95% 客户无需人工介入 |

### 痛点 2：客户主数据各业务系统不一致

| 维度 | 内容 |
|------|------|
| **业务痛点** | 客户改了联系方式，挂牌系统是新的、合同系统是旧的、仓单系统是更老的——客户投诉 |
| **业务影响** | 业务纠纷、合同送达失败、错失商机 |
| **根因** | 各业务系统维护自己的客户副本，靠 MQ 同步，断网就丢消息 |
| **系统模块** | 客户主数据中心（MDM）+ midservice 网关 |
| **解决机制** | **从"N 份副本"转向"1 份权威 + N 个引用"**——客户中心是唯一权威源，各业务系统不存副本，只通过 API 实时查 |
| **关键设计** | **短期止血**：本地消息表（outbox pattern）+ 消费端幂等 + 定时对账；**中长期治本**：MDM 改造 |
| **解决效果** | 客户数据一致性从 70% 提升到 99.9%，客户投诉归零 |

### 痛点 3：用户身份与操作权限混乱

| 维度 | 内容 |
|------|------|
| **业务痛点** | 采购员能看到销售员的菜单，销售员能修改采购价格——越权操作频发 |
| **业务影响** | 内部风险事件、合规审计不通过 |
| **根因** | 权限模型停留在"功能权限"，没有"业务角色"维度 |
| **系统模块** | RBAC + 业务角色层 + midservice 鉴权 |
| **解决机制** | **业务角色 = 采购商/销售商/平台运营/监管方**；不同业务角色看到不同菜单、不同数据范围、不同操作入口 |
| **关键设计** | **前后端协同**——后端 API 层按业务角色做数据过滤，前端按业务角色动态加载路由/组件；**菜单与数据范围都从 token/claim 来，不本地维护** |
| **解决效果** | 越权事件归零，审计一次性通过；前后端协同减少 50% 重复权限配置 |

## 3. 交易环节（5 个痛点）

### 痛点 4：热门资源多买家同时摘单，超卖风险

| 维度 | 内容 |
|------|------|
| **业务痛点** | 稀缺批次（如钢厂新到 100 吨螺纹钢）有 50 个买家同时摘单，必须确保"卖一份就是一份" |
| **业务影响** | 超卖 → 卖家拒绝部分买家 → 平台信用崩塌 |
| **根因** | 库存扣减和订单生成不是原子操作，中间有网络/系统故障窗口 |
| **系统模块** | C 撮合引擎 + DS 桥接 + Java 业务层 |
| **解决机制** | **三道防线**：①C 引擎单线程内存撮合 + CAS 扣减；②DS 超时熔断 + 幂等校验；③Java 业务层 `resource_id + version` 乐观锁 |
| **关键设计** | **三道防线独立演进、互不依赖**——任何一道失守都不会全局崩盘；C 引擎不重试（C 内已确定），DS 不重试（C 状态为准），业务层兜底 |
| **解决效果** | 三年内 0 超卖事件，热点资源摘单成功率 99.99% |

### 痛点 5：撮合时延不可控，价格窗口失效

| 维度 | 内容 |
|------|------|
| **业务痛点** | 客户报价 100 万/吨，但 500ms 后成交时市场价已变，客户亏损 |
| **业务影响** | 客户体验差，平台公平性受质疑 |
| **根因** | Java GC 停顿不可预测——99.9% 请求 10ms，但 0.1% 因 Full GC 飙到 500ms |
| **系统模块** | C 撮合引擎 |
| **解决机制** | **C 单线程内存撮合 + CAS 替代锁**——单线程本质上是把并发冲突限制在一个 CPU 核心的缓存行里，没有上下文切换，没有 GC |
| **关键设计** | **撮合主路径不引入 Java 服务**——所有撮合逻辑在 C 内完成，Java 侧只做撮合后的业务处理；**WAL 日志兜底**——极端情况撮合成功后 C 崩溃，WAL 回放恢复 |
| **解决效果** | 撮合时延 P99 < 1ms，0.1% 毛刺消失 |

### 痛点 6：多交易模式难以灵活支持

| 维度 | 内容 |
|------|------|
| **业务痛点** | 客户要挂牌、竞价、询价、基差等多类模式都要支持，每种都有自己的规则 |
| **业务影响** | 新业务上线周期长（1-2 月），错过市场窗口 |
| **根因** | 业务规则硬编码在代码里，新增模式 = 改代码 + 测试 + 上线 |
| **系统模块** | 规则配置中心 + 交易引擎 + 业务编排层 |
| **解决机制** | **策略模式 + 规则引擎**——把"业务规则"从代码中抽出来，运营/产品通过配置定义"A 类客户用 X 保证金比例 + Y 审批流 + Z 计价方式" |
| **关键设计** | **业务编排层（流程模板）**——"挂牌成交→生成合同→冻结保证金→触发电子合同"定义为可编排流程，新增业务模式 = 新建流程模板而非写新代码 |
| **解决效果** | 新业务上线周期从 1-2 月压到 1-2 周 |

### 痛点 7：交易模式与合同条款割裂

| 维度 | 内容 |
|------|------|
| **业务痛点** | 同一个挂牌成交，生成不同合同需要走不同流程、不同条款模板、不同审批链 |
| **业务影响** | 合同管理混乱，纠纷多 |
| **根因** | 合同中心没和交易引擎打通，每次成交后人工起草合同 |
| **系统模块** | 合同中心 + 交易引擎 + 规则配置 |
| **解决机制** | **成交即生合同**——交易引擎成交后自动触发合同生成，根据交易模式选择对应模板，套用规则配置 |
| **关键设计** | **合同模板引擎**——支持"挂牌模板/竞价模板/点价模板"等独立模板，模板内变量自动填充；**电子签章**——合同生成后自动调用电子签章服务 |
| **解决效果** | 合同生成从小时级压到秒级，合同纠纷率下降 60% |

### 痛点 8：跨期订单管理混乱

| 维度 | 内容 |
|------|------|
| **业务痛点** | 同一买家有多份 3 个月后的远期合同，每份有不同的合约月份、交割仓库、点价规则 |
| **业务影响** | 客户自己都理不清头绪，平台运营要逐个解释 |
| **根因** | 订单中心没聚合视图，各业务系统各管一段 |
| **系统模块** | 统一订单中心（事件驱动型）|
| **解决机制** | **订单事件上报**——挂牌单/合同单/仓单/交收单 各自向订单中心上报事件，订单中心聚合为"客户订单视图" |
| **关键设计** | **订单中心不替代业务系统，只做查询/统计/对账/风控入口**——避免单点风险；**订单号串联**——通过交易单号串联全链路 |
| **解决效果** | 客户订单视图一屏可查，运营答疑量减少 80% |

## 4. 履约环节（4 个痛点）

### 痛点 9：保证金冻结失败/状态不一致

| 维度 | 内容 |
|------|------|
| **业务痛点** | 撮合成功了但保证金没冻结成功 → 卖方货被拿走但没保障；或保证金冻结了但撮合回滚 → 钱被错扣 |
| **业务影响** | 资金安全事件，平台兜底损失 |
| **根因** | 撮合系统、资金服务、签约系统分布式部署，资金冻结是远程调用不是本地事务 |
| **系统模块** | 资金服务 + outbox 事务消息（Kafka）+ 履约状态机 |
| **解决机制** | **outbox 事务消息 + 最终一致 + 状态机约束**——①交易核心写本地事务（成交记录 + 履约单 状态=待冻结 + 消息表）；②事务提交后投递到 Kafka（冻结保证金事件）；③资金服务消费 → 调银行冻结（按幂等 key 去重）；④成功→履约单→已冻结；失败→履约单→交易取消 → 回滚成交；⑤定时扫消息表兜底未投递记录 |
| **关键设计** | **状态机编译期约束**——履约单 `status` 字段私有，所有变更走 `transition(事件)`，非法转移直接抛异常；**T+0 延迟消息 + T+1 定时扫表**阶梯定时 |
| **解决效果** | 三年内 0 资金安全事件，履约成功率 99.5% |

### 痛点 10：履约节点多、跟踪难

| 维度 | 内容 |
|------|------|
| **业务痛点** | 一笔交易从成交到交收有 8-10 个节点（冻结保证金→签合同→入库→过户→出库→交收→结算→释放保证金），客户和运营都搞不清当前在哪一步 |
| **业务影响** | 客户投诉"卡住了不知道找谁"，运营答疑成本高 |
| **根因** | 履约流程散落在多个业务系统，没有统一视图 |
| **系统模块** | 履约工作台 + 通知中心 + 统一订单中心 |
| **解决机制** | **履约时间轴**——一笔交易的所有节点按时间线展示，每个节点显示状态、责任方、预计完成时间；**自动预警**——节点超时自动通知运营和客户 |
| **关键设计** | **事件驱动**——每个节点变更都发布事件，履约工作台订阅事件聚合视图；**阶梯定时 + 延迟消息**双轨——短时用延迟消息，长时用定时扫表 |
| **解决效果** | 客户自助查询率从 20% 提升到 70%，运营答疑量减半 |

### 痛点 11：违约处置慢、扣罚不力

| 维度 | 内容 |
|------|------|
| **业务痛点** | 卖方到期不发货，平台要手动查合同、手动发起扣罚、手动通知银行——周期 3-5 天 |
| **业务影响** | 违约成本低，违约率居高不下 |
| **根因** | 违约判定靠人工，扣罚靠流程驱动 |
| **系统模块** | 风控引擎 + 履约状态机 + 资金服务 + 通知中心 |
| **解决机制** | **自动违约判定**——到期时间到 + 履约节点未推进 → 自动判定违约；**自动扣罚**——判定违约后自动调用保证金扣罚接口；**自动通知**——短信+App+站内信三通道通知 |
| **关键设计** | **阶梯定时 + 状态机触发**——到期前 N 天预警（提醒），到期当日自动判定（无需人工），违约后 N 小时自动扣罚；**人审兜底**——重大违约可人工复核 |
| **解决效果** | 违约处置从 3-5 天压到 1 小时内，违约率从 5% 降到 0.5% |

### 痛点 12：履约保证金额度难计算

| 维度 | 内容 |
|------|------|
| **业务痛点** | 不同客户、不同品类、不同交易模式，保证金比例都不同——人工算易错 |
| **业务影响** | 客户投诉"为什么我比别人多冻结 10%"，运营解释成本高 |
| **根因** | 保证金规则硬编码，规则散落在多个业务系统 |
| **系统模块** | 规则配置中心 + 风控引擎 |
| **解决机制** | **规则引擎 + 多维参数化**——客户信用分 × 品类风险系数 × 交易模式系数 × 行情波动率 = 保证金比例；所有参数可配置 |
| **关键设计** | **规则可解释**——客户问"我为什么冻结 15%"，系统能展示 4 个参数的具体值；**规则可回溯**——每次冻结都记录规则版本号，纠纷时有据可查 |
| **解决效果** | 保证金计算准确率 100%，客户投诉下降 90% |

## 5. 物流/仓储环节（3 个痛点）

### 痛点 13：电子仓单造假/重复质押

| 维度 | 内容 |
|------|------|
| **业务痛点** | 同一批货开多张仓单（虚假仓单），或一张仓单同时在多家银行质押 |
| **业务影响** | 银行被骗贷，平台失信，监管处罚 |
| **根因** | 仓单无唯一性标识，跨机构不可见 |
| **系统模块** | 仓单服务 + 第三方存证接口（区块链/电子证据）|
| **解决机制** | **仓单唯一码 + 上链存证**——每张仓单生成唯一码，关键属性（货主/数量/仓库/状态）上链存证；**质押登记**——每次质押都登记，所有方可见 |
| **关键设计** | **状态机**——仓单状态：未质押/已质押/已解押/已转让，状态变更通过 `transition` 防止非法变更；**链上链下双校验**——链上存关键摘要，链下存完整数据 |
| **解决效果** | 仓单造假事件从行业普遍存在到平台 0 发生 |

### 痛点 14：多仓库分散、库存查询难

| 维度 | 内容 |
|------|------|
| **业务痛点** | 货分布在 10 个仓库，每个仓库有自己的 WMS 系统，客户想知道"我有多少货在哪个仓库" |
| **业务影响** | 客户要打电话问 10 个仓库，运营答疑成本高 |
| **根因** | 多 WMS 数据不互通，缺统一库存视图 |
| **系统模块** | 仓储服务 + 9+ 外部接口（WMS） |
| **解决机制** | **仓储中台**——对接所有 WMS 系统，定时同步+实时事件上报，聚合为"客户库存视图" |
| **关键设计** | **数据归一**——不同 WMS 的字段命名/数据格式不同，中台做归一化；**事件驱动**——出入库事件实时上报，库存视图秒级刷新 |
| **解决效果** | 客户库存查询响应从 1 天压到 1 秒 |

### 痛点 15：物流在途状态不透明

| 维度 | 内容 |
|------|------|
| **业务痛点** | 货发出去了，运输公司在路上，客户不知道到哪了，会不会延误 |
| **业务影响** | 客户焦虑电话，运营答疑成本高 |
| **根因** | 运输公司不主动同步轨迹，平台无追踪能力 |
| **系统模块** | 物流接口（9+ 外部接口之一）+ 履约工作台 |
| **解决机制** | **物流轨迹 API 聚合**——对接多家物流公司 API，实时拉取轨迹，平台归一化展示；**延误自动预警**——预计到达时间前 N 小时未签收，自动预警运营 |

## 8.4 架构治理类（3 个痛点）

### 痛点 24：无统一商品中心，各业务商品割裂

| **解决机制** | **统一品类编码体系**——建立"大类 → 品种 → 规格/SKU"三层结构，大类编码与细分品种编码建立映射关系；**商品主数据唯一权威源**——基础属性（名称/品类/规格/计量单位/交收标准）只在商品中心维护，各系统通过 API 引用 |

| **解决效果** | 交收配货从人工核对变为自动匹配，错配事件归零 |

### 痛点 25：前端架构老旧，首页渲染慢

| 维度 | 内容 |
|------|------|
| **业务痛点** | 首页打开慢，采购方与销售方两套 UI 同时加载，首屏要等全部组件和菜单就绪 |
| **业务影响** | 客户首次体验差；行情看板是交易决策界面，加载延迟直接影响下单时机 |
| **根因** | Vue 传统 SPA 未做路由懒加载与资源优化；前端没有做"按角色按需加载"的架构设计 |
| **系统模块** | 前端构建体系 + midservice 网关（接口拆分） |
| **解决机制** | **路由懒加载**——各业务模块路由改为动态 import，首屏只加载核心框架与导航；**按角色拆分包**——采购视图与销售视图分别打包，按业务角色动态加载 |
| **关键设计** | **渐进式演进**——先做懒加载+分包+CDN（2 周见效），微前端（qiankun / Module Federation）作为中长期方向；**接口拆分**——首页接口从 N合一拆为按需并行请求，关键数据优先返回 |
| **解决效果** | 首屏加载时间显著下降，首页接口从串行等待改为并行按需返回 |

### 痛点 26：业务流程割裂，跨模块协同成本极高

| 维度 | 内容 |
|------|------|
| **业务痛点** | 新增一种交易模式（如基差贸易）要改 6 个系统；仓单↔挂牌↔合同↔交收数据不通，自动配货做不到 |
| **业务影响** | 新业务上线周期 1-2 月，错过市场窗口；各模块重复造轮子 |
| **根因** | 各业务模块高耦合、缺乏统一领域模型和业务编排层；域间直接读对方数据库而非通过接口/事件通信 |
| **系统模块** | 交易流程编排引擎 + 各限界上下文（客户域/商品域/订单域/仓单域/合同域/交收域/支付域/风控域） |

## 9. 跨环节解决方案（系统级能力）

26 个业务痛点的解决方案背后，依赖 6 个**跨环节系统级能力**。这些能力是平台的核心壁垒。

### 能力 1：DS 数据中心（异构桥接层）—— 解决"异构系统通信"问题

```
Java 业务中台 ──Hessian over HTTP（同步）──> DS 数据中心 ──Socket（异步）──> C 撮合引擎
Java 业务中台 ──HTTP/适配器（外部协议）──> DS 数据中心 ──> 9+ 外部接口（银行/物流/CTRM/...）
```

- **作用**：所有跨语言/跨系统通信的"翻译官"
- **关键价值**：**作为 Java 技术经理，DS 是你能直接 review 代码的地方**——C 撮合引擎是黑盒，但 DS 是 Java，黑盒的所有输入输出都在 DS 这一层被校验、转换、兜底
- **覆盖痛点**：4/5/9/22（涉及 C 撮合引擎的痛点都依赖 DS）

### 能力 2：outbox 事务消息 + 状态机（分布式一致性）—— 解决"分布式事务"问题

```
本地事务 (成交记录 + 履约单 + 消息表)  ──提交后投递──> Kafka  ──> 资金服务消费  ──> 调银行
                                                    ↓
                              成功回调 <──────────┴──────────> 失败回调
                              ↓                              ↓
                       履约单→已冻结                  履约单→交易取消 → 回滚
```

- **作用**：跨服务的数据最终一致，替代 Seata/XA 全局事务
- **关键设计**：**outbox pattern（本地消息表）**——业务操作与消息写入同一本地事务，投递后按幂等 key 去重 + 定时扫表兜底；配 **状态机**（禁止非法跳转）+ **幂等**（重试不重复）
- **MQ 口径**：本项目统一 **Kafka**，不引入 RocketMQ 半消息；事务语义由 outbox + Kafka 消费幂等实现
- **覆盖痛点**：9/11/17/19（涉及资金/履约一致性的痛点）

### 能力 3：Canal + 缓存服务（数据同步）—— 解决"异构数据同步"问题

```
C 撮合引擎 ──成交→── MySQL  ──binlog──>  Canal  ──>  缓存服务  ──>  Redis + 三端推送
```

- **作用**：让 Java 侧和前端能拿到 C 撮合的实时数据
- **关键设计**：**写时通知 + 读时拉取**（不是推送全量数据，只推变更通知）；**三端推送策略**（大屏全量/PC 增量/移动轮询）
- **覆盖痛点**：20/21（行情类痛点）

### 能力 4：规则配置中心（业务灵活性）—— 解决"业务变更响应慢"问题

```
运营/产品 ──配置规则──> 规则中心  ──推送──>  各业务服务  ──按规则执行
                                         ↑
                                    客户/品类/模式/时间
```

- **作用**：让业务规则不再硬编码在代码里
- **关键价值**：**新业务上线从"改代码 1-2 月"压到"改配置 1-2 周"**；运营/产品可自助配置，技术团队不被业务变更打断
- **覆盖痛点**：6/7/12/26（涉及业务规则可配置的痛点）

### 能力 5：midservice 网关（统一入口）—— 解决"客户端接入复杂"问题

```
三端客户端  ──>  midservice 网关（鉴权/限流/路由/灰度）──>  12+ 业务服务
                                ↓
                            midmon 监控（健康度/链路追踪/告警）
```

- **作用**：所有客户端请求的统一入口
- **关键设计**：**鉴权+限流+路由+灰度**一体化；**midmon 配套监控**（midservice 挂了一秒内告警，定位到具体实例）
- **覆盖痛点**：3/22/23（涉及权限/风控/合规的痛点）

### 能力 6：9+ 外部接口（生态连接）—— 解决"全功能闭环不可能"问题

```
平台核心（撮合/中台/规则）──> 9+ 外部接口
                             ├── 银行/支付（资金服务外包给银行）
                             ├── 物流（运输服务外包给物流公司）
                             ├── CTRM（行情/风控数据外包给专业数据商）
                             ├── 企查查（征信数据外包给第三方）
                             ├── 证书服务（电子签章外包给 CA 机构）
                             └── ...（短信/开票/咨询/供应链金融）
```

- **作用**：行业能力外包给生态，平台聚焦核心
- **关键设计**：**DS 是外部接口的统一适配层**——新增外部接口 = 在 DS 加适配器，业务侧无感；**适配器模式**——每家银行/物流/CA 独立适配器，互不影响
- **覆盖痛点**：1/13/15/16/17（涉及外部能力的痛点）

## 附录 C：五大架构决策速查（原 04 速查手册第一部分 §4，2026-10-31 并入）


> 面试中常被问"为什么这么设计"，不是问"怎么实现"。本节只保留**决策结论与话术**。
> **完整技术展开**：决策 1/2 见 `05 痛点 4/5` 及本文件附录 D 难点六；决策 3 见 `05 能力 2` 及附录 D 难点一 / 难点五；决策 4 见 `05 能力 3` 及附录 D 难点四；决策 5 见 `05 能力 4` 及附录 D 难点三；分布式事务框架见 `01-架构方法论与选型设计手册.md` 第 2.8 节。

#### 决策 1：为什么 C + Java 异构架构（而不是统一 Java）

**结论**：业务倒逼分层——撮合要微秒级用 C 单线程内存撮合，业务要灵活用 Java 微服务，**DS 数据中心做防腐层**（C 只暴露二进制协议，DS 翻译为 Hessian，Java 侧无感）。

**话术**：
> 「**业务的自然分层倒逼了技术的分层**。我们不是「为了异构而异构」——C 引擎是性能极致，Java 中台是业务灵活，DS 是我能 review 的治理抓手。**这正是技术经理的价值：管住 DS 就管住了整个异构链路的稳定性**。」

#### 决策 2：为什么异步落库（而不是同步等 MySQL ACK）

**结论**：撮合的核心职责是成交不是存储——内存订单簿（微秒级）→ 后台线程池写 MySQL → 失败写 WAL 回放；代价"内存有但库无"用「内存为准 + 异步回放 + 幂等补偿 + 定时对账」兜底。

**话术**：
> 「如果撮合完要等 MySQL ACK 确认，撮合性能就被数据库写入能力绑死了。**异步落库换来的是撮合吞吐量和确定时延**，代价是引入数据一致性复杂度——这部分我们用「内存为准 + WAL 回放 + 定时对账」来兜底。」

#### 决策 3：为什么用 outbox 事务消息而不是 Seata/XA（保证金场景）

**结论**：银行冻结接口耗时 3 秒，全局事务持锁 3 秒会拖垮履约吞吐；MQ 统一 **Kafka**，事务语义由 **outbox 本地消息表 + 消费幂等 + 定时扫表兜底** 实现（不用半消息），再叠加状态机禁止非法跳转。

**话术**：
> 「金融场景下，Seata 的全局锁是「正确但不可用」——3 秒锁持有时间会拖垮履约吞吐。我们的 MQ 统一是 Kafka，事务语义不用半消息，而是用 **outbox 本地消息表 + 消费幂等 + 定时扫表兜底** 落地，再叠加状态机约束：**分布式系统设计的第一原则是「让系统可恢复」而不是「让系统不出错」**。」

#### 决策 4：为什么用 Canal + 缓存服务（而不是直接 Redis Cluster）

**结论**：缓存服务不是简单 Redis 封装，而是「行记录 → KV 转换 + 三端推送分发」的中间层——前端只关心 Redis 最终态，不关心数据怎么来，Canal 直推前端会让前端耦合 binlog 格式。

**话术**：
> 「**缓存服务是「数据结构转换 + 推送分发」的中间层**。前端只关心 Redis 里的最终态，不关心数据怎么来。Canal 挂了不影响交易（不影响 C 撮合主流程），缓存服务挂了不影响撮合，只影响行情展示——**降级边界清晰**。」

#### 决策 5：为什么用规则配置中心（而不是写死业务逻辑）

**结论**：B2B 业务规则多变（不同品类/客户/模式的保证金比例、审批流、计费规则都不同）；改代码 1 周上线，改配置 1 分钟生效且可回滚，元能力是让业务人员自助驱动业务变化。

**话术**：
> 「**B2B 业务最贵的成本是「每开一个新业务就要改一次代码」**。规则配置中心的本质是「把业务策略从代码中抽出来」——业务人员通过配置就能定义「A 类客户用 X 保证金比例 + Y 审批流」，技术团队不再被业务变更打断。」

### 9. 难点一：银行资金存管的资金流一致性

#### 业务场景

客户在平台下单 → 平台向银行存管系统发送扣款指令 → 银行执行资金划付 → 平台更新订单状态。**资金在银行侧，交易状态在平台侧，两者必须最终一致，不能出现"钱扣了订单没成"或"订单成了钱没扣"的情况。**

#### 技术难点

```
平台交易系统 ──(扣款指令)──→ 银行存管系统
     │                              │
     │ ←──(扣款结果)─────┘
     │
     ├── 成功 → 更新订单为"已支付"
     ├── 失败 → 订单回滚
     └── 超时 → ??? (最棘手的情况)
```

**核心挑战**：

| 问题 | 难点说明 |
|------|---------|
| **网络超时** | 银行接口超时，不知道钱到底扣了没扣，需要主动查询对账 |
| **幂等性** | 重试机制下，同一笔扣款不能执行两次 |
| **状态机一致性** | 订单状态、资金流水、银行回单三方状态必须一致 |
| **T+1 对账** | 银行按日结算，平台实时交易，存在跨日对账差异 |
| **多银行适配** | 每家银行接口协议不同（上海银行/兴业/中原/平安/工行），需要适配层 |

#### 面试讲法（建议话术）

> "我们对接了 5 家银行的存管系统，核心难点是**平台交易状态与银行资金状态的最终一致性**。银行接口存在超时、重试、异步回调等不确定性，我们采用了**本地消息表 + 定时补偿 + 银行对账文件核对**的三层保障机制。每笔资金操作先写本地消息表（保证与业务事务同库），异步投递到银行，超时后主动查询银行接口，T+1 再用银行对账文件做全量核对。所有资金操作设计了**幂等键**（订单号+操作类型），确保重试不会重复扣款。"

#### 深挖问题预案

| 面试官追问 | 你的回答要点 |
|-----------|-------------|
| "超时了怎么办？" | 主动查询银行接口（queryByReqId），根据查询结果决定继续/回滚 |
| "查询也超时了呢？" | 标记为"不确定状态"，进入人工对账队列，T+1 对账文件兜底 |
| "幂等怎么设计的？" | 幂等键 = 会员ID + 订单号 + 操作类型 + 日期，银行侧也用 reqId 去重 |
| "多银行怎么适配？" | 适配器模式，定义统一的 BankGateway 接口，每家银行一个实现类 |
| "一致性保证了，性能呢？" | 异步化+批量处理，非核心链路异步补偿，TPS 受限于银行接口（通常 50-200 TPS） |

#### 与你背景的关联

你在 Agent Harness 中用 FastAPI 做 MainLoop 编排，本质上也是**多步骤状态机的一致性管理**。可以这样桥接：

> "这和我做 Agent Harness 时的任务状态管理很像——每个 Agent 步骤也有超时、重试、补偿的需求，我用了类似的状态机+补偿机制来保证 Agent 任务流的最终一致性。"

### 10. 难点二：区块链 + 物联网 + WMS 三层仓单可信链

#### 业务场景

大宗商品仓单融资中，最大的风险是**虚假仓单**——同一批货物开多张仓单、货物根本不存在、货物被偷偷运走。用三层架构解决：

```
┌─────────────────────────────────────────┐
│  区块链层：仓单上链，不可篡改，可溯源       │
│  ← 解决"仓单数据是否可信"                  │
├─────────────────────────────────────────┤
│  WMS 层：入库→质检→注册仓单→在库→出库     │
│  ← 解决"仓单与货物是否对应"                │
├─────────────────────────────────────────┤
│  物联网层：视频监控+温湿度+RFID+出入库管控  │
│  ← 解决"货物是否真实存在"                  │
└─────────────────────────────────────────┘
```

#### 技术难点

| 层 | 技术难点 | 说明 |
|----|---------|------|
| **物联网层** | 多源异构数据实时采集 | 视频（RTSP）、温湿度（Modbus/MQTT）、RFID、门禁系统，协议各异，需要统一接入网关 |
| **物联网层** | 边缘计算 vs 云端处理 | 视频流不能全上云（带宽成本），需要在边缘做行为检测（如异常搬货），只上事件 |
| **WMS 层** | 仓单生命周期状态机 | 仓单状态：待注册→已注册→已质押→部分解押→已提货，状态流转需严格防非法跳转 |
| **WMS 层** | 仓单与物理货物映射 | 货物可能分批入库、合并堆放、分批出库，仓单-货物映射是 N:M 关系 |
| **区块链层** | 链上链下数据同步 | 区块链写入有延迟（秒级~分钟级），不能阻塞交易流程，需要异步上链+回执确认 |
| **区块链层** | 仓单拆分与合并 | 融资场景需要仓单拆分（一张拆多张）或合并（多张合一），链上状态变更复杂 |
| **跨层** | 三层数据一致性 | WMS 注册仓单 → 物联网验证货物存在 → 区块链上链，任一环节失败需要跨层回滚 |

#### 面试讲法

> "仓单可信链是我认为最有技术含量的一块。难点不在于单独某一层，而在于**三层之间的数据一致性**。物联网层采集到货物入库事件后，WMS 才能注册仓单，仓单注册后才能上链。但物联网数据可能误报（比如摄像头误识别）、WMS 可能操作回滚、区块链上链可能延迟。我们设计了**事件驱动的跨层编排**：每层操作都是幂等的，通过事件溯源（Event Sourcing）记录所有状态变更，上链失败时通过补偿事件回滚 WMS 状态。物联网层用边缘网关做预处理，只把结构化事件（入库/出库/异常）上传，避免视频流直传云端的带宽问题。"

#### 深挖问题预案

| 面试官追问 | 你的回答要点 |
|-----------|-------------|
| "区块链上链慢怎么办？" | 异步上链，先返回"上链中"状态，后台轮询确认，交易流程不阻塞 |
| "物联网数据怎么保证可信？" | 多传感器交叉验证（视频+RFID+称重），异常告警人工复核 |
| "仓单拆分怎么实现？" | 原仓单状态置为"已拆分"，生成 N 张子仓单上链，链上记录拆分关系 |
| "三层回滚怎么做？" | Saga 模式，每步有补偿动作：区块链标记无效→WMS 回滚仓单→物联网标记误报 |

### 11. 难点三：多交易模式的可插拔引擎

> 速查结论与"为什么配置驱动"的决策话术见附录 C 决策 5。

#### 业务场景

支持多类交易模式：挂牌、竞价、询价、基差等。每种模式的**交易流程、结算规则、风控规则、合同模板**都不同，但会员管理、资金管理、仓储管理是共享的。

#### 技术难点

```
                    ┌──────────────┐
                    │  交易引擎核心  │
                    └──────┬───────┘
                           │
          ┌────────┬───────┼───────┬────────┐
          ▼        ▼       ▼       ▼        ▼
      ┌──────┐┌──────┐┌──────┐┌──────┐┌──────┐
      │挂牌模式││竞价模式││点价模式││预售模式││ ...  │
      └──┬───┘└──┬───┘└──┬───┘└──┬───┘└──────┘
         │       │       │       │
         ▼       ▼       ▼       ▼
    ┌─────────────────────────────────┐
    │      共享服务层                    │
    │  会员 │ 资金 │ 仓储 │ 物流 │ 风控  │
    └─────────────────────────────────┘
```

**核心挑战**：

| 问题 | 难点 |
|------|------|
| **模式差异大** | 点价需要实时期货行情，竞价需要定时撮合，挂牌是实时摘牌，流程完全不同 |
| **可扩展性** | 新增交易模式不能影响现有模式，需要开闭原则 |
| **配置化 vs 硬编码** | 过度配置化会导致复杂度爆炸，过度硬编码无法复用 |
| **风控规则差异** | 不同模式的风控阈值、保证金比例、涨跌停规则不同 |

#### 面试讲法

> "多类交易模式如果每个写一套，代码量爆炸且无法维护。我们用了**策略模式 + 模板方法模式**的组合：定义交易流程骨架（挂单→撮合→成交→结算→交收）作为模板方法，每种模式实现自己的策略类。风控规则用**规则引擎**（Drools/自研 DSL）外部化，不同模式绑定不同规则集。新增交易模式只需要实现策略接口+配置规则集，不动核心引擎。这和我在 Agent Harness 里做节点编排的思路一致——MainLoop 是骨架，每个 Agent 是可插拔的策略。"

#### 架构设计要点

```python
# 面试时可以画的简化代码
class TradeMode(ABC):
    @abstractmethod
    def create_order(self, req: OrderRequest) -> Order: ...
    @abstractmethod
    def match(self, order: Order) -> TradeResult: ...
    @abstractmethod
    def settle(self, result: TradeResult) -> Settlement: ...

class ListingMode(TradeMode):  # 挂牌交易
    def create_order(self, req): ...  # 实时摘牌
    def match(self, order): ...       # 即时匹配
    def settle(self, result): ...     # T+0 结算

class PricingMode(TradeMode):  # 点价交易
    def create_order(self, req): ...  # 需要期货行情
    def match(self, order): ...       # 点价时点匹配
    def settle(self, result): ...     # 当日结算
```

### 12. 难点四：点价交易的期现实时联动

> 速查结论与"为什么 Canal + 缓存服务"的决策话术见附录 C 决策 4。

#### 业务场景

点价交易中，挂牌方报价 = **期货实时价格 ± 升贴水**，摘牌方选择某个时点的价格摘牌。这意味着系统需要**实时获取期货行情、动态计算现货价格、在毫秒级窗口内锁定价格**。

#### 技术难点

```
期交所行情源 ──(WebSocket/FAST协议)──→ 行情接入网关
                                          │
                                    ┌─────┴─────┐
                                    │ 行情分发   │
                                    └─────┬─────┘
                    ┌─────────────────┼─────────────────┐
                    ▼                 ▼                  ▼
              ┌──────────┐    ┌──────────┐      ┌──────────┐
              │ 点价引擎  │    │ 前端推送  │      │ 风控监控  │
              │ 价格计算  │    │ WebSocket │      │ 波动告警  │
              └──────────┘    └──────────┘      └──────────┘
```

| 挑战 | 难点 | 量化指标 |
|------|------|---------|
| **行情接入延迟** | 期交所行情推送频率高（每秒数百 tick），需要低延迟接入 | 行业标准：<10ms |
| **价格锁定原子性** | 摘牌时必须锁定当时的期货价格，不能出现"摘牌时看到的价格和成交价格不一致" | 需要时间戳+版本号 |
| **行情分发性能** | 同时有数千交易商查看实时行情，需要高效广播 | 需支持万级并发推送 |
| **白盘/夜盘切换** | 期货有日盘和夜盘，行情源切换不能中断服务 | 需要无缝热切换 |
| **基差监控** | 期现价差（基差）实时计算+预警 | 数据延迟从 2-5 分钟降至 10 秒 |

#### 面试讲法

> "点价交易最核心的技术挑战是**价格的实时性和锁定原子性**。期货行情通过 WebSocket 接入，每秒数百个 tick，我们在行情接入层做了**背压控制**防止行情风暴打爆下游。摘牌时用'行情快照+版本号'机制——摘牌请求携带当前版本号，如果引擎当前版本号已更新则摘牌失败，需要重新确认价格，保证价格锁定的原子性。前端推送用 WebSocket 批量合并（100ms 窗口聚合成一帧），减少推送次数同时保持实时性。"

### 13. 难点五：全流程模块化的数据一致性

> 速查结论与"为什么 outbox 而不是 Seata/XA"的决策话术见附录 C 决策 3。

#### 业务场景

郑大 B2B 平台有 8 个核心模块（会员、交易、资金、结算、风控、合同、仓储、运输），一笔交易涉及**全部 8 个模块的状态联动**。比如：下单→冻结资金→生成合同→锁定仓单→调度物流→风控审核→结算→解冻资金。

#### 技术难点

| 问题 | 难点 |
|------|------|
| **跨服务事务** | 8 个微服务，一个交易流程跨全部服务，不能用数据库本地事务 |
| **部分失败处理** | 资金冻结成功但仓单锁定失败，需要回滚资金冻结 |
| **事件顺序保证** | 合同生成必须在交易成交之后，物流调度必须在仓单锁定之后 |
| **状态查询性能** | 交易全链路状态查询不能查 8 个服务，需要聚合视图 |
| **幂等+补偿** | 每个步骤都可能重试，必须幂等；失败必须可补偿 |

#### 面试讲法

> "8 个模块的状态联动，如果用分布式事务（如 Seata）性能太差，我们用了**事件驱动 + Saga 编排**的方案。核心交易流程定义为一个 Saga，每个步骤有对应的补偿动作。比如'冻结资金'的补偿是'解冻资金'，'锁定仓单'的补偿是'释放仓单'。事件通过 Kafka 传递，保证顺序性。状态查询用 CQRS 模式——写库用各服务本地库，读库用一个聚合视图（ElasticSearch/Redis），异步同步。"

#### Saga 编排示意

```
下单成功
  ├─→ 冻结资金 ──(失败)──→ 回滚订单
  ├─→ 生成合同 ──(失败)──→ 解冻资金 → 回滚订单
  ├─→ 锁定仓单 ──(失败)──→ 作废合同 → 解冻资金 → 回滚订单
  ├─→ 调度物流 ──(失败)──→ 释放仓单 → 作废合同 → 解冻资金 → 回滚订单
  └─→ 风控审核 ──(失败)──→ 取消物流 → 释放仓单 → 作废合同 → 解冻资金 → 回滚订单
```

#### 与你背景的关联

> 这和你 Agent Harness 中的**6 节点流水线**高度一致——微信公众号流水线（采集→清洗→生成→配图→排版→发布）也是多步骤、可补偿的 Saga 流程，可以直接用来类比。

### 14. 难点六：高并发交易撮合与流式风控

> 速查结论见附录 C 决策 1 / 决策 2（原第一部分 Q4 / Q6 速查未随迁，原手册已归档）。

#### 业务场景

竞价交易模式下，多个买方同时出价，系统需要**实时撮合 + 实时风控**——每笔出价都要检查保证金是否充足、是否触发涨跌停、是否异常交易。

#### 技术难点

| 挑战 | 方案 |
|------|------|
| **内存撮合** | 撮合引擎纯内存操作（类似交易所撮合），订单簿用红黑树/优先队列 |
| **流式风控** | 每笔订单实时过风控规则引擎，延迟 <5ms |
| **熔断降级** | 风控服务不可用时，交易是"拒绝"还是"放行"？需要熔断策略 |
| **峰值应对** | 竞价截止前集中出价，峰值可达日常 10-50 倍 |
| **数据持久化** | 内存撮合结果需要异步落库，宕机不能丢数据（WAL 机制） |

#### 面试讲法

> "撮合引擎参考了交易所的设计——订单簿维护在内存中，买单按价格降序、卖单按价格升序，撮合是 O(log N) 的红黑树操作。风控用流式处理，每笔订单过规则引擎，单次 <5ms。为了防风控故障导致交易中断，设计了**熔断+降级**策略：风控服务超时率超阈值时，切换到本地规则缓存（宽松模式），同时告警人工介入。撮合结果用 WAL（Write-Ahead Log）先写日志再撮合，宕机可恢复。"
