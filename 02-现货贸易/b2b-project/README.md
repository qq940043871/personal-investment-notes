# b2b-project · 项目实证档案

> **本目录回答一个问题：这套系统实际是怎么写的、实际能扛多少。**
> 证据标准：源码可回溯（`文件:行号`）、压测口径可核对、缺陷可复现。凡是"应该怎样设计"的推演，不写在这里。

---

## 一、这一层负责什么（边界）

| 内容类型 | 归属 | 说明 |
|---|---|---|
| 源码走读、类与方法的实际行为、缺陷清单、容量测算、压测计划、改造实录 | **本目录** | 必须是"代码里能看到 / 压测能量到"的事实 |
| 设计为何如此、方案取舍、面试追问口径、机制图 | `../03-架构决策/` | 回答"为什么这么设计、被追问怎么答" |
| 通用工程问题（高可用 / 缓存 / 分库分表 / JVM / 监控 等 20 章） | `../电商项目问题指南/` | 行业方案为主，逐章标注经验锚点 |
| 业务价值、客户案例 | `../01-业务与价值/`、`../02-客户与案例/` | 业务语言，不含实现 |

**不写进本目录的三类内容**：

1. **没有证据的架构主张** —— 至少要有反编译源码行号、配置项名称或实测数据之一，否则写"待核实"。
2. **行业通用做法的科普** —— 那是 `电商项目问题指南` 的活。
3. **同一结论的第二份副本** —— 见第五节「单一信息源」。

## 四、三条推荐路径

1. **面试叙事路径**（20 分钟）：`overview.md` 的"三个死结 + 四层异构桥接" → 手绘架构图 → `5万QPS与1000TPS-容量攻坚全案` 的 §7 未决项 → `dataShare-并发能力与缺陷清单` 的 §2.8 最窄瓶颈。**结论先行、数字带口径**。
2. **接手/排障路径**：`overview.md` 架构图 → `midservice/HandlerController` 的请求链路（协议路由 → 校验 → 反射调用 → 响应治理） → `midservice/慢查询慢服务故障传导分析` → `../03-架构决策/生产问题排查/12-生产排查步骤-四类场景与六步SOP.md`。
3. **容量攻坚路径**：`5万QPS与1000TPS-容量攻坚全案` 阶段 0（先证实）→ `连接池参数配置建议` → `全链路容量压测计划` → 回到全案 §8 验收门槛。

## 六、证据等级（写文档时必标）

| 标记 | 含义 |
|---|---|
| 【代码证实】 / `文件:行号` | 反编译源码可查 |
| 【配置证实】 | 配置文件 / DB 表里有值 |
| 【静态推算】 | 按 RT / Little 定律推出，未实测 |
| 【设计目标】 | 方案里写了，未验证 |
| 【未压测】 / 待核实 | 方法已成文，结果未产出 |

> 源码为 JD-Core 0.6.0 反编译还原，业务代码的类名/行号以此为准；配置与线程模型以生产 `jstack` / `jmap` 实测为准。
