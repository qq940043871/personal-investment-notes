5 Whys 追问法 & 业务-技术映射地图

B2B技术经理速查卡 · A4单页 · 从技术排障到业务洞察

一、5 Whys 追问法

丰田生产方式迁移 · 从表面症状到决策层根因

  1. L1 现象 可见的故障表现是什么？服务超时 / 数据丢失 / 接口报错 / 用户投诉
  2. L2 操作 是什么操作触发了这个现象？找出导致异常的具体行为或变更：上线/配置/流量
  3. L3 原理 底层技术原理层面的根因？并发竞争 / 缓存失效 / 索引失效 / 内存碎片 / GC
  4. L4 设计 架构设计是否存在缺陷或权衡失当？耦合设计 / 缺少熔断 / 数据模型不合理
  5. L5 决策 最初的技术选型决策是否有根本偏差？选型假设 / 容量预估 / CAP取舍 / 成本约束

实战案例：订单查询慢

L1 查询P99从200ms→8s
L2 新功能引用了WHERE DATE()函数
L3 函数运算破坏B+Tree有序性→索引失效→全表扫描
L4 设计阶段未识别高频时间范围查询模式
L5 缺少查询模式评审机制，索引策略未按业务查询驱动

▸ 面试答到L3=及格，L4=加分，L5=技术决策者水平

二、业务-技术映射地图

三维标注体系 · 让技术人员看到代码背后的业务代价

三维标注结构

维度 标注内容 回答的问题
① 业务语言 用业务方能听懂的语言描述该环节的业务目标与价值 "这一步在业务上干什么？"
② 技术模块 标注支撑此环节的技术模块及依赖关系 "技术上是哪些系统在跑？"
③ 业务损失 量化故障后的业务代价（金额/客户/合规） "挂了会损失什么？"

示例：大宗交易核心链路

业务环节 技术模块 & 依赖 故障代价
挂牌报价 交易模块 → 行情服务 → MinIO 挂不上 = 没生意
询价撮合 C撮合引擎 ← DS桥接 ← 业务中台 撮不上 = 不成交
合同签约 合同模块 → 电子签章 → 模板引擎 签不了 = 前功尽弃
结算支付 支付网关 → 银行接口 → 对账服务 付不了 = 直接资损
履约发货 履约保证 → 物流接口 → 状态机 发不出 = 违约赔付

两条方法的关系

5 Whys 从技术故障向下钻（技术→原理→决策）；映射地图从业务链路向上联（业务→技术→代价）。两者合起来构成 "从代码到老板" 的完整叙事链。

面试中的用法

问技术题 → 用 5 Whys 展示深度（至少到L3）；问业务题 → 用映射地图展示全局视野；问价值题 → 映射地图的"业务损失"一列直接翻译为"我守住的是什么"。

落地口诀

每个事故追五层，每个环节标三栏。
排障不是结束，是学习开始。
代码背后的钱，才是真正的价值。
