# B2B 全链路容量探顶压测计划

> 目标：**把 C 内存撮合引擎、DB、网关三层分别打到瓶颈**，拿到各层真实容量天花板，并验证「慢协议不拖慢快协议」的隔离效果。
> 方法论：双口径（缓存命中/未命中）+ 阶梯/稳态/洪峰 + 分层逐层加压 + P95/P99 判定。

---

## 一、压测目标与范围

### 1.1 三个「打满」+ 一个「验证」

| # | 目标 | 含义 | 判据 |
|---|---|---|---|
| T1 | **打满 C 撮合引擎 CPU** | 撮合计算（%usr）逼近多核上限 | 所有核 `%usr` ≥ 90%，撮合笔/秒不再随并发增长 |
| T2 | **打满 DB** | 连接数 / CPU / IO 任一逼近上限 | `Threads_connected` 到 `max_connections`，或 CPU/IO util 打满、慢查询暴涨 |
| T3 | **打满网关** | 网关 CPU 打满或线程/连接池/吞吐封顶 | Tomcat 线程耗尽、DS 池 `maxCon` 耗尽、或 CPU 打满、吞吐拐点 |
| V1 | **协议隔离验证** | 慢协议注入，快协议无感 | 慢协议熔断 fail-fast，快协议 P99 不劣化 |

### 1.2 打满顺序（关键：逐层隔离加压）

一次只针对**一层**加压，其余层留足余量，否则无法定位「这层的天花板到底是多少」：

```
第一轮：只打网关（后端用缓存/桩，不压后端）      → 拿到网关吞吐上限
第二轮：只打 DS + 撮合（网关留余量，DB 用测试库） → 拿到撮合 CPU 上限
第三轮：只打 DB（走 DB 类协议，绕过撮合）         → 拿到 DB 容量上限
第四轮：全链路联合压测（按业务比例混合）          → 找到整条链路的最窄瓶颈
```

## 二、系统拓扑与被测对象

```
压测端(JMeter/Python 多台)
   │  HTTP /api、/toBack
   ▼
midservice（Tomcat 网关，HandlerController / ToBackController）
   │  DSClientAPI（11字节二进制协议）
   ▼
dataShare（NIO 数据中心，HandlerImpl.run 协议分发）
   │  connType 分派
   ├─ connType=0 → Redis / Kafka / JDBC（系统内置）
   ├─ connType=1 → Hessian 微服务
   ├─ connType=2 → 私有 TCP 协议栈（撮合主链路）
   └─ connType=3 → HTTP
   ▼
后端：C 内存撮合引擎 / DB(MySQL) / Redis / 微服务
```

**被测对象清单**：

| 层 | 组件 | 压测关注点 |
|---|---|---|
| 网关 | midservice（Tomcat） | Tomcat `maxThreads`、CPU、GC、DS 池 `maxCon`、per-user 锁 |
| 数据中心 | dataShare（NIO） | IO 线程数、`ansyKey`、后端池 `SOCKET_MAX`、全局归还锁 |
| 撮合 | C 内存撮合引擎 | 各核 `%usr`、撮合笔/秒、撮合延迟、队列深度 |
| 数据 | MySQL / Redis | QPS/TPS、连接数、CPU/IO、慢查询、buffer pool 命中率 |

## 三、测试环境搭建（需要什么）

### 3.1 拓扑与规模

- **被测环境独立一套**，不碰生产；规格与生产**同构**（缩配需在报告中标注缩配比例与换算）。
- **压测端 2~4 台**（JMeter 分布式 `-R` 或 Python 自研脚本），与被测系统**同机房/同网段**，排除网络抖动成为假瓶颈。

### 3.2 数据准备（决定压测是否可信）

| 数据 | 内容 | 备注 |
|---|---|---|
| 测试账号 | 覆盖三种 `USERFLAG`：1 个人/管理员、2 机构、3 第三方 | 登录/鉴权链路需要 |
| 撮合场次 | 挂牌/竞价/询价/基差各建**测试场次**，`BIDSTATE=1`（可竞价） | **写操作仅限测试场次** |
| 商品/合约 | 挂牌品种、行情模板、交货地等基础数据 | 供 GP9xxx 公开查询协议 |
| DB 配置 | `TB_DS_PROTOCOL`（含 `SOCKET_MAX/SOCKET_INIT/SOCKET_TIMEOUT`） | 决定后端池，必须先确认 |
| Redis 预热 | 行情/公告/配置等缓存数据 | 命中口径的前提 |

### 3.3 监控体系（每台被测机）

```bash
# 通用：CPU/内存/网络/中断
top -H / htop（看每核 %usr %sys %softirq）
dstat -cndm 5、vmstat 1、iostat -x 1、sar -n DEV 1

# 网关/DS（JVM）
jstack <pid> | grep -A5 "http-nio"       # Tomcat 线程数 & 是否打满
jstack <pid> | grep -A5 "nio.reactor"    # ★ 验证 dataShare 是否单 IO 线程
jstat -gcutil <pid> 1000                 # GC 频率/暂停
jmap <pid> | grep -i ConnectPool         # 实际连接池大小（核实 maxCon 是否=5）

# DB
SHOW PROCESSLIST / SHOW GLOBAL STATUS    # Threads_connected、Com_select/insert...
SHOW GLOBAL STATUS LIKE 'Innodb_%'       # buffer pool 命中率、行锁等待
慢查询日志（long_query_time=0.1）

# C 撮合引擎
引擎自带队列深度/撮合笔数/延迟指标；无则 top -H 看每核 + /proc/interrupts
```

> 建议统一接 **Prometheus + node_exporter + Grafana**，把 `%usr`、连接数、QPS、撮合笔数做成一块大盘，分层打满时一眼看出瓶颈落在哪层。

## 五、分层打满策略（核心）

### 5.1 打满 C 撮合引擎 CPU（T1）

**原理**：撮合引擎 CPU 密集在「撮合匹配计算」，打满是靠**订单量**而非请求数——要制造大量真实撮合。

**方法**：

1. 用**竞价出价**打：底价爬梯（每次出价 = 实时底价 +1），连续出价触发价格优先+时间优先的撮合匹配，撮合量巨大。
2. 高频**挂牌 + 撤单**：挂牌触发撮合，撤单触发订单簿回滚，双向都吃 CPU。
3. **基差点价**：涉及基差计算，CPU 密集。
4. 用 Python 脚本直发 `connType=2` 私有协议，**绕过网关限流直连 DS**（先测撮合引擎裸容量），再走全链路复测。

**监控与判据**：

```bash
top -H -p <撮合进程>   # 看所有核 %usr 是否都逼近 90%+
# 若只有单核 100%、其余核空闲 → 撮合引擎本身是单线程或锁竞争，这是重大瓶颈发现
```

| 指标 | 打满判据 |
|---|---|
| 各核 `%usr` | 全部 ≥ 90%，且撮合笔/秒不再随请求增长 |
| 撮合笔/秒 | 到达平台期（拐点） |
| 撮合延迟 P95 | 开始劣化（> 基线 2 倍） |
| `%softirq` | 若软中断过高，说明瓶颈在网卡收包而非撮合计算，需区分 |

> **关键观察点**：撮合引擎若「单核打满、多核空转」，说明撮合是单线程模型——这与 dataShare「单 IO 线程」假设一脉相承，是整条链路的根本瓶颈，要单独记录。

### 5.2 打满 DB（T2）

**三种打满路径，分别对应不同瓶颈**：

| 路径 | 打法 | 打满的目标 |
|---|---|---|
| **连接数打满** | 高并发压 `00010101` 配置读取（**每请求一次 JDBC**），或慢查询协议 | `Threads_connected` 逼近 `max_connections` |
| **CPU 打满** | 压复杂查询协议（JOIN/排序/聚合/大表扫描） | DB 进程 `%usr` 打满 |
| **IO 打满** | 压下单落库 + Outbox 写（写密集） | `iostat` 的 `%util` ≈ 100% |

**监控与判据**：

```sql
SHOW GLOBAL STATUS LIKE 'Threads_connected';   -- 连接数
SHOW GLOBAL STATUS LIKE 'Com_select';          -- 读 QPS
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read_requests';  -- 命中率分母
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_waits';             -- 锁等待
```

| 指标 | 打满判据 |
|---|---|
| `Threads_connected` | ≥ `max_connections`（连接耗尽） |
| DB `%usr` / IO `%util` | ≥ 90% / ≈ 100% |
| 慢查询数 | 显著增长（`long_query_time=0.1`） |
| buffer pool 命中率 | 明显下降（< 90%，说明数据在刷盘） |

> **重点验证**：源码走读发现 `PubConfigCache`（5s TTL）**已实现但从未接线**，导致 `00010101` 每请求查一次库。压测 DB 时用「配置读取协议」可以**定量复现这个 N+1 热点**，作为改造前基线。

### 5.3 打满网关（T3）

**网关的瓶颈不止 CPU 一种，要区分「CPU 打满」和「资源打满」**：

| 瓶颈类型 | 制造方法 | 判据 |
|---|---|---|
| **CPU 打满** | 高频协议 + 关闭缓存（未命中口径），把序列化/反射/校验/脱敏/敏感词吃满 | 网关 `%usr` ≥ 90% |
| **线程打满** | 高并发 + 慢后端（或人为注入慢协议），Tomcat 线程被占死 | `jstack` 看到 `http-nio` 线程全在等后端 |
| **DS 池打满** | 高并发 DS 调用，打满 `maxCon`（源码疑似=5） | `jmap` 看 ConnectPool，或压测第 6 并发起 RT 突增到 5s |
| **per-user 锁封顶** | 单用户单 API 高并发 | 吞吐封顶在 1/RT，与并发数无关 |

**方法**：

1. **高频 API**：登录 `MT1100`、公开查询 `GP9xxx`、批量协议 `directives`（一次 20 协议）。
2. **双口径**：缓存命中（PUB/FRM/CLI 命中）vs 未命中（`is.open` 关缓存或换参数），两轮分别测——命中口径看纯计算上限，未命中口径看穿透后端的上限。
3. **核实关键配置**（压测前必做，决定网关天花板）：

```bash
grep -o 'maxThreads="[0-9]*"' $CATALINA_HOME/conf/server.xml   # Tomcat 线程
grep -rn "setMaxCon\|setInitCon" $APP_HOME/1018/core/          # DS 池是否=5
# is.open.syncLock + syncLockMap 取值（决定 per-user 锁是否生效）
```

### 5.4 打满 dataShare 数据中心（补充，T3 依赖它）

- 用 Python 直发二进制协议打 DS 入口，观察 `jstack` 里的 `nio.reactor` 线程。
- **判据**：若只有 1 个 reactor 线程在跑 `HandlerImpl.run` → 单 IO 线程模型成立，DS 的 TPS ≈ 1/RT_后端；这是压测**最重要的单一结论**，直接改写全链路容量。

## 六、场景与负载模型

### 6.1 场景阶梯（每层独立跑一套）

| 场景 | 并发/速率 | 时长 | 目的 |
|---|---|---|---|
| S0 冒烟 | 1~10 | 2min | 脚本/断言/场次校验 |
| S1 阶梯 | 50 | 5min | 基线 |
| S2 阶梯 | 100 | 5min | 找拐点 |
| S3 阶梯 | 200 | 5min | 找拐点 |
| S4 阶梯 | 500 | 5min | 逼近上限 |
| S5 稳态 | 拐点前 80% | 15~20min | 稳定性、是否泄漏 |
| S6 洪峰 | 集合点瞬时爆发 | 单独跑 | 瞬时过载表现 |
| S7 长稳 | 稳态量 | 2~4h | 资源泄漏、GC、连接泄漏（需运维配合） |

### 6.2 双口径

| 口径 | 做法 | 用途 |
|---|---|---|
| **A 未命中（最坏）** | 关缓存 / 每次换参数，穿透到后端 | 暴露后端/DB 容量 |
| **B 缓存命中（常态）** | 缓存预热 + 固定参数 | 干净的网关/协议口径，**指标判定以此为准** |

### 6.3 写操作安全

- 出价/下单仅限**测试场次**，触发脚本带显式确认参数；定价跟随实时底价（爬梯），先试写一笔再批量。
- 避开生产高峰与闭市窗口；长稳勿跨闭市。

## 七、指标与判定

参考 M 框架裁剪为「分层容量指标」：

| 层 | 指标 | 判定 |
|---|---|---|
| 网关 | 吞吐 QPS、接口 RT P95/P99、错误率 | P95 ≤ 500ms、P99 ≤ 1s；错误率 < 0.1%（稳态） |
| 网关 | Tomcat 线程利用率、GC 频率 | 线程不 100% 占满、无频繁 FGC |
| DS | 协议吞吐、IO 线程模型、`ansyKey` 池 | 单 IO 线程成立则记录为架构瓶颈 |
| 撮合 | 各核 `%usr`、撮合笔/秒、延迟 P95 | 打满判据见 §5.1 |
| DB | QPS/TPS、`Threads_connected`、CPU/IO、慢查询 | 打满判据见 §5.2 |
| Redis | QPS、连接数、命中率 | 命中率 > 95% |
| 全链路 | 最窄瓶颈位置 | 用 min(各层容量) 公式定位 |

> 判定一律用 **P95/P99，不用平均值**——长尾才是容量风险。

## 八、协议间隔离验证（V1，对应前文的舱壁改造）

**目的**：验证「慢协议不拖慢快协议」，也是舱壁隔离改造的验收标准。

```
1. 基线：快协议 A（如行情 GP9xxx）打到 3000 QPS，记录 A 的 P99
2. 注入：慢协议 B（如撮合，注入 5s 后端延迟 / 触发超时），并发打到其上限
3. 观察：A 的 P99 是否波动

  改造前（现状）：A 的 P99 从 50ms 飙到 5s+  —— 复现「慢拖快」✅
  改造后（预期）：A 的 P99 稳定在 50ms 内 —— 舱壁 + 熔断生效 ✅
```

再叠加**熔断验证**：让 B 持续慢调用，观察 B 是否触发熔断 fail-fast、C 协议（另一快协议）是否全程无感。

## 九、执行规范与避坑

1. **写操作必须业务方指定测试场次 + 书面授权**，避开真实高峰（交易类 8:30–17:30）。
2. **逐层加压**：一次只打一层，否则拿不到单层天花板（§1.2）。
3. **双口径分开统计**：命中/未命中不合并，结论必歪。
4. **健康窗口复测**：若某轮所有指标统一劣化（空载基线抬升），判定用复测值，劣化单独归因。
5. **jtl 追加写**：重跑先删旧文件，每轮新文件名。
6. **集合点类名是 `SyncTimer`**，`groupSize=0` 全量汇合 → 洪峰单独跑，别卡其他组。
7. **中止照实标注**「部分数据（中止）」，从 jtl 捞出来补录，别当 0。
8. **熔断护栏**：滚动错误率（近 200 次）超阈值自动停压。
9. **时钟**：延迟测量两端同机；跨机先 NTP。
