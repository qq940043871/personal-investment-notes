## 0. 定位与口径（开场必背）

- **midservice**（`HandlerController.java`，2581 行，反编译自 `midservice-1.1.188.228.5.jar`）＝ 证券/金融中台**唯一统一南北向入口**，本身不写业务，只做 6 件事：**协议路由 → 安全校验 → 参数校验 → 反射调用 → 响应治理 → 可观测**。
- 业务逻辑全在 `handler/*` 54 个执行器，靠 `api.json` 配置表动态绑定（**加接口零发版**）。
- **两个组件**：`midservice`＝流量治理**执行者**；`midmon`＝流量治理**观察者**（只发现报告，动作由 midservice 执行）。
- **双通道**：前台 `/api`（面向互联网 C 端，纵深防御）；后台 `/toBack`（面向内网运营，按菜单功能码 `func_id` 授权）。

## 第一部分：安全防护措施（源码级，八层）

### 1. 传输与加密层

| 措施 | 实现 |
|---|---|
| 混合加密闭环 | 客户端 RSA 加密传 AES Key → 业务体 `AES/CBC/PKCS5Padding` 加密；**响应用同一 AES Key 回加密** |
| 明文通道收口 | 非加密模式每个协议必须进 `rsaAllowMap` 白名单，否则 `"no auth"` |
| 公钥下发 | `/api/encrypt/publicKey` 返回 `{modulus, publicExponent}` |

### 2. 鉴权与认证层

- **登录强度分级 `checkLoginType`（四套体系）**：契约锁 QYS / 上上签 SSQ / 平台认证 PLAT / 默认分级。默认把 `LOGINTYPE` 映射 1/2/3 级：**查询类密码登录即可，交易类强制证书/UKey**（金融合规核心设计）。
- **Token 自动巡检**：被动失效检测，Redis 被踢的 Token 靠巡检发现并 `logout_clear`（清 Cookie → removeToken → DS 注销 → 广播登出）。
- **AppKey 验签**：`AppKeyUtils.verifySignature`，第三方走 `USERFLAG=3` 通道。

### 3. 防重放 / 防篡改层

- **防重放**：`sha256(curtime+"czzdit") == signdata`，且 `|now-curtime| ≤ 60000ms`，超窗即拒。
- **协议号防伪**：长度 >32 时校验 `首16位 + 尾16位 == md5(中间部分)`，防协议号枚举篡改。
- **客户端签名验签**：客户端私钥签名 + 服务端公钥验签。

### 4. 参数校验与注入防护层

- **注入防护**：`Validate.isSafe()` 拦 SQL 注入 / XSS。
- **参数校验 `valide()`**：必填、长度截断、正则、默认值、类型严格转换，规则全来自 `api.json`。
- **敏感词过滤**：`SensitivewordFilter`（协议级开关）。

### 5. 访问控制 / 越权防护层

- **协议级授权 `checkApiAuth`**：Redis `3002_API_AUTH_LIST`。
- **外部机构代客 `checkPowers`**：`SF_` 前缀强制 `USERFLAG=2` + `1001_AGENTFIRM_USERID` 代理关系校验，**防机构越权代客操作**（监管硬要求）。
- **网关隔离**：`APISTYLE=inner` 内部协议在网关模式直接拒绝，**防内部接口被外呼**。
- 其他：`DF_` 前缀=管理员、`checkAllowThird` 强制机构通道、`checkDaPing` 大屏白名单、`checkStatus` 挂起、`checkValidDate` 有效期、`checkAgree` 协议签订。

### 6. 幂等与并发防护

- **Greencard 幂等卡**：解决客户端超时重试导致重复执行，失败重试带卡号、≤4 次复用、超限废弃。
- **用户维度串行锁**：`ReentrantLock(api_tokenId)` + finally 释放，防重复下单。
- **批量上限**：`maxMultiApiCount`。

### 7. 响应治理与信息泄露防护

- **三层信息泄露防护**（源码亮点）：
  1. SQL 关键字脱敏：响应含 `insert/update/select` → 替换「数据库异常」；
  2. 连接池降噪：`could not get jdbc` 等 →「系统异常，可忽略」；
  3. 调试开关：`develop.error_append` 控制错误码前缀。
- **出参字段级脱敏 `doAuthRtn`**：协议级配置脱敏字段，命中替换 `*****`。
- **日志脱敏**：`api.json` 标 `[隐私]` 的参数自动进 `privateParamNames`，日志里替换 `******`。
- **Cookie 安全**：自定义 `NewCookie` 支持 `SameSite`，`SameSite=None` 时**自动 `setSecure(true)`**。

### 8. 审计与可观测

- **安全审计日志**：登录/注销/改密/重置密码全量留痕 → `publishInfo("1018_APP_LOG")`，满足等保留痕。
- **全链路 logKey**：`ThreadLocal` 贯穿 `[api][version][serialNo][ip][port][tokenId/userId/phone]`。
- **三套日志流**：全量 DEBUG、慢接口（>1s WARN）、监控协议独立流。

## 渗透测试与 DDoS 攻击防护（攻击视角）

> 口径纪律（务必诚实）：**渗透测试和 DDoS 是两类不同攻击**，midservice 能管的范围不同。`电商项目问题指南/17-安全防护体系.md` 的"个人经验锚点"原文明确：**DDoS 高防清洗、WAF 规则运营、风控反欺诈模型属行业通行方案，本人未主导过大规模安全攻防体系**——面试时不可把高防/WAF 讲成自研。

### 1. 先分清两类攻击

| | 渗透测试 | DDoS |
|---|---|---|
| 本质 | 找**应用层漏洞**（SQL 注入、越权、上传、逻辑漏洞） | **资源耗尽**（带宽/连接/CPU/线程） |
| 防护位置 | 应用层（代码、网关） | 网络层（高防清洗）+ 应用层（限流限速） |
| midservice 能管 | ✅ 大量直接对应 | ⚠️ 只能管"应用层"那部分 |

### 2. 渗透测试防护映射（源码直接对应）

| 渗透测试检查项 | midservice 防护措施（源码） |
|---|---|
| SQL 注入 / XSS | `Validate.isSafe()` 拦注入 + 参数类型严格（`int` 不收 `"1 or 1=1"`）+ 危险字符拒 |
| 越权（水平/垂直） | 请求里 `tenantId/customerId/userId` **不可信**，只信会话并比对；`checkPowers` 防机构代客越权；协议授权；`APISTYLE=inner` 隔离 |
| 文件上传 | 扩展名白名单 + MIME + **魔数校验** + 服务端重命名 + 隔离存储 + 下载一次性令牌 |
| 重放攻击 | 时间戳 `sha256` + 时间窗 60s + nonce 去重 |
| 篡改/伪造 | 客户端私钥签名 + 服务端公钥验签 |
| 协议号枚举 | 协议号 MD5 防伪 + 契约注册表白名单收口 |
| 扫描器探测 | **闸门排序**：非法接口编码在"契约校验"关（本地 Map）即拒，一次请求代价 = 查一次本地 Map |
| 信息泄露 | 三层信息泄露防护 + 输出白名单 + 字段级脱敏 |

### 3. DDoS 防护分两层（诚实口径）

**① 网络层 / 流量型 DDoS（midservice 管不了）**：SYN Flood、UDP 放大、CC 大流量 → 靠**运营商/云厂商 DDoS 高防清洗 + WAF**，流量在进网关前被清洗。**属行业方案，非本项目自研。**

**② 应用层（midservice 能做的）**：

| 防线 | 实现 |
|---|---|
| 三级配额限流 | 租户级 / 应用级（AppKey）/ 接口级，慢接口全局限流 200 QPS |
| 触发源四类识别 | ①频率超限 ②高频错误 ③**扫描特征**（非法编码、参数连续失败、路径穿越）④**行为异常**（同 IP 切换多账号、异地并发、脚本特征） |
| 处置阶梯 | 告警 → 限流(429) → 临时封禁 15 分钟（自动解封）→ 黑名单（人工解封+申诉） |
| 防误伤 | 内部互调/健康检查/监控探针白名单、双信号校验、机构客户触发同步通知值班 |
| 单账号互斥 | 同账号异地登录踢下线 |

### 4. 面试口径

1. **DDoS 高防清洗、WAF、风控反欺诈按"通用方案"讲**——口径："入口前面有运营商高防 + WAF，网关做应用层限流和黑名单"。
2. midservice 是**应用层防线**：渗透测试应用层漏洞它源码管得全；纯流量型大流量 DDoS 由高防承担——两层各司其职。
3. 一套话术：**"渗透测试靠网关纵深防御——注入防护、越权校验、上传魔数校验、防重放签名；DDoS 分两层——网络层靠高防清洗和 WAF（行业方案），应用层靠三级配额限流、扫描特征识别、处置阶梯封禁。"**

## 第二部分：熔断限流与慢协议隔离（现状 vs 目标）

### 1. 源码现状：只有"简化/人工版"

| 能力 | 源码实际 | 缺失 |
|---|---|---|
| 熔断 | **系统级全站熔断**（人工 `SysPara 40310`，发版维护用） | 无单协议自动熔断、无三态/半开探针 |
| 限流 | **批量协议数量上限** `maxMultiApiCount` | 无 QPS 限流、无租户/接口分级配额 |
| 隔离 | 无 | 无舱壁、无超时分层 |
| 间接缓解 | 三级缓存（挡读流量）、用户维度锁、Greencard、慢接口告警（只观察不阻断） | — |

### 2. 根因（一句话背下来）

> **一请求一线程、自顶向下全同步阻塞，且协议之间共享同一批执行资源。** 具体三个病灶：
> ① 共享 Tomcat 线程池 → 慢协议占住线程挤占他人；
> ② 全局串行点（`DSUtils.getClient()` static synchronized ×135 调用点、`releaseConnection()`、`ShardedReidsPool.getConnect()`）；
> ③ 无熔断无舱壁 → 故障沿共享资源横向扩散。

### 3. 事故佐证（瓶颈后移）

> 扩容前：慢接口占用网关工作线程，**队头阻塞拖垮整机吞吐** → 扩容 ×5 后：入口容量放大、DB 出口不变，**几分钟打穿 DB 全站不可用**。

### 4. 目标态设计（五层防线 + 四支柱）

**五层防线**：网关限流/熔断/降级 → 后端线程池隔离/队列削峰 → 缓存 90% 命中 → DB 连接数/慢查询治理 → 架构规范兜底。

**四支柱（协议互不影响）**：异步化（资源不被阻塞占用）＋ 舱壁（资源不被共享争抢）＋ 熔断（故障不扩散）＋ 无状态（容量可水平扩展）。

**故障隔离四件套**：

| 机制 | 关键设计 |
|---|---|
| 熔断器 | 三态 CLOSED/OPEN/HALF_OPEN；`slowCallRate + slowCallDuration` **专识别"慢"而非"错"**；熔断后 fail-fast 释放资源 |
| 超时 | 逐层递减：网关 1s > 后端 800ms > DB 500ms > JDBC 400ms；**不自动重试**（幂等+对账兜底） |
| 限流 | 每协议 QPS 令牌桶；慢接口全局限流 200 QPS，单实例 40 QPS |
| 背压 | 有界队列 + 拒绝策略（拒绝而非无限堆积） |

### 5. 配置基线速查（一张表背完）

| 层 | 参数 | 值 | 推导 |
|---|---|---|---|
| 网关 | 慢接口全局限流 | 200 QPS | DB 上限 230 × 60% |
| 网关 | 单实例限流 | 40 QPS | 全局 ÷ 5 实例 |
| 网关 | 接口超时 | 1s | ＞ 后端 800ms ＞ DB 500ms |
| 网关 | 熔断 | 慢/异常 ≥50%，熔断 5s | 滑动窗口 10s/20 请求 |
| 后端 | 慢接口线程池 | core 15 / max 30 / queue 100 | 在途 = 40×0.3=12 |
| 后端 | 连接池 | max 20 / min 5 / timeout 1s | 5×20=100 连接 |
| 后端 | 单查询条数 | ≤200，必须 limit | SQL 红线 |
| 缓存 | L1 本地 / L2 Redis | 30s / 5~30min±10% | 命中率 ≥90% |
| DB | max_connections | 200 | Σ连接池 + 运维 100 |

### 6. 隔离验收硬标准（慢协议注入压测）

> 注入 5s 慢协议 → 看快协议 P99：**隔离前从 50ms 飙到 5s+，隔离后稳定在 50ms 内**，即为生效。

## 第三部分：面试速答（90 秒）+ 追问预案

### 速答脚本

> midservice 是自研 Java Web 网关，南北向唯一入口，只做横切的事。安全上分了八层：传输 RSA+AES 混合加密闭环、四套登录认证体系（交易类强制证书）、防重放+协议号防伪、参数注入防护、协议级授权+机构代客防越权、幂等卡+用户串行锁、三层信息泄露防护+字段级脱敏、审计留痕。
>
> 但熔断限流这块，**现状是短板**：只有人工开关的全站熔断和批量协议数量上限，没有自动熔断、没有 QPS 限流、没有舱壁隔离。慢协议和快协议共享 Tomcat 线程池和三处全局锁，慢协议队头阻塞会横向扩散——我们真实发生过"网关扩容把 DB 打穿"的事故，本质是**瓶颈后移**。
>
> 治理方案是五层防线加四支柱：异步化、舱壁隔离（慢接口独立线程池 15/30/100）、熔断（慢调用≥50% 熔断 5s 半开探针）、限流（慢接口 200 QPS，用利特尔法则反推：DB 安全吞吐 230×60%）、超时逐层递减不重试。验收靠慢协议注入压测：快协议 P99 不波动才算隔离成功。

### 追问预案表

| 追问 | 回答要点 |
|---|---|
| 为什么扩容反而打穿 DB？ | 瓶颈后移：入口 ×5、出口不变、中间无闸门；扩容是放大器不是解药，先限流再扩容 |
| 200 QPS 怎么定的？ | 反推法：DB 安全吞吐 = 连接数÷SQL RT×利用率 = 100÷0.3×0.7≈230，取 60% 水位 |
| 为什么不直接调大连接池？ | 连接数多≠吞吐高，DB CPU/IO 是硬上限，连接多了排队更长更慢 |
| 线程池隔离 vs 信号量隔离？ | 慢接口/独立下游用线程池（Bulkhead）；快接口/纯缓存路径用信号量 |
| 查询接口能异步削峰吗？ | 不能，查询是同步语义，靠"隔离+限流+缓存"；异步只适用写入/通知类 |
| 超时为什么不能重试？ | 重试会把故障放大成流量风暴；靠幂等卡 + 对账兜底 |

## 附录：设计文档 vs 源码实现 差异对照

| 设计文档主张（目标态） | 源码实际实现（现状） | 差异风险 |
|---|---|---|
| 入参白名单（未定义字段**拒绝**） | 参数校验以 `api.json` 声明为准 | 需核对是否严格执行 |
| 防重放签名用 HMAC-SHA256 | `sha256(curtime+"czzdit")` + 时间窗 | 硬编码盐属"混淆"而非"认证" |
| IV 应随机且与 Key 不同 | `aesKey.getBytes()` 同时当 Key 和 IV | **不符合 CBC 语义**，存在模式攻击风险 |
| 单接口自动熔断 + 半开探针 | 仅人工全站熔断 | 慢协议无法自动 fail-fast |
| 舱壁隔离（慢接口独立线程池） | 无，共享 Tomcat 线程池 | 慢协议队头阻塞横向扩散 |
| 每协议 QPS 限流 | 仅批量协议数量上限 | 无流量级保护 |
