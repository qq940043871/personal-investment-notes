# 容量目标实现方案：5 万 QPS + 1000 TPS

> 目标：**50000 QPS（读）+ 1000 TPS（写）**，在现有架构上如何实现？必须改造时，给出**最少改造**方案。
> 核心结论：**读和写是两条链路，必须分开算、分开改造**——读走「Redis 直连 + 缓存」短链路，写走「dataShare 完整链路」，读写物理隔离。

---

## 一、先拆指标：QPS 与 TPS 不是一回事

| 指标 | 本质 | 典型接口 | 链路 |
|---|---|---|---|
| **50000 QPS** | 读（查询） | 行情快照、挂牌品种、合约/模板、公告、配置 | 网关 → 三级缓存 / Redis（可**不穿透 DS**） |
| **1000 TPS** | 写（事务） | 撮合、下单、出入金、冻结 | 网关 → dataShare → C 撮合 / 微服务 → DB |

> 读是写的 50 倍，符合「读多写少」。**如果读也走 dataShare 慢链路，dataShare 的单 IO 线程（待实测）会把 5 万 QPS 直接卡死在 ~100 TPS**——所以读写分离是前提，不是可选项。
>
> ⚠️ 另一个隐蔽来源：**读 QPS 里很大一部分是前端轮询产生的**（行情、竞价最优价、出价记录等实时数据定时轮询），`QPS = 在线用户数 × 轮询频率`。这些实时数据恰好「变更快 + 强一致、不可缓存」，轮询是 QPS 的放大器，需用**主动推送**从源头削减（见《竞价详情页轮询改造-WebSocket事件驱动方案》）。

---

## 二、现状架构的容量天花板（能到多少）

### 2.1 读（QPS）

| 瓶颈点 | 量级 | 结论 |
|---|---|---|
| 网关 Tomcat 同步线程（200） | 理论 200/RT；RT=20ms → ~10000 QPS/机 | 纯堆机器可凑，但被下方 DS 卡死 |
| 读穿透 dataShare（`getRedisInfo` 走 DS） | 单 IO 线程 ~100 TPS（待实测） | **致命**：读走 DS 则全链路 ≤ 100 |
| `http.maxConnections=5` | Hessian 并发 5 | 读若走 Hessian 则更惨 |

**现状结论**：读 50000 QPS **达不到**，除非①读全部命中网关三级缓存且②dataShare 非单 IO，否则被 DS 卡死。

### 2.2 写（TPS）

| 瓶颈点 | 量级 | 结论 |
|---|---|---|
| dataShare 单 IO 线程（`HandlerImpl.run` 无线程移交） | ~100 TPS（待实测） | **致命**：1000 TPS 需 10 台 DS，且撮合全局有序难分片 |
| 全局锁（`getClient`/`releaseConnection`/`getConnect`） | 全协议串行 | 进一步压降吞吐 |
| 连接池（DS `maxCon` 疑似 5、`SOCKET_MAX`） | 并发封顶 | 池小了直接打满 |

**现状结论**：写 1000 TPS **达不到**，硬瓶颈在 dataShare 单 IO 线程 + 全局锁 + C 引擎撮合能力。

## 三、最少改造方案（读写分离 + 三件套）

> 原则：**能不改架构就不改，必须改就改局部**。按「改动量从小到大」排序。

### 改造 0｜零代码（纯配置 + 堆机器，只能救读）

- 网关水平扩展（LB + 多实例）。
- 连接池调大（见《连接池参数配置建议》）。
- **只能凑读 QPS，救不了写 1000 TPS**，且读若穿透 DS 仍被卡。

### 改造 1｜低风险（接线 + 去锁，读的关键）

| 项 | 动作 | 源码依据 |
|---|---|---|
| **读 Redis 直连** | 用 `00010030` 下发 Redis 连接串，网关读请求**直接连 Redis，绕过 dataShare** | `getRedisInfo("00010030")` 能力已存在，未接线 |
| **三级缓存接线** | `PubConfigCache`（5s TTL）已实现未接线，接上后热点读走本地缓存 | `PubConfigServiceImpl` 每请求 JDBC |
| **去全局锁** | `DSUtils.getClient()`（`static synchronized`）、`releaseConnection()`、`ShardedReidsPool.getConnect()` 三处去锁 | 消除全协议串行 |

**收益**：读请求不再经过 dataShare → dataShare 单 IO 线程不构成读瓶颈 → 读靠「缓存命中 + 多台网关」达标。

### 改造 1.5｜主动推送替代轮询（读 QPS 降源，不可缓存数据的关键）

| 项 | 动作 | 收益 |
|---|---|---|
| **实时数据主动推送** | 行情、竞价最优价、出价记录等「不可缓存」数据，用 WebSocket 事件驱动替代定时轮询 | 读 QPS 从「用户数×频率」降到「实际变动次数」，降 1~2 个数量级 |
| **低频数据仅穿透网关层** | 场次状态、公告、费率等「慢变」数据配 PUB/FRM 缓存，轮询仅打到网关层 | 后端穿透归零 |

> 与「改造 1 缓存」互补：**缓存解决「可缓存的读」，主动推送解决「不可缓存的读」**。详见《竞价详情页轮询改造-WebSocket事件驱动方案》。

### 改造 2｜中风险（dataShare worker 池，写的关键）

| 项 | 动作 | 收益 |
|---|---|---|
| **dataShare 加业务 worker 线程池** | `HandlerImpl.run()` 解析后**移交线程池**，不再单 IO 线程执行 | 打破 ~100 TPS 封顶 |
| **写链路超时分级 + 熔断 + 不自动重试** | 每协议独立超时；撮合不自动重试（幂等/对账兜底） | 防慢撮合拖垮快链路 |

### 改造 3｜较大（可选，仅当改造 2 仍不够）

- 网关 Servlet AsyncContext 异步化（读接口释放 Tomcat 线程）。
- 撮合链路 Netty 异步多路复用（`ansyKey` 配对，见《网关百万并发与协议隔离设计》）。

### 3.5 读 QPS 构成与消解路径（一张表看懂降源）

| 读 QPS 构成 | 典型数据 | 数据特性 | 能否缓存 | 消解手段 | 命中/穿透位置 |
|---|---|---|---|---|---|
| 轮询实时数据 | 行情、竞价最优价、出价记录、成交流水 | 变更快 + 强一致 | ❌ 不可缓存 | **主动推送**（WebSocket 事件驱动） | 事件驱动，无轮询 |
| 可缓存读 | 配置、字典、合约模板、公告 | 慢变 + 弱一致 | ✅ PUB/FRM | **三级缓存** | 网关层返回 |
| 低频慢变 | 场次状态、费率、规则 | 慢变 + 弱一致 | ✅ PUB/FRM | **仅穿透网关层**（Redis 直连） | 网关 / Redis |
| 强一致穿透读 | 余额、持仓、风控校验 | 强一致 + 交易决策 | ❌ 不可缓存 | **按需查询**（交易动作触发，非轮询） | 穿透后端 |

> 四类数据四种手段：**轮询实时→推送、可缓存→缓存、慢变→网关层、强一致→按需穿透**。消解后，真正需要穿透到后端（DS→撮合/DB）的读，只剩「强一致穿透读」这一类低频请求，其余全在网关层或事件通道消化。

## 四、改造后容量测算（能否达标）

### 4.1 读 50000 QPS ✅

| 命中口径 | RT | 单机 QPS | 达标所需机器 |
|---|---|---|---|
| 三级缓存命中（90%+） | ~1ms | 数万 | 2~3 台 |
| Redis 直连（未命中 10%） | ~2ms | 1 万+ | 并入上面 |

**结论**：读 90% 命中缓存 + 10% 走 Redis 直连，**完全不经过 dataShare**，2~3 台网关 + LB 即可到 50000 QPS。主动推送进一步把「不可缓存的实时数据」的轮询 QPS 从源头削掉，降低对机器数的依赖。

### 4.2 写 1000 TPS ✅（有条件）

```
dataShare worker 线程池 64 线程 ÷ 撮合 RT 50ms = 1280 TPS/台
```

**结论**：dataShare 加 64 线程 worker 池，单台即 1280 TPS > 1000 TPS。**前提**：C 撮合引擎能扛 1000 撮合/秒（这是 C 侧承诺，需实测）。

## 五、硬顶与必须确认的前置项

| 硬顶 | 必须确认 |
|---|---|
| **C 撮合引擎撮合能力** | 能否 1000 撮合/秒？撮合全局有序，无法靠分片扩容，是写链路的最终天花板 |
| **dataShare 单 IO 线程假设** | `jstack` 看 `nio.reactor` 线程数，实测证实/证伪 |
| **DB 容量** | 1000 TPS 写 + 慢 SQL 治理；读写分离/分库分表 |
| **Redis 容量** | 5 万读 × 10% 未命中 = 5000 QPS 打 Redis，需够大 |
| **缓存命中率** | 三级缓存 PUB/FRM/CLI 能否到 90% 命中（否则读要更多机器） |

## 六、最少改造清单（一张表）

| # | 改造 | 改动量 | 对应指标 | 优先级 |
|---|---|---|---|---|
| 1 | 读 Redis 直连接线（`00010030`） | 低 | 读 QPS | **必做** |
| 2 | 三级缓存接线（`PubConfigCache`） | 低 | 读 QPS | **必做** |
| 3 | 去 3 处全局锁 | 低 | 读写吞吐 | **必做** |
| 4 | 连接池调大 | 低 | 读写吞吐 | 必做 |
| 4.5 | 主动推送替代轮询（WebSocket 事件驱动） | 中 | 读 QPS（降源） | **必做** |
| 5 | dataShare 加 worker 线程池 | 中 | 写 TPS | **必做** |
| 6 | 网关水平扩展 + LB | 低（运维） | 读 QPS | 必做 |
| 7 | 超时分级 + 熔断 + 不自动重试 | 低 | 稳定性 | 必做 |
| 8 | Servlet 异步化 | 中 | 读 QPS（可选） | 按需 |
| 9 | 撮合 Netty 多路复用 | 高 | 写延迟/吞吐（可选） | 按需 |

> **一句话结论**：50000 QPS 靠「读走 Redis 直连 + 缓存 + **主动推送降源** + 多台网关」解决；1000 TPS 靠「dataShare 加 worker 池 + 去锁 + C 引擎扛得住」解决。**最少改造 = 上面 1~7 项（含主动推送 4.5），均不碰核心协议与撮合逻辑**；改造 8/9 是在压测不达标时的备选。
