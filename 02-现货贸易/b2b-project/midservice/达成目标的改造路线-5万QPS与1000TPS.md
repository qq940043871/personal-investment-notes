# 达成目标的改造路线：5 万 QPS 与 1000 TPS

> **目标**：读 50000 QPS、写 1000 TPS。本文从目标倒推：每一跳需要多少并发、现状卡在哪、要改哪里、怎么验收。
> **证据口径**：本文自用五级标记——【代码证实】源码可查 / 【配置证实】配置文件有值 / 【静态推算】按 RT 公式推出 / 【设计目标】未验证 / 【未压测】方法已成文结果未产出；未标等级的数字一律按【静态推算】理解。
> **与其他文档的关系**：`容量目标实现方案-5万QPS与1000TPS.md` 给出了改造清单；本文补上「并发需求推导」「每跳判据」「分阶段验收」，两份互相引用，口径以本文为准。

---

## 一、先算并发需求（Little 定律）

所需并发数 = 目标吞吐 × 端到端响应时间。每一跳的并发上限都要大于它，否则该跳就是瓶颈。

| 目标 | 响应时间假设 | 所需并发（×2 余量） | 说明 |
|---|---|---|---|
| 写 1000 TPS | 端到端 60ms（DS + 撮合 50ms + 其他） | 60，余量后 120 | 撮合 RT 50ms 是假设，需实测 |
| 读 50000 QPS | 加权平均 1.1ms（90% 缓存 1ms + 10% Redis 2ms） | 约 55，余量后 110 | 命中率 90% 是设计假设 |

> 反过来算：并发上限固定时，吞吐 = 并发上限 ÷ RT。这就是后面所有瓶颈判断的公式。

## 二、逐跳核对：现状上限 vs 目标需求

### 2.1 写链路（1000 TPS）

| 跳 | 现状上限 | 目标需求 | 判定 | 证据 |

| ⑧ Hessian 后端（connType=1） | JVM 默认 `http.maxConnections=5`/主机 【静态推算】 | 若 RT 60ms 需 120 连接 | **不达标**，吞吐上限 ≈ 5/RT ≈ 83 TPS/主机 | JVM 默认值 |

| ⑪ 数据库 | 1000 笔交易的写入与慢 SQL 未评估；交易逻辑每笔若多条 SQL，DB 负载是 TPS 的数倍 【静态推算】 | 待压测 | **未知** | 全链路压测计划 §数据层 |

**结论**：写链路要到 1000 TPS，必须同时满足五件事：舱壁协议级覆盖（②）、去归还全局锁（④）、DS 改为 worker 池（⑤）、Hessian 连接数放开或改走 Socket（⑧）、撮合与 DB 实测达标（⑩⑪）。其中 ⑤ 是否成立，决定整个写链路是否需要重构，必须最先证实。

### 2.2 读链路（50000 QPS）

| 跳 | 现状 | 目标需求 | 判定 | 证据 |
|---|---|---|---|---|
| ① 网关节点数 | 未定，单节点 Tomcat 300 理论上可达约 10 万 QPS（RT 3ms） | 3 节点，每节点约 1.7 万 QPS | 达标（理论） | 【静态推算】 |
| ② 单协议舱壁 | 默认 100/节点 | 热点协议：50000 × RT 5ms ÷ 3 节点 ≈ 83 | **接近上限**，热点协议需覆盖到 300 | `bulkhead.properties` |
| ③ 读是否经过 DS | 部分接口依赖 DS 的 `getRedisInfo`（如 `3002_API_AUTH_LIST`、`1001_GATEWAY_API`），但仅在特定用户状态下调用 【代码证实】 | 读 0 跳 DS | **不达标**，需接 Redis 直连 | `HandlerController.java:1925/1956/2001` |
| ④ 每请求 JDBC | `PubConfigServiceImpl` 每请求查库，`PubConfigCache`（5s TTL）已写未接线 【文档证实，待代码确认】 | 缓存命中 90% | **不达标**，需接线 | 容量方案 §三 改造 1 |
| ⑤ 单用户串行锁 | 读接口若也被锁，单用户读并发 = 1 【代码证实】：`syncLockMap` 为 null 时默认加锁 | 读不加锁 | **不达标**，读接口需显式关闭 | `HandlerController.java:1749-1750` |
| ⑥ Redis 直连容量 | 未命中 10% = 5000 QPS 打 Redis，远低于单实例能力 | 5000 QPS | 达标（需确认分片与热 key） | 容量方案 §五 |
| ⑦ 轮询放大 | 「用户数 × 轮询频率」会占相当比例的读 QPS，且实时数据不可缓存 | 推送替代轮询 | **需改造**，见 2.4 | 竞价详情页改造方案 |

**结论**：读链路的核心是「读不进 DS、读不进串行锁、读要有缓存」。三件事做完，Tomcat 300 线程本身够用，**不需要 Servlet 异步化**。

### 2.3 单用户串行锁与交易吞吐的关系

这是最容易被忽略的约束。开关开启时，同一用户同一接口的请求全部串行，因此：

- 单用户写吞吐上限 = 1 ÷ RT。RT 60ms 时约 16.7 TPS/用户。
- 全平台写吞吐 ≈ 活跃用户数 × 16.7（前提是每个用户的请求都能及时发出）。
- 达到 1000 TPS 需要至少约 60 个用户并发下单；如果实际只有几个做市账户，**这个锁会先于其他瓶颈卡住写链路**。

处理方式：

1. 串行锁只保留给确实需要「同用户同接口顺序执行」的写接口（如撤单后改单）。
2. 读接口、查询接口在 `syncLockMap` 中显式设为 0。
3. 对做市类账户，业务上允许的并发模型需要单独确认，不能一刀切。

### 2.4 读 QPS 的构成与降源

50000 QPS 中有多少是轮询，决定了推送改造的规模。估算方式：

```
轮询 QPS = 在线用户数 × 轮询频率
例：10000 在线用户 × 每 2 秒一次 = 5000 QPS（仅一个页面）
```

| 数据类型 | 处理 |
|---|---|
| 行情、竞价最优价、出价记录（实时、不可缓存） | WebSocket 事件驱动推送，见竞价详情页改造方案 |
| 配置、字典、合约模板、公告（慢变） | 三级缓存，网关层直接返回 |
| 场次状态、费率（慢变但需要及时） | Redis 直连，仅穿透到网关层 |
| 余额、持仓、风控（强一致） | 按交易动作触发查询，不轮询 |

## 三、改造清单（按阶段）

每一阶段都有验收判据。判据不通过，不进入下一阶段。

### 阶段 0：先证实（不改代码，1–2 周）

| 动作 | 目的 | 验收判据 |
|---|---|---|
| 生产 jstack 观察 dataShare 的业务线程 | 证实或证伪「单 IO 线程」 | 若高并发下仅 1 个线程执行协议处理，B1 成立 |
| 核实生产配置 | 找出与代码默认值不一致的项 | 列出 `ds.maxCon`、Tomcat 线程、`http.maxConnections`、`is.open.syncLock` 与各接口的 `syncLockMap` 实际值 |
| 撮合引擎压测 | 找出 C 引擎真实天花板 | 得到可持续撮合 TPS 与 P99，判断 1000 是否可达 |
| 接口盘点 | 找出读接口中依赖 DS、依赖串行锁、每请求查库的接口 | 形成清单：每个接口的依赖跳数 |
| APM 打点各跳 RT | 替换 06 文档中所有 RT 假设 | 写链路与读链路各跳 P50/P99 有实测值 |

> 阶段 0 的结果决定后面是否需要阶段 3 的重构。如果 jstack 证实不是单线程，阶段 3 的工作量会大幅减少。

### 阶段 1：纯配置（不改代码，约 1 周）

| 改造 | 配置项 | 目标值 | 解决的跳 |
|---|---|---|---|
| 协议级舱壁覆盖 | `bulkhead.properties` 的 `protocol.<写协议>.maxConcurrent` | ≥ 150 | 写 ②，读 ② |
| 写协议慢调用阈值 | `protocol.<撮合协议>.slowThresholdMs` | 按实测 P99 设定，如 1000 | 熔断准确性 |
| Hessian 连接数 | JVM `-Dhttp.maxConnections` | ≥ 200 | 写 ⑧ |
| DS 池 | `ds.maxCon` | 核实生产值，目标 200 | 写 ③ |
| 撮合协议池 | `TB_DS_PROTOCOL.SOCKET_MAX / INIT / TIMEOUT` | 200 / 40 / 1000 | 写 ⑥ |
| 读接口串行锁 | `syncLockMap` 读接口设为 0 | 全部读接口 | 读 ⑤ |
| 限流开关 | `qpsLimit` 保持 0 或设为高于目标的值 | 不得低于 3 节点的目标峰值 | 防误伤 |

### 阶段 2：低风险代码改造（读链路）

| 改造 | 位置 | 验收判据 |
|---|---|---|
| 读 Redis 直连，替代 `getRedisInfo` 走 DS | `HandlerController` 的 `DSUtils.getClient().getRedisInfo(...)` 调用点 | 压测时 dataShare 的读请求数为 0 |
| 接线 `PubConfigCache`（5s TTL） | `PubConfigServiceImpl` | 配置类接口的 JDBC 调用数接近 0 |
| 三级缓存接线与命中率统计 | 网关层 | 读接口缓存命中率 ≥ 90% |
| 读接口压测 | 3 节点 | 50000 QPS 稳态 15 分钟，P99 ≤ 500ms，错误率 < 0.1% |

### 阶段 3：写链路改造（最关键，可能是重构）

前提：阶段 0 的 jstack 证实单 IO 线程模型。如果不成立，这一阶段只做 3.2 和 3.3。

| 改造 | 位置 | 验收判据 |
|---|---|---|
| 3.1 dataShare worker 线程池：协议解析后移交线程池执行 | dataShare 协议调用入口，`DSStandardProtocol.execute` 所在路径 | jstack 中可见 ≥ 64 个 worker 同时执行；单节点吞吐 ≥ 目标 ÷ 节点数 |
| 3.2 归还连接去全局锁：按 `clientFlag` 分段锁 | `SocketClientConnectManager.java:56`、`:63` | 归还锁争用为 0；去锁后 TPS 不再卡在 1k |
| 3.3 Redis 借连接移出全局锁 | `ShardedReidsPool.java:58-63` | 借连接耗时 P99 ≤ 1ms，无全局排队 |
| 3.4 热路径 `static synchronized` 清理 | `DSUtils.java:35`、`ServiceUtils.java:169`、`SerialService.java:31` | 每请求无全局同步点 |
| 3.5 有界队列与高水位 | worker 队列 | 60% 告警，80% 明确拒绝，不堆积到 OOM |
| 3.6 写协议超时分级与熔断 | 舱壁协议级覆盖 | 撮合协议超时 1000ms，不自动重试，熔断后快速失败 |

**worker 池容量公式**（需要实测替换 RT）：

```
单节点写 TPS ≈ worker 线程数 ÷ 撮合 RT
64 ÷ 0.05s = 1280 TPS（撮合 RT 50ms）
64 ÷ 0.06s ≈ 1067 TPS（端到端 RT 60ms）
```

### 阶段 4：可靠性（随吞吐提升必须做）

吞吐越高，丢消息和重复消息的绝对数量越大，可靠性不能推迟到容量达标之后。

| 改造 | 位置 | 验收判据 |
|---|---|---|
| MQ 发布等待 Kafka 确认 | `T00010033` 发布路径 | 发布返回成功即代表 broker 已确认 |
| 消费失败不取消订阅，失败回流 | `T00010040` 相关逻辑 | 单条消费失败不影响后续消息 |
| offset 按批次提交，去掉固定 60 秒刷库 | offset 刷库逻辑 | 崩溃后重复消息数在可接受范围 |
| 分布式锁改为原子 `SET NX PX` | `T00010040` 的 `setnx + expire` | 进程崩溃不会留下永不过期的锁 |
| 送达型动作使用本地消息表 + 批次号 + 阶梯重试 | 设计见 `12-跨系统调用一致性方案.md` | 落地工程需确认；未在三工程源码中找到 |

### 阶段 5：扩展（仅当阶段 4 之后仍不达标）

| 改造 | 触发条件 |
|---|---|
| 网关水平扩展到 3 节点 + LB | 读链路单节点 CPU 打满 |
| Servlet AsyncContext 异步化 | RT 增长后 Tomcat 线程不够，约 RT ≥ 150ms 时才需要 |
| 撮合链路 Netty 多路复用 | 单连接串行成为瓶颈 |
| 撮合按品种分片 | C 引擎单实例撮合能力不够，且撮合可以按品种独立 |

## 四、验收：分阶梯压测

压测方法沿用 `全链路容量压测计划.md`，这里只给目标门槛。

| 场景 | 负载 | 通过判据 |
|---|---|---|
| 读稳态 | 50000 QPS，15 分钟 | P99 ≤ 500ms；错误率 < 0.1%；dataShare 读请求为 0 |
| 写稳态 | 1000 TPS，15 分钟 | P99 ≤ 1s；错误率 < 0.1%；无熔断误开 |
| 写拐点 | 阶梯 100 → 200 → 500 → 1000 → 1500 | 找到拐点并记录拐点处的瓶颈层 |
| 混合 | 读 50000 + 写 1000 同时 | 写指标不因读流量下降超过 10% |
| 慢协议隔离 | 人为把撮合 RT 拉到 500ms | 行情读不受影响（舱壁隔离生效） |

拐点判定：吞吐不再随负载线性增长，或 P99 陡升，或 jstack 显示某一跳线程全部阻塞。拐点处的瓶颈层即为下一步改造对象。

## 五、达成条件与未决项

| 项 | 状态 | 影响 |
|---|---|---|
| 撮合引擎能否 1000 撮合/秒 | **未知** | 不成立则写目标只能降到撮合上限，改造 3 与 5 的收益都在撮合之后兑现 |
| dataShare 是否单 IO 线程 | **未证实** | 成立则阶段 3 必做；不成立则阶段 3 工作量大幅减少 |
| 生产 `ds.maxCon` 与 `is.open.syncLock` | **未核实** | 决定阶段 1 的配置改动 |
| 数据库能否支撑 1000 笔交易的写入 | **未知** | 需要慢 SQL 治理与可能的分库分表 |
| Redis 热 key | **未评估** | 行情类热 key 集中到单分片时会成为读瓶颈 |
| 读接口在 50000 QPS 中的占比与轮询占比 | **未盘点** | 决定推送改造的范围 |

**一句话**：5 万 QPS 的达成条件是「读不进 DS、读不进串行锁、读有缓存、实时数据走推送」，四件事全部做完，Tomcat 300 线程即可支撑，不需要异步化。1000 TPS 的达成条件是「DS 不再是单线程、归还与借连接去全局锁、舱壁与 Hessian 连接数放开、撮合与 DB 实测达标」，其中撮合能力是最终天花板，必须先实测。
