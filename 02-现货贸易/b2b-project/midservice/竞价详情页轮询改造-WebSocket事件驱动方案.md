# 竞价详情页轮询改造：WebSocket 事件驱动技术方案

> 目标：**移除竞价详情页所有实时轮询**，用 WebSocket 事件驱动替代；对「变化不频繁」的数据保留低频轮询，但**仅穿透到网关层**（缓存/Redis 命中，不下穿 DS→后端）。
> 范围：前端页面 / **独立 WebSocket 服务**（推送侧）/ midservice 网关（查询侧）/ C 撮合引擎（事件出口）。
> 架构前提：**推拉分离**——推送由 C 核心直推独立 WS 服务，查询仍走 midservice 网关；推送链路**不复用 dataShare 的订阅 / MQ / 推送通道**。

## 一、现状问题分析

### 1.1 竞价详情页当前的轮询模式

```
页面定时器（500ms~1s） ──轮询──▶ 最优价 / 出价记录 / 成交流水
        │
        ▼
   每次轮询都穿透完整链路：网关 → dataShare → C 撮合引擎（5 跳）
```

### 1.2 轮询的四大合理性缺陷

| 缺陷 | 说明 | 后果 |
|---|---|---|
| **空轮询** | 数据没变也照打后端 | 绝大多数轮询是无效请求，浪费后端算力 |
| **延迟与频率的天然矛盾** | 间隔短→延迟低但压力大；间隔长→压力小但延迟高 | 无法两全，实时性被轮询间隔锁死 |
| **后端压力随在线用户线性放大** | QPS = 在线用户数 × 轮询频率 | 竞价高峰（用户集中盯盘出价）时后端压力陡增 |
| **不可缓存 → 必然穿透** | 最优价/出价记录是实时撮合数据，不能走缓存 | 每次轮询都是完整 5 跳穿透，RT 长、连接/线程占用高 |

### 1.3 协议「不可缓存」的硬约束

最优价、出价记录命中了缓存判断的**③变更快 + ⑤强一致**两条，**绝不能进 PUB/FRM/CLI 缓存**：

- 最优价：每次出价都可能变，毫秒级变更；
- 出价记录：实时追加，强一致；
- 成交流水：实时产生，强一致。

> 结论：这三类实时数据「要么穿透查询、要么事件推送」，**没有缓存这条中间路**。轮询的问题本质是「把『事件驱动』该干的活，用『定时穿透』硬扛」。

## 二、WebSocket 事件驱动的查询机制设计

### 2.1 核心思想：从「拉」到「推」

```
改造前（拉）：客户端定时轮询 → 服务端被动响应（大多空转）
改造后（推）：出价变动 → 服务端主动推送事件 → 客户端按需查询/更新
```

### 2.2 事件流：C 核心直推独立 WebSocket 服务

```
C 撮合引擎（撮合结果：最优价 / 档位变化 / 成交）
   │  ① 事件出口：C 侧直接产出结构化事件，投递到有界队列
   │     （非阻塞投递，队列满即丢最旧——撮合线程绝不因推送阻塞）
   ▼
WebSocket 服务（独立部署，只干三件事）
   │      · 会话管理：连接 / 一次性票据鉴权 / 心跳 / 踢下线
   │      · 订阅路由：topic → 连接集合
   │      · 扇出推送：按连接有界队列发送
   │  ② 按订阅关系扇出
   ▼
客户端（收到事件 → 更新本地快照；或按事件通知触发一次拉取）
```

**这是一个明确取舍：不复用 dataShare 的推送能力。**

原设想复用 dataShare 已有通道（订阅 `00010034` / MQ `00010033` / `0x08` 推送 `AnsyResponseQueue`），链路为 `C 核心 → dataShare → 网关 → 客户端`。现改为 C 核心直推独立 WS 服务，链路缩为两跳：

| 维度 | 经 dataShare 中继 | C 核心直推独立 WS 服务 |
|---|---|---|
| 端到端延迟 | 多一次汇聚 + 一次编解码 | 少一跳，事件直达 |
| 语义耦合 | dataShare 需理解竞价事件语义 | 数据交换与推送彻底解耦，各管各 |
| 故障面 | dataShare 抖动直接打穿推送链路 | 推送故障不影响查询链路 |
| 事件可靠性 | 白拿 MQ 的缓冲与重放 | **要自己做**（见 2.5.6） |
| 数据一致性 | 可在 DS 侧读库补齐 | 只能靠 `seq` + 快照自愈（见 2.5.5） |

选后者的理由：竞价详情页对延迟敏感、事件语义极简（本质就是「某场次最优价变了」），不值得为它拉一个通用数据中心做中转；而 dataShare 一旦成为推送的必经节点，推送的可用性就被 DS 的发布窗口绑架。

代价必须写明白：**直推省掉的那一跳，换来的是「事件不丢」的责任转移。** 原来由 MQ 兜住的断线窗口，现在由 WS 服务自己兜。

**C 侧的硬约束**：撮合线程单线程运行，绝不能因推送阻塞。事件出口必须是「有界队列 + 非阻塞投递」，队列满时丢弃最旧事件，**绝不反压撮合线程**。丢弃是可接受的——丢的是「高频可覆盖」类事件，下一次事件或快照即可自愈。

**推拉分离的边界**：

| 通道 | 承担 | 部署 |
|---|---|---|
| 推送通道 | 只发不取，无查询能力 | 独立 WebSocket 服务，按连接数扩容 |
| 查询通道 | `GP24B0` / `GP2457` / `GP0105` / `GP0023` 等拉取 | midservice 网关 → dataShare → DB / C 核心 |

两条通道独立扩容、独立发布、独立故障——这也是 2.5.8 降级策略能成立的前提。

> 配图：**图 1**（`图1-竞价推送架构-推拉分离.html` / `.png`）——一图看清「红蓝两条通道互不共用节点」以及直推省掉的那一跳去了哪。

### 2.3 推送策略：事件 + 快照 + 按需拉取（混合）

| 数据 | 推送方式 | 理由 |
|---|---|---|
| 最优价 | **事件 + 最新快照**（变动即推） | 数据小，直接随事件下发，省一次查询 |
| 出价记录 | **事件通知 + 按需拉取** | 列表可能大，客户端收到事件后拉最近 N 条 |
| 成交流水 | 事件通知 + 按需拉取 | 同上 |

### 2.4 WebSocket 协议设计

#### 2.4.1 连接与鉴权

```jsonc
// 连接：直连独立 WS 服务，用一次性票据而非长 Token
wss://ws.<domain>/bid?ticket=<一次性票据>

// 票据由网关查询接口签发（用现有登录 Token 换取），30s 有效且一次性使用
// 理由：长连接 URL 会被接入层日志、浏览器历史、代理留存，长 Token 不能进 URL

// 订阅 / 退订（携带 lastSeq，便于服务端判断能否续传）
{ "action": "subscribe",   "topic": "bid_<场次ID>", "lastSeq": 10231 }
{ "action": "unsubscribe", "topic": "bid_<场次ID>" }

// 订阅确认：客户端必须收到 ack 才算订阅生效
{ "type": "sub_ack", "topic": "bid_xxx", "seq": 10231, "epoch": 7 }
```

#### 2.4.2 统一消息信封

所有推送共用信封，业务字段进 `data`。信封是后面全部稳定性机制的载体（去重、跳号检测、世代识别都靠它）：

```jsonc
{ "type": "best_price_changed",
  "topic": "bid_xxx",
  "msgId": "7-10232",     // epoch-seq，全局去重键
  "seq": 10232,           // topic 内单调递增
  "epoch": 7,             // 服务端实例世代号，重启 +1
  "ts": 1698000000000,    // 服务端事件产生时间（毫秒）
  "data": { "bestPrice": "1020", "bestBidder": "xxx" } }
```

| type | 载荷 | 客户端动作 |
|---|---|---|
| `best_price_changed` | 最优价 + 出价方 | 直接更新快照（数据小，随事件下发） |
| `bid_log_changed` | 仅通知 | 按需拉取最近 N 条出价记录 |
| `status_changed` | 场次状态 | **必达**，更新状态机（见 2.6.4） |
| `stale` | 上游数据停滞标记 | 提示「数据可能延迟」+ 主动拉快照（见 2.5.6） |

#### 2.4.3 关闭码约定

| close code | 含义 | 客户端应做 |
|---|---|---|
| 1000 | 正常关闭 | 按需重连 |
| 1006 | 异常断开（无 close 帧） | 立即进入退避重连 |
| 1008 | 策略违规 / 被踢 | 不重连，提示重新登录 |
| 1012 | 服务端重启 | 按服务端下发的延迟（如 3~5s）错峰重连 |
| 1013 | 服务端过载 | 退避加长，切降频轮询兜底 |
| 4001（自定义） | 票据失效 | 重新取票后重连 |

区分关闭码的意义：`1012` 与 `1006` 必须区别对待——服务端发布时若不区分，全部客户端会用同一节奏同时扑回来（见 2.5.4）。

### 2.5 复杂网络环境下 WebSocket 的稳定性设计（关键）

WebSocket 在局域网里很稳，在真实互联网里**必然断**。所以这一节不是「异常处理」，是「常态处理」。

> 配图：**图 2**（`图2-WebSocket稳定性-故障检测与兜底.html` / `.png`）——故障形态、三层检测、兜底动作的对应关系。

#### 2.5.1 先承认：WS 只会以五种方式坏掉

| 故障形态 | 表现 | 根因 | 客户端能察觉吗 |
|---|---|---|---|
| **静默半开** | 连接对象还在，发消息无回应也不报错 | NAT / 防火墙 / 负载均衡空闲超时静默清会话（常见 60s / 300s） | 察觉不到，只能靠心跳 |
| **网络切换** | 移动端 WiFi↔4G、基站切换、IP 变化 | 旧连接的路由已不存在，但没有 FIN/RST | 察觉不到 |
| **中间设备干预** | 握手被拒、被降级、消息被缓冲 | 企业代理 / WAF / 部分 CDN 不支持或篡改 WS | 能察觉（握手失败） |
| **服务端发布** | 全员同时断线 | 进程重启 | 能察觉（close 帧） |
| **弱网抖动** | 心跳超时、消息堆积乱序 | 高 RTT / 丢包 | 部分察觉 |

> 关键结论：**前两种占了线上故障的绝大多数，而它们的共同特征是「客户端不知道自己已经断了」。** 所以整套设计的核心不是「断线后怎么重连」，而是「怎么尽快发现已经断了」。

#### 2.5.2 保活：不能依赖 TCP keepalive

- TCP keepalive 默认 **2 小时**，对中间设备 60s 的空闲清理毫无意义；
- 必须做**应用层心跳**，间隔小于链路上最「短命」的空闲超时；
- **双向心跳**：客户端主动 `ping`（防止自己这侧被清），服务端也主动 `ping`（防止客户端侧静默）；
- **判死不靠一次超时**：连续 2 次 pong 未回才判死，避免一次抖动误杀；
- 判死后的动作不是「等」而是「立即重连 + 拉快照」。

| 参数 | 建议值 | 依据 |
|---|---|---|
| 客户端心跳间隔 | 25s | 小于常见 60s 空闲超时，留一倍余量 |
| 服务端读空闲超时 | 75s | 约 3 个心跳周期 |
| 判死阈值 | 连续 2 次 pong 丢失 | 抗单次网络抖动 |
| 浏览器后台标签页 | 不做精细计时 | 后台定时器被降频，靠服务端 ping 兜住 |

#### 2.5.3 断线检测三层，缺一层就有盲区

| 层 | 手段 | 能发现 | 发现不了 |
|---|---|---|---|
| TCP 层 | RST / FIN、写失败 | 对端正常关闭或重置 | 静默半开 |
| 应用层 | ping/pong 超时 | 静默半开、假死 | 服务端 hang 但 socket 仍活（需心跳带服务端时间戳佐证） |
| 业务层 | `seq` 跳号、`epoch` 变化、`stale` 标记 | 消息丢失、服务端重启、上游断流 | 不含业务变动的事件缺失 |

业务层检测是唯一能发现「连接好好活着，但数据已经不新鲜」的手段——这一点在 2.5.6 会再出现一次。

#### 2.5.4 重连：退避 + 抖动 + 错峰

```
1s → 2s → 4s → 8s → 16s → 30s（封顶，之后固定 30s 持续重试）
每个间隔叠加 ±20% 随机抖动
```

- **抖动不是可选项**：没有抖动，服务端发布后所有客户端会在同一毫秒扑回来，刚恢复的实例被自己的用户打死（惊群）；
- 触发即重置退避：`online` 事件、`visibilitychange` 回前台、心跳判死；
- 连续失败达 K 次（如 5 次）→ 进入 2.5.8 降级；
- 重连期间 UI 必须显示「连接中 / 已断开」，**不能假装数据是实时的**——静默失败比报错更危险。

#### 2.5.5 状态恢复：seq + epoch + 快照，三条缺一不可

| 客户端观察到 | 判断 | 动作 |
|---|---|---|
| `epoch` 不变、`seq` 连续 | 正常 | 直接应用 |
| `epoch` 不变、`seq` 跳号 | 丢事件 | 拉快照对齐，跳到最新 seq |
| `epoch` 变大 | 服务端重启 | 拉快照 + 重新订阅（seq 已归零，不可比） |
| `seq` 倒退 | 乱序或重复 | 丢弃旧帧，只保留最大 seq |

- **跳号不补中间事件**：补历史要求服务端保留完整事件流，成本远高于拉一次快照；
- **去重键 `msgId = epoch-seq`**：重连重放不会造成重复渲染；
- 完整重连时序见 2.6.3（拉快照 → 校时钟 → 重订阅）。

#### 2.5.6 直推方案特有的一环：WS 服务与 C 核心之间也会断

这是「不复用 dataShare」后**新增的故障点**，也是最容易漏的一个：

原来 `C 核心 → dataShare` 之间有 MQ 缓冲，DS 宕了事件还在队列里；现在直推，这条链路一断，**WS 服务会安静地停止推送，而客户端心跳一切正常**——客户端连的是 WS 服务，它无从知道上游已经没数据了。

三层兜底：

| 层 | 机制 |
|---|---|
| 链路层 | WS 服务与 C 核心之间也做应用层心跳，超时即重连并告警 |
| 数据层 | C 侧保留短期事件环形缓冲（如最近 5000 条 / 30s），WS 服务重连后按 `seq` 续传 |
| 业务层 | WS 服务维护每 topic 的「最后事件时间」，超阈值（如 30s）未更新 → 下发 `stale` 标记，客户端提示延迟并主动拉快照 |

业务层兜底是最后一道防线：它能覆盖「链路看起来活着但数据不流动」的所有情况，包括 C 侧撮合停滞、事件过滤规则误配这类心跳发现不了的问题。

#### 2.5.7 慢客户端：一条连接可以拖垮整个广播

服务端扇出时，每个连接必须有**独立有界发送队列**，不能共用缓冲区：

| 事件类型 | 队列满时 | 理由 |
|---|---|---|
| 高频可覆盖（最优价） | 丢弃最旧帧，保最新 | 下一次事件自然修正 |
| 必达（场次状态变化） | 不丢；持续满则主动断开（close 1013） | 让客户端走重连 + 快照，比在队列里排队等死好 |

同时：扇出按 topic 分桶遍历连接集合，禁止全连接扫描；单机连接数设硬上限，超限拒绝建连而非拖垮整机。

#### 2.5.8 降级兜底：WS 永远只是「加速器」

**架构地基：任何实时数据都不能只有推送一条路。**

- WS 不可用（代理不支持、握手被拒、连续失败 K 次）→ 自动切**降频轮询**（3~5s），页面仍可用；
- 同时后台以 30s 间隔试探 WS，恢复后切回并停掉轮询；
- 用户可见提示「实时推送不可用，已切换为定时刷新」——把降级说清楚，比让用户盯着一个不动的数字强。

这条决定了改造的性质：**收益是「更快、更省」，而不是「唯一通道」**。任何把它做成唯一通道的设计，都会在某个运营商或某家企业内网里翻车。

#### 2.5.9 可观测：先能量化「稳不稳」

| 指标 | 用途 |
|---|---|
| 在线连接数 / 建连成功率 | 容量与鉴权健康度 |
| **平均连接时长** | **最灵敏的稳定性指标**：若平均只有几分钟就断，先查中间设备空闲超时，而不是查代码 |
| 重连次数分布 | 区分「偶发抖动」与「系统性断连」 |
| 心跳 RTT P99 | 弱网用户占比 |
| 事件端到端延迟 P99 | C 侧产生 → 客户端渲染 |
| 发送队列积压 / 慢客户端数 | 扇出健康度，预警广播卡顿 |
| close code 分布 | `1012` 突增 = 发布导致；`1006` 突增 = 网络或中间设备 |

> 对比基线：同一场次的「推送延迟」与「轮询延迟」必须同时可见。否则既无法证明改造成效，也无法在出问题时判断「是推送坏了，还是数据本身慢了」。

### 2.6 接口与协议号分工、客户端接入时序

前面 2.2~2.5 讲的是「通道怎么建」，这一节落到**具体接口与协议号**：哪条数据走推、哪条走拉、客户端按什么顺序建立状态。

> 口径说明：链路结构、协议号均为【实证】（链路默写 + 2026-10-28 复核确认）。其中 `go 行情` 是**独立接口**而非 GP 协议号，聚合返回 `sort` / `market` / `countdown` 三项。

#### 2.6.1 数据面分工：谁推送、谁拉取

| 接口 / 协议号 | 数据内容 | 数据源 | 交付方式 | 可靠性等级 |
|---|---|---|---|---|
| `GP24B0` | 最新价标的（最优价） | C 撮合引擎 | WS 事件 + 快照下发 | 高频，可被下一帧覆盖 |
| `GP2457` | 委价列表（买卖档位） | C 撮合引擎 | 事件通知 + 快照/diff 拉取 | 高频且体量大，**禁止全量推** |
| `go 行情` | 行情页聚合：`sort` 排序方式 / `market` 市场 / `countdown` 倒计时 | 行情服务 | 客户端拉取（进入行情页时） | 界面初始态，容忍秒级旧值 |
| `GP0105` | 标的行情 | DB | 客户端拉取（首次 / 重连） | 快照基准 |
| `GP0023` | 标的详情 | DB | 客户端拉取 | 慢变，可走网关缓存 |
| `GP2458` | 核心时间（服务端时钟） | C 撮合引擎 | 定时同步 | 时钟基准，唯一来源 |

三类数据的性质截然不同，不能混在一个通道里用一种语义处理：

- **结果面**（`GP24B0` / `GP2457`）：撮合产生的输出，只能推、不能靠轮询拿准；
- **查询面**（`GP0105` / `GP0023` / `go 行情`）：用于冷启动、重连与进入页面时建立基准；
- **时钟面**（`GP2458`）：不携带业务数据，但决定倒计时的正确性。

> 【推演】`go 行情` 返回的 `countdown` 是进入行情页时的一次性初值，持续倒计时仍应由 `GP2458` 校准后本地插值。两套口径不能并存，否则会出现「页面初值与服务端时钟差几秒」的错位，越接近截止时刻越危险。

#### 2.6.2 客户端接入三件事（顺序不可换）

```
① 先查询 DB（GP0105 标的行情 / GP0023 标的详情）
        + 拉一次 go 行情（页面聚合 sort / market / countdown）
        │  建立本地快照，页面先渲染出可用状态
        ▼
② 与服务端时间同步（GP2458）
        │  校准倒计时基准，此后 UI 只做本地插值
        ▼
③ 维持 WS 通道，接收主动推送
        │  按推送类型调用对应接口：GP24B0 更新价 / GP2457 拉档位 diff
        ▼
   处理状态机与倒计时
```

顺序为什么不能换：

| 若颠倒 | 后果 |
|---|---|
| 先订阅后拉快照 | 订阅生效到快照返回之间存在空窗，增量落在无基准的状态上，出现拼接错值 |
| 先渲染倒计时后校时钟 | 本地钟漂移或用户改系统时间，竞价截止时刻会被算错——这是资金相关错误，不是显示问题 |
| 把取数逻辑塞进推送 | 推送通道承载大对象（如整档委价），长连接被单条消息拖垮，且失去按需拉取的削峰能力 |

一句话：**推送只负责告诉你「变了」，取数仍走对应接口。**

#### 2.6.3 断线重连 = 重放 2.6.2 的完整三步

重连不是简单「重新订阅」。断线期间漏掉的档位变化无法从后续增量补齐，必须：

```
重连成功 → ① 拉快照（GP0105）→ ② 校时钟（GP2458）→ ③ 重新订阅 → ④ 以快照为准丢弃过期事件
```

这与 2.5.5 的「状态恢复」是同一件事，本节给出的是**时序上的严格顺序**。若只做「重订阅」而无快照对齐，`seq` / `epoch` 检测到的丢事件无法修复——补偿机制实际不成立。

> 配图：**图 3**（`图3-断线到恢复五步时序.html` / `.png`）——五步顺序与每步依据，重点看第三、四步为什么不能省。

#### 2.6.4 两类推送必须分可靠性等级

| 推送类型 | 典型数据 | 丢失后果 | 处理策略 |
|---|---|---|---|
| 高频可覆盖 | 出价变动、最新价 | 下一帧自然修正，用户无感 | 允许丢，不重放 |
| 低频必达 | 标的状态变化（挂牌 / 停牌 / 成交 / 结束） | 客户端状态机卡在错误状态，页面操作全部失效 | 带递增序号或重放；重连后以快照为准 |

倒计时属于「必达 + 时钟派生」：它丢失不会报错，只会让页面安静地停在错误状态——这类问题最难排查，也最容易被当成前端 bug。

## 三、轮询移除清单与改造范围

### 3.1 移除的轮询

| 轮询项 | 原频率 | 替代方案 |
|---|---|---|
| 最优价 | 500ms~1s | WebSocket 事件 + 快照 |
| 出价记录 | 1s | WebSocket 事件通知 + 按需拉取 |
| 成交流水 | 1s | WebSocket 事件通知 + 按需拉取 |
| 竞价倒计时 | 1s | 本地插值，基准来自 `GP2458` 服务端时钟（见 2.6.2） |

### 3.2 保留但降频/降穿透的轮询

| 轮询项 | 原穿透 | 改造后 | 说明 |
|---|---|---|---|
| 场次状态/竞价规则 | 穿透 DS→DB | **仅穿透网关层**（PUB 缓存/Redis） | 变更慢，5~10s TTL |
| 公告/合约模板 | 穿透 DS→DB | 仅穿透网关层 | 变更慢 |
| 费率 | 穿透 DS→DB | 仅穿透网关层（FRM） | 变更慢 |

### 3.3 改造范围（五端）

| 端 | 改造内容 |
|---|---|
| 前端 | 移除轮询定时器；接入 WebSocket（取票/连接/订阅/重连/心跳/降级）；事件驱动查询 |
| **独立 WebSocket 服务** | **新建并独立部署**：会话管理（票据鉴权/心跳/踢下线）、topic 订阅路由、按连接有界队列扇出、事件缓冲续传、`stale` 检测 |
| 网关 midservice | **只承担查询侧**：票据签发、`GP24B0`/`GP2457`/`GP0105`/`GP0023` 拉取接口、低频数据 PUB/FRM 缓存；不参与推送 |
| dataShare | **不参与本链路事件流转**，仅保留慢变数据的查询穿透 |
| C 撮合引擎 | **新增事件出口**：有界队列 + 非阻塞投递（禁止反压撮合线程）；保留短期事件环形缓冲供续传 |

## 四、低频轮询数据「仅穿透网关层」的实现策略

「仅穿透到网关层」= **请求在网关层返回，不下穿 DS→后端**。

| 策略 | 做法 | 适用 |
|---|---|---|
| **网关三级缓存（PUB/FRM）** | 给场次状态/公告/规则/费率配 `ApiCacheMap` 缓存，TTL 5~10s，命中即网关层返回 | 变更慢、共享度高的数据 |
| **Redis 直连** | 网关直接连 Redis 查（`00010030` 下发连接串），绕过 DS | 需要跨实例一致的缓存 |
| **本地缓存 + 事件失效** | `PubConfigCache` 类本地缓存，配合事件推送触发失效/刷新 | 配置类数据 |

**关键**：低频数据仍在轮询，但轮询请求在网关层就被挡住，**后端穿透降为 0**，只剩网关层的轻量内存/Redis 查询。

## 五、可缓存与不可缓存协议的划分标准

复用缓存判断五判据，落到竞价场景：

| 数据 | 变更频率 | 一致性 | 是否缓存 | 处理方式 |
|---|---|---|---|---|
| 最优价 | 毫秒级 | 强一致 | ❌ 不可缓存 | WebSocket 事件 + 快照 |
| 出价记录 | 实时追加 | 强一致 | ❌ 不可缓存 | WebSocket 事件 + 按需拉取 |
| 成交流水 | 实时 | 强一致 | ❌ 不可缓存 | WebSocket 事件 + 按需拉取 |
| 可用资金/持仓 | 实时 | 强一致 | ❌ 不可缓存 | 出价前按需查询 |
| 场次状态/规则 | 慢（分钟级） | 弱一致 | ✅ PUB，TTL 5~10s | 仅穿透网关层 |
| 公告/合约模板 | 慢 | 弱一致 | ✅ PUB，TTL 10~30s | 仅穿透网关层 |
| 费率 | 慢 | 弱一致 | ✅ FRM，TTL 60s | 仅穿透网关层 |

**划分标准一句话**：**「实时 + 强一致 + 影响交易决策」→ 事件推送/穿透查询，绝不缓存；「慢变 + 弱一致 + 展示类」→ 网关层缓存，仅穿透网关层。**

## 六、改造后的性能与一致性预期

### 6.1 性能

| 指标 | 改造前（轮询） | 改造后（事件驱动） |
|---|---|---|
| 后端穿透 QPS | 在线用户 × 轮询频率（高峰巨大） | 仅「实际出价变动」时触发，降低 1~2 个数量级 |
| 最优价延迟 | 轮询间隔 500ms~1s | 事件推送 <100ms，**实时性反而更好** |
| 网关层负载 | 全量穿透 DS | 低频数据被网关缓存挡住 |
| 连接资源 | 每次轮询建/用连接 | 一条 WebSocket 长连接复用 |

### 6.2 一致性

- **最优价/出价记录**：事件驱动后客户端看到的是「变动后立即推送/查询」的最新值，**一致性和实时性均优于轮询**（轮询在两次间隔之间本来就看不到中间态）。
- **低频数据**：网关层缓存 TTL 内可能稍旧（秒级），但这类数据变更慢，业务可接受；配合事件失效可进一步收敛。

## 七、分阶段实施计划

| 阶段 | 内容 | 交付 | 风险 |
|---|---|---|---|
| **P1 通道打通** | C 侧事件出口（有界队列）+ 独立 WS 服务（会话/订阅/扇出）+ 一次性票据鉴权，先推最优价事件 | 事件能端到端到达 | 中 |
| **P2 前端接入** | 前端接入 WebSocket，移除最优价/出价记录轮询，事件驱动查询 | 核心轮询移除 | 中 |
| **P3 低频缓存化** | 场次状态/公告/费率配 PUB/FRM 缓存，轮询仅穿透网关层 | 后端穿透降为 0 | 低 |
| **P4 优化收敛** | 事件带快照、出价记录增量、压测验证、灰度放量 | 性能达标报告 | 低 |

**灰度策略**：新老双通道并存（WebSocket + 轮询降频），按比例切流，观察事件送达率与数据一致性后逐步放量。

## 八、风险点与应对

| 风险 | 说明 | 应对 |
|---|---|---|
| **事件丢失/乱序** | 推送通道丢消息或乱序，客户端看到旧数据 | 事件带递增序号；重连补偿全量快照；关键交易数据出价前强制查询 |
| **WebSocket 连接管理** | 大量长连接、断线、假死 | 心跳保活；连接数监控；负载均衡 + 会话迁移 |
| **竞态一致性** | 「推送变动」与「客户端查询」之间数据又变 | 客户端查询接口返回带版本/时间戳，页面取最新 |
| **撮合引擎改造受限** | C 侧事件出口要改 C 代码，排期不可控 | 短期过渡：WS 服务定时比对快照生成事件（延迟升至秒级），**仅作临时方案**，不作长期架构 |
| **直推链路静默断流** | C 核心 ↔ WS 服务断开时客户端毫无感知（心跳仍通） | 链路心跳 + C 侧环形缓冲续传 + `stale` 标记三层兜底（见 2.5.6） |
| **失去 MQ 缓冲** | 直推后断线窗口内事件无人保存 | `seq` + `epoch` + 快照自愈；出价关键路径强制走查询接口（见 2.5.5） |
| **网关缓存失效** | 低频数据缓存后，事件要能触发失效 | 事件同时触发网关缓存失效/刷新 |
| **灰度双通道** | 新老并存期间数据可能不一致 | 灰度期用事件序号 + 快照对齐，出价关键路径不依赖缓存 |

## 九、结论

竞价详情页的改造核心是**把「实时强一致数据」从「定时穿透」换成「事件推送」**，把「慢变数据」从「穿透后端」降到「网关层缓存」。改造后：

1. **移除所有实时轮询**，最优价/出价记录改为 WebSocket 事件驱动，实时性更高、后端压力降 1~2 个数量级；
2. **低频轮询仅穿透网关层**，后端穿透归零；
3. 划分标准清晰：**实时强一致 → 事件推送；慢变弱一致 → 网关缓存**；
4. **推送链路独立**：C 核心直推独立 WS 服务，不经 dataShare 中继，推送与查询两套通道独立扩容、独立故障；直推新增的可靠性责任由 `seq`/`epoch`/`stale` 与降级轮询共同兜底。

---

*本方案推送链路为 **C 核心直推独立 WebSocket 服务**，不复用 dataShare 的订阅 / MQ / 推送通道；查询链路仍复用 midservice 网关与三级缓存 `ApiCacheMap`。C 侧事件出口与独立 WS 服务为新增改造项；`seq` / `epoch` / `stale` / 关闭码为两端共同实现的协议约定。*
