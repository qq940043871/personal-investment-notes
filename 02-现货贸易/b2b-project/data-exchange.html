DS 数据中心（数据交换总线）

Data Exchange Bus — 4 字节命令号统一寻址，收敛 40+ 异构子系统的协议转换与共享中间件能力

技术经理 / Java 侧负责人 ESB 式服务总线 异构协议互通 源码级容量诊断

一、项目背景与要解决的问题

平台是「C 内存撮合引擎 + Java 微服务业务中台」的异构组合，规模化后接入方超过 40+ 子系统：撮合/交易类系统走私有 TCP 二进制协议（5 套报文栈），Java 微服务走 Hessian，外部集成走 HTTP，还有 Go 侧系统透传（gomti 栈）。早期各业务方直连目标系统，问题很快暴露：

协议异构，各拼一套

5 套出向报文栈头长不同（11/32/16 字节）、编码不同（UTF-8/GBK）、分片阈值不同（4096/30720），直连方要各自实现一遍。

点对点强耦合

连接管理、登录认证、超时重试散落在各调用方；新增一个后端系统，每个调用方都要改一轮、发一轮版。

平台能力重复建设

缓存、消息、分布式锁、通知每个服务自建一套，口径不一、资源浪费，出问题没有统一的观测点。

核心定位：自研 DS 数据交换总线（dataShare）——本质是 ESB 式协议转接器 + 共享中间件代理。业务方经一套 SDK 以命令号发起调用，DS 按配置完成协议转换并转发到目标系统；同时把 Redis 缓存、Kafka 消息、分布式锁、通知等平台能力以命令号形式统一供给。对 C 撮合引擎而言，这一层就是 Java 侧的防腐层：报文细节被 DS 吸收，两侧独立演进。

边界澄清（高频追问点）：DS 不是注册中心——没有服务注册、心跳上报、动态发现，也没有负载均衡和熔断。寻址是静态的：协议配置在 DB 表（TB_DS_PROTOCOL / TB_DS_REGISTEERED_SERVICE）中维护，启动时全量加载进内存，改配置后通过管理命令号（0001fa03）在线重载。没有选 Dubbo/Spring Cloud，是因为要打通的核心是私有二进制协议栈与共享中间件代理，而给 40+ 存量子系统做无侵入接入，一套轻量命令号总线比引入全套 RPC 治理框架更可控。

三、协议设计：11 字节头 + 4 字节命令号

MainHeader（11 字节定长头，后接变长 body）
┌─────────┬──────────────────────┬────────┬────────────┬──────────────┐
│ length  │ mainHigh·mainLow·    │ state  │ encryption │ ansyKey      │
│ 2B 大端 │ subHigh·subLow  4×1B │ 1B     │ 1B         │ 3B（24bit）  │
│ body长度│ 4 字节命令号          │ 位标志 │ DES(未启用)│ 请求响应配对 │
└─────────┴──────────────────────┴────────┴────────────┴──────────────┘
命令号 = "DS" + 8 位十六进制，如 DS00010001；四段各 1 字节，子类只实现 low 两段

state 位标志（1 字节按位复用）

  • 0x40 处理成功（默认置位）
  • 0x20 分片续包——还有下一片
  • 0x10 body 已 gzip 压缩
  • 0x08 服务端异步推送包
  • 0x02 Base64 编码 / 0x01 Hessian 序列化

系统命令号（节选）

  • 00010000/01 心跳探活 / 登录认证
  • 00010030~36 缓存：取连接串/写/读/删/TTL
  • 00010033/34 消息发布 / 订阅（Kafka）
  • 00010040~43 分布式锁：加/解/批量加/批量解
  • 0001fa03 协议配置在线重载（读 DB 重建连接）

两级路由

粗键（前 2 字节）查内存 ProtocolCache 得 connType（走哪种协议栈）；细键（4 字节）按 t+8位hex+Service 约定分发到处理器。新协议=加一条配置+一个类，不改总线。

分片与压缩

body ≤ 4096 字节单包直发；超出按 4096 切片，每片带完整 11 字节头，中间片置 0x20 续包标志，读侧循环拼接后按 0x10 标志 gunzip。

ansyKey 配对设计

3 字节 24bit 请求-响应配对键，客户端池化 65534 个；按 JVM 实例随机选 30 档基数段填充——多实例 key 空间天然不重叠，服务端无需感知实例标识即可把响应还对线程。

SDK 线程模型

  • 同步调用占业务线程，1 连接 = 1 请求（同步 BIO），并发能力 = 连接池大小
  • init() 启动 9 个后台线程：假死扫描 ×1（10s 无更新判假死）+ 订阅重连 ×3（100ms 轮询）+ 推送分发 ×5
  • 读响应时遇 0x08 推送包投入异步队列继续读——同步业务线程永不串包
  • 默认超时 5000ms；仅响应头异常递归重试 1 次，其余异常直接关连接抛出

控制面 / 数据面分离（缓存）

  • 通道 A：命令号代理（00010031 写 / 00010032 读），小数据量经总线
  • 通道 B：00010030 向总线索取 Redis 连接串，客户端本地建 ShardedJedis 分片池直连
  • 大流量数据面不走总线，总线只承担控制面——避免总线成为缓存流量瓶颈
  • 命名空间按 module-key 隔离，各业务互不覆盖

五、平台能力矩阵（按 connType 分派）

connType=0 · 内置能力（35 个 T*Service）

  • Redis 缓存读写删/TTL，直接操作共享 Redis
  • Kafka 消息发布/订阅，offset 存 DB（60s 全量刷盘）支持断点续传
  • 分布式锁：setnx+expire 实现，TTL 默认 600s；批量锁先按键排序再依次加锁防死锁
  • 业务配置读取、短信/邮件通知等公共服务

connType=1 · Hessian 微服务

  • 按命令号用 ASM 动态生成接口字节码，建 JDK 动态代理发起 Hessian HTTP 调用
  • 任意 Java 对象跨进程直传（Hessian2 序列化），性能优于 JSON 栈
  • 后端元数据经协商接口拉取（class desc），接口无需提前对齐 jar

connType=2 · 私有 TCP（C 引擎）

  • 5 套报文栈适配（见上表），连接与池参数全部来自 TB_DS_PROTOCOL（SOCKET_TIMEOUT / SOCKET_INIT / SOCKET_MAX）
  • C 撮合引擎的委托/成交/行情均经此栈进出——Java 侧不触碰二进制细节

connType=3 · HTTP 集成

  • 外部 HTTP 服务统一封装调用与超时
  • 消息语义兜底：offset 在推送前记录（可能重复/丢失），业务侧以 Outbox + 消费幂等 + 对账补偿——与平台数据一致性口径一致

六、源码走读 + 压测：瓶颈诊断与 worker 线程池改造

接入压测后端到端 TPS 始终上不去。我们没有盲目加机器，而是先做反编译源码静态走读，把一次调用的每一跳线程模型、锁与连接池都摸清，再对照压测现象定位。结论：瓶颈是串行化设计，不是资源不足。

P0-1 · 网关 per-user 锁跨越整个远程调用

网关按 api+"_"+tokenId 加进程内锁包住从校验到远程调用的全程——单用户单 API 并发恒为 1，下游 RT=1s 时该用户该接口上限 1 QPS。压测怎么都上不去的根因是锁粒度而不是容量。

P0-2 · DS 业务处理同步阻塞在 IO 线程

HandlerImpl.run() 无线程移交，协议转换与后端调用直接在 reactor 线程上执行；代码里现成的线程池是无界 cachedThreadPool 且从未被接到请求路径。按单 reactor 推算 TPS≈1/RT（RT=50ms 时约 20），一次 10s 后端读超时=全系统停摆 10s，水平扩 midservice 也无效——DS 是链路上的单点。

P0-3 · 全局归还锁串行化所有请求

连接归还方法为 static synchronized——所有协议、所有请求在归还连接时排成单线，天花板 ≈1k TPS；另有 3 个全局 synchronized 在网关每请求路径上。

P0-4 · 池耗尽关整池 + 递归重试 = 雪崩路径

借连接超时（5s）后关闭整池（在途连接全部强杀）再递归重建，所有并发请求同时失败；Socket 路径递归重试上限 100 层，一次 10s 超时可放大为约 1000s 连接占用。Redis 借连接全局锁 + 业务锁自旋还构成正反馈崩溃回路。

改造方案：worker 线程池（结构性改造，收益最大）

① 有界 worker 池 + 背压

core 32 / max 128 / 队列 1000 / CallerRunsPolicy——队列满时 reactor 自己执行，天然退化为现状同步模型：不丢请求（交易系统不能丢），实现背压。

② 按 connType 分组隔离

TRADE_POOL 64 线程（撮合类）与 QUERY_POOL 32 线程（查询类）分开——慢撮合请求占不满查询线程，故障隔离。

③ 配套改造（缺一不可）

去掉归还连接的 static 全局锁；SOCKET_MAX 与 DS 池 ≥ worker 并发；递归重试收短为循环+指数退避+熔断；超时按协议分级。

预期收益：并发执行能力从 1 个 reactor 线程 → 64 worker 线程；撮合链路（RT=50ms）TPS 约 20 → 1280（64×）；慢后端从「停摆全平台」变为「只占满自己的 worker」。

走读中发现的典型缺陷（可作深挖谈资）

  • 锁序倒置：MQ 发布与短信投递共用的加锁逻辑在持全局锁时取业务锁——一个业务锁不释放，两类功能全体卡死（已给出修复：锁序反转，全局锁只保护 Map）。
  • 构造函数笔误：SDK 配置类把 this.userPswd=... 误写成给 userName 赋值——不显式设置密码就登录失败，正是联调期反复排查的诡异问题。
  • 命令号撞号：退订命令号低字节与订阅撞车，只能靠 body 区分——后来把命令号分配收进登记表流程，杜绝再犯。
  • 并发容器缺位：6 处承载路由/缓存的裸 HashMap/TreeMap 在并发下有 resize 成环与 CME 风险——逐个替换为 ConcurrentHashMap/快照遍历。

七、关键实现

SDK 同步调用核心流程

ansyKey 配对 + 分片发送 + 推送包分流，同步线程永不串包（机制示意，类名为真实命名）。

// DSClientAPI.executeCall 骨架（机制示意）
public byte[] executeCall(IProtocol protocol) {
    String key = headerKeyPool.getKey();          // 取 3B ansyKey（池 65534）
    SocketClient sc = BIOSocketConnectManager
            .getSocketClient(config);             // 池取连接，登录态已就绪
    try {
        protocol.getHeader().setAnsyKey(key);
        protocol.sendTo(sc.getOutputStream());    // 写头 + 分片(4096) + body
        MainHeader head;
        while (!(head = BIOProtocolReadUtils
                .readMainHeader(sc)).getAnsyKey().equals(key)) {
            if (head.isAnsyFlag())                // 0x08 服务端推送包
                ansyResponseQueue.offer(head);    // → 异步队列，继续读
        }
        byte[] body = BIOProtocolReadUtils
            .readProtocolBodyByteByNext(sc);      // 按 0x20 续包拼接
        if (head.isCompression()) body = GZipUtils.ungzip(body);
        if (!head.isStateOk()) throw new DSException(body); // 0x40
        return body;
    } finally {
        headerKeyPool.returnKey(key);
        BIOSocketConnectManager.releaseConnection(sc);
    }
}

worker 线程池改造（方案代码）

reactor 线程只做解码分派，业务执行移交有界 worker 池；CallerRunsPolicy 兜底背压。

// ConnServerThreadUtils：无界 cachedThreadPool → 有界业务池
private static final ThreadPoolExecutor TRADE_POOL =
    new ThreadPoolExecutor(64, 64, 60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000),
        new ThreadFactoryBuilder().setNameFormat("ds-trade-%d").build(),
        new ThreadPoolExecutor.CallerRunsPolicy());   // 满则 reactor 自跑=背压

private static final ThreadPoolExecutor QUERY_POOL =
    new ThreadPoolExecutor(32, 32, 60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000),
        new ThreadFactoryBuilder().setNameFormat("ds-query-%d").build(),
        new ThreadPoolExecutor.CallerRunsPolicy());

// HandlerImpl.run()：解码后移交，reactor 立即返回
public void run() {
    int connType = parseConnType(header);      // 粗键 → connType
    ThreadPoolExecutor pool = (connType == 2)
            ? TRADE_POOL : QUERY_POOL;
    pool.execute(() -> {
        try {
            dispatch(commandParse);            // 原同步 switch 分派
        } catch (Throwable e) {
            session.writeErr(header, e);       // 异常兜底回写
        }
    });
}

分布式锁命令号（setnx + expire，批量锁排序防死锁）

DS 的锁是命令号 00010040~43 的自研实现（非 Redisson），批量加锁按键排序规避死锁；同时我们清楚它的边界——锁值无 owner、无看门狗续期，Redis failover 场景可能丢锁，所以只用于可容忍极小概率互斥失效的场景。

// T00010040_LockBusinessService 机制示意
String lockKey = "DS-LOCK-DETAIL_" + module + "-" + key;
// setnx + expire：获得互斥；TTL 默认 600s 防死锁
if (setnx(lockKey, "1")) { expire(lockKey, 600); return true; }

// 批量锁：先排序再依次加锁，破坏循环等待条件
public boolean lockAll(List<String> keys) {
    Collections.sort(keyList);                 // 全局同一顺序 → 无死锁
    for (String k : keyList)
        if (!tryLock(module, k)) { unlockAll(keyList); return false; }
    return true;
}
