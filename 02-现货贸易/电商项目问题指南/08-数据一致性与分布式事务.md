## 🏗️ 一、CAP 定理

### 1.1 理论

```
                CAP 定理
                    │
        ┌───────────┼───────────┐
        │           │           │
        ▼           ▼           ▼
   ┌────────┐  ┌────────┐  ┌────────┐
   │   C   │  │   A   │  │   P   │
   │一致性  │  │可用性  │  │分区容错│
   └────────┘  └────────┘  └────────┘
   
   结论：只能同时满足 CA、CP 或 AP
   原因：网络分区不可避免，必须在 C 和 A 之间权衡
```

### 1.2 电商场景选择

| 场景 | CAP选择 | 说明 |
|------|---------|------|
| 支付核心 | CP | 强一致性优先 |
| 商品查询 | AP | 可用性优先 |
| 订单创建 | CP | 必须一致 |

## 🔄 二、BASE 理论

### 2.1 核心思想

```
BASE = Basically Available + Soft State + Eventually Consistent

基本可用：系统在故障时允许降级
软状态：允许中间状态存在
最终一致：经过一段时间后达到一致
```

### 2.2 vs 传统ACID

| 特性 | ACID | BASE |
|------|------|------|
| 一致性 | 强一致 | 最终一致 |
| 可用性 | 低 | 高 |
| 扩展性 | 差 | 好 |
| 适用场景 | 金融、订单 | 电商、社交 |

## 🛠️ 三、分布式事务解决方案

### 3.1 Saga 模式（本人 B2B 大宗平台实际采用）

> 本人在 B2B 大宗平台用 **Saga + 状态机 + 事件溯源** 处理跨月长事务：每个业务节点（下单→配货→发运→结算）由状态机驱动、可补偿，事件溯源留痕便于对账与追溯。

```
Saga执行流程：

订单创建 ──► 库存扣减 ──► 支付扣款 ──► 订单完成
    │            │            │
    ▼            ▼            ▼
  成功       成功        失败/补偿
    │            │            │
    └────────────┴────────────┘
                 │
                 ▼
           补偿事务执行
           退款 ──► 库存恢复 ──► 订单取消
```

### 3.2 本地消息表（本人 B2B 用 Kafka + outbox 落地）

> 本人在 B2B 平台采用 **Kafka + outbox** 变体：业务写库的同时写 outbox 表/事件，由 XXL-Job/Canal CDC 投递到 Kafka，消费端做幂等，保证"业务落库"与"消息投递"最终一致。

```java
@Service
public class OrderService {
    
    @Autowired
    private OrderDao orderDao;
    
    @Autowired
    private MessageDao messageDao;
    
    @Transactional
    public void createOrder(OrderDTO dto) {
        // 1. 创建订单
        orderDao.insert(dto);
        
        // 2. 记录消息（本地消息表）
        messageDao.insert(new Message()
            .setBizType("ORDER_CREATE")
            .setBizId(dto.getOrderId())
            .setStatus(0)  // 0=待发送
            .setRetryCount(0));
    }
}

// 消息发送定时任务（由 XXL-Job 调度）
public void sendPendingMessages() {
    List<Message> messages = messageDao.selectPending(100);
    
    for (Message msg : messages) {
        try {
            // 发送消息
            mqProducer.send(msg.getTopic(), msg.getContent());
            
            // 更新状态
            messageDao.updateStatus(msg.getId(), 1);
        } catch (Exception e) {
            // 失败重试
            messageDao.incrementRetry(msg.getId());
        }
    }
}
```

## 🎯 五、实战建议

### 5.1 选择原则

| 场景 | 推荐方案 |
|------|----------|
| 同库多表事务 | 本地事务 |
| 超长业务流程 | Saga |
| 非核心异步 | MQ消息 |

### 5.2 最佳实践

```java
// 1. 事务边界要小
@Transactional  // 控制在方法级别
public void createOrder() {
    // 事务内只做核心操作
}

// 2. 补偿机制要幂等
@Retryable(value = Exception.class, maxAttempts = 3)
public void compensate(Order order) {
    // 补偿操作必须幂等
}
```
