# 在线客服系统 · 完整设计文档

> **定位**：Spring Boot + Netty + Redis 的在线客服系统**从需求到落地**的完整设计文档——把「用户提问 → 智能首答 → 人工排队 → 客服接待 → 会话归档」做成一条**不丢消息**的链路。
> **角色**：后端负责人（架构 + 核心链路实现）。
> **适用场合**：方案评审 / 面试追问 / 交接与复盘。需要「为什么这么设计」的口径，也需要「哪里还没做好」的诚实清单。
> **口径约定**：本文按 §1 标注 `【底稿】`（源页面已写明的事实）、`【推演】`（本文补充的设计推导与数值测算，未在源页面出现）、`【待确认】`（源材料缺失或自相矛盾，需以实测/代码为准）。

---

## 零、三句话（被问到时先答这三句）

1. **这套系统不是「加个聊天框」，而是把咨询的潮汐削平**：下单高峰与故障期咨询量放大数倍、其余时间人力大量闲置，所以解法是「机器先答重复问题 + 排队把人力削峰」，而不是按峰值配人。
2. **两个决定性的技术选择**：通信层用 **Netty WebSocket 长连接替代 HTTP 轮询**（成本从「在线人数 × 轮询频率」变成「在线人数」）；在线态**全部收敛到 Redis**（在线表 / 排队队列 / 会话消息 / 客服能力），靠 TTL 自清理，不写清理任务。
3. **长连接的难点从来不是「连上」，而是「断了之后怎么办」**：客户端 3 秒重连 + 按序号补拉，服务端**在线态以 Redis 为准、不以 Channel 对象为准**，消息**先落 Redis 再转发**——这三条决定了「存住的」和「发出的」是同一份。

## 二、问题定义

### 2.1 业务背景

交易类业务的咨询有明显**时间潮汐**：下单高峰与故障期间咨询量瞬间放大几倍，其余时间人力大量闲置。同时用户主入口在微信，客服用的却是另一套企业内网系统。成本结构因此很特殊：**按峰值配人一定浪费，按均值配人在峰值一定崩**。

### 2.2 四个真问题（不是「有个聊天框」）

| # | 问题 | 不解决的后果 | 对应设计 |
|---|---|---|---|
| Q1 | **用户身份怎么统一**（微信 / 第三方认证） | 每个渠道一套账号，客服看到三个「同一个人」 | 微信 OAuth2.0 只做身份源，业务侧自签 sessionToken |
| Q2 | **消息怎么实时送达且不丢**（长连接而非轮询） | 轮询在高峰把服务器压垮；断线丢片段变成投诉 | Netty WebSocket + 序号补拉 + 先落库后转发 |
| Q3 | **人力怎么排队不浪费**（技能匹配 + 优先级 + 超时提醒） | 一条全局队列 → 懂技术的人被迫接财务问题 | 技能分队列 ZSet + score 公式 + 会话数负载均衡 |
| Q4 | **重复问题怎么不占人力**（先机器后人工） | 机器人打太极，用户被迫打「转人工」 | 知识库精确匹配 → 相似度 0.7 → 明确转人工出口 |

### 2.3 目标与非目标

| 类型 | 内容 |
|---|---|
| **目标** | ① 消息端到端可达且可恢复（断线不丢片段）；② 排队顺序可解释（VIP 插队但普通用户不被无限后推）；③ 客服能力实时影响派单；④ 会话可复盘（量 / 时长 / 满意度）；⑤ 在线态重启自愈、不依赖清理任务 |
| **非目标** | ① 不做全渠道客服工作台（电话 / 邮件 / 工单不在本期）；② 不做客服质检与 AI 训练闭环；③ 不做跨租户 SaaS 多租户隔离；④ 不承担超 30 天的会话归档（转数仓，见 §5 尾部） |

### 2.4 验收指标【推演】

| 类别 | 指标 | 目标值 | 判定方式 |
|---|---|---|---|
| 可达性 | 消息送达率（落库且对端最终渲染） | ≥ 99.99% | 落库条数 vs 客户端 seq 连续段 |
| 恢复性 | 断线重连后补拉成功率 | 100% | 注入断网 30s 后检查片段完整性 |
| 实时性 | 同机房消息端到端延迟 P99 | < 300ms | Netty 入站 → 客户端渲染 |
| 排队 | 派单正确率（技能不匹配 = 错） | ≥ 99.5% | 抽检派单日志 vs 技能标签 |
| 排队 | 等待位次与实际次序一致率 | 100% | ZRANK 重算比对 |
| 首答 | 知识库命中率 / 误答率 | 命中 ≥ 40%，误答 ≤ 2% | 抽样人工标注 |
| 容量 | 单实例长连接 / 集群并发会话 | 见 §8 | 压测 |

### 3.1 分层职责与「谁说了算」

| 层 | 职责 | 唯一权威 |
|---|---|---|
| 接入层 | 建连、鉴权、心跳、消息收发的搬运与扇出 | **不代表在线态**（见 D4） |
| 业务服务层 | 会话状态机、排队算法、能力判定、检索与过滤 | 业务规则唯一处 |
| Redis（在线态） | 在线与否、队列次序、消息内容、客服能力 | **在线真相源** |
| MySQL（离线态） | 客服主数据、> 30 天会话归档、审计流水 | 历史真相源【推演】 |

> 划分原则：**在线态是「有 TTL 的、可重建的」；历史态是「永久的、可审计的」**。两者混在一张表里，就会出现「为了查三个月前的聊天记录而给在线表加索引」这种反模式。

## 四、关键技术决策（决策 / 备选 / 代价）

### D1 通信层：Netty WebSocket 长连接，不用 HTTP 轮询

| 维度 | HTTP 轮询 | **Netty WebSocket（选定）** |
|---|---|---|
| 服务端成本 | 在线人数 × 轮询频率 | 在线人数（一连接一成本） |
| 高峰行为 | 咨询潮汐叠加轮询放大，请求量指数级上升 | 连接数可预期 |
| 消息延迟 | 被轮询间隔锁死 | 毫秒级直推 |
| 双向能力 | 需另建通道（客服主动推） | 原生双向 |

**代价**：长连接要自己解决**假死检测、重连风暴、慢客户端、单机连接上限**——这些在轮询模型里不存在。兜底见 §9。

### D2 数据层：不引入 MySQL 做在线态，在线态全收敛到 Redis

- **理由**：在线用户、排队队列、会话消息、客服能力四类数据的共同特征是「**生命周期短、读写频繁、可重建**」。Redis 的 ZSet / List / Hash + TTL 天然对上，且**不用写清理任务**（TTL 自过期）。
- **代价**：Redis 内存成为主要成本项；持久化策略必须明确（见 §9 故障矩阵）；**不能用 `keys` 扫描**（§12 缺陷 2）。
- **边界**：客服账号主数据、超 30 天归档、审计流水**不放进 Redis**。

### D3 消息顺序：先落 Redis 再转发，客户端按 seq 补拉

```
错误顺序：过滤 → 转发 → 落库     → 对端连接假死时消息永久丢失
正确顺序：过滤 → 落库 → 转发     → 转发送不出去，重连后按 seq 补拉回来
```

**代价**：落库在关键路径上，Redis 写延迟进入消息延迟；因此 Redis 必须与 Netty 同机房，且写失败要能降级为「先转发 + 标记丢失」（§9）。

### D4 在线态：以 Redis 为准，不以 Channel 对象为准

`Channel.isActive()` 在 **TCP 半开**（NAT/防火墙静默清会话、手机切网）时**依然返回 true**——此时写出去的消息会静默丢弃。所以在线判定只看 Redis 在线表（带 TTL 与心跳续期），Channel 仅作为「发送句柄」。

**代价**：多一次 Redis 读；且 Redis 在线表与真实连接之间存在**秒级窗口**（心跳间隔），不能用于计费类强一致场景。

### D5 排队：一条 score 公式的 Redis ZSet，不用「维护位次字段」

```
score = (100 - priority) × 1e12 + 入队毫秒
```

- 高位放优先级、低位放时间戳 → **一次排序同时满足「优先级高者在前」与「同级先来先服务」**，不需要额外比较逻辑，并发插入天然有序。
- 位次永远 `ZRANK + 1` 现算，**不维护位次字段**：队列每出一个人，全队列位次都变，维护字段等于每次出队批量更新几百条，自造写热点。

**代价**：score 的双精度与系数需校验（§7.2 给出上界推导与更严谨的取值建议）。

### D6 身份：不新建账号体系，Provider 模式接企业已有认证

`ldap / oauth / sso` 三个 `AuthProvider` 实现，新增一种认证只加一个类 + 一条配置。客户从自建 LDAP 换 ADFS，改的是配置与一个实现类，不是整个登录流程——这是多客户交付里最省事的一层抽象。

**代价**：认证失败/超时的责任边界在客户侧，需要明确的降级（本地应急账号）与审计。

### D7 转接：只改会话归属人，不新建会话

会话 ID 不变、客服 ID 变 → 历史消息天然延续、用户不用重讲、统计能算清「这个会话经过几个人」。新建会话会把上下文割裂。

### D8 两个「顺序敏感点」（这套系统真正区别于「能跑通」的地方）

| 场景 | 正确顺序 | 反过来的后果 |
|---|---|---|
| 排队分配 | **先建会话成功 → 再从队列移除** | 建会话失败 → 用户既不在队列也没有客服（最典型的丢单方式，极难排查） |
| 客服下线 | **先转接名下会话 → 再置离线** | 会话停在「已分配但没人看」，用户等到自己放弃 |
| 客服上线 | **先配能力 → 再置在线** | 以 0 能力上线、看起来在线却永远接不到单 |

## 五、数据模型（Redis 在线态）

| Key | 结构 | 语义 | TTL | 写入方 | 读放大风险 |
|---|---|---|---|---|---|
| `online:user:{uid}` | String / Hash | 用户在线表（含最后心跳、连接实例 ID） | 心跳间隔 × 3 | 接入层 | 低 |
| `online:cs:{csId}` | Hash | 客服在线状态 + 当前连接实例 | 心跳 × 3 | 接入层 | 低 |
| `queue:{skill}` | **ZSet** | 技能队列，member = queueId，score = 公式值 | 无（元素级） | 排队服务 | 低（O(logN)） |
| `queue_user:{queueId}` | Hash | 队列条目上下文（userId / skill / joinTime / priority） | 与条目同生共死 | 排队服务 | 低 |
| `chat_messages:{sessionId}` | **List** | 会话消息流（按 seq 递增，rightPush） | 会话结束后 24h【推演】 | 接入层 | **高（无裁剪，见 §12 缺陷 4）** |
| `session:{sessionId}` | Hash | 会话元数据（用户、当前客服、状态、起止时间） | 同会话 | 会话服务 | 低 |
| `cs_info:{csId}` | Hash | 能力（capacity / current_sessions）、技能标签、状态 | 长期 | 客服服务 | **高（全量扫描，见 §12 缺陷 2）** |
| `cs_sessions:{csId}` | List | 客服 → 会话 ID 列表（复盘用） | 30 天 | 客服服务 | 低 |
| `session_record:{sessionId}` | Hash | 单条会话记录（起止、满意度、归属客服） | 30 天 | 客服服务 | 低 |

**为什么不给「位次」建字段**：位次 = 队列位置的派生值，任何持久化都会在出队时变成写热点（见 D5）。

**为什么消息用 List 而不是 ZSet**：消息只需「按写入顺序追加 + 按 seq 游标读增量」，List 的 `rightPush` + `LRANGE` 足够；用 ZSet 反而要为每条消息算 score，白付 O(logN)。

**离线态（MySQL）【推演】**：`cs_account`（工号、认证源、状态）、`session_archive`（> 30 天，按月分区）、`audit_log`（敏感词命中、越权访问、派单变更）。

## 六、核心链路时序

### 6.1 一次提问的全链路

```
用户(H5)                接入层(Netty)               业务层               Redis
   │ ① 微信授权建连         │                          │                    │
   ├──────────────────────►│ 握手鉴权（sessionToken）   │                    │
   │                       ├─ 写 online:user ─────────────────────────────►│
   │ ② 发消息              │                          │                    │
   ├──────────────────────►│ 敏感词 Trie 过滤（落地前）  │                    │
   │                       ├─ ③ rightPush chat_messages:{sid} ────────────►│
   │                       ├─ ④ 智能首答检索 ─────────►│                    │
   │ ◄── 命中则立即回答案 ───┤                          │                    │
   │                       │ 未命中 → ⑤ 入队 queue:{skill} ─────────────►│
   │ ◄── 告知「前面还有 N 人」┤                          │                    │
   │                       │ ⑥ tryAssign（在线∩空位∩技能）                  │
   │ ◄── 分配给客服 A，双向可见 ──────────────────────►│                    │
```

**唯一不可调换的是 ③→④→转发的顺序**：过滤滞后 → 原文入库（合规风险）；落库滞后 → 消息丢失（体验事故）；转发先于过滤 → 双份风险。

### 6.2 断线重连与增量补拉

```
ws.onclose → 3s 后重连（退避可加权，避免服务重启全员同时打进来）
          → 握手带 sessionToken + lastSeq
          → 发 { type: 'RESUME', sessionId, afterSeq: lastSeq }
          → 服务端从 chat_messages:{sid} 取 > afterSeq 的增量
          → 客户端 if (msg.seq <= lastSeq) 丢弃   ← 幂等，防重放重复渲染
```

**重连必须是幂等的**：不能每次重连都把历史数组重放一遍，否则用户看到重复消息。

### 6.3 排队 → 派单 → 出队

```
入队：ZADD queue:{skill} score(queueId)  +  HSET queue_user:{queueId} ...
     ↓ 入队即 tryAssign（空闲客服不空转）
可用集：status=ONLINE ∩ current_sessions < capacity ∩ skills∋skill
     ↓ 按 current_sessions 升序取第一个（最不忙的优先）
先建会话 → assign(queueId, csId) → 成功后 ZREM queue:{skill} queueId
     ↓ 失败则成员留在队列，下一轮巡检重试
```

### 6.4 会话转接（换人不重讲）

`session:{sid}.csId = B`，同时 `cs_sessions:{A}` 移除、`cs_sessions:{B}` 追加，`current_sessions` 双向增减。**sessionId 不变**。

### 6.5 客服下线

```
transferSessions(csId)   ← 先：名下有进行中会话则按能力重新派/回队
        ↓
status = OFFLINE          ← 后：才置离线
```

## 七、关键机制详解

### 7.1 消息顺序、幂等与可靠性等级

| 消息类型 | 丢失后果 | 策略 |
|---|---|---|
| 聊天正文 | 用户重复描述、投诉 | 先落库后转发 + seq 补拉，**必达** |
| 排队位次通知 | 用户以为没进展 | 可重算，允许丢（下次巡检重发） |
| 会话状态变化（已分配 / 已结束） | 前端状态机卡死 | 随消息流带状态字段，落库，**必达** |
| 客服在线状态 | 派单到离线客服 | Redis TTL + 派单前二次校验 |

### 7.2 排队 score 公式的上界推导【推演】

设 `score = (100 - priority) × 1e12 + ts`，`priority ∈ [0,100]`，`ts` 为毫秒时间戳（当前约 `1.76e12`）。

1. **双精度是否够用**：IEEE754 double 可精确表示 `2^53 = 9.007e15` 以内的整数。本公式 score 上界 ≈ `100e12 + 1.766e12 ≈ 1.02e14 < 9e15` ✅ **不会因精度丢失碰撞**。
2. **「高位 / 低位」的位数直觉是错的，但排序结论是对的**：`1e12 ms ≈ 31.7 年`，即「优先级差 1 级」等价于「时间差 31.7 年」——任何现实排队窗口内**优先级都严格优先**。但要注意 `ts` 的绝对值已到 `1.766e12`，**已经超过 `1e12` 这个「一级优先级」的宽度**，所以「低 12 位放时间戳」的划分并不成立（score 实际在 `1.0e14` 量级）。这不影响排序正确性（差值仍由系数决定），但说明一件事：**系数不能改小**。若为了「数字好看」把系数改成 `1e10`，时间项就会反超优先级，出现「VIP 排到普通用户后面」的隐性 bug，而这种 bug 在测试环境小数据量下几乎不会暴露。
3. **更清晰的取值（建议）**：`score = (100 - priority) × 1e13 + (ts - tsBase)`，`tsBase` 取当日 0 点，把低位压到 `8.64e7`（8 位）。上界 `1e15 + 8.64e7 ≈ 1e15 < 9e15` ✅，且「高位 / 低位」与直觉一致，跨天只需重算 score、不必迁移。
4. **同毫秒并发**：同一毫秒入队、且同优先级的两个条目 score **完全相同** → ZSet 按 member 字典序作 tie-break，**不是先来先服务**。若需严格，低位改为「毫秒 × 1000 + 自增序列」或改用 `(ts, seq)` 复合评分。

> 这一段是「一条公式」叙事最容易被追问的地方：能说清「系数为什么是这个量级、哪里会翻车」，比背公式本身值钱。

> 这一段是「一条公式」叙事最容易被追问的地方：能说清「公式在什么窗口内成立、边界在哪」，比背公式本身更值钱。

### 7.3 分配原子性【推演 · 缺陷与改进】

源设计的 `tryAssign` 是「**读 head → 分配 → 移除**」三步非原子操作，并发下有两个真实风险：

| 风险 | 场景 | 后果 |
|---|---|---|
| 同一排队条目被两个客服抢 | 两个实例同时 `range(0,0)` 拿到同一 queueId | 重复建会话 / 用户收到两个客服 |
| 客服被塞爆 | 并发派单同时通过 `hasRoom` 判定 | `current_sessions` 超 capacity |

**改进方案（按成本递增）**：

1. **`ZPOPMIN` 替代 `range+remove`**：出队是原子的，但「建会话失败要回滚」需要 `ZADD` 回补（回补用原 score 可保序）。
2. **单 key 用 Lua 脚本**：把「取 head + 校验 capacity + 占用会话位 + 移除条目」写成一个脚本，Redis 单线程保证原子。
3. **按客服分片的分布式锁**：`SET lock:cs:{csId} NX PX 3000`，锁粒度落在客服而非队列，避免全队列串行。

**为什么不直接上分布式锁**：派单是高频路径，锁粒度太粗会把排队吞吐打回单机水平。优先用 **Lua + 分片锁兜底**，而不是全局锁。

### 7.4 智能首答：必须有「答不了」的明确出口

```
用户提问
  ├─ ① 精确匹配（同义问法归一化后）         → 命中即答 + 提示「回复『转人工』可接入」
  ├─ ② 相似度匹配，阈值 0.7                  → 命中即答（低于阈值不硬答）
  └─ ③ 未命中 / 阈值不达                     → 直接转人工队列
```

**设计原则：宁可早转，不要瞎答。** 做不好这件事的系统会陷入更糟的体验：机器人反复打太极，用户被迫学会打「转人工」。

**代价**：0.7 是全局阈值，不同类目（费率咨询 vs 功能咨询）应可分别配置；阈值越低命中越高但误答风险上升——**误答的成本高于转人工**，所以阈值宁高不低。

### 7.5 敏感词：过滤在「落地之前」而不是「展示之前」

- **Trie 树一次扫描 O(n)**：不需要对词库里每个词跑一次 `contains`（O(n×m)）。
- **顺序强制**：先滤后存。一旦先存后滤，Redis 里就留下未过滤原文，等于把风险存进日志。
- **双层**：内置词库（快、离线可用）+ 可选第三方内容安全（覆盖变体、拼音、拆字）。
- **合规冲突**【推演】：审计往往需要看原文。正解是**脱敏原文单独进审计域（加密 + 独立权限 + 独立留存期）**，而不是让它留在会话消息里。

### 7.6 归档与统计口径

- 记录结构：`cs_sessions:{csId}`（List）+ `session_record:{sid}`（Hash），查「某人某天」只扫这个人的列表，**不做全表扫描**。
- **统计口径写入时固定**：时长 = `endTime - startTime`，**只算已结束会话**。否则事后统计会出现「同一个数字三种算法」。
- 留存 30 天（TTL 自过期），超期转数仓。

## 八、容量与资源测算【推演 · 需实测替换】

### 8.1 连接与内存

| 项 | 估算 | 依据 / 说明 |
|---|---|---|
| 单实例长连接 | 1 万 ~ 5 万 | 4C8G / 堆 4G，受 fd 上限（需调 `ulimit -n` 至 10 万+）与 GC 影响 |
| 单连接内存 | 5 ~ 20 KB | Netty Channel + 读写缓冲（含 `ByteBuf` 池化后余量） |
| 单条消息 | 0.3 ~ 1 KB | 纯文本；图片走对象存储只存 URL |
| 单会话消息量 | 200 ~ 500 条 | 超出后滚动裁剪（见 §12 缺陷 4） |
| Redis 在线表 | 10 万用户 × 0.5 KB ≈ **50 MB** | Hash 字段少、值短 |
| Redis 会话消息 | 1 万活跃会话 × 300 条 × 0.5 KB ≈ **1.5 GB** | **内存主要成本项** |

### 8.2 峰值与放大

| 项 | 公式 | 备注 |
|---|---|---|
| 消息扇出 | 每消息 = 1 次落库 + 1~2 次转发 | 转接期间是 2 |
| 派单峰值 | 咨询潮汐 × 优先级插入 | ZSet 写 O(logN)，可忽略 |
| 巡检成本 | 队列数 × (30s 一次) | 位次现算，巡检只查「等待 > 5min」的头部 |

### 8.3 压测要点

1. **连接风暴**：重启 1 万客户端同时重连（验证退避与抖动是否生效）；
2. **消息洪水**：单会话 100 msg/s 持续 5 分钟（验证 List 增长与客户端渲染）；
3. **Redis 抖动**：注入 200ms 延迟（验证关键路径降级）；
4. **派单并发**：100 用户同时入队、5 客服（验证 §7.3 的超卖）。

## 九、故障矩阵与降级

| 故障 | 表现 | 根因 | 动作 |
|---|---|---|---|
| **连接静默半开** | 连接对象在、发消息无回应 | NAT/防火墙空闲超时静默清会话（常见 60s/300s） | 应用层心跳（间隔 < 最短空闲超时）<br>连续 2 次未回才判死（抗抖动）<br>判死后立即重连 + 补拉 |
| **Redis 不可用** | 消息无法落库 | 单点 / 内存满 | 关键路径降级为「先转发 + 内存队列暂存 + 标记未落库」，恢复后补写；**宁可短时不可靠，不要整条链路停摆** |
| **单 Netty 实例挂** | 该实例上全部连接断 | 进程 OOM / 发布 | 客户端退避重连 + 抖动错峰；在线表靠 TTL 自动清理**幽灵在线** |
| **多实例会话路由** | 客服与用户连在不同实例，消息发不出去 | 单机 `Map<userId, Channel>` 不可跨实例 | **见 §12 缺陷 1：需引入路由层（Redis 记录 uid→实例）+ 实例间转发（MQ/Redis Pub/Sub）** |
| **智能首答超时** | 用户等待 | 检索/LLM 抖动 | **超时直接转人工**，不让用户等模型 |
| **微信接口超时** | 无法登录 / 拉不到资料 | 微信侧限流 | access_token 与用户资料**缓存而非每次实时拉取**，避免把微信变成链路单点 |
| **客服突然关页面** | 会话无人应答 | 未点「离线」 | 心跳超时自动置离线 + 自动触发转接（复用 §6.5 顺序） |
| **慢客户端** | 单连接拖慢扇出 | 客户端不读 | 每连接独立有界发送队列，满则丢弃可覆盖消息（位次类）；聊天正文不丢 |

## 十二、已知缺陷与技术债（诚实清单）

> 这一节是本文与「宣传稿」的分界线。前 5 条是源页面设计中的真实薄弱点，第 6 条起是演进缺口。

| # | 缺陷 | 影响 | 建议动作 |
|---|---|---|---|
| 1 | **单机 `CHANNELS` 映射，多实例不可达** | 客服与用户连在不同 Netty 实例时消息发不出（源页面未涉及集群路由） | Redis 记 `uid → instanceId`，跨实例走 MQ / Redis Pub/Sub 转发；或接入层做一致性哈希 |
| 2 | `redisTemplate.keys("cs_info:*")` 全量扫描 | 生产环境 `keys` 是**阻塞式**命令，客服数上百即可能拖慢整个 Redis | 改用 `SET cs_pool:{skill}` 索引 + 批量 `HGETALL`；客服池变更时维护 |
| 3 | 派单「读 head → 分配 → 移除」非原子 | 并发重复派单 / 客服超载（§7.3） | `ZPOPMIN` 或 Lua 脚本 + 按客服分片锁 |
| 4 | `chat_messages:{sid}` 无裁剪策略 | 长会话内存单调增长 | `LTRIM` 保留最近 N 条 + 更早的落冷存；或按会话分段 key |
| 5 | 无应用层消息 ACK | 依赖客户端 seq 补拉，服务端不知道「是否真收到」 | 补拉已覆盖可用性；若要精确投递需引入 ACK + 重投窗口 |
| 6 | 排队超时「只提醒不兜底」 | 等待 5 分钟的用户仍可能无线可接 | 加「留言转工单」「预约回呼」出口，避免用户无出口流失 |
| 7 | 首答阈值全局固定 0.7 | 不同类目误答率差异大 | 阈值按技能/类目配置 + 误答样本回流 |
| 8 | 无多活 / 无 Redis 持久化口径 | Redis 重启丢失在线态与队列 | 明确 AOF 策略；在线态可重建，**队列需持久化**（否则重启丢排队） |
| 9 | token 时长两处不一致（12h / 24h） | 安全与体验口径混乱 | 定一处为准，写进配置而非散落代码 |
| 10 | 敏感词与审计的合规冲突未落地 | 审计要原文、合规要脱敏 | 双写：会话库脱敏版 + 审计域加密原文 |

## 十四、高频追问预案

**Q1：为什么不用轮询？轮询不是更简单吗？**
简单，但成本随「在线人数 × 频率」放大，而咨询本身就是潮汐场景，**峰值叠加轮询放大最危险**；且客服主动推送（新消息提醒、被转接通知）在轮询下必须另建通道。轮询只适合「变化慢、可缓存」的数据。

**Q2：长连接断了怎么办？**
三层一体：**客户端** 3 秒重连 + 退避抖动；**服务端** 应用层双向心跳判死（不依赖 TCP keepalive，默认 2 小时太长）；**数据** 消息先落库 + seq 游标补拉 + 幂等去重。关键不是「断了怎么连」，而是「怎么尽快发现已经断了」——静默半开时客户端根本不知道自己断了。

**Q3：Redis 挂了怎么办？消息会不会全丢？**
在线态可重建（用户重连即恢复在线表），**队列不能丢**（要 AOF 持久化）；消息在落库失败时进入「先转发 + 暂存 + 补写」的降级路径，并打点上报。**宁可短时不可靠，不可整链停摆**。

**Q4：一条 score 公式真的够吗？边界在哪？**
够用。`1e12 ms` ≈ 31.7 年，所以「一级优先级」的权重远大于任何现实排队窗口，优先级永远优先；双精度上界 `9e15` 也远大于 score 的 `1e14` 量级，不会碰撞。三个真实的边界是：① **系数不能改小**（改成 `1e10` 就会被时间项反超）；② 同毫秒且同优先级的条目靠 member 字典序 tie-break，不是先来先服务；③ 直觉上「低 12 位放时间戳」不成立（时间戳已是 13 位），要严格就减基准到当日 0 点（§7.2）。

**Q5：VIP 插队会不会把普通用户饿死？**
这是必须承认的风险。梯度只解决「同队列内顺序」，不解决「长期饥饿」。兜底应是：优先级档位有限（如 3 档而非连续分值）、对等待超阈值的普通用户升级优先级、或用加权排队而非绝对优先。

**Q6：派单怎么保证不超卖？**
源设计的「读时判定」比「缓存布尔值」正确（缓存必然在并发下抢爆最后一位），但仍需原子化：`ZPOPMIN` / Lua / 按客服分片锁（§7.3）。**读时判定解决「看到的状态新」，原子操作解决「两个人同时看到同一个新状态」**。

**Q7：为什么不给排队用户存「位次」字段？**
位次是队列位置的派生值。只要出一个人，后面所有人的位次都变——维护字段就等于每次出队批量更新几百条记录，这是**自己制造的写热点**。`ZRANK+1` 是 O(logN)，读多写零。

**Q8：智能首答答错了不是更糟？**
是。所以设计成「精确 → 相似度 0.7 → 转人工」三级，且**未命中直接转人工，不硬答**。误答成本 > 转人工成本。

**Q9：客服和用户连在不同实例怎么办？**
这是源设计的缺口（单机 Channel Map）。正解是路由：Redis 记 `uid → instanceId`，跨实例转发；或接入层按 uid 做一致性哈希。已在 §12 缺陷 1 明确列为待补。

**Q10：转接为什么不是新建会话？**
新建会割裂上下文，用户要重讲一遍。改归属人则历史消息天然延续，统计还能算「经过几个人」。代价是会话状态机要能表达「多客服参与」。

**Q11：客服下线时手上还有会话怎么办？**
**先转接、后离线**。反过来的会话会永远停在「已分配但没人看」——用户等到自己放弃。心跳超时也要走同一条路径。

**Q12：这套系统最难的部分是什么？**
不是功能，是**「顺序」和「真相源」**：过滤/落库/转发的顺序、建会话/出队的顺序、转接/离线的顺序；以及「在线态以 Redis 为准，不以连接对象为准」。这四件事错了任何一件，系统都能演示，但都会在真实弱网高峰里出事。
