# 前端登录态三存储不一致 — 页面显示已登录、接口却不认（排查与治理实录）

> **文档定位**：典型故障排查实录（前端通用问题，非特定项目事故）。回答"`localStorage` / `sessionStorage` / `Cookie` 各自管什么、谁说了算；当它们判断出来的『当前登录人』不一致时，页面为什么会呈现自相矛盾的状态"。讲**状态治理能力**：不是教你多存一份，而是教你砍掉多余的事实源。
>
> **配套阅读**：`06-Cookie认证失败-5Why根因分析.md`（Cookie 在网络链路被打断的另一种失效）；`11-网关扩容打穿DB-性能开发规范.md`（同样是"先立规矩再加机器"的思路）。

## 1. 现象：一个页面，两个"当前登录人"

### 1.1 故障表现

| 维度 | 描述 |
|------|------|
| **界面表现** | 右上角稳定显示「张三 · 已登录」，下拉菜单里有"退出登录"；账户中心还能读出头像、公司名、手机号 |
| **业务表现** | 点任何一个业务按钮 → 接口返回 401 / 提示"登录已过期，请重新登录" / 被踢到登录页；重新登录后好一会儿，刷新又变回去 |
| **浏览器** | 全程没有关闭浏览器，也没有清理过数据；无痕窗口 / 另一台电脑上一切正常 |
| **DevTools 取证** | `Application → Local Storage` 里 `user = {uid: 1001, name: "张三"}`；`Application → Cookies` 里 `token` 已过期，或解出来的 `uid = 1002`，或**根本不存在** |
| **复现率** | 特定路径必现（登出后再登录 / 换账号 / 隔夜后再来 / 新开标签页），不是偶发 |

### 1.2 一句话定性

> **前端有两个事实源，而且没有仲裁规则。**
>
> `localStorage` 说"你是谁"（负责渲染），`Cookie` 说"服务端认不认你"（负责鉴权）。
> 两者独立写入、独立过期、独立清理，谁也没校验谁 —— 于是页面照着 `localStorage` 画，接口照着 `Cookie` 判，
> 必然出现"**显示已登录，实际未登录**"这类自相矛盾的状态。

```
┌─────────────────────────── 浏览器 ───────────────────────────┐
│                                                              │
│   localStorage.user.uid = 1001  ──▶  渲染层：头部/菜单/按钮    │
│        （永不过期，没人清就一直躺着）        ▲                 │
│                                            │ 无交叉校验       │
│   Cookie.token (HttpOnly) ────────▶  请求层：每次自动带上      │
│        （7 天过期 / 被踢下线 / 被覆盖）      ▼                 │
│                                        服务端 Redis 校验      │
└──────────────────────────────────────────────────────────────┘
        两个源各说各话 → 页面"已登录"，接口"未登录"
```

### 1.3 危害分级（别只当成 UI bug）

| 级别 | 表现 | 后果 |
|:---:|------|------|
| **L1 体验** | 假登录态：页面有名字、点啥都 401 | 用户反复登录反复失败，投诉"系统坏了" |
| **L2 数据（严重）** | A 标签页显示账号 1，请求实际带的是账号 2 的 Cookie | **串号**：看到别家公司的报价/订单 —— 这是安全事故，不是体验问题 |
| **L3 权限** | 按 `localStorage.user.roleCode` 决定按钮显隐 | 后台已降权/改角色，前端仍显示"审批"入口；点了 403 是轻的，后端漏校验就是越权 |
| **L4 排查成本** | 三个存储面板各自都有值，都对不上 | 一线只会说"清一下缓存试试"，根因永远不落到代码里 |

## 2. 三存储的能力边界（先分清谁管什么）

### 2.1 对照表

| 维度 | Cookie | localStorage | sessionStorage |
|------|--------|--------------|----------------|
| 容量 | ≈ 4 KB / 域名（按个数还有上限） | ≈ 5–10 MB | ≈ 5–10 MB |
| 生命周期 | `Expires`/`Max-Age` 到期；不设则为会话级（关浏览器清除，但"恢复上次会话"可能保留） | **永不过期**，只能显式删 | 当前标签页关闭即清除 |
| 是否随请求自动发送 | **是**，同源请求自动带 | 否，要手动塞 Header | 否 |
| 作用域 | 域名 + Path（可跨子域，`Domain=.corp.com`） | 同源（协议+域名+端口），**不跨子域** | 同源 + **单标签页** |
| JS 可读写 | 非 HttpOnly 可读；**HttpOnly 完全不可读不可删** | 可读可写 | 可读可写 |
| 跨标签页共享 | 是（同一浏览器同一域名） | 是（同一源） | **否**（每标签各一份） |
| 抗 XSS | HttpOnly 时可防窃取 | 完全暴露给 XSS | 完全暴露给 XSS |
| SSR / 首屏可用 | 是（请求头里就有） | 否（要等 JS 起来） | 否 |

### 2.2 三个反直觉点（八成的坑都在这）

**① `sessionStorage` 是"每个标签页一个"，不是"每个会话一个"。**
用户在中台点了个链接新开标签页 → 新标签的 `sessionStorage` 是空的 → "明明刚登录，怎么又要登录"。而**复制标签页**会连同 `sessionStorage` 一起复制，于是两个标签各自持有一份互不感知的副本，一个登出另一个毫无反应。

**② Cookie 允许"同名多份"共存。**
`Domain=.corp.com` 写下的 `token`，和某子域 host-only 写下的 `token`，是**两条独立记录**。请求头里就会出现 `Cookie: token=新值; token=旧值`，服务端按实现取第一个或最后一个 —— 于是"刚登录成功，下一个请求却用了旧 token"。`Path` 不同也会造成同样的重复。

**③ HttpOnly 的 Cookie，前端 JS 删不掉。**
`document.cookie = 'token=; Max-Age=0'` 对 HttpOnly 那条**无效**（这是它的设计目的）。所以"退出登录"如果只是 `localStorage.clear()`，Cookie 原封不动 —— 页面显示已登出，服务端却仍然认你。这是"登出没登干净"的头号原因。

## 3. 不一致的九种产生路径（故障地图）

| # | 场景 | localStorage | Cookie | 用户看到 |
|:---:|------|--------------|--------|---------|
| **A** | 登出只清了前端，没调后端 logout（或 Cookie 是 HttpOnly 删不掉） | 已清空 | 仍有效 | 页面"未登录"，接口"已登录"；再点登录提示已登录 |
| **B** | 两端过期时间不同：`localStorage` 永久，Cookie 7 天 | 还在 | 已过期 | **隔夜/一周后必现**的"显示已登录、点啥都 401" |
| **C** | 用户/插件清了站点数据："关浏览器清 Cookie，但保留站点数据" | 还在 | 没了 | 上面那条的加速版 |
| **D** | 同名 Cookie 多份（子域 / Path / Secure 与非 Secure 并存） | 新值 | 旧值先被取到 | 登录成功但请求被当成旧会话 |
| **E** | 多标签页并发登录**不同账号** | 全局一份，后写覆盖 | 全局一份，后登录覆盖 | A 标签显示账号 1、B 标签显示账号 2，请求统一带最后那个 → **串号** |
| **F** | 只存了 `uid`/`user` 对象，没存版本或时间戳 | 陈旧快照 | 已轮换/已失效 | 改了密码、被踢下线、被改角色，前端毫不知情 |
| **G** | 前端 `document.cookie` 自己写一份，后端 `Set-Cookie` 又写一份，值不同 | — | 两份不同值 | 前端按自己写的判断"已登录"，服务端认另一份 |
| **H** | 隐身窗口 / 另一浏览器 / 另一设备登录，服务端单点踢人 | 本机仍在 | 已被服务端作废 | 单设备登录策略下的"假登录" |
| **I** | SPA 只更新内存 store，没写回持久层（或反之） | 与实际不符 | 正常 | **刷新就变脸**：不刷新好好的，一刷新就掉登录 / 或反过来 |

> **归纳**：A、C、D 是**清理不彻底**；B、F、H 是**过期不同步**；E、G 是**写入无仲裁**；I 是**内存与持久层脱节**。
> 四类问题的修法完全不同，所以第一步必须先定位到"哪一类"，别上来就 `localStorage.clear()`。

## 4. 5Why 根因分析

### Why 1：为什么页面会显示"已登录"？

头部组件判断登录态的方式是 `if (store.user || localStorage.getItem('user'))` —— **只要对象存在就渲染已登录**。它判断的是"有没有缓存"，不是"凭证还有没有效"。

### Why 2：为什么接口不认？

网关鉴权只读 Cookie 里的 token，去 Redis 查会话。查不到 / 已过期 / 与请求方不匹配，一律 401。**鉴权链路完全不看 `localStorage`** —— 这本身是对的。

### Why 3：为什么两个源会不一致？

因为它们是**两条互不相干的写入/清理链路**：

| | localStorage | Cookie |
|---|---|---|
| 谁写 | 前端 JS 登录成功后 | 后端 `Set-Cookie`（HttpOnly，前端碰不到） |
| 何时失效 | 没人清就永不失效 | 到期 / 服务端删会话 / 被新登录覆盖 |
| 谁清 | 前端登出逻辑（可能漏） | 后端 `Max-Age=0` / 浏览器策略 |

两套生命周期、两套清理责任、没有一致性约束（无版本号、无交叉校验、无登出原子性），**不一致只是时间问题，不是概率问题**。

### Why 4：为什么设计时允许两个源？

初衷是合理的分工：Cookie 给服务端（HttpOnly 防 XSS），`localStorage` 给前端（省掉每次刷新都请求 `/api/me`）。**错不在分工，错在没有指定谁是唯一权威。**

### Why 5：为什么没指定权威？

因为前端把**缓存**当成了**状态**。缓存可以丢、可以过期、可以陈旧，丢了顶多多一次请求；状态必须由服务端裁决，判错了就是假登录、串号、越权。设计时没人写下"登录态的唯一真相在服务端，前端一切展示都是可丢弃的缓存"这条不变量。

### 根因总结

> **直接根因**：`localStorage` 中的用户快照与 Cookie 中的凭证各自独立维护，前端以缓存的存在性代替凭证的有效性做登录判定，且登出/过期/换号等场景缺少原子清理与交叉校验，导致两个事实源长期不一致。
>
> **深层根因**：登录态缺少"唯一权威源 + 缓存可丢弃"的架构约束，前端用展示层缓存承担了本该由服务端裁决的身份判定职责。

## 5. 排查手册（四步定点，别猜）

### Step 1 三个面板同时打开，抓三个 `uid`

| 取证点 | 位置 | 看什么 |
|--------|------|--------|
| ① 渲染态 | `Application → Local Storage` | `user.uid` / `token` / `roleCode` / 有无版本戳 |
| ② 凭证态 | `Application → Cookies` | `token` 是否存在、`Expires` 是否已过、`HttpOnly/Secure/Domain/Path` |
| ③ 真实态 | `Network → 任意业务请求 → Response`（或手动调 `/api/me`） | 服务端认定的当前用户 |

**三者对齐 → 不是本文问题；①②一致但 ③ 不同 → 凭证失效（B/C/F/H）；① ③ 一致但 ② 不同 → 前端有脏缓存（A/E）；② ③ 一致但 ① 不同 → 渲染层读了旧源（I）。**

### Step 2 看请求头有没有重复的 Cookie 名

```
Cookie: token=eyJhbGci...(新); token=eyJhbGci...(旧)   ← 同名两份，必查 D
```

一条请求里出现两个同名 Cookie，说明**历史上用不同 `Domain`/`Path` 写过**，旧的那条不会因为你写新值而消失。

### Step 3 跑一遍"六种复现矩阵"，把范围缩到一行

| 操作 | 现象 | 指向 |
|------|------|------|
| 仅 F5 刷新 | 掉登录 / 变脸 | I（内存与持久层脱节） |
| Ctrl+点击新开标签页 | 新标签未登录 | 用了 sessionStorage 存凭证 |
| 复制标签页 | 两个标签状态不一致 | E（各自持有副本） |
| 关闭浏览器再打开 | 掉登录 | B（会话级 Cookie 或过期） |
| 换个账号登录 | 显示旧账号名 | A/E（清理或覆盖不彻底） |
| 手动删掉 Cookie 后刷新 | 仍显示已登录 | **100% 确诊**：渲染完全依赖 localStorage |

### Step 4 控制台一键取证

```javascript
// 贴到 Console，一次打印"三个事实源"
(() => {
  const ls = { ...localStorage }, ss = { ...sessionStorage };
  const ck = Object.fromEntries(
    document.cookie.split('; ').filter(Boolean).map(s => {
      const i = s.indexOf('='); return [s.slice(0, i), s.slice(i + 1)];
    })
  );
  const decode = t => { try {
    return JSON.parse(atob(t.split('.')[1].replace(/-/g, '+').replace(/_/g, '/')));
  } catch { return null; } };
  console.table({
    'localStorage.user': ls.user,
    'localStorage.token(uid/exp)': (() => { const p = ls.token && decode(ls.token);
      return p ? { uid: p.uid, exp: new Date(p.exp * 1000).toLocaleString() } : '无或非JWT'; })(),
    'Cookie 非 HttpOnly 可见项': ck,
    'Cookie 是否 HttpOnly': '若 Network 有、这里没有 → HttpOnly（正常，但 JS 删不掉）',
    'sessionStorage 键': Object.keys(ss),
  });
  fetch('/api/me', { credentials: 'include' }).then(r => r.json())
    .then(d => console.log('服务端认定的当前用户 =', d)).catch(e => console.warn('未取到 /api/me', e));
})();
```

> 最后那行 `fetch` 是关键：**只有服务端说的才算数**。判完立刻能区分"前端脏"还是"凭证失效"。

## 6. 治理方案：一个权威源 + 三条铁律

### 6.1 铁律一：Cookie 是唯一凭证，前端永不"自证身份"

- **token 只放 `HttpOnly + Secure + SameSite=Lax` 的 Cookie**（跨站场景按需 `None; Secure`），前端 JS 不写、不读、不解析它当身份 —— 最多解 `exp` 做提前续期。
- `localStorage` 降级为**纯展示缓存**，且必须带版本戳：

```json
{ "uid": 1001, "name": "张三", "roleCode": "BUYER",
  "sessionId": "s_8f3a...", "tokenVersion": 7, "fetchedAt": 1762000000000 }
```

- 展示缓存**允许缺失**：缺了就去请求 `/api/me`，绝不能因为缺了就误判"未登录"，也不能因为"有值"就误判"已登录"。

### 6.2 铁律二：所有"已登录"判定以服务端为准（启动校验 + 401 收口 + 版本戳）

| 场景 | 判定 | 动作 |
|------|------|------|
| 有 Cookie，无缓存 | 登录中 | 调 `/api/me` 补齐缓存，失败即按未登录处理 |
| 有 Cookie，缓存过期（`fetchedAt` 超阈值，如 30 分钟） | 登录中 | 后台静默刷新 `/api/me`，界面先按缓存渲染 |
| **无 Cookie，有缓存** | **未登录（缓存不可信）** | **立即清全部缓存 + 跳登录**，禁止渲染已登录 |
| 接口返回 401 / 419 | 会话已失效 | 统一收口函数：清 store → 清 storage → 跳登录并带 `redirect` |
| `/api/me` 的 `sessionId`/`tokenVersion` ≠ 缓存 | 被踢下线 / 改密 / 换号 | 丢弃缓存，按服务端结果重置（必要时提示"账号已在别处登录"） |

**关键实现约束**：401 处理必须是**唯一出口**（请求拦截器里集中处理），禁止每个页面各写一遍 `if (res.code === 401)` —— 有 N 个页面就有 N 个漏清理的机会。

### 6.3 铁律三：登出必须是"原子三步 + 失败兜底"

| 步 | 动作 | 责任方 | 说明 |
|:---:|------|:---:|------|
| ① | 调 `POST /api/logout` | 后端 | 删 Redis 会话 + 返回 `Set-Cookie: token=; Max-Age=0; HttpOnly` |
| ② | 清 `localStorage` + `sessionStorage`（白名单式清，别 `clear()` 把草稿也干掉） | 前端 | 顺序不重要，但**不能省** |
| ③ | 关闭 WebSocket / 取消订阅 / 清定时器 | 前端 | 否则登出后还能收到推送 |

**兜底**：后端不可达时也要执行 ②③，并在缓存里打 `pendingLogout: true`，下次启动先补一次 logout 再放行 —— 绝不允许"因为接口挂了所以没退出"。

> ⚠️ 前端**不要**手写 `document.cookie = 'token=; Max-Age=0'` 来"删 Cookie"。HttpOnly 时无效，且 `Domain`/`Path` 写错还会**新增**一条同名脏记录（见 §3-D）。

### 6.4 跨标签页同步：别指望 `storage` 事件自动解决

```javascript
// authBus：登录 / 登出 / 换号 三件事广播，其他标签只做"重置状态"，绝不做"重新登录"
const ch = new BroadcastChannel('auth');
function emitAuth(type, payload) {
  applyAuthLocal(type, payload);      // ← storage/BroadcastChannel 不通知本页，本页必须自己跑
  ch.postMessage({ type, ...payload });
  // 注意：setItem 会触发【其他】标签页的 storage 事件，本页永远收不到自己那一次
}
ch.onmessage = e => {
  if (e.data.type === 'logout') { clearLocal(); location.replace('/login'); }
  if (e.data.type === 'login')  { location.reload(); }   // 简单可靠：整页重载，别做局部状态同步
};
```

三条约束：
1. **`storage` 事件只通知"其他"标签页，不通知本页** —— 写完忘了更新本页，就是"本标签正常、别的标签没反应"。
2. `sessionStorage` **不跨标签**，也不能用 `storage` 事件监听（它不走这条总线）。所以**它永远不参与登录态判定**，只放表单草稿、一次性 nonce、单标签向导进度。
3. 多标签同步**只做"整页重载"级别**的粗粒度动作，别搞局部状态对账 —— 前端状态对账的复杂度是无底洞，而登录态切换本身是低频率事件。

### 6.5 多账号并行：要么禁止，要么物理隔离

如果产品确实需要"一个人同时开两个公司的后台"：

- ❌ 不要"Cookie 单份 + 页面多份" —— 这就是 §3-E 串号的来源，必炸。
- ✅ **强制单账号**：新登录使旧会话失效，旧标签收到 401 统一收口 → 跳登录，语义清晰。
- ✅ **物理隔离**：不同租户用不同子域（`a.corp.com` / `b.corp.com`），Cookie 按域隔离，代价是要处理跨子域 SSO。

| 反模式 | 为什么错 | 正确做法 |
|--------|---------|---------|
| `isLogin = !!localStorage.getItem('token')` | token 存在 ≠ 有效；且 token 本就不该放 localStorage | 以 `/api/me` 或 401 收口为准 |
| `localStorage.setItem('user', JSON.stringify(user))` 无版本无时间 | 无法判断陈旧，改密/踢人都感知不到 | 带 `sessionId` + `tokenVersion` + `fetchedAt` |
| 登出只 `localStorage.clear()` | HttpOnly Cookie 纹丝不动 | 后端 logout + 三步清理 |
| 前端 `document.cookie = 'token=...'` | 绕过 HttpOnly、易产生同名重复项 | 一律由后端 `Set-Cookie` |
| 401 只 `toast('请重新登录')` | 状态没清，下一页又是"已登录" | 统一收口函数 |
| token 存 `sessionStorage` | 新开标签即掉登录 | 存 Cookie |
| 每个页面各写 401 判断 | 漏一处就是一处脏状态 | 请求拦截器唯一出口 |
| 用 `roleCode` 缓存控制按钮显隐 | 权限变更后按钮与后端不一致 | 显隐可缓存，**但操作前必须由后端校验**；权限以 `/api/me` 的 `permissions` 为准 |

## 8. 上线红线 Checklist

- [ ] token 仅在 `HttpOnly` Cookie（或 `Authorization` Header，见 `06` 文档的 M-1 方案）中，`localStorage` 无任何凭证
- [ ] 所有"已登录"判定经过**同一处** `authService.isAuthenticated()`，页面里无裸 `localStorage.getItem`
- [ ] **无 Cookie 有缓存** → 强制按未登录处理并清缓存（这条最容易被漏，也最直接消灭"假登录"）
- [ ] 401/419 有唯一收口函数，且会清 store + storage + 跳登录
- [ ] 登出走后端接口，三步清理齐全；后端不可达时有 `pendingLogout` 兜底
- [ ] 缓存带 `sessionId` / `tokenVersion` / `fetchedAt`，与 `/api/me` 交叉校验
- [ ] 跨标签用 `BroadcastChannel` 广播，且**本页同步执行**同一动作
- [ ] `sessionStorage` 不参与任何登录态判断
- [ ] 同名 Cookie 已排查（子域 / Path / Secure 组合），请求头无双 `token`
- [ ] 各端（PC / 移动 / 小程序）登出语义一致：一端登出，其他端最迟下次请求失效

## 9. 面试速答（90 秒）

> **一句话**："登录态只能有一个权威源 —— 服务端。Cookie 是凭证，localStorage 只是可丢弃的展示缓存。"
>
> **展开**："我们踩过的坑是页面显示已登录、接口全 401：渲染读 localStorage 里的 user 快照（永不过期），鉴权读 Cookie 里的 token（7 天过期）。两套生命周期、两套清理责任，必然错位。修法三条：① 凭证只放 HttpOnly Cookie，localStorage 不许存 token；② 无 Cookie 有缓存时一律判未登录并清缓存，401 只在请求拦截器一个出口统一处理；③ 登出走后端销毁会话 + 清本地 + 关连接，后端不可达也要本地清并标记待补偿。另外缓存里带 sessionId 和 tokenVersion，解决被踢下线和改密的感知问题。"

**追问预案**

| 追问 | 要点 |
|------|------|
| 为什么不干脆全放 localStorage？ | XSS 一条 `document.cookie` 就抄走；HttpOnly 不可读是唯一能挡住的机制。另外 SSR 首屏拿不到。 |
| Cookie 的 4KB 装不下 JWT 怎么办？ | 缩短声明，或改 `Authorization` Header 传递（企业内网 DLP 场景下 Header 反而更稳，见 `06`）。 |
| 怎么防止"点了退出、按返回键又回去了"？ | 退出只清凭证不够，SPA 里还要清路由缓存 / 内存 store，并在路由守卫上每次校验登录态；`Cache-Control: no-store` 防浏览器回退缓存页面。 |
| 多标签页同步为什么不用 `storage` 事件？ | 它**不通知触发变更的那个页面**，且 `sessionStorage` 不走这条总线；要可靠就用 `BroadcastChannel` + 本页显式执行。 |
| 为什么要带 `tokenVersion`？ | "被踢下线/改密/权限变更"时服务端不会主动通知浏览器；版本号让下一次 `/me` 就能发现差异，比等 401 早一步。 |
