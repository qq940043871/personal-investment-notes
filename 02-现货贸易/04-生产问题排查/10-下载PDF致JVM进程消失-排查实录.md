# Word 模板转 PDF 时并发修改 PDF 文件导致 JVM 崩溃 — 排查实录

> **文档定位**：典型故障排查实录（基于真实架构的代表性场景），回答"'进程跑着跑着突然没了、日志里什么都没有'这类问题怎么排查"。核心方法：**先定性质（进程是怎么没的），再定根因（为什么会没）**。本案例最终定性为**代码 bug：word 模板转 PDF 过程中，另一个线程无锁地并发修改同一个 PDF 文件，触发 native 渲染引擎崩溃，进而拖垮整个 JVM**。

---

## 1. 问题描述

### 1.1 背景链路（排查的地图）

```
浏览器/接口（合同生成、履约凭证导出、批量下载）
   │ HTTPS
   ▼
合同服务（Java 微服务，K8s 部署，多副本）
   │  ① 读取 word 模板（.docx），填充业务数据
   │  ② 调用 native 渲染引擎，把 word 转成 PDF（写临时文件 tmpPdf）
   │  ③ PDF 落盘 / 上传 MinIO / 返回下载
   │
   │  ← 隐患：另一个线程（水印/盖章/下载/归档/预览）无锁地操作同一个 PDF 文件
   ▼
文件系统 / MinIO
```

- 履约凭证、合同等通过 word 模板 + 数据渲染生成 PDF；
- 转换引擎为 native 库（JNI / 外部渲染进程），对文件的读写发生在 native 层；
- 同一个 PDF 中间文件被多个线程（转换、加水印、上传、下载）共享操作，却**没有并发控制**。

### 1.2 故障现象

| 维度 | 描述 |
|------|------|
| **故障表现** | 生成/下载 PDF 过程中，服务进程突然消失，请求中断、页面 502 |
| **进程状态** | "合同服务"进程消失：`ps` 查不到 PID、监控 Agent 掉线、K8s restartCount +1 后自动拉起 |
| **日志特征** | 应用日志最后一行是正常业务日志，**无任何 Java 异常堆栈**；工作目录出现 `hs_err_pid*.log` |
| **影响范围** | 单个服务实例（多副本挂 1 个），正在生成/下载的任务全部中断 |
| **复现率** | 预发环境按"并发转换同一批凭证"压测**必现**（定位闭环的关键一步） |

### 1.3 关键差异条件

| 对比维度 | 单份串行转换 | 并发转换/批量导出 |
|----------|:----------:|:----------------:|
| 服务存活 | ✅ 正常 | ❌ 进程消失 |
| hs_err | 无 | 有 `hs_err_pid*.log` |
| 响应 | 正常返回 | 生成中断 / 502 |

### 1.4 已排除的假设

| 假设 | 根因方向 | 排除依据 |
|------|---------|---------|
| Java OutOfMemoryError | 应用内存 | Java OOM 会抛异常并写堆栈、进程不一定退出；本案日志无异常堆栈 |
| cgroup OOM（容器超限被杀） | 内核 | `dmesg` 无 `Memory cgroup out of memory` 记录，退出码不是 137 |
| 人为 kill / 发布重启 | 运维 | 无发布记录，时间点与"转换动作"强相关 |
| 宿主机整机 OOM / 宕机 | 硬件 | 同宿主机其他容器正常 |
| liveness 探针杀（假死被驱逐） | K8s | 探针杀是 SIGTERM→143 且有探针失败事件；本案有 hs_err，指向 JVM 自身崩溃 |

## 2. 排查过程：先定性质，再定根因

> "进程消失"类问题的排查铁律：**不要先看应用代码，先回答"进程是怎么没的"**。判定树三问：①退出码是什么？②有 hs_err 吗？③hs_err 说谁崩的？

### 2.1 第一问：进程是怎么没的？— 看退出码

```bash
kubectl describe pod contract-service-xxx
# Last State: Terminated   Reason: Error   Exit Code: 134 / 139（native 崩溃典型值）
```

退出码是判定"性质"的第一把钥匙。native 崩溃（JVM 自己崩）的典型退出码落在 **134（SIGABRT）或 139（SIGSEGV）**，与被强杀的 137、优雅停机的 143 有本质区别：

| 退出码 | 信号 | 含义 | 下一步 |
|:---:|:---:|------|--------|
| 134 | SIGABRT(6) | JVM abort：致命错误（native 崩溃常见） | 找 `hs_err_pid*.log`（本案方向） |
| 139 | SIGSEGV(11) | 段错误：JNI / native 库踩内存 | 找 `hs_err_pid*.log`（本案方向） |
| 137 | SIGKILL(9) | 强杀：OOM Killer / `kill -9` | 查 dmesg / 审计 |
| 143 | SIGTERM(15) | 优雅停机：发布 / 探针驱逐 | 查发布记录、探针事件 |
| 1 | — | Java 未捕获异常退出 | 看应用日志堆栈 |

> 注：判定"性质"的关键不是背退出码数字，而是先区分两条大分支——**"JVM 自己崩（有 hs_err）"** vs **"被外部杀（无 hs_err）"**。本案落在前者。

### 2.2 第二问：JVM 自己崩了吗？— 找 hs_err

```bash
ls /app/logs/hs_err_pid*.log    # 有结果 → JVM native 崩溃
```

`hs_err_pid*.log` 是 JVM 崩溃时必留的现场文件。native 崩溃的 hs_err 头部通常给出三样关键信息（示意）：

```
# A fatal error has been detected by the Java Runtime Environment:
#  SIGSEGV (0xb) ...                              ← 崩溃信号
# Problematic frame: C [libxxx_render.so+0x...]  ← 崩在哪个 native 库
# Current thread: "pdf-convert-3"                ← 哪个线程崩的
```

- 有 hs_err → 排除"被 OOM Killer / 人为强杀"（那些场景不产生 hs_err）；
- `Problematic frame` 指向 **native 渲染引擎**（word→PDF 的 C/C++/JNI 库）→ 崩溃发生在转换的 native 层。

### 2.3 第三问：崩的时候，谁在动这个文件？— 线程与并发

hs_err 里 `Current thread` 显示崩溃线程正卡在 PDF 转换的 native 调用栈上；结合线程快照交叉比对：

```bash
jstack <pid> > threads.txt      # 抓全量线程栈（若能抓到）
head -60 hs_err_pid*.log        # 看 Java frames / native frames
```

交叉发现：**崩的瞬间，除"转换线程"外，还有另一个线程正在对同一个 PDF 文件做写入操作**（加水印 / 覆盖 / 删除 / 边读边传）。两个线程操作同一个文件句柄、同一份字节内容，且**没有任何锁或临时文件隔离**。

### 2.4 代码定位 — 是谁在并发改这个 PDF

```java
// 转换线程：把 word 模板渲染成 PDF，写临时文件
String tmpPdf = "/data/pdf/" + contractNo + ".pdf";
convertEngine.convert(wordTemplatePath, tmpPdf);   // native 引擎正在读/写 tmpPdf

// 另一个线程：无锁地修改同一个 PDF 文件（bug 所在）
pdfService.addWatermark(tmpPdf);        // 或
pdfService.upload(tmpPdf);              // 转换还没写完就开读
// 甚至：另一个转换任务复用同一个 tmpPdf 路径，互相覆盖
```

**bug 本质**：`tmpPdf` 被多线程共享操作，转换过程中的中间文件（native 引擎正在写入、尚未写完）被另一线程并发读写/覆盖。native 引擎内部假设"文件独占"，一旦文件内容在其处理过程中被外部篡改（截断、覆盖、句柄失效），就会触发段错误/断言失败，把整个 JVM 带走。

### 2.5 闭环：预发复现

并发触发"同一批凭证的转换 + 下载/水印"压测：必现 hs_err + 进程消失；给文件加锁 / 换成独立临时目录后，同一压测不再崩溃——**能复现、能解释、修复后能验证**，排障闭环完成。

## 3. 根本原因总结

### 3.1 直接根因

> **word 模板转 PDF 过程中，另一个线程无锁地并发修改同一个 PDF 文件（覆盖/读写中间文件），导致 native 渲染引擎崩溃（SIGSEGV/SIGABRT），JVM 随之崩溃、进程消失。本质是代码 bug——对共享文件的并发访问缺少控制。**

### 3.2 深层根因

1. **并发控制缺失**：中间 PDF 文件被多线程共享，却没有任何锁、临时文件隔离或"先转换后改名"的原子替换；
2. **文件生命周期管理违规**：native 引擎写入尚未完成，其他线程就开始读/改/覆盖同一个文件；
3. **对 native 依赖的健壮性假设**：默认 native 库"能扛住并发"，实际 native 层对文件独占性、内存安全远比 Java 层脆弱，一旦被并发干扰就整体崩溃，无法像 Java 那样抛异常兜底。

### 3.3 根因因果链

```
word 模板转 PDF（业务正常操作）
  → 中间 PDF 文件被多个线程无锁共享（代码 bug）
    → native 渲染引擎处理过程中，文件被另一线程并发修改/覆盖
      → native 层段错误 / 断言失败（SIGSEGV/SIGABRT）
        → JVM 崩溃，产生 hs_err，进程消失
          → 生成/下载中断 502
```

## 4. 处置经过与改进措施

### 4.1 应急处置（当天）

| 序号 | 措施 | 说明 |
|:---:|------|------|
| S-1 | K8s 自动拉起 + 人工确认恢复 | 多副本架构保住可用性，另一副本顶住 |
| S-2 | 转换入口临时串行化（全局信号量=1） | 消除并发，先止血 |
| S-3 | 大批量导出入口临时切异步队列 | 避开并发转换窗口 |

### 4.2 中期技术改进（1-2 周）

| 序号 | 措施 | 优先级 | 说明 |
|:---:|------|:-----:|------|
| M-1 | **独立临时文件 + 原子替换**：每个任务用唯一临时路径（`tmp/contractNo_UUID.pdf`），转换完成后 `Files.move` 原子改名到目标路径 | **P0** | 从根上杜绝"并发写同一路径" |
| M-2 | **文件级/任务级加锁**：对同一 `contractNo` 的转换、水印、上传做串行化，或按合同号维度加锁 | **P0** | 即使路径相同也不会并发操作 |
| M-3 | **转换任务统一走队列**：转换、水印、上传作为流水线串行执行，不并发操作同一文件 | P1 | 生命周期清晰 |
| M-4 | native 引擎实例池化/线程安全复核，限制并发转换数 | P1 | 控制 native 引擎压力 |
| M-5 | 转换失败兜底：native 异常时捕获、落失败记录、可重试，不拖垮进程 | P1 | 缩小爆炸半径 |

### 4.3 长期预防（流程与规范）

| 序号 | 措施 | 层面 | 说明 |
|:---:|------|------|------|
| L-1 | **文件生命周期规范**：临时文件必须唯一命名、写完再原子替换；禁止多线程直接共享中间文件路径 | 设计规范 | 根治类问题 |
| L-2 | 并发写文件、共享可变状态纳入 Code Review 红线 | 流程 | 提前拦截 |
| L-3 | 观测补齐：hs_err 文件采集与告警、native 崩溃率监控、转换任务耗时/失败率大盘 | 可观测 | "进程消失"提前预警 |
| L-4 | JVM 参数基线化：崩溃现场保留（`-XX:ErrorFile`、core dump 开关）纳入排障标准动作 | 运维 | 保留 hs_err 现场 |

### 4.4 改进优先级路线图

```
当天               1 周内                2 周内               持续
┌──────────┐   ┌────────────────┐   ┌───────────────┐   ┌──────────┐
│ 串行止血  │ → │ M-1 唯一临时   │ → │ M-3 队列化    │ → │ L-1~L-4  │
│ 自动拉起  │   │ M-2 文件级锁   │   │ M-4 引擎池化  │   │ 规范/评审 │
```

## 5. 附录

### 5.1 "进程消失"判定树（通用）

```
进程没了（日志干净）
  ├─ 看退出码
  │   ├─ 134 / 139 ─→ JVM 自身崩溃（native/JNI）：找 hs_err_pid*.log ★本案
  │   │                 → 按 hs_err 头部信号 + Problematic frame 定位 native 库
  │   │                 → 交叉线程快照，找并发写/并发访问
  │   ├─ 137 (SIGKILL) ─→ 被强杀：dmesg/journalctl 查 OOM 或审计 kill -9
  │   │     ├─ "Memory cgroup out of memory" → cgroup OOM（容器超限）
  │   │     └─ "Out of memory: Kill process"  → 整机 OOM（宿主机内存）
  │   ├─ 143 (SIGTERM) ─→ 发布/探针驱逐：查发布记录、K8s events
  │   └─ 1              ─→ Java 异常：看应用日志堆栈
  └─ 有 hs_err_pid*.log？─→ 有：JVM 自身崩溃，读头部信号/线程/栈
```

### 5.2 常用命令速查

| 目的 | 命令 |
|------|------|
| 容器退出码/重启原因 | `kubectl describe pod <pod>`、`kubectl get pod --sort-by=.status.containerStatuses[0].restartCount` |
| JVM 崩溃现场 | `ls hs_err_pid*.log`、`head -60 hs_err_pid*.log`（看信号、线程、Problematic frame） |
| 线程快照 | `jstack <pid> > threads.txt` |
| 内核 OOM 记录（排除用） | `dmesg -T \| grep -iE "out of memory\|killed process"`、`journalctl -k` |
| cgroup OOM 计数（排除用） | `cat /sys/fs/cgroup/memory.events`（看 `oom_kill`） |
| 崩溃现场保留 | JVM 参数 `-XX:ErrorFile=./hs_err_pid%p.log` |
| 文件并发审计 | 代码侧搜索共享临时路径、无锁读写；`lsof` 看谁在开同一文件 |

### 5.3 三种"进程消失"的区分（面试高频）

| 类型 | 触发者 | 现象 | 证据 |
|------|--------|------|------|
| JVM 自身崩溃（native） | JVM / native 库 | 进程消失、日志干净、有 hs_err、退出码 134/139 | `hs_err_pid*.log`（本案） |
| Java OOM | JVM | 抛 `OutOfMemoryError`，日志有堆栈，进程可能不死 | 应用日志 + heap dump |
| cgroup OOM | 容器内核 | 进程消失、退出码 137、日志干净、无 hs_err | dmesg `Memory cgroup out of memory` |

### 5.4 面试速答（90 秒版）

> "生成/下载 PDF 的时候 Java 进程突然没了——`ps` 查不到、应用日志里没有任何异常。这类问题我先**定性质**再定根因：一看退出码是 134/139，这是 SIGABRT/SIGSEGV，是 JVM 自己崩了，不是被 OOM Killer 或人杀掉；二看工作目录有 `hs_err_pid*.log`，头部 `Problematic frame` 指向 native 渲染引擎，确认崩在 word→PDF 的 native 层。接着交叉线程快照：崩的瞬间，除了转换线程，还有另一个线程在无锁地读写同一个中间 PDF 文件——这就是根因，一个**代码 bug：对共享文件的并发访问没有控制**，native 引擎处理中被外部篡改文件内容，直接段错误把整个 JVM 带走。修复方向：一是独立临时文件 + 写完原子替换，从根上杜绝并发写同一路径；二是文件级锁/转换队列化，串行化同一文件的操作；三是把并发写文件、共享可变状态纳入 Code Review 红线，并补上 hs_err 采集告警。"

**追问预案**：

| 追问 | 回答要点 |
|------|---------|
| 为什么应用日志里什么异常都没有？ | native 崩溃发生在 JVM 之外，Java 层来不及抛异常/刷日志；hs_err 才是崩溃现场，不是应用日志 |
| 这和 OOM 杀掉进程怎么区分？ | OOM Killer 强杀是退出码 137、无 hs_err、dmesg 有 OOM 记录；native 崩溃是退出码 134/139、有 hs_err、dmesg 无 OOM 记录 |
| 为什么 native 库比 Java 脆？ | Java 有异常体系兜底，越界/非法访问会抛异常；native 层一旦踩内存/文件句柄失效就是段错误，直接 abort 整个进程 |
| 怎么根治而不是只加锁？ | 加锁是止血，根治靠"唯一临时文件 + 原子替换 + 生命周期规范"，让文件从诞生到改名前根本不会被第二个线程碰到 |
| 为什么之前没暴露？ | 单份串行转换时文件天然独占，bug 被隐藏；并发/批量场景才把竞态暴露出来 |
