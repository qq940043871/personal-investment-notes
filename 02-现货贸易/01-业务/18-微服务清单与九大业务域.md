# 12+ 微服务与九大业务域清单

> **用途**：面试被追问「12+ 微服务到底是哪几个」「九大业务域怎么分」时，按本文口径展开；简历只保留「12+ 微服务 · 九大业务域」的概括。
>
> **口径说明**：
> - 对外统一说 **12+ 微服务**，指 Java 业务中台的**部署单元**口径。
> - 内部按业务能力拆分，实际为 **15 个核心业务服务 + 3 个平台服务**。
> - **C 撮合引擎、DS 数据中心、midservice 网关、midmon 监控不计入 Java 微服务数**，它们是异构架构的独立层。
> - 不同租户 / 套餐按「能力集」按需部署，所以对外用「12+」而不是固定数字。

---

## 一、九大业务域总览

九大业务域按「交易 → 履约 → 资金 → 货权 → 票税 → 金融」的主链路划分，认证与公共服务作为横向底座。

| # | 业务域 | 一句话职责 | 核心服务 | 关键单据 / 事件 | 外部依赖 |
|:--:|---|---|---|---|---|
| 1 | **交易** | 挂牌 / 竞价 / 询价 / 基差，订单、委托、成交与风控 | 交易服务、商品中心、创新挂牌、自由竞价、风控服务 | 订单、委托、成交、行情、限额 | C 撮合引擎（经 DS）、行情 / CTRM |
| 2 | **支付结算** | 保证金冻结解冻、收付款、支付路由、结算与对账 | 资金服务、账本服务 | 收付款单、资金流水、结算单、对账单 | 多家银行、支付渠道 |
| 3 | **合同履约** | 合同模板 / 要素 / 签章 / 变更，履约计划与交收 | 合同中心、履约服务 | 合同、补充协议、履约计划、交收单 | 电子签章、CA 证书 |
| 4 | **仓单** | 电子仓单注册 / 注销 / 过户 / 质押 / 解押 | 仓单服务 | 仓单、质押单、出入库单 | WMS、仓储、区块链存证 |
| 5 | **物流** | 运力、运单、轨迹、仓储 WMS 集成与运费 | 物流服务 | 运单、轨迹、运费单 | WMS、TMS、GPS |
| 6 | **税务** | 发票开具 / 抵扣 / 红冲，四流合一 | 发票 / 税务服务 | 发票、进项、税务凭证 | 税务 / 开票平台 |
| 7 | **供应链金融** | 确权、授信、融资、放款、还款、贷后与对账 | 供应链金融服务 | 确权单、融资申请、放款 / 还款单 | 银行、保理、征信 |
| 8 | **公共服务** | 通知、规则配置、文档 / 翻译 / OCR / 审批流 / 视频 | 通知服务、规则配置中心、公共能力服务 | 消息、配置版本、解析任务 | 短信、OCR 外部服务 |
| 9 | **认证** | 登录、租户、角色权限、功能授权码 | 认证服务、客户中心 | 会话、Token、授权码、客户档案 | CA、短信 |

> **记忆顺序**：交易 → 支付结算 → 合同履约 → 仓单 → 物流 → 税务 → 供应链金融 → 公共服务 → 认证。前七个是业务主链，后两个是横向底座。

## 三、3 个平台服务

平台服务不直接对应业务域，但被多个域复用，是「12+」里的横向支撑。

| # | 服务 | 核心职责 | 关键接口 / 事件 | 主要使用方 |
|:--:|---|---|---|---|
| 16 | **通知服务** | 站内信、短信、邮件、WebSocket 推送 | 消息发送、模板管理、已读回执 | 全部业务域 |
| 17 | **规则配置中心** | Drools 规则、交收模板、付款 / 保证金规则、灰度与版本 | 规则发布、版本回滚、规则命中查询 | 交易、履约、资金、风控 |
| 18 | **公共能力服务** | 文档转换、翻译、OCR（外部服务）、审批流、视频网关（RTSP / RTMP） | 转换、翻译、OCR、审批流、播放地址 | 合同、履约、客服、门户 |

> **公共能力服务**按能力拆为独立微服务、只暴露 API；OCR 走外部服务统一封装，不把第三方 SDK 散落到业务代码。

## 四、域间主链路

```text
客户端 / 三端
   │
   ▼
midservice 网关（认证 / 协议号 / 限流 / 脱敏）
   │
   ├── 交易域：挂牌 / 竞价 → 交易服务 → DS → C 撮合 → 成交
   │
   ├── 合同履约域：成交 → 合同中心 → 履约服务（双轨 / 交收节点）
   │
   ├── 支付结算域：履约节点 → 资金服务（冻结 / 支付）→ 账本服务（记账）
   │
   ├── 仓单域：履约 / 质押 → 仓单服务 → WMS
   │
   ├── 物流域：履约 → 物流服务 → WMS / TMS / GPS
   │
   ├── 税务域：结算完成 → 发票 / 税务服务 → 开票平台
   │
   └── 供应链金融域：合同 / 仓单 / 交易数据 → 供应链金融服务 → 银行 / 保理
```

**同步与异步**：

- **同步（Hessian over HTTP）**：下单、撤单、资金冻结、合同创建等需要立即知道结果的短链路。
- **异步（Kafka + outbox）**：成交回写、履约节点推进、通知、对账、发票等可最终一致的长链路。
- **跨异构（DS + Socket 私有 TCP 帧）**：Java 交易服务 → DS → C 撮合引擎。
- **一致性**：强一致只保「交易 + 资金预检」；其余最终一致 + 幂等 + 日终对账兜底。

**关键领域事件（示例）**：

`OrderCreated` → `TradeMatched` → `ContractSigned` → `FulfillmentNodeCompleted` → `FundFrozen` → `ReceiptRegistered` → `ShipmentDispatched` → `InvoiceIssued`

## 五、拆分与治理规则

1. **按业务能力垂直切**，不按技术层水平切；每个服务对应一个限界上下文。
2. **每服务独占 schema**，禁止跨库 join；跨域只能走接口或领域事件。
3. **5 人以下团队维护的不拆**，避免「拆太细、运维成本反噬」；采用演进式拆分。
4. **幂等与 traceId**：所有写接口带幂等键；traceId 经网关 → Java → DS → C 全链路透传。
5. **同步短、异步长**：强一致链路短，长事务用 outbox + 状态机 + 对账兜底。
6. **多租户**：tenantId 上下文注入，已落地行级 tenant_id 数据隔离；Schema 级 / 分区级为三级混合方案中的设计规划；租户 / 站点差异走配置不走分支。
7. **容量**：慢接口 200 QPS 限流、连接池每实例 20 + 快速失败、Redis 单层缓存（TTL + 随机抖动）、列表读走从库；扩容前先核出口容量。Tomcat 是共享线程池，不做独立线程池舱壁。

## 六、面试口径

**被问「12+ 微服务是哪几个」时，不要逐个背，按域报：**

> 「按九大业务域拆，核心是交易、支付结算、合同履约、仓单、物流、税务、供应链金融七个业务域，加公共服务和认证两个底座。落地是 15 个核心服务 + 3 个平台服务。对外说 12+，是因为不同租户按能力集部署，不是每个环境都全量。」

**被问「你自己拆了哪几个」时：**

> 「交易、合同、资金、仓单、履约这几条主链的边界是我主导定的；认证、商品、通知属于底座，更多是复用和治理。」

**被问「会不会拆太细」时：**

> 「三条纪律：5 人以下团队维护的不拆；每服务独占库表、禁止跨库 join；先按域拆、再按流量和团队规模演进，不追求一次拆到位。」
