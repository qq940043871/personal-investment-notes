多轮 RAG 系统 · 完整架构与状态管理图

公司项目 · Dify 主线 ｜ 三层架构定位 · 三条状态线 · 单轮 8 段管道 · 多轮迭代环 · 平台已实现 vs 必须自补。 一句话定位：多轮 RAG 的「记忆」不在模型里，在会话态里 —— Dify 记住 conversation_id 与消息历史， 权限、槽位、历史重鉴权、审计归自研业务中台；上下文态是每轮拼出来的，不是存出来的。

轨道 · 三层架构

实证接入层（渠道 / 身份 / 限流）→ 智能层 Dify（社区版私有化二开：Workflow / Agent / RAG 管道 / Prompt）→ 业务层自研中台（统一身份、细粒度鉴权、工具网关、审计、token 计量、会话与单据关联）→ 能力层（模型、向量库、政策与产品知识库、直击库、解析产物）。

参与边界（讲述必带限定语）

本人真实参与 = 前期选型复盘 + MinerU 复杂 PDF 解析改造 + 分块元数据与向量库入库链路 + 解析调度与失败兜底；编排调优、状态实现由团队推进。本图是对该设计方案的归纳，不是上线实测报告。

STATE 01 · 跨轮次

会话态

生命周期：跨轮次、跨请求 ｜ 不可丢 · 外置存储
conversation_id 首轮留空、响应返回后由业务侧持久化；user 是会话隔离维度
身份与权限画像 clearance / groups / jurisdiction_set / valid_until，每轮重新加载
槽位 intent / entities / legal_entity / history_refs / attempt_count、会话摘要、情绪与渠道
生命周期五态：新建 → 活跃 → 静默超时（上下文保留但不混入新会话） → 跨渠道接续 → 关闭
存放：Dify 侧 PostgreSQL（应用配置 / 会话 / 权限）＋ 中台会话表与单据关联。⚠️ Service API 会话 ≠ WebApp 会话，同一 user 在 API 侧连续调用才保持上下文。
STATE 02 · 单轮 run

轮次态

生命周期：单次 run ｜ 跑完归档 · 可追溯
trace_id 贯穿全链路（审计用）；本轮 query + 改写后 query（原查询必须保留）
结构化过滤条件：on_date / 地域 / 领域 / 密级；权限画像快照
候选池、混合检索两路结果、Rerank 分数与 TopK、条款级引用清单
◆ 闸门 A（检索前权限硬过滤）与 ◆ 闸门 B（生成后引用 / 位阶 / 密级核验）的判定结果
存放：节点级 trace + 工作流运行日志（状态 / token / 步数 / 耗时）＋ append-only 审计日志。事后能还原「当时他到底能看到什么」。
STATE 03 · 单次模型调用

上下文态

生命周期：单次模型调用 ｜ 可丢 · 内存重建
拼给模型的 messages = 系统提示词 + 历史轮次（按权限打标）+ 本轮检索 chunks + 槽位
重建公式：会话态（有权部分）＋ 轮次态 ＋ 本轮检索结果，随时可重新拼装
预算裁剪：话题切换清理旧槽位；指代 / 省略补全；无法消解 → 追问，不猜
历史轮次携带的文档，本轮鉴权时逐份重新校验，无权者从上下文中剔除
存放：只在内存。⚠️ Dify 会话历史压缩策略较粗糙，超长会话要自己在工作流层面处理（会话摘要 + 截断）。
判据 → 能丢的放内存，不能丢的落库
上下文态可重建，会话态 / 轮次态不可重建；权限画像每轮重载、绝不缓存复用，否则第 3 轮有权的内容会在第 5 轮权限回收后泄露。设计

◆ 闸门 A · 检索前

权限硬过滤

Code + 知识检索节点元数据过滤（手动模式，从上游变量显式传入）
判定：密级 ≤ clearance AND ACL ∩ groups ≠ ∅ AND 地域在可访问集合
绝对禁止先检索后过滤：敏感文档一旦参与相似度计算就可能经排序 / 分数 / 截断片段泄露
兜底 · 候选为 0 → 走「未找到依据」，严禁放宽过滤条件重试

C 组 · 检索

混合检索 + Rerank

Knowledge Retrieval：向量 + 关键词（BM25 / 倒排）并行；文号 / 条款号走关键词通道
两级过滤：知识库级定候选池，节点级做重排 / 截断
TopK 与 Score 阈值只在 Rerank 阶段生效；不开 Rerank 等于白配
坑 · 节点挂多知识库时元数据过滤不可用 → 按类目拆库
读 轮次态写 轮次态

D 组 · 上下文组装

按权限重拼上下文

Code / Template：系统提示词 + 历史轮次 + 本轮 chunks，逐份重新鉴权
超预算主动裁剪；会话摘要替代全量历史
检索为空 → 条件分支明确拒答，不把空上下文硬塞给 LLM
三层防御 · Score 阈值 / 空结果分支 / Prompt 显式约束「不知道就说不知道」
读 会话态+轮次态写 上下文态
06
◆ 闸门 B · 生成后

受约束生成与核验

LLM：JSON schema / temp=0 / 强制条款级引用；数字由变量占位符填充，不由模型生成
Code 三道核验：quote 逐字比对、效力位阶、密级与权限
有效期 / 效力位阶 / 引用真伪一律代码算，不交给模型判断
兜底 · 核验不过 → 重试 1 次 → 门控降级 / 转人工
读 上下文态写 轮次态

① 继承

指代与省略补全

用 history_refs 回指上文实体；「它」「这个」「刚才说的」定位到具体文档 / 单号。无法消解 → 追问，不猜。

② 清理

话题切换清槽位

检测到新话题 → 清理旧槽位，避免带着上一个话题的参数答新问题；静默超时的上下文保留但不混入新会话。

③ 重鉴

权限每轮重载

权限画像不缓存；历史轮次携带的文档逐份重新鉴权，无权者从上下文剔除；连续多轮触及权限边界 → 会话级告警。

④ 失效

权限降级清会话

离职 / 调岗导致权限回收时，主动失效该用户所有活跃会话 —— 否则第 3 轮有权的内容会在第 5 轮泄露。

⑤ 压缩

超长会话治理

会话摘要 + 上下文预算裁剪；Dify 会话历史压缩策略较粗糙，超长会话必须在工作流层面自己处理。

职责分界
Dify 智能层
vs 自研业务中台
谁实现 / 谁兜底

Dify 智能层 · 平台已实现（开箱可用，语义仍要逐条核对）

定位：解决「AI 怎么做得快、怎么调得好」
四种应用形态的会话记忆边界：Chatbot / Chatflow 有，Workflow / Completion 无
conversation_id + user 隔离；会话列表 / 消息历史 / 重命名 / 删除 / 会话变量读写
系统变量 sys.query / sys.user_id / sys.conversation_id；节点变量 {{#节点ID.字段#}}
节点级 trace 与工作流运行日志（状态 / token / 步数 / 耗时）；DAG 引擎保证终止性（仅 Loop / Iteration 容器内可循环）
Annotation 标注回复命中即返回（0 token）；result 变量自带分段内容 / 标题 / 元数据，天然可溯源
缺口（官方诚实清单）：无端到端评估体系、元数据自动模式不可观测、会话历史压缩策略粗糙、元数据过滤不支持多知识库节点。

自研业务中台 · 必须自己补（管得住的那一半）

定位：解决「AI 怎么接得稳、怎么管得住」
统一身份与权限画像每轮重载；历史文档逐份重鉴权；权限降级失效活跃会话
会话与单据关联；上下文对象与 session_id 强绑定，并发会话独立上下文空间（防串线）
跨渠道接续（网页 → APP 带摘要）、静默超时与关闭、转人工交接包
超长会话压缩与会话摘要；legal_entity 强制注入；金额模板化、撮合状态带时点输出
append-only 审计（含权限画像快照）、token 计量、未命中样本回流与直击库治理
硬约束：Dify 不直连业务数据库；所有数据访问走中台受控工具，权限永远在中台执行，不把过滤责任交给 Prompt。
红线 · 六条
违反任意一条，多轮 RAG 就会从「答得准」滑向「答得像但不敢用」。
确定性不交给模型：有效期 / 效力位阶 / 密级权限 / 引用真伪一律 Code 节点算。
先过滤后检索：ACL 是检索的前置条件，不是检索后的清洗步骤。
权限每轮重载：绝不复用会话缓存，历史文档逐份重新鉴权。
上下文串线 = 隐私事故：A 主体的资料绝不出现在 B 主体会话里。
工作流内不写复杂业务逻辑：只做路由、拼装、调用与格式化。
API 会话 ≠ WebApp 会话；Harness / FastAPI 属个人储备，不混入平台技术栈。
