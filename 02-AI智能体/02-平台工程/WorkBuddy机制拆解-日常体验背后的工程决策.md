# WorkBuddy 机制拆解：日常体验背后的 12 个工程决策

> 版本：v1.0（2026-11-19）
> 姊妹篇：`WorkBuddy工程化实现思路-可扩展智能体系统.md`（架构地图）
> 本篇定位：**解剖层**——不讲"有哪些模块"，讲"为什么用起来顺手，代价是什么"
> 数据来源：本机 `C:\Users\qq940\.workbuddy\` 与 `workbuddy.db`（只读查询），全部标注实测值

---

## 0. 先说结论：不是"聪明"，是"处处有兜底"

一个直觉类比：

| 部件 | 对应 | 缺了会怎样 |
|---|---|---|
| 发动机 | 大模型 | 不会思考 |
| 变速箱 | 模型路由 + 思考等级 | 简单活也烧大钱，难题又不够力 |
| 底盘 | Agent 循环 + 工具层 | 只能聊天，干不了活 |
| 油箱与油表 | 上下文窗口 + 用量台账 | 聊到一半"失忆"，且不知道为什么 |
| 行车记录仪 | trace + 审计链 | 出事只能猜 |
| 保养手册 | 提示词分片 + 版本目录 | 改一次全车趴窝 |

**核心判断**：WorkBuddy 的体验优势，七成来自"把不确定的东西做成可观测、可回滚、可配额"，三成来自模型本身。下面 12 条机制，逐条拆。

## 2. 十二个机制

每条统一四段：**你感受到的** → **实际机制** → **证据** → **代价**。

### M1 它为什么"记得住你"——记忆是分层的，权限是分级的

**你感受到的**：新开会话，它已经知道你的机器上 Python 要指定 anaconda、你的开发者署名是 `hasWhere`、你不喜欢它乱改文件。

**实际机制**：三层，各写各的，互不越权。

| 层 | 文件 | 谁写 | 本机实测 |
|---|---|---|---|
| 云端 profile | 服务端生成，会话开始注入 | 系统自动学习 | 用户不可改，改了下次被覆盖 |
| 用户级 | `C:\Users\qq940\.workbuddy\MEMORY.md`（47 KB） | 只在你明确要求时写 | 限额 4,000 字符/会话 |
| 工作区级 | `<workspace>\.workbuddy\memory\2026-11-19.md` + `MEMORY.md`（16 KB） | 干完活自动追加 | 限额 3,000 字符/会话 |

**关键设计**：这不是"缓存分级"，是**写入权分级**。自动学习的不许人工覆盖，人工写的不许自动改写，工作区的绝不外溢到别的项目。三层错了任何一层，就会出现"我给你讲过的规矩它下周忘了"或者"它把 A 项目的规定套到 B 项目"。

配套还有一个**蒸馏**动作：工作区日志按日 append（只增不改），超过 30 天按主题压缩进 `MEMORY.md` 再删旧文件。所以长期记忆是"越用越薄、越用越准"，不是"越用越长"。

**证据**：`~\.workbuddy\plugins\cache\...\prompt-common\fragments\` 下有三个专门的记忆片段——`workbuddy-memory-system.md`、`workspace-project-memory.md`、`cloud-memory-platform-system.md`。**三层各有一份提示词模板**，不是一段通用话术。

**代价**：三层边界需要人维护。写错层（比如把环境坑写进工作区记忆）不会报错，只会在别的项目里"莫名失效"。

### M2 它为什么"不会越聊越傻"——上下文是配额制，不是自助餐

**你感受到的**：聊了十几轮，它还记得前面定的方案；但如果让它读 50 个文件，它就开始"忘事"。

**实际机制**：四道闸。

1. **窗口足够大**：本机默认 300k token，部分会话开到 1,000k。当前这轮用了 86k，还有 71% 余量。
2. **占用可查**：每次请求后更新 `session_usage.used/size`，不是黑箱。
3. **压缩有七种手段**（结果折叠 / 子 Agent 隔离 / schema 延迟 / 技能懒加载 / 日志蒸馏 / 检索式回忆 / 回答长度约束）。
4. **单块上下文有硬预算**：记忆 4k、3k 字符，最终回答 50–70 行，技能只进 `name + description`。

**为什么"回答长度"要限制**？因为输出会变成下一轮的输入。一个 300 行的回答，等于自己给自己加了 300 行上下文债。这条约束是**为下一轮省预算**，不是为了排版好看。

**证据**：`session_usage` 表 142 行台账，字段 `used / size / updated_at / credit_json`；我这条会话 `used=86433, size=300000`。

**代价**：压缩必然有损。折叠掉的工具输出如果后面要用，只能重新执行一次——所以"读文件"次数远高于"改文件"（Read 576 vs Edit 395，实测比例 1.46:1）。

### M3 它为什么"工具选得准"——名字常驻，正文按需

**你感受到的**：你说"帮我看下这个表"，它会自己去用表格工具；你说"发个邮件"，它不会去翻文件系统。

**实际机制**：两段式加载。

```
第一段（常驻上下文，只占几行）：工具名 + 一句话能力
第二段（按需拉取）：完整 JSON Schema + 参数约束
        ↑ 通过 ToolSearch 现取，通过 DeferExecuteTool 执行
```

本机 `mcp-tool-list.json` 有 **138 KB** 工具清单——如果全塞进上下文，光工具定义就吃掉小半个窗口。所以工具被分成两组：**可直接调用**（内置高频）与**需先搜索**（MCP 长尾）。

再加三层"路由提示"：

1. **命名空间**：`mcp__server__tool` 三段式，模型看到名字就知道属于哪个系统。
2. **技能描述即路由键**：31 个技能的 `description` 是唯一进上下文的部分，写法直接决定触发准确率（`skill-creator` 那句 "used when users want to create a new skill" 就是标准范式）。
3. **`disableModelInvocation` 开关**：`skill-list-cache.json` 里每个技能都有这个字段——可以配置成"禁止模型自动调用、只能用户显式触发"。这是**把可靠性问题变成权限问题**的典型手法：不确定它会不会乱调，就先不让它自动调。

**证据**：`mcp-tool-list.json` 结构为 `{version, entries: {serverHash: [{name, description}]}}`，按连接器指纹分组——连接器一变，只失效对应那一组缓存。

**代价**：多一次往返（先搜后调）。所以高频工具必须留在第一段，否则每轮都多一跳。

### M4 它为什么"能装能扩"——四类扩展点，从松到紧

**你感受到的**：装个连接器就能查腾讯文档；装个技能就多一套工作流；换个专家就换一套方法论。

| 扩展点 | 粒度 | 能力 | 本机示例 |
|---|---|---|---|
| **MCP 连接器** | 一个外部系统 | 提供工具集 | `ima-mcp`、`lexiang`、`tencent-docs` |
| **Skill** | 一套工作流 | 提供"怎么做"的知识 + 脚本 | `tool-book-learning`、`dev-web-stress-test` |
| **Plugin** | 一个可版本化包 | 任意组合上述 + 提示词 + 子 Agent | `workbuddy-docx`（writer→formatter→converter 三工位） |
| **Expert** | 一个角色 | 方法论 + 语气 + 领域知识 | 专家包（`experts\`、`my-experts\`） |

再往上还有一层联邦：**A2A（Agent to Agent）**——通过 Agent Card 发现远端 Agent，把任务连同完整上下文派出去。提示词片段里明确规定：走 A2A 时**不要**用本地 Agent 工具或工具搜索，两条路不能混。

**关键洞察**：扩展点是**从"给工具"到"给知识"到"给角色"**逐级抽象。工具解决"能不能做"，技能解决"会不会做"，角色解决"以谁的立场做"。三级分开，才不会出现"为了改个语气要重装插件"。

**代价**：四类扩展点各有自己的清单格式与校验规则，注册中心会分散（`installed_plugins.json`、`skill-list-cache.json`、`mcp-tool-list.json` 各管一摊）。

### M5 它为什么"改文件不出事"——编辑协议比模型自觉更可靠

**你感受到的**：让它改文档，它不会把整个文件重写一遍；偶尔手滑也会先警告你。

**实际机制**：五道约束，全部是**协议级**的，不靠模型"记得小心"。

| 约束 | 做法 | 解决什么 |
|---|---|---|
| **先读后写** | `Edit` 必须先 `Read` 过该文件，否则工具直接失败 | 防止基于想象改文件 |
| **唯一锚点** | 替换串必须在文件中唯一，否则报错 | 防止批量误替换 |
| **并行写警告** | 同一文件多个 Edit 并行会互相覆盖（读-改-写竞态），提示词要求串行 | 已写进规则，不靠运气 |
| **原子写脚本** | 多处改动用一次性脚本整体覆写 | 避免中间态 |
| **危险操作四步** | 只读扫描 → 列清单 → 明示风险 → 二次确认；删除走回收站 | 不可逆操作 |

还有一层**信任决策**：`workbuddy.db` 里有 `workspace_trust_decisions` 表（本机 23 行），记录"这个工作区你信不信"。不可信目录直接限制能力，从源头减少误伤。

**证据**：每轮会话必须先声明工作区信任（你这次进来也收到了同样的一次性提示），决策落表而不是只存在内存里。

**代价**：慢。先读才能改，串行才能安全——牺牲吞吐换正确性，这个取舍在文件操作上是划算的。

### M6 它为什么"长任务不丢"——异步有三件套，还有超时兜底

**你感受到的**：跑构建、跑爬虫，你没盯着也不会丢；想停能停。

**实际机制**：

```
提交 → 拿到任务 ID → 主循环继续干别的
                    ├─ TaskOutput：要结果时拉取（阻塞/非阻塞两档）
                    └─ TaskStop：要中止时掐掉
```

配套两个细节：

- **超时上限**：自动化会话的 `session_settings.timeoutMs = 5,400,000`（90 分钟）。没有超时的后台任务就是僵尸。
- **中断记账**：`session_turn_interruptions` 表（`session_id / request_id / reason_code / presentation`）专门记录"为什么被打断"。本机 0 行——**机制在位但没触发过**，这比"没这个机制"重要得多。

还有一条容易被忽略：自动化会话会**主动关掉无关功能**——`disableSessionSummary`、`disableSessionTitle`、`disableTerminalTitle` 全开（即禁用），并注明 `sandboxDisabledReason: background-automation-no-approval-ui`。翻译过来：**后台任务没有审批界面，所以沙箱不敢开，改用权限模式兜底**。这是很清醒的工程判断——缺 UI 的能力不该硬上。

**代价**：异步任务多了以后，需要人来看"哪些还在跑"。所以有 `/tasks` 这类视图，而不是让你自己记。

### M7 它为什么"升级不出事"——目录就是发布系统

**你感受到的**：版本更新很频繁，但你没遇到过"更新到一半打不开"。

**实际机制**（本机实测三层）：

```
workbuddy-docx\
├── 5.11.3-wb.43806934.gecace0f7.ha395516167d4\   ← 在用（.in_use\ 里有 12 个 pid）
└── 5.9.3-wb.42398134.gd4692421.h480e8d1fee0f\    ← 旧版（.orphaned_at 标记待回收）
```

四个动作叠加才成立：

1. **版本号内嵌 git 短哈希**（`gecace0f7`）——版本串能直接追溯到提交，不靠人工维护语义版本号。
2. **新版本写新目录**，绝不在原目录覆盖——升级是"加目录 + 改指针"，回滚是"改回指针"。
3. **`.in_use\<pid>` 引用计数**——进程活着就占位。本机 `prompt-common` 下有 12 个 pid 占位，说明多个会话/进程共用一个版本，谁都没资格删它。
4. **`.orphaned_at` 孤儿标记 + 清单登记**（`installed_plugins.json` 记 `installPath/version/installedAt/dependencies`）。

**为什么这点最关键**：它把"发布"这个高风险动作，降级成了"文件系统操作"。不需要灰度基础设施，不需要回滚脚本，也不需要停机窗口。

**代价**：磁盘只增。`plugins\cache` 会越堆越多，必须有 GC；GC 判据就是"没人占位 + 有孤儿标记"。

### M8 它为什么"出了事查得清"——三面观测，各管一段

**你感受到的**：它偶尔会告诉你"我卡在某一步了"，而不是笼统说"出错了"。

| 面 | 记录什么 | 粒度 | 本机位置 |
|---|---|---|---|
| **Trace** | 每次生成、每次工具调用、每轮工具清单 | span 级 | `traces\<pid>\trace_*.jsonl` |
| **Log** | 主进程 / 渲染进程 / 守护进程 / MCP 应用 | 进程级 | `logs\main.log` 等 4 个 |
| **Audit** | 谁在什么时候做了什么，链式哈希防篡改 | 事件级 | `audit-log\<date>.jsonl` + `state.json` |

trace 的结构是 **OpenTelemetry 语义**：`traceId / spanId / parentId / name / type / agentName / startedAt / duration / status / error`。本机实测的 span 类型有 `generation`（模型生成）、`function`（工具调用，名字就是工具名）、`custom`（自定义事件，如 `mcp_tools`）、`agent`（子 Agent）。

**三个设计细节值得抄**：

1. **工具 span 名 = 工具名**（`Bash`、`Read`、`Edit`）。不用额外打标签，按 name 聚合就能出"工具使用画像"（我就是这样统计出 Read:Edit = 1.46:1 的）。
2. **`agentName` 挂在 span 上**。多 Agent 场景如果只记 `parentId`，链路一串就乱；挂上角色名才能回答"是哪个岗位干的"。
3. **审计是链式的**：每条记 `lastHash` 指向上一段，segment 关闭时落 `firstHash/lastHash/fileSha256`，全局 `sequence` 只增（本机已到 **15,989**）。这不是日志，是**证据**。

**代价**：全量落盘。trace 目录按 pid 分，会话越多目录越碎，需要定期归并。

### M9 它为什么"贵的活干得省"——模型池 + 三档旋钮

**你感受到的**：简单问答很快，复杂任务明显"想得久"。

**实际机制**：三个正交旋钮，全部 per-session 记录在案。

| 旋钮 | 字段 | 本机实测取值 |
|---|---|---|
| **选哪个模型** | `sessions.model` | 7 种型号 + `auto` 自动路由 |
| **想多深** | `sessions.thought_level` | `disabled / enabled / medium / high / max`（high 最多，146 次） |
| **给多大窗口** | `sessions.context_window` | 300k 默认，1M 可选 |
| **花多少钱** | `session_usage.credit_json` | 按 request id 记账（如 `{"01a1f159…": 9.34, "01a1f160…": 4.2}`） |

**关键在"auto"**：41 个会话把模型选择权交给了路由。这意味着平台侧有"按任务复杂度选模型"的策略——难题上强模型，废话上快模型。这是成本能压住的主要原因，比任何提示词优化都有效。

**代价**：路由判错就两头不讨好（难题给小模型 → 反复重试，成本反而更高）。所以必须有 `thought_level` 这种人工覆盖开关兜底。

---

### M10 它为什么"提示词能迭代"——模板渲染，不是整篇硬编码

**你感受到的**：同一个它，在 Plan 模式下只出方案不动手，在 Agent 模式下直接干活。

**实际机制**：提示词是**渲染出来的**，不是写死的。本机片段里能看到三种模板语法：

```
{{ ToolResultPresentationPrompt }}                    ← 变量占位
{%- if WecomAgentAvailable -%} … {%- endif -%}        ← 条件块
{% include "prompt-common/fragments/agent-to-agent.md" %}  ← 片段引用
```

再加上**按模式装不同片段**——这就是"同一套内核、不同人格"的物理实现：

| 模式 | 片段数 | 多出来的 |
|---|---|---|
| `plan` | 6 | 基础六件套（agent-loop / current-mode / interaction / result-presentation / task-management / tool-use） |
| `craft`（Agent 模式） | 8 | 多 `browser-computer-use.md`、`interaction-tool-use.md`、`plugin-recommendation.md`，且 `tool-use` 换成 `interaction-tool-use` |

公共片段库 `prompt-common\fragments\` 共 **11 个**：3 个记忆 + 4 个企业微信路由 + agent-to-agent + channel-prompts 等。**用 include 复用，而不是每个模式复制一遍**——这是提示词工程里最容易被忽略的"去重"。

还有个细节：`plan` 与 `craft` 的 `current-mode.md` 都是 **0 字节**。模式约束由运行时注入，静态文件只留位置。**能从状态推导的，就不要写进模板**——否则状态一变，模板就开始说谎。

**代价**：组合复杂度。8 个片段 × 若干条件块，出问题时要能定位到"是哪个片段哪一行"——所以片段要短（实测 800–4,400 字节/个），长了就没法维护。

---

### M11 它为什么"像懂你的行话"——项目上下文是每轮刷新的

**你感受到的**：它一上来就知道你在哪个目录、项目是什么结构、有哪些文档。

**实际机制**：每轮注入的 `project_context` 是**实时快照**，不是缓存记忆。加上工作区身份文件（`SOUL.md` / `IDENTITY.md` / `USER.md`）与风格配置（语气、地区惯例、货币符号）。

四块拼出"语境"：

1. **物理语境**：cwd + 目录树快照（所以它说"你项目里有个 index.html"，是真的看到了）。
2. **身份语境**：`SOUL.md` 定行为准则，`USER.md` 定你是谁，`IDENTITY.md` 定它是谁。
3. **惯例语境**：地区惯例（涨红跌绿、¥ 符号）、引号规则（代码用直引号、中文用弯引号）。
4. **状态语境**：`connector-status`（哪些连接器连上了）、当前时间。

**注意"每轮刷新"这个成本**：目录树快照进上下文是要花 token 的，但换来的是"不会拿三天前的目录结构瞎指挥"。这个取舍几乎总是值得的——**过期的上下文比没有上下文更危险**。

**代价**：大目录（几千文件）快照会被截断，截断后模型对结构的判断会失真。所以项目里要有清晰的顶层组织，别指望它自己猜。

---

### M12 它为什么"不瞎编"——把"不知道"做成一种可交付状态

**你感受到的**：它会说"这里我没查到，标为假设"，而不是硬编一段听起来很专业的话。

**实际机制**：这是**提示词层的强制格式**，不是道德要求。

| 手法 | 具体做法 |
|---|---|
| **证据分级** | 要求给结论贴标签（实证 / 行为 / 假设 / 口径），不同强度不同采信方式 |
| **假设显式化** | 信息不足处必须写"假设"，并单列一节"信息缺口" |
| **禁止补全** | 未暴露的实现细节（如向量库型号）不许编，只能给结构 |
| **引用绑定** | 结论要挂回具体来源（文件路径、行号、`file_id`） |
| **干跑文化** | 批量操作先 dry-run 打印命中，人工核对再落盘 |

**为什么这条能生效**：因为它给了模型一个**体面的退路**。"标注假设"是一个合法交付物，"编造细节"不是。人也是这样——你给下属一个"可以说不知道"的通道，他才不会编。

**代价**：回答会显得"啰嗦"（一堆标记和缺口清单）。这是刻意的：**宁可交付一份带缺口清单的诚实文档，也不要一份读起来顺滑但站不住的漂亮文档**。

## 3. 一次请求的完整数据流（含钱和字节）

| 阶段 | 产生什么 | 落到哪 | 大小/量级（实测） |
|---|---|---|---|
| 1 组装上下文 | system context（10 块）+ 历史 | 内存 → 请求体 | 当前会话累计 86 KB 级 token |
| 2 模型生成 | `generation` span | `traces\<pid>\` | 3,298 个 span（200 trace 样本） |
| 3 工具决策 | 工具名 + schema（按需拉取） | `mcp-tool-list.json` | 138 KB 清单，命中即用 |
| 4 工具执行 | 文件读写 / 命令 / MCP 调用 | 磁盘 / 外部系统 | Bash 1,559 次、Edit 395 次（样本） |
| 5 结果回填 | 折叠后的观察 | 上下文 | 受"回答 50–70 行"约束 |
| 6 记账 | token 用量 + 额度 | `session_usage` | 142 行台账，`used/size/credit_json` |
| 7 落盘 | trace / log / audit | 三个数据面 | 审计 `sequence` 已到 15,989 |
| 8 沉淀 | 工作区日志追加 | `.workbuddy\memory\YYYY-MM-DD.md` | 每日 1 个文件，只增 |

**注意第 6 步的位置**：记账发生在**每次请求后**，不是会话结束时。这样即使进程崩了，账也不会丢——本机 753 个会话 vs 142 条 usage 记录，说明只有"真的产生过用量"的会话才落账，其余是空会话或已清理。

## 4. 三个最值得记住的反直觉

### 反直觉一：能力不是"加"进去的，是"延迟加载"进去的

常规思路：功能越多，提示词越长。WorkBuddy 的做法相反——**名字进上下文，正文留在磁盘**。31 个技能 + 54 个插件 + 若干 MCP，如果全量注入，窗口当场爆掉。现在的做法让"能力规模"和"上下文成本"解耦：装 100 个技能，上下文只多 100 行描述。

### 反直觉二：上下文管理的核心不是"压缩"，是"配额"

大多数人以为要研究更聪明的摘要算法。实际上更有效的是**给每块定死预算**（4k / 3k 字符、50–70 行、只进描述）。配额制的好处是**可预测**：你知道最坏情况是多少。摘要算法的好坏是不可预测的——同样一段内容，今天压成 3 行，明天可能压成 30 行。

### 反直觉三：可扩展性来自文件系统，不是插件框架

版本管理不靠数据库、不靠注册中心，靠**目录名 + 占位文件**（`<version含哈希>\` + `.in_use\<pid>` + `.orphaned_at`）。这套东西土得掉渣，但它满足三个硬要求：可 diff、可回滚、可并发。插件框架再优雅，做不到这三点就是负债。

## 5. 想抄的话，抄这 8 条（按优先级）

| # | 做什么 | 一句话理由 | 落地成本 |
|---|---|---|---|
| 1 | **先做 trace，再做功能** | 没有 span 的多 Agent 系统等于不可维护 | 低（一个 JSONL 写入器） |
| 2 | **工具两段式加载** | 工具一多，选择准确率断崖下跌 | 中（要拆分注册表） |
| 3 | **上下文配额表** | 每块定死预算，比研究摘要算法有效 | 低（一张常量表） |
| 4 | **记忆三层 + 写入权限分级** | 防越权，也防"讲过的规矩忘了" | 中（要定归属规则） |
| 5 | **目录即版本 + pid 占位** | 回滚从"运维动作"变成"改指针" | 低 |
| 6 | **编辑协议：先读后写 + 唯一锚点** | 可靠性靠协议，不靠模型自觉 | 低（两条校验） |
| 7 | **危险操作四步 + 信任决策落表** | 不可逆操作必须有人为闸门 | 低 |
| 8 | **假设显式化 + 信息缺口清单** | 让"不知道"成为合法交付 | 极低（纯提示词） |

反过来，**先别做**的两件：自研向量库（先用现成的）、多 Agent 编排（单 Agent + 子 Agent 隔离够用很久）。

## 6. 它做得还不够好的地方（诚实清单）

| 问题 | 表现 | 原因 | 缓解 |
|---|---|---|---|
| **子 Agent 重复劳动** | 派出去探索的子 Agent 看不到主对话，可能重读同一批文件 | 上下文隔离的必然代价 | 在派发 prompt 里写全背景与已知结论 |
| **长会话仍需人工分层** | 聊太久后，早期细节只能靠检索找回 | 折叠不可逆 | 关键结论及时落到记忆/文档 |
| **磁盘只增** | `plugins\cache`、`traces`、`audit-log` 都是只增结构 | 可回滚与可审计的前提 | 需定期 GC（孤儿版本 + 老 trace） |
| **依赖模型能力** | 提示词能约束格式，约束不了推理质量 | 模型是变量 | 关键路径加回归用例，模型换代先跑评测 |
| **配额会误伤** | 复杂任务被 50–70 行上限压得说不清 | 单一阈值难适配所有任务 | 明确任务类型后允许超限 |
| **信任决策是粗粒度** | 工作区级"信/不信"，没有目录级细粒度 | 简化模型 | 靠危险操作四步兜底 |
