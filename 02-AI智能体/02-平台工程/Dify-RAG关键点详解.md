## 0. 一句话结论

**RAG 的准确度不是被某一个开关决定的，而是被一条"逐级收窄的漏斗"决定的。**

漏斗的四层（全部候选 → 元数据过滤 → 重排 → TopK/阈值），每一层漏了都会导致最终答案错。绝大多数团队的问题不是"模型不够强"，而是**漏斗第二层压根没开**。

## 1. 卡点总表

| # | 卡点 | 典型表象 | Dify 的解法 | 配置位置 |
|---|---|---|---|---|
| 1 | 数据源单一 | 只能传文件，Notion/网页/云盘进不来 | Knowledge Pipeline + Datasource 插件 | 知识库 → Pipeline 编排 |
| 2 | 表格/图片丢失 | 答案里缺图表，问"图上写了什么"答不出 | 图片抽取存 URL + 多模态 embedding | Pipeline 图片节点 + 模型选择 |
| 3 | 分块粒度 | 上下文截断 / 语义断裂 / 答非所问 | 通用 / 父子 / QA 三种分块结构 | 分段设置 |
| 4 | 索引成本 | 灌一遍知识库烧掉几百块 token | 经济型（10 关键词倒排） vs 高质量（embedding） | 索引方式 |
| 5 | 重复建设 | 已有 Milvus/RAGFlow，还要灌一遍 | **外部知识库 API**，Dify 只当编排层 | 知识库 → 外部 API |
| 6 | 增量更新 | 改一个字要重建全库 | 文档/分段级 CRUD API，改段落自动重索引 | Knowledge API |
| 7 | 漏召回 | 型号、缩写、专有名词检索不到 | 混合检索（向量 + 全文/倒排） | 检索设置 |
| 8 | 排不准 | 正确答案排在 Top3 之外 | Rerank 模型 / 加权分数 | 知识库级 + 节点级 |
| 9 | 越权可见 | 财务部看到 HR 的内容 | 元数据过滤（内置 + 自定义） | 知识检索节点 |
| 10 | 上下文断裂 | 召回的是一个孤立句子 | 父子分块（Small-to-Big） | 分段模式 |
| 11 | 意图混杂 | 售前/售后问题混在一个库里答 | 多知识库 + 分类器路由 / Agent 工具化检索 | 工作流编排 |
| 12 | 瞎编 | 知识库没有，LLM 硬编 | Score 阈值 + 空结果条件分支 + Prompt 约束 | 节点 + 条件分支 |
| 13 | 不可溯源 | 用户无法验证答案来源 | `result` 变量自带分段内容/标题/元数据 | LLM 上下文变量 |
| 14 | 高频成本 | 同一个问题每天问 500 次 | Annotation 标注回复命中即走 | 应用 → 标注 |
| 15 | 无法调优 | 不知道为什么召回错了 | 知识库 UI 的"召回测试" + 节点级 trace | 知识库 / 运行日志 |
| 16 | 静默故障 | 升级完检索悄悄失效，无报错 | 遵守 Weaviate 分阶段升级路径 | 部署运维 |

## 2. 索引侧（离线）—— 决定了天花板的那一半

> 业内的常识：**RAG 质量 70% 取决于入库这一步**。召回器再强，也找不回从来没被正确索引的东西。

### 2.1 数据接不进来 → Knowledge Pipeline + Datasource 插件

传统形态：知识库 = 上传一堆文件，Dify 内部固定流程跑完。
Pipeline 形态：**数据源 → 抽取 → 清洗 → 转换 → 分块 → 索引**，全部可视化可编排。

- 一个知识库可以挂**多个数据源**（本地文件、在线文档、云盘、网页爬虫）
- 支持**单节点单独试运行**、查看中间变量、变量 inspector 里 Markdown 预览
- Pipeline 本身可导出/导入 **DSL**，能复用、能进 Git
- 旧版知识库支持**一键迁移**到 Pipeline 架构

**价值**：以前"这个格式的文档解析不好"是无解的（黑盒），现在可以只替换中间某个 processor 节点。

### 2.2 表格和图片全丢 → 多模态索引

这是 RAG 最痛的一刀，尤其在投研/财报/技术手册场景：

- **Image Extraction & Retrieval**：从文档中抽出图片，以 URL 形式入库
- 选带 **Vision 图标的多模态 embedding 模型** → 图片也被向量化索引 → 该知识库被标记为 Multimodal
- LLM 节点开启 **Vision** 后，检索到的图片会被自动处理（不需要手动再引一遍上下文变量）

**⚠️ 必踩的坑**：用了多模态 embedding，**就必须同时配多模态 Rerank 模型**，否则检索到的图片会在重排环节被直接丢掉，最终答案里一张图都没有。

### 2.3 分块策略 —— 三选一，别再纠结

| 结构 | 机制 | 适用 | 可用索引 |
|---|---|---|---|
| **通用 General** | 固定规则切块 | 大多数文档 | 高质量 / 经济型 |
| **父子 Parent-child** | 子块做索引保精度，父块回填保上下文 | 长文档、需要完整段落 | 仅高质量 |
| **Q&A 问答对** | 直接按问答对建 | FAQ、客服、制度问答 | 仅高质量（2.0 起有 Q&A Processor 插件） |

**参数经验值（起手配置，别瞎创新）：**

| 场景 | max_tokens | overlap |
|---|---|---|
| 事实型问答（查数、查条款） | 300–500 | 10–15% |
| 摘要 / 综述型 | 500–800 | 15–20% |
| 父子模式 | 父 ~1000 / 子 ~200–300 | 父 100 / 子 20 |

还有个小技巧：用**标记语言型元数据 / 分段标识符**（比如在 Markdown 里放自定义分隔符）来控制分段边界，粒度比自动切词靠谱得多。

### 2.4 索引方式：高质量 vs 经济型（**不可逆**）

| | 高质量 High-Quality | 经济型 Economical |
|---|---|---|
| 原理 | embedding 转向量 | 每块抽 10 个关键词，倒排索引 |
| 可用检索 | 向量 / 全文 / 混合 | 仅倒排索引 |
| token 消耗 | 有 | **零** |
| 精度 | 高 | 一般 |
| 可切换 | **建完后不能降回经济型** | 可单向升级到高质量 |

**决策线**：先拿经济型跑通链路、验证分块合不合理；确认要上生产再切高质量。反过来不行 —— 手一抖建了高质量，看着账单哭去吧。

### 2.5 别重复造轮子 → 外部知识库 API

如果你的检索服务已经存在（RAGFlow、自建 Milvus 集群、ES 检索服务），**完全不需要把数据再灌一遍进 Dify**。

Dify 只做编排层：发 query 给外部 API，拿回 chunks，塞给 LLM。这既省了双份存储，也让已有检索资产的调优成果得以保留。这是最被低估的一个功能。

### 2.6 增量更新 → 分段级 API + 幂等键

- `Update Chunk`：改某一段内容，**自动触发该段重新索引**，不用重建整个文档
- 父子模式下一堆 child chunk 的 CRUD 也都有对应接口
- **最佳实践**：把外部系统的 source_id 存成自定义元数据，同步时按它过滤找到对应文档做更新，而不是靠文件名猜（文件名会重、会改）

## 3. 检索侧（在线）—— 两级过滤架构

**这是必须理解的核心设计**：检索设置分**知识库级**和**节点级**两层，可以理解为**先后两道筛选**。

```
知识库级设置  → 决定初步候选池长什么样（用向量还是关键词，还是两者）
节点级设置    → 在这个池子上做重排/过滤/截断
```

**后果**：知识库级选错了，节点级再怎么调 Rerank 也救不回来 —— 因为正确的文档压根没进池子。

### 3.1 第一层：混合检索（解决"漏召回"）

| 检索方式 | 长处 | 短处 |
|---|---|---|
| 向量检索 | 语义泛化好，换个说法也能找到 | 型号/缩写/专有名词/代码 命中差 |
| 全文检索 | 关键词精确匹配 | 同义词、多语言表现差 |
| **混合检索** | 两者取并集 | 需要调权重或上 Rerank |

**中文场景特别注意**：产品型号（`BGE-M3`）、缩写（`EBITDA`）、人名、化学式，纯向量检索大概率漏。混合检索不是"优化项"，在某些场景下是"必需项"。

**经济型路线**：混合检索可以不用 Rerank 模型，改用**权重设置**（语义权重 vs 关键词权重，1:0 到 0:1 之间调），零额外延迟零额外成本。代价是精度低于真正的 Rerank。

### 3.2 第二层：Rerank（解决"排不准"）

Rerank 模型（Cohere、bge-reranker 等）对候选 chunk 逐个打分重排，是**从"能召回"到"排得对"最关键的增量**。

**⚠️ 三个官方设定，不知道就等于白配：**

1. **TopK 和 Score 阈值只在 Rerank 阶段生效。** 也就是说，**不启用 Rerank 模型，这两个参数基本不落地**。很多人调了半天 TopK 发现毫无变化，就是这个原因。
2. Rerank 默认关闭，需要自己配 API Key。
3. 多模态知识库必须配多模态 Rerank，否则图片被排除。

**默认值**：TopK = 3，Score 阈值 = 0.5。这两个值适合"先跑起来看看"，不适合生产 —— 调优时以召回测试的实际 score 分布为准。

### 3.3 元数据过滤（解决"越权"和"版本混乱"）

Dify 1.1.0 引入，是企業级 RAG 的刚需。

- **内置元数据**（默认关闭，需手动开启，生成后不可改）：`document_name`、`uploader`、`upload_date`、`last_update_date`、`source`
- **自定义元数据**（自己建）：string / number / time 三类，支持批量编辑、单文档编辑、元数据 API
- 三种典型用法：
  - **string** → 部门/项目/文档类型，提升语境相关性
  - **number** → 密级数值，实现检索层访问控制
  - **time** → 版本管理，只检索最新版本

**两种模式**：
- **手动**：直接配过滤条件，多条件 AND / OR
- **自动**：让 LLM 从用户问题里提取过滤条件（听起来很美，见下面的坑）

**⚠️ 三个已知的坑（血泪）：**

1. **知识检索节点一旦挂了多个知识库，元数据过滤功能直接不可用。** 想在多库场景用 ACL，只能把多库合并成一个库 + 用元数据区分，或者层加一层预处理把它塞进 query。
2. **自动模式不输出提取日志**，你没法确认它到底提取对了没有。生产环境建议用手动模式，把过滤条件从上游变量（比如用户部门）显式传进来 —— 可观测、可测试。
3. **元数据不向终端用户开放**（问答页面无法让用户自己选标签）。这是产品定位，不要指望终端用户能自助筛选。

**另有一支狠用法**：把外部系统 ID 存成元数据，即上文提到的幂等同步。

### 3.4 父子检索（解决"上下文断裂"）

小 chunk 检索保精度，命中后返回它的父 chunk 保证语义完整。适合"你只需要引用条款第 3.2 条，但模型需要看到第 3 条全貌"的场景。

副作用是上下文开销变大，TopK 会自动按模型的上下文窗口调整 —— 别自己硬算，让系统调。

### 3.5 路由：一个库装不下所有意图

四种递进方案：

1. **多知识库检索**：节点直接挂多个库。**前提：内容别重叠**，否则重复结果会把上下文挤爆。
2. **N-to-1 / 多路径检索**：一个节点并行查多路，汇聚后再生成。
3. **Question Classifier + 分支**：先分类，不同意图走不同的知识检索 + 不同 Prompt。
4. **Agent 把 Knowledge Retrieval 当工具**：让 Agent 自己决定要不要检索、检索几次、换什么 query。支持多轮检索，适合复杂问答。

选哪个取决于你的意图是否清晰可分。**能分类就别上 Agent** —— Agent 是最后的兜底方案，不是首选。

## 4. 生成侧 —— 最后一公里

### 4.1 上下文注入与溯源

知识检索节点输出 `result` 变量：一个数组，每项含**分段内容 + 元数据 + 标题**（有图片时还有 `files` 字段）。把这个变量挂到 LLM 节点的"上下文"上即可。

有了元数据，答案天然可溯源 —— Prompt 里要求"引用来源文件名"，用户就能点回去验证。**不可溯源的答案在企业场景等于没有答案。**

### 4.2 空结果怎么办

检索为空时，LLM 会非常乐意地编一个看起来很专业的答案。**必配三层防御：**

1. Score 阈值过滤掉低相关内容
2. 条件分支：检索结果为空 → 走"明确告知未找到"分支，而不是硬塞空上下文给 LLM
3. Prompt 里显式约束："若上下文不足以回答，直接说不知道，不要推测"

### 4.3 Annotation 标注回复

高频、高确定性、或曾经答错的问题，直接配标注答案，命中即返回，**不消耗 LLM token**。同时它天然是一个"失败样本 → 人工修正 → 沉淀为标准答案"的闭环机制。

### 4.4 Vision

LLM 支持视觉时打开开关，检索到的图文会被一起处理。注意前面提到的多模态 Rerank 配套问题。

## 5. 运维侧 —— 那些不出错则已、一出错就致命的部分

### 5.1 调优的唯一正确入口

**别拍脑袋调参。** 正确顺序：

1. 在知识库 UI 里跑**召回测试**，看目标 chunk 到底有没有被召回
2. 没召回 → 问题在索引侧（分块/检索方式），回去改 2.3 和 3.1
3. 召回了但排得后 → 上 Rerank
4. 排对了但答错 → 才是 Prompt / 模型的问题
5. 把 score 打进日志，观察分布，再定 Score 阈值

**绝大多数"AI 答错了"的工单，查到最后都是第 2 步。**

### 5.2 成本控制清单

- 经济型索引跑通再切高质量
- Embedding 有缓存，别重复跑同一批内容
- TopK 越小越便宜（也是放缓堆收益最直接的旋钮）
- 模型路由分层：决定命运的节点用强模型，批量处理用便宜模型
- Fallback 链配完整
- 高频问题用 Annotation 拦截，直接 0 token

### 5.3 静默故障（自托管必读）

> **1.17.1 升级警告**：内置 Weaviate 从 1.27.0 → 1.39.2，**跨了 12 个小版本，官方明确不支持跳过中间版本**。直接拉新镜像重启会**静默且永久地破坏向量检索**。

新部署、用外部 Weaviate、或用其他向量库的部署不受影响。生产环境升个版本把检索搞挂且**没有任何报错**，属于 AI 应用里最贵的一类 bug —— 它不会报警，只会在几个月后被业务方发现"最近回答越来越离谱"。

### 5.4 权限最小化

用 **Dataset 级 API Key**，按知识库粒度发放。**一个全局 key 打通所有知识库是等着出事。** 1.17.1 也修了一个文档摄取环节的 SSRF 隐患，保持版本跟进。

## 6. Dify 没替你解决的部分（诚实清单）

省得你踩进去以后骂它是 bug：

1. **没有原生 GraphRAG / 知识图谱索引。** 需要实体关系推理的场景得自己接外部图库。
2. **没有端到端的自动化评估体系。** 没有召回率/忠实度的指标看板，测试集要自己维护。这是当前所有 RAG 平台的共同短板。
3. **元数据过滤不支持多知识库节点**（见 3.3）。
4. **元数据自动模式不可观测**，看不到 LLM 提取了什么。
5. **元数据不向终端用户开放**，无法做用户自助筛选。
6. **会话历史压缩策略**比较粗糙，超长会话要自己在工作流层面处理。
7. **中文分词细节不可控**，全文检索质量依赖底层向量库的分词器。

## 7. 可以直接抄的起手配置

| 环节 | 配置 |
|---|---|
| 索引方式 | 高质量（生产） / 经济型（验证期） |
| 分块 | 通用，500 token，overlap 15%；长文档改父子（父 1000 / 子 250） |
| 检索方式 | **混合检索** |
| Rerank | 开启（生产必开），配非多模态知识库用 bge-reranker |
| TopK | 5（默认 3 偏少） |
| Score 阈值 | 0.5 起步，按实际 score 分布再调 |
| 元数据 | 开启内置字段 + 自建 `department` / `security_level` / `doc_version` |
| 元数据模式 | **手动**（自动模式不可观测） |
| 空结果 | 条件分支 → 明确拒答分支 |
| Prompt | 显式约束"上下文不足须明说不知道" |
| 高频问题 | 首批 20 条配 Annotation |

## 8. 出问题时的排查 SOP

```
答案不准
 ├─ 跑召回测试：正确 chunk 被召回了吗？
 │   ├─ 没有 → 索引侧问题
 │   │   ├─ 分块粒度不对吗？            → 调 max_tokens / 换父子模式
 │   │   ├─ 是关键词型的专有名词吗？      → 开混合检索 / 调高关键词权重
 │   │   └─ 内容根本没被正确解析进来？    → 检查文档解析、表格图片抽取
 │   └─ 召回了 → 排序/生成侧问题
 │       ├─ 排在第几？>3 → 上 Rerank
 │       ├─ Score 分布如何？            → 调 Score 阈值
 │       ├─ 上下文够完整吗？            → 换父子模式
 │       └─ 都不是 → 改 Prompt / 换模型
 └─ 别忘了一件事：先确认检索根本没问题（Weaviate 升级陷阱见 5.3）
```
