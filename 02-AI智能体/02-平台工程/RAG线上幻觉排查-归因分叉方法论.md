## 0. 一句话结论与总原则

**线上幻觉绝大多数不是"模型不够强"，而是检索层压根没把正确内容送到模型面前；而检索层出问题的第一嫌疑，往往不是算法，而是这次上线动作本身改了什么。**

两条铁律，写在最前面，后面所有步骤都是它的展开：

1. **先怀疑上线动作，再怀疑算法链路。** 上线后出问题，第一问永远是"这次上线改了流量 / 配置 / 数据里的哪一项"，而不是"要不要换个更强的模型、把温度调低、重写提示词"。后三者是**最后**才动的旋钮，不是第一反应。
2. **先定位是哪一层坏，再动手修。** 检索层、生成层、评测层是三件事，混在一起修等于蒙眼换零件。定位的方法就是 §2 的"归因分叉"。

> 一句话记住：**换模型 / 调温度 / 改提示词，都只作用在生成端；如果正确内容根本没被召回，这三招一发都打不中靶子，纯属浪费算力。**

## 1. 误区与总判断

### 1.1 常见错误排查思路（反面清单）

| 错误动作 | 为什么没用 | 真正该先做的 |
|---|---|---|
| 盲目改提示词 | 提示词只能约束"怎么用上下文"，不能创造上下文。上下文里没有正确答案，再精妙的 prompt 也编不出来 | 先跑召回测试，确认正确 chunk 进没进上下文 |
| 降低温度 | 降温只让模型更"保守地复述上下文"，上下文错了会更稳定地复述错答案 | 先确认上下文对不对 |
| 换更强的模型 | 强模型在错误上下文上一样会幻觉，只是编得更流畅、更自信 | 同上；模型是最后一层变量 |
| 一上来怀疑算法链路 | 忽略"上线动作"这个最高频变量，把工程问题当算法问题查，方向就错了 | 先查这次上线改了什么（见下表） |

### 1.2 总判断：上线动作三查

**出问题的第一现场不是模型，是这次上线本身。** 按这三类逐项核对：

| 上线变量 | 典型变化 | 会直接导致的幻觉形态 |
|---|---|---|
| **流量** | 请求量突增、用户群变化、问题分布漂移 | 超时熔断、链路被跳过；新问题类型没覆盖 |
| **配置** | Rerank 被关、TopK 被调小、Score 阈值变动、召回条数缩减 | 正确 chunk 被截断在候选池外 —— "召回层静默失效" |
| **数据** | 知识库重新灌库、文档更新 / 下架、版本切换 | 数据过期、旧文档未清、多版本答案冲突 |

> 判据：**如果这次上线同时动了这三类里的任何一类，先回滚 / 对比上线前后，再谈调模型。** 没有"改动记录"的排查，是从一开始就没打算查明白。

## 2. 排查步骤：可观测性与归因

### 2.1 先建全链路日志（没有观测就没有排查）

幻觉排查的前提是**每一跳都留痕**。至少要记录这五段：

| 阶段 | 必须落日志的内容 | 用来回答什么问题 |
|---|---|---|
| ① 查询改写 | 原始 query + 改写后 query（含多轮指代解析结果） | 检索用的到底是不是用户真正想问的 |
| ② 召回 | 命中 chunk 列表 + 各自 score + 召回来源（向量 / 全文） | 正确内容有没有进候选池 |
| ③ 重排 | 重排后顺序 + Rerank 分数 + 是否被跳过 | 正确内容排第几、有没有被截断 |
| ④ 最终提示词 | 实际拼给模型的完整上下文 | 模型真正"看到"了什么 |
| ⑤ 模型输出 | 输出文本 + 引用来源 + trace_id | 答案有没有超出上下文、引错了哪条 |

> 【设计·项目映射】本项目的 `trace_id` 贯穿方案见 `政策解读Agent-通用设计.md` §10（轨迹层串起召回清单+分数、位阶判定、引用核验、闸门 B 结果、降级档位）——**一次答错能定位到具体哪一步坏**，正是这一节"全链路日志"的项目级实现。`【设计】` 未标注为线上实测。

### 2.2 幻觉四分类（先分类，别混为一谈）

不同幻觉指向不同根因，笼统说"幻觉"会让排查失去方向。先分四类：

| 类型 | 表象 | 典型根因指向 |
|---|---|---|
| **凭空编造** | 上下文里根本没有，模型自己编了一个答案 | 空结果没走拒答分支 + Prompt 缺拒答约束（→ 生成层，但常由检索为空触发） |
| **事实反转** | 上下文里有 A，模型说成非 A / 相反结论 | 模型没用对上下文、上下文内部有冲突未裁决（→ 生成层 or 知识源冲突） |
| **冲突信息** | 一份说能办、一份说不能办，模型随便挑一个答 | 知识库多版本 / 多效力文档并存，无仲裁（→ 数据层 / 规则层） |
| **数据过期** | 引用了已废止 / 已过时的旧版本内容 | 旧文档未下架、版本未过滤、时效字段缺失（→ 数据层） |

> 【实证·项目映射】后两类（冲突 / 过期）在政策场景是高频致命项，项目把《立法法》适用顺序写成确定性裁决函数 + 版本时间轴，而不是让模型判断——详见 `00-知识库/RAG四大高阶难题-解法深度拆解.md` §3。`【实证】` 仅限版本元数据字段衔接；裁决函数与闸门为团队实现 `【设计】`。

### 2.3 归因分叉（本节核心）

有了日志、分好类，用一棵决策树把问题定位到唯一一层：

```
线上幻觉 / 答案不准
 │
 ├─ 第一步：这次上线改了什么？（流量 / 配置 / 数据）
 │     └─ 有改动 → 先做上线前后对比 / 回滚，排除"上线动作"本身
 │
 ├─ 第二步：跑召回测试 —— 正确内容召回了吗？
 │     │
 │     ├─ 未召回 ──────────────────► 【检索层 / 数据层】
 │     │     ├─ 内容根本没解析入库？      → 查解析、表格图片抽取
 │     │     ├─ 是专有名词 / 型号 / 缩写？ → 纯向量漏召回，开混合检索
 │     │     ├─ 切分粒度不对（过大/过小）？ → 调 chunk / 换父子分块
 │     │     ├─ 多轮指代没改写？          → 补 query 改写
 │     │     └─ 配置被裁（TopK/重排/召回条数）→ 查配置漂移
 │     │
 │     ├─ 召回了，但答错 ───────────► 【生成层】
 │     │     ├─ 排在第几？>3            → 上 / 修 Rerank
 │     │     ├─ 上下文够完整吗？          → 父子回填
 │     │     ├─ 缺拒答约束 / 温度过高？    → 改 Prompt / 调温度（终于轮到它们）
 │     │     └─ 模型硬编？               → 空结果分支 + 引用核验
 │     │
 │     └─ 召回了、也答对了，却被判"幻觉" ─► 【评测标准 / 知识源】
 │           ├─ 评测标准过严 / 答案不唯一？ → 校准评测集、LLM-as-judge 偏差
 │           └─ 知识源之间真冲突？          → 数据版本治理 / 效力裁决
```

**三个分叉的判据要能脱口而出：**

- **未召回 → 数据 / 检索层**：改提示词、换模型一律无效，因为正确信息压根没进上下文。
- **召回了但答错 → 生成层**：这时候才轮到重排、Prompt 拒答约束、温度、模型能力。
- **召回了且答对、却被判幻觉 → 评测层或知识源**：别去改模型，先质疑"评测标准是不是错了"或"知识源自己是不是打架"。

## 3. 深度排查：数据与检索工程

> 这一层是幻觉排查的主战场。业内的常识是 **RAG 质量 70% 取决于入库与检索**，而不是生成。

### 3.1 配置漂移：先查"链路是不是被悄悄裁掉了"

上线为降本 / 提速常做链路裁剪，这些改动**不会报错**，只会让答案悄悄变差：

| 漂移项 | 表象 | 核查方法 |
|---|---|---|
| 延迟熔断导致重排被跳过 | 正确 chunk 召回后排在后面，直接被截断 | 看 §2.1 ③ 的日志：本次请求 Rerank 到底执行了吗 |
| 召回条数被缩减 | TopK / 候选池变小，正确内容掉出截取范围 | 对比上线前后配置，看 score 分布 |
| Rerank 未启用 / 未配 key | TopK、Score 阈值"调了没反应" | TopK 与阈值**只在 Rerank 阶段生效**，这是常见假象 |
| Score 阈值抬升 | 低分但正确的 chunk 被过滤 | 用召回测试的实测 score 分布重定阈值 |

> 【方法论】"配置漂移"是 §1.2"上线动作三查"里"配置"那一类的具体展开。**先证明链路完整，再谈调参**——`Dify-RAG关键点详解.md` §5.3 的 Weaviate 跨版本升级静默破坏检索，就是配置 / 部署漂移最贵的一种。

### 3.2 数据新鲜度与一致性

| 检查项 | 做法 | 不做的后果 |
|---|---|---|
| 知识库同步 | 确认增量更新链路通、source_id 幂等同步生效 | 库里是旧快照，用户问的新政策查不到 |
| 清除废止旧文档 | 下架 / 标记废止版本，避免新旧并存 | 数据过期型幻觉、引用已失效文件 |
| 版本过滤 | 按 `doc_version` / 时效字段只检索现行版本 | 多版本答案冲突，模型随机挑 |
| 多源冲突治理 | 冲突显式标注，判不了就并列呈现，不给胜出方 | 冲突信息型幻觉，还答得一本正经 |

> 【实证·项目映射】本项目按"事项"建版本时间轴（`status` / `supersedes` / `expire_date` / `level` 字段），在落向量库阶段就固化版本关系——见 `RAG四大高阶难题` §3。`【实证】` 仅限元数据字段衔接；时效过滤 / 位阶排序 / 效力裁决函数为 `【设计】`。

### 3.3 切分策略：过大与过小都会制造幻觉

| 问题 | 机制 | 修正方向 |
|---|---|---|
| **切分过大** | 一个 chunk 塞太多内容 → 噪声稀释，正确句子被无关信息淹没，相似度反而下降 | 调小 max_tokens，控制 overlap |
| **切分过小** | 语义断裂，召回的是孤立句子，缺主语 / 缺限定条件 → 模型补全时编造 | 调大 chunk 或换父子分块（子块检索、父块回填） |
| **专有名词漏召回** | 型号、缩写、代号（如 `BGE-M3`、`EBITDA`）纯向量命中差 | 配混合检索（向量 + 全文 / 倒排），必要时调高关键词权重 |

> 【方法论】起手经验值见 `Dify-RAG关键点详解.md` §2.3 / §7：事实型问答 300–500 token、overlap 10–15%；长文档父子模式（父 ~1000 / 子 ~200–300）。**别把切分当玄学，先跑召回测试看目标 chunk 长什么样。**

### 3.4 多轮处理：指代必须改写，否则检索效果极差

多轮对话里用户说"那它的有效期呢""第二条呢"——`它` / `第二条` 指什么，只有结合上下文才知道。

- **必须对多轮 query 做指代消解 / 查询改写**，把"它"还原成具体实体，再送检索。
- 不改写直接检索：query 里全是代词，向量检索拿到的是一堆语义无关的 chunk，**检索效果极差且表现为"幻觉"**（模型拿错误上下文硬答）。
- 【设计·项目映射】本项目的三条状态线与每轮鉴权、会话状态管理见 `多轮RAG系统架构与状态管理图.html` 与 `Dify-RAG关键点详解.md` §6；平台能力事实见 `Dify快速深入指南.md` §3 / §8.7。`【设计】`

> 排查动作：看 §2.1 ① 的日志里"改写后 query"——如果它跟原始 query 一样带着代词，问题就在这一层。

## 4. 生成端与最终优化（最后才动这里）

### 4.1 什么时候才轮到生成端

只有 §2.3 归因分叉判定为"召回正确、排序也 OK、但答案错"，才进入这一层：

| 检查项 | 表象 | 修正 |
|---|---|---|
| 缺拒答约束 | 上下文不足时模型硬编一个专业答案 | Prompt 显式写"上下文不足直接说不知道，不要推测" + 空结果条件分支 |
| 温度过高 | 同样问题每次答案飘、爱自由发挥 | 降低温度（事实型问答宜低温度） |
| 上下文被污染 | 错误引用混进来带偏模型 | 引用核验 / 输出白名单 |

### 4.2 建立回归测试集（拒绝打补丁式开发）

**每发现一个坏例，就固化成一个测试用例**，而不是当场改两句 prompt 就收工。

- 每题标注三样：**问题 + 参考答案 + 证据位置**（哪份文档 / 哪个 chunk）。缺证据位置，评测就退化成"看答案像不像"。
- 题型覆盖四类：**直接事实 / 改写 / 多跳 / 无答案**——尤其"无答案"类，漏了它系统就会变成"该拒不拒"。
- 开发集 / 回归集 / 保留集分开，避免调参时把测试集当训练集。
- 让修复可回归：**"没有回归集的修复等于赌博"**——改完跑一遍，确认没有修好一个、弄坏三个。

> 【方法论】回归集建设的具体分层指标（Recall@K / Faithfulness / 解析侧四层验收）见 `RAG四大高阶难题` §4 与 `00-RAG面试实战手册.md` Q22。

### 4.3 常见根因排序（按命中频率从高到低）

排查时间有限时，按这个概率序优先验证：

1. **分布漂移且无监控** —— 用户问题分布变了，新问题类型没覆盖，而系统没有任何漂移告警（最常见，也最容易被忽视）。
2. **多轮查询未改写** —— 代词 query 直接检索，检索效果崩溃。
3. **知识库不更新** —— 旧版本、废止文档还在库里，数据过期 / 冲突型幻觉。
4. **上线为降本裁剪链路** —— 重排被熔断跳过、召回条数被缩减、Rerank 没开，链路静默失效。
5. 生成端问题（拒答约束 / 温度 / 模型能力）—— **排在最后**，虽然它最常被当成第一怀疑对象。

## 5. 面试怎么讲

### 5.1 一句话版（口径：方法论，不冒充亲历事故）

> "线上 RAG 冒幻觉，我的第一反应不是改模型——换模型、调温度、改提示词都只作用在生成端，正确内容没召回时一发都打不中。我会先问这次上线改了什么，流量、配置还是数据；然后看全链路日志，把幻觉分成凭空编造、事实反转、冲突信息、数据过期四类；再用归因分叉定位：未召回查数据和检索层，召回答错才查生成层，召回且答对却被判幻觉就查评测标准或知识源冲突。检索层重点查配置漂移——重排被熔断跳过、召回条数被缩减这些不报错的改动，还有切分粒度和多轮指代改写。最后才动生成端，并且把每个坏例固化成回归用例，不打补丁式开发。"

### 5.2 追问应对

| 追问 | 答 |
|---|---|
| 你亲自处理过哪次线上幻觉？ | 【方法论】这套是我按 RAG 工程通法沉淀的排查框架，不是某次亲历事故的复盘。项目里我主责的是 MinerU 解析改造和落向量库（版本 / 效力元数据字段衔接），对应的是排查链里"数据层"那一段；线上编排、闸门实现由团队推进，我不冒充。 |
| 为什么说先怀疑上线动作？ | 因为上线同时动了流量 / 配置 / 数据，这三类都是高频根因，且比"模型突然变笨"概率高得多。配置漂移（重排被跳过、TopK 缩减）尤其阴险——不报错，只让答案悄悄变差。没有改动记录的排查等于没查。 |
| 召回了还答错，怎么定位是重排还是生成？ | 看 §2.1 日志：先看重排后正确内容排第几，>3 就是重排没做好；排第一还答错，才看 Prompt 拒答约束、温度和引用核验。指标上 Recall@K 高但 Faithfulness 低 = 生成层问题，不是检索的锅。 |
| 提示词到底什么时候改？ | 最后。确认召回对、排序对、上下文完整之后，才用 Prompt 补拒答约束。上下文本身错的时候改 prompt，是在错误地基上装修。 |
