## 0. 先厘清一件事：智能客服 ≠ 知识库问答

很多人把智能客服做成"挂了个知识库的问答机器人"，然后在真实业务里被投诉 —— 因为它只解决了三分之一的问题。

**真正的差别在这三件事：**

| | 知识库问答 | 智能客服 |
|---|---|---|
| 目标 | 给出**正确答案** | **解决客户的问题** |
| 答不出来时 | 说"没找到"就结束 | **必须转人工**，且不能让客户重复说一遍 |
| 会话结束后 | 结束 | 工单 / 回访 / 质检 / 知识回流，**闭环** |

再加一条最容易被忽略的：**客服有将近一半的问题根本不是"知识问题"**。"我的保证金什么时候解冻""这笔合同的电子签章到哪一步了""我这车货到哪了"——这类问题知识库里永远没有答案，因为答案是**因企业、因单、因时而异的实时业务数据**。把它交给 RAG 是智能客服的头号事故来源（见 §5.1）。

> **在 B2B 现货平台上，这条分界线比 ToC 场景更要命。** ToC 场景下答错一笔账单，代价是一笔钱的争议；现货平台上一笔合同动辄百万级，且"撮合是否已成交""仓单是否已解押"这类状态**来自 C 语言内存撮合引擎经 DS 数据中心桥接后的数据，存在可观时滞**（详见 §8.5 与 `02-现货贸易/03-架构决策/13-C核心单线程内存一致性设计.md`）。客服一旦把"时点状态"说成"当前状态"，就可能引发真实的货款争议。

## 1. 智能客服的十个独有约束

| # | 约束 | 与知识库问答的差别 | 做错的后果 |
|---|---|---|---|
| 1 | **服务属性** | 目标是"解决问题"，不是"给出答案" | 答对了但没解决，客户照样不满意 |
| 2 | **必须能转人工** | 转人工是**设计的一部分**，不是失败 | 死循环、客户暴怒、升级投诉 |
| 3 | **有状态、有生命周期** | 会话会超时、会跨渠道、会被接续 | 客户重复说、上下文丢失 |
| 4 | **高并发多会话** | 同一机器人同时服务成千上万个客户 | **上下文串线** —— 把 A 的资料说给 B（重大事故） |
| 5 | **情绪是独立变量** | 情绪与意图**正交**，同样的问题不同情绪走不同路径 | 火上浇油 |
| 6 | **一半问题要查业务数据** | 答案来自业务系统，不是文档 | RAG 永远答不对，且会一本正经地编 |
| 7 | **话术有合规红线** | 不能乱承诺、不能报错价、不能给法律意见 | 合规风险、赔付、监管处罚 |
| 8 | **必须闭环** | 会话结束只是开始 | 问题没真正解决，同一个客户反复来 |
| 9 | **一个账号可能挂多个主体** | B2B 场景下一个登录账号常关联母公司 / 子公司 / 多品类经营主体 | 把 A 主体的合同说给 B 主体（见 §3.2 与 §8.5） |
| 10 | **金额与数量错一位就是事故** | 现货客单价数十万到上千万 | 数字被模型改写 = 真实货款争议（见 §8.3） |

> 第 4 条是客服独有的、也是破坏力最大的：政策解读是一问一答的独立请求，而客服是**长生命周期、多轮、并发**的会话。上下文管理稍有疏忽，就会把客户的隐私信息串给别人。
>
> 第 9、10 条是**现货平台专属**的：ToC 客服的身份是一维的（这个人），B2B 客服的身份是二维的（这个账号 + 这个法律主体），且答案里大量出现金额、数量、质检指标这类"错一位就出事"的数字。这两条直接决定了下面 §3.2 的身份模型与 §8.5 的 API 白名单为什么必须做成那样。

## 3. 【细】接入层

### 3.1 渠道矩阵

| 渠道 | 特点 | 特殊要求 |
|---|---|---|
| 网页 / APP 在线客服 | 主战场，支持富媒体 | — |
| 微信公众号 / 小程序 | 移动端为主 | 消息长度限制、不能富文本 |
| 电话语音 | 实时、无视觉 | 需 ASR + TTS，**需支持打断**、无"返回上一步" |
| 邮件 / 工单 | 异步 | 响应时效按 SLA 计 |
| 企业 IM（企微/钉钉） | 内部员工服务（IT/HR 客服） | 身份从组织架构取 |

**关键设计**：**渠道适配层要与业务逻辑解耦**。渠道差异只在"输入怎么来、输出怎么回"，从 §4 开始的全链路必须统一。否则会变成"每个渠道一套机器人"，维护成本爆炸。

### 3.2 身份识别（三级）

客服的身份识别不只是"鉴权"，更是"**加载客户档案**"：

| 级别 | 识别方式 | 能做什么 |
|---|---|---|
| L1 设备级 | 设备 ID / 会话 ID | 只能答通用规则问题 |
| L2 账号级 | 登录态 | 可查本账号关联主体的合同、订单、结算 |
| L3 实名级 | 企业实名认证 / 授权书 | 可办敏感业务（解押、放款、开票）、可授权他人代办 |

**红线**：**数据类问题的可回答范围严格绑定身份级别**。未登录状态下问"我的合同签完了吗"，正确动作是**引导登录**，而不是"查不到"也不是"随便给一个"。

> **B2B 补充：身份是二维的（级别 × 主体）。** L1/L2/L3 只解决了"能查多深"，还没解决"能查谁"。一个登录账号常挂多个法律主体（母/子公司、多品类经营主体、买卖双重身份），因此每次数据类查询都必须再绑定 `legal_entity`（见 §6.1）。
> **判定顺序不能颠倒**：先定级别（能查多深）→ 再定主体（能查谁）→ 最后才校验单号归属。**顺序反了会出现"主体对了但越了级"或"级别够了但串了主体"两种漏洞。**

### 3.3 会话生命周期

| 状态 | 说明 | 关键动作 |
|---|---|---|
| 新建 | 首次进入 | 加载客户档案、历史会话摘要（老客户别让他重复说） |
| 活跃 | 正常对话 | 多轮上下文维护 |
| 静默超时 | 若干分钟无输入 | **上下文保留但不混入新会话** |
| 跨渠道接续 | 网页聊一半转到 APP | 凭会话 ID 接续，带上摘要 |
| 关闭 | 主动结束 / 超时结束 | 触发 §16 的闭环动作 |

**并发隔离红线**：每个会话必须有独立的上下文空间，且**上下文对象要与 `session_id` 强绑定**。这是 §1 第 4 条那个"串线事故"的唯一防线。

## 4. 【细】客户输入理解

### 4.1 输入规范化

| 处理 | 说明 |
|---|---|
| 口语归一 | "咋弄""能不能""帮我搞一下" → 规范表述 |
| 错别字纠正 | 业务专名纠错（错一个字，检索就空） |
| 简写 / 拼音 / 首字母 | "fy"、"kf" 这类要能还原 |
| 多模态 | 图片（截图报错、身份证、票据）、语音、短视频 |
| 文件 | 用户上传的 PDF / 表格 |

**图片类输入要特别对待**：客服场景里"发张截图"是极高频动作。截图往往包含**报错信息、订单号、金额**——OCR 抽取后要走"数据类"通道校验，而不是塞给 RAG。

### 4.2 情绪识别（独立通道，必须与意图并行）

情绪**不是意图的一种**，它是与意图正交的第二个维度。同是"我的账单怎么还没出来"：

| 情绪 | 策略 |
|---|---|
| 平静 | 正常应答 |
| 焦急 | 缩短回答、优先给结论、加快转人工阈值 |
| 愤怒 / 威胁监管投诉 | **立即降级为安抚话术 + 优先转人工**，不再试图讲道理 |

**设计要点**：情绪判定必须**独立于意图判定**。如果把它塞进意图分类的枚举里，就会出现"既像咨询又像投诉"时的纠结，而正确答案是**两个维度各自输出**。

### 4.3 上下文与指代消解

| 场景 | 处理 |
|---|---|
| 指代 | "它""这个""刚才说的" → 回指上文实体 |
| 省略 | "那电费呢" → 补全为"电费是多少" |
| 话题切换 | 检测到新话题 → **清理旧槽位**（否则会带着上一个话题的参数答新问题） |
| 无法消解 | **追问，不要猜** |

## 5. 【细】意图识别

### 5.1 ★ 第一分岔：知识类 / 数据类（本文最重要的一节）

**这是智能客服与知识库问答最本质的分界线。**

| 类型 | 特征 | 例子（现货平台口径） | 正确通道 |
|---|---|---|---|
| **知识类** | 答案是"规定 / 说明"，**对所有客户都一样** | 保证金比例怎么算、基差点价怎么操作、提货需要带什么材料、电子签章流程是什么、某品类需要什么经营资质 | 直击库 / RAG |
| **数据类** | 答案是"**某个主体的某个单的实时值**"，因主体、因单、因时而异 | 我的保证金解冻了吗、这份合同的签章到哪一步了、我这车货到哪了、这张仓单解押了吗、这笔结算款打出来没 | **必须调业务 API** |
| **混合类** | 前半是规定、后半是数据 | 我这种情况算不算违约、我这单现在撤单要扣多少、我这家企业能不能参与这个场次 | **先规则后数据**（两步） |

**为什么这条线必须画死？**

> RAG 的机制是在**文档库里找最相似的段落**。而"我的保证金解冻了吗"这个问题的答案**根本不在任何文档里** —— 它在资金系统的数据库里，而且每一秒都可能变。
>
> 一个没有这条分界线的客服系统，遇到"我的保证金"会检索到一段《保证金规则说明》，然后生成一段听起来非常专业、但**跟你这单毫无关系**的文字。用户会以为系统在敷衍他。更糟的是，某些模型会"顺着"编一个解冻时间出来 —— 在百万级合同上，这就是一次货真价实的客诉。

**可写成规则的判定线索：**

- 出现**第一人称所属物**（我的 / 我这家 / 我账户 / 我名下 / 我方）+ 可量化名词 → **数据类**
- 出现**具体单号**（合同号 / 订单号 / 仓单号 / 提货单号 / 发运单号 / 结算单号 / 场次号）→ **数据类**
- 出现"进度 / 状态 / 余额 / 冻结 / 解押 / 到哪了 / 什么时候到 / 打出来没" → **倾向数据类**
- 全是"怎么 / 是什么 / 需要什么 / 能不能 / 比例是多少"（无具体指向）→ **知识类**
- 句中出现"我这个情况……""我这单……" → **混合类**

**混合类必须两步走**：先从知识库取出规则（"违约认定需同时满足 X、Y"），再用规则去业务系统取数据算结论（"你这单目前只满足 X"）。**顺序不能颠倒**，也不能把两步混成一次生成。

> **现货平台的一条专属警告**：混合类的第二步**绝不能让模型"替客户做判定"**。"我这单算不算违约"的正确输出是"依据《XX规则》第 X 条，违约认定需满足 A 与 B；你这单目前 A 已成立、B 未成立"，而不是"你这单不算违约"。是否构成违约是**平台运营方的裁决权**，客服系统只能摆事实与依据 —— 这条与 §7.4「不代替客户判断」是同一条红线在 B2B 场景下的加重版。

### 5.2 客服意图分类体系（5 大类 · 22 子类 · 现货平台版）

> 分类体系的编号 `A1`…`E4` 是**直击库 `faq_id` 的归属标签**（见 §7.3），也是意图模型的枚举输出空间。换业务不用换架构，但要换这张表。

| 大类 | 子类 | 典型问法 | 走哪条路 |
|---|---|---|---|
| **A 咨询类** | A1 **交易规则咨询** | 挂牌和竞价有什么区别、保证金比例多少、手续费怎么收 | 知识类 |
| | A2 **操作流程指引** | 怎么报名这个场次、怎么签电子合同、提货要带什么 | 知识类 |
| | A3 **政策与合规咨询** | 这个品类需要什么资质、危化品运输有什么要求、税票政策 | 知识类（**强时效**，见 §5.2.1） |
| | A4 **术语释义** | 基差是什么、点价怎么点、升贴水、背书、交割 | 知识类 |
| | A5 **商品与规格咨询** | 这个牌号对应什么质量标准、可替代规格有哪些 | 知识类 |
| **B 办理类** | B1 办理指引（怎么办） | 企业认证怎么过、资质怎么上传 | 知识类 |
| | B2 **办理进度查询** | 我的企业认证审到哪一步了 | **数据类** |
| | B3 办理条件判断（我符不符合） | 我这家企业能不能参与这个场次 | **混合类** |
| **C 查询类** | C1 **交易查询** | 我的挂牌成交了吗、这笔报价还在有效吗 | **数据类**（★ 带时点，见 §8.5） |
| | C2 **合同履约查询** | 合同签完了吗、电子签章到哪一步 | **数据类** |
| | C3 **物流与提货查询** | 我这车货到哪了、提货单开了吗 | **数据类** |
| | C4 **结算与资金查询** | 保证金解冻了吗、货款打出来没、账户余额 | **数据类**（★ 金额模板化，见 §8.3） |
| | C5 **仓单查询** | 这张仓单质押中还是已解押、库存多少 | **数据类** |
| | C6 **发票与税务查询** | 发票开了吗、什么时候能寄出 | **数据类** |
| | C7 **融资进度查询** | 我那笔仓单融资审到哪一步 | **数据类** |
| **D 售后 / 争议类** | D1 **交易异常** | 为什么被撤单、这单流标了怎么办、价格异常 | 混合类（先规则后建单） |
| | D2 **货损货差 / 质量异议** | 到货数量短少、质检指标不符 | 混合类 + **必建工单** |
| | D3 **催办 / 加急** | 催放款、催提货、催开票 | 数据类 + 转人工 |
| | D4 **投诉 / 纠纷** | 要投诉、要赔付、要走仲裁 | **直转人工** |
| **E 会话控制** | E1 显式要求转人工 | 转人工、找客服 | **直转人工** |
| | E2 闲聊 / 测试 | 你是机器人吗 | 引导话术 |
| | E3 情绪宣泄 | 骂人、威胁投诉到监管 | 安抚 + 优先转人工 |
| | E4 越权 / 违规请求 | 帮我查一下 XX 公司的合同 | **拦截** |

> **A3 与 C4 必须分开**（最高频的混淆点）：前者是"保证金比例是多少"（知识类，对所有企业相同，但有强时效性）；后者是"我的保证金解冻了吗"（数据类，必须查且带时点）。这两者被混淆是极高频的错误。
>
> **D2（质量异议）是现货平台最贵的一类会话**：它往往牵着质检报告、短少称重、赔付谈判，且**一旦进入争议流程，所有对外表述都可能成为证据**。因此 D2 一律**先建工单再回答**，不允许在会话里即兴定责 —— 与 §7.4「不给法律意见」「不代替客户判断」同源。

#### 5.2.1 A3（政策类咨询）的特殊处理

A3 是唯一一个**要跨到政策解读 Agent** 的意图。处理方式不是"客服自己答"，而是**转交**：

| 情况 | 处理 |
|---|---|
| 问的是**平台规则**（交易规则、违约处理、费率） | 客服知识库自行回答（这是平台规则，不是法） |
| 问的是**行业 / 监管政策**（资质、税务、危化品、交易场所监管） | **转交政策解读 Agent**，带回带文号、带时效、带条款的答案 |
| 两者混在一起 | **必须分开答**，并明确标注哪部分是平台规则、哪部分是法定依据 |

> ⚠️ **这是 B2B 场景独有的一条红线**：把"平台交易规则"说成"根据 XX 规定"是**越权且虚假**的。平台规则是**合同契约**，不是法规。知识库建库时这两类文档必须**用元数据字段分开**（见 §20.3），否则 Agent 会稳定地把自家规则包装成法规 —— 这类错误在监管检查中是致命的。

### 5.3 三层识别架构

```
       输入（已规范化）
          │
  ┌───────▼────────┐
  │ 第一层 · 规则前置 │  零成本、确定性
  │  强信号词 / 正则  │
  └───────┬────────┘  命中即返回，跳过模型
          │ 未命中
  ┌───────▼────────┐
  │ 第二层 · 轻量模型 │  枚举分类 + 置信度 + 理由
  └───────┬────────┘
          │ 置信度 < 门槛（如 0.6）
  ┌───────▼────────┐
  │ 第三层 · 保守兜底 │  ★ 不是"随便猜一个"，
  └────────────────┘     而是降级为"澄清追问"或"转人工"
```

**规则层优先的理由**：客服话术里强信号极多 —— "转人工""投诉""退钱""我的订单""加急"。这些命中比模型准、快、且免费。模型只负责规则覆盖不到的自然表述。

**第三层的关键**：客服场景的兜底**不能像知识问答那样降级为"只给原文"** —— 客户要的不是原文，是解决。所以兜底应该是**澄清追问**（"您是想问 A 还是 B？"）或**转人工**。

### 5.4 多意图与主意图

客户常一句话说几件事：*"我这单货款三天了还没到账，发票也没开，你们是不是有问题。"*

| 处理 | 说明 |
|---|---|
| 拆解 | 切分为多个意图：C4（结算款未到）+ C6（发票未开）+ E3（情绪） |
| 排序 | 按 **紧急度 × 情绪 × 能否自助解决** 排序 |
| 先接住情绪 | 情绪永远排在第一位处理（一句话安抚），再逐条解决 |
| 逐条闭环 | 每条都要有明确归宿（答了 / 转了 / 建单了） |

> **严禁只答第一个问题就把其余丢掉。** 客户会觉得"你根本没听我说"。

### 5.5 显式转人工请求

客户说"转人工""找客服""别跟我机器人说话" —— **必须无条件、立即执行**，不做任何"要不要我先帮您看看"的挽留。

挽留是客服系统里最常见的自作聪明：客户已经明确表达了不信任，再拦一次只会让情绪升级。**把"转人工"做成一键直达，是体验设计，也是成本设计**（省下的那点人工费，远不够赔一次投诉升级）。

### 5.6 置信度与保守兜底

| 置信度 | 动作 |
|---|---|
| ≥ 0.8 | 按识别结果正常执行 |
| 0.6 – 0.8 | 执行，但**答案里带一句轻确认**（"如果您问的是 X，那么……"） |
| < 0.6 | **不猜** → 澄清追问 或 转人工 |

## 6. 【细】槽位抽取

| 槽位 | 说明 | 缺失处理 |
|---|---|---|
| `intent` | 意图（可多个，§5.2 编号） | 追问 |
| `intent_type` | 知识类 / 数据类 / 混合类 | **必判，不可缺** |
| `entities` | **合同号 / 订单号 / 场次号 / 仓单号 / 提货单号 / 发运单号 / 结算单号 / 发票号**、日期、品类、牌号 | 数据类问题**必填**，缺则按 §6.1 处理 |
| `legal_entity` | **当前会话所代表的法律主体**（母/子公司、多品类主体） | ★ B2B 必填，缺则**必须澄清**，不得默认取账号主主体 |
| `emotion` | 平静 / 焦急 / 愤怒 | 默认平静 |
| `urgency` | 普通 / 加急 | 默认普通 |
| `identity_level` | L1 / L2 / L3（来自 §3.2） | 从会话取 |
| `channel` | 渠道 | 从接入层取 |
| `attempt_count` | 同一问题已尝试轮数 | 用于转人工判定 |
| `history_refs` | 上文引用的实体 | 用于指代消解 |

**`entities` 缺失的处理是客服的一个分水岭**：用户说"我的合同签完了吗"但没给合同号 —— 正确做法是**先去客户档案里找"最近一份进行中的合同"**（有身份就能查），找不到再追问。直接追问"请提供合同号"是不合格的，因为客户会觉得"我都登录了你还问我"。

### 6.1 ★ `legal_entity` 是 B2B 独有的槽位（不可省略）

ToC 客服的身份是一维的（这个人就是这个人）；**B2B 现货平台一个登录账号常常挂着多个法律主体**——集团公司下的贸易子公司、不同品类各自的经营主体、以及"既是买方又是卖方"的双重身份。

| 情形 | 处理 |
|---|---|
| 账号只挂一个主体 | 静默绑定，不打扰 |
| 账号挂多个主体，但问题里带了单号 | **用单号反查所属主体**，并以该主体为本次查询边界 |
| 账号挂多个主体，问题里没有单号（如"我的保证金解冻了吗"） | **必须澄清**："请问是查询 A 公司还是 B 公司？" |
| 客户提到的单号不属于其任一主体 | **拒绝并留痕**，不报"查无此单"（避免泄露单号存在性） |

> **为什么不能默认取主主体？** 因为一旦默认，就会出现"把子公司的合同信息展示给了母公司的操作员"。这在 B2B 里不是隐私瑕疵，是**商业机密泄露**——合同价格、成交量、上下游关系全在里面。这条与 §8.2「身份绑定」是同一条红线，只是把"账号级"收紧到了"主体级"。

## 7. 【细】直击库匹配（匹配到就直接返回）

### 7.1 三级直击

| 级 | 命中方式 | 成本 | 适用 |
|---|---|---|---|
| **L0** | 标注回复（精确匹配固定问法） | 0 token | 高频 Top 20、话术必须逐字合规 |
| **L1** | 精确命中（单号 / 产品名 / 条款号） | 0 token | "XX 业务怎么办"这类标准问法 |
| **L2** | 语义匹配（embedding） | 仅 embedding | "换了说法的同一问题" |

**客服场景 L0 的价值特别高**：涉及**合规话术**的问题（退款政策、隐私说明、投诉处理时限）必须逐字输出，让模型每次换一种说法是法律风险。

### 7.2 ★ 命中校验四道关

**命中 ≠ 可以直接返回。** 客服比知识问答多一道关：

```
直击命中
  │
  ├─ 关一 · 时效校验
  │    关联的规则/资费文件是否仍有效？（价格类、政策类必查）
  │
  ├─ 关二 · 身份校验
  │    这条答案要求的身份级别，当前客户达到了吗？
  │    （未登录客户不能拿到"仅本人可见"的答复）
  │
  ├─ 关三 · 一致性校验
  │    该 FAQ 关联的源规则是否已被新规则替代？
  │
  └─ 关四 · 话术合规校验  ← 客服独有
       答案里是否包含承诺性表述、绝对化用语、法律意见、
       或其他需要资质才能说的内容？
       └─ 命中红线 → **驳回**，改走"人工话术模板"或转人工
  │
  ▼
四关全过 → 直接返回   ／   任一不过 → 静默走后续链路
```

> **关四为什么必须有？** 知识问答答错了，用户自己会判断；客服答错了，用户会**当成官方承诺**。一句模型自己发挥出来的"可以的，肯定能退"，就可能变成一次赔付纠纷。
>
> **静默降级**同样重要：不要告诉客户"我有一条但过期了"，那会暴露知识库组织信息，也会让客户觉得系统"知道却不告诉他"。

### 7.3 客服 FAQ 库字段

| 字段 | 说明 |
|---|---|
| `faq_id` | 主键 |
| `question` | 标准问法（可挂多个同义问法） |
| `answer` | 标准答案（**合规话术必须逐字**） |
| `intent` | 归属意图（§5.2 编号） |
| `answer_type` | 知识类 / 数据类 / 混合类 |
| `required_identity` | 所需身份级别（L1/L2/L3） |
| `channel_scope` | 适用渠道 |
| `effective_from` / `effective_to` | 有效期（资费类必填） |
| `source_ref` | 依据来源（内部规则 / 公开说明），**便于审计** |
| `compliance_level` | 是否属于合规话术（是 → 禁止模型改写） |
| `status` | draft / active / retired |
| `hits` | 命中计数 |
| `review_on` | 下次复核日期 |

### 7.4 客服话术的合规红线

| 红线 | 说明 |
|---|---|
| 不承诺 | "肯定可以""一定能退""保证解决" |
| 不报错价 | 价格必须来自当前有效的资费表 |
| 不给法律意见 | 涉及纠纷、责任认定 → 转人工 |
| 不代替客户判断 | "您这个肯定符合条件" → 只能说"依据 XX，需满足以下条件" |
| 不泄露他人信息 | 含查询他人账户、他人订单的请求一律拒 |

### 7.5 阈值与命中率

- L2 语义阈值 **0.85** 起手（Rerank 必开 —— **TopK 与 Score 阈值只在 Rerank 阶段生效**，不开就是摆设）
- **错命中的代价 ≫ 漏命中**：错命中 = 给客户一个看似权威但答非所问的答案；漏命中 = 多花点钱走 RAG 或转人工
- 直击命中率健康区间 **20%–40%**；低于 10% 说明收集的不是真高频问题

## 8. 【细】数据类：走 API，不是走 RAG

### 8.1 为什么必须走 API

数据类问题的答案**不存在于任何文档**，只存在于业务系统。用 RAG 处理这类问题，结果只有两种：答不出，或者编一个。

### 8.2 设计要点

| 要点 | 说明 |
|---|---|
| **白名单** | 只有预定义的查询动作可被调用，不允许模型自由构造请求 |
| **参数校验** | 单号、户号格式校验；**参数必须来自客户档案或客户明确提供，不得由模型推断** |
| **身份绑定** | 查询主体**强制取自当前会话的登录身份**，模型不能指定别人的 ID |
| **超时与重试** | 短超时、有限重试，避免客户干等 |
| **降级** | 接口失败 → 明确告知 + 转人工，**不得用缓存数据冒充实时数据** |
| **可追溯** | 每次调用留痕（谁、何时、查了什么、返回什么），便于争议取证 |

> **身份绑定这条是安全红线。** 模型输出的是"建议查询哪个客户"，但真正执行的 ID 必须由会话身份强制注入。任何"让模型决定查谁"的设计都是越权漏洞。

### 8.3 数据 → 自然语言

拿到结构化数据后要**话术化**，但不能改变数值。数字部分由模板填充（保证逐字准确），解释部分可由模型生成（受约束）。

### 8.4 数据类的失败处理

| 情况 | 处理 |
|---|---|
| 无数据（如"您还没有订单"） | 如实告知 + 给出下一步建议 |
| 权限不足 | 引导提升身份级别（登录 / 实名），**不暴露"有数据但你没权限"** |
| 单号不属于当前主体 | **拒绝并留痕**，不报"查无此单"（避免泄露单号存在性，见 §6.1） |
| 接口异常 | 致歉 + 转人工，**不猜** |
| 数据异常（如金额为负、数量为 0） | 转人工（可能是业务问题，也可能是**撮合/结算链路真的出了故障**） |

### 8.5 ★ B2B 现货平台的数据类 API 白名单（本文与平台结合的核心）

白名单是**唯一允许模型触发的动作集**。模型不能自由构造请求，只能在下面这张表里选一个动作、填参数，参数由会话身份强制注入。

> 所有调用一律经**自研业务中台的工具网关**出网，不直连业务库；网关侧的入参白名单、分页默认 100、分级限流、输出白名单、可观测由 `02-现货贸易/03-架构决策/11-midservice网关职责与治理设计.md` 统一兜底 —— **客服侧不要自己再实现一套鉴权**。

| # | 动作（白名单） | 承接意图 | 必填入参 | ★ 该动作的专属口径红线 |
|---|---|---|---|---|
| 1 | `query_trade_status` | C1 交易查询 | 场次号 / 订单号 | **状态必须带时点输出**（见下）；不得把"排队中"说成"已成交" |
| 2 | `query_contract` | C2 合同履约 | 合同号 | 合同金额、签署状态**逐字返回**，不得摘要、不得四舍五入 |
| 3 | `query_shipment` | C3 物流提货 | 发运单号 / 提货单号 | 车船号、司机信息按脱敏规则输出；**不得承诺到货时间** |
| 4 | `query_settlement` | C4 结算资金 | 结算单号 | ★ **金额一律模板填充**，模型不得复述或改写数字 |
| 5 | `query_margin` | C4 保证金 | 场次号 / 合同号 | 冻结 / 解冻是**资金系统事实**，不得推断"应该已经解冻了" |
| 6 | `query_warrant` | C5 仓单 | 仓单号 | 质押 / 解押状态必须来自仓单系统，**不得由合同状态推断** |
| 7 | `query_invoice` | C6 发票税务 | 发票申请单号 | 税额、票面金额逐字；不得承诺开具时限 |
| 8 | `query_financing` | C7 融资 | 融资申请号 | **只返回当前节点**，不预测审批结论、不透露评分规则 |
| 9 | `query_certification` | B2 办理进度 | 主体 ID | 缺失项如实告知，不替客户判断"应该能过" |

**两类动作明确不进白名单**：

| 不做什么 | 理由 |
|---|---|
| 任何**写操作**（撤单、改价、解冻、放款、开票、解押） | 客服场景一律不赋写权限。需要写 → 转人工或走工单（见 §8.6） |
| 任何**跨主体查询** | `legal_entity` 强制注入，模型无权指定主体（见 §6.1） |

#### 8.5.1 ★ 撮合类状态必须"带时点输出"——与 C 引擎内存一致性直接挂钩

这是现货平台客服**最容易踩、也最容易被面试官追问**的一条。

平台的撮合状态由 **C 语言单线程内存撮合引擎**产生，经自研 **DS 数据中心（Hessian / Socket 桥接）**送到 Java 业务中台。这条链路上存在三类客观风险（详见 `02-现货贸易/03-架构决策/13-C核心单线程内存一致性设计.md`）：**易失、时滞、回写失败**。

对应的客服口径必须是：

```
❌ 错误："您这笔已经成交了。"
✅ 正确："截至 14:32:05，系统显示这笔报价状态为【已成交】，成交量 500 吨。
        该状态来自撮合引擎，最终以结算单为准。"
```

| 风险 | 客服侧的表现 | 必须的输出约束 |
|---|---|---|
| **时滞** | 引擎已成交、中台还没落库 | 状态**必须带"截至 XX 时点"**，并注明以结算单/合同为准 |
| **易失** | 进程重启后内存状态丢失 | 重启后的会话**不得**引用重启前的口头状态，提示以单据为准 |
| **回写失败** | 撮合成功但落库失败（进死信队列） | 接口返回"处理中/未知"时 → **如实说"正在确认"并建工单**，绝不猜 |

> 这条约束的本质，与 `02-现货贸易/03-架构决策/12-跨系统调用一致性方案.md` 讲的是同一件事：**"只需送达"的场景可以重试兜底，但"必须补偿"的场景（涉及钱和货权）不允许靠口头状态结案。** 客服看到的中间态，永远不是终态。

#### 8.5.2 金额与数量：模板填充，模型零改写

B2B 客单价数十万到上千万，数字错一位就是真实争议。因此：

- 金额、数量、单价、税率、质检指标 → **由模板从接口返回值逐字填充**，模型负责填充前后的自然语言连接部分
- 禁止模型对数字做四舍五入、单位换算、"大约""左右"这类模糊化
- 一次应答中出现的所有数字，必须能在接口返回值里**逐字找到出处**（纳入 §10 闸门 B-1 的核验范围）

### 8.6 写操作怎么办：转工单，不转权限

客户常会要求"帮我撤单""帮我把保证金退了"。**正确做法不是给客服 Agent 开放写权限，而是生成一张带上下文的工单**：

| 客户诉求 | 处理 |
|---|---|
| 客户要求撤销 / 修改 | 生成工单，工单内携带单号、主体、诉求、会话摘要 → 由业务方在后台按权限处理 |
| 客户要求加急 | 工单标记加急 + 按 §12 分派 |
| 客户要求赔付 | **直转人工**（§11.1 条件 ⑦），不走工单自助 |

> 参照 `02-现货贸易/03-架构决策/12-跨系统调用一致性方案.md` 的三段式骨架：客服侧只做**"同步本地事务"**（建工单、落审计），真正的业务动作由后台**"异步派发"**完成，**"兜底人工"**永远保留。让对话机器人直接写业务库，是把"客服体验"建立在"资金风险"之上。

## 9. 【细】未命中 → RAG 全链路

复用 `02-AI智能体/03-业务设计/政策解读Agent-通用设计.md` 的六层架构与两道闸门，客服场景的差异：

| 环节 | 客服场景的差异 |
|---|---|
| 闸门 A（权限前置） | 除密级外，还要按**渠道**（内部知识不能出现在对客渠道）和**身份级别**过滤 |
| 混合检索 | 关键词通道要覆盖产品名、业务专名、政策文号 |
| Rerank | 必开，生效 top_k = 3–5 |
| 时效校验 | 价格、政策、活动规则必须校验有效期 |
| 上下文组装 | 只放条款/规则原文，**不放客户隐私数据** |
| 生成 | temp = 0；强制引用来源；禁止行动指导以外的承诺 |

**一个客服特有的取舍**：`top_k` 可以比政策解读更小（3–5 而非 5–15），因为客服答案通常只需要一条规则；给多了反而容易让模型拼凑出一个"综合"答案，而客服要的是**明确的单一口径**。

## 10. 生成与两道闸门（要点）

- **强制结构化输出**：`conclusion / basis[] / next_step / disclaimer`
- **强制引用**：每条结论挂来源（文档名 + 条目）
- **禁止承诺**：系统提示里明确写死
- `uncertainty` **必填**

**闸门 B（输出前）**：

- B-1 引用核验：引用来源是否真实存在、摘录是否逐字一致
- B-2 越权复核：是否带出了他人信息、内部信息、超身份级别的内容

**客服再加一道：**

- **B-3 合规终检**：承诺性表述、绝对化用语、法律意见、价格数值与资费表是否一致

## 11. 【细】转人工决策

**转人工不是失败，是设计的一部分。** 一个转人工率为 0 的智能客服，要么在硬撑，要么在撒谎。

### 11.1 七条触发条件

> v1.0 此处标题误写为"六大"，与表内七条及 §16/§17 的"七条件"矛盾，v1.1 已统一为七条。

| 条件 | 说明（现货平台口径） | 优先级 |
|---|---|---|
| **① 显式请求** | "转人工""找客服" | 最高，立即转 |
| **② 情绪升级** | 愤怒、威胁投诉、提及监管/媒体 | 高，先安抚再转 |
| **③ 高风险话题** | 资金、赔付、违约责任认定、安全、隐私 | 高，必转 |
| **④ 连续未解决** | 同一意图连续 2 轮未解决，或客户重复问第 3 次 | 中 |
| **⑤ 高价值客户** | 大客户 / 战略客户 / 长期协议客户 | 中（提前转） |
| **⑥ 系统异常** | 数据类接口连续失败，或**撮合/资金接口返回"处理中/未知"**（见 §8.5.1） | 中 |
| **⑦ 明确要求赔偿** | 提出赔付、退款金额争议、**质量异议定责** | 高 |

> **③ 在现货平台要特别收紧**：凡是"这算不算违约""责任算谁的""能不能赔"这类**需要平台行使裁决权**的问题，一律转人工。客服系统只能摆依据与事实（§5.1），不能下结论 —— 一旦会话里出现定责性表述，就可能成为后续争议的证据。

### 11.2 交接包（不能让客户重复说）

转人工时必须把上下文打包给坐席，**客户不该有"又要从头说一遍"的体验**：

```
交接包内容：
  · 客户档案（身份级别、历史服务记录、标签）
  · 会话摘要（一句话说清客户到底要什么）
  · 已识别意图与槽位（含已提供的单号等）
  · 情绪与紧急度
  · 机器人已尝试的动作与结果（试过什么、为什么没解决）
  · 已召回的知识条目（坐席可复用）
  · 建议的下一步（给坐席参考，不强制）
```

> **没有交接包的转人工，等于把机器人的难题丢给人，客户还得再讲一遍 —— 体验比直接排队人工还差。**

### 11.3 转人工的体验设计

| 环节 | 要求 |
|---|---|
| 排队 | 显示预估等待时间；提供"留言回电"替代方案 |
| 高峰期 | 自动推荐自助方案，但**不强制** |
| 无人可用 | 建工单 + 承诺回复时效，**不能只是"稍后再试"** |
| 转接过程 | 保留会话上下文，不重置 |

### 11.4 转人工率的健康区间

- **20%–35%** 属正常
- **< 10%** 要警惕：可能该转不转，客户在自助里被绕晕（短期数据好看，长期投诉上升）
- **> 45%** 说明自助能力不足，或问题定位不准

## 12. 工单与闭环

| 环节 | 说明 |
|---|---|
| 建单 | 自助未解决 / 需线下处理 / 客户要求 → 自动生成工单，**带上下文** |
| 分派 | 按业务域、地域、技能组路由 |
| 跟踪 | 客户可查进度（走 §8 数据类通道） |
| 回访 | 解决后主动通知 |
| 归档 | 工单结论回写知识库（见 §14） |

**关键**：工单号要**当场告知客户**，并支持后续用这个号查询。否则客户下次来又是从零开始。

---

## 13. 会话结束 · 满意度 · 质检

| 动作 | 说明 |
|---|---|
| 结束判定 | 客户主动结束 / 超时 / 问题闭环 |
| 会话小结 | 自动生成结构化摘要（意图、结果、是否解决），供坐席和质检用 |
| 满意度 | 轻量邀请，**不骚扰**（不要每次都弹） |
| 质检 | 抽样 + 规则命中（合规红线必检）+ 情绪恶化会话必检 |

**质检的对象是双份**：既查**人的服务**（坐席话术），也查**机器人的回答**（幻觉、合规、错误知识）。后者常被忽略，但它是知识库质量的唯一真实来源。

## 14. 回流：对话日志 → 知识资产

**这是智能客服相对知识库问答最大的结构性优势：它有海量真实对话。**

```
对话日志
   │
   ├─ 未解决问题 ──────► 候选知识池 ──► 人工审核 ──► 直击库 / 文档
   ├─ 高频繁问题 ──────► 晋升为 L0 标注回复
   ├─ 答错的会话 ──────► 定位是知识错还是流程错 ──► 修文档 / 改话术
   └─ 转人工会话 ──────► 分析转人工根因 ──► 补知识 或 改流程
```

**闭环的三个指标**：

| 指标 | 意义 |
|---|---|
| 自助解决率变化趋势 | 知识库是否在真正变好 |
| 同一问题重复咨询率 | 是否"假解决"了 |
| 转人工根因分布 | 下一轮优化的靶子 |

> **没有回流闭环的智能客服，上线那天就是它的最佳状态** —— 之后只会随业务变化而逐渐失准。

## 15. 人机协作（坐席辅助）

智能客服不只是"全自动机器人"。**坐席辅助**往往是投入产出比更高的一块：

| 能力 | 说明 |
|---|---|
| 实时话术推荐 | 根据坐席与客户的对话，实时推候选回答与知识条目 |
| 自动摘要 | 会话结束自动生成工单摘要，省坐席时间 |
| 合规提醒 | 坐席说了违规话术时实时提示 |
| 知识直达 | 坐席不用翻手册，一句话检索到位 |
| 情绪提示 | 提示客户情绪状态，建议沟通策略 |

> 全自动机器人解决的是"高频简单问题"；坐席辅助解决的是"**所有问题**"。**先上坐席辅助往往是更稳的第一步** —— 它没有幻觉风险（人来把关），却能立刻省掉大量查询时间。

## 18. 验收指标

| 指标 | 目标 | 说明 |
|---|---|---|
| **一次解决率（FCR）** | ≥ 70% | 客服的**第一指标**，比准确率重要得多 |
| **幻觉率** | **0** | 红线，客服答错=官方承诺 |
| **上下文串线** | **0** | 红线，是隐私事故 |
| 直击命中率 | 20%–40% | 低于 10% 说明问题集选错 |
| 转人工率 | 20%–35% | 过低过高都要查（§11.4） |
| 意图识别准确率 | ≥ 92% | 含知识/数据分类准确率 ≥ 95% |
| 首次响应时延 | < 2s | 直击命中应 < 500ms |
| 数据类调用准确率 | ≥ 99% | 涉及钱的数字，不允许错 |
| 满意度（CSAT） | 跟踪趋势 | 单次波动无意义 |
| 重复咨询率 | 下降趋势 | 检验是否"假解决" |

**必测的八类用例：**

1. **知识/数据混淆**：问"我的保证金解冻了吗"绝不能被路由到 RAG（必须走 `query_margin`）
2. **身份越权**：未登录问"我的合同"→ 引导登录；问"XX 公司的合同"→ 拒
3. **主体隔离（B2B 专属）**：账号挂多主体时问"我的保证金"→ **必须澄清主体**，不得默认取主主体（§6.1）
4. **时点输出**：撮合类状态答案必须带"截至 XX 时点"；接口返回"处理中/未知"→ 如实说在建工单，不得猜（§8.5.1）
5. **金额逐字**：应答中的金额、数量必须能在接口返回值里逐字找到出处（§8.5.2）
6. **合规话术**：答案里不能出现承诺性表述，也不能出现**违约/责任的定责性表述**（§11.1 条件 ③）
7. **转人工**：显式说"转人工"→ 必须 0 挽留直达
8. **上下文隔离**：并发会话下，A 主体的资料绝不出现在 B 主体的会话里

## 19. 分期落地（B2B 现货平台版）

| 期 | 范围 | 覆盖意图 | 交付标准 |
|---|---|---|---|
| **一期 · 坐席辅助 + 直击库** | 步骤 10–12 + 坐席辅助（§15） | A 类全部（知识类） | 人在把关，**零幻觉风险**；先省下坐席翻交易规则手册的时间 |
| **二期 · 自助机器人（知识类）** | 加 01–09、14–17 | A 类 + B1 | 只承接**知识类**，C 类（查数）与 D 类（争议）一律转人工 |
| **三期 · 数据类接入** | 加 13 + §8.5 白名单 | C1–C7 逐批放开 | ★ **按风险由低到高放开**：先开物流/发票，再开合同/仓单，**结算与保证金最后开** |
| **四期 · 政策类转交** | §5.2.1 A3 转交政策解读 Agent | A3 | 行业政策问题带回带文号、带时效的解读 |
| **五期 · 闭环与治理** | 加 18–20 + §14 回流 | 全部 | 工单、质检、知识回流自动化 |

**三期为什么必须"由低到高"放开**：C3 物流、C6 发票答错了是**麻烦**；C4 结算资金、C5 仓单答错了是**事故**（钱和货权）。同样是数据类，风险量级差两个档次，不能因为"都是调接口"就一起上。

> 一期先做**坐席辅助**而不是全自动机器人 —— 因为它不需要客户信任一个还不成熟的机器人，却立刻能省下坐席大量翻手册的时间。这是投入产出比最高、风险最低的起点。

## 20. ★ 在 B2B 现货平台的落地规划

> 这一节回答"这套设计落到 `02-现货贸易/b2b-project/overview.md` 描述的那个平台上，具体要做什么"。**架构不变，变的是接什么、切什么、按什么顺序开。**

### 20.1 接入面：AI 客服在平台里站在哪

```
  客户（贸易商 / 上下游企业）
        │  网页 / APP / 小程序 / 企微
        ▼
┌──────────────────────────────────────────┐
│  渠道适配层（§3.1）                        │  差异只在这里收敛
└──────────────────┬───────────────────────┘
                   ▼
┌──────────────────────────────────────────┐
│  Dify（智能层）· 20 步 Workflow（§16）     │
│  理解 / 意图 / 直击 / 检索 / 生成 / 核验    │
└──────────────────┬───────────────────────┘
                   │  ★ 只走工具网关，不直连业务库
                   ▼
┌──────────────────────────────────────────┐
│  自研业务中台（业务层）                     │
│  统一身份（含 legal_entity）· 鉴权 · 审计   │
│  工具网关 · 工单 · token 计量               │
└──────────────────┬───────────────────────┘
        ┌──────────┼──────────┬──────────┐
        ▼          ▼          ▼          ▼
   交易/撮合   合同履约    仓单·物流   结算·税务·金融
   （经 DS 桥接 C 引擎）              （对接银行 / WMS / 税务）
```

**三条接入纪律**（与 `02-现货贸易/03-架构决策/11-midservice网关职责与治理设计.md` 对齐）：

1. **AI 侧不直连业务库**，一切业务数据经中台工具网关出网，网关统一做入参白名单、限流、审计。
2. **权限校验在中台侧执行**，不把过滤责任交给 Prompt（这也是平台定位文档 §2 硬指标 3 的要求）。
3. **AI 调用必须带 `trace_id`**，与客户、单据、坐席操作日志可关联，争议时可取证。

### 20.2 知识库怎么切（决定闸门 A 能不能生效）

Dify 的已知坑：**单节点挂多个知识库时，元数据过滤不可用**（§17）。所以必须**按维度拆库**，而不是一个大库靠过滤。

| 知识库 | 内容 | 元数据关键字段 | 可见范围 |
|---|---|---|---|
| `kb-platform-rules` | **平台规则**：交易规则、违约处理、费率、操作流程 | `doc_type=platform_rule`、`effective_from/to`、`biz_domain` | 全部客户 |
| `kb-industry-policy` | **行业/监管政策**：资质、税务、危化品、交易场所监管 | `doc_type=legal`、`位阶`、`jurisdiction`、`文号` | 全部客户（按密级再拆） |
| `kb-internal-sop` | **内部 SOP**：客服话术、处理时限、升级路径 | `doc_type=internal` | **仅内部坐席，绝不出对客渠道** |
| `kb-faq-direct` | 直击库（L0/L1/L2） | `intent`、`channel_scope`、`required_identity`、`compliance_level` | 按字段过滤 |
| `kb-product-spec` | 品类、牌号、质量标准、规格对照 | `category`、`grade` | 全部客户 |

> **★ `kb-platform-rules` 与 `kb-industry-policy` 必须分开**，理由见 §5.2.1：平台规则是合同契约，不是法规。混库会让 Agent 稳定地把自家规则说成"根据 XX 规定"——这类错误在监管场合是致命的，且**闸门 B 查不出来**（引用是真实的，只是性质被错误归类）。因此这条要靠**建库阶段的元数据字段**来防，而不是靠输出核验。

### 20.3 分阶段路线（含依赖与验收）

| 阶段 | 目标 | 依赖（必须前置就绪） | 验收口径 |
|---|---|---|---|
| **S0 · 建库** | 五库拆分 + 元数据字段落地 | 平台规则与政策文档归集、密级评定 | 元数据必填字段完整率 100% |
| **S1 · 坐席辅助** | §15 上线 | Dify 部署 + 内部知识库 | 坐席检索耗时下降（趋势） |
| **S2 · 知识类自助** | A/B1 意图自助 | 直击库 Top 50 条目 + 合规话术审核 | 直击命中率 20%–40%、幻觉率 **0** |
| **S3 · 查数类（低风险）** | C3 物流、C6 发票 | 中台工具网关 + 接口白名单 3/6/7 | 数据类调用准确率 ≥ 99% |
| **S4 · 查数类（高风险）** | C2 合同、C5 仓单、C4 结算 | 金额模板化 + 时点输出（§8.5.1）+ 工单联动 | 金额逐字一致率 100%、状态必带时点 |
| **S5 · 政策转交** | A3 转政策解读 Agent | 政策解读 Agent 二期完成（其 §11 分期） | 带回结果带文号、带时效状态 |
| **S6 · 闭环治理** | §14 回流 + 质检 | 工单系统 + 会话日志落库 | 重复咨询率呈下降趋势 |

**S3 → S4 之间那道坎是本规划的咽喉**：低风险查数做成之后，团队很容易顺势把结算、保证金一起放开。但这两类一旦答错就是真实的资金争议，因此 S4 的准入条件是**金额模板化与时点输出两项机制先做完**（§8.5.1 / §8.5.2），而不是"接口调通了"。

### 20.4 一句话给面试官的版本

> "这套客服不是挂在平台外面的聊天框，它是**长在业务中台上的**：身份是二维的（账号 + 法律主体），查数只走中台工具网关的白名单动作，涉及钱和货权的接口强制模板化输出并带时点，写操作一律转工单不开放权限。知识库按'平台规则 / 行业政策 / 内部 SOP'三拆，因为平台规则不是法规 —— 混在一起会让 Agent 把自家规则包装成监管要求。"
