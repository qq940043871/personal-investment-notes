## 0. 三句话结论（给没时间的人）

1. **它是什么**：在公司 B2B 大宗商品交易平台之上，加的一层**企业级 AI 能力底座**——由 Dify（社区版私有化二开）承担"智能层"，自研业务中台承担"业务层"，对外统一输出智能客服、知识检索、政策解读三类应用。
2. **它解决什么**：解决三件线下和传统 IT 都干不好的事——**政策看不懂/看错**（时效错、效力错、越权看）、**问一个同样的问题要打三次电话**（7×24 咨询、跨系统查数）、**知识散在十几个人脑子里**（人走知识走、口径不一）。
3. **它值多少**：价值不在"用了大模型"，而在**把三件高风险、高人力的重复性脑力劳动，从"靠人"变成"靠系统"**——效率、成本、合规风险、知识资产、组织能力五个维度同时收益，且**一次建设、多处复用**。

## 1. 平台是什么

### 1.1 三层结构（谁干什么）

```
┌──────────────────────────────────────────────────────────────┐
│  应用层（对外交付什么）                                        │
│  智能客服 │ 知识检索 │ 政策解读（含电力垂直版） │ 内部效率助手    │
└───────────────────────────┬──────────────────────────────────┘
                            │  统一走中台暴露的 API / 工具
┌───────────────────────────▼──────────────────────────────────┐
│  智能层 = Dify（社区版 · 私有化二开）                          │
│  Workflow 编排 / Agent / RAG 管道 / Prompt 管理 / 可观测       │
│  职责：把"模型能力"变成"可编排、可调、可回滚的应用"             │
└───────────────────────────┬──────────────────────────────────┘
                            │  OpenAI-compatible / 本地推理 Runtime
┌───────────────────────────▼──────────────────────────────────┐
│  业务层 = 自研业务中台（AI 的门禁与总线）                       │
│  统一身份 · 细粒度鉴权 · 工具网关 · 审计留痕 · token 计量        │
│  会话与单据关联 · 多渠道前端 · 存量系统集成（ERP/OA/CRM）        │
│  职责：把"AI 应用"变成"能被组织管住的生产系统"                   │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  能力层 = 模型 + 知识资产                                      │
│  第三方模型 / 内网私有化模型 · 向量库 · 政策与产品知识库        │
│  直击库（已验证问答） · 解析产物（Markdown 中间态）             │
└──────────────────────────────────────────────────────────────┘
```

**一句话记法**：Dify 解决"AI 怎么做得快、怎么调得好"，自研中台解决"AI 怎么接得稳、怎么管得住"。

### 1.2 它和"外挂一个机器人"的区别

这是团队对齐时最需要说清的一件事。市面上大量所谓"企业 AI 应用"长这样：**一个聊天框 + 一个向量库 + 一段提示词**。区别在下面这张表：

| 维度 | 外挂式聊天机器人 | 本平台 |
|---|---|---|
| 目标 | 给出**答案** | **解决问题**（答不出要能转人、能闭环） |
| 数据 | 常见做法是把文档丢给公有云 | **数据不出域**，敏感链路走内网私有化 |
| 模型 | 钉死一家厂商 | **模型中立**，可换厂商、可换国产、可换私有 |
| 权限 | 靠提示词"请不要说其他人数据" | **权限校验在中台侧执行**，不把过滤责任交给 Prompt |
| 出错 | 编了就编了 | **两道纯代码闸门**（政策）/ **命中校验四关**（客服）|
| 成本 | 每问必进大模型 | **直击库**截流，已验证问题 0 生成 token |
| 归谁管 | 业务部门偷偷买的一个工具 | 有审计、有计量、有配额、有退场路径 |

### 1.3 能力全景（八个模块，各自解决什么）

| # | 能力模块 | 解决什么 | 主要使用者 |
|---|---|---|---|
| 1 | **智能客服** | 7×24 咨询、多轮对话、情绪识别、该转人时转人 | 外部客户 / 客服部门 |
| 2 | **知识库与智能检索** | 商品、规格、流程、制度"问得出来、答得一致" | 外部客户 / 内部全员 |
| 3 | **政策解读（通用 + 电力垂直）** | 政策时效、效力位阶、条款级溯源、角色适配 | 业务部门 / 法务 / 客户 |
| 4 | **RAG 系统** | 让答案"有依据"，可溯源到原文位置 | 全平台共用底座 |
| 5 | **智能体开发** | 把多步骤流程（查数→判断→写回）串成可执行任务 | 平台建设方 |
| 6 | **大模型管理** | 多模型接入、切换、监控，避免厂商锁定 | 平台建设方 / IT |
| 7 | **模型微调** | 垂直场景效果调优（非必选项，效果瓶颈时才上） | 平台建设方 |
| 8 | **数据标注** | 效果评估与持续迭代的燃料（标注集=回归测试集） | 业务 + 平台 |

> 其中 **1、2、3 是"看得见的价值出口"**，4–8 是让前三个能跑稳、能迭代的底座。团队对齐时别只讲底座，业务方听不懂。

## 2. "企业级"三个字意味着什么

很多平台自称企业级，实际上是"能跑起来的 demo"。企业级是可检验的，用六条硬指标：

| # | 硬指标 | 具体含义 | 平台对应机制 |
|---|---|---|---|
| 1 | **数据不出域** | 敏感数据不进第三方；或至少按敏感度分级走不同通道 | 内网私有化部署 + 按数据敏感度划通道（通用咨询走第三方、涉密走内网） |
| 2 | **模型中立** | 换模型不改业务代码、不影响业务连续性 | OpenAPI 兼容端点 + 中台网关抽象，保留"换编排引擎"的退出路径 |
| 3 | **权限收口** | 越权访问在系统层被拦，不靠模型自觉 | 统一身份 + 工具网关统一鉴权；**校验永远在中台侧** |
| 4 | **可审计可计量** | 每一次 AI 调用可归因到人、到部门、到单据 | trace_id 关联业务操作日志与 AI 调用日志；token 按部门/租户计量分摊 |
| 5 | **可降级不崩** | 模型挂了/超时了/答不准了，系统给"信息更少但更确定"的结果 | 门控降级三档（完整解读 / 仅原文 / 未找到依据）；转人工为设计的一部分 |
| 6 | **可退出** | 不被单一厂商路线图卡死 | 协议宽松（Apache-2.0 修改版）+ 可二开 + 可插件/MCP 扩展 |

**一句话**：**企业级的本质不是"能力更多"，是"出错时可解释、可追责、可恢复"。** 这也是为什么下面 §6 会把"纯代码闸门"单列一节——那些正是企业级与玩具的分水岭。

## 3. 它到底有什么用：三类使用者的场景清单

### 3.1 外部客户（平台上的贸易商 / 上下游企业）

| 场景 | 客户原来的做法 | 现在 |
|---|---|---|
| 政策口径咨询 | 自己上网找文件、易抓到已废止的版本 | 问一句，给**带文号、带条款位置、带时效状态**的解读 |
| 平台规则/流程咨询 | 打电话、等人工、问三个人得三个答案 | 7×24 自助，口径统一 |
| 商品规格/可替代性查询 | 逐家问价、Excel 手工比对 | 标准化编码并排对比 + 履约数据 |
| 单据/进度查询 | "我的单子到哪一步了"打三个电话 | 会话内直接查（走业务 API，**不是查文档**） |
| 该找谁办、走什么流程 | 靠关系、靠经验 | 按角色（买方/卖方/不同品类）给差异化指引 |

### 3.2 内部业务部门

| 部门 | 原来的痛点 | 平台给什么 |
|---|---|---|
| 客服 | 重复问题占大头，人力被低价值问答吃掉 | 高频问题由直击库截流，人工只接"必须人接"的 |
| 法务 / 合规 | 政策更新靠人盯，条款引用靠翻 | 政策库时效监测 + 效力位阶裁决 + 条款级溯源 |
| 业务 / 销售 | 新人培训周期长，口径靠师父带 | 知识库 + 智能助手，口径统一可查 |
| 风控 / 运营 | 合同、条款、材料的初审耗人 | 条款抽取与风险点提示（AI 出草稿，人做决策） |
| 管理层 | 想要"数据在哪、谁在用、值不值" | 用量、效果、成本可观测 |

### 3.3 企业自身

- **能力平台化**：一套底座服务多条业务线，避免每来一个 AI 需求就从零买一遍、建一遍。
- **迭代方式变了**：Prompt 与代码解耦后，调优从"提需求→开发→发版"变成"改配置→预览→发布"，业务方可以直接参与。
- **组织能力沉淀**：AI 工程能力（解析、检索、评测、观测）留在自己团队，而不是留在一份采购合同里。

### 3.4 场景优先级矩阵（建议）

| 优先级 | 场景 | 理由 | **在 B2B 现货平台的落点** |
|---|---|---|---|
| **P0** | 知识检索 + 智能客服（高频问答部分） | 见效最快、效果可量化、风险可控 | 交易规则 / 操作流程 / 品类规格咨询（智能客服 §5.2 的 A 类） |
| **P0** | 政策解读（垂直版先行） | 价值最硬（直接关钱、关合规），但要选**一个**垂直场景做透 | **选大宗商品现货**（平台主业），六类政策源见政策解读 §13.1；电力版是并列的第二个行业实例 |
| **P1** | 单据查询类客服（查数类问题） | 依赖中台工具网关就绪，价值高但要打通业务 API | 按风险**由低到高**放开：物流/发票 → 合同/仓单 → **结算与保证金最后**（智能客服 §19、§20.3） |
| **P1** | 合同/材料初筛 | 高风险场景，必须"AI 出草稿 + 人做决策" | 合同条款抽取、资质材料初筛（供应链金融进件） |
| **P2** | 微调、多智能体协作、复杂流程自动化 | 前两阶段跑顺、评测集攒够再上，否则纯烧钱 | 暂不排期 |

> **为什么政策解读的垂直版要先选现货而不是电力**：电力版虽然是现成的深水区实例，但**电力不是本平台的主业客群**。给面试官或客户讲"我们挑了哪个垂直场景做透"，选主业更有说服力——因为政策解读的价值恰恰在于"它服务的就是这批客户的这笔生意"。电力版保留为"换行业只需换 §13"的证明件。

## 4. 解决了客户的什么问题

### 4.1 行业侧的四个真痛点（与 B2B 平台痛点版一一对应）

参考 `04-备战手册/01-产品定位/04-B2B大宗贸易平台-产品三维度分析.md` §一 的痛点切法，AI 平台在其中的补位关系：

| 行业痛点 | 传统 IT 的解法 | AI 平台的补位 |
|---|---|---|
| **信任壁垒**（不敢跟新客户做生意） | 保证金、履约数据、平台担保 | 帮助客户**读懂规则与政策**，降低"因不懂而踩坑"的风险 |
| **信息不对称**（价格/货源不透明） | 标准化编码、行情对接、比价 | 自然语言检索 + 规格对比，把"会查库"的门槛降到"会说话" |
| **交易效率**（一笔交易跑断腿） | 在线协同、银企直连、物流可视 | 单据进度自助查询、流程指引，减少"打电话问进度"的环节 |
| **资金约束**（有好机会缺钱） | 供应链金融三种模式 | 材料初筛与合规提示，缩短金融业务的进件周期 |

### 4.2 三个"不做就出事"的场景 —— 价值最硬的地方

这三处不是"锦上添花"，是**企业级与玩具的分水岭**，也是这套设计真正的含金量：

**① 政策时效：引用已废止文件 = 误导**

政策不是"追加新版本"，是"失效/被替代"。有效期、施行日与公布日是两个日期、被替代链条——这些全都有法定规则，**必须用代码算**，不能交给模型猜。

**② 效力位阶：拿地方试点文件否定国务院条例 = 定性错误**

上位法优于下位法、特别法优于一般法（**仅限同一机关**）、新法优于旧法、变通法优于被变通法。还有最容易被忽略的：**"工作方案""会议纪要"根本不构成行政管理依据**——正确答案是如实告知，而不是硬凑一段解读。

**③ 权限与密级：征求意见稿、内部文件泄露 = 事故**

权限画像每轮重载不缓存；检索前先过权限闸门；输出前再复核一次越权。

> **一条贯穿全局的原则**：所有降级都朝"**信息更少但更确定**"的方向走，绝不朝"信息更多但更不确定"的方向走。

### 4.3 一个反直觉但重要的判断

政策解读的绝大部分风险，**不是模型不够聪明，而是把确定性的事情交给了模型去猜**。

时效、效力位阶、权限边界、引用真伪——这四件事全都有法定规则可循，**必须用代码算**；只有"把条款翻译成人话"这一件事，才交给大模型。

这条分界线，就是整套方案"稳"和"准"的全部来源。

## 5. 项目价值（企业级视角 · 五维）

> 下表每一维都给"**怎么度量**"。数字栏标 `待实测` 的，表示原型期未采集、需要在 POC 阶段补测——**这是当前最大的材料缺口**。

### 5.1 效率价值

| 价值点 | 机制支撑 | 度量口径 | 现状 |
|---|---|---|---|
| 高频咨询免人工 | 直击库 L0/L1 命中直接返回 | 自助解决率 = 未转人工会话 / 总会话 | `待实测` |
| 首次响应时长下降 | 7×24 + 秒级检索 | 首字延迟（P50/P95） | `待实测` |
| 政策查询从"几小时"到"几分钟" | 条款级溯源 + 直击 | 单次查询耗时 | `待实测` |
| 业务方自主调优 | Prompt 与代码解耦 | 从需求提出到上线配置的天数 | `待实测` |

### 5.2 成本价值

| 价值点 | 机制支撑 | 度量口径 |
|---|---|---|
| 客服人力从低价值问答释放 | 直击库截流 + 转人工只接"该接的" | 人均接待量变化 / 人力编制变化（`待实测`） |
| 单次问答成本下降 | L1 强命中 0 生成 token；Rerank 精准减少无效上下文 | 平均单会话 token 消耗（`待实测`） |
| 避免重复建设 | 一套底座多业务线复用 | 每新增场景的边际人日（`待实测`） |
| 避免厂商计费溢价 | 自部署"只为模型付费" | 同等调用量下的 TCO 对比（`待实测`） |

### 5.3 风险与合规价值（本平台最不可替代的一维）

| 价值点 | 机制支撑 |
|---|---|
| 政策误读风险 | 时效校验 + 效力位阶裁决 + 条款级引用核验 |
| 引用已废止文件 | 有效期硬规则（≤5 年；暂行/试行 ≤3 年；届满未延续自动失效） |
| 越权与泄密 | 权限画像每轮重载 + 检索前闸门 + 输出前复核 |
| 模型幻觉 | 受约束生成（强制 schema + 强制引用 + temp=0）+ 纯代码核验 |
| 合规话术风险 | 输出前终检（不能乱承诺、不能报错价、不能给法律意见） |
| 事故可追溯 | trace_id 关联业务日志与 AI 调用日志 |

> 这一维的度量方式与效率不同——**它主要用"避免的事故数/避免的损失"来度量**，天然难以先验量化。所以团队对齐时建议这样表述：**"这一维的价值不在于赚了多少，在于它让上面那些效率收益敢放开做。"**

### 5.4 资产价值

| 价值点 | 说明 |
|---|---|
| **已验证问答 = 知识资产** | 召回测试里"答对了"的样本，沉淀成独立 Q&A 库，可被多个应用共享、可进版本管理 |
| **文档 → 结构化中间态** | 多格式文档统一解析为 Markdown 再由上游入库，形成可复用的解析产物与清洗管道 |
| **评测集** | 标注数据同时是效果评估与回归测试的燃料，是"能迭代"的前提 |
| **口径统一** | 把散在个人脑子里的口径变成平台可查的唯一版本 |

> 一句话：**每一次召回测试的"答对"，都不该蒸发在聊天记录里。**

### 5.5 战略与组织价值

| 价值点 | 说明 |
|---|---|
| 能力平台化 | 从"每来一个 AI 需求做一个项目"变为"在底座上配一个应用" |
| 不被厂商套牢 | 模型中立 + 编排引擎可替换 + 协议宽松可二开 |
| 组织 AI 工程能力 | 解析、检索、评测、观测、权限收口这套工程经验留在自己团队 |
| 对外可讲的故事 | "AI 不是 demo，是生产系统"——这在客户、投资方、招聘三个场合都是硬通货 |

### 5.6 五维价值一句话总结

> **效率上省时间，成本上省人力，合规上避事故，资产上攒数据，战略上攒能力。**
> 前两维算得出 ROI，后三维决定这件事值不值得长期投。

## 6. 价值为什么能兑现：机制支撑

价值叙事容易写，难的是**兑现**。以下机制是"这些话不是 PPT"的依据：

### 6.1 一条总纲（先记住这句）

> **确定性的事交给代码，只有"翻译成人话"这件事交给模型。**

判断一个环节该不该用模型，就用这一句过筛：凡是看到某处"让模型自己判断时效/效力/权限"，那就是事故的起点。

### 6.2 四组硬机制

| 机制 | 在哪 | 解决什么 |
|---|---|---|
| **两道闸门**（政策） | 检索前权限闸门 + 生成后核验闸门，纯规则 | 越权、引用不实 |
| **命中校验四关**（客服） | 直击命中后仍需校验才可直接返回 | "命中了但答案已过期/不适用"的隐性事故 |
| **直击库三档**（L0/L1/L2） | 标注回复 / 强命中 / 弱命中 | 省 token、保一致性；默认交付 L1 |
| **三硬约束**（架构规范） | 权限校验在中台 / 不直连业务库 / 工作流不写复杂业务逻辑 | 责任错位、耦合失控 |

### 6.3 前置条件（价值兑现的依赖，务必对齐）

| 价值 | 依赖 |
|---|---|
| 效率与成本收益 | 知识库内容质量 + 直击库覆盖率（覆盖不到就退化成"每次进模型"） |
| 政策类价值 | 政策数据源的**更新时效**与**解析质量**（源头脏，下游全废） |
| 单据查询类价值 | 中台工具网关就绪、业务 API 可用、身份收口完成 |
| 合规价值 | 权限画像数据准确；审计链路打通 |
| 全部价值 | 评测集与观测体系——**没有评测，就没有"变好了"的证据** |

## 7. 能力边界：它不解决什么（团队对齐必备）

同样重要的一节。以下六件事**别指望它**：

1. **不替代业务决策。** 它出草稿、给依据、标风险，**决定权在人**。合同、授信、定级一律"AI 建议 + 人确认"。
2. **不做算法创新。** 定位是"把成熟能力接进业务"，不是训练新模型。微调只在效果瓶颈明确时才上。
3. **不解决数据本身脏的问题。** 源头文档解析错、版本乱，下游一律错——这是数据治理问题，不是 AI 问题。
4. **不直连业务数据库。** 所有数据访问走中台受控工具/API，**这是硬约束不是建议**。
5. **不承诺"零幻觉"。** 只能做到"无依据不开口 + 降级到原文 + 可溯源"。宣称零幻觉的材料一律不合格。
6. **不承担合规责任主体。** 平台给的是辅助，最终合规责任仍在业务流程与责任人。

## 8. 落地优先级建议

| 阶段 | 做什么 | 判定"可以进入下一阶段"的条件 | **B2B 现货平台承接点** |
|---|---|---|---|
| **阶段一 · 打地基** | 知识库 + 直击库 + 解析管道 + 权限收口 + 观测 | 评测集建成；直击库覆盖率与命中准确率有基线数据 | 五库拆分（智能客服 §20.2）；政策元数据建到**市级 jurisdiction**（政策解读 §13.1） |
| **阶段二 · 出价值** | 智能客服（高频问答）+ 一个垂直政策解读场景做透 | 自助解决率、首字延迟、转人工率有稳定周数据 | 客服 A/B1 意图 + 现货政策解读；**平台规则与法规分库并强制标注**（政策解读 §13.3） |
| **阶段三 · 接业务** | 单据查询类客服（打通中台工具网关）、材料初筛 | token 成本可控；越权测试用例全绿 | 九个白名单动作按风险分批（智能客服 §8.5）；**写操作一律转工单**（§8.6） |
| **阶段四 · 再扩展** | 微调 / 多智能体 / 跨系统流程自动化 | 前三个阶段的价值已被度量并认可 | 暂不排期 |

> 排序原则：**先做"效果可量化、风险可控"的，后做"价值高但打通成本大"的。** 反过来做，很容易在打通业务 API 上耗掉整个预算，什么价值都没证明。

### 8.1 ★ 三条与 B2B 主业咬合的硬约束（跨文档口径，改任何一篇都要同步）

这三条是"AI 平台"与"B2B 现货平台"真正的咬合点，分散在三篇文档里，此处集中对齐：

| # | 约束 | 出处 | 为什么是"咬合点" |
|---|---|---|---|
| 1 | **平台规则 ≠ 法规**，建库必须分开且输出强制标注 | 政策解读 §13.3 / 智能客服 §5.2.1、§20.2 | 只有同时懂监管合规与平台自家规则才会意识到；**闸门 B 查不出来**（引用是真的，性质是错的） |
| 2 | **撮合状态必须带时点输出**，不得把中间态说成终态 | 智能客服 §8.5.1 / `02-现货贸易/03-架构决策/13` | 直接承接 C 引擎内存一致性的三类风险（易失 / 时滞 / 回写失败） |
| 3 | **写操作不开放给 AI**，一律转工单走人工兜底 | 智能客服 §8.6 / `02-现货贸易/03-架构决策/12` | 涉及钱与货权，符合"必须补偿 vs 只需送达"的分工 |

> 这三条的共性：**都不是 AI 技术问题，是"AI 踩到业务要害"的问题**。面试或汇报时讲这三条，比讲"我们用了 RAG + Rerank"有力得多——因为它们无法从通用 AI 知识推导出来，只能来自对这个平台的真实理解。
