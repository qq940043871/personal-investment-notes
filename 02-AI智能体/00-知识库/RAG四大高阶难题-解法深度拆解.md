## 1. 多跳推理（Multi-hop）

### 1.1 难题本质

单次检索只能命中"语义相近"的 chunk，而**多跳问题的答案不在任何一个 chunk 里，要靠多个 chunk 拼出一条证据链**。

政策场景天然就是多跳的，三种典型形态：

| 形态 | 例子 | 断在哪 |
|---|---|---|
| 引用链 | "A 办法引用 B 标准，B 的有效期怎么算" | 查到 A，拿不回 A 引用的 B |
| 层级链 | "上位法 + 下位法 + 实施细则，到底听谁的" | 查到上位法，漏了下位法的变通 |
| 替代链 | "2019 年的奖补政策现在还适用吗" | 查到 2019 文件，不知道它已被 2025 文件替代 |

### 1.2 为什么难（面试要能说出"难在哪"，不是"我知道这个概念"）

1. **检索器是"单跳"的**：一个 query 对一坨 chunk 算相似度。第二跳需要的文档，字面往往和问题不相似（"B 办法"三个字在 A 条款里只是被提了一嘴），向量分不高，根本进不了候选池。
2. **跳数不固定**：查之前不知道要几轮，"查→读→再查"的迭代次数没法预设。
3. **断裂后模型会硬编**：拿不到第二跳证据，模型不会说"我还需要一份文件"，而是顺着第一跳的证据往下编——这是多跳场景幻觉的根因。

### 1.3 解法拆解（通用四招 → 项目怎么选）

**通用四招**（面试通用层，要能讲清各自适用边界）：

| 招 | 做法 | 适用 | 代价 |
|---|---|---|---|
| 查询分解 | 把复合问题拆成子问题逐个查 | 跳数少、可枚举 | 拆错子问题会带偏 |
| 迭代检索（Agentic RAG） | 查→读→再查，读到新引用就再发起检索 | 跳数不固定 | 多了循环、停止条件、成本 |
| 工具化检索 | 模型显式"还缺 X，去查 X" | 证据类型明确 | 依赖模型判断何时该查 |
| GraphRAG | 把引用/替代/上位关系建模成图，沿边游走 | 关系网络复杂 | 建图成本高、维护重 |

**项目的选择：不是"上最重的 GraphRAG"，而是"结构化场景用结构化手段"。**

### 1.4 本项目怎么接（口径：部分化解 + 三期预判，未完整落地）

政策场景的"跳"有一个通用场景没有的幸运——**引用关系、替代关系、位阶关系都是显式的、可穷举的**，不是靠语义推断出来的。所以我们的解法分两层：

**第一层：把"跳"压成元数据字段（实证/参与，在我落向量库范围内）**

- `supersedes` / `superseded_by` 字段把"替代链"从"向量碰运气"变成"代码层 join"——查 2019 文件时，顺着链一步就知道它已被 2025 文件替代。
- `level`（位阶）字段把"上位/下位"变成可过滤、可排序的枚举，不是让模型判断"谁大谁小"。
- 条款级定位符（`doc_number` + 条款号 + `chapter_path`）让"引用关系"能在代码层精确回指，而不是靠检索相似度模糊命中。

> 这一层是我落向量库时"格式与元数据衔接"的直接产物——**把多跳需要的"关系"在入库阶段就固化下来**，而不是等到检索时再让模型现推。

**第二层：完整的文件对比多跳 = 三期预判（未落地，团队编排侧）**

三期"文件对比（multihop）"方案已经设计好（见政策侧问答 I5），核心三步：

1. 槽位增加"对比对象 A/B"，两份文件**各自召回、各自过闸门 A**（权限前置不变）。
2. **复用同一套效力裁决规则**做冲突判定，输出效力说明——**不另起炉灶**。
3. 输出 schema 扩展为"差异项列表"，每项挂双边 basis，**每边都过闸门 B-1 引用核验**。

> 一句话原则：**新增能力新增的是规则和数据，不是模型的自由度。** 这是把"多跳"从"让模型多查几轮"变成"把跳的路径写成规则"的关键判断。

**为什么不急着上 GraphRAG**：政策场景的"跳"高度结构化（引用链、替代链、位阶链都显式存在），用元数据字段就够，不需要图数据库。**能说清"为什么不用 GraphRAG"比"我会 GraphRAG"更值钱**——这说明你是按场景选工具，不是追热点。

### 1.5 面试一句话版

> 政策场景天然是多跳的——上位法、下位法、实施细则三层嵌套，还带新旧替代链。我的处理分两层：先在落向量库时把引用关系压成元数据字段（`supersedes`/`level`/条款定位符），让"跳"从"向量碰运气"变成"代码层 join"；完整的文件对比多跳放三期，方案已设计好——两份文件各自召回、各自过闸门 A，冲突判定复用同一套效力裁决规则，不另起炉灶。我们没上 GraphRAG，因为政策场景的跳是显式结构，用字段就够，图是给隐式关系准备的。

**追问应对**：

| 追问 | 答 |
|---|---|
| 那你们现在做多跳了吗？ | 没落地。现在解决的是"单份文件内条款定位"+"跨文件的替代链/位阶链"（元数据层），完整的多文件对比是三期。诚实说边界。 |
| 为什么不上 GraphRAG？ | 见 §1.4。结构化场景用结构化手段，建图成本花在隐式关系上才值。 |

**依据指针**：`03-业务设计/政策解读Agent-通用设计.md` §3.1（元数据 16 字段）/ §3.3（版本时间轴）/ §11（三期 multihop）；`政策解读Agent-面试问题与回答要点.md` I4/I5。

## 2. 表格数值推理

### 2.1 难题本质

表格**解析对了、也召回了**，但让 LLM 对表格做数值计算（求和、比大小、多条件筛选）会错——**LLM 是语言模型，不是计算器**，它的"算术"是概率生成，不是精确运算。

### 2.2 为什么难

1. **"召回对但算不对"比"召回错"更隐蔽**：证据是对的，用户天然更容易信；错了还很难一眼看出。
2. 大数、多步运算、跨列聚合、带单位的换算，模型必错，且**错得理直气壮**（会一本正经给你一个错的数）。
3. 政策/电力场景有真实的数值问题：电价、补贴额度、容量上限、有效期年限——这些错一个就是"算错钱"。

### 2.3 解法拆解（三层，从根上不让模型心算）

| 层 | 做法 | 目的 |
|---|---|---|
| ① 结构化解耦 | 表格从"文本段落"变成"可解析的结构化数据"（HTML → DataFrame） | 让精确计算成为可能 |
| ② 计算外置 | 模型只生成计算表达式/结构化查询，由工具执行（代码/DataFrame/SQL），模型不心算 | 消除模型算术误差 |
| ③ 固定答案 | 关键数值问题走直击库 L1，答案逐字固定、不过生成模型 | 从根上不给心算机会 |

### 2.4 本项目怎么接（口径：解析侧实证 + 数值推理设计/团队）

**解析侧（我主责，实证）——这是"数值推理"的地基，但要诚实定性：**

MinerU 方案 3 的表格专项强化：
- **改 HTML 输出**（不是 Markdown）：保留 `rowspan`/`colspan` 语义，Markdown 里合并单元格语义会丢。
- **跨页续表合并**：检测相邻页表头重复 + 列宽相似度超阈值 → 自动合并、标"（续表）"。

这两步的意义是：表格从"一串被打断的文本"变成"结构完整、行列语义清楚的数据"，**一行代码就能进 DataFrame**。这是数值推理能做的地基——没有结构化的表格，精确计算无从谈起。

> ⚠️ **诚实口径**：解析改造的直接目标是 **RAG 召回和溯源**，不是给数值计算铺路。"解析 → DataFrame → 代码计算"这条链是事后反推出来的伏笔，面试时说"我解析阶段就把表格做成能进 DataFrame 的结构，这为数值推理铺了路"是成立的；但别说"我做解析就是为了让模型做数值计算"，那是过度声明。

**数值推理本身（设计，团队编排侧，未展开）——项目用更干脆的解法：**

我们**没有做"Code Interpreter 执行计算"这一层**。政策场景的数值问题（典型是电价），解法是：

- **电价必绑三要素**：文号 + 时点 + 地域，缺一不给具体价格——这本身就是"拒绝让模型瞎算"的设计。
- **答案走直击库 L1**：电价类问题命中直击库，答案逐字固定，**不过生成模型**，模型连心算的机会都没有。
- **执行周期校验**：电价一年一调、带执行周期，命中后还要核对周期是否覆盖 `on_date`，否则算错钱。

> 这是**场景选择，不是能力缺失**：政策场景的数值问题高度集中（电价、额度、上限），用"结构化元数据 + 直击库固定答案 + 时点绑定"就能解决，不需要引入"让模型写代码算"这套重机制。能说清"为什么我们不需要 Code Interpreter"，比"我会用 Code Interpreter"更见判断力。

### 2.5 面试一句话版

> 表格数值推理的坑是"召回对但算不对"——LLM 是语言模型不是计算器。我在解析侧做的事正好是它的地基：表格改 HTML 输出、跨页续表合并，让表格从文本段落变成能进 DataFrame 的结构化数据。但我们的场景里数值问题（电价）的解法更干脆——电价必须绑文号+时点+地域三要素，答案走直击库固定、不过生成模型，从根上不给模型心算的机会。我们没上 Code Interpreter，因为政策场景的数值问题高度集中，用结构化元数据+直击库就够了，引入代码执行是过度设计。

**追问应对**：

| 追问 | 答 |
|---|---|
| 那如果遇到真的需要算的问题呢？ | 政策场景里需要"算"的主要是电价/补贴，已经用直击库+三要素+执行周期校验解决了。真要引入计算，方向是"模型只生成表达式、工具执行"，模型不碰数字。 |
| 表格 HTML 化对数值推理到底帮了什么？ | 让表格从"文本"变"数据"——HTML 的 rowspan/colspan 保住了行列语义，才能进 DataFrame 精确取值；Markdown 会丢合并单元格语义，取出来就是错位的数据。 |

**依据指针**：`02-平台工程/minerU复杂PDF识别优化方案与选型分析.md` 方案 3；`03-业务设计/政策解读Agent-面试问题与回答要点.md` I2（电价三要素）；`03-业务设计/电力政策解读Agent-完整设计.md` §6.4（命中校验）。

## 3. 知识冲突 / 版本冲突 ★（最强差异化，最该花力气）

### 3.1 难题本质

RAG 库里存在**新旧文档、上下位文档、权威源打架**的情况，检索可能召回一个**过期版本或低效力版本**，还一本正经地解读。

### 3.2 为什么难（这题的"难"不在检索，在裁决）

1. **向量分不出新旧**：已废止文件和现行文件语义几乎一样（就是同一件事的新旧两个说法），相似度都高，向量检索天然分不出该用谁。
2. **模型默认"给啥说啥"**：召回一个已废止文件，模型不会主动问"这个还有效吗"，会直接当成现行文件解读。
3. **冲突的裁决有法定规则**：不是"相似度"能解决的，也不是"让模型判断"能解决的——它有一条明确的《立法法》适用顺序。

### 3.3 解法拆解（这是把"冲突消解"从"调 Prompt"升级为"确定性规则层"的完整方案）

**数据层 → 规则层 → 输出层，三道一起做：**

**① 数据层：按"事项"建版本时间轴，不孤立看单份文件**

```text
事项：高新技术企业认定奖补
 ├─ 2019  市人民政府〔2019〕8号      已废止（有效期届满）
 ├─ 2022  市科技局〔2022〕15号       被替代 ──┐
 └─ 2025  市科技局〔2025〕3号        现行有效 ←┘ （supersedes 指向上一条）
```

关键字段：`status`（现行/废止/被替代/修订/征求意见稿）、`supersedes`/`superseded_by`（替代链）、`expire_date`（届满日）。查询必须锚定时点 `on_date`——问"2023 年的政策"和"现在的政策"答案可能完全不同。

**② 规则层：时效过滤 + 位阶排序 + 冲突裁决，全走代码**

- **时效过滤**：剔除"未施行 / 已废止 / 已过期"的文档。注意第三种状态——**公布日 ≠ 施行日**，存在"已公布、尚未施行"，不建模这个状态必答错。
- **位阶排序**：位阶表（宪法 > 法律 > 行政法规 > 地方性法规 > 规章 > 规范性文件 > 内部文件），未知层级按最低处理（保守优先）。
- **冲突裁决**：把《立法法》写成 if/elif 函数（见 §3.4）。

**③ 输出层：冲突显式标注，不给胜出方时并列呈现**

检出冲突时输出"效力说明"（谁上位、谁现行、以谁为准）；判为"需有权机关裁决"时，**不得给胜出方**，并列呈现两份规定并说明应由谁裁。

### 3.4 核心：把《立法法》写成函数

```text
if a.level != b.level:
    → 上位法优于下位法                    # 规则一，绝对优先
elif a.issuer != b.issuer:
    → 不得自行裁定，标记「需有权机关裁决」  # 规则二/三仅限同一机关
else:
    if a 有变通权且覆盖 b 的变通事项:      → 变通法优先
    elif a.is_special and not b.is_special: → 特别法优先
    elif a.publish_date > b.publish_date:   → 新法优先
```

**关键是 `elif a.issuer != b.issuer` 那一行**——大量方案在这里直接套"新法优于旧法"，但它**只适用于同一机关制定的文件**，跨机关直接套用是**法律适用错误**。判为"需裁决"时如实说明"依《立法法》应由 XX 机关裁决"，并并列呈现两份规定。**承认"我不知道该用哪个"，比自信地选错负责得多。**

### 3.5 为什么这题最能拉开差距

别人讲"知识冲突"的解法通常是：**"调 Prompt 让模型注意新旧版本"**——这是概率手段，不可回归、随模型升级悄悄变。

我们的解法是：**两道纯代码闸门 + 效力裁决函数 + 版本时间轴**——这是把"冲突消解"从"业务细节"拔高成"通用 RAG 难题的确定性解法"：

| 维度 | 别人（Prompt） | 我们（规则层） |
|---|---|---|
| 可回归性 | 不可，一次模型升级就变 | 可离线回归、逐条写验收用例 |
| 稳定性 | 靠模型"自觉" | 规则固化，不随模型变 |
| 可解释性 | "我认为 A 更适用" | 能输出"依《立法法》第 X 条，上位法优先" |
| 失败模式 | 静默选错 | 判不了就明说"需有权机关裁决" |

### 3.6 本项目怎么接（口径：元数据衔接是我落库范围，裁决函数是团队/我参与判定清单）

- **版本元数据字段**（`status`/`supersedes`/`superseded_by`/`expire_date`/`level`）：我落向量库时"格式与元数据衔接"的直接产物，属于我的边界。
- **效力裁决函数 + 闸门实现**：团队编排侧，我参与的是**规则层判定清单的定义**（§12 那 11 项判定）。
- **B2B 独有红线（平台规则 vs 法规）**：`doc_type` 三值（`legal`/`platform_rule`/`internal`）——平台自定的交易规则是**合同契约不是法规**，文风与法规极像（都有"第 X 条""应当""不得"），模型看文本分不出，必须靠元数据在建库阶段分开并强制标注。这是"知识冲突"的一种隐蔽变体：**引用是真的、性质是错的，闸门 B 查不出来**。

### 3.7 面试一句话版

> 知识冲突在政策场景是高频也是致命的——引用一个已废止文件等于误导。别人的做法是调 Prompt 让模型注意新旧版本，我们直接做成确定性规则：数据层按事项建版本时间轴（status/supersedes 链），规则层做时效过滤+位阶排序+冲突裁决，其中冲突裁决是把《立法法》写成了函数——上位法优于下位法绝对优先，但"新法优于旧法"只适用同一机关，跨机关冲突我们判"需有权机关裁决"、并列呈现两份规定、不给胜出方。这套比 Prompt 高一个层级：可回归、不会随模型升级悄悄变。还有一个隐蔽变体——平台自己的交易规则不是法规是合同契约，文风和法规一样，模型分不出，我们在建库阶段就用 doc_type 字段强制分开。

**追问应对**：

| 追问 | 答 |
|---|---|
| "新法优于旧法"哪错了？ | 它只适用**同一机关**制定的文件。跨机关（地方性法规 vs 部门规章）直接套用是法律适用错误，正确做法是标"需有权机关裁决"。 |
| 冲突你亲自实现的吗？ | 效力裁决函数和闸门是团队落地的，我参与的是规则层判定清单的定义；版本元数据字段（status/supersedes）是我落向量库时做的衔接。边界如实说。 |

## 4. 评测难题

### 4.1 难题本质

RAG 的评测比传统 NLP 难一个数量级：**答案不唯一、端到端"对不对"太粗、Faithfulness（忠实度）难自动测、LLM-as-a-judge 有偏差需要校准**。Dify 官方都承认"没有端到端自动化评估体系"。

### 4.2 为什么难

1. **端到端总分太粗**：一个"答错了"可能出在检索（没召回）、生成（召回了没用对）、引用（引了个不支持的）三层的任何一层，压成一个总分就失去了定位能力。
2. **检索层和生成层是两回事**："证据有没有召回"（Recall@K）和"答案有没有编造"（Faithfulness）不能用一个指标糊过去。
3. **解析侧还有隐蔽故障**："文字对但顺序错"——每个字都对、语义是错的、**不报错、还污染召回**。这比解析失败更危险，因为失败你还能看见。

### 4.3 解法拆解（分层，每一层各管一件事）

**① 解析侧四层验收（我主责，实证）**

四类指标**分开记**，不压成一个"解析准确率"：

| 层 | 指标 | 抓什么错 |
|---|---|---|
| 文字 | 字符准确率 | 漏字、错字 |
| 顺序 | 编辑距离（切分后逐段比对） | **"文字对但顺序错"**（最隐蔽） |
| 结构 | Table-TEDS / Formula-CDM | 表格结构还原度、公式结构 |
| 定位 | 页码/坐标人工比对 | 能不能回到原页原区域 |

配套：自建评测集（200–500 页代表性文档人工标注）+ 坏例回流（低置信度样本自动进标注队列 → 补训练数据 → 微调）。**"没有回归集的解析器升级等于赌博"。**

**② 检索生成侧分层指标（设计/团队）**

| 指标 | 查哪层 | 说明 |
|---|---|---|
| Recall@K | 检索 | 正确证据进没进前 K |
| Precision@K | 检索 | 候选里的噪声 |
| MRR | 检索 | 第一条正确证据排多前 |
| Faithfulness | 生成 | 每个事实能否被上下文支持 |

**核心纪律：不要把所有指标压成一个总分**——指标冲突恰恰是定位信号：Recall 高但答案错 = 生成层的问题（证据找回来了但没用对），不是检索的锅。

**③ 任务/轨迹/成本三层评估（政策 Agent 设计）**

- **任务层**：四个硬指标——引用真实率 100%、越权拦截率 100%、时效正确率 ≥99.5%、该拒就拒率 ≥95%（这些是**设计目标**，不是已上线实测值）。
- **轨迹层**：`trace_id` 串起召回清单+分数、位阶判定、引用核验结果、闸门 B 结果、降级档位——**一次答错能定位到是哪一步坏的**。
- **成本层**：直击命中率、平均延迟下降、月度淘汰率。

**④ 评测集怎么建（Q22 的完整版）**

- 每题标注三样：**问题 + 参考答案 + 证据位置**（哪份文档/哪页/哪个 chunk），缺证据位置，评测就退化成了"看答案像不像"。
- 题型覆盖四类：**直接事实 / 改写 / 多跳 / 无答案**——尤其"无答案"类，漏了它系统就会变成"该拒不拒"。
- 数据集分版本：开发 / 回归 / 保留集分开，**避免调参时把测试集当训练集**。
- LLM 可辅助生成初稿，但**必须人工核对**（LLM-as-a-judge 有偏差，不盲信）。

### 4.4 本项目怎么接（口径：解析侧实证 + 检索生成侧设计/团队）

- **解析侧四层验收 + 自建评测集 + 坏例回流**：我主责（MinerU 方案 7）。
- **检索生成侧分层指标 + 三层评估 + 四个硬指标**：设计/团队推进，我参与规则层判定清单（判定的可回归性正是评测能落地的前提）。

> 一个能升华的点：政策场景的评测有一个开放域没有的**红利**——"对错可判"。引用是否真实（文号/条款存在性）、时效是否有效、是否越权，都是**确定性判定**，可以离线全量回归，不需要 LLM-as-a-judge。**把"难评测"的场景变成"可穷举评测"的场景，本身就是这个方案的价值。** 这就是为什么我们的四个硬指标能定 100%，而不是"大约 95%"——红线场景的验收标准是"必须全对"，不是"尽量对"。

### 4.5 面试一句话版

> RAG 评测难在"端到端答案对不对"太粗。我的做法是分层：解析侧四类指标分开记（文字/顺序/结构/定位），因为最隐蔽的故障是"文字对但顺序错"——每个字都对、语义是错的、还不报错；检索生成侧不把 Recall@K 和 Faithfulness 压成一个总分，前者查检索、后者查生成，指标冲突恰恰告诉你该修哪一段；再往上加轨迹层——trace_id 串起召回清单、引用核验、降级档位，一次答错能定位到具体哪一步坏。评测集必须带证据位置，题型覆盖"无答案"。政策场景还有个红利：引用真伪、时效、越权都是确定性判定，可离线全量回归，不需要 LLM-as-a-judge，所以我们敢把红线指标定成 100% 而不是"大约 95%"。

**追问应对**：

| 追问 | 答 |
|---|---|
| 引用真实率 100%，你们真测出来了吗？ | 这是验收**红线**，不是已上线实测值。核验逻辑本身是代码判定，可离线全量回归；线上真实率要看样本积累，还在标定。我不报没测过的数字。 |
| LLM-as-a-judge 你们用了吗？ | 政策场景能用确定性判定替代大部分——引用/时效/越权都可穷举比对，不需要 judge；judge 只在"解读是否恰当"这类软性维度上有用，且要人工校准。 |
