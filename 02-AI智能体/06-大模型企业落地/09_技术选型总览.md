## 一、核心选型复盘（真实参与）

### 1.1 平台底座：Dify vs 自研

| 维度 | Dify（低代码平台） | 自研（FastAPI + LangChain 等） |
|------|-------------------|------------------------------|
| 前期开发效率 | 可视化编排，出活快 | 需自建，前期慢 |
| 定制化能力 | 受平台能力约束 | 完全可控 |
| 数据与安全 | 需评估部署形态与数据边界 | 可完整内网化 |
| 运维成本 | 平台本身需维护 | 全栈自维护 |
| 团队适配 | 业务 / 非技术亦可用 | 依赖研发投入 |
| 与既有体系集成 | 需适配 | 可与 Java 后端深度集成 |

**本人的选型结论（判断，非落地结果）**：

- **前期验证 / 快速试错**阶段：可用 Dify 提速，先跑通链路；
- 涉及**涉密数据、深度定制、与既有 Java 后端体系集成**时：倾向**自研（或以自研为主 + 平台辅助）**；
- 实际项目中，本人负责该**选型对比与结论输出**（平台底座），后续落地由团队推进。

### 1.2 数据敏感度分层通道策略

**核心原则：数据敏感度决定模型通道。**

| 数据敏感度 | 通道 | 取舍 |
|-----------|------|------|
| 通用咨询 / 公开知识 | 第三方大模型 API | 能力强、成本可控；数据出境需评估 |
| 涉密 / 内部数据 | 内网私有化部署（vLLM 等候选） | 数据不出内网；牺牲部分能力与成本 |
| 混合场景 | 路由 / 脱敏后分流 | 敏感字段脱敏或本地处理 |

**判断依据**：数据是否出境、合规要求、能力要求、成本、时效。

**本人工作**：完成该**分层通道判断**；**未做生产级 vLLM / Ollama / Qdrant 部署**。

### 1.3 文档解析链路选型：MinerU（本人参与）

**选择理由**：把**多格式文档统一成结构化 Markdown**，降低下游向量化的格式耦合。

| 环节 | 选择 | 关注点 |
|------|------|--------|
| 文档解析 | MinerU | 多格式（PDF/Word/Excel/PPT/扫描件）→ Markdown，表格/公式/版面结构保真 |
| 分块与元数据 | 结构化分块 | 元数据可对齐，便于检索过滤 |
| 向量化与入库 | Embedding + 向量库 | 统一下游入库格式，减少格式差异耦合 |

**本人负责**：批量解析调度、失败兜底、下游入库格式衔接（详见 [`./02_商品知识库与智能检索.md`](./02_商品知识库与智能检索.md)）。

## 二、选型评估维度

### 2.1 选型评估维度

| 维度 | 评估要点 |
|------|---------|
| 能力匹配 | 能否满足业务场景需求 |
| 成本 | API费用/硬件成本/运维成本 |
| 性能 | 响应速度/并发能力/准确率 |
| 安全合规 | 数据安全/隐私保护/合规要求 |
| 运维难度 | 部署复杂度/监控告警/容灾备份 |
| 团队能力 | 学习曲线/人员储备 |
| 生态支持 | 社区活跃度/技术支持/更新频率 |
