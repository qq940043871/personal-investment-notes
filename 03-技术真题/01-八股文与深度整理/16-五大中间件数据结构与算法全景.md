## 00 一页纸结论

**一句话主线**：数据放在哪（内存 / 磁盘 / 对象）决定了结构，结构决定了算法，算法决定了能扛什么场景，而这一切的边界条件都是操作系统给的。

| 中间件 | 主导数据结构 | 主导算法 | 典型场景 | 量级【量级】 | 最依赖的 OS 能力 |
|---|---|---|---|---|---|
| **MySQL / InnoDB** | B+ 树（16KB 页）、Buffer Pool、redo/undo 日志 | 页内二分、WAL + LSN、MVCC 可见性判定、next-key lock、代价优化 | 强一致事务、点查 + 范围 + 关联、可更新 | 点查 µs~ms；单机简单查询 1w~10w QPS；写 几千~几万 TPS | `fsync` / `O_DIRECT` / 4K 对齐 / readahead |
| **Redis** | dict（双哈希 + 渐进式 rehash）、跳表、listpack/quicklist、intset、HLL、rax | 哈希分桶、跳表随机层高、调和平均、采样淘汰、CRC16 分槽 | 亚毫秒缓存、排行榜、计数、限流、锁、轻量消息 | GET/SET 10w QPS 级、P99 亚毫秒 | `epoll` / `fork` COW / 页表 / 禁 THP |
| **Elasticsearch / Lucene** | 倒排索引、FST、Doc Values（列式）、BKD 树、不可变 segment | BM25、倒排表交集（跳表 + 堆 + WAND）、TopK 最小堆、段合并 | 全文检索、多条件过滤、聚合、日志时序 | 写入 万~十万 docs/s/分片；查询 几十~几百 ms；NRT 1s | **mmap / page cache**、`mlock`、禁 swap、fd |
| **MongoDB / WiredTiger** | B 树、BSON 文档、checkpoint 快照、journal、capped oplog | COW 页、snapshot isolation、多数派提交、chunk 分裂 | 半结构化文档、schema 演进、水平扩展、高写入 | 点查 0.1~1ms；写 几千~几万 docs/s | 自管 cache、XFS、禁 THP、小 readahead、NUMA |
| **MinIO** | 扁平命名空间、纠删集、RS 分片、`xl.meta`、bitrot 校验 | Reed–Solomon 编解码、quorum 读写、一致性哈希选集、后台 heal | 海量大对象、S3 兼容、备份归档、一次写多次读 | 吞吐 GB/s 级（大对象）；空间利用率 K/N | `O_DIRECT` + 4K 对齐、XFS、JBOD、`sendfile` |

> **表格口径**：以上是**通用原理对照表，不是本人系统清单**。实际使用 = MySQL / Redis / ES / MinIO；MongoDB 一栏仅为原理对照，本项目未使用。

**三条判据（后面反复用）**

1. **随机 IO 贵、顺序 IO 便宜** → 一切结构都在把随机变顺序：B+ 树用有序叶子、WAL 用追加、segment 用不可变、MinIO 用流式分片。
2. **内存易失、磁盘可信但慢** → 一切持久化都在做「追加日志 + 校验 + 周期性合并」：redo / AOF / translog / journal / `xl.meta` 是同一件事的五个名字。
3. **内核态切换、锁竞争、上下文切换贵** → 一切高性能都在做「批处理 / 零拷贝 / 用户态缓存 / 单线程或分片无锁」：Redis 单线程、ES 靠 page cache、MinIO 靠 `O_DIRECT`、MySQL 靠 group commit。

> **面试第一句话建议这么说**：「这五个不是一个维度的东西，MySQL 和 MongoDB 是**要把数据存对**，Redis 是**要把数据放在离 CPU 最近的地方**，ES 是**要按内容找数据**，MinIO 是**要按字节流存大文件**。结构差异的根因是查询谓词形态不同，不是谁比谁先进。」
>
> 讲这句前先补一句「其中 MongoDB 我们没上，我是拿它做结构对照的」——否则很容易被顺势追问「那你们分片键怎么选的」「WT cache 调过没」，接下来就得靠编故事圆了。

### 1.1 约束一：分层存储的速度差是数量级的，不是百分比

CPU 看内存是「隔壁」，看磁盘是「跨城」。更狠的是**同一块盘上随机读和顺序读的差距**：机械盘随机读要寻道（~5–10 ms），顺序读能跑满 100–200 MB/s；NVMe 把随机延迟压到 ~50–100 µs，但顺序带宽仍是 3–7 GB/s。所以：

- 数据结构的第一目标不是「时间复杂度 O(log n) 比 O(n) 好看」，而是 **减少随机 IO 的次数**。B+ 树 3~4 层能扛上亿行，就是因为把「27 次随机读的二叉树」压成了「3 次」。
- 写路径的第一目标不是「写得快」，而是 **把随机写改写成顺序追加**。这就是 WAL 存在的唯一理由。

### 1.2 约束二：OS 用 4KB 页管一切，缓存权归谁是个设计选择

内核以 4KB 页管理内存与块设备，读文件先进 page cache，`read()` 可能只是内存拷贝；写文件默认只是写进 page cache 就返回，真正的落盘靠内核 writeback 或应用显式 `fsync()`。于是每个中间件都要回答一个问题：

> **缓存交给 OS，还是自己管？**

- 交给 OS（ES/Lucene 用 `mmap`）：省一次拷贝、热数据自动缓存、重启后缓存还在；代价是内存不受控、被别的进程挤掉、swap 一来直接雪崩。
- 自己管（MySQL Buffer Pool、WiredTiger cache、`O_DIRECT`）：淘汰策略可控、不会双缓存浪费、能按业务语义预读；代价是要自己实现 LRU、checkpoint、预热。
- 完全不靠磁盘缓存（Redis）：数据本来就在内存，OS 只在 RDB/AOF 时帮忙。

**这三种态度是本文最有价值的横向对照**（§07.2 图 7）。顺带一提，MySQL 的 **double write buffer** 就是被「OS 4KB 页 vs InnoDB 16KB 页」逼出来的：断电时一个 16KB 页可能只写成功前 4KB（partial page write），redo log 记的是页内变更，在残缺页上重放会越修越坏。所以先顺序写一份完整页镜像到 doublewrite 区，再写真实位置。

### 1.3 约束三：陷内核、切上下文、抢锁，都要付 µs 级门票

一次 `read()`/`write()` 是系统调用，一次线程切换要保存恢复寄存器与 TLB，多核抢一把锁会引发缓存行在核间弹跳。**当单次操作本身只有几 µs 时，这些开销反而成了主体**。于是：

| 通用动作 | 躲的是什么 | 谁在用 |
|---|---|---|
| **顺序化 / 追加** | 随机 IO、寻道 | B+ 树叶子链、redo、AOF、translog、journal、MinIO 分片流 |
| **不可变 + 后台合并** | 原地更新的锁与随机写 | ES segment、WT checkpoint、Redis AOF rewrite、RDB、MinIO heal |
| **索引换查找** | 全表 / 全盘扫 | B+ 树、倒排、FST、BKD、dict、跳表 |
| **批处理 / 组提交** | 每次 fsync / 每次 syscall | group commit、bulk、pipeline、multipart |
| **零拷贝 / mmap** | 内核态↔用户态拷贝 | ES mmap、MinIO `sendfile`、Redis `fork` COW |
| **单线程或分片无锁** | 锁竞争、上下文切换 | Redis 命令单线程、Cluster 分槽、MinIO 分 set、Mongo 分片 |

### 1.4 约束四：内存易失，网络不可靠

进程被 `kill -9`、机器掉电、盘上一块扇区静默损坏（bitrot）、网络分区后两边都认为自己是主 —— 这些不是异常，是常态假设。于是：

- **持久性**：日志必须 `fsync` 才能算「已提交」，所以 `fsync` 次数直接决定写 TPS 上限，组提交（group commit）就是把多个事务攒成一次 `fsync`。
- **完整性**：校验和（InnoDB page checksum、MinIO HighwayHash、WT checksum）用来发现静默损坏；多副本 / 纠删码用来修复。
- **一致性**：quorum、任期号（term/epoch）、栅栏令牌，防止脑裂后的旧主继续写。

> **这一节要背下来的就一句**：「MySQL 的 redo、Redis 的 AOF、ES 的 translog、Mongo 的 journal、MinIO 的 xl.meta，本质是同一条 WAL 不变量的五种实现。」

## 02 MySQL／InnoDB：把随机 IO 变成顺序 IO 的账本

### 2.1 场景与要解决的问题

**场景**：钱、货权、合同状态这类**不能错、要能改、要能查范围、要能多表关联**的数据。ACID 是硬需求，磁盘是最终真相，内存只是加速器。

**三个互相打架的目标**：① 点查要快（希望索引）；② 范围/排序/关联要快（希望有序）；③ 写入要快且崩溃不丢（希望追加）。B+ 树解决前两个，WAL 解决第三个，Buffer Pool 把两者粘起来。

### 2.2 用了哪些数据结构与算法

| 层 | 数据结构 | 关键算法 / 机制 | 解决什么 |
|---|---|---|---|
| 索引 | **B+ 树**（聚簇 = 主键 + 整行；二级 = 列 + 主键） | 根节点二分下降、页内 **slot 数组二分 + ≤8 条记录链比较**、叶子双向链表右扫 | 点查 H 次页读；范围查询退化为顺序扫 |
| 页 | **16KB 页**（File Header / Page Header / Infimum+Supremum / User Records / Page Directory / Trailer） | 槽位稀疏索引、记录单向链表、页内变长字段 | 一次 IO 拿一整页，摊薄随机 IO |
| 空间 | 段 / 区（extent 1MB = 64 页）/ 页 | 区分配、页分裂与合并 | 让相邻页物理相邻，配合 readahead |
| 内存 | **Buffer Pool**（hash 表按 `space_id+page_no` 定位 + LRU 链表） | **midpoint insertion LRU**：链表按 5:3 分 young/old（old 默认 37%），新页插 midpoint，`innodb_old_blocks_time` 防全表扫污染；自适应 flushing 刷脏 | 热点常驻，避免一次大扫描把缓存冲光 |
| 持久 | **redo log**（环形追加文件 + LSN）、**undo log**（版本链 + rollback segment）、**binlog**（server 层逻辑日志） | **WAL**（先日志后页）、checkpoint 按 LSN 推进、崩溃重放、**两阶段提交**（redo prepare → binlog → redo commit） | 崩溃不丢；主从一致；MVCC 与回滚 |
| 并发 | **MVCC ReadView**（`m_ids` / `min_trx_id` / `max_trx_id` / `creator_trx_id`）+ undo 版本链 | 可见性判定：`trx_id < min` 可见；`>= max` 不可见；在 `m_ids` 中不可见，否则可见；不可见就沿版本链回退 | 读不阻塞写，写不阻塞读 |
| 锁 | 行锁（本质是**索引项上的锁**）、gap lock、next-key lock、意向锁 | **wait-for graph DFS 死锁检测**（或超时回滚）、RR 下用 next-key lock 封住区间防幻读 | 有序列结构天然能做区间锁 |
| 写优化 | **change buffer**（二级非唯一索引的变更缓存）、**double write buffer**、AHI 自适应哈希 | 唯一索引必须读页校验，故 change buffer 只缓存非唯一二级索引；AHI 对高频访问页建哈希 | 减少随机读、防部分写、热点再加速 |
| 执行 | 代价优化器、filesort、临时表、hash join（8.0.18+） | join 顺序枚举（贪心 + 动态规划）、cardinality 采样估计、快排 + 多路归并、hash join 构建/探测 | 把 SQL 翻译成尽量少的结构动作 |

**为什么页恰好 16KB**：不是玄学，是三方的公约数 —— ① OS 页 4KB 的整数倍，`O_DIRECT` 时对齐不跨额外页；② 一次 IO 足够多记录，扇出大（非叶只存 key + 4B 页号，16KB 可塞 ~900–1200 项 → 3 层就能覆盖上亿行）；③ 再大会放大「只读一行却搬 64KB」的浪费与 Buffer Pool 污染。同目录 `15-MySQL又矮又胖` 有完整算术，这里不重复。

### 2.3 为什么是 B+ 树，而不是别的

| 候选 | 为什么被淘汰 | 关键代价算式 |
|---|---|---|
| 哈希表 | 等值 O(1) 很香，但 `>` `BETWEEN` `ORDER BY` 直接失效；扩容要全表重哈希 | 范围查询退化为全表扫 O(N) |
| 二叉搜索树 / 红黑树 | 每节点只有 2 个分支，1 亿行要 ~27 层 = 27 次随机 IO | HDD 上 27 × 8ms ≈ 216 ms/次点查 |
| 跳表 | 内存里很好（Redis 在用），但节点大小不贴磁盘页、指针不局部，预读失效 | 每层一次随机 IO，且无法用页批量 |
| B 树 | 非叶也存整行 → 扇出骤降（~80），树高 5 层；范围查询要中序遍历跨层 | 多 2 次随机 IO + 路径不稳定 |
| **LSM 树** | 写吞吐更强，但读放大（多层查找 + bloom）、后台 compaction 占 IO、范围更新与事务实现复杂 | 读放大 10–50×；InnoDB 定位是**读写均衡 OLTP**，不是写吞吐怪兽 |
| **B+ 树（选中）** | 非叶纯导航、叶子有序且双向链表，点查 H 次、范围 H + 顺序扫 | 1 亿行 H≈3，根常驻内存 → 实际 2~3 次 IO |

**为什么 redo 是环形追加而不是也用 B+ 树**：因为写一条事务如果先去改 B+ 树页，可能触发页分裂、多个随机位置的脏页回写；而追加日志只有一次顺序写 + 一次 `fsync`。**日志记的是「输入」，页记的是「状态」**——把状态更新推迟到 checkpoint/刷脏，就把随机写摊平了。这正是 §01.3 那条不变量。

**为什么 undo 用版本链而不是直接覆盖**：MVCC 要求「旧版本还在」，于是每次更新把旧值串进 undo 链，行的隐藏列 `DB_ROLL_PTR` 指向它。代价是长事务会让 purge 线程追不上、undo 表空间膨胀 —— 这是「读不阻塞写」的账单。

**崩溃恢复矩阵**（面试常追问「写到哪一步断电」）：

| 断电时刻 | 恢复动作 | 结果 |
|---|---|---|
| redo 未落盘 | 事务未返回成功，直接丢弃 | 一致 |
| redo prepare 已落、binlog 未写 | 恢复时发现 XID 无对应 binlog → 回滚 | 主从一致 |
| binlog 已写、redo 未 commit | 恢复时补齐 commit | 一致 |
| 已返回成功、脏页未刷 | 重放 redo 重建脏页 | 不丢 |

### 2.5 性能指标【量级】

| 指标 | 量级 | 前提 / 瓶颈 |
|---|---|---|
| 主键点查（Buffer Pool 命中） | 几十 µs ~ 0.2 ms | 纯内存，瓶颈在 SQL 解析 + 网络 |
| 主键点查（未命中，NVMe / HDD） | 0.1~0.3 ms / 5~10 ms | 2~3 次随机 IO |
| 单机简单查询 QPS | 1w ~ 10w | 短事务、命中率 >99%、连接池合理、无复杂 join |
| 写 TPS | 几千 ~ 几万 | **受 fsync 次数支配**：NVMe + group commit + `sync_binlog`/`innodb_flush_log_at_trx_commit` 折中 |
| B+ 树高度 | 3~4 层覆盖千万~上亿行 | 扇出 ~1000 |
| Buffer Pool 命中率 | 生产目标 >99% | 掉到 95% 以下延迟会陡增 |
| 单表容量 | 千万~亿级开始考虑分区/分库 | **不是硬阈值**，取决于索引数量、行宽、查询形态 |

**速算**：写 TPS ≈ `fsync 能力 × 组提交批量`。NVMe 单次 fsync ~0.1–0.3 ms，若一个 fsync 批次攒 20 个事务，理论上限就是几千~上万 TPS。这也解释了为什么「开了双一（`sync_binlog=1` + `innodb_flush_log_at_trx_commit=1`）」的库写性能会掉一个档：两个文件都要各自 fsync。

### 2.6 与操作系统的关联，以及为什么这么设计

| OS 能力 | InnoDB 的用法 | 为什么这么设计 / 反例 |
|---|---|---|
| **`O_DIRECT`** | 数据文件绕过 page cache，自己用 Buffer Pool 管 | 若走默认 buffered IO，同一页在内核 page cache 和 Buffer Pool 各存一份 → 内存翻倍、淘汰策略互相打架 |
| **`fsync` / `fdatasync`** | redo、binlog 提交时强制落盘 | 不 fsync 就等于把数据托付给内核 writeback，掉电即丢；但每次调用 ~0.1–10 ms，所以必须组提交 |
| **4KB 页 / 块对齐** | 页 16KB = 4 个 OS 页 | 不对齐时一次 16KB 写会跨 5 个物理页 → 断电部分写 → **double write** 就是补这个洞 |
| **readahead** | 区（1MB 连续 64 页）配合线性预读 | 范围扫描提前把相邻页拉进 Buffer Pool，把 N 次随机读变成顺序读 |
| **文件系统** | 推荐 XFS/ext4，关 `atime`，`swappiness` 调低 | 大文件 + 高并发 IO 下 XFS 的 extent 分配更稳；swap 命中等于把 µs 级内存访问换成 ms 级磁盘 |
| **NUMA / 内存** | Buffer Pool 大时注意内存局部性、`innodb_buffer_pool_instances` 分片 | 单实例巨大 LRU 链表会有 mutex 争用；NUMA 远端内存访问延迟更高 |
| **线程与调度** | 后台 purge / flush / read-ahead 线程分离 | 把重 IO 从用户线程挪走，避免前台延迟毛刺 |

> **一句话答「为什么这么设计」**：「因为磁盘是真相但随机 IO 太贵，所以 InnoDB 把**状态**放在 B+ 树里慢慢刷，把**输入**放在 redo 里顺序追加，用户等的是一次 fsync 而不是整棵树落盘；`O_DIRECT` + 16KB 页是为了不让 OS 再插一层不可控的缓存。」

## 03 Redis：把全部数据结构塞进 CPU 缓存行

### 3.1 场景与要解决的问题

**场景**：会话、热点缓存、计数器、排行榜、限流、分布式锁、轻量消息队列。共同点是**数据量能放进内存、访问要亚毫秒、一次操作只碰一两个 key、不需要多表关联**。

**要解决的不是「存得下」，而是「每次操作少付多少 CPU 与 syscall」**。当一次 GET 本身只有几 µs，一个指针追逐造成的 cache miss、一次线程切换、一次系统调用都会成为主要成本。所以 Redis 的每条设计都在做同一件事：**减少内存碎片、减少指针追逐、减少锁、减少 syscall**。

### 3.2 用了哪些数据结构与算法（逐个说透）

**① SDS（Simple Dynamic String）**：`len` / `alloc` / `flags` / `buf[]` 头部 + 字节数组。相比 C 字符串：O(1) 取长度、二进制安全（不靠 `\0` 截断）、自动扩容且预留空间（小于 1MB 翻倍，超过按 1MB 增量），避免每次 append 都 realloc。**为什么**：缓存 key/value 绝大多数是短字符串，一次 `strlen` 的 O(n) 与一次 realloc 都是无谓成本。

**② dict（哈希表）**：两个 `dictht` 数组 `ht[0]` / `ht[1]`，链地址法解决冲突，哈希函数用 SipHash 系（抗哈希洪泛攻击）。负载因子 ≥1（无后台子进程时）或 ≥5（有 BGSAVE/BGREWRITE 时，避免 fork 期间扩容放大 COW）触发扩容到 ≥2× 的 2 的幂。

**渐进式 rehash 是这里的重点算法**：一次性搬完整张表会造成秒级停顿（单线程，整个世界都卡住）。做法是把搬运摊到每次增删查改上：维护 `rehashidx`，每处理一个请求就顺带把 `ht[0]` 的一个桶迁到 `ht[1]`，查找时两张表都查、插入只进 `ht[1]`，直到搬完再把 `ht[1]` 换成正表。**这就是「把一次大停顿换成 N 次微小成本」**，和 LSM 的增量 compaction、ES 的增量 merge 是同一类思想。

**③ 跳表（skiplist）**：多层有序链表，每个节点随机层高（Redis 用 `p = 0.25`，最大 32 层，平均层数 1.33），上层是下层的「快进索引」。查找/插入/删除 O(log n)，且**天然支持按 score 范围遍历**（`ZRANGEBYSCORE`、排行榜分页），层与层之间用 `span` 记录跨度，所以 `ZRANK` 求排名也是 O(log n)。

**为什么 zset 不用红黑树或 B+ 树**：① 范围查询要中序遍历、实现复杂，跳表直接从底层链表右扫；② 跳表插入只改局部指针，不用旋转再平衡；③ 内存里没有「页」的概念，B+ 树的胖节点优势消失；④ 实现简单到能一眼审完，对单线程系统尤其重要。代价是**指针多、内存开销比连续结构大**，所以元素少时反而先用 listpack。

**④ listpack / quicklist**：listpack（Redis 7 起全面替代 ziplist）把一组 entry 连续排在一块内存里，每 entry 用变长编码记长度与类型，支持反向遍历；去掉了 ziplist 的「级联更新」隐患。quicklist 则是「双向链表 + 每个节点一个 listpack」，因为一整块连续内存太大时插入会引发大范围 memmove。**这是一次典型的分层折中：连续内存赢局部性，分段赢修改成本。**

**⑤ intset**：有序整数数组 + 二分查找，元素类型统一为 int16/int32/int64，插入更大类型时整体升级（只升不降）。全是小整数时，比哈希表省掉所有指针与桶开销。

**⑥ 概率结构**：
- **HyperLogLog**：把元素哈希后分到 16384 个寄存器，记录前导零个数的最大值，用**调和平均**（抗极端大值）估算基数，标准误差 `1.04 / √16384 ≈ 0.81%`，内存恒定 12KB。**为什么用调和平均而不是算术平均**：单个超大前导零会把算术均值拉飞，调和平均对离群值不敏感。
- **Bitmap**：直接在 SDS 的字节数组上做位运算，日活/签到用 1 bit/用户。
- **GEO**：把经纬度编成 52 位 geohash 整数当 score 存进 zset，复用跳表做附近搜索，不新造索引结构。

**⑦ 过期与淘汰**：`expires` 字典单独存 key→过期时间。
- **惰性删除**：访问时才发现过期才删 —— 省 CPU，但可能留垃圾。
- **定期删除**：每秒约 10 轮（`server.hz`），每轮随机采样若干 key，删掉过期的；若过期比例 >25% 就再来一轮，同时设时间上限（约 25ms）防止卡死主线程。**这是带预算的概率算法**，不是精确扫描。
- **内存淘汰**：`maxmemory` 满时按策略（allkeys-lru / allkeys-lfu / volatile-ttl / noeviction 等）从**随机采样**（默认 5 个）里挑最差的删。为什么不维护全局精确 LRU 链表？因为每次访问都要移动链表节点，在 10w QPS 下这个开销比「少淘汰准一点」贵得多。LFU 用 24 位字段里的 8 位对数计数器 + 16 位衰减时间，用概率递增模拟访问频次。

**⑧ 持久化**：RDB = `fork()` 子进程利用 **COW（写时复制）** 拍快照；AOF = 追加写命令 + `fsync` 策略（always / everysec / no）+ AOF rewrite（子进程重写 + 期间增量写入重写缓冲）。7.0 起 multi-part AOF 把 base + incr 分开，减少重写放大。

**⑨ 集群与网络**：
- **单线程事件循环 + `epoll`**：命令执行串行，避免锁与上下文切换；6.0+ 的 I/O 多线程只分担**网络读写与协议解析**，命令执行仍然单线程。
- **CRC16 分槽**：`slot = CRC16(key) mod 16384`，`{hash_tag}` 让多个 key 落到同一槽以支持多键操作。客户端能自己算槽 → 无需中心查表、无需一致性哈希环的虚拟节点迁移复杂度。

### 3.3 为什么这么选：把被淘汰的方案摆出来

| 决策点 | 选了 | 没选 | 原因 |
|---|---|---|---|
| 索引 | 哈希表 O(1) | 树 O(log n) | 内存里不需要「页」，log n 的常数和指针追逐都是纯浪费 |
| 有序集合 | 跳表 | 红黑树 / B+ 树 | 范围遍历 + 实现简单 + 插入只改局部指针 |
| 小对象编码 | 连续内存 listpack | 一个个 `robj` + 指针 | 一次 cache line 能装多个元素；省掉指针本身占的内存 |
| 命令执行 | 单线程 | 多线程 + 锁 | 瓶颈在网络与内存带宽，不在 CPU；加锁反而引入缓存行弹跳 |
| rehash | 渐进式 | 一次性 | 单线程下「停 1 秒」= 全部请求超时 |
| 基数统计 | HLL | HashSet 精确计数 | 12KB 恒定内存 vs 亿级 key 的 GB 级内存，误差 0.81% 可接受 |
| 过期清理 | 采样 + 惰性 | 定时全扫 + 精确定时器 | 每个 key 一个定时器在百万 key 下不可行 |
| 分槽 | CRC16 固定 16384 | 一致性哈希环 | 客户端可自算、迁移单位明确、实现极简 |

### 3.4 场景是怎么被解决的（机制链路）

| 场景 | 用哪个结构 | 链路 | 常见坑 |
|---|---|---|---|
| 热点缓存 | dict + expires | 旁路缓存：读 miss → 回源 → SET EX；写走「先更新 DB 再删缓存」 | 穿透（布隆过滤/空值缓存）、击穿（互斥重建/逻辑过期）、雪崩（TTL 加随机抖动）、大 key、热 key |
| 排行榜 | zset | `ZADD` O(log n) → `ZREVRANGE` 按底层链表右扫 | 分数相同按字典序，要带时间戳做二级排序 |
| 滑动窗口限流 | zset 或 `INCR+EXPIRE` | 窗口外 `ZREMRANGEBYSCORE` → `ZCARD` 判定 → 原子性靠 Lua | 计数器方案是固定窗口，边界会放行 2 倍流量 |
| 分布式锁 | `SET key val NX PX` | 随机值 + Lua 比对再删保证「只删自己的锁」；Redlock 多实例多数派有时钟与 GC 停顿争议 | 没设过期 / 业务超时锁过期 / 主从切换丢锁 → 需要 fence 令牌 |
| 消息 | Stream = rax + listpack | `XADD` → 消费组 `XREADGROUP` → PEL 待确认 → `XACK` | 不 ACK 会堆 PEL，需定时 `XAUTOCLAIM` 转移 |
| 会话 | Hash / String | 集中式存储，重启不丢（取决于持久化策略） | 把 Redis 当持久库用 → 掉电丢 |

### 3.5 性能指标【量级】

| 指标 | 量级 | 前提 / 瓶颈 |
|---|---|---|
| 单节点 GET/SET QPS | 10w 级 | 小 value、pipeline、同机房、CPU 非瓶颈 |
| pipeline 批量 | 可达 50w~100w ops/s | 收益来自**摊薄 RTT 与 syscall**，不是 CPU 变快 |
| 延迟 P99 | 亚毫秒 ~ 1ms | 超过 1ms 要查大 key / 慢命令 / fork / 网络 |
| 单实例内存 | 实践建议 ≤10~20GB | 再大：`fork` COW 期间内存翻倍风险、RDB 恢复慢、主从全量同步久 |
| 慢命令典型 | `KEYS *`、大范围 `SMEMBERS`、大 key 删除 | O(N) 命令会卡住单线程上的所有人 |
| 持久化代价 | RDB fork 期间延迟毛刺；AOF everysec 最多丢 1s | `THP` 打开会让 COW 复制 2MB 大页而非 4KB 页 |

**速算**：单线程理论上限 ≈ `1 / 单次操作耗时`。若一次 GET 净耗时 5 µs，理论 20w ops/s；实际受网络与 syscall 限制落在 10w 级。所以优化方向永远是「少来几次网络往返」（pipeline / mget / Lua），不是「给 Redis 加线程」。

### 3.6 与操作系统的关联，以及为什么这么设计

| OS 能力 | Redis 的用法 | 为什么 / 反例 |
|---|---|---|
| **`epoll` + 非阻塞 IO** | 单线程事件循环一次收就绪 fd 集合，批量处理 | 一个线程服务数万连接；若用每连接一线程，光线程栈与切换就吃掉内存与 CPU |
| **`fork()` + COW** | RDB / AOF rewrite 靠子进程拍一致性快照，父进程继续服务 | 内核只复制**页表**不复制内存，写时才复制被改的页 → O(页表) 而非 O(内存) |
| **透明大页 THP** | **必须关闭** | COW 粒度从 4KB 变成 2MB：写 1 字节也要复制 2MB，fork 期间内存暴涨、延迟毛刺 |
| **swap** | **必须避免** | 内存数据库一旦被换出，µs 级操作变成 ms 级；`vm.swappiness` 调低 + `maxmemory` 预留 |
| **内存预留** | `maxmemory` 通常设物理内存的 60~70% | 给 fork COW、复制积压缓冲、OS 自身留空间，否则高峰 OOM Killer 直接杀进程 |
| **page cache** | 数据**不**走 mmap；只有 RDB/AOF 文件借 OS 缓存，`appendfsync` 控制落盘 | 若数据也交给 OS 管缓存，就失去了精确淘汰策略与亚毫秒确定性 |
| **绑核 / NUMA** | 单线程实例可绑核减少迁移，多实例分散到多核 | 单线程吃不满多核 → 一台机跑多实例是常态 |
| **网络协议栈** | `SO_REUSEPORT`、TCP backlog、批量写 | pipeline 的收益本质是「N 个命令一次 read/write + 一次 RTT」 |

> **一句话答「为什么单线程还快」**：「瓶颈在网络 IO 和内存带宽，不在 CPU；单线程省掉了锁竞争、上下文切换和缓存行弹跳，还能让所有操作天然原子。真要扩，是先加实例分槽，不是给命令执行加线程 —— 6.0 的 I/O 多线程也只碰网络读写，不碰命令。」

### 4.2 用了哪些数据结构与算法

| 层 | 结构 / 算法 | 为什么需要 |
|---|---|---|
| **倒排索引** | `term → postings(docID, tf, positions, offsets)` | 把「文档里有没有这个词」预计算成集合；`LIKE '%x%'` 的全扫变成查表 |
| **term dictionary = FST** | 有限状态转换器，共享前缀与后缀 | 千万级 term 不能全放哈希表；FST 既压缩又能做前缀/模糊查询 |
| **postings 压缩** | docID 差值（delta）+ FOR / PForDelta 整数压缩、跳表（skip list）加速跳越 | 一个热门词可能有千万个 docID，不压缩内存放不下；跳表让求交时跳过整块 |
| **Roaring Bitmap** | filter 缓存 / bitset，按 65536 分桶，稀疏用数组、密集用位图 | 过滤条件复用，集合求交变成位运算 |
| **Doc Values** | 列式存储（per segment），排序/聚合按列顺序读 | 聚合若按行取 `_source`，等于几千万次随机读；列式把它变成顺序扫一列 |
| **BKD 树** | 多维 kd-tree 变体，按块存盘 | 数值范围（价格 > 100）无法枚举成 term，需要专门的多维索引 |
| **segment 不可变** | 每个 refresh 生成新段；删除写 live docs 位图 | 并发读无锁、能被 page cache 长期缓存；代价是更新=删+插、需要 merge |
| **translog** | 追加 WAL | refresh 只让段在内存/文件缓存里可搜，未 fsync 的段掉电会丢 → 靠 translog 重放 |
| **打分** | **BM25**：`TF` 饱和（k1≈1.2）+ 文档长度归一化（b≈0.75）+ IDF | 词出现 10 次不该比 1 次重要 10 倍；长文档天然词多要惩罚 |
| **求交与 TopK** | 多路归并（最小堆）/ 跳表跳跃；**WAND、Block-Max WAND** 用分数上界剪枝；TopK 用大小为 K 的最小堆 | 只要 Top10，不必给全部命中文档打分；上界不够就整块跳过 |
| **模糊查询** | Levenshtein 自动机（编辑距离 DFA 与 FST 求交） | 穷举所有编辑距离内的词不可行 |
| **段合并** | TieredMergePolicy（size-tiered 思路，控制每层段数、段大小上限） | 段太多会让每次查询打开太多文件、fd 爆、归并成本线性涨 |
| **分布式** | `shard = hash(_routing) % 主分片数`；query_then_fetch 两阶段；sequence number + global checkpoint + primary term | 打分需要全局 IDF 时走 `dfs_query_then_fetch`；副本一致性靠序号与任期防脑裂 |

### 4.3 为什么是倒排 + 不可变段

| 候选 | 为什么不合适 |
|---|---|
| B+ 树 / 哈希索引 | 谓词是「包含」而非「等于/前缀」，中间通配符无法定界；多条件 AND 要做多次索引查找再回表求交，不如倒排表直接归并 |
| 原地更新的段 | 一写就加锁、缓存失效、并发读被阻塞；不可变段让读路径完全无锁，且 OS 可以放心长期缓存 |
| 删除时真删 | 要在每个段里改动压缩过的 postings，随机写 + 重压缩；用位图标记是 O(1)，真正清理推给后台 merge |
| 把结果缓存在 JVM 堆里 | 堆越大 GC 越痛、且重启缓存全失；交给 OS page cache 后，缓存跨进程重启仍在（只要不换出） |

**refresh 为什么是 1 秒而不是实时**：每次生成段都要构建倒排、写文件、开 reader；真「实时」等于每写一条就 refresh，段数量爆炸、merge 追不上。**NRT 是用 1 秒可见性换写入吞吐与段数可控**，这是明确的工程取舍。

### 4.4 场景是怎么被解决的（一次写 + 一次查）

**写**：客户端 bulk → 协调节点按 routing 路由到主分片 → 主分片本地写 index buffer + translog → 并行转发给 in-sync 副本 → 达写入条件返回 → 1s refresh 后可搜 → flush 时 segment fsync、清 translog → 后台 merge 合并小段。**副本确认与 translog 是两个独立的耐久性开关**：前者防单机故障，后者防掉电。

**查**：协调节点把请求发到相关分片 → **query 阶段**各分片在本地用倒排表求交 + 最小堆取 TopK，只回 docID 与分数 → 协调节点归并出全局 TopK → **fetch 阶段**按 docID 回各分片取 `_source` → 组装返回。两阶段是为了**只在必要时传输文档正文**。

**日志时序场景**：按时间建索引 + rollover + ILM（热/温/冷/删），查询时按时间范围直接砍掉无关索引；写多读少，副本可先设 0 再补，refresh_interval 可放宽到 30s 换吞吐。

### 4.5 性能指标【量级】

| 指标 | 量级 | 前提 / 瓶颈 |
|---|---|---|
| 可见延迟（NRT） | ~1s（默认 `refresh_interval`） | 日志场景可放宽到 30~60s 换写入吞吐 |
| 单分片 bulk 写入 | 万 ~ 十万 docs/s | 字段数、分析器复杂度、副本数、translog 是否每次 fsync、段合并 IO |
| 简单 term 查询 | 几 ms ~ 几十 ms | 热数据全在 page cache |
| 多条件 + 聚合 | 几十 ms ~ 数秒 | Doc Values 列扫量、聚合桶数、跨分片归并、GC |
| 单分片大小 | 建议 20~50GB（日志可更宽） | 太大则恢复/迁移/merge 慢，太小则分片开销高 |
| JVM heap | ≤30~31GB（保压缩指针），且不超过物理内存一半 | **另一半必须留给 page cache** |
| 分片数 | 每节点分片数按堆与文件数控制，忌「一个索引几百片」 | 分片 = Lucene 实例，每个都吃 fd、堆、线程 |

**速算**：一次查询成本 ≈ `命中段数 × 每段 postings 归并 + 跨分片网络归并`。所以 ES 调优的核心不是加机器，而是**减少需要打开的段数（合理 merge / force_merge 只读索引）与减少参与分片数（routing / 索引生命周期）**。

### 4.6 与操作系统的关联，以及为什么这么设计

**这一节是 ES 最值钱的部分，也是与 MySQL/MongoDB/MinIO 最鲜明的对照。**

| OS 能力 | ES 的用法 | 为什么 / 反例 |
|---|---|---|
| **mmap + page cache** | Lucene 索引文件大量通过 mmap 映射，热段由内核缓存 | 省一次内核→用户态拷贝、缓存跨重启保留、淘汰由内核按全局内存压力决定 |
| **内存分配纪律** | heap ≤31GB 且 ≤ 物理内存 50% | ① 超过 ~32GB 压缩指针失效，对象引用从 4B 变 8B，堆有效容量反而下降；② **留内存给 OS**，否则段文件全部走磁盘，查询慢一个数量级 |
| **swap 绝对禁用** | `vm.swappiness=1` / `bootstrap.memory_lock=true` 锁堆 | 对「靠 page cache 吃饭」的系统，换出一页就等于一次磁盘随机读；GC 时更会引发换入风暴 |
| **`vm.max_map_count`** | 调到 262144 以上 | mmap 段多 → 进程的 VMA 区域数暴涨，默认 65530 会直接 OOM 报错 |
| **文件描述符 ulimit** | 65536+ | 每个段多个文件；段多 + 分片多 = fd 线性涨 |
| **文件系统与 SSD** | SSD/NVMe、预留 ~15% 空间、XFS/ext4 | 预留空间维持 SSD 写入放大与性能；merge 是重 IO 操作 |
| **SIMD** | postings 整数压缩（FOR/PForDelta）解码用向量指令 | 归并阶段是 CPU 密集型，一次解 16 个 docID 比循环快数倍 |
| **GC 与调度** | G1、避免大堆、避免大聚合把 fielddata 撑爆 | 用户态停顿直接变成 P99 长尾；fielddata 放堆里不如 Doc Values 放磁盘+page cache |
| **零拷贝对比** | ES 靠 mmap 而非 `sendfile` | 查询要在用户态做打分与归并，无法纯内核转发；MinIO 整块转发才用得上 `sendfile` |

> **一句话答「为什么 heap 不能设 64GB」**：「因为 ES 把缓存托付给了操作系统。堆吃满内存，Lucene 的段文件就只能走磁盘，P99 直接崩；而且超过 32GB 压缩指针失效，同样的堆存的对象更少。ES 的堆是给聚合与协调用的，不是给数据用的 —— 数据缓存在 page cache。」

## 05 MongoDB／WiredTiger：文档模型与 COW 快照

> **本章口径：MongoDB 在本人业务系统中未使用，整章是纯通用原理对照，不是项目实证。** 留着它只因为它是最好用的三块「反差镜」：① B 树 + 文档聚合边界 vs InnoDB B+ 树 + 行；② 页级 COW 快照 vs undo 版本链；③ WT 自管 cache vs ES 把缓存交给 OS（外加 MMAPv1 被取代这个反面教材）。**本章任何参数、调优、分片经验都不得说成亲历**；被问「用过吗」按 §9.4 的三句式答。

### 5.1 场景与要解决的问题

**场景**：字段经常变的业务实体（商品属性、用户画像、IoT 事件、内容）、需要按整条文档读取、 schema 要能演进、数据量与写入量都要能水平扩展。典型如「订单头 + 明细数组 + 物流轨迹」这类**一次查询就想拿全、很少跨表 JOIN** 的数据。

**要解决的矛盾**：既要有 B 树的稳定读延迟与更新能力（不能像 ES 那样更新=删+插），又要让写吞吐与崩溃恢复别被原地改页拖死，还要让分布式扩展不需要中心协调。答案是 **B 树 + 页级 COW + WAL + 文档即聚合边界**。

### 5.2 用了哪些数据结构与算法

| 层 | 结构 / 算法 | 解决什么 |
|---|---|---|
| **文档 = BSON** | 二进制 JSON，每个字段带类型与长度前缀 | 反序列化时可**跳过不需要的字段**（不用解析整串）；类型保真（区分 int32/int64/date）；可逐字段比较排序 |
| **主存储（WiredTiger）** | **B 树**（默认表引擎；另有 LSM 实现但 MongoDB 未作为用户选项暴露） | 点查与范围查找都稳定，更新就地改页，读放大远低于 LSM |
| **页级 COW** | 修改页时**复制新页**，不原地覆盖；checkpoint 时把新页写入并原子切换根指针 | 一致性快照 + 崩溃恢复只需回到上一个 checkpoint，不需要 undo 回滚 |
| **journal（WAL）** | 追加写 + 组提交（默认约 100ms 提交间隔，可配 `w:majority, j:true` 强制） | 补两次 checkpoint 之间（默认 60s）的持久性窗口 |
| **WT cache** | 自管缓存，默认约 `max(256MB, (RAM−1GB)/2)`；按 LRU-ish + 脏页比例做 eviction | 不依赖 OS page cache，淘汰策略与压缩页格式自己说了算 |
| **MVCC / 事务** | snapshot isolation：事务读一个一致的快照（读/写 timestamp、oldest timestamp），页的多版本链 | 长查询不被写入阻塞，副本同步与回滚也有统一的时间点 |
| **索引** | `_id` B 树、单/复合/多键（数组每元素一条索引项）、TTL、geohash / S2 地理、文本（简版，非 Lucene）、哈希 | 复合索引遵循最左前缀；多键索引让数组元素可查，但会放大索引体积 |
| **oplog** | **capped collection**（固定大小、环形追加） | 副本集同步的输入流；条目设计成**幂等**（自增被改写成 `$set`）便于重复重放 |
| **副本集** | PV1 类 Raft 选举（term / 投票 / 心跳）、**majority commit point**、回滚未多数派确认的写 | 选主防脑裂；已向客户端确认的写不丢 |
| **分片** | 按 shard key 做**范围 chunk**（或哈希分片），chunk 满则分裂，balancer 迁移；config servers 存映射 | 水平扩展，mongos 只做路由与结果归并 |
| **聚合管道** | 流式 pipeline，`$match`/`$sort` 能下推到索引，`$lookup` 近似嵌套循环 | 把计算放在存储侧，减少网络传输 |

### 5.3 为什么是 B 树 + 文档，而不是别的

**① 为什么默认 B 树，而不是 LSM（这是高频追问）**

| 维度 | WiredTiger B 树 | LSM（若用） |
|---|---|---|
| 读延迟 | 稳定，一次树下降 | 多层查找 + bloom，长尾更明显 |
| 更新 | 改页即可，COW 落地 | 追加新版本，读时合并，空间放大 |
| 后台 IO | checkpoint（周期、可控） | 持续 compaction，容易抢前台 IO |
| 定位 | **通用 OLTP 文档库**：读写均衡、查询形态杂 | 写吞吐优先（HBase/Cassandra/RocksDB 场景） |

MongoDB 要做「按 `_id` 点查 + 按时间范围查 + 频繁更新文档字段」的通才，LSM 的写优势换不来读延迟的确定性，所以默认 B 树。WiredTiger 内部有 LSM 实现，但 MongoDB 并未把它作为常规配置开放 —— 这本身就是答案。

**② 为什么用 BSON 而不是 JSON 文本或行式关系表**
- 文本 JSON 每次取一个字段要解析整串；BSON 的长度前缀支持**跳过**。
- 文档模型把「一次业务读取需要的字段」放在物理相邻位置，避免关系模型的多表 JOIN 与随机 IO；代价是**冗余 + 更新放大**（改一个大文档的一个字段要重写整页甚至整文档），所以 MongoDB 明确不建议无界增长的数组。

**③ 为什么 checkpoint 要 COW**：如果不复制页，checkpoint 与前台写入并发时会把「半新半旧」的页写进快照，恢复后数据自相矛盾。COW 让 checkpoint 只需在结束时原子更新根指针 —— **一致性快照不需要阻塞写入**，代价是写放大与需要后台回收旧页。

**④ 为什么 oplog 是 capped + 幂等**：固定大小环形追加保证写 oplog 是纯顺序 IO 且空间有上界；幂等条目让「副本断线重连后重复拉一段」不会把自增字段加两次。**oplog 窗口大小**直接决定副本掉队多久还能追上，追不上就只能全量同步。

### 5.4 场景是怎么被解决的（一次写 + 一次读）

**写（`w:majority, j:true`）**：mongos/驱动 → 主节点写 journal（组提交 fsync）→ 在 WT cache 中修改 B 树页（COW 产生新版本）→ 写 oplog → 副本拉取 oplog 并重放 → 主节点收到多数派确认后推进 commit point 并返回 → 每 ~60s 的 checkpoint 把脏页刷成新快照并回收旧页。

**读**：解析查询 → 命中索引 B 树 → 拿到 RecordId → 若页在 WT cache 直接返回；否则从磁盘读页进 cache → 按 BSON 跳过无关字段 → 返回文档。**主节点读保证读到已多数派提交的数据；`readPreference` 允许读从节点时要接受可能读到旧值**（这是明确的取舍，不是 bug）。

**分片查询**：mongos 查 config 的 chunk 映射 → 只把请求发给相关分片（若 shard key 命中）→ 各分片本地执行 → 需要全局排序时 mongos 做归并。**shard key 选错 = 广播查询（scatter-gather）**，这是 MongoDB 分片最大的性能陷阱。

### 5.5 性能指标【量级】

| 指标 | 量级 | 前提 / 瓶颈 |
|---|---|---|
| 点查（cache 命中） | 0.1~1 ms | 索引可命中、文档不大 |
| 单节点写入 | 几千 ~ 几万 docs/s | 受 journal fsync、索引条数（每个索引一次 B 树写）、文档大小、`w` 一致性级别支配 |
| 副本集 | 常见 3 节点（1 主 2 从 / 含仲裁） | `w:majority` 要多等一个节点确认，延迟换持久性 |
| WT cache | 默认约 `(RAM−1GB)/2`，下限 256MB | 命中率掉下去后随机读直接落到磁盘 |
| checkpoint | 默认 ~60s | 会产生周期性 IO 尖峰，靠平滑 eviction 缓解 |
| chunk | 默认 64MB / 128MB（版本相关） | 太大迁移慢，太小元数据与 balancer 压力大 |
| 单集合规模 | 数十亿文档靠分片 | 依赖 shard key 基数与分布，单调递增键会形成写入热点 |

**速算**：写成本 ≈ `1 次 journal 顺序写 + (1 + 索引数) 次 B 树页修改 + 副本网络往返`。所以「加索引能加速查询」在写侧是**逐条乘法**，不是免费午餐。

### 5.6 与操作系统的关联，以及为什么这么设计

> **这一节和 ES 那一节要对着看：两者对 page cache 的态度完全相反，是面试里的高分对照。**

| OS 能力 | MongoDB 的用法 | 为什么 / 反例 |
|---|---|---|
| **自管 cache，不靠 page cache** | WiredTiger 自己缓存解压后的 B 树页，压缩页格式、淘汰策略、脏页比例全自控 | 若交给 OS，OS 缓存的是**压缩后的磁盘块**，每次读还要解压，且无法按事务语义淘汰；ES 的段文件则天然适合直接 mmap |
| **历史反面教材 MMAPv1** | 旧引擎直接 mmap 文件，靠 OS page cache | 集合级/库级锁、无法压缩、写放大不可控 —— MongoDB 换 WT 的根本原因就是「不能把缓存和并发粒度交给 OS」 |
| **XFS + `noatime`** | 官方推荐 XFS（大文件、extent 分配、并发 IO） | 每次读都更新 atime = 每次读都带一次元数据写 |
| **禁用 THP** | 与 Redis 同理 | WT 是大量 4KB~几十 KB 的随机页访问，2MB 大页会放大 COW 与内存占用 |
| **readahead 调小**（约 8~32 sectors） | 文档访问是随机的 | 默认的大预读会把无关页读进内存，污染 WT cache 与 IO 带宽 |
| **NUMA interleave** | `numactl --interleave=all` 启动 | 否则 cache 集中在一个 NUMA 节点，跨节点访问延迟翻倍 |
| **ulimit / 文件句柄** | 连接与文件数多，需放开 | WT 表文件 + 连接 fd 叠加 |
| **journal 与数据分盘** | 顺序写 journal 与随机写数据分离 | 避免两类 IO 互相抢寻道/带宽；checkpoint 尖峰可隔离 |
| **COW 与 `fsync`** | checkpoint 原子换根 + journal 组提交 | 与 InnoDB 的「redo + 脏页」思路同源，但用 COW 避免了 undo/rollback 的复杂度 |

> **一句话答「MongoDB 和 MySQL 都是 B 树，差在哪」**：「索引结构确实同源，但**聚合边界**不同：MySQL 的一行是关系模型的一个元组，跨实体要 JOIN；MongoDB 把整个实体塞进一个 BSON 文档，一次读就拿全，代价是冗余和文档更新放大。实现上 MySQL 用 redo + undo 版本链做 MVCC，WiredTiger 用**页级 COW + 事务快照**做 MVCC；MySQL 靠 Buffer Pool、MongoDB 靠 WT cache，两者都自己管缓存，都不把命门交给 page cache。」

## 06 MinIO：把冗余从副本换成代数

### 6.1 场景与要解决的问题

**场景**：图片、视频、模型权重、备份包、日志归档 —— **单个对象大（MB~GB）、一次写多次读、总量 PB 级、几乎不做「按内容查找」、要 S3 兼容、要在廉价盘上做到可靠**。

**和前四个的根本差别**：前面四个都在回答「怎么根据条件找到一条记录」，MinIO 只回答「给我这个 key 的字节流」。它**不需要通用索引**，所以可以把元数据压到极轻，把全部精力放在两件事：**吞吐**和**用尽量少的冗余空间扛坏盘**。

### 6.2 用了哪些数据结构与算法

| 层 | 结构 / 算法 | 解决什么 |
|---|---|---|
| **命名空间** | **扁平 key→object**（bucket/prefix 只是字符串，不是目录树） | 不需要 inode/B+ 树/目录锁；元数据极轻，扩展时没有目录热点 |
| **纠删集（erasure set）** | 一组 4~16 块盘为一个独立容错域；对象按确定性哈希选 set，set 内分片位置确定 | 故障域隔离；扩容加 pool 不搬老数据 |
| **Reed–Solomon 纠删码** | 在 GF(2⁸) 有限域上用生成矩阵（Vandermonde / Cauchy 系）把 K 个数据片线性组合出 M 个校验片；恢复时对 K 个可用片组成的子矩阵**求逆**解线性方程 | 任意 K 片可还原全部数据，容忍 M 块盘同时失效 |
| **SIMD 加速** | GF 乘法用查表 + AVX2/SSSE3/NEON 向量指令并行处理多字节 | 纯标量 RS 编码单核约数百 MB/s，向量化后可到数 GB/s 量级 |
| **quorum 读写** | 写需成功写入 K 片（数据片数），读拿到任意 K 片即可解码；读时先验每片 hash，坏片剔除并重算 | 在网络抖动/坏盘时仍可用，且**不会把损坏的数据返回给客户端** |
| **bitrot 防护** | 每分片独立 **HighwayHash**（流式边写边算，不二次读）、`xl.meta` 存校验与 EC 布局、后台 scrub/heal | 对抗「盘没坏但某个扇区静默错了」；这是三副本也未必能发现的问题 |
| **`xl.meta`** | 每对象一份小元数据文件：版本、EC 分布、校验和、对象锁/保留策略 | 元数据随数据走，无中心元数据 DB → 无单点、无元数据瓶颈 |
| **multipart** | 大对象切 part 上传，每 part 独立校验，最后合并元数据 | 断点续传、并行上传、失败只重传一个 part |
| **对象锁 / 版本** | WORM 保留期 + 版本链 | 备份与合规场景防误删、防勒索篡改 |
| **后台 heal** | 扫描校验和 → 发现坏片 → 用其余 K 片重算 → 写到健康盘 | 冗余自愈，不依赖人工换盘才恢复 |

### 6.3 为什么是纠删码，而不是别的

| 候选 | 为什么不选 / 什么时候才选 |
|---|---|
| **三副本** | 空间开销 3×，只能容忍 2 份同时失效（且多数派判定还要求至少 2 份在线）；纠删码 EC:4 在 16 盘下只多花 33% 空间就能容忍 4 盘失效。**代价是 CPU 编码 + 修复读放大 + 小对象不划算**（小对象分片后每片太小，元数据与 IO 次数占比过高） |
| **简单 XOR 奇偶（RAID5 思路）** | 只能容 1 块盘失效；RS 在 GF(2⁸) 上做线性组合才能容 M 块 |
| **硬件 RAID 下面再跑纠删码** | 叠两层冗余，硬件 RAID 会掩盖单盘故障信号、把坏盘变成「慢盘」，还会引入额外写放大；MinIO 明确要 **JBOD + 每盘独立 XFS 文件系统** |
| **中心元数据服务（如 HDFS NameNode）** | 单点 + 扩容瓶颈 + 元数据也要做 HA；MinIO 让每个对象自带 `xl.meta`，靠确定性哈希定位，节点挂了目录不丢 |
| **B+ 树索引** | 没有「按条件查」的需求，key 是精确查找；树只会带来写放大与锁 |
| **把对象数据放进 Go 堆** | GC 会灾难；实际是流式 buffer 复用 + `O_DIRECT` 直接落盘 |

**为什么用 Go**：goroutine 让「K+M 片并行写盘 / 并行读取」写成同步代码且开销极低，`netpoller` 底层就是 `epoll`；对象数据走流式 buffer 与 direct IO，不驻留堆，所以 GC 压力与对象大小解耦。

### 6.4 场景是怎么被解决的（一次 PUT / GET / 坏盘）

**PUT**：S3 请求 → 认证与 bucket 策略 → 按 key 算出 erasure set → 流式切 K 片并 RS 编码出 M 片 → K+M 个 goroutine 并行 `O_DIRECT` 写不同盘，边写边算 HighwayHash → 写 `xl.meta` → 达到写 quorum 返回 200。

**GET**：算出 set → 并行向各盘请求分片 → 每片先验 hash（坏片直接丢弃）→ 拿够任意 K 片 → 若全是数据片直接拼接，若含校验片则做 RS 解码 → 流式返回客户端（可走 `sendfile` 零拷贝）。

**坏盘 / bitrot**：后台 scrub 发现校验不符 → 标记该片 → 从其他盘读 K 片重算 → 写入替换盘 → 更新 `xl.meta`。**修复一个对象要读 K 片**，所以修复流量是受损容量的 K 倍 —— 这就是为什么大集群必须给 heal 限流，否则修复本身会把正常业务打垮。

**扩容**：新增一个 server pool，老 pool 的 set 不变、数据不迁移；新对象按策略落到新 pool。这是「确定性哈希 + 无中心元数据」换来的运维红利。

### 6.5 性能指标【量级】

| 指标 | 量级 | 前提 / 瓶颈 |
|---|---|---|
| 大对象吞吐 | GB/s 级（单节点 NVMe 多盘） | 瓶颈通常是网络（10/25GbE）或盘数，不是 CPU |
| 小对象 QPS | 显著低于大对象吞吐 | 元数据 fsync、分片数固定、每片一次 IO → 小对象固定成本占比高 |
| RS 编码速度 | 标量单核数百 MB/s，SIMD 后数 GB/s | 取决于指令集与实现（AVX2/GFNI） |
| 空间利用率 | `K / (K+M)`，16 盘 EC:4 → 75% | 三副本只有 33% |
| 可容忍失效 | M 块盘（EC:4 容 4 块） | 前提是故障分布在同一个纠删集内不超 M |
| 修复读放大 | 修一个对象需读 K 片，流量 ≈ 受损容量 × K | 需要限速与错峰 |
| 延迟 | 大对象 ms~百 ms 级起步，随对象大小线性增长 | 并行分片 + 流式，首字节延迟受最慢盘影响 |

**速算**：有效写入带宽 ≈ `min(总盘顺序写带宽, 网络带宽) × K/(K+M)`；读带宽 ≈ `min(总盘读带宽 × 并行度, 网卡)`。所以 MinIO 调优的第一件事永远是**网络与磁盘带宽配比**，不是调 GC 参数。

### 6.6 与操作系统的关联，以及为什么这么设计

| OS 能力 | MinIO 的用法 | 为什么 / 反例 |
|---|---|---|
| **`O_DIRECT` + 4K 对齐** | 对象分片直接落盘，绕过 page cache | 一个 1GB 视频若走 buffered IO，会把 page cache 里所有热数据冲光，**对大对象来说 page cache 是敌人不是朋友**（与 ES 完全相反）；`O_DIRECT` 要求 buffer、偏移、长度都按块对齐 |
| **XFS + 每盘独立文件系统** | 大文件 extent 分配、并发 IO 好；一盘一个 FS | 坏盘可整盘拔换；故障域清晰；叠硬件 RAID 会掩盖坏盘信号 |
| **`noatime`** | 关闭访问时间更新 | 每次 GET 都写元数据 = 无谓写放大 |
| **`sendfile` / 零拷贝** | 对象从盘直接流到网卡，不进用户态 | 注意：**启用 TLS 会破坏零拷贝**（需在用户态加密），这是安全与吞吐的明确取舍 |
| **`epoll`（Go netpoller）** | 海量并发连接由少量线程承载 | 与 Redis 同款思路，只是藏在 runtime 里 |
| **文件描述符与 inode** | 小对象海量时 fd/inode 是硬约束 | 扁平命名空间虽轻，但「每对象一文件」在小对象场景仍会压垮元数据层 |
| **NUMA / 网卡中断绑核** | 高吞吐下减少跨节点内存访问与软中断抖动 | GB/s 级流量下，一次跨 NUMA 拷贝都会体现在 CPU 上 |
| **Go runtime 与 GC** | 数据不驻留堆，流式 buffer 池化复用 | 若把对象读进 `[]byte` 再写，GC 会在 PB 级流量下成为主要瓶颈 |

> **一句话答「为什么 MinIO 不做目录树和元数据集群」**：「因为 S3 的对象名只是字符串，查询只有精确 key。目录树、B+ 树、中心元数据服务全是为了『按条件找』而生的，这里用不上；去掉它们就没有单点、没有锁热点，扩容只需加 pool 不搬数据。代价是 LIST 要遍历，所以 LIST 高频的场景不适合对象存储。」

### 7.3 三条同构洞察（把五个背成一个）

1. **写路径都在做 WAL**：redo / AOF / translog / journal / 分片 + `xl.meta`。日志记「输入」，快照记「状态」，后台合并记「待办」。恢复 = 回到最近一致快照 + 重放日志，**绝不重新执行业务逻辑**。
2. **持久结构都在做「不可变 + 后台合并」**，只是浓度不同：ES segment merge 最彻底（段完全不可变），WiredTiger checkpoint 是页级 COW，Redis AOF rewrite 与 RDB 是周期性重写，MySQL 靠 purge + checkpoint 清理 undo 与脏页，MinIO 靠 heal 重建分片。**LSM 不是一个产品，是一种处理写放大的思路**。
3. **并发模型都在躲锁**：Redis 单线程命令执行、Cluster 分槽；ES 分片内多段无锁读；MongoDB 分片 + 文档级锁；MinIO 按 set 隔离故障域；MySQL 靠 MVCC + 行锁把锁粒度压到索引项。**能分就分，不能分就串行，实在不行才加锁。**

## 08 性能指标怎么用才不挨打

### 8.1 三条纪律（比数字本身重要）

1. **所有数字都要带前提**：硬件（NVMe / SSD / HDD）、数据量与是否命中缓存、读写比、一致性级别（是否 `fsync`、是否 `w:majority`）、单条数据大小。脱了前提的 QPS 就是营销材料。
2. **看 P99 不看平均**：merge / compaction / GC / checkpoint / fork COW 都是**周期性尖峰**，平均值完全掩盖它们。ES 的 GC、MongoDB 的 checkpoint、Redis 的 fork、MySQL 的刷脏，都是典型的「平时很稳、每隔一阵抖一下」。
3. **区分「单机基准」与「你的系统」**：本文所有 `【量级】` 是通用工程常识与公开基准的数量级，**不是本项目的实测数据**；讲项目时一律回到 `00-面试计划/02-项目叙事-B2B.md` 的 `【实证】/【简历口径】/【推演】/【待实测】` 口径，别把两者混着说。

### 8.2 五个速算式（现场能自己推）

| 场景 | 速算 | 说明 |
|---|---|---|
| 点查延迟 | `树高 × 单次随机 IO`（未命中）或 `纯内存开销`（命中） | 所以 B+ 树要「矮胖」，Buffer Pool 命中率要 >99% |
| 写 TPS | `fsync 能力 × 组提交批量` | 双一配置要 fsync 两个文件，直接掉一档 |
| 单线程 QPS | `1 / 单次操作耗时` | Redis 优化方向是少 RTT（pipeline），不是加线程 |
| 查询成本 | `命中段数 × 归并量 + 跨分片网络` | ES 调优是减段数、减参与分片数 |
| 对象吞吐 | `min(盘总带宽, 网卡) × K/(K+M)` | MinIO 先配平网络与盘，别先调 GC |

### 8.3 五个最容易踩的指标坑

- 拿厂商 benchmark 里的「最高吞吐」当自己的容量上限（那是大对象、无副本、顺序 IO、内存全命中的理想值）。
- 忽略副本与一致性：`w:majority` / `acks=all` / 双一配置都是拿延迟换持久性。
- 忽略后台任务：merge / compaction / heal / checkpoint 与前台共享同一块盘。
- 忽略数据倾斜：热 key、单调递增 shard key、ES 一个大分片，都能让集群平均指标好看但 P99 爆炸。
- 忽略「指标随时间退化」：段变多、undo 变长、oplog 窗口变小、碎片变多，上线第一天与第三个月的数字不是一回事。

## 09 面试话术与追问链

### 9.1 60 秒版（一句话主线 + 五个落点）

> 「这五个中间件其实是同一组 OS 约束下的五种取舍。磁盘随机 IO 比顺序 IO 贵两到四个数量级，所以 MySQL 用 B+ 树把点查压到 3 次页读、用 redo 把写变成顺序追加；Redis 干脆把数据全放内存，用哈希表和跳表换亚毫秒；ES 的查询是『包含』，B+ 树处理不了，所以用倒排索引把查询变成集合求交，再用不可变段把读做成无锁；MongoDB 也是 B 树，但聚合边界是整个 BSON 文档，用页级 COW 做快照；MinIO 没有按条件查询，只有按 key 取字节流，所以敢砍掉元数据集群，用 RS 纠删码把冗余从三副本降到 1.33 倍。它们对 OS page cache 的态度正好分三类：ES 全交给 OS、MySQL/Mongo/MinIO 自己管、Redis 根本不需要 —— 这一条基本能把『为什么这么设计』全串起来。」

### 9.2 3 分钟版（加一层推导 + 一个反例）

在 60 秒版基础上补两点：

1. **从约束往下推**：「我一般先讲四条物理约束（分层存储速度差、4KB 页与 page cache、系统调用与切换成本、易失与不可靠），再讲六个通用动作（顺序化、不可变+合并、索引换查找、批处理、校验冗余、单线程或分片无锁）。五个中间件不过是这六个动作的不同浓度。」
2. **主动给反例**：「比如 ES 的 heap 不能设 64GB，不是因为 JVM 不行，是因为它把缓存托付给了 OS —— 堆吃满内存，段文件只能走磁盘，P99 直接崩；而 MongoDB 恰恰相反，WT 必须自己管缓存，因为 OS 缓存的是压缩块、没法按事务语义淘汰。这两个放一起讲，比单背一个参数更能说明真懂。」

### 9.3 八条高频追问与答案骨架

| # | 追问 | 答案骨架 |
|---|---|---|
| 1 | MySQL、ES、MongoDB 索引为什么不一样？ | **查询谓词形态决定结构**：等值/范围 → B+ 树；包含/相关度 → 倒排；文档字段 → B 树 + 多键索引；数值范围 → BKD |
| 2 | Redis 为什么单线程还快？什么时候不快？ | 瓶颈在网络与内存带宽，单线程省锁与切换且天然原子；**大 key、O(N) 命令、fork COW、swap** 时会卡住所有人 |
| 3 | ES 为什么是近实时？heap 为何 ≤31GB？ | 每次 refresh 建段太贵 → 1s 换吞吐；>32GB 压缩指针失效 + 要给 page cache 留内存 |
| 4 | MySQL 和 MongoDB 都 B 树，差别在哪？ | 聚合边界（行 vs 文档）、MVCC 实现（undo 版本链 vs COW 快照）、缓存（Buffer Pool vs WT cache）、扩展（应用分库 vs 原生分片） |
| 5 | MinIO 为什么不做元数据服务？坏盘怎么恢复？ | 精确 key 查找不需要索引；确定性哈希选 set + 对象自带 `xl.meta`；后台 heal 用其余 K 片解 RS 方程重建并验 hash |
| 6 | 五者谁最依赖 page cache？谁最怕 swap？ | ES 最依赖（mmap），Redis 最怕 swap（内存库被换出 = 灾难），两者都要禁 swap；MinIO/MySQL/Mongo 用 `O_DIRECT` 自管 |
| 7 | 为什么大家都在用 WAL？ | 把随机写变顺序追加，用户只需等一次 fsync；日志记输入、快照记状态，恢复靠重放而非重跑业务 |
| 8 | 让你设计一个中间件，怎么从 OS 推到结构？ | 先定查询谓词与数据大小 → 定放哪层存储 → 定索引结构 → 定写路径（WAL/COW/不可变）→ 定缓存归属（OS 还是自管）→ 定并发与一致性与恢复矩阵 |

### 10.2 十条辟谣（说错会被立刻追问）

1. ❌「B+ 树比哈希表快」→ 等值查询哈希更快，B+ 树赢在**范围、排序、磁盘页局部性**。
2. ❌「Redis 单线程所以不能利用多核」→ 一台机跑多实例 / Cluster 分槽；6.0+ I/O 多线程分担网络读写（命令执行仍单线程）。
3. ❌「跳表比红黑树快」→ 渐进复杂度同阶，赢在**范围遍历与实现简单**，代价是指针内存。
4. ❌「ES 是实时搜索」→ 默认 1s 近实时；`refresh` 不是 `flush`，前者可搜、后者才落盘。
5. ❌「ES 索引数据都在 JVM 堆里」→ 段文件在磁盘 + **page cache**，堆只放聚合/缓存/协调。
6. ❌「MongoDB 是 LSM，写吞吐才高」→ 默认 WiredTiger **B 树 + COW**，不是 LSM。
7. ❌「MMAPv1 靠 mmap 所以更先进」→ 恰恰因为把缓存与并发粒度交给 OS 才被 WT 取代。
8. ❌「MinIO 用三副本」→ 用 **RS 纠删码**；三副本是另一类取舍（小对象延迟更好、空间 3×）。
9. ❌「`O_DIRECT` 一定比 buffered IO 快」→ 它牺牲了预读与缓存，只有在**自己有更好的缓存策略或数据太大**时才划算。
10. ❌「WAL 是为了加速写」→ WAL 是为了**崩溃可恢复**；加速写是把随机写变顺序写的副产品。
