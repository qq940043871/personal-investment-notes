## 00 系统锚点：这套系统里 MySQL 在哪、管什么

> 读法：先记住这一节，后面 13 条链都是从这里的某个格子长出来的。链内「依据指针」用相对 `02-现货贸易/` 的简写，完整路径见文末。

### 0.1 数据链路（一句话版）

浏览器 / 外部系统 → **midservice 网关**（自研 Java Web，多实例：契约、限流、脱敏、租户路由）→ 业务服务 → **MySQL 双实例（主写从读）**。其中：行情 / 挂牌列表这类高频读由**独立缓存服务（封装 Redis，Canal 订阅 binlog）** 承接；**最新出价 / 成交**由 midservice **直连 C 单线程内存撮合引擎**（不落 MySQL、不走 DS）；**标的详情**走 **DS 数据交换中心 → 业务服务 → MySQL**；出价写入落库后用 **outbox 事务消息（Kafka）** 通知风控、财务、仓储。

### 0.2 MySQL 在本系统里的四个真实身份

| 身份 | 具体对象 | 口径 |
|---|---|---|
| 业务真相源 | 挂牌 `t_listing`、出价 `t_quote`、合同 / 交收 / 结算、待发送表 | 【实证】写与「写后读」走主库 |
| 事件源 | binlog → Canal → 独立缓存服务；binlog 也是缓存更新流的唯一驱动 | 【实证·场景】09 号故障即 Canal 位点停滞 |
| 一致性载体 | 待发送表 + 本地事务 + 批次号原子认领（一条 UPDATE 改状态并打号） | 【实证】12 号一致性方案 |
| 容量出口 | 5 实例 × 20 连接 = 100；`max_connections` 200；慢查询 1s kill | 【实证·场景】11 号扩容打穿 DB |

### 0.3 三条口径红线（背错就是过度声明）

1. **物理分库分表没做过**：实际落地是「共用 MySQL 实例 + 按领域垂直分 schema（逻辑分库）+ 读写分离」，跨域检索交给 ES，历史按时间归档。被问分片键按「通用方案储备」答，不许说成「我们做了分片」。
2. **C 核心以内存为准**：撮合结果异步回写 DB，DB 只是最终一致的副本；运营点重试只重放回写、**绝不重新撮合**。
3. **故障场景不冒充亲历**：`04-生产问题排查/09、11、13` 是「基于真实架构的代表性场景」，讲的时候说「按这套架构复盘」，别说成「我当晚在场」；数值是复盘基线，不是压测报告。

## 🔥 追问链 01｜竞价列表这条 SELECT 为什么把主库打到 97%

> **场景锚点**：09 号排查实录：竞价专场开市 15 分钟后 `/api/bid/list` P99 从 150ms 涨到 3.2s，成功率仍 100%（慢而不报错）。midmon 按 traceId 拆出「网关 20ms / 竞价服务 3180ms（其中 MySQL SELECT t_listing 2950ms）/ C 引擎直连 45ms」，同时 Redis 命中率 98%→31%、Canal 消费位点停滞 22 分钟。【实证·场景】
>
> **考察意图**：能不能把「一条 SQL 慢」拆到具体层，而不是只会背「连接器→分析器→优化器→执行器」。
>
> **依据指针**：`04-生产问题排查/09-竞价页面突然变慢-排查实录.md` §2.2 / §2.5；`11-网关扩容打穿DB-性能开发规范.md` §6.2

### L0 · 主问题：竞价页面开市后变慢，你怎么证明是 MySQL 慢，而不是网关或 C 撮合引擎慢？
**答**：先分层定界，再谈 SQL。① DevTools 看 waterfall，静态资源 5ms、XHR 3s+ → 服务端问题；② midmon 用 traceId 把一次慢请求拆开：网关 20ms、竞价服务 3180ms（其中 `SELECT t_listing` 2950ms）、C 引擎直连查最新出价 45ms；③ 排除 GC（无 Full GC）与撮合链路（TPS / 队列深度平稳）——**「竞价慢」不是「撮合慢」，是查询慢**；④ `SHOW FULL PROCESSLIST` 与慢日志确认大量 `t_listing` / `t_quote` 查询排队，主库 CPU 97%。

落到 MySQL 原理：一条 SELECT 是 `连接器 → 分析器 → 优化器 → 执行器 → 存储引擎(handler)`。本例慢在**执行器反复调用 handler 做大范围扫描**（缓存击穿后列表查询失去保护，且列表读被错配到主库），不是连接建立慢，也不是优化器选错索引。面试官要的是这条「现象 → 分段证据 → 原理定位」的链，不是背六个组件名。

### L1 · 追问：为什么查询缓存救不了这里，缓存必须放在 MySQL 外面？
**答**：查询缓存以 SQL 文本为 key 缓存结果集，**只要表有任何更新，该表所有缓存整体失效**；高并发下命中率低，且缓存维护、失效加锁反而成为瓶颈。缓存应由应用层（Redis）按业务语义来做，而不是数据库按 SQL 文本做。

### L2 · 追问：优化器怎么决定走哪个索引？
**答**：基于**代价模型（Cost Model）**，不是规则：根据统计信息（`innodb_stats_*`、表行数、索引区分度/基数 cardinality）估算不同执行计划的 CPU + IO 代价，选代价最小的。这也是为什么 `rows` 是**估算值**、统计信息失真会导致"明明有索引却走全表扫描"。

> **落回系统**：09 号故障里 Canal 停滞导致热点 key 过期后回源，优化器按统计信息选的执行计划本来没走错，一旦回源量翻几十倍，代价估算再准也扛不住——所以先治命中率与回源并发保护，再谈改 SQL。

### L3 · 追问：执行器和存储引擎是怎么交互的？
**答**：通过统一的 `handler` 抽象接口。Server 层不直接碰数据文件，只调用 `handler` 的 `open/read_first/read_next/index_read` 等方法，具体读写由各引擎实现。这就是"插件式存储引擎"能换引擎的原因。

### L4 · 追问：权限到底在哪里检查？为什么不是连接器一次查完？
**答**：连接器阶段先读一次权限并**缓存到连接会话**；执行器在打开表时再校验一次（在优化器之后）。注意顺序：**优化器不检查权限，执行器才检查**。若连接建立后权限被修改，需重连或用 `FLUSH PRIVILEGES` 才生效。

### L5 · 追问：如果这是一条 UPDATE，流程会多出什么？
**答**：多出**日志与两阶段提交**：定位行加锁（当前读）→ 改内存页 → 写 undo（用于回滚/MVCC）→ 写 redo(PREPARE) → 写 binlog → redo(COMMIT) → 返回，脏页延迟刷盘。核心是 redo 与 binlog 用**两阶段提交**保证崩溃恢复时二者一致。详见追问链 08。

> **落回系统**：出价写入那条 UPDATE 不是孤立的：它和 outbox 待发送表写在同一个本地事务里，redo / binlog 提交后 Canal 才会看到变更去刷缓存（见追问链 08、13）。

|---|---|---|
| 竞价列表查询 | midmon traceId 分段 20ms / 2950ms / 45ms | 排查 09 §2.2 |
| 慢 SQL 红线 | 禁 `select *`、单次 ≤200 条、必须 limit | 规范 11 §6.2 |

## 🔥 追问链 02｜挂牌列表的联合索引为什么长这样

> **场景锚点**：竞价 / 挂牌按「租户 + 品种 + 状态 + 时间」翻页查 `t_listing`；网关把分页压到 100、时间跨度卡 31 天，SQL 红线单次 ≤200 条。主键用 Snowflake 趋势递增 ID，跨域检索交给 ES。【实证】+【设计推演】索引形态
>
> **考察意图**：能否从「磁盘 IO 次数」讲清索引结构选型，并落到本系统列表查询的具体设计，而不是背一句「扇出大」。
>
> **依据指针**：`04-生产问题排查/11-网关扩容打穿DB-性能开发规范.md` §6.2；`03-架构决策/arch/07-数据库选型与分库分表.md` §五

### L0 · 主问题：挂牌表一天几百万行，要按品种 + 状态查、按时间倒序翻页，索引怎么设计？为什么不是哈希或跳表？
**答**：先说系统怎么落：① 主键用 **Snowflake 趋势递增 bigint**（顺序追加写，避免随机 UUID 的页分裂，二级索引也不会被宽主键拖胖）；② 列表查询用「**等值列在前、范围列在后、排序列紧随**」的联合索引，只取列表需要的列走覆盖索引；③ 深分页靠游标 / 网关分页 100 + SQL ≤200 条把范围锁死，不让它演变成大范围扫描；④ 多条件组合检索交给 ES，不逼 MySQL 硬扛。

再说原理：B+ 树非叶子只存键 + 指针（16KB 页约 1170 分叉）、叶子双向链表且存数据，三层约 2000 万行、最多 3 次磁盘 IO，同时支持等值 / 范围 / 排序；哈希不支持范围与排序，红黑树层高，跳表是为内存设计、节点不按页对齐。**介质决定结构**——这句话本身不值钱，值钱的是能指着 `t_listing` 说出我们为什么这么建。

### L1 · 追问：那 C 撮合引擎内存里的订单簿为什么不能用同一套思路？
**答**：哈希表等值 O(1) 但不支持范围/排序/前缀匹配；红黑树/AVL 是二叉树，千万级数据 20+ 层 = 20+ 次随机磁盘 IO；B 树非叶子也存数据，扇出小、树更高，范围查询要中序遍历。

### L2 · 追问：说"3 层就能存 2000 万"，具体怎么算的？
**答**：InnoDB 一页 16KB。非叶子节点每项 = 主键 8B + 指针 6B ≈ 14B，一页约装 `16KB/14B ≈ 1170` 个分叉。叶子节点假设一行 1KB，一页约 16 行。三层 B+ 树：`1170 × 1170 × 16 ≈ 2190 万行`，即**最多 3 次磁盘 IO**（根页常驻内存时实际 2 次）。

### L3 · 追问：主键为什么推荐自增？不自增会怎样？
**答**：自增主键是**顺序追加写**，新记录总是落在最右叶子，几乎不引发页分裂；UUID/随机主键无序，插入时频繁**页分裂**，产生碎片、随机 IO，且二级索引要冗余存主键，主键越宽，二级索引越占空间。可答：雪花算法/号段生成**趋势递增**的 bigint 是生产常用折中。

> **落回系统**：本系统主键用 Snowflake 趋势递增正是为了避开页分裂；C 引擎内部内存结构由 3 人 C 团队实现，我只定 Java 侧契约，被问到内部结构按 BOUNDARY 划界，不替他们编。

### L4 · 追问：页分裂具体发生了什么？
**答**：当叶子页写满还要插入时，InnoDB 申请一个新页，把原页约一半数据搬过去，再更新父节点指针，插入新值。主键有序时新页追加在尾部，几乎不搬数据；主键随机时插入点落在中间，频繁搬一半数据，产生大量碎片和随机 IO。

### L5 · 追问：那为什么不用跳表（Skip List）？Redis 不是用跳表吗？
**答**：跳表也是 O(log n)，但它是**内存数据结构**：节点靠多层随机指针串联，指针跳转在内存里很快，但在磁盘上是**随机 IO**，且跳表节点不按页对齐、扇出小、树高，无法像 B+ 树那样把连续键紧凑塞进一页实现顺序预读。一句话：**跳表为内存优化，B+ 树为磁盘优化**，介质决定结构。

> **落回系统**：Redis ZSet 用跳表在内存里做行情 / 风控 Top N，MySQL B+ 树在磁盘上扛列表查询——一个系统里两种结构并存，正好用来答「介质决定结构」，比只举 Redis 一个例子有说服力。

**本链在系统里的落点**

| 场景 | 系统里的落点 | 依据 |
|---|---|---|
| 列表索引 | 等值在前 / 范围在后 / 覆盖索引 | 本链 L0、L4 |
| 主键策略 | Snowflake 趋势递增 bigint | arch/07 §五 |
| 物理分片 | **未做**；垂直分 schema + 读写分离 | arch/07 §五 |

## 🔥 追问链 03｜列表页为什么把 `select *` 写进上线红线

> **场景锚点**：11 号性能规范的 SQL 红线：禁 `select *`、单次最多 100~200 条、分页必须带 limit、慢 SQL 上线前过审核；合同正文 / 质检报告这类大字段按领域拆扩展表。【实证】+【设计推演】拆表
>
> **考察意图**：能否把「回表是随机 IO」这条原理，翻译成一条能写进代码评审的规范。
>
> **依据指针**：`04-生产问题排查/11-网关扩容打穿DB-性能开发规范.md` §6.2 / §8.2；`09-竞价页面突然变慢` §4.1 S-4

### L0 · 主问题：为什么我们把 `select *` 写进上线红线，而不是等慢 SQL 出来再优化？
**答**：因为在这套系统里它会在最坏的时刻放大成故障。列表接口走二级索引命中主键后，若还要回表取整行，**回表是随机 IO**；09 号故障里缓存击穿、回源量翻几十倍，这类查询直接把 Buffer Pool 的热点页挤出，主库 CPU 打到 97%，连接池等待 200+。合同正文、质检报告这类大字段还会触发 off-page 额外 IO，所以拆到扩展表，列表只查必要列。

原理收口：聚簇索引叶子存整行，二级索引叶子存「索引列 + 主键值」，用二级索引查到主键再回聚簇取数叫**回表**；所需列全在索引里即**覆盖索引**（`Extra: Using index`），不回表。`select *` 同时干掉覆盖索引、放大网络与大字段 IO、让表结构变更变脆弱——所以它是规范问题，不是调优技巧。

### L1 · 追问：业务表为什么强制显式主键？没有主键 InnoDB 会怎么做？
**答**：InnoDB 按优先级选：① 第一个**非空唯一索引**；② 都没有则生成隐藏的 6 字节 `ROW_ID` 作聚簇索引。所以最好显式建主键，避免依赖隐藏 row_id（不可控、不能复用）。

### L2 · 追问：二级索引为什么存主键值，而不是存行指针（MyISAM 那样）？
**答**：因为聚簇索引的**数据会随主键变更/页分裂而移动**。若二级索引存物理地址，数据一移动所有二级索引都要更新；存主键值（逻辑地址），数据移动时二级索引不用动，代价只是多一次回表。这是 InnoDB 与 MyISAM 的核心差异。

> **落回系统**：二级索引叶子存的是主键值（逻辑地址）而不是物理行指针，意味着主键越宽所有二级索引越占空间——本系统用 bigint Snowflake 主键而不是 UUID 字符串，就是这个道理的直接落地。

### L3 · 追问：EXPLAIN 里怎么看出是覆盖索引、还是用了 ICP？
**答**：`Extra` 列。`Using index` = 覆盖索引（不回表，最优）；`Using index condition` = 索引下推 ICP（引擎层先过滤，减少回表）；`Using where` = Server 层过滤；`Using filesort`/`Using temporary` 是警告信号。

### L4 · 追问：回表的代价是什么？MRR 怎么优化？
**答**：回表是**随机 IO**——二级索引叶子里的主键是无序的，回聚簇索引读整行时磁盘寻道频繁。**MRR（Multi-Range Read）** 把二级索引查到的主键先排序，再**按主键顺序**回表，把随机读变成近似顺序读，减少磁盘寻道。可通过 `optimizer_switch` 的 `mrr=on` 控制。

> **落回系统**：09 号应急 S-4 把列表查询临时切到从库，本质是把回表的随机 IO 从主库挪走；治本仍是恢复缓存命中率 + 覆盖索引，切从库只是争取时间。

## 🔥 追问链 04｜多租户挂牌列表的联合索引列顺序

> **场景锚点**：B2B 多租户（机构客户 / 普通客户 / 外部大屏只读），所有列表查询都带租户维度；网关契约里分页 100、时间跨度 31 天、排序字段白名单都是硬校验，且**请求里的租户 ID 不可信，只信会话**。【实证】+【设计推演】索引形态
>
> **考察意图**：能否把最左前缀的「整体字典序」物理本质，讲成一次可评审的索引设计。
>
> **依据指针**：`00-面试计划/05-网关与高并发.md` §1.1 / §2.1；`03-架构决策/网关与高并发/11-midservice网关职责与治理设计.md`

### L0 · 主问题：挂牌列表要按租户 + 品种 + 状态查、按时间倒序翻页，联合索引的列顺序怎么排？
**答**：系统侧顺序是 `tenant_id → variety_id / status → create_time`。租户 ID 必须打头：它既是所有查询的等值条件，也是**数据权限边界**（网关只信会话里的租户，不信请求参数）；品种 / 状态同为等值紧随；时间既是范围又是排序列，放最后，让 `ORDER BY create_time DESC` 也能吃到索引有序性、不 filesort。网关把时间跨度硬卡在 31 天、分页卡在 100，等于从入口保证这个范围列不会放开成大范围扫描。

原理收口：联合索引叶子按 `(a,b,c)` **整体字典序**排列，先比 a、a 相同才比 b；`a>?` 是范围，范围内 b 无序，所以**范围列之后的列不再参与定位**；跳列查询只能靠 ICP 顺带过滤。口诀「等值在前、范围在后、排序列紧随」不是经验，是 B+ 树叶子有序性的直接推论。

### L1 · 追问：查询条件跳过了状态列，这个索引还吃得住吗？
**答**：`a` 能走索引，`c` 因为跳过了 `b` 无法直接定位，只能靠**索引下推（ICP）**在遍历 `a=1` 的行时顺带过滤 `c=3`，比全表回表好，但不如 `(a,c)` 高效。

### L2 · 追问：`WHERE a>1 AND b=2`，为什么 b 失效？
**答**：因为索引按 (a,b) 排序，`a>1` 是**范围**，范围内 `a` 各不相同的行，其 `b` 是**无序的**，无法用 b 继续二分定位。**范围列之后的列都失效**——这是最左前缀最常见的坑。

> **落回系统**：时间跨度被网关硬卡 31 天，正是为了不让 `create_time > ?` 这个范围废掉后续列之后还要在海量行上过滤；入口闸门与 DB 索引是同一套设计的两端。

### L3 · 追问：为什么不能跳过 a 直接查 b？
**答**：B+ 树叶子按 (a,b,c) **整体字典序**排列：先比 a，a 相同再比 b。若只按 b 查，索引里 b 是全局无序的，无法用 b 定位，只能全索引扫描。这就是"最左前缀"的物理本质。

### L4 · 追问：怎么设计才能既查 a 又按 b 排序？
**答**：把排序列也纳入联合索引。如 `WHERE a=? ORDER BY b` 需要 `(a,b)`；`WHERE a=? AND b>? ORDER BY c` 需要 `(a,b,c)` 才能排序也不 filesort。核心口诀：**等值在前、范围在后、排序列紧随其后**，让排序也能"吃"到索引的有序性。

> **落回系统**：`ORDER BY create_time DESC` 想不 filesort 就得让排序列紧跟等值列；这条与网关「排序字段白名单」是配套——入口限制形状，DB 才能保住有序性。

**本链在系统里的落点**

| 场景 | 系统里的落点 | 依据 |
|---|---|---|
| 多租户隔离 | 请求里的租户 ID 不可信，只信会话 | 网关 11 §7 |
| 压力参数 | 分页 100 / 跨度 31 天 / 排序字段白名单 | 主线件 05 |
| 索引形态 | 等值在前、范围在后、排序列紧随 | 本链 L0 / L4 |

## 🔥 追问链 05｜出价写入 + outbox 那个本地事务里到底隔离了什么

> **场景锚点**：12 号一致性方案第一条铁律：业务表与待发送表写在**同一个本地事务**，远程调用一律挪到事务提交之后；11 号规范把长事务卡在 >5s 告警 + kill。【实证】
>
> **考察意图**：能否把隔离级别 / MVCC 讲成「为什么事务里不能塞远程调用」，而不是背四个隔离级别的名字。
>
> **依据指针**：`03-架构决策/一致性与异构/12-跨系统调用一致性方案.md` §1 / §2；`04-生产问题排查/11-网关扩容打穿DB-性能开发规范.md` §7

### L0 · 主问题：你们说「业务表 + 待发送表同一个本地事务」，这个事务到底保证了什么、又没保证什么？
**答**：保证的是**本地原子性**——「单据变更」与「要通知谁（欠账记录）」要么一起落库、要么一起回滚，绝不会出现「业务成了但没记欠账」。**不保证**两个下游都被调用成功，那是 12 号异步派发 + 阶梯重试 + 幂等去重要解决的事（只保证最终被确认）。所以远程调用一律挪到事务提交之后：事务里调下游，超时会把本地事务拖长，还会出现「下游收到了、本地回滚了」的幽灵副作用。

落到 MySQL：RR 下**快照读**靠隐藏字段 + undo 版本链 + ReadView，读不加锁；**UPDATE 是当前读**，必须基于最新值并加锁，否则会丢更新。事务里读到的旧值能不能用来做业务判断，取决于你用的是快照读还是 `SELECT ... FOR UPDATE`——这正是「先查再改」竞态的根源。

### L1 · 追问：为什么事务里不能穿插远程调用？跟 undo / purge 有什么关系？
**答**：靠**隐藏字段 + undo 版本链 + ReadView**。每行有 `DB_TRX_ID`（最近修改的事务 id）、`DB_ROLL_PTR`（指向 undo 里的历史版本）；读时沿版本链找到"本事务可见"的版本，通过版本判断而非加锁实现一致性快照。

### L2 · 追问：ReadView 的可见性判断规则是什么？
**答**：ReadView 记录 `m_ids`（当前活跃事务集合）、`min_trx_id`、`max_trx_id`、`creator_trx_id`。对某版本的事务 id `trx_id`：
```
trx_id == creator_trx_id   → 自己改的，可见
trx_id <  min_trx_id       → 已提交，可见
trx_id >= max_trx_id       → 视图之后的事务，不可见
trx_id ∈  m_ids            → 仍在活跃，不可见
否则                        → 已提交，可见
```

### L3 · 追问：RR 和 RC 的 MVCC 差在哪？
**答**：**ReadView 生成时机不同**。RC：每次快照读都生成新 ReadView，所以能读到别的事务新提交的数据（不可重复读）；RR：**事务内第一次快照读**生成 ReadView 并复用，全程同一快照，所以可重复读。

> **落回系统**：本系统没有对隔离级别做特殊调优的公开声明，按 MySQL 默认 RR 使用更稳妥；能讲清「我们靠短事务 + 状态机 CAS 控并发，不靠调隔离级别」比编一个「我们切了 RC」安全得多。

### L4 · 追问：MySQL 为什么默认 RR，而不是像 Oracle 用 RC？
**答**：历史原因——**5.7 之前 binlog 默认 STATEMENT 格式**，主从复制靠 SQL 回放，若用 RC 会出现"主库事务执行顺序与 binlog 回放结果不一致"的幻读风险；RR + 间隙锁能保证 STATEMENT 复制下主从一致。5.7.7 后 binlog 默认 ROW，才逐渐有公司切 RC 提并发。能答出这条"历史包袱"是明显加分。

### L5 · 追问：undo log 会被清理吗？什么时候？
**答**：会，由后台 **purge 线程**异步清理。判断依据是：某 undo 版本**不再被任何活跃事务的 ReadView 引用**时才可回收。**长事务会拖着 purge 无法推进**，导致 undo 空间暴涨、版本链变长、查询变慢——这就是长事务危害的底层原因。

> **落回系统**：11 号把 >5s 定为长事务告警 + kill，底层原因就是长事务拖住 purge、undo 版本链变长、查询变慢；规范是用工程手段替 DB 兜底，这类「数字背后的原理」最容易被追问。

**本链在系统里的落点**

| 场景 | 系统里的落点 | 依据 |
|---|---|---|
| Outbox 本地事务 | 业务表 + 待发送表同一事务 | 一致性 12 §2 |
| 远程调用 | 一律放事务提交之后 | 一致性 12 §1 |
| 长事务红线 | >5s 告警 + kill | 规范 11 §7 |

## 🔥 追问链 06｜批次号凭什么能一次性认领整批

> **场景锚点**：12 号 §3.3：派发线程先取**全局唯一批次号**，再用**一条带批次号的 UPDATE** 把整批记录原子认领——`状态=发送中`、`batch_no=本批次号`、`认领时间=当前时间` 三件事同一条 SQL。判据：「改状态」和「打批次号」拆成两条，并发窗口就重新打开。【实证】
>
> **考察意图**：能否用当前读 / 行锁解释「不需要分布式锁」，而不是只会说「加个 Redis 锁」。
>
> **依据指针**：`03-架构决策/一致性与异构/12-跨系统调用一致性方案.md` §3.3 / §4 / §7

### L0 · 主问题：多实例派发器同时扫同一张待发送表，凭什么不会重复派发？不用分布式锁吗？
**答**：靠**数据库的条件更新 + 行锁**，不靠 Redis / ZK 锁。系统里的认领是 `UPDATE ... SET status='发送中', batch_no=?, claim_time=? WHERE status='待发送' AND batch_no IS NULL LIMIT N`——一条记录只可能落进某一个批次，天然互斥。12 号明确写了：批次号认领本身就是一次原子互斥操作，**不需要再引入分布式锁**；只有库不支持可靠条件更新时，才退回「分布式锁 + 批量认领」，而那时锁会成为新的单点，只作降级方案。

落到 MySQL：UPDATE 是**当前读**，RR 下按索引范围加 next-key lock，别的事务既改不了已命中的行、也插不进扫描的间隙；如果写成 `SELECT` 捞出来再逐条 UPDATE，就是典型的 check-then-act 竞态。批次号还必须**全局唯一、禁单机自增**，否则一上集群就撞号——这类问题只在扩容那一刻暴露，最贵。

### L1 · 追问：为什么不能先 SELECT 捞出待发送记录，再逐条 UPDATE？
**答**：两条腿。**快照读**靠 MVCC（读的是事务开始时的快照，别人插入看不到）；**当前读**靠 **next-key lock（记录锁 + 间隙锁）**，把查询范围锁住，阻止其他事务插入，从根上消除幻读。

### L2 · 追问：为什么间隙锁只在 RR 及以上才有？
**答**：间隙锁锁的是"记录之间的空隙"，代价是降低并发。RC 没有间隙锁（只有记录锁），因为它容忍幻读；RR 为了基本消除幻读才引入。这也是 RC 并发更高、RR 更容易死锁的原因。

### L3 · 追问：RR 能 100% 避免幻读吗？边界在哪？
**答**：**不能严格 100%**。经典反例：事务 A 先**快照读**（`SELECT * WHERE id>5`，MVCC 不加锁），此时事务 B 插入一条 `id=10` 并提交；A 再**当前读**（`SELECT ... FOR UPDATE` 或 `UPDATE`）时会看到这条新插入的行，产生"幻影"。所以严格说 RR 只是"基本解决"，能主动点出这个边界是加分项。

> **落回系统**：状态机里没有独立的「僵死」态：扫描器按**认领超时**把记录回收成「待重试」，可按批次号整批定位；重试是一次新的派发动作 → 取新批次号，历史批次另存流水，需要时按业务单号串起来。

### L4 · 追问：InnoDB 的加锁规则是什么？
**答**：丁奇总结的四原则 + 两优化：① 加锁基本单位是 next-key lock（前开后闭）；② 访问到的对象才加锁；③ 等值查询向右遍历到第一个不满足等值条件的值，退化为**间隙锁**；④ 唯一索引等值命中，退化为**记录锁**。另有已知现象：唯一索引**范围查询**会锁到第一个不满足条件的值。

> **落回系统**：认领 SQL 的 WHERE（`status` + `batch_no`）必须走索引，否则会退化成锁全表——与 11 号「WHERE 条件必须走索引、禁止大事务」是同一条纪律，只是这次踩坑的后果是重复派发而不是慢查询。

**本链在系统里的落点**

| 场景 | 系统里的落点 | 依据 |
|---|---|---|
| 原子认领 | 一条 UPDATE 改状态 + 打号 + 记时间 | 一致性 12 §3.3 |
| 批次号 | 全局唯一、禁单机自增 | 一致性 12 §3.3 |
| 僵死回收 | 认领超时 → 待重试，按批次号整批定位 | 一致性 12 §4 |

## 🔥 追问链 07｜一次没走流程的 DDL 怎么把竞价页拖垮

> **场景锚点**：09 号根因：开市前 30 分钟运营对竞价标的表执行一次 **DDL（加字段）**，未走变更流程、未通知下游；Canal 对该 DDL 事件解析失败、消费线程退出、**位点停滞 22 分钟且无告警** → 缓存更新流静默中断 → 热点 key 过期击穿回源 → 主库 CPU 97%。【实证·场景】
>
> **考察意图**：能否把 MDL 锁的原理讲成一次「变更治理」事故，而不是只答「DDL 会锁表」。
>
> **依据指针**：`04-生产问题排查/09-竞价页面突然变慢-排查实录.md` §2.6 / §3.2 / §4.2~4.3

### L0 · 主问题：线上给一张表加个字段，为什么能把整个竞价页拖慢 20 倍？
**答**：两条链叠在一起。**数据库层**：DDL 需要 MDL **写锁**，增删改查自动持 MDL 读锁，读写互斥；一个未提交的长事务持有读锁，`ALTER TABLE` 就一直排队，后续新来的 DML 又排在 DDL 后面，形成「DDL 阻塞 DML 进而雪崩」——所以大表 DDL 才要 Online DDL / pt-osc / gh-ost。**系统层**（本例更隐蔽）：DDL 事件进了 binlog，Canal 解析失败直接退出、位点停滞，缓存更新流断了却没人知道，热点 key 陆续过期后击穿回源，开市峰值叠加把主库打满。

治理三条正好对应根因：L-1 **DDL 走变更流程、避开交易时段、提前通知下游消费方**；M-1/M-2 **Canal 位点停滞 >1min、命中率 <90% 告警**；L-2 **XXL-Job 定时对账**，Canal 挂了也能分钟级自愈。面试官问「怎么防再发」，答流程与可观测，别只答「加个 Online DDL」。

### L1 · 追问：意向锁、MDL、行锁在这条链路里分别卡在哪一层？
**答**：解决"**表锁与行锁的冲突判断**"。事务加行锁前先给表加意向锁；别人要加表锁时，只需看表上有没有意向锁，就知道有没有行锁，而不用逐行扫描。它是表级标记、不阻塞、只用于快速判断兼容性。

### L2 · 追问：MDL 锁是什么？为什么大表 DDL 会阻塞 DML？
**答**：MDL（元数据锁）保护表结构：增删改查自动加 MDL **读锁**，DDL 需要 MDL **写锁**，读写互斥。一个未提交的长事务持有 MDL 读锁，后面的 `ALTER TABLE` 拿不到写锁就一直排队，而后续新来的 DML 又排在 DDL 后面——造成"DDL 阻塞 DML、进而雪崩"。这是 `Online DDL` 与 `pt-osc/gh-ost` 要解决的问题。

> **落回系统**：这条是系统里最有说服力的变更治理案例：MySQL 没崩，崩的是**DDL 的下游消费者（Canal）没被纳入变更通知范围**——很多人排查到 MDL 就停了，其实真正的故障在缓存更新流。

### L3 · 追问：死锁怎么检测？怎么处理？
**答**：InnoDB 维护**锁等待图**，发现**环路**即判定死锁，**自动回滚事务量最小（undo 最少）的那个**，抛 1213 错误，让应用重试。查看 `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 定位是哪两条 SQL 互相持有对方要的锁。

### L4 · 追问：工程上怎么避免死锁？
**答**：① 按**固定顺序**访问多行/多表（不同事务锁序一致）；② 尽量**缩小锁范围**（精确索引、少用范围）；③ 控制事务粒度，事务内不穿插远程调用/长查询；④ 高并发热点可降级 RC（无间隙锁）或用锁等待超时 `innodb_lock_wait_timeout` 兜底；⑤ 应用侧捕获 1213 自动重试。

> **落回系统**：派发器按批次号固定顺序访问记录、事务里不穿插远程调用，就是把死锁概率压到最低；11 号的长事务 kill 与 12 号的短事务设计是同一目的。

## 🔥 追问链 08｜binlog 不只是复制，它是缓存与事件的源头

> **场景锚点**：09 号 §1.1：独立缓存服务（封装 Redis）由 **Canal 监听 binlog** 同步高频读数据；出价写入落库后用 **outbox 事务消息（Kafka）** 通知风控 / 财务 / 仓储。两条下游链的可靠性都押在「事务提交后 binlog 完整」上。【实证】
>
> **考察意图**：能否把 redo / binlog 两阶段提交从「主从复制知识点」升级成「我们系统的事件总线底座」。
>
> **依据指针**：`04-生产问题排查/09-竞价页面突然变慢-排查实录.md` §1.1 / §2.6；`02-现货贸易/01-业务与价值/02-业务全链路场景手册.md` 场景 3

### L0 · 主问题：你们说缓存由 binlog 驱动、下游靠 outbox 通知——那 redo 和 binlog 谁先谁后？崩在中间怎么办？
**答**：先讲系统为什么在乎：应用**只写 DB**，Canal 订阅 binlog 去刷独立缓存服务，outbox 事务消息（Kafka）通知下游；这两条链都要求「提交了的变更，binlog 一定完整且可解析」。MySQL 用**两阶段提交**保证这点：`写 redo(PREPARE) → 写 binlog → 写 redo(COMMIT)`。崩溃恢复时扫描 PREPARE 事务比对 binlog：**binlog 已写 → 提交**（从库 / Canal 会看到，主库必须有），**binlog 不存在 → 回滚**，已 COMMIT 直接提交。否则会出现「主库有、缓存和下游没有」或反过来。

边界：redo 是 InnoDB 层物理日志、循环写、管崩溃恢复；binlog 是 Server 层逻辑日志、追加写、管复制与恢复。**binlog 的具体格式属【待实测】，面试不主动报**；只答「两阶段提交保证不丢变更」即可，别把没核过的配置说成项目事实。

### L1 · 追问：为什么不能先写 binlog 再写 redo？Canal 会不会读到半截事务？
**答**：因为 redo 和 binlog 分属两层、**独立写入**，若一个成功一个失败，就会不一致：redo 成功 binlog 失败 → 主库有数据、从库没有（主从不一致）；binlog 成功 redo 失败 → 从库有、主库没有。两阶段提交让二者"要么都成功、要么都失败"。

### L2 · 追问：两阶段提交的具体流程？
**答**：
```
1. 写 redo log，状态 = PREPARE
2. 写 binlog
3. 写 redo log，状态 = COMMIT，事务提交成功
```

### L3 · 追问：崩溃后怎么判断该提交还是回滚？
**答**：扫描 redo 里的 PREPARE 事务，再比对 binlog：
- redo 是 PREPARE + binlog **不存在** → 回滚（redo 未提交，binlog 也没写，主从都无）
- redo 是 PREPARE + binlog **存在** → 提交（binlog 已写，从库会执行，主库必须提交保持一致）
- redo 是 COMMIT → 直接提交

> **落回系统**：09 号 Canal 解析 DDL 事件失败退出，恰恰说明 Canal 依赖的是**完整、可解析的 binlog 事件流**；崩溃恢复判据（PREPARE + binlog 存在 → 提交）保证 Canal 不会看到一个主库根本没有的事务。

### L4 · 追问：组提交（Group Commit）是什么？为什么能提性能？
**答**：两阶段提交里最贵的操作是 **fsync 刷盘**（redo 和 binlog 各一次）。组提交把**并发事务的 fsync 合并成一次**——多个事务的日志一起刷，分摊 fsync 开销，大幅提升写入吞吐。开启 `binlog_group_commit_sync_delay` 可进一步攒批。

### L5 · 追问：要"数据绝对不丢"，三个刷盘参数怎么配？
**答**：① `innodb_flush_log_at_trx_commit=1`（每次提交 fsync redo）；② `sync_binlog=1`（每次提交 fsync binlog）；③ `innodb_doublewrite=1`（防部分页写）。即"双 1 + 双写"最安全，代价是写入性能下降，通常用**组提交 + 批量刷盘**平衡。

> **落回系统**：资金 / 结算类动作不靠「绝对不丢」的口号：12 号的待发送表 + 阶梯重试 + 死信转人工才是业务层兜底。数据库双 1 是底座，最终一致是上层——两层分开讲，被追问「那还用不用 Outbox」就不会自相矛盾。

|---|---|---|
| 缓存更新流 | Canal 订阅 binlog → 独立缓存服务 | 排查 09 §1.1 |
| 下游通知 | outbox 事务消息 → Kafka | 业务全链路手册 场景 3 |

## 🔥 追问链 09｜读写分离都做了，主库为什么还被打满

> **场景锚点**：MySQL 双实例读写分离；09 号故障时「**从库反而很闲**」——列表类读被错配到主库做强一致读；应急 S-4 把列表查询临时切从库释放主库压力，M-4 把「明确哪些读必须主库」列为中期改进。11 号规范：读（列表 / 报表）走从库，写与写后读走主库。【实证·场景】
>
> **考察意图**：能否把主从延迟讲成一次「读路径治理」，并说清哪些读能容忍延迟。
>
> **依据指针**：`04-生产问题排查/09-竞价页面突然变慢-排查实录.md` §2.5 / §4.1 S-4 / §4.2 M-4；`11-网关扩容打穿DB` §7

### L0 · 主问题：你们做了读写分离，为什么故障时主库 CPU 97%、从库却很闲？
**答**：**做了 ≠ 用对了**。当时列表 / 报表这类读被统一配成主库「强一致读」，从库没接住流量；缓存击穿后回源风暴全砸在主库，CPU 97%、慢查询堆积、连接池等待 200+。应急 S-4 把列表查询临时切到从库（先确认这类读可容忍秒级延迟），主库立刻缓解；治本是 M-4 把**强一致读范围收敛**并写进规范：写后读、资金 / 结算类必须主库，列表 / 报表 / 历史类走从库，不靠每个开发临场判断。

原理收口：主从是异步复制，主库并发写、从库 SQL 线程串行回放，大事务 / DDL 会放大延迟；8.0 writeset 按事务冲突关系并行回放，同库不冲突也能并行。GTID 让切换后自动跳过已执行事务。**判据一句话：能容忍延迟的读才配走从库**——这条比背 `Seconds_Behind_Master` 有用。

### L1 · 追问：怎么判断哪些读能容忍主从延迟？
**答**：主库并发写（多线程），从库 **SQL 线程是单线程串行回放**，跟不上主库吞吐；大事务、DDL、从库自身负载也会放大延迟。监控指标 `Seconds_Behind_Master`。

### L2 · 追问：怎么解决主从延迟？
**答**：**并行复制**——5.7 按库并行（`DATABASE`），8.0 用 **writeset**（`WRITESET`）按事务冲突关系并行，同库不冲突的事务也能并行回放；配合拆分大事务、一主多从分流、只读从库。

### L3 · 追问：GTID 是什么？解决了什么问题？
**答**：GTID = `server_uuid:transaction_id`，为每个事务分配**全局唯一编号**。传统基于位点的复制在切换主从时要手动找 `File+Position`，容易错位；GTID 让从库能**自动跳过已执行的事务、续传未执行的**，主从切换和故障恢复更可靠。

> **落回系统**：09 号故障里「主库 CPU 97%、慢查询堆积，从库很闲」这个反差，就是读路径没梳理最直观的证据；面试讲这个现场，比复述 GTID 定义更能证明你看过线上大盘。

### L4 · 追问：异步、半同步、MGR 分别什么场景？脑裂怎么办？
**答**：异步不等确认、延迟小但可能丢数据；半同步等至少一个从库 ACK 才返回，降低丢数据风险（从库故障需降级异步避免阻塞）；MGR 用 Paxos 共识实现强一致+自动选主，需 3 节点。**脑裂**靠"过半仲裁"解决：网络分区后只有多数派能写，少数派自动降级只读，配合 fencing 强制旧主下线。

> **落回系统**：强一致读范围要写进规范（11 号 §7）。C 核心那条链更极端：内存为准、DB 只是最终一致副本，压根不参与这条读路径——别把两套一致性模型混着讲。

| 场景 | 系统里的落点 | 依据 |
|---|---|---|
| 读路径 | 列表 / 报表走从库，写后读 / 资金类走主库 | 规范 11 §7 |
| 应急 S-4 | 列表查询临时切从库 | 排查 09 §4.1 |
| 强一致读收敛 | M-4 读路径梳理 | 排查 09 §4.2 |

## 🔥 追问链 10｜「你们怎么分库分表的」是道陷阱题

> **场景锚点**：arch/07 §五写得很直白：本人 B2B 大宗平台实际落地的是**共用 MySQL 实例 + 按领域垂直分 schema（逻辑分库）+ 读写分离**，配 Snowflake 分布式 ID、ES 承接跨域检索、历史按时间归档；**物理分库分表为通用方案储备，未在本项目落地**。【实证】
>
> **考察意图**：敢不敢承认没做过，并把「为什么不做」讲成一次有依据的选型判断。
>
> **依据指针**：`03-架构决策/arch/07-数据库选型与分库分表.md` §五；`00-面试计划/06-一致性与异构.md` §2.1

### L0 · 主问题：你们交易量这么大，怎么做的分库分表？
**答**：**我们没做物理分片**，先诚实答这一句，再讲做了什么：按领域垂直分 schema（交易 / 订单 / 合同 / 结算逻辑分库）、读写分离、Snowflake 分布式 ID、跨域检索交给 ES、历史数据按时间归档缓解单表膨胀。判断依据是 B2B 交易量级远没到单库扛不住，先做减法（归档、索引、SQL 红线、缓存、读写分离）比引入分片中间件划算；**合同 / 交收是强关联域**，分片的跨库 join、事务、分页成本尤其不划算。

然后才展示储备（明确说「如果真到亿级我会这么做」）：垂直 vs 水平、分片键选最频繁等值条件、基因法解决按订单号与按用户 ID 双维路由、跨库 join 用应用层组装 / 字段冗余 / 宽表 / ES、跨库事务用 Outbox 而不是 XA、深分页用游标、扩容用双写 + canal 追增量 + 校验 + 灰度。**把「没做过」和「不会」分开，是这题的得分点。**

### L1 · 追问：那单表真到亿级了，你会怎么平滑迁？
**答**：垂直分库按**业务域**（用户库/订单库/库存库），垂直分表拆**大字段**到扩展表；水平分表是**同结构拆多张**，靠路由定位。垂直解决"表太宽/库太杂"，水平解决"行太多"。

### L2 · 追问：分片键怎么选？基因法是什么？
**答**：分片键选**最频繁的等值条件**（如 user_id），保证均匀、避免时间热点。**基因法**：订单号末尾嵌入 user_id 的哈希后缀，使订单既能按订单号直接路由、也能按 user_id 路由，解决"按 user_id 查订单却要全库扫"的痛点（电商经典）。

> **落回系统**：分片键若按业务单号哈希，会和 12 号「一条下游一条记录 + 批次号原子认领」打架——跨库的原子认领没了。所以真要分片，待发送表这类**一致性载体必须独立规划**，不能跟着业务表一起切。

### L3 · 追问：跨库的 join、事务、分页怎么办？
**答**：join——应用层组装 / 字段冗余 / 宽表 / ES；事务——XA（刚性慢）/ TCC / **本地消息表 + MQ（最终一致，最常用）**/ Saga；分页——各分片 limit 后归并，深分页用**游标翻页**。中间件：ShardingSphere-JDBC（客户端）/ Proxy、MyCat（服务端）。

> **落回系统**：本系统跨库事务不靠 XA：12 号 Outbox 管「只需送达」，05 号 Saga 管「必须补偿」，两者互补且常嵌套；讲这个分工，比背 ShardingSphere 配置更像架构师。

### L4 · 追问：怎么平滑扩容？
**答**：**双写 + 全量迁移 + 校验 + 灰度切换**：新老分片同时写，用 canal 订阅 binlog 追增量，`pt-table-checksum` 校验一致后灰度切读、再停旧库。取模分片**翻倍扩容只迁一半数据**，是常见低成本方案。

## 🔥 追问链 11｜为什么用 Canal，而不是让应用顺手删缓存

> **场景锚点**：09 号 §1.1：高频读数据（行情 / 挂牌列表）的缓存更新**完全由 Canal 解析 binlog 驱动**；故障正是这条链断了——位点停滞 22 分钟、无告警，命中率 98%→31%。11 号 M-4 列了「缓存对账兜底：XXL-Job 定时校验缓存与 DB 一致性」。【实证·场景】
>
> **考察意图**：能否讲清 binlog 驱动的一致性收益，以及它带来的**单点代价**怎么兜。
>
> **依据指针**：`04-生产问题排查/09-竞价页面突然变慢-排查实录.md` §1.1 / §2.4 / §4.2 / §4.3；`11-网关扩容打穿DB` §5

### L0 · 主问题：更新数据时为什么不让应用顺手删缓存，非要绕一圈 Canal？
**答**：多服务各自双写，会踩「两个请求交叉写导致缓存旧值」的坑；把一致性交给**数据库变更事件**驱动，应用只写 DB，解耦、可靠、可重放，这是主流做法。本系统里行情 / 挂牌列表的缓存就是 Canal 订阅 binlog 更新到独立缓存服务。

但代价必须一起讲：**这条链成了单点**。09 号故障里 Canal 解析一次未走流程的 DDL 事件失败退出、位点停滞 22 分钟且无告警，缓存更新流静默中断，热点 key 陆续过期没重建，命中率 98%→31%，击穿回源把主库打满。所以兜底是三层：**M-1 位点停滞 >1min 告警 + M-2 命中率 <90% 告警**（先能看见）、**M-3 本地 Caffeine 30s 二级缓存 + singleflight 回源保护**（Redis / Canal 全挂也能扛 30s）、**L-2 XXL-Job 定时对账自动重建**（分钟级自愈）。原理层再补 Cache Aside、延迟双删与穿透 / 击穿 / 雪崩的防线。

### L1 · 追问：Canal 挂了为什么表现为「变慢」而不是「数据错」？
**答**：**先删缓存**：删完、DB 未更新前，旧请求把旧值写回缓存 → 读到旧值；**先更新 DB 后删缓存**：更新完、删缓存前，读请求可能命中旧缓存 → 短暂读到旧值。二者窗口不同，主流是**先更 DB 再删缓存**，窗口更短。

### L2 · 追问：延迟双删是解决什么的？怎么用？
**答**：解决"**先更 DB 后删缓存**"仍可能出现的脏缓存：更新 DB 后删一次，**延时（如 1~2 秒）再删一次**，把并发写回的脏值二次清掉。是简单可靠的兜底，但不是银弹。

### L3 · 追问：生产里更推荐什么方案？
**答**：**canal 订阅 binlog 删缓存**：应用只写 DB，canal 解析 binlog 变更后异步删缓存。解耦、可靠、可重放，是主流大厂做法。核心思想：**一致性交给"数据库变更事件"驱动，而不是应用手动维护**。

> **落回系统**：09 号追问预案里有标准答案：Canal 只负责缓存更新，过期后回源 DB **数据仍正确，只是慢**；如果同步的是搜索 / 索引数据，才会表现为「数据错」。能分清「错」与「慢」，排障时就不会去重启 MySQL 白忙一场。

### L4 · 追问：缓存穿透、击穿、雪崩分别怎么防？
**答**：穿透（查不存在的 key 打穿到 DB）——布隆过滤器 / 缓存空值；击穿（热点 key 过期瞬间集中打 DB）——互斥锁重建 / 逻辑过期 / 热点不过期；雪崩（大量 key 同时过期/缓存宕机）——过期时间加随机抖动 / 多级缓存 / 限流降级。

> **落回系统**：本系统防雪崩是 TTL ±10% 抖动 + L1 本地 30s + L2 Redis + 熔断限流（11 号 §5），开市前还有缓存预热（09 号 L-3）——把开市当大促对待，这是 B2B 交易系统的节奏感。

## 🔥 追问链 12｜回源风暴为什么把主库 CPU 打到 97%

> **场景锚点**：09 号 §2.5：缓存失效 → 挂牌 / 行情列表查询回源大范围扫描 → 主库 CPU 97%、慢查询堆积、服务线程池打满、DB 连接池等待 200+；11 号护栏是连接池 20/实例、慢查询 1s kill、长事务 >5s kill、单查询 ≤200 条。【实证·场景】
>
> **考察意图**：能否把 Buffer Pool 冷热分区讲成「为什么缓存一崩 DB 就死」的正反馈链。
>
> **依据指针**：`04-生产问题排查/09-竞价页面突然变慢-排查实录.md` §2.5 / §3.3；`11-网关扩容打穿DB` §6.3 / §7

### L0 · 主问题：缓存一失效，为什么 MySQL 不是「慢一点」，而是直接被打死？
**答**：因为它是一条**正反馈链**：命中率 98%→31% → 回源请求放大几十倍 → 列表查询大范围扫描，把 Buffer Pool 里的热点页挤出 → 本来能命中内存的查询也变成磁盘 IO → 单条 SQL 更慢、连接占用更久 → 连接池（20/实例）被打满、线程全在等 DB → 更慢。09 号现场就是主库 CPU 97%、连接池等待 200+，而成功率仍 100%（慢而不报错，最容易被漏掉）。

原理收口：Buffer Pool 缓存数据页，读写都先经过它；**冷热分区**（新页先进冷区，停留超过 `innodb_old_blocks_time` 且被再次访问才晋升热区）正是为了防止**一次全表扫描把热点数据全挤走**。脏页由后台线程按 checkpoint / 比例 / 空闲页不足时刷回，刷盘风暴会叠加 IO 抖动。护栏的意义是**不让 DB 承受超过出口容量的流量**：连接池卡死、慢查询 1s kill、长事务 kill、单查询 ≤200 条。

### L1 · 追问：你说的「热点被挤掉」，在 InnoDB 里具体怎么发生的？
**答**：**冷热分区**（冷区约占 37%）：新读入的页先放**冷区头部**，只有被再次访问且停留时间 > `innodb_old_blocks_time`（默认 1000ms）才晋升热区。这样**全表扫描的一次性页不会挤掉热点数据**。

### L2 · 追问：脏页什么时候刷回磁盘？
**答**：不是每次更新都刷，而是由后台线程按需刷：redo log 空间水位触发的 **checkpoint**、脏页比例超过 `innodb_max_dirty_pages_pct`、Buffer Pool 空闲页不足、MySQL 空闲/关闭时。脏页过多会导致刷盘风暴、IO 抖动。

### L3 · 追问：怎么衡量 Buffer Pool 是否够用？
**答**：看**命中率**：`Innodb_buffer_pool_read_requests / (read_requests + read_ahead)`，命中率应 >99%。若命中率低且 `Innodb_buffer_pool_reads`（磁盘读）高，说明池太小或数据量超内存，需扩容或分库分表。

> **落回系统**：命中率在系统里有两层：**Redis 命中率 ≥90%**（11 号 §5，工程指标）与 **Buffer Pool 命中率 >99%**（原理层指标）。09 号故障先崩前者，再把后者拖下水；面试时把两层分开说，不会显得把缓存和 DB 混为一谈。

### L4 · 追问：为什么大表全表扫描会让系统变卡？
**答**：全表扫描会不断把新页读入 Buffer Pool，若无冷热分区保护，会把**热点页全部挤出**，导致后续热点查询全部落盘、整体变慢。冷热分区正是为此设计；也可用 `innodb_buffer_pool_size` 多 instance 降低争用。

> **落回系统**：应急 S-2「热点缓存预热」本质就是抢在回源风暴前把热点数据重新灌回缓存层，避免 DB 冷启动；这和 11 号「缓存命中率进看板」是同一件事的救火版与常态版。

|---|---|---|
| 放大链路 | 缓存失效 → 回源 → Buffer Pool 污染 → 更慢 | 排查 09 §3.3 |
| 护栏 | 连接池 20/实例、慢查询 1s kill、长事务 kill | 规范 11 §6.3 / §7 |
| 预热 | 开市前热点缓存预热 | 排查 09 L-3 |

## 🔥 追问链 13｜把批次号认领那条 UPDATE 讲到底（压轴）

> **场景锚点**：12 号 §3.3 认领 SQL 三件事一次做完：`状态=发送中`、`batch_no=本批次号`、`认领时间=当前时间`；判据是「改状态」与「打批次号」必须在**同一条 SQL**。提交后异步派发器才调下游，失败按 1s→2s→4s 阶梯重试、超限熔断进死信转人工，下游用业务幂等键去重。【实证】
>
> **考察意图**：能否把前面 12 条链串成一条线：一条 UPDATE 从进 MySQL 到落盘、到崩溃恢复、再到业务层最终一致。
>
> **依据指针**：`03-架构决策/一致性与异构/12-跨系统调用一致性方案.md` §3.3 / §4；`13-C核心单线程内存一致性设计.md`；`00-面试计划/06-一致性与异构.md` §2.1

### L0 · 主问题：把「派发器用一条 UPDATE 原子认领整批」从 SQL 进 MySQL 到落盘，完整讲一遍。
**答**：**业务侧**先取全局唯一批次号 → 执行带条件的批量 UPDATE（`WHERE status='待发送' AND batch_no IS NULL`）→ 事务提交 → 异步派发器按批次号取记录调下游 → 失败按 1s→2s→4s 阶梯重试、超上限熔断进死信并通知运营 → 下游用业务幂等键去重，「超时了不知道成功没有」变成可以放心重试的问题。

**MySQL 侧**：执行器按索引定位行（当前读 + X 锁 / next-key lock）→ 数据页读入 Buffer Pool（未命中则磁盘 IO）→ 写 undo（版本链，供回滚 / MVCC）→ 改内存页成脏页 → 写 redo(PREPARE) → 写 binlog（Canal / outbox 下游的事件源头）→ 写 redo(COMMIT) → 返回成功；数据页由后台线程异步刷盘，这就是 WAL「提交快」的原因。

**崩溃恢复**：重放 redo 前滚已提交事务（COMMIT 或 PREPARE + binlog 存在），用 undo 回滚未提交事务，回到崩溃前一致状态。再往上，12 号的幂等 + 对账保证业务层最终一致——**数据库保证「这条 UPDATE 生效一次」，业务保证「这次派发最终被确认」**，两层别混。

### L1 · 追问：这条 UPDATE 为什么必须是当前读？用快照读会怎样？
**答**：**当前读**。UPDATE 必须基于**最新数据**修改，且要加锁防止并发修改冲突；快照读（MVCC）读的是历史快照，不能用于更新基础，否则会丢更新。

### L2 · 追问：没有索引的 WHERE 条件下 UPDATE 会怎样？
**答**：InnoDB 行锁是**加在索引记录上**的，无索引时无法定位具体行，会**退化为全表扫描 + 锁全表所有行**（实际上锁住所有记录和间隙），并发极差、极易死锁。这是"WHERE 条件必须走索引"的根因。

> **落回系统**：认领条件 `status='待发送' AND batch_no IS NULL` 必须走索引，否则无索引 UPDATE 会退化成锁全表所有行和间隙——11 号「WHERE 必须走索引」在这条一致性链上是硬要求，踩了就是重复派发，不只是慢。

### L3 · 追问：redo log 满了会怎样？checkpoint 是干嘛的？
**答**：redo log 是**循环写**，`write pos` 追上 `checkpoint` 即"满了"，此时必须停下写入、强制把脏页刷盘以推进 checkpoint 腾出空间，导致写入卡顿。checkpoint 标记"哪些脏页已刷盘、对应 redo 可覆盖"，是 redo 循环复用的关键。

### L4 · 追问：从提交到"数据真正落盘"中间发生了什么？
**答**：事务提交只保证 **redo 落盘**（持久性），数据页仍在 Buffer Pool 是脏页，由后台线程异步刷盘。这就是 WAL（先写日志）的威力——提交快，因为只刷顺序的 redo，而非随机写数据页。

### L5 · 追问：崩溃重启后，这条 UPDATE 怎么恢复？
**答**：重放 redo log **前滚**已提交事务（redo 是 COMMIT 或 PREPARE+binlog 存在的），再用 undo log **回滚**未提交事务（redo 是 PREPARE 但 binlog 不存在），最终回到崩溃前的一致状态。

> **落回系统**：崩溃恢复后运营点重试，**只重放回写、按业务单号幂等 upsert，绝不重新撮合**（13 号 C 核心）；这与「认领只发生一次、回写可以重放无数次」是同一个思想在不同层的投影，压轴题收在这里最有分量。

**本链在系统里的落点**

| 认领 SQL | 一条 UPDATE 改状态 + 打号 + 记时间 | 一致性 12 §3.3 |
| 派发 | 1s→2s→4s 阶梯重试、超限转人工 | 一致性 12 §4 |
| 幂等 | 下游业务幂等键去重 + 定时对账 | 一致性 12 §2 / 主线件 06 |

## 新增高频题（现有题库缺失的补充）

### 补01 · 为什么索引列不建议用 NULL？
**答**：NULL 值参与比较需额外处理（IS NULL / 不等判断），优化器处理更复杂、部分场景索引失效；占用额外字节标志位。规范上建表 `NOT NULL DEFAULT`，把"空"语义用默认值表达。

### 补02 · EXPLAIN 的 key_len 有什么用？
**答**：`key_len` 是**实际用到的索引字节数**。通过它判断联合索引"用了几列"：如 `(name VARCHAR(20) utf8mb4, age INT)`，只匹配 name 时 key_len ≈ 20×4+2=82，再命中 age 会 +4。是验证最左前缀、定位索引没吃满的利器。

### 补03 · 索引的区分度/选择性怎么算？低于多少不建议建索引？
**答**：`区分度 = COUNT(DISTINCT col) / COUNT(*)`，越接近 1 越好。区分度极低的列（如性别、状态位）走索引收益小，优化器可能直接全表扫。经验：低于 20% 一般不单独建索引，可作为联合索引的辅助列。

### 补04 · 自适应哈希索引（AHI）是什么？
**答**：InnoDB 观察高频等值查询模式，自动在内存为热点索引页建**哈希索引**，等值查询 O(1)。无需人工干预，但只对**等值、热点、重复模式**有效，范围查询用不上。`SHOW ENGINE INNODB STATUS` 可看 AHI 使用情况。

### 补05 · 为什么 MySQL 不用跳表、也不把 B 树换成"更好的"结构？
**答**：见追问链 02 L5——介质决定结构。B+ 树把连续键紧凑塞进 16KB 页实现顺序预读 + 高扇出 + 矮树高，是为**磁盘随机 IO 贵**而生的最优解；跳表/红黑树等为内存设计，在磁盘上会退化为大量随机 IO。

### 补06 · 当前读 vs 快照读，最常见的"踩坑"场景？
**答**：RR 下，事务先 `SELECT`（快照读，看到旧值）再 `UPDATE`（当前读，基于最新值修改），改完再 `SELECT` 仍显示旧值——因为快照读复用同一 ReadView。**业务判断若依赖"我刚读到的值"，必须用 `SELECT ... FOR UPDATE`（当前读）**，否则会基于过期数据做决策。

### 补07 · undo log 空间一直涨怎么办？
**答**：定位长事务——`information_schema.innodb_trx` 查 `trx_started` 最早、`trx_rows_modified` 最大的事务；`SHOW PROCESSLIST` 找执行时间长的会话。根治：缩短事务、及时 COMMIT、事务内不做远程调用/大查询、设置 `max_execution_time`、监控 undo 使用率告警。

### 补08 · MDL 锁写锁的"雪崩"是怎么发生的？怎么避免？
**答**：长事务持 MDL 读锁 → DDL 申请写锁排队 → 后续所有 DML 申请读锁排在 DDL 后 → 业务读写全阻塞。避免：大表 DDL 用 **Online DDL（INSTANT/INPLACE + LOCK=NONE）** 或 `pt-osc/gh-ost`（影子表 + binlog 同步，不长时间持锁）。

### 补09 · InnoDB 为什么没有"锁升级"（lock escalation）？
**答**：InnoDB 行锁存在内存哈希表里，**内存开销可控**，无需像 Oracle/SQL Server 那样"行锁太多时升级成表锁省内存"。代价是可能锁大量行，但换来更细粒度的并发，这与其"行锁+MVCC 高并发"的设计目标一致。

### 补10 · 锁等待超时 和 死锁，有什么区别？
**答**：锁等待超时是**单边等待**超过 `innodb_lock_wait_timeout`（默认 50s），报 1205；死锁是**互相等待成环**，被死锁检测立即识别并回滚，报 1213。死锁是"等不到头"，超时是"等太久"；处理上死锁靠重试，超时靠排查慢事务。

### 补11 · redo log 为什么要设计成循环写、固定大小？
**答**：redo 只需保证"崩溃能恢复最近未刷盘的修改"，一旦脏页刷盘、对应 redo 就无用了，可覆盖复用。**固定大小 + 循环写**既省空间又性能稳定（顺序写、无需扩容），checkpoint 推进即可复用。

### 补12 · binlog 里的 XID event 是干什么的？
**答**：XID 是**事务提交标识**，用于两阶段提交时在 binlog 中标记事务边界。崩溃恢复时，redo 的 PREPARE 事务通过 **XID 去 binlog 里查找对应事务是否存在**，从而决定提交还是回滚——XID 是 redo 与 binlog 关联的桥梁。

### 补13 · 8.0 的 writeset 并行复制为什么比 5.7 强？
**答**：5.7 按**库**并行（不同库可并行，同库串行），单库热点无法并行；8.0 的 `WRITESET` 记录每事务**改动的行集合**，只要两个事务改的行不冲突就能并行回放，**同库内也能并行**，大幅提升单库从节点吞吐。

### 补14 · 半同步复制从库挂了会怎样？怎么兜底？
**答**：主库等不到从库 ACK，写入会**阻塞直到超时**（`rpl_semi_sync_master_timeout`），超时后**自动降级为异步**，从库恢复后再自动升回半同步。避免单点故障拖垮主库，是半同步的常见保护机制。

### 补15 · 怎么校验主从数据是否一致？
**答**：**pt-table-checksum** 对主库分块计算校验和，与从库对比定位不一致的表/块；不一致用 **pt-table-sync** 回补。预防：binlog 用 ROW 格式、启用 GTID、禁止在从库手工写数据、定期巡检。

### 补16 · 订单超时未支付自动取消，数据库层面怎么做？
**答**：不要靠"实时扫描全表"。主流：**延迟队列/RocketMQ 延迟消息**投递超时事件，或**定时任务扫"已创建且超时"的订单**（状态 + 过期时间建索引，分批游标扫描），配合状态机流转 + 幂等取消 + 库存回补。核心：**按过期时间索引、增量处理、幂等**。

### 补17 · 排行榜/点赞数这种场景，MySQL 合适吗？
**答**：高频写、实时排序、读多写多，MySQL 压力大。更优：**Redis ZSet**（天然有序、O(log N) 写、实时 rank）。MySQL 做持久化兜底，Redis 做实时榜单，异步落库。能答出"不同数据结构选不同存储"是加分。

### 补18 · 热点行高并发更新（如库存/余额）怎么优化？
**答**：① 把单行**拆成多行**（如库存拆 10 份，随机取一行扣减，再汇总）；② **排队削峰**（MQ 串行化）；③ **合并批量更新**；④ 适当降级 RC、关死锁检测、锁超时兜底；⑤ 余额类用**流水表 + 汇总**替代单行频繁 UPDATE。核心：**分散热点，避免单行串行成为瓶颈**。

### 补19 · 读写分离下，写完立刻读主从延迟导致读到旧数据怎么办？
**答**：一致性敏感场景**强制走主库**（如"写后立即读"）；或用**路由标记**（会话内写后 N 秒内读主）；或**读从库+版本号校验**；长期靠**降低主从延迟**（并行复制、拆分大事务）。核心原则：**能容忍延迟的读才走从库**。

### 补20 · 分库分表后，唯一性约束（如手机号唯一）怎么保证？
**答**：分片后单库唯一索引失效，需全局唯一：① 用**唯一列作为分片键**（按手机号哈希分片，天然唯一）；② 若不能，用**全局唯一表/Redis 预占**（先抢唯一性再写）；③ 应用层先查后写 + 唯一表兜底。能指出"分片键选择与唯一性约束冲突"这一根本矛盾是加分。

### 补21 · 账户余额并发扣减，怎么保证不超扣、不丢更新？
**答**：`UPDATE balance = balance - ? WHERE id=? AND balance >= ?` 条件更新，**受影响行数=0 则重试/拒绝**（乐观锁思路，本质是"读-判断-写"变原子条件更新）；或用行锁 `SELECT ... FOR UPDATE`。**绝不能**先 SELECT 判断再 UPDATE（非原子，并发下超扣）。

### 补22 · 为什么金额字段要用 DECIMAL 而不是 FLOAT/DOUBLE？
**答**：FLOAT/DOUBLE 是**二进制浮点**，无法精确表示十进制小数（如 0.1），运算有误差；DECIMAL 是**定点精确存储**，适合金额。金额用 `DECIMAL(18,2)`，运算在应用层用 BigDecimal 或整数分，避免浮点误差。

### 补23 · DATETIME 和 TIMESTAMP 怎么选？
**答**：TIMESTAMP 是 4 字节、带时区、范围到 2038 年（**2038 问题**）；DATETIME 是 8 字节、范围大、不含时区。需要精确记录到远未来或不受时区转换影响时用 DATETIME，需要毫秒用 `DATETIME(3)`。8.0 后默认推荐 DATETIME。

### 补24 · 一条 SQL 为什么"时快时慢"？
**答**：可能原因：① **缓冲池命中波动**（冷数据第一次查慢，热了变快）；② **脏页刷盘/checkpoint** 导致的 IO 抖动；③ **锁等待**（被别的事务阻塞）；④ **执行计划变化**（统计信息更新后换了索引，甚至走错索引）；⑤ 网络/连接池抖动。排查：`SHOW PROCESSLIST` 看状态，`EXPLAIN` 对比执行计划，慢日志看是否同一条 SQL 波动。

### 补25 · MySQL 的 IO 是同步还是异步的？
**答**：8.0 之前 InnoDB 用**原生 AIO（异步 IO）**，可并发发起多个磁盘请求；Windows 等平台用模拟 AIO。异步 IO 让多个页的读写并行，减少等待。能答出"IO 模型"层面属于进阶加分。

### 补26 · 为什么说"不要用 SELECT *"？
**答**：① 多读无用列，**大字段**会触发 off-page 额外 IO；② 破坏**覆盖索引**，导致回表；③ 增加网络与内存开销；④ 表结构变更时结果集列数变化，代码脆弱。应**只 SELECT 必要列**，最好走覆盖索引。
