# Canal 弱项深度整理（面试补充版 · 按本项目技术栈）

> **定位**：Canal 是「变更通道」，不是「一致性方案」。讲弱项时先承认边界，再讲我们在这套栈里怎么放置它。
> **项目口径**：本项目的业务中台是**服务化拆分**——12+ 个独立部署的业务服务（平台后端整体 40+ 子系统），服务间经自研 DS 总线 RPC 与 Kafka 事件通信，未用 Spring Cloud。Canal 的消费方是**独立部署的缓存调度服务**，不是某个业务服务。下文所有「服务」指的都是这些真实部署单元。
> **口径标记**：`【实证】` 有记录可复述 ｜ `【推演·实录】` 基于真实架构的典型场景，回答时说明「我们架构下会这样」，不冒充亲历 ｜ `【设计口径】` 来自架构设计文档，代码与线上是否一致待核实 ｜ `【待确认】` 资料之间有冲突或缺口。

## 〇、先对齐项目技术栈（面试前必读）

| 层 | 现网组件 | 与 Canal 的关系 |
|---|---|---|
| 接入层 | **midservice** 自研网关（Java Web，多实例）+ midmon 监控 | 不直接涉及 Canal |
| 业务层 | **服务化拆分**：12+ 个独立部署的业务服务（用户、商品、交易、合同、履约、结算、通知、配置等），服务间走 DS 总线 RPC（Hessian）与 Kafka 事件 | Canal 订阅的 binlog 来自这些服务对应的 schema |
| 异构桥接 | **DS 数据中心**（dataShare，防腐层）：Hessian over HTTP（同步）+ Socket 长连接（异步） | 撮合结果不经过 Canal，走 DS |
| 撮合层 | **C 撮合引擎**，单线程内存撮合 | 不经过 Canal |
| 缓存层 | **独立缓存调度服务**（Java，独立进程）+ **Redis**（部署形态待确认） | Canal 的唯一下游消费方 |
| 数据层 | **MySQL 双实例**（主写、从读，半同步复制）；按领域垂直分 schema、共用一个实例（逻辑分库） | Canal 的数据源 |
| 消息 | **Kafka** 为统一 MQ；跨模块或跨进程事件用 **Outbox** 本地消息表 | Canal 可能参与 outbox 中继，待确认 |
| 其他 | Redisson（分布式锁）、XXL-Job（调度）、MinIO（对象存储）、Drools（规则） | — |

**三条口径纪律**：
1. 对外说「**独立缓存调度服务**封装 Redis」，不说「我们用 Redis 做缓存」。
2. 业务侧说「**12+ 个独立部署的服务（微服务式拆分）**，按限界上下文划分，自研 DS 总线治理」，不说「模块化单体」。`【已确认】` 2026-10-25 对齐：后端 40+ 子系统独立部署、走网络调用，属服务化拆分；「模块化单体」仅是《01-架构方法论》下篇的绿地设计建议，不代表现网。
3. 不说「Feign 直调」。服务之间靠 DS 总线 RPC（Hessian）与 Kafka 事件通信，缓存更新走独立调度服务。

> **Spring Cloud / Feign / Nacos 的使用范围**：`【已确认】` 现网三者均未使用（2026-10-25 对齐）。相关声明已从全部简历、底稿与备战材料清除；`01-架构方法论` 中的 Nacos 属绿地设计方案，非现网。现网服务寻址 = DB 配置表（TB_DS_PROTOCOL / TB_DS_REGISTEERED_SERVICE）+ 命令号路由，无心跳动态发现；被问服务发现就这么答。

## 一、博文明确提到的弱项

1. **同步链路有开销**：博文用 Canal 监听 binlog 后，再通过 Feign 调用服务更新缓存，调用链有性能消耗，作者建议引入 Kafka 解耦。
2. **额外运维组件**：需要单独部署 canal-server，并维护 `instance.properties` 等配置。
3. **强依赖数据库配置**：MySQL 必须开启 binlog 且格式为 `ROW`；canal 账号需要 `SELECT, REPLICATION SLAVE, REPLICATION CLIENT` 权限，缺一项就无法同步。

> **对照本项目**：我们没有走「Canal → Feign 直调业务服务」的路线，而是 Canal → 独立缓存调度服务 → Redis。调用链上少了一次跨业务服务的 RPC，但多了一个必须单独监控的调度进程。博文第 1 条的问题，我们靠「缓存调度服务收口」规避，代价是故障面多一层。

## 二、补充弱项，按本项目落地

### 2.1 变更源侧

**① 多库订阅，DDL 面广**
业务中台按领域分 schema（共用一个 MySQL 实例），Canal 要订阅多个 schema 的 binlog。两种做法各有代价：一个 instance 订阅多个库，DDL 在任一库上解析失败都会卡住整条流；每库一个 instance，运维对象变多。
**本项目的应对**：`【待确认】` 当前是一个 instance 还是按库拆分，资料里没有写明。面试时要能说清 DDL 出现在哪个库，影响面就限定在该库对应的缓存上。

**② 连接主库还是从库**
我们是 MySQL 双实例（主写从读）。Canal 连从库，主从延迟会直接叠加到缓存延迟上；连主库，又会给主库增加一个 dump 连接。主从切换时，位点如何接续也需要单独处理。
**本项目的应对**：`【待确认】` 当前 Canal 的连接对象和切换预案。

**③ 只做增量，没有全量**
新表或新缓存接入时，要先做全量预热，再从某个 binlog 位点接续增量。位点接错会丢数据或重复数据。Debezium 自带 snapshot 阶段，这是它的优势。
**本项目的应对**：`【待确认】` 资料中没有记录全量预热流程，需要补一份。

### 2.2 语义侧

**④ 至少一次投递**
客户端 ack 后位点才前进。缓存调度服务处理成功前宕机，或 HA 切换时，同一批 binlog 会被重复投递。
**本项目的应对**：缓存删除天然幂等，重复删除无害；缓存调度服务用 Redis `SETNX` 做去重标记（与异构手册 §二 的可靠投递设计一致）。`【设计口径】`

**⑤ 有序性受限**
同一 instance 内 binlog 有序，但多线程消费会打乱顺序；MQ 模式下要按主键 hash 分区才能保证同一记录有序，跨库、跨表没有全局顺序。
**本项目的应对**：缓存失效只关心「某个 key 最终被删掉」，不依赖跨表顺序。需要顺序的业务（如履约状态机）不走 Canal，走模块内事务和 Kafka 按业务键分区。

**⑥ 它只是变更通道，不是一致性方案**
Canal 只保证「变更最终会被收到」，不保证读写一致。
**本项目的应对**：资金类不以缓存为准，走 DB 为准 + 对账兜底（`06-一致性与异构` 口径）。

### 2.3 解析侧

**⑦ DDL 是最脆弱的环节（本项目的真实痛点）**
Canal 解析 DDL 依赖自己维护的表结构元数据。遇到未覆盖的 DDL 语法或版本不兼容时，解析线程退出，位点停住，默认无告警。
**本项目的应对**：DDL 纳入发布管控，交易时段冻结表结构变更；位点延迟监控 + 中断告警。详见第四节。

**⑧ 大事务**
模块内的批量更新（如一次更新百万行的结算调整）会整体进入解析内存，可能 OOM，也会造成延迟抖动。
**本项目的应对**：批量更新分批执行、限速，避免单条 SQL 产生超大事务。

**⑨ 版本兼容要查矩阵**
GTID、MySQL 8.x 新特性、新认证方式，不同 Canal 版本支持程度不同。
**本项目的应对**：`【待确认】` 资料中没有记录 Canal 与 MySQL 的具体版本。

### 2.4 运维与生态侧

**⑩ 过滤与转换弱**
过滤只能基于库表正则，没有字段级过滤和转换。表结构演进后，缓存调度服务要自己兼容新旧字段。
**本项目的应对**：调度服务只消费白名单库表，字段映射在调度服务内处理。

**⑪ 可观测性自建，社区偏慢，SDK 以 Java 为主**
消费延迟要自己算（binlog 事件时间戳与当前时间之差）。官方监控有限，需要自建 exporter 和告警。
**本项目的应对**：我们的调度服务本身就是 Java，客户端不是问题；延迟、命中率、回源 QPS 三个指标联动告警（第五节）。

## 三、缓存链路与边界

### 3.1 链路
```
业务写（模块库，MySQL 主库）
   │ 事务提交
   ▼
MySQL binlog ──► Canal ──► 独立缓存调度服务 ──► Redis ──► 行情 / 挂牌列表读
                              │
                              └─ 去重（SETNX）+ 删除/刷新 key + 失效重试
```
- **为什么包一层调度服务**：业务与缓存隔离、读加速、协议屏蔽。替换 Redis 集群或换缓存实现，业务代码无感。`【实证】` `00-面试计划/08` Q16。
- **为什么不让模块直接删缓存**：多个模块共享同一批缓存 key 时，删缓存的逻辑会散落在各模块里，漏删一处就是不一致。由调度服务统一收口。`【设计口径】`

### 3.2 失效口径
- **先写 DB，成功后由 Canal 异步失效缓存**。不能先删缓存再写，否则写失败会回源到旧数据（`02` Q17）。
- **击穿**：热点 key 不过期 + 后台刷新，或互斥重建 / 逻辑过期（`08` Redis 表）。
- **雪崩**：TTL 加抖动，多级缓存分散压力。
- **穿透**：空值缓存 + 布隆过滤器。
- **一致性级别**：行情类允许秒级不一致；资金类不以缓存为准，走 DB 为准 + 对账（`09` P1 #21）。

### 3.3 覆盖范围：Canal 管什么，不管什么
- **Canal 管的**：行情、挂牌列表等慢变高频读数据（`02` 架构图）。
- **Canal 不管的**：
  - 撮合结果、最优价、出价记录、成交流水：强一致、毫秒级变化，不可缓存，由 DS → C 撮合和 WebSocket 事件驱动（`竞价详情页轮询改造` 方案 §五）。
  - 模块之间的业务事件：走模块内 Spring Events 或 Outbox + Kafka，不走 Canal。
- **低频展示数据**：场次状态、公告、费率走网关层缓存（PUB / FRM，TTL 5–60s）。`【待确认】` 这类缓存的失效是 Canal 驱动还是事件驱动，底稿只写了「事件同时触发网关缓存失效」。

> **面试中的关键区分**：被问「Canal 延迟大，为什么不用它推实时行情」时，答法是：Canal 是秒级的缓存失效通道，适合慢变数据；强一致实时数据本来就不应该走缓存，我们用 DS 和事件推送。

### 3.4 Redis 部署形态（口径冲突，待确认）
- `05-缓存系统设计` 底稿写的是「单机 / 主从 Redis + Redisson，未使用大规模集群」。
- `01-架构方法论` 设计口径是「哨兵模式（1 主 2 从 3 哨兵），中后期集群」。
- `02-异构架构手册` 写的是「Redis 集群」。

面试时只能说一种。`【待确认】` 以线上实际为准，建议统一为「哨兵模式」或「主从」，并注明是否已迁移集群。

## 四、故障复盘：DDL 导致 Canal 位点停滞（竞价变慢）

> **标签说明**：`02-项目叙事-B2B` §5.5 标为【推演·实录】；`07-JVM与线上排查` 标为【实证】，并写「本人在现场」。两处口径冲突，`【待确认】` 面试前统一。

### 4.1 现象
- 竞价专场开市约 15 分钟后，页面变慢，成功率仍是 100%，典型的「慢而不报错」。
- 竞价查询接口 P99 从 150ms 涨到 3.2s，P99.9 达到 8s；主库 CPU 97%。
- 竞价页面高频读两类数据：行情 / 挂牌列表走 Canal → 缓存调度服务 → Redis；最新出价走 DS → C 撮合；标的详情走 MySQL（`竞价页面突然变慢` 实录 §1.1）。

### 4.2 排查路径（逐层定界）
1. **链路拆分**（traceId）：网关 20ms、DS→C 撮合 45ms、MySQL 查询 2950ms，瓶颈收敛到 DB。
2. **排除嫌疑**：GC 日志正常，C 引擎 TPS 与队列深度平稳，所以「竞价慢」其实是「查询慢」。
3. **缓存层**：缓存命中率从 98% 跌到 31%。
4. **根因**：开市前有人对标的表加字段，走了 DDL 但没走变更流程；Canal 解析失败，线程退出，位点停滞 22 分钟，且无告警。
5. **放大**：缓存更新流断开，热点 key 过期后直接回源、无并发保护，叠加开市峰值，击穿打到主库。

### 4.3 处置与治本
- **应急**：重启 Canal 校正位点，热点缓存预热，非核心查询降级，约 30 分钟恢复（`07` §1.2 A）。
- **治本三件**：
  1. Canal 位点延迟监控 + 缓存命中率告警；
  2. 热点 key 二级缓存 + 回源并发保护（互斥重建 / 逻辑过期）；
  3. DDL 变更纳入发布管控，交易时段冻结表结构变更。
- **分 schema 隔离下的启示**：DDL 发生在哪个 schema，影响面就限定在该 schema 对应的缓存上。这一点要能讲清楚，它也是按领域隔离的价值。

### 4.4 面试时的说法
> 这个案例是我们架构下的典型场景，我参与了治理方案和规范落地；现场处置是值班同学做的。（`02` §8 建议的说法。`【待确认】` 需与你的实际参与程度核对后再用。）

## 五、三连问：为什么用 / 怎么失败 / 怎么观测

### 5.1 为什么用
- 业务模块只管写本库，缓存更新与业务解耦（`09` P1 #22）。
- 缓存调度服务屏蔽 Redis 协议，换缓存实现业务无感（`02` Q16）。

### 5.2 怎么失败

| 失败模式 | 表现 | 处置 |
|---|---|---|
| 位点停滞（DDL 解析失败） | 缓存不更新，命中率下降 | 重启校正位点，DDL 流程管控 |
| 调度服务宕机 | 同上，Canal 位点不前进（会积压） | 进程存活探测 + 中断告警 |
| HA 切换 / 重启回放 | 少量重复消费 | 删缓存幂等，SETNX 去重 |
| 缓存删除失败 | 旧数据留存直到 TTL | 删除重试 + TTL 兜底 |
| 缓存整体失效 | 回源打爆 DB | 本地缓存 30s 逃生 + singleflight / 限流 + 从库分流 + 定时对账（`07` §5） |

### 5.3 怎么观测
- **位点延迟**：binlog 事件时间戳与当前时间之差，超阈值告警。
- **缓存命中率**：目标 90% 以上（`09` P1 #20）；骤降是最直接的信号。
- **回源 QPS 与 DB CPU**：命中率下降时两者同步上涨，用于确认影响面。

## 七、面试怎么答

### 7.1 30 秒版
> Canal 的弱项我分三类讲。变更源上，它只做增量、只支持 MySQL，我们是按领域分了多个 schema（共用实例），要订阅多个库，DDL 面更广；语义上，它是至少一次投递，下游必须幂等；解析上，DDL 最脆弱，我们在竞价场景踩过一次 DDL 导致位点停滞的情况。我们的做法是：Canal 只服务慢变的展示类缓存，资金类不以缓存为准，竞价实时数据走 DS 和 WebSocket 事件；DDL 纳入发布管控，位点延迟和命中率双告警。

### 7.2 常见追问

| 追问 | 答 |
|---|---|
| 你们是微服务吗？ | 是服务化拆分：12+ 个业务服务独立部署、按限界上下文划分，服务间走自研 DS 总线 RPC（Hessian）与 Kafka + Outbox，没有用 Spring Cloud 的注册中心体系；数据层按领域分 schema、共用 MySQL 实例。`【已确认】` 2026-10-25。 |
| 为什么数据层不分实例？ | 按领域分 schema 已经切开了写入边界与契约，跨域一律走服务接口/事件，不存在跨 schema join 的场景；物理共实例省掉跨实例分布式事务和一套库的运维成本。容量到顶时把热点 schema 平移到独立实例即可，服务代码不用动。 |
| 为什么不用 Debezium？ | 只有 MySQL、团队已有 ZK 运维经验时，Canal 成本更低；要多库异构或全量快照，Debezium 或 Flink CDC 更合适。 |
| Canal 挂了怎么办？ | 位点延迟监控和中断告警先发现；应急是重启并校正位点、预热热点；缓存整体失效时，本地缓存逃生加回源保护，不让 DB 被打穿。 |
| 多个 schema 的 binlog 怎么订阅？ | `【待确认】` 说清当前是单 instance 还是按 schema 拆 instance；DDL 按 schema 隔离的影响面。 |
| Canal 能保证强一致吗？ | 不能。它只保证变更最终被收到。资金类以 DB 为准，靠对账兜底。 |
| 竞价为什么不用 Canal 推最优价？ | 最优价强一致、毫秒级变化，不可缓存，改为 DS 撮合结果 + WebSocket 事件驱动。 |
| 博文用 Feign 更新缓存，你们为什么不这样做？ | 直接调用会把缓存更新耦合进消费线程，调用链变长；我们用独立调度服务收口，业务模块只写本库。 |

### 7.3 红线
- 不说「模块化单体」（与源码走读矛盾：后端 40+ 子系统独立部署、走网络调用，且自贬架构规模）；说「12+ 个独立部署的服务，微服务式拆分，自研 DS 总线治理」。
- 不说「我们用 Redis 做缓存」，说「独立缓存调度服务封装 Redis」。
- 不说「Canal 保证缓存一致」，说「最终一致，资金类以 DB 为准」。
- 不把 22 分钟事故说成亲历，除非与 `07` 的口径统一之后再用。
- 不说「Redis 性能高所以用 Redis」，说缓存的是什么数据、key 怎么设计、过期怎么定、失效后怎么回源、挂了怎么降级。

8. **Outbox 中继**：是 XXL-Job 轮询还是 Canal 监听 outbox 表投递 Kafka。`08-电商` 文档里两种说法都有。
9. **全量预热流程**：新表接入 Canal 时的全量与增量衔接方式，没有文档。
10. **命中率统计口径**：`09` 的目标 90%，事故中的 98% → 31% 来自哪个统计位置。
