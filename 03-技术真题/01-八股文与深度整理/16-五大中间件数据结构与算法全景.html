三条判据（后面反复用）

  1. 随机 IO 贵、顺序 IO 便宜 → 一切结构都在把随机变顺序：B+ 树用有序叶子、WAL 用追加、segment 用不可变、MinIO 用流式分片。
  2. 内存易失、磁盘可信但慢 → 一切持久化都在做「追加日志 + 校验 + 周期性合并」：redo / AOF / translog / journal / xl.meta 是同一件事的五个名字。
  3. 内核态切换、锁竞争、上下文切换贵 → 一切高性能都在做「批处理 / 零拷贝 / 用户态缓存 / 单线程或分片无锁」：Redis 单线程、ES 靠 page cache、MinIO 靠 O_DIRECT、MySQL 靠 group commit。

面试第一句话建议这么说：「这五个不是一个维度的东西，MySQL 和 MongoDB 是要把数据存对，Redis 是要把数据放在离 CPU 最近的地方，ES 是要按内容找数据，MinIO 是要按字节流存大文件。结构差异的根因是查询谓词形态不同，不是谁比谁先进。」

讲这句前先补一句「其中 MongoDB 我们没上，我是拿它做结构对照的」——否则很容易被顺势追问「那你们分片键怎么选的」「WT cache 调过没」，接下来就得靠编故事圆了。

01 坐标系：操作系统给的四条硬约束

1.1 约束一：分层存储的速度差是数量级的，不是百分比

CPU 看内存是「隔壁」，看磁盘是「跨城」。更狠的是同一块盘上随机读和顺序读的差距：机械盘随机读要寻道（~5–10 ms），顺序读能跑满 100–200 MB/s；NVMe 把随机延迟压到 ~50–100 µs，但顺序带宽仍是 3–7 GB/s。所以：

  • 数据结构的第一目标不是「时间复杂度 O(log n) 比 O(n) 好看」，而是 减少随机 IO 的次数。B+ 树 3~4 层能扛上亿行，就是因为把「27 次随机读的二叉树」压成了「3 次」。
  • 写路径的第一目标不是「写得快」，而是 把随机写改写成顺序追加。这就是 WAL 存在的唯一理由。

1.2 约束二：OS 用 4KB 页管一切，缓存权归谁是个设计选择

内核以 4KB 页管理内存与块设备，读文件先进 page cache，read() 可能只是内存拷贝；写文件默认只是写进 page cache 就返回，真正的落盘靠内核 writeback 或应用显式 fsync()。于是每个中间件都要回答一个问题：

缓存交给 OS，还是自己管？

  • 交给 OS（ES/Lucene 用 mmap）：省一次拷贝、热数据自动缓存、重启后缓存还在；代价是内存不受控、被别的进程挤掉、swap 一来直接雪崩。
  • 自己管（MySQL Buffer Pool、WiredTiger cache、O_DIRECT）：淘汰策略可控、不会双缓存浪费、能按业务语义预读；代价是要自己实现 LRU、checkpoint、预热。
  • 完全不靠磁盘缓存（Redis）：数据本来就在内存，OS 只在 RDB/AOF 时帮忙。

这三种态度是本文最有价值的横向对照（§07.2 图 7）。顺带一提，MySQL 的 double write buffer 就是被「OS 4KB 页 vs InnoDB 16KB 页」逼出来的：断电时一个 16KB 页可能只写成功前 4KB（partial page write），redo log 记的是页内变更，在残缺页上重放会越修越坏。所以先顺序写一份完整页镜像到 doublewrite 区，再写真实位置。

1.3 约束三：陷内核、切上下文、抢锁，都要付 µs 级门票

一次 read()/write() 是系统调用，一次线程切换要保存恢复寄存器与 TLB，多核抢一把锁会引发缓存行在核间弹跳。当单次操作本身只有几 µs 时，这些开销反而成了主体。于是：

1.4 约束四：内存易失，网络不可靠

进程被 kill -9、机器掉电、盘上一块扇区静默损坏（bitrot）、网络分区后两边都认为自己是主 —— 这些不是异常，是常态假设。于是：

  • 持久性：日志必须 fsync 才能算「已提交」，所以 fsync 次数直接决定写 TPS 上限，组提交（group commit）就是把多个事务攒成一次 fsync。
  • 完整性：校验和（InnoDB page checksum、MinIO HighwayHash、WT checksum）用来发现静默损坏；多副本 / 纠删码用来修复。
  • 一致性：quorum、任期号（term/epoch）、栅栏令牌，防止脑裂后的旧主继续写。

这一节要背下来的就一句：「MySQL 的 redo、Redis 的 AOF、ES 的 translog、Mongo 的 journal、MinIO 的 xl.meta，本质是同一条 WAL 不变量的五种实现。」

02 MySQL／InnoDB：把随机 IO 变成顺序 IO 的账本

2.1 场景与要解决的问题

场景：钱、货权、合同状态这类不能错、要能改、要能查范围、要能多表关联的数据。ACID 是硬需求，磁盘是最终真相，内存只是加速器。

三个互相打架的目标：① 点查要快（希望索引）；② 范围/排序/关联要快（希望有序）；③ 写入要快且崩溃不丢（希望追加）。B+ 树解决前两个，WAL 解决第三个，Buffer Pool 把两者粘起来。

2.3 为什么是 B+ 树，而不是别的

候选为什么被淘汰关键代价算式
哈希表等值 O(1) 很香，但 > BETWEEN ORDER BY 直接失效；扩容要全表重哈希范围查询退化为全表扫 O(N)
二叉搜索树 / 红黑树每节点只有 2 个分支，1 亿行要 ~27 层 = 27 次随机 IOHDD 上 27 × 8ms ≈ 216 ms/次点查
跳表内存里很好（Redis 在用），但节点大小不贴磁盘页、指针不局部，预读失效每层一次随机 IO，且无法用页批量
B 树非叶也存整行 → 扇出骤降（~80），树高 5 层；范围查询要中序遍历跨层多 2 次随机 IO + 路径不稳定
LSM 树写吞吐更强，但读放大（多层查找 + bloom）、后台 compaction 占 IO、范围更新与事务实现复杂读放大 10–50×；InnoDB 定位是读写均衡 OLTP，不是写吞吐怪兽
B+ 树（选中）非叶纯导航、叶子有序且双向链表，点查 H 次、范围 H + 顺序扫1 亿行 H≈3，根常驻内存 → 实际 2~3 次 IO

为什么 redo 是环形追加而不是也用 B+ 树：因为写一条事务如果先去改 B+ 树页，可能触发页分裂、多个随机位置的脏页回写；而追加日志只有一次顺序写 + 一次 fsync。日志记的是「输入」，页记的是「状态」——把状态更新推迟到 checkpoint/刷脏，就把随机写摊平了。这正是 §01.3 那条不变量。

为什么 undo 用版本链而不是直接覆盖：MVCC 要求「旧版本还在」，于是每次更新把旧值串进 undo 链，行的隐藏列 DB_ROLL_PTR 指向它。代价是长事务会让 purge 线程追不上、undo 表空间膨胀 —— 这是「读不阻塞写」的账单。

03 Redis：把全部数据结构塞进 CPU 缓存行

3.1 场景与要解决的问题

场景：会话、热点缓存、计数器、排行榜、限流、分布式锁、轻量消息队列。共同点是数据量能放进内存、访问要亚毫秒、一次操作只碰一两个 key、不需要多表关联。

要解决的不是「存得下」，而是「每次操作少付多少 CPU 与 syscall」。当一次 GET 本身只有几 µs，一个指针追逐造成的 cache miss、一次线程切换、一次系统调用都会成为主要成本。所以 Redis 的每条设计都在做同一件事：减少内存碎片、减少指针追逐、减少锁、减少 syscall。

3.2 用了哪些数据结构与算法（逐个说透）

① SDS（Simple Dynamic String）：len / alloc / flags / buf[] 头部 + 字节数组。相比 C 字符串：O(1) 取长度、二进制安全（不靠 \0 截断）、自动扩容且预留空间（小于 1MB 翻倍，超过按 1MB 增量），避免每次 append 都 realloc。为什么：缓存 key/value 绝大多数是短字符串，一次 strlen 的 O(n) 与一次 realloc 都是无谓成本。

② dict（哈希表）：两个 dictht 数组 ht[0] / ht[1]，链地址法解决冲突，哈希函数用 SipHash 系（抗哈希洪泛攻击）。负载因子 ≥1（无后台子进程时）或 ≥5（有 BGSAVE/BGREWRITE 时，避免 fork 期间扩容放大 COW）触发扩容到 ≥2× 的 2 的幂。

渐进式 rehash 是这里的重点算法：一次性搬完整张表会造成秒级停顿（单线程，整个世界都卡住）。做法是把搬运摊到每次增删查改上：维护 rehashidx，每处理一个请求就顺带把 ht[0] 的一个桶迁到 ht[1]，查找时两张表都查、插入只进 ht[1]，直到搬完再把 ht[1] 换成正表。这就是「把一次大停顿换成 N 次微小成本」，和 LSM 的增量 compaction、ES 的增量 merge 是同一类思想。

③ 跳表（skiplist）：多层有序链表，每个节点随机层高（Redis 用 p = 0.25，最大 32 层，平均层数 1.33），上层是下层的「快进索引」。查找/插入/删除 O(log n)，且天然支持按 score 范围遍历（ZRANGEBYSCORE、排行榜分页），层与层之间用 span 记录跨度，所以 ZRANK 求排名也是 O(log n)。

为什么 zset 不用红黑树或 B+ 树：① 范围查询要中序遍历、实现复杂，跳表直接从底层链表右扫；② 跳表插入只改局部指针，不用旋转再平衡；③ 内存里没有「页」的概念，B+ 树的胖节点优势消失；④ 实现简单到能一眼审完，对单线程系统尤其重要。代价是指针多、内存开销比连续结构大，所以元素少时反而先用 listpack。

④ listpack / quicklist：listpack（Redis 7 起全面替代 ziplist）把一组 entry 连续排在一块内存里，每 entry 用变长编码记长度与类型，支持反向遍历；去掉了 ziplist 的「级联更新」隐患。quicklist 则是「双向链表 + 每个节点一个 listpack」，因为一整块连续内存太大时插入会引发大范围 memmove。这是一次典型的分层折中：连续内存赢局部性，分段赢修改成本。

⑤ intset：有序整数数组 + 二分查找，元素类型统一为 int16/int32/int64，插入更大类型时整体升级（只升不降）。全是小整数时，比哈希表省掉所有指针与桶开销。

⑥ 概率结构：

  • HyperLogLog：把元素哈希后分到 16384 个寄存器，记录前导零个数的最大值，用调和平均（抗极端大值）估算基数，标准误差 1.04 / √16384 ≈ 0.81%，内存恒定 12KB。为什么用调和平均而不是算术平均：单个超大前导零会把算术均值拉飞，调和平均对离群值不敏感。
  • Bitmap：直接在 SDS 的字节数组上做位运算，日活/签到用 1 bit/用户。
  • GEO：把经纬度编成 52 位 geohash 整数当 score 存进 zset，复用跳表做附近搜索，不新造索引结构。

⑦ 过期与淘汰：expires 字典单独存 key→过期时间。

  • 惰性删除：访问时才发现过期才删 —— 省 CPU，但可能留垃圾。
  • 定期删除：每秒约 10 轮（server.hz），每轮随机采样若干 key，删掉过期的；若过期比例 >25% 就再来一轮，同时设时间上限（约 25ms）防止卡死主线程。这是带预算的概率算法，不是精确扫描。
  • 内存淘汰：maxmemory 满时按策略（allkeys-lru / allkeys-lfu / volatile-ttl / noeviction 等）从随机采样（默认 5 个）里挑最差的删。为什么不维护全局精确 LRU 链表？因为每次访问都要移动链表节点，在 10w QPS 下这个开销比「少淘汰准一点」贵得多。LFU 用 24 位字段里的 8 位对数计数器 + 16 位衰减时间，用概率递增模拟访问频次。

⑧ 持久化：RDB = fork() 子进程利用 COW（写时复制） 拍快照；AOF = 追加写命令 + fsync 策略（always / everysec / no）+ AOF rewrite（子进程重写 + 期间增量写入重写缓冲）。7.0 起 multi-part AOF 把 base + incr 分开，减少重写放大。

⑨ 集群与网络：

  • 单线程事件循环 + epoll：命令执行串行，避免锁与上下文切换；6.0+ 的 I/O 多线程只分担网络读写与协议解析，命令执行仍然单线程。
  • CRC16 分槽：slot = CRC16(key) mod 16384，{hash_tag} 让多个 key 落到同一槽以支持多键操作。客户端能自己算槽 → 无需中心查表、无需一致性哈希环的虚拟节点迁移复杂度。

04 Elasticsearch／Lucene：把「包含」变成集合运算

4.1 场景与要解决的问题

场景：商品/政策文档全文检索、日志与链路追踪、多条件组合过滤 + 聚合分析。特征是读多写少、查询谓词是「包含某个词」而不是「主键等于几」、允许秒级以内的近实时（NRT）、数据量大到必须分片。

B+ 树在这里为什么不行：LIKE '%大宗%' 无法定界，索引只能全扫；而倒排索引直接把「词 → 哪些文档」预计算好，多条件查询变成集合求交，复杂度从「逐行判断」变成「有序链表归并」。

4.3 为什么是倒排 + 不可变段

候选为什么不合适
B+ 树 / 哈希索引谓词是「包含」而非「等于/前缀」，中间通配符无法定界；多条件 AND 要做多次索引查找再回表求交，不如倒排表直接归并
原地更新的段一写就加锁、缓存失效、并发读被阻塞；不可变段让读路径完全无锁，且 OS 可以放心长期缓存
删除时真删要在每个段里改动压缩过的 postings，随机写 + 重压缩；用位图标记是 O(1)，真正清理推给后台 merge
把结果缓存在 JVM 堆里堆越大 GC 越痛、且重启缓存全失；交给 OS page cache 后，缓存跨进程重启仍在（只要不换出）

refresh 为什么是 1 秒而不是实时：每次生成段都要构建倒排、写文件、开 reader；真「实时」等于每写一条就 refresh，段数量爆炸、merge 追不上。NRT 是用 1 秒可见性换写入吞吐与段数可控，这是明确的工程取舍。

4.4 场景是怎么被解决的（一次写 + 一次查）

写：客户端 bulk → 协调节点按 routing 路由到主分片 → 主分片本地写 index buffer + translog → 并行转发给 in-sync 副本 → 达写入条件返回 → 1s refresh 后可搜 → flush 时 segment fsync、清 translog → 后台 merge 合并小段。副本确认与 translog 是两个独立的耐久性开关：前者防单机故障，后者防掉电。

查：协调节点把请求发到相关分片 → query 阶段各分片在本地用倒排表求交 + 最小堆取 TopK，只回 docID 与分数 → 协调节点归并出全局 TopK → fetch 阶段按 docID 回各分片取 _source → 组装返回。两阶段是为了只在必要时传输文档正文。

日志时序场景：按时间建索引 + rollover + ILM（热/温/冷/删），查询时按时间范围直接砍掉无关索引；写多读少，副本可先设 0 再补，refresh_interval 可放宽到 30s 换吞吐。

05 MongoDB／WiredTiger：文档模型与 COW 快照

本章口径：MongoDB 在本人业务系统中未使用，整章是纯通用原理对照，不是项目实证。 留着它只因为它是最好用的三块「反差镜」：① B 树 + 文档聚合边界 vs InnoDB B+ 树 + 行；② 页级 COW 快照 vs undo 版本链；③ WT 自管 cache vs ES 把缓存交给 OS（外加 MMAPv1 被取代这个反面教材）。本章任何参数、调优、分片经验都不得说成亲历；被问「用过吗」按 §9.4 的三句式答。

5.1 场景与要解决的问题

场景：字段经常变的业务实体（商品属性、用户画像、IoT 事件、内容）、需要按整条文档读取、 schema 要能演进、数据量与写入量都要能水平扩展。典型如「订单头 + 明细数组 + 物流轨迹」这类一次查询就想拿全、很少跨表 JOIN 的数据。

要解决的矛盾：既要有 B 树的稳定读延迟与更新能力（不能像 ES 那样更新=删+插），又要让写吞吐与崩溃恢复别被原地改页拖死，还要让分布式扩展不需要中心协调。答案是 B 树 + 页级 COW + WAL + 文档即聚合边界。

5.2 用了哪些数据结构与算法

层结构 / 算法解决什么
文档 = BSON二进制 JSON，每个字段带类型与长度前缀反序列化时可跳过不需要的字段（不用解析整串）；类型保真（区分 int32/int64/date）；可逐字段比较排序
主存储（WiredTiger）B 树（默认表引擎；另有 LSM 实现但 MongoDB 未作为用户选项暴露）点查与范围查找都稳定，更新就地改页，读放大远低于 LSM
页级 COW修改页时复制新页，不原地覆盖；checkpoint 时把新页写入并原子切换根指针一致性快照 + 崩溃恢复只需回到上一个 checkpoint，不需要 undo 回滚
journal（WAL）追加写 + 组提交（默认约 100ms 提交间隔，可配 w:majority, j:true 强制）补两次 checkpoint 之间（默认 60s）的持久性窗口
WT cache自管缓存，默认约 max(256MB, (RAM−1GB)/2)；按 LRU-ish + 脏页比例做 eviction不依赖 OS page cache，淘汰策略与压缩页格式自己说了算
MVCC / 事务snapshot isolation：事务读一个一致的快照（读/写 timestamp、oldest timestamp），页的多版本链长查询不被写入阻塞，副本同步与回滚也有统一的时间点
索引_id B 树、单/复合/多键（数组每元素一条索引项）、TTL、geohash / S2 地理、文本（简版，非 Lucene）、哈希复合索引遵循最左前缀；多键索引让数组元素可查，但会放大索引体积
oplogcapped collection（固定大小、环形追加）副本集同步的输入流；条目设计成幂等（自增被改写成 $set）便于重复重放
副本集PV1 类 Raft 选举（term / 投票 / 心跳）、majority commit point、回滚未多数派确认的写选主防脑裂；已向客户端确认的写不丢
分片按 shard key 做范围 chunk（或哈希分片），chunk 满则分裂，balancer 迁移；config servers 存映射水平扩展，mongos 只做路由与结果归并
聚合管道流式 pipeline，$match/$sort 能下推到索引，$lookup 近似嵌套循环把计算放在存储侧，减少网络传输

5.3 为什么是 B 树 + 文档，而不是别的

① 为什么默认 B 树，而不是 LSM（这是高频追问）

维度WiredTiger B 树LSM（若用）
读延迟稳定，一次树下降多层查找 + bloom，长尾更明显
更新改页即可，COW 落地追加新版本，读时合并，空间放大
后台 IOcheckpoint（周期、可控）持续 compaction，容易抢前台 IO
定位通用 OLTP 文档库：读写均衡、查询形态杂写吞吐优先（HBase/Cassandra/RocksDB 场景）

MongoDB 要做「按 _id 点查 + 按时间范围查 + 频繁更新文档字段」的通才，LSM 的写优势换不来读延迟的确定性，所以默认 B 树。WiredTiger 内部有 LSM 实现，但 MongoDB 并未把它作为常规配置开放 —— 这本身就是答案。

② 为什么用 BSON 而不是 JSON 文本或行式关系表

  • 文本 JSON 每次取一个字段要解析整串；BSON 的长度前缀支持跳过。
  • 文档模型把「一次业务读取需要的字段」放在物理相邻位置，避免关系模型的多表 JOIN 与随机 IO；代价是冗余 + 更新放大（改一个大文档的一个字段要重写整页甚至整文档），所以 MongoDB 明确不建议无界增长的数组。

③ 为什么 checkpoint 要 COW：如果不复制页，checkpoint 与前台写入并发时会把「半新半旧」的页写进快照，恢复后数据自相矛盾。COW 让 checkpoint 只需在结束时原子更新根指针 —— 一致性快照不需要阻塞写入，代价是写放大与需要后台回收旧页。

④ 为什么 oplog 是 capped + 幂等：固定大小环形追加保证写 oplog 是纯顺序 IO 且空间有上界；幂等条目让「副本断线重连后重复拉一段」不会把自增字段加两次。oplog 窗口大小直接决定副本掉队多久还能追上，追不上就只能全量同步。

5.4 场景是怎么被解决的（一次写 + 一次读）

写（w:majority, j:true）：mongos/驱动 → 主节点写 journal（组提交 fsync）→ 在 WT cache 中修改 B 树页（COW 产生新版本）→ 写 oplog → 副本拉取 oplog 并重放 → 主节点收到多数派确认后推进 commit point 并返回 → 每 ~60s 的 checkpoint 把脏页刷成新快照并回收旧页。

读：解析查询 → 命中索引 B 树 → 拿到 RecordId → 若页在 WT cache 直接返回；否则从磁盘读页进 cache → 按 BSON 跳过无关字段 → 返回文档。主节点读保证读到已多数派提交的数据；readPreference 允许读从节点时要接受可能读到旧值（这是明确的取舍，不是 bug）。

分片查询：mongos 查 config 的 chunk 映射 → 只把请求发给相关分片（若 shard key 命中）→ 各分片本地执行 → 需要全局排序时 mongos 做归并。shard key 选错 = 广播查询（scatter-gather），这是 MongoDB 分片最大的性能陷阱。

06 MinIO：把冗余从副本换成代数

6.1 场景与要解决的问题

场景：图片、视频、模型权重、备份包、日志归档 —— 单个对象大（MB~GB）、一次写多次读、总量 PB 级、几乎不做「按内容查找」、要 S3 兼容、要在廉价盘上做到可靠。

和前四个的根本差别：前面四个都在回答「怎么根据条件找到一条记录」，MinIO 只回答「给我这个 key 的字节流」。它不需要通用索引，所以可以把元数据压到极轻，把全部精力放在两件事：吞吐和用尽量少的冗余空间扛坏盘。

6.2 用了哪些数据结构与算法

层结构 / 算法解决什么
命名空间扁平 key→object（bucket/prefix 只是字符串，不是目录树）不需要 inode/B+ 树/目录锁；元数据极轻，扩展时没有目录热点
纠删集（erasure set）一组 4~16 块盘为一个独立容错域；对象按确定性哈希选 set，set 内分片位置确定故障域隔离；扩容加 pool 不搬老数据
Reed–Solomon 纠删码在 GF(2⁸) 有限域上用生成矩阵（Vandermonde / Cauchy 系）把 K 个数据片线性组合出 M 个校验片；恢复时对 K 个可用片组成的子矩阵求逆解线性方程任意 K 片可还原全部数据，容忍 M 块盘同时失效
SIMD 加速GF 乘法用查表 + AVX2/SSSE3/NEON 向量指令并行处理多字节纯标量 RS 编码单核约数百 MB/s，向量化后可到数 GB/s 量级
quorum 读写写需成功写入 K 片（数据片数），读拿到任意 K 片即可解码；读时先验每片 hash，坏片剔除并重算在网络抖动/坏盘时仍可用，且不会把损坏的数据返回给客户端
bitrot 防护每分片独立 HighwayHash（流式边写边算，不二次读）、xl.meta 存校验与 EC 布局、后台 scrub/heal对抗「盘没坏但某个扇区静默错了」；这是三副本也未必能发现的问题
xl.meta每对象一份小元数据文件：版本、EC 分布、校验和、对象锁/保留策略元数据随数据走，无中心元数据 DB → 无单点、无元数据瓶颈
multipart大对象切 part 上传，每 part 独立校验，最后合并元数据断点续传、并行上传、失败只重传一个 part
对象锁 / 版本WORM 保留期 + 版本链备份与合规场景防误删、防勒索篡改
后台 heal扫描校验和 → 发现坏片 → 用其余 K 片重算 → 写到健康盘冗余自愈，不依赖人工换盘才恢复

6.3 为什么是纠删码，而不是别的

候选为什么不选 / 什么时候才选
三副本空间开销 3×，只能容忍 2 份同时失效（且多数派判定还要求至少 2 份在线）；纠删码 EC:4 在 16 盘下只多花 33% 空间就能容忍 4 盘失效。代价是 CPU 编码 + 修复读放大 + 小对象不划算（小对象分片后每片太小，元数据与 IO 次数占比过高）
简单 XOR 奇偶（RAID5 思路）只能容 1 块盘失效；RS 在 GF(2⁸) 上做线性组合才能容 M 块
硬件 RAID 下面再跑纠删码叠两层冗余，硬件 RAID 会掩盖单盘故障信号、把坏盘变成「慢盘」，还会引入额外写放大；MinIO 明确要 JBOD + 每盘独立 XFS 文件系统
中心元数据服务（如 HDFS NameNode）单点 + 扩容瓶颈 + 元数据也要做 HA；MinIO 让每个对象自带 xl.meta，靠确定性哈希定位，节点挂了目录不丢
B+ 树索引没有「按条件查」的需求，key 是精确查找；树只会带来写放大与锁
把对象数据放进 Go 堆GC 会灾难；实际是流式 buffer 复用 + O_DIRECT 直接落盘

为什么用 Go：goroutine 让「K+M 片并行写盘 / 并行读取」写成同步代码且开销极低，netpoller 底层就是 epoll；对象数据走流式 buffer 与 direct IO，不驻留堆，所以 GC 压力与对象大小解耦。

6.4 场景是怎么被解决的（一次 PUT / GET / 坏盘）

PUT：S3 请求 → 认证与 bucket 策略 → 按 key 算出 erasure set → 流式切 K 片并 RS 编码出 M 片 → K+M 个 goroutine 并行 O_DIRECT 写不同盘，边写边算 HighwayHash → 写 xl.meta → 达到写 quorum 返回 200。

GET：算出 set → 并行向各盘请求分片 → 每片先验 hash（坏片直接丢弃）→ 拿够任意 K 片 → 若全是数据片直接拼接，若含校验片则做 RS 解码 → 流式返回客户端（可走 sendfile 零拷贝）。

坏盘 / bitrot：后台 scrub 发现校验不符 → 标记该片 → 从其他盘读 K 片重算 → 写入替换盘 → 更新 xl.meta。修复一个对象要读 K 片，所以修复流量是受损容量的 K 倍 —— 这就是为什么大集群必须给 heal 限流，否则修复本身会把正常业务打垮。

扩容：新增一个 server pool，老 pool 的 set 不变、数据不迁移；新对象按策略落到新 pool。这是「确定性哈希 + 无中心元数据」换来的运维红利。

6.5 性能指标【量级】

指标量级前提 / 瓶颈
大对象吞吐GB/s 级（单节点 NVMe 多盘）瓶颈通常是网络（10/25GbE）或盘数，不是 CPU
小对象 QPS显著低于大对象吞吐元数据 fsync、分片数固定、每片一次 IO → 小对象固定成本占比高
RS 编码速度标量单核数百 MB/s，SIMD 后数 GB/s取决于指令集与实现（AVX2/GFNI）

速算：有效写入带宽 ≈ min(总盘顺序写带宽, 网络带宽) × K/(K+M)；读带宽 ≈ min(总盘读带宽 × 并行度, 网卡)。所以 MinIO 调优的第一件事永远是网络与磁盘带宽配比，不是调 GC 参数。

O_DIRECT + 4K 对齐对象分片直接落盘，绕过 page cache一个 1GB 视频若走 buffered IO，会把 page cache 里所有热数据冲光，对大对象来说 page cache 是敌人不是朋友（与 ES 完全相反）；O_DIRECT 要求 buffer、偏移、长度都按块对齐

noatime关闭访问时间更新每次 GET 都写元数据 = 无谓写放大
sendfile / 零拷贝对象从盘直接流到网卡，不进用户态注意：启用 TLS 会破坏零拷贝（需在用户态加密），这是安全与吞吐的明确取舍
epoll（Go netpoller）海量并发连接由少量线程承载与 Redis 同款思路，只是藏在 runtime 里
文件描述符与 inode小对象海量时 fd/inode 是硬约束扁平命名空间虽轻，但「每对象一文件」在小对象场景仍会压垮元数据层
NUMA / 网卡中断绑核高吞吐下减少跨节点内存访问与软中断抖动GB/s 级流量下，一次跨 NUMA 拷贝都会体现在 CPU 上
Go runtime 与 GC数据不驻留堆，流式 buffer 池化复用若把对象读进 []byte 再写，GC 会在 PB 级流量下成为主要瓶颈

一句话答「为什么 MinIO 不做目录树和元数据集群」：「因为 S3 的对象名只是字符串，查询只有精确 key。目录树、B+ 树、中心元数据服务全是为了『按条件找』而生的，这里用不上；去掉它们就没有单点、没有锁热点，扩容只需加 pool 不搬数据。代价是 LIST 要遍历，所以 LIST 高频的场景不适合对象存储。」

7.3 三条同构洞察（把五个背成一个）

  1. 写路径都在做 WAL：redo / AOF / translog / journal / 分片 + xl.meta。日志记「输入」，快照记「状态」，后台合并记「待办」。恢复 = 回到最近一致快照 + 重放日志，绝不重新执行业务逻辑。
  2. 持久结构都在做「不可变 + 后台合并」，只是浓度不同：ES segment merge 最彻底（段完全不可变），WiredTiger checkpoint 是页级 COW，Redis AOF rewrite 与 RDB 是周期性重写，MySQL 靠 purge + checkpoint 清理 undo 与脏页，MinIO 靠 heal 重建分片。LSM 不是一个产品，是一种处理写放大的思路。
  3. 并发模型都在躲锁：Redis 单线程命令执行、Cluster 分槽；ES 分片内多段无锁读；MongoDB 分片 + 文档级锁；MinIO 按 set 隔离故障域；MySQL 靠 MVCC + 行锁把锁粒度压到索引项。能分就分，不能分就串行，实在不行才加锁。

08 性能指标怎么用才不挨打

8.1 三条纪律（比数字本身重要）

  1. 所有数字都要带前提：硬件（NVMe / SSD / HDD）、数据量与是否命中缓存、读写比、一致性级别（是否 fsync、是否 w:majority）、单条数据大小。脱了前提的 QPS 就是营销材料。
  2. 看 P99 不看平均：merge / compaction / GC / checkpoint / fork COW 都是周期性尖峰，平均值完全掩盖它们。ES 的 GC、MongoDB 的 checkpoint、Redis 的 fork、MySQL 的刷脏，都是典型的「平时很稳、每隔一阵抖一下」。
  3. 区分「单机基准」与「你的系统」：本文所有 【量级】 是通用工程常识与公开基准的数量级，不是本项目的实测数据；讲项目时一律回到 00-面试计划/02-项目叙事-B2B.md 的 【实证】/【简历口径】/【推演】/【待实测】 口径，别把两者混着说。

8.3 五个最容易踩的指标坑

  • 拿厂商 benchmark 里的「最高吞吐」当自己的容量上限（那是大对象、无副本、顺序 IO、内存全命中的理想值）。
  • 忽略副本与一致性：w:majority / acks=all / 双一配置都是拿延迟换持久性。
  • 忽略后台任务：merge / compaction / heal / checkpoint 与前台共享同一块盘。
  • 忽略数据倾斜：热 key、单调递增 shard key、ES 一个大分片，都能让集群平均指标好看但 P99 爆炸。
  • 忽略「指标随时间退化」：段变多、undo 变长、oplog 窗口变小、碎片变多，上线第一天与第三个月的数字不是一回事。

09 面试话术与追问链

9.1 60 秒版（一句话主线 + 五个落点）

「这五个中间件其实是同一组 OS 约束下的五种取舍。磁盘随机 IO 比顺序 IO 贵两到四个数量级，所以 MySQL 用 B+ 树把点查压到 3 次页读、用 redo 把写变成顺序追加；Redis 干脆把数据全放内存，用哈希表和跳表换亚毫秒；ES 的查询是『包含』，B+ 树处理不了，所以用倒排索引把查询变成集合求交，再用不可变段把读做成无锁；MongoDB 也是 B 树，但聚合边界是整个 BSON 文档，用页级 COW 做快照；MinIO 没有按条件查询，只有按 key 取字节流，所以敢砍掉元数据集群，用 RS 纠删码把冗余从三副本降到 1.33 倍。它们对 OS page cache 的态度正好分三类：ES 全交给 OS、MySQL/Mongo/MinIO 自己管、Redis 根本不需要 —— 这一条基本能把『为什么这么设计』全串起来。」

9.2 3 分钟版（加一层推导 + 一个反例）

在 60 秒版基础上补两点：

  1. 从约束往下推：「我一般先讲四条物理约束（分层存储速度差、4KB 页与 page cache、系统调用与切换成本、易失与不可靠），再讲六个通用动作（顺序化、不可变+合并、索引换查找、批处理、校验冗余、单线程或分片无锁）。五个中间件不过是这六个动作的不同浓度。」
  2. 主动给反例：「比如 ES 的 heap 不能设 64GB，不是因为 JVM 不行，是因为它把缓存托付给了 OS —— 堆吃满内存，段文件只能走磁盘，P99 直接崩；而 MongoDB 恰恰相反，WT 必须自己管缓存，因为 OS 缓存的是压缩块、没法按事务语义淘汰。这两个放一起讲，比单背一个参数更能说明真懂。」

10.2 十条辟谣（说错会被立刻追问）

  1. ❌「B+ 树比哈希表快」→ 等值查询哈希更快，B+ 树赢在范围、排序、磁盘页局部性。
  2. ❌「Redis 单线程所以不能利用多核」→ 一台机跑多实例 / Cluster 分槽；6.0+ I/O 多线程分担网络读写（命令执行仍单线程）。
  3. ❌「跳表比红黑树快」→ 渐进复杂度同阶，赢在范围遍历与实现简单，代价是指针内存。
  4. ❌「ES 是实时搜索」→ 默认 1s 近实时；refresh 不是 flush，前者可搜、后者才落盘。
  5. ❌「ES 索引数据都在 JVM 堆里」→ 段文件在磁盘 + page cache，堆只放聚合/缓存/协调。
  6. ❌「MongoDB 是 LSM，写吞吐才高」→ 默认 WiredTiger B 树 + COW，不是 LSM。
  7. ❌「MMAPv1 靠 mmap 所以更先进」→ 恰恰因为把缓存与并发粒度交给 OS 才被 WT 取代。
  8. ❌「MinIO 用三副本」→ 用 RS 纠删码；三副本是另一类取舍（小对象延迟更好、空间 3×）。
  9. ❌「O_DIRECT 一定比 buffered IO 快」→ 它牺牲了预读与缓存，只有在自己有更好的缓存策略或数据太大时才划算。
  10. ❌「WAL 是为了加速写」→ WAL 是为了崩溃可恢复；加速写是把随机写变顺序写的副产品。
