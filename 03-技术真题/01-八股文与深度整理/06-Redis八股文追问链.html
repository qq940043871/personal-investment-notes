0.3 四条口径红线（旧稿就是踩了这些）

  1. 资金 / 合同 / 结算的真相在 MySQL，不在 Redis。跨系统一致靠 12 号 Outbox（待发送表 + 批次号原子认领 + 阶梯重试），不靠 Redis 分布式锁，也不靠 Seata / 2PC。

  3. 未落地大规模 Redis Cluster：实际是单机 / 主从 Redis + Redisson（arch/05 个人经验锚点）。被问集群 slot、hash tag 按「通用方案储备」答，别说成「我们上了 Cluster」。
  4. 故障场景不冒充亲历：04-生产问题排查/09、11、13 是「基于真实架构的代表性场景」，讲的时候说「按这套架构复盘」；数值是复盘基线不是压测报告。

2 追问链 01｜行情 / 挂牌列表的缓存谁来更新

场景锚点：排查 09 §1.1 的链路图——竞价页高频读三类数据，其中行情 / 挂牌列表走「Canal 监听 binlog → 独立缓存服务（封装 Redis）」；应用只写 DB，缓存由数据库变更事件驱动。【实证·场景】

考察意图：能否讲清「为什么不是应用双写」，以及 binlog 驱动带来的单点代价怎么兜。

依据指针：02-现货贸易/04-生产问题排查/09-竞价页面突然变慢-排查实录.md §1.1 / §2.6 / §4.2

L0 · 主问题：行情和挂牌列表为什么放 Redis？缓存由谁更新？

答：系统侧：这两类数据是开市期间的高频读（前端轮询 / 推送都要用），直接打 MySQL 会把主库压垮，所以放进独立缓存服务，命中率目标 ≥90%（规范 11）。关键是应用不负责删缓存——业务服务只写 DB，由 Canal 订阅 binlog 解析变更后刷缓存，这样多服务不会各自双写产生交叉写脏，链路可重放、可追溯。原理侧就是 Cache Aside 的升级版：把「谁来保证一致」从应用代码挪到数据库变更事件上。

L1 · 追问：那为什么不让应用「先更 DB 再删缓存」？

答：先更 DB 再删缓存是通用正解，窗口更短；但它要求每个写路径都记得删，漏一处就是长期脏数据，且并发下「A 写 DB、B 写 DB、B 删缓存、A 删缓存」仍可能把旧值写回。binlog 驱动把这件事收敛成一条链路，代价是这条链路成了单点——面试要主动把代价说出来，只讲优点显得没上过线。

L2 · 追问：Canal 挂了会怎样？是数据错还是变慢？

答：数据仍正确，只是变慢。Canal 只负责缓存更新，热点 key 过期后回源 DB 拿到的还是对的；如果同步的是搜索 / 索引数据才会表现为「数据错」。排查 09 就是这个形态：位点停滞 22 分钟 → 命中率 98%→31% → 回源风暴 → 主库 CPU 97%、P99 150ms→3.2s，成功率仍 100%。能分清「错」与「慢」，就不会跑去重启 MySQL 白忙一场。

L3 · 追问：这条链断了怎么自愈？

答：三层兜底。① 能看见：M-1 Canal 位点停滞 >1 分钟 / 消费延迟 >30s 告警，M-2 核心 key 命中率 <90% 告警；② 扛得住：M-3 本地 Caffeine 30s 二级缓存 + singleflight 回源保护，Redis / Canal 全挂也能扛 30s；③ 能自愈：L-2 XXL-Job 定时对账缓存与 DB，偏差自动重建。应急 S-1 重启 Canal 并校正位点、S-2 热点预热，5 分钟内命中率回到 95%。

L4 · 追问：哪些数据你绝不放进这套缓存？

答：① 资金 / 结算 / 合同真相（必须 MySQL 强一致，写后读走主库）；② C 核心的最新出价 / 成交（以内存为准，midservice 直连 C 引擎查询，压根不经过 Redis）；③ 待发送表这类一致性载体（靠批次号原子认领，不靠缓存）；④ 大字段与敏感合规数据。判据一句话：能容忍短暂不一致、且丢了能重建的读多数据，才配进缓存。

L5 · 追问：如果让你重做，会怎么改这条链？

答：不会推翻 binlog 驱动，而是补三件事：变更治理（DDL 必须走流程、避开交易时段、通知 Canal 等下游消费方，09 号 L-1）、消费端可观测与自动拉起（位点校验、解析失败自动恢复而不是静默退出）、缓存与 DB 的定时对账。这是把「单点」变成「可发现、可降级、可自愈」，而不是简单加个双写备份。

3 追问链 02｜热点 key 过期为什么把主库打穿

场景锚点：排查 09 §2.4——Canal 停滞后，热点 key（挂牌列表 / 行情）大批过期未重建，未命中直接回源、无并发保护，叠加开市峰值，主库 CPU 97%。【实证·场景】

考察意图：能否把「击穿」讲成一次有 traceId 证据的故障，而不是背三个名词。

依据指针：排查 09 §2.2 / §2.4 / §4.1；规范 11 §5

L0 · 主问题：一个热点 key 过期，为什么能把整个竞价页拖慢 20 倍？

答：现场证据先摆出来：midmon 按 traceId 拆一次慢请求——网关 20ms、竞价服务 3180ms（其中 SELECT t_listing 2950ms）、C 引擎直连 45ms；同时间 Redis 命中率 98%→31%、服务线程池打满、DB 连接池等待 200+。击穿的物理含义是：热点 key 失效瞬间，大量并发请求同时未命中、同时回源，DB 被同一条查询重复打 N 遍；再叠加开市峰值，就从「慢一点」变成「打满」。注意排除项：GC 正常、C 引擎 TPS 与队列深度正常，所以竞价慢不是撮合慢。

L1 · 追问：互斥锁重建、逻辑过期、热点不过期，怎么选？

答：互斥锁 / singleflight：同 key 的并发回源合并成一次，其余等待或读旧值——数据最新，但会阻塞。逻辑过期：value 里存逻辑过期时间，读时发现过期先返回旧值、异步重建——不阻塞、体验好，但短暂读到旧值、实现复杂。不过期 + 后台刷新：最稳，适合可预知的热点。本系统开市前的缓存预热就是把可预知热点提前灌进去，属于第三类。

L2 · 追问：行情价格能容忍「短暂旧值」吗？

答：不能一刀切。挂牌列表 / 标的详情这类展示数据允许秒级滞后（回源 DB 也是对的，只是慢）；但成交价、最新出价在本系统里根本不从 Redis 取——midservice 直连 C 引擎查，那里以内存为准。所以正确答法不是纠结缓存策略，而是先把数据分级、把强实时数据从这条链路上摘出去，这也是排查 09 里 45ms 那条直连链路存在的意义。

L3 · 追问：应急时先做什么？

答：按排查 09 的 S-1~S-5：重启 Canal 校正位点 → 热点缓存预热（5 分钟命中率回 95%）→ 网关对非核心查询降级限流 → 列表查询临时切从库 → 观察 30 分钟解除降级。不要先重启 MySQL：根因在缓存更新流中断，重启只是把打满的 CPU 清零，几分钟内会被回源流量再次打爆。

L4 · 追问：怎么防再发？

答：把「击穿」当架构缺陷治：热点 key 二级缓存（本地 30s）+ 回源 singleflight / 信号量并发保护 + 命中率水位告警 + 定时对账自愈 + 开市前预热与巡检 checklist（L-3）。只加互斥锁不改可观测性，下次还是靠客户投诉发现——这是 09 号最值钱的一条教训。

4 追问链 03｜开市峰值的多级缓存怎么排

场景锚点：规范 11 §5——L1 本地缓存 Caffeine / Guava，热点 key TTL 30s、maximumSize 10000；L2 Redis 通用 TTL 5~30min；预热脚本在开市 / 大促前主动加载；目标 90% 请求在缓存返回，完全不进服务层与 DB。【实证·场景】

考察意图：能否把穿透 / 击穿 / 雪崩三个名词落到一套具体的分层参数上。

依据指针：04-生产问题排查/11-网关扩容打穿DB-性能开发规范.md §5 / §8.2；排查 09 L-3

L0 · 主问题：开市这种峰值，缓存分层怎么设计才稳？

答：本地（30s）→ Redis（5~30min，TTL ±10% 抖动）→ DB。L1 是「逃生层」：Redis 或 Canal 全挂时，本地缓存还能扛 30s，给告警和降级争取时间；L2 承担共享热点；DB 只承受 ≤10% 回源（命中率 ≥90%）。开市前跑预热脚本把挂牌 / 行情热点提前灌入，把开市当大促对待。再往上还有网关限流 200 QPS 与服务层线程池隔离，缓存只是五层防线里的第二层。

L1 · 追问：穿透怎么防？（结合不存在的挂牌 ID）

答：① 参数校验（ID 格式 / 范围）先挡一层；② 缓存空值（查不到也缓存 60s 空标记）；③ 布隆过滤器放合法 ID 集合。B2B 场景挂牌 ID 相对有限且由平台生成，空值缓存 + 参数校验够用；布隆更适合 ID 空间巨大、且允许一定误判的场景。注意空值 TTL 要短，否则真数据创建了长时间读不到。

L2 · 追问：雪崩怎么防？

答：TTL 加 ±10% 随机抖动（避免大批 key 同一秒过期）+ 多级缓存 + 熔断限流兜底 + 缓存集群高可用。本系统里「权限、字典」这类全员热读数据尤其怕雪崩——它们一挂，不是某个页面慢，是所有接口一起卡。

L3 · 追问：本地缓存和 Redis 不一致怎么办？

答：本地缓存 TTL 只有 30s，本质是有界陈旧，用短 TTL 换逃生能力，不追求强一致；真正需要一致的写后读强制走主库，不经过本地缓存。要讲清「哪层允许旧、旧多久、谁兜底」，比笼统说「最终一致」强得多。

L4 · 追问：为什么命中率 ≥90% 这个数这么重要？

答：它是容量模型的输入，不是拍的：限流放行 200 QPS，命中率 90% 时实际回源 ≤20 QPS，DB 安全吞吐约 230 QPS，余量留给突发；命中率一旦掉到 31%，回源瞬间放大到几百 QPS，直接超过 DB 出口容量——缓存命中率是这个系统里的一级容量指标，所以要进看板、要设 <90% 告警。

5 追问链 04｜登录态为什么只认 Redis 里的会话

场景锚点：排查 13 的 5Why——网关鉴权只读 Cookie（HttpOnly）里的 token，去 Redis 查会话，查不到 / 已过期 / 与请求方不匹配一律 401；localStorage.user 只是前端展示缓存，鉴权链路完全不看它。根因是「前端有两个事实源且没有仲裁规则」。【实证】

考察意图：能否把 TTL、过期删除、key 设计讲成一次「唯一权威源」的状态治理。

依据指针：04-生产问题排查/13-登录态三存储不一致-前端误判已登录-排查与治理.md；网关 11 §7 等保拦截

L0 · 主问题：页面显示已登录、接口却 401，Redis 在这里扮演什么角色？

答：Redis 是登录态的唯一服务端事实源：网关拿 Cookie 里的 token 查会话，命中且未过期才放行。localStorage.user 永不过期、只用于渲染，两个源独立写入 / 独立过期，于是出现「页面照着 localStorage 画、接口照着 Cookie 判」。根因不是 Redis 配错了，是把缓存当成了状态——正解是写下不变量：登录态的唯一真相在服务端，前端一切展示都是可丢弃的缓存。

L1 · 追问：会话 key 怎么设计？TTL 怎么定？

答：sess:{token} → 用户 ID / 租户 / 角色版本 / 过期时间；HttpOnly Cookie 防 XSS 窃取，前端 JS 删不掉它（所以登出必须调后端 logout，只 localStorage.clear() 是登不干净的）。TTL 与 Cookie 的 Max-Age 对齐；被踢下线 / 改角色 / 改密码时，主动删会话或升角色版本号，让旧快照立刻失效。同一账号多标签并发登录不同公司账号会串号（看到别家报价），这是安全事故不是体验问题。

L2 · 追问：过期 key 是怎么删的？为什么不能靠「到期立刻触发」？

答：惰性删除 + 定期删除：访问时发现过期才删，后台再周期性抽样清理。它不是精确定时器，所以业务动作不能挂在 Redis 过期事件上。交收超时、冻结释放这类要改 DB 状态的事，得用 XXL-Job 定时扫表 / 延迟队列，并且释放逻辑幂等 + DB 状态兜底。

L3 · 追问：内存满了把会话淘汰掉行不行？

答：绝对不行。会话 / 幂等键这类不可重建的数据必须 noeviction——宁可写入报错，也不能静默把用户踢下线或把去重凭据抹掉。普通可重建缓存才用 allkeys-lru / allkeys-lfu。判据是「这个 key 丢了能不能从 DB 重建」，不是「它热不热」。

L4 · 追问：多实例网关下，会话放本地不行吗？

答：不行。midservice 是多实例，用户请求可能落到任意一台，本地缓存各存一份无法保证全局一致；Redis 是集中式共享存储，所有实例认同一份会话。但字典、权限这类可容忍秒级不一致的热读数据，放本地 L1 反而合适——共享与一致诉求决定放哪层，这条和链 03 是同一个判据。

6 追问链 05｜行情与风控 Top N 用什么结构

场景锚点：业务全链路手册场景 6 给了真实用法——每笔交易完成 ZINCRBY risk:volume:24h amount customerId，定时任务检查 Top N 大户、异常波动预警；行情 / 挂牌列表按价格与时间排序也是有序读。【实证】+【设计推演】

考察意图：能否按「读写形状」选结构，而不是万物皆 String。

依据指针：02-现货贸易/01-业务与价值/02-业务全链路场景手册.md 场景 1 / 场景 6；03-架构决策/arch/05-缓存系统设计.md §二

L0 · 主问题：风控 24h 交易额 Top N、行情榜单，为什么用 ZSet 而不是 DB ORDER BY？

答：系统侧：交易完成时对 risk:volume:24h 做 ZINCRBY，定时用 ZREVRANGE 取 Top N 大户做异常预警；这是高频写 + 实时有序读。DB 每次 ORDER BY 都要排序，高并发下不可接受。原理侧：ZSet 是内存有序结构，插入 O(log N)、按排名取 O(log N + M)，member 唯一天然去重，还支持 ZINCRBY 增量调价 / 累加，比「整行 UPDATE + 重新排序」轻得多。

L1 · 追问：String / Hash / Set / ZSet 在系统里各管什么？

答：String：字典、开关、计数器、序列化后的只读对象；Hash：标的详情这种按字段局部读写的对象（HGET/HINCRBY 改一个字段不用整体反序列化）；Set：去重与集合运算（如同时持有 A/B 合同的企业用 SINTER）；ZSet：需要顺序 / 排名的（行情按价格、风控按交易额、流水按时间）。判据：要顺序/排名 → ZSet，只要去重 → Set，有字段级更新 → Hash，纯只读整对象 → String。

L2 · 追问：ZSet 底层为什么是跳表？和 MySQL 的 B+ 树差在哪？

答：跳表是内存结构，靠多层随机指针做 O(log N) 查找，指针跳转在内存里很便宜、实现简单、范围遍历自然；但节点不按页对齐、扇出小，放到磁盘上会退化成大量随机 IO。B+ 树把连续键紧凑塞进 16KB 页、高扇出矮树高，是为磁盘设计的。介质决定结构——本系统里 Redis ZSet 扛实时榜单、MySQL B+ 树扛 t_listing 列表查询，正好是一对现成的对照（呼应 MySQL 追问链 02 L5）。

L3 · 追问：竞价高潮期这个 ZSet 自己成了热 key 怎么办？

答：① 按品种 / 场次 / 租户隔离 key，把热点打散；② 读多写多时主写从读 + 本地缓存承载榜单快照；③ 关键写动作用 Lua 把「校验 + 累加」原子化；④ 真到单 key 打爆，再考虑拆多副本聚合（【设计推演】，本系统未声明落地）。先按业务维度拆，比一上来改架构便宜。

L4 · 追问：这些统计能当财务口径吗？

答：不能。Redis 里的榜单是实时监控与预警口径，内存数据可能丢、可能滞后；对账、结算、发票必须用 MySQL 的明细流水与汇总快照。面试里主动划清「监控数」和「账务数」，比多背两个命令有用得多。

7 追问链 06｜开市时段哪些 Redis 命令会要命

场景锚点：Redis 单线程执行模型；排查 14（Java 架构师实战排障手册）把 Redis 慢查询列为一类独立排障场景；开市时段任何一次阻塞都会被轮询 / 推送流量放大。【通用方案】+【实证】单线程模型

考察意图：能否把「单线程为什么快」反过来讲成「哪些操作会卡死全场」。

依据指针：04-生产问题排查/14-Java架构师实战排障手册.md Redis 章；arch/05 §三

L0 · 主问题：Redis 单线程为什么还这么快？

答：① 纯内存操作；② IO 多路复用（epoll）单线程高效处理海量连接；③ 无锁、无上下文切换。瓶颈通常不在 CPU，而在内存与网络。6.0 之后的多线程只用于网络 IO 读写与协议解析，命令执行仍是单线程——这正是 Lua 脚本能保证「读-判-写」原子的原因。

L1 · 追问：那哪些命令会阻塞？

答：KEYS *（全库扫描）、大 key 的 DEL、HGETALL / SMEMBERS 打大集合、SORT / 大集合 SINTER、FLUSHALL。它们单线程执行耗时长，期间所有其他命令排队——开市时段等于把整个缓存层按了暂停。生产禁用 KEYS，用 SCAN 渐进式遍历；删除大 key 用 UNLINK 异步删。

L2 · 追问：大 key 怎么定位、怎么处理？

答：定位 redis-cli --bigkeys 或 MEMORY USAGE key；大 key 会带来阻塞、网络传输大、内存分布不均、主从同步慢。处理：按 ID 哈希拆成多个小 key、集合用 HSCAN/SSCAN 分批读、避免把整张挂牌列表塞进一个 String / Hash。本系统按租户 / 品种 / 场次拆 key，本身也是防大 key 的设计。

L3 · 追问：怎么发现慢查询？

答：SLOWLOG GET 看命令与耗时 → 排查 KEYS / 大 key / O(N) 命令 → 看 used_memory、内存碎片率、阻塞客户端数 → redis-cli --latency 测延迟。配合 midmon 的分段耗时，才能把「Redis 慢」和「DB 慢」分开（排查 09 里 Redis GET 未命中只花 12ms，真正慢的是后面 2950ms 的 MySQL）。

L4 · 追问：为什么「缓存慢」有时候其实是「缓存没命中」？

答：Redis 自己 GET 一次通常 12ms 级；没命中后回源 DB 才产生秒级耗时。所以看板要同时有命令耗时和命中率两个指标，只有前者会把人带偏。排查 09 的 traceId 拆解就是标准示范：先分段，再归因。

8 追问链 07｜Redis 挂了，会话和缓存怎么办

场景锚点：arch/05 个人经验锚点写得很清楚——本项目使用单机 / 主从 Redis + Redisson，未使用大规模 Redis Cluster；缓存三大问题治理是通用工程手段。【实证】

考察意图：能否把高可用方案按项目真实边界讲，不把 Cluster / 多活吹成已落地。

依据指针：03-架构决策/arch/05-缓存系统设计.md 个人经验锚点；规范 11 §5

L0 · 主问题：你们 Redis 什么部署形态？挂了会怎样？

答：单机 / 主从 + Redisson，没上大规模 Cluster。所以答这题要先划边界：主挂了由哨兵切主，切换期间可能有秒级不可用与少量未同步数据；业务侧影响分两类——缓存类数据可回源重建（配合本地 L1 30s 与限流降级扛过去），会话类数据不可重建（切换丢会话会导致用户被踢下线，需要重新登录，不能静默当成没事）。

L1 · 追问：RDB 和 AOF 怎么选？

答：RDB 是全量快照、恢复快但两次快照间可能丢；AOF 是追加命令日志、丢得少但文件大、恢复慢；常见是混合持久化。本系统的取舍按数据可重建性分级：纯缓存丢了能从 DB 重建，持久化可以放宽；会话 / 幂等键这类不可重建的，宁可牺牲一点性能也要少丢（AOF everysec + 定期 RDB 兜底）。具体参数属【待实测】，面试不主动报。

L2 · 追问：主从切换丢数据怎么办？

答：主从异步复制，切换瞬间可能有写未同步。兜底不是靠 Redis 自己，而是DB 兜底：幂等靠业务唯一键 / 唯一索引，状态靠 DB 状态机，最终一致靠 12 号 Outbox 的待发送表 + 阶梯重试 + 对账。一句话：Redis 是加速层，不是真相源；把正确性押在 Redis 上，主从切换那天一定会出事。

L3 · 追问：Cluster 的 slot 是什么？你们用了吗？

答：【通用方案】CRC16(key) % 16384 映射 slot，slot 分布到多个主节点；跨 slot 的多 key 操作 / Lua 会失败，要用 hash tag {bizId} 把相关 key 落到同一 slot；热 key 会集中打单节点。本系统未落地 Cluster，被问就按储备答，并补一句「我们的规模用主从 + 哨兵够，真要分片先把 key 按业务维度拆」。别把知识储备说成项目事实。

L4 · 追问：热 key 怎么办？

答：按品种 / 场次 / 租户拆 key 打散；本地 L1 缓存扛读；读写分离让从节点分摊；限流保护主节点。核心是把单点的集中读写打散，而不是给单 key 加更多机器。

9 追问链 08｜TTL 与淘汰策略怎么定

场景锚点：规范 11 §5——L2 Redis 通用 TTL 5~30min 且加 ±10% 随机抖动，L1 本地 30s；开市前预热。排查 13 里会话 TTL 与 Cookie 过期时间不一致正是「假登录态」的产生路径之一。【实证·场景】

考察意图：能否把过期机制讲成「按数据等级配置」，而不是背淘汰算法名。

依据指针：规范 11 §5；排查 13 §3 不一致路径 B/F

L0 · 主问题：Redis 的过期 key 到底什么时候删？

答：惰性删除 + 定期删除结合：访问时发现过期才删，后台周期性抽样清理。既不让过期 key 长期占内存，又不让删除阻塞单线程。由此推出一条重要工程结论：过期不是精确定时器，业务动作（交收超时、释放、对账）不能只挂在过期事件上，必须走延迟队列 / 定时任务 + DB 兜底，且逻辑幂等。

L1 · 追问：内存满了会怎样？策略怎么选？

答：按 maxmemory-policy：noeviction（不淘汰、写入报错）、allkeys-lru / volatile-lru、allkeys-lfu / volatile-lfu、random、ttl。本系统按数据分级：会话 / 幂等键这类不可重建的必须 noeviction（宁可报错也不静默丢），可重建的普通缓存用 LRU，热点明显的用 LFU。判据仍是「丢了能不能从 DB 重建」。

L2 · 追问：为什么 TTL 要加 ±10% 抖动？

答：防雪崩——如果大批 key 在同一时刻写入、设同一个 TTL，就会在同一秒集体过期，瞬时回源把 DB 打穿。抖动把过期时间摊开；再叠加多级缓存与熔断限流兜底。这条与排查 09 的「热点 key 陆续过期未重建」是同一个风险的两种触发方式：一个是同步过期，一个是更新流断了。

L3 · 追问：会话 TTL 和 Cookie 有效期不一致会怎样？

答：排查 13 里的经典路径 B：localStorage 永久、Cookie 7 天、服务端会话又是一个 TTL，三者各自过期 → 隔夜后「页面显示已登录、点啥都 401」。解法是把生命周期收敛到一个权威：服务端会话为准，前端展示全是可丢弃缓存，登出走后端原子清理，改角色 / 改密码主动作废会话或升版本号。

L4 · 追问：LRU 和 LFU 在本系统里怎么选？

答：LRU 按最近访问时间淘汰，LFU 按访问频率、更能保护「访问频繁但偶有空窗」的热点。字典 / 权限这类长期热点可用 LFU，通用缓存 LRU 足够；会话与幂等键不参与淘汰。别把「选 LRU 还是 LFU」当成架构决策，它只是可重建缓存内部的调参。

10 追问链 09｜批次号认领为什么不用分布式锁

场景锚点：一致性 12 §3.3 明写——批次号认领靠数据库的条件更新 + 行锁，本身就是一次原子互斥操作，不需要再引入 Redis / ZooKeeper 分布式锁；只有库不支持可靠条件更新时才退回「分布式锁 + 批量认领」，而那时锁会成为新的单点，只作降级方案。这一条直接推翻了旧稿「资金预扣必须加 Redis 锁」的整套叙事。【实证】

考察意图：能不能分得清「哪些并发互斥该交给 DB，哪些才该交给 Redis」——这是本份最容易被追问、也最能拉开差距的一链。

依据指针：02-现货贸易/03-架构决策/一致性与异构/12-跨系统调用一致性方案.md §3.3；00-面试计划/06-一致性与异构.md §2.1

L0 · 主问题：多实例派发器同时扫待发送表，为什么不加 Redis 分布式锁？

答：因为要保护的资源就在数据库里，用数据库的原子条件更新最自然：先取全局唯一批次号，再用一条 UPDATE ... SET status='发送中', batch_no=?, claim_time=? WHERE status='待发送' AND batch_no IS NULL 一次性认领整批；一条记录只会落进一个批次。行锁由 InnoDB 持有、与事务同生命周期，不需要额外的锁服务和续期机制。再引入 Redis 锁，等于多引入一个可能不一致的协调者：锁过期了业务没跑完、主从切换丢锁、锁与 DB 事务不同步，全是无收益的新故障面。

L1 · 追问：那 Redis 分布式锁在本系统里还有用武之地吗？

答：有，但不在 DB 条件更新能覆盖的地方。比如跨多个外部系统、没有共享 DB 事务的临界区（重复触发某个外部接口、非 DB 资源的互斥、防重复提交的第一道闸门），可以用 Redisson 做短临界区互斥。判据一句话：能用一个原子的 DB 条件更新解决的，不要用分布式锁；锁只管「DB 管不到」的那段。

L2 · 追问：真要用，标准姿势是什么？

答：SET key value NX PX 30000（value 用 UUID + 线程号）+ finally 里用 Lua 先校验 value 再删（直接 DEL 会误删别人超时后抢到的锁）+ 看门狗续期（Redisson 默认 30s 锁、每 10s 续）解决「业务没跑完锁先过期」。锁的 key 精确到最小冲突单元，绝不锁全局，临界区尽量短，业务本身仍要幂等。

L3 · 追问：主从切换把锁丢了怎么办？RedLock 靠谱吗？

答：Redis 主从异步复制，主挂了从升主，锁可能已丢。RedLock 向多个独立节点加锁、过半才算成功，但依赖时钟假设、节点故障时仍有窗口，工程上争议大。更实际的是把正确性别押在锁上：业务侧幂等键 + DB 唯一索引 / 状态机永远兜底，锁只用来减少冲突、不用来保证正确性。资金 / 一致性场景优先 DB 或 etcd 这类 CP 协调（【设计推演】，本项目未落地）。

L4 · 追问：幂等键放 Redis 还是 DB？

答：DB 是最终裁决：结算 / 派发的业务唯一键加唯一索引，或状态字段做 CAS（UPDATE ... WHERE status='待发送'），影响行数=0 说明已被处理。Redis SETNX 只是把「已处理」的判断提前到内存层、减少 DB 压力，是可以丢的第一道闸门；缓存可丢、DB 不可丢，这个顺序反了就是资金事故。

L5 · 追问：把这条和 C 核心的「运营点重试」放一起看，共同点是什么？

答：动作只发生一次，重放可以无数次。派发器重试只重放「发送」、C 核心运营点重试只重放「回写 DB」（按业务单号幂等 upsert，绝不重新撮合）；二者都不靠锁去重，而靠幂等键 + 状态机 + 对账。面试官追到这一层，你要答的已经不是 Redis，而是「这套系统怎么定义唯一事实」。

11 追问链 10｜网关限流 200 QPS 怎么用 Redis 落

场景锚点：主线件 05 §2.2~2.3——限流 200 QPS 是用利特尔法则从 DB 出口容量反推的（100 连接 ÷ 0.3s × 0.7 ≈ 230 QPS，取 60% 水位），5 实例分摊 40 QPS/实例；网关有租户级 / 应用级 / 接口级三级配额。【实证·场景】

考察意图：能否讲清「限流在保护什么」决定「计数要多精确」。

依据指针：00-面试计划/05-网关与高并发.md §2.2 / §2.3；网关 11 §4

L0 · 主问题：限流计数为什么常放 Redis？

答：网关是多实例（5 台），本地计数各算各的会超放；Redis 是集中式共享存储，能做全局配额。但要先问「限流在保护什么」：保护 DB 可容误差，用本地分片令牌桶（配额按实例数切分，省一次网络往返，误差约 ±实例数）；计量计费等必须精确的场景才走集中式 Redis 令牌桶，每次往返换准确性。这一句判据比背算法值钱。

L1 · 追问：200 QPS 这个数怎么来的？

答：利特尔法则 + DB 安全吞吐反推：在途并发 = QPS × RT；DB 安全 QPS ≈ 连接数 ÷ SQL 平均 RT × 利用率 = 100 ÷ 0.3 × 0.7 ≈ 230，取 60% 水位放行 200 QPS，再 ÷5 实例 = 40 QPS/实例；在途 = 40 × 0.3 = 12，对应慢接口线程池 core 15 / max 30 / queue 100。这是示例基线，以全链路压测为准，但推导方法本身就是答案。

L2 · 追问：固定窗口、滑动窗口、令牌桶怎么实现？

答：固定窗口 INCR + EXPIRE 60，简单但有临界突刺；滑动窗口用 ZSet（时间戳做 score，ZREMRANGEBYSCORE 清窗口外 + ZCARD 计数）；令牌桶用 Lua 把「按速率补令牌 + 扣令牌」原子化。多命令组合必须 Lua，因为 Redis 单线程执行脚本才是真原子；MULTI/EXEC 只保证一起执行、不保证回滚。

L3 · 追问：触发限流的只有 QPS 吗？

答：不是。网关的触发源还有高频错误、扫描特征、行为异常；处置阶梯是告警 → 限流 → 临时封禁 15 分钟（自动解封）→ 黑名单（人工解封），并做防误伤。这属于「信誉」维度，不是纯计数能覆盖的。超限返回 HTTP 429 + 兜底文案，目的只有一个：不让超过 DB 承受能力的流量进来。

L4 · 追问：Redis 挂了限流是不是就失效了？

答：本地分片令牌桶那一层还在（它本来就不依赖 Redis），所以保护 DB 的能力不会归零；集中式精确计量那一档要降级（例如切本地计数 + 事后对账）。限流要分层，别把所有闸门都挂在一个 Redis 上——这跟缓存要 L1+L2 是同一个思路。

12 追问链 11｜下游通知为什么是 Kafka 不是 Redis Stream

场景锚点：业务全链路手册场景 3——支付成功后通过 outbox 事务消息（Kafka） 通知风控调额度、财务记账、仓储备货；一致性 12 的落地是「业务表 + 待发送表同一本地事务 → 异步派发 → 阶梯重试 → 死信转人工」。【实证】

考察意图：能否按可靠性等级选组件，而不是「Redis 什么都能干」。

依据指针：02-现货贸易/01-业务与价值/02-业务全链路场景手册.md 场景 3；一致性 12 §2 / §4

L0 · 主问题：系统用事件通知下游，Redis 能做消息队列吗？

答：能，但只适合尽力而为的场景。List 的 LPUSH/BRPOP 是简易队列；Redis Stream（5.0+）有消费组、ACK、Pending 列表，能处理消费者故障接管。而本系统的出价事件、支付成功事件要求不丢、可回溯、可重试到上限转人工、能对账——所以用 Kafka + outbox 待发送表，不用 Redis Stream。

L1 · 追问：差别到底在哪？

答：可靠性等级不同。Kafka / RocketMQ 有多副本持久化、消息回溯、死信队列、按 key 分区保序、消费组 lag 可观测；Redis 做队列的持久化依赖 AOF 配置，宕机可能丢，且没有「按批次号认领 + 阶梯重试 + 死信转人工」这套业务级兜底。一句话：Redis Stream 是数据结构，Outbox + Kafka 是一套一致性方案。

L2 · 追问：那 outbox 到底解决什么？

答：解决「本地事务和远程调用不能兼得」：业务数据与「要通知谁（欠账记录）」在同一个本地事务里原子落库，远程调用一律挪到事务提交之后；派发器用全局唯一批次号 + 一条 UPDATE 原子认领整批，失败按 1s→2s→4s 阶梯重试，超限熔断进死信并通知运营；下游用业务幂等键去重。所以「超时了到底成功没有」不需要知道，重试是幂等的。

L3 · 追问：消费端幂等怎么保证？

答：MQ 是至少一次投递，重复消息必然存在。消费端用业务唯一键（事件 ID / 业务单号）做幂等，DB 侧再加唯一索引 / 状态机 CAS 兜底；顺序性靠同一业务单号发同一分区（同键保序、异键并行），幂等靠业务键，两者叠加才可靠。Redis 的 SETNX 最多算第一道快速闸门，不能当最终裁决（见链 09 L4）。

L4 · 追问：Redis 在这条链路里就完全没事做？

答：有，但都是配角：限流计数（链 10）、幂等的快速闸门、只读结果的缓存。把职责说清楚比「我们全用 Redis」更可信——面试官最怕听到的就是某个组件包打天下。

13 追问链 12｜把 Redis 放回扩容打穿 DB 那张图（压轴）

场景锚点：规范 11 的完整事故——网关横扩到 5 实例能扛 2500 并发，几分钟后后端 DB 被打死；本质是瓶颈后移：入口是放大器、DB 是单通道出口、中间没有闸门。缓存是五层防线的第二层，命中率 ≥90% 是容量模型的硬输入。【实证·场景】

考察意图：能不能把 Redis 从「一个组件」讲成「容量模型里的一环」，并串起前面 11 条链。

依据指针：04-生产问题排查/11-网关扩容打穿DB-性能开发规范.md 全文；排查 09 §3.3；主线件 05 §1.2

L0 · 主问题：网关扩容为什么会把 DB 打死？Redis 在这张图里站哪一层？

答：扩容前慢接口占着网关工作线程、并发跟不上；横扩到 5 实例后入口容量 ×5，能扛 2500 并发——但缓存未命中 / 缺失，流量 100% 回源，出口 DB 容量没变，几分钟就打满连接、拖死全站。Redis 站在第二层防线：网关（限流 200 QPS / 熔断 / 降级）→ 缓存（L1 30s + L2 Redis，挡掉 90%）→ 服务层（线程池隔离 / 队列削峰 / SQL 红线）→ DB（连接池 20/实例、max_connections 200、慢查询 1s kill）→ 规范与流程。它不是主角，是让放大后的流量安全落地的闸门之一。

L1 · 追问：当晚四步急救为什么有「热点缓存」这一步？

答：S-1 限流断洪水、S-2 热点数据加本地缓存 30s + 预热、S-3 慢接口独立线程池 15/30/100、S-4 连接池每实例卡 20。其中 S-2 是唯一直接降低回源倍数的措施：命中率上去后实际回源 ≤20 QPS，DB 立刻活过来。限流是止血，缓存是减负，隔离和连接池是防复发，四步少了任何一步都会再炸。

L2 · 追问：命中率掉下来时，Redis 侧应该先看什么？

答：按排查 09 的顺序：命中率水位（98%→31%）→ Canal 消费位点 / 延迟（停滞 22 分钟）→ 热点 key TTL 与重建情况 → Redis 命令耗时（SLOWLOG，GET 只有 12ms 级，别误判成 Redis 慢）→ 再用 traceId 把总耗时拆到层。先证明「不是 Redis 慢、是没命中且回源无保护」，再动手，别一上来重启 Redis。

L3 · 追问：怎么保证下次扩容不再出事？

答：把数值写进 SOP：扩容前先核 DB 出口容量（新增实例 × 连接池 ≤ max_connections 配额；放行 QPS ≤ DB 上限 × 60%）；新接口容量申报、读接口 QPS >100 必须有缓存层、命中率进看板；慢 SQL 红线、隔离红线、超时逐层递减；全链路压测常态化 + 缓存击穿演练。扩容是放大器不是解药，这条要能脱稿。

L4 · 追问：把 12 条链收成一句话？

答：Redis 负责让绝大多数读请求不走到 DB，但正确性永远由 DB 与业务幂等兜底。所以它一旦失效，表现是「系统变慢直至被打垮」，而不是「数据错」——排查 09 里成功率 100% 却 P99 3.2s，就是这句话最贵的一次注脚。

L5 · 追问：如果只能给这套缓存系统加一个改进，你加什么？

答：可观测性——Canal 位点停滞告警、命中率水位告警、分段耗时（网关 / 服务 / 缓存 / DB）进看板。09 号故障的根因不是 Redis 不够强，是「缓存更新流静默断了 22 分钟没人知道」。加机器、加集群、加多级缓存都治不了「看不见」；能被秒级发现的故障，才配谈自愈。

14 补充题（改成主线系统口径后的 14 道速答）

原稿 14 道补题全部保留编号与主题，但答案里的 p001 资金池 / 预扣冻结 / Seata 口径已统一替换为本系统口径。

补01 · Redis 和 Memcached 的区别？

答：Redis 有丰富数据结构、持久化（RDB/AOF）、主从 / 哨兵、原子 Lua；Memcached 只有 String、纯内存、多线程。本系统要「会话 + 有序榜单 + 限流计数 + 多级缓存」，只能用 Redis；但别顺口说资金原子扣减也靠 Redis——那是 DB 的活（链 09）。

补02 · 为什么用集中式 Redis 而不用本地缓存？

答：会话、配额、行情是跨实例共享状态，midservice 多实例下本地各存一份会不一致；Redis 是共享事实源。本地缓存只做 L1 逃生层（30s），且只放可容忍陈旧的数据。

补03 · 分布式锁的 value 为什么用 UUID + 线程号？

答：释放时要校验「这把锁是不是自己加的」，固定值会误删别人超时后抢到的锁；配合 Lua GET == value 才 DEL。前提先说清楚：本系统的一致性主路径不靠这把锁（链 09 L0）。

补04 · key 设计有哪些规范？

答：业务前缀 + 冒号分层（bid:list:{tenant}:{variety}、sess:{token}、risk:volume:24h）；可读、控长度；按业务维度拆 key 防热 key 与大 key；相关 key 用 hash tag 保证同 slot（仅 Cluster 场景，本系统未上）。

补05 · 缓存与 DB 双写为什么会错乱？

答：两个请求交叉写会把旧值写回缓存。本系统不靠应用双写，靠 Canal 订阅 binlog 驱动更新，让 DB 成为唯一真相、缓存被动跟随；再配定时对账兜底。

补06 · 为什么说 Redis 适合做缓存、不适合做数据库？

答：内存在、持久化尽力而为、宕机可能丢、事务只有单命令 / Lua 级原子、没有复杂查询与强约束。资金、合同、结算、待发送表一律 MySQL；Redis 只做加速与并发控制。

补07 · 怎么保证「出价落库」和「通知下游」一致？

答：Outbox：业务表 + 待发送表同一本地事务 → 批次号原子认领 → 异步派发 → 阶梯重试 → 死信转人工 → 下游幂等。不是 XA / 2PC / TCC / Seata；Saga 只管「必须补偿」的长事务（05 号），与 Outbox 互补。

补08 · pipeline、MULTI/EXEC、Lua 有什么区别？

答：pipeline 批量发命令省 RTT、不保证原子；MULTI/EXEC 命令排队后原子执行但不回滚；真正要「读-判-写」原子（限流令牌、原子累加）用 Lua，因为命令执行是单线程。

补09 · Redis 事务为什么不支持回滚？

答：入队时已做语法校验，运行时错误属编程错误，应在开发期发现；为它引入回滚不值当。需要原子性用 Lua。

补10 · 缓存雪崩时怎么限流降级保护交易链路？

答：网关按接口限流（慢接口 200 QPS）、非核心查询返回兜底 / 排队、慢接口独立线程池隔离、列表读切从库；优先保出价写入与结算，历史成交 / 导出类先降级（排查 09 S-3/S-4）。

补11 · Redis 集群里幂等键放哪个节点？

答：【通用方案】用 hash tag {bizId} 把余额 / 幂等键 / 锁相关 key 落到同 slot，保证 Lua 多 key 可用。本系统未上 Cluster，幂等最终靠 DB 唯一索引，不依赖 slot 分布。

补12 · 怎么用 Redis 做限流？

答：固定窗口 INCR + EXPIRE；滑动窗口 ZSet 按时间戳 score 清理 + ZCARD；令牌桶用 Lua 原子补扣。选哪种先看「限流在保护什么」：保护 DB 可用分片本地桶，计量计费要集中式精确（链 10）。

补13 · keyspace 通知能用来做交收超时释放吗？

答：不能只靠它。通知是尽力而为，客户端断线就丢；而且 Redis 过期是惰性 / 定期，不是精确定时。要改 DB 状态的释放动作，必须「延迟队列 / XXL-Job 定时扫表 + 幂等释放 + DB 状态兜底」。

补14 · 逻辑过期和互斥锁重建怎么选？

答：逻辑过期不阻塞、先返回旧值再异步重建，适合可容忍秒级滞后的展示数据（挂牌列表 / 标的详情）；互斥锁数据新但会阻塞，适合不允许旧的读。最新出价 / 成交压根不在这条链上——直连 C 引擎（链 02 L2）。
