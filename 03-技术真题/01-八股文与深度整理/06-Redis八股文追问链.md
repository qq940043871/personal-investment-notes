## 00 业务背景：Redis 在这个系统里干什么

**系统定位**：B2B 大宗商品交易（挂摘牌/现货）的合同履约系统，核心是把「合同（商业契约）」与「履约（执行））」解耦，用双轨引擎支持顺序交收（状态机强管控）与自由交收（事件驱动）。

**五大微服务**：合同、履约、资金、物流仓储、票务；基础设施层明确标注 **Redis（锁 / 缓存）**、Kafka/RocketMQ（事件总线）、Seata/消息最终一致。

**Redis 承担的四大业务职责**：
1. **资金池余额缓存**：`fund_pool(Plan-001).Paid_Pool.balance` 预存款池余额的读写缓存。
2. **分布式锁**：资金预扣/冻结（`preFreeze → confirmSettlement`）与履约状态机推进的并发互斥。
3. **幂等控制**：结算、退款等资金动作的幂等键，防止重复扣款/重复结算。
4. **读缓存**：合同详情、商品、字典、权限、大屏看板等读多写少数据。

**核心资金铁律**（来自系统设计）：*「没有资金预扣/冻结成功的业务流转，都是耍流氓」*——业务操作意向 → 资金预扣/冻结 → 冻结成功 → 业务状态推进 → 最终结算，预扣失败则事务回滚。Redis 就是这条链路上「预扣原子性 + 并发互斥 + 幂等」的物理实现。

## 🔥 追问链 01｜资金池余额缓存与一致性

> 考察意图：资金余额是「强一致」数据，为什么还敢用 Redis 缓存？能否说清「缓存余额」与「DB 余额」的分工与兜底。

### L0 · 主问题：资金池余额（fund_pool.balance）为什么要放 Redis？
**答**：余额是**高频读写 + 热点**数据——每一笔预扣、结算、退款都要读/改余额，直接打 DB 会成瓶颈。Redis 内存读写 + 单线程原子操作，能把余额的读写扛到万级 QPS。但**余额是资金核心，不能只靠缓存**，DB 才是最终权威。

### L1 · 追问：缓存余额和 DB 余额怎么保证一致？
**答**：核心思想是「**Redis 承担并发原子扣减，DB 承担最终落账**」：扣减先走 Redis（Lua 原子判余额并扣减），DB 用**流水 + 汇总快照**异步落账；两者通过**对账机制**（安全网）定期比对，不平则冲正。**资金场景不追求强一致缓存，追求「最终一致 + 可对账 + 可冲正」**。

### L2 · 追问：并发扣减怎么做到原子？DECRBY 直接减行不行？
**答**：不行，`DECRBY` 只会无脑减，可能把余额减成负数。必须用 **Lua 脚本**：
```lua
-- 原子判余额并扣减，防止超扣
local cur = redis.call('GET', KEYS[1])
if not cur or tonumber(cur) < tonumber(ARGV[1]) then
  return -1   -- 余额不足
end
return redis.call('DECRBY', KEYS[1], ARGV[1])
```
Redis **单线程执行 Lua**，整个「读-判-扣」脚本是原子的，天然避免并发超扣。

### L3 · 追问：扣减成功了，但 DB 落账失败了怎么办？
**答**：这是分布式场景的经典「先扣缓存、后落账」顺序问题。方案：① 扣减成功但落账失败 → **回滚 Redis 余额**（补偿）或记入待处理队列重试；② 更稳的做法是**先落 DB 流水（记流水表），再异步扣 Redis**，用**对账任务**兜底；③ 生产常用「**DB 流水为准 + Redis 余额为加速 + 对账冲正**」三层，任何中间态都能通过对账纠偏。

### L4 · 追问：Redis 崩了/缓存被清了，余额怎么办？
**答**：**DB 兜底 + 重建**。缓存失效后从 DB 的「汇总快照 + 流水」重建余额缓存；重建期间若并发写，用**分布式锁**串行化或**双写**。这就是为什么资金余额的 DB 侧一定是「明细流水 + 汇总快照」而非只存一个裸 balance——**流水是余额的真相来源，缓存只是快照**。

### L5 · 追问：那资金余额到底适不适合用缓存？边界在哪？
**答**：分两段：**查询余额**可以缓存（读多，允许短暂延迟，配合对账）；**扣减动作**必须原子且最终以 DB 为准。更严谨的方案是「**扣减走 DB 行锁 + 乐观锁，Redis 只缓存读**」或「**余额不入缓存，用 Redis 做扣减的原子闸门 + DB 落账**」。能讲清「**缓存放什么、不放什么、谁兜底**」这条边界，就是资深水平——资金领域，**正确性 > 性能**。

## 🔥 追问链 02｜资金预扣/冻结的分布式锁

> 考察意图：分布式锁的完整实现链路与工程坑，能否从 SET NX PX 一路讲到 RedLock 和锁粒度。

### L0 · 主问题：preFreeze（资金预扣/冻结）为什么要加分布式锁？
**答**：同一履约单/同一资金池，可能被「确认收货结算」和「退款解冻」等多条链路并发操作；若不互斥，会出现**预扣和结算同时改余额、状态推进错乱**。分布式锁保证「同一资金操作时刻只有一个执行者」，配合 2PC 的 preFreeze→confirmSettlement 顺序。

### L1 · 追问：Redis 分布式锁怎么实现？
**答**：核心命令 `SET key value NX PX 30000`——`NX` 保证只当 key 不存在才成功（互斥），`PX` 设过期时间（防死锁），`value` 用唯一标识（如 UUID+线程号）。加锁成功才执行业务，finally 里释放。

### L2 · 追问：为什么要设 PX 过期时间？锁超时了业务还没跑完怎么办？
**答**：设 PX 是**防死锁**——持有锁的进程宕机，锁会自己过期，不会永久阻塞别人。但业务执行超过锁的 TTL，锁被释放、别人抢到，会导致**并发执行**。解法：**看门狗续期**（Redisson 的 watchdog，默认 30s 锁、每 10s 续期），锁在业务完成前自动续命，业务结束才真正释放。

### L3 · 追问：释放锁为什么必须用 Lua？直接 DEL 行吗？
**答**：不行。若 A 的锁过期了、B 抢到锁，此时 A 执行完去 `DEL`，会**把 B 的锁误删**。必须用 Lua **先校验 value 是自己的再删**：
```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```
「**加锁 SET NX PX + 释放 Lua 校验 value**」是分布式锁的标准姿势。

### L4 · 追问：主从切换导致锁丢失怎么办？RedLock 靠谱吗？
**答**：Redis 主从是异步复制，主挂了、从升主，**锁可能已丢**。RedLock 思路是向 N 个独立 Redis 节点（如 5 个）分别加锁，拿到过半（≥3）才算成功。**但 RedLock 有争议**（依赖时钟、节点故障时仍有窗口），且牺牲性能。工程上多数场景：**用 Redis 单主/哨兵 + 看门狗，把锁的临界区做短、业务本身做幂等**，比迷信 RedLock 更实际。资金极端场景可考虑 **ZooKeeper/etcd**（CP 强一致）做锁。

### L5 · 追问：你们资金场景锁的 key 和粒度怎么设计？
**答**：锁 key 要**精准到最小冲突单元**，避免锁太粗影响并发。如 `lock:fund:pool:{poolId}`（锁资金池）或 `lock:fulfillment:{planId}:{node}`（锁履约单的某个节点）。**粒度原则**：资金预扣锁 `fund_pool` 维度，状态推进锁 `fulfillment_plan` 维度；绝不锁全局（如 `lock:all`），否则退化成单点串行。

## 🔥 追问链 03｜结算幂等

> 考察意图：资金动作「重复执行不重复扣钱」是底线，能否给出幂等键的完整设计。

### L0 · 主问题：confirmSettlement（预扣转实结）为什么必须幂等？
**答**：结算涉及真金白银。网络超时重试、MQ 重复投递、定时任务重跑，都可能导致同一笔结算被执行多次。**幂等保证「同一笔资金业务操作，重复执行也只生效一次」**，否则就是重复扣款事故。

### L1 · 追问：幂等键怎么设计？用 SETNX 吗？
**答**：用**业务唯一键**做幂等标识，如 `settle:{settlementNo}` 或 `settle:{planId}:{node}`。执行前 `SETNX settle:xxx 1 EX 86400`：**抢到（返回1）才执行**，抢不到说明已处理过，直接返回成功。SETNX 的原子性天然适合「先占坑再干活」。

### L2 · 追问：光靠 Redis SETNX 就够了吗？Redis 丢了怎么办？
**答**：不够。Redis 是加速层，**兜底必须是 DB**：① 结算表对业务唯一键加**唯一索引**，重复插入直接报冲突；② 或结算单状态字段做 **CAS 乐观锁**（`UPDATE ... WHERE status='PRE_FROZEN'`，影响行数=0 说明已处理）。**Redis 幂等键 + DB 唯一索引/状态机，双保险**，Redis 只是把「已处理」的判断提前到内存层减少 DB 压力。

### L3 · 追问：幂等键的过期时间怎么定？过期了又重试怎么办？
**答**：过期时间要**覆盖「重试窗口」**，通常设到业务重试周期之外（如结算重试 24h，幂等键设 25~48h）。但更稳妥的是：**幂等键过期了也没关系，因为 DB 唯一索引/状态机永远兜底**——Redis 幂等键只是「第一道快速闸门」，失效后落到 DB 层照样拦住。这就是「**缓存可丢、DB 不可丢**」的设计哲学。

### L4 · 追问：幂等 + 事务 + 锁怎么组合才不出问题？
**答**：资金动作的标准组合是「**锁 + 幂等 + 事务**」三层：分布式锁保证并发互斥 → 幂等键保证重复调用只生效一次 → DB 事务保证「扣款 + 改状态 + 记流水」原子。**顺序**：加锁 → 幂等检查 → 事务内完成资金变更与状态流转 → 释放锁。任何一层缺失都可能在极端并发下出资金事故。

## 🔥 追问链 04｜履约状态机防重

> 考察意图：状态流转的并发控制，乐观锁与分布式锁的选型判断力。

### L0 · 主问题：履约状态机推进（如「待发货 → 已发货」）怎么防并发重复推进？
**答**：核心是**状态流转必须「从旧状态原子地跳到新状态」**。用 DB 乐观锁：`UPDATE fulfillment SET status='SHIPPED', version=version+1 WHERE id=? AND status='TO_SHIP'`，影响行数=0 说明已被别人推进过，直接放弃或报「状态已变更」。

### L1 · 追问：乐观锁（CAS）和分布式锁（悲观锁）怎么选？
**答**：**冲突概率低、单行更新** → 乐观锁，无锁等待、吞吐高；**冲突概率高、多行/多资源联动** → 分布式锁，串行化避免浪费重试。资金+状态机场景常用**组合**：外层分布式锁串行化复杂编排，内层状态字段 CAS 做最后防线。

### L2 · 追问：状态机 + 分布式锁 + 事务的组合，顺序有讲究吗？
**答**：有。标准顺序「**加锁 → 读状态校验 → 业务动作 → 事务内改状态 → 释放锁**」。坑点：① 锁必须**包住「读状态 + 改状态」**的整个临界区，否则读到的旧状态会并发改写；② 释放锁要在事务提交后（finally），避免事务没提交锁就放了。

### L3 · 追问：锁超时导致状态推进「卡住」了怎么办？
**答**：先区分「锁被误释放导致并发推进」和「业务真的慢」。前者靠**看门狗续期 + 释放锁 Lua 校验**解决；后者靠**把状态推进拆成短事务 + 幂等重试**，确保即使锁超时、重试也能安全推进到目标状态（幂等保证不重复副作用）。

### L4 · 追问：为什么状态机里最忌讳「先查状态再更新」？
**答**：因为「查」和「更新」之间有时间差，两个线程都查到 `TO_SHIP`，都去更新，就都推进成功——**典型的 check-then-act 竞态**。正确做法是把状态作为**更新条件**（`WHERE status='TO_SHIP'`）或加锁把「查+改」变成原子，绝不能「裸 SELECT 判断再裸 UPDATE」。

## 🔥 追问链 05｜缓存一致性

> 考察意图：缓存更新策略的演进，以及「资金数据」与「普通数据」的一致性边界。

### L0 · 主问题：更新合同/商品数据时，更新缓存还是删缓存？
**答**：**删缓存（Cache Aside）**。更新缓存在并发下可能写脏，不如「先更新 DB，再删除缓存」，让下次读按需回源。系统里合同详情、商品、字典都用这套。

### L1 · 追问：先删缓存还是先更新 DB？
**答**：主流**先更新 DB，再删缓存**，不一致窗口更短。但仍可能短暂读到旧值（更新完、删缓存前有请求命中旧缓存），可接受最终一致。

### L2 · 追问：删缓存失败了怎么办？
**答**：**延迟双删**（删一次，延时 1~2s 再删一次，清掉并发写回的脏值）；或更可靠用 **canal 订阅 binlog**——应用只写 DB，canal 解析 binlog 变更后异步删缓存，解耦且可重放。资金系统里普通业务数据（合同/商品）用这套就够。

### L3 · 追问：资金类数据（余额、流水）也能这么删缓存吗？
**答**：**不能简单套用**。资金数据是强一致诉求，删缓存重建有窗口会读到「扣减前」的旧余额。所以资金余额不靠「删缓存重建」，而靠**原子扣减 + 对账冲正**（见追问链 01）。**关键认知：缓存一致性策略要按数据一致性等级分级——普通数据「最终一致」，资金数据「强一致/可对账」**。

### L4 · 追问：哪些数据你绝不会放进缓存？
**答**：① **资金流水/账本**（真相来源，必须 DB 强一致）；② **结算、预扣的中间状态**（一旦缓存丢失会破坏 2PC 语义）；③ **需跨服务强一致读的数据**；④ 大字段/敏感合规数据（如银行授权、电子签章原文）。一句话：**「能容忍短暂不一致的读多数据」才配进缓存，其余交给 DB**。

## 🔥 追问链 06｜缓存穿透/击穿/雪崩

> 考察意图：三大缓存问题的场景化应对，能否结合履约高峰给出具体方案。

### L0 · 主问题：缓存穿透、击穿、雪崩分别是什么？
**答**：穿透——查**不存在**的数据，缓存没挡住、直接打 DB（如伪造的商品 ID）；击穿——**某个热点 key** 过期瞬间，海量请求集中打 DB（如爆款合同详情）；雪崩——**大量 key 同时过期或缓存整体宕机**，DB 被瞬间压垮。

### L1 · 追问：穿透怎么防？（结合商品/合同 ID）
**答**：① **布隆过滤器**：把所有合法 ID 预先存进布隆，请求先过布隆，不存在直接拦截；② **缓存空值**：查不到也缓存一个短 TTL 的空结果；③ 参数校验（ID 格式/范围）兜底。B2B 场景商品 ID 相对有限，布隆过滤器 + 空值缓存最实用。

### L2 · 追问：击穿怎么防？（热点合同被疯狂查询）
**答**：核心是**避免「失效瞬间」的并发回源**。① **互斥锁重建**：只让一个请求回源查 DB 重建缓存，其余等待或读旧值；② **逻辑过期**：缓存不设物理过期，存一个「逻辑过期时间」，读时发现逻辑过期就异步重建、先用旧值顶着；③ 热点数据**永不过期 + 后台定时刷新**。

### L3 · 追问：雪崩怎么防？（履约高峰期大量字典/权限同时过期）
**答**：① **过期时间加随机抖动**（如 1h ± 10min），避免同时失效；② **多级缓存**（本地 Caffeine + Redis）；③ **限流降级**：缓存/DB 都扛不住时熔断、返回兜底数据；④ 缓存集群**高可用**（哨兵/集群），避免单点宕机。资金系统里「权限、字典」这类热读数据尤其要防雪崩。

### L4 · 追问：履约高峰期，整体缓存怎么设计才稳？
**答**：分层设计：**本地缓存（热点字典/权限）→ Redis（业务数据）→ DB（真相）**。热点合同详情用「互斥锁重建 + 逻辑过期」；资金余额用「原子扣减不入常规缓存」；配合**限流 + 降级 + 预热**（高峰期前把热点数据提前灌入缓存）。核心是**让热点永不「裸奔」打 DB**。

## 🔥 追问链 07｜事件总线与消息去重

> 考察意图：EDA 事件驱动的消息可靠性，以及 Redis 做队列的边界。

### L0 · 主问题：系统用 EDA 事件总线，Redis 能做消息队列吗？
**答**：能。**List** 可以做简单队列（LPUSH/BRPOP），**Redis Stream**（5.0+）是真正的消息队列结构，支持消费组、ACK、消息持久化。但 Redis 做队列是「**尽力而为**」，消息持久化靠 AOF，宕机可能丢消息。

### L1 · 追问：领域事件消费为什么必须幂等？
**答**：MQ 的**至少一次投递**语义下，事件可能被重复投递（重试、分区再平衡）。「合同生效 → 生成履约计划」「资金状态变更 → 推进履约进度」这类事件，重复消费会导致重复生成计划/重复推进。所以**消费端必须幂等**——用事件 ID 做幂等键（见追问链 03）。

### L2 · 追问：Redis Stream 的消费组是什么？怎么用？
**答**：消费组允许多个消费者**并行消费同一条 Stream**，每个消息被组内一个消费者处理，通过 `XACK` 确认；没 ACK 的消息进 **Pending 列表**，可重新投递给其他消费者——天然支持「消费者故障接管」。`XADD` 生产、`XREADGROUP` 消费、`XACK` 确认。

### L3 · 追问：资金类事件为什么用 RocketMQ/Kafka 而不用 Redis？
**答**：**可靠性等级不同**。资金事件（结算、退款）要求**不丢、可回溯、顺序保证**：RocketMQ/Kafka 有**多副本持久化、消息回溯、死信队列、事务消息**。Redis 做队列在宕机时可能丢消息、且 Stream 的持久化依赖 AOF 配置，**扛不住资金级的可靠性要求**。所以系统里「**普通事件可上 Redis Stream，资金事件必须上 MQ**」。

### L4 · 追问：消息的顺序性 + 幂等 + 去重，怎么一起保证？
**答**：① **顺序性**：同一资金池/履约单的事件发到**同一分区**（按 poolId/planId 做 key 哈希），单分区内有序；② **幂等/去重**：消费端用**业务唯一键（事件 ID/业务单号）**做幂等，重复消息直接跳过；③ **兜底**：DB 状态机 + 唯一索引拦截非法状态流转。顺序靠分区，幂等靠业务键，两者叠加才可靠。

## 🔥 追问链 08｜挂摘牌防重 + 竞价排行

> 考察意图：交易撮合场景的并发防重与有序结构选型。

### L0 · 主问题：挂摘牌/竞价里，Redis 承担什么角色？
**答**：① **防重复摘牌**：同一挂牌单只能被摘一次，用 SETNX 抢占；② **竞价/挂单排序**：用 ZSet 按价格排序，O(log N) 插入、O(1) 取最高/最低价；③ **交易撮合状态缓存**：挂牌/摘牌状态高频查询。

### L1 · 追问：摘牌怎么防重复？
**答**：`SETNX listing:lock:{listingId} userId EX 300` 抢占挂牌单，**抢到才允许摘牌**；DB 侧挂牌单状态字段 `WHERE status='ON_LISTING'` 乐观锁兜底。Redis 是「快速闸门」，DB 状态是「最终裁决」。

### L2 · 追问：竞价怎么用 ZSet 实现价格排序？
**答**：`ZADD auction:{auctionId} price bidderId`，用价格做 score；`ZREVRANGE` 取最高价、`ZREMRANGEBYRANK` 踢出局、`ZINCRBY` 加价。出价即 `ZADD`，若新价低于当前最高价直接拒绝。ZSet 的**有序 + 去重（member 唯一）**天然适合竞价簿。

### L3 · 追问：挂单行情/排行榜这种「实时有序」数据，为什么用 ZSet 而不是 DB ORDER BY？
**答**：ZSet 是**内存有序结构**，`ZRANGE/ZREVRANGE` 是 O(log N + M)，万级挂单毫秒级返回；DB 的 `ORDER BY` 每次全表排序，高并发下不可接受。且 ZSet 支持**实时增量更新**（`ZINCRBY` 调价），DB 每次都是整行 UPDATE + 重新排序。

### L4 · 追问：竞价高潮期 ZSet 本身成为热点怎么办？
**答**：① 竞价簿的 key 按**单品/场次**隔离（`auction:{id}`），热点打散；② 读多写多时，**主写从读**（写主、读从）或用**本地缓存 + 定期同步**；③ 关键竞价动作加**分布式锁**串行化，避免并发改价错乱；④ 极端场景用 **Lua 脚本**把「校验 + 出价」原子化。

## 🔥 追问链 09｜数据结构选型

> 考察意图：是否清楚每种 Redis 数据结构适合的业务场景，而非只会用 String。

### L0 · 主问题：Redis 有哪几种核心数据结构？
**答**：String、List、Set、ZSet、Hash，外加 Bitmap、HyperLogLog、Geo、Stream 等扩展结构。

### L1 · 追问：资金流水、待办清单、履约进度分别用什么结构？
**答**：**资金流水**（时序、可裁剪）→ List 或 ZSet（按时间 score 排序）；**待办清单/任务**（去重、状态）→ List 做队列，或 Set 做去重集合；**履约进度/节点状态**（字段化）→ Hash，`HSET fulfillment:{planId} payment 1 delivery 0`，一次读写多个字段。

### L2 · 追问：为什么「对象/行数据」用 Hash 而不是把整个 JSON 塞进 String？
**答**：Hash 能**按字段局部读写**（`HGET/HINCRBY`），改一个字段不用序列化整个对象；String 存 JSON 每次都要整体 GET→改→SET，浪费且易并发覆盖。**对象有字段级更新需求 → Hash**；纯只读缓存 → String JSON 也行。

### L3 · 追问：大屏实时看板（05-screen）这类「统计」数据用什么？
**答**：**Bitmap**（签到/活跃用户/去重计数）、**HyperLogLog**（海量 UV 去重，误差 0.81%）、**ZSet**（Top N 排行）。如「今日成交额 Top 10 商品」用 ZSet，「活跃企业数」用 Bitmap 或 HLL。统计类用这些结构**内存占用极小、实时性高**，比 DB `GROUP BY` 强得多。

### L4 · 追问：Set 和 ZSet 的区别？什么时候用哪个？
**答**：Set 是**无序去重**集合，适合「去重 + 集合运算」（如「同时持有 A/B 合同的企业」用 SINTER）；ZSet 是**有序去重**，适合「排名/区间」（如「资金流水按时间、竞价按价格」）。**需要顺序/排名 → ZSet，只要去重 → Set**。

## 🔥 追问链 10｜持久化与高可用

> 考察意图：资金缓存的数据可靠性，RDB/AOF/主从/集群/热 key 的完整体系。

### L0 · 主问题：RDB 和 AOF 的区别？
**答**：RDB 是**快照**，把某个时刻内存全量 dump 到文件，恢复快但两次快照间可能丢数据；AOF 是**追加日志**，每条写命令都记，丢得少但文件大、恢复慢。默认混合：RDB 全量 + AOF 增量。

### L1 · 追问：资金缓存用什么持久化策略？
**答**：**AOF everysec**（每秒 fsync 一次，最多丢 1 秒数据）+ 定期 RDB 兜底。资金余额/幂等键这类，宁可牺牲一点性能也要少丢；而纯缓存数据（可重建的）甚至可以**关闭持久化**。核心是**按数据重要性分级配置**——资金状态要 AOF，普通缓存可不持久化。

### L2 · 追问：主从、哨兵、集群分别解决什么问题？
**答**：**主从**解决读扩展 + 数据冗余（主写从读）；**哨兵**解决高可用（主挂了自动选新主）；**集群（Cluster）**解决水平扩展（数据按 slot 分片到多个主节点）。资金系统通常是「**主从 + 哨兵**」保证可用，数据量大再上「**集群**」。

### L3 · 追问：集群的 slot 哈希是什么？会有什么问题？
**答**：集群把 key 按 **CRC16(key) % 16384** 映射到 slot，slot 分布到各节点。问题：**跨 slot 的多 key 操作**（MGET、Lua 多 key）会失败，需要 hash tag（`{poolId}`）把相关 key 落到同一 slot；**热 key**会集中打某一节点导致单点瓶颈。

### L4 · 追问：资金余额是天然热 key，怎么办？
**答**：① **拆 key**：`fund:balance:{poolId}` 无法拆时，用**多副本 key**（`balance:0/1/2...`）读时随机、写时全量或聚合；② **本地缓存**：余额短期缓存在应用内存（Caffeine），减少打 Redis；③ **读写分离**：读走从节点分摊；④ **限流**保护主节点。核心是**把单点的集中读写打散**。

### L5 · 追问：主从切换期间，幂等键/锁丢了会怎样？怎么兜底？
**答**：主从**异步复制**，切换瞬间可能有数据未同步，导致幂等键/锁丢失 → 重复扣款/重复执行风险。兜底：① **DB 唯一索引/状态机永远是最终裁决**（Redis 丢了也能拦住）；② 关键资金操作**降级为 DB 强一致**（短暂牺牲性能换正确性）；③ 监控主从延迟，延迟过高时告警或熔断。**资金场景的底线永远是 DB，Redis 只是加速**。

## 🔥 追问链 11｜单线程模型与性能

> 考察意图：Redis 单线程「快」的本质，以及哪些操作会踩性能坑。

### L0 · 主问题：Redis 是单线程，为什么还这么快？
**答**：① **纯内存操作**；② **IO 多路复用**（epoll）单线程高效处理海量连接；③ **单线程无锁无上下文切换**，避免了多线程竞争开销。瓶颈不在 CPU 而在内存和网络。

### L1 · 追问：6.0 之后不是多线程了吗？
**答**：6.0 的多线程**只用于网络 IO 的读写解析**（收发数据、协议解析），**命令执行仍是单线程**。这样既利用多核处理 IO，又保持命令执行的原子性和无锁优势。

### L2 · 追问：哪些命令会阻塞 Redis？为什么危险？
**答**：**KEYS \***（全库扫描）、**大 key 的 DEL**、**SMEMBERS/HGETALL 大集合**、**flushall**、复杂排序。因为它们**单线程执行、耗时长**，期间所有其他命令排队，整个 Redis 卡顿。生产**禁用 KEYS**，用 `SCAN` 渐进式遍历；大 key 要拆分。

### L3 · 追问：大 key 会带来什么问题？怎么定位和处理？
**答**：大 key（单个 String 几 MB、集合几十万元素）会：**阻塞单线程**（读写/删除都慢）、**网络传输大**、**内存分布不均**、**主从同步慢**。定位：`redis-cli --bigkeys` 或 `MEMORY USAGE key`。处理：**拆分成多个小 key**（如大 Hash 按 ID 哈希拆 N 份）、集合用 HSCAN/SSCAN 分批读、删除用 `UNLINK`（异步删）。

### L4 · 追问：怎么定位 Redis 慢查询？
**答**：① `SLOWLOG GET` 看执行慢的命令及耗时；② 排查 `KEYS`/大 key/复杂度高的命令（`SORT`、`SINTER` 大集合）；③ 监控**内存碎片率**、`used_memory`、阻塞客户端数；④ 用 `redis-cli --latency` 测延迟。发现慢命令就改写（SCAN 替代 KEYS、拆分大 key、避免 O(N) 命令打大集合）。

## 🔥 追问链 12｜过期与淘汰策略

> 考察意图：内存管理与资金「冻结超时释放」的落地，能否把 TTL 机制用对。

### L0 · 主问题：Redis 的过期 key 是怎么删除的？
**答**：**惰性删除 + 定期删除**结合。惰性删除：访问 key 时发现过期才删；定期删除：后台周期性抽样检查过期 key 删除。两者配合，既不让过期 key 长期占内存，又不让删除阻塞。

### L1 · 追问：内存满了怎么办？淘汰策略有哪些？
**答**：按 `maxmemory-policy` 淘汰：**noeviction**（报错不淘汰，资金场景常用）、**allkeys-lru / volatile-lru**（LRU 淘汰）、**allkeys-lfu / volatile-lfu**（LFU 淘汰热点不敏感）、**random**、**ttl**（先删快过期的）。**资金/幂等键这类不能丢的，必须 noeviction**，宁报错也不静默丢。

### L2 · 追问：资金冻结的 TTL 怎么设？「冻结超时自动释放」怎么做？
**答**：系统设计里有「冻结超时自动释放」（如 2 小时超时释放，保护客户资金不被锁死）。实现：① 冻结 key 设 **TTL=2h**，配合 **keyspace 通知**（`EXPIRE` 事件）在过期时触发释放逻辑；② 或**延迟队列**（ZSet 用「过期时间戳」做 score，轮询取出已过期的冻结单释放）；③ DB 侧冻结单状态 + 定时任务扫描兜底。**超时释放必须幂等**（可能多次触发）。

### L3 · 追问：为什么不用「到期立刻删除」而是靠通知/轮询？
**答**：Redis 的过期是**惰性/定期**，不是「到期精确触发」；且业务释放动作（改 DB 状态、回补余额）**必须在业务侧做**，Redis 只能当触发器。所以用 keyspace 通知或延迟队列「**通知业务去释放**」，业务释放逻辑幂等 + DB 兜底。

### L4 · 追问：LRU 和 LFU 有什么区别？资金缓存用哪个？
**答**：LRU 按「**最近访问时间**」淘汰，LFU 按「**访问频率**」淘汰。LFU 更能保护「访问频繁但偶尔不被访问」的热点 key。资金/幂等缓存**不参与淘汰**（noeviction，宁可满也不丢）；普通缓存热点多的用 **LFU**，通用的用 **LRU**。

## 新增高频题（结合业务的 Redis 补充题）

### 补01 · Redis 和 Memcached 的区别？
**答**：Redis 支持**丰富数据结构**（String/List/Set/ZSet/Hash/Stream…）、**持久化**（RDB/AOF）、**主从/集群**、**原子 Lua**；Memcached 只支持 String、纯内存无持久化、多线程。资金系统需要「原子扣减 + 锁 + 幂等 + 持久化」，只能用 Redis。

### 补02 · 为什么资金余额用 Redis 而不用本地缓存（Caffeine）？
**答**：余额是**跨实例共享**的强一致数据，本地缓存每个实例各有一份，无法保证「全局唯一余额」和「原子扣减」。Redis 是**集中式共享内存**，所有实例读同一个余额、扣减原子。本地缓存只适合「字典、权限」这类**可容忍不一致、单实例热读**的数据。

### 补03 · 分布式锁的 value 为什么用「UUID + 线程号」而不是固定值？
**答**：释放锁时要**校验「这把锁是不是自己加的」**。固定 value 无法区分「A 的锁」和「B 的锁」，误删风险高；用 UUID+线程号唯一标识加锁者，Lua 释放时 `GET == value` 才删，避免误删别人的锁。

### 补04 · Redis 的 key 设计有哪些规范？
**答**：① **有业务前缀 + 冒号分层**：`fund:balance:{poolId}`、`settle:idem:{no}`；② **可读、见名知义**；③ **控制长度**（太长占内存）；④ **避免热 key**（热点拆多副本）；⑤ **避免大 key**（集合过大拆分）；⑥ 用 `hash tag {poolId}` 保证相关 key 同 slot。

### 补05 · 缓存与 DB 双写，为什么会「数据错乱」？怎么用「双写一致性」解决？
**答**：并发下两个请求交叉写：A 写 DB、B 写 DB、B 删缓存、A 删缓存，最终缓存可能是旧值。解决：**串行化**（同 key 的写操作加锁/队列）、**延迟双删**、**canal 订阅 binlog 驱动**（DB 为准，缓存由 binlog 事件刷新），核心是**让 DB 成为唯一真相、缓存只能被动跟随**。

### 补06 · 为什么说「Redis 适合做缓存，不适合做数据库」？
**答**：Redis 数据在内存、持久化是「尽力而为」，**宕机可能丢数据、内存容量有限、事务只有单命令/Lua 的原子性**，没有关系型数据库的强事务和复杂查询。所以资金流水、账本这类「真相数据」必须落 MySQL/PostgreSQL，Redis 只做加速和并发控制。

### 补07 · 怎么保证「余额扣减」和「订单状态」两个动作的一致性？
**答**：这是**跨服务分布式事务**问题。方案：① **本地消息表 + MQ**（最终一致，系统常用）：本地事务同时写业务数据 + 消息表，MQ 投递驱动余额扣减，失败重试；② **TCC**（Try-Confirm-Cancel）：预扣（Try）→ 确认（Confirm）/ 取消（Cancel）；③ **Seata** 分布式事务框架。B2B 资金场景常用「**本地消息表 + MQ + 幂等 + 对账**」的组合，而非强一致 XA。

### 补08 · Redis 的 pipeline 和事务（MULTI/EXEC）有什么区别？
**答**：pipeline 是**批量发送命令减少 RTT**，但不保证原子性、无回滚；MULTI/EXEC 是**事务**，命令排队、EXEC 时原子执行（但**没有回滚**，某命令出错其他命令仍执行）。真正要「读-判-写」原子，用 **Lua 脚本**（Redis 单线程执行脚本，真正原子）。资金扣减用 Lua，批量查询用 pipeline。

### 补09 · 为什么 Redis 事务不支持回滚？
**答**：Redis 追求简单高效，命令在入队时已做语法校验，运行时错误（如对 String 做 LPUSH）**难以回滚且代价高**；Redis 认为**这类错误是编程错误，应在开发阶段发现**，不值得为它引入回滚机制。需要原子性用 Lua。

### 补10 · 缓存雪崩时，怎么用「限流 + 降级」保护资金链路？
**答**：① **限流**：网关/Redis 令牌桶（`INCR` + 过期做计数器）限制打到资金服务的 QPS；② **降级**：非核心读接口降级为返回缓存/兜底值，甚至关闭；③ **熔断**：资金 DB 压力过大时熔断非核心链路，**优先保证扣款/结算等核心资金动作**；④ **隔离**：资金服务的 Redis 与普通缓存 Redis **物理隔离**，避免普通缓存雪崩拖垮资金。

### 补11 · Redis 集群中，资金幂等键应该放哪个节点？怎么保证一致性？
**答**：用 **hash tag `{poolId}`** 让同一资金池相关的「余额、幂等键、锁」落到**同一 slot/节点**，保证相关 key 的 Lua 多 key 操作可用、且本地化减少跨节点请求。幂等键的最终一致性靠 **DB 唯一索引兜底**，不依赖 Redis 集群的强一致。

### 补12 · 如何用 Redis 做「限流」？（结合接口防刷）
**答**：① **固定窗口**：`INCR rate:user:{id}` + `EXPIRE 60`，超过阈值拒绝；② **滑动窗口**：ZSet 用时间戳做 score，`ZREMRANGEBYSCORE` 清理窗口外 + `ZCARD` 计数；③ **令牌桶/漏桶**：Lua 脚本原子实现令牌生成与扣减。资金系统的「支付接口防刷、结算接口限流」常用滑动窗口 + Lua。

### 补13 · Redis 的 keyspace 通知可靠性如何？资金释放能只靠它吗？
**答**：keyspace 通知是**尽力而为**，**不保证送达**（客户端断线、通知丢失都可能发生）。所以**资金冻结超时释放不能只靠 keyspace 通知**，必须「**keyspace 通知（快）+ 延迟队列/ZSet 轮询（稳）+ DB 定时任务扫表（最终兜底）**」多层冗余，释放逻辑幂等。

### 补14 · 什么是 Redis 的「缓存击穿」的「逻辑过期」方案？和「互斥锁」比有何优劣？
**答**：逻辑过期：缓存存「值 + 逻辑过期时间」，读时若逻辑过期，**先返回旧值**、异步开线程重建；互斥锁：过期后**只让一个线程回源**、其余等待。逻辑过期**用户体验好（不阻塞）**，但可能短暂读到旧值、实现复杂；互斥锁**数据新**，但会阻塞等待。资金热点余额用「原子扣减」不在此列，普通热点合同/商品用逻辑过期更平滑。
