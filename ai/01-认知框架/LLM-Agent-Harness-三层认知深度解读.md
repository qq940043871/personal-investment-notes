# LLM / Agent / Harness 三层认知深度解读

> 本文是**认知框架文章**，不写代码、不做技术栈声明。
>
> **缘起**：本文由一段自发的"顿悟"整理而来——原作者用自己的话描述了三层关系，并类比了传统工程的"业务功能 → 工程化"。本文的工作是：**先给这段理解逐句打分**（§0），**再把它补成一条完整的推导链**（§1–§4），最后落回项目（§7）。
>
> **术语说明**：Harness，读作"哈内斯"，原意**挽具**（套在马身上、用来驾驭马的那套皮具）。文中出现的 "Harmony" 系笔误，统一按 Harness 理解。

## 0. 先给这段理解逐句打分

这段原话的质量相当高——**核心框架是对的，而且"类比传统工程"这一手，比市面上绝大多数讲 Agent 的文章都更接近本质**。但有两个**词放错了位置**，而这两个位置恰好是后面所有翻车的起点。

| # | 原话 | 判定 | 要拧的地方 |
|---|---|---|---|
| 1 | LLM 是"最基础的**中间件**"，相当于一个**函数** | ⚠️ **一半对** | "函数"这个比喻**极其准确，保留**；但"中间件"**用反了**——中间件恰恰是 **Harness** 的角色，LLM 是**引擎本身** |
| 2 | 把很多知识库做了一个**聚合压缩** | ❌ **要改** | 参数里存的是**分布**，不是**库**。这个区别不是抠字眼——它是 **RAG 存在的全部理由** |
| 3 | Agent 让 LLM 具备**执行操作、连接万物**的能力 | ✅ 基本对 | 但"连接万物"这个能力**不是模型长出来的**，是被工程"接"上去的。载体是**工具协议** |
| 4 | Harness 更像 **Agent 工程**，让 Agent **更稳定、更节省、更安全** | ✅ **对** | 三个词都对，而且**比原话想的还要贴**——§4.3 逐个拆开 |
| 5 | 类比传统工程：业务功能 → 工程化（等保 / 健壮 / 扩展） | ✅✅ **完全成立** | 这是理解 Harness **最短的一条路**，§4.1 会把它拆成三层对应（含三处"对不上"） |

**一句话收束这五条：**

> 把"**中间件**"这个词从 LLM 头上摘下来，戴到 Harness 头上；把"聚合**压缩**"里的"库"改成"分布"。这两处一改，整张图就立住了。

## 1. 三层总览：一张图定位

```
        ┌─────────────────────────────────────────────────────┐
        │  Harness  ·  工程骨架  ──  让它「可靠」               │
        │  循环 · 状态 · 权限 · 恢复 · 卡点 · 观测               │
        │  ── 它不产生业务语义，它产生「约束」 ──                │
        ├─────────────────────────────────────────────────────┤
        │  Agent    ·  业务语义  ──  让它「会做事」             │
        │  决策体 · 动作空间 · 循环                             │
        │  ── 它决定「该做什么、说什么」──                      │
        ├─────────────────────────────────────────────────────┤
        │  LLM      ·  推理引擎  ──  让它「会说话」             │
        │  无状态纯函数：  messages[]  →  文本 / tool_calls     │
        │  ── 它只做一件事：预测下一个 token ──                 │
        └─────────────────────────────────────────────────────┘
                          ▲ 底座：算力 + 语料
```

| 层 | 一句话定位 | 产生什么 | 失败时的表现 | 传统工程里的对应物 |
|---|---|---|---|---|
| **LLM** | 推理引擎 | 概率性的文本与「调用意图」 | 胡说、幻觉、不会做但硬答 | **CPU / 引擎** |
| **Agent** | 业务语义与动作空间 | 业务决策：意图、步骤、输出 | 做错事、跑偏、原地绕圈 | **应用 / 业务逻辑** |
| **Harness** | 工程约束 | 可靠性、可管性、可观测、可中断 | *（它的失败是"看不出失败"）* | **操作系统 + 中间件 + 运维体系** |

> 🔑 **这三层里，只有 LLM 是不可替代的。**
> Agent 长什么样、Harness 装哪些机制，全都是**工程选择**。换一代模型，LLM 那层整体换代，下面两层的设计逻辑基本不动 —— 这正是一个成熟分层该有的样子。

## 2. LLM 层：它是引擎，不是中间件

### 2.1 "函数"这个比喻，比它看起来更重要

原话里"它更相当于一个函数"——这句是**全篇最好的一个比喻**。展开它，LLM 的全部工程特性就自动浮出来了：

| 函数的特性 | LLM 的对应 | 由此推翻了什么 |
|---|---|---|
| **有明确的输入输出契约** | 输入 `messages[]`，输出文本或 `tool_calls` | 它不会凭空"想做点什么"，一切意图都得经由输出表达 |
| **无状态** | 同一次调用**不记得**上一次；所谓"多轮对话"是 Harness 每次把历史**重新塞进去** | 🔴 记忆不属于模型，属于 Harness |
| **纯函数**（无副作用） | 它**不写库、不下单、不发消息** | 🔴 **所有"执行"都发生在模型外面** |
| 可重放但不可复现 | `temperature > 0` 时同输入**不同输出** | 🔴 没法用 `assert 相等` 来测试它 |

一句话写死：

> **LLM = f(上下文) → 下一个 token 的概率分布。**
>
> 它就是一个**把"上下文"映射成"下一个词"的概率函数**，仅此而已。它不"知道"任何事，它只是**非常擅长预测下一个词该是什么**，而预测得足够好时，看起来就像"懂"了。

### 2.2 "聚合压缩"要改一个词：是「分布」，不是「库」

这是最需要纠正的一处，因为**它直接决定了你后面会不会给 RAG 排错位置**。

预训练做的事情，确实可以叫"压缩"——把海量语料的信息量，压进固定的参数量里。但这是**有损压缩**，而且**优化目标是"预测下一个词"，不是"记住每一句话"**。所以参数里存下来的，是**统计规律和分布**，不是**可检索、可溯源的条文**。

| | 知识库（RAG 用的那个"库"） | 模型参数里的"知识" |
|---|---|---|
| **存的是什么** | 原文，可逐字引用 | 统计规律 / 分布 |
| **能否检索** | ✅ 按 key / 向量精确取 | ❌ 只能靠"提问"间接唤醒，唤出来的是**重构版** |
| **能否溯源** | ✅ 给得出出处、条款号 | ❌ **说不出**这段话是从哪来的 |
| **能否更新** | ✅ 改一条就是一条，立即生效 | ⚠️ 要重训 / 微调，且改一处常坏一片 |
| **输出一致性** | ✅ 确定 | ❌ 同一个问题问两次，措辞可能不同 |

> 🔑 **这五条差异，就是 RAG 存在的全部理由。**
>
> 也解释了你项目里两条最"反直觉"的设计：**为什么要强制逐字引用 + 引用核验**（因为模型会"重构"原文）、**为什么直击库命中就逐字输出不过模型**（因为"这个文件有效期几年"这类答案，必须逐字固定）。

**顺带回答一个必然的追问：那幻觉是哪来的？**

不是模型"学坏了"。是**有损压缩的必然副产品**：

- 参数容量远小于语料 → 高频事实记得牢，**低频细节被模糊化**；
- 训练目标只要求"续写合理"，不要求"事实正确" → 于是在记不清的地方，它会**自动生成一个"看起来合理"的续写**。

所以幻觉的物理来源是：**模型在"模糊区"里做了一次概率最高的猜测，而它的猜法极其流畅，你听不出破绽。** 这不是 bug，是它的工作方式。

### 2.3 LLM 的四个先天缺陷 —— 这是后面所有工程的靶子

| # | 先天缺陷 | 直接后果 | 谁来兜 |
|---|---|---|---|
| 1 | **不确定**（概率生成） | 同输入不同输出，没法断言相等；会跑飞、会死循环 | Harness · 闸门 + 评测 |
| 2 | **无状态** | 不记得上一轮，长任务断了没法续 | Harness · 状态管理 |
| 3 | **会说谎**（目标是"像"不是"真"） | 会幻觉、会编工具名、会越权试探 | Harness · 核验闸门 + 权限收口 |
| 4 | **按 token 计费** | 成本随文本线性涨，失控 = 烧钱 | Harness · 预算闸门 |
| 5 | *（额外）* **不能承担外部后果** | 它可以"决定下单"，但它赔不起 | Harness · 人工介入 |

> 🔑 **LLM 的每一个优点，翻过来都是一个工程问题。**
> "会说话"→ 会胡说；"会推理"→ 会钻牛角尖；"能调工具"→ 能误操作。
> **这五条就是 Agent 和 Harness 存在的全部理由**——不是"AI 需要更多功能"，而是"这个引擎有五个洞，得有人堵"。

## 3. Agent 层：给引擎接上传动轴

### 3.1 原话要补一个动词：能力是"被接上去的"

原话"Agent 是让大模型具备可以执行一些操作、连接万物的功能"——方向对，但要补一个关键动词：**接**。

模型自己**长不出**手。它只能"说"（输出文本），所以它说"我想调用查天气这个工具"——**这句话本身就是一段文本**。真正去查天气，是**外面那层**听了这句话之后干的。

Agent 的最小充分条件（三件套）：

| # | 条件 | 含义 | 你项目里的形态 |
|---|---|---|---|
| 1 | **一个决策体** | 谁来决定"下一步做什么" | 轻量分类模型（意图/槽位）+ 生成模型（解读） |
| 2 | **一个动作空间** | 能做什么 | 检索 / 直击匹配 / 规则裁决 / 生成 |
| 3 | **一个循环** | 拿到结果后还能不能再走一步 | 直击未命中 → 回落 RAG；核验失败 → 重试 1 次 → 降级 |

**缺任何一个，都不是 Agent：**

> - 有模型、无动作 → **Chatbot**
> - 有动作、无循环 → **Workflow**（路径人写死的）
> - 有循环、无决策体 → **定时任务**

### 3.2 "连接万物"的真正载体：工具 + 协议（这里有个高频幻觉）

这是面试和方案评审里**被说错最多的一处**，必须先钉死：

> 🔴 **大模型从头到尾不知道 MCP 是什么。它只会吐 `tool_calls`。**

```
   ①  模型看到 tools 定义（一段 JSON Schema）
                  │
                  ▼
   ②  模型输出 tool_calls —— 这只是一段 JSON，什么都没发生
                  │
                  ▼
   ③  ★ Harness 解析这段 JSON ★ ← 权限校验、参数校验、是否要人工审批，全在这一层
                  │
                  ▼
   ④  Harness 去执行 —— 走本地函数，或走 MCP Server
                  │
                  ▼
   ⑤  Harness 把结果回灌给模型，进入下一轮
```

| 概念 | 它到底是什么 | 谁在用它 |
|---|---|---|
| **Function Call** | 模型表达"我想调什么"的**语法**（吐 JSON 的能力） | 模型 → Harness |
| **Tool** | 真正被执行的**函数 / HTTP 接口** | Harness |
| **MCP** | 把工具标准化成"**可插拔**"的协议 | Harness ↔ 外部服务 |

> 所以"Agent 连接万物"的准确说法是：**Harness 通过工具（必要时通过 MCP）去连接万物，模型只负责"说要连哪个"。**
>
> 这个心智模型立不住，后面权限、审批、幂等、超时的位置**全会放错**——因为你会以为"模型在直连数据库"，从而把校验做在错误的层上。

### 3.3 Agent 的代价：它把 LLM 的缺陷放大到"有副作用"的世界

只做问答时，模型的缺陷顶多是"答案不准，重问一次"。**一旦有了动作，同一个缺陷就变成了事故：**

| 缺陷 | 只做问答时 | **有了动作之后** |
|---|---|---|
| 不确定 | 答案不稳定，重问 | 🔴 **同一指令执行两次 → 扣两次钱** |
| 会说谎 | 编个答案 | 🔴 **编出一个不存在的工具名并尝试调用** |
| 无状态 | 忘了上下文 | 🔴 **长任务中断后无法续做，只能从头来** |
| 按 token 计费 | 有点贵 | 🔴 **死循环 = 无限烧钱** |
| 不能担后果 | —— | 🔴 **它自主下单了，但没人能负责** |

> 🔑 **结论：Agent 越强，Harness 就必须越硬。**
> 给它装上手，就得同时装上**刹车**（闸门）、**安全带**（权限）、**行车记录仪**（trace）。**只装手不装刹车，那不叫升级，那叫事故。**

## 4. Harness 层：工程化，让能力变成产品

### 4.1 那个工程类比完全成立 —— 但要拆成三层才看得全

原话：*"正常的一个工程，它可能就是只能满足业务功能。但是工程化可以让它满足等保测评，更健壮，扩展性更好。"*

这个类比的价值在于：**它把 Harness 从"AI 黑话"变回了你熟悉的传统工程语言。**

但"一一对应"这个说法只说对了三分之二。**要补全它，得分三层看**：能直接对上的（大多数）、要改语义才能对上的（少数但关键）、以及传统工程里**压根没有对应物的新东西**（恰恰是最贵的部分）。三层都看完，你才不会在评审时说出一句危险的话——"这不就是加了个中间件嘛"。

#### ▌第一层：成熟度阶梯 —— "能跑" 与 "能上生产" 的同一道断层

先把类比拉回最粗的骨架上。传统工程从"能跑"到"能上生产"要爬五级阶梯，Agent 工程一模一样：

| 成熟度 | 传统工程 | Agent 工程 |
|---|---|---|
| **L1 能跑** | 功能跑通，本地能演示 | Prompt 调通，能答、能调工具 |
| **L2 能测** | 单元测试 · 断言 · CI 门禁 | 评测集 · 回归 · 双跑比对 |
| **L3 能运维** | 日志 · 监控 · 告警 · 重试 | trace 全链路 · 四层恢复链 |
| **L4 能审计** | 权限 · 留痕 · 等保合规 | 鉴权跟用户走 · 工具分级 · 审批留痕 |
| **L5 能扩展** | 分层解耦 · 水平扩容 | 状态外置 · 工具注册表 · 实例无状态 |

> 🔑 **同一个断层，出现在两个地方**：L1 与 L2 之间，就是"Demo"和"系统"的分水岭。
>
> Harness 的使命，是把 Agent 从 **L1** 推到 **L4 / L5**。这件事传统工程走了二十年，Agent 工程得在两年内走完——**因为它的出事概率，比传统软件高一个数量级。**

#### ▌第二层：十维逐项对照

| # | 传统工程在做的事 | 对应的 Harness 机制 | 不做会怎样 |
|---|---|---|---|
| 1 | **等保 / 合规**：权限、审计、留痕 | 鉴权跟用户走 · 工具三级分类 · 审计留痕 | AI 成为系统里的**新权限旁路** |
| 2 | **健壮性**：超时 / 重试 / 熔断 / 降级 | 四层恢复链（重试→降级→补偿→熔断） | 一次超时毁掉整个任务 |
| 3 | **一致性 / 事务**：幂等、Saga、对账 | 幂等键 · 检查点 · 补偿动作 | 重试一次 = 多扣一次钱 |
| 4 | **可观测**：监控 / 日志 / 链路追踪 | `trace_id` 全链路 + 三层评测 | 分不清"是模型选错工具"还是"工具挂了" |
| 5 | **可扩展**：分层 / 解耦 / 水平扩容 | 状态外置 · 工具注册表 | 请求必须回到同一实例，扩不了容 |
| 6 | **审批流**：双人复核 / 灰度发布 | HITL 人工卡点 | 不可逆动作被模型自主执行 |
| 7 | **成本控制**：容量规划 / 限流 | 预算闸门 · token 护栏 · 小模型路由 | 成本失控，而且是"悄悄失控" |
| 8 | **配置与版本管理** | Prompt 版本化 · 工具 schema 版本化 · 参数外置 | 改一处 Prompt 悄悄影响十条链路，还回滚不了 |
| 9 | **契约与兼容性**：IDL / 接口版本 | 工具 schema 即契约 · 新旧版本并存期 | 字段对不上，运行期才炸 |
| 10 | **变更安全**：灰度 / 回滚 / 演练 | 评测门禁 · 双跑比对 · 故障注入演练 | "改好了 A 场景、改坏了 B 场景"你永远不知道 |

#### ▌第三层：具名映射 —— 六个机制在传统工程里的"前世"

这一层最实用：**六机制不是新发明，它们在传统工程里全都有具名的对应物**，你的经验可以直接迁移。

| Harness 机制 | 传统工程里的具名对应物 | 可迁移的经验 |
|---|---|---|
| 机制一 · 执行循环 + 终止闸门 | 工作流引擎 / **Saga 编排器** / 状态机（Temporal、Camunda） | 多步流程的推进、超时、死循环保护 |
| 机制二 · 状态管理 + 检查点 | **outbox 事件表** / 会话外置 / 快照 / 断点续传 | 进程杀掉能续，且不重复执行 |
| 机制三 · 权限控制 | 网关鉴权 + **RBAC / ABAC** + 数据行级权限 | 鉴权跟请求方身份走，不跟执行通道走 |
| 机制四 · 异常恢复 | 退避重试 / 降级 / 补偿 / **熔断**（Hystrix、Resilience4j）/ 隔离舱 | 失败必须分级，不能一把梭 |
| 机制五 · 人工介入（HITL） | **审批流** / 双人复核 / 工单 / 灰度发布 | 不可逆动作前必须先卡一道 |
| 机制六 · 评测观测 | On-call / 指标监控 / **链路追踪**（Jaeger、SkyWalking）/ 对账 / 双跑比对 | 出问题能定位、能归因、能追责 |

> 权威展开见 `ai/01-认知框架/Harness-详细设计与项目落地.md` **§2**（六机制总览的"我的同构经验"列）与 **§4.5**（与 Saga 的同构关系）。本文只做总纲映射，不复述细节。

#### ▌★ 第四层：有三处对不上 —— 而这恰恰是 Harness 真正的新东西

上面说"几乎一一对应"。但**恰恰是这三处对不上，构成了 Harness 不可替代的部分**。只记住"一一对应"，你会在技术评审里说错话。

**① 传统工程里没有"会说谎的组件"，所以"核验"是凭空新增的。**

传统工程的组件是**确定性的**：函数返回什么就是什么，接口不会"编造"一个字段。
而模型会**自信地编造**——编工具名、编参数、编引用来源。所以 Harness 必须加一道传统工程里**找不到对应物**的机制：**输出核验**（引用核验、schema 校验、事实一致性检查）。

> 你项目里的"**强制逐字引用 + 引用核验**"就是这道闸门。它的传统工程等价物是——**没有**。传统工程不需要核验"一个组件有没有说真话"。

**② 传统工程的幂等靠主键；Agent 的幂等要靠"语义级意图判定"。**

传统工程里，同一个 `request_id` 重放，数据库唯一约束就挡住了。
但 Agent 场景下，**两次调用可能参数不同、意图却相同**（模型"重试"时会把 `{"amount":300}` 顺手改写成 `{"amount":300,"note":"确认"}`），主键拦不住。所以 Agent 的幂等必须升级成**语义级**：按"工具 + 业务键 + 时间窗"判重，而不是按字面参数。

> 这就是为什么"**重复检测**"这道闸门比传统"幂等键"难得多——也解释了"模型用同一工具、同一套参数原地打转"为什么这么难防。

**③ 传统工程的测试靠断言；Agent 的测试只能靠评测集。**

传统工程：`assert f(3) == 6`——输入确定、输出确定。
Agent：同一输入两次输出不同（`temperature > 0`），**没有"唯一正确答案"，只有"可接受分布"**。于是测试手段整体换掉：断言 → **评测集 + 评分器 + 双跑比对 + 人工抽检**。

> 🔑 **这条是"Agent 工程比传统工程更难"的物理原因**：你**失去了最便宜、最基础的那个工程工具——断言**。
>
> 也正因如此，§4.3 里的"评测与观测"必须与"执行循环"平起平坐，而不是当成一个可选项。

**收束 —— 修正版的一句话对应关系：**

> 🔑 **Harness 之于 Agent ≈ 工程化之于能跑的代码，**
> **但多出三样传统工程里没有的东西：核验（防说谎）· 语义级幂等（防绕圈）· 评测（因为失去了断言）。**
>
> 前 80% 你可以用传统工程的经验**直接迁移**——这省下大量试错；
> 后 20% 是全新的——**这决定了你会不会在评审时说错话。**
>
> Demo 和产品的差距，从来不在功能多少，而在"出事的时候谁兜着"。传统软件是这样，Agent 更是这样——**因为 Agent 的出事概率，比传统软件高一个数量级。**

### 4.2 第一性原理：五个约束源 → 六个机制

这是 Harness 的**推导链**，不是功能清单。**看懂这张表，第六章的机制就全是它的推论。**

| 模型的物理约束 | 直接后果 | 衍生的 Harness 机制 |
|---|---|---|
| **不确定**（概率生成） | 会跑飞、会死循环 | 机制一 · 执行循环（含终止闸门）<br>机制六 · 评测观测 |
| **无状态** | 长任务断了没法续 | 机制二 · 状态管理 |
| **会说谎** | 会幻觉、会编工具名、会越权尝试 | 机制三 · 权限控制<br>机制四 · 异常恢复 |
| **按 token 计费** | 失控 = 烧钱 | 机制一 · 预算闸门<br>机制六 · 成本护栏 |
| *（第五）* **不能担后果** | 不可逆动作没人负责 | 机制五 · 人工介入（HITL） |

> 🔑 **判据：任何一条机制，如果你说不出它在兜哪个约束，那它多半是过度设计。**

### 4.3 "更稳定 / 更节省 / 更安全" —— 逐个拆开

原话这三个词选得很准。逐个拆，看 Harness 具体靠什么做到：

#### ▌更稳定

| 手段 | 具体做法 |
|---|---|
| **防跑飞** | 四道闸门：步数上限 · 预算上限 · 墙钟超时 · **重复检测** |
| **防崩溃** | 四层恢复链：重试 → 降级 → 补偿 → 熔断转人工 |
| **防断链** | 状态外置 + 检查点，**杀掉进程能恢复**，且不重复执行工具 |
| **降级纪律** | 所有降级朝"**信息更少但更确定**"的方向走，绝不反向 |

> ⚠️ **四道闸门里，最容易被漏的是"重复检测"。** 模型拿同一个工具、同一套参数**原地打转**，是生产环境最典型的失控形态。只靠步数上限兜的话，**你会在烧掉几十万 token 之后才发现它在绕圈**。

#### ▌更节省 —— 注意：省的不是"模型少说话"，而是"**模型少被调用**"

这是最容易被理解偏的一条。真正的省钱逻辑是**分层拦截**：

| 手段 | 省在哪 | 你项目里的对应 |
|---|---|---|
| **直击库命中直返** | **0 生成 token** | Q&A 直击库 L0/L1/L2，命中即逐字返回 |
| **小模型路由** | 分类任务不走大模型 | 意图识别 / 槽位抽取用轻量模型 |
| **规则前置** | 能正则命中的不问模型 | 文号、条款号正则命中直接返回 |
| **上下文预算** | 防上下文膨胀吃掉 token | 按预算表裁剪，超了主动裁 |
| **缓存** | 相同问题复用结果 | 高频问题缓存 |
| **预算闸门** | 失控即止损 | 单次运行 token / 金额上限 |

> 🔑 **你项目里最值钱的一句话就是这条：「18 步里只有 3 步进模型」。**
> 剩下 15 步用代码做——**不只是为了准，也正是为了省**。省 token 的最高级形态，不是让模型答得简短，是**让它压根不用出场**。

#### ▌更安全

| 手段 | 铁律 |
|---|---|
| **鉴权** | 🔴 **跟着用户身份走，不跟着 Agent 走** —— 否则 AI 就是系统里的一个新权限旁路 |
| **工具分级** | 只读免审批 / 写操作记录 + 幂等 / **高危必须人工确认** |
| **两道闸门** | A（检索前）管"**模型能看到什么**" · B（输出前）管"**用户能看到什么**" |
| **人工卡点** | 🔴 唯一安全插入点 = **模型响应之后、工具执行之前** |

> ⚠️ **两条最容易翻车的细节：**
> 1. **权限画像获取失败时，必须拒绝服务。** 兜底成"默认宽松"= 整套权限体系作废，而且**日志上一切正常**。
> 2. **人工拒绝后，仍然必须回灌一条结果。** "不执行" ≠ "不回消息"。跳过被拒的调用，下一轮立刻报错——这是人工介入上线后最常见的线上故障。

## 5. 三层总表：谁产生什么、改一层要动哪里

| 维度 | LLM | Agent | Harness |
|---|---|---|---|
| **抽象层次** | 引擎 | 应用 / 业务逻辑 | OS + 中间件 + 运维体系 |
| **它产生什么** | 文本 / 调用意图 | 业务决策 | **约束** |
| **它不负责什么** | 一切执行、记忆、权限 | 可靠性 | 业务语义 |
| **失败时的表现** | 胡说八道 | 做错事 / 跑偏 | *（表现为"看不出失败"）* |
| **换掉它要改什么** | 换 API / 换模型 | 改 Prompt 与工具描述 | **基本不用动** |
| **优化方向** | 换更大的模型 | 改工具与流程设计 | 加闸门 / 评测 / 状态 |
| **你项目里的实体** | 各模型 API | 政策解读 Agent（Dify 承载） | Dify 引擎替承载 / 自研 MainLoop |

**一句能背下来的分工：**

> **LLM 会说话；Agent 会做事；Harness 让它「做得可靠、管得住、看得见、停得下」。**

再补一句最容易被糊掉的分工（来自 `ai/01-认知框架/Agent-详细设计与项目落地.md` §6）：

> - **Agent** 决定"该做什么、说什么"（业务语义）
> - **Harness** 保证"它做的每一步都可靠、可管、可查、可停"（工程约束）

## 6. 六个常见误解（前两个就是你原话里踩的）

| # | 误解 | 正解 |
|---|---|---|
| 1 | "LLM 是个中间件" | 它是**引擎**。**中间件是 Harness** —— 这个位置一换，整张图就通了 |
| 2 | "模型把知识库压缩进参数，需要时检索出来" | 参数是**分布**、**不可检索**、**不可溯源** → 这才是 RAG 存在的理由 |
| 3 | "模型直连 MCP / 直连数据库" | 模型只吐 `tool_calls`（一段 JSON），**一切执行与校验都在 Harness** |
| 4 | "Agent 就是更聪明的模型" | Agent 是**使用模型的模式**（决策体+动作+循环），同一个模型既能做 Chatbot 也能做 Agent |
| 5 | "上了 Agent 就不用工程了" | **恰好相反**：能力越强、副作用越大，兜底必须越重 |
| 6 | "Harness 是平台的事，业务同学不用管" | 平台（Dify / LangGraph）替你实现的那些，**仍需逐条核对语义是否满足** —— 比如元数据过滤在"单节点挂多知识库"时**静默失效**、TopK/Score 阈值**只在 Rerank 阶段生效** |

## 7. 落到你的项目：三层的具体投影

| 层 | 项目里的实体 | 口径 / 边界 |
|---|---|---|
| **LLM** | Dify 里挂的**生成模型** + **轻量分类模型** | 唯一真正需要"把条款翻译成人话"的地方（18 步里的 04/05/15） |
| **Agent** | **政策解读 Agent**（六层 + 两道闸门） | **公司项目**；个人参与边界 = 前期选型（Dify vs 自研）+ MinerU 解析改造 |
| **Harness** | ① Dify 引擎替承载的骨架；② **个人储备**：FastAPI + MainLoop | 个人部分明确标注**"个人技术储备"**，**绝不混入公司平台技术栈** |

> 🔑 **一个必须记住的结构性事实：在你项目里，Agent 和 Harness 走的是两条不同的轨道。**
>
> 政策解读 Agent 跑在 **Dify** 上（业务编排，公司项目）；而 Agent Harness（FastAPI + MainLoop）是**个人储备**。两者讲的是**同一层职责，但承载方不同**。任何材料里把 FastAPI / Python 说成平台后端栈，都算**过度声明**——这条口径红线，比任何概念都重要。

## 附：四问速答（可直接用于面试）

**Q1：LLM、Agent、Harness 三者什么关系？**

LLM 是引擎——一个把上下文映射成下一个 token 分布的无状态函数，它只会"说"。Agent 是应用层——用决策体、动作空间、循环这三件套，让模型从"会说话"变成"会做事"，决定该做什么、说什么。Harness 是套在外面的工程骨架，它不产生业务语义，只产生**约束**：循环、状态、权限、恢复、卡点、观测。一句话：**LLM 会说话，Agent 会做事，Harness 保证它做得可靠、管得住、看得见、停得下。**

**Q2：为什么必须有 Harness？**

因为模型有五个先天缺陷：**不确定、无状态、会说谎、按 token 计费、不能承担外部后果**。只做问答时，这些缺陷顶多是"答案不准"；一旦给了它动作，同一个缺陷就变成事故——重复执行会扣两次钱，编造工具名会去调不存在的接口，死循环等于无限烧钱，它自主下单了但没人能负责。所以能力越强，兜底就必须越重。**Agent 的可靠性不来自模型，来自 Harness。**

**Q3：模型是怎么调用工具和 MCP 的？**

关键要先破一个幻觉：**模型从头到尾不知道 MCP 是什么。** 它的职责只有一件事——吐出一段 `tool_calls` JSON，说"我想调哪个工具、参数是什么"。真正解析这段 JSON、做权限校验、判断要不要人工审批、然后去执行的，是 **Harness**。走本地函数还是走 MCP Server，是 Harness 的决定。所以"Agent 连接万物"的准确说法是：**Harness 通过工具去连接万物，模型只负责说要连哪个。**

**Q4：Harness 和你熟悉的后端工程有什么关系？**

分三层说。**第一层是成熟度阶梯**：传统工程从"能跑的代码"到"能上生产"要过测试、监控、审计、扩容四道关，Agent 一模一样——Harness 的使命就是把 Agent 从 L1 能演示，推到 L4 能审计、L5 能扩展。**第二层是逐维对应**：等保合规→权限收口与审计留痕，健壮性→重试降级熔断补偿，事务一致性→幂等与检查点，链路追踪→`trace_id` 全链路，审批流→HITL 人工卡点，成本控制→预算闸门。**第三层是具名迁移**：六机制在传统工程里都有"前世"——Saga 编排器、outbox 事件表、RBAC、熔断、审批流、链路追踪。

但**必须补一句关键的**：有**三处对不上**，而且恰恰是最值钱的三处。① 传统工程的组件不会说谎，"输出核验"是 Harness 凭空加的机制——你项目里"强制逐字引用 + 引用核验"就是它；② 传统工程幂等靠主键，Agent 两次调用可能参数不同、意图相同，得升级成"语义级幂等"，这就是"重复检测"比幂等键难的原因；③ 传统工程靠断言来测，Agent 同输入不同输出、没有唯一正确答案，只能换成评测集 + 评分器。

所以准确的说法是：**Harness 之于 Agent ≈ 工程化之于能跑的代码，但多出三样传统工程里没有的东西——核验（防说谎）、语义级幂等（防绕圈）、评测（因为失去了断言）。前 80% 可以直接迁移经验，后 20% 决定了你会不会在评审时说错话。**
