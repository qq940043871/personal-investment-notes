## 0. 一句话总纲

> **Agent 的可靠性不来自模型，来自 Harness。**
>
> 循环上限、状态外置、权限分级、失败补偿、人工卡点、评测观测 —— 这六个机制，一个都不能少。少了任何一个，你交付的不是"智能体"，是"一个会说人话但随时会失控的黑盒"。

模型是**概率性的、无状态的、按 token 收费的、会说谎的**。Harness 就是套在它外面的那层工程骨架，把这四个先天缺陷逐一兜住。

## 1. Harness 是什么

### 1.1 定义

> **Harness（挽具）= 套在模型外面的那层工程骨架，把"一个会说人话的模型"变成"一个可靠、可管、可观测的执行体"。**

它不产生任何业务语义 —— 它产生的是**约束**。

### 1.2 与相邻概念的边界

这四个词经常被混着用，但职责完全不同：

| | 是什么 | 产生什么 | 典型代表 |
|---|---|---|---|
| **Model** | 推理服务 | 文本 / 调用意图 | GPT 系、Claude 系、本地模型 |
| **Harness** | **执行骨架** | **约束**：循环、状态、权限、恢复、卡点、观测 | 本文；OpenAI Agent SDK 的执行层；自研 MainLoop |
| **Agent** | 业务语义 | 业务决策：意图、槽位、解读 | 政策解读 Agent（见配对文档） |
| **编排平台 / Framework** | 承载 Harness 的容器 | 载体 | Dify、LangGraph、Temporal（对 Agent 场景） |

**一句话分清 Agent 和 Harness：**

> **Agent 决定"该做什么、说什么"；Harness 保证"它做的每一步都可靠、可管、可查、可停"。**

**一句话分清 Harness 和编排平台：**

> 编排平台是**装 Harness 的盒子**。Dify 帮你实现了循环、状态、日志的一部分 —— 但**它替你实现的那些，仍然需要你逐条核对语义是否满足**（详见 §9.2）。
>
> **与传统工程的对应关系（速览）**：六机制在传统工程里几乎都有"前世"——Saga 编排器、outbox 事件表、RBAC、熔断、审批流、链路追踪（详见 §2 的"我的同构经验"列与 §4.5）。但**有三处对不上**：核验（防说谎）、语义级幂等（防绕圈）、评测（因失去断言）。完整的三层映射见 `ai/01-认知框架/LLM-Agent-Harness-三层认知深度解读.md` §4.1。

### 1.3 为什么必须有：四条物理约束 → 六个机制

这是整份文档的推导链。**看懂这张表，后面全是它的推论。**

| 模型的物理约束 | 直接后果 | 衍生出的 Harness 机制 |
|---|---|---|
| **不确定**（概率生成，同输入可不同输出） | 没法断言相等；会跑飞、会死循环 | 机制一 · 执行循环（含终止闸门）<br>机制六 · 评测观测 |
| **无状态**（模型不记得上一轮） | 上下文要自己拼；长任务中途失败没法续 | 机制二 · 状态管理 |
| **会说谎**（目标是"像"不是"真"） | 会幻觉、会编工具名、会越权尝试 | 机制三 · 权限控制<br>机制四 · 异常恢复（错误也是一种"胡说"） |
| **按 token 计费** | 成本随文本线性涨；失控 = 烧钱 | 机制一 · 预算闸门<br>机制六 · 成本护栏 |

**第五条不在表里但同样关键 —— 外部动作不可逆。**
模型可以"决定下单"，但它不能承担后果。所以必须有 **机制五 · 人工介入**。

> 这五个源头，就是六机制存在的**全部理由**。任何一条机制，如果你说不出它在兜哪个约束，那它多半是过度设计。

## 2. 六机制总览

| # | 机制 | 要解决的问题 | 不做会怎样 | **我的同构经验** | 落地形态（个人储备） |
|---|---|---|---|---|---|
| 1 | **任务执行循环** | 感知→规划→行动→观察的推进与终止 | 无限循环、烧钱、跑飞 | 工作流编排 / **Saga 编排器** / 状态机 | FastAPI 承载的 **MainLoop** |
| 2 | **状态管理** | 会话与任务状态放在外部，每步可恢复可回放 | 重启即丢、长任务断了没法续 | **outbox 事件表 / 幂等 / 会话外置** | 外置存储 + 检查点快照 |
| 3 | **权限控制** | 工具分级；高危需显式授权 | AI 变成系统里的新权限旁路 | **鉴权收口中台 / RBAC** | 工具注册表 + 分级白名单 |
| 4 | **异常恢复** | 工具失败重试 + 降级 + 补偿；熔断转人工 | 一次超时毁掉整个任务 | **重试 / 降级 / 补偿 / 熔断** | 四层恢复链 |
| 5 | **人工介入（HITL）** | 写操作前审批、低置信度转人工 | 不可逆动作被模型自主执行 | **审批流 / 双人复核 / 灰度发布** | 中断 + 检查点 + 恢复 |
| 6 | **评测观测** | 每步 trace 落日志；指标与成本护栏 | 改好了 A 场景、改坏了 B 场景你不知道 | **On-call / 监控 / 对账 / 双跑比对** | trace_id 全链路 + 评测集 |

> **承接一句话**（可作为面试里的自我定位）：
> "Agent 的可靠性不来自模型，来自 Harness —— 循环上限、状态外置、权限分级、失败补偿、人工卡点、评测观测。这六个机制我在企业级系统里都做过同构版本，AI 版的差异我清楚在哪。"

## 3. 机制一 · 任务执行循环（MainLoop）

### 3.1 循环的五个阶段

```
感知（用户输入 / 上一轮工具结果）
   │
   ▼
规划（下一步做什么 —— 由模型决定，或由规则决定）
   │
   ▼
行动（调用工具 / 检索 / 生成）
   │
   ▼
观察（拿到结果，判定是否可用）
   │
   ▼
判定（继续 / 终止 / 转人工）
   │
   └── 继续 ──► 回到感知
```

这就是 **ReAct 模式的工程化版**。注意最后那个"判定"节点 —— **它不是循环的一部分，它是循环的出口**，而且判定的依据**不是模型的自评**（见 §3.4）。

### 3.2 报文级时序

MainLoop 与模型之间的每一帧报文（请求 / 响应 / 工具结果回灌 / 并行调用）在 `ai/01-认知框架/Agent-Harness-LLM报文全链路拆解.md` §3 有完整展开。此处只强调 **MainLoop 侧必须记住的四条铁律**：

| # | 铁律 | 违反后果 |
|---|---|---|
| 1 | 必须先把带 `tool_calls` 的 assistant 消息**原样放回历史**，再跟工具结果 | 400 |
| 2 | **N 个工具调用必须回 N 条结果**，一个都不能少 | 400 |
| 3 | 工具结果必须**按 `tool_call_id` 关联**，不能按数组下标 | 并行/流式下结果串台 |
| 4 | **工具失败也要回一条结果**，写明错误，不要抛异常中断循环 | 模型失去自愈机会 |

> 第 4 条尤其重要：**Agent 出错不是"抛异常"，而是"返回了一段胡说八道"。** 所以错误也必须作为**正常结果**回灌，让模型自己决定换参数重试还是换路径。

### 3.3 循环状态机（判定清单形式）

MainLoop 主循环的判定顺序，**从上往下，先命中先执行**：

| 序 | 判定条件 | 动作 |
|---|---|---|
| 1 | 命中「终止型工具」调用 | 取参数作为最终结果，**结束循环**（不回灌） |
| 2 | 还有普通工具调用 | 执行 → 回灌 → 进入下一轮 |
| 3 | 无工具调用且内容非空 | **结束**，返回内容 |
| 4 | 无工具调用且内容为空 | **结束**，返回兜底话术 |
| 5 | 命中任一硬闸门 | **终止或转人工**（见 §3.4） |
| 6 | 其余情况 | 异常路径：告警 + 终止 |

> 第 1 条是"让模型显式声明收尾"的技巧 —— 给模型一个只用于收尾的工具，它调这个工具就等于宣布任务完成，Harness 不执行、不回灌，直接取参结束。好处是**能带结构化元数据（置信度、引用、是否需人工）且能被 schema 校验**。报文细节见报文文档 §4.3。

### 3.4 ★ 防失控三闸门 + 一条最容易被漏的

| # | 闸门 | 触发条件 | 动作 |
|---|---|---|---|
| 1 | **步数上限** | 循环步数 ≥ N | 终止，返回当前最优 + 标注"未收敛" |
| 2 | **预算上限** | 累计 token / 金额超阈值 | 终止 |
| 3 | **墙钟超时** | 单次运行耗时超阈值 | 终止 |
| 4 | **🆕 重复检测** | 连续 N 轮的 `(工具名, 参数)` 指纹完全相同 | **立即终止**，判定为死循环 |

> **第 4 条最容易被漏掉，也最贵。**
>
> 模型在原地打转 —— 同一个工具、同一套参数，反复调 —— 是生产环境最典型的失控形态。**光靠步数上限兜住的话，你会在烧掉几十万 token 之后才发现它在打转。** 正确做法是维护一个"调用指纹集合"，连续 N 轮指纹相同就立刻中止。

> 🔴 **终止判定的第一原则：终止原因必须透出。**
> "达到最大轮次，结果可能不完整"和"模型正常答完"，在 UI 上都是"转圈停了"，用户分不出来 —— 但这俩的可信度差着十万八千里。**静默结束是 Agent 产品体验的头号杀手。**

### 3.5 循环与"业务分档"的关系

在政策解读项目里，MainLoop 的**出口**不是"模型说完了"，而是**门控定档**（完整解读 / 仅原文 / 未找到依据）。这三档的输入全部来自确定性指标：

| 定档输入 | 来源 | 是否采信模型自评 |
|---|---|---|
| 引用核验结果 | 代码 | ❌ 不采信 |
| 召回最高分 | 检索组件 | ❌ |
| 是否检出"需裁决" | 规则 | ❌ |
| 是否越权 | 规则 | ❌ |

> **"Agent 停在哪里，不由模型说了算，由规则说了算。"** 这条在业务项目和自研 Harness 里是同一句话。

## 4. 机制二 · 状态管理

### 4.1 三条状态线，别混在一起管

| 状态线 | 内容 | 生命周期 | 存放 |
|---|---|---|---|
| **会话态** | 用户身份、权限画像、历史轮次 | 跨轮次、跨请求 | 外置存储 |
| **任务态** | 当前 run 的步数、已调工具、待办、检查点 | 单次 run | 外置存储（**必须**） |
| **上下文态** | 拼给模型的 messages | 单次模型调用 | 内存（可重建） |

**关键区分**：**上下文态是可以随时重建的**（从会话态 + 任务态 + 检索结果重新拼装），但**会话态和任务态不行**。所以：**可以丢的放内存，不能丢的放外置存储。**

### 4.2 状态外置：为什么不能放内存

| 放内存的后果 | 触发场景 |
|---|---|
| 重启即丢 | 部署、扩缩容、机器维护 |
| 无法水平扩容 | 请求必须回到同一实例 |
| 长任务断链 | 用户等 30 秒后刷新页面 |
| 审批挂起失败 | 人工审批等了几小时，进程早就重启过 |

> 🔴 **凡是把审批状态放在内存里的 Agent，上线第一天就会在某次发布重启后卡住一批单子。** 这不是"可能发生"，是"必然发生" —— 因为部署是必然会发生的。

### 4.3 检查点与恢复

对长耗时任务（尤其是需要人工审批的），必须把 run 状态**检查点化**：

| 字段 | 作用 |
|---|---|
| `checkpoint_id` | 检查点主键 |
| `trace_id` | 全链路关联 |
| `status` | running / suspended / done / failed |
| `turn` | 当前步数（防重复执行） |
| `pending_action` | 待执行的动作（工具名 + 参数） |
| `messages_snapshot_ref` | 上下文快照的存储引用（**不是内联**） |
| `resume_token` | 恢复凭据 |
| `interrupt_id` | 关联的待裁决项（如有） |

**恢复流程的判定清单：**

| 序 | 判定 | 动作 |
|---|---|---|
| 1 | `resume_token` 有效且未过期 | 继续；否则拒绝，需重新发起 |
| 2 | `turn` 与当前实际执行进度一致 | 继续；**不一致 → 拒绝**（防重复执行） |
| 3 | `pending_action` 是否已产生副作用 | 已产生 → 走对账流程；未产生 → 正常执行 |
| 4 | 待裁决项是否已裁决 | 已裁决 → 转成结果回灌；未裁决 → 保持挂起 |

> **第 2 条是复用检查点时最容易忽略的一步**：同一个检查点被恢复两次，就会执行两次工具。所以恢复时**必须比对 `turn`**，防止重复执行。

### 4.4 幂等：恢复能力的前提

**没有幂等，检查点恢复就是灾难而不是保障。**

| 设计点 | 做法 |
|---|---|
| 幂等键 | `trace_id + turn + 工具名` 作为唯一键 |
| 写操作 | 服务端按幂等键去重，重复请求返回首次结果 |
| 非幂等工具 | 执行前**先查状态**，确认上次是否已生效 |
| 重试 | 重试必须带同一个幂等键，**不能生成新键** |

判据很简单：**这个工具重跑一次，会不会产生第二次副作用？** 会，就必须有幂等键；有幂等键，检查点才敢恢复。

### 4.5 与 Saga 的同构关系

这是我个人项目里最直接的迁移经验：

| Saga 模式 | Harness 里的对应物 |
|---|---|
| 事务发起 | 用户请求 / 任务创建 |
| 正向步骤 | 循环的每一轮（工具调用） |
| 补偿动作 | 失败后的回滚 / 降级 / 人工接管 |
| 断点续跑 | 检查点恢复 |
| 最终一致性 | 对账兜底 |

> 我在 Agent Harness 里用 FastAPI 做 MainLoop 编排，**本质上也是多步骤状态机的一致性管理** —— 和 B2B 平台里 Saga 编排解决的是同一类问题：**多步流程的推进、超时、重试、补偿、最终一致。**

个人项目里最典型的实例是**微信公众号 6 节点流水线**（采集 → 清洗 → 生成 → 配图 → 排版 → 发布）：它就是一条**多步骤、可补偿的 Saga 流程**，任一节点失败要能重试并从中断处续跑。

## 5. 机制三 · 权限控制

### 5.1 铁律：鉴权跟着用户走，不跟着 Agent 走

> 🔴 **工具的鉴权不能跟着 Agent 走，必须跟着发起请求的用户身份走。**
>
> Agent 只是一个**执行通道**，它没有自己的人格化权限。这条是硬约束 —— 否则 AI 就成了系统里的一个**新权限旁路**。

推论（这三条在业务项目里同样适用）：

| # | 约束 |
|---|---|
| 1 | 身份**穿透传递**，校验永远在业务中台侧执行 |
| 2 | **不把数据过滤交给 Prompt** —— 提示词不是权限边界 |
| 3 | 模型不能自己声明身份（"我是管理员"这类一律无效） |

### 5.2 工具三级分类

| 级别 | 判定依据 | 处理 | 例子 |
|---|---|---|---|
| **只读** | `readOnlyHint: true` | 免审批直接执行 | 查行情、检索、读文件 |
| **写** | `readOnlyHint: false` | 记录 + 幂等 + 可回滚窗口 | 落库、更新状态、发消息 |
| **高危** | `destructiveHint: true` 或 `openWorldHint: true` | **必须人工确认** | 下单、资金划转、删除 |

> MCP 协议把这几个 hint 定义在工具描述里（`annotations`），就是这个用途：**工具的危险等级由工具的提供方声明，而不是由调用方推断。** 详见报文文档 §2.4。

### 5.3 AI 旁路的三个新风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **权限旁路** | Agent 用系统身份调工具，绕过了用户级权限 | 身份穿透；工具调用带用户身份 |
| **Prompt 越权取数** | 用户用自然语言诱导模型去查无权数据 | 权限在**工具层**收口，不在 Prompt 层 |
| **多轮权限残留** | 历史轮次有权限的内容留在上下文里 | 每轮重载权限；历史文档逐份重新鉴权 |

第三条是**最容易翻车**的一条：用户第 3 轮有权看某文件，第 5 轮权限被回收，但第 3 轮的内容还在对话历史里 —— 如果上下文直接拼接历史，第 5 轮就泄露了。

### 5.4 与闸门 A 的配合

Harness 的权限骨架负责**"能不能调这个工具"**；业务项目的闸门 A 负责**"能看到哪些数据"**。两层必须都做：

```
用户请求
   │
   ├─ Harness 层：这个用户能调这个工具吗？          ← 工具级
   │
   └─ 业务层（闸门 A）：这个用户能看到这些文档吗？   ← 数据级，进检索引擎 filter
```

> 只有工具级权限：用户能调检索工具，但检索结果里混进了无权文档。
> 只有数据级权限：用户不能看某类文档，但能调那个会改数据的工具。
> **两层都做，才算权限收口。**

## 6. 机制四 · 异常恢复

### 6.1 四层恢复链

```
工具调用
   │
   ├─ 第 1 层 · 重试      同参数带幂等键重试，指数退避，有次数上限
   │      └─ 仍失败 ↓
   ├─ 第 2 层 · 降级      换更弱但更可靠的路径（例：语义检索挂 → 仅关键词）
   │      └─ 仍不可用 ↓
   ├─ 第 3 层 · 补偿      回滚已产生的副作用（Saga 反向操作）
   │      └─ 无法补偿 ↓
   └─ 第 4 层 · 熔断转人工 停止自动处理，交人工接管
```

**每一层都必须有明确的触发条件。** 没有触发条件的降级，等于没有降级。

### 6.2 错误分层：两种错误，处理方式完全不同

| 层 | 表现 | 含义 | 处理 |
|---|---|---|---|
| **协议层错误** | 请求被拒 / 调用格式错 | **Harness 自己的 bug** | 修代码，重试无用 |
| **业务层错误** | 调用成功但结果是失败 | 参数合法但执行失败 | **作为正常结果回灌给模型**，让它换路 |

> 🔴 **把业务层错误当异常抛出，是最常见的错误实现。** 正确做法是把它转成一条普通的结果消息回灌 —— 模型看到"标的不存在"，多半会自己修正参数重试。**这才是 Agent 该有的自愈能力。**

### 6.3 失败矩阵

| 故障 | 表现 | 兜底动作 | 严禁 |
|---|---|---|---|
| 身份/权限获取失败 | 拉不到画像 | **拒绝服务** | 用默认宽松权限放行 |
| 检索服务超时 | 主通道无返回 | 降级到备通道 + 置信降档 | 返回上一次的缓存结果 |
| 重排服务不可用 | 无法精排 | 降级为粗排 + **强制"只给原始结果"模式** | 用粗排分数冒充精排分 |
| 生成模型超时 | 无输出 | 降级到非生成路径 | 让用户重试且不带提示 |
| 输出校验不通过 | 结构/引用不合规 | 重试 1 次 → 降级 | 放行不合规输出 |
| 上下文为空 | 无材料可给 | **直接拒答，不调用模型** | 空上下文调用模型 |
| 元数据缺失 | 无法判定 | 该数据源**直接不可用** + 告警 | 用默认值补齐 |

> **贯穿全表的一条原则：所有降级都朝"信息更少但更确定"的方向走，绝不朝"信息更多但更不确定"的方向走。**

## 7. 机制五 · 人工介入（HITL）

### 7.1 四个触发源，一个唯一安全插入点

**唯一安全插入点：模型响应之后、工具执行之前。**

| 为什么只能是这里 | |
|---|---|
| 模型输出已完整落盘 | 调用意图是完整 JSON，不存在流式半截 |
| **尚无任何副作用发生** | 工具还没执行 —— 没有下单、没有写库、没有发消息 |
| 状态自洽 | 消息历史干净，随时可存档走人 |
| 可安全持久化 | 是检查点最理想的切分位置 |

**换到别的位置插，代价立刻上来：**

| 插入位置 | 后果 |
|---|---|
| 工具执行**中途** | 可能已扣款但没记录，对账地狱 |
| 回灌**之后** | 要回滚模型上下文，等于重新构造一次对话 |
| 请求**之前** | 没有上下文可给审批人看，他不知道自己在批什么 |

**四个触发源：**

| 源 | 谁发起 | 典型场景 |
|---|---|---|
| **A. 模型主动** | 模型调用"转人工"工具 | 意图含糊、超出能力边界、无权决策 |
| **B. Harness 策略** | Harness 判定 | 高危工具、金额超阈值、连续失败、循环无进展 |
| **C. 工具服务** | 工具端中途要输入 | 执行前确认、缺必填参数 |
| **D. 用户主动** | 用户中断 / 纠偏 | 发现跑偏、想补充约束 |

> 四者的**下游处理必须收敛到同一个中断报文格式**，由同一套审批 UI 承接。否则你会维护四套互不兼容的审批逻辑。

**触发源 B 的判定依据表：**

| # | 判定条件 | 依据来源 |
|---|---|---|
| 1 | 工具不在白名单内 | 模型幻觉出的工具名 |
| 2 | `destructiveHint: true` | 工具注解 |
| 3 | `openWorldHint: true` 且为写操作 | 工具注解 |
| 4 | `idempotentHint: false` 且本次要重试 | 工具注解 |
| 5 | 金额 / 数量 / 影响面超阈值 | 解析并校验后的参数 |
| 6 | 置信度低于阈值 | 模型的置信度字段 |
| 7 | 连续 N 轮无进展 | 循环指纹 |
| 8 | 同一工具连续失败 3 次 | 错误计数 |

### 7.2 裁决回灌铁律

> 🔴 **无论用户怎么裁决，那个工具调用都必须对应一条结果消息。**

"用户拒绝了所以不执行" **不等于** "不用回消息"。直接跳过被拒绝的那次调用，下一轮请求立刻被拒 —— **这是人工介入功能上线后最常见的线上故障。**

| 裁决 | 回灌内容 | 关键提醒 |
|---|---|---|
| **通过** | 正常执行结果 | — |
| **改参后通过** | 按改后参数执行的结果 | **必须说明真实执行值** |
| **拒绝** | 不执行，但回一条"用户已拒绝" | **必须写"请勿重试"** |
| **超时** | 回一条"审批超时已取消" | 标注真实原因 |

**两个容易做错的细节：**

1. **改参后必须说明真实执行值。** 模型以为执行的是它给的原参数，如果你不告诉它真实值，它后续推理会建立在错误前提上（"我买了 300 股"）—— **这个 bug 不报错，只会一路错到底。**
2. **拒绝时必须明确写"请勿重试"。** 否则模型会把"被拒绝"理解成"参数不对"，换个参数再来一次，形成请求-拒绝死循环。

> 详细报文（四种裁决的回灌格式）见 `ai/01-认知框架/Agent-Harness-LLM报文全链路拆解.md` §5.6。

### 7.3 长审批必须做检查点，不能阻塞

| 方式 | 适用 | 代价 |
|---|---|---|
| 阻塞等待（进程持住循环） | 秒级审批 | 进程/连接被占，易超时，重启即丢 |
| **检查点 + 恢复** | 分钟级及以上 | 要能把整个 run 状态序列化并持久化 |

**判断标准很简单：审批等待时间会不会超过你的进程或连接超时。** 会，就必须做检查点。而"会不会超过"这个问题，在金融和政企场景里的答案几乎总是"会"。

## 8. 机制六 · 评测与可观测

### 8.1 trace 设计：一个 ID 串起全链路

| 记录项 | 位置 | 用途 |
|---|---|---|
| `trace_id` | 贯穿全链路 | 关联模型调用 / 工具调用 / 业务操作 |
| `turn` | 每轮循环 | 定位是在第几步出问题 |
| `tool_call_id` | 每次工具调用 | 关联调用与结果 |
| 每轮 token 用量 | 每次模型调用 | 成本归因 |
| 工具耗时 | 每次工具调用 | 定位慢在哪 |
| 终止原因 | 循环结束 | **区分"答完了"和"没查全"** |
| 命中的闸门 | 每次拦截 | 判断是闸门过严还是模型在硬答 |

> **"终止原因"这一项最容易被漏，但它是产品体验的关键。** 见 §3.4。

**归因判据（出问题时先看哪一步）：**

| 现象 | 大概率问题 |
|---|---|
| 模型选错工具 | 工具描述写得含糊 / 工具太多 |
| 同一工具反复调 | 无进展检测缺失 |
| 引用核验大量失败 | 上下文没给对 / Prompt 约束不够 |
| 闸门频繁拦截 | 阈值过严 或 模型在试探越权 |
| 成本异常升高 | 上下文膨胀 / 循环没收敛 |

### 8.2 三层评测

| 层 | 评什么 | 指标 | 怎么建 |
|---|---|---|---|
| **检索层** | 材料找对了吗 | Hit Rate、Recall@k、MRR | 标注"问题→应召回片段" |
| **生成层** | 答得对吗 | 准确率、忠实度、格式合规率 | 标注"问题→标准答案" |
| **端到端** | 用户满意吗 | 解决率、人工转接率、坏例率 | 线上埋点 + 人工抽检 |

**离线 vs 在线：**

- **离线**：固定评测集，每次改动前后各跑一遍 → 防止"改好了 A 场景、改坏了 B 场景"（**回归测试的 AI 版**）。
- **在线**：A/B 分流、用户反馈、**badcase 回流**（线上错例补进评测集，集子越用越准）。

> **方法论点：先建评估集，再谈优化。** 没有评估集，调参就是盲人摸象。

### 8.3 成本护栏

| 手段 | 说明 |
|---|---|
| 上下文预算 | 按预算表分配，超了主动裁剪 |
| 输出上限 | 设 `max_tokens`，防失控输出 |
| 缓存 | 相同问题命中缓存 |
| **小模型路由** | 简单问题走便宜模型（分类任务不需要大模型） |
| 直击库 | 命中即返回，0 生成 token |
| 循环预算 | 单次运行 token / 金额上限 |
| 分租户计量 | 按部门/租户统计与限额告警 |

> 最后一条正好接业务中台的计量能力 —— 这是"AI 能力接入企业系统"里最容易被忽略、但企业最关心的一环。

## 9. 部署形态与集成

### 9.1 个人储备形态

```
┌──────────────────────────────────────────────────┐
│  客户端层                                         │
│   PyQt6（桌面端）  ·  Vue3（Web 端）               │
└───────────────────────┬──────────────────────────┘
                        │  SSE / WebSocket（流式输出）
┌───────────────────────▼──────────────────────────┐
│  Harness 服务层（FastAPI）                        │
│   ├─ MainLoop 编排      循环推进 / 终止判定        │
│   ├─ 状态管理           外置存储 + 检查点          │
│   ├─ 工具注册表         分级白名单 + 参数校验      │
│   ├─ 权限骨架           身份穿透 + 分级授权        │
│   ├─ 恢复链             重试 / 降级 / 补偿 / 熔断  │
│   ├─ 人工卡点           中断报文 + 裁决回灌        │
│   └─ 观测                trace_id + 指标 + 护栏    │
└───────────────────────┬──────────────────────────┘
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   模型 API        本地工具         外部服务
  (LLM 推理)     (函数/HTTP)    (MCP Server)
```

**典型实例：微信公众号 6 节点流水线** —— 采集 → 清洗 → 生成 → 配图 → 排版 → 发布。这是一条典型的多步骤、可补偿流程，正好把六机制全部用上：

| 节点 | 用到的机制 |
|---|---|
| 采集 | 重试 + 幂等（同一篇不重复采） |
| 清洗 | 降级（清洗失败用原文兜底） |
| 生成 | 循环（生成→校验→重生成）+ 预算护栏 |
| 配图 | 超时 + 降级（配图失败不阻断发布） |
| 排版 | 检查点（排版完成后可暂停待审） |
| 发布 | **HITL（发布前人工确认）+ 幂等（防重复发布）** |

### 9.2 Dify vs 自研 Harness：什么时候用哪个

这是我实际做过的**选型判断**，也是这个项目里我参与最深的一块。

| 维度 | 用 Dify 承载 | 自研 Harness |
|---|---|---|
| 循环/状态/日志 | 平台已实现，开箱可用 | 自己实现，可控性最高 |
| **元数据过滤** | ⚠️ **单节点挂多知识库时不可用** | 无限制 |
| **阈值精度控制** | ⚠️ **TopK / Score 阈值只在 Rerank 阶段生效** | 无限制 |
| 权限收口 | 需与中台对接 | 可直接内嵌 |
| 复杂业务逻辑 | 不适宜（应只做路由/拼装/调用/格式化） | 适宜 |
| 交付速度 | 快 | 慢 |
| 运维成本 | 平台托管 | 自负 |

**选型结论（可直接说的三条硬约束）：**

1. **权限校验永远在中台侧，不把数据过滤交给 Prompt**
2. **编排平台不直连业务数据库** —— 只通过中台暴露的受控工具/API 访问
3. **工作流里不写复杂业务逻辑**，只做路由 / 拼装 / 调用 / 格式化

> 这三条就是"**确定性业务逻辑与 AI 能力分层**"的落地版本：跟钱、合规、状态强相关的走确定性逻辑，AI 只负责非结构化理解、检索汇总、草稿建议。

**平台特性陷阱（必须逐条核对，不能假设平台替你兜住了）：**

| 陷阱 | 后果 | 对策 |
|---|---|---|
| 元数据过滤在"单节点挂多知识库"时不可用 | 权限过滤静默失效 | 按密级/地域**拆成多个知识库**，节点级各管一个 |
| TopK / Score 阈值只在 Rerank 阶段生效 | 不启 Rerank 时阈值形同虚设 | 该开的 Rerank 一个都不能省 |
| 平台内部字段不易导出分析 | 治理数据锁死在平台里 | 主数据放外部（如 CSV/DB），平台只放成品 |

> 最后一条是通用原则：**别把治理字段放在平台内部。** 外部主数据比平台内字段更可控、更容易导出分析、更容易进 Git。

### 9.3 集成层七件套

AI 接入企业系统的**集成层**，全是传统后端的活：

| 问题 | 本质 | 做法 |
|---|---|---|
| **流式输出** | 逐 token 生成，要边生成边推 | SSE / WebSocket，**转发不改语义**，断线重连要幂等 |
| **鉴权收口** | AI 网关不该自带权限语义 | 身份穿透传递，**校验永远在中台侧执行** |
| **幂等** | 用户可能重发、网络可能重试 | 请求 ID 幂等键，写操作幂等 |
| **异步长任务** | 多步执行可能几十秒 | 转后台任务 + 事件回调/轮询，超时可控 |
| **超时/重试/降级** | 模型服务会超时、会限流 | 超时设上限、重试带退避、降级到缓存或转人工 |
| **多租户隔离** | 不同客户数据不能串 | 数据源隔离 + 上下文隔离，**防 Prompt 越权取数** |
| **审计留痕** | 合规要求可追溯 | 业务日志 + AI 调用日志用 **trace_id 关联** |

## 10. 落地路线

| 期 | 范围 | 交付标准 |
|---|---|---|
| **一期 · 循环 + 观测** | MainLoop + 报文层 + trace | 能跑通一轮"提问→调工具→回灌→回答"，且每一步都有日志 |
| **二期 · 状态外置 + 恢复** | 检查点 + 幂等 + 恢复 | **能杀掉进程再恢复**，且不重复执行工具 |
| **三期 · 权限骨架 + 恢复链** | 工具分级 + 重试/降级/补偿/熔断 | 高危工具走审批；主通道挂了能自动降级 |
| **四期 · HITL + 评测** | 中断报文 + 裁决回灌 + 评测集 | 人工审批全链路可持久化；上线前有基线评测集 |

> **一期的验收标准里，"每一步都有日志"和"能跑通"同等重要。** 一个没有 trace 的 Harness，出问题时你连"是模型选错工具还是工具挂了"都分不出来 —— 而没有可观测性的系统，等于没有运维能力。

## 11. 面试速答

**Q1：Harness 是什么？为什么需要它？**

Harness 是套在模型外面的工程骨架。它不产生业务语义，它产生**约束**。原因很直接：模型是**概率性的、无状态的、按 token 收费的、会说谎的**，而且它**不能承担外部动作的后果**。这五个源头分别对应六个机制 —— 执行循环、状态管理、权限控制、异常恢复、人工介入、评测观测。一句话：**Agent 的可靠性不来自模型，来自 Harness。**

**Q2：怎么防 Agent 死循环？**

四道闸门：步数上限、预算上限（token/金额）、墙钟超时，还有一道最容易被漏的 —— **重复检测**：连续 N 轮 `(工具名, 参数)` 指纹完全相同就立即中止。只靠步数上限的话，你会在烧掉几十万 token 之后才发现它在原地打转。而且**终止原因必须透出** —— "达到最大轮次"和"正常答完"在 UI 上都是转圈停了，但可信度差着十万八千里。

**Q3：Agent 的状态怎么管？**

分三条线：会话态（跨请求，外置存储）、任务态（单次 run，**必须**外置存储）、上下文态（内存，可随时重建）。关键区分是**上下文态可以重建，会话态和任务态不行**。所以能丢的放内存，不能丢的放外置。长任务要做检查点 —— 而且恢复时必须比对步数，防止同一个检查点被恢复两次导致工具重复执行。**没有幂等，检查点恢复就是灾难而不是保障。**

**Q4：你的 Harness 权限怎么设计？**

一条铁律：**鉴权跟着用户身份走，不跟着 Agent 走。** Agent 只是执行通道，它没有自己的人格化权限 —— 否则 AI 就成了系统里的一个新权限旁路。工具分三级：只读免审批、写操作记录加幂等、高危必须人工确认。另外权限收口要分两层：Harness 管"能不能调这个工具"，业务层管"能看到哪些数据"，两层都得做。

**Q5：工具调用失败了怎么办？**

先分性质。**协议层错误**是 Harness 自己的 bug，修代码，重试无用；**业务层错误**是参数合法但执行失败，这个要**当作正常结果回灌给模型**。这里最常见的错误实现是把业务错误当异常抛出来 —— 那模型就失去了自愈机会。正确做法是回一条"标的不存在"，模型多半会自己修正参数重试。整体上恢复是四层：重试 → 降级 → 补偿 → 熔断转人工。

**Q6：什么时候该让人介入？**

唯一安全的插入点是**模型响应之后、工具执行之前**。此刻模型输出已完整落盘、尚无任何副作用、状态可以安全持久化。换到工具执行中途插，可能已经扣款但没记录，对账地狱。四个触发源：模型主动请求、Harness 策略命中（高危工具、金额超阈值、连续失败）、工具端要求输入、用户主动中断。有一条铁律：**无论用户怎么裁决，那个工具调用都必须回一条结果消息 —— 拒绝也要回。** 直接跳过被拒的调用，下一轮直接报错。而且拒绝时要写明"请勿重试"，否则模型会换个参数反复试。

**Q7：你用过 Dify，为什么不全都用自研？**

是权衡。Dify 把循环、状态、日志这些骨架开箱就给了，交付快。但它有两个已知陷阱必须逐条核对：**元数据过滤在单节点挂多个知识库时不可用**，**TopK 和 Score 阈值只在 Rerank 阶段生效**。所以我的做法是分层 —— 权限校验永远放在业务中台侧、不把数据过滤交给 Prompt；编排平台不直连业务库，只通过中台暴露的受控工具访问；工作流里只做路由、拼装、调用、格式化，不写复杂业务逻辑。**这就是"确定性业务逻辑与 AI 能力分层"。**

**Q8：怎么保证 Harness 改动的效果是正的？**

评测先行。三层评测：检索层看材料找对没（Hit Rate、Recall@k、MRR），生成层看答得对不对（准确率、忠实度、格式合规率），端到端看用户满意不满意。关键是**离线评测集** —— 每次改动前后各跑一遍，防止"改好了 A 场景、改坏了 B 场景"。再加上线上 badcase 回流，评测集越用越准。**没有评测集，调参就是盲人摸象。**
