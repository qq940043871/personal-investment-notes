## 0. 一句话结论

**每一次召回测试里"答对了"的那部分样本，是这个系统最值钱的资产 —— 别让它蒸发在聊天记录里。**

直接命中方案的核心：**把验证过的问答沉淀成一个独立的 Q&A 知识库，查询进来先查它，命中就不再走昂贵的完整 RAG 链路。**

## 1. 三档"命中"，先搞清楚你要哪一档

这是最大的认知坑。所有人都以为"直接命中"是一件事，其实有三档：

| 档位 | 机制 | 是否过 LLM | token | 一致性 | 适用 |
|---|---|---|---|---|---|
| **L0 · 标注回复** | Dify Annotation，命中即截断对话 | 否 | **0** | 逐字固定 | 高频 Top 20、话术必须统一的场景 |
| **L1 · 强命中** | Q&A 库高阈值检索 → 条件分支 → 直接输出 `answer` | 否 | ≈ 0（仅 embedding） | 逐字固定 | 政策条款、术语释义、固定流程 |
| **L2 · 弱命中** | Q&A 库命中 → 仍交给 LLM 润色生成 | 是 | 正常消耗 | 有漂移 | 需要结合上下文改写、个性化的场景 |

**本目录默认交付 L1（强命中）**，理由：

- L0 的 Annotation 很好，但它绑在**单个应用**上，跨应用复用不了，也没有版本管理，导出导入能力弱 → 适合做"高频兜底"，不适合做"知识资产"。
- L1 的 Q&A 库是**可被多个应用共享的知识资产**，能用 Knowledge API 批量管、能接元数据、能随 DSL 进 Git。
- L2 丧失了"直接命中"的意义（又慢又可能漂移），只在答案必须二次加工时才用。

**推荐形态：L0 + L1 双层。** 真正高频且必须逐字统一的进 Annotation；其余已验证样本进 Q&A 库走 L1。

## 2. 目录结构与文件职责

```
rag-cases/
├── README.md                 ← 本文件：方案、SOP、治理规则
├── registry.csv              ← 主数据（唯一事实来源），含全部治理字段
├── import-to-dify.csv        ← 由 registry 导出的导入文件（question,answer 两列）
└── candidates.example.jsonl  ← 候选样本格式示例（采集投递格式）
```

**铁律：`registry.csv` 是唯一事实来源，`import-to-dify.csv` 永远是它的导出副本，禁止手改。**

### registry.csv 字段

| 字段 | 说明 | 例 |
|---|---|---|
| `id` | 稳定主键，永不复用 | `QA001` |
| `question` | 用户真实问法（保留口语、错别字、缩写） | `topk调了没用` |
| `answer` | 已验证的成品答案。**写成可直接输出的形态** | 见下 §4 |
| `category` | 类目，用于建库拆分与统计分析 | `检索调优` |
| `source_doc` | 溯源：答案依据的原文位置 | `ai/02-平台工程/Dify-RAG关键点详解.md §3.2` |
| `verified_by` | 谁验证的 | `hasWhere` |
| `verified_at` | 验证日期 | `2026-10-10` |
| `hits` | 被问到的累计次数（决定是否值得入 L0） | `7` |
| `status` | `active` / `draft` / `retired` | `active` |
| `review_on` | 下次复核日期（答案有效期） | `2027-04-10` |

### import-to-dify.csv 字段

只有两列 —— `question,answer`。这是 Dify Q&A 分段模式导入能识别的最小形态，多余的列大概率被忽略或导致导入失败，所以分层存放。

## 3. 有了 Q&A 库之后，工作流怎么改

### 3.1 节点蓝图（Chatflow / Workflow 通用）

```
Start (sys.query)
   │
   ▼
① Knowledge Retrieval ── L1 直击库（Q&A 模式）
   │   top_k = 1          ← 只要最像的那一条
   │   score_threshold = 0.85   ← 高阈值，宁可不命中也不错命中
   │   rerank = 开
   │
   ▼
② IF/ELSE：result 非空？
   │
   ├─ 是 ─→ ③ Template 节点：输出 {{#1712345678901.result[0].content#}}
   │          │
   │          └─ 直接 End / Answer（不经 LLM，零生成成本）
   │
   └─ 否 ─→ ④ Knowledge Retrieval ── L2 原始文档库（混合检索 + Rerank）
              │
              ▼
           ⑤ LLM 节点生成 + 引用溯源
              │
              └─ ⑥ 记录未命中样本 → 进 §5 的候选池
```

### 3.2 三个必须配对的细节

1. **① 必须开 Rerank。** 前面文档说过：**TopK 和 Score 阈值只在 Rerank 阶段生效**。不开 Rerank，你设的 0.85 阈值等于摆设 —— 然后你会得到一个"什么都命中"的直击库，准确率惨不忍睹。
2. **阈值宁高勿低。** `0.85` 是起手值。错命中的代价（用户拿到一个答非所问的成品答案）远高于漏命中（退回常规 RAG，多花几毛钱）。
3. **⑥ 是闭环的入口。** 未命中样本就是下一批要沉淀的内容，不记录就永远是"越用越笨"。

### 3.3 元数据粒度警告 ⚠️

**Dify 的元数据是文档级的，不是分段级的。** 所以想在 Dify 侧按 `category` 做元数据过滤，前提是 Q&A 导入时**一行 = 一个文档**。

务实做法（两条路，选一）：
- **按 category 拆成多个知识库**（每个类目一个库）—— 天然支持路由，也能绕开"节点挂多库时元数据过滤不可用"的已知限制。
- **别依赖 Dify 元数据做细粒度治理**，把 `category` / `hits` / `review_on` 全部放在 `registry.csv` 里管，Dify 侧只放成品。推荐这条 —— 外部主数据比平台内部字段更可控、更容易导出分析。

## 4. 什么样的答案配进库（写作规范）

直击库里的 `answer` 是**会被直接原样输出给用户看的**，不是"给 LLM 看的上下文"。三条写法：

1. **自足**：不依赖上下文变量，不出现"如上所述""见前文"。用户可能是从任何入口撞进来的。
2. **可操作**：给出判断依据 + 具体动作 + 参数值。反例："可以调整相关设置"；正例："score_threshold 设 0.85，且必须启用 Rerank 才生效"。
3. **带边界**：说明不适用情形。反例会让人在错误场景照做。

反例（不能入库的写法）：
> 这个可能需要根据具体场景来看，建议调整分块策略。

正例（可以入库的写法）：
> 事实型问答 300–500 token、重叠 10–15%；摘要综述型 500–800 token、重叠 15–20%；父子模式父约 1000 / 子 200–300。以上为起手值，最终以知识库 UI 的召回测试结果为准，不要凭手感调。

## 5. 采集闭环 SOP

```
① 召回测试 / 线上会话
      │
      ▼
② 打标：命中(output=✓)、赞踩、人工修正后的答案
      │
      ▼
③ 定量筛选（满足任一）：
   · 同一语义被问 ≥ 3 次            → 说明是真需求
   · 人工修正过答案                   → 说明答案珍贵
   · 曾答错且已定位到根因             → 说明是坑点
      │
      ▼
④ 人工审核 → 按 §4 改写为成品答案 → status=draft
      │
      ▼
⑤ 复核通过 → status=active → 由 registry 重新导出导入文件 → 导入 Dify 重索引
      │
      ▼
⑥ 到期：
   · hits ≥ 20 且话术固定     → 晋升 L0（Annotation）
   · 源文档变更 / review_on 到期 → status=retired，重新验证或删除
```

**关键点：③ 的定量门槛不能省。** 凭感觉收集的样本会退化成"看起来很全其实没人问"的摆设 —— 那种库维护成本极高，命中率极低，几个月后必然烂尾。

## 6. 治理：怎么让它不腐化

| 风险 | 症状 | 防线 |
|---|---|---|
| 源文档更新后答案过期 | 答案与原文矛盾 | `source_doc` 强制填写 + `review_on` 到期强制退回 `draft` |
| 重复条目互相打架 | 相似问题返回不同答案 | 入库前字面判重（字符 bigram Jaccard，阈值 0.75）＋ 语义判重（调 Dify 检索接口，阈值 0.85） |
| 低价值占位 | 库越来越大，命中率越来越低 | 每次 review 淘汰 `hits` 长期为 0 的条目 |
| 脏问法污染 | 把错别字当新条目 | 归一化去重；保留口语但要归并到同一 canonical 问法 |
| Dify 侧手工改动漂移 | 平台里被改了，主数据不知道 | 禁止在 Dify UI 里改 Q&A 库内容，一律改 registry 后重新导入 |

## 7. 维护动作清单

库的日常维护是六个动作，全部只改 `registry.csv`，导出文件永远重新生成：

| 动作 | 做什么 | 时机 |
|---|---|---|
| 自检 | 查重复、必填字段、status 合法性、是否到期 | 每次改动后 |
| 采集 | 追加候选样本（jsonl / json / csv，至少含 question 与 answer） | 定期 |
| 语义判重 | 入库时做 embedding 判重（阈值 0.85） | 采集时 |
| 计数 | 按会话日志累加 hits | 每日 |
| 晋升 | 达到门槛且已溯源的 draft 自动升为 active | 每周 |
| 失效 | 把某条改为 retired | review 到期 |

> 这六个动作应当**全部脚本化并做成例行任务** —— 靠人记得做的库，几个月后必然腐化。

### 7.1 语义判重的两种手段

字面判重用的是**字符 bigram 的 Jaccard 系数**，语序无关 —— 「为什么 TopK 调了没反应」和「TopK 调了为什么没反应」能判出来（实测 0.81，阈值 0.75）。

但它抓不住**语义相同却一个字都不像**的问法（例如「怎么防模型瞎编」与「检索为空怎么办」只有 0.25）。这类必须靠 embedding，最直接的办法是**让知识库自己判重**：

需要准备三项配置：**API 地址**、**Dataset 级 API Key**、**直击库 ID**；语义阈值默认 0.85。

未配置这三项时，语义判重应安静跳过，不影响字面判重的结果。

> 阈值 0.75 不是拍脑袋定的：库内所有不相关条目两两最高分只有 0.105，而真实重复写法普遍在 0.8 以上。换了自己的数据后建议重跑一次标定，别直接沿用。

建议把自检做成**导出前的强制关卡**：校验不通过就不生成导入文件，从源头卡住脏数据。

## 8. 验收指标

直接命中方案上线后盯这四个数：

| 指标 | 目标 | 说明 |
|---|---|---|
| **直击命中率** | 15–35% | 低于 10% 说明样本选错了（收集的不是真高频） |
| **直击准确率** | ≥ 98% | 低于 95% 立刻抬高 `score_threshold`，错命中的代价太大 |
| **平均延迟下降** | ≥ 40% | 未命中的部分不该变慢；如果整体变慢说明多查了一次库却没省 LLM |
| **月度淘汰率** | 5–10% | 长期为 0 说明没人维护，库正在腐化 |

**第三个指标最容易露馅**：如果加了直击库、延迟却几乎没降，说明命中率太低而每次查询都要多付一次 L1 检索的开销 —— 这时要么扩大样本覆盖，要么把 L1 换成零开销的 Annotation。
