三

★ 有三处对不上 —— 这才是 Harness 真正不可替代的部分

只记住「一一对应」，你就会在技术评审里说错话

前 80% 可迁移 · 后 20% 是全新的

① 核验（防说谎）

传统工程的组件是确定性的：函数返回什么就是什么，接口不会编造字段。而模型会自信地编造工具名、参数、引用来源。
→ 必须新增输出核验：引用核验 · schema 校验 · 事实一致性检查。项目对应 = 强制逐字引用 + 引用核验。

② 语义级幂等（防绕圈）

传统工程幂等靠主键：同一个 request_id 重放，唯一约束就挡住了。
但模型「重试」时会把 {"amount":300} 顺手改写成 {"amount":300,"note":"确认"} —— 参数变了、意图没变，主键拦不住 → 必须按「工具 + 业务键 + 时间窗」判重。

③ 评测（因为失去了断言）

传统工程：assert f(3) == 6，输入确定、输出确定。
Agent：同输入两次输出不同，没有唯一正确答案，只有可接受分布 → 断言换成评测集 + 评分器 + 双跑比对 + 人工抽检。这是 Agent 工程更难的物理原因。

修正版一句话

Harness 之于 Agent ≈ 工程化之于能跑的代码，但多出三样传统工程里没有的东西：核验（防说谎）· 语义级幂等（防绕圈）· 评测（因为失去了断言）。　前 80% 你可以用传统工程的经验直接迁移 —— 这省下大量试错；后 20% 是全新的 —— 这决定了你会不会在评审时说错话。
