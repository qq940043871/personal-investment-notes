## 0. 一页总览

| # | 故障类型 | 一句话特征 | 第一步动作 | 判定后主要出口 |
|:--:|---|---|---|---|
| 1 | JVM 内存溢出（OOM） | 日志出现 `OutOfMemoryError`，或老年代涨到 FGC 不回落 | 先分清 OOM 关键字 | 堆 → dump；元空间 → 动态类；堆外 → DirectByteBuffer；线程 → 转 4 |
| 2 | CPU 飙高 | 进程 `%CPU` 长期 80%+，Load 接近或超过核数 | `top -c` 定进程 → `top -Hp` 定线程 | 栈顶是 GC → 转 3；是业务 → 死循环/热点 |
| 3 | 频繁 Full GC / 停顿抖动 | FGC 持续增长，接口周期性卡顿 | `jstat -gcutil` 看 O 与 FGC | 泄漏 → 转 1；配置/晋升/大对象 → 本页调参 |
| 4 | 线程问题（死锁 / 池耗尽） | 线程数暴涨、大量 BLOCKED / WAITING、接口 hang | 间隔 5 秒抓两份 `jstack` | 死锁 → 锁；池耗尽 → 查外呼超时；线程失控 → 查 new Thread |
| 5 | 接口慢 / 超时 | 单接口 P99 飙升，调用方大量 read timeout | `curl -w` 分解耗时 | 等 DB → 转 6；等下游 → 补超时；GC → 转 3；池满 → 转 4 |
| 6 | 数据库问题（慢查询 / 连接池 / 锁） | 获取连接超时、大量线程卡 `socketRead`、DB CPU 高 | 应用侧看连接池 active/wait | 慢 SQL → `EXPLAIN`；泄漏 → 查 finally；锁 → 查 `pg_locks` |
| 7 | 日志风暴 / 磁盘满 | `df` 100%、日志每分钟 GB 级、同一异常刷屏 | `df -h` + `df -i` 定挂载点 | 异常风暴 → 降级限频；句柄未释放 → `lsof` |
| 8 | 网络问题（CLOSE_WAIT / 连接堆积） | `CLOSE_WAIT` 数万不降、偶发超时 | `ss -s` 看状态分布 | 本端没 close → 查代码/连接池；短连接 → 连接池化 |
| 9 | 服务假死（进程在但不干活） | 端口在听，请求全超时，健康检查 DOWN | 本机直连 `/health` 绕网关 | GC 死循环 → 转 1；线程全卡 → 转 4；锁死 → 转 4 |
| 10 | 应急响应（先恢复，再定位） | 大面积不可用，需要立即决策 | 1 分钟评估影响面 | 止血 → 保现场 → 观察 → 工单 → 复盘 |

### 五条铁律（十类场景通用）

1. **先止损，再定位**：回滚最近变更（发布 / 配置 / DDL / 网络）优先；30 分钟定不了位就升级。
2. **先保现场，再重启**：两份 `jstack` + heap dump + `jstat` 采样 + 日志尾部 + `top`，落到 `/tmp` 并拷出。直接重启 = 根因永远未知。
3. **先定性质，再定根因**：崩溃（有 `hs_err` / OOM 栈）还是被杀（SIGKILL / 137）？错误率涨（故障）还是只 RT 涨（慢而不报错）？方向不同，工具不同。
4. **一条证据链解释全部现象**：包括"为什么别的机器没事"。解释不了，就是还没到底。
5. **修复后固化三件套**：补监控（盲区）、补告警（阈值 + 分级）、补压测用例（回归）。能进 checklist 的不靠记忆。

## 1. JVM 内存溢出（OOM）

> 深入命令与 MAT 操作见 `java-architect-troubleshooting-handbook.md` 第 2 章；进程被杀（137）见 `10-下载PDF致JVM进程消失-排查实录.md`。

### 1.1 现象

- 日志出现 `OutOfMemoryError: Java heap space`
- 老年代占用持续上涨、Full GC 后不回落
- 响应越来越慢直到无响应，进程被杀
- `Metaspace` / `Direct buffer memory` 相关 OOM

### 1.2 先分清 OOM 类型（决定后续全部动作）

| OOM 关键字 | 含义 | 主查方向 |
|---|---|---|
| `Java heap space` | 堆内存不足 | 大结果集 / 无界集合 / 缓存无上限 / 队列积压 |
| `GC overhead limit exceeded` | 堆快满且 GC 低效（堆溢出的变体） | 同上，先看 GC 是否已陷入空转 |
| `Metaspace`（JDK8+） | 元空间耗尽 | 动态类生成：CGLIB / 反射 / 热部署；JDK7 对应 `PermGen space`，看 `jmap -permstat` |
| `Direct buffer memory` | 堆外直接内存耗尽 | NIO / `DirectByteBuffer` / Netty；查 `-XX:MaxDirectMemorySize` |
| `unable to create new native thread` | 线程数 / 栈空间耗尽 | 线程失控，转「4 线程问题」；同时看 `ulimit -u`、`nproc` |
| `Requested array size exceeds VM limit` | 单次分配超大数组 | 定位该次分配的业务代码（全量查询 / 大文件读入） |

### 1.3 六步作业单

| 步 | 动作 | 命令 / 观察 | 判读与分流 |
|:--:|---|---|---|
| ① | 先分清 OOM 类型，别急着抓 dump | 日志搜 `OutOfMemoryError`，看后面跟的关键字 | 按 1.2 表定方向；不同关键字方向完全不同 |
| ② | 保现场：抓堆转储 | `jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>` | dump 会 STW（大堆几十秒），有条件先切流/摘流量；若已配 `-XX:+HeapDumpOnOutOfMemoryError`，直接找 `.hprof` |
| ③ | 快速看堆里堆的是什么 | `jmap -histo:live <pid> \| head -30` | `char[]` / `byte[]` 靠前 → 大字符串、大结果集；`HashMap$Node` 靠前 → 无界集合；业务实体类靠前 → 大结果集 |
| ④ | 观察回收行为 | `jstat -gcutil <pid> 2000 30` | `O` 列 100% 且 FGC 持续增长、FGC 后不回落 → 泄漏或堆过小；偶发 FGC 后回落 → 大对象 / 流量尖峰 |
| ⑤ | 分析 dump 定位持有链 | MAT / VisualVM；**>1GB 用流式工具**（见下） | 看类直方图 → 最大对象支配树 → `Path to GC Roots`（排除 weak/soft）；`char[]` 内容取证：里面是 SQL 结果字段或某业务字段，基本锁定来源 |
| ⑥ | 对照根因改代码并验证 | 修完回第 ④ 步观察 | 老年代基线应稳定、FGC 不再增长；否则回到 ⑤ 继续找持有链 |

**MAT 四步**：打开 dump → Leak Suspects → Dominator Tree 找最大占用 → 右键 `Path to GC Roots`（exclude weak/soft）→ "谁在持有"就是泄漏点。

**大 dump（>1GB）**：MAT 需要接近等量的内存，分析 OOM 的工具自己 OOM 是常态。用本机 `jvm-triage` skill 的零依赖流式工具：`HprofHistogram`（类直方图 + 全量 CSV）→ `HprofArrays`（基本类型数组长度指纹 + `char[]` 关键词取证）→ `scan_bytecode.py`（按数组长度回代码找分配点）。分析顺序固定：**直方图 → 可疑类与数组 → 长度分布 → 关键词 → 字节码反查 → jstack 交叉验证**。

**口径提醒**：活进程手工定位泄漏用 `:live`（会先触发一次 Full GC，只看存活对象）；OOM 自动生成的 dump，以及事故取证时的 `jmap -histo`（不加 `:live`），包含不可达对象——历史峰值也是线索。按目标选口径，别混用。

### 1.4 常见根因

- 查询全量拉取：无分页、无 limit 的大结果集
- 无界集合：`static Map/List` 持续 add 无清理
- 缓存无上限：本地缓存未设容量与过期
- 异步积压：MQ 消费慢、线程池队列无界
- 资源未关闭：流、连接、Channel 泄漏
- 元空间泄漏：动态代理类反复生成（CGLIB / 反射 / 热部署）

### 1.5 关联

- 进程**没有日志就消失**、Exit Code 137 → 不是 OOM 崩溃，是 cgroup OOM Killer 杀的，转 `10-下载PDF致JVM进程消失-排查实录.md`（`limits.memory = Xmx + 堆外预算`）。
- 面试口径的数字与四个实录仍以 `00-面试计划/07-JVM与线上排查.md` 为准，本件不新增数字。

## 2. CPU 飙高

> 详见 handbook 第 1 章；速查卡见 `java-troubleshooting-quickcards.md` 卡片 1。

### 2.1 现象

- `top` 里 Java 进程 `%CPU` 长期 80% 以上
- `load average` 接近或超过核数
- 接口变慢但内存正常
- 单核打满（`top` 按 `1` 看各核）

### 2.2 六步作业单

| 步 | 动作 | 命令 / 观察 | 判读与分流 |
|:--:|---|---|---|
| ① | 找最耗 CPU 的进程 | `top -c`（按大写 `P` 以 CPU 排序） | 记下 Java 进程 PID；多个进程同时高 → 疑似宿主机资源不足或互踩 |
| ② | 找进程内最耗 CPU 的线程 | `top -Hp <pid>` | 记下 `ThreadId`，可能不止一个 |
| ③ | 线程号转十六进制 | `printf '%x\n' <tid>` | `jstack` 里的 `nid` 是十六进制 |
| ④ | 抓栈定位线程在干什么 | `jstack <pid> \| grep -A 30 "nid=0x<hex>"` | 栈顶是 `GC task thread` / `VM Thread` → 转「3 频繁 Full GC」；栈顶是业务代码 → 继续 ⑤ |
| ⑤ | 连抓 2–3 次对比 | `jstack <pid> > /tmp/s1.txt; sleep 5; jstack <pid> > /tmp/s2.txt` | 栈一直不变 → 热点在固定代码（死循环 / 正则回溯）；栈快速变化 → 大量小任务并发（序列化 / 加解密 / 字符串处理）；再用 `jstat -gcutil` 确认不是 GC 在烧 CPU |
| ⑥ | 对照根因处置 | 见 2.4；用 `vmstat 1 5` 看 `cs` 列 | `cs` 极高 → 线程数远超核数，上下文切换开销；`wa` 高 → 先查 IO |

### 2.3 栈顶特征对照

| 栈顶特征 | 判断 |
|---|---|
| `Pattern$Curly.match` 等正则内部 | 正则灾难性回溯（嵌套量词 + 长文本） |
| `MessageDigest` / `Base64` | 大文件加解密 |
| jackson 反序列化 | 超大 JSON |
| `GC task thread` / `VM Thread` | 是 GC 引起 → 转 3 |
| 业务方法且栈不变 | 死循环 / 全表遍历 / 边界条件空转 |

### 2.4 常见根因

- 死循环或边界条件导致的空转
- 正则表达式灾难性回溯
- 频繁 GC：GC 线程占满 CPU
- 大报文序列化 / 反序列化热点
- 线程数过多导致频繁上下文切换

**阈值**：Load ≈ 核数 = 满负荷；Load ≫ 核数且 `wa` 高 → 先查 IO（`iostat -x 1`、`iotop -oP`）。

## 3. 频繁 Full GC / 停顿抖动

> 详见 handbook 第 3 章；速查卡见卡片 3。

### 3.1 现象

- GC 日志频繁出现 `Full GC`
- `jstat` 里 `FGC` 列持续增长
- 接口每隔几分钟抖一次
- 老年代锯齿状快速升降

### 3.2 六步作业单

| 步 | 动作 | 命令 / 观察 | 判读与分流 |
|:--:|---|---|---|
| ① | 确认 FGC 频率与形态 | `jstat -gcutil <pid> 1000 60` | 看 `O`（老年代）、`FGC`（次数）、`FGCT`（总耗时）；FGC 每分钟多次且每次几秒 → 必须处理；每次回收后基线逐步抬升 → 泄漏型 |
| ② | 看是不是大对象推动 | `jmap -histo:live <pid> \| head -20` | `byte[]` / `Object[]` / 业务大实体靠前 → 查一次性载入大数据的代码；单次分配几 MB 以上大对象直接进老年代 |
| ③ | 核对堆配置是否太小 | `jinfo -flags <pid>` | `Xmx` 远小于机器内存或业务峰值需要 → 调大；以老年代稳态占用 ×1.5 再留余量校准 `Xmx` |
| ④ | 排查提前晋升 | 核对 `SurvivorRatio`、`MaxTenuringThreshold`；`jstat` 看 Eden 满的频率 | Eden 频繁满且晋升快 → 增大年轻代或 Survivor |
| ⑤ | 查 `System.gc()` 显式触发 | GC 日志里 `Full GC (System)` 代表显式调用 | 周期固定（整点/每小时）→ 大概率定时任务；RMI / NIO 某些路径 / 代码手写都可能；可加 `-XX:+DisableExplicitGC` 屏蔽（依赖显式 GC 回收堆外内存的场景需先评估） |
| ⑥ | dump 分析残留对象 | `jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>` | 以上都对不上时，走「1 OOM」第 ⑤ 步分析存活对象持有链 |

### 3.3 判断树

```text
Full GC 后老年代是否下降？
├── 降   → 对象创建太快 → 减对象 / 增大堆 / 调新生代
└── 不降 → 内存泄漏 → dump + MAT（Leak Suspects → Dominator Tree → Path to GC Roots）
Young GC 太频繁？  → Eden 太小 / 短命对象多
单次 STW 过长？    → 堆过大 / GC 器不当 → G1 / ZGC
```

### 3.4 常见根因

- 堆配置偏小：`Xmx` 不匹配业务量
- 大对象直接进老年代
- 显式 `System.gc()` 触发
- Survivor 过小导致对象提前晋升
- 内存泄漏：老年代基线逐步抬升

### 3.5 关键参数

```bash
-Xms8g -Xmx8g                    # 固定堆，避免动态伸缩
-Xmn3g                           # 新生代
-XX:SurvivorRatio=8              # Eden : Survivor
-XX:MaxTenuringThreshold=15      # 晋升年龄
-XX:+UseG1GC -XX:MaxGCPauseMillis=200
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags   # JDK11+
```

## 4. 线程问题（死锁 / 池耗尽）

> 详见 handbook 第 4、5 章；速查卡见卡片 4、5。

### 4.1 现象

- 线程数几百上千且持续增长
- `jstack` 出现 `Found one Java-level deadlock`
- 大量线程 `BLOCKED` / `WAITING`
- 接口全部 hang，重启才恢复

### 4.2 六步作业单

| 步 | 动作 | 命令 / 观察 | 判读与分流 |
|:--:|---|---|---|
| ① | 抓两份线程栈 | `jstack <pid> > /tmp/s1.txt; sleep 5; jstack <pid> > /tmp/s2.txt` | 对比线程状态是否变化 |
| ② | 先搜死锁标记 | 搜 `Found one Java-level deadlock`、`BLOCKED` | 出现 deadlock 段落 → JVM 已给出互等的两条线程与锁对象，直接读；AB-BA 死锁 → 统一加锁顺序 / `tryLock(timeout)` |
| ③ | 统计线程状态分布 | `grep -c "BLOCKED" /tmp/s1.txt`；按 `Thread.State` 分组计数 | 大量 `BLOCKED` 等同一把锁 → 锁竞争热点（慢操作持锁）；大量 `WAITING` 在 `getTask` → 工作线程空闲，问题在上游 |
| ④ | 看线程池队列是否积压 | 栈里找 `pool-N-thread-M` | 都 `WAITING` 且上游仍超时 → 查调用方；都 `RUNNABLE` 卡同一外部调用 → 外呼无超时占满线程（典型：全卡 `socketRead` 且没配 `connectTimeout`/`readTimeout`） |
| ⑤ | 数线程数与趋势 | `ps -o nlwp <pid>`（或 `ls /proc/<pid>/task \| wc -l`） | 持续增长不回落 → 每次请求新建线程未复用、定时任务反复起线程；`unable to create new native thread` 就是线程失控的终点 |
| ⑥ | 对照根因处置 | 修锁粒度 / 补超时 / 换有界队列 + 拒绝策略 | 线程池四必看：`getActiveCount` / `getQueue().size()` / `getPoolSize()` / `getCompletedTaskCount()` |

### 4.3 常见根因

- 外部调用无超时：线程被 `socketRead` 长期占用
- 锁竞争热点：慢操作持锁（锁内做 RPC / IO）
- 线程池队列无界导致积压甚至 OOM
- 动态新建线程未复用
- 双锁交叉导致死锁

**经典坑**：`Executors.newFixedThreadPool()` 底层是**无界** `LinkedBlockingQueue`，`maxPoolSize` 永远用不上 → 队列无限堆积 → OOM。生产必须手写 `ThreadPoolExecutor` + 有界队列 + 自定义拒绝策略。

## 5. 接口慢 / 超时

> 分层定界方法见 `09-竞价页面突然变慢-排查实录.md`（网关 20ms / DS→C 45ms / MySQL 2950ms 的分段实例）。

### 5.1 现象

- 某接口 P99 / P95 飙升
- 用户反馈"点一下卡半天"
- 调用方大量 read timeout
- 偶发慢，难以复现

### 5.2 六步作业单

| 步 | 动作 | 命令 / 观察 | 判读与分流 |
|:--:|---|---|---|
| ① | 用 `curl` 分解耗时 | `curl -o /dev/null -s -w "连接:%{time_connect} 首字节:%{time_starttransfer} 总:%{time_total}\n" <url>` | 首字节慢 → 服务端慢；连接慢 → 网络 / 端口积压；总慢但首字节快 → 响应体太大 |
| ② | 看访问日志定位层 | 网关 / Nginx `access log` 对比 `upstream_response_time` 与 `request_time` | 前者慢 → 应用慢；两者都小但客户端感觉慢 → 网络 / 客户端问题 |
| ③ | 卡点抓栈 | `jstack <pid> \| grep -A 15 "http-nio.*exec"` | `socketRead` 指向已知 IP → 对端慢；栈在自身业务 → 代码慢；栈在 GC → 转 3；线程池满 → 转 4 |
| ④ | 分类转专题 | 按 ③ 的栈顶分流 | 等 DB → 转 6；等下游 HTTP → 查下游 + 本方补超时；锁等待 → 转 4 |
| ⑤ | 复现路径逐层计时 | Arthas `trace <类> <方法> '#cost>100'`，或对可疑方法打点 | 逐层下钻到最慢的一层再优化；先量化再优化，避免凭感觉改 |
| ⑥ | 检查超时与重试配置 | HTTP / DB / 缓存都要有明确超时；重试设上限与退避 | 没有超时的调用是雪崩之源；防止"超时 → 重试 → 更慢"的恶性循环 |

### 5.3 常见根因

- 慢 SQL / 缺索引（最常见）
- 下游服务慢且本方未设超时
- 锁竞争 / 线程池排队
- 频繁 GC 停顿
- 响应体过大 / N+1 查询

## 6. 数据库问题（慢查询 / 连接池 / 锁）

> MySQL 命令与连接池细节见 handbook 第 6 章；网关扩容打穿 DB 的容量教训见 `11-网关扩容打穿DB-性能开发规范.md`。

### 6.1 现象

- 应用报 `Connection is not available` / 获取连接超时
- 线程栈大量 `socketRead` 指向数据库 IP
- 数据库 CPU 飙高
- 长事务 / 锁等待告警

### 6.2 六步作业单

| 步 | 动作 | 命令 / 观察 | 判读与分流 |
|:--:|---|---|---|
| ① | 应用侧：看连接池状态 | Druid / Hikari 监控：`active` 接近 `max`、`wait` 大量增长 | `active=max` 且持续 → 有连接被长期占用（慢 SQL 或泄漏）；先确认 `max` 是否配太小 |
| ② | 应用侧：谁占着连接 | `jstack <pid> \| grep -A 15 "socketRead"` | 都等同一 SQL → 慢查询；各等各的 → DB 整体慢；连接借出后线程已结束却没归还 → 泄漏（查异常分支是否漏了 `finally close`） |
| ③ | DB 侧：谁在跑（openGauss / PG） | `SELECT pid, state, now()-xact_start AS 事务时长, left(query,80) FROM pg_stat_activity WHERE state<>'idle' ORDER BY xact_start;` | `active` 查询多且都慢 → 全局性问题（资源 / 锁）；少量长查询 → 单点 SQL |
| ④ | DB 侧：锁等待 | `SELECT * FROM pg_locks WHERE NOT granted;`；PG 9.6+ 可用 `pg_blocking_pids(pid)` 找堵源；MySQL 看 `information_schema.innodb_trx`（8.0 另有 `performance_schema.data_lock_waits`） | 锁等待常见于大事务、唯一键并发冲突、外键；MySQL 死锁用 `SHOW ENGINE INNODB STATUS\G` 看 `LATEST DETECTED DEADLOCK` |
| ⑤ | 慢 SQL 分析 | `EXPLAIN ANALYZE <慢SQL>;`（openGauss 另有 `EXPLAIN PERFORMANCE`）；openGauss 结合 `pg_stat_statements` 找累计耗时 Top SQL | 大表 `seq scan`、估算行数与实际差几个量级 → 统计信息或索引问题；MySQL 危险信号：`type=ALL` / `key=NULL` / `rows` 很大 / `Using filesort` / `Using temporary` |
| ⑥ | 对照根因处置 | 补索引 / 拆大事务 / 修泄漏 / 调池 / 隔离报表查询 | 处置后用 ① 的连接池 `active` 与 ② 的线程栈复验 |

**MySQL 侧命令**

```sql
SHOW FULL PROCESSLIST;                       -- 当前连接与执行中的 SQL
SHOW VARIABLES LIKE 'slow_query%';           -- 确认慢查询日志已开
SHOW ENGINE INNODB STATUS\G                  -- LATEST DETECTED DEADLOCK
SELECT * FROM performance_schema.data_lock_waits;   -- MySQL 8 当前锁等待
```

### 6.3 常见根因

- 慢 SQL：缺索引或执行计划劣化（函数、隐式转换、`like` 前缀）
- 长事务 / 大事务持锁与持连接
- 连接泄漏：借出未归还
- 连接池 `max` 配置过小
- 锁等待链条：互相堵塞
- 报表类大查询挤占业务

## 7. 日志风暴 / 磁盘满

> handbook 未单列本篇；异常风暴的堆内指纹（`StackTraceElement` / `char[]` 关键词）见本机 `jvm-triage` skill 的判读手册。

### 7.1 现象

- `df` 使用率 100%，业务写入失败
- 日志每分钟增长 GB 级
- 同一异常重复刷屏（异常风暴）
- 清理文件后空间不释放

### 7.2 六步作业单

| 步 | 动作 | 命令 / 观察 | 判读与分流 |
|:--:|---|---|---|
| ① | 找到满的挂载点 | `df -h; df -i` | 确认哪个目录所在盘满；海量小文件可能把 inode 用光，一并看 |
| ② | 逐层定位大目录 | `du -sh /* 2>/dev/null \| sort -rh \| head` | 应用日志目录暴增 → 优先判断是否异常风暴 |
| ③ | 识别是否日志风暴 | `tail -1000 <log> \| grep Exception \| sort \| uniq -c \| sort -rn \| head` | 同一异常每秒几十次全栈打印 → 异常风暴（典型：下游挂了，每个请求都打一遍全栈）；单一异常占比极高 → 先降级别 / 限频，再修根因 |
| ④ | 清盘后空间不释放 | `lsof \| grep deleted` | 文件已删但进程还持着句柄 → 空间不释放；让进程关句柄（重启）或 `truncate` 该 fd；`echo "" > 大日志` 比 `rm` + 重启更稳妥 |
| ⑤ | 恢复与止损 | 顺序：日志降级 / 抑制重复 → rotate 清旧日志 → 确认根因修复（下游恢复 / SQL 修正）→ 再撤临时措施 | 不要直接 `rm` 正在被写的日志文件 |
| ⑥ | 防复发 | `logrotate` 按天 + 保留 N 份；磁盘告警阈值 85%；异常聚合打印（同一异常限频）；清理脚本纳入例行运维 | 日志级别不当（生产 debug 未关）也是常见根因 |

### 7.3 常见根因

- 异常风暴：同一异常高频全栈打印
- 下游故障导致重试 / 断连日志刷屏
- 日志级别不当：生产 debug 未关
- 轮转缺失：日志无限增长
- 被删文件仍被进程占用，空间不释放

## 8. 网络问题（CLOSE_WAIT / 连接堆积）

> 网关 502/504 与内核参数见 handbook 第 9 章；多机房线路定位见 `08-多机房多线路网络故障-排查实录.md`。

### 8.1 现象

- `CLOSE_WAIT` 数万且不降
- `TIME_WAIT` 爆表
- 偶发 `connect timeout` / `read timeout`
- 端口能通但请求失败

### 8.2 六步作业单

| 步 | 动作 | 命令 / 观察 | 判读与分流 |
|:--:|---|---|---|
| ① | 连接状态总览 | `ss -s` | 看总量与各状态分布，和平时基线对比（平时几千，突然几万就是异常） |
| ② | 分状态计数 | `ss -antp \| awk '{print $1}' \| sort \| uniq -c \| sort -rn` | `CLOSE_WAIT` 大量堆积 → 对端已关闭、本端应用没调 close（代码没关连接，或线程卡住没走到关闭逻辑，常与线程问题联动）；`TIME_WAIT` 短时暴增 → 大量短连接（该上连接池 / 长连接） |
| ③ | 找 `CLOSE_WAIT` 归属 | `ss -antp state close-wait \| head` | 看集中在哪个进程、哪条外部链路（目标 `IP:PORT`），锁定出问题的外呼组件；集中在数据库端口 → DB 侧已断连而连接池没回收（空闲剔除 / `maxLifetime` 要配） |
| ④ | 基础连通性 | `telnet <host> <port>`（或 `nc -zv`） | 端口不通 → 防火墙 / 监听挂了；通但慢 → 对端负载高 |
| ⑤ | 抓包取证（必要时） | `tcpdump -i any host <ip> and port <port> -w /tmp/a.pcap` | Wireshark 看谁先发 FIN、有无重传 / 零窗，确定责任方 |
| ⑥ | 对照根因处置 | 连接池配空闲检测与 `maxLifetime`；短连接改连接池 / 长连接 | 修完用 ① ② 复验状态分布回落 |

### 8.3 常见根因

- `CLOSE_WAIT` 堆积：应用未关闭连接
- 连接池空闲剔除缺失：对端已断本地不知
- 短连接滥用：`TIME_WAIT` 暴增
- 对端过载：响应慢引发超时
- 防火墙 / 安全组变更导致不通

## 9. 服务假死（进程在但不干活）

> handbook 未单列本篇；这是"进程活着但请求全超时"的独立形态，比崩溃更难，因为现象全是"正常"的。

### 9.1 现象

- 进程存活、端口在监听，但请求全部超时
- 健康检查 UP 变 DOWN 但进程不退出
- CPU 极低，或某单核打满
- 重启后短时间内又复发

### 9.2 六步作业单

| 步 | 动作 | 命令 / 观察 | 判读与分流 |
|:--:|---|---|---|
| ① | 确认入口层真实状态 | `curl -v --max-time 5 http://127.0.0.1:<port>/health` | 本机直连绕过网关：本机也 hang → 应用自身问题；本机正常 → 网关 / 网络问题 |
| ② | 抓栈看工作线程在干嘛 | `jstack <pid> > /tmp/s.txt`；搜 `http-nio-*-exec-*`（Tomcat） | 全 `WAITING` 空闲但请求进不来 → 线程池 / accept 配置；全 `BLOCKED` → 锁死；全卡 `socketRead` → 下游全慢拖死线程池 |
| ③ | 排查 GC 死循环 | `jstat -gcutil <pid> 1000 10` | `O` 列长期 100%、每秒 FGC 且耗时极长 → 堆陷入 GC 循环（接近 OOM 的典型形态），业务线程拿不到时间片；确认后转「1 OOM」 |
| ④ | 检查单点串行瓶颈 | 看栈里是否有线程卡在 `log` / `flush`；单线程消费卡死、同步代码块串行化、日志同步刷盘都可能堵死入口 | 单线程瓶颈阻塞入口 → 拆异步 / 加缓冲 / 改批量 |
| ⑤ | 保现场再重启 | `jstack <pid> > /tmp/s1.txt; sleep 5; jstack <pid> > /tmp/s2.txt`；再抓 heap dump、`jstat` 采样、日志尾部、`top` | 假死的现场重启后就没了；先花 1–2 分钟抓齐落到 `/tmp` 并拷出 |
| ⑥ | 复盘定位根因 | 按抓到的栈分类：死锁 → 4；GC 循环 → 1；全卡外呼 → 补超时 | 修复后压测验证，确认不再复发 |

### 9.3 常见根因

- 堆耗尽引发 GC 死循环（最常见假死根因）
- 线程池全被无超时外呼占满
- 全局锁死锁
- 单线程瓶颈阻塞入口
- 日志 / 磁盘 IO 卡住同步写

## 10. 应急响应（先恢复，再定位）

> 方法论见 `12-生产排查步骤-四类场景与六步SOP.md` 第 2 节；本页是故障当场的动作顺序。

### 10.1 现象

- 线上大面积报错 / 不可用
- 需要立即决策的故障时刻
- 不知道先做什么时

### 10.2 六步作业单

| 步 | 动作 | 要点 |
|:--:|---|---|
| ① | 评估影响面（1 分钟内） | 哪些接口、哪些用户受影响？有无资损 / 数据一致性风险？影响面决定动作级别（重启 / 切流 / 降级 / 回滚）；数据类风险（重复写入、半提交）优先保全数据，不急着恢复 |
| ② | 快速止血 | 按成本从低到高：重启实例（无状态服务首选）→ 摘除节点 / 切流量 → 开降级开关 → 版本回滚；止血动作必须留痕：谁、几点、做了什么 |
| ③ | 止血前保现场（2 分钟） | 两份 `jstack`、heap dump、`jstat` 采样、日志尾部、`top`，落到 `/tmp` 并拷出；宁可多花 2 分钟保现场，也不要重启后从零猜 |
| ④ | 观察恢复后状态 | 立即验证：接口成功率、线程数、内存基线、连接数；快速反弹回原状态 → 周期性问题未根治，重点盯 |
| ⑤ | 落工单记录时间线 | 新建工单：时间线（发现 / 响应 / 止血 / 恢复）、现象、临时措施；已定位的根因与永久修复项列出 |
| ⑥ | 复盘与防复发 | 48 小时内出复盘：根因、为何没被提前发现（监控缺口）、永久修复项与负责人；同类故障的排查步骤沉淀回本工作台 |

**保现场一键命令**

```bash
jstack <pid> > /tmp/s1.txt; sleep 5; jstack <pid> > /tmp/s2.txt
jstat -gcutil <pid> 1000 10
top -b -n 1 -p <pid>
netstat -antp | grep <pid> | wc -l
```

> 更完整的自包含采集用本机 `jvm-triage` skill 的 `scripts/jvm_diag.sh <pid>`：jstack / GC / 堆直方图 / Perm / 句柄 / 连接 / 系统指标一键打包（兼容 JDK7 目标进程，产物 `manifest.txt` 可判读）。

### 10.3 常见根因（应急失分点）

- 无监控告警导致发现滞后
- 止血动作无留痕导致无法复盘
- 现场未保存导致根因丢失
- 修复未验证导致复发

## 11. 命令速查（六组）

### 11.1 JVM 内存与 GC

| 命令 | 用途 |
|---|---|
| `jmap -histo:live <pid> \| head -30` | 堆内对象直方图 Top30：看谁实例数多、占用大（会 STW） |
| `jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>` | 抓堆转储（会 STW，先切流；大堆几十秒） |
| `jstat -gcutil <pid> 1000 60` | GC 概览 1 分钟：各代占用 %、FGC 次数与耗时 |
| `jstack <pid> > /tmp/s1.txt` | 抓线程栈（间隔几秒抓 2–3 次便于对比） |
| `jinfo -flags <pid>` | 查看启动参数：`Xmx`、GC 算法等 |
| `jmap -permstat <pid>` / `jmap -clstats <pid>` | JDK7 PermGen / JDK8+ 类加载器统计 |

### 11.2 进程与 CPU

| 命令 | 用途 |
|---|---|
| `top -c` | 进程 CPU 排行（按大写 `P` 以 CPU 排序） |
| `top -Hp <pid>` | 进程内线程 CPU 排行，记下 `ThreadId` |
| `printf '%x\n' <tid>` | 线程号转十六进制（对应 `jstack` 的 `nid`） |
| `pidstat -t -p <pid> 1 5` | 线程级 CPU 采样 5 秒 |
| `vmstat 1 5` | 看 `cs`（上下文切换）与运行队列 |
| `ps -o nlwp <pid>` | 进程当前线程数 |

### 11.3 数据库（MySQL / openGauss·PG）

| 命令 | 用途 |
|---|---|
| `SHOW FULL PROCESSLIST;` | MySQL：当前连接与执行中的 SQL |
| `SELECT pid, state, now()-xact_start AS 事务时长, left(query,80) FROM pg_stat_activity WHERE state<>'idle' ORDER BY xact_start;` | openGauss / PG：活动会话与长事务 |

| `EXPLAIN ANALYZE <慢SQL>;` | 执行计划与实际耗时（openGauss 另有 `EXPLAIN PERFORMANCE`） |
| `SHOW VARIABLES LIKE 'slow_query%';` | MySQL：确认慢查询日志已开 |

### 11.4 网络

| 命令 | 用途 |
|---|---|
| `ss -s` | 连接状态总览，与基线对比 |
| `ss -antp \| awk '{print $1}' \| sort \| uniq -c \| sort -rn` | 各状态连接计数：`CLOSE_WAIT` 堆积 = 未关闭 |
| `ss -antp state close-wait \| head` | 看 `CLOSE_WAIT` 集中在哪个进程哪条链路 |
| `curl -o /dev/null -s -w "连接:%{time_connect} 首字节:%{time_starttransfer} 总:%{time_total}\n" <url>` | 接口耗时分解 |
| `tcpdump -i any host <ip> and port <port> -w /tmp/a.pcap` | 抓包取证 |

### 11.5 磁盘与系统

| 命令 | 用途 |
|---|---|
| `df -h; df -i` | 磁盘空间与 inode 使用率 |
| `du -sh /* 2>/dev/null \| sort -rh \| head` | 逐层定位大目录 |
| `lsof \| grep deleted` | 已删但被占用的文件：空间不释放的真凶 |
| `free -m` | 内存与 swap |
| `tail -c 2000 <log>` | 看日志尾部：识别异常风暴刷屏 |

### 11.6 现场采集（重启前必抓）

| 命令 | 用途 |
|---|---|
| `jstack <pid> > /tmp/s1.txt; sleep 5; jstack <pid> > /tmp/s2.txt` | 连续两份线程栈：对比定位卡点 / 死锁 |
| `jstat -gcutil <pid> 1000 10` | 10 秒 GC 观察 |

## 12. 故障工单字段（工作台数据层）

工作台的"故障记录"页用 localStorage 存工单，字段设计可直接复用（建库 / 建表时照此）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `id` | string | ✅ | 自动生成 |
| `title` | string（≤60） | ✅ | 如"iface 节点2 OOM 重启" |
| `type` | enum | ✅ | 十类故障之一（即本件 §1–§10） |
| `severity` | enum | — | P1 紧急 / P2 高 / P3 中（默认）/ P4 低 |
| `status` | enum | — | 排查中（默认）/ 已定位 / 已解决 |
| `symptom` | text（≤600） | — | 现象 |
| `root_cause` | text（≤600） | — | 根因 |
| `solution` | text（≤600） | — | 解决措施 |
| `done_steps` | text（≤2000） | — | 步骤进度（存 JSON 数组，勾选到第几步） |
| `note` | text（≤800） | — | 复盘笔记 |
| `resolved_at` | string（≤40） | — | 解决时间 |
| `created_at` | datetime | ✅ | 自动生成 |

**工单填写纪律**：时间线要能还原"发现 → 响应 → 止血 → 恢复"；临时措施与永久修复分开写；根因未定位时 `status` 保持"排查中"，不提前写"已解决"。

## 14. 使用方式

1. **故障当场**：先按 `12` 的六步 SOP 定流程 → 打开本件 §0 选故障类型 → 照该页六步走；命令细节回 handbook 对应章。
2. **日常巡检**：用 §11.6 的采集命令 + 卡片 11 的"一分钟体检"，平时存一份基线（闲时），告警时再采一份做差。
3. **复盘沉淀**：工单按 §12 字段记录；同类故障的排查步骤回写本件对应页，不另起新文档。
4. **面试口径**：方法论讲 `12` 的六步 SOP，讲实录用 `00-面试计划/07` 的四个案子；本件是"技术动作层"的依据库，不替代主线件。
