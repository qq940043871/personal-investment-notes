# 多机房多线路网络故障 — 如何定位到是哪条线路的问题（排查实录）

> **文档定位**：典型故障排查实录（基于真实架构的代表性场景），回答"多机房多线路环境下，网络访问异常时如何快速定位到具体线路"。讲排障方法论 + 治乱能力。

---

## 1. 问题描述

### 1.1 网络架构背景（排查的地图）

```
                    智能 DNS（GSLB，按"地域 × 运营商"调度）
        ┌─────────────────────────┴─────────────────────────┐
        ▼                                                   ▼
  主机房（华东）                                        灾备机房（华北）
  ┌──────────────────┐                                  ┌──────────────────┐
  │ 电信线路 VIP-A   │  ←── 电信用户就近接入            │ BGP 多线 VIP-C   │
  │ 联通线路 VIP-B   │  ←── 联通用户就近接入            │（电信/联通/移动）│
  │                  │                                  │                  │
  │ midservice × N   │                                  │ midservice × N   │
  │ midmon 监控告警  │                                  │ midmon 监控告警  │
  └──────────────────┘                                  └──────────────────┘
        └───────────── 内网专线互通（数据同步/容灾）────────────┘
```

- 三端接入（外部大屏 / 普通客户 / 机构客户，PC + 移动），入口为 **Java 自研网关 midservice 多实例**，midmon 承担监控告警与拨测。
- 双机房容灾 + 每机房双线路接入；用户访问走哪个 VIP 由 GSLB 按地域和运营商决定。

### 1.2 故障现象

| 维度 | 描述 |
|------|------|
| **故障表现** | 华北 / 山东客户反馈页面打开慢、频繁超时、报价提交失败；华东客户一切正常 |
| **发现时间** | 某周二 10:20，客服工单开始聚集（47 条 / 30 分钟） |
| **影响范围** | 走"联通线路访问主机房"的用户；电信用户、灾备机房域名均正常 |
| **触发条件** | 联通宽带 / 联通 4G 必现（约 30% 请求超时）；同一切换手机热点（移动网络）立刻正常 |
| **复现率** | 约 30% 请求失败（**丢包型故障**，不是全断） |

### 1.3 关键差异条件（第一时间要拼出的对照表）

| 对比维度 | 联通→主机房 | 电信→主机房 | 联通→灾备机房 | 同一用户→移动网络 |
|----------|:----------:|:----------:|:------------:|:---------------:|
| 页面打开 | ❌ 慢/超时 | ✅ 正常 | ✅ 正常 | ✅ 正常 |
| 后台服务指标（midservice QPS/RT/错误率） | 正常 | 正常 | 正常 | — |

**这张表本身就是第一个结论**：同机房服务正常 + 同用户换网络正常 + 同运营商换机房正常 → 问题收敛在"**主机房联通这一条线路**"上，而不是服务端、不是客户侧、不是全局 DNS。

### 1.4 已排除的假设

| 假设 | 根因方向 | 排除依据 |
|------|---------|---------|
| 服务端故障（midservice / 中台服务） | 应用层 | 同机房电信用户完全正常，midmon 显示服务 QPS/RT/错误率无异常 |
| 全局 DNS 解析错误 | 调度层 | 各地 dig 解析结果正确，用户拿到的 VIP 符合调度策略 |
| 机房内部网络（核心交换 / 防火墙） | 机房内网 | 同机房电信线路正常、内网拨测 0 丢包 |
| 客户侧设备 / 浏览器 | 客户端 | 同一台电脑切换手机热点立刻正常 |
| 客户侧安全设备（如 06 号文档的 DLP 场景） | 中间设备 | 现象是丢包超时而非认证改写；跨几十家客户同时出现，不可能是单一客户设备 |

## 2. 排查过程：四步定位法

> **核心问题只有一个：是哪条线路的哪一段坏了。** 排查按"定域 → 对照 → 逐跳 → 包级"四步收敛，全程控制变量。

### 2.1 第一步：定域 — 用故障矩阵回答"谁不通"

把客服工单、客户端埋点、拨测数据按 **地域 × 运营商 × 入口（机房/线路 VIP）× 时间** 聚合成矩阵：

| | 电信 | 联通 | 移动 |
|---|:---:|:---:|:---:|
| **华东 → 主机房** | ✅ | ❌ 30% 超时 | ✅ |
| **华北 → 主机房** | ✅ | ❌ 25% 超时 | ✅ |
| **华北 → 灾备机房** | ✅ | ✅ | ✅ |

**矩阵判读规则（通用）**：

| 现象组合 | 结论 |
|---------|------|
| 同地域、不同运营商表现不同 | **运营商线路问题**（本案命中） |
| 同运营商、跨地域都异常 | 该运营商骨干网问题或我方对应出口问题 |
| 一个机房所有线路都异常 | 机房内部问题（交换机/防火墙/LB）或服务端问题 |
| 所有机房所有线路都异常 | 服务端 / DNS / 全局性故障 |
| 零散客户异常、与运营商无关 | 客户侧网络或客户侧安全设备（转 06 号文档排查） |

### 2.2 第二步：对照拨测 — 控制变量钉死线路

从多个探测点（多地多运营商拨测节点 + 一台内网机器）对**同一组目标**做四象限对比拨测，每项测 TCP 建连成功率、TLS 握手、TTFB：

| 对照组 | 目标 | 实测结论 |
|--------|------|---------|
| 同宿异线 | 同一机房的电信 VIP-A vs 联通 VIP-B | A 正常、B 丢包 12% → **B 线路有问题** |
| 同线异宿 | 联通→主机房 VIP-B vs 联通→灾备 VIP-C | B 异常、C 正常 → **不是联通全网问题，是我方联通这根线** |
| 内网直连 | 机房内直连 midservice 实例端口 | 0 丢包、RT 正常 → 排除机房内网与服务 |
| 参照组 | 同探测点访问公网无关站点 | 正常 → 排除探测点自身 |

分段计时脚本（curl -w 把耗时拆开，区分"建连慢"还是"应用慢"）：

```bash
#!/bin/bash
# 线路对照拨测：跑 50 次，统计成功率与分段耗时
run_probe() {
  local name=$1 url=$2
  for i in $(seq 1 50); do
    curl -o /dev/null -s -m 5 -w \
      "$name dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} code=%{http_code}\n" \
      "$url"
  done | tee /tmp/probe_$name.log | awk '
    /code=200/{ok++} END{printf "成功率 %d/50\n", ok}'
}
run_probe "电信VIP-A" "https://trade.example.com/api/ping"
run_probe "联通VIP-B" "https://trade-cnc.example.com/api/ping"
run_probe "灾备BGP-C"  "https://trade-dr.example.com/api/ping"
```

**判读**：`tcp` 段变长或 `code=000`（超时）→ 传输层问题，跟应用无关；`tcp` 正常但 `ttfb` 大 → 转应用侧排查（见 09 号文档）。本案 VIP-B 大量 `code=000` 且 `tcp` 建连失败率 30% → 纯传输层。

### 2.3 第三步：逐跳定位 — mtr 找到丢包开始的"边界跳"

正常路径与异常路径各跑一次长测，对比逐跳丢包：

```bash
mtr -rwzbc 100 目标VIP     # 100 个包，报告模式，AS 号显示
```

实测摘录（异常路径）：

```
HOST                    Loss%   Snt   Last   Avg  Best  Wrst
1. 客户网关               0.0%   100    1.2   1.5   1.0   8.2
2. 市级汇聚               0.0%   100    8.1   9.3   7.2  22.0
3. 省干（联通 AS48xx）     0.0%   100   18.5  20.1  17.0  55.0
4. 骨干网（联通 AS48xx）   0.0%   100   25.2  26.8  24.1  60.0
5. 机房联通出口（我方边界） 12.0%  100   28.0  30.5  26.2  900+   ← 丢包从这里开始
6. 核心交换                12.0%  100   28.3  30.7  26.5  900+
7. midservice VIP          12.0%  100   28.5  30.9  26.7  900+
```

**判读规则**：
- **丢包从某一跳开始、之后每一跳都持续丢** → 那一跳就是故障边界。本案边界在"机房联通出口"这一跳（运营商骨干 0 丢包 → 运营商侧干净，问题在我方出口段）。
- ⚠️ **ICMP 限速假象**：中间某一跳丢包、但后面跳不丢、末跳不丢 → 是设备对 ICMP 限速，不是故障，以**末跳**为准。
- 对照组：电信路径全程 0 丢包、RTT 正常 → 双线对照坐实"联通这根线"。

### 2.4 第四步：包级验证 — 抓包 + 硬件证据定责任

在机房入口交换机/网关抓包，验证"丢的是什么"：

```bash
# 服务端侧：看 SYN 到达率（正常应接近 100%）
tcpdump -i eth0 -c 1000 'tcp[tcpflags] & tcp-syn != 0 and dst port 443' -nn
```

实测：SYN 到达率仅 **~70%**，且部分 SYN-ACK 发出后客户端回不来 ACK → **请求在链路上被丢**，服务端无辜。

硬件层证据（边界在我方出口段之后的收敛）：

| 检查项 | 命令/位置 | 实测值 | 判读 |
|--------|----------|--------|------|
| 网卡错包/丢包 | `ip -s link` / `nstat -az \| grep -i retrans` | 错包持续增长 | 链路质量差 |
| 交换机端口误码 | 接入交换机 `show interface counters errors` | GE0/0/1 CRC error 持续增长 | 误码→丢包 |
| 光模块收光功率 | 交换机 `show transceiver diagnostics` | rx **-19.8 dBm**（灵敏度 -18 dBm） | **光衰越过临界值** |
| 对端（运营商 PE）收光 | 运营商侧确认 | 正常 | 排除运营商骨干 |

**收敛结论**：主机房**联通出口上联光模块老化**，收光功率劣化到灵敏度临界之下，机房温度升高后误码率上升 → 链路层丢包 8%~15% → 用户侧 30% 请求超时。仅联通线路受影响，电信/BGP 正常。

## 3. 根本原因总结

### 3.1 直接根因

> **主机房联通出口上联光模块老化导致光衰劣化（rx -19.8 dBm，低于 -18 dBm 灵敏度），链路误码率升高产生 8%~15% 丢包，联通线路用户请求大量超时。**

### 3.2 深层根因

> **线路级可观测性缺失**：监控只有"从机房往外"的业务拨测，没有"从外向内、分运营商"的多点探测；线路故障只能靠客户报障发现——发现慢（30 分钟工单聚集才察觉），定位也慢（缺对照数据，第一轮怀疑错了方向）。

### 3.3 根因因果链

```
出口光模块老化（硬件寿命）
  → 收光功率劣化到灵敏度临界（-19.8dBm < -18dBm）
    → 机房温度升高后误码率上升（CRC error）
      → 联通线路链路层丢包 8%~15%（电信线路不受影响）
        → 用户 TCP 建连/请求 30% 超时（丢包型，非全断）
          → 页面慢、报价提交失败（客服工单聚集）
            → 无分线路拨测告警，故障靠客户报障才被发现（发现/定位慢）
```

## 4. 处置经过与改进措施

### 4.1 应急处置（本次，当天恢复）

| 序号 | 措施 | 耗时 | 说明 |
|:---:|------|:---:|------|
| S-1 | GSLB 把联通调度切到灾备机房 BGP 入口 | 5 分钟 | 注意 DNS 缓存 TTL，先降权重再观察 |
| S-2 | 带 mtr + 丢包区间数据向联通报障 | 并行 | 数据越具体，运营商响应越快 |
| S-3 | 更换上联光模块（备件库常备） | 40 分钟 | 换后 rx 回到 -14 dBm，CRC 清零 |
| S-4 | 拨测观察 30 分钟后 GSLB 回切 | 30 分钟 | 确认误码为零才回切 |

### 4.2 中期技术改进（1-2 周）

| 序号 | 措施 | 优先级 | 说明 |
|:---:|------|:-----:|------|
| M-1 | **多点拨测体系**：分运营商探测点（电信/联通/移动各至少 2 点），TCP 建连 + HTTP 两层指标，每分钟一次 | **P0** | "从外向内"探测，故障矩阵自动绘制 |
| M-2 | **分线路 SLO 看板与告警**：丢包 > 0.5% 或 TCP 建连成功率 < 99% 即告警，按线路维度展示 | **P0** | 告警直接指名"哪条线路"，而不是笼统"用户反馈慢" |
| M-3 | GSLB 健康检查联动：连续失败自动摘除故障线路并告警 | P1 | 自动化切换，缩短 MTTR |
| M-4 | 出口链路硬件纳管：光功率 / 误码 / 温度纳入巡检与告警 | P1 | 光衰在劣化到故障前就能发现 |

### 4.3 长期预防（流程与规范）

| 序号 | 措施 | 层面 | 说明 |
|:---:|------|------|------|
| L-1 | 网络冗余设计规范 | 架构 | 双上联、双出口、光模块/备件常备，任何单条线路故障不影响业务可达 |
| L-2 | 运营商 SLA 与联合演练 | 商务/运维 | 明确响应时限，每年一次割接/故障联合演练 |
| L-3 | **故障矩阵模板**纳入排障知识库 | 知识库 | 网络类问题先填矩阵再动手，避免第一轮方向跑偏 |
| L-4 | 网络故障分级预案 | 运维 | 明确哪些情况 GSLB 自动切、哪些人工确认切、切换验证清单 |

## 5. 附录

### 5.1 命令速查表

| 目的 | 命令 |
|------|------|
| 逐跳丢包定位 | `mtr -rwzbc 100 目标IP` |
| DNS 调度核查 | `dig +short 域名 @各地DNS` / `nslookup 域名` |
| 分段计时 | `curl -o /dev/null -w 'tcp=%{time_connect} ttfb=%{time_starttransfer} code=%{http_code}\n' URL` |
| 服务端 SYN 到达率 | `tcpdump -i eth0 -c 1000 'tcp[tcpflags] & tcp-syn != 0 and dst port 443' -nn` |
| 连接队列/丢弃 | `ss -s`、`netstat -s \| grep -Ei 'listen|overflow|drop'` |
| 主机网络错误计数 | `ip -s link`、`nstat -az \| grep -iE 'retrans|drop'`、`sar -n DEV,TCP,ETCP 1` |
| 交换机误码/光功率 | `show interface counters errors`、`show transceiver diagnostics` |

### 5.2 线路故障判定矩阵（速记）

```
第一步：故障矩阵（地域 × 运营商 × 机房）→ 圈出"谁不通"
第二步：对照拨测（同宿异线 / 同线异宿 / 内网 / 参照）→ 锁定"哪条线路"
第三步：mtr 逐跳对比 → 丢包开始的边界跳 = 故障段落归属
第四步：抓包 + 端口误码/光功率 → 线路侧 or 机房侧，定责任方
```

### 5.3 术语说明

| 缩写 | 全称 | 说明 |
|------|------|------|
| GSLB | Global Server Load Balance | 全局负载均衡/智能 DNS，按地域运营商调度入口 |
| BGP | Border Gateway Protocol | 边界网关协议，多线接入由运营商广播同一 VIP |
| mtr | Matt's Traceroute | traceroute + ping 统计，逐跳丢包/延迟 |
| RTT | Round Trip Time | 往返时延 |
| PE | Provider Edge | 运营商边缘路由器 |
| CRC | Cyclic Redundancy Check | 循环冗余校验，端口误码计数 |
| SYN | Synchronize Sequence Number | TCP 建连握手首包，SYN 到达率反映链路丢包 |
| 光衰 | Optical Loss | 光功率衰减，越过接收灵敏度即误码/丢包 |

### 5.4 面试速答（90 秒版）

> "客户反馈部分地区访问慢，我先做**定域**：把工单按地域×运营商×机房拼成故障矩阵，发现'联通→主机房'单格异常、其他正常，服务端指标干净——先排除应用和客户侧。第二步**对照拨测**：同机房电信 VIP 正常、联通 VIP 丢包 12%，联通访问灾备机房又正常——同宿异线、同线异宿两个对照一做，钉死是我方联通这根线。第三步 **mtr 逐跳**：丢包从'机房联通出口'这一跳开始，运营商骨干全程 0 丢包，边界在我方出口段。第四步**抓包和硬件证据**：入口 SYN 到达率只有 70%，交换机端口 CRC 误码持续增长，光模块收光 -19.8dBm 已越过 -18dBm 灵敏度——根因是出口光模块老化光衰劣化。当天 GSLB 把联通切到灾备 BGP 入口恢复，换光模块后回切。治本是补上'从外向内分运营商'的多点拨测和分线路告警——以前这类故障只能靠客户报障发现。"

**追问预案**：

| 追问 | 回答要点 |
|------|---------|
| 怎么确定不是服务端问题？ | 同机房电信用户正常 + 内网直连 0 丢包 + midservice QPS/RT/错误率平稳，三条证据同时指向传输层 |
| mtr 中间跳丢包是不是故障？ | 不一定，中间设备 ICMP 限速常见；看末跳和"丢包是否从某跳开始持续到底"，边界跳之后全丢才是故障 |
| 为什么不直接全量切走？ | GSLB 切换受 DNS 缓存 TTL 影响，先降权重灰度回切验证；盲目切换可能把故障域放大 |
| 如何防止再发生？ | 硬件侧光功率/误码纳管告警（劣化期就能发现）；观测侧多点拨测 + 分线路 SLO；架构侧双上联 + 备件 + 自动切换预案 |
| 如果是运营商骨干坏了怎么办？ | 同线异宿对照能区分"运营商侧/我方侧"；运营商侧则按 SLA 报障 + GSLB 切换到另一机房/线路兜底，同样在预案里 |
