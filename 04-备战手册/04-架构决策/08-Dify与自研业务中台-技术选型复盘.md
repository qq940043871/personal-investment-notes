# 技术选型复盘：为什么是「Dify + 自研业务平台」

> 定位：AI 智能服务平台**底座选型决策复盘**——先在"框架层自研 / 云厂商 PaaS / 开源平台"三条路线中定盘，再确定"谁做智能层、谁做业务层"的边界。  
> 结论：**Dify（社区版，Apache-2.0 修改版，私有化二开）承担智能层 + 自研业务中台承担业务主干**，两者的边界用 API 划清。  
> 适用场合：技术选型评审 / 架构决策答辩 / 面试讲"AI 平台怎么选型"。

## 一、候选清单与各自定位（先对齐"它们在比什么"）

这六个选项并非同一层级的竞品，混在一起比较容易导致选型失焦。先按层次归类：

| 层次       | 候选                       | 本质定位                          |
| -------- | ------------------------ | ----------------------------- |
| 框架层（代码库） | LangChain / LlamaIndex   | 给程序员用的 SDK，需要自建编排、API、监控、调试界面 |
| 云厂商 PaaS | 阿里云百炼                    | 托管式 Agent/RAG 平台，绑阿里云生态与计费    |
| 开源应用平台   | Dify / FastGPT / RAGFlow | 可视化编排 + RAG + API 交付的一体化底座    |
| 通用自动化    | n8n                      | 系统间流程自动化，AI 是其能力之一而非主线        |

选型的核心在于：在"框架层自研"、"买云上 PaaS"、"用开源平台"这三条路中选一条，再从开源平台里挑一个。

## 二、评估维度与权重

| 维度                                        | 权重 | 说明          |
| ----------------------------------------- | -- | ----------- |
| 数据不出域 / 私有化部署                             | 高  | 一票否决项       |
| 模型中立（可换模型、可换厂商）                           | 高  | 避免二次锁定      |
| 编排能力（Workflow + Agent + 工具调用）             | 高  | 场景复杂度决定     |
| RAG 工程成熟度（解析 / 分块 / 混合检索 / ReRank / 召回测试） | 高  | 效果基线        |
| 协议与长期可控（能否商用、能否二开、能否换掉）                   | 高  | 法务 + 架构双重约束 |
| 交付形态（API 优先、可被中台调用）                       | 中  | 决定能否"只取智能层" |
| 非技术人员可参与调优                                | 中  | 迭代节奏问题      |
| 权限 / 审计 / 多租户                             | 中  | 可由中台补位      |
| 团队上手成本与周期                                 | 中  | 原型期关键       |

## 三、逐项淘汰理由

### 3.1 纯自研 LangChain + LlamaIndex —— 输在"重复建设 + 周期"

**保留的理由**：控制力最强；LlamaIndex 检索策略（多索引 / 子查询 / Rerank / GraphRAG）最细；LangChain / LangGraph 做复杂 Agent、人机协同最灵活。

**淘汰原因**：

- **缺的是"平台"而不是"库"。** 可视化调试、Prompt 版本管理、知识库管理界面、召回测试、标注与日志、流式 API 网关、多模型配置——这些全部要自研，工作量远超预期，且与业务价值无关。
- **MVP 到生产的落差大。** 原型 3 天能跑通，但做到"产品可用"（重试、降级、限流、可观测、权限注入、评测集回归）通常要 2–3 周起步，且没有现成运营界面，产品和业务无法参与调优，迭代必然回到"提需求 → 开发 → 发版"的慢循环。
- **版本漂移成本高。** LangChain 大版本间 import 路径与 Chain API 变动频繁，长期维护要有人专职跟生态；我们的团队规模不适合把人力押在框架兼容性上。

**结论**：框架层能力只在"有独特算法壁垒或检索精度是生死线"时值得自研。当前场景的瓶颈在业务集成与治理，不在检索算法的上限。（注：RAG 深度定制仍可能回退到此方案，见第八节）

### 3.2 阿里云百炼 —— 输在"锁定 + 合规口径"

**保留的理由**：全生命周期管理（数据处理 → 微调 → 评估 → 部署）、企业级权限 / 审计 / 限流原生完备、SLA 与技术支持有保障、专属版支持 VPC / 专有云 / 物理隔离部署。

**淘汰原因**：

- **数据与模型绑定同一厂商。** 模型以通义系为主，切换外部模型虽有路径但非一等公民；一旦效果或价格出现更优选项，迁移成本极高。
- **计费不可控。** 按 token / 调用量计费且平台侧存在溢价，规模化后 TCO 线性增长，无法像自部署那样"只为模型付费"。
- **合规口径仍需自证。** 即便专属版支持隔离部署，"模型跑在哪、数据落哪、密钥谁管、外部链路通不通"仍需单独论证；而自部署的答案可以直接指向自己的机房。
- **采购与上线周期长**，不符合原型期"几周出东西"的节奏。

**结论**：作为二期备选或灾备链路（例如国产化合规强制要求、或需要深度微调时再引入），不作为主底座。

### 3.3 FastGPT —— 输在"编排广度不足"

**保留的理由**：知识库专精（QA 对模式、手动标注、索引增强），中文体验好，私有化零抽成，部署简单，Apache-2.0（附：不得白标运营多租户 SaaS、不得移除 LOGO）。

**淘汰原因**：

- **Workflow 与 Agent 能力弱于 Dify。** 工具调用、复杂分支、子流程复用、多模型路由等能力较基础，而我们明确有"跨系统业务流程 + 确定性兜底"的需求。
- **定位偏"知识问答系统"而非"AI 应用底座"。** 若未来扩展到内容生成、流程助手、多 Agent 协作，天花板更低。

**结论**：如果最终场景收敛为纯知识库问答，FastGPT 是更好的选择；当前选 Dify 是为后续场景扩展留余地。

### 3.4 RAGFlow —— 输在"能力偏科"

**保留的理由**：文档理解最深（DeepDoc 深度解析、表格图表处理、引用溯源），支持 GraphRAG / RAPTOR，知识库可控性最好，Apache-2.0，纯 CPU 也可跑。

**淘汰原因**：

- **强在 RAG，弱在应用层。** 工作流编排、Agent、多渠道交付、运营闭环不如 Dify 完整，我们需要的不只是"答得准"，还有"接得进业务"。
- **我们的文档复杂度尚未触及其优势区间。** 当前以结构化 / 半结构化文档为主，表格密集、版式复杂的合同标书占比不高，深度解析的收益不足以抵消应用层能力的损失。

**结论**：将其作为"解析器插件"保留——复杂文档走 RAGFlow / 自研解析后再入库 Dify，取其长而不受其限。（这是最容易被忽略的组合用法。）

### 3.5 n8n —— 输在"定位错位 + 协议风险"

**保留的理由**：400+ 集成节点、跨系统数据流转成熟、可写代码控制、错误重试机制完善，做"系统对接胶水"极强。

**淘汰原因**：

- **协议不是 OSI 开源。** 采用 Fair-code / Sustainable Use License：内部自用免费，但禁止白标转售、禁止对外托管收费、销售价值主要源于 n8n 功能时需签商业协议。对外交付或嵌入产品向客户收费的场景存在合规不确定性，法务评审成本高。
- **AI 能力是附加项而非主线。** 缺少成熟的 RAG 管道（分块、混合检索、ReRank、召回测试）、无 Prompt 管理与标注运营体系，做 AI 应用仍是半套。
- **编排语义不同。** n8n 擅长"事件触发 → 数据搬运"，Dify 擅长"对话态 + 记忆 + 生成 + 检索"，后者才是我们的主交互形态。

**结论**：n8n 不与 Dify 竞争，而是互补——后续若出现大批量异构系统定时同步、非对话式自动化任务，可放在中台侧或用 n8n 承担，不进入智能层选型。

<a id="四"></a>

## 四、为什么最终是 Dify

在剩下的选项中，Dify 是唯一同时满足以下条件的：

- **可私有化且协议宽松**：社区版基于 Apache-2.0（修改版），自用 / 单租户自部署免费、可商用、可二开；限制仅在于不得未经授权使用源码搭建多租户 SaaS、不得移除前端 LOGO——这两条对我们的自用场景均不触发。
- **模型完全中立**：OpenAI-compatible 端点 + 本地推理 Runtime，国产模型、私有模型随时切换，模型选型风险不由架构承担。
- **RAG 达到生产门槛**：分块、清洗、混合检索、ReRank、召回测试界面一应俱全，自建这部分投入产出比最低。
- **Workflow + Agent 双模**：关键路径用 Workflow 保确定性与可解释，开放环节用 Agent 做检索与工具选择——这是满足业务稳定性要求的必要组合。
- **API 优先交付**：应用一键发布为 REST / 流式 API，天然适合作为业务中台的下游能力服务，前端与中台无需感知 AI 内部实现。
- **Prompt 与代码解耦**：Prompt 变成可在控制台修改、预览、AB 的配置项，迭代节奏从"发版"变为"改配置"，产品与业务可直接参与。
- **可观测与运营闭环原生具备**：日志、标注、用量统计、效果评估有数据来源，这是原型走向生产的必要条件。
- **部署形态可平滑演进**：原型期 Docker Compose 快速起量，生产期切 K8s + 外部 RDS / Redis / 对象存储。
- **社区活跃、可二开、有退出路径**：遇到边界问题可以改源码或用插件 / MCP 扩展，不会被厂商路线图卡死。

**一句话总结**：Dify 赢在"能力全面度 × 可控性 × 周期"的综合最优，而不是单项第一。

<a id="五"></a>

## 五、为什么还要自研业务平台（Dify 的边界）

Dify 的定位是 LLMOps 与应用编排，以下问题它不解决，而这些恰好是业务系统的主干：

| Dify 社区版的短板                     | 由自研中台承接                             |
| ------------------------------- | ----------------------------------- |
| RBAC 只到工作空间 / 应用级，无行级、组织级、数据级权限 | 统一身份 + 细粒度鉴权，校验永远在中台侧执行             |
| 无内置应用版本控制、复杂工作流难维护              | DSL 纳入 Git + CI，环境分离，发布走流水线         |
| 审计日志、SSO、多租户在企业版才完备             | 业务操作日志 + AI 调用日志通过 trace_id 关联留痕    |
| 不直连也不该直连业务 DB                   | 只通过中台暴露的受控工具 / API 访问，Dify 不直连业务数据库 |
| 无事务、幂等、补偿机制                     | 写操作的事务边界在中台，LLM 调用天然不具备 ACID        |
| 计量计费、配额分摊只是用量统计                 | 按部门 / 租户 / 项目的 token 计量、分摊、限额、告警    |
| 存量系统集成（ERP / OA / CRM / BPM）    | 中台统一收敛接口、鉴权、限流、熔断                   |
| 多渠道前端交付                         | Web / 小程序 / 企微 / iframe 由中台承载       |
| 知识资产的权属与更新流程                    | 入库审批、同步周期、过期下架是业务流程不是技术问题           |

**三条硬约束（写进架构规范）**：

1. 权限校验永远在中台侧执行，不把数据过滤责任交给 Prompt。
2. Dify 不直连业务数据库，只通过中台工具网关访问。
3. 工作流内不写复杂业务逻辑，只做路由、拼装、调用与格式化。

<a id="六"></a>

## 六、已识别风险与应对

| 风险                    | 应对                                |
| --------------------- | --------------------------------- |
| Dify 版本升级导致二开失效       | 锁定版本、升级前独立环境回归、二开优先插件 / MCP 而非改核心 |
| 社区版权限 / 审计不足影响合规      | 由中台补全 RBAC 与审计，生产前完成差距清单闭环        |
| 复杂工作流可读性下降            | 单工作流节点数设上限、子工作流复用、强制注释与模板化        |
| Workflow 不支持循环、切分策略有限 | 迭代逻辑交由 Agent 或中台调度；高级切分在外部的预处理层完成 |
| 并发与长链路延迟              | 流式输出、异步任务化、高频问答缓存、向量库独立扩容         |
| 工具调用的越权 / 误操作         | 工具网关统一鉴权、只读优先、写操作加人工确认节点          |
| 事实上的供应商锁定             | 所有 AI 能力经中台网关抽象，保留"换编排引擎"的退出路径    |

<a id="七"></a>

## 七、一句话给评审

> 我们不造大模型的轮子，也不把业务交给开源平台。Dify 解决"AI 怎么做得快、怎么调得好"，自研业务平台解决"AI 怎么接得稳、怎么管得住"。前者省下半年的基建时间，后者保住长期的可控与合规。两者的边界用 API 划清，未来无论换模型还是换编排引擎，业务都不受影响。

## 八、如果把它变成正式报告，还缺三样东西

1. **评分表**：把第二节维度量化打分（建议 5 人背靠背打分后取中位数，避免一个人拍板）。
2. **架构图**：画出"前端 → 中台（鉴权 / 上下文 / 工具网关 / 审计 / 计量）→ Dify → 模型 & 向量库"的调用链与故障域。
3. **POC 验证用例**：挑 3 个真实场景 + 1 个失败场景（低置信度 / 超时 / 越权请求），用 Dify 和备选各跑一遍，用召回率、首字延迟、人工干预率、人日投入四个指标说话。

> 补充具体的业务场景、数据敏感等级、团队人力、上线时间表，即可把这份复盘直接填成带评分表和架构图的正式版选型报告。
