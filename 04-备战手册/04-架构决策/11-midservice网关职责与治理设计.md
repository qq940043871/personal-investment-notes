# midservice 网关职责与治理设计 — 契约 · 校验 · 防护 · 可观测

> **文档定位**：把"中间件网关到底管什么"从口口相传的口径，沉淀为**可评审、可落地、可追责**的设计文档。回答六个历史项目的欠账问题：① 接口（协议）唯一编码与入参契约；② 压力参数强制校验；③ 请求参数格式预校验；④ 恶意攻击与高频调用账号的限流/黑名单；⑤ 等保测评要求的拦截与校验（含文件上传）；⑥ 响应侧敏感字段脱敏。外加 **midmon** 在**多实例** midservice 下的两个看家本事：慢协议预警、接口调用量与调用耗时统计。
>
> **一句话总纲**：网关只做**与业务无关的、横切的、可配置的**事——凡是需要领域知识才能判断的，一律下沉到业务层。
>
> **口径统一（重要）**：本平台历史上把"接口"称作**协议**（协议号 / 协议授权 / 协议权限级别 / 协议缓存）。本文统一表述为「**接口（协议）**」，即"协议号 = 接口唯一编码"。凡早期材料里出现"协议"维度的地方，与本文的接口编码是同一回事，不要再当成两套东西讲。
>
> **素材来源**：本文由三处既有资产收敛而来——`../05-技术管理/01-技术整改十一项与落地.html` 第 2/5/6/7/8 项（授权码 / DS+MID / 等保信创 / 统一开放网关 / 数据脱敏）、`04-架构决策/生产问题排查/11-网关扩容打穿DB-性能开发规范.md`（限流与容量数值）、`02-项目底稿/b2b-project/middleware-gateway.html`（早期协议网关的功能清单，**该文件用的是通用网关示例代码、非本平台真实实现，口径以本文为准**）。

## 1. 网关在架构中的位置与两个组件

### 1.1 位置

```
① 接入与网关层   ← 本文范围
   三端接入：外部大屏 / 普通客户（PC+移动）/ 机构客户
   midservice × N 多实例（统一入口 · 契约校验 · 身份与授权 · 限流与防护 · 响应治理）
   midmon（监控 · 预警 · 链路追踪 —— 同套技术栈，是网关的一部分，不是独立产品）
        │  HTTP + traceId 透传
        ▼
② Java 业务中台（12+ 微服务）
        │  Hessian over HTTP / Kafka
        ▼
③ DS 数据中心（异构防腐层，协议转换的关键节点）
        ▼
④ C 撮合引擎（单线程内存撮合）
```

### 1.2 两个组件的分工（一句话分清）

| 组件 | 定位 | 职责 | 不在它范围内的 |
|------|------|------|--------------|
| **midservice** | 流量治理**执行者** | 身份、契约、校验、授权、限流、防护、缓存、转发、响应治理 | 不碰业务规则、不做事务编排 |
| **midmon** | 流量治理**观察者** | 指标采集、慢协议预警、调用量与耗时统计、链路追踪聚合、看板告警 | **不参与**请求放行决策（预警→熔断的**动作**由 midservice 执行） |

> **设计纪律**：观察者与执行者分离。midmon 只负责"发现并报告"，它发现异常后**通过配置下发**让 midservice 去执行限流/熔断，而不是自己写在请求链路里。好处是监控挂了不影响交易，且限流策略始终只有一个执行点。

### 1.3 为什么自研

| 维度 | 说明 |
|------|------|
| 业务背景 | 平台有 **3 类租户**（外部大屏只读 / 普通客户 / 机构客户），并发等级、鉴权口径、限流配额差异极大 |
| 通用方案的错配 | 通用网关要么太重（插件多但二次开发难），要么太轻（L7 能力弱），难匹配"**租户级分级路由 + 分级配额**" |
| 自研收益 | 租户维度路由（数据隔离域）+ 多级限流（机构客户配额远高于普通）+ 灰度发布与流量染色；一次请求路由效率高于通用网关 |
| 表述纪律 | 自家入口一律说「**Java Web 自研 midservice**」；**不要把 Nginx / Spring Cloud Gateway / Kong 讲成自家组件**——面试官会拿架构图核对。通用网关只作为"为什么没选它们"的对比出现 |

## 2. 职责全景：请求从进门到出门的十道关

### 2.1 处理链路

```
请求进入
   │
   ├─ ① 接入与身份        ── 身份是谁？（认证：会话 / Token / AppKey 签名）
   │
   ├─ ② 契约校验          ── 这个接口存在吗？入参在契约里定义过吗？     ← 需求点 1
   │
   ├─ ③ 参数预校验        ── 参数"形状"对不对？（类型/长度/格式/枚举）  ← 需求点 3
   │
   ├─ ④ 压力参数强制校验  ── 会不会把后端打疼？（分页/时间跨度/批量）   ← 需求点 2
   │
   ├─ ⑤ 授权              ── 这个人/这个应用，有没有权力调这个接口？
   │                          （角色权限 + 协议授权 + 登录级别 + 能力授权码）
   │
   ├─ ⑥ 频率与信誉        ── 是不是恶意/高频？（限流 + 黑名单）         ← 需求点 4
   │
   ├─ ⑦ 合规与安全        ── 等保要求拦住了吗？（防重放/签名/越权/上传）← 需求点 5
   │
   ├─ ⑧ 协议缓存          ── 能不能不打扰后端？（命中即返回）
   │
   ├─ ⑨ 转发              ── 超时/熔断/隔离/租户路由（数值见 生产问题排查/11）
   │
   └─ ⑩ 响应治理          ── 脱敏 / 统一信封 / 审计留痕                  ← 需求点 6
                                    全程由 midmon 采集指标           ← midmon 部分
```

### 2.2 闸门排序原则（本设计的核心思想）

> **拒绝要早、要便宜。** 闸门顺序按「拦截成本」从低到高排：

| 位置 | 拦截成本 | 典型拒绝动作 |
|:---:|---------|------------|
| ②③④ | **本地内存**（契约注册表在本地缓存，零 IO） | 直接拒，不产生任何下游开销 |
| ⑤⑥ | **本地计数 + 一次缓存读** | 直接拒，不产生业务开销 |
| ⑦ | **一次签名/时间戳计算** | 直接拒 |
| ⑧ | **一次缓存读** | 命中直接返回，**完全不打后端** |
| ⑨ | **一次网络调用** | 最贵——所以前面的关必须把脏流量榨干 |

**收益**：一个扫描器狂扫不存在的接口编码，在 ② 就被拒（连鉴权都不用做），一次请求的代价是"查一次本地 Map"。这就是"早拒绝"的价值：**把攻击和误用的成本压到最低，把资源留给真实业务请求**。

> ⚠️ **反面清单（早期实现里的糊涂账）**：把参数校验、压力参数限制、脱敏全放到业务服务里各写一遍 → 规则不一致（同一个字段三个服务三种校验）、新增接口必漏、改一处要改 N 处。网关的意义就是**一处定义、处处生效**。

## 3. 接口（协议）唯一编码与入参契约 —— 需求点 1

### 3.1 要解决的历史问题

| 历史状态 | 造成的后果 |
|---------|-----------|
| 接口靠 URL 约定，无统一编号 | 网关无法识别"这是不是一个合法接口"；新增/改名随意，监控维度对不上、日志对不上、限流配额挂不上 |
| 入参靠各服务自己 `if` 判断 | 同一个字段三个服务三种校验规则；多余字段被静默接收（**参数注入 / 越权赋值**风险） |
| 接口文档与实现漂移 | 联调扯皮，第三方对接每家一个"项目" |

### 3.2 编码规则：分段编址

与 `../05-技术管理/01` 第 7 项的**统一错误码字典**同构（同一种"分段编址"方法论，学会一个会两个）：

```
接口编码 =  SVC 段 - MOD 段 - IF 段 @ 版本

  SVC  服务/系统段（3 位字母）   例：TRD 交易、CON 合同、FIN 资金、WRH 仓储
  MOD  模块段（3 位字母）        例：ORD 下单、QTE 报价、STL 结算
  IF   接口段（4 位数字，服务内唯一）
  VER  版本（v1/v2...，破坏性变更才升版本）

示例：TRD-ORD-0001@v1   交易服务 · 下单模块 · 第 1 号接口 · 版本 1
```

**规则清单**：

| # | 规则 |
|:-:|------|
| 1 | 一个接口**一生只有一个编码**，编码不复用（接口下线后编码永久保留，禁止回收给新接口） |
| 2 | 编码由**网关侧的契约注册表**统一发放，业务服务无权自定义 |
| 3 | 兼容性变更（加可选字段）**不升版本**；破坏性变更（删字段/改语义/改类型）**必须升版本**，新旧版本并行一段时间 |
| 4 | 错误码同样分段编址（`系统段-模块段-错误段`），与 `08` 第 7 项一致 |
| 5 | 灰度/下线以**编码**为单位操作，不按 URL 模糊匹配 |

### 3.3 契约注册表：一处定义、四处生效

**契约注册表的字段清单**（这是"每个接口都有唯一编码，并定义入参"的落地形式）：

| 分组 | 字段 | 说明 |
|------|------|------|
| 标识 | 接口编码 / 接口名称 / 版本 / 状态（草稿·生效·灰度·下线） | 状态机管控，未生效的编码一律拒绝 |
| 路由 | 所属服务 / 目标实例组 / HTTP 方法 / 路径 | 白名单式收口，路径不在表内 = 不存在 |
| **入参** | 字段名 / 类型 / 必填 / 长度 / 取值范围 / 正则 / 枚举 / **是否压力参数** | 契约的核心，见 3.4 |
| 授权 | 权限点 / 所属授权码能力 / 允许的登录级别 / 协议授权范围 | 供第 ⑤ 关使用 |
| 流量 | 限流配额档位 / 是否允许突发 / 是否可缓存（TTL） | 供第 ⑥⑧ 关使用 |
| 输出 | **输出字段白名单** / 脱敏字段与策略 | 供第 ⑩ 关使用 |
| 治理 | 责任人 / 最近变更时间 / 容量申报（预估 QPS·RT 预算） | 与 `生产问题排查/11` §8.2 的"容量申报制"衔接 |

**"四处生效"是什么意思**：

```
        一份契约（注册表）
   ┌──────────┬──────────┬──────────┬──────────┐
   ▼          ▼          ▼          ▼
 校验规则    接口文档    监控维度    限流/脱敏配置
（第③④关）  （对外可见） （midmon） （第⑥⑩关）
```

> 契约不是"文档"，是**配置源**。改契约 = 同时改了校验、文档、监控、限流四件事——这就是"把不变收敛到底座、把变化交给配置"的具体形态。

### 3.4 入参白名单制（关键设计决策）

| 决策 | 规则 | 理由 |
|------|------|------|
| **未定义字段的处理** | **拒绝**（返回参数校验失败），**不是忽略也不是透传** | 忽略 = 埋雷（前端改了字段名没人知道）；透传 = 参数注入风险（攻击者塞 `isAdmin=true`、`tenantId=别家`） |
| **类型严格** | 声明 `int` 就不能收 `"123"`（字符串）| 松类型是越权与 SQL 注入的温床（`"1 or 1=1"` 这类） |
| **必填必须有** | 契约声明必填但没传 → 拒 | 避免业务层空指针兜底满天飞 |
| **长度必须有上限** | 每个字符串字段都要有 maxLength | 没有上限 = 攻击者塞 10MB 字符串打内存 |
| **枚举必须封闭** | 状态、类型类字段用枚举白名单，不做"其他" | 防异常值进入状态机 |

> **这一条是整套设计的地基**：因为"中间件只接收定义过的入参"，网关才敢在 ③④ 关做**无副作用**的本地校验，也才敢在 ⑩ 关做"只输出契约声明字段"的输出白名单。入参与输出白名单**对称**——两侧都靠契约兜住，中间的业务代码就不必反复自证清白。

### 3.5 契约的生命周期

```
提出（业务/前端） → 注册（网关侧发放编码） → 评审（安全 + 性能双签） → 发布（生效）
                                                                      ↓
   下线归档 ← 观察期（零调用 90 天） ← 灰度 ← 变更（兼容性判断 → 是否升版本）
```

**变更影响面判定（决策树）**：

| 变更类型 | 是否升版本 | 是否需评审 | 备注 |
|---------|:---------:|:---------:|------|
| 新增可选入参 | 否 | 否 | 契约登记即可 |
| 新增必填入参 | **是** | 是 | 对存量调用方是破坏性变更 |
| 收紧取值范围/长度 | **是** | 是 | 会对存量合法流量产生 400 |
| 放宽取值范围/长度 | 否 | **是** | 放宽可能带入压力参数，必须过性能评审 |
| 删除字段 / 改语义 / 改类型 | **是** | 是 | 新旧并行，给调用方迁移窗口 |
| 调整限流配额 | 否 | 是 | 见 `生产问题排查/11` 容量红线 |

## 4. 请求参数格式预校验 —— 需求点 3

### 4.1 校验矩阵（网关侧只校验"形状"）

| 校验项 | 规则 | 失败动作 |
|-------|------|---------|
| 必填 | 契约声明必填项缺失 | 拒（参数校验失败） |
| 类型 | 与契约声明一致，不做隐式转换 | 拒 |
| 长度 | 不超过契约 maxLength，空字符串按"未传"处理 | 拒 |
| 取值范围 | 数值上下界、日期范围、金额精度 | 拒 |
| 正则/格式 | 手机号、邮箱、统一社会信用代码、身份证、日期时间格式 | 拒 |
| 枚举 | 落在封闭白名单内 | 拒 |
| 集合大小 | 数组/列表元素个数 ≤ 契约声明 | 拒（**压力参数，见第 5 节**） |
| 编码 | 统一 UTF-8；非法字符（未转义控制字符）拒绝 | 拒 |
| 危险字符 | SQL 关键字与引号、脚本片段、路径穿越片段（`../`、`..%2f`） | 拒 + **计入信誉分（第 6 节）** |

### 4.2 网关与业务的校验分界线（必须划清，否则两边都写、都不清）

| 维度 | 网关管（形状） | 业务层管（含义） |
|------|--------------|----------------|
| 举例 | `orderQty` 是不是正整数、在 1~100000 之间 | `orderQty` 是否超过库存、是否超过授信额度 |
| 举例 | `settleDate` 格式是不是 `yyyy-MM-dd`、是否在合理区间 | `settleDate` 是否符合本客户的交收模板规则 |
| 举例 | `customerId` 是不是合法 ID 格式 | `customerId` 是不是**你**（会话所属租户）的客户 |
| 判据 | 不需要查任何业务数据就能判定 | 必须查业务数据 / 领域规则才能判定 |

> **铁律**：网关不做业务判断（不查库存、不查授信、不判状态机）。一旦网关开始"懂业务"，它就从"横切底座"退化成"第二个业务系统"——耦合、难改、还容易被业务需求绑架。

### 4.3 越权防护（格式校验之外最容易漏的一类）

| 检查项 | 规则 |
|-------|------|
| **请求里的身份字段不可信** | 请求体/URL 里带的 `tenantId` / `customerId` / `userId` **一律不作为鉴权依据**；正确做法是从会话上下文取，并与请求值**比对**，不一致即拒 |
| 水平越权 | A 客户改 URL 参数查 B 客户的合同 → 网关侧"会话租户 ≠ 请求租户"直接拒（这是等保与渗透测试的必测项） |
| 垂直越权 | 普通角色调管理接口 → 第 ⑤ 关的权限点判定 |
| 数据隔离域 | 三端接入按租户路由到独立数据隔离域，路由参数由会话决定，不由请求决定 |

> 这条与需求点 5（等保）强相关，本质是等保"访问控制"要求的网关侧落点，放在这里是因为它常被"参数校验"顺带实现——顺带实现 = 一定漏。

## 5. 压力参数强制校验 —— 需求点 2

### 5.1 压力参数清单（这些参数不改 DB 就必须拦住）

| 参数类型 | 典型字段 | 默认上限 | 超限动作 |
|---------|---------|:-------:|---------|
| 分页条数 | `pageSize` | **100** | 拒（400 + 明确提示"单页最大 100"） |
| 页码 | `pageNum` | 合理上界（如 1000） | 拒（防深分页拖垮 DB） |
| 时间跨度 | `startTime/endTime` | 默认 ≤ 31 天 | 拒（防一次扫一年数据） |
| 导出条数 | `exportLimit` | 默认 ≤ 5000（异步导出另通道） | 拒或降级为异步任务 |
| 批量提交 | `batchSize`（批量下单/批量审核） | 默认 ≤ 200 | 拒 |
| 数组/IN 元素数 | 列表型入参 | 默认 ≤ 100 | 拒 |
| 模糊查询关键词 | `keyword` | 长度 ≤ 50，禁前导通配 | 拒 |
| 排序字段 | `sortField` | **白名单**（契约声明可选列） | 拒（防按未索引列排序） |
| 树深度 / 递归层数 | 组织树、类目树 | 默认 ≤ 5 | 拒 |
| 文件大小 | 上传 | 见 7.2 | 拒 |
| 多值拼接串 | 逗号分隔 ID 串 | 元素数 ≤ 100 | 拒 |

### 5.2 两个关键设计决策

**决策一：默认拒绝，不做静默截断。**

| 方案 | 行为 | 评价 |
|------|------|------|
| ❌ 静默截断 | 传 `pageSize=10000`，网关偷偷改成 100 返回 | **危险**：调用方以为拿到了全量数据，实际缺 9900 条——数据静默丢失是最难查的一类事故 |
| ✅ 显式拒绝 | 返回明确错误码与提示 | 调用方立刻知道要改；数据不会悄悄少 |

> **例外**：仅对**已在契约里声明的"可截断"接口**允许截断，且响应中必须带标记（如 `truncated: true` + 实际条数），调用方必须感知到被截断。

**决策二：默认值 100，白名单上限 200 —— 两层不是重复，是纵深。**

对齐既有性能规范（`生产问题排查/11` §5.2）：

```
第一层（网关，默认闸门）： pageSize 默认上限 100 —— 面向所有调用方的统一红线
第二层（后端 SQL，最后红线）： 单次查询 ≤ 200 条、必须带 limit —— 面向所有路径的兜底
```

| 场景 | 网关闸门 100 | 后端红线 200 |
|------|-------------|-------------|
| 普通接口 | 直接按 100 拦 | 永不会触发（已被上游拦住） |
| 白名单接口（如财务对账、运维导出） | 提额到 200（**申请审批制**） | 刚好卡住 200 上限 |
| 内部调用绕过网关 | 拦不住 | **在这里被拦** |
| 业务代码自己拼 SQL 漏了 limit | 拦不住 | **在这里被拦** |

> **提额机制**：白名单接口需要「申报用途 + 预估 QPS + 预计返回行数」→ 性能评审 → 加入提额清单。**提额是有记录的例外，不是默认放宽**——否则三个月后所有人都"特批"成 10000，等于没有红线。

### 5.3 兜底原则

| 层 | 兜底动作 |
|----|---------|
| 网关 | 压力参数超限直接拒；未在契约声明的压力参数一律拒 |
| 业务层 | 对契约声明的字段做二次上限校验（防内部调用绕过网关） |
| DAO/SQL | `limit` 强制注入（保底截断）+ 慢 SQL 监控（`生产问题排查/11` §5.3） |

## 6. 限流与黑名单 —— 需求点 4

### 6.1 三级配额（不是一刀切）

| 配额维度 | 主体 | 说明 |
|---------|------|------|
| **租户级** | 机构客户 / 普通客户 / 外部大屏 | 与"三类租户"的既有口径对齐；机构客户配额远高于普通；外部大屏只读且配额最低 |
| **应用级** | 第三方 AppKey（见 `08` 第 7 项：应用注册制 + 配额分配） | 第三方滥用只影响自己那份配额，不殃及平台客户 |
| **接口级** | 慢接口单独配额 | 慢接口与快接口**不共享配额**（舱壁思想，对齐 `11` §4.4/§5.1） |

**接口级配额取值**：直接复用 `生产问题排查/11` 的容量推导结论（慢接口全局限流 200 QPS ÷ 5 实例 = 40 QPS/实例），本文不重复推导。

### 6.2 多实例下的计数一致性（自研网关的真实难点）

| 方案 | 说明 | 取舍 |
|------|------|------|
| 单机计数 | 各实例各算各的 | ❌ 5 实例等于配额 ×5，且用户重连落在不同实例就绕过了限制 |
| **集中式令牌桶** | 令牌存 Redis，全局共享 | ✅ 准确；代价是每请求一次 Redis 往返 |
| **分片令牌桶** | 按租户/接口哈希固定落某个实例领令牌 | ✅ 省 Redis 调用；代价是实例故障要重分片 |
| 本地 + 定期同步 | 本地计数、定期上报汇总校准 | ⚠️ 有窗口误差，适合"防突发"而非"精确计费" |

> **选择判据**：**限流要不要精确，取决于它保护什么**。保护 DB 的容量限流可以容忍误差（余量留够）；**计量计费**（接授权码/订阅计量）必须精确——所以计量口径走独立的高精度通道，不与限流计数复用。

### 6.3 触发源四类（不只是"QPS 太高"）

| 触发源 | 特征信号 | 说明 |
|-------|---------|------|
| ① 频率超限 | QPS 超租户/应用/接口配额 | 常规限流 |
| ② 高频错误 | 滑动窗口内 4xx/5xx 占比超阈值 | 通常是调用方 bug 或攻击试探 |
| ③ 扫描特征 | 大量"接口编码不存在"、参数校验连续失败、路径穿越尝试 | 攻击扫描器特征最明显的一类 |
| ④ 行为异常 | 同 IP 短时间切换多账号、同账号异地并发、请求时间间隔极度规律（脚本特征） | 撞库/爬虫/薅羊毛特征 |

### 6.4 处置阶梯（决策树：先轻后重，可回退）

```
发现异常行为
   │
   ├─ 轻（只观察）       → 记录 + 告警 + 计入信誉分         ← 不打断真实用户
   │
   ├─ 中（降速）         → 排队 / 降到最低配额档位           ← 保接口可用，削掉爆发
   │                        （对齐 11 §4.4：队列 100，≈2.5s 容忍）
   │
   ├─ 重（临时封禁）     → 429 + 临时封禁 15 分钟（自动解封） ← IP / 账号 / AppKey 维度
   │
   └─ 最重（黑名单）     → 长期封禁，**人工解封 + 申诉通道**   ← 需留痕，防误伤
```

| 处置 | 适用 | 解封方式 |
|------|------|---------|
| 告警 | 首次异常、低频异常 | 自动（无） |
| 限流（429） | 频率超限 | 自动（窗口滑过即恢复） |
| 临时封禁 | 扫描特征、高频错误 | **自动**（15 分钟）——避免因为一次误伤永久断客 |
| 黑名单 | 确认恶意、重复触发 | **人工**，必须留操作审计 |

### 6.5 误伤防护（不做这个，第一个投诉的就是真客户）

| 措施 | 说明 |
|------|------|
| 白名单 | 内部服务互调、健康检查拨测、监控探针、办公出口 IP 一律不参与自动封禁 |
| 灰度观察期 | 新阈值上线先只告警不拦截，跑满一个业务周期（含高峰期）再切换为拦截 |
| 双维度校验 | 封禁前要求**至少两个信号同时成立**（如"高频错误 + 扫描特征"），单信号只告警 |
| 客户感知 | 被限流时返回可读文案 + 错误码（"系统繁忙，请稍后重试"），不返 500 或空白 |
| 大客户保护 | 机构客户触发限流必须**同步通知值班**，避免静默降速影响交易 |

## 7. 等保测评的拦截与校验（含文件上传）—— 需求点 5

### 7.1 等保要求 → 网关侧动作对照表

等保体系本身（分区分域、双因子、审计留痕、传输存储加密、安全开发生命周期）见 `../05-技术管理/01` 第 6 项。本表只列**网关侧必须落地的拦截项**：

| 等保关注点 | 网关侧具体动作 | 判定形式 |
|-----------|-------------|---------|
| 身份鉴别 | 会话/Token 有效性、登录级别校验、敏感接口强制双因子 | 校验项清单 |
| 访问控制 | 权限点 + 协议授权 + 能力授权码（`08` 第 2 项） | 授权矩阵 |
| 入侵防范 | 时间戳 + nonce **防重放**（窗口 5 分钟）、签名校验**防篡改**、危险字符拦截 | 判定表 |
| 数据保密性 | 传输层强制加密、**响应脱敏**（第 8 节）、下载鉴权 | 策略表 |
| 数据完整性 | 请求签名、响应可选签名（关键报文） | 策略表 |
| 安全审计 | **全链路留痕**：谁 / 何时 / 从哪 / 调了什么编码 / 结果 / 耗时 → 不可篡改审计流 | 审计字段清单 |
| 剩余信息保护 | 网关日志不落明文敏感字段（与脱敏同一套规则） | 日志脱敏规则 |
| 漏洞利用防护 | 统一错误响应：**不返回堆栈 / 不暴露内部路径与服务名** | 错误信封规范 |

**请求签名与防重放判定表**：

| 检查 | 规则 | 失败动作 |
|------|------|---------|
| 时间戳窗口 | 与服务器时间偏差 ≤ 5 分钟 | 拒（防重放） |
| nonce 唯一 | 同 AppKey 下 nonce 不重复（窗口内去重） | 拒（防重放） |
| 签名 | 按约定字段序 + Secret 签名比对 | 拒（防篡改） |
| 幂等键 | 写类接口强制幂等键（`08` 第 7 项） | 拒或返回上次结果 |

### 7.2 文件上传专项（等保必查、实战最易翻车）

**上传校验判定表（逐项通过才放行）**：

| 序号 | 检查项 | 规则 | 不做的后果 |
|:---:|-------|------|-----------|
| 1 | 身份与授权 | 该角色是否有上传权限（不是所有登录用户都能传） | 越权上传 |
| 2 | 扩展名白名单 | 只放业务需要的类型（PDF / JPG / PNG / XLSX 等），**白名单不是黑名单** | 上传 `.jsp` / `.php` 直接拿服务器 |
| 3 | MIME 类型 | 与扩展名匹配 | 伪造类型绕过 |
| 4 | **魔数（文件头）校验** | 读取文件头字节与真实类型比对 | **改扩展名的图片木马**——只查扩展名一定被绕过 |
| 5 | 大小限制 | 合同/仓单扫描件类 ≤ 10MB，图片 ≤ 5MB；同时限**单次请求总量**与**单位时间总量** | 撑爆磁盘/内存（`生产问题排查/10` 就是这类事故的亲戚） |
| 6 | 文件名处理 | **重命名**（服务端生成唯一名），剥离路径分隔符与 `../` | 路径穿越覆盖服务器文件 |
| 7 | 隔离存储 | 先落**隔离区**，不落 Web 可访问目录；校验与扫描通过后才转入正式区 | 上传即可访问 = 免鉴权下载 |
| 8 | 内容扫描 | 病毒/恶意内容扫描（异步），未通过不进正式区 | 病毒分发 |
| 9 | 频率限制 | 单账号上传频率与总量配额（防被当免费图床/网盘） | 资源滥用 |
| 10 | **下载鉴权** | 下载走**一次性令牌 / 短时效签名 URL**，不可用可猜的自增文件 ID | 越权下载（遍历 ID 拿别人合同，等保/渗透必测项） |
| 11 | 图片处理 | 重新编码（剥离 EXIF 与嵌入脚本），而非原样转发 | 图片马、隐私信息泄露（拍摄地点等） |

> **边界**：网关管"**能不能进**"（身份、类型、大小、频率、隔离）；业务管"**进来之后是什么**"（业务归属、内容合规、与订单/仓单的关联）。别让网关去理解合同内容。

## 8. 响应侧治理：脱敏与统一信封 —— 需求点 6

### 8.1 两级脱敏（与 `08` 第 8 项的分工，不重复引擎设计）

| 级别 | 位置 | 职责 | 特点 |
|------|------|------|------|
| **精确脱敏** | 业务层（脱敏引擎 + 注解声明） | 按角色/场景决定脱敏粒度，需要业务上下文（这个人是不是风控） | 主战场 |
| **兜底脱敏** | **网关（本节）** | 按契约声明的敏感字段做**最后一道掩码**，防止业务层漏标、新字段漏加注解、老接口忘改 | 不需要业务上下文，纯配置驱动 |

> **为什么网关也要做一遍**：因为脱敏的失效模式是"**漏**"——漏一个字段就是一次事故。网关这层用**契约 + 字段清单**做机械校验，与业务层基于业务上下文判断形成互补：业务层管"该不该给"，网关管"绝不裸奔"。

### 8.2 字段清单与策略

| 字段类别 | 示例 | 默认策略 |
|---------|------|---------|
| 身份证 / 统一社会信用代码 | — | 掩码（保留首尾，`1101**********1234`） |
| 银行账号 | — | 掩码（保留后 4 位） |
| 手机号 | — | 掩码（`138****5678`） |
| 邮箱 | — | 掩码（保留域名） |
| 法人 / 联系人姓名 | — | 掩码（姓 + `*`） |
| 客户名称 | — | 按调用方角色：内部运营可见、对外接口掩码（口径：**面试不报名单**，接口侧同样脱敏） |
| 合同金额 / 结算流水 | — | 按角色：财务/风控可见明文（**留痕审计**），其他角色区间化或掩码 |
| 地址 / 坐标 | — | 掩码到城市级 |

**规则**：

| # | 规则 |
|:-:|------|
| 1 | 明文查看权限 = 角色 × 接口 × 场景三维判定，且**明文查看全程留痕**（谁 / 何时 / 看了哪条）——与 `08` 第 8 项的"接口脱敏"一致 |
| 2 | 日志与审计流**同一套脱敏规则**（杜绝"日志即泄露源"） |
| 3 | 错误响应绝不带敏感字段、不带堆栈、不带内部服务名与路径 |

### 8.3 统一信封 + 输出白名单

**响应信封**（与 `08` 第 7 项一致）：`code / message / data / timestamp / traceId`

**输出白名单（本设计强调的进阶做法）**：

| 做法 | 说明 |
|------|------|
| 常规做法 | 过滤已知敏感字段 → 新字段默认输出 → **新字段泄露**（脱敏永远在追着新字段跑） |
| **白名单做法** | **只输出契约声明过的输出字段**，未声明的字段不输出 → 新字段默认不暴露 → 泄露面从"随开发数量增长"变成"随契约评审数量增长" |

> 这与第 3.4 节的**入参白名单对称**：入口只认定义过的，出口只给定义过的。两侧都封死，中间的链路就干净了。

## 9. midmon：多实例网关的可观测与预警

### 9.1 定位与数据来源

**midmon 是网关的一部分**（同套技术栈），不是独立产品。三个数据来源：

| 来源 | 内容 | 用途 |
|------|------|------|
| 访问日志（结构化） | 接口编码 / 租户 / 应用 / 实例 / RT / 结果码 / traceId | 明细查询、审计、Top-N 统计 |
| 指标聚合 | 按接口编码 × 实例 × 时间窗口的计数与分位值 | 看板、预警 |
| 链路追踪 | traceId 串起 **midservice → 业务服务 → DS 桥接 → C 撮合** | 定位耗时到底花在哪一段 |

### 9.2 多实例带来的两个真问题（不讲清楚就是空谈）

| 问题 | 表现 | 处理 |
|------|------|------|
| **聚合口径** | 5 个实例各报各的，看单实例"很健康"，全局其实在抖 | 指标必须带**实例标签**，看板同时提供「实例视图」与「全局聚合视图」；预警只看全局 |
| **实例漂移** | 同一个慢接口，用户请求落在 A 实例慢、落在 B 实例正常（队头阻塞、GC、本机热点不均） | 预警必须带上**实例维度**——"接口 XX 在实例 3 上 P95 超标"才是可行动的告警；只说"接口 XX 慢"让人无从下手 |
| 时钟偏差 | 多机时间不同步导致窗口错位 | 统一 NTP；窗口以**服务端时间**归集 |
| 重连重复计数 | 长连接重连导致同一请求重复上报 | 以 traceId 去重 |

### 9.3 慢协议预警（需求点：响应慢的协议要预警）

| 要素 | 设计 | 理由 |
|------|------|------|
| **看哪个数** | **P95 / P99**，不看平均值 | 平均值骗人：9 个请求 10ms + 1 个请求 10s，平均 1s，看着"还行"，实际每 10 个用户就有 1 个在骂娘 |
| **什么算慢** | 单请求 RT 超阈值（对齐 `11` §4.2：慢调用判据 RT > 500ms） | 与熔断判据用同一套阈值，预警与动作口径一致 |
| **什么时候报** | **比例 + 持续性**双条件：滑动窗口（1 分钟）内慢请求占比 ≥ 10%，且**连续 3 个窗口**成立 | 单点抖动不报警（否则天天狼来了）；持续劣化才报 |
| **报给谁、报什么** | 必须落到四元组：**接口编码 + 实例 + 租户 + 下游服务** | "网关慢"不是告警是废话；"TRD-ORD-0001 在实例 3、机构客户租户、下游合同服务段 P95 1.2s"才可行动 |
| **分级** | 🟡观察（只记录）/ 🟠预警（通知值班 + 看板高亮）/ 🔴熔断（联动 `11` 的熔断动作，慢调用比例 ≥ 50% 触发） | 先观察后动作，与 6.5 的灰度观察期一致 |
| **对比基线** | 同比上周同日同时段 + 环比前一窗口 | 绝对阈值会被"业务本来就慢"骗过；**相对劣化才是信号** |
| **趋势** | 同一接口编码的 P95 周环比曲线 | 缓慢劣化（每周 +3%）比某天突然 +100% 更难发现，也更致命 |

**慢协议预警判定树**：

```
接口 RT 超阈值？
   ├─ 否 → 不报（但计入调用量与耗时统计）
   └─ 是 → 该请求计入"慢请求"
            ↓
        滑动窗口（1min）慢请求占比 ≥ 10%？
           ├─ 否 → 🟡观察（记录，不通知）
           └─ 是 → 连续 3 个窗口成立？
                    ├─ 否 → 🟡观察（等待持续性验证）
                    └─ 是 → 定位维度（实例 / 租户 / 下游段）
                             ↓
                          🟠预警 + 通知（带四元组）
                             ↓
                         慢调用比例 ≥ 50%（10s 窗口 / 20 请求）？
                             ├─ 否 → 继续观察，看是否自愈
                             └─ 是 → 🔴熔断降级（midservice 执行，5s 后半开探针）
```

### 9.4 调用量与耗时统计（需求点：哪些接口调用多、调用时长）

**统计维度与指标**：

| 维度 | 用途 |
|------|------|
| **接口编码** | Top-N 排行、容量规划、下线决策 |
| **租户 / 客户** | 配额校准、客户用量报告、异常客户发现 |
| **应用（AppKey）** | 第三方治理、计量计费（接授权码 `08` 第 2 项） |
| **实例** | 负载均衡是否均匀、单实例劣化 |
| **下游服务** | 定位耗时归属（是网关慢、还是后端慢、还是 DS 段慢） |
| **时间窗口** | 分钟 / 小时 / 日 / 峰谷对比 |

**指标清单**：调用次数 · 总耗时 · 平均耗时 · **P95 / P99** · 错误率 · 限流次数 · 慢请求次数 · 参数校验失败次数 · 缓存命中率。

**四类用途（统计不是收集数据，是为了做决定）**：

| 用途 | 具体动作 |
|------|---------|
| **容量规划** | Top-N 高频接口优先加缓存/优化；高频高耗时的进"优先治理清单" |
| **限流阈值校准** | 先观察实测分布 → 再定阈值（而不是拍脑袋）；上线后按命中与误伤持续校准（对齐 `11` §10.2） |
| **接口下线决策** | 连续 90 天零调用的接口编码 → 下线候选清单（契约生命周期的一部分） |
| **计量与对账** | 调用量作为订阅计量与第三方结算的数据源（**精确计量走独立通道**，见 6.2） |

### 9.5 看板与告警清单

| 看板 | 核心指标 | 阈值/触发 |
|------|---------|----------|
| 全局大盘 | QPS、错误率、P95、限流次数 | P95 超基线 30% 告警 |
| 慢协议榜 | 按接口编码 P95 排序（带同比） | 同 9.3 判定树 |
| 调用量榜 | Top-N 接口/租户/应用 | 无（观察为主） |
| 限流与封禁 | 触发次数、涉及租户、误伤申诉数 | 误伤数 > 0 即复盘 |
| 契约健康度 | 参数校验失败率、非法编码请求数、未声明字段请求数 | 失败率突增 → 前端/调用方变更未同步 |
| 容量水位 | 线程池水位、连接池等待数、缓存命中率 | 对齐 `11` §8.2 第 8 条 |

## 10. 边界：网关**不该**做什么

| ❌ 不做 | 为什么 | 该谁做 |
|--------|-------|-------|
| 业务规则校验（库存/授信/状态机/风控规则） | 需要领域知识，放网关 = 网关变第二个业务系统，且业务一变就要动网关 | 业务服务 / 规则引擎 |
| 跨服务事务编排 | 网关无状态、无补偿能力，编排需要持久化状态与补偿链路 | `04-架构决策/05-Saga编排器详细介绍.md` |
| 重计算与复杂聚合 | 会占用转发线程，拖垮吞吐（网关慢会放大成全局慢） | 业务服务 / 离线任务 |
| 数据持久化（业务数据） | 网关是横切通道，不是数据归属方 | 业务服务 |
| 复杂权限逻辑（如"这个客户在这个品种上的额度"） | 属领域规则 | 业务服务 |
| **允许** | 审计日志、限流计数、契约注册表配置 | —— |

> **一条判据记一辈子**：**网关只做与业务无关的、横切的、可配置的事。** 任何需要问"这个客户是谁、这笔业务合不合法"才能做的判断，都不属于网关。

## 11. 落地路线（按"止血收益 ÷ 改造成本"排序）

| 阶段 | 事项 | 收益 | 说明 |
|------|------|------|------|
| **P0（先收口）** | ① 接口编码规则发布 + 契约注册表建表 | 让后面所有能力有挂载点 | 没有编码，限流/监控/授权都无处挂 |
| | ② **压力参数强制校验**（分页 100 等） | **直接止血**：防一次查询拖垮 DB | 与 `11` 已有防线形成纵深 |
| | ③ 统一响应信封 + 错误码字典 | 联调与排障成本立刻下降 | 与 `08` 第 7 项同源 |
| **P1（补防线）** | ④ 参数格式预校验 + 入参白名单（未定义字段拒绝） | 拦掉脏流量与参数注入 | 契约有了才敢做 |
| | ⑤ 分级限流 + 黑名单处置阶梯 | 恶意/高频流量隔离 | 复用 `11` 的配额推导 |
| | ⑥ 响应兜底脱敏 + 输出白名单 | 堵住"漏字段"这一类事故 | 与 `08` 第 8 项互补 |
| | ⑦ midmon 慢协议预警 + 调用量/耗时统计 | **可观测先于优化**：不测量就不知道优化什么 | 多实例聚合口径必须先定 |
| **P2（合规与精细化）** | ⑧ 等保专项：防重放 / 签名 / 审计留痕 / 越权防护 | 投标硬门槛（与 `08` 第 6 项衔接） | 与测评节奏对齐 |
| | ⑨ 文件上传十一项校验 + 下载鉴权 | 等保与渗透必查项 | 见 7.2 |
| | ⑩ 契约即输出白名单、契约健康度看板 | 从"防漏"升级为"默认不暴露" | 体系成熟后的自然演进 |

> **顺序理由**：先有**编码与契约**（挂载点），再有**校验与限流**（防线），再有**可观测**（用数据校准阈值），最后做**合规精细化**。反过来做（先上等保专项、没有契约）会导致每个安全规则都要在代码里硬编码，改一次动一片。
