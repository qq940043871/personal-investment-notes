## 一、为什么这个产品的技术管理不一样

通用系统里，技术经理主要管"交付速度、质量、稳定"；在 B2B 现货贸易这个产品上，技术管理被四个**结构性特征**顶到了更难的位置。这四条是本产品技术管理区别于其他系统的根，后面每个管理动作都能回溯到其中一条。

| # | 结构性特征 | 由此产生的管理难题 |
|---|---|---|
| ① | **异构栈**：C 撮合引擎 + Java 微服务中台 + Vue 前端，三拨不同技能的人 | 团队不能靠"统一技术栈"管，得靠**契约与边界**管 |
| ② | **资金是心脏**：单笔百万级，资金差错 = 公司生死 | 首要 KPI 不是交付速度，而是**资金零差错** |
| ③ | **多租户非标**：每个客户的交易规则、审批流、单据模板都不同 | 核心矛盾是"**定制需求** vs **交付质量与速度**" |
| ④ | **跨月长事务**：一笔交易从合同到结算可跨月、跨服务 | 评审与测试要覆盖**跨越数月的状态流转**，不是 happy path |

> **一句话收口**：这个产品里，技术管理的动作跟着产品的四个"非标"走——**栈非标**靠契约治理、**钱非标**靠管控闭环、**客户非标**靠配置化、**时间非标**靠状态机评审。

## 二、四个产品特有难点 × 对应管理动作

每个难点按「难在哪 → 我怎么管 → 证据 / 口径」三段呈现。

### 难点一：异构团队协同（C 撮合 + Java 中台 + Vue 前端）

**难在哪**：C 撮合团队、Java 团队、Vue 团队是三种技能栈、三套语言，互相读不懂对方代码；C 工程师在撮合领域稀缺难招；两套系统之间唯一的"语言"是接口协议。管理上稍一松懈，就是"C 改一个字段、Java 全崩"的边界事故。

**我怎么管**：

- **组织站位**：20 人团队按 3 C / 6 Java / 5 Vue / 5 测试拆分，我作为 C 与 Java 之间的**技术接口人**，向上对齐目标、向下评审方案。
- **契约治理（核心抓手）**：协议 / 接口契约变更**必须双方评审 + 我拍板**；两侧通过 **DS 数据中心（Java 防腐层，Hessian + Socket）** 做协议转换，让 C 和 Java 各自独立演进、互不阻塞。C 黑盒的二进制协议在 DS 里翻译成 Java 能消费的数据，这是架构治理的抓手。
- **边界划分**：C 只管"快"（单线程内存撮合、确定性低延迟），Java 管"稳"（业务编排、事务、外部集成），Vue 管"好用"；把规则多变、延迟不敏感的部分留在 Java，把确定性、高性能、改动风险高的撮合核心留在 C。
- **协作机制**：每周技术对齐会同步 C 侧近况与桥接 SDK 状态；跨模块故障以桥接 SDK 日志为第一排查依据；C 逻辑变更走小流量灰度，不能灰度的核心尽量不动。
- **关键决策故事**：新人提出"用 Java 重写撮合引擎统一技术栈"，我**坚决否决**——撮合是资金链路心脏，GC 停顿不可接受，重写收益远小于一次可能长达数月的重写悬崖。

**证据 / 口径**：20 人（3/6/5/5）、DS 数据中心防腐层、9+ 外部接口、12+ 微服务；异构架构设计本体见 `../../02-现货贸易/03-架构决策/02`、桥接细节见 `../../02-现货贸易/03-架构决策/15`。

### 难点二：资金安全管控（资金是心脏）

**难在哪**：一笔交易几百万到上千万，任何资金差错都是合规事故乃至公司生死；资金链路跨服务、跨月，强一致与最终一致要在同一套系统里各归其位。管理上最难的是：**把"不出错"从个人自觉变成机制**。

**我怎么管**：

- **技术底线（评审必查）**：资金扣款 / 冻结用**数据库行锁 + 乐观锁**（不用 Redis 分布式锁）；资金操作的"扣款"与"发消息"用本地消息表（Outbox）保证原子；跨服务长事务走 **Saga + 状态机 + 事件溯源**，任意单据可回溯。
- **稳定性三线闭环**：目标层（重大故障 ≤1 次/年、中等 ≤3 次/年，均为**当时设定的考核线**）+ 机制层（上线评审 + 压测 + 监控告警 + On-call）+ 闭环层（故障报告 → 复盘 → 转成规范或自动化检查项）。
- **复盘纪律**：每次线上问题明确原因、责任人、改进措施、预防方案，**复盘的产出永远是"防再发"，不是事故报告**。

**证据 / 口径**：**3 年零资金差错**（项目总览口径）、银行 100% 存管、对账从 9 人天压到 2 小时；一致性设计权威见 `../../02-现货贸易/03-架构决策/12`、`../../02-现货贸易/03-架构决策/13`，Saga 见 `../../02-现货贸易/03-架构决策/05`。

### 难点三：多租户交付质量（非标定制）

**难在哪**：每个客户的交易规则、审批流、单据模板、行业名词都不同，早期靠"改代码 + 加开关"交付——参数组合爆炸、测试永远覆盖不全，新客户上线周期被拉长到数月，定制越积越多成为技术债。

**我怎么管**：

- **架构手段（治本）**：把定制从代码下沉到配置——能力集 + 套餐三层模型（参数不许直接挂客户）、功能授权码（一套代码按客户付费开 capability）、国际化词库（行业自定义名词改配置即时生效）。这条主线一句话概括：**把"每次定制都要改代码"变成"配置与契约"**。
- **流程手段（治标）**：六道评审闸门——需求收口 → 设计 → 技术 → QA 验收 → 发布 → 移交，**不通过不流转**，把需求不清、设计不足、测试遗漏的返工挡在开发之前。
- **落地载体**：我主导的**技术整改十一项**（国际化 / 授权码 / 交收三元组 / 统一支付 / DS+MID 网关 / 等保信创 / 开放网关 / 数据脱敏 / 统一基础模块 / 规范脚手架+AI / 缓存改革），逐项按「背景问题 → 方案 → 效果」呈现。

**证据 / 口径**：新客户上线周期 **2 个月 → 1 周**（项目总览口径）；十一项整改清单见本目录 `01-技术整改十一项与落地.html`，多租户架构权威见 `../../02-现货贸易/03-架构决策/03`。

---

### 难点四：跨月长事务评审（时间非标）

**难在哪**：一笔大宗交易从合同签署 → 备货 → 发运 → 验收 → 结算，可跨月、跨多个服务；传统事务覆盖不了，测试也很难把跨越数月的状态路径全测一遍。评审如果只看"主流程能跑通"，跨月的边角状态就会在线下暴雷。

**我怎么管**：

- **技术手段**：用**状态机**描述单据生命周期、**Saga** 编排跨服务补偿、**事件溯源**保留全量状态变迁历史——让"任意时刻的单据在哪一步、怎么走到这步"都可回答、可回溯。
- **评审重点（区别于普通评审）**：技术评审不只看 happy path，重点盯三件事——**状态机边界**（非法跃迁是否被拦）、**补偿完备性**（每个正向操作有没有对等补偿）、**幂等**（重试 / 重复投递会不会重复入账）。
- **测试策略**：按状态机路径做覆盖，重点补"跨月卡在某状态"这类长尾场景，而不是堆 happy path 用例。

**证据 / 口径**：**3 年零资金差错**、任意单据可回溯（项目总览口径）；状态机 + Saga + 事件溯源决策见 `../../02-现货贸易/b2b-project/overview.md` 决策 ③。

## 三、稳定性与故障管理的产品落点

- **高峰容量保障**：冬储（下游囤货季）是资金与交易的双高峰，连续两季**冬储零 P0、核心接口稳定在 200ms 内**（项目总览口径）；容量压测计划见 `../../02-现货贸易/b2b-project/midservice/全链路容量压测计划.md`。
- **排障与治乱**：生产问题按"四类场景地图 + 六步 SOP"走，方法总纲见 `../../02-现货贸易/03-架构决策/生产问题排查/12`，五篇排查实录（Cookie 认证 / 多线路 / 竞价变慢 / 进程消失 / 网关打穿 DB）各带 90 秒速答与追问预案。
- **闭环动作**：每次故障复盘落到"规范或自动化检查项"，重复问题不再靠人记。

## 四、口径红线（讲这个产品的技术管理必守）

1. **团队结构脱口而出**：20 人 = 3 C / 6 Java / 5 Vue / 5 测试，向总经理汇报；从业 13 年 = 前 2 年金融级清算 + 后 11 年本司。
2. **指标带限定语**：重大故障 ≤1 次/年、并发 ≥1000/秒等，一律讲"当时设定的团队目标 / 考核线"；"3 年零资金差错""2 个月 → 1 周"等实证结果，按项目总览口径引用。
3. **报类别名不报客户名**：客户与内部系统一律脱敏。
4. **技术栈不混**：平台 = Java 微服务 + C 撮合 + 自研 DS 桥接 + Vue3；FastAPI / Python 只作为个人 Agent Harness 储备，**绝不混入平台技术栈**。
