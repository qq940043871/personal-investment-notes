### 4.1 你面试中可能被问到的关于C核心的问题

| 面试官可能问 | 正确回答思路 |
|-------------|-------------|
| "你们的撮合系统怎么设计的？" | "我们采用C撮合引擎+Java桥接SDK的异构架构。C侧单线程内存撮合（O(logN)排序树），Java侧通过桥接SDK做协议封装、连接管理、熔断限流。C负责极致的撮合延迟确定性，Java负责灵活的业务编排。" |

| "Java和C怎么通信？" | "基于TCP Socket + 自定义二进制协议，Java侧封装了桥接SDK（连接池/超时/熔断/重试），C撮合结果是异步落库的。" |
| "你怎么管一个你不熟的C模块？" | "见下文BOUNDARY框架（同一主题的其他文档）——我用接口契约和技术尽调框架来管，不读C代码也能有效把控全局。" |

### 4.2 一段式话术（1分钟版本）

> "我们的B2B大宗交易平台采用异构架构：核心撮合引擎是C语言实现，单线程内存撮合，追求的是纳秒级的延迟确定性和GC零停顿；业务编排层是Java+Vue，负责订单管理、风控、结算、生态对接等灵活业务逻辑。两层之间通过TCP二进制协议+Java桥接SDK通信。
>
> 这个架构的选择很明确：撮合不能停顿，Java的微服务生态更适合业务编排。我的角色是守住中间这块——定义好撮合输入输出的协议契约、建设Java桥接SDK的可用性保障（熔断限流监控）、以及用可观测系统保证全链路透明。
>
> 作为Java出身的技术经理，我不会写C代码，但我能通过桥接SDK的日志和指标判断撮合系统是否在健康工作。这就像飞行员不需要会修发动机，但必须知道仪表盘的每一个数值代表什么。"

## 二、Socket 长连接接入——面试话术（2分钟版）（原 02 Socket 篇 §七）

> "我们的缓存服务是 Java 调度服务连 Redis 集群，接入异构系统的 Socket 长连接时，我的设计分三层：
>
> **传输层**做可靠投递——每条消息带唯一 msgId，接收方先落地再回 ACK，超时用指数退避重发，重复消息用 Redis 的 SETNX 去重。这样保证不丢不重。
>
> **连接层**做断线自愈——Netty 的 IdleStateHandler 做双向心跳，断线后指数退避加随机抖动重连，避免惊群；重连后从 Redis 里存的 offset 断点续传，未确认的消息重发。
>
> **一致性**上我不追求强一致，走最终一致——ACK 加幂等解决 99.9%，再加定时对账和日终全量对账兜底剩下的 0.1%。异构系统之间强一致代价太高，最终一致加对账才是务实的选择。
>
> 高可用方面，Redis 集群本身有主从切换，异构对端挂了就熔断降级、消息暂存待发队列、恢复后回放。整个服务无状态化，状态都存 Redis，所以可以多实例水平扩展。
>
> 关键是可观测性——连接数、消息积压、去重命中率、P99 延迟都要监控，否则故障了都发现不了。"

### 第一部分：30秒电梯版 —— "你们系统长什么样？"

> "我们的 B2B 大宗交易平台是一个**四层异构架构**：最上层是三端接入（外部大屏、普通客户、机构客户），通过网关层（midservice 多实例）做负载均衡和路由；中间是业务中台，以**DS 数据中心和交易核心为双核驱动**，周围环绕 12 个以上业务微服务（认证、用户、账本、合同、资金、运力、创新挂牌、自由竞价等）；底层是 MySQL 双实例加 MinIO 对象存储；右侧对接了银行、物流、CTRM、企查查、供应链金融等 9 个以上外部系统。
>
> 我主要负责业务中台的管理系统和业务服务集群这块，同时负责跨模块协调和技术治理。"

**关键词锚定**：四层 / 双核驱动(DS+交易) / 三端 / 9+外部接口 / 12+微服务。

### 第二部分：2分钟架构版 —— "详细讲讲你的技术架构"

#### 2.1 分层展开（建议配合白板画图）

##### 第一层：接入层（多端适配）

> "我们有三类终端：**外部大屏**用于实时行情展示和运营监控，**普通客户端**面向中小企业的采购销售操作，**机构客户端**面向大客户，提供更深度的数据分析和管理功能。每类都覆盖 PC 和移动端。"

**追问应对：为什么分三类？**
> "因为 B2B 客户差异极大——中小企业关注'怎么快速下单'，大机构关注'怎么管资金风险和数据决策'。不同角色用不同界面，避免一个系统塞太多功能导致臃肿。"

##### 第二层：网关层（流量入口与治理）

> "网关层部署了 **midservice1/2/3 多实例**做负载均衡，还有 **midmon 做监控**。网关承担了统一鉴权、限流、路由分发、请求日志这几件事。多实例保证了单节点故障不影响整体可用性。"

**追问应对：网关用的什么技术？**
> "midservice 和 midmon 都是我们**用 Java Web 自研的**。midservice 承担统一鉴权、限流、租户路由（不同客户请求打到对应数据隔离空间）、请求日志；midmon 是自建监控面板，实时展示各服务健康状态。多实例部署保证单节点故障不影响可用性。"

##### 第三层：业务中台（核心）

这是你最能展开的部分：

> "业务中台是我们平台的心脏，分为三大块：
>
> **第一块是管理系统**——包括客户管理、超级账本、商品类目、交易管理、合同管理、门户管理、系统管理、权限管理、交易风控等。这部分主要面向平台运营方，管理整个平台的规则和配置。
>
> **第二块是 DS 数据中心 + 交易核心的双核组合，这也是我们异构架构的核心设计。** 交易核心是 **C 语言撮合引擎**（单线程内存撮合 + 异步落库，保证延迟确定性）；而 **DS 数据中心是 Java 开发，专门负责协议转换、解决 C 撮合引擎与 Java 业务层的异构通信问题**——本质上它就是我们系统里的"桥接 / 防腐层（Anti-Corruption Layer）"：C 侧只暴露二进制协议，DS 把它翻译成 Java 业务服务能消费的标准接口和领域事件。所有异构复杂度都收敛在 DS 这一层，让 C 撮合引擎保持纯性能导向、不被业务耦合污染。
>
> **（技术细节补充，面试官追问时可用）**：DS 与 C 之间的协议转换采用 **Hessian 序列化**（二进制、跨语言友好、体积小），同步调用走 Hessian over HTTP，异步场景则通过 **Socket 服务**通信——这也是为什么 C 撮合结果能低延迟地回灌到 Java 业务层。选 Hessian 而不用 JSON，是因为撮合是高频率二进制交互，Hessian 的序列化和解析开销远低于文本协议。"
>
> **（这句话是面试杀手锏）**："我们最巧妙的设计就是——不把 Java 写进 C 撮合引擎，也不把 C 逻辑外泄到 Java 业务层，而是用 DS 数据中心做协议转换的'翻译官'。这样 C 团队和 Java 团队各自独立演进，互不阻塞。"
>
> **第三块是业务服务集群**，围绕交易核心展开——认证服务、用户管理、账本服务（记账）、**创新挂牌、自由竞价**（这是我们支持的多模式交易）、合同服务、**资金管理**、**运力交易**、商品类目管理等。每个都是独立的微服务，通过内部 RPC 通信。"
>
> **（如果面试官问C撮合，接之前那篇异构架构的话术）**

##### 第四层：数据存储

> "底层存储方面，数据库用的是 **MySQL 双实例**，做读写分离和容灾备份；文件和凭证（合同PDF、仓单扫描件、质检报告）走 **MinIO 对象存储**；还有一个文件服务统一管理文件的上传下载和权限控制。"

##### 第五层：外部接口（生态）

> "右侧是我们的生态对接矩阵——**银行接口**（支付/融资）、**短信接口**（验证码/通知）、**证书接口**（CA数字签名）、**物流接口**（仓储/运输）、**CTRM 接口**（大宗商品风险管理）、**开票接口**（税务）、**咨询接口**（行情资讯）、**企查查接口**（企业资质核验）、**供应链金融接口**（保理/应收账款融资）。这些接口让我们的平台不只是个交易工具，而是连接了资金流、信息流、物流的一站式服务平台。"

##### 第六层：基础治理

> "最底层是执行体系、战略管理和企业文化——这不是技术层面的，但作为技术经理，我参与了技术团队的执行体系建设（协同机制、闭环管理、精细管理）和敏捷文化的落地。"

### 第三部分：5分钟深挖版 —— "你在其中的角色是什么？解决了什么难题？"

#### 3.1 你的角色定位（结合之前BOUNDARY框架）

> "我的技术深度集中在**业务中台的管理系统和业务服务集群**这一块——具体来说就是客户管理、交易管理、合同管理、资金管理、创新挂牌、自由竞价、交易风控这几个模块。
>
> 对于**交易核心的C撮合引擎**，我采用的是**契约治理 + 可观测性**的方式来管理——定义好输入输出协议、通过 DS 数据中心的桥接日志和指标判断撮合系统是否健康工作。而 **DS 数据中心本身是 Java 开发的**，它恰好在我的技术栈覆盖范围内，所以我能直接 review 它的协议转换逻辑——这也是我作为 Java 技术经理能"管住"异构系统的关键抓手。
>
> 对于**外部接口**（银行/物流/CTRM等），我主导了接口规范制定和异常处理策略，确保任何外部系统故障不会引发连锁反应。"

#### 3.2 你解决的核心难题（挑2-3个讲）

##### 难题一：多模式交易的撮合一致性（交易模式 × C引擎）

> "我们支持多种交易模式——挂牌、竞价、询价、代采等，每种模式的撮合规则不一样。我的工作是把这些业务规则翻译成 C 撮合引擎能够理解的**标准化指令格式**，同时保证撮合结果异步落库时的一致性。具体做法是在 Java 侧建立了一套**规则配置引擎**，运营可以在后台配新的交易模式，Java桥接层自动把它转成C引擎的指令序列，不需要改C代码。"

##### 难题二：九个外部接口的稳定性保障（生态对接）

> "我们对接了银行、物流、CTRM 等 9 个以上外部系统，任何一个挂了都可能影响交易链路。我做的三件事：
> 1. 给每个外部接口建立了**熔断降级策略**——银行接口连续失败3次就自动切换到备用通道；
> 2. 建立了**对账机制**——每天凌晨跑一次全量对账，发现不一致立即告警；
> 3. 把外部接口调用全部**异步化**——不阻塞主交易流程，通过消息队列回调处理结果。"

##### 难题三：多租户数据隔离与性能平衡（DS数据中心）

> "我们有普通客户和机构客户两类租户，网页访问的读多写少特征很明显。为了加快页面访问，我们独立建了一个**缓存服务（Java 服务，封装 Redis）**——Canal 监听 MySQL binlog，把变更实时同步到这个缓存服务，前端读请求优先打缓存、命中即返回，大幅降低数据库压力和页面延迟。这也是 Canal 数据同步的主要消费方。"

#### 3.3 ⚠️ 图2 的 AI/智能体服务 —— 暂不纳入当前面试叙事

> **（重要提醒）**：第二张架构图里的智能体引擎、Dify/n8n/ragflow、minaru、vlm/qwen/lge-m3 等 AI 相关服务，**你已明确"暂时不考虑"**。因此：

> - 如果面试官问"你们有没有用 AI"，可以轻描淡写说"有探索方向但还不是核心生产链路"，然后把话题拉回你真正掌控的交易/缓存/异构架构。
> - 等这些服务真正在生产落地、你也能讲清架构后再纳入话术。
