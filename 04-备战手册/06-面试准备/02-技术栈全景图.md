### 一、Redis — 不止是缓存，是"快"的答案

#### 场景1：交易页面数据缓存（String）

**业务场景**：大宗商品价格实时波动，交易员每次刷新行情页面都要查数据库，数据库扛不住。

**技术方案**：
```
期货实时价格 → Redis String → 前端轮询
KEY: "price:RB2410:realtime"
VALUE: "3750"
TTL: 5秒（价格5秒更新一次）
```

**为什么是 Redis String？**
- O(1) 读写，毫秒级响应
- 设置 TTL 自动过期，不担心脏数据堆积
- 单线程模型天然原子性，并发读价格不会出现不一致

**追问："你们价格缓存怎么保证跟数据库一致？"**

→ Cache Aside 模式：更新数据库时删缓存，下次查询重建。关键：**先删缓存再更新数据库**（避免并发读写入旧缓存）。极端场景用延迟双删：删缓存→更新DB→等500ms→再删一次。

---

#### 场景2：防止重复提交（String + SETNX）

**业务场景**：大宗交易金额巨大，用户手抖点两次"确认下单"，千万不能创建两笔订单。

**技术方案**：
```java
String lockKey = "order:submit:" + orderNo;
Boolean locked = redisTemplate.opsForValue()
    .setIfAbsent(lockKey, "1", 30, TimeUnit.SECONDS);
if (!locked) {
    throw new BizException("请勿重复提交");
}
// 执行业务逻辑...
redisTemplate.delete(lockKey); // 处理完释放
```

**为什么用 SETNX 而不是数据库唯一约束？**
- 数据库唯一约束只能防"存进去"，不能防"业务逻辑执行两遍"
- SETNX 在业务入口就拦截，减少无效的数据库操作和第三方调用

**追问："SETNX 有什么坑？"**
- 锁过期时间设置：设太短业务没执行完锁就释放了（→ 用 Redisson 看门狗自动续期）
- 误删别人的锁：A 的锁过期，B 获取了锁，A 执行完删了 B 的锁（→ value 存 UUID，删之前比较）

---

#### 场景3：交易员操作权限缓存（Hash）

**业务场景**：每次操作都要查"这个交易员能不能做这笔交易"（额度限制、品种权限、合同范围），权限表 join 了 5 张表，查一次 200ms。

**技术方案**：
```
KEY: "trader:permission:10023"
HASH:
  "credit_limit" → "50000000"     (授信额度)
  "allowed_products" → "螺纹钢,热卷,铁矿石"  (可交易品种)
  "counterparty_list" → "1001,1002,1005"     (可交易对手方)
```

**为什么是 Hash 而不是多个 String？**
- 一次 HGETALL 拿到所有权限字段，不用多次网络往返
- 修改单个字段（如额度调整）只需 HSET 一条，不用重建整个对象
- 内存占用比多个 String key 小（共用 key 的元数据开销）

---

#### 场景4：延迟队列处理超时订单（ZSet）

**业务场景**：大宗交易中，买家确认合同后 30 分钟内必须支付保证金，超时自动取消。

**技术方案**：
```java
// 创建订单时
long cancelTime = System.currentTimeMillis() + 30 * 60 * 1000;
redisTemplate.opsForZSet().add("order:timeout:queue", orderNo, cancelTime);

// 定时任务每秒轮询
Set<String> timeoutOrders = redisTemplate.opsForZSet()
    .rangeByScore("order:timeout:queue", 0, System.currentTimeMillis());
// 逐个取消...
```

**为什么是 ZSet 而不是 MQ 延迟消息（Kafka）？**
- ZSet 的 score 就是取消时间，天然按时间排序，`rangeByScore` 一把捞到期订单
- Kafka **没有原生延迟消息**（不像 RocketMQ 有固定延迟级别），要自己做时间轮/延时 topic，30 分钟这种自定义延迟反而更麻烦
- ZSet + 轮询实现简单，业务可控，量级不大时是最性价比的方案

---

#### 场景5：排行榜/风控预警（ZSet）

**业务场景**：风控系统要实时展示"近 24 小时交易量最大的前 10 个客户"，监控异常交易。

```java
// 每笔交易完成时
redisTemplate.opsForZSet().incrementScore("risk:volume:24h", customerId, amount);

// 查询 Top 10
Set<ZSetOperations.TypedTuple<String>> top10 = redisTemplate.opsForZSet()
    .reverseRangeWithScores("risk:volume:24h", 0, 9);
```

### 二、MySQL — 数据的"保险柜"

#### 场景1：订单表设计 — 聚簇索引 vs 二级索引

**业务场景**：订单表每天新增 10 万条，需要按"下单时间"范围查询，又要按"客户 ID"查他的所有订单。

**建表决策**：
```sql
-- 主键：自增 bigint → 聚簇索引
-- 顺序插入，不会页分裂
CREATE TABLE t_order (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 聚簇索引，叶子存整行
    order_no VARCHAR(32) NOT NULL,
    customer_id BIGINT NOT NULL,
    product_code VARCHAR(20),
    amount DECIMAL(18,2),
    status TINYINT,
    create_time DATETIME,
    
    UNIQUE KEY uk_order_no (order_no),
    INDEX idx_customer_time (customer_id, create_time)  -- 联合索引
);
```

**面试要说清楚**：
- **聚簇索引（id）**：叶子节点存完整行数据，按 id 顺序排列。好处是按 id 范围查直接扫叶子链表；代价是二级索引要回表。
- **二级索引（idx_customer_time）**：叶子节点只存 (customer_id, create_time, id)，查到 id 后回表取完整行。如果 `SELECT id, customer_id, create_time FROM t_order WHERE customer_id=1001` — 覆盖索引，不用回表。

---

#### 场景2：联合索引的最左前缀原则 — 为什么这个查询慢了？

**业务场景**：客服查"客户 1001 在 2026 年 7 月的订单"，索引 `(customer_id, create_time)`

```sql
-- ✅ 走索引（等值查 customer_id + 范围查 create_time）
EXPLAIN SELECT * FROM t_order 
WHERE customer_id = 1001 AND create_time >= '2026-07-01';

-- ✅ 走索引（从最左 customer_id 开始）
EXPLAIN SELECT * FROM t_order WHERE customer_id = 1001;

-- ❌ 不走索引（跳过了 customer_id）
EXPLAIN SELECT * FROM t_order WHERE create_time >= '2026-07-01';

-- ⚠️ 只走 customer_id（create_time 用了函数，索引失效）
EXPLAIN SELECT * FROM t_order 
WHERE customer_id = 1001 AND DATE(create_time) = '2026-07-01';
```

**面试标准回答**："联合索引遵循最左前缀原则，查询条件必须从索引定义的第一列开始连续匹配。遇到范围查询（>、<、BETWEEN、LIKE 'xx%'）之后，后续列不再走索引。另外，对索引列用函数会导致索引失效，应该改成范围查询。"

---

#### 场景3：为什么 InnoDB 推荐自增主键？

**业务场景**：订单表用雪花算法生成的随机 ID vs 自增 ID，插入性能差多少？

**答案**：B+Tree 的叶子节点是按主键顺序存储的。自增主键每次插入都在最后面，几乎不会触发页分裂。随机主键插入位置不可预测，频繁引起页分裂 → 磁盘碎片 → 性能下降。

**追问："雪花算法就不行吗？"**

→ 可以，但要在业务层做优化：用"节点号+时间戳"保证趋势递增。或者用一个自增 ID 做聚簇索引，雪花 ID 做二级唯一索引。

---

#### 场景4：慢查询优化实战

**业务场景**：财务对账页面，一个 SQL 查 30 秒。

**排查流程（面试要能讲出这个流程）**：
```
1. SHOW FULL PROCESSLIST → 找到卡住的 SQL
2. EXPLAIN 看执行计划：
   - type=ALL → 全表扫描，没走索引
   - rows=200万 → 扫描行数太大
   - Extra=Using filesort → 排序没有用索引
3. 加联合索引 (company_id, settle_time, order_status)
4. 加完后 EXPLAIN 验证 type=range，rows 降到几千
5. 上预发布环境压测确认
```

### 三、消息队列 — 解耦的"神经系统"

> ⚠️ **对齐真实栈**：自家 MQ 统一是 **Kafka**。本节以 Kafka 为主线讲 MQ 的解耦 / 削峰 / 最终一致，RocketMQ / RabbitMQ 仅作为通用选型对比出现。事务语义一律落到 **outbox 本地消息表 + 消费幂等**（见 **本手册第二部分** 统一口径）。

#### 场景1：订单状态同步多个下游系统（Kafka）

**业务场景**：一笔大宗交易的订单状态变更（待确认→已确认→已付款→已发货→已收货→已结算），需要同步通知：仓储系统（备货/出库）、财务系统（记账/开票）、风控系统（额度调整）、客户 APP（推送通知）。

如果同步调用：
```
交易服务 → 仓储服务（等3秒）
         → 财务服务（等5秒）
         → 风控服务（等2秒）
         → 客户通知（等1秒）
总耗时 11秒，任何一个挂了整个链路崩
```

改成异步，一个 topic 多个消费组各取所需：
```java
// 订单状态变更后，发一条领域事件到 Kafka（key=orderNo 哈希分区，保证同订单分区内有序）
kafkaTemplate.send("order.status.changed", orderNo,
        OrderStatusChangedEvent.of(orderNo, from, to));

// 仓储 / 财务 / 风控 / 通知各自起一个消费组订阅同一 topic，
// 各自维护自己的 offset，独立消费、互不影响、互不抢消息
```

**面试要说清楚**：
- **解耦**：交易服务只发一个 topic，谁消费、消费几次由下游自己声明消费组，交易服务不感知
- **削峰**：冬储期日均订单量暴增 5 倍，Kafka 靠磁盘顺序写先把消息囤下来，下游按自己速度消费（消费组多实例并行 + 分区水平扩展）
- **最终一致性**：B2B 场景允许秒级延迟，不允许丢消息（→ `acks=all` + 消费幂等 + 死信 topic / 补偿表）
- **为什么这条链路用 Kafka 而不是 RabbitMQ**：同一份订单事件要被 4 个下游重复消费，Kafka 的"一个 topic 多个消费组各自维护 offset"天然适配；RabbitMQ 一条消息消费完即删，多下游要么多队列扇出、要么再抄一份，扩展成本高

---

#### 场景2：为什么我们选 Kafka 而不是 RocketMQ / RabbitMQ？

| 维度 | Kafka（自家选型） | RocketMQ | RabbitMQ |
|------|------------------|----------|----------|
| 定位 | 高吞吐分布式日志 / 流平台 | 业务消息 + 事务消息 | 轻量业务消息 |
| 吞吐 | 单机十万级+（顺序写 + 零拷贝 + 攒批） | 十万级 | 万级 |
| 多下游消费 | 一个 topic 多消费组天然扇出 | 支持，但 offset 模型不如 Kafka 顺手 | 靠多队列扇出，较重 |
| 顺序性 | 分区内有序（key 哈希分区） | 队列内有序 | 队列内有序 |
| 事务消息 | 无原生 half-message，用 outbox 本地消息表补 | 有原生事务消息 | confirm 机制 |
| 生态 | 流处理 / 数据管道 / 大数据一体 | 中小规模业务系统 | 简单业务解耦 |

**自家选型理由**：
- 大宗商品交易的事件量级 + 数据管道需求（行情、成交、履约凭证流的落库与分析）本来就要 Kafka，**一套 MQ 同时覆盖业务异步 + 数据管道**，不引入第二套中间件
- 一个事件被多下游重复消费是常态（订单事件同时喂仓储 / 财务 / 风控 / 通知），Kafka 多消费组模型最省心
- 团队只维护一套 MQ，学习成本和故障面都小

**追问："Kafka 没有事务消息，发消息和本地事务的一致性怎么保证？"**

→ 用 **outbox 本地消息表**：把业务操作和"待发送消息"写进同一个本地库的同一个事务（要么都成功、要么都回滚），再由独立线程 / 定时扫表把消息投递到 Kafka，投递成功打标。消费侧靠**幂等**（业务唯一键去重表 / 状态机判重）兜住重复投递。它比原生事务消息多一次轮询，但把一致性责任握在自己手里，也避免 MQ 不可用拖垮主链路。

---

#### 场景3：Kafka 消息丢了 / 重复了怎么办？

**面试三连问的标准答案（按 Kafka 讲）**：

```
生产者丢 → acks=all（等 ISR 中所有副本确认）+ retries 重试 + enable.idempotence=true（幂等生产者防重）
Broker丢  → replication.factor>=3 + min.insync.replicas>=2（至少 2 副本落盘才算成功），关闭 unclean.leader.election
消费者丢 → 关闭自动提交，业务处理完再手动 commit offset；异常不提交，交给重试 / 投递到死信 topic
重复消费 → 消费幂等：业务唯一键去重表 / 状态机判重，offset「至少一次」+ 幂等 = 业务上「恰好一次」
```

B2B 金融场景：**宁可慢，不可丢**。生产端 `acks=all` + 幂等生产者，Broker 多副本同步落盘，消费端手动提交 offset + 死信 topic + 补偿表，四重保障。

### 四、Elasticsearch — 搜索不是"LIKE"

#### 场景1：合同全文搜索

**业务场景**：法务要找"去年跟 XX 钢铁厂签的含'质量异议'条款的所有合同"。MySQL LIKE？5 亿条合同文本，查到天荒地老。

**技术方案**：
```
合同创建 → MySQL 存结构化字段（金额、日期、状态）
         → ES 存全文（合同正文、条款内容）
         
搜索时：ES 返回合同 ID 列表 → MySQL 查完整信息
```

**为什么用 ES？**
- 倒排索引：先把文档切词成"词条→文档ID"的映射表，搜索时直接翻字典，O(1)定位
- 不用扫全表，不用 like '%质量异议%'

**追问："ES 为什么快？MySQL 为什么慢？"**

→ MySQL B+Tree 索引最左前缀匹配，`LIKE '%质量异议%'` 无法利用索引必须全表扫描。ES 倒排索引是"词条→文档列表"的映射，"质量异议"这个词直接定位到包含它的所有文档。

---

#### 场景2：仓单/提单结构化搜索

**业务场景**：运营要筛选"上海仓库的螺纹钢仓单，库存>100吨，入库时间在最近30天"。

MySQL 能做，但 12 个筛选条件 + 4 张表 join + 百万级数据 → 慢。ES 的 filter 不参与打分，直接跳转到位图命中，毫秒级返回。

### 五、分布式事务 — B2B 绕不开的坎

#### 场景：下单扣库存 + 扣额度 + 创建合同

**业务场景**：大宗交易下单涉及三个操作：

```
1. 库存服务：锁定 500 吨螺纹钢
2. 风控服务：扣减客户授信额度 200 万
3. 合同服务：生成电子合同
```

**必须同时成功或同时失败**。

#### 方案演进（面试要能讲出这个思考过程）

**阶段1：本地事务** → 不行。三个服务三个数据库。

**阶段2：Seata AT 模式** → 自动回滚，但性能损耗大（两阶段提交，锁时间长），B2B 高并发交易扛不住。

**阶段3：Saga 模式（推荐）** → 每个服务执行成功调下一个，失败则调上一个的补偿接口：
```
下单成功 → 锁库存成功 → 扣额度成功 → 创建合同成功 ✅

如果"扣额度"失败：
下单补偿（释放库存）→ 释放库存（补偿）✅
```

**为什么 B2B 供应链适合 Saga？**
- 操作之间有几秒的时间差是可接受的（不像支付秒级）
- 补偿逻辑天然存在（锁库存→释放库存，扣额度→恢复额度）
- 不用全局锁，并发性能好

**追问："Saga 有什么问题？"**
- 隔离性问题：A→B→C 执行中，B 还在进行时，另一个事务已经读到了 A 的结果。B2B 供应链场景一般用"状态机"解决——状态未到达终态前，下游不认。

### 七、分布式锁 — 多节点下的"排队"

#### 场景：每日结算任务只能跑一次

**业务场景**：每天凌晨 2 点跑日终结算，生产环境部署了 3 个节点，如果三个节点同时跑，账就乱了。

```java
// Redisson 分布式锁
RLock lock = redisson.getLock("settle:daily:20260716");
try {
    if (lock.tryLock(0, 30, TimeUnit.MINUTES)) {
        // 执行结算逻辑
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

**追问："Redis 分布式锁有什么缺陷？主从切换怎么办？"**

→ 主节点刚写入锁，还没来得及同步到从节点，主挂了，从升级为新主——锁丢了。RedLock 算法：向多个（5个）独立 Redis 节点依次获取锁，超过半数成功才算加锁成功。但 RedLock 有争议（Martin Kleppmann 认为它不保证安全性），B2B 金融场景建议用 ZooKeeper 的临时顺序节点做分布式锁（依靠 ZAB 协议保证一致性）。

### 第二部分之网关层（midservice + midmon，Java Web 自研）

#### Q1：你们网关是自研的？为什么不用 Nginx / Spring Cloud Gateway / Kong？

**答题框架**：

| 维度 | 你的回答要点 |
|------|------------|
| 背景 | 平台有 3 类租户（外部大屏/普通客户/机构客户），并发等级、鉴权重、限流策略差异极大 |
| 挑战 | 通用网关要么太重（Kong插件多但二次开发难），要么太轻（Nginx L7能力弱），通用方案难匹配多租户分级路由 |
| 方案 | 基于 Java Web（Servlet + Netty）自研：① 租户维度路由（不同客户隔离域）② 多级限流（机构客户配额远高于普通）③ 灰度发布与流量染色 |
| 收益 | 一次请求路由效率比通用网关高 30%；租户故障隔离能力是 Kong 没有的 |
| midmon | 同套技术栈，监控/告警/链路追踪，**不是独立产品而是网关的一部分** |

> **口径**："我们的业务场景更匹配自研。"

#### Q2：midservice 多实例怎么做会话一致？

**答题要点**：① 无状态化（Session 抽到 Redis）② 路由策略：一致性 Hash（同一用户落同一实例）+ 健康检查剔除 ③ 写操作走 MQ 异步（避免实例间数据不一致）。

> 关键不是"怎么做"，是"为什么这种做法在你的场景最划算"。

#### Q3：网关挂了怎么办？3 道防线讲清楚

**三层防线**（按时间序）：
1. **接入层** → midservice 多实例 + 健康检查 + 自动剔除（**实例级容错**）
2. **熔断层** → midmon 触发熔断、限流、降级（**故障级容错**）
3. **兜底层** → 静态兜底页 + 关键读操作降级到缓存服务（**业务级容错**）

### 第二部分之业务中台（Java 微服务，12+ 集群）

#### Q4：12+ 个微服务怎么治理？不会拆得太细吗？

**答题框架（重点题）**：
- **拆分原则**：**按业务能力垂直切**（不是按技术层水平切），每个服务对应一个完整的"业务动作"（如下单服务 = 订单生成 + 校验 + 持久化的全流程）
- **避免过度拆分**：判断标准 = 5 人以下团队维护的不要拆（拆了反而增加协作成本）
- **服务通信**：同步 = Hessian over HTTP；异步 = 内部 MQ
- **数据归属**：每个服务拥有自己的库表，跨服务走 API 或领域事件，**禁止直接 join 别人的库**（这是关键纪律）

> **加分点**：主动提"演进式拆分"——早期单体，按业务成熟度逐步拆，而不是一开始就上 12 个。

#### Q5：微服务的链路追踪怎么做？

**答题框架**（基于实际栈）：
- 入口：midservice 生成 traceId，注入请求头
- 传递：HTTP 用 Header 透传；Socket 用协议字段透传
- 落点：DS 桥接层是**关键转换点**（Hessian 二进制里要预留 traceId 字段）
- 聚合：midmon 收集 + ES 存储 + 可视化
- 价值：定位一笔交易从下单→撮合→落库→缓存刷新的全链路耗时

> **杀手追问**："Hessian 协议怎么加 traceId？"——答：自定义 Hessian 序列化器扩展字段，或在协议头加固定偏移字段。
> 口径：链路追踪讲"关键节点全打通"，表述最稳。

#### Q6：服务间调用超时怎么设？雪崩怎么防？

**答题框架**：
- **超时分级**：核心交易 200ms / 一般业务 1s / 后台异步不设超时
- **三件套**：超时 + 重试（2次）+ 熔断（Resilience4j）
- **雪崩防线**：① 线程池隔离（不同服务不同池）② 快速失败（达到阈值直接返回兜底）③ 降级（返回缓存/默认值）
- **B2B 特殊点**：大宗交易**不能降级**（涉及钱），所以宁可拒绝也不返回错值——这是和电商最大的区别

### 第二部分之DS 数据中心（Java 防腐层，Hessian + Socket）⭐ 核心杀手锏

#### Q7：DS 是什么？为什么需要它？（必问，**最该背熟**）

**满分答题框架**（5段式）：
1. **背景**：C 撮合引擎是单线程内存撮合 + 异步落库，性能极强但只暴露二进制协议；Java 业务层要的是标准 POJO/RPC 语义
2. **挑战**：如果让 Java 直接调 C，要么 Java 团队必须懂 C 协议（团队分裂），要么 C 团队被迫实现业务接口（性能被拖累）
3. **方案**：**DS 数据中心（Java）做协议转换的"翻译官"**——把 C 的二进制协议翻译成 Java 业务服务能消费的标准接口和领域事件（C 不感知业务，业务不感知 C）
4. **同步/异步双通道**：
   - 同步 = **Hessian over HTTP**（请求-响应，Java 业务调 C 撮合）
   - 异步 = **Socket 长连接**（C 撮合产生的事件反向推给 Java 业务，Java 消费做下游）
5. **我的角色**：作为 Java 技术经理，我**不需要写 C 代码，但能直接 review DS 桥接层**——这就是我"管住异构系统"的抓手

> **杀手级收尾**："异构系统的复杂度收敛在 DS 一层，C 团队和 Java 团队各自独立演进、互不阻塞——这是我们最巧妙的设计。"

#### Q8：为什么序列化用 Hessian 不用 JSON / Protobuf？

**答题框架**（讲清权衡）：

| 方案 | 优势 | 劣势 | 你的选择 |
|------|------|------|---------|
| JSON | 跨语言最通用、可读 | 体积大、解析慢、字段错位不报错 | 排除（性能+稳定性） |
| Protobuf | 体积小、强 schema | 需预生成代码、调试难、跨团队维护成本高 | 排除（团队协作成本） |
| **Hessian** | Java 生态成熟、跨语言、字节紧凑、调试比 PB 简单 | 比 PB 略大 | **采用**（团队已选） |

> **加分点**："选型要看团队成本——Hessian 学习成本最低、IDE 友好、自定义序列化器扩展 traceId 也方便。"

#### Q9：Socket 异步通信怎么保证消息不丢不重？

**答题框架**（4层可靠性）：

```
业务层     → 幂等消费（业务侧去重）
可靠传输层 → ACK + 重试 + 去重 + offset
连接管理层 → 心跳 + 重连 + 熔断
        ↕ Socket 长连接
        ↕ Redis 集群（去重表 + offset + 会话状态）
```

> **关键铁律**：先落地（写库/写Redis）再回 ACK，反过来就丢消息。

#### Q10：DS 高可用怎么设计？（C 撮合挂了怎么办）

**答题框架**（**异构系统必问题**）：
- **熔断降级**：DS 检测 C 不可用 → 立即熔断 → 业务请求走**降级队列暂存** → C 恢复后**回放**
- **请求排队**：DS 限流（不把 C 打爆）+ 排队（让 C 按自己的节奏消费）
- **数据兜底**：关键交易状态在 DS 侧**镜像一份**，C 挂了 Java 也能查询
- **应急开关**：极端情况下，业务方允许"只接单不撮合"，先保业务可用

> **B2B 核心原则**：**钱的事绝对不能错，宁可慢也不能乱**——这是 C 引擎 + DS 设计的第一约束。

### 第二部分之交易核心（C 语言单线程内存撮合）⭐ 差异化

#### Q11：为什么撮合引擎用 C 不用 Java？必问加分题

**满分答题框架**：
- **延迟确定性**：C 单线程无 GC 停顿，纳秒级；Java 即使调优也有 GC 抖动（10-100ms 不可控）
- **内存可控**：C 手动内存管理，撮合订单簿可用自定义内存池；Java 受 GC 影响不可控
- **CPU 亲和性**：C 可绑核、单线程无锁，CPU 缓存命中率高
- **行业对标**：郑商所、大商所、LME 等核心撮合都是 C/C++

> **口径**："在这个特定场景下，延迟确定性的要求让 C 是更优选。"
> **加分收尾**："我作为 Java 技术经理，不写 C，但我通过 DS 桥接层和监控仪表盘管住它的'健康'——飞行员不需要修发动机，但要读懂每个仪表。"

#### Q12：你不懂 C，怎么管交易核心？（诚实但不失分）

**答题框架**（**BOUNDARY 框架**，完整定义见 `01-面试核心策略手册.md` §2.5；下面是本场景的落地版）：
1. **B**oundary 承认边界："我的深度领域是 Java 业务层和异构桥接层，C 撮合核心是 C 团队的领域"
2. **O**wnership 守住接口："但我守三件事：① C 的输入输出协议（业务怎么调它、它回什么）② 异常行为的契约（C 出错怎么回、Java 怎么接）③ 全链路可观测（traceId 跨异构打通）"
3. **M**echanism 量化管控："通过 DS 桥接层的熔断/限流/重试，把 C 的爆炸半径控制在它自己域内"
4. **R**esult 协作机制："每周 15 分钟对齐会 + 接口契约 Review 我审批 + 事故联合复盘，协议变更从改 N 处降到改 1 处"

#### Q13：异步落库怎么做？数据一致性怎么保证？

**答题框架**（技术深度题）：
- **设计**：撮合完成 → 内存订单簿更新 → 异步队列 → 落库
- **一致性**：撮合是"主"，落库是"影子"——落库失败不能回滚撮合（会阻塞后续撮合），而是**记异常 + 重试 + 对账兜底**
- **故障恢复**：进程崩了，从内存订单簿 + 落库增量 offset 恢复状态
- **面试话术**："异步落库是典型的**最终一致**模型，靠对账兜底保数据正确性——这是分布式系统的基本功。"

#### Q14：C 撮合怎么扩多模式？（挂牌/竞价/询价/代采/预售）

**答题框架**：
- 撮合核心 = **撮合算法可插拔**（策略模式）
- 模式 = 算法（价格优先时间优先 / 数量优先 / 全量成交 / 部分成交）
- 新增模式 = 加算法实现 + 在 DS 侧加模式路由
- 关键设计：**撮合核心不感知业务模式名，只接收结构化指令**

> **加分**：提"规则配置驱动"——业务模式变化不改代码，只改规则配置。

### 第二部分之数据层（MySQL 双实例 + MinIO + 缓存服务）

#### Q15：MySQL 双实例是主从还是双主？一致性怎么保证？

**答题框架**：
- **大概率是主从**（双主易脑裂，中小公司慎用）
- **同步策略**：半同步复制（保证至少一从落盘）+ binlog 校验 + 定期全量对账
- **业务分流**：写主读从（读写分离）+ 关键交易强制读主（避免主从延迟导致资损）
- **C 撮合落库**：写主库（强一致需求），缓存同步走 Canal（异步最终一致）

> ⚠️ **如果你不确定是不是双主**——面试时说"读写分离 + 半同步"是较安全的回答。

#### Q16：Canal 同步到缓存服务是为什么？Redis 不是吗？

**答题框架**（**已确认的事实**）：
- **架构**：Canal 监听 MySQL binlog → 推送到**独立 Java 缓存服务**（封装 Redis，对外暴露统一 API）
- **为什么包一层**：
  ① **业务隔离**：业务不直接调 Redis，统一通过缓存服务（接入门槛低、调用规范统一）
  ② **读写加速**：高频读（行情/挂牌列表）走缓存，不打 MySQL
  ③ **协议屏蔽**：未来换缓存（Redis → Memcached → 本地缓存）业务无感
- **数据流**：MySQL → Canal → 缓存服务 → Redis → 业务读

> **加分**："独立缓存服务是**B2B 场景特有的'读多写少'优化**——行情刷新、挂牌列表这些高频读场景，没缓存会把 MySQL 打死。"

#### Q17：缓存一致性问题怎么解决？（cache aside 还是其他？）

**答题框架**（标准答案 + 你的场景化）：
- **基础模式**：Cache Aside（读时 cache miss 查 DB 写缓存；写时先更新 DB 再失效缓存）
- **你的特殊点**：大宗交易**不能用"先失效缓存再写 DB"**（可能写 DB 失败但缓存已失效，下次读 cache miss 又回源 DB → 数据未更新）→ **先写 DB，成功后异步失效缓存**（通过 Canal 触发）
- **进阶**：缓存击穿（热点 key 永不过期 + 后台异步刷新）/ 雪崩（过期时间加随机扰动）/ 穿透（布隆过滤器）

### 第二部分之生态接口（9+ 外部对接）

#### Q18：9 个外部接口怎么统一治理？（重点题）

**答题框架**（**必答，体现架构成熟度**）：
1. **统一接入层**：所有外部接口进同一 SDK（限流/重试/熔断/超时/签名统一）
2. **适配器模式**：每个外部接口一个 Adapter，业务只调统一接口
3. **异步回调 + 状态机**：外部接口**必然是异步的**（银行打款不可能秒回）→ 状态机跟踪：已请求→处理中→成功/失败
4. **日终对账兜底**：实时异步 + 日终批量对账是**双保险**（金融场景必须）
5. **失败重试策略**：对账不一致 → 人工介入 / 自动补单

> **杀手追问**："如果银行接口挂了 2 小时你怎么办？"
> 答：① 立即熔断（不让请求堆积）② 业务侧提示"支付延迟"③ 失败的请求进死信队列 ④ 银行恢复后批量回放 ⑤ 仍失败的进人工对账。

#### Q19：供应链金融接口怎么对接？和普通支付的区别？

**答题框架**（体现行业理解）：
- **本质区别**：供应链金融是**多方信任 + 资金路径长**（核心企业/银行/供应商/资金方）
- **关键能力**：授信管理 / 应收账款流转 / 资金清结算 / 风险预警
- **技术要点**：
  ① 强事务（涉及钱）→ 用可靠消息 + 幂等 + 对账
  ② 协议多变（不同银行不同接口）→ 适配器层必须灵活
  ③ 监管合规（数据留痕 / 反洗钱）→ 操作日志全审计
- **B2B 特色**：与"撮合引擎 + 履约保证"强耦合——金融的"放款"必须以"履约"为前提

#### Q20：描述一笔挂牌交易从下单到落库的全链路（**必考压轴题**）

**答题框架**（按 8 步讲清全链路）：

```
[1] 用户下单（Vue PC/移动）
   ↓
[2] midservice 网关：鉴权 + 限流 + 路由
   ↓
[3] 业务服务：参数校验 + 业务规则（规则引擎）
   ↓
[4] DS 桥接层：Hessian 序列化 → 调 C 撮合引擎
   ↓

   ↓
[6] 撮合结果：① 同步返回 DS → 业务响应用户
            ② 异步 Socket 推领域事件 → DS → 业务订阅
   ↓
[7] 异步落库：撮合结果进 MQ → 落库服务写 MySQL
   ↓
[8] Canal 监听 binlog → 同步到缓存服务 → Redis 缓存刷新 → 用户看到行情
```

> **核心讲清两件事**：
> ① **同步/异步边界**：用户感知的是同步（步骤 6①），系统内部是异步（步骤 6② + 7 + 8）
> ② **异构协同点**：DS 在第 4 步（Java→C）和第 6 步（C→Java）双向翻译

> **加分收尾**："全链路每一段都能独立容错，单点故障不会让整笔交易失败——这就是**异构架构的工程化成熟度**。"

#### 一、JVM 内存结构

##### 1.1 运行时数据区

```
┌──────────────────────────────────────────────────────┐
│                    JVM 进程内存                        │
├──────────────┬───────────────────────────────────────┤
│              │  ┌─────────┐ ┌─────────┐              │
│  线程私有     │  │ 虚拟机栈 │ │ 本地方法栈│              │
│（随线程生死） │  └────┬────┘ └─────────┘              │
│              │  ┌────┴────┐                           │
│              │  │ 程序计数器│                          │
│              │  └─────────┘                           │
├──────────────┼───────────────────────────────────────┤
│              │  ┌─────────────────────────────────┐  │
│  线程共享     │  │            堆 (Heap)             │  │
│（随 JVM 生死）│  │  ┌─────────┬─────────────────┐  │  │
│              │  │  │ 新生代   │     老年代        │  │  │
│              │  │  │Eden|S0|S1│                 │  │  │
│              │  │  └─────────┴─────────────────┘  │  │
│              │  └─────────────────────────────────┘  │
│              │  ┌─────────────────────────────────┐  │
│              │  │        方法区/元空间              │  │
│              │  │  类信息/常量池/静态变量            │  │
│              │  └─────────────────────────────────┘  │
└──────────────┴───────────────────────────────────────┘
```

| 区域 | 线程 | 存储内容 | OOM 类型 | Python 类比 |
|------|------|---------|----------|-------------|
| **虚拟机栈** | 私有 | 栈帧（局部变量表/操作数栈） | StackOverflowError / OOM | 函数调用栈 |
| **本地方法栈** | 私有 | Native 方法调用 | OOM | C 扩展调用 |
| **程序计数器** | 私有 | 当前执行字节码行号 | **不会 OOM** | — |
| **堆** | 共享 | 对象实例/数组 | OutOfMemoryError: Heap | Python 堆内存 |
| **方法区（元空间）** | 共享 | 类元数据/常量池/静态变量 | OOM: Metaspace | 模块/类对象 |

##### 1.2 堆内存分代

```
┌──────────────────── 堆 (Heap) ────────────────────────┐
│  ┌──────────────── 新生代 (Young) ──────────┐ ┌──────┐│
│  │   Eden (8)    │   S0 (1)   │   S1 (1)   │ │ Old  ││
│  │               │  (From)    │   (To)     │ │      ││
│  │  新对象分配    │  存活对象   │  复制存活对象│ │ 长期  ││
│  │               │            │            │ │ 存活  ││
│  └───────────────┴────────────┴────────────┘ │ 对象  ││
│           Minor GC（复制算法）         ↓      │      ││
│                                  Major GC / Full GC  ││
└───────────────────────────────────────────────────────┘
  新生代:老年代 = 1:2（默认）    晋升条件：年龄≥15 或 S 区放不下
```

| GC 类型 | 回收区域 | 触发条件 | STW |
|---------|---------|---------|-----|
| **Minor GC** | 新生代（Eden+S0/S1） | Eden 满 | ✅ 短暂停（毫秒级） |
| **Major GC** | 老年代 | 老年代满 | ✅ 较长 |
| **Full GC** | 整个堆+元空间 | 老年代满/System.gc() | ✅ 最长（应避免） |

##### 1.3 对象生命周期

```
new Object()
    │
    ├─→ 优先分配到 TLAB（Thread Local Allocation Buffer）
    ├─→ TLAB 满 → Eden 区分配
    │
    ├─→ Eden 满 → Minor GC
    │     ├─ 存活 → 复制到 S0（年龄+1）
    │     ├─ S0 满 → 复制到 S1（年龄+1）
    │     └─ 年龄 ≥ 15 → 晋升老年代
    │
    ├─→ 大对象 → 直接老年代（-XX:PretenureSizeThreshold）
    │
    └─→ 老年代满 → Full GC → 仍满 → OOM
```

#### 二、垃圾回收（GC）

##### 2.1 GC 算法

| 算法 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **标记-清除** | 标记存活→清除其余 | 简单 | **内存碎片** | CMS Old |
| **复制** | 存活对象复制到另一半 | 无碎片、快 | 浪费 50% 空间 | 新生代 |
| **标记-整理** | 标记存活→向一端移动 | 无碎片、不浪费 | 较慢 | Old |
| **分代收集** | 新生代复制+老年代标记整理 | 综合最优 | — | **主流 JVM** |

##### 2.2 GC Roots（根对象）

GC 从以下 Roots 开始可达性分析，不可达的对象即垃圾：

| GC Root 类型 | 说明 |
|-------------|------|
| 虚拟机栈中引用的对象 | 正在执行的方法的局部变量 |
| 方法区中类静态属性引用的对象 | static 变量 |
| 方法区中常量引用的对象 | static final 常量 |
| 本地方法栈 JNI 引用的对象 | Native 方法引用 |
| 活跃线程 | Thread 对象本身 |
| 同步锁持有的对象 | synchronized 持有的对象 |

##### 2.3 垃圾回收器对比

```
时间线：Serial → Parallel → CMS → G1 → ZGC/Shenandoah

吞吐量优先 ←─────────────────────────→ 延迟优先
Serial/Parallel ──── CMS ──── G1 ──── ZGC
```

| 回收器 | 分代 | 算法 | STW | 适用场景 | Python 类比 |
|--------|------|------|-----|---------|-------------|
| **Serial** | 新生代 | 复制 | 全程 STW | 单核、小内存 | — |
| **ParNew** | 新生代 | 复制 | 多线程 STW | 配合 CMS | — |
| **Parallel Scavenge** | 新生代 | 复制 | 多线程 STW | **吞吐量优先** | — |
| **CMS** | 老年代 | 标记-清除 | 4 阶段（部分并发） | 低延迟（已废弃） | — |
| **G1** | 全堆（Region） | 标记-整理+复制 | 可预测停顿 | **JDK9+ 默认** | gc 模块 |
| **ZGC** | 全堆（Region） | 染色指针+读屏障 | **<10ms** | 超低延迟（JDK11+） | — |

##### 2.4 G1 详解（面试重点）

```
G1 将堆划分为 2048 个等大 Region（1-32MB）
每个 Region 可以动态是 Eden / Survivor / Old / Humongous

GC 过程：
1. 初始标记（STW）→ 标记 GC Roots 直接引用
2. 并发标记 → 从 Roots 遍历对象图
3. 最终标记（STW）→ 处理并发标记期间的变更
4. 筛选回收（STW）→ 按回收价值排序，回收性价比高的 Region
```

**G1 核心优势**：
- 可预测停顿：`-XX:MaxGCPauseMillis=200`（目标 200ms 内）
- Region 化：不再严格分代，整体看是一组 Region
- 无内存碎片：整体标记-整理，局部复制

##### 2.5 常用 JVM 参数

| 参数 | 说明 | 推荐值 |
|------|------|--------|
| `-Xms` | 初始堆大小 | = `-Xmx`（避免动态扩缩） |
| `-Xmx` | 最大堆大小 | 物理内存的 60-70% |
| `-Xmn` | 新生代大小 | 堆的 1/3 |
| `-XX:MetaspaceSize` | 元空间初始大小 | 256M |
| `-XX:MaxMetaspaceSize` | 元空间最大大小 | 512M |
| `-XX:+UseG1GC` | 使用 G1 回收器 | JDK9+ 默认 |
| `-XX:MaxGCPauseMillis` | G1 目标停顿时间 | 200ms |
| `-XX:+PrintGCDetails` | 打印 GC 详情 | 排查必开 |

##### 2.6 OOM 排查

```

  → 堆内存不足，检查是否有内存泄漏

```

```
          │ Bootstrap ClassLoader │  ← 加载 rt.jar（java.lang.*）
```

| 热部署 | 自定义 loadClass() | 修改类后重新加载 |

#### 四、Java 内存模型（JMM）

##### 4.1 JMM 是什么

> JMM（Java Memory Model）定义了**多线程之间如何通过内存进行交互**的规范。它不是 JVM 内存结构（堆/栈），而是一组并发编程的规则。

```
线程 A                          线程 B
┌──────────┐                  ┌──────────┐
│ 工作内存   │                  │ 工作内存   │
│ (CPU缓存) │                  │ (CPU缓存) │
└────┬─────┘                  └────┬─────┘
     │ read/write                   │ read/write
     │                              │
┌────┴──────────────────────────────┴─────┐
│              主内存 (Main Memory)          │
│              共享变量存储                    │
└─────────────────────────────────────────┘
```

| 操作 | 说明 |
|------|------|
| **read** | 主内存→工作内存 |
| **load** | 放入工作内存变量副本 |
| **use** | 工作内存→执行引擎 |
| **assign** | 执行引擎→工作内存 |
| **store** | 工作内存→主内存 |
| **write** | 写入主内存变量 |

##### 4.2 三大特性

| 特性 | 说明 | 问题示例 |
|------|------|---------|
| **可见性** | 线程修改变量后，其他线程能立即看到 | 线程 A 改了 flag=true，线程 B 还看到 false |
| **原子性** | 操作不可分割，不被中断 | `count++` 不是原子的（读+加+写） |
| **有序性** | 代码执行顺序符合预期（防重排） | DCL 单例的 `new Object()` 可能被重排 |

##### 4.3 volatile（高频考点）

```java
// volatile 两大作用：
// 1. 可见性：写入后立即刷主内存，读取前从主内存刷新
// 2. 禁止指令重排：插入内存屏障

private volatile boolean running = true;

// 线程 A
running = false;  // volatile 写 → 刷主内存

// 线程 B
while (running) {  // volatile 读 → 从主内存刷新
    // 如果不加 volatile，B 可能永远看不到 running=false
}
```

**volatile 不保证原子性**：

```java
private volatile int count = 0;
count++;  // ❌ 不安全！count++ = 读+加+写，三步非原子
// 需要 AtomicInteger.count.incrementAndGet() 或 synchronized
```

**DCL 单例为什么要 volatile**：

```java
public class Singleton {
    private static volatile Singleton instance;  // ← 必须 volatile！

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                    // new Singleton() 分三步：
                    // 1. 分配内存  2. 初始化对象  3. 引用指向内存地址
                    // 如果 2 和 3 重排 → 其他线程拿到未初始化的对象！
                }
            }
        }
        return instance;
    }
}
```

##### 4.4 happens-before 规则

> 如果 A happens-before B，则 A 的操作结果对 B 可见。

| 规则 | 说明 |
|------|------|
| **程序顺序规则** | 同一线程内，代码前面的操作 HB 后面的 |
| **volatile 规则** | volatile 写 HB 后续的 volatile 读 |
| **锁规则** | unlock HB 后续 lock |
| **线程启动规则** | Thread.start() HB 线程内所有操作 |
| **线程终止规则** | 线程内所有操作 HB Thread.join() |
| **传递性** | A HB B 且 B HB C → A HB C |

#### 五、并发编程

##### 5.1 synchronized 锁升级（JDK 6+）

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁（不可逆）

┌──────┐   竞争    ┌────────┐  自旋失败  ┌──────────┐
│ 偏向锁 │ ──────→ │ 轻量级锁 │ ────────→ │ 重量级锁  │
│      │         │(CAS自旋) │          │(OS互斥量) │
└──────┘         └────────┘          └──────────┘
首个线程         2个线程交替          多线程激烈竞争
记录ThreadID     CAS竞争              进入内核态阻塞
几乎无开销       避免系统调用          上下文切换开销大
```

| 锁状态 | 适用场景 | 开销 |
|--------|---------|------|
| **偏向锁** | 单线程访问 | 几乎为零（CAS 记录 ThreadID） |
| **轻量级锁** | 两个线程交替访问 | CAS 自旋（用户态） |
| **重量级锁** | 多线程激烈竞争 | OS 互斥量（内核态阻塞） |

##### 5.2 synchronized vs ReentrantLock

| 维度 | synchronized | ReentrantLock |
|------|-------------|---------------|
| **实现** | JVM 内置（monitorenter/exit） | JDK API（AQS） |
| **锁释放** | 自动（出代码块/异常） | **手动** `finally { lock.unlock() }` |
| **可中断** | ❌ 不可中断 | ✅ `lockInterruptibly()` |
| **超时获取** | ❌ | ✅ `tryLock(timeout)` |
| **公平锁** | ❌ 非公平 | ✅ 可选公平/非公平 |
| **条件变量** | 1 个（wait/notify） | **多个** `Condition` |
| **锁升级** | 偏向→轻量→重量 | 直接 AQS |

##### 5.3 AQS（AbstractQueuedSynchronizer）

```
AQS 核心：state 变量 + CLH 双向等待队列

         ┌──────────────────────────────┐
         │        state (volatile int)    │
         │  0=未锁定  >0=锁定/重入次数     │
         └──────────────────────────────┘
                      │
    ┌─────────────────┼─────────────────┐
    │                 │                  │
  独占模式            共享模式           条件变量
  ReentrantLock      Semaphore          Condition
  writeLock          CountDownLatch     await/signal
                    readLock
                    CyclicBarrier

CLH 队列：
  head ←→ Node ←→ Node ←→ Node ←→ tail
            (ThreadA) (ThreadB) (ThreadC)
```

##### 5.4 CAS（Compare And Swap）

```java
// CAS 原理：比较并交换，CPU 原子指令（cmpxchg）
boolean compareAndSwap(Object obj, long offset, int expected, int newValue) {
    // 如果 obj.offset 的值 == expected，则设为 newValue，返回 true
    // 否则返回 false
}

// AtomicInteger.incrementAndGet() 底层就是 CAS
public final int incrementAndGet() {
    return U.getAndAddInt(this, VALUE, 1) + 1;
    // 自旋 CAS：do { v = getInt(this); } while (!cas(this, v, v+1));
}
```

| 优点 | 缺点 |
|------|------|
| 无锁，性能高 | **ABA 问题**（值从 A→B→A，CAS 认为没变过） |
| CPU 原子指令 | 自旋开销大（竞争激烈时） |
| | 只保证一个变量原子 |

**ABA 解决**：`AtomicStampedReference`（加版本号）

##### 5.5 线程池（ThreadPoolExecutor）

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    corePoolSize,      // 核心线程数
    maximumPoolSize,   // 最大线程数
    keepAliveTime,     // 非核心线程空闲存活时间
    unit,              // 时间单位
    workQueue,         // 任务队列
    threadFactory,     // 线程工厂
    handler            // 拒绝策略
);
```

**执行流程**：

```
提交任务
  │
  ├─ 当前线程数 < corePoolSize？→ 创建核心线程执行
  │
  ├─ 核心线程满？→ 放入 workQueue 队列
  │
  ├─ 队列满？→ 创建非核心线程（不超过 maximumPoolSize）
  │
  └─ 线程数达到 max 且队列满？→ 执行拒绝策略
```

| 拒绝策略 | 行为 |
|---------|------|
| **AbortPolicy**（默认） | 抛 RejectedExecutionException |
| **CallerRunsPolicy** | 调用者线程执行（降级，不丢任务） |
| **DiscardPolicy** | 静默丢弃 |
| **DiscardOldestPolicy** | 丢弃队列最老的任务，重试 |

**线程数设置**：

| 任务类型 | CPU 密集型 | IO 密集型 |
|---------|-----------|----------|
| 核心线程数 | **CPU 核数 + 1** | **CPU 核数 × 2~10** |
| 理论公式 | N+1 | N × (1 + W/C)（W=等待时间, C=计算时间） |

**为什么不推荐 Executors 工具方法**：

| 方法 | 问题 |
|------|------|
| `newFixedThreadPool` | 队列 `LinkedBlockingQueue` 无界 → **OOM** |
| `newCachedThreadPool` | 最大线程 `Integer.MAX_VALUE` → **OOM** |
| `newSingleThreadExecutor` | 同 FixedThreadPool → **OOM** |
| 推荐 | 手动 `new ThreadPoolExecutor(...)`，明确参数 |

##### 5.6 ThreadLocal

```java
// 每个线程独立副本，线程隔离
private static ThreadLocal<SimpleDateFormat> dateFormat =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

// 底层：每个 Thread 有一个 ThreadLocalMap
// Key = ThreadLocal 对象（弱引用），Value = 实际值（强引用）
```

**内存泄漏问题**：

```
Thread → ThreadLocalMap → Entry(WeakRef<ThreadLocal>, StrongRef<Value>)
                                          ↑                    ↑
                                    GC 可回收             GC 不可回收！
                                    Key=null              Value 仍在
```

- Key 是弱引用，ThreadLocal 被回收后 Key=null
- Value 是强引用，**线程不结束 Value 就不回收**
- 线程池中线程复用 → Value 积累 → 内存泄漏

**解决**：用完必须 `threadLocal.remove()`

##### 6.1 HashMap 源码（高频重点）

##### JDK 1.8 结构

```
table 数组
┌──┬──┬──┬──┬──┬──┬──┬──┐
│  │  │  │  │  │  │  │  │  ← 桶（Bucket）
└──┴──┴──┴──┴──┴──┴──┴──┘
       │              │
   ┌───┴──┐       ┌───┴──┐
   │ K:V  │       │ K:V  │  ← 链表节点
   │ next │──→   │ next │──→ null
   └──────┘       └──────┘
                       │
                   链表长度 ≥ 8 且 table ≥ 64
                       ↓ 红黑树化
                   ┌───────┐
                   │ K:V   │  ← 红黑树节点
                   │ left  │
                   │ right │
                   │ parent│
                   └───────┘
```

##### put 流程

```java
V put(K key, V value) {
    // 1. hash(key) → (h = key.hashCode()) ^ (h >>> 16)  扰动函数
    // 2. (n-1) & hash  →  定位桶下标（n 是 2 的幂，保证均匀分布）
    // 3. 桶为空 → 直接放入
    // 4. 桶非空：
    //    a. key 相同（== 或 equals）→ 覆盖 value
    //    b. 链表 → 尾插法插入（JDK1.7 是头插法，多线程会成环）
    //    c. 链表 ≥ 8 且 table ≥ 64 → 转红黑树
    // 5. size > threshold(容量×负载因子) → resize 扩容（2 倍）
}
```

##### 关键参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 初始容量 | 16 | `1 << 4` |
| 负载因子 | 0.75 | size > 容量×0.75 时扩容 |
| 链表转树阈值 | 8 | 链表长度 ≥ 8 |
| 树退化链表阈值 | 6 | 红黑树节点 ≤ 6 时退化 |
| 最小树化容量 | 64 | table < 64 时优先扩容不树化 |

##### 为什么容量是 2 的幂？

```
桶下标 = (n-1) & hash
当 n = 16 时：n-1 = 15 = 0000 1111
hash & 0000 1111 → 等价于 hash % 16，但位运算更快
且 2 的幂保证 n-1 全是 1，分布均匀
```

##### HashMap 线程不安全

| 问题 | JDK 1.7 | JDK 1.8 |
|------|---------|---------|
| 扩容时链表成环 → 死循环 | ✅ 会有 | ❌ 尾插法修复 |
| 数据覆盖 | ✅ | ✅ 仍有 |
| size 不准确 | ✅ | ✅ |

> **面试回答**：JDK 1.8 改为尾插法解决了死循环，但仍然线程不安全（put 可能覆盖）。多线程用 `ConcurrentHashMap`。

##### 6.2 ConcurrentHashMap

##### JDK 1.7 → 分段锁（Segment[]，默认 16 段，锁粒度段级别）

##### JDK 1.8 → CAS + synchronized 桶级锁

```
Node[] table
  ┌──┬──┬──┬──┬──┬──┬──┬──┐
  │  │  │  │  │  │  │  │  │  ← 桶
  └──┴──┴──┴──┴──┴──┴──┴──┘
           │
     ┌─────┴─────┐
     │ CAS 插入   │  ← 桶为空时，CAS 插入（无锁）
     │           │
     │ synchronized│  ← 桶非空时，锁桶头节点（细粒度）
     └───────────┘
```

**put 流程**：hash 定位桶 → 桶为空 CAS 插入 → 桶扩容中协助扩容 → 桶非空 synchronized 锁头节点 → 链表/树插入 → 检查扩容

**并发度**：从 1.7 的 16 段提升到 **桶级别**。

| 集合 | 底层 | 线程安全 | 特点 | Python 类比 |
|------|------|---------|------|-------------|

| LinkedList | 双向链表 | ❌ | 增删快 O(1)，查询慢 O(n) | collections.deque |
| HashMap | 数组+链表/红黑树 | ❌ | O(1) 查找 | dict |
| ConcurrentHashMap | 同 HashMap | ✅ | 桶级锁 | — |
| TreeMap | 红黑树 | ❌ | 有序 O(logN) | — |
| CopyOnWriteArrayList | 数组 | ✅ | 写时复制，读无锁 | — |

#### 七、Spring 框架

##### 7.1 IOC（控制反转）

```
传统方式：对象自己 new 依赖
  new Service() → new Dao() → new DataSource()

IOC 方式：容器创建并注入依赖
  容器创建 DataSource → 注入 Dao → 注入 Service
```

##### 传播行为（高频考点）

| 传播行为 | 说明 | 场景 |
|---------|------|------|
| **REQUIRED**（默认） | 有事务加入，无事务新建 | 大多数场景 |
| REQUIRES_NEW | 总是新建事务，挂起当前 | 日志记录（不受主事务影响） |
| NESTED | 嵌套事务（保存点） | 部分回滚 |
| SUPPORTS | 有事务加入，无事务非事务执行 | 查询方法 |
| NOT_SUPPORTED | 非事务执行，挂起当前 | 不需要事务的操作 |
| MANDATORY | 必须有事务，否则异常 | 强制要求事务 |
| NEVER | 必须无事务，否则异常 | 明确不能有事务 |

##### 事务失效场景（高频考点）

| 失效原因 | 说明 | 解决 |
|---------|------|------|
| **方法非 public** | Spring AOP 只代理 public 方法 | 改为 public |
| **自调用** | `this.method()` 不走代理 | 注入自己 `@Autowired self` 或 AopContext |
| **异常被 catch** | 事务管理器检测不到异常 | catch 后手动 `throw` 或 setRollbackOnly() |
| **异常类型错误** | 默认只回滚 RuntimeException | `@Transactional(rollbackFor = Exception.class)` |
| **数据库引擎不支持** | MyISAM 不支持事务 | 用 InnoDB |
| **传播行为错误** | NOT_SUPPORTED / NEVER | 检查传播行为配置 |

### 05-Saga 编排器：面试高频考点与话术（原 §9 · 9.1~9.5）

> 来源：`../../02-现货贸易/03-架构决策/05-Saga编排器详细介绍.md`（2026-10-23 归拢至此，原文留指针）

#### 9.1 "SAGA 和 2PC 的核心区别是什么？"

**话术模板**：

> "两者解决的是同一个问题——分布式事务一致性，但思路完全不同。
>
> 2PC 追求的是**强一致性**，通过两阶段提交让所有参与方同时提交或回滚。但它有三个致命缺陷：一是性能差，需要锁资源到第二阶段；二是可用性差，协调者挂了所有人阻塞；三是不适合异构系统，第三方服务根本不支持 XA 协议。
>
> SAGA 追求的是**最终一致性**，把长事务拆成一系列本地事务，失败了用补偿操作逆向撤销。它牺牲了即时一致性，换来了高吞吐、高可用，以及对异构系统的兼容性。
>
> 在我们 B2B 供应链场景里，一笔交易涉及银行、物流、开票等 9 个外部系统，2PC 根本不可行，SAGA 是唯一选择。"

#### 9.2 "Choreography 和 Orchestration 怎么选？"

**话术模板**：

> "核心看两个维度：流程复杂度和运维需求。
>
> Choreography 是事件驱动，服务自己监听事件做反应。简单场景下（比如下单→发短信→加积分 3 步以内）很好用，松耦合。
>
> 但流程一复杂就出问题——比如我们的交易履约有 7-15 个步骤，用 Choreography 的话，业务逻辑散落在 N 个服务里，新人根本看不懂全貌，出问题也难排查。
>
> Orchestration 把流程集中管理，有全局视图，补偿逻辑集中，监控和人工介入都很方便。唯一的代价是编排器成了关键路径，但做好无状态 + 持久化 + 分布式锁就能解决。
>
> **我们选 Orchestration，因为 B2B 流程复杂，业务可观测性比服务解耦更重要。**"

#### 9.3 "补偿失败了怎么办？"

**话术模板**：

> "这是 SAGA 落地的核心难点，我的处理方式是分级应对：
>
> 第一层：补偿操作本身配置指数退避重试（3-5 次），覆盖网络抖动和短暂不可用。
>
> 第二层：重试全部失败后，Saga 进入 PAUSED 状态，而不是直接标 FAILED。因为大部分补偿失败是暂时的——银行接口超时、物流系统维护——过几分钟可能就好了。
>
> 第三层：PAUSED 同时触发告警（钉钉 + 企业微信），通知对应的业务运营和值班开发。
>
> 第四层：运营后台提供 Saga 管理界面，可以看到每一步的状态、失败原因、重试次数，然后选择：手动重试 / 跳过该步（确认无害）/ 执行修复脚本。
>
> **这里的关键思想是：不要试图用代码覆盖所有异常，给人工留一个安全、可控的介入入口。**"

#### 9.4 "SAGA 怎么保证幂等？"

**话术模板**：

> "三层设计：
>
> 业务层：每个接口以业务唯一键（如 trade_id + step_id）为幂等键，数据库唯一索引兜底。
>
> 编排器层：每个 Step 的执行状态持久化到 Saga 实例表。编排器恢复时，检查已成功的步骤直接跳过，从失败的步骤继续。
>
> 基础设施层：如果用了消息队列（异步 SAGA），消费端做去重，利用消息 ID 或业务键。
>
> **核心原则是：'宁可重复执行被幂等拦截，也不遗漏任何一次必要执行'。**"

#### 9.5 "SAGA 最大的缺陷是什么？你怎么看？"

**话术模板**（展示批判性思维）：

> "SAGA 最大的理论缺陷是**缺乏隔离性**。ACID 的 I（Isolation）在 SAGA 里是不存在的——在 Saga A 执行到第 5 步时，Saga B 可能已经读到并修改了 Saga A 产生的中间数据。
>
> 这是一个真实的工程问题，不是纸上谈兵。比如：Saga A 创建了订单（第 1 步），Saga B 来取消这个订单（另一个 Saga），而此时 Saga A 的支付步骤（第 3 步）还没执行——就会出现支付了一个已取消的订单。
>
> 我们实际处理的策略是**业务层语义锁**：在订单状态上加 PROCESSING 中间态，配合乐观锁版本号。这不能从数学上证明隔离性，但在业务语义上够用。如果场景对隔离性要求极高（如金融清算），那就不应该用 SAGA，应该用 2PC 或 TCC。"

### 07-合同中心 vs 订单中心：面试/汇报话术（原 §五）

> 来源：`../../02-现货贸易/03-架构决策/07-B2B合同中心vsB2C订单中心-区别分析.md`（2026-10-23 归拢至此，原文留指针）

**面试被问"你们B2B的合同中心和普通电商订单系统有什么不同"：**

> "本质上，B2C订单是'一次性买单'，B2B合同是'持续性履约'。核心区别有三：第一，价格模型——我们支持固定价、浮动价、基差点价三种，合同签约时价格可能不确定，要等客户在期货盘面点价后才最终确定，结算时动态重算。第二，履约方式——一个合同可能分5批发货，每批独立质检、独立结算、独立开票，是合同→交货计划→发货单的三层模型。第三，风控——合同创建要通过授信检查、保证金冻结、敞口计算三道风控网关，这是B2C完全不存在的。如果拿一套B2C订单系统来改，光价格模型这个坑就填不平。"

### 11-midservice 网关：面试速答 90 秒版 + 追问预案（原 §12）

> 来源：`../../02-现货贸易/03-架构决策/11-midservice网关职责与治理设计.md`（2026-10-23 归拢至此，原文留指针）

#### 12.1 90 秒速答

> "我们的入口是**自研的 midservice 网关（多实例）+ midmon**。网关的核心设计原则是**拒绝要早、要便宜**——十道关按拦截成本排序，本地能判的绝不留到远程。
>
> 具体讲六件事。第一，**接口（我们内部叫协议）统一编码**：分段编址 `服务段-模块段-接口段@版本`，接口一生一个编码、编码可回收、破坏性变更才升版本；编码由网关的**契约注册表**统一发放，契约里定义入参、压力参数标记、权限、限流配额、脱敏字段——**一处定义、四处生效**（校验、文档、监控、限流脱敏配置都从契约读）。第二，**入参白名单**：只接收契约定义过的入参，未定义字段**拒绝**而不是忽略——这挡住了参数注入和越权赋值，也让后面的校验变成无副作用的本地操作。第三，**压力参数强制校验**：分页默认上限 100、时间跨度 31 天、批量 200、排序字段白名单；原则是**显式拒绝不做静默截断**——静默截断会让调用方以为拿到全量数据，是最难查的事故。100 是入口闸门，后端 SQL 还有一条 ≤200 的兜底红线，两层是纵深不是重复。第四，**限流与黑名单**：租户级/应用级/接口级三级配额，触发源不只是 QPS，还有高频错误、扫描特征、行为异常；处置阶梯是告警→限流→临时封禁 15 分钟（自动解封）→黑名单（人工解封），并且做了防误伤——白名单、灰度观察期、双信号校验。第五，**等保侧**：防重放（时间戳 5 分钟窗口 + nonce）、签名防篡改、越权防护（请求里的租户 ID 不可信，只信会话），文件上传做扩展名+ MIME + 魔数三重校验、服务端重命名、隔离存储、下载走一次性令牌。第六，**响应侧**：网关做兜底脱敏，业务层做基于角色的精确脱敏；更关键的是**输出白名单**——只输出契约声明过的字段，让泄露面不再随开发增长。
>
> midmon 解决的是**多实例下的可观测**：指标带实例标签、预警看全局聚合、按 traceId 去重。慢协议预警看 **P95 而不是平均值**，用"比例 + 持续性"双条件，告警必须落到**接口编码 + 实例 + 租户 + 下游服务**四元组，否则不可行动；调用量与耗时统计按接口/租户/应用/下游四个维度做 Top-N，用途是容量规划、限流阈值校准、接口下线决策和计量对账。
>
> 最后一条纪律：**网关只做与业务无关的、横切的、可配置的事**——库存、授信、状态机这些需要领域知识的判断，一律下沉到业务层。"

#### 12.2 追问预案

| 追问 | 回答要点 |
|------|---------|
| 为什么不用通用网关？ | 三类租户的分级路由与分级配额差异极大，通用网关要么太重、要么 L7 能力弱；不是"开源不够好"，是"我们的场景更匹配自研" |
| 多实例下限流怎么保证准确？ | 集中式令牌桶（准确、代价是 Redis 往返）vs 分片令牌桶（省调用、代价是重分片）；判据是"限流保护什么"——保护 DB 可容误差，**计量计费必须精确**故走独立通道 |
| 未定义入参为什么拒绝而不是忽略？ | 忽略埋雷（前端改字段无人知），透传是参数注入（`isAdmin`、`tenantId`）；拒绝是唯一安全选项 |
| 分页 100 是怎么定的？ | 入口闸门：与后端 SQL 红线（≤200，见 `生产问题排查/11` §5.2）形成纵深；100 面向全体调用方的统一红线，200 是白名单接口的审批提额上限 |
| 为什么不静默截断？ | 静默截断 = 数据静默丢失，调用方以为拿到全量；显式拒绝让问题在联调期暴露 |
| 慢接口预警为什么不用平均值？ | 平均值被长尾掩盖：9 个 10ms + 1 个 10s，均值 1s 看着还行，实际每 10 个用户 1 个在骂；必须看 P95/P99 |

| 网关会不会成为性能瓶颈？ | 正因为是瓶颈，才强调"拒绝要早"（把脏流量榨干在本地判断）+"网关不做重计算与业务规则"（第 10 节的边界清单） |
| 等保测评你们具体做了什么？ | 分区分域、双因子、最小权限、全链路审计留痕、传输存储加密、SDL（代码扫描 + 上线安全评审）；网关侧落点是防重放/签名/越权/上传/脱敏五项，见 7.1 |
| 文件上传怎么防图片马？ | 扩展名 + MIME + **魔数（文件头）**三重校验 + 服务端重命名 + 隔离存储 + 重新编码剥离 EXIF；只查扩展名一定被绕过 |

### 12-跨系统调用一致性：面试速答（原 §7）

> 来源：`../../02-现货贸易/03-架构决策/12-跨系统调用一致性方案.md`（2026-10-23 归拢至此，原文留指针）

**Q：为什么不用 2PC？**
A：本地事务跨不了库，2PC 要求下游支持 XA 且全程持锁，可用性和性能都赔不起；而"确认收货同时通知资金与仓单"这个场景里，两个动作可以独立完成，本就不需要强一致。

**Q：怎么保证一次业务两次调用都成功？**
A：不保证"都成功"，只保证"最终被确认"。做法是把"要通知谁"在本地事务里写成数据，异步线程去派发，阶梯重试到 N 次，超限熔断给运营。

**Q：超时了到底成功没有？**
A：不知道，也**不需要知道**——因为重试是幂等的。这正是本方案的地基：幂等键 + 下游去重，让"不确定"变成一个可以放心重试的问题。

**Q：资金成功、仓单失败了怎么办？**
A：只重试失败的那条记录，已成功的记录不动。这就是"一条下游一条记录"的设计价值——把部分成功从"灾难"降级为"两个独立进度"。

**Q：为什么重试要有上限，还要转人工？**
A：因为"发不出去"和"发出去但下游拒绝"是两类问题：前者等下游恢复就行，后者的根因（参数错、业务不允许）代码解决不了，必须有人介入。上限 + 告警就是**把不可自动收敛的问题及时交出去**。

**Q：这套方案怎么支持集群部署？**
A：关键在一个**派发批次号**。每次扫描先取一个全局唯一批次号，用**一条带批次号的 UPDATE** 把整批记录原子认领（改状态、打号、记认领时间在同一条 SQL 里完成），这一批就共享同一个号。此后回写、重试计数、僵死回收都只认自己的批次号，所以多个实例各管各的批次——**既不重复派发，也不互相覆盖**；实例宕机还能按批次号整批回收。**即使现在只跑一个实例，也按批次号来做**，将来加实例就是直接加，派发逻辑不用改。

**Q：界面端的重试按钮和异步重试是什么关系？**
A：异步重试是主路径，界面重试是兜底。界面重试只把记录重置成"待发送"重新入队，**不产生第二笔业务**；语义上跟运营线下处理后手动触发完全一致。

### 13-C 核心单线程内存一致性：面试速答（原 §10）

> 来源：`../../02-现货贸易/03-架构决策/13-C核心单线程内存一致性设计.md`（2026-10-23 归拢至此，原文留指针）

**Q：单线程撮合怎么保证数据一致性？**
A：单线程保证的是**内存内**——串行、无锁、可复现（输入序列定则输出定）。但**内存外**要用三段兜：镜像文件（write-ahead，防丢）、异步回写 + 阶梯重试（追 DB）、死信队列 + 运营重试（收敛卡死）。口径是**内存为准**，DB 是最终一致的副本。

**Q：为什么不用同步落库？**
A：同步落库等于**把撮合速度绑死在 DB 写入能力上**，一次 DB 抖动就变成撮合停顿。异步换来的吞吐和确定时延，代价就是"内存有、库无"的时滞——用「内存为准 + 异步回放 + 幂等补偿 + 定时对账」兜住。

**Q：先落地镜像文件，落的是什么？**
A：本质是 **write-ahead**——"记下来"必须早于"改内存"。落地上分三种：命令日志（记输入，用于重放重建内存）、定期快照（记状态，加速恢复）、回写待办（记还欠 DB 什么）。常用组合是**命令日志 + 定期快照**。

**Q：如果先改内存、后写文件会怎样？**
A：在那个窗口里崩溃 → **这笔成交彻底蒸发**：不在内存（已丢）、不在日志（没写）、不在 DB（没回写）。所以"先落地"这条次序不变量不能破。

**Q：回写失败 N 次了怎么办？**
A：不能闷头重试——**重试解决不了"发不出去"这类根因**（DB 挂了、数据脏）。所以熔断进死信队列、发运营短信，把问题**从机器交给能判断的人**。短信必须带单号 + 原因 + 次数，否则运营也不知道做什么。

**Q：运营点"重试"是不是重新撮合一遍？**
A：**绝对不是**。运营重试**只重放"回写 DB"这一步**，按业务单号幂等 upsert。重新撮合会算出第二笔业务、资金重复变动。**撮合只发生一次，回写可以重放无数次。**

**Q：内存和 DB 不一致了怎么发现？**
A：**定时对账**——定期比对内存态、DB 态、下游态，差异报警。它是"兜底的兜底"：前面所有机制都是"尽量不出错"，对账保证"出错了也一定被发现"。

**Q：仲裁者自己挂了怎么办？**
A：**整体停摆——这是正确行为**。仲裁失联时，系统无法区分"主真的挂了 / 主只是卡顿 / 网络分区"，而这三种情况要的动作**恰好相反**，所以只能拒绝服务（宁可停，不可双主）。正解**不是让它永不挂**，而是**把仲裁者做成多数派**（3 节点容 1 挂、5 节点容 2 挂；每个节点极轻，只维护任期号 + 租约），或直接**复用已有的 HA 组件**（etcd / DB 租约表）。两个硬细节：**任期号必须持久化**（否则重启后会投出矛盾票，一个任期两个主）、**下游必须校验栅栏令牌**（否则卡死的"僵尸主"仍可能写）——"主会自觉停服"是假设，"下游拒绝旧令牌"才是事实。

**Q：C 核心怎么做热备？**
A：核心是**不复制结果、只复制输入**——备机收主的命令日志、自己重放，因为撮合确定，重放必得同一个内存。再加**仲裁者**防脑裂（“是不是主”不能由主备自己投票），切换时从“已完整落盘的 LSN”续位点、回写靠**幂等**吸收重复。RPO 由“**对外应答前是否已同步到备**”决定，不由“改内存前是否已同步”决定。

**Q：C 核心这套一致性设计，和 ZooKeeper + Kafka 是什么关系？**
A：**同一个形态的两个平面**——ZK / 仲裁者管“谁来当主”（协调平面），Kafka / C 核心主备管“数据怎么复制”（数据平面）。不是“看着像”，是同一招：**栅栏令牌 = Kafka 的 leader epoch**（都用来拒绝脑裂旧主的写入）、**“对外应答前同步到备” = ISR + `acks=all`**、**幂等 upsert = 幂等生产者**。更有价值的是演化：Kafka 用 **KRaft** 把 ZK 干掉了，但**协调角色没消失、只是不再用另一套系统跑**——即“**角色分离 ≠ 进程分离**”。对 C 核心的推论是**倾向外部协调**（撮合线程不能阻塞，别把共识塞进去），但“外部”可复用已有 etcd / DB 租约表，不必自造 ZK。

### 15-DS 数据交换中心：面试速答（原 §11）

> 来源：`../../02-现货贸易/03-架构决策/15-DS数据交换中心-C-Java异构桥接设计.md`（2026-10-23 归拢至此，原文留指针）

**Q：DS 数据交换中心是干什么的？**
A：C 撮合与 Java 中台之间的**防腐层**。C 只会说 Socket 二进制帧，Java 只说 Hessian / HTTP——DS 把两边互译成统一报文，让 C 团队和 Java 团队各自独立演进，互不阻塞。"不把 Java 写进 C 引擎，也不把 C 逻辑外泄到 Java 层"。

**Q：为什么同步走 Hessian over HTTP、异步走 Socket？**
A：跟着语义走。请求-响应要结果，HTTP 的状态码 / 超时 / 重试都现成；高频回执和行情要吞吐，Socket 长连接省掉反复建连和 HTTP 头开销，而且 C 侧本来就只会 Socket。**不是追潮流，是各取所长。**

**Q：这个系统怎么支持高并发？**
A：四件事。**IO 模型**——epoll / Netty Reactor，一连接一线程是自杀；**背压**——有界队列 + 高水位三级处置，宁可明确拒收不堆到 OOM；**并行**——按业务单号分片，同键保序、异键并行；**批量**——小包合并、批量落库。再加上对 C 单线程的适配：DS→C 只写无锁队列，绝不让撮合线程等我们。

**Q：大概能扛多少并发？**
A：分三层说。**连接数** 10 万级，但内部交换实际只有几十~几百条，免测；**接入吞吐** 10 万级 QPS（小报文）；**端到端 1~3 万 TPS，瓶颈在下游 DB 不在 DS**。生产 3 节点基线，真实峰值远未触及上限。**扩容前先算账**——日均 × 开盘集中度 = 峰值，再按 min(CPU, 网卡, DB) 定单节点能力、留 2 倍余量。接入层扩容治不好 DB 打穿，这个坑库里有案。

**Q：怎么保证消息不丢不重？**
A：复用 12 号的范式——消息先落**本地待发送表**（与发送同一事务）→ 取全局唯一批次号、一条 SQL 原子认领整批 → 阶梯重试 1s→2s→4s 上限 N → 熔断转人工 → 死信队列 + 运营界面重试。去重靠三层：帧序号保通道内、requestId 保窗口内、业务幂等键保永久。

**Q：C 是单线程撮合，DS 会不会把它堵死？**
A：不会，这是设计前提不是运气。DS→C 的所有动作都收敛成"往无锁 SPSC 队列放消息"，C 按自己节奏消费；C→DS 用独立 IO 线程读。DS 绝不做任何可能阻塞撮合线程的事。

**Q：流量突增把队列打爆怎么办？**
A：有界队列 + 高水位三级：60% 告警、80% 明确拒绝或转落盘。**宁可明确拒收让上游重试，也不能无界堆内存**——丢一条是事故，OOM 是全站停摆。这和网关"显式拒绝不做静默截断"是同一条纪律。

**Q：为什么用 Hessian 不用 JSON？**
A：撮合是高频二进制交互，序列化开销直接进时延预算。Hessian 二进制体积小、编解码快；JSON 留给配置和需要人看的场合。Protobuf 更快但存量迁移成本 > 收益，不推倒重来。
